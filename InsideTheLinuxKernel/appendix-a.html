The chapters of this book describe a Linux kernel in full operation. This appendix steps outside that assumption to ask a more primitive question: how does the kernel come to be running in the first place? System startup—the sequence that carries a machine from the instant power is applied to the moment a user can log in—is the one part of the system that must work before any of the subsystems the other chapters cover are available. The appendix follows that sequence in the order the machine executes it: the firmware that runs at reset, and the part of it that stays behind; the boot loaders and boot protocols that hand over the kernel image, or the EFI stub that lets firmware run the kernel directly; the decompression and address randomization that place the kernel in memory; the architecture-specific entry code, mostly assembly, that brings each architecture to the portable start_kernel; the initialization that function drives, including how the kernel learns what hardware it is running on; and the creation of processes 0, 1, and 2, which ends with the user-space init. It closes with the paths that sit beside the normal boot: the early console, which makes the first moments observable; kexec and kdump, by which one kernel boots another; the hand-over mechanisms that let chosen memory survive that jump; and the resume from hibernation, a complete boot that ends by discarding itself. The book's two reference architectures, x86_64 and ARM64, are traced side by side until they meet at start_kernel. Rather than the 32-bit BIOS PC boot path of Linux 2.6, the account here reflects the UEFI firmware, the relocatable and randomized kernel, and the dual-architecture reality of Linux 7.0.12, including recent changes such as the x86 EFI stub decompressing the kernel itself and, new in 7.0, an initramfs that can be left behind with an ordinary pivot_root.

From Power-On to User Space

Every other chapter of this book takes for granted that the kernel is already running: that there is a scheduler to dispatch processes, a memory manager to hand out pages, a virtual filesystem to open files. This appendix asks how that state comes to exist in the first place. When power is applied to a computer, the RAM holds random noise, no page tables map anything, the CPU is in its most primitive addressing mode, and there is no operating system in sight. The journey from that inert state to a login prompt is called bootstrapping—after the paradoxical image of a person lifting themselves by pulling on their own boots—and it is, of necessity, the most architecture-specific code in the entire system. Every stage of it must also make do without the facilities the rest of the book relies on: there is no allocator to ask for memory, no scheduler to run anything else, and, at first, no console on which to report a failure. Each stage builds by hand just enough of that world for the stage after it.

On a 32-bit BIOS PC, Linux 2.6.11 booted through a sequence of historical "ages": the BIOS, the boot loader (LILO), the real-mode setup() function, the startup_32() assembly routines, and finally start_kernel(). Almost every rung of that ladder has been rebuilt since. The BIOS has given way to UEFI; LILO is gone, replaced by GRUB 2, systemd-boot, and—most strikingly—by the kernel's own ability to boot itself as a UEFI application through the EFI stub; the kernel image is now relocated to a randomized address by KASLR; and ARM64, which Linux 2.6.11 did not support at all, dispenses with real mode, BIOS, and boot sectors entirely, entering a 64-bit kernel straight from firmware or a loader with a device tree in a register. This appendix still follows one continuous thread from the first instruction to user space, but for the hardware and kernel of today.

Why spend an appendix on this at all, when the rest of the book assumes a running kernel? Because the boot path is where several of the book's themes become concrete and where a great deal of real-world debugging happens. A system that will not boot, or that boots to a black screen, or that panics before the console comes up, can only be understood by someone who knows the sequence of stages and what each one requires of the last. The boot path is also where the kernel's security posture is established—Secure Boot, the measured trust chain, and KASLR all live here—and where the split between architecture-specific and portable code is starkest. It is, finally, where boot time is spent—a figure that matters for phones, cars, and virtual machines started on demand—and the kernel makes it measurable: every log message carries a timestamp from the first moments of start_kernel, and the initcall_debug parameter reports how long each initialization function took. Reading this appendix, then, is partly about satisfying curiosity over how the machine wakes up, and partly about acquiring a mental model precise enough to reason about failures that occur before any of the machinery the other chapters describe is available.

The Bootstrap Problem

The difficulty of booting is fundamentally a chicken-and-egg problem: the code that knows how to load and initialize the operating system is itself part of the operating system, which is not yet loaded. The hardware breaks the cycle by guaranteeing one fixed starting point. When the CPU is released from reset it begins executing from a hardwired address in non-volatile memory—on x86, 16 bytes below the 4 GiB boundary; on ARM64, an address fixed by the system-on-chip design (§2)—where the platform firmware lives. That firmware is deliberately minimal—it knows just enough to test memory, enumerate a few devices, and find and run the next stage. Each stage in turn knows how to set up the environment for and load the stage after it, and so the system pulls itself up in a series of steps, each more capable than the last, until a full kernel is running with virtual memory, interrupts, and a scheduler.

It is worth asking why the process is broken into so many stages rather than having firmware simply load the whole kernel in one shot. The answer is that each stage exists to lift a specific constraint that the stage before it could not. The earliest stage is tiny because it must fit somewhere fixed and trusted—the legacy boot sector was a mere 512 bytes, too small to understand a filesystem, so its only job was to load a larger loader. That larger loader can read files and present menus but runs in a restricted firmware environment, so it in turn loads the kernel and steps aside. The kernel arrives compressed to save space and boot I/O, so a decompressor must unpack it. And the unpacked kernel starts in a constrained CPU mode, so assembly code must build page tables and switch modes before portable C can run. Each stage, in other words, is the minimal thing that can create the environment the next stage assumes—the boot sequence is a ladder precisely because no single rung can span the whole gap from firmware to a running kernel.

This staged structure also underpins the platform's security model, which is a significant addition since Linux 2.6. Because each stage loads the next, it is in a position to verify the next before running it, and modern systems exploit this to build a chain of trust. Under Secure Boot the firmware refuses to run a boot loader whose cryptographic signature it does not trust, the loader refuses to run an unsigned kernel, and on measured-boot systems each stage records a hash of the next into the platform's trusted platform module (TPM) before handing over. Linux takes part in both halves. The EFI stub measures the initrd and the command line it was given into TPM register PCR 9—or, in a confidential-computing guest, through the firmware's equivalent confidential-computing measurement protocol—and passes the firmware's measurement log on to the kernel (drivers/firmware/efi/libstub/tpm.c), so the record covers exactly what the kernel was started with. The kernel in turn notes whether Secure Boot was on and, where the IMA architecture policy is configured (security/integrity/ima/ima_efi.c), insists on valid signatures for the modules and kexec images it later loads, extending the chain past the boot itself (§8.2). A boot sequence is thus not only a relay of capability but potentially a relay of trust, in which every link vouches for the one after it—an idea with no counterpart in the legacy BIOS world of Linux 2.6, where any code in the boot sector simply ran.

Two properties make this process awkward to describe in one narrative. First, it is stateful in hardware: at each step the processor may be in a different mode (real, protected, and then long mode on a BIOS-booted x86, although UEFI firmware already runs in long mode; EL2, then EL1, and possibly EL2 again on ARM64), with different addressing rules, and code compiled for one stage cannot simply call into another. Second, it is deeply architecture-specific—so much so that the early boot code shares almost nothing between x86_64 and ARM64. What the two share is the destination. Both funnel, after all their machine-specific preparation, into start_kernel in init/main.c, the first function that looks the same on every architecture Linux supports. C code runs well before it—the EFI stub, x86's __startup_64, and ARM64's early_map_kernel are all C—but that is C written under stage-specific rules, built to run before the kernel sits at its final address and private to one architecture; start_kernel is where the ordinary, portable kernel begins. The rest of this appendix is organized around that funnel: the machine-specific climb up to start_kernel, and then the common path from there to user space.

The Modern Boot Chain

Before diving into any one stage it helps to see the whole chain at once, because the individual pieces make more sense once their place in the sequence is clear. On a modern system the path from power-on to user space passes through five broad phases. First the firmware (UEFI, or a legacy BIOS, or a boot monitor such as U-Boot) initializes the platform and locates something to boot. Second a boot loader—or the kernel's own EFI stub acting in its place—loads the kernel image and an optional initial ramdisk into memory and hands over according to a defined boot protocol. Third the kernel is unpacked and placed. On a legacy x86 boot the decompressor wrapped around the kernel does this; on an x86 EFI boot the stub does it; an ARM64 kernel usually arrives uncompressed, or is unpacked by its loader or by the EFI zboot wrapper. Whichever code does the work also chooses a randomized physical address. Fourth the architecture entry code, mostly assembly with a growing share of tightly constrained C, builds the first page tables, switches the CPU into its final operating mode, and sets up a C runtime. Only then, fifth, does the portable kernel run: start_kernel initializes every subsystem and spawns the first processes, the last of which executes the user-space init program. Figure A-1 lays out this pipeline, noting which parts are architecture-specific and where the two architectures rejoin.

One element the five-phase sketch glosses over deserves naming here because it recurs throughout the appendix: the initial ramdisk, or initramfs. The kernel that firmware loads is often unable to mount the real root filesystem directly—the drivers for the disk controller, the logical-volume or RAID layer, or the network may themselves be modules that live on that root filesystem, a second chicken-and-egg problem. The boot loader solves it by loading, alongside the kernel, a small compressed archive of a temporary root filesystem into memory. The kernel unpacks this into a RAM-based filesystem and runs an init program from it; that early user space contains just enough tools and modules to find and mount the true root, after which it hands off to the real init. The initrd is thus a miniature user space interposed between the kernel and the final one, and it is why the "user space" at the end of the chain may in fact be reached in two steps rather than one; §1.3 follows how the kernel unpacks it and how the hand-over to the real root works.

The other idea the pipeline makes visible is that each stage is transient: having built the environment for its successor, a stage is meant to disappear. The firmware's boot services are explicitly torn down at ExitBootServices and can never be called again, and the memory they used becomes ordinary RAM; the decompressor and the EFI stub are simply left behind once the kernel they prepared is running; and, as §7.3 will show, the kernel even reclaims its own one-time initialization code once boot is complete. The one deliberate exception is the set of UEFI runtime services of §2.2, which stay callable for the life of the system; the kernel maps them into a dedicated address space, efi_mm, that is switched in only for the duration of a firmware call (§2.4). This relay quality—each runner handing the baton forward and leaving the track—is what lets a fully general, multi-gigabyte operating system emerge from a few bytes of firmware without any single component having to be all things at once. It also explains a practical fact of boot debugging: once a later stage is running, the earlier ones are simply gone, so a problem must be diagnosed from the vantage point of whichever stage is still alive.

What Travels Down the Chain

Each hand-off in the chain passes on more than control. What travels from stage to stage is a small bundle of data the kernel needs before it can discover anything for itself: a description of physical memory, a pointer to the hardware description (ACPI tables or a device tree), the location of the initial ramdisk, the command line, and, increasingly, security material such as a seed for the random-number generator and the log of what was measured. The packaging is architecture-specific—x86 collects the bundle in the boot_params structure and a chain of setup_data records, ARM64 hands over a single device-tree pointer in x0, and the EFI stub can gather all of it from firmware itself (§3)—but the contents are nearly the same everywhere. The random seed shows how carefully some of it is handled: the kernel mixes it into the entropy pool with add_bootloader_randomness and then erases it, zeroing the x86 SETUP_RNG_SEED record and the UEFI seed table and deleting the rng-seed property from the device tree, so that nothing later—a kexec'd kernel, or a reader of /proc/device-tree—can recover it.

The command line deserves a closer look, because it is the one channel through which a person can reach into the kernel before it is running. It is a single string of at most 2,048 bytes on both architectures (COMMAND_LINE_SIZE), assembled by the loader or taken from the EFI load options, and optionally combined with a string built into the kernel (CONFIG_CMDLINE). The EFI stub and the x86 decompressor scan it for the few options they need, such as nokaslr, but the kernel proper reads it twice. Early in setup_arch, parse_early_param handles only the parameters declared with early_param—options such as mem= or earlycon that must take effect before memory management or the console exists. Later, start_kernel (init/main.c) passes the whole string through parse_args (kernel/params.c), handing each word to the handler registered for it with __setup or to a built-in module's parameter. What no handler claims is not discarded: an unrecognized name=value becomes an environment variable of the init process and a bare word becomes one of its arguments—except dotted module.param settings for modules not yet loaded, which are left for modprobe to find in /proc/cmdline—while everything after a lone -- is passed to init as arguments without being examined at all. The kernel prints the string it booted with as "Kernel command line:" and lists the unknown parameters it is passing to user space, so a misspelled option shows up in the log instead of vanishing.

For settings too long or too numerous for one line, Linux 5.6 added a structured supplement, bootconfig. A bootconfig file is a tree of key.subkey = value entries, appended to the end of the initrd behind a size, a checksum, and the magic string #BOOTCONFIG (the bootconfig tool in tools/bootconfig/ does the appending), or embedded in the kernel image with CONFIG_BOOT_CONFIG_EMBED. When bootconfig appears on the command line, or CONFIG_BOOT_CONFIG_FORCE is set, setup_boot_config parses it: keys under kernel. are added to the kernel's command line, keys under init. to the init program's, and other subtrees are left for in-kernel users such as the boot-time tracer, which reads its event and probe definitions from the ftrace. subtree.

The initramfs of §1.2 is a cpio archive in the "newc" format, usually compressed, and the kernel unpacks it in populate_rootfs (init/initramfs.c) into the first filesystem it mounts, rootfs: a tmpfs when no root= is given and tmpfs is configured, a plain ramfs otherwise. Every kernel carries an archive of its own linked into the image, built from CONFIG_INITRAMFS_SOURCE or, by default, holding nothing but a /dev/console node and an empty /root; an archive supplied by the loader is unpacked on top of it, so files from both appear. Early user space—usually an image generated by dracut or initramfs-tools, running systemd or a shell script—loads the storage drivers, assembles RAID arrays or unlocks an encrypted disk, mounts the real root, and then makes that the root of the process tree.

That last step changed in Linux 7.0. Until then rootfs was the absolute root of the mount tree and could never be unmounted, so pivot_root refused to move it, and early user space had to delete the initramfs contents file by file, move the real root over /, and chroot into it—the routine performed by the switch_root utility. Now init_mount_tree (fs/namespace.c) first mounts nullfs (fs/nullfs.c), an empty, immutable filesystem, as mount 1, and rootfs on top of it as mount 2. Because rootfs now has a parent, an ordinary pivot_root can swap in the real root and then detach the initramfs whole, or keep it mounted elsewhere; systemd, which already tried pivot_root before falling back to the old routine, takes the new path without change.

The older mechanism that gave the initrd its name is on its way out. A classic initrd is a filesystem image rather than an archive: when the data the loader supplied is not a cpio archive, the kernel saves it as /initrd.image and later copies it into the RAM disk /dev/ram0 (init/do_mounts_initrd.c). Its linuxrc mode, in which a program on that RAM disk ran before the real root was mounted, was deprecated in 2020 and removed in Linux 7.0. What remains, using /dev/ram0 itself as the final root, now prints a warning that it will be removed in January 2027, and the noinitrd parameter is deprecated with it.

Firmware: BIOS, UEFI, and ARM64

The first code a processor runs after reset is not part of Linux at all; it is firmware baked into the platform. Understanding what that firmware does—and how it has changed since Linux 2.6—matters because it defines the environment the kernel is handed: what mode the CPU is in, what memory is usable, how the hardware is described, and what services, if any, remain callable once the kernel takes over. This section looks at the three firmware worlds the book's two architectures inhabit: the legacy PC BIOS (§2.1), the UEFI firmware that has replaced it on both x86_64 and ARM64 (§2.2), and the exception-level model that makes ARM64's hand-off fundamentally unlike a PC's (§2.3). It closes with something a 2.6-era kernel could largely ignore but a modern kernel cannot: the firmware that stays behind after the hand-off, still callable and sometimes still running beneath the kernel (§2.4).

The Legacy BIOS

On the PC of the Linux 2.6 era, the firmware was the BIOS (Basic Input/Output System), a set of 16-bit routines stored in ROM. When the CPU leaves reset it starts in real mode—the primitive 8086-compatible mode in which a physical address is computed as segment × 16 + offset, with no paging and no protection—and begins executing near the top of the address space, at physical address 0xFFFFFFF0, which the chipset maps to the firmware ROM. Real mode can otherwise reach only the first megabyte; the processor makes this one exception by starting with a hidden code-segment base of 0xFFFF0000, so that the first instruction lies 16 bytes below 4 GiB. On today's PCs even that is not the true beginning: a separate security processor—Intel's Converged Security and Management Engine or AMD's Platform Security Processor—runs its own firmware first and, where Intel Boot Guard or AMD Platform Secure Boot is enabled, ensures that the firmware the main cores are about to execute is verified against a key fused into the chip, making the silicon itself the root of the chain of trust of §1.1. The BIOS ran a Power-On Self-Test (POST), initialized devices, and then searched a configured list of disks for a bootable one. On finding a disk whose first 512-byte sector—the Master Boot Record (MBR), which holds both the first-stage boot code and a four-entry partition table—ended in the signature bytes 0x55AA, it copied that sector to physical address 0x7C00 and jumped to it. That tiny program was the first stage of the boot loader. This scheme, essentially unchanged since the original IBM PC, is what "booting from the boot sector" meant.

What made the BIOS more than a boot-sector launcher was the set of service routines it left resident in memory, callable through software interrupts. An operating system in its earliest moments could ask the BIOS to read disk sectors (INT 13h), print characters or set video modes (INT 10h), or report the memory map (INT 15h, function E820h—the origin of the "e820" map Linux still speaks of). Peripheral cards contributed their own option ROMs, code the BIOS ran during POST so that, for instance, a disk controller could hook INT 13h and make itself bootable. The catch was that all of this lived in 16-bit real mode: once Linux switched the CPU into protected mode these routines became unusable. The kernel's real-mode setup code therefore makes one last round of BIOS calls—the e820 memory map, disk geometry through the Enhanced Disk Drive services (arch/x86/boot/edd.c), the video mode—records the answers in boot_params (§5.1), and never calls the BIOS again; every device is then driven by the kernel's own drivers. When UEFI first arrived, firmware vendors bridged the gap with a Compatibility Support Module (CSM) that emulated the legacy BIOS interface for older operating systems. Intel announced in 2017 that its platforms would drop the CSM by 2020, and on most new machines UEFI is now the only option.

Linux still contains code to be booted this way—the real-mode setup code in arch/x86/boot/ survives, and it is discussed in §5.1—but on contemporary hardware the legacy BIOS is a compatibility mode at best and absent at worst; its most common surviving home is the virtual machine, where SeaBIOS is still QEMU's default x86 firmware. Its limitations are exactly the ones that motivated its replacement: a 16-bit execution environment, a 1 MiB real-mode memory ceiling, a 512-byte first-stage boot program too small to understand a filesystem, a partition table limited to four primary entries and, with 512-byte sectors, 2 TiB of disk, no standard way to describe complex modern hardware, and no cryptographic verification of what it loads. UEFI Firmware

The Unified Extensible Firmware Interface (UEFI) is the modern replacement for the BIOS on both x86_64 and ARM64 systems, and it changes the boot environment profoundly. Where the BIOS ran 16-bit code and offered only real-mode interrupt calls, UEFI runs the CPU in a flat 32- or 64-bit mode in which memory is identity-mapped—virtual addresses equal physical ones, with paging (or, on ARM64, the MMU) already enabled on 64-bit platforms—and exposes a rich C-callable interface. It divides its services into two groups. Boot services are available only while firmware is still in charge—before the OS takes the machine—and include memory allocation, the protocol for reading files, device handles, and a graphics output protocol. Runtime services remain callable after the OS has booted and cover a small set of persistent functions: reading and writing firmware variables, the real-time clock, system reset, and the delivery of firmware-update capsules, plus SetVirtualAddressMap, through which the OS tells firmware where it will map the runtime code (§2.4). The transition between the two worlds is a single, sharp event: the OS loader fetches the final memory map and passes its key to ExitBootServices; if any allocation has changed the map in between, the call fails and must be repeated with a fresh map, which is exactly the dance efi_exit_boot_services (drivers/firmware/efi/libstub/efi-stub-helper.c) performs. Once it succeeds, the boot services vanish and the kernel owns the machine. UEFI itself is a specification, maintained by the UEFI Forum, rather than a single code base; most PC and server firmware derives from the open-source EDK II reference implementation, whose virtual-machine builds—OVMF for x86_64 and its ARM64 counterpart—are what QEMU boots when asked for UEFI.

UEFI also standardizes how an operating system is found and described. Bootable programs live as ordinary files on a FAT-formatted EFI System Partition (ESP), and a firmware boot manager, configured through non-volatile Boot#### variables, chooses which .efi application to run—no scanning for magic boot-sector bytes. The firmware hands the OS pointers to a set of configuration tables, most importantly the ACPI tables that describe the platform's devices, power model, and interrupt routing, and the SMBIOS tables that describe the board. And because the loaded program is a signed PE/COFF executable, UEFI can enforce Secure Boot, refusing to run any loader or kernel whose signature is not trusted. These facilities are the foundation on which the kernel's EFI stub (§3.4) is built: because the kernel can be packaged as a valid UEFI application and can call boot services itself, it can be loaded and entered by firmware directly, with the memory map, ACPI tables, and initrd all obtained through this interface rather than through a separate boot loader.

The most consequential thing firmware hands over is its memory map, returned by the GetMemoryMap boot service as a list of descriptors, each giving a physical range, a type, and attribute bits. The types tell the kernel what it may use. Conventional memory is free; boot-services code and data become free once boot services have been exited (§1.2); runtime-services regions must be preserved and mapped for later firmware calls; ACPI memory holds the tables, and ACPI NVS memory is firmware's own storage that must survive sleep states. Newer types describe persistent memory and, for confidential-computing guests on Intel TDX or AMD SEV-SNP, unaccepted memory, which a guest must formally accept from the hypervisor before touching it. Since Linux 6.5 the kernel accepts it lazily, as the page allocator first needs each range (drivers/firmware/efi/unaccepted_memory.c), so a large guest does not stall at boot accepting memory it may never use. An attribute bit, EFI_MEMORY_SP, marks "specific-purpose" memory such as on-package high-bandwidth memory, which the kernel sets aside for a device driver to claim rather than for general allocation, unless booted with efi=nosoftreserve. How the map reaches the kernel differs by architecture: the x86 EFI stub converts it into the e820 format the rest of the x86 code already understands (setup_e820, drivers/firmware/efi/libstub/x86-stub.c) and also leaves the raw map in boot_params, while the ARM64 stub records its location in the device tree (§2.3).

It is worth being concrete about how the firmware boot manager actually chooses what to run, since it replaces the boot-sector scan entirely. The firmware keeps an ordered list in the BootOrder variable, each entry pointing at a Boot#### variable that names a device and the path to an .efi application on it; the manager tries them in turn until one succeeds. Removable media that has no such variable is handled by a fallback path—a well-known file such as \EFI\BOOT\BOOTX64.EFI on x86_64 or \EFI\BOOT\BOOTAA64.EFI on ARM64—which is how a freshly written USB stick boots on any machine. The applications themselves reach firmware functionality through protocols, interface tables identified by GUIDs and looked up at run time, so the same mechanism that exposes disk I/O and graphics also exposes the random-number and loaded-image protocols the kernel's EFI stub relies on. Secure Boot, in turn, rests on a small hierarchy of key databases—the platform key, the key-exchange keys, and the allowed and forbidden signature databases (db and dbx)— against which every executable is checked; Linux distributions typically insert a small signed shim loader into this chain so their kernels can be trusted without every vendor's key being enrolled in firmware.

Shim, signed by Microsoft's third-party UEFI certificate authority, which nearly all PC firmware trusts, carries the distribution's own certificate and adds a list the machine's owner controls, the Machine Owner Key (MOK) list, so that a locally built kernel or module can be trusted without touching firmware. Because revoking every vulnerable loader by hash would overflow dbx, shim and the binaries it loads also carry an SBAT section of generation numbers, which lets a whole vulnerable release be revoked by raising a single counter; since Linux 6.16 the kernel can embed one in its own EFI image (CONFIG_EFI_SBAT_FILE). The kernel reads the same databases as it boots, so that the trust decisions carry past the hand-off: certificates from db and the MOK list go into the platform or machine keyring, where they can verify a kexec_file_load image (§8.2), and the hashes in dbx and its MOK counterpart go into the blacklist keyring (security/integrity/platform_certs/load_uefi.c).

Firmware and Exception Levels on ARM64

ARM64 has no BIOS heritage at all, and its firmware story is best understood through the architecture's exception levels. An AArch64 processor runs at one of four privilege levels: EL0 for user space, EL1 for the kernel, EL2 for a hypervisor, and (optionally) EL3 for the secure firmware monitor. At reset the highest implemented level runs first, and a chain of firmware components—typically Trusted Firmware-A at EL3, then a platform loader, then either an EDK II-based UEFI or U-Boot—initializes the hardware and drops the processor down to a level suitable for the kernel. Linux expects to be entered in a well-defined state described precisely by the ARM64 boot protocol (Documentation/arch/arm64/booting.rst): the MMU off, caches in a defined state, and the CPU in non-secure EL2 if possible—so that the kernel can install the KVM hypervisor—or else in EL1. Those rules bind an external loader; the kernel's own EFI stub, being part of the kernel, may jump in with the firmware's MMU and caches still on, a case primary_entry detects (record_mmu_state, arch/arm64/kernel/head.S) and handles by skipping cache maintenance an MMU-off entry would need. Either way there is no real mode, no 1 MiB barrier, no boot sector: firmware hands off directly to a 64-bit kernel, which later reports the level it received in a boot message such as "CPU: All CPU(s) started at EL2", and taints itself if the CPUs disagree.

Because ARM64 hardware is far more varied than the PC and carries no legacy enumeration mechanism, firmware must also tell the kernel what hardware exists. It does this in one of two ways. Embedded and mobile systems pass a device tree—a compact binary description of the board's components—whose physical address firmware places in register x0 at kernel entry. Servers instead use the same ACPI tables as x86_64, presented through UEFI. Either way the kernel is handed a structured description rather than left to probe blindly, a subject we return to in §6.3. The result is that on ARM64, UEFI (or U-Boot) plus a device tree or ACPI plays the combined role that BIOS, the boot sector, and hardware probing played on the 2.6-era PC—but in a clean 64-bit environment from the very first instruction.

The two descriptions meet in the EFI stub. When the kernel boots through it, x0 always holds a device tree: the stub adds to the firmware's tree a /chosen node carrying the command line, the initrd location, a KASLR seed, and the addresses of the UEFI system table and memory map (linux,uefi-system-table, linux,uefi-mmap-start, and their companions, drivers/firmware/efi/libstub/fdt.c), and on an ACPI-only machine it creates an otherwise empty tree just to carry those properties. The kernel then chooses: ACPI is used if the device tree is such a stub with nothing but /chosen (dt_is_stub, arch/arm64/kernel/acpi.c) or if acpi=on or acpi=force is given, and the device tree is used otherwise. Arm's platform standards pin these choices down: the Server Base Boot Requirements (SBBR) mandate UEFI with ACPI for servers, while the Embedded Base Boot Requirements (EBBR) define the subset of UEFI—implemented by U-Boot itself—that lets an embedded board boot a distribution's generic kernel with a device tree; the Arm SystemReady program certifies hardware against both.

The chain of firmware components on ARM64 is worth making explicit, because it has no PC analogue. On a typical server or phone the reset vector lands in Trusted Firmware-A (TF-A, formerly ARM Trusted Firmware), whose stages—a small boot ROM (BL1), a trusted loader (BL2), and a resident EL3 secure monitor (BL31)—initialize the most sensitive hardware and set up the secure world, optionally start a trusted OS such as OP-TEE there (BL32), and finally hand off to the normal-world firmware (BL33: UEFI or U-Boot) that loads the kernel. The EL3 monitor does not disappear the way the BIOS did: it stays resident to service PSCI (Power State Coordination Interface) calls, the standard interface through which the kernel asks firmware to power CPUs on and off and to enter idle states. This is why bringing up a secondary processor on ARM64 (§5.3) is a firmware call rather than the intricate interrupt-handshake it is on x86: the kernel issues a PSCI CPU_ON through the monitor, which the kernel wires up in setup_arch via psci_dt_init or psci_acpi_init (arch/arm64/kernel/setup.c). The same interface powers the whole system off or resets it (SYSTEM_OFF, SYSTEM_RESET) and lets the cpuidle driver put cores into deep sleep (CPU_SUSPEND, drivers/cpuidle/cpuidle-psci.c). A PSCI call travels by an SMC instruction to EL3 or, inside a virtual machine, by HVC to the hypervisor, which implements PSCI itself; the device tree's method property or a flag in ACPI's FADT tells the kernel which (drivers/firmware/psci/psci.c). Machines without PSCI name an alternative enable-method for their secondary CPUs—a spin table polled by parked cores, or on ACPI systems the parking protocol (arch/arm64/kernel/cpu_ops.c). The preference for entering at EL2 is likewise practical: EL2 is the hypervisor level, and being there lets the kernel install KVM and, on cores with the Virtualization Host Extensions, run the host kernel itself at EL2 for efficiency. Firmware that drops the kernel all the way to EL1 forecloses those options, so the boot protocol asks for EL2 whenever the hardware provides it.

Firmware After the Hand-Off

Linux 2.6 could treat the BIOS as essentially finished once the kernel entered protected mode. Firmware on a modern machine does not disappear so neatly; three kinds of it survive the hand-off. The first is the UEFI runtime services of §2.2, which the kernel still calls to read and write variables, set the clock, reset the machine, or stage a firmware update. The second is firmware that runs beneath the kernel, at a privilege the kernel cannot reach. On x86 this is System Management Mode (SMM): a CPU mode entered on a System Management Interrupt (SMI), in which firmware code hidden in protected SMRAM handles platform events—and, on many PCs, the authenticated writes to Secure Boot variables—invisibly to the operating system, which sees only that time has gone missing; the kernel's hwlat tracer (kernel/trace/trace_hwlat.c) was written to catch exactly those gaps. On ARM64 the equivalent is the EL3 monitor and any trusted OS in the secure world. The third survivor is the descriptive data firmware leaves behind—the memory map, the ACPI and SMBIOS tables, the device tree—which the kernel keeps, consults, and in large part exports.

Calling firmware after boot is delicate, because its code was built to run in its own address space under its own assumptions, and Linux handles it the same way on both architectures. The runtime regions of the memory map are mapped into a private address space, efi_mm, that is switched in only for the duration of a call, and firmware is told those virtual addresses once through SetVirtualAddressMap—by the x86 kernel itself during boot (arch/x86/platform/efi/efi.c), and by the ARM64 stub just after ExitBootServices, unless efi=novamap is given. Where firmware supplies a Memory Attributes Table, the kernel uses it to map runtime code read-only and runtime data non-executable (efi_memattr_apply_permissions, drivers/firmware/efi/memattr.c) instead of leaving firmware both writable and executable. Every call is then funneled through a dedicated workqueue, efi_rts_wq (drivers/firmware/efi/runtime-wrappers.c), which serializes the calls and runs them from a kernel thread, so a fault inside firmware can be attributed: on x86 a page fault in a runtime service freezes the workqueue and disables runtime services rather than bringing the kernel down (efi_crash_gracefully_on_page_fault). Firmware can also declare through its EFI_RT_PROPERTIES_TABLE that some services are no longer available after boot, as EBBR firmware often does for variable writes, and the kernel then never calls them. On ARM systems whose variables live in secure-world storage, a driver added in Linux 6.8 (drivers/firmware/efi/stmm/) reaches them through OP-TEE instead of a runtime call. And because some firmware calls take long enough to ruin real-time latency, PREEMPT_RT kernels disable runtime services by default (CONFIG_EFI_DISABLE_RUNTIME), which efi=runtime overrides; efi=noruntime disables them on any kernel.

On ARM64 the conversation with resident firmware has a formal shape, the SMC Calling Convention (SMCCC), which fixes how a function identifier and its arguments are placed in registers before an SMC or HVC instruction and how results come back (drivers/firmware/smccc/). PSCI is one service defined on top of it; others the kernel uses include the TRNG interface, through which firmware supplies hardware entropy and which arch_get_random_seed_longs prefers even over the CPU's own RNDRRS register; SDEI, firmware-delivered events used for platform error reporting (drivers/firmware/arm_sdei.c); SCMI, through which the kernel asks a separate system-control processor for clock, voltage, and performance changes over an SMC or a mailbox (drivers/firmware/arm_scmi/); FF-A, the framework for talking to secure partitions (drivers/firmware/arm_ffa/); and the OP-TEE driver (drivers/tee/optee/). Even the mitigation for the Spectre variant 2 family is an SMCCC call into firmware (ARM_SMCCC_ARCH_WORKAROUND_1, arch/arm64/kernel/proton-pack.c).

Much of this is visible from a running system. The directory /sys/firmware/efi exists only after a UEFI boot, which makes it the standard test for one; its fw_platform_size file reports whether the firmware was 32- or 64-bit (the mixed-mode case of §3.4), and on x86 runtime-map records the runtime mappings so that a kexec'd kernel (§8.2) can reuse them. UEFI variables appear as files in efivarfs, mounted at /sys/firmware/efi/efivars, which is how efibootmgr edits BootOrder and the Boot#### entries and how mokutil requests key enrollment. The EFI System Resource Table under /sys/firmware/efi/esrt lists the firmware components that can be updated, the inventory update tools such as fwupd work from, and /dev/efi_capsule_loader lets a capsule be passed straight to firmware. The raw ACPI and SMBIOS tables are under /sys/firmware/acpi/tables and /sys/firmware/dmi/tables, the unflattened device tree under /sys/firmware/devicetree/base (with the original blob in /sys/firmware/fdt), and, on x86, the firmware memory map as the kernel received it under /sys/firmware/memmap. The boot log fills in the rest, with lines such as "efi: EFI v2.7 by ..." naming the firmware's revision and vendor, x86's "Secure boot enabled", and ARM64's report of the exception level its CPUs started at.

Boot Loaders and Boot Protocols

Between the firmware and the kernel sits the code that actually loads the kernel image into memory and transfers control to it. Classically this is a dedicated boot loader; increasingly it is the kernel's own EFI stub standing in for one. Either way the hand-off is not ad hoc: each architecture defines a boot protocol that fixes exactly how the kernel image is laid out, where its parameters go, and what state the machine must be in at the entry point. The bundle of data that crosses this boundary was introduced in §1.3; this section is about the containers and conventions that carry it. It surveys the boot loaders in use today and the platforms each one serves (§3.1), then examines the two architectures' boot protocols and the image headers that encode them (§3.2 and §3.3), and finally the EFI stub that lets the kernel dispense with a separate loader altogether (§3.4).

Boot Loaders Today

The classic PC loader, LILO (the Linux Loader), patched the MBR, and its map installer recorded the disk block list of the kernel because LILO could not read a filesystem. That world is gone. LILO is retired, and on today's systems one of a handful of modern loaders does the job. GRUB 2 is the most widely deployed: a full multiboot environment that can read dozens of filesystems, present a menu, edit kernel command lines interactively, and chain-load other operating systems. systemd-boot is a minimalist alternative for UEFI systems that simply lists the kernels found on the EFI System Partition. On embedded ARM64 boards, U-Boot often serves as both late-stage firmware and boot loader, loading a kernel image and device tree from storage or the network. What all of these share, and what distinguishes them from LILO, is that they understand filesystems and follow a documented boot protocol, so they load the kernel by name rather than by memorized disk sectors.

Each of these loaders has grown around the platform it serves. On UEFI PCs and servers GRUB 2 normally runs as an EFI application itself, started by shim under Secure Boot (§2.2), while still carrying the real-mode code that BIOS machines need. systemd-boot discovers its menu rather than being configured: it lists the Boot Loader Specification entry files under /loader/entries/ on the ESP or an extended boot partition, plus any unified kernel images placed in /EFI/Linux/. U-Boot speaks several protocols at once. Its booti command reads the ARM64 image header of §3.3 and jumps in with the device tree in x0; bootm loads a Flat Image Tree (FIT), a container in device-tree format that holds one or more kernels, initrds, and device trees, each hashed and optionally signed so that U-Boot can verify what it boots; and bootefi implements enough of the UEFI interface (the EBBR profile of §2.3) to run the kernel's EFI stub as firmware would. The kernel build can produce a FIT itself: make image.fit on ARM64 (scripts/make_fit.py, Linux 6.10) packs the Image together with every device tree built for the configuration, so one file can boot a whole family of boards. Android devices use a fixed-layout boot image holding the kernel and a ramdisk, with vendor-specific parts split into a separate vendor_boot image since header version 3, and since Android 12 they pass their androidboot.* properties in the bootconfig appended to the initrd (§1.3) instead of on the command line. At the other extreme, projects such as LinuxBoot and petitboot replace the loader with a small Linux kernel and user space, stored in flash or on disk, that finds the real kernel and starts it with kexec (§8.2).

The deepest change, though, is that a boot loader is now optional. Because the kernel can be built as a UEFI application (§3.4), firmware can load and run vmlinuz directly from the ESP with no intermediate loader at all—the boot manager entry points straight at the kernel. Many distributions still interpose GRUB 2 for its menu and multi-OS features, but the capability to boot the bare kernel is a structural shift: the kernel now carries enough of a loader inside itself to bootstrap from firmware unaided.

It is worth distinguishing what a boot loader does beyond copying the kernel into memory, since that residual work is what the EFI stub must replicate when no loader is present. A loader assembles the kernel's command line, loads the initial ramdisk alongside the kernel and tells the kernel where it landed, and selects among multiple installed kernels—the everyday job of a recovery entry or a post-update fallback. GRUB 2 does this in stages of its own, chaining a tiny disk-embedded boot.img to a filesystem-aware core.img to its full menu-driven normal mode, a miniature echo of the whole staged boot. A newer trend collapses much of this complexity: the Boot Loader Specification standardizes drop-in per-kernel configuration files so loaders need no hand-edited scripts, and the unified kernel image packages the kernel, initrd, and command line into a single signed EFI binary that firmware can verify and launch as one unit—pushing the "no separate loader" model to its logical end.

A unified kernel image is itself an example of the layering described in §3.4. It is built around systemd's own small EFI program, systemd-stub, to which a tool such as ukify adds the kernel as a .linux PE section, the initrd as .initrd, and the command line as .cmdline, optionally with a device tree, CPU microcode, OS release data, and an SBAT section (§2.2), before the whole file is signed. When firmware starts it, systemd-stub measures those sections into the TPM, offers the initrd through the LoadFile2 protocol of §3.4, and starts the embedded kernel, whose own EFI stub then runs exactly as if firmware had launched it. Because one signature covers the initrd and command line as well as the kernel, a UKI closes a long-standing gap in classic Secure Boot, under which a signed kernel could still be started with an unsigned initrd or an attacker's command line.

The x86 Boot Protocol and bzImage

On x86 the kernel is distributed as a bzImage, a composite file whose structure is dictated by the Linux/x86 boot protocol. Its first part is a small real-mode setup area that begins with a header, defined as struct setup_header (arch/x86/include/uapi/asm/bootparam.h); the rest is the compressed kernel payload. The header is how a boot loader and the kernel agree on everything about the load: it carries the signature bytes 0x55AA at the end of the boot sector and the four-byte magic HdrS (arch/x86/boot/header.S) that identify a Linux kernel, a version number, and fields through which the loader reports where it placed the kernel, the command line, and the initial ramdisk. The loader fills in these fields, then populates a larger structure called struct boot_params—the "zero page"—which gathers the command-line pointer, the memory map, the framebuffer information, the ACPI RSDP pointer, and the EFI data, and passes its address to the kernel.

This protocol is also where the modern relocatable, randomizable kernel announces itself. Header fields such as relocatable_kernel, kernel_alignment, and pref_address tell the loader that the kernel may be placed at a range of addresses rather than one fixed location, and xloadflags advertises what the kernel can do: provide a 64-bit entry point, be loaded above 4 GiB, accept the EFI handover entries, survive kexec under EFI, run with 5-level paging, and support memory encryption (the XLF_* bits in arch/x86/include/uapi/asm/bootparam.h). None of this existed in Linux 2.6.11, whose kernel loaded at a fixed address. Once the loader has filled in boot_params and placed the payload, it enters the kernel through one of the entry points described next; a loader running on UEFI can instead skip all of this and start the bzImage as an ordinary EFI application (§3.4).

The header's version field records how far the protocol has come. Linux 2.6.11 spoke protocol 2.03; Linux 7.0 reports 2.15, the .word 0x020f that follows HdrS in header.S. The versions between mark the milestones: 2.05 (2.6.20) made the kernel relocatable, 2.09 (2.6.26) added setup_data, 2.10 (2.6.31) relaxed the alignment rules and added pref_address, 2.11 (3.6) added the EFI handover entry, 2.12 (3.8) added xloadflags and loading above 4 GiB, and 2.15 (5.5) added kernel_info. Version 2.14 is officially void—"burnt", in the documentation's word, by an incorrect commit—and loaders are told to treat it as 2.13. The protocol also defines three ways in, all documented in Documentation/arch/x86/boot.rst. The 16-bit protocol, the original, jumps into the real-mode setup code 0x200 bytes past its start, which then queries the BIOS and switches to protected mode itself (§5.1). The 32-bit protocol, for loaders that have already left real mode, enters the protected-mode kernel at startup_32 with paging off, flat __BOOT_CS and __BOOT_DS segments, and the boot_params address in %esi; such a loader must supply what the BIOS calls would have found, the memory map above all. The 64-bit protocol enters 0x200 bytes further on, at the decompressor's startup_64, with the CPU already in long mode, the kernel, boot_params, and command line identity-mapped, and boot_params in %rsi—free, in this protocol, to sit anywhere in memory, even above 4 GiB.

Two later additions let the interface grow without running out of room. setup_data is a singly linked list of typed records, rooted in a header field, for data too large or too variable for the fixed zero page (arch/x86/include/uapi/asm/setup_data.h): memory-map entries beyond the 128 that fit in boot_params (SETUP_E820_EXT), a device tree (SETUP_DTB), PCI option ROM images (SETUP_PCI), the EFI data a kexec'd kernel needs (SETUP_EFI), Apple device properties, the Jailhouse hypervisor's platform description, the SEV-SNP confidential-computing blob (SETUP_CC_BLOB), the IMA measurement log carried across kexec, the random seed of §1.3 (SETUP_RNG_SEED), and, newest, the state that Kexec HandOver preserves for the next kernel (SETUP_KEXEC_KHO); SETUP_INDIRECT lets a record point at data held elsewhere. Because a loader must not pass a record type the kernel does not understand, protocol 2.15 added kernel_info, a separate, extensible structure tagged LToP (arch/x86/boot/compressed/kernel_info.S) whose first field, setup_type_max, names the highest type this kernel accepts. And because loaders have more than once copied a whole sector of the image into boot_params instead of zeroing it and copying only the header, the kernel defends itself. The image carries a nonzero sentinel byte just before the header, at offset 0x1ef, which a correct loader never copies; if sanitize_boot_params (arch/x86/include/asm/bootparam_utils.h) finds it set, it clears every field outside a known-good list before the kernel trusts the rest.

The name bzImage itself encodes a piece of this history. Early kernels shipped as a zImage ("compressed image") that had to be decompressed into low memory, below the 640 KiB real-mode ceiling, and so could not grow beyond about half a megabyte. The bzImage ("big zImage") lifted that limit by loading the compressed payload high, above 1 MiB, leaving only the small setup area low—which is why the protocol carries a loadflags bit telling the loader whether the kernel wants to be loaded high or low. The boot_params structure is likewise called the zero page because the loader allocates a clean page for it and zeroes the fields it does not fill, a convention that lets the kernel distinguish a modern loader's rich hand-off from an old one that filled in almost nothing. These details rarely matter to a user, but they explain the vocabulary that pervades the x86 boot code and the reason a single kernel file can be booted by loaders spanning three decades of the protocol's evolution.

The first 512 bytes of the file have changed meaning entirely. In the 2.6 era they were a boot sector, a relic of the days when a kernel could boot straight from a floppy; the residual code there, which only printed a message telling the user to use a boot loader, was removed in Linux 6.7. When CONFIG_EFI_STUB is set, as it is in every distribution kernel, those bytes now hold an MS-DOS MZ header and the start of a PE/COFF header (arch/x86/boot/header.S) that declares the file an x86-64 executable with .setup, .text, .sbat, and .data sections and sets the NX-compatibility flag, promising the firmware that the image never needs memory that is writable and executable at once. A single bzImage is thus three things: a boot-protocol image for GRUB, a payload for kexec, and an EFI application for firmware.

The ARM64 Boot Protocol and Image Header

ARM64's boot protocol is simpler and stricter, reflecting the absence of any legacy baggage. The kernel is distributed as a flat Image (optionally compressed by the loader as Image.gz) that begins with a 64-byte header, struct arm64_image_header (arch/arm64/include/asm/image.h). The header opens with two instructions—arranged so that the very first bytes double as the MZ signature of a PE/COFF executable, which is what lets the same image be recognized as a UEFI application—and records the kernel's magic value ARM\x64, its effective size in memory (image_size), a text_offset, load flags such as the endianness and preferred placement, and, in its last word at offset 0x3c, the location of the PE/COFF header, exactly where an MS-DOS header keeps it. The text offset is a vestige: kernels used to expect to run 512 KiB (0x80000) above a 2 MiB boundary, but Linux 5.10 removed TEXT_OFFSET, and arch/arm64/kernel/head.S now writes a constant zero. A loader reads this header to learn how large a memory region to reserve and where within it the kernel expects to run.

The protocol's requirements at the entry point are spelled out in Documentation/arch/arm64/booting.rst and are far more explicit than anything on x86. The loader must place the kernel in memory, load any device tree blob, and enter the kernel with the MMU off, the caches in a defined state, the CPU in EL2 (preferred) or EL1, and—crucially—the physical address of the device tree in register x0, with x1 through x3 zero. There is no negotiation structure like boot_params and no real-mode stub: the contract is a register convention and a documented machine state. Everything the kernel needs to know about the platform arrives either through that device tree pointer or, on ACPI systems, through the UEFI configuration tables.

The document's rules are concrete enough to quote. The device tree blob must sit on an 8-byte boundary, be no larger than 2 MiB, and not share a 2 MiB region with memory that needs special attributes, because the kernel maps it cacheable in blocks of that size. The Image goes at a 2 MiB-aligned base, with at least image_size bytes free from its start. An initrd must lie within a 1 GiB-aligned window of at most 32 GiB that also covers the kernel, and its location travels in the device tree's /chosen node as linux,initrd-start and linux,initrd-end, beside the command line in bootargs. All DMA-capable devices must be quiesced, all interrupts masked in PSTATE.DAIF, the MMU off, and the CPU in the non-secure world. The longest part of the document, though, is a list of more than twenty clauses, one per architectural extension—pointer authentication, SVE, SME, MTE, the fine-grained traps, Guarded Control Stacks, and others—each saying which EL3 and EL2 control registers firmware must set before entry so that the kernel can use the feature. The list grows with nearly every release, and it is how the boot protocol tracks the architecture: a feature that firmware leaves trapped at a higher exception level is one the kernel cannot enable for itself.

Two properties of the ARM64 image reward a closer look because they enable the randomization of §4. First, the flat Image is fundamentally position-independent: subject to a 2 MiB alignment, it can be placed and run at any physical address, so a loader—or the EFI stub—is free to drop it wherever memory is available, and KASLR is free to choose that address at random. This is unlike the x86 bzImage, which carries a self-decompressor; an ARM64 Image is the already-uncompressed kernel, and when distributions ship Image.gz it is the boot loader, not the kernel, that inflates it before entry. The exception is the generic EFI zboot format (CONFIG_EFI_ZBOOT, drivers/firmware/efi/libstub/zboot.c), shared with RISC-V and LoongArch, which wraps a gzip- or zstd-compressed Image in a small EFI application, vmlinuz.efi, that inflates the kernel using boot services and then continues into the ordinary EFI stub. Second, the header's flags field (arch/arm64/include/asm/image.h) is small but load-bearing: three bit-fields record the kernel's endianness, its page-size expectation (4 KiB, 16 KiB, or 64 KiB granule), and where it may be placed. That last bit, set by every kernel since Linux 4.6, says that any 2 MiB-aligned address within the 48-bit physical range will do; a kernel that leaves it clear must be placed as close as possible to the start of RAM, because older kernels could not reach memory below themselves through the linear map. A loader that honors these fields avoids the mismatch—wrong endianness, wrong granule—that would otherwise leave the kernel unable to enable its MMU. The build offers the Image in every form a loader might want: compressed as Image.gz, Image.zst, Image.xz, and four other formats for loaders that inflate it themselves, wrapped as vmlinuz.efi for EFI zboot, or packed into an image.fit; a plain make produces Image.gz, or vmlinuz.efi when CONFIG_EFI_ZBOOT is set (arch/arm64/Makefile).

The EFI Stub: the Kernel as an EFI Application

The single most important boot innovation since Linux 2.6 is that the kernel can boot itself. The EFI stub is a piece of code linked into the kernel image (drivers/firmware/efi/libstub/) that makes the image a valid PE/COFF UEFI application, so firmware can load and execute it like any other .efi program. When entered this way the stub runs while UEFI boot services are still available and does the job a boot loader would otherwise do—from inside the kernel. On x86 the firmware enters at efi_pe_entry, and the deprecated handover protocol at efi_handover_entry; both lead to the main routine, efi_stub_entry (drivers/firmware/efi/libstub/x86-stub.c). On ARM64 the entry point is the generic efi_pe_entry (drivers/firmware/efi/libstub/efi-stub-entry.c), shared with RISC-V and LoongArch, and only the placement of the kernel image is specific to the architecture (handle_kernel_image, drivers/firmware/efi/libstub/arm64-stub.c).

The stub uses boot services to assemble everything the kernel proper will need. It allocates memory for the kernel, at an address randomized from the UEFI random-number protocol when KASLR is enabled (§4.2); it loads the initial ramdisk and records its location; it queries the firmware for the ACPI and other configuration tables; and it retrieves the final memory map. Then comes the point of no return: the stub calls ExitBootServices, after which no boot service may be used again, and jumps to the kernel with the machine now belonging to it. Because the memory map can change between fetching it and exiting, the stub follows the well-known "get the map, try to exit, and retry if the map's key is stale" dance (efi_exit_boot_services, drivers/firmware/efi/libstub/efi-stub-helper.c). Where the stub jumps differs by architecture. On ARM64 it has placed the uncompressed Image and simply enters it. On x86, since Linux 6.6, it no longer hands the compressed image to the old decompressor at all: efi_decompress_kernel calls the decompressor's own inflate-and-relocate routine, decompress_kernel, which is linked into the same image, to unpack the kernel into its randomly placed allocation before boot services are exited, and enter_kernel then jumps straight to the decompressed kernel's startup_64 with the boot_params pointer in RSI. Figure A-2 contrasts the traditional loader hand-off with this EFI-stub path.

A few refinements make the stub more capable and more general than this sketch suggests. Most of its logic is architecture-independent, living in the shared libstub directory and reused by x86_64, ARM64, RISC-V, and others, with only a thin per-architecture entry and hand-off around it. The way it obtains the initrd has evolved from an early scheme, in which the stub read a file named on the command line, to a cleaner mechanism whereby the boot loader (or firmware) exposes the initrd through a UEFI LoadFile2 protocol on a well-known device path (LINUX_EFI_INITRD_MEDIA_GUID, drivers/firmware/efi/libstub/efi-stub-helper.c), so the kernel pulls the initrd from firmware rather than touching the filesystem itself. The old way has not disappeared: efi_load_initrd tries the device path first and falls back to initrd= options on the command line, a loader that since Linux 6.2 is always built in and can name a file on any volume by device path, while the stub option noinitrd turns both off. Whatever it loads, the stub publishes in a configuration table under the same GUID, which the kernel proper picks up early in boot (drivers/firmware/efi/efi.c); on x86 it also writes the address into boot_params. A loader can tell which of these methods a kernel supports without running it: the PE header's image version field holds LINUX_EFISTUB_MAJOR_VERSION (include/linux/pe.h), whose value 3 is read as a bit mask—bit 0 for the device-path initrd, bit 1 for the initrd= loader. On x86 the stub even supports mixed mode: a 64-bit kernel booted by 32-bit UEFI firmware, bridged by a thunk that switches the CPU into long mode (efi32_enable_long_mode, arch/x86/boot/startup/efi-mixed.S). And the historic EFI handover protocol, a special entry point through which loaders like GRUB called into the stub with a pre-filled boot_params, has largely given way to loaders invoking the kernel as a plain EFI application—simplifying the interface to the one UEFI already defines. The option that still builds it, EFI_HANDOVER_PROTOCOL, is now labeled deprecated; its help text calls the protocol "a practice that has no basis in the UEFI specification", and a kernel built without it ignores any boot_params a loader offers and allocates its own (efi_allocate_bootparams).

On its way to ExitBootServices, the x86 stub's main routine, efi_stub_entry, runs through a checklist that shows how much a modern loader is expected to do. Before anything else it refuses to boot an SEV-SNP guest whose firmware has enabled features this kernel cannot handle. It looks up the firmware's memory-attribute protocol so that it can mark the decompressed kernel's text read-only and executable (efi_adjust_memory_range_protection)—the other half of the NX-compatibility promise in the PE header, since firmware that takes the promise at its word may hand out memory that is non-executable by default—and it prepares the switch into 5-level paging if the kernel wants it (drivers/firmware/efi/libstub/x86-5lvl.c). Then, besides loading the initrd, it records whether Secure Boot is on in boot_params; asks the firmware, through the TCG memory-overwrite request, to wipe RAM if the system later resets without a clean shutdown (efi_enable_reset_attack_mitigation); passes a random seed in a configuration table (efi_random_get_seed) and the TPM's event log (efi_retrieve_eventlog); describes the framebuffer of the UEFI graphics output protocol so the kernel can draw on it before its own graphics driver loads; copies PCI option ROMs into setup_data; applies Apple-specific quirks; and builds the bitmap of unaccepted memory (§2.2). Its final memory map becomes the e820 table, overflowing into SETUP_E820_EXT records when necessary. The generic stub's common path, efi_stub_common (drivers/firmware/efi/libstub/efi-stub.c), does the same jobs for ARM64 and the other architectures where they apply—framebuffer, event log, reset-attack mitigation, initrd, random seed—and then, in efi_boot_kernel (drivers/firmware/efi/libstub/fdt.c), writes its findings into the device tree's /chosen node (§2.3), exits boot services, and installs the runtime-services virtual mapping (§2.4) before entering the kernel.

Decompression and KASLR

Whichever path delivers control to the kernel image, what it delivers control to on x86 is not the kernel proper but a small self-extracting wrapper around a compressed copy of it. This arrangement—shipping the kernel compressed and unpacking it at boot—dates back to the earliest Linux and persists because it saves storage and boot-time I/O. What is new since Linux 2.6 is that the unpacking stage has taken on a second job: choosing a randomized address at which to place the kernel, the kernel-side counterpart to the user-space ASLR of Chapter 20. Both jobs are divided differently on the two architectures. On x86 the decompressor, or the EFI stub in its place, does both; on ARM64 the loader or the EFI stub unpacks the kernel and picks its physical address, while the kernel picks its own virtual address once it is running. This section covers the unpacking (§4.1), the randomization of the kernel image (§4.2), and the randomization the kernel applies to the rest of its address space, together with the defenses that keep the secret (§4.3).

The Compressed Kernel

The kernel build produces two related objects whose relationship is worth naming. The uncompressed kernel—the real thing that will run—is compressed with gzip, xz, zstd, or another algorithm, and that compressed blob is embedded inside a small decompressor program. In the x86 build these are conventionally abbreviated VO (the uncompressed kernel image) and ZO (the compressed image plus decompressor); the bzImage carries ZO. On a boot that does not go through the EFI stub, the decompressor's entry code (arch/x86/boot/compressed/head_64.S) sets up a minimal environment and calls extract_kernel (arch/x86/boot/compressed/misc.c), which chooses the load address, inflates the compressed payload, parses the resulting ELF image, applies any relocations needed for the address it was placed at, and returns the entry point of the real kernel. The familiar console messages of the old kernels—"Decompressing Linux..." and "done."—come from exactly this stage, on kernels built with X86_VERBOSE_BOOTUP. An EFI boot reuses the same core, decompress_kernel, but calls it from the stub (§3.4), so it skips head_64.S and extract_kernel and prints neither message.

The pipeline that produces ZO is short and shows what the decompressor will receive (arch/x86/boot/compressed/Makefile). The linked vmlinux is stripped to a raw binary, vmlinux.bin; the host tool arch/x86/tools/relocs extracts from the unstripped kernel a table of every place that holds an absolute address, and that table is appended to the binary; the result is compressed, with its uncompressed size stored in the last four bytes; and mkpiggy wraps the compressed file as an assembler source, piggy.S, that defines input_data and the input and output lengths. That object is linked with the decompressor's own code into arch/x86/boot/compressed/vmlinux, which becomes the protected-mode part of the bzImage behind the setup code. Two generated headers, voffset.h and zoffset.h, carry symbol addresses from VO and ZO into the code that needs them, which is where the VO_ and ZO_ prefixes seen throughout arch/x86/boot/ come from.

Inside the decompressor, the work runs in a fixed order. The 32-bit entry, startup_32, reached from the real-mode setup code or directly from a loader that follows the 32-bit protocol of §3.2, builds page tables and enters long mode; the 64-bit entry, startup_64, then decides where the kernel will be unpacked—the preferred address of LOAD_PHYSICAL_ADDR, 16 MiB by default, or where the loader actually put it if the kernel is relocatable. It switches between 4- and 5-level paging if the kernel's choice differs from the current mode, using a trampoline it places below 1 MiB (configure_5level_paging), and then copies itself to the end of the buffer reserved for the unpacked kernel and jumps to the copy. That copy is what makes in-place decompression safe: the output is written from the start of the same buffer toward the moving input, and the header's init_size includes a worst-case margin, computed in arch/x86/boot/header.S, that guarantees the writer never overtakes the data it has not yet read. Next, initialize_identity_maps (arch/x86/boot/compressed/ident_map_64.c) maps the decompressor, boot_params, the command line, and the setup_data records, and installs a page-fault handler, do_boot_page_fault, that adds an identity mapping for any other address the code touches, so the decompressor never needs to know in advance which memory it will use. Only then does extract_kernel run. It sanitizes boot_params (§3.2), detects whether it is running as an Intel TDX or AMD SEV confidential-computing guest, opens a serial console if one is configured, finds the ACPI RSDP and records it for the kernel, chooses the destination (§4.2), accepts any unaccepted memory the destination covers (§2.2), and inflates. parse_elf then copies each loadable segment of the inflated image to its final offset, and handle_relocations walks the appended table backward from its end, adding the difference between the chosen and the link-time virtual address to every 32-bit and 64-bit pointer it lists—or, when the virtual address was not randomized, prints "No relocation needed" and skips the walk.

The choice of compression algorithm is a deliberate trade-off between image size and decompression speed, and the build offers seven (init/Kconfig), all supported on x86: gzip is the conservative default, bzip2, lzma, and xz squeeze the image smaller at the cost of slower unpacking, lzo and lz4 unpack fastest but compress least, and zstd, available since Linux 5.9, has become popular for striking a good balance of ratio and speed—significant when decompression sits squarely on the boot's critical path. The kernel image is compressed with zstd's large-window mode, which needs more memory to unpack than the ordinary one, because it is decompressed in a single pass into a buffer of known size. Whatever the algorithm, the decompressor runs in a deliberately austere environment: an identity mapping built on demand, a small stack, a fixed heap inside its own image, and no access to the kernel's own subsystems, since none of them exist yet. This is why the relocation step matters. The unpacked kernel is an ELF image built to run at a particular virtual address, but KASLR (next) will have placed it elsewhere, so the decompressor adjusts every absolute address to the actual load location—the same mechanism that makes a position-independent user program work, applied to the kernel itself.

This whole self-extracting arrangement is an x86 tradition. As §3.3 observed, the ARM64 Image is already uncompressed, so on ARM64 the "decompression" stage is either done by the boot loader inflating an Image.gz before entry, or done by the EFI zboot wrapper (drivers/firmware/efi/libstub/zboot.c). zboot supports only gzip and zstd, and since Linux 6.15 calls the kernel's library decompressors directly rather than through the single-pass wrappers the x86 decompressor uses; with KASLR enabled it allocates the destination at a random physical address (§4.2) before inflating the Image and starting the EFI stub inside it. In neither case is there a relocation table to walk before entry: the ARM64 kernel applies its own relocations in its early code (§5.2), reading them from the standard ELF RELA table and, by default, from a compact RELR table, a format that encodes runs of relative relocations as bitmaps and shrinks the table dramatically (arch/arm64/kernel/pi/relocate.c).

Randomizing the Kernel's Location

Chapter 20 described how the kernel randomizes the address space of every user process to frustrate exploits. The kernel's own address is just as attractive a target, and so the boot path applies the same idea to the kernel itself: kernel address-space layout randomization (KASLR), enabled by CONFIG_RANDOMIZE_BASE, which defaults to on for x86 and is enabled in the ARM64 defconfig and in mainstream distribution kernels. Rather than unpack the kernel to a fixed, well-known address, the boot code chooses a random location within the permissible range and relocates the image there, so that the addresses of kernel code and data differ from one boot to the next and an attacker cannot hard-code them. On x86 the legacy decompressor makes the choice in choose_random_location (arch/x86/boot/compressed/kaslr.c), which honors a nokaslr command-line override and on x86_64 randomizes the physical load address and the kernel's virtual base separately. On an EFI boot the stub makes the equivalent choice itself in efi_decompress_kernel: it draws a seed from the firmware's random-number protocol, mixed with the CPU's own entropy, and uses one half to pick a random physical allocation through efi_random_alloc and the other half to pick the virtual offset. Either way it sets KASLR_FLAG in the header's loadflags, which is how the running kernel's kaslr_enabled later knows that its address is a secret worth keeping.

The physical choice is a search for a hole. The decompressor first builds a list of ranges to avoid: its own image and the buffer it is decompressing into, the initrd, the command line, boot_params, and up to four regions reserved with memmap=—more than four and it gives up on physical randomization rather than risk a collision. It also respects mem=, and keeps clear of memory that hugepages= will want for 1 GiB huge pages. It then walks the firmware memory map, preferring the EFI map to the e820 table and, where the firmware marks some memory as mirrored for reliability, using only that; on a machine with hot-removable memory it consults the ACPI SRAT table and confines itself to memory that can never be unplugged. Every 2 MiB-aligned position in the surviving regions (up to 100 of them) where the whole kernel fits becomes a slot, and a random number picks one. The random number comes from kaslr_get_random_long (arch/x86/lib/kaslr.c), which starts from a hash of the kernel's build string and of boot_params and mixes in the RDRAND instruction if the CPU has it and the time-stamp counter—or, on very old hardware with neither, the legacy i8254 timer. The virtual choice is simpler: any 2 MiB-aligned base between 16 MiB and 1 GiB into the kernel's mapping, which the Kconfig help text counts as 9 bits of entropy, while the physical address may lie anywhere up to 64 TiB. The EFI stub follows the same rules where they apply—its efi_random_alloc prefers mirrored memory too, and it gives up physical randomization, taking the lowest suitable address instead, when the command line carries mem=, memmap=, or hugepages=, or on old AMI-based firmware on which a randomized placement has been seen to hang the machine during decompression.

On ARM64 the work is split in two. The EFI stub chooses the physical placement, drawing entropy from the UEFI random-number protocol (efi_kaslr_get_phys_seed, drivers/firmware/efi/libstub/kaslr.c); if the protocol is missing, or a loader has told the stub through a Linux-specific protocol that the image must stay where it is, the stub runs the image where the firmware loaded it, moving it only if its alignment requires. The stub also stores a second random value in the device tree's /chosen/kaslr-seed property. The virtual offset is chosen later by the kernel itself: kaslr_early_init (arch/arm64/kernel/pi/kaslr_early.c), called from the early mapping code of §5.2, reads that seed—and overwrites it with zero in the device tree, so it cannot be read back later—or, failing that, asks the CPU's own RNDR random-number instruction, and places the kernel somewhere in the middle half of the vmalloc area. The seed supplies the 2 MiB-aligned part of the offset; the bits below 2 MiB come from where the image physically landed. An ARM64 kernel can therefore be randomized even when booted without UEFI, provided the boot loader supplies a kaslr-seed or the CPU implements RNDR; with neither, or whenever nokaslr is given, the virtual address stays at its default. The kernel reports the outcome in the boot log as "KASLR enabled", "KASLR disabled on command line", or "KASLR disabled due to lack of seed" (arch/arm64/kernel/kaslr.c). The result on both architectures is that the location of the kernel is one more thing an attacker must discover rather than assume, closing a gap that the fixed-address kernels of Linux 2.6 left wide open.

The two architectures' windows differ greatly in size. On x86 the kernel must stay within the top 2 GiB of the address space, where code built with the compiler's kernel code model can reach it with 32-bit signed offsets, and at 2 MiB alignment only a few hundred virtual positions fit; the same constraint is why enabling KASLR shrinks the space left for modules from 1.5 GiB to 1 GiB. ARM64 has no such limit, and on a 48-bit configuration the middle half of the vmalloc area spans tens of terabytes, so the image can sit at any of tens of millions of 2 MiB-aligned positions. But in both cases the granularity is coarse in another sense: the kernel is relocated as a single unit, so discovering the address of any one function reveals every other. This makes KASLR vulnerable to information leaks—an uninitialized pointer, a side-channel timing difference, or a hardware flaw that reveals an address—any of which can collapse the randomization at a stroke, however many bits it began with.

Randomization Beyond the Kernel Image

Randomizing the kernel's load address is only part of the story. Once the kernel is running it also randomizes other parts of its address space, so that leaking one kernel pointer does not immediately reveal the others. On x86_64, kernel_randomize_memory (arch/x86/mm/kaslr.c), called from setup_arch and enabled by CONFIG_RANDOMIZE_MEMORY, shuffles the bases of the three largest regions—the direct map of physical memory (page_offset_base), the vmalloc area (vmalloc_base), and the vmemmap array of struct page (vmemmap_base)—through its kaslr_regions table. It keeps their order but divides the unused space between them at random, at 1 GiB granularity, which its help text estimates at about 30,000 possible positions for each; on kernels with memory hotplug, ten terabytes of padding are reserved by default after the direct map for memory added later, at some cost in entropy. Smaller targets get their own treatment. The module area starts at a random offset of 1 to 1,024 pages (execmem_arch_setup, arch/x86/mm/init.c), and since Linux 6.2 each CPU's entry area—the block of pages holding the GDT, TSS, and entry and exception stacks the CPU uses when it enters the kernel—sits in a randomly chosen slot rather than at an address computable from the CPU number, closing a leak that had let attackers locate data at a fixed address.

ARM64 randomizes less beyond the image, and recently less than before. Its modules go into a 128 MiB window, randomly placed so that it still covers the kernel text and modules can branch to it directly, inside a 2 GiB window placed the same way for modules that need longer-range branches through PLTs (module_init_limits, arch/arm64/mm/init.c). Until Linux 6.16 the kernel also randomized where physical memory sat inside the linear map, but that feature was removed: a kernel that supports memory hotplug could almost never use it, and on recent CPUs with wide physical address ranges it had no room to work. Both architectures share one more randomization that applies after boot: with CONFIG_RANDOMIZE_KSTACK_OFFSET, on by default, each system call starts its kernel stack at an offset that carries six (ARM64) or seven (x86_64) bits of fresh randomness, so that a stack address leaked by one call says little about the next.

Randomization is worth only as much as the secrecy of the result, and the kernel works to keep its addresses out of view. The %p format in printk prints a hash of a pointer rather than the pointer itself, unless no_hash_pointers is given at boot (lib/vsprintf.c); the kernel.kptr_restrict sysctl controls whether %pK and /proc/kallsyms show real addresses, with kallsyms_show_value (kernel/ksyms_common.c) combining that setting with the reader's CAP_SYSLOG capability to decide between real addresses and zeros. Hardware side channels need stronger measures. Kernel page-table isolation (KPTI), introduced against Meltdown, removes most of the kernel from the page tables used while user code runs, which also takes away the timing differences by which an attacker could probe for mapped kernel pages. ARM64 turns KPTI on whenever KASLR is in effect, for that reason alone, unless the CPU implements the E0PD extension, which makes kernel addresses fault in constant time from user mode and so achieves the same protection more cheaply (kaslr_requires_kpti, arch/arm64/include/asm/mmu.h).

The secret must still be shared with those entitled to it. When the kernel panics, a notifier prints "Kernel Offset: 0x… from 0x…" on both architectures (dump_kernel_offset), so that an address in the oops can be mapped back to the symbol table, and the vmcore-info note handed to the kdump capture kernel records the same value as KERNELOFFSET (§8.2), which crash and makedumpfile use to read the dead kernel's memory. Privileged tools such as perf read real addresses from /proc/kallsyms. A system being debugged can boot with nokaslr to get repeatable addresses, at the cost of the protection.

For all these reasons KASLR, exactly like its user-space counterpart in Chapter 20, is best understood as one layer among many rather than a standalone defense. It raises the cost of an exploit that depends on knowing kernel addresses, and it composes with the non-executable mappings, the read-only kernel text, the stack-protector canaries, and the control-flow-integrity features the kernel also employs. It does not fix the memory-safety bug an attacker would exploit; it denies them the reliable address their exploit needs and forces them to find and chain an information leak first. That its default-on presence is now taken for granted—when the fixed-address kernel of Linux 2.6.11 could not be randomized at all—is a measure of how much the threat model has shifted in the intervening years. With the kernel decompressed, relocated, and randomized, control finally passes to the architecture-specific entry code that prepares the machine to run it.

Architecture Startup: Reaching C Code

The decompressor hands control to the real kernel's entry point, but that entry point is not yet start_kernel. Between them lies a stretch of hand-written assembly whose task is to transform the machine from the constrained state firmware left it in into one where portable C code can run: a CPU in its final operating mode, a set of page tables mapping the kernel at its virtual address, a valid stack and a current task, a zeroed BSS, exception handlers that can at least report a fault, and per-CPU state that C code can address. This is the most machine-specific code in the kernel, and it is where x86_64 and ARM64 look least alike—one climbing out of a 16-bit-compatible lineage, the other descending through exception levels. This section walks each path to the point where it calls start_kernel (§5.1 and §5.2), after which the two converge for good, and then follows the shorter path by which every other CPU later joins the running kernel (§5.3).

Both paths share one delicate problem that shapes their design: the code must change the very address translation under which it is itself executing. The moment the MMU is switched on, or a new set of page tables is installed, the meaning of the program counter and every pointer can change—and if the currently executing instructions are not mapped identically on both sides of that switch, the CPU faults on the instruction after the one that flipped the setting. The universal remedy is an identity mapping (or a small trampoline): a region where virtual and physical addresses coincide, so that the code performing the transition remains at the same address before and after and can keep running while the world changes beneath it. This trick appears in different guises throughout this section—x86's real-mode trampolines for waking secondary CPUs, ARM64's idmap—and recognizing it makes the otherwise cryptic entry code legible. A second shared problem is that the earliest code runs before the kernel is at the address it was linked for, so it cannot simply dereference its own global variables; both architectures now confine that code to a separately built, position-independent corner of the tree, discussed below.

x86_64: From Real Mode to start_kernel

The x86 entry code still bears the scars of the architecture's history. When the kernel is booted through the legacy BIOS path, it begins in the real-mode setup code in arch/x86/boot/, whose main function (arch/x86/boot/main.c) performs the residual tasks that once filled the assembly-language setup() of Linux 2.6.11. That routine was rewritten in C for Linux 2.6.23, and the code is now compiled with -m16 so that ordinary C runs in 16-bit real mode. In order, it copies the boot header into the zero page (copy_boot_params), starts an early console, checks that the CPU can run this kernel at all (validate_cpu, which prints "Unable to boot - please use a kernel appropriate for your CPU" otherwise), tells the BIOS that the operating system intends to run in long mode, detects memory through the BIOS e820 interface (arch/x86/boot/memory.c), queries the keyboard, SpeedStep, APM, and EDD disk information the BIOS can still supply, and configures the display. Last, go_to_protected_mode (arch/x86/boot/pm.c) disables interrupts, enables the A20 gate, resets the floating-point coprocessor, masks the interrupt controllers, loads a null IDT and a provisional GDT, and switches the CPU into 32-bit protected mode with protected_mode_jump (arch/x86/boot/pmjump.S), jumping to the code32_start address in the header—the decompressor's startup_32, which enters long mode and unpacks the kernel as §4.1 described. This machinery—the A20 gate, the real-to-protected transition—is the direct descendant of the Linux 2.6 setup code, and it survives for BIOS compatibility. On a UEFI system it is bypassed entirely: the CPU is already in long mode when firmware starts the EFI stub, and the stub delivers it straight to the decompressed kernel (§3.4).

Either way, control reaches the 64-bit entry code in arch/x86/kernel/head_64.S. Its startup_64 routine—the common convergence point, reached from the legacy decompressor or directly from the EFI stub—runs on whatever identity-mapped page tables its caller left loaded. It receives the boot_params pointer in RSI and keeps it in a callee-saved register, sets up an early stack, zeroes the GS base so that per-CPU accesses reach the boot CPU's initial data, loads an early GDT and IDT (__pi_startup_64_setup_gdt_idt), and reloads the code segment so that returning from an exception works. On machines with AMD memory encryption it then calls __pi_sme_enable, which must run before any CPUID instruction because an SEV-SNP guest takes its CPUID values from a table the firmware validated rather than from the untrusted hypervisor, and verify_cpu confirms once more that the processor has the features the kernel was built for. Next comes __pi___startup_64 (arch/x86/boot/startup/map_kernel.c), which fixes up the statically built early page tables, early_top_pgt and level4_kernel_pgt, for the physical address the kernel actually landed at and, under SME, encrypts the kernel image in place. Since Linux 6.16, 5-level paging support is always built in. The kernel does not choose the paging mode here: the decompressor or the EFI stub has already chosen it, from the CPU's capability and the no5lvl option, and check_la57_support merely reads the LA57 bit in CR4 to learn which tables to build. Like ARM64's early code (§5.2), these routines carry a __pi_ prefix because they run before the kernel is at its link-time address; since Linux 6.16 they live together in arch/x86/boot/startup/, whose Makefile applies the prefix to every symbol so that a stray call into ordinary kernel code fails to link. With the tables fixed, startup_64 loads them into CR3—an SEV guest first checks that the hypervisor has not lied about which page-table bit marks memory as encrypted—and jumps to common_startup_64 at its proper virtual address.

common_startup_64 is the code the boot CPU shares with every secondary CPU (§5.3). It sets the paging-related bits of CR4, locates the current CPU's per-CPU area, loads that CPU's own GDT, clears the data segment registers, points the GS base at the per-CPU area, installs the early exception handlers, enables the no-execute bit in EFER, sets the final CR0, and calls into C through the pointer initial_code, which on the boot CPU is x86_64_start_kernel (arch/x86/kernel/head64.c). That function finishes the early memory setup: it discards the early identity mapping (reset_early_page_tables), switches the bases of the direct map, vmalloc area, and vmemmap to their 5-level-paging values when that mode is on (a capability new since Linux 2.6, extending the virtual address space beyond 47 bits), clears the kernel's BSS, completes the memory-encryption and KASAN setup, installs an early page-fault handler that builds mappings on demand, initializes the TDX guest state, copies the boot data to safety, loads any early microcode update for the boot CPU, and finally calls x86_64_start_reservations, which applies a few platform quirks and ends by calling start_kernel.

A striking detail of the x86 path is how many times the CPU changes mode. On a legacy BIOS boot the boot processor passes through all three of the architecture's operating modes in sequence—16-bit real mode, 32-bit protected mode, and finally 64-bit long mode—each transition a small ceremony of loading descriptor tables and setting control-register bits, a lineage that reaches back to the 8086. UEFI spares the boot processor this climb, but not, as §5.3 shows, the processors woken after it.

ARM64: From EL2 to start_kernel

The ARM64 entry path has no real mode to escape and no protected-mode transition; its central concern is instead exception levels and the MMU. Execution begins at primary_entry in arch/arm64/kernel/head.S, with the CPU where firmware left it and the device-tree pointer in x0. The boot protocol requires a loader to enter with the MMU off, but the EFI stub, since Linux 6.3, jumps in with the firmware's MMU and caches still on, which avoids a slow round of cache maintenance; so the first thing record_mmu_state does is note which case applies and fix the CPU's endianness if it does not match the kernel's. The code then preserves the boot arguments (preserve_boot_args), saving the device-tree pointer for later, and switches to a small early stack. It builds an identity map—an early page-table set in which virtual addresses equal physical addresses—so that it can safely turn the MMU on without the ground shifting under it; since Linux 6.9 this is done in C by __pi_create_init_idmap, followed by whatever cache cleaning or invalidation the recorded MMU state calls for. It then runs init_kernel_el. Entered at EL1, that routine simply resets the system-control register. Entered at EL2, it disables the EL2 MMU if it was on, initializes the EL2 control and trap registers, and installs a minimal hypervisor stub (__hyp_stub_vectors) there. It also copes with newer CPUs on which the VHE mode bit is fixed at one. In every case it then drops to EL1, returning the level it was entered at so that the choice can be revisited once the kernel is running.

With the exception level settled, __cpu_setup (arch/arm64/mm/proc.S) resets the debug and performance-monitor access controls so that user space cannot reach them, and programs the memory-attribute indirection register and the translation-control register—page granule, virtual and physical address sizes, hardware update of the page-table access flag, and, on CPUs that have it, permission indirection. Then __primary_switch enables the MMU through __enable_mmu, with only the identity map live and an empty table in the kernel half. Still running at its physical address, it calls __pi_early_map_kernel (arch/arm64/kernel/pi/map_kernel.c), C code that does most of the remaining work. It maps the device tree and clears the BSS and the initial page tables. It parses the command line for CPU-feature overrides (arch/arm64/kernel/pi/idreg-override.c), which is how options such as arm64.nopauth, arm64.nosve, arm64.nomte, kvm-arm.mode=nvhe, nokaslr, and rodata=off take effect before the features they disable are ever used. It decides the virtual-address size, falling back from 52 bits to 48 when the kernel supports large addresses (with 64 KiB pages, or with 4 KiB and 16 KiB pages through the LPA2 extension supported since Linux 6.9) but the CPU does not. It picks the KASLR offset (§4.2), and if KASLR is active on a CPU without E0PD, so that KPTI will be needed (§4.3), it marks the kernel's mappings non-global from the start rather than rewriting them later. Finally it builds the kernel's real page tables.

Those tables are usually built in two passes. The first maps the kernel text writable, so that the image's relocations can be applied for the chosen offset and, on CPUs that lack both pointer authentication and BTI, so that the compiler-emitted pointer-authentication instructions can be patched into shadow-call-stack operations, the alternative return-address protection, a dynamic switch available since Linux 6.2. The second pass remaps the text read-only and executable, marked as BTI-guarded pages when the CPU enforces branch targets. The root table is then copied to swapper_pg_dir, the kernel's permanent page-table root, and installed. Control then jumps to the virtual address of __primary_switched, which makes init_task the current task, installs the exception vectors, stores the saved device-tree address into the global __fdt_pointer (arch/arm64/kernel/setup.c) where the C code will find it, records the virtual-to-physical offset of the image (kimage_voffset) and the boot exception level, initializes KASAN's shadow mapping if configured, and calls finalise_el2. That call moves the kernel back up to EL2 when the CPU has the Virtualization Host Extensions, or, with kvm-arm.mode=protected, leaves the kernel at EL1 and prepares a hypervisor that itself runs in VHE style. Finally it branches to start_kernel. Figure A-3 places the two architectures side by side and marks where they meet.

Two mechanisms give the ARM64 path its character. The architecture provides two translation-table base registers, and the kernel uses them to make the MMU switch seamless: TTBR0 holds the identity map that covers the running transition code, while TTBR1 holds the kernel's high virtual mapping, so the MMU can be enabled under the identity map, the kernel mapping filled in beside it, and execution moved onto the kernel's real addresses by a single jump, without the running instructions ever becoming unmapped—the identity-map trick of this section's introduction, realized in hardware. The second mechanism is that much of the earliest code is position-independent, built from arch/arm64/kernel/pi/ with every symbol given a __pi_ prefix (as in __pi_create_init_idmap and __pi_early_map_kernel): because KASLR may have placed the kernel at a random physical address, this code cannot assume its link-time addresses and must run correctly wherever it landed, patching the kernel's own relocations before the normal, address-dependent code begins. Moving this work from assembly into C over the 6.x series made the early boot easier to read and to extend, at the price of a separate build and a few rules the code must follow: no tracing or sanitizer instrumentation, no stack protector, and access to the rest of the kernel only through explicitly exported aliases—on ARM64 a build-time checker, relacheck, also rejects any absolute reference that would need a relocation before the relocations have been applied.

Bringing Up the Secondary CPUs

Everything so far has happened on a single processor. The other CPUs sit idle, held in reset or parked by firmware, through the whole of start_kernel; they are started only later, when kernel_init calls smp_init (§7.2) and the CPU-hotplug machinery brings each one online in turn. Each such CPU, called an application processor in x86 parlance, takes a much shorter path than the boot CPU did: there is nothing to decompress, no KASLR choice to make, and no page tables to build, because the kernel is already mapped and running. What remains is to get the new CPU from its reset state into the kernel's mode and page tables, give it a stack and a task, and let it call a C function, start_secondary on x86 or secondary_start_kernel on ARM64, that sets up its per-CPU state and enters the idle loop.

On x86 that first step is the hard one, because an application processor comes out of its INIT/startup sequence in real mode, at an address below 1 MiB. Early in boot the kernel therefore reserves a block of low memory (reserve_real_mode) and copies into it a small real-mode blob built from arch/x86/realmode/rm/, which also holds the code used to resume from ACPI S3 sleep and to reboot through the BIOS. For each CPU, do_boot_cpu (arch/x86/kernel/smpboot.c) sets initial_code to start_secondary and sends the target an INIT and startup interrupt pointing at trampoline_start (arch/x86/realmode/rm/trampoline_64.S). The CPU climbs from there through protected mode into long mode and joins the kernel at secondary_startup_64, which loads the kernel's page tables and falls into the same common_startup_64 the boot CPU used. Since Linux 6.5 this happens in parallel: rather than waking one CPU and waiting for it, the kernel kicks all of them at once, and each finds its own CPU number by reading its APIC ID and looking it up in a table, while a lock in the trampoline keeps them from sharing its single stack at the same time. On a large server this cuts the time spent bringing CPUs online substantially. Confidential-computing guests break the pattern. A TDX guest's CPUs are released through an ACPI-defined mailbox, and Hyper-V environments supply their own wake-up hooks; both start the CPU already in long mode at trampoline_start64. An SEV-SNP guest, whose register state the hypervisor cannot simply set, asks the hypervisor to create each CPU from an encrypted register-save area and starts it at a dedicated sev_es_trampoline_start. TDX and SEV-ES guests also turn parallel bring-up off, because the code that reads the APIC ID cannot yet run there.

On ARM64 the kernel asks rather than pokes. Each CPU's enable-method selects a set of cpu_operations (arch/arm64/kernel/cpu_ops.c). With PSCI the kernel issues CPU_ON with the physical address of secondary_entry (arch/arm64/kernel/psci.c), and firmware starts the core there with its MMU off. With the older spin-table method the boot loader leaves each secondary core polling a release address named in the device tree; the kernel writes the address of its holding pen (secondary_holding_pen) there and wakes the cores with an event. Each core then waits in the pen until the kernel writes that core's hardware ID into secondary_holding_pen_release, and only then proceeds (arch/arm64/kernel/smp_spin_table.c). The ACPI parking protocol instead hands each core the address of secondary_entry through a per-CPU mailbox. However it arrives, the core runs init_kernel_el and __cpu_setup, as the boot CPU did, enables the MMU directly onto the permanent tables—the runtime identity map idmap_pg_dir in TTBR0 and swapper_pg_dir in TTBR1—and continues at __secondary_switched, which repeats the EL2 finalization, installs the vectors, takes the idle task and stack the boot CPU prepared for it, sets its pointer-authentication keys, and calls secondary_start_kernel. The kernel checks that every CPU started at the same exception level, warning "CPUs started in inconsistent modes" if not, and a core that cannot support the virtual-address size or page granule the boot CPU chose reports itself stuck rather than corrupt the running system. The whole affair is markedly simpler than x86's per-core mode climb.

start_kernel: The Architecture-Independent Boot

start_kernel (init/main.c) is the kernel's true beginning as a portable program. Every architecture, having done its machine-specific preparation, arrives here, and from here the same code runs on x86_64, ARM64, and everything else Linux supports. Its job is to bring every kernel subsystem to life in a careful order—each initialization depending on the ones before it—and then to spawn the first processes. The modern start_kernel makes about a hundred calls in sequence, reflecting how much the kernel has grown. This section looks first at the one call that is still architecture-specific, setup_arch, then at the broad shape of the initialization sequence and the initcall mechanism that extends it, and finally at how the kernel learns what hardware it is running on.

The function's declaration already says a good deal about the conditions it runs in. It is __init, so its code is discarded once boot is over, and __noreturn, because it ends by turning into the idle task rather than returning. It is compiled without stack protection (__no_stack_protector), because partway through it installs the boot CPU's stack canary, and a check against a value that changed under it would fail; and without KASAN instrumentation (__no_sanitize_address), because the shadow memory KASAN checks against is not yet complete. Its first lines run even before setup_arch: they write a magic value at the end of init_task's stack so that an overflow can be detected (set_task_stack_end_magic), give the earliest control-group code its root (cgroup_init_early), disable interrupts, and mark the boot CPU as possible, present, online, and active (boot_cpu_init). Then start_kernel prints the linux_banner string—"Linux version 7.0.12 …" followed by the compiler and build details—which is why that line opens every boot log.

setup_arch

The first substantial thing start_kernel does is call setup_arch, and although start_kernel itself is portable, setup_arch is implemented separately for each architecture—it is the bridge between the machine-specific boot and the generic kernel. Its purpose is to turn the raw information gathered during early boot into the initialized memory and platform state the rest of the kernel assumes. On x86 (arch/x86/kernel/setup.c) the function runs to some four hundred lines, and its order tells the story. It first identifies the CPU (early_cpu_init) and enables static keys and static calls so that later code can patch its own branches, then reads boot_params and the setup_data chain (§3.2) and turns the firmware memory map into the kernel's e820 table (e820__memory_setup). With the command line's early parameters parsed (§1.3), it initializes EFI, detects whether it is running under a hypervisor (init_hypervisor_platform), takes an early TSC calibration, randomizes the kernel's memory regions (§4.3), and converts the e820 map into the kernel's memblock early allocator (e820__memblock_setup). Only then does it build the direct mapping of physical memory (init_mem_mapping), reserve the initrd, read the ACPI tables, discover the NUMA topology (initmem_init), reserve the crash-kernel area, finish the kernel page tables, and parse the ACPI MADT to learn which CPUs and interrupt controllers exist (acpi_boot_init). Many of these steps are indirect calls through the x86_init operations table (arch/x86/kernel/x86_init.c), so that a Xen guest or an unusual platform can replace a step without changing the sequence.

On ARM64 (arch/arm64/kernel/setup.c) the function is shorter and driven by the device tree. setup_arch maps the FDT through a fixmap slot and scans it (setup_machine_fdt, §6.3), printing a "Machine model:" line—or, if the blob is invalid, a message about its required alignment and size before spinning forever, since nothing yet exists that could report a panic. It then parses early parameters, turns on the dynamic shadow call stack if the early code of §5.2 patched it in, unmasks debug exceptions and asynchronous SErrors, and removes the identity map used to switch on the MMU. It initializes EFI, builds memblock (arm64_memblock_init) and the linear map of all memory (paging_init), reads the ACPI tables if they are to be used, unflattens the device tree if they are not, and sets up NUMA, the DMA zone limits, the contiguous memory allocator, and the crash-kernel region (bootmem_init). The tail end learns how to start the other CPUs: it initializes PSCI from the device tree or ACPI, checks whether it is running as a Realm guest under Arm's Confidential Compute Architecture (arm64_rsi_init), and enumerates the CPUs and their MPIDR affinity values (smp_init_cpus, smp_build_mpidr_hash). A last check warns if the loader left nonzero values in x1–x3, which the boot protocol requires to be zero. Despite the different details, the two do the same job: hand start_kernel a machine whose memory and platform description are ready to use.

What setup_arch no longer does is as instructive as what it does. Until Linux 7.0 every architecture ended its memory setup by calling free_area_init with an array of zone limits, which sized the memory nodes and zones and initialized the memory map of struct page descriptors (Chapter 8). Linux 7.0 took that call away from every architecture: each now only reports its zone boundaries through arch_zone_limits_init, and start_kernel calls mm_core_init_early (mm/mm_init.c) right after setup_arch to reserve boot-time huge pages and their CMA area and to build the nodes, zones, and memory map in one generic place. The change removed duplicated code from some twenty architectures and the inconsistent ordering between huge-page reservation and memory-map setup that had grown up among them.

It is worth being clear about the peculiar environment in which start_kernel and setup_arch execute, because it explains many of their constraints. This code runs single-threaded, on the only CPU that is online so far, using the stack of the hand-built init_task, with interrupts disabled until start_kernel explicitly enables them well into the sequence. There is no scheduler to preempt it and no other task to switch to, so the ordering of initializers is not a matter of locking but of simple sequence: whatever a later step needs, an earlier step must already have built. The memory allocator available at this stage is not the full page allocator but memblock, a simple boot-time allocator that tracks which physical ranges are free and reserved. Once the core memory manager is up, memblock_free_all releases every unreserved page to the buddy allocator. On very large machines most of the struct page initialization is deferred (CONFIG_DEFERRED_STRUCT_PAGE_INIT) and finished by per-node kernel threads in page_alloc_init_late, after the other CPUs are online; memblock's own tables are then discarded unless the architecture keeps them, as ARM64 does. Almost all of this code is marked __init, and its data __initdata, a signal that it is needed only during boot and that its memory may be reclaimed afterward—the reclamation that §7.3 describes. The build checks the discipline: modpost warns about any ordinary code that references an __init symbol, and the rare legitimate exception is annotated __ref. The most important such exception is rest_init, the last call of start_kernel, which is deliberately not __init: the boot thread that runs it goes on to become the idle loop and must keep executing long after the init sections have been freed.

The Initialization Sequence

After setup_arch returns, start_kernel proceeds through a long, deliberately ordered series of initializer calls. The ordering is not incidental—it encodes the dependency graph of the kernel's subsystems, since each initializer assumes the facilities set up before it, and the comments in init/main.c often say so outright ("Set up the scheduler prior starting any interrupts", "This must be after timekeeping is initialized"). The sequence falls into two phases, divided by the moment interrupts are first enabled.

In the first phase, with interrupts off and only memblock to allocate from, start_kernel builds the memory map (mm_core_init_early), enables static keys and static calls so that the earliest security modules can use them (early_security_init), applies any bootconfig and saves the command line (§1.3), allocates a per-CPU data area for every possible CPU (setup_per_cpu_areas), and parses the command line. It seeds the random number generator from the CPU's hardware random instructions and the command line (random_init_early), enlarges the log buffer if log_buf_len= asks for it, allocates the large dentry and inode hash tables while big contiguous memblock allocations are still possible (vfs_caches_init_early), and installs the exception handlers (trap_init). Then comes the pivotal hand-off: mm_core_init passes memblock's free memory to the buddy allocator and brings up the slab allocator, vmalloc, and, on x86, page-table isolation. On that footing the kernel initializes ftrace, the scheduler (sched_init, which must precede any interrupt), early workqueues (so that work can be queued, though not yet run), read-copy-update (rcu_init), the trace-event subsystem, the interrupt descriptors and controllers (early_irq_init, init_IRQ), the tick, timer, high-resolution timer, and softirq machinery, and timekeeping (timekeeping_init, time_init). With a clock running, the random number generator is seeded again (random_init), and its output is put to use at once, by KFENCE and for the boot CPU's stack-protector canary.

Interrupts are enabled with local_irq_enable once perf events and cross-CPU function calls are ready, and console_init follows: it runs the console drivers registered with console_initcall, so that the messages buffered since the banner—shown until now only by an early console (§8.1), if one was configured—finally reach the real console. Lockdep and its self-tests come next, then ACPI loads its tables into the interpreter (acpi_early_init), and calibrate_delay computes the loops-per-jiffy value that short busy-wait delays use. This calibration once timed a busy loop against the timer tick; on both reference architectures it is now normally skipped, the value being derived from the known TSC or generic-timer frequency, and the log says "Calibrating delay loop (skipped), value calculated using timer frequency". Then arch_cpu_finalize_init, added in 6.5, gives the architecture a last word on the boot CPU: on x86 it completes CPU identification, selects the speculative-execution mitigations, initializes the FPU, switches the EFI runtime services to virtual mode, and patches the kernel's alternative instructions for the CPU it found. ARM64 does not implement this hook; it settles CPU features only after all CPUs are online, because a feature the kernel relies on system-wide must be present on every one of them. The final stretch creates the caches and roots of the process-level abstractions: PIDs, anonymous-memory reverse mapping, thread stacks, credentials and process creation (cred_init, fork_init), the UTS, time, and network namespaces, keys, the security framework (security_init), the VFS caches and page cache (vfs_caches_init, pagecache_init), /proc, nsfs and pidfs, cpusets, memory cgroups, and control groups (cgroup_init). Last, ACPI switches the hardware into ACPI mode (acpi_subsystem_init). Table A-2 lists the milestones of this sequence and the subsystem each brings up. Only once all of them have run does start_kernel make its final call, to rest_init, which creates the first processes.

The explicit sequence in start_kernel is only half of the kernel's initialization; it deliberately handles just the core subsystems that must exist before anything else, and defers the vast bulk of device and subsystem setup to a separate, table-driven mechanism: the initcalls. Throughout the kernel, an initialization function can be tagged with a macro (include/linux/init.h) that places a pointer to it in one of several ordered levels: pure_initcall, core_initcall, postcore_initcall, arch_initcall, subsys_initcall, fs_initcall, device_initcall, and late_initcall, numbered 0 through 7, most with a _sync companion that runs after the rest of its level. Two more stand outside the numbering: early_initcall functions run before the secondary CPUs are started, and a rootfs_initcall level between fs and device starts unpacking the initramfs. A built-in driver's module_init is simply a device_initcall. After boot reaches process context, do_initcalls (init/main.c, §7.2) walks these levels in order, running every registered function, which is how the hundreds of drivers and optional subsystems bring themselves up without start_kernel having to name them individually.

The mechanism is a linker trick. Each macro emits its pointer—or, on architectures that support it, including both reference architectures, a 32-bit offset that takes half the space—into a section named for its level, such as .initcall6.init, and the kernel's linker script gathers those sections in level order between symbols the kernel can walk. Within a level, functions run in link order, which follows the order of objects in the Makefiles; that is why drivers/Makefile lists its subdirectories in a deliberate sequence, with comments explaining which subsystem must come before which. Before each level runs, the command line is parsed again for parameters registered to that level. This two-tier design—a short hand-written spine of essential initializers, then a long machine-generated list of everything else—is why the explicit sequence in Table A-2 is far shorter than the full set of things that happen at boot, and why adding a new driver requires no edit to start_kernel at all. Each initcall can be timed with the initcall_debug parameter to diagnose slow boots, and one that hangs or misbehaves can be skipped by name with initcall_blacklist=.

Hardware Discovery: Device Tree and ACPI

Threaded through setup_arch and the initializer sequence is a question the 2.6-era PC largely answered by probing fixed I/O ports: what hardware is actually present? Modern Linux is told, through one of two structured descriptions. The device tree is a compact binary data structure—a flattened device tree (FDT) blob— that firmware passes to the kernel (its address arriving in x0 on ARM64). It describes the machine's CPUs, memory, buses, and peripherals as a tree of nodes with properties. Early in boot the kernel scans this blob for the few facts it needs at once (early_init_dt_scan, drivers/of/fdt.c): the root node's address and size cell counts; the /chosen node's command line, initrd location, and random seed, which it feeds to the random number generator and then erases from the blob so that it cannot be found again; and the /memory nodes that tell memblock where RAM is. The /reserved-memory node is honored a little later, as memblock is built. Afterward the kernel unflattens the blob (unflatten_device_tree) into an in-memory tree that device drivers consult to find and configure the hardware they manage. Device tree is the standard on embedded and mobile ARM64 systems, which have no self-describing bus to enumerate.

What each node's properties mean is fixed by a binding, a document that defines the properties a given kind of device must or may have. The 7.0 tree carries some 5,400 bindings written as YAML schemas, which the dt-schema tools check device trees against (make dtbs_check), and about 700 left in the older free-text form; arch/arm64/boot/dts/ holds some 1,500 board descriptions. x86 uses a device tree only on a few embedded platforms, where the loader usually passes it as a setup_data record.

The alternative, used on servers and on virtually all x86 systems, is ACPI (Advanced Configuration and Power Interface), whose tables the firmware exposes through a root pointer, the RSDP. On x86 the kernel finds it in boot_params, in the EFI configuration table, or, on a legacy BIOS machine, by scanning low memory for its signature; on ARM64 it comes from the EFI configuration table. ACPI describes not only the devices but a rich power-management and configuration model, parts of it written in a bytecode, AML, that the kernel runs in ACPICA, the reference interpreter it shares with other operating systems (drivers/acpi/acpica/). The kernel brings ACPI up in stages that track start_kernel: setup_arch reads the static tables, from which x86 learns its CPUs and interrupt controllers; acpi_early_init loads the AML into the interpreter's namespace; acpi_subsystem_init switches the hardware into ACPI mode; and acpi_init, a subsys_initcall, walks the namespace to create devices.

On x86 there is no choice between the two descriptions. On ARM64 the choice is the one §2.3 outlined, made in acpi_boot_table_init (arch/arm64/kernel/acpi.c): acpi=off forces the device tree, and otherwise ACPI is tried when acpi=on or acpi=force asks for it or when the device tree is an empty stub (which under Xen may also hold a /hypervisor node). If the tables then fail their sanity checks, the kernel disables ACPI again unless acpi=force insists. The two mechanisms are therefore mutually exclusive on a given boot—setup_arch unflattens the device tree only when ACPI is disabled—but they serve the same architectural purpose: replacing blind probing with a firmware-provided map of the machine, so the kernel's generic driver core can bind drivers to the devices that are genuinely present. This hardware description is the last piece of context the kernel assembles before handing the system to its first real processes.

What ties both descriptions to the rest of the kernel is the unified driver model. A device tree node or an ACPI object does not do anything by itself; it becomes a struct device that the kernel's bus-and-driver matching machinery can bind a driver to. On device-tree systems the kernel walks the unflattened tree and instantiates a platform device for each hardware node (of_platform_populate, called at the arch_initcall_sync level), matching each against drivers by its compatible string—a stable identifier such as "arm,pl011" for a particular UART. On ACPI systems the enumeration walks the ACPI namespace instead, matching by device IDs, but the resulting struct device objects flow into exactly the same driver core. Since 3.19 an ACPI device can even carry the special ID PRP0001 and a device-tree compatible property, so that one driver matches on both. A driver that needs more than a match need not care which description supplied its device, either: every struct device points to a firmware node (struct fwnode_handle, include/linux/fwnode.h), and the device_property_read_* family (include/linux/property.h) reads a named property from a device-tree node or from ACPI device data alike.

Firmware descriptions also record dependencies: a UART node names the clock and pin controller it needs, and its driver cannot work until their drivers have. When a supplier is not yet ready, the driver's probe returns -EPROBE_DEFER, and the device goes onto a deferred-probe list that is retried each time another driver binds. Since 5.13 the kernel also reads these references itself (fw_devlink, at its stricter default level rpm since 6.8) and creates device links that hold a consumer back until its suppliers have probed, removing most of the futile retries. This is why the two firmware descriptions, despite their very different form, converge on one mechanism: whichever produced them, the devices they describe are probed and driven by the same code, the driver model of Chapter 13. The firmware map and the driver core together replace the fixed-port probing of the 2.6-era PC with a general, data-driven way of discovering and claiming hardware.

The First Processes

A running Linux system is a tree of processes, and every tree needs a root. The final act of the boot sequence is to plant that root: to create the handful of original processes from which all others descend, and to launch the user-space init program that will bring up the rest of the system. This is where the kernel, having initialized itself, steps back and becomes the servant of user space. The mechanism is subtle—the boot thread does not simply call init, but transforms itself and spawns siblings in a particular choreography—and it has changed in instructive ways since Linux 2.6. This section follows rest_init as it creates the idle task, the kernel thread daemon, and the first user process (§7.1); traces the work process 1 does in kernel mode to finish the boot, from starting the other CPUs to running the initcalls (§7.2); and ends with the moment process 1 executes the user-space init program and the kernel's own boot is over (§7.3).

One variable tracks the whole progression. system_state (include/linux/kernel.h) starts at SYSTEM_BOOTING, becomes SYSTEM_SCHEDULING when rest_init has created the first processes and the scheduler may switch between them, passes through SYSTEM_FREEING_INITMEM while the boot-only code is discarded, and reaches SYSTEM_RUNNING just before init is executed. Code all over the kernel consults it: debugging checks such as might_sleep stay quiet until scheduling is possible, and some facilities behave differently while the system is still booting.

Process 0, the Idle Task, and rest_init

The thread of execution that has run everything so far—from the first kernel instruction through all of start_kernel—is not an ordinary process. It is process 0, hand-built at compile time as init_task (init/init_task.c) rather than created by fork. Its destiny is humble: once boot is finished it becomes the boot CPU's idle task, the process the scheduler runs when that CPU has nothing else to do. Every other CPU gets an idle task of its own, created by fork_idle when smp_init prepares to start it (§7.2); all of them share PID 0 and are named after the CPU they serve. The transformation happens in the last function start_kernel calls, rest_init (init/main.c). Rather than continue as itself, rest_init spawns the processes that will do the remaining work and then surrenders the boot CPU to idling. It must be careful about ordering, and it uses a completion to make process 1 wait until the kernel-thread daemon exists before either runs in earnest.

Concretely, rest_init tells RCU that the scheduler is about to start, creates two processes, and then retires. First it calls user_mode_thread to create process 1, running the in-kernel function kernel_init; this is the process that will become user-space init. It is created first precisely so that it receives PID 1, and it is pinned to the boot CPU, because task migration does not work properly until the scheduler's multiprocessor setup has run. Then rest_init calls kernel_thread to create process 2, running kthreadd, the daemon that spawns and manages all other kernel threads. It sets system_state to SYSTEM_SCHEDULING, signals the completion that releases process 1, calls schedule once so that the new processes can run, and finally calls cpu_startup_entry, entering the idle loop and completing its metamorphosis into the idle task. The kernel is now multitasking; three processes exist, and the boot narrative splits into the two it just created. rest_init itself is deliberately not marked __init (§6.1): the boot thread never returns from it, so its code must survive the freeing of the init sections that process 1 will soon perform.

Two aspects of this arrangement are easy to overlook. The first is why the idle task exists at all: the scheduler's invariant is that a CPU always has something runnable, so that its dispatch loop never faces an empty runqueue. Process 0—known by its traditional name swapper, which survives as swapper/0, swapper/1, and so on, one per CPU—is that something. It never appears in a process listing, since /proc has no entry for PID 0, but it is the parent PID that listings show for processes 1 and 2, and the name kernel messages report when an oops or warning strikes on an idle CPU. When it runs, the idle loop (do_idle, kernel/sched/idle.c) does not spin uselessly: it stops the periodic tick if it can (Chapter 6) and places the CPU into a low-power state through the cpuidle subsystem until an interrupt or a newly runnable task arrives, which is how an otherwise quiet machine saves energy. The second is the ordering care mentioned above. kernel_init will need to create kernel threads, and kernel-thread creation is handled by kthreadd; if process 1 ran before process 2 existed, its requests would go to a daemon that is not there. rest_init therefore has process 1 wait on a completion (kthreadd_done) that rest_init signals only after kthreadd has been created, guaranteeing the daemon is ready before its first customer runs.

kernel_init and kthreadd

The division of labor between processes 1 and 2 reflects a structural change since Linux 2.6.11, which had no dedicated kernel-thread daemon: there, kthread_create asked the keventd workqueue to spawn each new thread. kthreadd (process 2), added in 2.6.22, is the ancestor of every kernel thread: when any part of the kernel later asks for a worker thread—a per-device I/O thread, a filesystem journal thread, a workqueue worker—the request is served by kthreadd, which forks the new thread on its behalf. Its first act is to make itself a clean template, since every thread it creates inherits its state: it ignores all signals, allows itself every memory node, exempts itself from the freezer used during suspend, pins itself to the root control group, and binds itself to the CPUs that are not reserved for isolated workloads. This centralization gives all kernel threads a common parent and a clean creation path, which is why a process listing shows so many kernel threads (shown in brackets) descending from PID 2.

kernel_init (process 1) meanwhile carries the boot to completion. After waiting for kthreadd to be ready, it runs kernel_init_freeable, which performs the initialization that must happen in process context rather than during the single-threaded start_kernel. It first permits allocations that may block, since the scheduler can now put a waiting task to sleep, and lets workqueue workers start running the work queued since workqueue_init_early. It runs the early initcalls, starts the lockup detector, and then brings the other CPUs online with smp_init (kernel/smp.c): an idle task is forked for each CPU, the CPUs are started by the mechanisms of §5.3, and the log reports "Brought up 1 node, 8 CPUs" or the like. Once every CPU is running, sched_init_smp builds the scheduler's load-balancing domains and releases process 1 from the boot CPU, and page_alloc_init_late waits for any deferred memory-map initialization (§6.1) to finish.

Then comes do_basic_setup, the heart of the remaining boot. It first calls driver_init (drivers/base/init.c), which creates the skeleton of the driver model—devtmpfs, the device, bus, and class hierarchies, the platform and auxiliary buses, and the device objects for memory blocks, NUMA nodes, and CPUs—so that drivers have somewhere to register. Then it runs any C++-style constructors that coverage and sanitizer tools require and calls do_initcalls, which invokes the initcalls—the mass of driver and subsystem initialization functions registered throughout the kernel (§6.2)—thereby probing and binding drivers to the hardware discovered earlier. With the initcalls done, kernel_init_freeable runs any built-in KUnit tests, waits for the initramfs to finish unpacking, opens the console, and decides where the root filesystem comes from (§7.3). When it returns, and once every asynchronous initialization function has finished, the kernel is fully up: every CPU is running, every built-in driver is initialized, and the root filesystem is available. All that remains is to hand control to user space.

It is worth being precise about what a kernel thread is. A kernel thread runs only in kernel mode and has no user address space of its own—its mm pointer is null, and it simply borrows the address translation of whatever process ran before it—so it can never fault into user code the way an ordinary process can. Such threads are marked with the PF_KTHREAD flag and are created through the kthread_create family of helpers, which do not fork directly but enqueue a request that kthreadd services from its kthread_create_list (kernel/kthread.c), which is exactly why process 2 must exist first. On top of these sit higher-level forms: kthread_run creates and starts a thread in one call, a kthread_worker gives one thread a queue of work items, and the per-CPU threads such as ksoftirqd and migration are registered once with smpboot_register_percpu_thread and then created, parked, and unparked automatically as CPUs come and go. The kernel threads that remain—visible in a process listing with bracketed names such as [kworker/0:1] or [ksoftirqd/0]—are the workers that carry out deferred and asynchronous kernel work for the life of the system.

Process 1 is the exception that proves the rule. It too runs only kernel code until it executes init, and with no address space of its own, but it is destined to shed its kernel nature and acquire a user address space, which is the subject of the next subsection. Until Linux 5.19 it was created as an ordinary kernel thread with PF_KTHREAD set, and kernel_execve had to strip the kernel-thread state from it on the way to user space—an awkward transition that caused a use-after-free bug. Since 5.19 rest_init creates it with user_mode_thread (kernel/fork.c), which runs a kernel function in a new task without marking it a kernel thread at all; the user-mode helpers through which the kernel starts programs such as modprobe are created the same way.

The Handoff to User Space

The last thing kernel_init does is stop being a kernel function and become a user program. First it releases the memory that was only needed during boot. With system_state set to SYSTEM_FREEING_INITMEM, it lets kprobes, ftrace, and kgdb forget any references into the init sections, frees the bootconfig data, and calls free_initmem, which reclaims the kernel's __init code and data—all those one-time initializer functions—returning it to the page allocator and reporting "Freeing unused kernel image (initmem) memory" in the log, which is why the kernel's resident footprint shrinks once boot completes. Right after it, mark_readonly write-protects the kernel's text and read-only data, including the static-key tables that are never modified after boot, and, with CONFIG_DEBUG_WX, scans the kernel's page tables to confirm that no page is both writable and executable—one of the hardening layers §4.3 noted KASLR works alongside. On x86, page-table isolation then copies the now-final kernel mappings into the user-mode page tables. The state becomes SYSTEM_RUNNING, RCU stops the expedited grace periods it uses to speed boot, and any sysctl. settings given on the command line (since 5.8) are written to their /proc/sys files. Then it executes the user-space init program by calling kernel_execve, the in-kernel entry to the execve machinery of Chapter 20, logging "Run /sbin/init as init process" as it does. This is the same exec that replaces any process's image, applied here to process 1: it acquires its first user address space, that of the init binary, but the process identity—PID 1—survives, exactly as Chapter 20 described.

Which program becomes init is chosen with care. Before kernel_init gets that far, kernel_init_freeable has waited for the initramfs of §1.2 to be unpacked into the root filesystem (by populate_rootfs, init/initramfs.c, an initcall whose work runs asynchronously, as §1.3 described) and checked whether it contains an init program; if it does not, prepare_namespace (init/do_mounts.c) mounts the real root named by root= instead. That function waits for device probing to finish (and, with rootwait, for the root device to appear), mounts the root filesystem, mounts devtmpfs on its /dev, and makes it the root of the process tree. Through 6.x it did that by moving the new mount over / and calling chroot, leaving the empty rootfs underneath; since 7.0, with rootfs mounted above nullfs (§1.3), it performs a real pivot_root and detaches rootfs, logging "VFS: Pivoted into new rootfs".

kernel_init then tries, in order, the ramdisk's /init (or the path given by rdinit=), logging an error and moving on if it cannot be executed; the program named by init=, panicking if that one fails rather than quietly substituting another; a configured default (CONFIG_DEFAULT_INIT); and then the classic locations /sbin/init, /etc/init, /bin/init, and finally /bin/sh, panicking with "No working init found" only if none can be executed. On virtually every modern distribution the winner is systemd, installed as /sbin/init, which takes over as the user-space process manager—mounting filesystems, starting services, and eventually presenting a login prompt. When an initramfs is used, the first init is usually systemd or a script inside the initramfs, which mounts the real root itself and then executes the real root's init, still as PID 1. From this moment the kernel runs only in response to user space: through system calls, interrupts, and faults. The bootstrap is complete, and the system the rest of this book describes is fully alive. The user-space init inherits a deliberately spartan environment, and it keeps two special responsibilities for the rest of the system's life. Its initial state is minimal: the kernel passes it a fixed argument and environment vector—argv[0] set to the program's own path, and a couple of variables such as HOME=/ and TERM=linux (init/main.c), plus whatever unclaimed command-line words §1.3 described—and opens /dev/console as its standard input, output, and error so that its earliest messages have somewhere to go. From there it is on its own to mount the real filesystems, read its configuration, and start everything else. Its two enduring duties come from its position at the root of the process tree. First, PID 1 is the reaper of orphans: when any process's parent exits before it does, the orphan is reparented to init, whose job is to reap it when it terminates so that no zombie lingers forever. Since 3.4 a process can volunteer for part of that job by declaring itself a child subreaper (PR_SET_CHILD_SUBREAPER): orphans are then reparented to their nearest subreaper ancestor instead, which is how service managers, including systemd's per-user instance, keep track of daemons that double-fork. Second, PID 1 is irreplaceable. The kernel protects it by delivering to it only the signals it has installed handlers for, so not even SIGKILL sent by another process can stop it, and if it ever exits anyway the kernel has no one to reparent to and deliberately panics with the message "Attempted to kill init!" (kernel/exit.c). The init of a PID namespace inherits the same role inside its container (Chapter 25), where its exit kills the namespace rather than the machine. The humble boot thread that began as process 0 has, through process 1, produced the one process the kernel cannot live without.

Alternative and Auxiliary Boot Paths

The path traced so far—firmware to loader to kernel to init—is the common case, but several related facilities deserve mention because they either aid that path or replace part of it. The early console makes the otherwise silent opening moments of boot observable (§8.1). kexec lets a running kernel boot another directly, skipping firmware entirely, and its safety-critical application, kdump, uses it to capture the memory of a kernel that has crashed (§8.2). The newest of them, Kexec HandOver and the Live Update Orchestrator, extend kexec so that chosen memory, and eventually whole devices, survive the jump from one kernel to the next (§8.3). And resuming from hibernation is a boot that runs every stage of this appendix only to discard the result and return to a kernel saved on disk (§8.4). Kexec and kdump arrived in 2.6.13, and the live-update machinery only in the last few releases before 7.0.

The Early Console

For most of the boot sequence described in this appendix, the ordinary console is not yet available: console_init runs well into start_kernel, and the full driver-based consoles come up later still, during the initcalls. Anything that goes wrong before then would, by default, be invisible. The early console exists to close this blind spot. Enabled by the earlycon (or, on x86, the older earlyprintk) kernel command-line parameter, it wires kernel log output to a simple, directly programmed device—typically a serial UART or the UEFI framebuffer—very early in boot, long before the normal console infrastructure is ready. Both parameters are early parameters (§1.3), parsed by parse_early_param inside setup_arch (§6.1), so on ARM64 the early console starts as soon as the device tree has been mapped and on x86 shortly after the memory map is known. This is indispensable for diagnosing failures in setup_arch or the early initializers, where a hang would otherwise produce no output at all, and it is the modern equivalent of the boot messages a 2.6-era PC took for granted on a directly attached display.

The generic earlycon mechanism (drivers/tty/serial/earlycon.c, since 3.16) is table-driven. Each serial driver that can serve as an early console declares a small setup routine with EARLYCON_DECLARE, or with OF_EARLYCON_DECLARE if it should also match a device-tree compatible string; the macros place an entry in the __earlycon_table linker section, the same trick the initcalls use (§6.2), and about a hundred such entries exist in 7.0. A parameter such as earlycon=uart8250,mmio32,0xfe215040,115200n8 names the entry, the register access method, the physical address, and the line settings; the kernel maps the registers through a fixmap slot (FIX_EARLYCON_MEM_BASE), because the ordinary ioremap machinery is not yet available, and logs which device it chose. The console= parameter accepts the same syntax as an alias, and earlycon=efifb draws text directly onto the framebuffer UEFI's graphics protocol left behind, the natural choice on laptops without a serial port. x86's older earlyprintk (arch/x86/kernel/early_printk.c) predates the generic code and still offers destinations it lacks: legacy VGA text memory, a serial port by name or I/O address, a PCI serial card, the USB 2.0 debug port, the xHCI debug capability, and the Xen console, with a keep option that keeps it running after the real console appears.

Mechanically, the early console cooperates with the kernel's log buffer to lose nothing. Every printk from the very first message is stored in an in-memory ring buffer—a static array sized by CONFIG_LOG_BUF_SHIFT, enlarged early in boot if log_buf_len= asks for more, and lockless since 5.10—whether or not any console is registered; the early console is simply the first consumer able to drain that buffer to a device. It registers as a boot console, flagged CON_BOOT (kernel/printk/printk.c) and announced in the log as a "bootconsole", and when the real, driver-based console for the same device comes up later the kernel replays any pending messages to it and unregisters the boot console, so the log is continuous and not doubled. The keep_bootcon parameter suppresses that hand-over for debugging the real console itself, but a boot console whose code lives in init memory is removed regardless by a late initcall, with a warning, before free_initmem (§7.3) can pull the code out from under it. Boot consoles always use the legacy, console-lock-based printing path, which in most configurations prints synchronously in the context of the printk caller; since 6.12, real consoles whose drivers adopt the new non-blocking console interface instead print from a dedicated kernel thread, which is right for a running system but would be wrong for a boot that may hang on the very next instruction.

On systems where the administrator cannot easily guess the serial port, firmware can name it for the kernel—through the ACPI SPCR table on servers or the device tree's stdout-path property on embedded systems—so that a bare earlycon with no arguments still finds the right UART. A few further parameters make the early log more useful still: ignore_loglevel prints every message regardless of its priority, initcall_debug times each initcall (§6.2), and boot_delay= slows the output so that it can be read on a screen. The net effect is that the boot's earliest and most failure-prone moments become as observable as its later ones.

kexec and kdump

kexec is a facility that lets a running Linux kernel load and boot another kernel directly, bypassing the firmware, boot loader, and all of the early hardware initialization this appendix has described. Because it reuses the already-initialized machine and jumps straight into the new kernel's entry code, it can be dramatically faster than a full reboot—valuable for servers where firmware initialization takes minutes—and it decouples kernel updates from the firmware boot path. In effect kexec turns the running kernel into the boot loader for its successor. Using it takes two steps: a tool such as kexec from kexec-tools loads the new kernel, initramfs, and command line in advance, and a later reboot system call with LINUX_REBOOT_CMD_KEXEC—issued by kexec -e or by systemctl kexec after an orderly shutdown of user space—starts it. Both require CAP_SYS_BOOT, and the one-way sysctl kernel.kexec_load_disabled lets a system forbid further loads once it has staged the image it wants.

The mechanism has two forms. The original kexec_load system call (kernel/kexec.c) has a user-space tool stage the new kernel and initrd as a set of memory segments, which the kernel copies into place at reboot time; the newer kexec_file_load (kernel/kexec_file.c, 3.17 on x86 and 5.0 on ARM64) instead hands the kernel file descriptors and lets the kernel parse the image itself—a bzImage on x86, an Image on ARM64—and, crucially, verify its signature, extending the Secure Boot chain of trust across a kexec rather than breaking it (§1.1). With CONFIG_KEXEC_SIG_FORCE, or when the kernel is in lockdown, an image that fails verification is refused, and lockdown forbids the unverifiable kexec_load outright. Because the kernel builds the new kernel's environment itself under kexec_file_load, it also fills in what a boot loader would: on x86 a fresh boot_params with the command line, initrd location, and setup_data records (§3.2), on ARM64 a copy of the current device tree whose /chosen node is rewritten with the new command line, initrd range, and fresh kaslr-seed and rng-seed values, so the successor is randomized afresh (§4.2).

In both cases the switch happens in stages. kernel_kexec (kernel/kexec_core.c) first behaves much like an ordinary reboot: it runs the reboot notifiers and every driver's shutdown method so that devices stop DMA and interrupts, moves itself to the boot CPU, logs "Starting new kernel", and calls the architecture's machine_shutdown, which on x86 stops the other CPUs and returns the interrupt controllers to their boot-time mode and on ARM64 takes the other CPUs offline through PSCI (§5.3), treating any CPU that cannot be stopped as a fatal error. machine_kexec then jumps to a small architecture-specific routine (arch/x86/kernel/relocate_kernel_64.S, arch/arm64/kernel/relocate_kernel.S) that copies the staged segments to their final addresses, possibly over memory the old kernel was using. On x86 this runs from an identity-mapped control page; on ARM64, since 5.16, the copy runs with the MMU still on through a temporary copy of the linear map, which is far faster, and only then does the routine turn the MMU off and, if the kernel was booted at EL2, return to EL2 so the new kernel finds the CPU as firmware would have left it. On x86 control then passes to the purgatory, a tiny standalone program loaded with the new kernel, which checks a SHA-256 digest of the segments (arch/x86/purgatory/purgatory.c) before jumping on; ARM64's kexec_file_load needs no purgatory and goes straight to the new image. Either way the new kernel is entered at an ordinary entry point—the bzImage's 64-bit entry on x86, primary_entry on ARM64 (§5)—from software rather than firmware. What it inherits is exactly what a boot loader would pass, plus, on x86, the record of UEFI runtime mappings that lets it keep calling the same firmware services (§2.4); devices, however, are not reset by firmware, so drivers must cope with hardware that a previous kernel configured.

Its most important use is kdump, the crash-dump mechanism. A production kernel can reserve a region of memory—set aside during setup_arch (§6.1) by the crashkernel= command-line parameter—and pre-load a small capture kernel into it with kexec (kexec -p, or kexec_file_load with the KEXEC_FILE_ON_CRASH flag). The reservation can be a fixed size, a size that scales with installed memory (crashkernel=1G-64G:256M,64G-:512M), or a block above 4 GiB with a smaller companion below it for 32-bit DMA (,high and ,low); since 6.17, on x86 and PowerPC, an additional ,cma portion can be lent to the running system for movable pages, at the price of a less complete dump. If the main kernel then panics, instead of simply hanging or rebooting it calls __crash_kexec (kernel/crash_core.c), which saves the panicking CPU's registers, stops the other CPUs with NMIs or IPIs and records their registers too, and jumps into the capture kernel—skipping the orderly shutdown, since nothing in a crashed kernel can be trusted. The capture kernel boots in the reserved memory without disturbing the rest of RAM, usually with a single CPU and options such as reset_devices that tell drivers to reset hardware the dead kernel left mid-operation.

The capture kernel learns where the old kernel's memory lies from an ELF header prepared at load time and named by the elfcorehdr= parameter (on ARM64, by the linux,elfcorehdr property in the device tree, alongside linux,usable-memory-range confining the capture kernel to its reservation). It exposes that memory as /proc/vmcore, an ELF core file, and user space saves the image—the vmcore, often filtered and compressed by a tool such as makedumpfile—to disk or over the network for later analysis with the crash utility. Those tools find their way through the dead kernel's data with the help of the vmcoreinfo note (kernel/vmcore_info.c), which records symbol addresses, structure sizes and offsets, the page size, and the KASLR offset (§4.2). Recent releases have filled in the remaining gaps: since 6.6 the crash ELF header is updated in place when CPUs or memory are hot-plugged, rather than reloaded from user space, and since 6.16 the keys of an encrypted dm-crypt volume can be handed to the capture kernel so that it can write the dump to an encrypted disk.

Kexec HandOver and Live Update

An ordinary kexec deliberately forgets everything: the new kernel takes over the machine as if from firmware, and whatever the old kernel held in memory is lost. Kexec HandOver (KHO, kernel/liveupdate/kexec_handover.c, since 6.16) changes that for state that is chosen in advance. A subsystem preserves memory by marking pages or folios for hand-over and describing them in a flattened device tree that KHO builds alongside the new kernel; the format of each subsystem's description is a versioned ABI between the outgoing and incoming kernels (include/linux/kho/abi). kexec_file_load passes the location of that tree to the new kernel as a SETUP_KEXEC_KHO setup_data record on x86 or as linux,kho-fdt and linux,kho-scratch properties under /chosen on ARM64, and the new kernel reserves the preserved ranges in memblock before its page allocator can hand them out.

The difficulty is that a booting kernel allocates memory long before it can read any description of what to avoid. KHO solves it with scratch regions: physically contiguous ranges, one per NUMA node plus one general region, set aside on the first boot (sized automatically or by kho_scratch=). The incoming kernel is loaded into them and confines all of its early memblock allocations to them; while the system runs they are managed as CMA, which admits only movable pages, so no preserved page can ever land there. Every later kernel reuses the same regions, so hand-overs can be chained indefinitely. KHO is enabled with kho=on (or a configuration default), both kernels must be built with it, and in 7.0 it cannot be combined with deferred struct-page initialization (§6.1).

KHO is the mechanism; the Live Update Orchestrator (LUO, kernel/liveupdate/luo_core.c, since 6.19) is the policy built on it. Its target is a kernel update that the workload barely notices—above all a cloud host that must replace its hypervisor kernel while its virtual machines stay in memory and their passed-through devices keep running. User space drives it through /dev/liveupdate: an agent creates named sessions and places in them the file descriptors whose contents must survive, and when it issues the kexec reboot, kernel_kexec first asks LUO to serialize every session into KHO-preserved memory. After the jump, the new kernel's agent opens the sessions by name and retrieves the same objects. In 7.0 the preservable object is a memfd, enough for, say, a cache service to carry gigabytes of data across a kernel upgrade. The hypervisor case also needs KVM, IOMMU, and VFIO state to cross over, which LUO's callback interface is designed to carry but which no 7.0 subsystem yet preserves. LUO is off unless enabled with liveupdate=on. With it, kexec has grown from a fast reboot into a way to replace the kernel underneath a running workload.

Resuming from Hibernation

Hibernation (suspend-to-disk) writes a snapshot of memory to swap and powers the machine off. Waking from it is a boot in every sense this appendix has used: firmware, boot loader, decompressor, architecture startup, start_kernel, and the initcalls all run exactly as before, in a fresh kernel that knows nothing of the saved system. Only near the end does that kernel discover the snapshot—the hibernation image—and abandon itself in favor of the kernel recorded there. The check happens in software_resume (kernel/power/hibernate.c), called either from a late initcall, after every built-in driver has probed but before process 1 executes init (§7.3), or, when the swap device is only reachable after an initramfs has assembled it, when the initramfs writes the device number to /sys/power/resume. The resume= parameter names the swap device (with resume_offset= for a swap file), and noresume ignores any image, as when the snapshot is suspected stale.

Restoring is the reverse of saving. The boot kernel reads the image header, checks that its compression algorithm (LZO, or LZ4 since 6.9) is available, freezes its own user space and kernel threads, and reads the saved pages, loading each one straight into its original frame if the boot kernel is not using that frame and otherwise into a spare frame from which it must be copied later. It then quiesces its devices, takes the other CPUs offline, and calls swsusp_arch_resume, which copies the remaining pages to their original frames using code placed in a "safe" page that the copy will not overwrite—on x86 core_restore_code (arch/x86/power/hibernate_asm_64.S) running on temporary page tables, on ARM64 a routine running on a temporary copy of the linear map that also restores EL2's hypervisor stub. The last instruction jumps into the restored kernel, where control reappears inside the function that took the snapshot, as if it had just returned; that kernel resumes its devices and thaws user space, and the boot kernel's entire existence is overwritten without a trace.

The two architectures differ in how much the boot kernel must resemble the image kernel. The generic code rejects an image saved with a different amount of memory and, unless the architecture supplies its own header check, one from a different kernel version; x86_64 and ARM64 both supply one. x86 records the physical address of the image kernel's own restore code and a checksum of the firmware memory map, so a different kernel can perform the restore provided the memory map is unchanged; this is also why KASLR, which places the two kernels at different addresses, poses no problem. ARM64 insists that the image was written by the identical kernel build and brings up the very CPU that took the snapshot before jumping. Security limits the facility too. A hibernation image is unsigned kernel memory read from disk, so hibernation is disabled when the kernel is locked down (since 5.4), as distribution kernels typically arrange under Secure Boot; it is also unavailable while secret memory areas or CXL memory are in use, and nohibernate disables it outright. Hibernation thus closes this appendix on the same theme as kexec and kdump: in modern Linux, even the act of starting a kernel is something the kernel itself has learned to do, whether that means booting a successor, preserving a dying kernel's memory, or bringing a sleeping one back to life.

Summary

This appendix retraced the oldest story in the book—how a computer goes from powered-off silence to a running Linux system—for the hardware and kernel of today. The journey is a relay of ever more capable stages, each building just enough of the world for the next and then stepping aside. Firmware, now UEFI rather than the BIOS, initializes the platform, describes the hardware through ACPI or a device tree, and locates something to boot—and, unlike the BIOS, stays partly resident afterward, as UEFI runtime services and as the SMM or EL3 code that runs beneath the kernel. A boot loader, or increasingly the kernel's own EFI stub, loads the kernel image and initrd and hands over according to an architecture-specific boot protocol—a versioned header, the zero page, and its setup_data records on x86, a register convention and a device tree on ARM64—passing along the command line, a random seed, and a record of what was measured. The kernel is unpacked—by its own decompressor or, on x86 EFI boots, by the stub itself—at a randomized address, and once running it randomizes much of the rest of its address space as well. Architecture-specific entry code—climbing out of real mode on x86_64, descending through exception levels on ARM64—then builds the first page tables, switches the CPU into its final mode, and calls start_kernel, a path each secondary CPU later retraces in shortened form.

From start_kernel on, the boot is portable. Once setup_arch has turned the firmware's description into memblock, page tables, and a list of CPUs, start_kernel initializes the core subsystems in dependency order, on one CPU and with interrupts off until the scheduler, timers, and interrupt controllers exist, and leaves everything else to the table-driven initcalls. Its last call, rest_init, creates the first processes. Process 0 becomes the boot CPU's idle task; process 2, kthreadd, becomes the parent of every kernel thread; and process 1—a user-mode thread rather than a kernel thread since 5.19—starts the other CPUs, runs the initcalls that bind drivers to the devices the firmware described, finds its root filesystem in the initramfs or on the device root= names, frees the kernel's init memory, and executes init, after which the kernel runs only on behalf of user space. Beside this main path run the facilities of §8: the early console that makes the first moments observable; kexec, which lets one kernel boot another, and kdump, which uses it to capture a crashed kernel's memory; Kexec HandOver and the Live Update Orchestrator, which carry chosen memory across that jump; and resume from hibernation, a full boot that ends by handing the machine back to a kernel saved on disk.

The larger lesson mirrors the one Chapter 20 drew about running a program: how much of modern startup is shaped by portability, security, and structure. Booting Linux 2.6.11 on a PC was a single architecture's tour through BIOS, real mode, and a fixed-address kernel. Today two very different architectures share one kernel by isolating their differences beneath a common C entry point; the kernel randomizes its own load address, and much of the rest of its address space, just as it randomizes every process; each stage can cryptographically verify the next, so a signed chain of trust reaches from firmware to the running kernel; firmware hands over a structured description of the machine rather than leaving the kernel to probe; and the kernel has learned to act as its own boot loader and even to boot its own successor, carrying chosen memory across the jump when asked. Table A-4 collects these shifts. Yet the essential shape is unchanged from Linux 2.6 and from the earliest Unix: a chain of stages, each bootstrapping the next, ending in process 1 executing init—the moment the kernel finishes building the world and steps aside to run it.
