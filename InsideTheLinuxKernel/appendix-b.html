Chapter 1 introduced modules as Linux's way of gaining many of the structural advantages of a microkernel—optional, replaceable components—without paying the performance cost of running them as separate processes. A module is a piece of kernel code, compiled separately, that can be loaded into and unloaded from a running kernel on demand, executing in kernel mode with full access to the kernel's data structures once it is linked in. This appendix examines how that mechanism works in Linux 7.0.12, roughly in the order a module encounters it. It begins with what a module is—how one is built, the build-time choice between built-in and modular code, and the two jobs, linking and lifetime management, that the loader must perform (§1)—and then dissects a module's anatomy: the struct module descriptor, the typed memory regions the loader carves out for code and data, and the .modinfo metadata that describes it (§2). Next come the symbols that bind module and kernel together—exports, namespaces, and the version checksums that guard binary compatibility (§3)—and the system calls and states through which a module is loaded, reference-counted, and removed (§4). The kernel's defenses follow: cryptographic signatures, in-kernel decompression, and the taint flags that record anything it cannot vouch for (§5); then the machinery that loads modules automatically when hardware or a feature calls for them, and the parameters that configure them (§6); and finally the infrastructure that has turned modules from a device-driver packaging convenience into a general vehicle for extending the kernel, contributing tracing hooks, test suites, and BPF type information to other subsystems, and even delivering live patches for the running kernel itself (§7). Where Linux 2.6.11 had a simpler world of insmod and a single kernel/module.c, the 7.0 module subsystem lives in its own kernel/module/ directory, takes its memory from the same allocator that serves BPF and kprobes, collapses concurrent requests to load the same file into one, accepts post-quantum signatures, and loads modules written in Rust (Chapter 26) through the same path as C ones; this appendix follows those changes throughout.

What a Module Is

Before examining the machinery, it is worth being clear about what a module is, what it is good for, and what the kernel must do to support it. A module is not a program in the ordinary sense—it has no main, is never a process, and cannot run on its own. It is a relocatable object file—an ELF file of type ET_REL, which is the first thing the loader checks—that, once loaded, becomes an extension of the kernel: its code runs in kernel mode, shares the kernel's address space, and calls kernel functions directly. This section first follows a module from source file to .ko, then examines the decision of whether to build code as a module at all (§1.1) and the two fundamental jobs the kernel's module loader must perform to make loadable code safe (§1.2).

The design tension modules resolve is the one Chapter 1 framed as monolithic versus microkernel. A microkernel gains flexibility by running subsystems as separate, isolated servers that communicate by message passing—at the cost of crossing a protection boundary on every interaction. Linux keeps the performance of a monolithic kernel, where every subsystem shares one address space and calls another directly, but recovers much of the microkernel's modularity by letting those subsystems be loaded and unloaded at run time rather than compiled in permanently. The price of that bargain is that a module, once loaded, enjoys no isolation whatsoever: it runs with full kernel privilege and can touch any kernel data structure, so a buggy module can corrupt the whole system and a malicious one can own it. That absence of isolation is precisely why the later sections devote so much attention to a module's provenance—its license, its signature, its version compatibility—for the kernel's only real defense is to be careful about what it agrees to load in the first place.

Concretely, a module begins as ordinary kernel C—or, since Linux 6.1, Rust (Chapter 26)—with two distinguished entry points: module_init names the function to run when the module is loaded, and module_exit the one to run before it is removed (include/linux/module.h). A license declaration is mandatory—since Linux 5.11 the build fails for any module that omits MODULE_LICENSE—and since 6.5 a missing MODULE_DESCRIPTION draws a warning. The kernel's build system, Kbuild, compiles each object named on an obj-m line (a module built from several files lists its parts in a foo-y line) and then runs the modpost tool over the results. modpost checks every module's imports against the exports of vmlinux and of the other modules, and writes a small generated source file, foo.mod.c, that defines the module's descriptor—a struct module named __this_module, placed in the .gnu.linkonce.this_module section where the loader will look for it—together with the module's export table, version CRCs, device aliases, and list of the modules it depends on. The final link (scripts/Makefile.modfinal) combines foo.o, the compiled foo.mod.o, and a shared .module-common.o carrying the version-magic string (compiled once per build rather than once per module since Linux 6.12) under the linker script scripts/module.lds, and the result is foo.ko. Finally, make modules_install copies the .ko files under /lib/modules/release and runs depmod to build the index files that §6 relies on. A driver maintained outside the kernel tree is built the same way, against an installed kernel's build directory, with make -C /lib/modules/$(uname -r)/build M=$PWD.

To Be a Module or Not to Be

When a kernel developer adds new functionality, they face a basic choice: compile it as a module, or statically link it into the kernel image. As a rule, code that can be a module is written as one. Because modules load on demand, the kernel image stays small and boots quickly, carrying only what a given machine actually needs; the thousands of drivers a distribution ships sit as .ko files on disk, and only the few matching the hardware present are ever loaded. Nearly every higher-level component—filesystems, device drivers, network protocols, executable-format handlers—can be built modular, which is why a stock distribution kernel is a small core surrounded by a large library of loadable parts.

Some code, however, must be linked statically. The classic reason is that a module cannot change a data structure or a piece of machine code that the statically linked kernel has already fixed in memory. Code that must add a field to task_struct, or replace the page allocator, cannot be a module: the rest of the kernel was compiled against the original definitions and would not see the change. There is also a deliberate policy dimension. Some core facilities are kept non-modular precisely so that they cannot be supplanted by a proprietary binary-only replacement—a software-freedom decision rather than a technical one, enforced through the license and symbol machinery of §3 and §5. The practical upshot is that the module boundary falls where code can be cleanly added or removed at run time without disturbing the kernel's fixed foundations.

In practice the choice is expressed directly in the kernel's configuration system, where most components are tristate: each can be built into the kernel image (=y), built as a loadable module (=m), or omitted entirely (=n). The core scheduler and the page allocator are not optional at all, and features that reshape the core kernel rather than plug into it—SMP support, swapping, the networking core—are offered only as plain booleans, on or off. A crucial point, and the reason modules are chosen so freely, is that building a component as a module costs almost nothing at run time: once loaded and relocated, its functions are called exactly as if they had been compiled in, with none of the boundary-crossing overhead a microkernel's separate servers would incur. The one real caveat is bootstrapping. A driver needed to reach the root filesystem itself—the disk or storage controller—cannot be an ordinary module sitting on that very filesystem, so it is either built in or placed in the initramfs that Appendix A described, the small early root image from which such modules are loaded before the real root is mounted.

The third state is itself switchable. The MODULES option (kernel/module/Kconfig) carries Kconfig's special modules attribute, and in a kernel configured without it every tristate collapses to a boolean—there is no m to choose. The dependency rules respect the same hierarchy: an option that depends on another set to m can itself be only m or n, because code linked into the kernel image cannot call into a module that might never be loaded. Linux 7.0.12 declares nearly twelve thousand tristate options. Choosing y does not erase a component's identity as a module, either. The same source serves both builds: compiled in, module_init becomes an ordinary device-level initcall that runs during boot (Appendix A, §6.2), and module_exit is discarded, because built-in code can never be removed. The build records every built-in "module" in modules.builtin, with its metadata in modules.builtin.modinfo, so that modprobe treats a request for a built-in driver as already satisfied, and the component's parameters are set on the kernel command line as name.param=value and, like a loaded module's, appear under /sys/module/name/parameters (§6.3).

At the far end of the spectrum, a system may decline to load modules at all. Building with CONFIG_MODULES disabled removes the loader and its system calls from the kernel entirely, a choice favored by small embedded systems and hardened appliances whose hardware never changes. A general-purpose kernel can reach nearly the same state after boot by loading everything it needs and then writing 1 to the one-way modules_disabled sysctl (§6.1), or can refuse every load from the start with the nomodule boot parameter, which sets the same switch. Short of that, turning off CONFIG_MODULE_UNLOAD lets modules be loaded but never removed (§4.3). Each step trades flexibility for a smaller attack surface, and the choice belongs to whoever builds and administers the system.

The Loader's Two Jobs

To turn a relocatable object file into a working part of the kernel, the loader has two fundamental responsibilities, and almost everything else in this appendix is in service of one or the other. The first is linking: a module refers to kernel functions and variables by name—printk, kmalloc, and so on—and it in turn may offer functions of its own for other modules to call. The loader must resolve every symbol the module imports to the address where that symbol actually lives, and record the symbols the module exports so that later modules can find them. Unlike a user program's dynamic linker, this happens once, at load time: simplify_symbols (kernel/module/main.c) looks up each undefined symbol—waiting up to 30 seconds if the module that exports it is itself still initializing—and a reference that cannot be resolved fails the load with an "Unknown symbol" message, unless it was declared weak, in which case it simply resolves to zero. Once resolved, a module's references are patched into place and, apart from the deliberate run-time code patching described below, never revisited.

Patching happens in two steps, because a relocatable object records its references indirectly. simplify_symbols writes each resolved address into the module's own ELF symbol table; apply_relocations then walks the relocation sections—each entry names a location in the module, a symbol, and a relocation type—and hands them to the architecture's apply_relocate_add (arch/x86/kernel/module.c, arch/arm64/kernel/module.c) to compute and store the final values. The relocation types explain a constraint that shapes where modules live. x86-64 kernel code, modules included, is compiled with -mcmodel=kernel and reaches its callees through 32-bit PC-relative displacements (R_X86_64_PC32 and R_X86_64_PLT32), which span only ±2 GB, so the module area begins immediately above the kernel image mapping and ends where the fixmap begins, keeping every module within 2 GB of the kernel text it calls. ARM64's direct branch instructions reach only ±128 MB, so the kernel first tries to place modules in a 128 MB window that includes its own text and otherwise falls back to a 2 GB window, in which the loader inserts small PLT veneers (module_emit_plt_entry) to bridge the longer distances; both windows are randomized when KASLR is active (arch/arm64/mm/init.c). After relocation, the architecture's module_finalize performs on the module the same code patching the kernel applied to itself at boot: on x86 it applies CPU alternatives, rewrites retpoline and return-thunk call sites, sets up or seals the indirect-branch-tracking landing pads, and registers the module's ORC unwind tables; on ARM64 it applies alternatives, patches in shadow-call-stack instructions when that protection is enabled at boot, and sets up ftrace trampolines. Later still, static keys, ftrace, and livepatch (§7.2) may rewrite module text again, but always through the kernel's controlled text-patching interfaces rather than by revisiting the link.

The second responsibility is lifetime management. A module may be in use—its code executing, its data referenced, or another module depending on it—and unloading it at such a moment would corrupt the kernel. The loader therefore tracks each module through a small set of states and maintains a reference count and a dependency graph so that no module is removed while anything still needs it. A module progresses from MODULE_STATE_UNFORMED (still being set up), through MODULE_STATE_COMING (fully formed, running its initializer), to MODULE_STATE_LIVE (the normal running state), and finally MODULE_STATE_GOING (being removed)—the four values of enum module_state (include/linux/module.h). Figure B-1 shows these states and the operations that move a module between them.

Linux 2.6.11 had only three of these states—LIVE, COMING, and GOING. UNFORMED was added in Linux 3.8 to solve a race: the loader wants to publish a module's name early, so that a second attempt to load the same module finds the first, but must not let anyone resolve symbols against a module whose code is not yet in place. An UNFORMED module is therefore on the module list yet invisible to symbol lookup—find_symbol skips it. The states are also not purely internal. Each transition into COMING, LIVE, or GOING is announced on a notifier chain, module_notify_list, to which a long list of subsystems subscribe: jump labels and static calls patch the new module's code, tracepoints and kprobes track its probe points, and BPF records its type information (§7.1). Two subsystems that must act at a precise moment are called directly by the loader instead: ftrace, which records the module's traceable functions while it is still UNFORMED, and livepatch, which applies any pending patch to it just before it becomes COMING (§7.2). A module whose initializer fails takes a short detour that Figure B-1 compresses into a single arrow: it is marked GOING so that those subscribers can undo their work, and free_module then returns it to UNFORMED while it is torn down, still listed so that a concurrent duplicate load keeps waiting rather than racing it.

It is illuminating to contrast these two jobs with the user-space dynamic linking of Chapter 20. Both take a relocatable object with unresolved references and bind it to symbols provided elsewhere—but the differences are as telling as the similarity. A user program's dynamic linker runs in that program's own private address space and may resolve symbols lazily, the first time each is called; module loading happens once, eagerly, in the single shared kernel address space, and any unresolved symbol aborts the load outright rather than deferring the failure. There is no per-process indirection table, because there is only one kernel: a resolved reference is simply the callee's real address, patched into the caller's code. And lifetime management has no user-space analogue at all. A shared library can be left mapped in a process even after nothing uses it, at worst wasting memory; a kernel module that were freed while still in use would not waste memory but corrupt the kernel, so the loader must actively refuse to remove anything that is still referenced. These two jobs—bind the references, and never free code that is in use—organize everything the rest of this appendix describes.

Anatomy of a Loaded Module

A loaded module is not just its code; it is a bundle of code, data, metadata, and bookkeeping that the kernel tracks through a single descriptor. This section opens that descriptor—the struct module object—then looks at how a module's memory is carved into regions with different protections, and finally at the self-describing metadata every module carries. Together these determine how the kernel sees a module and how it enforces the safety and provenance rules of later sections.

All three have changed substantially since Linux 2.6. The descriptor is no longer a separate allocation but a variable compiled into the module itself and checked byte-for-byte against the running kernel's own idea of its layout; the old pair of core and init areas became seven typed memory regions in Linux 6.4, each sealed with its own page protections; and the metadata, once little more than a license and an author, now carries the facts that drive namespaces, dependencies, and the taints of §5.3. Each of these is decided at build time by the compiler and modpost (§1) and merely checked and honored by the loader, which is why a module built against one kernel's headers cannot simply be dropped into another.

The struct module Object

Every loaded module is represented by a struct module (include/linux/module.h), which is linked into a global list that /proc/modules and lsmod report. The structure has grown large, but its fields fall into a handful of groups: identity and lifecycle, the exported-symbol tables, the module's memory regions, its parameters and init/exit hooks, its reference count and dependency lists, and a long tail of optional features (tracepoints, BTF, livepatch state, and more) present only when the corresponding kernel option is configured. The structure is annotated __randomize_layout, so the compiler may shuffle its field order at build time as a hardening measure—one small sign of how much more security-conscious the module subsystem has become since Linux 2.6.11, whose struct module had no such protection. When CONFIG_RANDSTRUCT is enabled the shuffle is driven by a per-build seed, and a module compiled with a different seed would see a different layout of every randomized structure it shares with the kernel; the seed's hash is therefore folded into the module's version magic (§2.3) so that such a mismatch is refused rather than silently corrupting memory. Many of the optional members, such as the BTF pointers and the livepatch state, correspond directly to the modern uses of modules that §7 describes; others—the jump-label, static-call, tracepoint, ftrace, kprobe, and KUnit tables—record where the subsystems that patch or register a module as it loads (§1.2) should look inside it.

It is worth distinguishing the descriptor from the module it describes, and it is less separate than it looks. The struct module is not allocated by the loader at all: it is the __this_module variable that modpost emitted into the module's own .gnu.linkonce.this_module section (§1), so it arrives inside the .ko already holding the module's name and its init and exit pointers. Because it is compiled from the kernel headers, its size must match the running kernel's sizeof(struct module) exactly, and the loader refuses the module with -ENOEXEC when it does not—one of the first and bluntest compatibility checks. During loading the section is laid out like any other writable data, so the descriptor ends up living in the module's own MOD_DATA region, alongside the code and data that the mem[] array describes; that is why free_mod_mem releases MOD_DATA last—freeing it frees the descriptor too.

All the loaded descriptors are threaded onto one global list, modules, protected by module_mutex for modification and traversable under RCU for the many readers that only inspect it. The reverse question—which module, if any, contains a given address—is asked constantly, by an oops attributing a backtrace frame, by kallsyms, by perf and ftrace, sometimes from NMI context, so the kernel answers it without walking the list. Each module_memory region carries a node in a latched red-black tree, mod_tree (kernel/module/tree_lookup.c, built in whenever perf events, tracing, or CFI are), and __module_address first checks the address against the lowest and highest module addresses ever seen and only then searches the tree, a lookup that is safe from any context without taking a lock. Much of what the descriptor holds is surfaced to user space: /proc/modules (which lsmod formats) prints one line per module—name, total size, use count, the modules that depend on it, a state of Live, Loading, or Unloading, the text base address (shown as zero to readers who may not see kernel addresses), and any taint letters—while the richer /sys/module/<name>/ tree exposes individual fields as files: coresize, initsize, initstate, refcnt, taint, version, and srcversion, the dependents under holders/, the parameters under parameters/, the ELF notes under notes/, and the section addresses under sections/, readable only by root. That tree is how tools inspect and, where permitted, tune a running module, and how a debugger finds where each section landed.

Module Memory Layout

A module's code and data are not placed in one undifferentiated block. Modern kernels divide a module's memory into several regions by their access needs, so that each can be given the tightest possible protection—executable but not writable for code, writable but not executable for data, read-only for constants. The regions are enumerated by enum mod_mem_type (include/linux/module.h), and the module descriptor holds one struct module_memory slot for each in its mem[] array. Table B-2 lists them.

Table B-2. Module memory types (enum mod_mem_type)

This per-type layout, which replaced the older split of a module into just a core section and an init section (the change from module_layout to module_memory came in Linux 6.4), serves two purposes. The first is memory economy: the three INIT regions hold code and data used only while the module's initializer runs—one-time setup routines, probe tables—and are freed once initialization completes, exactly as the kernel frees its own __init code after boot (Appendix A, §7.3). The second is hardening. With CONFIG_STRICT_MODULE_RWX—which on both x86-64 and ARM64 is not even offered as a choice, but always on—the loader applies real page-level protections through the helpers in kernel/module/strict_rwx.c. In complete_formation, before the module enters the COMING state and before any of its code runs, module_enable_rodata_ro makes the read-only regions read-only, module_enable_data_nx makes every data region non-executable, and module_enable_text_rox makes text read-execute; only after the initializer returns does module_enable_rodata_ro_after_init seal MOD_RO_AFTER_INIT. Earlier still, module_enforce_rwx_sections rejects any module that contains a section flagged both writable and executable, since no single protection could honor it. A bug or attack that tries to write to module code, or execute module data, then faults instead of silently succeeding. (Booting with rodata=off leaves the read-only data regions writable, for debugging; text is still sealed and data still non-executable.)

How a module's sections come to be distributed across these regions is worth seeing, because it explains why the separation is possible at all. A relocatable object file is already divided into ELF sections, each tagged with flags describing how it is used, and the loader sorts them by those flags: layout_sections (kernel/module/main.c) places executable sections into the text region, writable ones into data, read-only ones into rodata, and those marked read-only-after-init into their own region, while module_init_layout_section routes any section whose name marks it as initialization-only into the matching INIT variant. Once the regions are sized, module_memory_alloc obtains each one from the kernel's shared execmem allocator (mm/execmem.c)—as EXECMEM_MODULE_TEXT for code and EXECMEM_MODULE_DATA for data, so that every architecture can steer them into the part of the address space it reserves for modules, the same allocator that also places BPF programs, kprobes, and ftrace trampolines. Then move_module copies each section's contents into its assigned region and records the final address, so that the relocation step of §4.2 can patch references to where the code and data actually landed. The reason the whole scheme works is that the compiler and linker have already segregated code from writable data from constants; the loader merely honors that segregation with hardware protections. The MOD_RO_AFTER_INIT region is a nice illustration of the payoff: it holds data that must be writable while the module initializes—function-pointer tables that are filled in once and then never legitimately change—and is sealed read-only afterward, the same technique the core kernel uses for its own __ro_after_init data to deny attackers a writable target.

Several regions have a more varied life than Table B-2 suggests. The module's symbol table is loaded twice over: the full ELF symbol and string tables are placed at the end of MOD_INIT_DATA, while layout_symtab (kernel/module/kallsyms.c) reserves room at the end of MOD_DATA for a trimmed copy holding only the symbols that point into core regions; while the initializer runs, mod->kallsyms points at the full table, and do_init_module switches it to core_kallsyms under RCU just before the init regions go away (a livepatch module keeps every symbol, since its relocations may still need them). The init regions themselves are not freed synchronously: do_init_module queues them on a list that a work item, do_free_init, releases after an RCU grace period, so that a concurrent kallsyms or backtrace walker never touches freed memory. When CONFIG_MODULE_UNLOAD is off, a module can never be removed, so module_init_layout_section sends its exit sections to the init regions too, and they are discarded with them. Two kinds of content live outside mem[] altogether. The module's per-CPU variables are allocated from a small area reserved for modules in the first per-CPU chunk (PERCPU_MODULE_RESERVE, 8 KB on SMP builds), which is why a module with large per-CPU data can fail to load with an allocation error long before memory is short. And MOD_RO_AFTER_INIT collects more than data explicitly marked __ro_after_init: module_mark_ro_after_init also routes the module's __jump_table and .static_call_sites sections there, since both are fixed up during loading and must never change afterward.

The allocator underneath has its own architecture-specific twist on x86-64. Since Linux 6.15 (a first attempt was reverted before 6.13 shipped), a 64-bit kernel with strict module protections takes module text from an execmem ROX cache: execmem maps 2 MB huge pages read-only and executable, pre-fills them with INT3 trap instructions, and carves module text out of them, so that many modules share a few large mappings, relieving pressure on the instruction TLB and sparing the kernel's direct map the fragmentation that per-module 4 KB permission changes cause. Such a region is marked is_rox in its module_memory; execmem_alloc_rw temporarily makes it writable so the loader can copy and relocate code into it, and module_enable_text_rox calls execmem_restore_rox instead of the ordinary set_memory_rox to seal it again. ARM64 keeps using ordinary page-granular vmalloc mappings for modules. Either way, the sizes are visible from user space: coresize and initsize under /sys/module/<name>/ report the total of the core and init regions, and the size column of lsmod is the sum of every region.

Module Metadata

Alongside its code and data, every module carries a block of self-describing metadata in a dedicated .modinfo ELF section. This is where the familiar MODULE_LICENSE, MODULE_AUTHOR, MODULE_DESCRIPTION, MODULE_VERSION, and MODULE_ALIAS declarations end up: each expands, through the MODULE_INFO macro (include/linux/moduleparam.h), into a static, NUL-terminated key=value string deposited in that section—since Linux 6.19 with a compile-time check that the value contains no embedded NUL, which would otherwise silently truncate it. User-space tools read it with modinfo, and the kernel reads it during loading with get_modinfo (kernel/module/main.c). The section is consulted only while loading: the loader clears its SHF_ALLOC flag so that it is never copied into the module's memory regions, and only the pieces the kernel still needs—the version and srcversion strings exposed in sysfs, the imported namespaces, the license-derived taints—are extracted and kept. When the same code is built into the kernel instead, MODULE_INFO prefixes each key with the module's name and the strings collect in the kernel image's own .modinfo, from which the build produces the modules.builtin.modinfo file of §1.1.

Two pieces of this metadata are load-bearing rather than merely informational. The license string (MODULE_LICENSE) is consulted to decide whether the module may use GPL-only symbols and whether loading it taints the kernel (§5.3). The version magic, or vermagic (include/linux/vermagic.h), is a string encoding the kernel release and a set of configuration options that affect binary compatibility, which the loader compares against its own to refuse a module built for an incompatible kernel. In 7.0 the string is the release followed by SMP, preempt or preempt_rt, mod_unload, and modversions when those options are set, an architecture tag (aarch64 on ARM64, nothing on x86-64), and the RANDSTRUCT_ seed hash of §2.1; it is compiled once per build into .module-common.o (§1) and linked into every module. A mismatch is reported as version magic '…' should be '…' and the load fails with -ENOEXEC. One subtlety ties the check to §3.3: when the module carries symbol CRCs, same_magic skips the release field and compares only the option flags, leaving it to the per-symbol checksums—including one for module_layout, a dummy symbol whose CRC stands for the layout of struct module itself—to decide whether a module from a different release is compatible. The module aliases, in turn, are what let the kernel autoload a driver by capability rather than by name, the subject of §6.2; most are not written by hand but generated by modpost from the driver's MODULE_DEVICE_TABLE. Metadata, in short, is not decoration: it is how the kernel decides whether a module may be loaded at all and what it is allowed to do.

The .modinfo section carries more than these headline fields. Among the most useful is srcversion, an MD4 digest of the module's source files that modpost computes at build time (scripts/mod/sumversion.c), which lets a tool confirm that a .ko on disk was built from exactly the sources expected—handy when several similar kernels are installed. The same build step records the module's name, a depends list of the modules whose symbols it imports, and the intree, staging, and test flags that drive the taints of §5.3; on x86 a retpoline entry says the module was compiled with that Spectre mitigation, and the loader warns when a module lacking it enters a kernel that depends on it. (The build ID and build salt, by contrast, travel as ELF notes rather than .modinfo strings.) A driver author can add arbitrary keys with MODULE_INFO—MODULE_FIRMWARE, MODULE_SOFTDEP, MODULE_WEAKDEP (added in 6.11, naming modules that may be requested at run time, which modprobe does not load but initramfs generators can include), and MODULE_IMPORT_NS are all thin wrappers around it—and MODULE_PARM_DESC documents each parameter. All of it is human-readable through the modinfo command, which simply prints the section. Finally, it is worth noting that the version checks driven by this metadata are strict but not absolute—though the escape is narrower than it is often described. A mismatched version magic or symbol CRC is always refused; what an administrator can do is ask, with modprobe --force (or its finer-grained --force-vermagic and --force-modversion), for the module's version records to be ignored, which finit_module receives as the flags MODULE_INIT_IGNORE_VERMAGIC and MODULE_INIT_IGNORE_MODVERSIONS (§4.1). The kernel then treats the module as unversioned, and try_to_force_load admits it only if the kernel was built with CONFIG_MODULE_FORCE_LOAD, off by default, raising TAINT_FORCED_MODULE (§5.3) when it does. The metadata thus gives the kernel firm defaults with a clearly-marked, self-incriminating escape hatch rather than an unconditional prohibition.

Symbols: Exporting and Resolving

The first of the loader's two jobs—linking—rests entirely on symbols: the named functions and variables through which a module and the kernel refer to one another. This section examines the three aspects of that machinery that matter most in a modern kernel: how the kernel and modules deliberately export a controlled subset of their symbols, how symbols can be grouped into namespaces that a user must explicitly opt into, and how symbol versioning guards against loading a module built for a subtly different kernel. Together they turn a flat namespace of addresses into a governed interface.

Each of these rules is enforced twice. modpost, the build step of §1, already knows every export in the kernel and every symbol each module imports, so it rejects most violations—an undefined symbol, a GPL-only symbol in a proprietary module, a missing namespace import—before a .ko is even produced; the loader then repeats the checks against the kernel that is actually running, because a module may be loaded long after, and far from, the build that made it. The machinery has also been rebuilt piece by piece since Linux 2.6: export tables have been generated by modpost rather than by the export macros since Linux 6.5, namespaces arrived in 5.4 and became string literals in 6.13, per-module exports in 6.16, and DWARF-based version checksums in 6.14.

Exporting Symbols

Not every function in the kernel is available to modules. A symbol becomes usable by a module only if it is explicitly exported, with one of the EXPORT_SYMBOL macros (include/linux/export.h). Exporting a symbol ultimately places a struct kernel_symbol record—pairing the symbol's name with its address and namespace—into a special table, and the loader searches those tables to resolve a module's imports. There are two principal forms. EXPORT_SYMBOL makes a symbol available to any module and its record ends up in the __ksymtab section; EXPORT_SYMBOL_GPL places it instead in __ksymtab_gpl and restricts it to modules that declare a GPL-compatible license. (Two variants added in Linux 2.6.17 and 2.6.18, EXPORT_SYMBOL_GPL_FUTURE and EXPORT_UNUSED_SYMBOL, were removed again in Linux 5.12.) When a module is loaded, simplify_symbols walks its unresolved references and calls resolve_symbol (kernel/module/main.c), which uses find_symbol to search first the kernel's own export tables and then those of each already-loaded module, patching each reference to the address it finds. A symbol that is not exported simply cannot be named by a module, which is how the kernel keeps its vast internal namespace private while offering a deliberate, curated interface.

The _GPL distinction is the technical expression of the licensing policy mentioned in §1.1. A module counts as GPL-compatible only if its MODULE_LICENSE is one of six exact strings—"GPL", "GPL v2", "GPL and additional rights", and the "Dual BSD/GPL", "Dual MIT/GPL", and "Dual MPL/GPL" forms (license_is_gpl_compatible, include/linux/license.h); anything else marks it proprietary and sets TAINT_PROPRIETARY_MODULE on it. For such a module resolve_symbol searches with gplok false, so the GPL-only tables are simply invisible to it and a reference to one of their symbols fails as "Unknown symbol"—and modpost has already refused to build it, with the error "GPL-incompatible module foo.ko uses GPL-only symbol", if it was compiled in a kernel tree. Kernel developers can therefore mark an interface as available only to free software, and a proprietary module that tries to use it fails to load. Since Linux 5.9 the rule also closes the obvious loophole of a GPL "shim" module that bridges GPL-only functionality and a proprietary one: inherit_taint gives any module that imports a symbol from a proprietary module the same proprietary taint, so its later GPL-only lookups fail, and refuses the import outright if the importer has already used GPL-only symbols (tracked in using_gplonly_symbols). This is not merely advisory—it is enforced in the resolver—and it is one of the main levers by which the kernel community keeps its core interfaces from becoming the foundation of closed derivative works.

The scale of that curation is worth appreciating. A kernel has hundreds of thousands of functions and variables—all visible to kallsyms for backtraces—yet only a deliberately chosen fraction is ever exported for modules to use: the 7.0.12 tree contains roughly 40,000 export annotations across all its architectures and drivers, of which any one configuration builds a part. How those annotations become tables changed in Linux 6.5. Today an EXPORT_SYMBOL emits nothing but a small record in a discarded .export_symbol section, naming the symbol's license, namespace, and address; modpost reads those records from the object files and generates the real table entries itself—into .vmlinux.export.c for the kernel and into each module's foo.mod.c—using the KSYMTAB_FUNC and KSYMTAB_DATA macros of include/linux/export-internal.h, which also lets it compute the version CRCs of §3.3 and the namespace checks of §3.2 in one place. Each entry goes into its own input section named ___ksymtab+name, and the linker scripts merge them with SORT, so the final tables come out ordered by name and resolution at load time is a binary search (bsearch over cmp_name, kernel/module/main.c) rather than a linear scan, which matters when a module imports hundreds of symbols. On x86-64 and ARM64, which select CONFIG_HAVE_ARCH_PREL32_RELOCATIONS, each struct kernel_symbol (kernel/module/internal.h) stores its value, name, and namespace as 32-bit offsets relative to the entry itself rather than as absolute pointers, halving the table's size on 64-bit machines and sparing a relocatable, KASLR-randomized kernel from having to fix up tens of thousands of entries at boot.

Exports can also be constrained or withdrawn as a whole. When a module is loaded, verify_exported_symbols refuses it with -ENOEXEC if it exports a name that the kernel or another module already exports—modpost catches the in-tree case as "exported twice"—so a symbol always has exactly one owner, and resolve_symbol records each import with ref_module, the dependency link that keeps the owner from being unloaded while the importer is present (§4.3). For an embedded system whose complete set of modules is known, CONFIG_TRIM_UNUSED_KSYMS goes further and drops from the export tables every symbol that no in-tree module uses (with CONFIG_UNUSED_KSYMS_WHITELIST naming any that must stay), shrinking the image, giving the compiler more freedom to optimize, and narrowing the interface an attacker-supplied module could reach. The everyday path is the automatic resolution just described, but the kernel also offers symbol_get for the rare case where code must look up an exported symbol by name at run time and take a reference to the module providing it—used, for instance, when an optional dependency is resolved dynamically rather than at load, and released with symbol_put. Since Linux 6.6 __symbol_get works only on GPL-only exports, so that the dynamic route cannot be used to sidestep the licensing rule above.

Symbol Namespaces

As the number of exported symbols grew into the tens of thousands, a flat export namespace became unwieldy, and a newer mechanism—symbol namespaces, added in Linux 5.4—was introduced to bring order to it. A symbol can be exported into a named namespace with EXPORT_SYMBOL_NS or EXPORT_SYMBOL_NS_GPL, and a module that wishes to use such a symbol must explicitly declare its intent with MODULE_IMPORT_NS (include/linux/module.h), which simply adds an import_ns= string to its .modinfo. If it does not, the loader refuses to resolve the symbol: resolve_symbol calls verify_namespace_is_imported (kernel/module/main.c), which compares the namespace recorded in the symbol's struct kernel_symbol with the module's imports and fails the load with -EINVAL and a message naming the missing namespace. A kernel built with CONFIG_MODULE_ALLOW_MISSING_NAMESPACE_IMPORTS downgrades both this check and modpost's (through its -N flag) to a warning—there is, as the option's own help text admits, no technical reason to insist on the import—but the default is to enforce it.

The purpose is not access control but clarity of dependency. By grouping, say, all the internal interfaces of a subsystem into a namespace, maintainers make it visible—both to reviewers and in the module's own metadata—exactly which modules reach into that subsystem's internals, and they can require a deliberate opt-in before a new caller does so. It is a governance tool layered on top of the export mechanism, turning "this symbol is exported to everyone" into "this symbol is exported to those who explicitly ask for its namespace," and it did not exist in Linux 2.6 at all.

The mechanism is convenient in practice because most of it is automatic. A source file can set DEFAULT_SYMBOL_NAMESPACE (include/linux/export.h) so that all its exports land in one namespace without annotating each, and the enforcement happens as early as the build: modpost checks, while assembling a module, that every namespaced symbol it uses is matched by a MODULE_IMPORT_NS, and fails the build with a message naming the namespace to add if one is missing. A developer can even let the build fix the problem: make nsdeps runs modpost in a mode that records each module's missing namespaces in modules.nsdeps, and the scripts/nsdeps script then inserts the matching MODULE_IMPORT_NS lines into the source files—the tool maintainers used when they first moved existing exports into namespaces. The same imports are recorded in the module's .modinfo (visible as import_ns in modinfo output) and re-checked at load. A representative use is a subsystem that walls off its internal helpers—USB storage, for example, exports its internals into the USB_STORAGE namespace so that only its own sub-drivers, which explicitly import it, may call them—and some namespaces cover widely used cross-subsystem interfaces instead, such as DMA_BUF, which some forty files in the 7.0.12 tree import to share buffers between devices. Well over two hundred distinct namespaces are imported somewhere in the tree, each an otherwise invisible web of dependencies made explicit and reviewable.

Two refinements have arrived recently. Since Linux 6.13 the namespace argument is an ordinary string literal—a module writes MODULE_IMPORT_NS("USB_STORAGE") rather than a bare identifier—which makes namespaces easy to search for and lets the macros be composed. And Linux 6.16 added a narrower form, now spelled EXPORT_SYMBOL_FOR_MODULES(sym, "mods"), for an interface meant for one or two named consumers rather than a whole subsystem: it exports the symbol GPL-only into an implicit namespace spelled module: followed by a comma-separated list of permitted module names, where a trailing * matches a prefix. verify_module_namespace (kernel/module/main.c) lets exactly those modules resolve the symbol without any import declaration, and the loader rejects with -EPERM any module that tries to gain access by naming a module: namespace in MODULE_IMPORT_NS. The memory-management core uses it, for example, to offer filemap_flush_nr to btrfs alone and its task-memory-policy helpers to KVM alone—an export that is, in effect, a private handshake between two named parts of the kernel.

Symbol Versioning

A module is compiled separately from the kernel it will run in, which raises a long-standing hazard: if the kernel's data structures or function signatures have changed since the module was built, loading it could corrupt memory in ways no relocation would catch. Linux guards against this with two complementary checks. The coarser is the version magic described in §2.3: check_modinfo compares the module's vermagic string against the kernel's and, unless they agree on the compatibility-critical options—and, for a module without symbol versions, on the exact kernel release as well—refuses the module. The finer-grained check is symbol versioning, enabled by CONFIG_MODVERSIONS.

Under modversions the build computes, for every exported symbol, a CRC that captures the layout of its arguments and of every type they transitively reference—effectively a checksum of the symbol's binary interface, traditionally produced by the genksyms tool from the preprocessed C source. These CRCs are stored beside the kernel's exported symbols, in the __kcrctab and __kcrctab_gpl tables that parallel the symbol tables entry for entry, and, for the symbols a module imports, in its __versions section. At load time check_version (kernel/module/version.c) compares the two as part of resolving each symbol: if the CRC the module was built against differs from the kernel's current CRC for that symbol, the interface has changed incompatibly, the kernel logs "disagrees about version of symbol", and the module is rejected. A related check, check_modstruct_version, verifies the layout of struct module itself. Together, version magic and per-symbol CRCs let a distribution ship modules that load only on kernels with which they are genuinely binary-compatible, and fail cleanly rather than dangerously otherwise.

The CRCs travel through the build in a way that explains how external modules can be versioned at all. genksyms runs as each object file is compiled and, since Linux 5.19, records its results as #SYMVER lines in the object's .cmd file; modpost collects them, emits the __kcrctab entries with the SYMBOL_CRC macro, writes a __versions array of name and CRC pairs for each module's imports into its foo.mod.c, and dumps every export—CRC, name, owning module, export type, and namespace, one per line—into Module.symvers. That file is the contract an out-of-tree build relies on: make M= reads the kernel's Module.symvers (plus any listed in KBUILD_EXTRA_SYMBOLS for other external modules) to learn the CRCs and namespaces of the symbols it imports, and distributions that promise a stable kernel ABI compare successive Module.symvers files to detect breakage. The struct module check works the same way through a trick: module_layout is an empty exported function whose parameters are pointers to struct module, struct modversion_info, struct kernel_param, struct kernel_symbol, and struct tracepoint, so its CRC changes whenever any of those core loader structures does, and every versioned module carries an entry for it. A symbol for which the module carries no version at all is accepted with a one-time "no symbol version" warning, on the assumption of a broken toolchain rather than a mismatch.

It helps to see why both checks exist rather than one. The version magic is a blunt instrument: it bundles the kernel release with a handful of options that change the calling environment so pervasively that no module built against a different setting can be trusted—whether the kernel is SMP, whether it is preemptible, the module ABI in use. A mismatch there means the module and kernel disagree about fundamentals, so it is refused wholesale. Per-symbol CRCs are the scalpel: they let a module built for one kernel load on a later one as long as every interface it actually touches is byte-for-byte compatible, which is exactly what lets a distribution ship a third-party driver that keeps working across a minor kernel update that changed unrelated internals. The checks are heuristics, not proofs—a behavioral change that leaves every type layout intact would slip past a CRC—but they reliably catch the structural breakages that cause the worst corruption. They can be waived only through the forced load that §2.3 described, which treats the module as unversioned—and, as §5.1 explains, as unsigned—is honored only under CONFIG_MODULE_FORCE_LOAD, and leaves the TAINT_FORCED_MODULE mark behind.

Linux 6.14 reworked how these checksums are produced and stored, largely to make room for Rust. Because genksyms parses C, it cannot compute a CRC for a symbol defined in Rust code; the alternative gendwarfksyms (scripts/gendwarfksyms/), chosen with CONFIG_GENDWARFKSYMS, derives the same type fingerprint from the DWARF debugging information the compiler emits, which works for any language, and a kernel that combines Rust with CONFIG_MODVERSIONS must use it (the RUST option depends on it and selects extended versions). It has requirements of its own—full, unsplit DWARF debug information, and no LTO, since it reads ordinary ELF objects—and, built with KBUILD_GENDWARFKSYMS_STABLE, it honors annotations (sketched in scripts/gendwarfksyms/examples/kabi.h) that let a distribution reserve padding or declare a changed field ABI-neutral, so that its stable-ABI kernels can evolve without changing the CRCs their partners' modules were built against. The classic __versions table, meanwhile, stores each entry as a fixed 64-byte struct modversion_info that leaves room for a name of at most 55 characters—far too short for Rust's mangled symbol names—so CONFIG_EXTENDED_MODVERSIONS adds a variable-length encoding in a pair of sections, __version_ext_names and __version_ext_crcs, which check_version consults in preference to the old table when present. CONFIG_BASIC_MODVERSIONS, on by default, keeps emitting the old table alongside, so that older modprobe and kmod tools can still read a module's versions. Chapter 26 shows how a Rust module is built against this machinery.

Loading and Unloading

With the vocabulary of symbols, memory, and metadata in place, we can follow a module through its life: from the system call that hands the kernel a blob of bytes, through the pipeline that turns that blob into running code, to the reference counting that decides when it may be removed. This section traces the load path in kernel/module/main.c, the largest and most intricate file in the module subsystem, and then the unload path that reverses it.

Much of this path has been rebuilt since Linux 2.6.11. That kernel offered only init_module, and removing a module froze every other CPU with stop_machine so that its per-CPU reference counts could be summed safely. finit_module arrived in Linux 3.8; the option that let rmmod wait for a busy module's users to go away was removed in 3.13; stop_machine left the unload path in 3.19, replaced by a single atomic counter; in-kernel decompression came in 5.17; the loader moved from the single file kernel/module.c into the kernel/module/ directory in 5.19; and since 6.4 and 6.5 the kernel collapses duplicate loads of the same module before they cost any memory. All three system calls involved—init_module, finit_module, and delete_module—first require CAP_SYS_MODULE and fail with -EPERM once the one-way modules_disabled sysctl of §1.1 has been set, and the loader and delete_module both record the module's name in the audit log.

The init_module and finit_module System Calls

User space asks the kernel to load a module through one of two system calls. The original, init_module (kernel/module/main.c), takes the entire module image in a user-space buffer, which copy_module_from_user copies into kernel memory after asking the security modules, through security_kernel_load_data, whether loading from a bare buffer is allowed at all. The newer and now preferred finit_module takes instead a file descriptor for the module file, which must be open for reading, and lets the kernel read the file itself—important because it allows the kernel to check a signature or apply an authenticity policy against the actual file—and it accepts a flags argument. Those flags— MODULE_INIT_IGNORE_MODVERSIONS (1), MODULE_INIT_IGNORE_VERMAGIC (2), and MODULE_INIT_COMPRESSED_FILE (4, since Linux 5.17)—let the caller relax the version checks of §3.3 (honored only in a kernel built with CONFIG_MODULE_FORCE_LOAD, §2.3) or declare that the file is compressed and must be decompressed first (§5.2); any other bit is refused with -EINVAL. Both calls also take a string of parameters, such as "debug=1 max_ports=4", which the loader parses against the module's declared parameters once it is linked (§6.3). Tools such as insmod and modprobe are thin wrappers over these calls—a current kmod's modprobe uses finit_module, and passes the compressed-file flag when /sys/module/compression shows that the kernel can decompress the module's format itself—and almost all of the real work happens in the common back end, load_module, that both invoke.

The reason finit_module is now preferred goes beyond convenience. Because the kernel reads the file itself—through the kernel_read_file path (include/linux/kernel_read_file.h), with the purpose tagged READING_MODULE or READING_MODULE_COMPRESSED—it can subject the load to the same file-based security machinery as any other sensitive read: an LSM can veto it (LoadPin, for instance, admits modules only from the filesystem that supplied the first one), an integrity-measurement policy (IMA) can measure and appraise the file, and kernel lockdown can forbid loading unsigned modules entirely. Passing a buffer, as init_module does, hides the file's identity from those checks, which is why such policies typically refuse init_module outright. The fd-based call also makes concurrent loads cheap. Since Linux 6.5, idempotent_init_module treats loads of the same file as idempotent, keyed on the file's inode: the first caller performs the load, and every concurrent caller for the same inode, rather than reading, decompressing, and allocating its own copy, waits for that load (interruptibly, since 6.11) and returns its result. The motivation was boot on very large machines, where user space could fire the same module request once per CPU and hundreds of simultaneous copies of one module exhausted the kernel's vmalloc space before all but one were thrown away. Either system call returns to user space only after the module's own initializer has run, so a failure inside the module's init propagates all the way back as the error code from insmod or modprobe.

Inside load_module

load_module is where a flat image becomes a live module, and it runs a long, ordered pipeline whose stages mirror the concepts of the previous sections. Its first act, before it trusts a single byte of the image, is to verify the module's signature (module_sig_check, §5.1), which needs only the length of the file and strips the appended signature from it. Only then does elf_validity_cache_copy—split in Linux 6.13 into a series of small checkers for the ELF header, the section table, the string tables, and the symbol table—confirm that every offset and size in the image stays inside the buffer, and record where the interesting sections lie: .modinfo, __versions, the symbol table, and the .gnu.linkonce.this_module copy of struct module (§2.1). early_mod_check then applies the cheap policy tests while the module still exists only as a temporary copy: a name listed in the module_blacklist= boot parameter (Linux 4.8) is refused with -EPERM, check_modstruct_version and check_modinfo compare the version magic, license, and other metadata of §2.3, and a module that is already loaded or loading is turned away before a single page is allocated. Only a module that has passed all of that reaches layout_and_allocate, which assigns its sections to the memory regions of §2.2, allocates those regions, and copies the sections into them.

From there the module is real. add_unformed_module registers it in the UNFORMED state so that concurrent loaders see it, module_augment_kernel_taints applies the taints its metadata calls for (§5.3), its per-CPU area and unload bookkeeping are set up, and the special sections—exports, parameters, exception tables, tracepoints, and dozens more—are located. Then the linking of §3 happens: simplify_symbols resolves every imported symbol, apply_relocations patches the code to its final addresses, and post_relocation sorts the exception table, copies in the initial per-CPU data, builds the module's kallsyms tables, and lets the architecture finish the job in module_finalize (§1.2), after which the instruction cache is flushed—a no-op on x86-64, whose caches are coherent, but essential on ARM64, where instruction fetch need not see freshly written data. With linking done, complete_formation rejects duplicate exports, applies the RWX protections of §2.2, and flips the module to COMING; prepare_coming_module then enables its ftrace call sites, lets livepatch apply any pending patches to it (§7.2), and calls the module notifier chain, any member of which may veto the load. Only now, with the module's code executable, are its parameters parsed—a parameter's setter can be a module function—and its /sys/module directory created, and finally do_init_module calls the module's own initializer and, on success, marks it LIVE—freeing the INIT regions afterward. Figure B-2 shows the pipeline.

Two things about this pipeline are easy to miss but important. The first is concurrency. The duplicate check runs twice: once in early_mod_check, before any memory is committed (since Linux 6.4), and again in add_unformed_module, which publishes the module's name under module_mutex before the expensive work begins. Both use module_patient_check_exists: if an instance of the same name is still UNFORMED or COMING, the newcomer waits on module_wq until that instance either goes live or fails, and then gives up—with -EEXIST if it went live, -EBUSY if it did not, since loading the same failing module again at once would only fail the same way—so two loads of the same code never proceed in parallel. Together with the inode-keyed idempotency of §4.1, this lets a burst of identical requests collapse into one load. The second is failure handling. The pipeline can fail at almost any stage—a bad signature, an unresolved symbol, a notifier veto, an init that returns an error—and load_module's error labels unwind in exactly the reverse order of the setup: a module that had reached COMING is moved to GOING and announced to the notifier chain again so that subscribers can undo whatever they did, the module is unlinked from the module list, and an RCU grace period passes before its memory is released, because kallsyms or a stack unwinder may be reading it concurrently. A rejected load thus leaves no trace beyond a counter: with CONFIG_MODULE_STATS (Linux 6.4), /sys/kernel/debug/modules/stats tallies failed loads and the memory they wasted, a tool for spotting a user space that loads modules it should not.

The last stage, do_init_module, is where the module first runs. It calls any compiler-generated constructors (do_mod_ctors, used by coverage instrumentation), then the module's init function through do_one_initcall—the same wrapper that runs built-in initcalls, so initcall_debug times module initializers too—in the context of the process that issued the system call. A negative return fails the load; a positive one, a common bug, draws a warning and is treated as success. The module then becomes LIVE, the notifier chain hears MODULE_STATE_LIVE, and only now is the KOBJ_ADD uevent for its /sys/module directory sent, so that udev never reacts to a module whose initialization might still fail. Unless the module asked for asynchronous probing—with its own async_probe parameter or, since Linux 6.0, the module.async_probe= default for all modules—the loader next waits in async_synchronize_full for any asynchronous work the initializer started, so that a driver's devices have been probed by the time modprobe returns. Finally it drops the extra reference held during initialization (§4.3), trims init-section entries from the exception table, switches kallsyms to the core-only copy (§2.2), seals the ro_after_init data, and releases the INIT regions. Even that last step has a subtlety: the regions are not freed inline but queued on a lock-free list for a work item, do_free_init (kernel/module/main.c). Kallsyms may still be walking the init symbols inside an RCU read-side section, so the memory may be freed only after a grace period; waiting for one inline would slow every successful load, and an RCU callback will not do because execmem_free must not run in interrupt context, so the work item waits for the grace period and frees the regions in process context instead. The pipeline, in short, is as much about doing nothing harmful when things go wrong as about the happy path Figure B-2 traces.

Reference Counting and Unloading

Removing a module is only safe when nothing is using it, and the kernel enforces this with a reference count and a dependency graph. The count is a single atomic_t, refcnt in struct module, which module_unload_init sets to MODULE_REF_BASE (1) plus one extra reference that the module holds on itself until its initializer finishes; module_refcount, which /sys/module/name/refcnt and lsmod report, subtracts the base. Any code that is about to rely on a module—by calling into it, or by holding a pointer into its data—takes a reference with try_module_get, which fails only once the module has begun to go away (state GOING) or its count has reached zero, and releases it later with module_put (kernel/module/main.c, declared in include/linux/module.h); __module_get is the unconditional form for a caller that already holds a reference. Inter-module dependencies are tracked automatically: when the loader resolves a symbol that one module imports from another, ref_module takes a reference on the provider through strong_try_module_get—which, stricter than try_module_get, also refuses a provider still in COMING with -EBUSY, so no module can bind to one whose initialization has not finished—and records the relationship in a struct module_use linked onto the provider's source_list and the user's target_list. This is why lsmod shows, for each module, both a use count and the list of modules that depend on it, and why the provider's holders/ directory in sysfs holds a link for each dependent. Every get and put also fires the module_get and module_put tracepoints, the usual way of finding out who is pinning a module that refuses to unload.

Unloading runs through the delete_module system call (kernel/module/main.c), the mechanism behind rmmod and modprobe -r. Under module_mutex it applies a fixed sequence of refusals: -ENOENT if no module has that name; -EWOULDBLOCK if other modules depend on it, so that dependents must be removed first; -EBUSY if it is not LIVE—still initializing, or already going; and -EBUSY again if it has an init function but no exit function, since such a module could never undo its own setup and is therefore permanent (marked [permanent] in /proc/modules). Only then does try_stop_module try to subtract the base reference atomically: if any other reference remains, it restores the count and fails with -EWOULDBLOCK, which rmmod reports as "Module foo is in use." The kernel never waits for the count to drain, and no freeze of the other CPUs is needed, because the atomic subtraction itself settles the race with a concurrent try_module_get, which can no longer raise a count that has reached zero. The module then moves to MODULE_STATE_GOING, the mutex is dropped, and the module's exit function runs to undo what its initializer did. The notifier chain hears MODULE_STATE_GOING, livepatch and ftrace release the module, outstanding asynchronous work is flushed, and the module's name and taint flags are remembered as the last unloaded—the [last unloaded: ...] suffix of the module list in an oops. free_module finally removes the sysfs directory, returns the module to UNFORMED while leaving it on the module list so that no second copy can be loaded during teardown, drops the references it held on the modules it depended on, unlinks it and waits for an RCU grace period, and frees its memory. With CONFIG_MODULE_UNLOAD_TAINT_TRACKING (Linux 5.19), a module that had tainted the kernel leaves its name and taint letters behind, in /sys/kernel/debug/modules/unloaded_tainted and in oops reports, so that the cause of a taint does not vanish with it.

All of this bookkeeping is compiled in only when CONFIG_MODULE_UNLOAD is enabled. A kernel built without it can load modules but never remove them: delete_module returns -ENOSYS, every module's exit code is discarded at load (§2.2), and try_module_get and module_put shrink to inline stubs, so the price of every reference taken anywhere in the kernel disappears. It is a trade of the ability to unload for slightly less overhead and a smaller attack surface—a configuration some hardened and embedded systems choose.

In practice, most references are taken not by explicit try_module_get calls but through the owner field that pervades the kernel's callback structures. When a driver registers a struct file_operations, a struct device_driver, or any of dozens of similar objects, it sets their owner to THIS_MODULE—a pointer to the module's own __this_module, or NULL in built-in code, where every get trivially succeeds. Some 4,600 such initializers appear in the 7.0.12 sources, and registration helpers such as platform_driver_register and pci_register_driver are macros that fill in THIS_MODULE on the caller's behalf. The kernel then bumps the module's reference count automatically whenever one of those objects is used—opening a character device, for example, pins the module that owns the cdev and then, through fops_get, the owner of its file operations, failing the open with -ENXIO if the module is already going, and the last close drops the references. This is the everyday mechanism behind the familiar experience that rmmod of a driver whose device is open, or whose filesystem is mounted, fails with "module in use." A kernel thread started by a module has the opposite problem: it must drop its reference to its own module as its very last act, without returning into code that may already have been freed, which is what module_put_and_kthread_exit (so named since Linux 5.17) does. For the situations where an administrator is certain a module is wedged and must go regardless, CONFIG_MODULE_FORCE_UNLOAD enables rmmod --force, which passes O_TRUNC in the system call's flags and bypasses both the reference-count check and the missing-exit check—a dangerous operation that can crash the kernel if the module really is still active, and one the kernel records by raising TAINT_FORCED_RMMOD and declaring lockdep's results unreliable from then on. As with the version and signature overrides, the escape hatch exists, but taking it marks the kernel indelibly.

Trust: Signing, Compression, and Tainting

Loading a module is one of the most powerful things a system can be asked to do: the new code runs in kernel mode, with no isolation from anything. A modern kernel therefore treats the provenance of a module as a first-class security concern, as Linux 2.6 did not. This section covers three related facilities: cryptographic signing, which lets the kernel refuse code it cannot authenticate; compression, which the kernel now unpacks itself; and tainting, the long-standing mechanism by which the kernel records that something unverifiable or non-free has been loaded.

The three facilities act at different moments of the load path of §4, and the order is deliberate. Decompression comes first, in init_module_from_file, before load_module is even called, so that every later check sees the real ELF bytes. The signature check is the very first step of load_module, ahead of any ELF parsing, so when enforcement is on the loader's parser is never exposed to bytes that have not been authenticated. Tainting comes last, in module_augment_kernel_taints, once a struct module exists on which to record the flags. All three have grown up since Linux 2.6. Module signing was merged in Linux 3.7; unsigned modules got their own taint letter, E, in 3.15; kernel lockdown, which ties signature policy to the integrity of the whole kernel, arrived in 5.4; in-kernel decompression came in 5.17, with zstd added in 6.2; the .machine keyring in 5.18; SHA-3 digests in 6.7; and Linux 7.0 itself adds post-quantum ML-DSA signatures while dropping SHA-1 as a signing digest.

Module Signing

A signed module carries a cryptographic signature appended to the end of its file. Read backward from the end, the layout is the marker string ~Module signature appended~ (with a trailing newline), preceded by a 12-byte struct module_signature trailer (include/linux/module_signature.h), preceded in turn by the signature itself: a detached PKCS#7 (CMS) message whose length the trailer's big-endian sig_len field records. The trailer's other fields (algorithm, hash, signer and key-ID lengths) are left over from an earlier format and must now be zero, with id_type set to PKEY_ID_PKCS7; mod_check_sig (kernel/module_signature.c) rejects anything else, because the PKCS#7 message itself names the signer, the key, and the algorithms. Since the signature is simply appended, the file is still a valid ELF object that ordinary tools read unchanged, and modinfo can show the signer, key ID, and digest by parsing the signature in user space. The build tool scripts/sign-file produces it. When a module is loaded, module_sig_check (kernel/module/signing.c) runs before anything else in load_module. It detects the marker, trims it, and calls mod_verify_sig, which peels off the trailer and the signature, shrinking info->len so that the rest of the loader never sees them, and passes the remaining bytes to verify_pkcs7_signature (certs/system_keyring.c). That function rejects a signer whose certificate is blacklisted or on the revocation list, then requires the signature to chain to a key on the .secondary_trusted_keys keyring, which links in the .builtin_trusted_keys compiled into the kernel and, where present, the .machine keyring of keys the platform owner has enrolled. On success info->sig_ok is set; it is later copied to mod->sig_ok, which module_sig_ok reports.

What happens when verification does not succeed depends on why it did not. Only three outcomes count as "no usable signature": the module carries no marker at all (-ENODATA), it was signed with crypto the kernel does not support (-ENOPKG), or it was signed by a key the kernel does not hold (-ENOKEY). For these, policy decides. If signature enforcement is on, through CONFIG_MODULE_SIG_FORCE or the module.sig_enforce boot parameter (queried via is_module_sig_enforced), the module is rejected with -EKEYREJECTED and a notice such as "Loading of unsigned module is rejected". If not, module_sig_check consults lockdown (below), and only if that also permits it does the module load with sig_ok false. Then module_augment_kernel_taints taints the kernel with TAINT_UNSIGNED_MODULE and logs, once per boot, "module verification failed: signature and/or required key missing - tainting kernel". Every other failure is fatal whatever the policy. A signature that is present but does not verify, a malformed trailer (-EBADMSG), a revoked or blacklisted signer, or a memory shortage aborts the load even on a kernel that would accept an unsigned module. The asymmetry is intentional: a missing signature may be a developer's convenience, but a wrong one is evidence of corruption or tampering. Two more details complete the picture. First, enforcement is a one-way switch. The parameter has the bool_enable_only type, so root can turn it on at run time through /sys/module/module/parameters/sig_enforce but never off again (the write fails with -EROFS). Second, a module loaded with MODULE_INIT_IGNORE_MODVERSIONS or MODULE_INIT_IGNORE_VERMAGIC (modprobe --force) has its signature ignored. A module whose version information is being disregarded is no longer the module that was signed, so such a load is treated exactly as an unsigned one. Figure B-3 shows the decision.

Where the trusted keys come from ties module signing into the platform's larger chain of trust. The build is given a signing key through CONFIG_MODULE_SIG_KEY, either a PEM file or a PKCS#11 URI naming a key held in a hardware security module. If the option keeps its default, certs/signing_key.pem, the build generates a fresh key pair automatically, and the public half is compiled into the kernel's built-in trusted keyring. With CONFIG_MODULE_SIG_ALL (the default), modules are signed during make modules_install, not when they are compiled (scripts/Makefile.modinst). Each module is copied, stripped if INSTALL_MOD_STRIP asks for it, then signed, so that no later strip can invalidate the signature. make modules_sign re-signs an installed tree. Beyond the built-in keys, a distribution can add keys to the secondary keyring at run time, but only keys that are themselves signed by a key it already trusts (and, with CONFIG_SECONDARY_TRUSTED_KEYRING_SIGNED_BY_BUILTIN, since 6.7, only by a built-in key). On UEFI systems a platform owner can enroll their own key into the .machine keyring through the firmware's Machine Owner Key list. That keyring is trusted for modules only when the shim boot loader signals that it should, through the MokListTrustedRT variable. The firmware's own db keys, held in the separate .platform keyring, are not trusted for modules (they serve kexec), while its dbx revocation list feeds the kernel's blacklist. In this way the Secure Boot trust chain of Appendix A, which vouched for the kernel, extends onward to vouch for the modules the kernel loads.

Two mechanisms make the connection binding. The first is kernel lockdown (security/lockdown/): when enforcement is off, module_sig_check falls through to security_locked_down(LOCKDOWN_MODULE_SIGNATURE). That is an integrity-level reason, so a kernel locked down in either the integrity or the confidentiality mode refuses a module without a usable signature with -EPERM, even though sig_enforce was never set. The same lockdown level also refuses to set any module parameter (§6.3) declared with module_param_hw, such as an I/O port, IRQ, or memory address, which could point a driver at arbitrary hardware. The dependency runs one way only: on a kernel built without CONFIG_MODULE_SIG, module_sig_check is an empty stub, and lockdown cannot stop unsigned modules at all. Mainline does not turn lockdown on merely because the machine booted under Secure Boot; that coupling is a patch most distributions carry. Upstream, lockdown comes from the lockdown= boot parameter or a CONFIG_LOCK_DOWN_KERNEL_FORCE_* option. The second mechanism is the integrity subsystem's architecture policy. With CONFIG_IMA_ARCH_POLICY, arch_get_ima_policy (security/integrity/ima/ima_efi.c) calls set_module_sig_enforced when the firmware reports Secure Boot active, switching signature enforcement on for the rest of the boot. On a kernel without module signing, the same policy instead requires every module to carry an IMA signature of its own. IMA can also appraise a module by the very same appended signature (its modsig type), so one signature serves both checks.

The signatures themselves use whichever algorithm the build selects in certs/Kconfig: RSA by default; ECDSA with a P-384 key (since 5.15), which refuses to pair with a 256-bit digest; or, new in 7.0, the post-quantum ML-DSA-44, ML-DSA-65, or ML-DSA-87 schemes of NIST FIPS 204. ML-DSA needs OpenSSL 3.5 or later at build time, and with OpenSSL 4 the whole module body is signed directly rather than through signed attributes. The digest, chosen in kernel/module/Kconfig, is SHA-256, SHA-384, or SHA-512 (the default since 6.14), or one of the SHA-3 variants added in 6.7. The weaker digests have been removed: SHA-224 in 6.7 and SHA-1, long deprecated because of practical collision attacks, in 7.0. Only new signing is affected; modules already signed with SHA-1 still verify. The digest algorithm must be built into the kernel, since a module cannot supply the algorithm needed to check its own signature. Adopting a lattice-based scheme well before any quantum computer threatens RSA reflects how seriously the kernel treats the integrity of the code it admits.

Module Compression

Modules can be stored compressed on disk, as .ko.gz, .ko.xz, or .ko.zst, and, unlike in the past, the kernel can decompress them itself rather than relying on user space to do it first. Since Linux 6.12, two separate options govern this. CONFIG_MODULE_COMPRESS chooses a single algorithm (gzip, xz, or zstd) and, with CONFIG_MODULE_COMPRESS_ALL, has make modules_install compress every installed module with it, external modules included. CONFIG_MODULE_DECOMPRESS separately builds the matching decompressor into the kernel. The kernel deliberately supports only that one algorithm, and it names it in /sys/module/compression, so that kmod can tell whether a file can be handed over still compressed; if not, kmod decompresses it in user space as before. When finit_module is called with the MODULE_INIT_COMPRESSED_FILE flag, init_module_from_file reads the whole compressed file and passes it to module_decompress (kernel/module/decompress.c) before load_module is called, so the loader proper never knows the module was compressed. The decompressor writes its output into individually allocated pages, growing its array of page pointers as it goes (starting at twice the compressed size), and then maps them into one contiguous virtual range with vmap. It needs neither the decompressed size in advance nor any large contiguous allocation. The compressed buffer is freed as soon as decompression finishes, and a failure is counted in the failed_decompress statistic of §4.2.

The ordering with signing matters and is worth remembering. modules_install copies each module, strips it if asked, signs it, and only then compresses it, so a module is signed first and compressed second. The kernel therefore decompresses the file back to its signed form before module_sig_check runs, and the signature covers the real module bytes rather than the compressed wrapper. A distribution can even recompress its modules with a different algorithm without signing them again. The security hooks see both forms of the file. The LSM hooks that run as the file is read see the compressed bytes, tagged READING_MODULE_COMPRESSED. Since Linux 6.19, init_module_from_file also calls security_kernel_post_read_file a second time on the decompressed bytes, tagged READING_MODULE, which lets IMA verify a module's appended signature even when the module was stored compressed. In-kernel decompression thus saves disk space without giving up the authenticity guarantee of §5.1.

It is worth asking why the kernel took on decompression at all, since user space could unpack a module and hand over the plain bytes, as it always used to. The answer is the file-based security of §4.1. A policy such as LoadPin trusts a module because of where it came from, a particular (typically read-only and verified) filesystem, and that judgment needs a file descriptor. Once user space has decompressed a module, it can pass the result only as an anonymous buffer through init_module, which severs the link between the bytes and their origin, so a LoadPin-protected system could not use compressed modules at all. Accepting the compressed file through finit_module and unpacking it internally restores that link and keeps modprobe simple. The choice among algorithms is the same trade-off Appendix A described for the kernel image itself: gzip is the conservative default (the first choice offered), xz compresses smallest, and zstd balances a good ratio against fast decompression, which matters when many modules are unpacked during boot. The xz case is tuned to the kernel's decoder. XZ Embedded, the in-kernel implementation, handles neither CRC64 integrity checks nor dictionaries larger than 1 MiB, so since 6.6 the build compresses modules with exactly those limits. The Kconfig help adds a practical note: modules that live inside an initramfs gain little from being compressed one by one, since compressing the whole ramdisk is more efficient.

Tainting

Not every questionable module can be refused—users have legitimate reasons to load proprietary drivers or force a mismatched module—so the kernel also has a softer mechanism: it records the fact. Tainting sets a flag in a global mask (and in the module's own taints field) noting that something has happened which may compromise the kernel's supportability or integrity, and that flag is printed in every subsequent oops and bug report. The point is honesty rather than prevention: a tainted kernel is one whose developers may decline to debug, because its behavior is no longer purely that of the released source. The letters are exactly those that appear in the "Tainted:" line of a kernel oops (kernel/panic.c). Together with signing, tainting gives the kernel a graduated response to untrusted code: refuse it outright when policy demands, or admit it but mark the kernel indelibly so that everyone, users and developers alike, knows the running kernel is no longer a pristine build.

Two properties of tainting are worth making explicit. First, taint is a whole-kernel, monotonic property, not a per-module one: add_taint_module records the flag on the module that raised it and calls add_taint to set it in the global tainted_mask, which persists for the rest of the boot and can never be cleared. Even the sysctl that exposes the mask, /proc/sys/kernel/tainted, can only add: a write (which needs CAP_SYS_ADMIN) ORs new bits in, one add_taint call per bit, so a test harness can mark a kernel but no one can clean one. The global mask is what an oops prints, and it is why a single proprietary or force-loaded module colors every crash report thereafter. The kernel cannot know that the tainting module was innocent of a later failure, so it refuses to vouch that it was. Second, the module flags in Table B-3 are only a subset of the kernel's 20 taint bits. The others record events unrelated to modules, such as a machine check, a bad page, a soft lockup, a warning having fired, or (new in 6.15) a request for debug write access to a device's firmware through the fwctl interface. A pristine kernel's oops line says simply "Not tainted". Otherwise it reads "Tainted:" followed by a fixed-width string with one position per flag (print_tainted, kernel/panic.c), holding the flag's letter if the condition occurred and a blank if it did not. The exception is the first, proprietary, position, which shows G ("good") when every loaded module is GPL-compatible. A 20-column string of mostly blanks is hard to read, so since Linux 6.11 dump_stack follows it with a second line naming only the flags that are set, such as Tainted: [P]=PROPRIETARY_MODULE, [O]=OOT_MODULE (print_tainted_verbose). For a maintainer triaging a bug, those lines are the first thing read: a report from a tainted kernel is routinely met with a request to reproduce on an untainted one, because the taint may well be the true cause.

Taint is also tracked, and acted on, per module. A module's own flags appear in /sys/module/<name>/taint, in parentheses after its name in /proc/modules, and in the "Modules linked in:" list of an oops, where a + or - also marks a module still loading or being unloaded. A tainting module that has since been unloaded is still remembered, in the [last unloaded: ...] note and the unloaded-tainted list of §4.3. The per-module record has consequences. The tracing subsystem refuses to register the tracepoints and trace events of any module carrying a taint other than O, C, E, N, or K (trace_module_has_bad_taint, kernel/tracepoint.c), because a proprietary or force-loaded module's view of the kernel's structures cannot be trusted. Indeed, the separate E letter exists because, before Linux 3.15, unsigned modules were marked F and so silently lost their tracepoints. An administrator who would rather not run a tainted kernel at all can boot with panic_on_taint= (Linux 5.8), giving a hexadecimal mask of taint bits; add_taint then panics the moment any of them is set. Appending ,nousertaint makes writes to /proc/sys/kernel/tainted that would trip the mask fail with -EINVAL, so that only a genuine kernel event can trigger the panic.

On-Demand Loading and Parameters

Modules would be far less useful if an administrator had to load each one by hand. The defining convenience of the module system is that the kernel can load what it needs automatically, the moment a device appears or a feature is first used. This section covers that on-demand machinery—how the kernel asks user space to load a module, how it names the module it wants without knowing the module's name, and how modules are configured through parameters.

Two roads lead to an automatic load, and Figure B-4 shows them side by side. On the first, kernel code that finds a feature missing—a filesystem type, a socket family, a crypto algorithm—calls request_module with a name it constructs, and the kernel starts modprobe itself. On the second, which now carries most driver loading, the kernel asks for nothing: it announces a new device in a uevent that carries the device's MODALIAS string, and the user-space device manager decides what to load. The roads meet in user space, where the same alias indexes and configuration files turn a name into a file, and then in the same finit_module system call (§4.1), so an autoloaded module passes exactly the signature, lockdown, and taint checks of §5 that a hand-loaded one does. The kernel never opens a module file on its own initiative. Parameters, the third topic, ride along on that same call as its argument string.

request_module and modprobe

When kernel code discovers it needs a module, it calls request_module, or request_module_nowait when it cannot afford to block; both are macros (include/linux/kmod.h) over __request_module (kernel/module/kmod.c). The name is a printf-style format, so callers build it from whatever they know: "fs-%.*s" from a filesystem type, "net-pf-%d" from an address family. __request_module itself is short. It warns if a waiting request comes from an async worker, since the module's initializer may wait for async work to drain (§4.2) and so deadlock; it returns -ENOENT at once if the modprobe path is empty, which is how autoloading is turned off; it formats the name, refusing one longer than MODULE_NAME_LEN; it gives security modules a veto through security_kernel_module_request, where SELinux checks its module_request permission; and it takes one of 50 slots in the kmod_concurrent_max semaphore. If all 50 stay busy for five seconds, the kernel concludes that modules are requesting one another in a loop, logs a warning, and fails the request; 2.6.11 had the same limit but failed the excess request immediately. Finally, after the module_request tracepoint fires, call_modprobe runs the program named by /proc/sys/kernel/modprobe—/sbin/modprobe unless CONFIG_MODPROBE_PATH (5.13) says otherwise—with the arguments -q -- and the name, in a fixed minimal environment. A waiting request returns modprobe's exit status; a non-waiting one returns as soon as the program has started. Either way the answer promises little, because success means only that modprobe succeeded, not that the module registered what was wanted, so callers always look again—the pattern try_then_request_module packages. Its best-known user is symbol_request, which loads whatever module exports a named symbol by asking for the alias symbol: plus the symbol's name, and which, because symbol_get works only on GPL-only exports (§3.1), can reach no others.

The work is handed to user space not because the kernel cannot read a file—since finit_module it reads module files routinely—but because everything needed to choose one lives there: where modules are installed, which one provides an alias, what must be loaded first, and the administrator's blacklists and options. The usermode helper that runs modprobe is started from a kernel worker thread, so it executes with full root credentials and in the initial namespaces, against the host's root filesystem, whatever process or container triggered the request. It does not exist early in boot: helpers are enabled only when the initramfs is being unpacked (populate_rootfs), and are disabled again while tasks are frozen for suspend, so a request made at those times fails with -EBUSY. On its side, modprobe treats a name listed in modules.builtin as already satisfied, otherwise resolves it through the alias index, honors the blacklist, options, softdep, and install lines in /etc/modprobe.d, adds any matching options it finds on the kernel command line, loads dependencies in modules.dep order, and calls finit_module for each file. Several requests for one module can still race into user space; the loader's one-load-per-file rule (§4.1) makes the duplicates harmless but not free, and the 6.4 debugging option CONFIG_MODULE_DEBUG_AUTOLOAD_DUPS reports them and folds them onto the first request. This division of labor—the kernel deciding what is needed, user space deciding which file provides it and how to reach it—is the same design Linux 2.6 implemented under the name kmod, and it remains the heart of automatic module loading.

This convenience has a security dimension that 2.6-era kernels scarcely had to consider. Because a request_module can be triggered by an unprivileged action—creating a socket of an unusual address family fires request_module("net-pf-%d", family), mounting an unknown filesystem type fires request_module("fs-%.*s", len, name), opening a character device with no driver fires a char-major- request—an ordinary user can indirectly coax the kernel into loading obscure, rarely-audited modules, which has been a recurring source of attack surface. The first defense is naming. A request an unprivileged user can trigger carries a subsystem prefix, so it can match only a module that opted in by declaring the matching alias. Mount requests gained the fs- prefix in Linux 3.9, matched by MODULE_ALIAS_FS, and crypto lookups the crypto- prefix in 3.19, matched by MODULE_ALIAS_CRYPTO; before that, a mount or an AF_ALG socket could name any module on disk. Since 2.6.38, dev_load, which looks up network interfaces by name, lets a CAP_NET_ADMIN caller request only netdev- aliases and reserves bare module names for CAP_SYS_MODULE. Legacy triggers can be switched off: loading a line discipline on demand requires CAP_SYS_MODULE unless CONFIG_LDISC_AUTOLOAD or the dev.tty.ldisc_autoload sysctl (5.1) allows it, and CONFIG_BLOCK_LEGACY_AUTOLOAD (5.18) controls loading a block driver because someone opened a device node by number. In Linux 6.14 the oldest trigger of all went away: execve no longer requests a binfmt- module when it meets an unknown executable format, a leftover of the move from a.out to ELF.

Beyond naming, the kernel constrains autoloading in layers. Loading itself requires CAP_SYS_MODULE (may_init_module, kernel/module/main.c), but that check cannot stop an autoload, because the helper's modprobe already runs as root. What does stop it is the one-way /proc/sys/kernel/modules_disabled sysctl, or the nomodule boot parameter, after which every load is refused with -EPERM; emptying /proc/sys/kernel/modprobe instead turns off only the kernel's own requests, leaving explicit loads working. Because the helper runs with full privilege, its inputs are themselves sensitive. The modprobe path is a root-only tunable and a well-known target for exploits that have gained a kernel memory write; the capabilities any helper receives can be narrowed through /proc/sys/kernel/usermodehelper/bset and inheritable; and CONFIG_STATIC_USERMODEHELPER routes every helper through one fixed program that decides what actually runs. Since 6.17 the modprobe and modules_disabled sysctls are registered by the module code itself rather than by the central sysctl table.

Aliases, depmod, and Autoloading

The elegant part of autoloading is that a device asks for its driver not by name but by capability: it describes itself, and something must translate that description into a concrete file. The translation starts in the driver. A PCI driver, for instance, lists the devices it supports in a struct pci_device_id table and declares it with MODULE_DEVICE_TABLE(pci, ids), which costs nothing at run time but plants a specially named alias symbol that encodes the module, the bus, and the table. At build time modpost, through scripts/mod/file2alias.c, finds that symbol, reads the table out of the object file using field offsets the build computes for each of more than fifty bus types, and turns every entry into an alias pattern, written as a MODULE_ALIAS line in the module's generated .mod.c and so into its .modinfo (§2.3). Fields the driver left as wildcards become *, so the xHCI driver's class-based entry becomes pci:v*d*sv*sd*bc0Csc03i30*, matching any USB 3 host controller from any vendor. At make modules_install, depmod collects every module's aliases into modules.alias and the dependency graph into modules.dep under /lib/modules/$(uname -r). Built-in drivers had a gap here until Linux 6.18: modpost generated no aliases for code linked into vmlinux, so user space could not tell that a device was already served by a built-in driver. Those aliases are now recorded too, under the driver's name, in modules.builtin.modinfo. This alias mechanism is what lets a single distribution kernel support thousands of devices while loading only the handful of drivers a given machine actually needs—the seamless hardware support Chapter 1 attributed to modules.

The run-time half is driven by events rather than by request_module. When the driver core registers a device, it sends a KOBJ_ADD uevent over netlink, and the bus's uevent callback adds a MODALIAS variable built from the same fields the build used—pci_uevent writes the vendor, device, subsystem, and class codes in the pci:v%08Xd%08X… format—while the device's modalias file in sysfs holds the same string. The kernel calls no helper for this. The user-space device manager, systemd-udevd on most systems, receives the event and loads every module whose alias pattern matches, normally in-process through libkmod rather than by running modprobe. Devices that existed before the manager started are handled by coldplug: udevadm trigger writes add to each device's uevent file in sysfs, and the kernel sends the event again. A newly discovered PCI device therefore does not make the kernel call request_module; it is udev, matching MODALIAS against modules.alias, that loads its driver. The 2.6.11 kernel still forked /sbin/hotplug for every event; that path survives only as CONFIG_UEVENT_HELPER, off by default because a fork per event could exhaust a small machine during boot. On ARM64 the same machinery works from the device tree. A platform device announces an of: alias, built from its node's name and compatible strings, when it has a device tree node, an acpi: alias when it has an ACPI one, and platform: plus its name only otherwise, so on a device-tree system it is a driver's of_device_id table that gets it loaded.

The alias strings follow conventions worth recognizing, because they appear throughout the kernel and in the index files. Requests the kernel makes itself carry a subsystem prefix—fs-, net-pf-, netdev-, crypto-, tty-ldisc-—or a device number, as in char-major-N-M and block-major-N-M, each retried without the minor number for drivers that claim a whole major. Event-driven aliases begin with the bus name—pci:, usb:, of:, acpi:, platform:, and dozens more—and even processors have them: a cpu: alias, generated from an x86cpu table on x86 or by module_cpu_feature_match on ARM64, autoloads an accelerated crypto driver such as aesni-intel or aes-ce-blk on a CPU with the matching feature. A third family, devname: aliases such as devname:fuse, lets user space create device nodes before any driver is loaded: depmod lists them in modules.devname, a boot-time kmod static-nodes step creates the nodes, and opening one triggers the char-major- request that loads the driver. Besides the text indexes, depmod writes binary forms (modules.alias.bin, modules.dep.bin, modules.builtin.alias.bin) for fast lookup, a modules.symbols map from each exported symbol to its module for symbol_request, and modules.softdep and modules.weakdep from the dependency hints of §2.3. Its inputs are the build's modules.order, modules.builtin, and modules.builtin.modinfo, installed alongside the modules. The MODULE_DEVICE_TABLE declaration a driver writes is thus the single source that the build turns into aliases, that depmod indexes, and that udev matches against real hardware.

Module Parameters

A module often needs configuration—which I/O port to probe, how large a buffer to allocate, whether to enable a debug mode—and Linux provides a uniform mechanism for this through module parameters. A module declares a parameter with module_param (or module_param_named, module_param_array, module_param_string, module_param_cb, and relatives in include/linux/moduleparam.h), giving its name, type, and the permissions of its sysfs file, and documents it with MODULE_PARM_DESC; the description and the type land in .modinfo as parm and parmtype entries, which modinfo prints. Each declared parameter becomes visible under /sys/module/<name>/parameters/, where a suitably privileged user can read—and, if the permissions allow, write—its value at run time. Parameters can be set when the module loads, as name=value arguments to insmod or modprobe, or persistently through options lines in /etc/modprobe.d; in parameter names a dash and an underscore are interchangeable. On the kernel command line the same parameter is written <module>.<param>=value, and who acts on it depends on how the module was built. For built-in code, MODULE_PARAM_PREFIX has already prefixed every parameter name with the module's name, and start_kernel applies the setting while it parses the command line; the sysfs files appear late in boot (param_sysfs_builtin), under the name the module would have had. For a loadable module, the kernel quietly skips any unrecognized option containing a dot, and modprobe later finds it in /proc/cmdline and passes it along. One declaration therefore serves both cases—modprobe some_driver debug=1 and some_driver.debug=1 at boot reach the same variable—giving every module a consistent, discoverable configuration surface without each having to invent its own.

Underneath the macros, each parameter is a struct kernel_param placed in the module's __param section: its name, owning module, operations, permission, an initcall level, flags, and a pointer to the variable (or to a string or array descriptor). The operations are a struct kernel_param_ops that supplies set, get, and an optional free callback, plus a KERNEL_PARAM_OPS_FL_NOARG flag for types, such as bool, that accept a bare name with no value. The common types come with ready-made ops—byte, short, ushort, int, uint, long, ulong, ullong, hexint (5.10), charp, bool, invbool, bint, and the one-way bool_enable_only that §5.1 met as sig_enforce—so module_param(name, int, 0644) wires a plain integer to sysfs with no further code, while a driver that needs validation or a side effect on change supplies its own ops through module_param_cb, often built from helpers such as param_set_uint_minmax. Array parameters take comma-separated values and can report how many were given. The permission argument is exactly the mode of the sysfs file, checked at compile time by VERIFY_OCTAL_PERMISSIONS, which rejects a world-writable mode or one that grants the group or others more than the owner. A value of 0 is meaningful: it creates no sysfs file at all, making the parameter settable only at load time or boot. The level matters only for built-in code: ordinary parameters are applied as soon as the command line is parsed, while those declared with core_param_cb, subsys_param_cb, device_param_cb, and their relatives are applied just before the initcalls of that level run (Appendix A).

Two flags mark parameters that need more care. One declared with module_param_unsafe (3.18) still works, but setting it logs "Setting dangerous option" and taints the kernel with TAINT_USER (U), so a bug report shows that someone turned a knob the developers consider risky. One declared with module_param_hw (4.12) records what the value configures—an I/O port, memory address, IRQ, DMA channel, or DMA buffer—and under lockdown param_check_unsafe refuses to set it, with -EPERM, at load time or through sysfs (§5.1). Load-time parsing happens in load_module (§4.2) after the module is fully formed and its MODULE_STATE_COMING notifiers have run, but before its sysfs directory exists or its initializer runs, so a module sees its configured values from the start; because a custom set callback is module code, this is the first point at which the module's own code can run. parse_args (kernel/params.c) matches each name=value against the module's table with the module's parameter lock held. A value that fails to parse aborts the load, but an unknown name only logs that it was ignored, as does anything after a lone --. Two names are accepted from every module without being declared: async_probe, which requests asynchronous device probing (§4.2), and dyndbg, which enables the module's dynamic debug messages from the moment it loads.

One subtlety catches newcomers: writing a writable parameter through sysfs calls its set operation and updates the underlying variable, but nothing tells the module; it notices only if it re-reads that variable or registered ops with a side effect—so many parameters are effectively load-time settings even when their file is writable, and only those a driver explicitly designed to be live actually change behavior on the fly. Such updates are serialized only against one another. Sysfs reads and writes and load-time parsing all hold kernel_param_lock, a mutex kept per module (built-in parameters share a global one), and code that reads a writable string parameter must take it too, because setting a charp frees the old string. Rust modules gained parameters in Linux 6.19 through a params block in the module! macro (Chapter 26); for now they are integers only and have permission 0, so they can be set at load time or boot but never appear in sysfs.

Modules as Kernel Infrastructure

Modules began almost entirely as a way to package device drivers. They remain that, but in the intervening years the module has also become a general vehicle for extending the kernel in ways that have little to do with drivers—carrying type information that other subsystems consume, supplying test suites, and even delivering live patches to the running kernel's own code. This closing section first looks at the general mechanism by which a module contributes to subsystems other than the driver core, and then at two such modern roles, both absent from Linux 2.6, that show how central the module mechanism has become to the kernel's evolution.

The common thread is the long tail of optional fields in struct module that §2.1 noted, together with the notifier chain of §1.2. The loader finds each kind of contribution by section name in find_module_sections (kernel/module/main.c)—__jump_table, .static_call_sites, __tracepoints_ptrs, _ftrace_events, _kprobe_blacklist, _error_injection_whitelist, __dyndbg, .printk_index, .kunit_test_suites, .BTF, and more—records where it lies, and leaves acting on it to the subsystem that owns it. About twenty subsystems subscribe to module_notify_list in 7.0.12, and most need only two events. On COMING, before any of the module's code has run, they adopt what it brings: jump labels and static calls patch its call sites to match the current state of their keys, tracepoints and trace events register its probe points and event definitions, kprobes records which of its functions may not be probed and arms probe events that were defined before it loaded, and BPF parses its type information. On GOING they let go. A few also act on LIVE, once the initializer has succeeded: KUnit runs the module's test suites only then, kprobes discards probes placed on its now-freed init text, and BPF makes its types available for programs to reference. The COMING announcement goes through a robust chain, so a subscriber that rejects the module—BPF refusing type information that does not match the kernel, for instance—causes every subscriber already notified to hear GOING, and the load fails.

Accepting contributions from loadable code raises the question that dominated §4.3: what keeps the module from disappearing while its contribution is in use? The answer is the same reference count that protects a driver. A BPF program that calls a function a module provides, or uses one of its types, takes a reference on that module when the program is verified and drops it only when the program is freed, so rmmod reports the module in use for as long as the program is loaded; an enabled livepatch holds a reference on its own module. The module, in other words, has become the kernel's general unit of pluggable extension, and its descriptor has grown a slot for every subsystem that wants to accept contributions from loadable code. The two roles below are the most illustrative, but they exemplify a broader pattern: if a kernel facility needs to be extensible at run time, it is very often a module that extends it.

Module BTF

BTF (BPF Type Format) is a compact description of the kernel's data types—structures, their fields, and their layouts, and the prototypes of its functions—that the kernel carries so that BPF programs can be written against kernel structures and adjusted automatically to whatever kernel they run on, the technique called CO-RE (compile once, run everywhere; Chapter 23). Types defined in modules need the same treatment, so since Linux 5.11, when CONFIG_DEBUG_INFO_BTF_MODULES is enabled (the default whenever the kernel itself has BTF), each module carries its own BTF in a .BTF section, and the loader records where it lies (btf_data in struct module). That section is not one the loader keeps—it is not allocated, and the pointer refers into the temporary copy of the file, so it is cleared once initialization finishes. The BPF subsystem must therefore take what it needs while the module is still loading. Its notifier, btf_module_notify (kernel/bpf/btf.c), copies and validates the BTF at COMING, gives it an ID, and publishes it as /sys/kernel/btf/<module>, readable by everyone, where bpftool and libbpf find it; it marks the BTF usable at LIVE, and at GOING it withdraws the ID and the file so that no new program can find the module's types. BTF that fails validation makes the notifier veto the load, unless CONFIG_MODULE_ALLOW_BTF_MISMATCH (5.18) is set, in which case the module loads without BTF. The payoff is that a BPF program or a kfunc can resolve types defined in a module just as it resolves types in the core kernel—so tracing tools and the growing body of BPF-based functionality extend naturally to modular code. Here the module is not adding a driver but supplying metadata that another subsystem consumes.

A little detail about how this BTF is produced and stored explains why it is practical, and why it is strict. The type information is not hand-written but extracted at build time by the pahole tool from the compiler's DWARF debug information and condensed into the compact BTF form; for a module this happens at its final link (scripts/Makefile.modfinal), driven in 7.0 by scripts/gen-btf.sh, which runs pahole and then resolve_btfids against the just-built vmlinux. Modules store split BTF: rather than each module duplicating the thousands of core kernel types it references, a module's BTF records only its own types, numbered to follow the base kernel's, and refers to the base kernel's BTF for everything else (base_btf in the BTF representation, kernel/bpf/btf.c), so the per-module cost is small. The price is that a module's BTF is bound to the exact vmlinux it was built against, since its references are indexes into that kernel's type list; that is why a mismatch is rejected rather than trusted. Out-of-tree modules, often built once and loaded into many rebuilds of a kernel, get relief from distilled base BTF (6.11). An external module build also emits a small .BTF.base section that describes the core types the module references by name and shape, and at load the kernel relocates the module's BTF against the running kernel's (btf_relocate), so the BTF survives as long as those types have not changed; in 7.0 resolve_btfids, not pahole, produces the distilled base. Rust code is excluded from pahole's output (--lang_exclude=rust), which is what allows a kernel to enable Rust and BTF together, so a Rust module (Chapter 26) contributes no BTF for its own types.

The most consequential consumer is the growing kfunc mechanism: a module can register functions that BPF programs may call directly, and the verifier uses the module's BTF to type-check those calls and match arguments, identifying each function through its BTF_KIND_FUNC entry. A module lists its kfuncs between BTF_KFUNCS_START and BTF_KFUNCS_END, tagging each with flags the verifier enforces—bpf_skb_ct_lookup in the netfilter connection-tracking module is marked KF_ACQUIRE | KF_RET_NULL, so a program must check its result for NULL and release what it acquired—and resolve_btfids fills in each function's BTF ID at build time; the module's initializer then calls register_btf_kfunc_id_set for each program type allowed to use the set. The TCP BBR congestion-control module, for example, registers its own bbr_init and bbr_main so that a congestion-control algorithm written in BPF can reuse them. Calls from BPF into module functions arrived in Linux 5.16, and since 6.9 a module can go further and define a new struct_ops type—a table of operations that BPF programs implement—as the SMC protocol module does for its handshake control (6.19). Through split BTF, kfuncs, and struct_ops, a module can safely widen the surface that BPF programs are allowed to touch, extending the kernel's programmability rather than merely its device coverage.

These contributions carry the lifetime obligations that the section introduction described. When the verifier accepts a program that calls a module's kfunc, attaches to one of its functions, or implements one of its struct_ops types, it takes a reference on the module through btf_try_get_module, and the reference lasts until the program is freed. That function succeeds only for a module whose BTF has been marked usable at LIVE, so a program can never bind to a module whose initializer might still fail—the same precaution strong_try_module_get takes for modules that depend on one another (§4.3). Conversely, once a module begins going away its BTF is withdrawn from the ID table at once, so no new program can find the module's types while it is being removed.

Livepatch

The most striking modern use of modules is livepatch (kernel/livepatch/), the mechanism for fixing bugs in a running kernel without rebooting—invaluable for servers that cannot easily be taken down for a security update. It arrived in Linux 4.0 for x86-64; ARM64 gained it only in 6.17, once its unwinder could produce the reliable stack traces described below. A livepatch is delivered as a kernel module: it is an ordinary .ko that, instead of registering a driver, describes a set of replacement functions, and it declares itself with MODULE_INFO(livepatch, "Y"). The loader marks such a module, refuses it with -ENOEXEC if the kernel lacks CONFIG_LIVEPATCH, and taints the kernel with TAINT_LIVEPATCH (K, §5.3), recording that the running kernel no longer exactly matches its source. Its structures—struct klp_patch, struct klp_object, and struct klp_func (include/linux/livepatch.h)—name the objects to be patched (vmlinux or a module), the functions to be replaced in each, with a position to tell apart static functions that share a name, and the new versions to run in their place. The module's initializer passes them to klp_enable_patch (kernel/livepatch/core.c), which since 5.1 both registers and enables the patch in one call. It checks that the patch is compatible with those already installed, takes a reference on its own module, creates /sys/kernel/livepatch/<patch>/, with files such as enabled, transition, and force, and starts switching the system over. Writing 0 to enabled later reverses the process; when that transition completes the reference is dropped, and only then can the module be removed.

The redirection itself reuses the kernel's function tracer. Every traceable function begins with a call site that ftrace normally leaves as a no-op; livepatch registers an ftrace handler, klp_ftrace_handler (kernel/livepatch/patch.c), on each patched function with the FTRACE_OPS_FL_IPMODIFY flag, which lets it change the saved instruction pointer so that when the ftrace trampoline returns, execution continues in the replacement rather than in the old body. No caller need be recompiled, and the patch takes effect everywhere the old function is reached, through direct calls and function pointers alike. Several patches may replace the same function; the handler keeps them on a stack and uses the newest. The handler also marks its ftrace registration permanent, so function tracing cannot be switched off underneath an applied patch. The approach has a cost in reach: a function the compiler inlined, or one marked notrace, has no call site of its own, so a patch must instead replace the functions that contain it.

The subtle part is switching a running kernel safely, since a thread might be executing inside a function at the moment it is patched, or a coordinated change might alter several functions that must not be mixed. Livepatch solves this with a consistency model (4.12): rather than switching the whole system at one instant, it moves each task individually from the old code to the new, and does so only at a moment when the task is provably running none of the affected functions. Each task carries a patch_state; during a transition the ftrace handler consults the current task's state to decide whether to run the old function or the new one, so every task sees either the complete old set or the complete new set. The transition (kernel/livepatch/transition.c) begins by setting the TIF_PATCH_PENDING thread flag on every task, and a task is switched, and its flag cleared, in any of several ways, as Figure B-5 shows. Once a second a worker walks the stack of each pending task that is not running, using the architecture's reliable unwinder (ORC on x86-64, frame records on ARM64), and switches every task whose stack contains no patched function. A task switches itself on its way back to user space—the exit work of Chapter 4—when no kernel function can be on its stack; the idle tasks switch in the idle loop; and since 6.16 a task about to be scheduled out checks itself in __schedule, which lets CPU-bound kernel threads converge (6.4 had hooked cond_resched for the same purpose). If tasks are still pending after fifteen seconds, livepatch sends a fake signal to user tasks to push them through the kernel exit path and wakes sleeping kernel threads. When the last task has crossed over the patch is fully in effect and transition reads 0. Without a reliable unwinder only the exit and idle paths remain, and a transition may never finish; klp_enable_patch warns about exactly that. An administrator can write to force to declare every task switched without proof, at a price: since some task might still be running old code, a forced patch module can never be removed.

Several further capabilities distinguish a livepatch module from an ordinary one. First, a livepatch must reach kernel symbols that are not exported—the whole point is to patch arbitrary internal functions, whose replacements call the internals around them—so livepatch modules carry special KLP relocations. These live in sections named .klp.rela.<object>.<section> and refer to symbols named .klp.sym.<object>.<symbol>,<position>, which the ordinary symbol resolution of §4.2 deliberately leaves alone, granting an access that ordinary module linking (§3) denies. They are resolved through kallsyms in two stages. Those that refer into vmlinux are applied while the patch module itself is loading, so that even its own initialization can use them. Those that refer into a module can be applied only when that module is present—when the patch is enabled if it is already loaded, or later, when klp_module_coming runs as it loads, before its notifiers or initializer; on x86-64 they are cleared again if it unloads (6.3), so that a reload can be relocated afresh. To make this late patching possible, the loader keeps a copy of the patch module's section headers and symbol table, described by struct klp_modinfo (copy_module_elf, kernel/module/livepatch.c). Second, because you cannot grow an existing structure in a running kernel—the very limitation §1.1 gave as a reason some code cannot be a module—livepatch offers shadow variables (klp_shadow_alloc, 4.15), a side table keyed by an object's address that attaches new fields to existing objects without changing their layout. Third, per-object callbacks (4.15) run before and after patching and unpatching, and a pre-patch callback can veto the patch, so that a fix that must also change data, such as enabling a feature, can be applied cleanly.

Patches also have to coexist over a kernel's lifetime. A patch with the replace flag (5.1) is cumulative: it supersedes all previous ones in a single transition, reverting any function that it no longer changes, after which the older patches are disabled and their modules can be removed—the way distributions ship fixes, each patch containing all its predecessors. System-state records (struct klp_state, 5.5) let a replacing patch declare which modifications of data its predecessors made that it knows how to maintain, and klp_enable_patch refuses a cumulative patch that omits a state an installed patch introduced, or any patch that carries one at an older version. Writing a patch module by hand is laborious, and for years it was done with out-of-tree tools; since Linux 6.19 the kernel provides scripts/livepatch/klp-build on x86-64. Given an ordinary source patch, it builds the kernel twice, before and after, with each function in its own section, and uses objtool klp diff to extract the changed functions and generate the KLP relocations they need, producing a cumulative patch module by default. That the same module machinery which loads a mouse driver can also rewrite the kernel's own code while it runs, task by task and without a reboot, is a measure of how far the mechanism has travelled from its origins as a way of packaging device drivers.

Summary

This appendix examined how Linux extends a running kernel with loadable modules. A module is a relocatable object file that Kbuild and modpost turn into a .ko already carrying its own struct module descriptor, its export table, and a .modinfo block of metadata; built in instead, the same source becomes an ordinary initcall. Supporting it requires the kernel to do two things: link the module—resolve each imported symbol against a curated set of exports, governed by GPL-only restrictions, symbol namespaces, and version checksums, and patch its code to the addresses found—and manage its lifetime through four states, a single atomic reference count, and a dependency graph, so that nothing is removed while it is still in use. The 7.0 loader does both in a long, ordered pipeline behind finit_module. It authenticates the image before parsing it, validates the ELF file and the metadata, lays the sections out in seven typed memory regions taken from the shared execmem allocator, relocates and patches the code, seals each region with the tightest page protections the hardware allows, and announces the module to the subsystems that subscribe to its arrival before running its initializer; it unwinds cleanly from any failure, and concurrent loads of one file collapse into one. Unloading reverses the path, refusing rather than waiting while any reference remains.

Around that core sit the facilities that decide what may be loaded, and when. A module's appended PKCS#7 signature—RSA, ECDSA, or, new in 7.0, post-quantum ML-DSA—is checked against keyrings that carry Appendix A's Secure Boot chain of trust onward to the code the kernel loads. A missing signature is a matter of policy, enforced by sig_enforce, lockdown, or IMA's Secure Boot policy, but a wrong one is always fatal. Compressed modules are unpacked by the kernel itself, before the signature check and without losing the file's identity, and whatever the kernel admits but cannot vouch for—proprietary, out-of-tree, unsigned, forced, or test code—is recorded indelibly as taint, globally and per module. Most modules, though, are loaded without anyone asking. Kernel code that finds a feature missing calls request_module, which runs modprobe as a usermode helper, limited by subsystem-prefixed names and a pool of 50 slots; a new device instead announces a MODALIAS that udev matches against the aliases modpost generated from the driver's device table. Both roads end in the same system call and the same checks, and module parameters, declared once, configure a module from the load command line, the kernel command line, or sysfs.

The larger theme is how much the module system has been hardened and generalized since Linux 2.6. What was once a matter of insmod resolving symbols and bumping a use count is now a pipeline that authenticates, decompresses, version-checks, write-protects, and records through tainting anything it cannot fully trust, and the interface it enforces is governed ever more closely, by namespaces, per-module exports, and a versioning scheme reworked so that modules written in Rust load through the same path as C ones. And the module has outgrown its original role. Through the notifier chain it contributes jump labels, tracepoints, test suites, and BTF type information to the subsystems that consume them; with kfuncs and struct_ops types it can widen what BPF programs may call and implement; and as a livepatch it can replace the running kernel's own functions, task by task, without a reboot. Table B-4 collects these shifts. The essential idea, though, is the one Chapter 1 introduced: modularity lets the kernel be small, flexible, and extensible without sacrificing the performance of running everything in one address space—and that idea has only grown more central to how Linux is built and maintained.
