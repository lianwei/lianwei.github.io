Overview

Linux is one of the most successful operating systems ever created. From its humble beginnings as a hobby project by Linus Torvalds in 1991—originally targeting the Intel 80386 processor—it has grown into the dominant operating system kernel, powering everything from embedded devices and smartphones (via Android) to the world's fastest supercomputers, cloud infrastructure, and spacecraft.

This book examines the internals of the Linux kernel version 7.0.12. Linux 2.6.11 was released in 2005. In the more than two decades since, the kernel has undergone revolutionary changes: the process scheduler has been rewritten more than once and now runs the EEVDF algorithm in place of the long-serving Completely Fair Scheduler; the memory-management subsystem has been fundamentally restructured around folios; the block layer has moved to a multi-queue design; whole new subsystems—io_uring for asynchronous I/O, eBPF for safe in-kernel programs, and the namespaces and control groups that underpin containers—have been added; and even a second programming language—Rust—has been introduced alongside C.

This book focuses on two architectures: x86_64 (AMD64/Intel 64) and ARM64 (AArch64). Today, x86_64 dominates servers and desktops while ARM64 dominates mobile, embedded, and increasingly server workloads.

This chapter sets the stage for the rest of the book. It begins with the license that governs the kernel and what the GPL and its syscall exception mean for user programs and modules, then places Linux among the other Unix-like kernels—a monolithic kernel that is nonetheless extensible through modules, eBPF, Rust, and livepatch, and whose preemption behavior is now chosen from the full and lazy models. It explains how kernel versions are numbered and maintained, reviews the basic operating-system concepts—users, groups, processes—and the Unix filesystem model of files, links, inodes, and permissions that Linux implements. The central part of the chapter is a guided tour of the kernel: how processes enter it, how they are represented, how their address spaces are organized, how concurrent code is synchronized, and how processes, scheduling, signals, memory, and device drivers fit together. The chapter then looks at what is hardware dependent and how x86_64 and ARM64 differ, introduces the modern subsystems that did not exist in 2.6.11, walks through the Kconfig/Kbuild build system and the tools used to check and test what it builds, sketches the boot-time path through start_kernel(), and closes with a map of the book. Each topic here is a preview; the chapters that follow give the full treatment, always grounded in the 7.0.12 source.

Licensing: The GNU General Public License

The Linux kernel is released under the GNU General Public License version 2 (GPL-2.0), with an explicit syscall exception. This is stated in the COPYING file at the root of the source tree:

The Linux Kernel is provided under:

    SPDX-License-Identifier: GPL-2.0 WITH Linux-syscall-note

The license is not a footnote to the kernel's design; it is one of the reasons the kernel exists in the form this book describes. The GPL's copyleft requirement—that anyone who distributes the kernel, modified or not, must also make the corresponding source available under the same terms—guarantees that improvements flow back to the common code base rather than disappearing into proprietary forks. That guarantee is what has let a globally distributed community of thousands build on each other's work for three decades, and it is why the complete source is available to be studied at all. Understanding the license is therefore a prerequisite to understanding how the kernel is developed and how code may legally be combined with it.

The GPL-2.0 license has been fundamental to Linux's success:

The Syscall Exception

The "Linux-syscall-note" exception (LICENSES/exceptions/Linux-syscall-note) is critically important: it clarifies that user-space programs that interact with the kernel solely through system calls are NOT considered derivative works. Without this exception, every program running on Linux would arguably need to be GPL-licensed. The UAPI headers under include/uapi/ can be freely used by non-GPL programs.

The reason the clarification is needed is that user programs must include kernel headers to make system calls—the constant definitions, structure layouts, and ioctl numbers that describe the kernel's ABI. Combining GPL-licensed headers into a program could, under a strict reading of the license, taint that program with the GPL. The exception draws an explicit line at the system-call interface: crossing it does not create a derivative work, so proprietary databases, web servers, games, and every other closed-source application can run on Linux without their authors ever inheriting the kernel's license. This single sentence is what makes Linux viable as a general-purpose platform rather than a purely free-software island, and it is why the kernel deliberately partitions its headers into the internal ones and the include/uapi/ ones that user space is allowed to see (a split this book returns to when discussing the system-call interface in Chapter 10).

SPDX License Identifiers

Since kernel 4.14, every source file includes a machine-readable SPDX identifier:

// SPDX-License-Identifier: GPL-2.0-only    ← Most kernel files
// SPDX-License-Identifier: GPL-2.0-or-later ← Permits later GPL versions
// SPDX-License-Identifier: MIT              ← Some library code

Before this convention, each file carried a paragraph or more of license boilerplate in its header comment, and those paragraphs were inconsistent, sometimes ambiguous, and impossible to process reliably by machine. The SPDX (Software Package Data Exchange) identifier replaces that boilerplate with one standardized line naming the exact license, so that automated tooling can verify the license of every file, flag incompatible combinations, and generate accurate license manifests for a build. The mass conversion, begun in the 4.14 cycle, added identifiers to hundreds of thousands of files, and today a new file is expected to carry an SPDX tag as its very first line. The identifiers are drawn from the license texts collected under the LICENSES/ directory, which records the full text of every license the tree uses.

GPL-2.0 vs GPL-3.0

Linus Torvalds has explicitly stated that the Linux kernel is licensed under GPL version 2 only — not "version 2 or later." When the FSF released GPL-3.0 in 2007 (adding anti-tivoization provisions), Linus disagreed with the additional restrictions, and the kernel remains firmly on GPL-2.0.

The distinction hinges on a few words. Many GPL projects license their code as “version 2 or later,” which lets recipients adopt a newer GPL version if the FSF publishes one; the kernel deliberately omits the “or later” clause, pinning itself to GPL-2.0 alone. The specific objection to GPL-3.0 was its anti-tivoization language, which requires that users be able to install modified versions of the software on the hardware it ships with—a rule Torvalds regarded as overreaching into how hardware makers build their products rather than how software is licensed. A practical consequence of the version-2-only choice is that the kernel can essentially never be relicensed: doing so would require the agreement of every one of the many thousands of copyright holders whose contributions make up the tree, many of them unreachable or deceased. The license the kernel has is, for all realistic purposes, the license it will always have—which is itself a kind of stability that contributors and companies can rely on.

Implications for Kernel Modules

The license has direct, mechanical consequences for loadable modules, because a module is linked into the running kernel's address space and therefore sits far closer to the kernel than a user program does. Every module declares its license with the MODULE_LICENSE() macro, and the kernel treats that declaration as a first-class fact: it governs which symbols the module may use and how the kernel marks itself once the module is loaded. Figure 1-2 summarizes the three cases.

The central mechanism is the distinction between two ways the kernel exports its internal functions to modules. EXPORT_SYMBOL() makes a symbol available to any module regardless of its declared license, whereas EXPORT_SYMBOL_GPL() makes it available only to modules whose MODULE_LICENSE() names a GPL-compatible license. Many of the kernel's most intimate interfaces are exported with the GPL-only form, encoding the developers' view that code reaching that deep into the kernel is a derivative work and must therefore be free software. A module that declares a proprietary license can still load and use the ordinary EXPORT_SYMBOL() interfaces, but it is denied the GPL-only ones—the same gate, incidentally, that governs Rust modules (Chapter 26), whose license field feeds exactly this check.

Loading a module also affects the kernel's taint state. The kernel records a set of taint flags describing anything that might compromise its integrity for debugging purposes, and loading a module sets a flag according to its provenance: P for a proprietary (non-GPL) module, O for an out-of-tree module, and others for forced loads or unsigned modules. The taint value is printed in every kernel oops and panic, so that a developer triaging a crash can immediately see whether an external or proprietary module was present—kernel maintainers will often decline to debug a report from a tainted kernel, since the out-of-tree code they cannot see may be the actual cause. None of this forbids proprietary modules outright; the kernel permits them as a long-standing, if contested, compromise, while making their presence visible and denying them the interfaces the community considers GPL-only. The mechanics of building, signing, and loading modules are the subject of Appendix B.

Where the 2.6 era had a field of competing Unix kernels, the modern picture is of Linux as the de facto standard, with the surviving alternatives thriving by occupying niches—high-assurance real-time, tightly integrated consumer devices—that play to a different set of design priorities.

Linux vs QNX: Monolithic Kernel vs Microkernel

One of the most instructive comparisons is with QNX Neutrino, a commercial POSIX-compliant RTOS by BlackBerry. QNX represents the opposite end of the kernel design spectrum: where Linux is a monolithic kernel, QNX is a true microkernel.

The distinction is fundamental and worth stating precisely. A monolithic kernel like Linux runs all of its core services—the scheduler, memory manager, filesystems, network stack, and device drivers—together in a single privileged address space, so that one subsystem calls another with an ordinary function call. A microkernel like QNX keeps only the barest essentials in privileged mode—scheduling, interprocess messaging, interrupt dispatch, and timers—and pushes everything else, including filesystems and device drivers, out into ordinary user-space processes (QNX calls them resource managers) that communicate with each other and with clients by message passing. The trade-off runs in opposite directions. Linux's design is faster, because a call from the VFS into a driver is a direct branch rather than a message and a context switch, but it is less isolated: a defect in any driver runs with full kernel privilege and can bring down the whole system. QNX's design pays a messaging cost on every interaction but gains strong fault isolation—a crashed driver is just a process that can be restarted while the kernel keeps running—which is what lets QNX be certified to the stringent functional-safety standards (such as ISO 26262 ASIL D) that automotive and medical systems demand. Neither approach is simply better; they optimize for different things, and Linux's monolithic choice is a deliberate bet that raw performance and a unified code base outweigh the isolation a microkernel provides.

Monolithic Kernel with Modern Extensions

Linux is a monolithic kernel—all core subsystems execute in a single privileged address space. However, it achieves modularity through multiple mechanisms, shown in Figure 1-4.

The oldest is the loadable module: ordinary kernel code, compiled separately and linked into the running kernel on demand, which is how most device drivers and many filesystems reach memory. eBPF programs take a different route: user space hands the kernel bytecode that an in-kernel verifier proves safe before a JIT compiler turns it into native instructions, so tracing, networking, and security policy can be extended without writing kernel C at all. Rust drivers are still kernel code, but written in a language whose type system rules out whole classes of memory errors. Livepatch replaces individual functions in a running kernel—typically to apply a security fix without a reboot—and is itself delivered as a special module. sched_ext lets a BPF program implement an entire scheduling class. All five share the defining property of a monolithic design: once admitted, the extension runs in the kernel's own address space and privilege level (Ring 0 on x86_64, EL1 on ARM64); what differs is the gatekeeping—signature checks for modules, the verifier for BPF, the compiler for Rust. Chapter 7 covers sched_ext, Chapter 23 covers eBPF, Chapter 26 covers Rust, and Appendix B covers modules and livepatch.

Loadable Kernel Modules: Microkernel Benefits Without the Cost

To achieve many of the theoretical advantages of microkernels without introducing performance penalties, the Linux kernel offers modules. A module is an object file whose code can be linked to (and unlinked from) the kernel at runtime. The object code typically implements a filesystem, a device driver, a network protocol, or other features at the kernel's upper layer.

Unlike the external layers of microkernel operating systems, a module does not run as a separate process. Instead, it is executed in Kernel Mode on behalf of the current process, exactly like any other statically linked kernel function. In Linux 7.0.12, the module subsystem is implemented across 16 source files in kernel/module/ (over 7,000 lines), with core loading logic in kernel/module/main.c.

Table 1-5. Advantages of Loadable Modules
AdvantageDescription
Modularized approach Because any module can be linked and unlinked at runtime, developers must introduce well-defined software interfaces to access data structures. This enforces clean API boundaries via EXPORT_SYMBOL() and EXPORT_SYMBOL_GPL().
Platform independence A module does not depend on a fixed hardware platform. A SCSI driver module works on x86_64 and ARM64 alike — the kernel's device model provides the abstraction layer.
Frugal memory usage A module can be loaded when needed and unloaded when no longer useful — vital for embedded systems with limited RAM (CONFIG_MODULE_UNLOAD).
No performance penalty Once linked, module code is equivalent to statically linked kernel code. Function calls are ordinary C calls — no message passing, no context switches, no serialization overhead.
Key difference from microkernels: A module executes in the same address space as the rest of the kernel, with the same privileges. There is no IPC overhead, no context switch, and no message serialization. The tradeoff is that a buggy module can crash the entire kernel — which is why module signing, strict RWX enforcement, and eBPF's verified sandbox exist as complementary approaches.

Preemption Models

A preemption model decides when a task running kernel code can be forced off the CPU in favor of a more urgent one. The 2.6.11 kernel offered a single compile-time switch, CONFIG_PREEMPT. Linux 7.0 has a richer menu, defined in kernel/Kconfig.preempt, but it also narrows that menu on modern architectures, as Table 1-6 shows.

Table 1-6. Preemption Models
Config OptionBehaviorAvailability in 7.0
PREEMPT_NONENo forced preemption; tasks yield only at cond_resched() or when they blockOnly on architectures that cannot preempt (ARCH_NO_PREEMPT)
PREEMPT_VOLUNTARYExtra explicit preemption points in long kernel pathsOnly on architectures without lazy preemption
PREEMPTFull preemption whenever no lock, IRQ-off, or preempt-off section is activeAll preemptible architectures
PREEMPT_LAZYLike full preemption, but a normal (SCHED_NORMAL) task is preempted only at the next tick or return to user spaceDefault on x86_64, ARM64, and other ARCH_HAS_PREEMPT_LAZY architectures
PREEMPT_RTSpinlocks become sleeping, priority-inheriting rt_mutex locks; interrupts are threadedSeparate option on top of the choice (EXPERT and ARCH_SUPPORTS_RT)

The first four entries form a single Kconfig choice. Commit 7dadeaa6e851 ("sched: Further restrict the preemption modes"), merged for 7.0, removed the two oldest models from architectures that implement lazy preemption: PREEMPT_NONE now survives only where the architecture cannot preempt at all, and PREEMPT_VOLUNTARY only where ARCH_HAS_PREEMPT_LAZY is absent. Because x86_64 and ARM64 both select ARCH_HAS_PREEMPT_LAZY, a 7.0 kernel for either offers exactly two models—full and lazy—with PREEMPT_LAZY as the default. Lazy preemption recovers most of the throughput the server-oriented models used to provide: when a normal task should be preempted, the scheduler sets a lazy need-resched flag that is honored only at the next timer tick or on return to user space, so a lock holder is rarely interrupted mid-section, while real-time tasks still preempt immediately. With CONFIG_PREEMPT_DYNAMIC, the model can also be chosen at boot with the preempt= parameter (full or lazy on these architectures), handled in kernel/sched/core.c. Chapter 7 examines how the scheduler acts on these flags.

PREEMPT_RT was developed out-of-tree for nearly 20 years before being fully merged into mainline in Linux 6.12. It transforms most spinlocks into sleeping rt_mutex locks, forces interrupt handlers into threads, and makes softirq processing preemptible, enabling bounded worst-case latencies for industrial control, robotics, and audio. Because it is a separate bool rather than a member of the choice, it is layered on top of the selected model; x86_64 and ARM64 both select ARCH_SUPPORTS_RT.

Linux Versions

The kernel has gone through several versioning schemes.

As Figure 1-6 shows, the numbering has evolved alongside the project's development model. The early 1.x kernels gave way in the late 1990s to the famous even/odd convention of the 2.0 through 2.4 series, in which an even second number (2.0, 2.2, 2.4) marked a stable branch meant for users and an odd one (2.1, 2.3) marked the unstable development branch where new work happened. The 2.6 series abandoned that split, keeping a single line that absorbed new features continuously, and the numbering has been essentially cosmetic ever since: the jumps to 3.x, 4.x, 5.x, 6.x, and now 7.x do not mark architectural breaks but simply reset the minor number before it grows uncomfortably large. Along the way the major series happen to coincide with landmark features—the arm64 port and the eBPF bpf() system call in the 3.x era, XDP, BTF, and RISC-V in 4.x, io_uring in 5.x, and in 6.x merged Rust, MGLRU, the EEVDF scheduler, sched_ext, and a mainline PREEMPT_RT, alongside removals such as the SLAB allocator (6.8) and bcachefs (6.18). The 7.0 release itself, tagged in April 2026, is notable mainly for narrowing the preemption choices described earlier—but these are milestones of the continuous development model, not consequences of the version bumps themselves.

The version is defined in the top-level Makefile:

# From /Makefile
VERSION = 7
PATCHLEVEL = 0
SUBLEVEL = 12

Since the 2.6 era, the kernel has abandoned the even/odd stable/development split. Major version bumps (e.g., 6→7) are cosmetic—Linus increments them when the minor number gets "uncomfortably large."

Release Categories

The kernel.org website maintains several categories of releases:

These categories correspond to stages in a kernel's life, each with its own maintainer and purpose. Mainline is the single tree where all new features are integrated; Linus Torvalds releases it on a time-based cadence of roughly nine to ten weeks, each cycle opening with a two-week merge window in which new work is pulled, followed by a series of prepatch or release-candidate builds (-rc1 through -rc7 or so) that accept only bug fixes as the release stabilizes. When a mainline version is released it becomes the basis for a stable series—the 7.0.1, 7.0.2, … updates that Greg Kroah-Hartman and Sasha Levin curate—which backports only fixes that meet strict rules: each must correct a real bug or security issue and must already be in mainline. This book tracks such a stable release, 7.0.12. Finally, a small number of stable series are designated longterm (LTS) and maintained with critical fixes for several years rather than a few months, which is what lets products commit to a kernel and receive security updates without chasing every mainline release.

Basic Operating System Concepts

The kernel has two main objectives: interact with hardware components, and provide an execution environment for user applications. To enforce separation between user programs and hardware, modern CPUs provide multiple execution modes, compared for x86_64 and ARM64 in Figure 1-8.

This chapter's remaining sections introduce the operating-system concepts the rest of the book assumes: the split between kernel and user mode, the multiuser model of users and permissions, and the process abstraction. How a process actually crosses into the kernel is taken up in the tour of the kernel later in the chapter. Readers already fluent in Unix fundamentals can skim these; readers newer to them will find here the vocabulary the later chapters build on.

The essential idea is that the processor runs code in one of two relevant modes. In user mode, a program can execute ordinary instructions and touch only its own memory; the privileged instructions that configure the MMU, program devices, or mask interrupts are forbidden. In kernel mode, all of that is permitted. The kernel runs in kernel mode with complete control of the machine, while every user process runs in user mode and must ask the kernel—through the system-call mechanism described later—to perform any operation that touches hardware or crosses another process's boundary. This single hardware-enforced distinction is what makes the kernel's protection guarantees possible: a buggy or malicious program simply cannot execute the instructions that would let it bypass them.

As Figure 1-8 shows, the two architectures name these modes differently. x86_64 defines four privilege rings, 0 through 3, but Linux uses only two of them: Ring 0 for the kernel and Ring 3 for user space, leaving rings 1 and 2 unused. ARM64 instead defines a stack of exception levels: EL0 runs user code and EL1 runs the kernel, exactly mirroring Ring 3 and Ring 0, while the two higher levels serve roles outside the x86 ring model—EL2 for a hypervisor (where KVM runs) and EL3 for the secure-monitor firmware. Throughout this book, then, “kernel mode” means Ring 0 on x86_64 and EL1 on ARM64, and “user mode” means Ring 3 or EL0; the transitions between them are the subject of Chapter 10.

Multiuser Systems and User/Group Management

Linux is a multiuser operating system — multiple people can interact with the computer simultaneously, running programs, reading files, and using CPU and memory, without their data bleeding into each other's workspaces or crashing the machine. Linux didn't add multiuser support as an afterthought; it was built from the ground up as a multiuser system, inheriting this DNA from Unix, which was designed in the 1970s for shared mainframes.

Design Philosophy: Three Pillars

User Database: /etc/passwd, /etc/shadow, and /etc/group

Linux does not care about human-readable usernames internally — the kernel works entirely with numeric UIDs and GIDs. The mapping between names and numbers is stored in user-space database files:

Supplementary Groups

In addition to a primary GID, each process can belong to a set of supplementary groups. These are stored in a struct group_info referenced from struct cred. When the kernel checks file access permissions, it checks against the effective UID, the effective GID, and all supplementary groups.

The supplementary group list is set by setgroups() (typically called by the login process after authenticating the user) and inherited across fork() and execve(). The kernel sorts the group list internally for efficient binary search during permission checks.

A Unix file is an information container structured as a sequence of bytes. The kernel does not interpret the contents of a file — it treats all files as unstructured byte streams. Hard and Soft Links

A filename in a directory is a hard link — a mapping from a name to an inode number. The same file (inode) can have multiple hard links in different directories:

The Process/Kernel Model

A process runs in User Mode until something forces it into Kernel Mode. There are three ways in:

  1. System calls — voluntary requests (SYSCALL on x86_64, SVC on ARM64)
  2. Exceptions — synchronous events caused by the current instruction (page faults, illegal instructions, divide-by-zero)
  3. Interrupts — asynchronous hardware events (disk, network, timer)

In every case the kernel runs on behalf of the current process, on that process's own kernel stack, and returns to User Mode when it is done—unless the scheduler decides on the way out that another task should run. The kernel is therefore not a separate process watching the others; it is code that each process executes in a privileged mode. The exceptions are kernel threads, such as kworker and ksoftirqd, which run only in Kernel Mode and have no user address space of their own. The system-call path, the most common way in, differs in detail between the two reference architectures:

🔵 x86_64 System Call

  1. User: SYSCALL instruction, number in rax
  2. CPU: switch to Ring 0, jump to the address in the LSTAR MSR
  3. Kernel: entry_SYSCALL_64 (arch/x86/entry/entry_64.S) calls do_syscall_64()
  4. Dispatch: x64_sys_call(), a generated switch on the number (arch/x86/entry/syscall_64.c)
  5. Return: SYSRET back to Ring 3 (or IRET on the slow path)

🟢 ARM64 System Call

  1. User: SVC #0 instruction, number in x8
  2. CPU: exception to EL1, jump into the VBAR_EL1 vector table (arch/arm64/kernel/entry.S)
  3. Kernel: el0t_64_sync_handler() → el0_svc() (arch/arm64/kernel/entry-common.c)
  4. Dispatch: invoke_syscall() indexes sys_call_table[x8] (arch/arm64/kernel/syscall.c)
  5. Return: ERET back to EL0

On x86_64 the familiar sys_call_table[] array still exists, but since the Spectre-era hardening it is kept only for tracing and auditing; dispatch goes through the switch in x64_sys_call(), which avoids an indirect call. CPUs with FRED (Flexible Return and Event Delivery) enter through arch/x86/entry/entry_64_fred.S instead. ARM64 still uses an array, but clamps the index with array_index_nospec() so that a mispredicted bounds check cannot be exploited. Chapter 4 covers the exception and interrupt entry paths and Chapter 10 the system-call machinery in full.

Not every service needs the trip. The kernel maps a vDSO (virtual Dynamic Shared Object) into every process—a small shared library containing user-mode implementations of time queries such as clock_gettime() and gettimeofday(). These read clock data that the kernel publishes in a shared page, so they complete without a mode switch at all.

Process Implementation

As described in the "Processes" section above, every process is represented by a struct task_struct (include/linux/sched.h) with approximately 316 fields in Linux 7.0.12. The task_struct is the kernel's central per-process data structure — all kernel subsystems access it to determine the process's identity, state, and resources.

Linux uses the same task_struct for both processes and threads. Threads are simply processes that share certain resources (address space, file descriptors, signal handlers) through clone flags. A thread group is identified by its TGID (Thread Group ID), which equals the PID of the group leader. The getpid() system call actually returns the TGID, not the per-thread PID.

Process creation (fork()/clone()/clone3()) and the entire lifecycle — including Copy-On-Write, exec(), zombies, and process groups — are covered in the "Process Management" section below.

Process Hierarchy and Namespaces

Every process except the first has a parent, so the processes on a system form a tree rooted at init (PID 1). Linux 7.0 layers namespaces on top of this model: each process belongs to one namespace of each of eight types, and a namespace gives its members a private view of one class of resource—their own PID numbering, mount table, network stack, hostname, and so on. A process inside a new PID namespace can thus be PID 1 in its own tree while having an ordinary PID in its parent's.

Namespaces are the foundation of container technologies like Docker and Kubernetes. Together with cgroups v2 (which limit and account for resource usage), they enable lightweight process isolation without full virtualization. The eight namespace types are listed in Containers, Namespaces, and Cgroups later in this chapter, and Chapter 25 covers both mechanisms in depth.

Process Address Space

Each process has a virtual address space described by struct mm_struct (include/linux/mm_types.h), containing the page table pointer (pgd), the maple tree of VMAs (mm_mt), and the mmap_lock read-write semaphore. Each virtual memory region is a struct vm_area_struct:

struct vm_area_struct {
    unsigned long vm_start;      /* start address (inclusive) */
    unsigned long vm_end;        /* end address (exclusive) */
    struct mm_struct *vm_mm;     /* owning mm_struct */
    pgprot_t vm_page_prot;       /* page protection flags */
    vm_flags_t vm_flags;         /* VM_READ, VM_WRITE, VM_EXEC, ... */
};

The excerpt shows only the fields that define a region; the full structure also records the backing file and offset, the anonymous-memory chain, and the operations table used to handle faults. A typical address space holds dozens to hundreds of VMAs, laid out as in Figure 1-20: program text, data, and BSS at the bottom; the heap growing upward from brk; shared libraries and other mmap() regions allocated top-down; the stack at the top of user space; and, above a non-canonical hole, the kernel half that user mode cannot touch. The Linux kernel is reentrant — multiple processes can execute kernel code simultaneously. Shared data structures must be protected. Linux 7.0.12 provides a hierarchy of synchronization primitives:

Key rule: Spin locks must be held for very short durations and you must never sleep while holding one. Mutexes allow sleeping but cannot be used from interrupt context. RCU provides the highest read scalability — readers never block and never cache-bounce — which is why it's used for the routing table, dcache, and many other read-heavy data structures.

Kernel Preemption Disabling

The simplest form of protection on a single CPU is to prevent the current process from being preempted while accessing shared data:

preempt_disable();
/* access per-CPU data safely */
preempt_enable();

Defined in include/linux/preempt.h, these macros increment and decrement a per-thread preempt_count. While preempt_count > 0, the scheduler will not preempt the current task, even on a PREEMPT or PREEMPT_RT kernel.

Preemption disabling is lightweight but only protects against preemption on the same CPU — it does not protect against concurrent access from other CPUs or from interrupt handlers.

Interrupt Disabling

To protect against both preemption and interrupt handlers on the local CPU, the kernel can disable interrupts:

unsigned long flags;

local_irq_save(flags);      /* save interrupt state and disable */
/* critical section — safe from interrupts on this CPU */
local_irq_restore(flags);   /* restore previous interrupt state */

Alternatively, the simpler local_irq_disable() / local_irq_enable() pair can be used when nesting is not a concern. These are defined in include/linux/irqflags.h.

Like preemption disabling, interrupt disabling only protects the local CPU. On SMP systems, spinlocks are needed for cross-CPU protection.

Per-CPU Variables

The most efficient form of synchronization is to avoid sharing entirely. Per-CPU variables give each CPU its own copy of a data structure:

DEFINE_PER_CPU(int, my_counter);

/* Access on current CPU (preemption must be disabled) */
this_cpu_inc(my_counter);
int val = this_cpu_read(my_counter);

Defined in include/linux/percpu-defs.h. Per-CPU variables are used extensively for counters, caches, and per-CPU run queues.

Spin Locks

Spin locks are the fundamental synchronization primitive for short critical sections on SMP systems. A spin lock busy-waits (spins) until the lock becomes available:

spinlock_t my_lock;
spin_lock_init(&my_lock);

spin_lock(&my_lock);          /* acquire — spins if held by another CPU */
/* critical section */
spin_unlock(&my_lock);        /* release */

Mutexes

Mutexes are sleeping locks designed for longer critical sections where the overhead of a context switch is acceptable:

struct mutex my_mutex;
mutex_init(&my_mutex);

mutex_lock(&my_mutex);        /* acquire — sleeps if held by another task */
/* critical section — may sleep here (e.g., allocate memory, do I/O) */
mutex_unlock(&my_mutex);      /* release */

Defined in include/linux/mutex.h. Key properties of mutexes:

  • The lock has an owner — only the task that locked it can unlock it
  • Recursive locking is not allowed (a task will deadlock on itself)
  • The task may sleep while holding the mutex
  • Cannot be used from interrupt context (because interrupts cannot sleep)
  • Supports adaptive spinning — if the owner is currently running on another CPU, the waiter briefly spins rather than sleeping (avoiding the cost of a context switch for short hold times)

The static initializer DEFINE_MUTEX(name) creates a mutex at compile time.

Semaphores

Semaphores are a more general sleeping synchronization mechanism with a counter rather than a simple locked/unlocked state:

struct semaphore my_sem;
sema_init(&my_sem, 3);        /* allow up to 3 concurrent holders */

down(&my_sem);                /* decrement counter; sleep if counter == 0 */
/* critical section */
up(&my_sem);                  /* increment counter; wake a waiter */

Defined in include/linux/semaphore.h. Unlike mutexes, semaphores:

  • Have no owner — up() can be called from a different context than down()
  • Can be used as counting semaphores (allowing N concurrent accessors)
  • Can be safely used from interrupt context (down_trylock() and up())

Semaphore variants include down_interruptible() (can be interrupted by a signal), down_killable() (interrupted only by fatal signals), and down_timeout().

In modern kernels, mutexes are preferred over binary semaphores for mutual exclusion because mutexes have better debugging support (ownership tracking) and performance optimizations (adaptive spinning).

Read-Write Semaphores

When data is read much more often than written, read-write semaphores allow concurrent readers while ensuring exclusive access for writers:

struct rw_semaphore my_rwsem;
init_rwsem(&my_rwsem);

down_read(&my_rwsem);         /* shared access — multiple readers allowed */
/* read data */
up_read(&my_rwsem);

down_write(&my_rwsem);        /* exclusive access — no other readers or writers */
/* modify data */
up_write(&my_rwsem);

Defined in include/linux/rwsem.h. The VMA mmap_lock in struct mm_struct is a prominent example — page fault handling takes the read lock (allowing concurrent faults), while operations that modify the VMA tree take the write lock.

RCU (Read-Copy-Update)

RCU is a lock-free synchronization mechanism optimized for read-heavy workloads. Readers access shared data without acquiring any lock or writing any shared memory—they only mark a read-side critical section, which on a non-preemptible kernel costs nothing more than disabling preemption and on a preemptible (CONFIG_PREEMPT_RCU) kernel increments a per-task nesting counter:

rcu_read_lock();              /* mark start of RCU read-side critical section */
ptr = rcu_dereference(global_ptr);  /* safely read the pointer */
/* use ptr — guaranteed valid until rcu_read_unlock() */
rcu_read_unlock();

Writers create a new copy of the data structure, update the pointer atomically, and then wait for all existing readers to finish before freeing the old copy:

new_data = kmalloc(...);
/* initialize new_data */
old_data = rcu_dereference(global_ptr);
rcu_assign_pointer(global_ptr, new_data);
synchronize_rcu();            /* wait for all readers to complete */
kfree(old_data);              /* safe to free the old version */

Defined in include/linux/rcupdate.h. RCU is used pervasively throughout the kernel — the routing table, the dcache (directory entry cache), and many other data structures rely on RCU for scalable, low-overhead read access.

Sequence Locks

Sequence locks provide a lightweight mechanism for data that is read very frequently and written very rarely. Readers never block the writer:

seqlock_t my_seq;
seqlock_init(&my_seq);

/* Writer */
write_seqlock(&my_seq);
/* modify data */
write_sequnlock(&my_seq);

/* Reader — retry loop, never blocks */
unsigned seq;
do {
    seq = read_seqbegin(&my_seq);
    /* read data */
} while (read_seqretry(&my_seq, seq));

Defined in include/linux/seqlock.h. The classic use case is timekeeping: the kernel's clock state in kernel/time/timekeeping.c is protected by a sequence counter (tk_core.seq) that ktime_get() and the clock_gettime() path read millions of times a second, while only the timer tick updates it. The 2.6-era xtime variable that played this role no longer exists.

Avoiding Deadlocks

Deadlocks occur when two or more execution contexts each hold a lock and wait for a lock held by the other. The kernel uses several strategies to prevent deadlocks:

  1. Lock ordering — always acquire multiple locks in a consistent, predefined order. The kernel documents lock ordering requirements in subsystem headers and enforces them with lockdep.
  2. Lockdep — a runtime lock dependency validator (CONFIG_LOCKDEP). Lockdep tracks every lock acquisition and detects potential deadlocks, lock ordering violations, and incorrect API usage before a real deadlock occurs. It reports violations through lockdep_assert_held() and related assertions. Documentation is in Documentation/locking/lockdep-design.rst.
  3. Try-lock variants — spin_trylock(), mutex_trylock(), and down_trylock() attempt to acquire a lock without blocking, returning immediately if the lock is unavailable. This breaks potential deadlock cycles.
  4. Lock nesting rules — the kernel enforces rules about what types of locks can be nested inside others. For example, you must never acquire a sleeping lock (mutex) while holding a spin lock. On PREEMPT_RT kernels, these rules are documented in Documentation/locking/locktypes.rst.
  5. Minimal critical sections — hold locks for the shortest time possible. Avoid performing I/O, memory allocation with GFP_KERNEL, or any operation that may sleep while holding a spin lock.

Process Management

The kernel creates processes with fork() (or more precisely, the clone() system call), which duplicates the calling process. In Linux 7.0.12, kernel_clone() in kernel/fork.c is the unified entry point — fork(), vfork(), and clone3() all funnel into it. The heavy lifter is copy_process(), which allocates a new task_struct, duplicates or shares resources depending on clone flags, and returns the new child.

Unix makes a clean distinction between a process and the program it executes. Three system call families embody this separation:

Table 1-19. Process-Management System Calls
System CallPurposeLinux 7.0.12 Implementation

_exit()Terminate the calling processdo_exit() in kernel/exit.c
execve()Load a new program into the current processdo_execveat_common() in fs/exec.c

When fork() is called, the kernel creates a child process that is an almost exact copy of the parent. The child then typically calls execve() to replace its address space with a new program — the classic fork-exec pattern. After execve() succeeds, the process resumes execution at the entry point of the newly loaded program, with a brand-new address space.

Process Relationships: The Process Tree

The process that invokes fork() is the parent; the new process is the child. Every task_struct maintains pointers that form a process tree (include/linux/sched.h):

struct task_struct {
    struct task_struct __rcu  *real_parent;  /* biological parent */
    struct task_struct __rcu  *parent;       /* recipient of SIGCHLD, wait4() */
    struct list_head          children;      /* list of child processes */
    struct list_head          sibling;       /* linkage in parent's children list */
    struct task_struct        *group_leader; /* thread group leader */
};

Note the distinction: real_parent is the process that originally forked this one, while parent receives SIGCHLD and collects exit status. These differ only when a process is being ptraced — the debugger becomes the parent.

Copy-On-Write (COW)

A naïve fork() would duplicate the entire address space — all page tables and physical pages. Modern Linux uses Copy-On-Write to defer page duplication:

This means a fork() followed by execve() — the most common pattern — is very cheap: the child never writes to the parent's pages because execve() replaces the entire address space. Only pages actually modified incur the copy cost.

vfork() is even cheaper — it avoids copying page tables entirely by sharing the parent's mm_struct (CLONE_VM) and suspending the parent until the child calls execve() or _exit().

When a process calls execve(), the kernel loads a new program through do_execveat_common() (fs/exec.c), which opens the executable, calls begin_new_exec() to tear down the old address space, sets up a new address space, and jumps to the entry point. Multiple binary formats are supported:

Zombie Processes

When a process terminates, it does not disappear immediately. The kernel calls do_exit() (kernel/exit.c), which releases most resources, records the exit status, sets exit_state = EXIT_ZOMBIE, sends SIGCHLD to the parent, and calls schedule(). The task_struct remains allocated so the parent can retrieve the exit status with wait()/waitpid().

Zombie accumulation is a common bug: if a parent never calls wait(), zombie task_structs accumulate, consuming PID space and kernel memory. The fix is to either call wait(), install a SIGCHLD handler with SA_NOCLDWAIT, or set the SIGCHLD disposition to SIG_IGN — the kernel then auto-reaps children. If the parent exits first, children are reparented to init (PID 1) or a designated subreaper (prctl(PR_SET_CHILD_SUBREAPER)).

Process Scheduling

The scheduler decides which runnable task each CPU executes next. Its core, kernel/sched/core.c, knows nothing about policy: it delegates every decision to a stack of scheduling classes, consulted in strict priority order. The stop class (used internally for CPU hotplug and task migration) comes first, then SCHED_DEADLINE, the real-time SCHED_FIFO/SCHED_RR class, the fair class that runs ordinary SCHED_NORMAL, SCHED_BATCH, and SCHED_IDLE tasks, the sched_ext class, and finally the per-CPU idle task. A lower class runs only when every higher class has nothing to do.

The fair class is where most tasks live, and it has been rewritten twice since Linux 2.6.11. The O(1) scheduler of that release gave way in 2.6.23 to the Completely Fair Scheduler (CFS), which ordered tasks by accumulated virtual runtime; since Linux 6.6 the same class implements EEVDF (Earliest Eligible Virtual Deadline First), which also gives each task a virtual deadline so that latency-sensitive tasks with short time slices are picked sooner. sched_ext, merged in 6.12, lets a BPF program supply a whole scheduling policy at run time and falls back to the fair class if the program misbehaves. On heterogeneous ARM64 systems, Energy-Aware Scheduling places tasks on big or little cores according to an energy model. The comparison below and Figure 1-25 summarize the change; Chapter 7 covers the scheduler in detail.

Linux 2.6

  • O(1) scheduler
  • Simple priority arrays
  • No energy awareness
  • Big Kernel Lock (BKL)
  • SCHED_FIFO/SCHED_RR only for RT

Linux 7.0 (this book)

  • EEVDF scheduler (virtual deadlines)
  • sched_ext (BPF-based scheduling)

Memory management is the most complex and performance-critical subsystem in the kernel, and it has changed more than any other since Linux 2.6: 5-level page tables, the SLUB allocator, maple trees for VMAs, folios and the XArray in the page cache, and Multi-Gen LRU for page reclaim. Caching

The kernel uses several layers of caching to reduce I/O:

Page Cache — the primary disk cache. File data passes through the page cache, which keeps recently accessed data in RAM. Linux 7.0.12 has restructured it around folios (struct folio) — an abstraction representing one or more physically contiguous pages as a single unit. The page cache uses an XArray (include/linux/xarray.h), which replaced the radix tree, to map (address_space, offset) pairs to folios with RCU-safe lock-free lookups. Large folios let a filesystem cache a file in multi-page units, cutting per-page overhead for big files. Dirty data is written back by per-device bdi_writeback work items running on workqueues, which replaced the 2.6-era pdflush kernel threads.

Dentry Cache (dcache) — caches filesystem directory entries (fs/dcache.c). Every pathname lookup checks the dcache first; a hit avoids reading the directory from disk entirely.

Inode Cache — caches struct inode objects (fs/inode.c). After a file's inode is read from disk, it stays cached until memory pressure forces eviction.

Device Drivers

The kernel interacts with hardware through device drivers. Linux 7.0 has a mature device model built around:

  • struct device — represents a hardware or virtual device
  • struct device_driver — the code that drives a device
  • struct bus_type — the bus connecting devices and drivers (PCI, USB, I2C, SPI, platform, etc.)
  • kobject/kset — kernel objects that form the basis of the device hierarchy
  • sysfs (/sys) — a virtual filesystem exposing the device tree to user space

Key improvements since Linux 2.6.11:

  • Device tree (OF — Open Firmware): On ARM64 and many embedded platforms, hardware is described by a device tree blob (DTB) rather than being hardcoded. The kernel parses the device tree at boot to discover and configure devices. Source: drivers/of/.
  • ACPI: On x86_64 (and increasingly ARM64 servers), hardware is described by ACPI tables. The kernel's ACPI subsystem (drivers/acpi/) handles power management, device enumeration, and thermal management.
  • Managed resources (devres): The devm_* API (include/linux/device.h) automatically frees resources when a device is removed, drastically reducing resource leak bugs in drivers.
  • regmap: A unified register access API (include/linux/regmap.h) that abstracts I2C, SPI, MMIO, and other register access methods.

Hardware Dependency

Linux 7.0.12 has 21 directories under arch/: 20 CPU architectures plus um, User-Mode Linux, which runs the kernel as an ordinary process on another Linux system. All architecture-dependent code lives there.

One of the kernel's defining design principles is a clean separation between architecture-independent code—the schedulers, filesystems, memory-management policy, and network stacks that make up the bulk of the tree and are written once for all machines—and the architecture-dependent code that adapts those subsystems to a specific processor. The latter lives under arch/, one directory per architecture, and supplies the pieces that genuinely differ between CPUs: the low-level context-switch and interrupt-entry assembly, the page-table format, the atomic and memory-barrier instructions, the system-call entry path, and the boot code. Everything above that layer calls into it through a common interface, so the same fair.c scheduler or ext4 driver runs unchanged whether the machine is an x86_64 server or an arm64 phone. This book uses those two architectures as its running examples throughout; Figure 1-28 places them among all the architectures the kernel supports.

The architectures fall into rough tiers of prominence. At the top are the two this book follows—x86_64, which dominates servers and desktops, and arm64, which dominates mobile and embedded devices and is now a major server architecture as well— both first-class targets with the deepest optimization and the widest hardware support. A growing tier, led by RISC-V and LoongArch, is where much current momentum lies as open and new instruction sets gain kernel support. A large established tier (32-bit ARM, PowerPC, s390 for IBM mainframes, MIPS, SPARC) remains maintained for the platforms that still depend on it, and an embedded/legacy tier keeps a long tail of niche and older processors alive. The dashed box records the reverse process: the kernel also removes architectures once they have no users left—Itanium (ia64) was dropped in 6.7, and many others have gone before it—which keeps the architecture-dependent code from accumulating dead weight. What matters for this book is that the concepts are universal; only the arch/ details differ, and we draw those from x86_64 and arm64.

Modern Linux Subsystems

Several major subsystems either did not exist in kernel 2.6 or have been transformed since. These are covered in dedicated chapters but deserve an introduction here.

Taken together, the four subsystems introduced below trace the directions in which the kernel has grown most since Linux 2.6, and each answers a different modern demand. eBPF makes the kernel programmable, letting verified user-supplied code run safely at kernel hooks. io_uring makes I/O asynchronous and low-overhead, replacing per-operation system calls with shared-memory rings. Namespaces and cgroups make one kernel present many isolated, resource-bounded views of the system—the foundation of containers. And Rust makes new kernel code memory-safe at compile time. The short previews here give just enough to place each in the architecture; they are the subjects of Chapters 23 through 26 in the book's final part, where each is developed in full against the 7.0 source.

eBPF Subsystem

eBPF has evolved from a simple packet filter into a general-purpose in-kernel virtual machine. Programs are verified for safety, JIT-compiled, and can attach to numerous kernel hooks:

  • Tracepoints and kprobes — for observability and tracing
  • XDP (eXpress Data Path) — for high-performance packet processing
  • cgroup hooks — for resource control
  • LSM hooks — for security policy enforcement
  • Scheduler (sched_ext) — for custom scheduling algorithms
  • Network TC — for traffic classification

The eBPF subsystem is implemented in kernel/bpf/ with key files:

  • verifier.c — the static analyzer that ensures program safety
  • core.c — the BPF interpreter and JIT dispatch
  • syscall.c — the bpf() system call implementation

Chapter 23 covers eBPF in detail.

io_uring

io_uring is a high-performance asynchronous I/O framework introduced in Linux 5.1. It uses a pair of shared memory ring buffers between user space and the kernel:

  • Submission Queue (SQ) — user space writes I/O requests (SQEs)
  • Completion Queue (CQ) — kernel writes I/O completions (CQEs)

This design can completely eliminate system call overhead in the fast path: the kernel can poll the submission queue and process requests without the user ever calling a system call. io_uring supports file I/O, networking, timers, and many other operations. Registered buffers and files let applications pre-pin resources, reducing setup overhead for repeated operations.

The io_uring subsystem has its own top-level directory (io_uring/), reflecting its importance. Key files include:

  • io_uring.c — core ring buffer management
  • rw.c — read/write operations
  • net.c — network operations
  • sqpoll.c — kernel-side submission queue polling

Chapter 24 covers io_uring in detail.

Containers, Namespaces, and Cgroups

Modern containers are not a single kernel feature but a combination of two independent mechanisms that together let one kernel present many isolated views of the system: namespaces, which virtualize what a process can see, and control groups (cgroups), which limit what it can consume.

Linux provides eight namespace types, each selected by a CLONE_NEW* flag to clone() or unshare():

  • Mount (CLONE_NEWNS) — the set of filesystem mounts
  • UTS (CLONE_NEWUTS) — hostname and domain name
  • IPC (CLONE_NEWIPC) — System V IPC and POSIX message queues
  • PID (CLONE_NEWPID) — the process-ID number space
  • Network (CLONE_NEWNET) — interfaces, addresses, and routing tables
  • User (CLONE_NEWUSER) — UID/GID mappings and capabilities
  • Cgroup (CLONE_NEWCGROUP) — the cgroup-hierarchy root a process sees
  • Time (CLONE_NEWTIME) — the boot and monotonic clock offsets

Control groups—organized in Linux 7.0 around the unified (v2) hierarchy—apply resource limits and accounting through per-resource controllers such as cpu, memory, io, and pids. The implementation lives in kernel/cgroup/, while the namespace machinery is spread across the kernel with kernel/nsproxy.c tying a task's namespaces together. A container runtime combines a set of namespaces and a cgroup to build the isolated, resource-bounded environment that tools like Docker and Kubernetes present.

Chapter 25 covers containers, namespaces, and cgroups in detail.

Rust Language Support

Linux 7.0 includes support for writing kernel code in Rust, a systems programming language that provides memory safety and thread safety guarantees at compile time. The Rust infrastructure is in the rust/ directory:

  • rust/kernel/ — safe Rust abstractions over kernel C APIs
  • rust/macros/ — procedural macros (for example, #[module] for defining kernel modules)
  • rust/uapi/ — Rust bindings for UAPI headers

Rust support is still in its early stages, with initial driver support and ongoing work to provide safe abstractions for more kernel APIs, including wrappers for reference- counted and synchronized patterns such as Arc-like ownership and Mutex-style locking in kernel-safe forms. The Kernel Build System: Kconfig, Kbuild, and Makefiles

Building the Linux kernel is a remarkably complex task — Linux 7.0.12 contains about 37 million lines of C, assembly, and Rust source across more than 90,000 files, supporting 21 architecture ports, hundreds of filesystems, and thousands of device drivers. The kernel uses a custom build system composed of three cooperating layers:

  1. Kconfig — the configuration language that defines what to build
  2. Kbuild — the build engine that knows how to build it
  3. Make — GNU Make orchestrates the process via hierarchical Makefiles

The version is defined at the very top of the root Makefile:

# /Makefile
VERSION = 7
PATCHLEVEL = 0
SUBLEVEL = 12
NAME = Baby Opossum Posse

The single idea that ties these layers together is that the build is configuration-driven. Kconfig collects the user's choices into one file, .config, which records for every option whether it is built in (y), built as a module (m), or left out. Kbuild then reads that file and compiles only the corresponding source, so the very same tree of 37 million lines produces a few-megabyte kernel for a tiny embedded device or a full-featured one for a server, purely according to the configuration. Figure 1-31 traces the flow: Kconfig turns the Kconfig files and the user's selections into .config; Kbuild turns .config plus the per-directory Makefiles into object files; and a final link-and-package step produces vmlinux, the compressed boot image, and the loadable .ko modules. Multi-File Modules

If a module is built from multiple source files, use the <module>-y pattern:

obj-$(CONFIG_EXT2_FS) += ext2.o

ext2-y := balloc.o dir.o file.o ialloc.o inode.o \
          ioctl.o namei.o super.o symlink.o trace.o

ext2-$(CONFIG_EXT2_FS_XATTR)     += xattr.o xattr_user.o xattr_trusted.o
ext2-$(CONFIG_EXT2_FS_POSIX_ACL) += acl.o

This excerpt is from fs/ext2/Makefile. Kbuild compiles each .o file separately, then links them into ext2.o, which becomes ext2.ko after the module post-processing stage (scripts/Makefile.modpost) when CONFIG_EXT2_FS=m. The ext2-$(CONFIG_…) lines show the idiom for optional parts of a module: each file is added to the composite object only when its own option is enabled.

Practical Example: Adding a New Driver

To illustrate the entire Kconfig/Kbuild workflow, here is a complete example of adding a simple character device driver to the kernel tree.

Step 1: Create the Driver Source

Create drivers/char/hello_dev.c:

// SPDX-License-Identifier: GPL-2.0
/*
 * hello_dev - minimal example character device driver
 */
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/fs.h>
#include <linux/miscdevice.h>
#include <linux/uaccess.h>

#define HELLO_MSG "Hello from the kernel!
"

static ssize_t hello_read(struct file *file, char __user *buf,
                          size_t count, loff_t *ppos)
{
    return simple_read_from_buffer(buf, count, ppos,
                                  HELLO_MSG, sizeof(HELLO_MSG) - 1);
}

static const struct file_operations hello_fops = {
    .owner = THIS_MODULE,
    .read  = hello_read,
};

static struct miscdevice hello_misc = {
    .minor = MISC_DYNAMIC_MINOR,
    .name  = "hello",
    .fops  = &hello_fops,
};

static int __init hello_init(void)
{
    pr_info("hello_dev: registering misc device
");
    return misc_register(&hello_misc);
}

static void __exit hello_exit(void)
{
    misc_deregister(&hello_misc);
    pr_info("hello_dev: unregistered
");
}

module_init(hello_init);
module_exit(hello_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Example");
MODULE_DESCRIPTION("A minimal character device driver");

Step 2: Add the Kconfig Entry

Add to drivers/char/Kconfig (inside the menu "Character devices" block):

config HELLO_DEV
    tristate "Hello example character device"
    default n
    help
      A minimal example character device driver that creates /dev/hello
      and returns "Hello from the kernel!" when read.

      To compile as a module, choose M here: the module will be called
      hello_dev.

      If unsure, say N.

Step 3: Add the Kbuild Entry

Add one line to drivers/char/Makefile:

obj-$(CONFIG_HELLO_DEV) += hello_dev.o

That single line is all Kbuild needs. When CONFIG_HELLO_DEV=y, the driver is compiled and linked into vmlinux. When CONFIG_HELLO_DEV=m, it is compiled as the loadable module hello_dev.ko.

Step 4: Configure, Build, and Test

# Enable the driver (select M for module, Y for built-in)
make menuconfig
# Navigate: Device Drivers → Character devices → Hello example character device

# Build
make -j$(nproc) modules

# Load the module
sudo insmod drivers/char/hello_dev.ko

# Test it
cat /dev/hello
# Output: Hello from the kernel!

# Unload
sudo rmmod hello_dev

Building the Same Driver Out-of-Tree

Build and load:

cat /dev/hello                    # test

Build System Architecture Summary

  1. User runs make menuconfig → Kconfig scripts parse all Kconfig files recursively → generate .config
  2. User runs make → top-level Makefile processes .config, sets compiler flags, architecture variables
  3. Recursive descent → Kbuild enters each subdirectory, reads local Makefile, evaluates obj-y/obj-m against CONFIG_* values
  4. Compilation → each .c → .o via the compiler (with Kbuild-generated flags)
  5. Linking → all obj-y objects are archived into built-in.a per directory, then linked together into vmlinux
  6. Module post-processing → obj-m objects go through modpost (scripts/Makefile.modpost) to resolve symbols and generate .ko files
  7. Final image → vmlinux is compressed into bzImage (x86_64) or Image.gz (ARM64)

Checking, Testing, and Alternative Toolchains

A clean compile is only the first check a change has to pass. The source tree also carries its own static checkers, two test frameworks, and the hooks a fuzzer needs, and all of them are run from the same top-level Makefile or from scripts/ and tools/. The patch-submission checklist (Documentation/process/submit-checklist.rst) expects a developer to have run several of them before sending a patch:

# Static checks
make W=1 drivers/char/                            # extra warnings (W=2, W=3: more; W=e: errors)
make C=1                                          # sparse on recompiled files (C=2: all files)
make coccicheck MODE=report M=drivers/char/       # Coccinelle semantic patches
scripts/checkpatch.pl --strict 0001-hello.patch   # style and common mistakes in a patch
scripts/checkpatch.pl -f drivers/char/hello_dev.c # ... or in a whole file

# Tests
make kselftest TARGETS="timers size"              # user-space tests (tools/testing/selftests)
./tools/testing/kunit/kunit.py run                # in-kernel unit tests, booted under UML

# The LLVM toolchain
make LLVM=1 -j$(nproc)                            # clang, ld.lld, llvm-ar, llvm-nm, ...
make LLVM=1 ARCH=arm64 -j$(nproc)                 # cross-compile without CROSS_COMPILE

Static checkers. W=1 adds compiler warnings that, in the words of the make help text, "may be relevant and do not occur too often", and many maintainers expect new code to build without them. C=1 runs the checker named by $(CHECK), by default Sparse, on each C file next to the compiler. Sparse understands the kernel's own type annotations: it reports a __user pointer dereferenced directly instead of through copy_from_user() (Chapter 10, Section 4.5), an __iomem pointer used without the MMIO accessors (Chapter 13, Section 2.3), an __rcu pointer read without rcu_dereference(), and a __le32 or __be16 value mixed with a native integer without byte-order conversion. Coccinelle works at a higher level. Its spatch tool applies semantic patches, rules written like a unified diff of C code but with metavariables that match any expression, type, or statement, so one rule can find or rewrite a pattern wherever it occurs, however the code is formatted. scripts/coccinelle/ holds 76 such rules, in the api, free, iterators, locks, misc, null, and tests directories, and make coccicheck runs them in one of four modes: report, patch, context, or org. Developers also use Coccinelle for tree-wide API conversions, and such commits often quote the semantic patch that produced them. scripts/checkpatch.pl, a Perl script of about 7,900 lines that has been in the tree since 2.6.22, checks a patch or a file against the coding style in Documentation/process/coding-style.rst (lines over 100 columns, misplaced braces, and so on) and against a long list of common mistakes, such as a missing Signed-off-by: line or the use of a deprecated API. Every message type it can emit is explained in Documentation/dev-tools/checkpatch.rst. Like the compiler warnings, its output is a guide: Documentation/process/submitting-patches.rst calls it a guide, "not a replacement for human judgment", and code that reads better with a violation is best left alone. With a recent enough Clang, the compiler itself also checks lock usage through context analysis (Chapter 5, Section 8.6).

Tests. kselftest (tools/testing/selftests/, since Linux 3.3) collects user-space programs that test the running kernel through its system-call interface: more than a hundred target directories, from timers and mm to bpf, net, and seccomp. Tests are built and run on the kernel under test, with the TEST() and ASSERT_*() macros of kselftest_harness.h as an optional harness, and report results in the TAP format so that test robots can parse them. KUnit (lib/kunit/, since 5.5) tests kernel code from inside the kernel. A test suite is a set of C functions, compiled into the kernel or a module, that call internal functions directly and check the results with KUNIT_EXPECT_*() and KUNIT_ASSERT_*(). By default kunit.py run builds a User-Mode Linux kernel (ARCH=um) and boots it as an ordinary process, so a run takes seconds and needs no virtual machine, and --arch=x86_64 or --arch=arm64 runs the same tests under QEMU. About 250 source files in 7.0.12 define KUnit suites, and the examples in the Rust kernel crate's documentation are also run as KUnit tests (Chapter 26, Section 2.1).

Coverage and fuzzing. With CONFIG_KCOV (Linux 4.6) the compiler inserts a call to __sanitizer_cov_trace_pc() at the start of every basic block, and the kernel records the addresses these calls report into a buffer that one task shares with user space. A process opens /sys/kernel/debug/kcov, sizes the buffer with the KCOV_INIT_TRACE ioctl, maps it with mmap(), and enables collection with KCOV_ENABLE. From then on the buffer receives the address of every basic block that the kernel executes on behalf of that one task. Collection is per task and skips interrupts and inherently nondeterministic code such as the scheduler, so the coverage depends only on the system calls the task makes. Supporting this is one of the small jobs of the context-switch path (Chapter 3, Section 9.2). Coverage-guided fuzzers are the main users, above all syzkaller, an external project that generates programs of system calls from descriptions of their arguments, keeps those that reach new kernel code, and mutates them further. Its continuously running instance, syzbot, tests the mainline and several maintainer trees and reports each crash to the responsible mailing list, and fixes credit it with a Reported-by: syzbot+<id>@syzkaller.appspotmail.com tag. A fuzzer finds bugs only when they become visible, so it is run on kernels built with the runtime checkers that turn silent corruption into a report, such as KASAN (Chapter 2, Section 13.9) and lockdep (Chapter 5, Section 8).

Building with Clang. GCC remains the default compiler, but since Linux 5.7 LLVM=1 switches the whole toolchain to LLVM: Clang as the compiler, ld.lld as the linker, and LLVM's versions of ar, nm, objcopy, and the other binary utilities. LLVM=-18 selects versioned binaries such as clang-18, and LLVM=/path/to/llvm/ selects a toolchain directory. One Clang binary normally contains every back end, so cross-compiling needs only ARCH=. A few kernel features depend on this toolchain. Link-time optimization (CONFIG_LTO_CLANG_THIN or CONFIG_LTO_CLANG_FULL, since 5.12, supported on both x86_64 and arm64) requires Clang, ld.lld, and LLVM's ar and nm. With it, each object file holds LLVM bitcode rather than machine code, and code generation happens at the final link, where calls can be inlined across files. The kernel's control-flow integrity, kCFI (since 6.1), makes the compiler check a hash of the target function's type before every indirect call. Its option was CONFIG_CFI_CLANG until Linux 6.18 renamed it to CONFIG_CFI, in preparation for GCC support, but it still needs a compiler that accepts -fsanitize=kcfi. On arm64, CONFIG_SHADOW_CALL_STACK keeps return addresses on a separate stack addressed by register x18, out of reach of a stack buffer overflow. Rust support uses libclang for bindgen regardless of which C compiler builds the rest of the kernel.

Kernel Initialization: start_kernel()

When the system boots, firmware and a boot loader load the kernel image, and a short stretch of architecture-specific assembly sets up a stack and minimal page tables: x86_64_start_kernel() in arch/x86/kernel/head64.c on x86_64, __primary_switched in arch/arm64/kernel/head.S on ARM64. Both then call start_kernel() in init/main.c—x86_64 by way of x86_64_start_reservations()—the architecture-independent function that initializes every kernel subsystem in a carefully ordered sequence, shown in Figure 1-34.

The order is dictated by dependencies. setup_arch() comes first because everything else needs to know the machine: it parses the firmware's memory map (E820 or UEFI on x86_64, the device tree or ACPI on ARM64) and builds the early page tables. The memory-management core follows—mm_core_init() hands memory to the buddy page allocator and brings up the slab allocator—so that later subsystems can allocate. sched_init() creates the run queues and turns the boot code into the idle task of CPU 0, rcu_init() starts RCU, and init_IRQ(), hrtimers_init(), softirq_init(), and timekeeping_init() prepare interrupts and time. Only then does local_irq_enable() switch interrupts on; until that point the CPU runs with them masked. The second half sets up the caches and frameworks that need a working allocator and timer: fork_init() for task structures, security_init() for the Linux Security Modules, vfs_caches_init() for the dentry and inode caches and the root filesystem, and cgroup_init() for control groups.

The last call, rest_init(), creates the first two real tasks: kernel_init, which receives PID 1, and kthreadd, PID 2, the parent of all later kernel threads. The boot task itself then becomes CPU 0's idle loop. kernel_init finishes the remaining initialization—bringing up the other CPUs, running the built-in drivers' initcalls, mounting the root filesystem—and finally execs /sbin/init (typically systemd), so that PID 1 becomes the first user-space process. Appendix A follows this whole path, from power-on to user space, in detail.

An Overview of This Book

This book is organized into four parts, followed by two appendices, as Figure 1-35 shows. The order is bottom-up, so that each chapter builds on the ones before it, with a fourth part for subsystems that did not exist in 2.6.11.

Part II, Core Kernel (Chapters 4–10), covers the machinery every other subsystem relies on: interrupts and exceptions, kernel synchronization, timing measurements, process scheduling, the allocation of physical memory, process address spaces, and the system-call interface. Summary

This chapter set the stage for the rest of the book. It introduced the Linux kernel as it stands in version 7.0.12—a monolithic, Unix-compatible kernel of some 37 million lines that has evolved almost beyond recognition since the 2.6 kernel, yet keeps the same fundamental design: a single privileged program that mediates between hardware and user processes, built and shared under the GPL-2.0 license whose copyleft and syscall exception shape both how the kernel is developed and how code may legally be combined with it. We placed Linux among the surviving Unix-like systems, contrasting its monolithic design with QNX's microkernel to make the central trade-off—performance and a unified code base versus fault isolation—concrete, and we saw how loadable modules, eBPF, Rust, and livepatching give the monolith much of a microkernel's flexibility without its cost. We also saw that 7.0 narrows the preemption choices on x86_64 and arm64 to full and lazy preemption, with PREEMPT_RT available on top, and how the version numbers, release categories, and longterm kernels are organized.

The middle of the chapter reviewed the operating-system concepts the later chapters assume: the hardware-enforced split between kernel mode and user mode (Ring 0/3 on x86_64, EL1/EL0 on arm64); the multiuser model of users, groups, and permissions; the process abstraction built on task_struct and the unified task model that treats threads as tasks sharing resources; and the Unix filesystem, from the byte-stream file and the inode to the file-descriptor / struct file / inode chain and the VFS that lets one set of system calls drive many filesystems. A tour of the kernel's own structure followed—the process/kernel model with its system-call entry paths and task states, the task and address-space structures, synchronization, process management, the class-based scheduler with EEVDF and sched_ext, signals and IPC, memory management from page tables and SLUB to the folio-based page cache, and device drivers—each a sketch developed in full later.

Finally, the chapter looked at what makes this a 7.0 book: the architecture-independent/dependent split under arch/, with x86_64 and arm64 as the running examples; the modern subsystems—eBPF, io_uring, containers, and Rust—that open Part IV, alongside its chapters on security infrastructure, KVM, and tracing; the configuration-driven Kconfig/Kbuild build system that turns one source tree into anything from an embedded kernel to a server kernel, together with the checkers, test frameworks, fuzzing hooks, and Clang/LLVM builds that go with it; and the start_kernel() initialization sequence that brings the machine to life, ending with a map of the book's four parts and two appendices.
