A system call is the mechanism by which an unprivileged user-space program asks the privileged kernel for a service: opening a file, mapping memory, creating a process, sending a packet, reading the clock. It is the only general-purpose way into the kernel, and it is by far the busiest. This chapter follows a system call from the trap instruction that issues it to the service routine that implements it, examines the validation, filtering, tracing, and restart machinery layered along that path, and closes with the two mechanisms — the vDSO and io_uring — built to avoid taking it.

All source-code references in this chapter refer to the Linux 7.0.12 tree. The files the chapter works from are listed by topic in Source Trails.

System Calls Introduction

System calls are the most heavily used control-transfer points in the Linux kernel. Every filesystem open, every network send, every process creation, every timer query that cannot be answered from a fast user-space cache eventually funnels through this interface. Without it, a user program would have no way to reach hardware, filesystems, or other processes at all: the kernel would be an isolated island of privileged code with nothing leading into it.

A system call is a controlled kernel entry point exported as part of the user-kernel ABI. User mode cannot directly touch arbitrary kernel memory, change page tables, schedule CPUs, or issue privileged instructions. Instead, user programs request services by placing a system call number and arguments in architecture-defined registers and then executing a special trap instruction — syscall on x86_64, svc on ARM64. The CPU switches privilege levels, the kernel validates the request, dispatches to a service routine, and eventually returns a result or an error code.

The system call boundary is one of the most important abstractions in operating system design. It separates the trusted kernel — which manages hardware, enforces access control, and maintains shared data structures — from untrusted user-space code that may be buggy, malicious, or simply unaware of other processes running on the same machine. Every crossing of this boundary involves a hardware privilege transition: the CPU switches from user mode (ring 3 on x86, EL0 on ARM64) to kernel mode (ring 0 / EL1), saves enough state to return later, and begins executing kernel code at a well-defined entry point.

What makes this interface worth a chapter of its own is that it is the only general-purpose entry point. A process can also enter the kernel involuntarily, through an interrupt or a page fault, but those entries are not requests: the process did not ask for them and cannot choose their arguments. Every deliberate service a program obtains from Linux — opening a file, mapping memory, sending a packet, creating a thread — arrives through the same narrow mechanism, described by the same numbering scheme, and subject to the same validation, filtering, tracing, and restart machinery. That concentration is what makes the boundary both a security chokepoint worth hardening and a performance chokepoint worth optimizing, themes that recur throughout the chapter.

The definition is narrower than the standard C library API exposed by POSIX, and the two do not correspond one to one in either direction. A POSIX function such as printf() may never enter the kernel if it only formats data into an already-buffered stream. A wrapper such as open() may translate its arguments, retry on EINTR, or issue a newer call such as openat() or openat2() under a legacy name. A call such as gettimeofday() may be served entirely from the vDSO without a trap at all, as Section 5 describes. And the relationship fails in the other direction too: some system calls have no library wrapper, and must be reached through the generic syscall() helper — which takes a number and up to six arguments and performs the trap directly — or through a dedicated library such as liburing. The user-space function name is therefore not the ABI boundary; the kernel entry number and calling convention are.

What makes that boundary difficult is not the privilege change itself but the assumption the kernel must adopt the moment it is crossed. On the kernel side of the trap, every value that arrived from user space is hostile until proven otherwise. A pointer argument may reference kernel memory, unmapped memory, or memory that a second thread is concurrently unmapping. A length may overflow when added to a base address. A file descriptor may be closed and reused between the moment it is validated and the moment it is dereferenced. A buffer that was readable when checked may be gone before it is copied. Much of the machinery in this chapter — the SYSCALL_DEFINE wrappers that sign-extend and type-check arguments, the copy_from_user() family, the exception tables that make a faulting kernel access recoverable, and the compat wrappers that translate 32-bit layouts — exists to make that hostility survivable rather than merely detectable.

The transition also costs real time, and the cost has grown. Beyond the unavoidable register saves and the cache and TLB effects of running a different working set, both architectures now unmap most of the kernel while user code runs, as a defense against Meltdown-class attacks that read kernel memory through speculative side channels. x86_64 calls this kernel page-table isolation (CONFIG_MITIGATION_PAGE_TABLE_ISOLATION) and ARM64 calls it unmapping the kernel at EL0 (CONFIG_UNMAP_KERNEL_AT_EL0); both default to on, though ARM64 gates the work behind a runtime CPU capability so that cores known to be unaffected pay nothing. Add the speculation barriers and branch-predictor flushes that Spectre-class mitigations insert on entry, and a system call that once cost on the order of a hundred cycles can cost several times that. This is the economic pressure behind two of the largest topics in this chapter. The vDSO answers certain requests — most importantly the time-of-day queries that some workloads issue millions of times a second — without crossing the boundary at all. io_uring goes the other way and amortizes the crossing, letting one entry submit and complete many operations, or in SQPOLL mode letting a busy application avoid the entry entirely. Neither would be worth its complexity if entering the kernel were free.

The implementation behind the system call interface differs sharply from Linux 2.6. On 32-bit x86 Linux 2.6, processes entered the kernel via int $0x80 or the Pentium II-era sysenter instruction, with system call numbers passed in eax and up to six arguments packed into general-purpose registers. Modern x86_64 kernels use the dedicated syscall/sysret instruction pair introduced with AMD64, while ARM64 systems use the svc (supervisor call) instruction to trap into EL1. The deeper change is that the work surrounding the call — tracing, seccomp filtering, audit, signal delivery, and rescheduling checks — has moved out of architecture-specific assembly and into C, in a fixed and documented order. It is worth being precise about how far that convergence goes, because it is easy to overstate. x86 selects CONFIG_GENERIC_ENTRY and uses the shared implementation in kernel/entry/common.c, reached through syscall_enter_from_user_mode() and syscall_exit_to_user_mode(). ARM64 does not select it; it runs an equivalent pipeline of its own in arch/arm64/kernel/syscall.c, where el0_svc_common() performs the same steps in the same order through syscall_trace_enter() and syscall_trace_exit(). The sharing is real but partial: the syscall-specific head of the pipeline is duplicated, while the final return to user mode is common code both architectures reach. They agree on the sequence and on the observable behavior more than on the source that implements it, and Section 3 follows each path separately for that reason.

The subsystem has also grown in scope. In Linux 2.6.11 the infrastructure was little more than a dispatch table, an entry stub, and a few parameter-checking macros. Linux 7.0.12 adds BPF-based system call filtering through seccomp, the vDSO shared library mapped into every process, a unified tracing and audit pipeline, restartable system call logic for calls interrupted by signals, and io_uring as a fundamentally different model for high-frequency I/O.

Against that churn in the implementation stands a promise about the interface: Linux does not break user space. For system calls that promise has a concrete and unusually visible form — a number, once assigned, is never reused for a different call, and a call that becomes obsolete keeps its number rather than yielding it to a successor. The numbering therefore accumulates history and never compacts. The clearest evidence is a hole. On x86_64 the table runs from 0 to 336, skips everything from 337 to 423, and resumes at 424. Every number in that gap was already spoken for on 32-bit x86 — ordinary calls through 386, the SysV IPC calls that 32-bit x86 later unpacked from its ipc() multiplexor, and finally the *_time64 variants that give 32-bit architectures 64-bit timestamps — so a 64-bit architecture that needed none of them could not reuse the numbers without breaking the rule that a given call has one number everywhere. Rather than reclaim the range, x86_64 leaves it empty. The resumption point matters too: since pidfd_send_signal took number 424, every new system call has received the same number on every architecture, so the divergence frozen into the low ranges is historical rather than ongoing.

How large is the interface? The figures usually quoted are table sizes rather than counts of usable calls, and the difference is substantial. Linux 7.0.12 sizes the ARM64 dispatch table with __NR_syscalls, which is 472, but that is the highest assigned number plus one and not a count of entries. The x86_64 table in arch/x86/entry/syscalls/syscall_64.tbl assigns 385 of those numbers — the ranges 0 through 336 and 424 through 471, with the 87-number hole just described. The table ARM64 uses, arch/arm64/tools/syscall_64.tbl, assigns 327 to native 64-bit tasks; the rest of its 472 slots are either unassigned or reserved for 32-bit and architecture-specific ABIs, as Section 2.1 describes. The comparable figure for Linux 2.6.11 is 289, the value of NR_syscalls on i386, of which 286 numbers were actually filled in. So the interface has grown by roughly a third on ARM64 and by about a half on x86_64 over twenty years — real growth, but less dramatic than comparing 289 against 472 would suggest.

The numbers a table does not assign are not holes at runtime. Both architectures arrange for every number below __NR_syscalls to reach sys_ni_syscall() in kernel/sys_ni.c, a one-line routine that returns -ENOSYS. ARM64 does this by pre-filling its table with a range initializer, [0 ... __NR_syscalls - 1] = __arm64_sys_ni_syscall, before the generated header overwrites the assigned slots; x86_64 reaches the same routine through the default: arm of the dispatch switch, as Section 2.2 shows. Numbers at or above __NR_syscalls are rejected by an explicit bounds check. The same routine also absorbs calls that exist in the table but were configured out of the build: the COND_SYSCALL macro declares a weak alias so that, for example, io_uring_setup resolves to sys_ni_syscall when CONFIG_IO_URING is disabled. An ENOSYS return therefore carries three distinct meanings — the number was never assigned, the call is too new for this kernel, or the feature was compiled out — and user space that probes for optional functionality must treat all three alike.

Much of the growth since the 2.6 era comes from facilities that had no 2.6 equivalent rather than from refinements of existing ones: pidfds for race-free process references, Landlock for unprivileged sandboxing, io_uring for asynchronous I/O, the file-descriptor-based mount API, futex2-style calls such as futex_waitv, and memory sealing via mseal. The three most recent additions at the time of writing — file_setattr, listns, and rseq_slice_yield at numbers 469 through 471 — continue the pattern. One convention runs through every entry in that table and is easy to overlook because C libraries hide it. A system call returns a single machine word in one register — RAX on x86_64, X0 on ARM64 — and errors are encoded in that same word as a small negative value: -EPERM is -1, -ENOENT is -2, and so on. There is no separate status flag and no out-of-band error channel. The library wrapper, not the kernel, is what turns that into the familiar POSIX contract: it tests whether the returned value falls in the error range, and if it does, negates it into the thread-local errno and returns -1 to the caller. Code that invokes syscall() directly sees the raw negative value, which is why kernel-side code and strace output speak of -EINVAL while application code speaks of errno == EINVAL.

This raises an obvious question: how does anyone distinguish an error from a legitimate return value that happens to be negative when interpreted as signed? The answer is a fixed boundary. include/linux/err.h defines MAX_ERRNO as 4095 and IS_ERR_VALUE() as a test for whether an unsigned value lies in the top 4096 addresses of the word — that is, whether it is between -4095 and -1. Only that narrow band is reserved for errors; everything else is a successful result. The boundary exists because several system calls legitimately return values that occupy the whole word. mmap() returns an address, and on a 64-bit kernel that address may have its high bits set; lseek() returns a file offset that can be enormous. Reserving 4095 codes rather than the entire negative half of the range keeps those returns unambiguous. The kernel relies on the same boundary internally: syscall_get_error() in arch/x86/include/asm/syscall.h and arch/arm64/include/asm/syscall.h applies IS_ERR_VALUE() to the saved return register to decide whether a completed call failed, and ptrace, audit, and seccomp all consume that verdict.

A stable ABI does not imply a static implementation. The int 0x80 entry, fixed vsyscall pages, and direct table lookups of Linux 2.6 can look like the permanent architecture of Linux. In Linux 7.0.12 the number for read is what it has always been on each architecture — 0 on x86_64, 63 on ARM64 — and the arguments still arrive in the same registers, but the trap instruction, the dispatch mechanism, the tracing hooks, the mitigations, and the fast paths have all been replaced at least once. The rest of this chapter is largely an account of what replaced them and why.

What that list does not show is that the parts answer four different questions. This section and Section 2 ask what a system call is: how it is numbered, where the table lives, and how a service routine is declared. Sections 3 and 4 ask how the boundary is crossed — the hardware entry and exit paths on each architecture, and how arguments are passed and validated once inside. Sections 5 and 9 ask how the crossing can be avoided or amortized, through the vDSO and through io_uring. Sections 6, 7 and 8 ask who else gets to observe or intervene: seccomp filters that can reject a call before it runs, the tracing and audit pipeline that records it, and the restart machinery that decides what happens when a signal arrives partway through. System Call Dispatch

When a user-space program executes a system call instruction, the CPU transfers control to a well-known kernel entry point. But the entry point itself does not know which service to perform — it only receives a raw integer in a register. The system call dispatch mechanism is the machinery that translates that integer into a call to the correct kernel function, with properly typed arguments, tracing metadata, and ABI safety wrappers.

Modern Linux dispatches a system call in three linked stages. First, the kernel assigns a stable number to each system call — a contract that, once published, is never broken. Second, the build system turns that numbering into architecture-specific dispatch tables or switch statements that the entry code can index at runtime. Third, each entry in the table is bound to a service routine defined with the SYSCALL_DEFINE* macro family, which generates type-safe wrappers, sanitizing layers, and tracing metadata around the human-written implementation.

This separation of concerns is what lets Linux maintain a stable user-space ABI across decades of internal refactoring. The number 0 has meant read on x86_64 since the architecture was introduced, even though the dispatch path, the wrapper layers, and the underlying VFS code have all been rewritten multiple times. In Linux 2.6 this dispatch was a simple array lookup: load eax as an index into sys_call_table and call the resulting function pointer. In Linux 7.0.12, the native x86_64 path actually uses a compiler-generated switch statement inside x64_sys_call() rather than an indirect call through the table — the array still exists, but primarily for tracing and compat paths. ARM64 retains a traditional function-pointer table, but wraps it in architecture-specific calling convention adapters.

That divergence is not an accident of taste, and it is worth stating the reason early because it explains a great deal of what Section 2.2 shows. A dispatch table indexed by a number that user space chooses is, viewed from a security standpoint, an attacker-steered indirect branch — historically the single most easily triggered one in the kernel. Both architectures hardened it, but against different speculative-execution problems and therefore in different ways. x86_64 replaced the indirect call itself, on the reasoning that a mispredicted switch merely runs the wrong system call, which is harmless, whereas a mispredicted indirect call can speculate into an attacker-chosen gadget. ARM64 kept the indirect call and instead relies on clamping the index with array_index_nospec(), so that a bounds check cannot be speculated past. The distinction is about the indirect branch, not about index sanitizing: both architectures clamp the index, because that defends Spectre variant 1 and is cheap. What x86_64 did in addition was remove the indirect branch that variant 2 targets.

System Call Numbering

Before the kernel can execute a service routine, it needs a stable number-to-handler mapping. That mapping is the most fundamental contract in the system call ABI: once a number is assigned and released to user space, the kernel commits to honoring it indefinitely. Removing or reassigning a number would silently break every existing binary that uses it — a violation of the kernel's backward-compatibility guarantee that Linus Torvalds has famously described as inviolable. Numbers can be deprecated (the kernel may print a warning), but they are never recycled.

Both architectures generate their numbering the same way, and in Linux 7.0.12 they do so from the same kind of file: a machine-readable table assigns numbers, the build generates prototypes and dispatch structures, and the UAPI headers expose __NR_* constants to user space. What differs is which table each one reads and which rows it takes from it. The tables also encode ABI class information — whether a call is available to native 64-bit tasks, 32-bit compat tasks, or the x32 ABI — so the build system can generate separate dispatch paths for each class.

On x86_64 the authoritative native table is arch/x86/entry/syscalls/syscall_64.tbl. Each non-comment row gives a number, an ABI class such as common, 64, or x32, the exported name, and the implementation symbol. The table begins with read, write, open, and close at numbers 0 through 3, and it continues to newer calls such as io_uring_setup, openat2, and mseal. Holes are preserved rather than reclaimed. The last native entry before the gap is uprobe at 336, and the next is pidfd_send_signal at 424; the file carries a comment warning contributors not to use numbers 387 through 423, which is the narrower range that was being actively reserved when the comment was written. The effective gap is larger than the comment suggests, because nothing between 337 and 423 is assigned on x86_64 either.

Descriptions of ARM64 numbering written for earlier kernels say that it comes from the asm-generic list in include/uapi/asm-generic/unistd.h, which expanded macros such as __SYSCALL, __SC_COMP, and __SC_3264 directly in a header. That is no longer how the ARM64 kernel is built. Linux 7.0.12 uses a table file, arch/arm64/tools/syscall_64.tbl, in exactly the same four-column format as the x86_64 one; the header still exists and is still included by include/linux/syscalls.h and kernel/sys_ni.c, but no file under arch/arm64/ includes it any longer.

The convergence goes further than a shared file format. ARM64’s table is byte-for-byte identical to scripts/syscall.tbl, the master list shared by every architecture that adopted the modern numbering, and both architectures feed their tables through the same two shell scripts described in Section 2.2. What remains architecture-specific is only which table is used and which ABI classes are selected from it — a much smaller difference than the one the older description implies.

The second column of both tables is an ABI class, and it is what lets one table describe several incompatible calling environments at once. On x86_64 the classes are common, 64, and x32: a common row is compiled into both the native and the x32 dispatch paths, a 64 row only into the native one, and an x32 row only into the x32 path for those structure layouts that x32 must handle differently. The shared table uses a longer list — common, 64, 32, time32, and a set of narrow classes such as renameat, rlimit, memfd_secret, and per-architecture names like riscv — and each architecture opts in to the ones it wants. ARM64 makes that selection in arch/arm64/kernel/Makefile.syscalls, a three-line file whose entire content is to add renameat, rlimit, and memfd_secret to the native ABI set and to point the build at its own table. A single row can therefore appear once for time32 and once for 64 with the same number and different implementations, which is how one list serves both a 32-bit and a 64-bit userspace without a second numbering.

The user-visible constants come from generated UAPI headers, not from either table directly: user space includes <asm/unistd.h> and receives __NR_read, __NR_openat2, and the rest from headers the build produced. The important point is that the number is architecture ABI, not a property of the POSIX name. Table 10-4 makes the divergence concrete, and it is larger than most readers expect: read is 0 on x86_64 and 63 on ARM64, mmap is 9 and 222, and openat is 257 and 56. The pattern breaks at 424. From pidfd_send_signal onward every call has the same number on both architectures — and on 32-bit x86, powerpc, and s390 as well — because the kernel adopted the rule that a new system call is allocated the same number everywhere. The low ranges preserve two independent histories; the high range is a single shared one.

Divergence in numbering is the smaller surprise. The larger one is that the two architectures do not implement the same set of calls. ARM64 has no open, no fork, no stat, no poll, no select, no pipe, no dup2, and no mkdir, rename, link, or chmod. The shared table was written on the principle stated in its own header comment — that no duplication of functionality should be added, and that new architectures should implement the less capable calls in user space — so it provides only the directory-fd-relative and extended forms: openat, clone, fstatat, ppoll, pselect6, pipe2, dup3, mkdirat, renameat2, linkat, and fchmodat. When a program on ARM64 calls open() or fork(), the C library is not thinning a wrapper around a matching system call; it is synthesizing a POSIX interface that the kernel does not offer. This is the sharpest available illustration of the point Section 1 made in the abstract, that the library function name is not the ABI boundary.

The System Call Tables

Numbering alone does not dispatch anything — it is merely a declaration. The build must also turn the declarative lists into concrete runtime objects that the entry code can use to find the correct function for a given number. This table-generation step is where architecture policy becomes visible, because x86_64 and ARM64 have made fundamentally different choices about how to perform the final dispatch.

The mechanical part of that step is shared, and naming it removes most of the mystery from what follows. Two shell scripts in the kernel’s scripts directory read a .tbl file and write C headers into the build tree. scripts/syscallhdr.sh produces the __NR_* constants — this is what generates asm/unistd_64.h for the kernel and for user space, and when invoked with --emit-nr it also emits the __NR_syscalls value that sizes the dispatch array. scripts/syscalltbl.sh produces the dispatch header — asm/syscall_table_64.h on ARM64, asm/syscalls_64.h on x86_64 — which is not itself a table but a bare sequence of __SYSCALL(nr, sym) invocations with no definition of __SYSCALL in sight. Both scripts take an --abis argument naming which ABI classes to include, which is how one table produces a native header, a compat header, and an x32 header without any per-architecture logic in the scripts themselves.

Leaving __SYSCALL undefined in the generated header is the whole trick. Because the header supplies only the data, the file that includes it supplies the meaning, and it can supply a different meaning each time. One pass defines __SYSCALL to declare a prototype, a second to emit an array initializer, a third to emit a case label. This "include-driven code generation" pattern is idiomatic in the kernel’s entry subsystem and lets a single numbering source produce every dispatch structure an architecture needs, with no possibility of the structures disagreeing about which number maps to which symbol.

On ARM64, the architecture-specific file arch/arm64/kernel/sys.c includes the generated table headers and materializes sys_call_table as an array of function pointers indexed by system call number. The same generated input can then be reused for compat dispatch in arch/arm64/kernel/sys32.c. 


/* arch/arm64/kernel/sys.c */
#define __SYSCALL(nr, sym)	asmlinkage long __arm64_##sym(const struct pt_regs *);
#include <asm/syscall_table_64.h>

#undef __SYSCALL
#define __SYSCALL(nr, sym)	[nr] = __arm64_##sym,

const syscall_fn_t sys_call_table[__NR_syscalls] = {
	[0 ... __NR_syscalls - 1] = __arm64_sys_ni_syscall,
#include <asm/syscall_table_64.h>
};

The __SYSCALL macro is the connective tissue that turns declarative numbering into C objects. On x86_64, arch/x86/entry/syscall_64.c includes the generated header multiple times with different definitions of __SYSCALL. One pass creates external prototypes, a second creates the trace-visible sys_call_table[], and a third expands into a giant switch inside x64_sys_call(). That last point is subtle and important: Linux 7.0.12 no longer dispatches native x86_64 system calls by indexing sys_call_table[] at runtime, even though the array still exists for tracing metadata. A comment above the array says so in as many words — that it is no longer used for system calls, and survives because kernel/trace/trace_syscalls.c still wants the service routine addresses.

The reason for the change is a speculative-execution mitigation, and the commit that made it states the argument plainly. An indirect call through a table indexed by a user-supplied number was the most easily triggered indirect branch in the kernel, and therefore the most attractive target for a Spectre variant 2 attack that trains the branch predictor to speculate into a chosen gadget. Compiling the dispatch as a switch lets the compiler emit a series of conditional branches instead. Those branches are predicted too, but the consequence of a misprediction is bounded: the CPU speculatively begins running a different system call, which is harmless, rather than speculatively running attacker-selected code found elsewhere in the kernel. The mitigation is deliberately narrow — it does not protect other indirect calls — but it removes the one an attacker can trigger most cheaply.

ARM64 keeps its function-pointer array and defends the same weakness differently, in invoke_syscall(). The number is first bounds-checked against sc_nr, and then, before it is used as an index, it is passed through array_index_nospec(), which rewrites it into a value that is architecturally guaranteed to be zero if the bounds check failed. This closes Spectre variant 1, where the CPU speculates past a bounds check and indexes the array with an out-of-range number. It would be tidy to say that the two architectures solve the problem by opposite means, but that is not what the code does. do_syscall_x64() in arch/x86/entry/syscall_64.c clamps its index with array_index_nospec() exactly as ARM64 does, before passing it to the switch. Index sanitizing is the common baseline on both, because variant 1 threatens any bounds-checked table lookup and the clamp costs a couple of instructions. The real asymmetry is the extra step: x86_64 also deleted the indirect branch, which is what variant 2 needs, while ARM64 kept it. The switch is therefore not a replacement for array_index_nospec() but a second layer on top of it.

x86_64 generates more than one such switch. Alongside x64_sys_call() for native tasks, arch/x86/entry/syscall_64.c builds x32_sys_call() under CONFIG_X86_X32_ABI, and arch/x86/entry/syscall_32.c builds ia32_sys_call() for 32-bit tasks under CONFIG_IA32_EMULATION. Each is generated from the same table with a different --abis selection, and each falls back in its default: arm to the sys_ni_syscall stub carrying its own prefix — __x64_sys_ni_syscall() for the two 64-bit dispatchers and __ia32_sys_ni_syscall() for the 32-bit one. 


/* arch/x86/entry/syscall_64.c */
#define __SYSCALL(nr, sym) __x64_##sym,
const sys_call_ptr_t sys_call_table[] = {
#include <asm/syscalls_64.h>
};
#undef  __SYSCALL

#define __SYSCALL(nr, sym) case nr: return __x64_##sym(regs);
long x64_sys_call(const struct pt_regs *regs, unsigned int nr)
{
	switch (nr) {
	#include <asm/syscalls_64.h>
	default: return __x64_sys_ni_syscall(regs);
	}
}

Linux 7.0.12 also preserves compatibility ABIs. A 64-bit x86 kernel still supports 32-bit i386 tasks through a compat table and legacy entry paths such as int 0x80 and SYSENTER. An ARM64 kernel can similarly host 32-bit AArch32 tasks and dispatch them through compat_sys_call_table in arch/arm64/kernel/sys32.c. This split is why the source tree carries native tables, compat tables, and wrapper layers that normalize arguments before the real work begins.

Compat tables follow the same pattern with different wrapper prefixes. The ARM64 file arch/arm64/kernel/sys32.c expands __SYSCALL into compat_sys_call_table for 32-bit tasks. The x86 side maintains IA32 and x32 support in separate generated headers and entry paths. This layered generation strategy keeps the ABI description centralized while still letting each architecture attach the calling convention it needs.

Defining Service Routines with SYSCALL_DEFINE

After numbering and table generation comes the service routine itself — the kernel function that actually performs the work requested by the system call. In early Linux kernels, developers wrote these routines as ordinary C functions with ad-hoc prototypes, manually ensuring that the function signature matched the register layout expected by the entry code. This was error-prone: mismatched types, missing sign-extension on 32-bit arguments passed in 64-bit registers, and inconsistent tracing metadata were common sources of subtle bugs.

Linux no longer expects maintainers to hand-code fragile assembly-callable stubs for every system call. Instead, most implementations are written with the SYSCALL_DEFINE0 through SYSCALL_DEFINE6 macro family in include/linux/syscalls.h. The digit indicates the argument count: SYSCALL_DEFINE0 takes no arguments (e.g., getpid), while SYSCALL_DEFINE6 takes six (the maximum supported by the register-based calling conventions on both x86_64 and ARM64). Each macro invocation generates multiple layers of wrapper code: a public ABI-facing symbol, argument-sanitizing wrappers that handle type widening and casting, and a final inline helper where the actual kernel logic lives. The upper limit is not arbitrary either: SYSCALL_DEFINE_MAXARGS is defined as 6 in the same header, and it is checked by the tracing metadata machinery.

The portable definition of that expansion looks like this. Read it as the fallback rather than as what happens on the architectures this book follows — the next few paragraphs explain why.

This macro stack solves several problems at once. It gives each syscall a standardized prototype shape. It centralizes sign extension and type casting for narrow integer arguments. It creates metadata objects used by tracepoints and syscall tracing. And it leaves the human-written body in a normal C function-like environment rather than in raw entry code. 


/* include/linux/syscalls.h */
#define SYSCALL_DEFINE3(name, ...) SYSCALL_DEFINEx(3, _##name, __VA_ARGS__)

#define SYSCALL_DEFINEx(x, sname, ...)\
	SYSCALL_METADATA(sname, x, __VA_ARGS__)\
	__SYSCALL_DEFINEx(x, sname, __VA_ARGS__)

#define __SYSCALL_DEFINEx(x, name, ...)\
	asmlinkage long sys##name(__MAP(x,__SC_DECL,__VA_ARGS__))\
		__attribute__((alias(__stringify(__se_sys##name))));\
	static inline long __do_sys##name(__MAP(x,__SC_DECL,__VA_ARGS__));\
	asmlinkage long __se_sys##name(__MAP(x,__SC_LONG,__VA_ARGS__));\
	asmlinkage long __se_sys##name(__MAP(x,__SC_LONG,__VA_ARGS__))\
	{\
		long ret = __do_sys##name(__MAP(x,__SC_CAST,__VA_ARGS__));\
		__MAP(x,__SC_TEST,__VA_ARGS__);\
		return ret;\
	}\
	static inline long __do_sys##name(__MAP(x,__SC_DECL,__VA_ARGS__))

The best way to read this is from the outside in. The externally visible symbol is sys_name, an alias for __se_sys_name. The __se_sys_* wrapper receives all arguments widened to long-sized slots, performs casting and test macros such as __SC_CAST and __SC_TEST, then calls the inline body __do_sys_*. That body is what developers mentally treat as the syscall implementation.

There is a catch, and it matters for a book that uses x86_64 and ARM64 as its examples: neither of them uses that definition. The whole block above sits inside #ifndef __SYSCALL_DEFINEx, so it applies only when the architecture has not supplied its own. Both x86 and ARM64 select ARCH_HAS_SYSCALL_WRAPPER in their Kconfig and provide a replacement in arch/x86/include/asm/syscall_wrapper.h and arch/arm64/include/asm/syscall_wrapper.h. The portable version is what an architecture gets if it asks for nothing; it is worth reading first because the arch versions are variations on it, but the symbol names and the calling convention it describes are not the ones a running x86_64 or ARM64 kernel uses.

The substantive difference is that the architecture stub takes no syscall arguments at all. It takes a single const struct pt_regs * and pulls the arguments out of the saved register frame itself. 


/* arch/arm64/include/asm/syscall_wrapper.h */
#define __SYSCALL_DEFINEx(x, name, ...)						\
	asmlinkage long __arm64_sys##name(const struct pt_regs *regs);		\
	ALLOW_ERROR_INJECTION(__arm64_sys##name, ERRNO);			\
	static long __se_sys##name(__MAP(x,__SC_LONG,__VA_ARGS__));		\
	static inline long __do_sys##name(__MAP(x,__SC_DECL,__VA_ARGS__));	\
	asmlinkage long __arm64_sys##name(const struct pt_regs *regs)		\
	{									\
		return __se_sys##name(SC_ARM64_REGS_TO_ARGS(x,__VA_ARGS__));	\
	}									\
	static long __se_sys##name(__MAP(x,__SC_LONG,__VA_ARGS__))		\
	{									\
		long ret = __do_sys##name(__MAP(x,__SC_CAST,__VA_ARGS__));	\
		__MAP(x,__SC_TEST,__VA_ARGS__);					\
		__PROTECT(x, ret,__MAP(x,__SC_ARGS,__VA_ARGS__));		\
		return ret;							\
	}									\
	static inline long __do_sys##name(__MAP(x,__SC_DECL,__VA_ARGS__))

Three things changed. The ABI-facing symbol is now __arm64_sys_read, not sys_read, and it is a real function rather than an alias, because it has actual work to do: SC_ARM64_REGS_TO_ARGS expands to a list of regs->regs[0] through regs->regs[5] references that unpack the frame. __se_sys_* has become static, since nothing outside the translation unit calls it any more. And the chain is now three functions deep rather than two: register-unpacking stub, sign-extending wrapper, typed body. x86_64 follows the same shape through __X64_SYS_STUBx and __IA32_SYS_STUBx, which generate up to four differently prefixed stubs from one definition — __x64_sys_* for native calls, __ia32_sys_* for 32-bit native and common compat calls, and __ia32_compat_sys_* and __x64_compat_sys_* where a compat-specific body is needed.

The reason for the convention is stated in the x86 header’s own comment: it avoids leaking random user-provided register content down the call chain. Under the old convention a service routine taking four arguments was still called with six argument registers live, the last two holding whatever the user program happened to leave there. Any function further down that later read those registers — through a miscompilation, an inline assembly block, or a speculative path — would be reading attacker-controlled data. With a pt_regs stub the compiler loads exactly the arguments the syscall declares and explicitly zeroes the rest; the header even reproduces the generated assembly for recv, where two xor instructions clear the unused registers before the call. The macro stack is not only an ergonomic convenience, then. It is also where an ABI-level hardening decision is enforced uniformly across every system call in the tree, without any individual author having to remember it.

Type safety matters because the hardware ABI only promises registers, not C types. A user program may place a 32-bit int, a 64-bit loff_t, or a tagged pointer-looking value into a register slot. The macro helpers __SC_LONG, __SC_CAST, and __SC_TEST ensure that the compiler sees the correct function signature after the entry wrapper has normalized the raw register contents. This is far safer than the 2.6-era style of sprinkling manual casts and architecture-specific calling stubs throughout the tree. 


/* fs/read_write.c */
ssize_t ksys_read(unsigned int fd, char __user *buf, size_t count)
{
	CLASS(fd_pos, f)(fd);
	ssize_t ret = -EBADF;

	if (!fd_empty(f)) {
		loff_t pos, *ppos = file_ppos(fd_file(f));
		if (ppos) {
			pos = *ppos;
			ppos = &pos;
		}
		ret = vfs_read(fd_file(f), buf, count, ppos);
		if (ret >= 0 && ppos)
			fd_file(f)->f_pos = pos;
	}
	return ret;
}

SYSCALL_DEFINE3(read, unsigned int, fd, char __user *, buf, size_t, count)
{
	return ksys_read(fd, buf, count);
}

The read example shows the layering in a compact form. The SYSCALL_DEFINE3(read, ...) declaration generates the ABI-facing wrappers. The wrapper body itself is tiny because the real logic is shared in ksys_read() and then continues into VFS code such as vfs_read(). This pattern is common: the syscall layer validates or normalizes ABI details, then hands the request to a helper that can be reused elsewhere in the kernel.

Tracing metadata is generated automatically as well. When tracing support is enabled, SYSCALL_METADATA() builds arrays of argument type strings and argument names, creates enter and exit trace-event descriptors, and places a struct syscall_metadata pointer in the __syscalls_metadata linker section. That is why tools such as ftrace, perf, and eBPF can attach to syscall tracepoints without every syscall author writing bespoke metadata blocks.

Zero-argument calls are a special case worth noting, because they are the one place where the layering collapses. SYSCALL_DEFINE0 is defined separately rather than through SYSCALL_DEFINEx: with no arguments there is nothing to unpack, widen, or sign-extend, so the macro emits the pt_regs stub and the body as a single function and skips the __se_sys_* and __do_sys_* layers entirely. The pt_regs parameter is named __unused. This is why getpid, so often used as the canonical syscall example, is atypical in the one respect that matters most for understanding the macro stack.

The high-level programming model survives all of this indirection intact: authors implement system calls as ordinary C functions with ordinary C types, and the macro stack absorbs the ABI glue, the sign-extension rules, the register-clearing discipline, the tracing metadata, and the per-architecture calling convention. That is the real achievement of SYSCALL_DEFINE, and it is why a chapter that must describe two architectures can present a single service-routine programming model for both.

Entering and Exiting a System Call

A modern system call path is best understood as one round trip, not as two unrelated halves. The user program executes a single trap instruction — syscall on x86_64, svc on ARM64 — and does not regain control until the kernel has saved state, dispatched the service routine, checked for pending signals, handled rescheduling requests, and finally restored user-mode context through a matching return instruction. Every one of these steps must be correct, in the right order, and resilient against concurrent interrupts, because the boundary crossing happens millions of times per second on a busy system.

Linux 2.6 had two x86-32 entry mechanisms — int $0x80 and sysenter — implemented as separate, nearly independent paths that converged only when they reached the shared system_call() or sysenter_entry() assembly. In Linux 7.0.12 the picture is both simpler and more complex. Simpler because most of the entry/exit policy has migrated from architecture-specific assembly into shared C code in kernel/entry/common.c and include/linux/entry-common.h. More complex because that shared pipeline must integrate security mitigations (KPTI page-table switching, speculation barriers, IBRS), hardware features (PAN, pointer authentication, MTE on ARM64; SMAP, SMEP on x86), and multiple tracing hooks (seccomp, ptrace, audit, tracepoints) that did not exist or were far less mature in 2.6.

Two warnings before the figure, because both are easy to get wrong and this section will return to each. The first is that "shared C pipeline" is a half-truth. x86 selects CONFIG_GENERIC_ENTRY and really does call into kernel/entry/common.c; ARM64 does not, and reimplements the syscall-specific entry and exit work in arch/arm64/kernel/syscall.c. What the two genuinely share is the tail — the final return-to-user loop. Section 3.4 draws the line precisely. The figure below therefore shows a common shape, not a common function.

The second is that x86_64 in 7.0.12 does not have one entry mechanism, or even two counting the legacy 32-bit doors. It has three. Alongside SYSCALL/SYSRET and the compatibility paths there is FRED, a hardware event-delivery redesign that replaces the entry assembly wholesale on CPUs that implement it. It converges on the same C code, so nothing else in this chapter changes, but a reader who studies only entry_SYSCALL_64 will be surprised by machines on which that function is never executed. Section 3.1 covers it after the classic path.

With those two caveats in mind, the figure shows the complete round-trip structure on both architectures, highlighting how the architecture-specific entry and exit assembly sandwiches the common C stages.

The x86_64 SYSCALL/SYSRET Path

The x86_64 system call entry is the most performance-critical code path in the kernel. On a busy web server or database, the entry_SYSCALL_64 label in arch/x86/entry/entry_64.S may be reached hundreds of millions of times per second. Every instruction in this path has been scrutinized for correctness, security, and performance — and the comments in the source warn future developers not to add even a single unnecessary instruction.

The x86_64 SYSCALL instruction is the architectural fast-path trap introduced with AMD's long mode. Unlike int $0x80, which pushes a full interrupt frame and looks up an IDT vector, SYSCALL performs only a minimal set of operations in hardware: it saves the return address in RCX, saves RFLAGS in R11, loads CS and SS from MSR_STAR, loads the entry RIP from MSR_LSTAR, and masks RFLAGS according to MSR_SYSCALL_MASK (clearing IF to disable interrupts, among other flags). Everything else — switching stacks, saving registers, switching page tables for KPTI — is software's responsibility.

On x86_64 the normal fast path begins when user space executes syscall. Hardware loads the target RIP from MSR_LSTAR, kernel and user code selectors from MSR_STAR, and clears selected flags according to MSR_SYSCALL_MASK, often called SFMASK in older documentation. Linux programs those MSRs in arch/x86/kernel/cpu/common.c during syscall_init() and idt_syscall_init(). Unlike Linux 2.6 on 32-bit x86, the hot path is not int 0x80; it is the dedicated long-mode syscall instruction. 


/* arch/x86/kernel/cpu/common.c */
static inline void idt_syscall_init(void)
{
	wrmsrq(MSR_LSTAR, (unsigned long)entry_SYSCALL_64);
	...
	wrmsrq(MSR_SYSCALL_MASK,
	       X86_EFLAGS_CF|X86_EFLAGS_PF|X86_EFLAGS_AF|
	       X86_EFLAGS_ZF|X86_EFLAGS_SF|X86_EFLAGS_TF|
	       X86_EFLAGS_IF|X86_EFLAGS_DF|X86_EFLAGS_OF|
	       X86_EFLAGS_IOPL|X86_EFLAGS_NT|X86_EFLAGS_RF|
	       X86_EFLAGS_AC|X86_EFLAGS_ID);
}

void syscall_init(void)
{
	wrmsr(MSR_STAR, 0, (__USER32_CS << 16) | __KERNEL_CS);
	if (!cpu_feature_enabled(X86_FEATURE_FRED))
		idt_syscall_init();
}

The actual entry point is entry_SYSCALL_64 in arch/x86/entry/entry_64.S. Its first visible steps are swapgs, saving the user stack pointer into per-CPU TSS scratch storage, switching to the kernel CR3 when KPTI is active, and loading the per-CPU top-of-stack pointer. The code then pushes user-mode SS, SP, RFLAGS, CS, RIP, and the original syscall number so that the kernel has a synthetic interrupt-like frame on its own stack. Only after the register state is safely captured does Linux call the C helper do_syscall_64(). 


SYM_CODE_START(entry_SYSCALL_64)
	swapgs
	movq	%rsp, PER_CPU_VAR(cpu_tss_rw + TSS_sp2)
	SWITCH_TO_KERNEL_CR3 scratch_reg=%rsp
	movq	PER_CPU_VAR(cpu_current_top_of_stack), %rsp

	pushq	$__USER_DS
	pushq	PER_CPU_VAR(cpu_tss_rw + TSS_sp2)
	pushq	%r11
	pushq	$__USER_CS
	pushq	%rcx
	pushq	%rax

	PUSH_AND_CLEAR_REGS rax=$-ENOSYS

	/* IRQs are off. */
	movq	%rsp, %rdi
	/* Sign extend the lower 32bit as syscall numbers are treated as int */
	movslq	%eax, %rsi

	/* clobbers %rax, make sure it is after saving the syscall nr */
	IBRS_ENTER
	UNTRAIN_RET
	CLEAR_BRANCH_HISTORY

	call	do_syscall_64		/* returns with IRQs disabled */

Two details are easy to miss but critical to understanding the ABI. First, syscall overwrites RCX and R11, which is why the x86_64 calling convention cannot use RCX as argument 4 and instead uses R10. Second, do_syscall_64() receives the syscall number as an int even though the raw register is 64 bits, because Linux treats system call numbers as signed 32-bit values and explicitly sign-extends the low half.

The three macros between the register save and the call are the ones a reader is most likely to skip, and they are the clearest measure of how much this path has changed since Linux 2.6, where the equivalent sequence had no counterpart at all. IBRS_ENTER writes the indirect branch restricted speculation bit on CPUs that need it, so that branch predictions trained in user mode cannot steer kernel indirect branches. UNTRAIN_RET addresses the return stack buffer, which some AMD parts allow user code to poison so that a kernel ret speculates to an address of the attacker's choosing. CLEAR_BRANCH_HISTORY flushes branch history on Intel parts affected by the history-injection variant. All three are ALTERNATIVE patch sites, so on a machine that does not need a given mitigation the bytes are rewritten to NOPs at boot and the cost is zero. Their placement is deliberate and the source says why: the comment notes that IBRS_ENTER clobbers %rax, so it must come after the syscall number has been saved. This is the concrete form of the argument made at the start of the chapter, that entering the kernel became measurably more expensive after 2018.

Once in C, do_syscall_64() adds a randomized kernel-stack offset, calls syscall_enter_from_user_mode(), invokes either the native x64 or x32 dispatch path, and then runs syscall_exit_to_user_mode(). The return value of do_syscall_64() is not the syscall result; it is a Boolean telling the assembly path whether a fast SYSRET exit is safe or whether the kernel must fall back to IRET. That Boolean connects entry to exit: after the common work is done, x86_64 must prove that the saved register state is clean enough for SYSRET before it can take the fastest way back to user mode.

The randomized offset deserves more than a clause. Under CONFIG_RANDOMIZE_KSTACK_OFFSET, add_random_kstack_offset() makes a variable-length allocation on the kernel stack so that the same system call does not place its stack frame at the same address on every invocation. The target is a class of exploits that relies on knowing, or on repeatedly probing for, where a particular kernel local variable will land. Randomizing per call turns a reliable overwrite into a guess. Both architectures do this, but the design is easy to misread: the offset used by this call was selected at the end of the previous one, by choose_random_kstack_offset(). Splitting the choice from the use keeps the random number generator off the entry fast path, and it means the value is already sitting in a per-CPU variable when the next call needs it. The ARM64 source is unusually candid about how little entropy survives: the raw value is masked to 10 bits, and because the AAPCS requires a 16-byte-aligned stack pointer at function boundaries the compiler discards the low 4, leaving 6 usable bits in SP[9:4]. Sixty-four possible positions will not stop a determined attacker who can retry, but it removes the assumption of a fixed layout that many published exploits depended on.

The dispatch itself contains one more check worth naming, because it is the counterpart on the x86 side of the sanitizing described in Section 2.2. do_syscall_x64() converts the signed number to unsigned int so that negatives become very large values and fail a single comparison against NR_syscalls, then passes it through array_index_nospec() before the switch. If both the x64 and x32 dispatchers decline the number, do_syscall_64() has one case left to distinguish. A number that is simply invalid gets __x64_sys_ni_syscall() and the -ENOSYS of Section 1. But a number of -1 means something entirely different: it is the convention by which seccomp or a ptrace supervisor cancels a system call, and the source comment marks the difference by calling the first case an "invalid system call, but still a system call." A cancelled call must not be dispatched and must not have its return value overwritten, because the supervisor has already set the value it wants user space to see. That is why the condition reads nr != -1 rather than simply testing the dispatchers. Section 6 returns to how a filter arranges this.

The x86_64 assembly path strongly prefers SYSRET because it is the fast architectural pair for SYSCALL. But Linux will use it only when the state is clean enough. The decision is computed in do_syscall_64() after syscall_exit_to_user_mode() has finished all common exit work. If any safety check fails, the assembly path jumps to swapgs_restore_regs_and_return_to_usermode and returns with IRET instead. 


/* arch/x86/entry/syscall_64.c */
/* XEN PV guests always use the IRET path */
if (cpu_feature_enabled(X86_FEATURE_XENPV))
	return false;

/* SYSRET requires RCX == RIP and R11 == EFLAGS */
if (unlikely(regs->cx != regs->ip || regs->r11 != regs->flags))
	return false;

/* CS and SS must match the values set in MSR_STAR */
if (unlikely(regs->cs != __USER_CS || regs->ss != __USER_DS))
	return false;

/* Non-canonical RIP would #GP in kernel space on SYSRET */
if (unlikely(regs->ip >= TASK_SIZE_MAX))
	return false;

/* SYSRET cannot safely restore RF or TF semantics */
if (unlikely(regs->flags & (X86_EFLAGS_RF | X86_EFLAGS_TF)))
	return false;

return true;

The non-canonical RIP check is the famous security gate. Intel CPUs can raise a general-protection fault in kernel mode if SYSRET tries to return to a non-canonical user RIP stored in RCX. Because user space also controls the user stack pointer, that fault historically created a path toward privilege escalation. Linux therefore rejects such contexts and forces the slower but fully general IRET path.

The assembly split is visible in arch/x86/entry/entry_64.S. If the Boolean returned in AL says fast return is safe, the code restores registers and executes sysretq. Otherwise it reconstructs an IRET frame, may copy it to a trampoline stack under KPTI, switches back to the user CR3, and finally executes the serializing IRET sequence.

syscall_return_via_sysret:
	IBRS_EXIT
	POP_REGS pop_rdi=0
	...
	SWITCH_TO_USER_CR3_STACK scratch_reg=%rdi
	...
	swapgs
	CLEAR_CPU_BUFFERS
	sysretq

swapgs_restore_regs_and_return_to_usermode:
	IBRS_EXIT
	...
	POP_REGS
	add	$8, %rsp
	...
	jmp	.Lnative_iret

The exit excerpt carries two mitigation macros that mirror the entry ones. IBRS_EXIT undoes the speculation restriction so that user code does not pay for it. CLEAR_CPU_BUFFERS expands to a single VERW instruction, whose architectural job is to check a segment selector but whose side effect on affected Intel parts is to flush the store buffer, fill buffers, and load ports. That flush is what closes the MDS and TAA family of attacks, in which a sibling hyperthread samples data left behind in those microarchitectural buffers by the kernel. Its position is not negotiable: it must be the last thing executed before the return to user mode, so both return paths carry their own copy rather than sharing one. Like the entry macros it is an ALTERNATIVE, present only on CPUs with the X86_FEATURE_CLEAR_CPU_BUF flag set.

Linux 2.6 discussions often present sysret as an obvious optimization over iret. Modern kernels still exploit that optimization, but only after threading through years of security hardening, Xen PV quirks, speculation controls, and canonical-address checks. A fast return is now a privilege that the register state must earn.

There is one more thing to say about the x86_64 path, and it undercuts the framing of everything above. The syscall_init() excerpt earlier in this section guarded its work with if (!cpu_feature_enabled(X86_FEATURE_FRED)), which was passed over at the time. That condition exists because Linux 7.0.12 supports a second, entirely separate mechanism for entering and leaving the kernel on x86_64: Flexible Return and Event Delivery, or FRED. On a machine where the CPU implements it and CONFIG_X86_FRED is set, MSR_LSTAR is never programmed, entry_SYSCALL_64 is never reached, and SYSRET is never executed. The SYSCALL instruction still exists and user code still issues it unchanged — the ABI is untouched — but the hardware delivers it somewhere else.

FRED's purpose is to replace an event-delivery design that has accumulated forty years of special cases. The legacy mechanism spreads the entry state across an IDT, a TSS, three different MSR pairs for SYSCALL and SYSENTER, and an interrupt stack table, and it leaves software to sort out awkward corners such as the one-instruction window after swapgs and the NMI-versus-IRET nesting problem. FRED replaces all of it with a single 4 KB-aligned entry point per privilege level and a stack frame that the hardware itself lays out, including the event type and vector. The consequence for this chapter is that a system call is no longer architecturally distinct from any other event. It arrives at asm_fred_entrypoint_user in arch/x86/entry/entry_64_fred.S, is classified by fred_entry_from_user() in arch/x86/entry/entry_fred.c as event type EVENT_TYPE_OTHER with vector FRED_SYSCALL, and only then is recognized as a system call. 


/* arch/x86/entry/entry_fred.c */
/* FRED EVENT_TYPE_OTHER vector numbers */
#define FRED_SYSCALL			1
#define FRED_SYSENTER			2

static __always_inline void fred_other(struct pt_regs *regs)
{
	/* The compiler can fold these conditions into a single test */
	if (likely(regs->fred_ss.vector == FRED_SYSCALL && regs->fred_ss.l)) {
		regs->orig_ax = regs->ax;
		regs->ax = -ENOSYS;
		do_syscall_64(regs, regs->orig_ax);
		return;
	} else if (ia32_enabled() &&
		   likely(regs->fred_ss.vector == FRED_SYSENTER && !regs->fred_ss.l)) {
		regs->orig_ax = regs->ax;
		regs->ax = -ENOSYS;
		do_fast_syscall_32(regs);
		return;
	} else {
		exc_invalid_op(regs);
		return;
	}
}

Two things about this code are worth dwelling on. First, it converges on do_syscall_64() — the same C function the legacy path calls. Everything this chapter says about dispatch, seccomp, tracing, signal checks, and the exit pipeline applies unchanged under FRED, because only the outermost shell was replaced. What FRED does in software is small precisely because it does so much more in hardware. Second, the checks are on fred_ss.l, the long-mode bit recorded in the hardware-supplied frame, which is how the same entry point distinguishes a 64-bit SYSCALL from a 32-bit SYSENTER without needing separate entry stubs for each.

The return side is where the contrast is sharpest. Everything earlier in this section — the five-way test in do_syscall_64(), the Boolean returned in AL, the branch between syscall_return_via_sysret and swapgs_restore_regs_and_return_to_usermode — exists because SYSRET cannot faithfully restore every user state and IRET can but is slow. FRED deletes the question. ERETU returns to user mode from the hardware-defined frame and restores the state correctly in every case, so the FRED assembly is a single unconditional instruction with no decision above it. The _ASM_EXTABLE_TYPE entry attached to it is the one remaining subtlety: if ERETU itself faults, the fixup re-enters at the FRED entry point rather than trying to unwind, using the exception-table machinery Section 4.4 describes. 


/* arch/x86/entry/entry_64_fred.S */
SYM_CODE_START_NOALIGN(asm_fred_entrypoint_user)
	FRED_ENTER
	call	fred_entry_from_user
SYM_INNER_LABEL(asm_fred_exit_user, SYM_L_GLOBAL)
	FRED_EXIT
1:	ERETU

	_ASM_EXTABLE_TYPE(1b, asm_fred_entrypoint_user, EX_TYPE_ERETU)
SYM_CODE_END(asm_fred_entrypoint_user)

FRED hardware is still uncommon, so the SYSCALL/SYSRET path described above remains the one almost every reader will actually execute, and it is the one to study. But it is worth knowing that the elaborate SYSRET eligibility test is not a permanent feature of x86_64. It is the cost of a 1997 instruction that was designed for speed before anyone had to think about what a hostile user-mode register state could do with it, and on FRED machines that cost is already gone.

The ARM64 SVC/ERET Path

ARM64's system call entry mechanism is architecturally cleaner than x86_64's because the AArch64 exception model was designed from scratch rather than being layered on top of decades of backward-compatible extensions. There is one instruction to enter the kernel (svc), one instruction to return (eret), and a well-defined exception vector table that routes all exceptions — synchronous traps, IRQs, FIQs, and system errors — through a uniform dispatch structure. The system call path is simply one particular synchronous exception from EL0 (user mode) to EL1 (kernel mode), identified by the exception syndrome register ESR_EL1.

The ARM64 path also integrates modern hardware features that x86_64 handles separately. Privileged Access Never (PAN) prevents accidental kernel reads of user memory. Pointer Authentication (PAC) signs and verifies return addresses on the stack. Memory Tagging Extension (MTE) can detect use-after-free and buffer-overflow bugs. All of these must be saved, restored, or re-enabled at the right points in the entry and exit sequence, making the assembly longer than a naive "save registers and call C" description would suggest.

On ARM64 the user instruction is svc #imm, which raises a synchronous exception from EL0 to EL1. The vector code in arch/arm64/kernel/entry.S saves general-purpose state with kernel_entry and branches into the higher-level handler selected by the exception class in ESR_EL1. For a 64-bit system call, the exception class is ESR_ELx_EC_SVC64. Current Linux 7.0.12 then lands in the C helper el0_svc() inside arch/arm64/kernel/entry-common.c, not directly in a monolithic assembly-only dispatcher as older descriptions sometimes imply. 


/* arch/arm64/kernel/entry-common.c */
static void noinstr el0_svc(struct pt_regs *regs)
{
	arm64_enter_from_user_mode(regs);
	cortex_a76_erratum_1463225_svc_handler();
	fpsimd_syscall_enter();
	local_daif_restore(DAIF_PROCCTX);
	do_el0_svc(regs);
	arm64_exit_to_user_mode(regs);
	fpsimd_syscall_exit();
}

Every line of that seven-line function does something the x86_64 path also has to do, just less visibly. arm64_enter_from_user_mode() performs the context-tracking transition that tells RCU and the time accounting that the CPU is now in the kernel, then calls mte_disable_tco_entry() to turn tag checking back on: user mode may have set the Tag Check Override bit, and the kernel must not inherit it. cortex_a76_erratum_1463225_svc_handler() works around a silicon defect in which a hardware single-step over an svc can be lost, which would let a debugged process run away from its debugger. fpsimd_syscall_enter() records the floating-point state, because the AArch64 procedure call standard lets a system call clobber the SVE and floating-point registers, and the kernel exploits that to avoid saving what it need not save. local_daif_restore(DAIF_PROCCTX) is the moment interrupts come back on. Its name refers to the four mask bits — Debug, SError, IRQ, and FIQ — that the hardware set on taking the exception, and DAIF_PROCCTX is the mask appropriate for ordinary process context. The ordering is the point: the context-tracking and tag-check state must be correct before the kernel can tolerate an interrupt, so the unmask comes last.

The actual syscall dispatch starts in do_el0_svc() within arch/arm64/kernel/syscall.c. Linux stores the syscall number in x8 for native tasks and then calls el0_svc_common(), which records orig_x0, stores the syscall number in regs->syscallno, handles ptrace and seccomp work if needed, and finally calls invoke_syscall(). The function pointer comes from sys_call_table, and the result is written back through syscall_set_return_value() so that the architecture ABI is consistently reflected in x0. 


/* arch/arm64/kernel/syscall.c */
void do_el0_svc(struct pt_regs *regs)
{
	el0_svc_common(regs, regs->regs[8], __NR_syscalls, sys_call_table);
}

static void el0_svc_common(struct pt_regs *regs, int scno, int sc_nr,
			   const syscall_fn_t syscall_table[])
{
	unsigned long flags = read_thread_flags();

	regs->orig_x0 = regs->regs[0];
	regs->syscallno = scno;
	...
	invoke_syscall(regs, scno, sc_nr, syscall_table);
	...
}

The three sets of ellipses in that excerpt hide the parts most worth reading, and each one is a case where ARM64 must do something x86_64 does not.

The first is Memory Tagging. Before anything else, el0_svc_common() checks _TIF_MTE_ASYNC_FAULT and, if it is set, writes -ERESTARTNOINTR as the return value and returns without dispatching the system call at all. An asynchronous tag check fault means user code touched memory with the wrong tag at some earlier, unknown instruction; the hardware recorded it rather than trapping immediately. The kernel must deliver that signal before the system call runs, not after, because the process is already in an undefined state. -ERESTARTNOINTR arranges for the call to be transparently retried once the signal handler is done, so a program with a benign tag fault does not also lose a system call.

The second is the skip protocol, the ARM64 counterpart of the nr != -1 case described for x86_64. Here the sentinel has a name, NO_SYSCALL, and a tracer skips a call by setting the number to it. The complication is stated at length in a source comment: this is indistinguishable from a user program calling syscall(-1). The kernel resolves it by pre-setting x0 to -ENOSYS whenever it sees NO_SYSCALL on the way in, so that if the tracer sets the number but forgets to set a return value, user space still sees a sane error instead of whatever its first argument happened to be. The comment concedes the result is "slightly odd" — a tracer that sets the number to -1 without initializing x0 gets x0 preserved for every case except a genuine syscall(-1) — and then observes that requesting a skip without setting a return value is not a sensible thing to do anyway. It is a good example of the kind of compromise an ABI promise forces.

The third is that the tracing flags are re-read after the call returns. The function samples read_thread_flags() once at the top, dispatches, and then checks again, because a system call can take a long time and a tracer can attach while it is running. The rule the code implements is asymmetric on purpose: if entry was traced then exit is traced unconditionally, matching what the old assembly did, but a call that was not traced on entry may still be traced on exit if the flags changed underneath it.

invoke_syscall() itself is where the index sanitizing discussed in Section 2.2 actually happens — syscall_table[array_index_nospec(scno, sc_nr)] — bracketed by the two halves of the stack-offset randomization described earlier: add_random_kstack_offset() at the top and choose_random_kstack_offset(get_random_u16()) at the very bottom, after the return value has already been stored. An out-of-range number falls to do_ni_syscall(), which on a compat task first offers it to compat_arm_syscall() for the ARM-private range before settling on sys_ni_syscall().

One thing el0_svc_common() deliberately does not do is also documented. A twenty-line comment explains that the architecture does not guarantee SPSR.BTYPE is zero when an svc is taken, so a process can return from a system call with a stale Branch Target Identification type and, if it has done something unwise with PROT_BTI, take a SIGILL. The kernel refuses to paper over this: it does not touch regs->pstate & PSR_BTYPE_MASK, on the grounds that a program that has arranged for this outcome should not be surprised by it. Silently sanitizing the field would hide a real bug in the program's own control-flow-integrity setup.

ARM64 entry code is less burdened by x86 segmentation history, but it has its own modern concerns. The exit and entry helpers must respect PAN, pointer authentication, MTE, shadow call stack state, and optional errata workarounds. In Linux 2.6 the ARM Linux story was primarily 32-bit ARM with SWI or OABI compatibility paths; today the mainstream path is AArch64 EL0 to EL1 with an explicitly saved pt_regs frame and a much richer common exit loop.

Once do_el0_svc() and the common return work have finished, ARM64 still has to restore EL0 state safely and hand control back with its architecture-specific return sequence. That final stage is shorter and cleaner than the x86_64 SYSRET versus IRET split, but it is still a full privileged restore path rather than a single naked instruction.

ARM64 uses a cleaner architectural return instruction: eret. But Linux still wraps it in a substantial amount of bookkeeping. After the C handler finishes, the assembly return path reaches ret_to_user in arch/arm64/kernel/entry.S. That label can re-enable single-stepping, erase the task stack when stackleak is enabled, and finally invokes kernel_exit 0. 


SYM_CODE_START_LOCAL(ret_to_user)
	ldr	x19, [tsk, #TSK_TI_FLAGS]
	enable_step_tsk x19, x2
#ifdef CONFIG_KSTACK_ERASE
	bl	stackleak_erase_on_task_stack
#endif
	kernel_exit 0
SYM_CODE_END(ret_to_user)

The kernel_exit macro restores ELR_EL1 and SPSR_EL1, reloads the general registers from the saved pt_regs frame, updates EL0-related state such as sp_el0, handles PAN and pointer-authentication details, and eventually executes eret. The macro is long because ARM64 entry code must integrate modern features like MTE, speculative-attack mitigations, and optional trampolines for unmapped-kernel-at-EL0 configurations. Conceptually, however, the rule is simple: the final user return is a privileged architectural restore of EL1-saved context. 


/* arch/arm64/kernel/entry.S, kernel_exit 0 excerpt */
msr	elr_el1, x21
msr	spsr_el1, x22
ldp	x0, x1, [sp, #16 * 0]
ldp	x2, x3, [sp, #16 * 1]
...
ldr	lr, [sp, #S_LR]
add	sp, sp, #PT_REGS_SIZE

Before ret_to_user is reached, arm64_exit_to_user_mode() has run, and its five lines are the mirror image of the entry helper. It disables interrupts, runs the shared exit preparation that handles pending signals and rescheduling, masks all four DAIF bits so that not even an SError can arrive during the final restore, calls mte_check_tfsr_exit() to fold any tag-check fault the kernel itself provoked into the task's state, and finally performs the context-tracking transition back to user mode. The comment above it states the constraint plainly: after it returns it is not safe to call regular kernel code, instrumentable code, or anything that might fault. Everything after that point is the assembly below. 


/* arch/arm64/kernel/entry-common.c */
static __always_inline void arm64_exit_to_user_mode(struct pt_regs *regs)
{
	local_irq_disable();
	exit_to_user_mode_prepare_legacy(regs);
	local_daif_mask();
	mte_check_tfsr_exit();
	exit_to_user_mode();
}

Two details in kernel_exit are worth naming because they have no x86_64 equivalent in the same shape. The first is the KPTI trampoline. When ARM64_UNMAP_KERNEL_AT_EL0 is active, the kernel is not mapped in the page tables that user mode will run with, so the return cannot simply eret from where it stands. An alternative_insn patch site turns a branch that skips the trampoline into a NOP, and the code instead stashes state, loads the per-CPU trampoline vector, points vbar_el1 at it, and branches to tramp_exit in the small region that is mapped in both address spaces. That trampoline performs the page-table switch and only then returns to EL0. The second is that the instruction after eret is sb, a Speculation Barrier. eret is an unconditional transfer, so nothing after it should ever execute, but some implementations will speculatively fetch past it; sb makes that harmless. Affected parts additionally emit tlbi vale1, xzr and dsb nsh beforehand under ARM64_WORKAROUND_SPECULATIVE_UNPRIV_LOAD.

The contrast with x86_64 is instructive, though not in the way the shorter version of this story suggests. ARM64 has no SYSRET-versus-IRET decision tree, and to that extent the return really is simpler. But it acquired an entirely different set of complications — the KPTI trampoline, the speculation barrier, the errata patch sites — that arrive as alternative_insn sites rather than as C branches, which makes them easy to overlook when reading the macro. The generic exit loop is shared in spirit; the last handful of instructions remain stubbornly architecture-specific on both sides.

Legacy and Compatibility Paths

One of Linux's strongest commitments is that old user-space binaries continue to work on new kernels. A statically linked i386 binary from 2003 that uses int $0x80 to invoke system calls must still run correctly on a kernel compiled in 2026 for x86_64. Similarly, a 32-bit ARM (AArch32) binary must work under an ARM64 kernel. This backward-compatibility guarantee means the kernel must maintain multiple entry paths, multiple dispatch tables, and multiple argument-conversion layers — even when the native fast path has long since moved to a different instruction.

Modern Linux still carries older doors into the kernel because old binaries continue to exist. A 64-bit x86 kernel can accept 32-bit system calls through int 0x80, through SYSENTER, or through the x32 ABI. The relevant assembly lives in files such as arch/x86/entry/entry_64_compat.S and arch/x86/entry/entry_32.S. The native fast path may be long-mode syscall, but compatibility code still matters for container images, legacy distributions, and testing.

It is worth naming the three doors, because they are not installed the same way and the difference matters. entry_SYSCALL_compat handles a 32-bit syscall instruction and is installed by writing its address to MSR_CSTAR, exactly parallel to how entry_SYSCALL_64 is installed through MSR_LSTAR. entry_SYSENTER_compat handles Intel's SYSENTER and is installed through the three MSR_IA32_SYSENTER_* registers. int80_emulation is different in kind: it is not an MSR-installed fast-path stub at all but an ordinary IDT gate at vector IA32_SYSCALL_VECTOR, installed alongside the page-fault and general-protection handlers in arch/x86/kernel/idt.c. The name is literal — on a 64-bit kernel int $0x80 is emulated through the normal exception machinery rather than served by a dedicated door, which is both slower and considerably easier to reason about. That is a reasonable trade for a path no performance-sensitive program has used in twenty years.

The idt_syscall_init() excerpt shown earlier elided the branch that chooses among them. The full function tests ia32_enabled(), and the else arm is the more interesting one. When 32-bit emulation is compiled out or disabled at boot, the kernel does not merely leave the MSRs alone: it points MSR_CSTAR at entry_SYSCALL32_ignore, sets MSR_IA32_SYSENTER_CS to an invalid segment, and zeroes the other two. The doors are not left unlocked, they are bricked up. This makes CONFIG_IA32_EMULATION and the ia32_emulation= boot parameter a genuine attack-surface control, not a mere space optimization: the compat syscall tables are a large body of code that most modern systems never execute, and a system that runs no 32-bit binaries can remove them from reach entirely. 


/* arch/x86/kernel/cpu/common.c */
static void wrmsrq_cstar(unsigned long val)
{
	/*
	 * Intel CPUs do not support 32-bit SYSCALL. Writing to MSR_CSTAR
	 * is so far ignored by the CPU, but raises a #VE trap in a TDX
	 * guest. Avoid the pointless write on all Intel CPUs.
	 */
	if (boot_cpu_data.x86_vendor != X86_VENDOR_INTEL)
		wrmsrq(MSR_CSTAR, val);
}

Even the act of installing these entry points carries archaeology. MSR_CSTAR is an AMD register; Intel CPUs do not implement 32-bit SYSCALL and have historically discarded writes to it. Discarding a write is harmless, so the kernel wrote it unconditionally for years. Then confidential computing arrived: inside a TDX guest that same ignored write raises a #VE. A line of code that had been correct-by-accident on every real machine became a fault on a new class of them, and the fix was to stop writing the register on Intel parts at all. The comment records the reasoning so the next reader does not "simplify" it back. Similarly, the ia32_enabled() arm carries a comment explaining that MSR_IA32_SYSENTER_EIP is truncated to 32 bits on AMD, which sounds alarming until the comment adds that AMD does not allow SYSENTER in long mode, so the truncated value is never used.

The x86 entry comments are equally blunt about why these paths cannot simply be deleted. In entry_64_compat.S the 32-bit SYSENTER path notes that some Android builds once inlined SYSENTER directly, forcing the kernel to keep support even when the ideal ABI would have routed everything through a libc veneer. This is the compatibility promise of Section 1 in its least glamorous form: a decision made by one vendor's build system a decade ago is now permanent kernel maintenance.

ARM64 has a parallel story through compat_sys_call_table and do_el0_svc_compat(). Native AArch64 tasks place the syscall number in x8; compat AArch32 tasks use regs->regs[7] and the compat table generated from arch/arm64/kernel/sys32.c. Keeping both paths side by side lets Linux present one kernel image as a host for multiple user-space ABIs.

The Common Exit Pipeline

Perhaps the most significant architectural change between Linux 2.6 and 7.0.12 in the system call subsystem is the creation of a unified, architecture-independent exit pipeline. In older kernels, each architecture implemented its own return-to-user logic in assembly, duplicating signal checks, rescheduling tests, and audit hooks across x86, ARM, MIPS, PowerPC, and every other supported platform. Bugs fixed in one architecture's exit path might go unfixed in another for months or years.

Linux 7.0.12 centralizes almost all of this logic in two C functions: syscall_enter_from_user_mode() and syscall_exit_to_user_mode(), both defined in include/linux/entry-common.h with their heavyweight implementations in kernel/entry/common.c. Architectures that select CONFIG_GENERIC_ENTRY — x86 among them — call these directly, so that seccomp filtering, ptrace notification, audit logging, signal delivery, rescheduling, and task-work callbacks all happen in one documented order. ARM64 is the instructive exception, and it is worth separating two things that are easily conflated. The syscall-specific enter and exit work is not shared: ARM64 does not select CONFIG_GENERIC_ENTRY, and el0_svc_common() in arch/arm64/kernel/syscall.c drives its own syscall_trace_enter() and syscall_trace_exit() through the same sequence of steps. The final return to user mode, however, genuinely is shared. arm64_exit_to_user_mode() calls exit_to_user_mode_prepare_legacy() and then exit_to_user_mode(), both from include/linux/irq-entry-common.h, which is the same last stage an architecture using the generic entry code reaches. So the tail of the pipeline is common to both architectures this book follows; the syscall-specific head is duplicated by design, and reading only one architecture's code will mislead you about the other.

The high-level entry/exit contract is documented in include/linux/entry-common.h. The function syscall_exit_to_user_mode() first runs one-time syscall-specific exit work, then disables interrupts and prepares the generic user-mode return loop, and finally calls exit_to_user_mode() for the architecture-neutral last stage. The actual loop that re-checks thread work flags lives in kernel/entry/common.c. 


/* include/linux/entry-common.h */
static __always_inline void syscall_exit_to_user_mode(struct pt_regs *regs)
{
	instrumentation_begin();
	syscall_exit_to_user_mode_work(regs);
	local_irq_disable_exit_to_user();
	syscall_exit_to_user_mode_prepare(regs);
	instrumentation_end();
	exit_to_user_mode();
}

The generic loop in kernel/entry/common.c looks for _TIF_NEED_RESCHED, _TIF_NEED_RESCHED_LAZY, _TIF_SIGPENDING, _TIF_NOTIFY_SIGNAL, _TIF_NOTIFY_RESUME, uprobes, livepatch state, and architecture-specific return work. If a signal is pending, the loop calls arch_do_signal_or_restart(). If rescheduling is needed, it calls schedule() before trying again. The return to user space is therefore conditional on the thread having no more mandatory kernel work.

This design is far more uniform than the 2.6 era. Older code scattered parts of the signal and reschedule logic through architecture-specific assembly return paths. Linux 7.0.12 still needs some per-architecture assembly on the final instruction boundary, but the policy loop is largely shared and easier to audit.

  • TIF_SIGPENDING means ordinary or fatal signals must be processed before resuming user mode.
  • TIF_NOTIFY_SIGNAL is not itself a POSIX signal, but it reuses the same return-to-user machinery to trigger notifications.
  • TIF_NEED_RESCHED and TIF_NEED_RESCHED_LAZY request a scheduler pass before returning.
  • TIF_NOTIFY_RESUME drives task-work and restart-sequence bookkeeping such as rseq state updates.

A common beginner mistake is to think that a syscall return value is written and user mode resumes immediately. In reality the return register is only one field in pt_regs until the entire exit loop has proven that returning is safe and complete.

Parameter Passing and Validation

A system call ABI is not just a number; it is also a contract about registers, pointer provenance, and fault behavior. When a user program invokes a system call, it places arguments into architecture-defined registers. Some of those arguments are simple scalar values — file descriptors, flags, byte counts — that the kernel can use directly. Others are pointers into user-space memory: buffer addresses, path strings, or structured control blocks that the kernel must read or write across the privilege boundary.

Handling pointers safely is arguably the most critical responsibility of the system call layer. User space can pass any value in a register — including NULL, a kernel address, an address inside a guard page, or a pointer to memory that is concurrently being unmapped by another thread. The kernel cannot simply dereference such a pointer the way it would dereference a kernel pointer. It must validate the address range, use specialized copy functions that can recover gracefully from page faults, and rely on hardware enforcement (SMAP on x86, PAN on ARM64) to catch accidental unprotected accesses. If any of these safeguards fail, the result can range from information leakage (reading kernel memory via a crafted user pointer) to full privilege escalation.

verify_area() was the 2.6-era function that validated user pointers before access. That function is long gone. Modern Linux uses a layered approach: access_ok() checks address-space boundaries, copy_from_user()/copy_to_user() perform the actual data transfer with fault recovery, and exception tables provide the low-level mechanism that turns a kernel-mode page fault into a clean -EFAULT return rather than a kernel panic. Hardware features like SMAP and PAN add a further layer of defense by making accidental unprotected user-memory access a CPU fault even when the page tables would have allowed it.

One framing is worth fixing before the details, because the section is easier to follow with it and the older literature does not supply it. Validating a system call argument is a two-sided problem. The obvious side is the user pointer, which is hostile by assumption and is what access_ok(), address masking, and the hardware features are for. The less obvious side is the kernel object at the other end of the copy, which is written by kernel programmers and is therefore trusted — and which is where the length usually comes from a user-supplied number. Linux checks both, at build time where it can and at run time where it cannot, and a reader who tracks only the first half will find half the code in these helpers unexplained.

Register Conventions

Unlike older system call mechanisms that passed some arguments on the stack (the 32-bit x86 int $0x80 path, for example, used all six registers but older Unix kernels sometimes used the user stack), modern 64-bit architectures pass all system call arguments in registers. This is both faster — no memory access is needed to read arguments — and safer, because the kernel does not need to touch the user stack at all during the initial argument extraction.

The x86_64 and ARM64 syscall ABIs both support up to six direct arguments, but they place them in different registers. On x86_64 the syscall number is in RAX and arguments go in RDI, RSI, RDX, R10, R8, and R9. On ARM64 the syscall number is in X8 and arguments go in X0 through X5. In both cases the return value comes back in the primary result register, RAX or X0. The six-argument limit is not an arbitrary choice — it matches the maximum number of registers both architectures are willing to dedicate to the system call interface, and very few system calls actually use all six slots.

The kernel extracts arguments from the saved pt_regs frame through architecture-specific helper functions. The syscall_get_arguments() function provides a uniform interface that tracing, ptrace, and seccomp can use to inspect arguments regardless of the underlying register layout. 


/* arch/x86/include/asm/syscall.h, the CONFIG_X86_64 definition */
static inline void syscall_get_arguments(struct task_struct *task,
					 struct pt_regs *regs,
					 unsigned long *args)
{
# ifdef CONFIG_IA32_EMULATION
	if (task->thread_info.status & TS_COMPAT) {
		*args++ = regs->bx;
		*args++ = regs->cx;
		*args++ = regs->dx;
		*args++ = regs->si;
		*args++ = regs->di;
		*args   = regs->bp;
	} else
# endif
	{
		*args++ = regs->di;
		*args++ = regs->si;
		*args++ = regs->dx;
		*args++ = regs->r10;
		*args++ = regs->r8;
		*args   = regs->r9;
	}
}


/* arch/arm64/include/asm/syscall.h */
static inline void syscall_get_arguments(struct task_struct *task,
					 struct pt_regs *regs,
					 unsigned long *args)
{
	args[0] = regs->orig_x0;
	args[1] = regs->regs[1];
	args[2] = regs->regs[2];
	args[3] = regs->regs[3];
	args[4] = regs->regs[4];
	args[5] = regs->regs[5];
}

The TS_COMPAT branch on x86_64 is not a detail to skim past, because it is the reason a security tool cannot simply read "argument 3" and be done. A 32-bit task entering through one of the compatibility doors of Section 3.3 delivers its arguments in an entirely different register set — BX, CX, DX, SI, DI, BP — and the same pt_regs field therefore means different things depending on which ABI the task is using. Every consumer of this interface has to know that. It is the reason struct seccomp_data carries an arch field at all, as Section 6 shows, and the reason a filter that inspects an argument without first checking that field is not a filter but a suggestion: the same numeric check applied to the wrong ABI reads the wrong register. ARM64 has the mirror-image arrangement in do_el0_svc_compat(), where the syscall number arrives in x7 rather than x8, but the argument registers happen to coincide, so its version of this function needs no branch.

Two more properties of the saved frame matter as much as the register list. The first is that args[0] on both architectures comes from the saved copy — orig_ax on x86_64 and orig_x0 on ARM64 — rather than from the live register. The live register is where the return value goes, so by the time anything wants to inspect the arguments of a completed call it has already been overwritten. Preserving the original is what makes both syscall restart (Section 8) and exit-time tracing possible at all. The second is that this interface is writable as well as readable: syscall_set_arguments() exists alongside the getter, and it is how a ptrace supervisor rewrites a call's arguments in flight, and how the skip protocol of Section 3 substitutes a different call entirely.

The x86_64 use of R10 instead of RCX is the classic interview fact, but its source is simple hardware behavior. The syscall instruction copies the user RIP into RCX and user RFLAGS into R11, so those registers cannot carry normal arguments across the boundary. The Linux ABI chooses R10 to keep six arguments available without spilling to memory.

The six-slot ceiling is a hard limit, and it has shaped the design of every interface added since. When a system call needs more than six values, or needs room to grow, it cannot add a seventh register; it must pass a pointer to a structure instead. That is exactly why the modern additions this chapter keeps returning to look the way they do: openat2() takes a struct open_how, clone3() takes a struct clone_args, io_uring_setup() takes a struct io_uring_params. Each of them also takes the structure's size as a separate argument, which turns a fixed six-register interface into an extensible one — and, less happily, converts a set of scalar arguments the kernel could use directly into a pointer that must be validated and copied. The rest of this section is about what that conversion costs.

Verifying the Parameters

Scalar arguments such as file descriptors, flags, and byte counts need validation too — a negative file descriptor is rejected, an invalid flag combination returns -EINVAL — but that validation is straightforward C logic inside each service routine. Pointer arguments are a fundamentally different problem because they cross the user-kernel trust boundary. The kernel must verify that a user-supplied pointer actually refers to user-space memory before it attempts to read or write through it, and even after that check, the access itself must be prepared to handle a page fault at any time.

Scalar arguments are cheap to decode, but pointer arguments are never trustworthy. A user task can pass a NULL pointer, a kernel-looking address, an unmapped range, a tagged address on ARM64, or a buffer that becomes invalid halfway through the syscall. That is why Linux separates parameter verification from the later copy or dereference step. The verification answers the question "is this address range plausibly in user space?" while the copy functions handle the separate question "can we actually access the memory right now?"

The first gate is usually access_ok(). It does not copy anything and it does not promise that the page is presently mapped; it only answers the narrower question of whether an address range is syntactically within the process-visible user portion of the virtual address space. The generic implementation in include/asm-generic/access_ok.h is two comparisons — size <= TASK_SIZE_MAX and addr <= TASK_SIZE_MAX - size — written that way so that the overflow case, where addr + size wraps around zero and lands back in user space, cannot slip through.

Both architectures replace that generic version, and the reasons differ enough to be worth following. ARM64 wraps it: if the task has opted into the tagged-address ABI, or if the access is being made by a kernel thread doing asynchronous I/O on behalf of such a task, access_ok() first calls untagged_addr() to strip the top-byte tag before comparing. The comment explains the second case, which is the non-obvious one: an AIO kernel thread does not carry the TIF_TAGGED_ADDR flag of the process whose memory it is touching, so the untagging must be unconditional for kernel threads or a legitimate tagged pointer would be rejected.

Pointer tagging is no longer an ARM64-only concern, which is a change since this chapter's predecessor was written. x86_64 gained Linear Address Masking, and under CONFIG_ADDRESS_MASKING the x86 untagged_addr() is a real instruction — an ALTERNATIVE-patched and against a per-CPU mask, present only when X86_FEATURE_LAM is set. Any code that assumes a user pointer's top bits are zero is now wrong on both architectures this book follows.

x86_64's replacement goes considerably further, and it is the piece the excerpt shown later in this section quietly depends on. Instead of asking whether a pointer is valid and branching on the answer, x86_64 can make it valid. 


/* arch/x86/include/asm/uaccess_64.h */
#define valid_user_address(x) \
	likely((__force unsigned long)(x) <= runtime_const_ptr(USER_PTR_MAX))

/*
 * Masking the user address is an alternative to a conditional
 * user_access_begin that can avoid the fencing. This only works
 * for dense accesses starting at the address.
 */
static inline void __user *mask_user_address(const void __user *ptr)
{
	void __user *ret;
	asm("cmp %1,%0\n\t"
	    "cmova %1,%0"
		:"=r" (ret)
		:"r" (runtime_const_ptr(USER_PTR_MAX)),
		 "0" (ptr));
	return ret;
}

Two instructions replace a check, a branch, and a speculation barrier. A pointer above USER_PTR_MAX is not rejected; it is clamped to USER_PTR_MAX by a conditional move, and the subsequent access simply faults on the guard page that the kernel guarantees sits between the top of user space and the non-canonical gap. The fault is then recovered by the exception table, which is machinery the copy helpers need anyway. The gain is that cmov is not a branch, so there is nothing for the CPU to mispredict and therefore no need for the barrier_nospec() that the checked path must execute after access_ok() succeeds. Removing a serializing barrier from the hot path of every copy_from_user() in the kernel is a large win, and it is available only because the address space happens to have a guard page in the right place.

USER_PTR_MAX is not a compile-time constant, because the boundary depends on features detected at boot. It is a runtime constant: runtime_const_init() patches the value directly into the instruction stream of every site that uses it, so the comparison costs an immediate operand rather than a memory load from a global. In Linux 7.0.12 the value is simply TASK_SIZE_MAX; the widening to (1UL << 63) - PAGE_SIZE that LAM would allow sits in the source as a commented-out block, gated on Linear Address Space Separation support that has not landed. That comment is worth noticing, because it records a case where a hardening feature is being deliberately held back until a second one exists to backstop it.

The mechanism is not universal. Only x86_64 and PowerPC define masked_user_access_begin, so can_do_masked_user_access() is 0 on ARM64 and the classic access_ok()-then-barrier_nospec() path is what runs there. ARM64 does have an equivalent idea, but it applies it at a different point and by a different trick: __uaccess_mask_ptr() clears bit 55 of the pointer with a single bic, which forces the address into the TTBR0 half of the address space. A speculatively-passed access_ok() therefore cannot reach kernel memory, because after the mask no user pointer can name kernel memory in the first place. The two architectures arrive at the same property — no branch to mispredict, no barrier to execute — from opposite directions: x86 clamps the value to a boundary, ARM64 clears the bit that defines which half the address is in.

Modern hardware then enforces that policy. SMAP on x86 blocks ordinary privileged data accesses to user pages unless the kernel explicitly opens a short access window, typically through helpers that emit stac and clac around the faultable instruction stream. PAN on ARM64 has the same goal but reaches it a different way, and the difference is easy to state wrongly. ARM64's ordinary user-access helpers do not disable PAN at all. They are built on ldtr and sttr, the unprivileged load and store instructions, which the hardware permission-checks as though EL0 had issued them even though the kernel is running at EL1. An ldtr against a kernel address fails for the same reason a user program's load would, so there is no window to open and nothing to close. uaccess_enable_privileged() and uaccess_disable_privileged() exist for the smaller set of accessors that must use ordinary loads and stores, and those really do toggle PSTATE.PAN through an ALTERNATIVE patched in only on CPUs with ARM64_HAS_PAN. On hardware without PAN, CONFIG_ARM64_SW_TTBR0_PAN emulates it by pointing TTBR0_EL1 at reserved_pg_dir so that user mappings are not merely forbidden but absent, which is also what makes the same helpers work under KPTI. Either way, generic kernel code that dereferences a user pointer directly faults immediately instead of silently reading or writing through it.

That layered design replaced the much older verify_area() model discussed in Linux 2.6-era material. Current kernels do not ask every syscall author to call one monolithic verifier and then trust the pointer forever. Instead they combine access_ok(), typed get_user() or copy_from_user()-style helpers, speculation barriers where needed, and exception-table fixups for the residual fault cases. The result is narrower, easier to audit, and much better aligned with hardware isolation features.

Accessing the Process Address Space

Once the address range has passed the access_ok() gate, the kernel must perform the actual data transfer between user and kernel memory. This is not a simple memcpy() — user memory may be swapped out, the page may not yet be allocated (demand paging), and the user-space thread may be concurrently modifying or unmapping the same memory region. Any of these conditions can cause a page fault during the copy, and the kernel must handle that fault gracefully rather than panicking.

Linux provides a family of helper functions for this purpose, each designed for a specific access pattern. Bulk transfers go through copy_from_user() and copy_to_user(). Single scalar reads and writes use get_user() and put_user(). All of these helpers share a common design: they attempt the access, and if a fault occurs, they recover through the exception table mechanism (described in the next subsection) rather than crashing. The key guarantee is that a fault in user memory access always returns an error code to the caller, never triggers a kernel oops. 


/* include/linux/uaccess.h */
static inline __must_check unsigned long
_inline_copy_from_user(void *to, const void __user *from, unsigned long n)
{
	unsigned long res = n;
	might_fault();
	if (should_fail_usercopy())
		goto fail;
	if (can_do_masked_user_access())
		from = mask_user_address(from);
	else {
		if (!access_ok(from, n))
			goto fail;
		/*
		 * Ensure that bad access_ok() speculation will not
		 * lead to nasty side effects *after* the copy is
		 * finished:
		 */
		barrier_nospec();
	}
	instrument_copy_from_user_before(to, from, n);
	res = raw_copy_from_user(to, from, n);
	instrument_copy_from_user_after(to, from, n, res);
	if (likely(!res))
		return 0;
fail:
	memset(to + (n - res), 0, res);
	return res;
}

The semantics are worth memorizing. copy_from_user() returns the number of bytes that could not be copied, not a simple success Boolean. The generic inline implementation zero-fills the uncopied tail when a short copy happens, preventing uninitialized kernel stack data from leaking into later logic. copy_to_user() mirrors the operation in the opposite direction, but it is not a symmetric mirror and the differences are all deliberate. _inline_copy_to_user() does not zero-fill on failure, because there is nothing to fill: the destination is user memory, and leaving a user buffer partially written is the caller's problem, not a kernel information leak. It also does not use the masking path, because masking works only for a dense access starting at the pointer and the write side has not been converted. It keeps the plain access_ok() test, and if that test fails it returns n without attempting anything at all.

Three other things happen in that function that a reader can pass over without noticing they are there.

might_fault() is a debugging assertion with real teeth. Copying user memory can sleep — the page may be swapped out, or not yet faulted in — so calling one of these helpers while holding a spinlock, or in any atomic context, is a bug that will deadlock only under memory pressure and therefore only in production. might_fault() catches it immediately on a kernel built with the relevant debug options, by running the same checks as might_sleep() and additionally asserting that mmap_lock could be taken here. It correctly does nothing when pagefault_disabled(), which is how the deliberately non-sleeping variants stay legal. Those variants are the ones to reach for when the context genuinely is atomic: copy_from_user_nofault() brackets the access with pagefault_disable() so that a missing page returns -EFAULT rather than blocking, which is what makes it usable from a tracing probe or a BPF program running in interrupt context.

should_fail_usercopy() is a fault-injection hook. Under CONFIG_FAIL_USERCOPY it can be told to fail a configurable fraction of user copies, so that the error paths — which in normal testing are essentially never taken — get exercised. This matters more than it sounds: the code that runs after a failed copy_from_user() is exactly the code most likely to leak a reference, forget a lock, or return a half-initialized structure, and without injection it is nearly unreachable from a test suite.

The instrument_copy_from_user_before() and ..._after() calls are where KASAN, KMSAN and KCSAN hook in. The split into two calls is not cosmetic. KMSAN in particular needs to mark the destination as initialized after the copy and only for the bytes that actually arrived, which is why the "after" variant is the one that receives res.

The most important omission in the account so far, though, is that everything described up to this point validates the user side of the transfer. The kernel side is equally capable of being wrong, and the classic bug has nothing to do with a hostile pointer: a driver holds a small kernel structure, accepts a length from user space, and copies that many bytes out of it. The user pointer is perfectly valid, access_ok() is satisfied, no fault occurs, and the call cheerfully copies whatever follows the structure in the slab — other objects, freed memory, or a pointer that defeats KASLR.

Linux guards this with two layers, both entered from check_copy_size(), which every copy_from_user() and copy_to_user() calls before anything else. 


/* include/linux/ucopysize.h */
static __always_inline __must_check bool
check_copy_size(const void *addr, size_t bytes, bool is_source)
{
	int sz = __builtin_object_size(addr, 0);
	if (unlikely(sz >= 0 && sz < bytes)) {
		if (!__builtin_constant_p(bytes))
			copy_overflow(sz, bytes);
		else if (is_source)
			__bad_copy_from();
		else
			__bad_copy_to();
		return false;
	}
	if (WARN_ON_ONCE(bytes > INT_MAX))
		return false;
	check_object_size(addr, bytes, is_source);
	return true;
}

The first layer is a compile-time one. When the compiler can determine the size of the kernel object through __builtin_object_size() and the length is also a constant, an over-long copy is not a runtime warning but a build failure: __bad_copy_from() and __bad_copy_to() are declared with __compiletime_error, and their error strings read "copy source size is too small" and "copy destination size is too small". A whole class of buffer overflow is thereby prevented from ever reaching a running kernel. When the size is known but the length is not, the same check runs at runtime and calls copy_overflow(), which is a BUG().

The second layer is hardened usercopy, reached through check_object_size() and enabled by CONFIG_HARDENED_USERCOPY. Where the compiler knows nothing, __check_object_size() in mm/usercopy.c asks the allocator at runtime whether the requested range actually fits inside a single legitimate object. It rejects a range that spans a slab object boundary, one that runs off the end of the current stack frame, one that overlaps kernel text — the check that stops a copy from exporting the kernel's own instructions — and one that names an address which is not a valid kernel object at all. Failure is not an error return but usercopy_abort(), which kills the machine, on the reasoning that a copy of this shape means kernel state is already corrupt. The check is gated behind a static key so that the cost is a patched-out NOP when the feature is off, and it is skipped entirely when the length is a compile-time constant, since that case was already settled at build time.

The division of labour is worth stating plainly, because the two halves are often conflated. access_ok() and the masking discussed earlier answer "may the kernel touch this user address?" check_copy_size() and hardened usercopy answer "does this kernel object really extend that far?" A copy needs both, and neither can substitute for the other.

For small scalar accesses, the macros get_user() and put_user() are cheaper and more precise. They still may fault, but they let the compiler operate on typed values and often compile into a single faultable load or store surrounded by exception-table annotations. The “unsafe” variants such as unsafe_get_user() and unsafe_put_user() are used inside explicitly scoped user-access windows where the caller already handled access_ok() and wants a compact fast path.

Those windows are opened by user_access_begin() and closed by user_access_end(), and they exist because the per-access overhead is not the copy itself but the permission toggle around it. On x86 each ordinary put_user() pays a stac and a clac; on ARM64 each one may pay a TTBR0 switch. For a routine that writes twenty fields of a structure one at a time — signal frame setup is the canonical example — paying that twenty times is pure waste. Opening the window once and using the unsafe_ accessors inside it pays it once. The price is that the unsafe_ accessors take an error label rather than returning a value, so the caller must supply the fault path explicitly, and that the code between begin and end runs with user access enabled and must therefore be short, must not call out to arbitrary functions, and must not be preempted into something that assumes the guard is up. It is a deliberately awkward interface, and the awkwardness is the point: it makes the window visible in the source.

The validator at the syscall boundary is often richer than a plain copy. The modern openat2() example in fs/open.c uses copy_struct_from_user() to support extensible structure versions, rejects undersized or absurdly large user buffers, and then normalizes the result before path resolution even starts. That sort of versioned structure ABI is increasingly common in post-2.6 interfaces because it avoids the flag-space exhaustion that plagued older multiplexed syscalls. 


/* fs/open.c */
SYSCALL_DEFINE4(openat2, int, dfd, const char __user *, filename,
		struct open_how __user *, how, size_t, usize)
{
	int err;
	struct open_how tmp;

	if (unlikely(usize < OPEN_HOW_SIZE_VER0))
		return -EINVAL;
	if (unlikely(usize > PAGE_SIZE))
		return -E2BIG;

	err = copy_struct_from_user(&tmp, sizeof(tmp), how, usize);
	if (err)
		return err;

	return do_sys_openat2(dfd, filename, &tmp);
}

The two bounds checks before the copy are not redundant with what copy_struct_from_user() does; they are the caller's half of a contract that the helper documents in detail. The rule for extensible structures is that new fields are only ever appended, and that a zeroed new field must mean what the old struct meant, and given that rule there are exactly three cases. If the user's size equals the kernel's, the structure is copied verbatim. If the user's size is smaller — an old program on a new kernel — the kernel zero-fills the fields the program did not know about. If the user's size is larger — a new program on an old kernel — the kernel cannot simply ignore the excess, because the program may be relying on a feature this kernel does not implement. It calls check_zeroed_user() on the trailing bytes and returns -E2BIG if any of them is non-zero. Silence would be the dangerous answer here: a program that asked for a security-relevant flag and was told "success" by a kernel that discarded it is worse off than one that got an error. This is the extensible-syscall pattern in miniature, and it is why interfaces added since 2.6 tend to carry a size argument rather than another flags word.

There is one very common class of pointer argument that none of the machinery described so far handles, and the chapter would be incomplete without it. A pathname is not a fixed-size object, so copy_from_user() cannot be used: the kernel does not know how many bytes to ask for, and asking for PATH_MAX would fault whenever the string happened to sit near the end of a mapping. The helper for this is strncpy_from_user(), which copies up to a limit but stops at the first NUL, returning the string length on success, the limit if the string was too long, and -EFAULT if the access failed. It reads word at a time rather than byte at a time, using the same can_do_masked_user_access() fast path as the bulk copy helpers.

The layer above it is getname(), and its design answers a question that the copy helpers alone do not. Why copy the pathname at all, rather than resolving it directly out of user memory? Because path resolution is long, it sleeps, and the string lives in memory that another thread of the same process can rewrite at any moment. Resolving in place would be a time-of-check-to-time-of-use bug of the most classic kind: a permission check performed on one path and the actual open performed on another. Copying the name into kernel memory once, at the very start, is what makes the rest of the resolution safe to reason about. 


/* fs/namei.c, do_getname() */
	kname = (char *)result->iname;
	result->name = kname;

	len = strncpy_from_user(kname, filename, EMBEDDED_NAME_MAX);
	/*
	 * Handle both empty path and copy failure in one go.
	 */
	if (unlikely(len <= 0)) {
		/* The empty path is special. */
		if (!len && !(flags & LOOKUP_EMPTY))
			len = -ENOENT;
	}

	/*
	 * Uh-oh. We have a name that's approaching PATH_MAX. Allocate a
	 * separate struct filename so we can dedicate the entire
	 * names_cache allocation for the pathname, and re-do the copy from
	 * userland.
	 */
	if (unlikely(len == EMBEDDED_NAME_MAX))
		len = getname_long(result, filename);

The result is a struct filename, and the allocation strategy in that excerpt is a good example of optimizing for the case that actually occurs. Almost every pathname is short, so the structure embeds a character array and the first copy targets it directly — one allocation from a dedicated cache, no separate buffer. Only if the name fills that embedded array does the kernel conclude it may be approaching PATH_MAX, allocate a full-size buffer, and copy again from the beginning. Paying for a second copy in the rare case buys a single allocation in the common one. Note also that the empty path and a failed copy are folded into one test, with LOOKUP_EMPTY deciding whether an empty string is -ENOENT or a legitimate request to operate on the directory file descriptor itself — the mechanism behind AT_EMPTY_PATH.

struct filename is reference counted and released with putname(), which matters because the same copied name is handed to the audit subsystem. A service routine that takes a pathname therefore has a resource to release on every exit path, including the error ones, which is a more common source of leaks in new syscall code than anything involving the copy itself.

Dynamic Address Checking: The Exception Tables

The access_ok() check and the copy_from_user() family provide the high-level interface, but the low-level mechanism that makes them work is the exception table. The fundamental problem is this: when the kernel executes a load or store instruction that touches user memory, and that memory is not currently mapped (or is mapped with the wrong permissions), the CPU raises a page fault. In normal user-space execution, the kernel handles such faults by allocating pages, reading from swap, or delivering SIGSEGV. But when the fault occurs while the kernel itself is executing — inside copy_from_user(), for example — the kernel cannot deliver a signal to itself. It needs a different recovery mechanism.

Exception tables provide that mechanism. They are small linker-collected data structures stored in the __ex_table section of the kernel binary. Each entry records a faultable instruction address and a recovery target, plus architecture-specific type metadata that tells the handler what kind of fixup is appropriate. When a kernel-mode page fault occurs, the fault handler searches these tables for the faulting instruction pointer. If a match is found, execution is redirected to the fixup address instead of panicking — typically a label that sets -EFAULT in the return register and continues normally. 


/* arch/x86/include/asm/extable.h */
struct exception_table_entry {
	int insn, fixup, data;
};

The two layouts look almost identical, and the difference is instructive. ARM64 spends a whole short on type and another on data. x86 has one int called data, and it is not a type field but a packed word: the low byte is the type, the next nibble names a register, the nibble above that carries flags, and the top sixteen bits hold a signed immediate. That encoding is what lets a single table entry say something as specific as "set the register named here to -EFAULT", "clear AX and DX on the way out", or, for EX_TYPE_UCOPY_LEN, "recompute the remaining byte count as reg + imm * cx". The alternative would be a distinct fixup label for each combination, and there are enough combinations that the table would be larger than the code it protects. Reading down Table 10-10, it is worth noticing how much of the list has nothing to do with user memory. The numbers run from 0 to 21 with one value retired, and only three of the twenty-one surviving types — EX_TYPE_UACCESS, EX_TYPE_UCOPY_LEN and the aliases built on EX_TYPE_IMM_REG — belong to the copy helpers at all. The rest recover machine-check-safe accesses, unimplemented MSRs, corrupted FPU state images, JIT-compiled BPF loads, a word-at-a-time string load that ran off the end of a page, and, at the top of the list, the FRED ERETU that Section 3.1 met. The exception table is best understood not as part of the user-copy machinery but as the kernel's general answer to "this instruction may fault and I know what to do about it" — user copies are simply its largest customer.

When a page fault or access fault occurs in kernel mode, the low-level fault handler asks whether the current instruction pointer is listed in an exception table. On x86 this leads to fixup_exception() in arch/x86/mm/extable.c. On ARM64 it leads to fixup_exception() in arch/arm64/mm/extable.c. If a matching entry exists and its type says the fault is recoverable, the handler rewrites registers or the program counter so execution continues at a safe fixup label instead of oopsing the kernel. If no entry exists, both architectures fall through to the oops path, which is the correct outcome: an unannotated kernel fault means the kernel dereferenced something it had no business dereferencing, and continuing would be worse than stopping.

The lookup itself spans three separate tables, searched in order by search_exception_tables(): the built-in kernel table, then every loaded module's table, then the tables registered by the BPF JIT. The last of these has to be dynamic, because BPF programs are compiled to machine code at load time and their faultable instructions do not exist when the kernel is linked.

One x86 handler is worth singling out because it documents a hazard rather than fixing one. ex_handler_uaccess() does nothing beyond calling the default handler, but it first issues a WARN_ONCE if the trap was a general protection fault at an address that does not look like a plausible user access. The reason is that a non-canonical address on x86_64 raises #GP, not #PF, so a user pointer sitting in the canonical hole arrives through a different vector than an unmapped one. User-access fixups must therefore accept #GP as well as #PF, and the warning is there to catch the case where accepting it has quietly papered over a genuine kernel bug.

Generating the Exception Tables and the Fixup Code

Exception tables do not appear automatically when the compiler emits a faultable load — the C compiler has no concept of "this load might fault and that's okay." Instead, the low-level user-access helpers use inline assembly with explicit annotations that pair each potentially-faulting instruction with a recovery label. These annotations emit records into the __ex_table linker section, where they accumulate from every compilation unit in the kernel. The result is a global table of "if this instruction faults, jump to this fixup" entries that the fault handler can binary-search at runtime.

Understanding how these entries are generated is important for two reasons. First, it explains why user-copy helpers can look like ordinary C code on the fast path — the fault recovery is out-of-line and only reached when something goes wrong. Second, it shows why writing new user-access code requires using the kernel's provided macros rather than raw pointer dereferences: without the __ex_table annotation, a kernel-mode fault on a user address will trigger a panic instead of a clean error return.

On x86, arch/x86/include/asm/asm.h defines macros such as _ASM_EXTABLE(), _ASM_EXTABLE_UA(), and _ASM_EXTABLE_FAULT(), all of which emit relative records into the __ex_table section with a faulting instruction address, a fixup address, and a type field. 


/* arch/x86/include/asm/asm.h */
#define _ASM_EXTABLE(from, to)						_ASM_EXTABLE_TYPE(from, to, EX_TYPE_DEFAULT)

#define _ASM_EXTABLE_UA(from, to)					_ASM_EXTABLE_TYPE(from, to, EX_TYPE_UACCESS)

The corresponding fixup code is usually kept out of the fast path. Historically that meant a dedicated .fixup section; in current trees you will also see shared handler labels such as __get_user_handle_exception and __put_user_handle_exception in the x86 user-access assembly. Either way, the normal instruction stream stays straight-line while the rare fault case branches to a side path that synthesizes -EFAULT, zeroes result registers when needed, or adjusts the remaining copy count. In arch/x86/mm/extable.c, ex_handler_default() advances regs->ip to the recorded fixup target, while ex_handler_fault() also stores the trap number in regs->ax before continuing.

Link time and early boot finish the job. The linker script keeps every __ex_table contribution, the generic sort helpers in lib/extable.c know how to order the relative entries, and sort_main_extable() in kernel/extable.c sorts the built-in table if build-time tools have not already done so. That sorting matters because the runtime lookup path is a binary search: search_exception_tables() walks the kernel, module, and BPF tables, and each table lookup eventually reaches search_extable(), which uses bsearch() over the ordered entries.

ARM64 uses the same overall idea with a different record layout. The emitted records are described by struct exception_table_entry in arch/arm64/include/asm/extable.h, and the assembler helpers in arch/arm64/include/asm/asm-extable.h fill in relative instruction and fixup offsets plus type and data fields for handlers such as EX_TYPE_UACCESS_ERR_ZERO and EX_TYPE_UACCESS_CPY. Older discussions sometimes describe this as an EX_ENTRY_HANDLER-style scheme; in Linux 7.0.12 the concrete helpers are the _ASM_EXTABLE_UACCESS* family, and the runtime fixup still lands in architecture-specific handlers selected from the encoded type.

ARM64 puts the table to a second use that has nothing to do with recovery. When an EL1 permission fault occurs on a user address, arch/arm64/mm/fault.c calls insn_may_access_user(), which looks the faulting instruction up in the exception tables and, for a copy annotation, additionally checks that the fault direction matches the direction the annotation claims. If the answer is no, the kernel does not attempt a fixup and does not oops generically; it calls die_kernel_fault() with the message "access to user memory outside uaccess routines". That last check is the reason ARM64 needs the KACCESS variant in Table 10-11 at all: a fixup type that behaves identically at fixup time still has to be distinguishable at audit time. The table has become the definition of where user access is permitted at all. This is the enforcement behind the discipline described earlier: an unannotated instruction that touches user memory is not merely unrecoverable, it is reported as the specific kind of bug it is.

For new code the practical rule is short. Never dereference a __user pointer directly. The annotation exists so that sparse can enforce this at build time with make C=1, and the discipline it enforces is exactly the one this section has been describing: a pointer that came from user space may only be touched through a helper that has an exception-table entry behind it and a check in front of it.

The Virtual Dynamic Shared Object (vDSO)

Some system calls are invoked so frequently that even the optimized SYSCALL/SYSRET or SVC/ERET round-trip becomes a measurable bottleneck. Time reads are the canonical example: a busy application may call clock_gettime() millions of times per second for profiling, event loops, or timestamping. Each call crosses the privilege boundary, saves and restores registers, runs the entry/exit pipeline, and returns — all to read a value that the kernel updates only periodically. The overhead adds up, especially on workloads that are latency-sensitive or throughput-bound.

The virtual dynamic shared object (vDSO) is Linux's answer to this problem. It is a small, kernel-built ELF shared library that the kernel maps into every process's address space at load time. The C library detects the vDSO through an auxiliary vector entry (AT_SYSINFO_EHDR) and, when available, routes certain function calls through the vDSO instead of issuing a system call. The vDSO code executes entirely in user mode — it reads shared data from kernel-maintained memory pages but never crosses the privilege boundary. This means a clock_gettime() call can complete in tens of nanoseconds rather than the hundreds of nanoseconds a full system call requires.

The design is more subtle than a simple shared-memory optimization. The vDSO is an ELF shared object with proper symbol versioning, so the dynamic linker can resolve it like any other library. It supports ASLR — each process gets the vDSO mapped at a randomized address, unlike the old fixed-address vsyscall page it replaced. It is architecture-specific in its exported symbols but shares a generic implementation framework across architectures through lib/vdso/. And it serves purposes beyond time queries: it provides the signal return trampoline, it accelerates random number generation, and on x86_64 it carries the instruction sequence that enters an SGX enclave.

Two properties are worth fixing before the details, because most of the design follows from them. The first is that the vDSO is the only kernel-supplied code that runs entirely unprivileged. It is compiled by the kernel build, shipped inside the kernel image, and mapped by the kernel, but it executes at CPL 3 or EL0 with the calling thread's own permissions, and a bug in it is a bug in the process, not in the kernel. That is what makes it safe to hand out; it is also why everything it reads must be mapped read-only and must be safe to read at any instant. The second is that it is a real ELF shared object, not a magic address. It exports versioned symbols under a version node named LINUX_2.6 on x86 and LINUX_2.6.39 on ARM64, it has a build ID, and it exports each routine twice: once under its architecture prefix (__vdso_clock_gettime) and once under a plain weak alias (clock_gettime). The C library looks up the prefixed name; the plain alias exists so that anything walking the symbol table sees a normal-looking library.

Mapping the vDSO into Every Process

The vDSO must appear in every process's address space before the process executes its first instruction. The kernel accomplishes this during execve() by calling an architecture-specific setup function after the new program's memory layout has been established. On x86_64, arch_setup_additional_pages() in arch/x86/entry/vdso/vma.c calls map_vdso(), which installs three special mappings into the process's address space: the [vdso] text pages containing the executable code, the [vvar] pages containing kernel-maintained shared data, and a [vvar_vclock] region for paravirtualized or Hyper-V clock sources.

The three are carved out of a single reservation, and the order is the opposite of what the names suggest. map_vdso() asks get_unmapped_area() for one region large enough to hold the image plus __VDSO_PAGES data pages, and then places the data at the bottom and computes text_start above it. Keeping the two adjacent and allocating them together is what lets the vDSO reach its data with a fixed PC-relative displacement, which as the next section shows is not a convenience but a requirement.

A near neighbour of map_vdso() is map_vdso_once(), which checks every VMA in the address space and returns -EEXIST if any vDSO mapping is already present before doing the same work. It is not used at execve() time; it backs the ARCH_MAP_VDSO_32, ARCH_MAP_VDSO_X32 and ARCH_MAP_VDSO_64 operations of arch_prctl(), which exist so that a checkpoint/restore tool can put the vDSO back where the checkpointed process expects it. The comment on the duplicate check is explicit that the point is to stop user space from abusing the special-mapping installer, which does not go through the usual accounting and rlimit paths.

On ARM64, the equivalent function is __setup_additional_pages() in arch/arm64/kernel/vdso.c, and it follows the same shape: one reservation, the [vvar] pages at the bottom, the [vdso] code image immediately above them. It adds one flag x86 does not. When system_supports_bti_kernel() is true the text mapping carries VM_ARM64_BTI, which marks the pages as guarded so that an indirect branch into them must land on a BTI instruction. The vDSO is an obvious target for a control-flow hijack precisely because it is executable, present in every process, and full of short useful sequences, so it is guarded like any other library.

The ARM64 path also handles AArch32 compatibility mode, which gets three separate mappings rather than one: the 32-bit vDSO, a [sigpage] holding the AArch32 signal return code, and the legacy kuser helpers that old ARM binaries call at the fixed address 0xffff0000. The kuser page is the last surviving fixed-address code mapping on ARM64 and exists for the same reason x86_64 still emulates vsyscall: binaries compiled against it cannot be recompiled. Both pages are allocated once at arch_initcall time and shared by every 32-bit process, and the signal page is deliberately pre-filled with a trap instruction pattern so that a stray branch into its padding faults rather than executing whatever happened to be there.

Both architectures pre-build the vDSO image at kernel compile time, and the build is unusual enough to be worth describing, because several of the constraints it enforces explain code that appears later in this section. The vDSO sources are compiled with the kernel's flags minus everything that only makes sense for kernel code: -mcmodel=kernel, -mfentry and -pg, the retpoline thunks, LTO, kernel CFI, structure randomization and stack erasure are all filtered out, and -fpic, -fno-stack-protector, -O2 and -fasynchronous-unwind-tables are added back. Frame pointers are kept deliberately — the comment says it is for ease of user-space debugging — and the link is done with -shared -Bsymbolic --build-id=sha1 -z noexecstack. ARM64 adds -z force-bti under CONFIG_ARM64_BTI_KERNEL and reserves x18 with -ffixed-x18 so that vDSO code cannot clobber a shadow call stack pointer the caller may be using.

Two flag decisions record a policy rather than a technical need. On x86 the build first resets the compiler's default control-flow protection with -fcf-protection=none and then re-enables only the return half under X86_USER_SHADOW_STACK; the branch half sits in the Makefile as a commented-out line waiting for user-space IBT support. This is the same pattern as the commented-out LAM widening in Section 4.2: a hardening feature written, understood, and deliberately held back until the rest of the platform catches up.

The strongest constraint is checked after linking rather than expressed as a flag. cmd_vdso_check in lib/vdso/Makefile.include runs readelf -rW over the finished library and fails the build if a single dynamic relocation survives. Nothing resolves symbols in the vDSO at runtime — there is no dynamic linker involved, the kernel simply maps the bytes — so a relocation that nobody will ever apply would be a silent wrong answer rather than a link error. Everything the vDSO touches must therefore be reachable by PC-relative addressing, which is the reason for both the adjacent data mapping described above and the hidden-visibility declarations in the next section.

The finished library takes different routes into the kernel image on the two architectures. x86 runs it through vdso2c (arch/x86/tools/vdso2c.c), a host tool that emits a C file containing the stripped image as a byte array together with a struct vdso_image recording the offsets of the symbols and sections the kernel needs at runtime. ARM64 links the .so into the kernel directly and generates a header of symbol offsets with gen_vdso_offsets.sh. Both strip the debug copy, and x86 additionally strips the __ex_table section from the mapped image, because the vDSO's exception table is consumed by the kernel from the vdso_image rather than being looked up in the mapped pages.

At boot, init_vdso_image() does something that is easy to miss and is the reason the image cannot simply be a constant blob: it calls apply_alternatives() over the image's .altinstructions section. The vDSO is patched at boot exactly like kernel text, so the instruction a process eventually executes depends on the CPU it booted on. That is how __vdso_getcpu() chooses between LSL and RDPID, and how the timekeeping code selects a hardware counter read appropriate to the clocksource. Because the patching happens once, to the single copy of the image, every process shares the result: vdso_fault() hands out pages of that one image with virt_to_page(), so the text is shared physical memory no matter how many processes map it.

The resulting VMAs are tagged as special mappings, which means the kernel owns the backing pages, supplies them from a fault handler of its own, and gives the VMA a name that /proc/pid/maps reports in brackets. The flag set on the text mapping repays a careful look. VM_READ|VM_EXEC is expected; VM_MAYWRITE is not, since nothing should ever write to the vDSO. The source comment gives the reason: MAYWRITE to allow gdb to COW and set breakpoints. Without it, a debugger could not place a breakpoint in __vdso_clock_gettime(), because mprotect() refuses to add a permission the VMA never claimed it might have. With it, a write triggers a private copy-on-write fault, the process gets its own modified copy of the page, and every other process on the system continues to run the pristine shared one. The permission is a debuggability concession, granted safely because the copy-on-write semantics contain the damage to the process that asked for it.

The data mapping is installed by vdso_install_vvar_mapping() in lib/vdso/datastore.c with a very different set: 


/* lib/vdso/datastore.c */
vma = _install_special_mapping(mm, addr, VDSO_NR_PAGES * PAGE_SIZE,
                               VM_READ|VM_MAYREAD|VM_IO|VM_DONTDUMP|
                               VM_PFNMAP|VM_SEALED_SYSMAP,
                               &vvar_mapping);

VM_MAYWRITE is absent, so no sequence of mprotect() calls can ever make the timekeeping data writable — the concession made for the text is explicitly not made for the data. VM_IO and VM_PFNMAP mark it as a raw frame mapping with no page reference counting, and VM_DONTDUMP keeps it out of core files, where it would be noise at best. VM_SEALED_SYSMAP is newer and is worth naming explicitly: defined in include/linux/mm.h as VM_SEALED when CONFIG_MSEAL_SYSTEM_MAPPINGS is enabled and as VM_NONE otherwise, it applies the mseal() memory-sealing mechanism to kernel-installed mappings. A sealed VMA cannot be unmapped, moved, or have its permissions changed at all, which closes a class of attack in which a process with an arbitrary-mmap primitive replaces a system mapping with content of its own choosing.

Sealing does not extend to the text mapping, because some legitimate users move it. If the process calls mremap() on the vDSO, vdso_mremap() updates mm->context.vdso and then calls vdso_fix_landing(), which examines the saved user instruction pointer and, if it points inside the region being moved, rewrites it by the same displacement. The scenario this exists for is checkpoint/restore: the restoring process relocates the vDSO to the address the checkpointed image expects while a thread is suspended inside vDSO code. Without the fixup that thread would resume at an address that no longer contains the instruction it was executing.

The vvar Shared Data Pages

The vDSO code cannot make system calls to get the information it needs — that would defeat the purpose. Instead, it reads from vvar pages: kernel-allocated memory that is mapped read-only into user space and updated by the kernel whenever the underlying data changes. The region is not an unstructured blob. enum vdso_pages in include/vdso/datapage.h assigns each kind of data a fixed page offset — VDSO_TIME_PAGE_OFFSET, VDSO_TIMENS_PAGE_OFFSET, VDSO_RNG_PAGE_OFFSET, then a range from VDSO_ARCH_PAGES_START to VDSO_ARCH_PAGES_END for architecture-private data, with VDSO_NR_PAGES as the total. Each store is declared as a union of its structure with a u8 page[PAGE_SIZE] array and checked with static_assert(), so a structure that outgrows its page breaks the build rather than silently colliding with the next one. Because the offsets are compile-time constants shared by both sides, the vDSO reaches any of them with a fixed displacement from its own text and never needs a pointer supplied at runtime.

Reaching them that way requires one more piece of cooperation from the compiler. The data symbols are declared with __attribute__((visibility("hidden"))), and the comment in include/vdso/datapage.h explains that hidden visibility is not an optimization here but a correctness requirement: a default-visibility reference would be routed through a GOT entry, and a GOT entry cannot work, because nothing at runtime can fill in an absolute address for the data page. This is the same constraint the build-time relocation check enforces from the other direction.

The two sides use different names for the same memory. The kernel writes through vdso_k_time_data, vdso_k_rng_data and friends, which are ordinary kernel addresses; the vDSO reads through vdso_u_time_data and vdso_u_rng_data, which are the hidden, PC-relative user-side aliases. The naming makes the direction of every access obvious at a glance, which matters in a file that is compiled into both the kernel and an unprivileged shared library.

The key data structure is struct vdso_time_data, defined in include/vdso/datapage.h. It contains everything the vDSO time functions need: the clocksource mode, base timestamps for each clock type, the multiplier and shift values for converting raw cycle counts to nanoseconds, and timezone information.

    u32                 hrtimer_res;
    u32                 __unused;
} ____cacheline_aligned;

Three details in that layout carry real weight. First, clock_data has only two entries — CS_HRES_COARSE and CS_RAW — while the auxiliary POSIX clocks live in a separate aux_clock_data array; the two are indexed by different arithmetic and must not be conflated. Second, max_cycles exists only under CONFIG_GENERIC_VDSO_OVERFLOW_PROTECT and is used by vdso_calc_ns() to decide whether the cheap (delta * mult + base) >> shift can be used or whether the wide-multiply fallback mul_u64_u32_add_u64_shr() is needed; a clocksource that has not been read for a long time can otherwise overflow the 64-bit product and produce time that jumps backwards. Third, and most consequential, basetime is a union with an array of struct timens_offset. The same bytes are either absolute base timestamps or per-clock namespace offsets, depending on which page the reader is looking at, and that union is the whole of the time-namespace mechanism.

The whole structure is ____cacheline_aligned and the frequently read fields — sequence counter, clock mode, cycle base, multiplier and shift — sit together at the front, so that the common case touches one or two cache lines. Consistency comes from a sequence lock: the vDSO reads seq, copies the fields it needs, reads seq again, and retries if the value changed or was odd, indicating that the kernel was mid-update. This is the classic seqlock pattern with one important adaptation for the cross-privilege case. The reader is unprivileged and untrusted, so it cannot be allowed to block the writer or to hold anything; a seqlock is the only synchronization primitive that gives a consistent snapshot while granting the reader no power at all over the writer. A malicious reader can spin forever, but only in its own time slice.

The time-namespace machinery is built on top of that same read loop rather than beside it. For a task in a non-initial time namespace the kernel installs a substitute page at VDSO_TIME_PAGE_OFFSET whose seq is 1 and whose clock_mode is VDSO_CLOCKMODE_TIMENS, and puts the real host data one page further along at VDSO_TIMENS_PAGE_OFFSET. Nothing is recomputed and no offsets are folded in; the two pages are simply swapped. do_hres() open-codes the sequence-lock read instead of calling vdso_read_begin() so that the odd-seq retry test can also test for the time-namespace mode in the same branch. A task in the initial namespace sees an even seq and a normal clock mode and pays nothing; a task in a time namespace takes the branch into do_hres_timens(), which finds the real data with __arch_get_vdso_u_timens_data() — literally the current page plus PAGE_SIZE — reads it under its own seqlock, and adds the offset[] entry from the union above. The permanently odd seq on the substitute page is what makes the diversion free: it reuses a test the fast path had to perform anyway.

Because the layout depends on the namespace, moving between namespaces has to invalidate what is mapped. vdso_join_timens() walks the address space and zaps the pages of the vvar VMA, so the next access re-faults and vvar_fault() installs whichever arrangement now applies.

For random number generation, a separate struct vdso_rng_data holds a generation counter and an is_ready flag. The kernel increments the generation whenever it reseeds the RNG, and the vDSO getrandom code uses this to decide whether its cached state is still valid.

All of this is arranged by vvar_fault() in lib/vdso/datastore.c, which switches on vmf->pgoff over exactly the enumeration given at the start of this section and returns VM_FAULT_SIGBUS for anything it does not recognize. One contiguous virtual region is therefore backed by pages drawn from entirely different places, chosen per process.

The architecture-private range is where x86's third mapping comes from. [vvar_vclock] holds the paravirtualized clock page under CONFIG_PARAVIRT_CLOCK and the Hyper-V TSC page under CONFIG_HYPERV_TIMER, and it exists so that a guest can read a host-maintained clock without a hypercall. The paravirtualized page is inserted with pgprot_decrypted(), because under SEV the guest's memory is encrypted with a key the host does not have, and a page the host must write has to be mapped unencrypted. On a bare-metal kernel with neither option the region is empty and any access raises SIGBUS.

vDSO-Accelerated Functions

The generic vDSO time implementation lives in lib/vdso/gettimeofday.c and provides the shared logic that all architectures use. Functions like do_hres() (high-resolution clock), do_coarse() (coarse-grained clock), and do_aux() (auxiliary clock) implement the actual time computation by reading the vvar data, applying the multiplier/shift arithmetic, and combining the result with the base timestamp. Each architecture wraps these generic functions with thin entry points that have architecture-specific symbol names.

The wrapping is textual rather than link-time. x86's vclock_gettime.c literally contains #include "lib/vdso/gettimeofday.c", and ARM64 achieves the same effect with -include in its Makefile. Pulling the generic implementation into the same translation unit as the entry points lets the compiler inline everything and, more importantly, guarantees that no cross-object reference survives to become a relocation the build check would reject.

Dispatching on the clock ID is done with a bitmask rather than a switch, which is worth seeing because it is the hottest branch in the whole path: 


/* lib/vdso/gettimeofday.c — __cvdso_clock_gettime_common() */
    u32 msk;

    /* Check for negative values or invalid clocks */
    if (unlikely(!vdso_clockid_valid(clock)))
        return -1;

    /*
     * Convert the clockid to a bitmask and use it to check which
     * clocks are handled in the VDSO directly.
     */
    msk = 1U << clock;
    if (likely(msk & VDSO_HRES))
        vc = &vc[CS_HRES_COARSE];
    else if (msk & VDSO_COARSE)
        return do_coarse(vd, &vc[CS_HRES_COARSE], clock, ts);
    else if (msk & VDSO_RAW)
        vc = &vc[CS_RAW];
    else if (msk & VDSO_AUX)
        return do_aux(vd, clock, ts);
    else
        return -1;

    return do_hres(vd, vc, clock, ts);

vdso_clockid_valid() is a single unsigned comparison against CLOCK_AUX_LAST, which rejects negative clock IDs — the dynamic POSIX clock IDs used for per-process and per-thread CPU clocks — with the same instruction that rejects out-of-range ones. The four masks group the clocks by which arithmetic answers them: VDSO_HRES covers CLOCK_REALTIME, CLOCK_MONOTONIC, CLOCK_BOOTTIME and CLOCK_TAI; VDSO_COARSE covers the two _COARSE variants, which need no hardware read at all because they simply return the last tick's timestamp; VDSO_RAW is CLOCK_MONOTONIC_RAW, which uses the unadjusted CS_RAW data; and VDSO_AUX is a __GENMASK() over the auxiliary clock range.

Auxiliary clocks are the newest addition and are easy to overlook. Enabled by CONFIG_POSIX_AUX_CLOCKS, they occupy the clock IDs from CLOCK_AUX to CLOCK_AUX_LAST and expose additional hardware time bases — a PTP-disciplined clock, for instance — through the ordinary POSIX clock interface. do_aux() indexes vd->aux_clock_data[clock - CLOCK_AUX] rather than clock_data, and unlike the other paths it can legitimately fail even on a healthy system: an auxiliary clock that has not been enabled has clock_mode == VDSO_CLOCKMODE_NONE, and the request falls through to the system call.

Each name appears twice in the version script, once prefixed and once bare, producing the weak aliases described earlier.

The differences between the two lists are informative. ARM64 has no vDSO getcpu, because it has no cheap unprivileged way to obtain the current CPU number; a 32-bit vDSO on x86 has extra _time64 entry points because its native timespec is too narrow to survive 2038. The SGX entry point is the odd one out in a different way: it is not an accelerated system call at all but a hand-written assembly sequence that executes ENCLU[EENTER], and it lives in the vDSO because the kernel needs to control the exact instruction sequence around enclave entry and exit.

__vdso_getcpu() is worth a moment because it reads no memory whatsoever. vdso_read_cpunode() in arch/x86/include/asm/segment.h uses alternative_io() to select between an LSL against a dedicated GDT selector and a plain RDPID, patched at boot by the apply_alternatives() pass described earlier. The kernel encodes the CPU number and NUMA node into the limit field of that GDT descriptor in setup_getcpu(), and into MSR_TSC_AUX for RDPID; the vDSO then obtains both numbers by loading a segment limit into a register. No cache line is touched, and there is nothing for an attacker to write.

The SGX entry point also explains the third exception table introduced in Section 4.4. A fault taken inside an enclave surfaces on the ENCLU instruction, and the kernel must hand control back to the vDSO's own recovery code rather than kill the process. fixup_vdso_exception() in arch/x86/entry/vdso/extable.c performs a linear search of the table carried in the vdso_image, and on a match redirects regs->ip into the vDSO while passing the trap number, error code, and fault address in rdi, rsi and rdx. It refuses to act on #DB and #BP, with the comment that it is impossible to tell whether a debug or breakpoint exception originated inside an enclave — a case where the kernel declines to guess rather than risk swallowing a debugger's trap.

The crucial property is that the fast path stays entirely in user mode. The vDSO text reads timekeeping data from the shared vvar pages, performs carefully bounded arithmetic to compute the current time, and returns without changing privilege level. If the fast path cannot answer a request — for example, if the clocksource mode is set to VDSO_CLOCKMODE_NONE because the kernel's clocksource does not support user-space reading — the code falls back to the ordinary system call. That fallback is one reason the vDSO is best understood as an optimization layer on top of the syscall ABI rather than a replacement for it.

The getrandom vDSO Extension

Linux 7.0.12 extends the vDSO beyond time queries with a getrandom() acceleration path. Unlike time functions, which are stateless reads from shared data, random number generation is inherently stateful: the vDSO must maintain a per-thread cryptographic DRBG (deterministic random bit generator) based on ChaCha20, reseed it when the kernel's entropy pool changes, and handle edge cases like fork() (which requires re-keying to avoid parent-child state sharing) and signal-handler reentrancy.

The implementation in lib/vdso/getrandom.c works through an opaque state buffer that user space allocates and passes on every call. There is no dedicated allocation system call for it; the vDSO function itself doubles as the query interface. Calling __vdso_getrandom(NULL, 0, 0, &params, ~0UL) — the sentinel opaque length ~0UL is what marks the call as a query — fills in a struct vgetrandom_opaque_params with the size of the state and, crucially, the exact mmap() protection and flag values the caller must use. The C library then performs an ordinary mmap() with those values and carves per-thread states out of the result. Handing back the mapping parameters rather than fixing them in a header means the kernel can change them without breaking a library compiled against an older kernel.

The values the kernel returns are PROT_READ|PROT_WRITE and MAP_DROPPABLE|MAP_ANONYMOUS, and MAP_DROPPABLE is the load-bearing part of the whole design. In mm/mmap.c it implies VM_DROPPABLE | VM_NORESERVE | VM_WIPEONFORK | VM_DONTDUMP, and each of those four flags answers a problem the RNG code would otherwise have to solve itself:

  • VM_WIPEONFORK is the fork story. A child inherits the mapping as zeroes rather than as a copy of the parent's state, and since the kernel guarantees that the generation counter is never zero, the child's zeroed generation can never match and its very first call is forced through the reseeding path. Parent and child therefore cannot emit the same byte stream, and the RNG code contains no fork handler at all — the memory management subsystem provides the guarantee.
  • VM_DROPPABLE pages are never swapped (see mm/rmap.c), so ChaCha20 key material cannot reach persistent storage.
  • The same flag allows the kernel to reclaim the pages under memory pressure by simply zeroing them, which is safe for exactly the same reason the fork case is safe: a zeroed state is a state that will be reseeded.
  • VM_DONTDUMP keeps the key material out of core files.

The generation counter is the synchronization mechanism between the two sides. drivers/char/random.c publishes it with smp_store_release() after a reseed, and the vDSO reads it and issues an smp_rmb() before using the state, so a reader that observes a new generation is guaranteed to observe the reseeded data behind it. The kernel deliberately stores one more than its internal counter, because the two sides use different sentinels: the kernel's invalid value is ULONG_MAX and the vDSO's is zero, and the offset makes the two ranges line up.

The ordering inside the vDSO is subtler still. When a reseed is required, WRITE_ONCE(state->generation, next_gen) happens before the fallback system call that fetches the new key, not after. The comment explains the alternative: if the state were marked fresh only after the syscall returned, a fork() in the intervening window would hand the child a state that already contained the new key but still carried the old generation, and both processes would then agree that no reseed was needed and produce identical output.

Two further checks guard the fast path, and neither is a lock. The state must not straddle a page boundary — the code returns -EFAULT if it does, because the pages can be zeroed independently at any moment and half a state is worse than none. And state->in_use is a plain flag, not an atomic, whose purpose is signal-handler reentrancy rather than mutual exclusion: the comment reasons that a signal handler runs to completion before the interrupted code resumes, so the read-then-write race is benign within a thread. The consequence is a rule the API cannot express in its signature — one state may safely be shared between a thread's main flow and its signal handlers, but never between two threads.

The batch refill uses memcpy_and_zero_src(), which zeroes each block of the batch as it copies it out. The comment notes that zeroing at the same time as copying helps preserve forward secrecy: bytes already handed to the caller cannot be recovered from the state afterwards, so an attacker who later reads the state learns nothing about the output that preceded the compromise. This is the standard fast key erasure construction, and it is the reason the batch is consumed strictly front to back.

Everything that does not fit falls back to the real system call, and the list of triggers is short: any flag outside GRND_NONBLOCK|GRND_RANDOM|GRND_INSECURE, an opaque length that does not match the kernel's current structure size (which the comment attributes to checkpoint/restore across kernel versions), an RNG that is not yet ready during early boot, and a state already marked in_use. The result is that the common case — a short read with the RNG seeded and the state fresh — completes entirely in user space, while every awkward case is handled by code that was going to exist anyway.

The Signal Return Trampoline

The vDSO serves another purpose that has nothing to do with performance optimization: it provides the signal return trampoline. When the kernel delivers a signal to a user-space process, it pushes a signal frame onto the user stack and arranges for the signal handler to return to a special code sequence that invokes rt_sigreturn (or sigreturn on older 32-bit paths). This code sequence must live at a known, executable address in the process's address space, and the vDSO is the natural place for it.

On x86 32-bit, arch/x86/entry/vdso/vdso32/sigreturn.S defines __kernel_sigreturn and __kernel_rt_sigreturn. Both are three or four instructions long, and both carry a warning comment that fixes their exact byte encodings — 58 b8 77 00 00 00 cd 80 for the non-realtime variant — with the instruction not to change them in any way. The reason is a defect in the libgcc unwinder that persists as of gcc 15.2: it fails to recognize the DWARF signal-frame flag and falls back to a legacy path that pattern-matches on those exact bytes. The same comment requires that at least one byte before each entry point fall outside any function, a condition the file satisfies with an explicit nop placed before the alignment directive. Note also that the CFI annotations are conditional: .cfi_offset eflags is emitted only for GNU as or LLVM 16.0.1 and newer, because older assemblers reject it.

ARM64's arch/arm64/kernel/vdso/sigreturn.S reaches the same destination by a different and even more explicit route. The functional body is two instructions, mov x8, #__NR_rt_sigreturn followed by svc #0, bracketed by comments reading PLEASE DO NOT MODIFY. Around that body the file describes itself as a hall of shame for poor unwinders and documents three concessions.

  • A mysterious NOP precedes the entry point, because some unwinders — the comment names libc++ — unconditionally subtract one from the value returned by _Unwind_GetIP() before looking up the enclosing function, and without the padding instruction that adjusted address falls outside the trampoline entirely. The workaround was borrowed from powerpc, which had hit the same problem.
  • Every .cfi directive in the file is commented out. Emitting correct unwind information turns out to make things worse: it triggers segmentation faults in libgcc when unwinding out of a SIGCANCEL handler. Omitting it forces the unwinder onto an ARM64-specific fallback that recognizes the signal frame by other means and works.
  • The trampoline is defined with SYM_CODE_START rather than SYM_FUNC_START, specifically so that no BTI landing pad is emitted. Recall that the ARM64 vDSO text is mapped with VM_ARM64_BTI, so an indirect branch into a location without a landing pad faults — which is exactly the desired outcome here. The trampoline is only ever reached by the RET at the end of a signal handler, never by an indirect branch, so omitting the pad costs nothing and removes a legitimate branch target from the process's address space.

The pattern across both files is the same, and it is a good illustration of what an ABI commitment actually costs. Three or four instructions of functionality are surrounded by a page of comments, conditional assembly, and deliberate omissions, all of it dictated not by what the kernel needs but by what user-space unwinders happen to do.

Before the vDSO existed, the kernel would write the sigreturn trampoline directly onto the user stack. This worked but conflicted with non-executable stack protections (NX bit, W^X policies). By placing the trampoline in the vDSO — which is mapped executable — the kernel can enforce a fully non-executable stack without breaking signal delivery.

Legacy vsyscall Emulation

The vDSO replaced an older mechanism called vsyscall, which existed only on x86_64. The vsyscall page was mapped at a fixed virtual address (0xffffffffff600000) in every process and contained three entry points: gettimeofday, time, and getcpu. Applications — and, more importantly, the C library — would call these fixed addresses directly.

The fixed-address design was a serious problem for security. Because every process had executable kernel code at the same virtual address, it became a target for return-oriented programming (ROP) attacks: an attacker who could control the instruction pointer could jump to the vsyscall page as a known gadget. ASLR could not help because the address was fixed by ABI.

Linux solved this incrementally. First, the real code at the fixed address was replaced by emulation: the page is mapped without read permission, the faults it generates are recognized in the page fault path, and emulate_vsyscall() in arch/x86/entry/vsyscall/vsyscall_64.c performs the requested operation. The actual emulation page in arch/x86/entry/vsyscall/vsyscall_emu_64.S is three stubs — each loading a syscall number and executing syscall — padded with int3 trap instructions so that a jump into the gaps is caught rather than executed as whatever the padding happens to encode.

The emulator is unusually defensive, and its checks are worth listing because each one closes a way of turning a compatibility feature into an exploitation primitive. It refuses to act on write faults or on faults taken in kernel mode. It requires the faulting address to equal regs->ip, since anything else means the process was reading the page rather than executing it, and where the CPU supports NX it additionally WARNs if the hardware did not confirm an instruction fetch. It checks that the address is one of the three exact entry points and reports a misaligned one as a probable exploit attempt. It reads the return address from the user stack with get_user() and fails cleanly if the stack is bad. It validates every pointer argument with write_ok_or_segv() before the call rather than relying on the underlying syscall to do it, because a real vsyscall delivered SIGSEGV for a bad pointer and the emulation must reproduce that. Every one of these refusals goes through warn_bad_vsyscall(), whose rate-limited messages name the vsyscall= boot parameter explicitly, so that an administrator who has hardened a system and broken an old binary can find out why.

Seccomp is handled with particular care. The emulator sets regs->orig_ax to the syscall number and regs->ax to -ENOSYS before calling secure_computing(), so that a filter sees exactly what it would see for the equivalent real system call, and then verifies afterwards that the filter changed neither the syscall number nor the instruction pointer. A filter that tried to do so is killed with SIGSYS. Without that check, a seccomp filter permitted to rewrite the syscall number could redirect a vsyscall to an arbitrary system call from an address that no filter author expected to be a syscall site.

Linux 7.0.12 still contains this code, but the balance among the three modes has shifted, and the shift is not visible from the vsyscall= parameter alone. Only two of them remain build-time choices: CONFIG_LEGACY_VSYSCALL_XONLY, which is the default, and CONFIG_LEGACY_VSYSCALL_NONE. The full EMULATE mode has no Kconfig option at all — the initializer of vsyscall_mode ends in #error VSYSCALL config is broken if neither of the two survives — and can now be reached only by passing vsyscall=emulate on the kernel command line. The xonly mode maps the page execute-only, so an attacker cannot even read the three stubs to locate gadget bytes; none omits the mapping entirely, and get_gate_vma() then returns NULL.

One implementation detail explains something visible in /proc. The vsyscall page is not an ordinary VMA belonging to an address space; it is a single static gate_vma, shared by every process, whose vm_ops->name returns the string [vsyscall]. That is why the region appears in every process's map at an address above the user/kernel split, and why enabling or disabling it is a global boot-time decision rather than something an individual mapping can opt out of.

New applications should never use vsyscall. The vDSO provides the same functionality with ASLR support, broader architecture coverage, and a richer set of accelerated functions. The vsyscall emulation exists solely to keep decades-old statically linked binaries running — a reminder that ABI commitments in the Linux kernel are effectively permanent.

System Call Filtering with seccomp-BPF

The system call interface is the primary attack surface that user-space programs present to the kernel. A typical application uses only a small fraction of the hundreds of available system calls, yet every system call it could invoke represents a code path that a compromised process might exploit. Kernel vulnerabilities are frequently found in obscure system calls — calls that the target application would never use in normal operation. If the kernel could simply refuse to execute those calls for a particular process, the exploitable surface would shrink dramatically.

This is exactly what seccomp (secure computing) provides. It allows a process — or a supervisor acting on its behalf — to declare a policy that restricts which system calls the process may invoke and, in filter mode, what argument values are acceptable. Once installed, a seccomp policy cannot be loosened; it can only be further tightened. This one-way ratchet, combined with inheritance across fork() and preservation across exec(), makes seccomp the foundation for sandboxing in browsers, container runtimes, Android, and systemd service hardening.

Seccomp did not exist in Linux 2.6.11. Strict mode appeared in 2.6.12, and the vastly more useful BPF-based filter mode arrived in 3.5. By Linux 7.0.12, seccomp has grown into a sophisticated subsystem with user-space notification, file descriptor injection, a per-filter action cache, and integration with the generic entry pipeline. All of its implementation lives in kernel/seccomp.c, with UAPI definitions in include/uapi/linux/seccomp.h.

One constraint shapes everything in that file and is worth stating before the details. Seccomp runs on the system call entry path, before the call is dispatched, on every call the task makes. A sandboxed process pays for its filter on every read() and every write(), not only on the calls the filter is interested in. That is why the subsystem contains a bytecode interpreter, a bitmap cache in front of it, a static validator that removes the need for runtime bounds checks, and a great deal of care about which locks the fast path takes — none of which would be necessary if the check happened somewhere colder.

Strict Mode and Filter Mode

Linux supports two seccomp modes, reflecting two generations of the feature's evolution.

SECCOMP_MODE_STRICT is the original, hard-coded mode introduced in Linux 2.6.12. It permits exactly four system calls — read, write, exit, and sigreturn — and kills the thread instantly if any other call is attempted. There is no configurability: the allowed set is compiled into the kernel in the mode1_syscalls[] array. Note that it is read and write, not open: a strict-mode task can only use file descriptors it already possessed when the mode was set, which is the whole point. This mode was designed for compute-only workloads like distributed processing tasks that needed to execute untrusted code on worker nodes. 


/* kernel/seccomp.c — strict mode allowed list */
static const int mode1_syscalls[] = {
    __NR_seccomp_read, __NR_seccomp_write,
    __NR_seccomp_exit, __NR_seccomp_sigreturn,
    -1, /* sentinel */
};

static void __secure_computing_strict(int this_syscall)
{
    const int *allowed_syscalls = mode1_syscalls;
    ...
    /* If the syscall is not in the list: */
    current->seccomp.mode = SECCOMP_MODE_DEAD;
    seccomp_log(this_syscall, SIGKILL, SECCOMP_RET_KILL_THREAD, true);
    do_exit(SIGKILL);
}

SECCOMP_MODE_DEAD in that excerpt is not a mode user space can ask for. It is defined privately in kernel/seccomp.c as SECCOMP_MODE_FILTER + 1 and is written into the task immediately before it is killed, so that if the task somehow reaches another system call entry the dispatcher in __secure_computing() finds a mode it does not recognize, issues a WARN_ON_ONCE(), and calls do_exit(SIGKILL) outright. The comment above that case reads Surviving SECCOMP_RET_KILL_* must be proactively impossible. It is a backstop for a bug that should not exist, placed on the hottest path in the kernel because the consequence of the bug would be a process that survived a kill verdict.

SECCOMP_MODE_FILTER, added in Linux 3.5, is the mode that made seccomp practical for real applications. Instead of a fixed allowed list, user space supplies a BPF program that the kernel evaluates on every system call entry. The program examines the syscall number, architecture, and argument values, and returns an action code that tells the kernel how to proceed — allow, deny with an error, send a signal, notify a supervisor, or kill the process. This is the mode that Chrome, Docker, systemd, and Android all use.

A process enters seccomp mode through one of two interfaces: prctl(PR_SET_SECCOMP, mode, ...) or the dedicated seccomp(SECCOMP_SET_MODE_FILTER, flags, prog) system call. The seccomp() system call, added in 3.17, is preferred because it supports flags that prctl() cannot express, such as SECCOMP_FILTER_FLAG_TSYNC (synchronize the filter across all threads) and SECCOMP_FILTER_FLAG_NEW_LISTENER (return a notification file descriptor). Both paths ultimately call seccomp_set_mode_filter() in kernel/seccomp.c. The seccomp() call also carries two purely informational operations that have nothing to do with entering a mode: SECCOMP_GET_ACTION_AVAIL reports whether the running kernel understands a particular return action, and SECCOMP_GET_NOTIF_SIZES reports the sizes of the three notification structures. Both exist so that a sandbox can discover what the kernel supports instead of guessing from the kernel version, and the second is what makes the notification structures extensible.

SECCOMP_FILTER_FLAG_LOG Log every action this filter produces except SECCOMP_RET_ALLOW, subject to the global actions_logged setting.
SECCOMP_FILTER_FLAG_SPEC_ALLOW Opt out of the speculative-execution mitigation that installing a filter otherwise turns on. The default is the safe one; the flag exists for callers that have measured the cost and accepted the risk.

SECCOMP_FILTER_FLAG_WAIT_KILLABLE_RECV Once the supervisor has received a notification, put the notifying thread into killable rather than interruptible sleep. Only valid together with NEW_LISTENER.

The third entry is the one most likely to surprise. seccomp_assign_mode() calls arch_seccomp_spec_mitigate() unless SECCOMP_FILTER_FLAG_SPEC_ALLOW was passed, with the comment Assume default seccomp processes want spec flaw mitigation. Installing a seccomp filter therefore has a side effect that has nothing to do with system calls: on x86_64 it enables Speculative Store Bypass Disable for the task, and it does so permanently, because seccomp state can only tighten. The reasoning is that a process is almost always sandboxed because it is about to run something untrusted, and a process running untrusted code is exactly the one that should not be speculating across a store. The cost is real, which is why the opt-out exists, but the default is chosen for the caller who did not think about it.

Installing and Chaining Filters

Installing a seccomp filter is a privileged operation with deliberate restrictions. The caller must either have set the no_new_privs flag (via prctl(PR_SET_NO_NEW_PRIVS, 1)) or hold CAP_SYS_ADMIN in the current user namespace. The no_new_privs requirement exists to prevent an unprivileged process from installing a filter and then exec()ing a setuid binary — the filter would run in the context of the elevated privilege, potentially allowing the unprivileged user to influence privileged operations. With no_new_privs set, the kernel guarantees that exec() will never grant additional privileges, making the filter safe. The check is made in seccomp_prepare_filter() and fails with -EACCES; note that it uses ns_capable_noaudit(), so an unprivileged process that legitimately relies on the no_new_privs route does not generate a stream of capability denials in the audit log.

The installation path in seccomp_prepare_filter() copies the user-space struct sock_fprog (which contains a pointer to an array of BPF instructions and a count), validates every instruction against a seccomp-specific whitelist of allowed BPF operations, and builds an internal struct seccomp_filter. Each filter holds a reference-counted pointer (prev) to the previously installed filter. New filters are always prepended — seccomp_attach_filter() sets filter->prev = current->seccomp.filter and makes the new filter the head.

From any one task the result looks like a singly linked list, but the global structure is not a list. Because fork() gives the child a reference to the same head, and because either process can then install a further filter of its own, several filters can share a single prev. The comment on struct seccomp_filter describes the true shape as a unidirectional tree, and notes the analogy with namespaces: every task walks its own path from a leaf towards the root, and paths merge as they ascend. This matters for two reasons. It is why filters are strictly immutable once attached — a modification would be visible to unrelated processes sharing the node — and it is why the instruction budget described below is enforced per path rather than per process.

The lifetime of a node in that tree is governed by two reference counts rather than one, and the reason is subtle enough that the header documents it at length. refs is the ordinary count that keeps the object allocated; users counts only the tasks that could still run the filter. When users falls to zero the filter can never fire again even though it is still allocated, because a listener file descriptor is still holding a reference to it — and at that moment __seccomp_filter_orphan() wakes the listener's wait queue with EPOLLHUP. A supervisor blocked in poll() on its notification descriptor therefore learns that every process it was supervising has exited, instead of waiting forever for a notification that can no longer arrive. The second refcount exists entirely to make that one event expressible.

This chain model has an important consequence: filters can only accumulate, never be removed. A process (or its children) can install additional filters, each of which further narrows the allowed set. When the kernel evaluates the chain, it runs every filter in order and takes the least permissive result. Actions are compared numerically, and the comparison contains a trick worth pausing on. The constants are not assigned in order: SECCOMP_RET_KILL_THREAD is 0x00000000 and SECCOMP_RET_KILL_PROCESS is 0x80000000, so as unsigned values the strongest action is the largest. The macro ACTION_ONLY() casts to s32 before comparing, which makes 0x80000000 the most negative value and restores the intended ordering: KILL_PROCESS < KILL_THREAD < TRAP < ERRNO < USER_NOTIF < TRACE < LOG < ALLOW. The signed cast is doing real work; without it a filter chain would fail open in exactly the case where it matters most.

One further consequence follows from the comparison being strict. seccomp_run_filters() starts at the most recently installed filter and only replaces the running verdict when a later filter is strictly more restrictive, so when two filters return the same action the earliest one examined — that is, the most recently installed — provides the matching filter. For most actions this is invisible, but for SECCOMP_RET_USER_NOTIF it decides which supervisor is asked, and the UAPI header spells the consequence out: a newly added notifying filter takes precedence over an older one and can answer with SECCOMP_USER_NOTIF_FLAG_CONTINUE, overriding what the older filter's supervisor would have decided. The one-way ratchet applies to the set of actions a chain can produce, not to which supervisor gets to speak.

The instruction budget is enforced at attach time. MAX_INSNS_PER_PATH is defined as (1 << 18) / sizeof(struct sock_filter) — 256 KB worth of classic BPF, or 32,768 instructions — and seccomp_attach_filter() walks the prev chain summing the lengths, charging each filter its instruction count plus four as a per-filter overhead so that a chain of trivial filters is also bounded. Exceeding the budget fails with -ENOMEM.

Filters are inherited across fork() — the child gets a reference-counted copy of the parent's filter chain via copy_seccomp() in kernel/fork.c. They are also preserved across exec(): the kernel does not clear the seccomp state during program replacement. This means a container runtime can install a filter before execing the container's init process, and the filter will persist throughout the container's lifetime and all its descendant processes.

fork() propagates a filter automatically; propagating one to the threads that already exist is the job of SECCOMP_FILTER_FLAG_TSYNC, and it is more delicate than it sounds. seccomp_can_sync_threads() first walks the thread group and checks that every other thread is either unfiltered or already running a filter that is an ancestor of the caller's, since forcing a filter onto a thread that had installed a different one would be a way to relax that thread's policy. If a thread fails the test its PID is returned, which is useful for diagnosis but collides with the file descriptor returned by NEW_LISTENER: both are non-negative values with entirely different meanings. The kernel refuses to guess, and rejects the combination of TSYNC and NEW_LISTENER with -EINVAL unless TSYNC_ESRCH is also set to make TSYNC report failure as a plain error instead. The whole sequence runs under cred_guard_mutex so that no thread can be midway through execve() while the group's seccomp and no_new_privs state is being changed.

A related check guards notification listeners. has_duplicate_listener() refuses with -EBUSY any attempt to install a second notifying filter into a chain that already contains one. Two listeners in the same chain would mean that a supervisor could end up blocked behind another supervisor's unanswered notification, with no way for either to make progress.

The seccomp_data Structure and Classic BPF

The BPF program that a seccomp filter executes does not have access to the full kernel state — it operates on a fixed, architecture-neutral snapshot called struct seccomp_data. This structure is populated by populate_seccomp_data() at syscall entry time using syscall_get_nr(), syscall_get_arch() and syscall_get_arguments(), which extract information from the saved pt_regs frame using exactly the accessors described in Section 4.1. 


/* include/uapi/linux/seccomp.h */
struct seccomp_data {
    int   nr;                  /* syscall number (may differ from arch) */
    __u32 arch;                /* AUDIT_ARCH_* value */
    __u64 instruction_pointer; /* user-space IP at time of syscall */
    __u64 args[6];             /* syscall arguments */
};

Three things about that structure decide how filters must be written, and getting any of them wrong produces a filter that looks correct and can be bypassed.

  • arch must be checked, and checked first. The same numeric value in nr means different system calls under different ABIs, so a filter that blocks call number 59 without first confirming AUDIT_ARCH_X86_64 blocks execve for a 64-bit task and something entirely different for a 32-bit one entering through the compatibility door of Section 3.3. A filter that omits the architecture check is not merely imprecise; on a kernel with CONFIG_IA32_EMULATION it can be stepped around by re-issuing the call through the other ABI.
  • args[] is an array of __u64 while classic BPF is a 32-bit machine, so a filter that wants to constrain a pointer or a flags word must load and compare the two halves separately. Checking only the low half of a 64-bit argument is the classic seccomp defect.
  • args[] holds copies of the register values, not the memory they point to. A filter can compare a pointer but can never dereference one, so seccomp can express "no open() at all" and cannot express "no open() outside /tmp". That limitation is deliberate and is the reason SECCOMP_RET_USER_NOTIF exists.

The filter language is classic BPF (cBPF, the original "socket filter" bytecode), not the extended BPF that modern tracing and networking use. Classic BPF is a small accumulator machine with one scratch register, sixteen memory slots, forward-only jumps, and no loops, so every program terminates by construction and no verifier as elaborate as eBPF's is required. What actually executes, however, is eBPF: bpf_prog_create_from_user() validates the classic program with bpf_check_classic(), then translates it into eBPF and runs it through bpf_prog_run_pin_on_cpu(), so a JIT-enabled kernel executes native code. Classic BPF is the interface seccomp presents, not the machine it uses.

The seccomp-specific validation in seccomp_check_filter() is easy to describe as a whitelist, but it is really a rewrite pass, and the difference matters. 


/* kernel/seccomp.c — seccomp_check_filter(), the interesting cases */
    case BPF_LD | BPF_W | BPF_ABS:
        ftest->code = BPF_LDX | BPF_W | BPF_ABS;
        /* 32-bit aligned and not out of bounds. */
        if (k >= sizeof(struct seccomp_data) || k & 3)
            return -EINVAL;
        continue;
    case BPF_LD | BPF_W | BPF_LEN:
        ftest->code = BPF_LD | BPF_IMM;
        ftest->k = sizeof(struct seccomp_data);
        continue;

Every absolute word load is rewritten to a seccomp-private opcode that means "load from seccomp_data at this fixed offset", and its offset is checked for both range and four-byte alignment at install time. The consequence is that the running filter performs no bounds check at all: there is nothing to check, because no instruction that could go out of range survived installation. Length loads are folded into an immediate, since the buffer is always the same size. Everything else must appear in an explicit list of permitted opcodes — arithmetic, the sixteen-slot scratch memory, register transfers, forward jumps and returns — and anything not listed is rejected with -EINVAL. Two omissions are worth noticing: there is no modulo instruction, and there are no byte or halfword loads, so a filter can only ever see seccomp_data as an array of aligned 32-bit words. The ancillary "negative offset" loads that socket filters use to reach packet metadata are absent for the same reason — there is no packet, and no other kernel memory the filter is permitted to name.

The original classic program is kept alongside the translated one whenever CONFIG_CHECKPOINT_RESTORE or an architecture action cache is configured. Checkpoint/restore needs it because PTRACE_SECCOMP_GET_FILTER hands the original bytecode back to a sufficiently privileged tracer so that a sandbox can be recreated after a restore; the cache described below needs it because it interprets the program itself.

Individual filter programs are limited to BPF_MAXINSNS (4,096 instructions), and the total across a filter path is limited as described above. In practice, well-designed filters are much shorter — a typical Chrome seccomp policy compiles to a few hundred instructions.

The Constant-Action Cache

Running even a few hundred instructions on every system call is a real cost, and it is a cost paid overwhelmingly by calls the filter has no opinion about. A container allowlist spends most of its execution deciding, again and again, that read() is fine. Linux 7.0.12 removes that work entirely for the calls where the answer cannot depend on anything but the call number.

The observation behind the optimization is that a typical seccomp filter is a decision tree over nr and arch alone. If a program, evaluated with a particular nr and arch and with every other field treated as unknown, reaches a BPF_RET carrying SECCOMP_RET_ALLOW without ever needing an unknown value, then that syscall is unconditionally allowed by that filter and running the program can be skipped.

seccomp_cache_prepare() establishes this at install time. For each architecture the filter can see, it walks every valid syscall number and calls seccomp_is_const_allow(), a small interpreter that understands only the subset of classic BPF that can be evaluated with nr and arch known: absolute loads of exactly those two fields, constant comparisons, unconditional jumps, AND with a constant, and returns. Any other instruction — including a load of args[] or of the instruction pointer — makes the result unknown and the answer is conservatively "not cacheable". The verdict is recorded as one bit per syscall number in a bitmap held in the filter, and the bitmap is seeded by copying the previous filter's, so a chain's cache narrows monotonically and can never become more permissive than any filter below it. 


/* kernel/seccomp.c — the fast path in seccomp_run_filters() */
    if (seccomp_cache_check_allow(f, sd))
        return SECCOMP_RET_ALLOW;

/* ... and the lookup itself */
static inline bool seccomp_cache_check_allow_bitmap(const void *bitmap,
                                                    size_t bitmap_size,
                                                    int syscall_nr)
{
    if (unlikely(syscall_nr < 0 || syscall_nr >= bitmap_size))
        return false;
    syscall_nr = array_index_nospec(syscall_nr, bitmap_size);

    return test_bit(syscall_nr, bitmap);
}

An allowed call now costs a bounds check and a bit test instead of a bytecode program, and only the head filter's bitmap needs consulting because the copy-from-previous rule has already folded the whole chain into it. The array_index_nospec() is the Spectre-v1 clamp of Section 4.2 appearing for the third time in this chapter: the bitmap is indexed by a number that came from user space, immediately after a bounds check that a CPU may speculate past.

The bitmaps are per architecture — allow_native always, and allow_compat on kernels that support a second ABI — and are sized by SECCOMP_ARCH_NATIVE_NR, which is simply NR_syscalls. On a native-only build the architecture check disappears at compile time; on x86_64 with IA-32 emulation, sd->arch selects the bitmap and an architecture that is neither triggers WARN_ON_ONCE() and falls back to running the filters. Under CONFIG_SECCOMP_CACHE_DEBUG the whole cache is visible as /proc/pid/seccomp_cache, one line per syscall reading ALLOW or FILTER, readable only with CAP_SYS_ADMIN in the initial user namespace — because, as the comment says, a sandboxed process should not be able to learn what its own filters consist of.

There is one deliberate hole in this mechanism, and it is worth knowing about because it is a genuine exception to the claim that seccomp filters every system call. seccomp_is_const_allow() begins by calling seccomp_uprobe_exception(), which returns true for __NR_uprobe and __NR_uretprobe on the native architecture, and the comment reads Our single exception to filtering. Those two calls are not issued by the program; they are issued by trampolines the kernel itself patches into user space to implement uprobes, and a filter that happened to deny them would break tracing in a way the program never asked for and could not diagnose. Because the exception is applied while building the cache, their bits are set unconditionally and the filter genuinely never runs for them. A seccomp policy cannot block uretprobe.

Return Actions and the Evaluation Order

The BPF program returns a 32-bit value whose upper 16 bits encode an action and whose lower 16 bits carry action-specific data (for example, an errno value for SECCOMP_RET_ERRNO). The kernel's __seccomp_filter() function dispatches on the action after running all filters and selecting the least permissive result. The split is made by two masks: SECCOMP_RET_ACTION_FULL (0xffff0000) selects the action and SECCOMP_RET_DATA (0x0000ffff) the payload. Note that the data is compared away before the least-permissive selection, so two filters returning SECCOMP_RET_ERRNO with different errno values are treated as equally restrictive and the tie rule of Section 6.2 decides which errno the caller sees.

Table 10-14. seccomp Return Actions
Action Value Meaning Typical effect
SECCOMP_RET_KILL_PROCESS 0x80000000 Terminate the process Strongest action; used for non-negotiable policy violations.
SECCOMP_RET_KILL_THREAD 0x00000000 Terminate the current thread The original kill action, still the value of the SECCOMP_RET_KILL alias. Dumps core only if it is the last live thread.
SECCOMP_RET_TRAP 0x00030000 Force SIGSYS User space can install a handler or crash with diagnostic information.
SECCOMP_RET_ERRNO 0x00050000 Pretend the syscall failed Kernel writes a chosen -errno, capped at MAX_ERRNO, and skips dispatch.
SECCOMP_RET_USER_NOTIF 0x7fc00000 Notify a supervising process Container runtimes can emulate or broker selected operations.
SECCOMP_RET_TRACE 0x7ff00000 Defer to ptrace Lets tracers inspect or rewrite the call before final disposition. Fails the call with -ENOSYS if no tracer is attached.
SECCOMP_RET_LOG 0x7ffc0000 Allow after logging Useful for learning and audit modes.
SECCOMP_RET_ALLOW 0x7fff0000 Permit the syscall The dispatch path continues normally.

The exact position of seccomp in the entry pipeline is subtle and has changed from some older descriptions. In Linux 7.0.12, the generic syscall_trace_enter() handles Syscall User Dispatch first, then ptrace entry, then seccomp, then tracepoints, and finally audit entry. Seccomp runs after ptrace on purpose: if a tracer modifies the syscall number or arguments, the filter sees the modified values. That ordering is visible directly in include/linux/entry-common.h, where the comment on the seccomp branch reads simply Do seccomp after ptrace, to catch any tracer changes.

One escape hatch runs before any of this. On a kernel built with CONFIG_CHECKPOINT_RESTORE, __secure_computing() returns immediately if the task carries PT_SUSPEND_SECCOMP, set by a tracer through PTRACE_O_SUSPEND_SECCOMP. Setting it requires CAP_SYS_ADMIN in the initial user namespace and, in kernel/ptrace.c, is refused outright if the tracer is itself under seccomp or already has the option set — a confined process must not be able to lift confinement from anything, including by way of a process it traces. It exists so that checkpoint/restore can replay a process's system calls while rebuilding it, and it is the only way seccomp can be switched off short of the process exiting. 


/* kernel/seccomp.c — filter evaluation and dispatch (simplified) */
static int __seccomp_filter(int this_syscall,
                            const bool recheck_after_trace)
{
    u32 filter_ret, action;
    struct seccomp_data sd;
    ...
    populate_seccomp_data(&sd);
    filter_ret = seccomp_run_filters(&sd, &match);
    action = filter_ret & SECCOMP_RET_ACTION_FULL;

    switch (action) {
    case SECCOMP_RET_KILL_PROCESS:
        ...
    case SECCOMP_RET_KILL_THREAD:
        ...
    case SECCOMP_RET_TRAP:
        /* Deliver SIGSYS with siginfo */
        ...
    case SECCOMP_RET_ERRNO:
        /* Set return value to -(data & 0xffff) */
        ...
    case SECCOMP_RET_USER_NOTIF:
        return seccomp_do_user_notification(...);
    case SECCOMP_RET_TRACE:
        /* Notify ptrace tracer */
        ...
    case SECCOMP_RET_LOG:
        seccomp_log(...);
        return 0;
    case SECCOMP_RET_ALLOW:
        return 0;
    }
}

Several of the cases do more than the summary in the table suggests.

Both kill actions begin by setting SECCOMP_MODE_DEAD, and then diverge on one question: whether a core dump would be useful. KILL_PROCESS, and KILL_THREAD when the dying thread is the last live one in the group, call syscall_rollback() to restore the pre-entry register values and then raise SIGSYS so that a dump is produced showing the offending call as user space issued it. KILL_THREAD with other threads still running instead calls do_exit(SIGSYS) and produces no dump, because a dump of a process that is still executing would be misleading. That asymmetry, rather than any difference in strength, is the practical distinction between the two.

SECCOMP_RET_TRAP also calls syscall_rollback() first, with the comment Show the handler the original registers. A SIGSYS handler that inspects the register context therefore sees what the program actually attempted, not the partially updated state left behind by entry processing — which is what makes the action usable for emulating a missing system call in user space.

SECCOMP_RET_TRACE is the most involved case and contains a fail-closed decision that is easy to miss. If no tracer is attached, the call does not proceed: it fails with -ENOSYS, on the reasoning that a policy which delegated the decision to a supervisor that is not there has not made a decision to allow. If a tracer is attached, the tracer may change the syscall number or its arguments, so after the stop the kernel re-reads the number and calls __seccomp_filter() again with recheck_after_trace set. On that second pass a further SECCOMP_RET_TRACE verdict simply returns success rather than stopping again, which is what prevents a tracer and a filter from looping forever. The path also checks for a pending fatal signal between the two, and skips the call if one arrived, so that a process being killed during the stop does not resume into a call the tracer never got to inspect.

Which of these actions is logged is a system-wide decision, not a per-filter one. seccomp_log() consults the global seccomp_actions_logged bitmask, exposed as /proc/sys/kernel/seccomp/actions_logged and writable only with CAP_SYS_ADMIN; the companion read-only actions_avail lists the action names the running kernel understands, which is how a sandbox library discovers whether a newer action exists. The write handler refuses to enable logging for SECCOMP_RET_ALLOW — which would log every system call on the system — and every change is itself reported to the audit subsystem with both the old and new settings. A filter's own SECCOMP_FILTER_FLAG_LOG can only request logging for actions the administrator has already permitted to be logged.

User-Space Notification

The most powerful seccomp action is SECCOMP_RET_USER_NOTIF, which turns the kernel into a mediator between the sandboxed process and a supervising process. When a filter returns this action, the kernel does not execute the system call. Instead, it suspends the calling thread and queues a notification containing the full seccomp_data — syscall number, arguments, and instruction pointer — to a special file descriptor that the supervisor holds. This is the action that lifts the fundamental limitation described earlier: a BPF filter can compare a pointer but cannot follow it, whereas a supervisor holding the target's PID can read the target's memory through /proc or process_vm_readv() and decide on the basis of what the pointer actually refers to.

Each suspended call is represented by a struct seccomp_knotif allocated on the notifying thread's kernel stack, which is sound precisely because that thread is blocked for the whole lifetime of the notification. It moves through three states. A new notification is INIT; SECCOMP_IOCTL_NOTIF_RECV hands out the first INIT entry it finds and marks it SENT; a reply marks it REPLIED and completes the waiter. If a signal interrupts the notifying thread before a reply arrives, the entry returns to INIT so that the notification will be delivered again — a supervisor must therefore be prepared to see the same call twice and to have a request it is working on become stale. SECCOMP_IOCTL_NOTIF_ID_VALID exists for exactly that: it reports whether the cookie the supervisor is holding still names a request in the SENT state, which is how the supervisor avoids acting on behalf of a process that has since died.

Two fail-safes are built into the wait. If the filter has no listener at all — because the supervisor closed the descriptor, or was killed — the notifying thread does not block; it receives -ENOSYS, so a sandbox whose supervisor disappears fails closed rather than hanging. And the sleep is interruptible by default, so a signal can rescue a thread whose supervisor is merely slow. That default is wrong once the supervisor has actually received the request and may already have acted on it, which is what SECCOMP_FILTER_FLAG_WAIT_KILLABLE_RECV addresses: with that flag the sleep becomes interruptible only until the notification reaches state SENT, after which nothing short of a fatal signal will wake the thread. The transition happens mid-wait, and the loop in seccomp_do_user_notification() deliberately re-checks it before treating an interruption as an error.

The supervisor obtains this file descriptor when it installs the filter with the SECCOMP_FILTER_FLAG_NEW_LISTENER flag. The returned fd supports several ioctl operations:

Table 10-15. seccomp Notification ioctl Commands
ioctl Purpose
SECCOMP_IOCTL_NOTIF_RECV Block until a notification arrives, then copy it to user space. The supplied buffer must be entirely zero, which is how the structure stays extensible.
SECCOMP_IOCTL_NOTIF_SEND Send a response (allow with a value, deny with an errno, or continue) back to the kernel. Exactly one reply per request is accepted; a second gets -EINPROGRESS.
SECCOMP_IOCTL_NOTIF_ID_VALID Check whether the notification ID still names a request awaiting a reply. An older, wrongly encoded command number is also accepted forever for compatibility.
SECCOMP_IOCTL_NOTIF_ADDFD Inject a file descriptor into the target task's fd table, optionally at a chosen number and optionally atomically with the reply.
SECCOMP_IOCTL_NOTIF_SET_FLAGS Set per-listener behaviour; currently only SECCOMP_USER_NOTIF_FD_SYNC_WAKE_UP, which wakes the peer on the current CPU to trade throughput for latency.

This mechanism enables container runtimes to emulate system calls that cannot be safely exposed to the sandboxed process. For example, a container might intercept mount() calls, validate the arguments in the supervisor, perform the actual mount in the supervisor's namespace, and then inject the resulting file descriptor back into the container. The SECCOMP_IOCTL_NOTIF_ADDFD command, added in Linux 5.9, makes this pattern practical by allowing the supervisor to push open file descriptors into the target without the target needing to do anything. Two flags refine it. SECCOMP_ADDFD_FLAG_SETFD installs the descriptor at a number the supervisor chooses rather than the lowest free one, which matters when emulating a call whose result the target already expects at a particular index. SECCOMP_ADDFD_FLAG_SEND performs the injection and the reply as one operation, returning the new descriptor number as the syscall's result — without it there is a window in which the descriptor exists in the target but the call that was supposed to create it has not yet returned, and a signal arriving in that window could leave the target holding a descriptor it never asked for. The injection itself is performed by the notifying thread, which is woken for the purpose and then goes back to waiting; that is why struct seccomp_kaddfd carries its own completion and why a request that finds the target already gone is answered with -ESRCH.

The descriptor also supports poll(), and its three conditions map onto the state machine above: EPOLLIN when a request is waiting to be received, EPOLLOUT when a received request is waiting to be answered, and EPOLLHUP when the filter has been orphaned because every task that could trigger it has exited. The last of these is the event that the second reference count discussed earlier exists to make possible.

One curiosity in the ioctl table is a permanent scar. When SECCOMP_IOCTL_NOTIF_ID_VALID was introduced its command number was built with the wrong direction bit, describing a read where the kernel in fact only writes. The number was fixed, but the old one is still accepted under the name SECCOMP_IOCTL_NOTIF_ID_VALID_WRONG_DIR, with a comment saying it must keep working until all userspaces stop using the wrong command number — which, as Section 5.6 observed about vsyscall, means indefinitely.

The UAPI header include/uapi/linux/seccomp.h is unusually blunt about the limits of all this. Its warning on SECCOMP_USER_NOTIF_FLAG_CONTINUE states that the seccomp notifier cannot be used to implement a security policy, and the emphasis is the header's own. The concern is a time-of-check to time-of-use race: between the moment the supervisor inspects the arguments and the moment the kernel executes the call, another thread in the target process can rewrite whatever the pointer arguments refer to. The supervisor is looking at the target's memory, and the target is still running.

The header's conclusion is worth stating precisely, because it is narrower than "be careful". The notifier is intended for a more privileged process to relax a restriction for a less privileged one in a situation the privileged process has determined is safe — a container manager performing a mount on behalf of a container, for instance — and never for a supervisor to be the thing that stops a hostile process. Anything that must hold against an attacker has to be enforced by a mechanism the attacker cannot race: the filter's own verdict, which is computed from register values that are copies, or the kernel's ordinary permission checks. The same reasoning applies to SECCOMP_RET_TRACE, and the header notes that a CONTINUE reply can override a TRACE verdict from an older filter in the same chain. Where a decision must be enforced rather than merely advised, the safe patterns are to answer with an error or an emulated result rather than CONTINUE, or to inject a descriptor the supervisor opened itself, so that the object the target ends up using is one the supervisor chose rather than one it merely inspected.

Deployment and Ecosystem

Seccomp-BPF has become one of the most widely deployed kernel security mechanisms. Chrome and Firefox use it to sandbox renderer processes, restricting them to a narrow set of IPC-related syscalls and blocking anything that could interact with the filesystem, network, or other processes directly. Docker and other OCI-compliant container runtimes install a default syscall allowlist (typically around 300 of the 472 calls on x86_64) that blocks potentially dangerous operations like reboot(), kexec_load(), and raw device access. A policy of that shape is precisely the case the constant-action cache was written for: almost every rule is a comparison against nr alone, so almost every allowed call ends up as a set bit and the bytecode never runs at all in steady-state operation.

systemd supports a SystemCallFilter= directive in unit files that compiles a seccomp filter at service startup. Administrators can specify either an allowlist or a denylist using syscall group names (@network-io, @file-system, @privileged), making it practical to harden services without writing BPF programs by hand. Android uses a related approach where the zygote process installs a seccomp filter before forking application processes, ensuring that every app inherits a baseline restriction policy.

User-space libraries like libseccomp provide a higher-level API for constructing filters. Instead of writing raw BPF instructions, developers express rules like "allow read, allow write, deny everything else with EPERM", and the library compiles these into an optimized BPF program — typically a balanced binary search over syscall numbers rather than a linear chain of comparisons, since the instruction budget and the entry-path cost both scale with the length of the path actually executed. A library is also the right place to enforce the rules of Section 6.3 that the kernel cannot: emitting the architecture check before the syscall comparison, and comparing both halves of a 64-bit argument. Tools like strace --seccomp-bpf also leverage seccomp internally: strace installs a filter that returns SECCOMP_RET_TRACE only for syscalls it wants to intercept, reducing the ptrace overhead for calls it doesn't care about.

System Call Tracing and Auditing

Because system calls define the ABI boundary between user space and the kernel, they are natural observation points for debugging, security monitoring, performance analysis, and compliance auditing. Every interesting thing a process does — opening files, sending network packets, creating child processes, mapping memory — passes through a system call, so instrumenting this boundary provides a complete record of a process's kernel interactions.

Linux 7.0.12 exposes system calls to multiple tracing and monitoring subsystems: ptrace (used by strace and debuggers), static tracepoints (used by ftrace and perf), eBPF programs, and the kernel audit subsystem. Rather than requiring each architecture to implement these hooks independently, the generic entry/exit helpers in include/linux/entry-common.h centralize the sequencing. This means that x86_64, ARM64, and every other architecture that uses the generic entry code get a consistent, well-ordered hook pipeline without duplicating the logic.

These mechanisms are not variations on one idea; they occupy genuinely different points in a design space, and choosing among them is mostly a matter of deciding which axis matters. The first axis is whether the observer stops the observed thread or merely samples it as it goes past: ptrace stops, everything else does not. The second is scope — ptrace and seccomp are attached to a process tree, while tracepoints, eBPF, and audit are system-wide and see every task on the machine. The third is whether the observer may change what happens: ptrace and seccomp can, audit deliberately cannot, and tracepoints occupy an awkward middle ground examined in Section 7.3. The fourth is who the mechanism was built for. Tracing tools are built for developers and optimize for flexibility and low overhead; audit is built for security administrators and optimizes for completeness and non-repudiation, which is why it is the only mechanism here that accumulates state during the syscall rather than sampling its endpoints.

The ordering of these hooks matters greatly. A ptrace tracer may rewrite the syscall number before seccomp evaluates it; seccomp may kill the process before audit records it; tracepoints must see the final syscall number that will actually be dispatched. Getting this order wrong would create security holes (seccomp bypasses) or audit gaps (missing records). The following subsections examine each hook mechanism and explain where it fits in the pipeline.

The Entry Pipeline Order

The syscall entry pipeline in Linux 7.0.12 is a fixed sequence of hooks that every system call passes through before reaching the actual service routine. The sequence is encoded in syscall_trace_enter() in include/linux/entry-common.h and is driven by per-thread work flags stored in thread_info. Each hook is guarded by its own flag (SYSCALL_WORK_SYSCALL_TRACE, SYSCALL_WORK_SECCOMP, etc.), so hooks that are not active for a particular thread are skipped with minimal overhead — a single bitmask test.

The gating is two-level, and the outer level is what keeps the common case free. syscall_enter_from_user_mode_work() reads current_thread_info()->syscall_work once and tests it against the composite mask SYSCALL_WORK_ENTER, which is the bitwise OR of every entry-side flag. A thread with no tracer, no seccomp filter, no audit rules, and no dispatch configuration has a zero word there, so the entire pipeline collapses to one load, one AND, and one not-taken branch; syscall_trace_enter() is never called at all. Only when the composite test fires does the inner sequence run and pay for the individual flag tests. Notice also that the flags live in thread_info, not in task_struct: they are read on the hottest path in the kernel, and thread_info is the structure the entry code can reach without an extra dereference. 


/* include/linux/entry-common.h */
static __always_inline long syscall_trace_enter(struct pt_regs *regs,
                                                unsigned long work)
{
    long syscall, ret = 0;

    /*
     * Handle Syscall User Dispatch.  This must comes first, since
     * the ABI here can be something that doesn't make sense for
     * other syscall_work features.
     */
    if (work & SYSCALL_WORK_SYSCALL_USER_DISPATCH) {
        if (syscall_user_dispatch(regs))
            return -1L;
    }

    /*
     * User space got a time slice extension granted and relinquishes
     * the CPU. The work stops the slice timer to avoid an extra round
     * through hrtimer_interrupt().
     */
    if (work & SYSCALL_WORK_SYSCALL_RSEQ_SLICE)
        rseq_syscall_enter_work(syscall_get_nr(current, regs));

    /* Handle ptrace */
    if (work & (SYSCALL_WORK_SYSCALL_TRACE | SYSCALL_WORK_SYSCALL_EMU)) {
        ret = arch_ptrace_report_syscall_entry(regs);
        if (ret || (work & SYSCALL_WORK_SYSCALL_EMU))
            return -1L;
    }

    /* Do seccomp after ptrace, to catch any tracer changes. */
    if (work & SYSCALL_WORK_SECCOMP) {
        ret = __secure_computing();
        if (ret == -1L)
            return ret;
    }

    /* Either of the above might have changed the syscall number */
    syscall = syscall_get_nr(current, regs);

    if (unlikely(work & SYSCALL_WORK_SYSCALL_TRACEPOINT))
        syscall = trace_syscall_enter(regs, syscall);

    syscall_enter_audit(regs, syscall);

    return ret ? : syscall;
}

Order Hook Reason for its position

2 rseq time-slice extension Cancels a granted slice extension before anything can block, so the slice timer is stopped without a round trip through hrtimer_interrupt().

4 seccomp Evaluates the syscall after ptrace modifications, per the comment "Do seccomp after ptrace, to catch any tracer changes."

8 dispatch Calls the actual service routine or ni_syscall fallback.

Two details in the excerpt repay attention because they are the mechanism behind claims made elsewhere in this section. The first is the explicit re-read of the syscall number after seccomp: the number the architecture code loaded from the register and passed into the entry helper is discarded, and everything downstream — the tracepoint, the audit record, and the table lookup itself — uses the value that syscall_get_nr() returns at that point. Without that line, a tracer that rewrote the number would fool the dispatcher but not the audit log, or vice versa. The second is return ret ? : syscall, which looks redundant because both surviving paths leave ret at zero, but which documents the contract: a non-zero return that is not -1L would be propagated as the syscall number, and callers must treat -1L as "skip this call" rather than as a valid number.

On exit, the common helper mirrors the entry pipeline but in a different order, and it opens with a special case rather than with audit. syscall_exit_work() first checks whether Syscall User Dispatch cancelled this call; if current->syscall_dispatch.on_dispatch is set, it clears the flag and returns immediately, so audit and the tracers see nothing at all. The kernel's own comment gives the reason: the tracers are skipped "for the same reason as the entry side was not invoked" — the ABI of a dispatched call is unknown, and recording arguments the kernel cannot interpret would be worse than recording nothing. After that, audit exit runs to record the return value, tracepoints log the result, and finally ptrace can observe the finished syscall before the generic return-to-user loop handles signals, rescheduling, or live-patching.

The final ptrace report on the exit path is guarded by a slightly larger condition than the entry one, because it does double duty. report_single_step() returns true when SYSCALL_WORK_SYSCALL_EXIT_TRAP is set and syscall emulation is not, in which case the exit report substitutes for the single-step trap that would normally follow the syscall instruction — this is what makes PTRACE_SYSEMU_SINGLESTEP deliver exactly one stop rather than two. When emulation is active, report_single_step() returns false unconditionally, because the entry stop already told the tracer everything and the call never ran.

The one-time exit work is carefully separated from the potentially repeating user-mode exit loop so that tracing does not accidentally run multiple times for one logical syscall. syscall_exit_to_user_mode_work() runs the hooks exactly once with interrupts enabled; only afterwards does control enter the loop that handles pending signals and reschedules, and that loop can iterate many times without re-emitting a single audit record or tracepoint event.

This ordering differs from simplified older diagrams that put seccomp before ptrace or treat tracing as a single monolithic step. The code in Linux 7.0.12 is the authoritative source, and it reflects years of edge-case handling for tracers, syscall emulation, seccomp rechecks, and audit correctness.

ptrace Syscall Tracing

The ptrace() system call is the oldest and most widely used syscall tracing mechanism in Linux. Tools like strace, ltrace, and GDB use ptrace to stop a process at every syscall entry and exit, inspect the arguments and return value, and optionally modify them before allowing the process to continue. Despite its age, ptrace remains the primary interface for interactive debugging and per-process syscall tracing.

The basic mechanism works through the PTRACE_SYSCALL request. When a tracer calls ptrace(PTRACE_SYSCALL, pid, ...), the kernel sets the SYSCALL_WORK_SYSCALL_TRACE flag on the target thread. This flag causes syscall_trace_enter() to stop the tracee at the next syscall entry, and again after the service routine returns, so the tracer can read the return value. The tracer reads the syscall number and arguments from the tracee's registers and can optionally rewrite them before resuming with another PTRACE_SYSCALL.

The stop itself is not a distinct ptrace event; it is an ordinary signal-delivery stop synthesized by ptrace_report_syscall() in include/linux/ptrace.h, which calls ptrace_notify() with SIGTRAP. This is the source of a well-known annoyance: a bare syscall stop is indistinguishable from a genuine SIGTRAP raised by a breakpoint. The fix is the PTRACE_O_TRACESYSGOOD option, which sets PT_TRACESYSGOOD and makes the kernel report SIGTRAP | 0x80 instead, so the tracer can tell the two apart by inspecting bit 7 of the stop signal. Distinguishing the entry stop from the exit stop is a second problem, and historically tracers solved it by keeping a per-thread toggle — which desynchronizes if the tracer attaches in the middle of a syscall. Linux now passes PTRACE_EVENTMSG_SYSCALL_ENTRY or PTRACE_EVENTMSG_SYSCALL_EXIT as the notification message, retrievable with PTRACE_GETEVENTMSG, so the kernel answers the question directly.

Reading and writing the tracee's registers is the part of ptrace that is least portable. x86_64 offers the classic PTRACE_GETREGS and PTRACE_PEEKUSER requests, but ARM64 implements neither: it exposes only the regset interface, PTRACE_GETREGSET and PTRACE_SETREGSET with an NT_PRSTATUS iovec. Even where both exist, a tracer that wants to rewrite the syscall number has to know which register holds it on the target architecture and, on some architectures, that the same register also holds the return value — a detail that PTRACE_SET_SYSCALL_INFO, described below, exists to hide.

A more specialized variant, PTRACE_SYSEMU, sets the SYSCALL_WORK_SYSCALL_EMU flag. This causes the kernel to stop the tracee at syscall entry but skip the actual service routine entirely: the entry helper returns -1L immediately after the ptrace report, without consulting seccomp, the tracepoints, or audit. The tracer is expected to emulate the syscall's behavior itself. This mode was originally designed for User-Mode Linux (UML), which runs as a user-space process and needs to intercept all guest syscalls without letting them reach the host kernel. It has since been largely superseded for that purpose by Syscall User Dispatch (Section 7.6), which achieves the same interception without the two context switches per call, but PTRACE_SYSEMU remains the only option when the emulator is a different process from the one being emulated.

Linux 5.3 introduced PTRACE_GET_SYSCALL_INFO, which provides a structured view of the syscall state in a single request, avoiding the need for multiple PTRACE_PEEKUSER calls and, more importantly, avoiding any architecture-specific knowledge of which register holds what. The struct ptrace_syscall_info in include/uapi/linux/ptrace.h packages the operation kind, architecture, instruction pointer, stack pointer, syscall number, all six arguments, and the exit return value into one structure. 


/* include/uapi/linux/ptrace.h */
struct ptrace_syscall_info {
    __u8 op;                /* PTRACE_SYSCALL_INFO_* */
    __u8 reserved;
    __u16 flags;
    __u32 arch;             /* AUDIT_ARCH_* value */
    __u64 instruction_pointer;
    __u64 stack_pointer;
    union {
        struct {            /* op == ENTRY */
            __u64 nr;       /* syscall number */
            __u64 args[6];  /* syscall arguments */
        } entry;
        struct {            /* op == EXIT */
            __s64 rval;     /* return value */
            __u8 is_error;  /* 1 if rval is a -errno */
        } exit;
        struct {            /* op == SECCOMP */
            __u64 nr;
            __u64 args[6];
            __u32 ret_data; /* SECCOMP_RET_DATA */
            __u32 reserved2;
        } seccomp;
    };
};

There are four operation kinds, not three. PTRACE_SYSCALL_INFO_NONE is returned when the tracee is stopped for a reason unrelated to a system call — a signal-delivery stop, a group stop, an exec event — and it is the value that lets a tracer ask the question unconditionally instead of tracking why it stopped the tracee. PTRACE_SYSCALL_INFO_SECCOMP corresponds to the stop produced by a SECCOMP_RET_TRACE verdict, and it is the only kind that carries ret_data, the sixteen bits of filter-supplied payload described in Section 6.5. The request is size-negotiated in the same style as the extensible structures of Section 4.3: the tracer passes the size of its buffer in addr, the kernel writes min(actual, user_size) bytes and returns the size it would have written, so a tracer built against an older header still works and can detect that it received a truncated view.

Linux 6.16 completed the pair with PTRACE_SET_SYSCALL_INFO, the write counterpart, and it is the more consequential of the two because it finally makes syscall rewriting portable. Before it existed, a tracer that wanted to redirect open to openat or turn a call into a no-op had to know the architecture's register file layout, use PTRACE_SETREGS on x86_64 and PTRACE_SETREGSET on ARM64, and cope with architectures where the first argument register and the return-value register are the same. ptrace_set_syscall_info() in kernel/ptrace.c hides all of that behind syscall_set_nr() and syscall_set_arguments().

Its validation is worth noting because it is the kind of check that only matters on a 32-bit tracee driven by a 64-bit tracer. Each field is written into a native-width local and compared back against the 64-bit value the tracer supplied; if the round trip is lossy the call fails with -ERANGE rather than silently truncating. Setting the number to -1 is a special case that skips the argument write entirely, precisely because of the shared argument/return register mentioned above — writing arguments to a cancelled call "would also clobber the syscall return value on those architectures that share the same register". Two further restrictions apply: flags and reserved must be zero, which is how the kernel reserves room for future extensions, and the op field must match the kind of stop the tracee is actually in, since "changing the type of the system call stop is not supported yet".

A practical limitation of ptrace-based tracing is performance: every syscall entry and exit causes a context switch between the tracee and the tracer, so a traced call costs at least four context switches instead of none. For high-frequency workloads, this overhead can slow the traced process by 10–100×. Modern strace mitigates this with --seccomp-bpf, which installs a seccomp filter that returns SECCOMP_RET_TRACE only for the specific syscalls strace wants to observe, letting uninteresting calls pass through without a ptrace stop. The cost of the calls strace does not care about then falls to the constant-action cache of Section 6.4 — a bitmap lookup — which is why the combination is dramatically faster than plain PTRACE_SYSCALL even though it adds a second mechanism to the path.

Static Tracepoints and perf

For lower-overhead system-wide tracing, Linux provides static tracepoints at syscall entry and exit. These are defined in include/trace/events/syscalls.h as the raw_syscalls:sys_enter and raw_syscalls:sys_exit events. Unlike ptrace, tracepoints do not stop the traced process — they execute an attached callback (or eBPF program) inline within the syscall path and then let the process continue. The overhead is much lower: typically microseconds per event rather than the two context switches that ptrace requires.

Each tracepoint payload includes the syscall number and either all six arguments (on entry) or the return value (on exit) — a wider view than audit's four-argument record. Note that the arguments are not passed to the tracepoint; the TP_fast_assign block calls syscall_get_arguments() itself, so the values recorded are read from pt_regs at the moment the event fires, after every rewrite the pipeline permits. The exit event likewise re-reads the number with syscall_get_nr() rather than trusting a cached copy.

Enabling either event is a system-wide operation with a system-wide cost, and the mechanism is unusually blunt. The tracepoints are declared with the reg and unreg callbacks syscall_regfunc() and syscall_unregfunc(), and the first registration walks the entire task list under tasklist_lock setting SYSCALL_WORK_SYSCALL_TRACEPOINT on every thread on the machine; the last unregistration walks it again to clear the flag. There is no way to enable the raw syscall tracepoints for one process. A single reference count, sys_tracepoint_refcount, arbitrates between the two events and between multiple consumers, which is why enabling sys_exit after sys_enter is nearly free while the first enable is not.

In addition to the generic raw_syscalls events, the kernel generates per-syscall tracepoints like syscalls:sys_enter_openat and syscalls:sys_exit_read that include decoded, named fields. These are built at boot from the struct syscall_metadata records that SYSCALL_DEFINE emits (Section 2.3), matched against the syscall table by symbol name. That matching is the reason both architectures covered here need a custom comparison function. Because the wrappers rename the real entry point, x86_64's arch_syscall_match_sym_name() has to strip a __x64_, __ia32_, or __do_sys prefix before comparing, and ARM64's has to skip a fixed eight characters of __arm64_. The mapping from syscall numbers to per-syscall metadata and event formats lives in kernel/trace/trace_syscalls.c.

The per-syscall tracepoints have a limitation that the raw ones do not, and it affects both architectures in this book. A 32-bit compat task uses a different syscall table, so number 5 does not mean the same thing to it as to a native task, and reporting sys_enter_openat for a compat call would be simply wrong. Rather than maintain two metadata tables, both x86 and ARM64 define ARCH_TRACE_IGNORE_COMPAT_SYSCALLS, and trace_get_syscall_nr() returns -1 for any task where arch_trace_is_compat_syscall() is true. The named events therefore do not fire at all for 32-bit processes. The ARM64 header states the consequence and the workaround together: tracing compat syscalls "may result in reporting bogus syscalls or even hang-up, so just do not trace them… If the user really wants these, then they should use the raw syscall tracepoints with filtering."

The perf tool is the primary user-space consumer of these tracepoints. perf trace opens tracepoint events using the PERF_TYPE_TRACEPOINT event type and decodes the payloads using format files exported by tracefs. It prefers raw_syscalls:sys_enter and raw_syscalls:sys_exit when available, falling back to the per-syscall tracepoints on older kernels. Because perf uses the ring-buffer infrastructure rather than ptrace stops, it can trace all processes system-wide with overhead comparable to a few percent of CPU time even under heavy syscall loads.

ftrace can also attach to these tracepoints through the tracefs filesystem (/sys/kernel/tracing/). Administrators can enable raw_syscalls:sys_enter and apply filters like id == 2 (for open) to capture specific syscalls into the trace buffer. The trace output includes timestamps, CPU numbers, process names, and the full argument/return-value payload. Both events carry TRACE_EVENT_FL_CAP_ANY, which marks them as capable of exposing data belonging to any task on the system; perf therefore requires the usual privilege for system-wide events rather than permitting an unprivileged self-profiling attachment.

One property of these two tracepoints sets them apart from every other tracepoint in the kernel and matters a great deal to the eBPF programs of the next subsection. They are declared with TRACE_EVENT_SYSCALL rather than TRACE_EVENT, and that macro expands to a faultable tracepoint: the generated trace_sys_enter() begins with might_fault() and takes an RCU Tasks Trace read-side section instead of disabling preemption. An ordinary tracepoint runs with preemption disabled and cannot take a page fault, which is why a probe attached to one may not dereference a user pointer. The syscall tracepoints can, and that is the whole reason the distinction exists. It is also the answer to the limitation of Section 6.3: a seccomp filter sees register copies it cannot follow, but a program on sys_enter sees the same registers and may read the memory they point at.

eBPF Syscall Tracing

Extended BPF (eBPF) programs can attach to syscall tracepoints, providing programmable in-kernel analysis that avoids the overhead of copying every event to user space. An eBPF program attached to raw_syscalls:sys_enter runs in the kernel's tracepoint callback context and can filter, aggregate, or transform events using BPF maps — hash tables, arrays, ring buffers — before passing only the interesting results to user space.

There are two attachment styles. A BPF_PROG_TYPE_TRACEPOINT program attaches to a named tracepoint and receives the tracepoint's formatted payload as its context — for sys_enter, a struct trace_event_raw_sys_enter with the number and six arguments already unpacked. A BPF_PROG_TYPE_RAW_TRACEPOINT program attaches to the same tracepoint but receives raw bpf_raw_tracepoint_args — essentially the unformatted arguments passed to the tracepoint macro, which for the syscall tracepoints means the struct pt_regs * itself — giving it lower overhead and more flexibility at the cost of having to decode the arguments itself. A third type, BPF_PROG_TYPE_RAW_TRACEPOINT_WRITABLE, exists for the small set of tracepoints whose context the kernel is willing to have modified; the syscall tracepoints are not among them.

Because the syscall tracepoints are faultable, the BPF core treats links attached to them specially. bpf_link_init_sleepable() is passed tracepoint_is_faultable(btp->tp), which selects RCU Tasks Trace rather than SRCU for the teardown grace period and, on the attach side, permits a program marked sleepable to run. The practical consequence is the one that makes syscall tracing genuinely more powerful than syscall filtering: a program on sys_enter may call bpf_copy_from_user() to read the pathname an openat is about to resolve, or the iovec array a writev is about to consume, and take a page fault doing so. A seccomp filter, running on the same registers a few instructions earlier, cannot.

The corollary is that a probe on these tracepoints is not purely passive. trace_syscall_enter() in kernel/entry/syscall-common.c is a long-returning wrapper for exactly this reason, and its comment is explicit: "Probes or BPF hooks in the tracepoint may have changed the system call number. Reread it." The tracepoint context is read-only, so this is not a supported way to redirect a call, but the registers a probe can reach through other means are the live ones, and the kernel takes the defensive position of trusting the register file over its own local variable. 


/* Example: eBPF program counting openat syscalls */
SEC("tracepoint/syscalls/sys_enter_openat")
int count_openat(struct trace_event_raw_sys_enter *ctx)
{
    u64 key = ctx->id;   /* syscall number */
    u64 *count = bpf_map_lookup_elem(&syscall_counts, &key);
    if (count)
        __sync_fetch_and_add(count, 1);
    return 0;
}

Tracepoints are not the only eBPF attachment point relevant to system calls. A BPF_PROG_TYPE_TRACING program with attach type BPF_TRACE_FENTRY or BPF_TRACE_FEXIT can hook an individual service routine — __x64_sys_openat on x86_64, __arm64_sys_openat on ARM64 — using the BTF type information to get typed access to its arguments and, for fexit, its return value. This is more precise than the tracepoint when the interest is one syscall rather than all of them, because it costs nothing on any other call and does not require setting a work flag on every thread in the system. It is also less portable, since the symbol name embeds the architecture prefix that Section 2.3 introduced.

Tools like bpftrace make eBPF syscall tracing accessible through a high-level scripting language. A one-liner like bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args->filename)); }' can trace all openat calls system-wide with per-event formatting and negligible overhead. Production observability tools like BCC (BPF Compiler Collection) provide pre-built eBPF programs for common syscall analysis tasks — latency histograms, argument pattern matching, and error counting.

The Audit Subsystem

The Linux audit subsystem provides tamper-resistant logging of security-relevant events for regulatory compliance (PCI-DSS, SOX, HIPAA) and forensic analysis. Unlike tracing tools that are designed for developers, audit is designed for security administrators: its records are structured for long-term storage, its rules persist across reboots, and its log stream is protected against user-space tampering.

Audit hooks into the syscall path through audit_syscall_entry() and audit_syscall_exit(), which are called from the generic entry/exit helpers. The entry hook records the syscall number, the architecture as reported by syscall_get_arch(), and the arguments into the per-task audit_context structure. The exit hook records the return value and then emits the completed audit record to the audit log via netlink to the auditd daemon.

Two details of the entry hook are easy to miss and both constrain what audit rules can express. The first is that only four arguments are captured: syscall_enter_audit() reads all six with syscall_get_arguments() but passes only args[0] through args[3] to audit_syscall_entry(), and struct audit_context has an argv[4] to match. This is why auditctl accepts -F a0= through -F a3= and nothing beyond; a rule cannot match on the fifth or sixth argument of any system call. The second is context->dummy = !audit_n_rules, which records at entry whether any syscall rules are loaded at all, so that a machine with an allocated audit context but an empty rule set skips almost all of the later work.

Audit rules, managed by the auditctl command, control which syscalls are recorded. Rules can match on syscall number, architecture, UID/GID of the calling process, specific argument values, file paths, and other criteria. The rule matching engine in audit_filter_syscall() evaluates the loaded rules against the accumulated audit_context, allowing rules like "log all unlinkat calls by UID 1000 that succeed" without logging the millions of other syscalls that the system processes.

That evaluation happens only at syscall exit, and the point is structural rather than incidental. audit_filter_syscall() consults exactly one list, AUDIT_FILTER_EXIT; the old entry-time list still has a constant, AUDIT_FILTER_ENTRY, but kernel/auditfilter.c now rejects any rule added to it with the message "AUDIT_FILTER_ENTRY is deprecated". An entry-time filter could only ever match on the four arguments and the caller's credentials — the same information seccomp has — whereas by the time the exit filter runs the context holds the pathnames that were actually resolved, the inodes they resolved to, and whether the call succeeded. Deciding late costs work on calls that turn out not to be interesting, and buys the ability to write the rules administrators actually want.

There is still a cheap early exit, but it lives at fork rather than at syscall entry. audit_alloc() runs once per new task, evaluates the AUDIT_FILTER_TASK list, and if the verdict is AUDIT_STATE_DISABLED it clears SYSCALL_WORK_SYSCALL_AUDIT and allocates no context at all — that task will never enter the audit path again for its whole lifetime. Otherwise it allocates a context in one of two states: AUDIT_STATE_BUILD fills the context on every syscall so that a record can be produced if some other part of the kernel asks for one, while AUDIT_STATE_RECORD also emits unconditionally. The distinction is what allows a rule keyed on a filesystem watch to produce a complete syscall record even though no syscall rule matched.

The audit_context structure, allocated per-task by audit_alloc(), accumulates information throughout the syscall's lifetime. As the service routine executes, it may add auxiliary records — file names resolved during pathname lookup, IPC object identifiers, socket addresses — by calling functions like __audit_inode() or audit_log_link_denied(). By the time audit_syscall_exit() runs, the context contains a complete record of what the syscall did, not just what arguments it was called with. This is a fundamental difference from tracepoint-based tracing, which can only see the entry arguments and the exit return value. It is also the reason audit cannot be replaced by a seccomp filter, an eBPF program, or a clever auditctl rule evaluated at entry: the information audit reports does not exist yet when the call begins.

One further wrinkle keeps the subsystem from feeding on itself. Both audit_filter_syscall() and audit_filter_uring() return immediately if auditd_test_task() says the current task is the audit daemon, and __audit_syscall_entry() applies the same test while in AUDIT_STATE_BUILD. Without it, every write auditd performed while draining the queue would generate another record to drain.

Because io_uring executes operations without a system call per operation (Section 9), it needs its own path through the same machinery, and it has one. struct audit_context carries a context discriminant that is either AUDIT_CTX_SYSCALL or AUDIT_CTX_URING, the io_uring path records a uring_op instead of a syscall number, and audit_filter_uring() matches it against a separate rule list, AUDIT_FILTER_URING_EXIT. An administrator who audits openat and does not also write a rule for the corresponding io_uring opcode has a gap in the log, which is a good illustration of how thoroughly io_uring is a second system-call interface rather than an optimization of the first.

Syscall User Dispatch

Syscall User Dispatch (SUD) is a mechanism that runs at the very beginning of the syscall entry pipeline — before ptrace, seccomp, tracepoints, and audit. It is not a tracing or auditing tool in the traditional sense; rather, it allows user space to intercept system calls from specific code regions and handle them without kernel involvement. Its primary use case is running Windows applications under Wine: when a Windows DLL executes a Linux syscall instruction (because it happens to be running on a Linux CPU), SUD can redirect it back to Wine's emulation layer instead of letting it reach the kernel.

SUD is configured per-task via prctl(PR_SET_SYSCALL_USER_DISPATCH, ...), which sets a code range and a pointer to a user-space selector byte. There are two "on" modes and they invert each other. PR_SYS_DISPATCH_EXCLUSIVE_ON names a range that is exempt: a syscall issued from inside it always proceeds, and everything outside it is subject to dispatch. That is the shape Wine wants, since the native loader and libc live in one contiguous region and the emulated Windows code is everywhere else. PR_SYS_DISPATCH_INCLUSIVE_ON names a range that is subject to dispatch, with everything outside it exempt — the shape wanted by a process that has loaded one foreign library and trusts the rest of itself. The kernel implements the second by inverting the range at prctl time (offset += len; len = -len;) so that the single unsigned comparison on the fast path serves both, relying on wrap-around.

On every syscall entry the kernel performs that one comparison, instruction_pointer(regs) - sd->offset < sd->len, and returns immediately if it succeeds. Only if the instruction pointer is in the dispatched region does it read the selector byte, and only if the selector holds SYSCALL_DISPATCH_FILTER_BLOCK does it act. The selector exists so that user space can toggle dispatch on and off with a single store, without a system call — which is essential, because the handler that emulates a dispatched call generally needs to make real system calls itself and would otherwise recurse. A selector value that is neither ALLOW nor BLOCK is treated as corruption and kills the process with an unblockable force_exit_sig(SIGSYS), as is a selector pointer that faults. Note also that access_ok() on the selector is checked once, at prctl time, and that the check untags the address so that a tracer without memory tagging enabled can still set the selector of a tagged tracee.

When the call is blocked, the kernel calls syscall_rollback() to restore the registers the architecture's entry code may have shuffled, then delivers SIGSYS with si_code = SYS_USER_DISPATCH. The siginfo carries si_syscall, si_arch, and si_call_addr; the arguments are not in the siginfo but in the register set of the ucontext passed to the handler, which is also where the handler writes the emulated return value.

There is one unconditional exemption, and it exists to keep the mechanism from trapping itself. arch_syscall_is_vdso_sigreturn() is consulted before the selector is even read, so the signal-return trampoline of Section 5.5 is never dispatched. Without that check a handler could be entered but never left: rt_sigreturn is a system call, it is issued from the vDSO rather than from the exempt code range, and dispatching it would deliver a fresh SIGSYS from inside the SIGSYS handler.

A key property of SUD-intercepted syscalls is that they are invisible to the rest of the tracing pipeline. Because SUD runs first and returns -1L (skip) when it intercepts, the syscall never reaches ptrace, seccomp, tracepoints, or audit. This is by design — the intercepted calls are not "real" Linux syscalls, so recording them in the audit log or exposing them to seccomp would be misleading. The exit side honours the same rule through a different route: syscall_user_dispatch() sets current->syscall_dispatch.on_dispatch before raising the signal, and syscall_exit_work() tests that flag first and returns without running audit or the tracers. The flag is a one-shot; it is cleared by the very test that reads it.

The implementation lives in kernel/entry/syscall_user_dispatch.c and is controlled by the SYSCALL_WORK_SYSCALL_USER_DISPATCH work flag. Because the configuration is per-task state that a checkpoint/restore tool must reproduce exactly, it is also reachable from outside: PTRACE_GET_SYSCALL_USER_DISPATCH_CONFIG and PTRACE_SET_SYSCALL_USER_DISPATCH_CONFIG read and write a struct ptrace_sud_config on a stopped tracee. The getter is lossy, and knowing how is worth more than knowing that it exists. It reports the mode as PR_SYS_DISPATCH_ON — which is defined as PR_SYS_DISPATCH_EXCLUSIVE_ON — because the task holds only the already-inverted range and cannot tell afterwards which mode produced it. Feeding that report straight back to the setter therefore reconstructs an inclusive configuration as an exclusive one over the inverted range, and the exclusive-mode overflow check rejects an inverted range outright, so a checkpoint tool must record the original mode itself rather than rely on the round trip.

Syscall Restart and Signal Interaction

Signals and blocking system calls interact in ways that every serious Unix program eventually encounters. A task sleeping in read(), poll(), nanosleep(), or futex() may receive a signal before the requested work completes. The kernel must then decide: should it return an error to user space, should it transparently restart the interrupted operation, or should it use a more elaborate restart mechanism that preserves intermediate state?

This problem has existed since the earliest days of Unix, and the solution has evolved through several generations of increasingly sophisticated mechanisms. The simplest approach — always returning EINTR — places the entire burden on user-space programmers, who must wrap every blocking call in a retry loop. POSIX improved this with the SA_RESTART signal flag, which tells the kernel to automatically restart certain interrupted calls. But even SA_RESTART is insufficient for operations like nanosleep(), where a simple re-execution would sleep for the full original duration instead of just the remaining time. Linux solves this with the restart_block mechanism, which stores continuation state so that the restarted call can pick up where it left off.

The entire restart mechanism is invisible to well-behaved user-space programs — they either see EINTR or the call completes normally. But understanding the internal machinery is essential for kernel developers, because every blocking syscall must choose the correct restart code, and every architecture must implement the register manipulation that makes transparent restart possible.

It is worth being precise about where in the pipeline this happens, because "signal delivery" is doing a lot of work in the paragraphs above. The restart decision is made by arch_do_signal_or_restart(), which the generic exit loop in kernel/entry/common.c calls when either _TIF_SIGPENDING or _TIF_NOTIFY_SIGNAL is set. That is stage 2 of the exit sequence described in Section 7.1 — after the one-time syscall exit work, so ptrace and audit have already seen the raw -ERESTARTSYS value, and before the final transition to user mode. Two consequences follow from that placement.

The first is that a restart can be triggered with no signal involved at all. _TIF_NOTIFY_SIGNAL is set by task_work_add(…, TWA_SIGNAL), which io_uring and several other subsystems use to force a task out of a sleep in order to run deferred work; the interrupted call then reaches the same switch statement and is restarted with nothing having been delivered. The second is that the whole thing lives inside a while loop that re-reads the thread flags on each iteration, so arch_do_signal_or_restart() can be entered more than once for a single syscall. Both architectures have to make the second and later passes harmless, and Section 8.5 shows that they do it in noticeably different ways.

The Internal Restart Error Codes

When a blocking system call is interrupted by a signal, it does not immediately return -EINTR to user space. Instead, the service routine returns one of four internal error codes defined in include/linux/errno.h. These codes live at 512, 513, 514 and 516, deliberately above the largest POSIX errno, in the same private block as ENOIOCTLCMD and EPROBE_DEFER. The signal delivery code inspects them and translates them into either a visible -EINTR or a transparent restart before control returns to the application.

The header states the contract in two sentences that are easy to skim past and worth reading closely. "To return one of ERESTART* codes, signal_pending() MUST be set" — a service routine that returns -ERESTARTSYS without a pending signal produces a task that returns 512 to user space, because the restart switch is only reached when a signal-related thread flag is set. And "note that ptrace can observe these at syscall exit tracing, but they will never be left for the debugged user process to see" — the codes do escape the kernel, just not to the process that issued the call. A tracer stopped at the syscall-exit stop of Section 7.2 reads the raw -ERESTARTSYS, because that stop runs in syscall_exit_work() before the restart switch runs. Tracer authors who print strace-style output have to translate the value themselves, which is why strace displays the pseudo-errno ERESTARTSYS rather than a number.

The choice of restart code is made by the service routine itself, and it depends on the semantics of the operation. Most interruptible waits — file reads, socket receives, untimed futex waits — use -ERESTARTSYS, which gives user space control via SA_RESTART. In practice most of them never choose it explicitly. prepare_to_wait_event() in kernel/sched/wait.c returns -ERESTARTSYS when signal_pending_state() says the sleep must be abandoned, and ___wait_event() propagates that value out, so every wait_event_interruptible() in the kernel yields -ERESTARTSYS by default. The frequent belief that wait_event_interruptible() returns -EINTR is wrong, and a driver that "fixes" the value by returning -EINTR instead has silently disabled SA_RESTART for its users. The same is true of wait_event_killable(), which uses TASK_KILLABLE so that signal_pending_state() aborts only for a fatal signal, but still reports the abort as -ERESTARTSYS.

The select() and poll() family use -ERESTARTNOHAND, and the comment above core_sys_select() in fs/select.c records the real reason, which is not the one usually given. POSIX permits but does not require the EINTR; what settled the matter was compatibility. "We can actually return ERESTARTSYS instead of EINTR, but I'd like to be certain this leads to no problems… Update: ERESTARTSYS breaks at least the xview clock binary, so I'm trying ERESTARTNOHAND which restart only when you want to." The canonical user of the code is not select() at all but sigsuspend(), whose entire purpose is to wait until a handler runs: restarting it after the handler would defeat the call, and returning EINTR when no handler ran would defeat it equally, so it needs precisely the "restart if and only if no handler ran" semantics.

-ERESTARTNOINTR is the rarest of the four and its users share a shape: the syscall has done no user-visible work yet, so replaying it is not merely permitted but is the only correct answer. copy_process() checks task_sigpending() before allocating anything and returns -ERESTARTNOINTR if a signal is already pending, so an interrupted fork() is simply retried. prepare_bprm_creds() returns it when the interruptible acquisition of cred_guard_mutex fails, since no part of the execve() has happened. futex_lock_pi() converts a late -EINTR into it because a PI lock acquisition may already have altered the futex word and cannot be reported as a failure. And madvise() uses it internally, up to MAX_MADVISE_GUARD_RETRIES times, when installing guard pages races: the comment notes that it "would not be correct to repeat the operation in aggregate, and would be surprising to the user".

close() is the instructive counter-example, and it points the other way from what one might expect. fs/open.c does not return a restart code; it converts every one of the four into -EINTR, with the comment "can't restart close syscall because file table entry was cleared". By the time anything in close() can block, the descriptor has already been removed from the table, so a restart would re-enter close() on a number that now refers to nothing — or, worse, to a descriptor some other thread has since opened. This is the general rule the four codes exist to express: a call may be restarted only if re-executing it from the beginning is indistinguishable from having executed it once.

SA_RESTART and Signal Disposition

The SA_RESTART flag in struct sigaction is the user-space knob that controls whether -ERESTARTSYS becomes a transparent restart or a visible -EINTR. When a process installs a signal handler with sigaction() and includes SA_RESTART in the flags, it is telling the kernel: "after my handler runs, please restart any interrupted system call rather than returning an error."

The interaction is straightforward but easy to get wrong. When signal delivery encounters a syscall that returned -ERESTARTSYS, it checks the signal handler's flags. If SA_RESTART is set, the kernel restores the original syscall arguments and rewinds the instruction pointer so that the syscall instruction will re-execute after the signal handler returns. If SA_RESTART is not set, the kernel replaces the return value with -EINTR and lets the application see the error.

The other restart codes bypass SA_RESTART entirely. -ERESTARTNOINTR always restarts regardless of the flag. -ERESTARTNOHAND restarts only when no user handler runs at all — if a handler does run, it becomes -EINTR even with SA_RESTART. -ERESTART_RESTARTBLOCK follows the same restart-vs-EINTR logic as -ERESTARTNOHAND, but uses the restart_syscall() mechanism instead of replaying the original instruction.

Note what the "no handler runs" case actually covers, because it is broader than it sounds. The kernel reaches the restart switch whenever a signal-related thread flag was set and get_signal() declined to deliver a handler. That includes a signal whose disposition is SIG_IGN, a signal that only stopped and continued the process, a SIGCHLD the parent is not catching, and — as Section 8 noted — a _TIF_NOTIFY_SIGNAL wake-up with no signal at all. In every one of those cases an -ERESTARTNOHAND call is restarted, which is exactly why sigsuspend() can use the code to mean "wait until a handler runs" without ever returning early for an unrelated wake-up.

A subtle consequence is that the same signal can cause different behavior depending on which syscall it interrupts. A SIGALRM handler with SA_RESTART will transparently restart an interrupted read() (which uses -ERESTARTSYS) but will still cause select() to return EINTR (because select() uses -ERESTARTNOHAND). This surprises many programmers, and the surprise is not confined to select(): any call that uses the restart block is equally immune to SA_RESTART once a handler runs.

The sharpest illustration is a single syscall that changes category depending on its arguments. futex_wait() returns a bare -ERESTARTSYS when the caller passed no timeout, so FUTEX_WAIT with a null timeout honours SA_RESTART. When a timeout was passed the same function stores its state in the restart block and returns -ERESTART_RESTARTBLOCK instead, because a blind replay would restart the full timeout. The same call, interrupted by the same signal, with the same handler installed, is therefore restarted in one case and returns EINTR in the other, purely because the caller supplied a deadline. That is not a defect: honouring SA_RESTART for a timed wait would require re-arming a timer the register file no longer describes, and the restart block is the only place that information survives.

The restart_block Mechanism

Simple syscall restart works by rewinding the instruction pointer and restoring the original arguments: the CPU re-executes the same syscall instruction with the same register values, and the service routine runs again from the beginning. This works perfectly for calls like read() where re-execution is semantically correct. But it fails for calls where the restarted execution needs different arguments than the original.

The classic example is nanosleep(). If a process calls nanosleep(&{5, 0}, ...) to sleep for 5 seconds and gets interrupted after 3 seconds by a signal, simply re-executing the original call would sleep for another 5 seconds — a total of 8 instead of the requested 5. The correct behavior is to sleep for only the remaining 2 seconds. But the original syscall arguments in the registers say "5 seconds," and the kernel cannot change them without a mechanism to store the updated state.

The restart_block mechanism, defined in include/linux/restart_block.h, solves this problem. Each task has a restart_block embedded in its task_struct. When a syscall needs a stateful restart, it stores continuation data in this structure and returns -ERESTART_RESTARTBLOCK. If the kernel decides to restart the call (rather than returning EINTR), it does not replay the original syscall instruction. Instead, it rewrites the syscall number to __NR_restart_syscall and lets the process re-enter the kernel through that tiny system call.

Two things about that structure are worth stating before the excerpt, because they explain choices that otherwise look arbitrary. The union has exactly three arms, and it always has: the restart block is not an extension point. Adding a user means adding a member to a union embedded in every task_struct on the system, so the mechanism is reserved for the handful of calls whose semantics genuinely cannot survive a replay, and everything else uses one of the other three codes. And the block is per-task, not per-call, so it holds the state of at most one outstanding restart — which is safe only because a task can be inside at most one system call at a time, and is the reason each restart handler disarms the block before doing anything else. 


/* include/linux/restart_block.h */

The restart_syscall() service routine is trivial: it calls the function pointer stored in the restart block. That function — for example, hrtimer_nanosleep_restart() for nanosleep or futex_wait_restart() for futex — reads the saved continuation state and performs the remaining work. The pattern is always the same: the original syscall fills in the union fields with the state needed to resume and then calls set_restart_fn(restart, handler).

That helper is smaller than it looks and does one thing the caller might not expect. It is defined in include/linux/thread_info.h, it stores the function pointer, it invokes the architecture hook arch_set_restart_data(), and then it returns -ERESTART_RESTARTBLOCK. Callers therefore write return set_restart_fn(restart, handler); rather than setting up and returning separately, which is why the restart code never appears literally in most of the call sites that use it. The architecture hook is a no-op almost everywhere; x86 defines it to capture current_thread_info()->status into arch_data, for a reason Section 8.5 comes back to.

The complementary half of the protocol is disarmament, and every user of the block observes it. do_no_restart_syscall() in kernel/signal.c is a two-line function that returns -EINTR, and it is what the block is set to whenever no restart is pending. nanosleep() installs it at the top of the call, before doing anything that could sleep, so that a restart block left over from an earlier syscall can never be reached. futex_wait_restart() assigns it to restart->fn as its first statement, so a restart handler that is somehow re-entered a second time fails cleanly instead of repeating. The "stale function pointer" that a careless implementation might invoke is therefore not an unbounded hazard: the worst case is a spurious -EINTR.

Temporary Signal Masks and TIF_RESTORE_SIGMASK

A family of system calls — pselect(), ppoll(), epoll_pwait(), io_pgetevents() and sigsuspend() — exists to close a race that cannot be closed in user space. An application that wants to wait for either a descriptor or a signal must unblock the signal and then wait; if it does those as two separate operations, a signal arriving in between is lost, and the wait blocks forever. The p-suffixed calls take a signal mask as an argument and install it atomically with respect to the wait, which removes the window. The mechanism they use to do it interacts directly with the restart machinery, and it is the reason for the two absences noted at the end of the previous subsection.

The mask is not passed down into the wait. set_user_sigmask() in kernel/signal.c copies the caller's real mask into current->saved_sigmask, installs the temporary mask with set_current_blocked(), and sets the TIF_RESTORE_SIGMASK thread flag. From that point the task is running with a mask its own user-space code did not install, and everything that follows exists to make sure the original one comes back. 


/* kernel/signal.c */
int set_user_sigmask(const sigset_t __user *umask, size_t sigsetsize)
{
    sigset_t kmask;

    if (!umask)
        return 0;
    if (sigsetsize != sizeof(sigset_t))
        return -EINVAL;
    if (copy_from_user(&kmask, umask, sizeof(sigset_t)))
        return -EFAULT;

    set_restore_sigmask();
    current->saved_sigmask = current->blocked;
    set_current_blocked(&kmask);

    return 0;
}

There are two exits from that state, and the kernel takes exactly one of them. If the wait finishes without a signal, restore_saved_sigmask() copies the saved mask back and clears the flag; both x86_64 and ARM64 call it at the end of arch_do_signal_or_restart() when get_signal() reported nothing to deliver. If a signal is being delivered, the mask must not be restored yet, because the signal frame has to record the mask that sigreturn will reinstate — and that is the caller's original mask, not the temporary one. sigmask_to_save() in include/linux/sched/signal.h encodes exactly this: it returns &current->saved_sigmask when the flag is set, and clears the flag, so the frame built by the architecture code carries the right value and sigreturn does the restoration for free.

set_restore_sigmask() also sets TIF_SIGPENDING, and the comment in include/linux/thread_info.h explains why: it is there "to ensure that the arch signal code always gets run when TIF_RESTORE_SIGMASK is set". Without it a task could return to user space with the temporary mask still installed, because nothing else would force the exit loop to call into the signal code. This is the same coupling that makes _TIF_NOTIFY_SIGNAL able to trigger a restart: the flag that means "there is signal-related work" is not the same thing as "there is a signal".

The decision point for an interrupted wait is restore_saved_sigmask_unless(), which takes a single boolean meaning "this call is about to be interrupted". poll_select_finish() in fs/select.c calls it with ret == -ERESTARTNOHAND, so the temporary mask is deliberately left installed precisely when the call is going to be either restarted or turned into EINTR. If the call is restarted, it re-executes from the beginning with the temporary mask still in force and re-derives everything it needs; if a handler runs instead, the handler executes under the temporary mask, which is what the caller asked for, and sigreturn puts the original mask back. 


/* include/linux/sched/signal.h */
static inline void restore_saved_sigmask_unless(bool interrupted)
{
    if (interrupted)
        WARN_ON(!signal_pending(current));
    else
        restore_saved_sigmask();
}

This is why ppoll() cannot use the restart block while poll() can. A restart-block restart re-enters the kernel through restart_syscall(), which knows nothing about signal masks; the temporary mask would either be lost or left installed with no record of what to restore. Re-executing the original ppoll() instruction, by contrast, calls set_user_sigmask() again from the caller's real mask and reproduces the correct state exactly. The price is that ppoll(), like select(), restarts with its original relative timeout rather than the remaining one — an accepted trade, since a call whose entire purpose is to wait for a signal is rarely restarted in practice.

sigsuspend() is the mechanism reduced to its minimum. It saves the mask, installs the caller's, sleeps in TASK_INTERRUPTIBLE, and returns -ERESTARTNOHAND unconditionally. If a handler runs, the code becomes EINTR and the frame restores the original mask; if no handler runs, the code restarts the call, which re-installs the same temporary mask and sleeps again. pause() is the same shape without the mask. Neither can be expressed with SA_RESTART semantics or with a restart block, which is precisely why -ERESTARTNOHAND exists.

Architecture-Specific Restart Paths

The policy for choosing between restart and EINTR is architecture-independent, but the mechanism for actually restarting a syscall is deeply architecture-specific. The kernel must manipulate the saved register frame so that when control returns to user space, the CPU re-executes the syscall instruction (or executes restart_syscall() instead). Each architecture has different registers, different instruction sizes, and different calling conventions, so the register manipulation code differs.

The two architectures this book follows illustrate the point unusually well, because they do not merely differ in register names. They order the work differently: x86_64 waits until it knows whether a handler will run and only then touches the register frame, while ARM64 rewinds the frame first, before get_signal() is called, and undoes the rewind afterwards if it turns out to have been wrong. Each order buys something the other does not, and neither is a historical accident.

On x86_64, the restart logic is split across two switch statements in arch/x86/kernel/signal.c. The first is in handle_signal() and runs only when a handler is about to be invoked; it is guarded by syscall_get_nr(current, regs) != -1, so a signal that interrupted ordinary user code never reaches it. The handler inspects the code and the signal's SA_RESTART flag. For a simple restart, it restores RAX from orig_ax (which holds the original syscall number, preserved across the entire syscall) and subtracts 2 from RIP — the size of the x86_64 syscall instruction — so that the instruction re-executes after the signal handler returns. For -ERESTART_RESTARTBLOCK, it writes __NR_restart_syscall into RAX and rewinds RIP by 2. 


/* arch/x86/kernel/signal.c — restart handling during signal delivery */
switch (syscall_get_error(current, regs)) {
case -ERESTART_RESTARTBLOCK:
case -ERESTARTNOHAND:
    regs->ax = -EINTR;  /* default: return EINTR */
    break;
case -ERESTARTSYS:
    if (!(ksig->ka.sa.sa_flags & SA_RESTART)) {
        regs->ax = -EINTR;
        break;
    }
    fallthrough;
case -ERESTARTNOINTR:
    regs->ax = regs->orig_ax;  /* restore syscall number */
    regs->ip -= 2;              /* rewind to syscall insn */
    break;
}

The second switch is in arch_do_signal_or_restart() itself and runs when get_signal() returns false — no handler will be invoked, because the signal was ignored, was consumed by a stop, or was never a signal to begin with. Here all three of -ERESTARTNOHAND, -ERESTARTSYS and -ERESTARTNOINTR collapse to the same action, since with no handler running the distinction between them is meaningless: restore RAX from orig_ax and rewind RIP. -ERESTART_RESTARTBLOCK takes the extra step of choosing a syscall number. 


/* arch/x86/kernel/signal.c - no handler will run */
    if (syscall_get_nr(current, regs) != -1) {
        switch (syscall_get_error(current, regs)) {
        case -ERESTARTNOHAND:
        case -ERESTARTSYS:
        case -ERESTARTNOINTR:
            regs->ax = regs->orig_ax;
            regs->ip -= 2;
            break;

        case -ERESTART_RESTARTBLOCK:
            regs->ax = get_nr_restart_syscall(regs);
            regs->ip -= 2;
            break;
        }
    }

    /* If there is no signal to deliver, we just put the saved sigmask back. */
    restore_saved_sigmask();

get_nr_restart_syscall() is where the otherwise mysterious arch_data field earns its place in struct restart_block. A 32-bit process running under CONFIG_IA32_EMULATION must re-enter through the ia32 restart entry, whose number is 0, not through the 64-bit one, whose number is 219; an x32 process must keep __X32_SYSCALL_BIT set so the number is dispatched against the x32 table. The kernel cannot decide this at restart time, because by then it is running in a context that no longer distinguishes them reliably. So arch_set_restart_data(), called from set_restart_fn() at the moment the block is armed, snapshots current_thread_info()->status — which carries TS_COMPAT — into arch_data, and get_nr_restart_syscall() reads it back. 


/* arch/x86/include/asm/thread_info.h */
#ifdef CONFIG_COMPAT
#define arch_set_restart_data(restart)  \
        do { restart->arch_data = current_thread_info()->status; } while (0)
#endif

/* arch/x86/kernel/signal.c */
static unsigned long get_nr_restart_syscall(const struct pt_regs *regs)
{
#ifdef CONFIG_IA32_EMULATION
    if (current->restart_block.arch_data & TS_COMPAT)
        return __NR_ia32_restart_syscall;
#endif
#ifdef CONFIG_X86_X32_ABI
    return __NR_restart_syscall | (regs->orig_ax & __X32_SYSCALL_BIT);
#else
    return __NR_restart_syscall;
#endif
}

Note also that x86 is protected against a second pass through the exit loop by the shape of its own switches rather than by an explicit flag. Once RAX holds either orig_ax or -EINTR, it no longer matches any case, so re-entering arch_do_signal_or_restart() is a no-op.

ARM64 reaches the same outcomes by the opposite route. arch_do_signal_or_restart() in arch/arm64/kernel/signal.c records the return value and computes restart_addr as PC minus the size of the instruction that entered the kernel — 4 bytes for an AArch64 svc, or 2 bytes in AArch32 Thumb mode — and then rewinds the frame for all four restart codes unconditionally, with no reference to SA_RESTART and before get_signal() has been called. It also calls forget_syscall(), which sets regs->syscallno to NO_SYSCALL so that a second pass through the exit loop sees no syscall in progress and skips the block entirely — the explicit equivalent of the implicit protection x86 gets from its switch conditions. 


/* arch/arm64/kernel/signal.c */
    if (syscall) {
        continue_addr = regs->pc;
        restart_addr = continue_addr - (compat_thumb_mode(regs) ? 2 : 4);
        retval = regs->regs[0];

        /* Avoid additional syscall restarting via ret_to_user. */
        forget_syscall(regs);

        /*
         * Prepare for system call restart. We do this here so that a
         * debugger will see the already changed PC.
         */
        switch (retval) {
        case -ERESTARTNOHAND:
        case -ERESTARTSYS:
        case -ERESTARTNOINTR:
        case -ERESTART_RESTARTBLOCK:
            regs->regs[0] = regs->orig_x0;
            regs->pc = restart_addr;
            break;
        }
    }

The comment gives the motive: "we do this here so that a debugger will see the already changed PC". get_signal() can enter a ptrace signal-delivery stop, and a tracer examining the frame at that stop should see the syscall about to be replayed, not the instruction after it. The cost of showing the tracer the rewound frame is that the rewind may have been premature, so the decision has to be revisited once get_signal() returns. 


/* arch/arm64/kernel/signal.c - continued */
    if (get_signal(&ksig)) {
        int ret;

        /*
         * Depending on the signal settings, we may need to revert the
         * decision to restart the system call, but skip this if a
         * debugger has chosen to restart at a different PC.
         */
        if (regs->pc == restart_addr &&
            (retval == -ERESTARTNOHAND ||
             retval == -ERESTART_RESTARTBLOCK ||
             (retval == -ERESTARTSYS &&
              !(ksig.ka.sa.sa_flags & SA_RESTART)))) {
            syscall_set_return_value(current, regs, -EINTR, 0);
            regs->pc = continue_addr;
        }

        handle_signal(&ksig, regs);
        return;
    }

    /*
     * Handle restarting a different system call. As above, if a debugger
     * has chosen to restart at a different PC, ignore the restart.
     */
    if (syscall && regs->pc == restart_addr) {
        if (retval == -ERESTART_RESTARTBLOCK)
            setup_restart_syscall(regs);
        user_rewind_single_step(current);
    }

    restore_saved_sigmask();

The regs->pc == restart_addr guard, which appears in both places, is the substantive difference between the two architectures. A tracer stopped inside get_signal() may have written a new PC using PTRACE_POKEUSER or PTRACE_SETREGSET, and ARM64 treats that as authoritative: if the program counter is no longer the one the kernel rewound it to, the kernel neither reverts the rewind nor rewrites the syscall number, and the tracer's choice stands. x86_64 has no equivalent check, because it never rewound the frame before the stop and therefore has nothing to detect a conflict against. The claim that the two architectures run the same state machine is not accurate; they run the same policy through materially different mechanisms, and the ptrace interaction is where the difference is visible.

setup_restart_syscall() also carries a compat wrinkle of its own, matching the one get_nr_restart_syscall() handles on x86. For a native AArch64 task it writes __NR_restart_syscall into X8, the AArch64 syscall number register. For an AArch32 task it defers to compat_setup_restart_syscall() in arch/arm64/kernel/signal32.c, which writes __NR_compat32_restart_syscall into X7 — because the AArch32 calling convention passes the syscall number in R7, and the compat number differs from the native one. 


/* arch/arm64/kernel/signal.c */
static void setup_restart_syscall(struct pt_regs *regs)
{
    if (is_compat_task())
        compat_setup_restart_syscall(regs);
    else
        regs->regs[8] = __NR_restart_syscall;
}

/* arch/arm64/kernel/signal32.c */
void compat_setup_restart_syscall(struct pt_regs *regs)
{
    regs->regs[7] = __NR_compat32_restart_syscall;
}

From user space, all of this machinery is usually invisible. Blocking syscalls either complete normally or return EINTR, and well-written applications handle both cases. But understanding the internal restart mechanism matters for anyone writing or debugging kernel code, because choosing the wrong restart code causes bugs that are hard to attribute. Returning -EINTR where -ERESTARTSYS belonged silently disables SA_RESTART for every user of the interface; returning -ERESTARTNOINTR from a path that has already produced a visible effect makes that effect happen twice; and returning any restart code without signal_pending() set leaks the number 512 to user space as an errno nobody can interpret.

io_uring — Beyond Traditional System Calls

The traditional system call model requires one privilege transition per operation: every read(), write(), accept(), or poll() crosses the user-kernel boundary, saves registers, runs the entry pipeline, dispatches the service routine, and returns. For most applications this overhead is negligible — a few hundred nanoseconds per call. But for high-performance I/O workloads — database engines issuing millions of random reads per second, web servers handling tens of thousands of concurrent connections, or storage systems saturating NVMe devices — the aggregate cost of boundary crossings becomes a first-order bottleneck.

io_uring, introduced in Linux 5.1 and substantially expanded in every release since, attacks this problem structurally. Instead of one syscall per operation, io_uring lets user space batch many operations into a shared-memory submission queue and reap their results from a shared-memory completion queue. A single io_uring_enter() call can submit dozens or hundreds of requests at once. In the most aggressive mode (SQPOLL), the kernel polls the submission queue autonomously, and the steady-state hot path involves zero system calls.

io_uring is not a replacement for the traditional syscall interface — simple programs that perform occasional I/O have no reason to use it. But for workloads where throughput is limited by syscall overhead, it represents the most significant evolution of the Linux I/O interface since the introduction of epoll. By Linux 7.0.12 the opcode enumeration runs from IORING_OP_NOP to IORING_OP_URING_CMD128, 65 operations in all, covering file I/O, networking, timers, futexes, file-system operations such as openat2 and statx, and a device passthrough channel in IORING_OP_URING_CMD.

The whole of that surface is reached through three system calls: io_uring_setup() at 425, io_uring_enter() at 426 and io_uring_register() at 427 on x86_64, with the same three numbers on ARM64 because they were added after the shared table described in Section 1. Everything else — which operation runs, on which file, with which arguments — is encoded in shared memory rather than in registers. This is a structural change, not merely a performance one, and Section 9.2 examines the consequence that follows most directly from it: none of the mechanisms Sections 6 and 7 described operate on an SQE, because from their point of view the process issued io_uring_enter() and nothing else.

Chapter 24 is devoted to io_uring and follows a request through the rings, the worker pool, registered resources, and multi-shot and zero-copy completion. This section looks at io_uring only from where this chapter stands, the system-call boundary: which three calls carry it, what they do, and what the rest of the system-call machinery can no longer see once the description of the work has moved into memory.

Three System Calls and Two Rings

io_uring_setup(entries, params) (io_uring/io_uring.c) creates an io_uring instance and returns a file descriptor for it. The application then maps the instance's memory into its own address space with mmap() on that descriptor, using fixed offsets to select each region: IORING_OFF_SQ_RING for the submission-queue ring, IORING_OFF_CQ_RING for the completion-queue ring, and IORING_OFF_SQES for the array of submission-queue entries (SQEs). With IORING_SETUP_NO_MMAP the application supplies that memory instead and the kernel pins it. Either way, both sides now share two single-producer, single-consumer rings, each with a head index that the consumer advances and a tail index that the producer advances.

To issue work, the application fills SQEs—an opcode, a file descriptor, a buffer address, an offset, a length, and a user_data tag—and advances the submission tail. io_uring_enter(fd, to_submit, min_complete, flags, argp, argsz) then does up to two jobs in one crossing: it consumes up to to_submit entries, and, if IORING_ENTER_GETEVENTS is set, it sleeps until at least min_complete completions are present. Each completion is a completion-queue entry (CQE) carrying the original user_data and a result that has the same meaning as the return value of the equivalent system call: a byte count or a negative errno. The application reads CQEs and advances the completion head without entering the kernel at all. io_uring_register(fd, opcode, arg, nr_args) (io_uring/register.c) is the slow-path control call: it pre-registers files and buffers so that per-request lookups and page pinning disappear, attaches an eventfd, and installs the restrictions and filters described below.

With IORING_SETUP_SQPOLL even io_uring_enter() leaves the steady state. A kernel thread polls the submission ring and issues whatever it finds, so an application that keeps the thread busy performs I/O with no system call at all. When the thread has been idle for its configured period it sleeps and sets IORING_SQ_NEED_WAKEUP in the shared ring flags, and the application's next io_uring_enter() with IORING_ENTER_SQ_WAKEUP restarts it. What the System-Call Layer No Longer Sees

Section 6 described seccomp-BPF as the kernel's general answer to “let this process make only these system calls”, and Section 7 described how audit and tracing observe the same choke point. Every one of those mechanisms is attached to the syscall entry pipeline, and every one of them keys off the syscall number. io_uring moves the description of the work out of that pipeline and into shared memory, and the consequence is exact: a seccomp filter that permits io_uring_enter permits every operation io_uring can perform. A sandbox that painstakingly denies openat has not denied IORING_OP_OPENAT2; a sandbox that denies socket has not denied IORING_OP_SOCKET.

This is not an oversight in seccomp, and it is not fixable there. A seccomp filter is invoked once per system call, with the general-purpose registers as its only input, and it is forbidden from dereferencing pointers precisely because the memory behind them can change after the check (Section 6.3; Section 6.6 shows the same race defeating the user-space notifier). An SQE is exactly such a pointer target, sitting in memory another thread of the same process can rewrite. Filtering io_uring from seccomp would require doing the one thing seccomp is designed not to do. The other observers lose sight in the same way: the per-syscall tracepoints and ptrace stops fire once for io_uring_enter() however many operations it carries, strace shows one call where a thousand operations occurred, and audit needs the separate io_uring path of Section 7 to record operations at all.

The controls that do work are therefore io_uring's own, and Chapter 24 (§8) describes them in full. Two are blunt and process-wide: a seccomp filter can deny io_uring_setup itself, and the kernel.io_uring_disabled sysctl can refuse new rings to everyone (2) or to everyone outside the group named by kernel.io_uring_group (1). Two are fine-grained and belong to the application: IORING_REGISTER_RESTRICTIONS installs allow-lists of opcodes, registration operations, and SQE flags on a ring created with IORING_SETUP_R_DISABLED, and IORING_REGISTER_BPF_FILTER, new in 7.0, attaches classic-BPF programs to individual opcodes. The filter mechanism is deliberately modelled on seccomp: the program is loaded through bpf_prog_create_from_user() with its own validator, io_uring_check_cbpf_filter(), which confines every load to the fields of struct io_uring_bpf_ctx; filters stack and can only narrow; and installing one requires no_new_privs or CAP_SYS_ADMIN. Unlike seccomp, a filter sees already-validated arguments rather than raw registers—the address family of a socket, the resolve flags of an openat2—and its only verdicts are allow and -EACCES. Both controls can also be registered with no ring at all (a file descriptor of −1), in which case they attach to the task, are copied into every ring it later creates, and are inherited across fork() and execve(), which is what makes them a sandbox rather than a per-ring convenience.

For the purposes of this chapter, though, the more interesting observation is what io_uring reveals about the rest of it. Almost every mechanism the preceding sections described turns out to have been attached to a particular place — the entry pipeline — rather than to the concept of "a request to the kernel". Move the request description out of registers and into shared memory, and seccomp stops filtering, the per-syscall tracepoints stop firing, audit needs a separate filter list and a per-opcode opt-out, strace shows one call where a thousand operations occurred, and the SYSCALL_DEFINE wrapper machinery of Section 2.3 has no role at all. What survives the move is the smaller, harder set: array_index_nospec() still guards the dispatch index, READ_ONCE() still guards against a racing writer, credentials still have to be bound explicitly to the work, and the parameter-validation discipline of Section 4 reappears in io_init_req() almost unchanged. Those are the parts of the system-call story that were never really about system calls.

Kernel Wrapper Routines

System call code is not only for user space. The kernel itself frequently needs to perform the same operations that system calls expose — opening files, reading data, mapping memory, mounting filesystems — from within kernel context. But calling a system call from inside the kernel is not straightforward: the SYSCALL_DEFINE* wrappers expect to be invoked from the entry pipeline, with a saved register frame, tracing hooks, and user-space pointer semantics. An in-kernel caller has none of these.

The obstacle is more concrete than "not straightforward", and it is worth stating precisely, because it is the reason every other mechanism in this section exists. On both x86_64 and ARM64 — any architecture that sets CONFIG_ARCH_HAS_SYSCALL_WRAPPER — the symbol the syscall table points at does not have the signature the system call appears to have. Section 2.3 showed why: SYSCALL_DEFINE3(read, unsigned int, fd, char __user *, buf, size_t, count) generates __x64_sys_read(const struct pt_regs *regs), which pulls the three arguments out of the saved register frame. There is no C function named sys_read that takes a file descriptor and a buffer. In-kernel code cannot call the system call implementation even if it wants to; the compiler would reject it, and on an architecture where the alias happens to exist it would silently reinterpret the first argument as a pt_regs pointer. This is a deliberate and rather elegant piece of design: the ABI entry point is made structurally uncallable from C, so the question "should I call sys_read() from the kernel?" never arises.

Linux therefore uses a layered design that separates the ABI-facing wrapper from the core implementation. The SYSCALL_DEFINE* macro generates the outermost entry point — the function that the syscall dispatch table points to. Below it sit one or more helper functions (ksys_*, do_sys_*) that contain the actual logic but accept ordinary C arguments directly. In-kernel callers invoke these helpers rather than the ABI wrapper, avoiding the entry pipeline overhead and the register-frame decoding. This design also means that the native 64-bit syscall, the 32-bit compat wrapper, and any in-kernel caller all share the same core implementation, eliminating code duplication and the bugs that come with it.

One caution before going further. "Kernel-resident arguments" is not what distinguishes a ksys_* helper from its system call — ksys_read() still takes a char __user *, and calling it with a kernel buffer is exactly as wrong as calling read() with one. The layering solves the calling convention problem, not the address-space problem. Those are separate concerns with separate solutions, and conflating them is the mistake that set_fs(KERNEL_DS) institutionalized for two decades. The address-space problem is solved by a different family — kernel_read(), kernel_write(), getname_kernel(), the init_* helpers — covered in Sections 10.3 through 10.5.

The ksys_* and do_sys_* Helpers

The naming convention in the kernel reflects call depth and abstraction level. sys_* (or the architecture-generated equivalent) is the ABI-facing entry point — the function that the syscall table dispatches to. ksys_* functions sit one layer below: they implement the full service logic, including user-pointer handling, but are callable from the ABI wrapper, from compat wrappers, and from any in-kernel code that genuinely has a user pointer to work with. do_sys_* functions sit even lower and typically work with already-decoded kernel structures or VFS objects rather than raw user pointers. The declarations that other subsystems are meant to use live together in include/linux/syscalls.h, under a comment that introduces them as "the ksys_xyzyyz() functions prototyped below"; there are roughly forty of them, which is a small fraction of the syscall table and a fair indication that this is an escape hatch rather than a general architecture.

A ksys_* helper that no other file needs is simply static, and several are: ksys_dup3() in fs/file.c and ksys_umount() in fs/namespace.c keep the naming convention as documentation of their role while remaining private to their translation unit. The convention, in other words, describes what a function is rather than who is allowed to call it. 


/* fs/read_write.c — the read() layering */
ssize_t ksys_read(unsigned int fd, char __user *buf, size_t count)
{
    CLASS(fd_pos, f)(fd);
    ssize_t ret = -EBADF;

    if (!fd_empty(f)) {
        loff_t pos, *ppos = file_ppos(fd_file(f));
        if (ppos) {
            pos = *ppos;
            ppos = &pos;
        }
        ret = vfs_read(fd_file(f), buf, count, ppos);
        if (ret >= 0 && ppos)
            fd_file(f)->f_pos = pos;
    }
    return ret;
}

SYSCALL_DEFINE3(read, unsigned int, fd, char __user *, buf, size_t, count)
{
    return ksys_read(fd, buf, count);
}

That body is worth reading closely, because it does not look like the read() implementation in any older kernel text and the difference is not cosmetic. There is no fdget() call and no matching fdput(), no goto out and no error label. CLASS(fd_pos, f)(fd) declares f as a scope-guarded object built by fdget_pos(fd) and destroyed by fdput_pos(f) when control leaves the block, by any path. The class is declared once, in include/linux/file.h, as DEFINE_CLASS(fd_pos, struct fd, fdput_pos(_T), fdget_pos(fd), int fd), alongside fd and fd_raw variants and a DEFINE_FREE(fput, ...) for bare file pointers.

This is the scope-based cleanup infrastructure of include/linux/cleanup.h, built on the compiler's __attribute__((cleanup)), and by Linux 7.0.12 it has spread through exactly the files this section is about — fs/open.c uses CLASS() thirteen times, fs/read_write.c fourteen. Its significance for the present chapter is that it removes an entire category of syscall bug. The classic failure mode of a system call implementation was an early return on a validation error that forgot to drop a reference taken a few lines earlier, and every added error path was a fresh opportunity to reintroduce it. Under this idiom the release is attached to the declaration, so there is no error path to forget. Notice too that ksys_read() now has a single return statement and expresses failure as an initial value of ret — a shape that is only comfortable once cleanup is automatic.

The ksys_* pattern is widespread. ksys_write() in fs/read_write.c handles all write logic shared by write() and its compat variant. ksys_mmap_pgoff() in mm/mmap.c implements the core mmap logic shared by the native mmap syscall, the old-style mmap compat path, and architecture-specific wrappers including ARM64's aarch32_mmap2. ksys_unshare() in kernel/fork.c is called by both the unshare() syscall and internal kernel code like devtmpfs, which needs to unshare its mount namespace during initialization. ksys_sync_helper() in kernel/power/main.c is the suspend path's entry to the same work sync() does, and is stubbed out entirely when CONFIG_PM_SLEEP is off.

ksys_ftruncate() deserves a closer look, because it shows the second thing a ksys_* helper is for. It carries a parameter its system call does not have: 


/* fs/open.c */
int ksys_ftruncate(unsigned int fd, loff_t length, unsigned int flags)
{
    if (length < 0)
        return -EINVAL;
    CLASS(fd, f)(fd);
    if (fd_empty(f))
        return -EBADF;

    return do_ftruncate(fd_file(f), length, !(flags & FTRUNCATE_LFS));
}

SYSCALL_DEFINE2(ftruncate, unsigned int, fd, off_t, length)
{
    return ksys_ftruncate(fd, length, 0);
}

FTRUNCATE_LFS, defined in include/linux/syscalls.h as bit 0, means "allow truncating beyond 32 bits." Plain ftruncate() passes zero and therefore inherits the small-file limit; ftruncate64() and the compat ftruncate64 pass the flag. The helper's signature is thus not merely the syscall's signature with the wrapper removed — it is the union of what all its callers need, with the differences between ABI variants hoisted into an explicit parameter. That is the general shape of a good ksys_* helper, and it is why the pattern eliminates duplication rather than just relocating it.

The do_sys_* helpers go a step further. do_sys_openat2() in fs/open.c accepts an already-decoded struct open_how and performs the actual file open, shared by open(), openat(), openat2(), and all their compat variants. do_sys_poll() in fs/select.c implements the common poll logic shared by poll(), ppoll() and both of their compat forms — the select family has its own parallel pair, core_sys_select() and do_select(). do_sys_truncate() performs pathname-based truncation shared by truncate() and truncate64().

The distinction between the two prefixes is real but softer than the naming suggests, and it is better understood as a difference in what has already been decided than in argument types. ksys_read() still takes a char __user *; what makes it a ksys_ is that the calling convention has been resolved. do_sys_openat2() takes a fully built struct open_how; what makes it a do_sys_ is that the three different ways of arriving at those flags — open's implicit defaults, openat's dfd, openat2's explicit structure — have collapsed into one representation. Neither prefix is a promise about address spaces, and the kernel is not perfectly consistent about either: do_ftruncate() in fs/open.c plays the same role without the sys infix at all. 


/* fs/open.c — do_sys_openat2 is the real implementation */
static int do_sys_openat2(int dfd, const char __user *filename,
                          struct open_how *how)
{
    struct open_flags op;
    int err = build_open_flags(how, &op);
    if (unlikely(err))
        return err;
    CLASS(filename, name)(filename);
    return FD_ADD(how->flags, do_file_open(dfd, name, &op));
}

/* All open-family syscalls funnel through do_sys_openat2 */

                int, flags, umode_t, mode) { ... }
SYSCALL_DEFINE4(openat, int, dfd, ...) { ... }
SYSCALL_DEFINE4(openat2, int, dfd, ...) { ... }

Compat Syscall Wrappers

When a 32-bit application runs on a 64-bit kernel — ia32 on x86_64, or AArch32 on ARM64 — the kernel must translate between the 32-bit and 64-bit ABI before reaching the core implementation. Arguments may need sign-extension or zero-extension, 64-bit values that were split across two 32-bit registers must be reassembled, and pointer sizes differ. The COMPAT_SYSCALL_DEFINE* macro generates these translation wrappers.

A compat wrapper's job is purely mechanical: it converts the 32-bit argument representation into the native 64-bit form and then calls the same ksys_* or do_sys_* helper that the native syscall uses. This ensures that the actual logic is implemented exactly once, regardless of how many ABI variants exist.

The most common translation by far is reassembling a 64-bit value that the 32-bit ABI passes as two argument slots, and the kernel has a small set of macros for it so that no individual wrapper has to think about it. They are worth quoting because they encode a subtlety that hand-written glue routinely got wrong: 


/* include/asm-generic/compat.h */
#ifndef CONFIG_CPU_BIG_ENDIAN
#define compat_arg_u64(name)        u32  name##_lo, u32  name##_hi
#define compat_arg_u64_dual(name)   u32, name##_lo, u32, name##_hi
#else
#define compat_arg_u64(name)        u32  name##_hi, u32  name##_lo
#define compat_arg_u64_dual(name)   u32, name##_hi, u32, name##_lo
#endif
#define compat_arg_u64_glue(name)   (((u64)name##_lo & 0xffffffffUL) | \
                                     ((u64)name##_hi << 32))

The order in which a 32-bit caller places the two halves depends on the endianness of the ABI, so compat_arg_u64_dual() declares the parameters in the right order for the target and compat_arg_u64_glue() reassembles them by name rather than by position. A wrapper written against these macros is endian-correct without its author having considered endianness — which matters because ARM64 supports big-endian and the same fs/ code serves both. The result is that the wrappers themselves become nearly content-free: 


/* fs/open.c — generic compat wrappers, gated on __ARCH_WANT_* */
#if defined(CONFIG_COMPAT) && defined(__ARCH_WANT_COMPAT_TRUNCATE64)
COMPAT_SYSCALL_DEFINE3(truncate64, const char __user *, pathname,
                       compat_arg_u64_dual(length))
{
    return ksys_truncate(pathname, compat_arg_u64_glue(length));
}
#endif

#if defined(CONFIG_COMPAT) && defined(__ARCH_WANT_COMPAT_FTRUNCATE64)
COMPAT_SYSCALL_DEFINE3(ftruncate64, unsigned int, fd,
                       compat_arg_u64_dual(length))
{
    return ksys_ftruncate(fd, compat_arg_u64_glue(length), FTRUNCATE_LFS);
}
#endif

Note the __ARCH_WANT_COMPAT_* guards. A compat wrapper is not compiled merely because CONFIG_COMPAT is set; each architecture opts in individually, because whether a 32-bit ABI ever had a given call, and in what form, is a property of that ABI's history rather than of the kernel. The same conditional-compilation discipline that Section 2.2 described for the syscall tables reappears here one layer down.

Architecture-private wrappers live under arch/, and the x86 ones are instructive precisely because they are not COMPAT_SYSCALL_DEFINE: 


/* arch/x86/kernel/sys_ia32.c */
#define AA(__x)     ((unsigned long)(__x))

/* warning: next two assume little endian */
SYSCALL_DEFINE5(ia32_pread64, unsigned int, fd, char __user *, ubuf,
        u32, count, u32, poslo, u32, poshi)
{
    return ksys_pread64(fd, ubuf, count,
                ((loff_t)AA(poshi) << 32) | AA(poslo));
}

These use SYSCALL_DEFINE because on x86 the ia32 entry points are ordinary native definitions that happen to be reachable only from the ia32_sys_call_table; the ia32_ prefix and the table entry, not the macro, are what make them 32-bit. They also predate compat_arg_u64_dual(), which is why one of them carries a hand-written comment warning that it assumes little endian — exactly the class of assumption the generic macros were introduced to retire.

ARM64's compat layer, in arch/arm64/kernel/sys32.c, is smaller — eleven wrappers — and every one of them exists to reproduce a quirk of the 32-bit ARM kernel rather than to translate an argument. aarch32_mmap2 takes an offset in 4 KB units, rejects it if it cannot be converted to the kernel's page size, and then calls ksys_mmap_pgoff(). aarch32_statfs64 is stranger still: 32-bit ARM applied a fixup that treats a size of 88 as 84, and because binaries in the wild may depend on it, ARM64 reproduces the bug deliberately, with a comment citing the 2005 commit that introduced it. This is what a compat layer really is — not a translation of types, but a promise to keep behaving like an older kernel, indefinitely.

kernel_read and kernel_write

Some kernel subsystems need to read from or write to files — loading firmware, reading configuration, writing core dumps, executing binaries during boot. These operations cannot use the normal read()/write() path because the data buffers are in kernel memory, not user space, and copy_from_user()/copy_to_user() would fail or (worse) corrupt memory if fed a kernel pointer.

Linux provides kernel_read() and kernel_write() in fs/read_write.c for this purpose. These functions bypass the user-copy semantics entirely by constructing a kvec-based iov_iter that tells the VFS layer the buffer is in kernel space. The file's read_iter or write_iter method then operates on the kernel buffer directly, without access_ok() checks or fault-recovery paths.

The mechanism is the iov_iter type discriminator rather than any address-space override. An iov_iter tagged ITER_KVEC carries kernel pointers and is copied with plain memcpy(); one tagged ITER_UBUF or ITER_IOVEC carries user pointers and is copied with the fault-tolerant helpers of Section 4. Because the tag travels with the iterator, every layer below kernel_read() knows unambiguously what kind of pointer it is holding, and there is no window in which a piece of code has to guess. That is the whole architectural difference from set_fs(), which conveyed the same information out-of-band, in a per-thread variable, to code that had no way to check whether the answer was still true. 


/* fs/read_write.c — kernel-space file I/O */
ssize_t __kernel_read(struct file *file, void *buf, size_t count, loff_t *pos)
{
    struct kvec iov = {
        .iov_base   = buf,
        .iov_len    = min_t(size_t, count, MAX_RW_COUNT),
    };
    struct kiocb kiocb;
    struct iov_iter iter;
    ssize_t ret;

    if (WARN_ON_ONCE(!(file->f_mode & FMODE_READ)))
        return -EINVAL;
    if (!(file->f_mode & FMODE_CAN_READ))
        return -EINVAL;
    if (unlikely(!file->f_op->read_iter || file->f_op->read))
        return warn_unsupported(file, "read");

    init_sync_kiocb(&kiocb, file);
    kiocb.ki_pos = pos ? *pos : 0;
    iov_iter_kvec(&iter, ITER_DEST, &iov, 1, iov.iov_len);
    ret = file->f_op->read_iter(&kiocb, &iter);
    ...
}

ssize_t kernel_read(struct file *file, void *buf, size_t count, loff_t *pos)
{
    ssize_t ret;

    ret = rw_verify_area(READ, file, pos, count);
    if (ret)
        return ret;
    return __kernel_read(file, buf, count, pos);
}
EXPORT_SYMBOL(kernel_read);

Three details in that function are easy to skim past and each is load-bearing. The WARN_ON_ONCE on FMODE_READ exists because the caller is kernel code that opened the file itself, so passing a write-only file is a bug in the kernel rather than a user error, and it deserves a backtrace rather than a quiet -EBADF. The test !file->f_op->read_iter || file->f_op->read refuses any filesystem that still implements the old non-iterator read method, calling warn_unsupported() to print a rate-limited warning naming the file and the calling process; such a filesystem simply has no way to be handed a kernel buffer safely, and the refusal is explicit rather than silent corruption. And MAX_RW_COUNT clamps the length exactly as the syscall path does, because a kernel caller is no more entitled to hand the VFS an unbounded transfer than a user one is.

kernel_write() follows the same shape with ITER_SOURCE and brackets the transfer with file_start_write() and file_end_write() so that filesystem freezing works. Its lower half, __kernel_write(), is exported with a comment that is unusually candid about the API's status: the export is described as being "more of a EXPORT_SYMBOL_DONTUSE()", present only because autofs is a modular in-tree user and "really isn't appropriate for any other kernel modules." The distinction between the two is that kernel_write() calls rw_verify_area() and the underscore-prefixed form does not.

For the common case of loading a whole file into memory there is a higher-level interface still, kernel_read_file() in fs/kernel_read_file.c, which allocates the buffer, reads the file in full, and — crucially — takes an enum kernel_read_file_id saying what the file is for: READING_FIRMWARE, READING_MODULE, READING_KEXEC_IMAGE, READING_KEXEC_INITRAMFS, READING_POLICY, READING_X509_CERTIFICATE. That identifier is not decoration: it is passed to the LSM and IMA hooks so that a security policy can require, say, that kernel modules be signed while firmware need not be. It is the same idea as the personality field in an io_uring SQE — when work is initiated by the kernel on someone's behalf, the kernel has to say explicitly whose behalf and for what purpose, because none of it can be inferred from the calling context.

These functions are used extensively during boot (loading the initramfs, executing /sbin/init), in the module loader (kernel/module/), in the firmware loading subsystem (drivers/base/firmware_loader/), and in the ELF binary handler (fs/binfmt_elf.c). They represent the clean modern alternative to the old set_fs(KERNEL_DS) trick, which used to change the address-space limit so that the kernel could pass kernel pointers to functions that expected user pointers.

The Removal of set_fs(KERNEL_DS)

Linux 2.6 relied on a technique called set_fs(KERNEL_DS) that was central to how the kernel called its own system call implementations internally. The idea was simple but dangerous: by changing the per-thread address-space limit from USER_DS to KERNEL_DS, the kernel could make access_ok() accept any address, including kernel pointers. This allowed code to call sys_read() with a kernel buffer as if it were a user buffer.

This technique was always fragile. It violated the principle that kernel code should never pretend to be user space, and it created an entire class of confused-deputy bugs: if any code path under the address-limit override accidentally touched a real user pointer, it would succeed without the normal safety checks. A kernel vulnerability that could trick the kernel into performing a set_fs(KERNEL_DS) operation — or that could exploit code already running under that override — could bypass all user-pointer validation.

Its worst property was that the override was ambient. set_fs() wrote a value into thread_info, and every access_ok() in the kernel consulted that value implicitly, so the meaning of "is this pointer safe?" depended on state established by a caller several frames up that the checking code could not see and had no way to interrogate. A function was correct or catastrophic depending on its dynamic context, which is precisely the property that makes code impossible to review. It also interacted badly with everything that can interpose on execution: a signal delivered, a preemption, a page fault, or a kprobe taken while KERNEL_DS was in force ran that unrelated code under a lifted address-space limit as well. Compounding all of it, the override had to be saved and restored across every context switch, so a mechanism used by a handful of call sites imposed a cost on all of them.

The removal was a multi-year effort, largely by Christoph Hellwig, and it did not conclude before the 5.x series — it concluded well inside it. The transitional helpers force_uaccess_begin() and force_uaccess_end() arrived in 5.10 to mark the remaining sites explicitly, architectures were converted one at a time behind a CONFIG_SET_FS symbol added in 5.18, and the commit that deleted that symbol — uaccess: remove CONFIG_SET_FS — landed for 5.18 in February 2022. The pace is itself the lesson: removing one per-thread variable took roughly two years and touched every architecture, because an ambient mechanism has no enumerable list of users.

In Linux 7.0.12 the cleanup is total, and can be verified in a few seconds: there is no set_fs(KERNEL_DS) anywhere in the tree, no definition of KERNEL_DS or USER_DS, no CONFIG_SET_FS in any Kconfig, and the transitional force_uaccess_begin() and force_uaccess_end() are gone as well. The replacement is not one API but a family, each member of which makes the address space of a pointer a visible property of the call: kernel_read() and kernel_write() for file I/O, iov_iter_kvec() for scatter-gather, getname_kernel() for pathnames, copy_strings_kernel() for argument vectors, the init_* helpers of Section 10.5 for boot-time filesystem work, and the ksys_*/do_sys_* helpers for the separate problem of calling convention. Every one of them is a distinct symbol, so the set of places where the kernel handles a kernel pointer as though it were a user pointer is finite, greppable, and reviewable — which the set_fs() world never was.

There is a general principle here worth carrying out of this chapter, because it recurs elsewhere in the kernel. The fix for a dangerous global mode is rarely a safer version of the mode; it is a set of explicit operations that make the mode unnecessary. The same reasoning produced copy_from_user() instead of a "trusted pointer" flag, the ITER_KVEC tag instead of an address-space variable, and the SYSCALL_DEFINE signature that makes sys_read() uncallable instead of a comment asking people not to call it.

Init-Time Kernel Calls

The earliest stages of kernel boot need to perform operations that look remarkably like system calls — mounting the root filesystem, changing directories, executing the init process — but there is no user-space process yet to issue them. The kernel handles this by calling dedicated init_* helpers or kernel_* functions that perform the same work as their syscall counterparts but operate entirely in kernel context.

These helpers are not scattered through the boot code; they are collected in one small file, fs/init.c, and declared in one header, include/linux/init_syscalls.h. Seventeen of them exist, and the list is essentially the subset of the file-system ABI that bringing up a root filesystem requires: init_mount, init_umount, init_chdir, init_chroot, init_chown, init_chmod, init_eaccess, init_stat, init_mknod, init_link, init_symlink, init_unlink, init_mkdir, init_rmdir, init_utimes, init_dup and init_pivot_root. Every one is marked __init, so the whole file is discarded from memory once boot completes — a small but pointed piece of evidence that these are not a general-purpose in-kernel filesystem API and are not meant to become one. 


/* fs/init.c */
int __init init_mount(const char *dev_name, const char *dir_name,
        const char *type_page, unsigned long flags, void *data_page)
{
    struct path path;
    int ret;

    ret = kern_path(dir_name, LOOKUP_FOLLOW, &path);
    if (ret)
        return ret;
    ret = path_mount(dev_name, &path, type_page, flags, data_page);
    path_put(&path);
    return ret;
}

int __init init_mknod(const char *filename, umode_t mode, unsigned int dev)
{
    CLASS(filename_kernel, name)(filename);
    return filename_mknodat(AT_FDCWD, name, mode, dev);
}

Compare init_mount() with SYSCALL_DEFINE5(mount, ...) and the pattern is immediate. The system call must first copy four strings in from user space with copy_mount_string() and resolve the mount point with user_path_at(); init_mount() already has kernel strings, so it goes straight to kern_path() and calls the same path_mount() the syscall eventually reaches. The shared implementation is once again below the ABI, and the init_* layer is the user-copy step removed rather than reimplemented. init_mknod() shows the same idea expressed through the cleanup idiom: CLASS(filename_kernel, name) builds a struct filename from a kernel string via getname_kernel() and releases it on scope exit, where the syscall's CLASS(filename, name) builds one from a user pointer via getname(). The two classes differ in exactly one respect — which address space the source string lives in — and that difference is now written at the call site instead of being implied by a thread-wide flag.

The root filesystem mount in init/do_mounts.c uses init_mount() and init_chdir(); init_pivot_root() and init_chroot() perform the switch from the initramfs to the real root. The initramfs unpacking code in init/initramfs.c uses these same helpers to recreate the archive's directories, devices and symbolic links in the initial rootfs — which is why init_mknod and init_symlink are on the list at all. Once that is done, run_init_process() in init/main.c calls kernel_execve() to execute /sbin/init, or one of the fallbacks /etc/init, /bin/init and /bin/sh. 


/* init/main.c — launching the first user-space process */
static int run_init_process(const char *init_filename)
{
    const char *const *p;
    argv_init[0] = init_filename;
    pr_info("Run %s as init process\n", init_filename);
    pr_debug("  with arguments:\n");
    for (p = argv_init; *p; p++)
        pr_debug("    %s\n", *p);
    ...
    return kernel_execve(init_filename, argv_init, envp_init);
}

kernel_execve() is the in-kernel equivalent of the execve() system call. It performs the same work — loading an ELF binary, setting up the new address space, constructing the argument and environment vectors — but it can be called before any user-space process exists, because it does not require a user-mode register frame or a syscall entry path. This is the function that creates the very first user-space process (PID 1), the ancestor of all subsequent processes on the system.

Structurally it is a point-for-point translation of the syscall path with every user-space step swapped for its kernel counterpart. Where do_execveat_common() obtains its struct filename from getname() and counts and copies the vectors with count() and copy_strings(), kernel_execve() uses CLASS(filename_kernel, filename), count_strings_kernel() and copy_strings_kernel(), then hands the same struct linux_binprm to the same bprm_execve(). All the interesting work — searching the binfmt handlers, building the new mm_struct, tearing down the old address space, resetting credentials for a setuid binary — is shared, because it was never the part that cared where the strings came from. The function opens with WARN_ON_ONCE(current->flags & PF_KTHREAD) and the comment "It is non-sense for kernel threads to call execve", which is the boundary condition: kernel_execve() replaces the caller's address space, so the caller must be a task that is on its way to becoming a user process, not a permanent kernel thread.

That constraint explains the one remaining member of this family. When a running kernel needs to invoke a user-space program — a hotplug helper, a core-dump pipe, the request_module() path that loads a module by name — it cannot call kernel_execve() from wherever it happens to be, for exactly the reason above. call_usermodehelper() in kernel/umh.c resolves this by queueing the request to a workqueue, forking a fresh task, and calling kernel_execve() there, optionally waiting for the result with UMH_WAIT_PROC. It is the same primitive as run_init_process(), arranged so that it can be used after boot. Because handing the kernel an arbitrary program path is an obvious escalation surface, CONFIG_STATIC_USERMODEHELPER allows a hardened build to redirect every such invocation to a single fixed binary named by CONFIG_STATIC_USERMODEHELPER_PATH, which then decides what to run.

Absent System Calls: COND_SYSCALL and sys_ni_syscall

There is a final wrapper in this family, and it is the one that handles a system call which is not there at all. A kernel configured without System V IPC, without CONFIG_ADVISE_SYSCALLS, or without CONFIG_FANOTIFY still has syscall numbers allocated for those calls, and every entry in the dispatch table must point to a real function — Section 2.2 showed that the table is a dense array, and a null entry would be an indirect branch to zero. 


/* kernel/sys_ni.c */
asmlinkage long sys_ni_syscall(void)
{
    return -ENOSYS;
}

#ifndef COND_SYSCALL
#define COND_SYSCALL(name) cond_syscall(sys_##name)
#endif

/* include/linux/linkage.h — the generic mechanism */
#ifndef cond_syscall
#define cond_syscall(x) asm(                \
    ".weak " __stringify(x) "\n\t"          \
    ".set  " __stringify(x) ","             \
         __stringify(sys_ni_syscall))
#endif

The generic implementation is a linker trick: it declares the symbol weak and aliases it to sys_ni_syscall, so if the real implementation is compiled in, the strong definition wins, and if it is not, the reference resolves to the stub that returns -ENOSYS. Nothing is decided at run time and the table needs no special case. On x86_64 and ARM64 the architecture overrides COND_SYSCALL with a weak function rather than a weak alias, because the table entries take a pt_regs pointer and the types must match: 


/* arch/x86/include/asm/syscall_wrapper.h */
#define __COND_SYSCALL(abi, name)                   \
    __weak long __##abi##_##name(const struct pt_regs *__unused);   \
    __weak long __##abi##_##name(const struct pt_regs *__unused)    \
    {                               \
        return sys_ni_syscall();                \
    }

kernel/sys_ni.c consists of little else: roughly 280 COND_SYSCALL and COND_SYSCALL_COMPAT lines, one per optional system call, ordered by subsystem. The file is the authoritative answer to "which system calls can this kernel be built without", and it is worth reading once for that reason alone.

The -ENOSYS it produces is the same value user space sees for a syscall number past the end of the table, and that is intentional: a program probing for a feature cannot and should not distinguish "your kernel is too old to have this call" from "your kernel was built without it." It is also the value strace reports, which is why an ENOSYS from a call that plainly exists in the manual page is nearly always a configuration answer rather than a bug. Section 7's tracing hooks see the call normally — dispatch is unaffected — so the stub is invisible to everything except its return value.

The rule of thumb for all kernel wrapper routines is simple: if code is serving the user ABI, it belongs under SYSCALL_DEFINE* and must honor all user-copy, tracing, and restart conventions. If code is shared internally, push the implementation into a helper below the ABI wrapper — ksys_*, do_sys_*, or kernel_* — so that native syscalls, compat wrappers, and in-kernel callers all benefit from one implementation without any of them compromising the safety guarantees of the others.

Underneath that rule are two questions that this section has kept deliberately apart, and the reason to separate them is that the kernel spent twenty years answering both at once and got the second one wrong. The first is how the arguments arrive: from a register frame for a native call, from a register frame plus reassembly for a compat call, or as ordinary C arguments for an in-kernel caller. That is what the ksys_* and do_sys_* layering solves, and the pt_regs signature that SYSCALL_DEFINE generates on x86_64 and ARM64 is what makes solving it mandatory rather than optional. The second is which address space a pointer belongs to, and it has an entirely separate family of answers — kernel_read(), iov_iter_kvec(), getname_kernel(), copy_strings_kernel(), the init_* helpers. set_fs(KERNEL_DS) was an attempt to answer the second question with a mechanism suited to neither, by making a kernel pointer temporarily indistinguishable from a user one, and its removal is the single largest structural change to this area since Linux 2.6.

It is worth noticing how much of that outcome came from types rather than from rules. The reason nobody calls sys_read() from the kernel is not a comment asking them not to — no such comment exists — but that the symbol takes a const struct pt_regs * and the compiler refuses. The reason no layer below kernel_read() mistakes a kernel buffer for a user one is not a convention but the ITER_KVEC tag travelling inside the iterator. The reason a reference taken at the top of ksys_read() is released on every error path is not reviewer diligence but CLASS(fd_pos, f) and the compiler's cleanup attribute. Each is the same move: take a property that used to live in the programmer's head, or in ambient thread state, and make it something the toolchain can check.

Summary

The system call is the kernel’s most visible and most conservative interface: a number and a register convention that must keep working for binaries older than the kernel running them. What this chapter has tried to show is how much machinery Linux 7.0.12 puts behind that unchanging promise, and how little of it resembles the single dispatch table that older kernel literature describes. Four ideas run through the chapter, and they are more useful to carry away than any individual function name.

The first is that most of the safety in this subsystem is enforced by types and generated code rather than by rules that programmers are asked to remember. Section 2 showed that SYSCALL_DEFINE3(read, ...) does not produce a function anyone can call with three arguments; it produces __x64_sys_read(const struct pt_regs *), and the C-callable body is hidden behind a name no caller is meant to know. Section 10 showed the consequence: the reason in-kernel code must go through ksys_read() is not a documented prohibition but the simple fact that nothing else exists to call. The same pattern recurs everywhere. The __user annotation of Section 4 is invisible to the compiler but load-bearing for sparse. copy_from_user() returns the number of bytes not copied, so the only natural way to write the check is the correct one. copy_struct_from_user() makes forward and backward compatibility of an extensible argument structure a property of the helper rather than of each caller’s diligence. Exception tables are emitted by the assembler from the instruction that might fault, so a fixup cannot drift away from the access it protects. And COND_SYSCALL makes an unconfigured system call resolve to sys_ni_syscall through a weak alias, so a hole in the table is impossible to create by omission.

The second is that the entry path is where the hardware architecture, the ABI, and the current generation of CPU vulnerability mitigations all meet, which is why it is the least portable code in the chapter and the fastest-changing. Section 3 followed syscall/sysret on x86_64 and svc/eret on ARM64 instruction by instruction, and the striking result was how little of that code is about system calls. The stack switch through cpu_current_top_of_stack, the KPTI page-table swap and its trampoline stack, IBRS_ENTER, UNTRAIN_RET, CLEAR_BRANCH_HISTORY, the VERW buffer flush on the way out, the kernel stack offset randomization whose offset is deliberately chosen at the end of the previous call, ARM64’s MTE tag-check reconfiguration and its speculative-unprivileged-load workaround — none of these are things a system call needs, and all of them are things a privilege boundary needs. FRED, which replaces the whole ad-hoc x86 entry state machine with a hardware-defined stack frame, is the clearest statement that this complexity was never inherent. Section 3 also showed why sysret is guarded by five separate eligibility tests before it can be used, and why the safe, slow iret path can never be deleted.

The third is that many mechanisms we habitually call “system call features” are in fact bound to the entry pipeline, not to the idea of asking the kernel to do something. This distinction is invisible as long as every request crosses the boundary the same way, and the chapter deliberately arranged two sections that make it visible. The vDSO of Section 5 answers clock_gettime() and, in 7.0.12, getrandom() without entering the kernel at all, by publishing kernel-maintained data in read-only pages. io_uring (Section 9 here, Chapter 24 in full) goes the other way: it enters the kernel once and then carries an unbounded number of requests across shared submission and completion rings, so with SQPOLL a program can perform I/O with no boundary crossing at all. Section 6’s seccomp filters, Section 7’s ptrace stops, tracepoints, and audit records all observe system calls because they hook the entry pipeline — which is exactly why none of them can see an io_uring operation, and why io_uring grew its own IORING_REGISTER_BPF_FILTER mechanism rather than inheriting one. The lesson is not that io_uring is unsafe but that a security policy is only as broad as the chokepoint it is attached to.

The fourth is that two questions which the old set_fs(KERNEL_DS) answered together have been permanently separated, and Section 10 was built around that separation. How do a call’s arguments arrive? is a calling-convention question, and it is answered by the ksys_* and do_sys_* layering, by the compat wrappers of arch/x86/kernel/sys_ia32.c and arch/arm64/kernel/sys32.c, and by helpers such as compat_arg_u64_dual() that reassemble a 64-bit value from a register pair. Which address space does this pointer belong to? is a memory-safety question, and it is answered by an entirely different family: kernel_read() and kernel_write(), getname_kernel(), kernel_execve(), and the seventeen __init helpers in fs/init.c. Conflating the two is precisely what set_fs() did, and it is why a single forgotten restore could turn any user-pointer bug into an arbitrary kernel write. CONFIG_SET_FS was removed in 5.18; Section 8’s restart machinery, with its four internal error codes and the restart_block, is another case of the same discipline — state that used to be reconstructed by hand in architecture assembly is now recorded explicitly in the task structure.

Compared with Linux 2.6, the practical differences are easy to list. The dominant architectures are x86_64 and ARM64 rather than 32-bit x86, and ARM64 now draws its numbering from the same scripts/syscall.tbl master list that the other modern architectures use. The fast x86 entry is syscall, not int 0x80, and int 0x80 survives only as an emulated IDT gate. The fixed vsyscall page has become the vDSO plus a shrinking legacy emulation. The exit path is a documented C pipeline rather than per-architecture assembly that each maintainer fixed separately. set_fs(KERNEL_DS) is gone, and the syscall entry points themselves have been made uncallable from C. And the subsystem has grown whole capabilities that 2.6 had no equivalent for: seccomp-BPF sandboxing with user-space notification and fd injection, Syscall User Dispatch, pidfds, structured extensible calls such as openat2, and io_uring. Taken together they have widened “the system call subsystem” from a dispatch mechanism into the kernel’s primary policy and observability boundary.
