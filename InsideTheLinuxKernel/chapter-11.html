A signal is an asynchronous notification delivered to a thread: a terminal generated Ctrl-C, a child exited, a timer expired, a memory access could not be repaired, or a debugger wants the target to stop. Unlike a system call, which the running thread initiates, a signal is injected from outside and acted on only when the target next reaches a point at which the kernel may return to user mode. This chapter follows a signal through the Linux 7.0.12 implementation on x86_64 and ARM64, from the moment it is generated to the moment the interrupted thread resumes.

Signals Introduction

A signal is not a message queue in the general distributed-systems sense. It is a constrained kernel object with a numeric identity, a disposition, an optional siginfo payload, and delivery rules that are partly global to a thread group and partly private to a single thread. The kernel can mark the signal pending without running the user handler immediately. Only when a thread leaves the kernel, or blocks in a signal-aware wait path, does Linux examine masks, default actions, and handler state to decide what to do next. Because delivery is deferred in this way, signal handling reaches into scheduling, exception handling, credentials, timers, ptrace, and even the coredump code, which is why this chapter has to borrow vocabulary from so many other parts of the kernel.

Linux 2.6 signal handling is usually studied on i386 alone, and some of what looks inherent there turns out to be an artifact of a single 32-bit architecture. The semantics are still recognizable — a number, a disposition, a mask, a pending set — and two mechanisms that are easy to mistake for recent additions were already there: real-time signals, and the split between a thread’s private pending queue and the thread group’s shared one. What changed is the machinery around them. A sigset_t is not wider in Linux 7.0.12 than it was in Linux 2.6; _NSIG has been 64 throughout, and the mask is still exactly 64 bits. What changed is that on x86_64 and ARM64 those 64 bits occupy a single unsigned long rather than two, which is why so much of kernel/signal.c carries a one-word special case beside the general loop. Around that unchanged core the kernel has since added pidfds, signalfd, scalable vector register state that makes the signal frame variable-sized, and return trampolines that no longer live on the user stack. This chapter therefore follows the Linux 7.0.12 implementation rather than the historical API surface alone: where an old concept survives, the text says so, and where the modern kernel split, wrapped, or generalized it, the text explains why.

Linux 7.0.12 keeps the classic split between standard signals and real-time signals. Standard signals occupy numbers 1 through 31 and historically behave like bits: if the same standard signal is generated twice while already pending, the kernel usually collapses the duplicates into one pending bit. Real-time signals occupy 32 through 64 on native x86_64 and ARM64, and they are queue-based by design. A sender can therefore enqueue multiple instances, each carrying its own payload, subject to memory pressure and RLIMIT_SIGPENDING.

It is worth being precise about what that split is in the code, because it is not a flag or a type. The boundary is the single comparison sig < SIGRTMIN, and it appears verbatim throughout kernel/signal.c: in legacy_queue(), which is what actually collapses a duplicate standard signal; in the choice of whether to charge a queue entry against RLIMIT_SIGPENDING; in the decision of whether a failed allocation should return -EAGAIN or silently drop the payload; and, as Section 1.1 shows, inside the siginmask() macro that every default-action test goes through. There is no third category and no per-signal descriptor. A signal number below 32 behaves one way and a signal number of 32 or above behaves the other, and everything the rest of this chapter describes follows from that one comparison.

Standard Signals and Default Actions

The numbering mostly looks familiar to readers of the old i386 chapter. The standard signal numbers on x86_64 and ARM64 match the generic Linux numbering from the 2.6 era, so SIGKILL is still 9 and SIGSEGV is still 11. What changed is the representation around those numbers. On 32-bit i386, a 64-signal mask consumed two machine words; on 64-bit x86_64 and ARM64, the same mask fits in one unsigned long, so many mask operations collapse to single-word arithmetic and scanning.

Signal numbering is nominally per-architecture: x86 keeps its own list in arch/x86/include/uapi/asm/signal.h, while ARM64 has no architecture header of its own and takes the generic list in include/uapi/asm-generic/signal.h. For the two architectures this book follows, the two lists agree on every number, which is why a single pair of tables can serve both. That agreement is not universal — Alpha, MIPS, PA-RISC and SPARC all renumber parts of the range, which is why the kernel keeps the list architecture-overridable at all — but it does mean an x86_64 reader and an ARM64 reader can use the same constants without qualification. Both headers also carry the historical aliases: SIGIOT is 6 (that is, SIGABRT), SIGPOLL is defined as SIGIO, and SIGUNUSED is 31 (that is, SIGSYS, which acquired a real meaning when seccomp began using it). SIGLOST appears in both files but is commented out in both, a fossil of an NFS file-locking notification that was never adopted. SIGSTKFLT, number 16, is the reverse case: an i386 coprocessor artifact that the generic list inherited and that ARM64 therefore reserves without ever generating.

The default action taxonomy also survives intact. Some signals terminate the process, some additionally request a core dump, some stop the whole thread group, some resume it, and some are ignored unless a program installs a handler. The important modern twist is that default actions now interact with group-exit state, pid namespaces, seccomp, ptrace, alt stacks, and architecture-specific frame construction. A simple phrase like “SIGSEGV kills the process” is still true at a user level, but internally it now means get_signal() recognizes a fatal default action, sets PF_SIGNALED, and may route the thread group through vfs_coredump() before exit.

The kernel does not store a per-signal “default action” field; it derives the action from a handful of compile-time bitmasks in include/linux/signal.h and tests membership with helpers like sig_kernel_stop(), sig_kernel_coredump(), and sig_kernel_ignore(). Any signal not named by one of these masks defaults to plain termination, which is why the masks only need to enumerate the exceptions. These same macros reappear throughout the delivery path in Section 4, so it is worth meeting them here.

Three details in that excerpt are easy to skim past and each explains something the rest of the chapter depends on.

The first is siginmask(). Every one of the sig_kernel_* tests goes through it, and it contains the guard (sig) < SIGRTMIN. That single clause means the entire default-action taxonomy is inert for real-time signals. sig_kernel_coredump(40) is false, sig_kernel_stop(40) is false, sig_kernel_ignore(40) is false, and so by the rule that unnamed signals terminate, the default action of every real-time signal is plain termination with no core dump. This is not stated anywhere as a policy; it falls out of the range check. It is also why the masks can be written as fixed 64-bit constants without worrying about the real-time range at all.

The second is SIGEMT_MASK, which is conditional on the architecture defining SIGEMT — an emulator-trap signal that Alpha, MIPS, PA-RISC and SPARC have and that neither x86_64 nor ARM64 does. On the two architectures this book follows, SIGEMT_MASK expands to 0 and both masks that mention it are exactly as short as they look. It is included here because a reader diffing this excerpt against the header would otherwise think a line had been dropped, and because it is a small example of a pattern that recurs throughout the signal code: an architecture difference absorbed by a macro that evaluates to nothing rather than by an #ifdef around the user of the macro.

The third is SIG_SPECIFIC_SICODES_MASK, which postdates Linux 2.6; it was added in 4.14. It is not a default action; it is a statement about the siginfo payload. Most signals carry an si_code drawn from a small general namespace that says who sent this: SI_USER for kill(), SI_KERNEL, SI_QUEUE for sigqueue(), SI_TIMER for a POSIX timer, and so on. The eight signals named by this mask instead carry a signal-specific si_code that says what went wrong: SEGV_MAPERR versus SEGV_ACCERR for SIGSEGV, ILL_ILLOPC for SIGILL, FPE_INTDIV for SIGFPE, CLD_EXITED versus CLD_STOPPED for SIGCHLD, SYS_SECCOMP for SIGSYS. Because the two namespaces overlap numerically, code that copies or interprets a siginfo must know which interpretation applies, and sig_specific_sicodes() is how it asks. Section 4 returns to this when it explains how a kernel_siginfo is flattened for user space, and Section 7 returns to it again for signalfd.

sig_fatal(), at the end of the excerpt, is the formal version of the “everything unnamed terminates” rule. A signal is fatal to a thread when it is neither ignored-by-default nor a stop signal and the thread’s current disposition is still SIG_DFL. Note what it does not test: it does not consult the signal mask. Blocking a signal postpones its delivery, but a blocked signal whose disposition is SIG_DFL is still fatal in this sense. The one caller, complete_signal(), adds the mask test itself, and the mask it consults is t->real_blocked rather than t->blocked — the temporary set installed by rt_sigtimedwait(), which is the one case in which a thread has genuinely asked to receive a signal by other means. Section 3 returns to this, because it is the decision that turns one signal into a whole-group exit before any thread has dequeued anything.

Read together, these masks describe five possible default outcomes: terminate (the unnamed default), terminate with a core dump (SIG_KERNEL_COREDUMP_MASK), ignore (SIG_KERNEL_IGNORE_MASK), stop the thread group (SIG_KERNEL_STOP_MASK), and continue a stopped group (the special case of SIGCONT). SIG_KERNEL_ONLY_MASK is different in kind: it names SIGKILL and SIGSTOP, the two signals a process can never catch, block, or ignore. That is why rt_sigprocmask() and rt_sigaction() silently strip those two numbers—the kernel guarantees that root, a debugger, or the out-of-memory killer always retains a way to stop or destroy a runaway thread group.

Real-Time Signals and the Queued Range

Real-time signals were added to Linux long before the kernel this book describes, but on 2.6-era i386 they still sat beside the classic mechanism as an optional extra. That framing no longer fits. On x86_64 and ARM64 the real-time ABI is the only one user space uses even for signal 2, and the real-time numbers are the only part of the range with no predefined meaning. Keeping those two facts apart is the main thing this subsection is for: rt_sigaction() is the system call every program uses to install a SIGINT handler, and it has nothing to do with whether SIGINT queues.

Three behavioral differences follow from the number being 32 or above. A second instance is queued rather than collapsed, because legacy_queue() only collapses when sig < SIGRTMIN. Each instance keeps its own siginfo, so a payload survives to the receiver instead of being merged away. And, as Section 1.1 showed, the default-action masks do not apply, so an uncaught real-time signal terminates the process without a core dump regardless of what it was used for. Although the standard numbering is stable, the surrounding ABI surface is more uniform than on 2.6-era i386. User space on x86_64 and ARM64 installs handlers with rt_sigaction, blocks signals with rt_sigprocmask, suspends with rt_sigsuspend, and waits with rt_sigtimedwait. The older non-RT syscalls survive only as compatibility baggage for legacy ABIs. In other words, “real-time” no longer names a niche subsystem; it names the default signal ABI for 64-bit Linux.

The Signal Lifecycle

The single most useful thing to fix in mind before reading any of the code is that the sender never delivers a signal. A thread calling kill() does four things and then returns: it checks permission, it records the signal in a pending set belonging to the target, it decides which thread in the target group should notice, and it sets that thread’s TIF_SIGPENDING flag and wakes it if it was sleeping. At no point does it run a handler, change a disposition, or touch the target’s registers. Everything that a programmer thinks of as “the signal happening” occurs later, in the target’s own context, on its way out of the kernel. Figure 11-1 arranges the four stages in that order.

The consequence is that signal latency is not a property of the signal but of the target. A thread spinning in user code will notice at its next timer interrupt, because the return from that interrupt passes through the same exit path a system call does. A thread blocked in an interruptible sleep is woken and notices immediately. A thread blocked in an uninterruptible sleep notices nothing at all, which is why the kernel added TASK_KILLABLE — TASK_WAKEKILL | TASK_UNINTERRUPTIBLE — and why signal_pending_state() distinguishes the two cases: an interruptible sleeper breaks out for any pending signal, a killable one only for a fatal one. That is the mechanism behind the familiar observation that SIGKILL cannot rescue a process stuck in disk wait, and behind the equally familiar fact that on a modern kernel it usually can, because most such waits have been converted to killable form.

The second thing to fix in mind is that TIF_SIGPENDING is a hint rather than a fact. It says “this thread may have work to do before returning to user mode”, and it is deliberately allowed to be set when no deliverable signal exists — for instance because the only pending signal has since been blocked. recalc_sigpending() is the function that reconciles the flag with reality, and it is called after every operation that could change the answer: altering the mask, dequeuing a signal, changing a disposition. The cost of a spurious set flag is one wasted trip through the delivery path; the cost of a spuriously clear one would be a signal that is never delivered, so the code errs firmly in one direction.

Figure 11-1 also highlights an architectural point that becomes easy to miss when reading only kernel/signal.c. The generic code decides which signal to deliver and whether a handler should run, but only the architecture code knows how to describe that delivery in user ABI terms. That division barely mattered in the old i386 chapter because there was only one target architecture. In this book, the distinction is part of every diagram: generic code feeds two separate frame builders, one for x86_64 and one for ARM64, and each can add arbitrarily large architecture state.

The boundary between the two halves is a single function pointer’s worth of interface. Generic code calls get_signal(), which either handles the signal entirely on its own — terminating the group, stopping it, or discarding an ignored signal, none of which needs architecture knowledge — or fills in a struct ksignal and returns true, meaning “a user handler must now run, and the rest is your problem.” Only then does architecture code appear: x64_setup_rt_frame() in arch/x86/kernel/signal_64.c or setup_rt_frame() in arch/arm64/kernel/signal.c builds the user-visible frame, and both finish by calling the generic signal_setup_done() to report success or failure. The architecture code is reached from arch_do_signal_or_restart(), which is the same hook Chapter 10 described as the point at which the return-to-user pipeline pauses to do signal work. Sections 4.4 and 4.5 take the two frame builders apart in detail; the point here is only that the split is narrow and that everything above it is shared.

Signal Data Structures

Signals are deceptively small from user space: a process sees an integer, a mask, and maybe a handler function. Inside the kernel, however, the implementation is spread across several structures with different sharing rules. Some are per-thread, such as task_struct.pending and task_struct.blocked. Some are per-thread-group, such as signal_struct.shared_pending and the stop or exit bookkeeping needed to coordinate all threads in a process.

Linux 7.0.12 still organizes these structures around one master lock, sighand->siglock. That lock covers handler installation, pending queues, blocking masks, group-stop state, and most observable signal transitions. The design is intentionally asymmetric: signal_struct has no private lock, because sharing a signal_struct already implies sharing the sighand_struct that owns the lock. This is one of the clearest examples of how Linux keeps the data model simple enough for extremely hot paths.

Compared with Linux 2.6, the names are slightly more explicit and the payload objects are richer. The in-kernel form of siginfo_t is now kernel_siginfo_t. Queue elements remember ucounts so that queued real-time signals can be charged against RLIMIT_SIGPENDING in the right user namespace. The basic idea did not change, but the structures now reflect namespaces, scalability, and modern 64-bit state.

The ownership model is easiest to understand as a three-tier hierarchy rooted at task_struct. Each thread keeps its own blocked mask, alternate-stack state, and private pending queue inside task_struct. The sighand_struct is shared by every thread created with CLONE_SIGHAND—in practice, all POSIX threads in one process—and owns both the handler table and the single spinlock that serializes signal mutations. The companion signal_struct is shared by the whole thread group and carries process-wide state: the shared pending queue, group-stop coordination, coredump state, curr_target wakeup rotation, and resource-limit data.

All of that mutable state is protected by sighand->siglock. Linux takes it with interrupts disabled via spin_lock_irqsave() because signal generation can happen from interrupt context, such as timer expiry, and the same lock must cover both enqueue and delivery decisions. Under that one lock live both pending queues, handler installations, the blocked mask while delivery is being prepared, and the group-stop or group-exit transitions that make signals visible across a thread group. The single-lock design keeps the data model straightforward and avoids secondary lock-ordering problems, but it also means siglock can become a contention point in thread-heavy workloads.

The memory layout is deliberately split across separate allocations and cache footprints. A sighand_struct is refcounted and allocated independently so that unshare_sighand() during exec can hand the exec'ing task a private handler table without disturbing the parent or sibling threads. The signal_struct is likewise separately allocated and refcounted, while each sigqueue node comes from a dedicated SLAB cache. That separation lets fork, exec, and exit adjust sharing relationships without copying one giant monolithic signal object.

The Signal Set

The smallest but most frequently manipulated signal structure is sigset_t. In Linux 7.0.12 it is defined in the UAPI as an array of unsigned long words sized for _NSIG bits. Because x86_64 and ARM64 both use 64-bit longs and Linux exposes 64 signal numbers, native 64-bit kernels typically operate on a single word. The old i386 chapter described more explicit bitmap loops because the same mask was split across two 32-bit words.

This difference sounds cosmetic, but it affects the hot path. Functions such as next_signal(), sigaddset(), sigdelsetmask(), and sigandsets() can often finish with one load, one mask, and one bit-scan instruction. That is why Linux preserves a bitmap even though real-time signals also need a list. The bitmap answers the cheap question “is anything of this number pending?” while the linked list preserves payload and ordering. 



#define _NSIG        64
#define _NSIG_BPW    __BITS_PER_LONG
#define _NSIG_WORDS  (_NSIG / _NSIG_BPW)

typedef struct {
    unsigned long sig[_NSIG_WORDS];
} sigset_t;

int next_signal(struct sigpending *pending, sigset_t *mask)
{
    unsigned long i, *s, *m, x;
    int sig = 0;

    s = pending->signal.sig;
    m = mask->sig;
    x = *s & ~*m;
    if (x) {
        if (x & SYNCHRONOUS_MASK)
            x &= SYNCHRONOUS_MASK;
        sig = ffz(~x) + 1;
        return sig;
    }
    ...
}

The kernel uses several distinct masks per thread. current->blocked is the mask currently enforced for asynchronous delivery. current->real_blocked is temporarily used by wait paths such as rt_sigtimedwait() when Linux needs to unblock an interest set while sleeping. The user-visible abstraction is still the mask manipulated by sigprocmask(), but modern kernels sometimes need multiple snapshots to implement restartable waits without losing state.

The key practical rule is that the bitmap is authoritative for eligibility, not for payload. A pending bit can exist without a live queue node, because standard signals are allowed to collapse and because Linux will still deliver at least one instance even if it cannot preserve every siginfo payload. That design is one of the reasons the signal subsystem ages well. It preserves POSIX semantics in low-memory situations without forcing every send to allocate memory.

The scan in next_signal() also gives special priority to synchronous fault signals collected in SYNCHRONOUS_MASK. That mask holds exactly six numbers — SIGSEGV, SIGBUS, SIGILL, SIGTRAP, SIGFPE, and SIGSYS — and if any unblocked instance of one of them is pending, Linux dequeues it before it considers an unrelated asynchronous signal such as SIGUSR1. That priority rule keeps fault delivery anchored close to the instruction stream that caused the exception instead of letting a queued user signal delay the diagnostic path.

It is worth being precise about what the mask does not contain, because the membership list is easy to guess wrong. SIGABRT is not in it: abort() is a library call that sends an ordinary asynchronous signal to the caller, not a trap the CPU raised, so there is no faulting instruction for the kernel to stay close to. SIGKILL is not in it either, and does not need to be — a fatal SIGKILL never reaches the dequeue path at all, because complete_signal() has already begun tearing the group down before get_signal() gets a chance to choose anything.

The priority is also structurally limited to the first bitmap word. Reading next_signal() again with that in mind, the special case is applied to *s &~ *m — word zero only — and the loop over the remaining words does a plain lowest-number scan with no mask test. On x86_64 and ARM64 that limitation is invisible, because _NSIG_WORDS is 1 and every signal lives in word zero. It mattered on 32-bit architectures, where signals 33 through 64 occupied a second word; the six synchronous signals are all below 32, so putting the test in the first-word fast path lost nothing and saved the general loop from carrying a mask comparison it would almost never satisfy.

The extra masks real_blocked and saved_sigmask exist to make restartable waits behave correctly. During rt_sigtimedwait(), Linux may temporarily widen the interest set while preserving the caller's original mask in real_blocked so it can be restored after the wait completes. If a handler runs during that window, saved_sigmask works with TIF_RESTORE_SIGMASK to reapply the pre-wait mask after signal delivery returns to user mode. User space never sees these snapshots directly, but without them the kernel could not combine signal waits, handler execution, and restart semantics without losing the caller's original blocking state.

Describing real_blocked as a save slot undersells it, though, because the send path reads it too. The sequence in do_sigtimedwait() is exact: copy blocked into real_blocked, intersect blocked with the complement of the wait set so the awaited signals become deliverable, sleep, then restore from real_blocked and clear it. While that window is open, real_blocked holds the caller's original mask, which by construction includes the very signals the thread is waiting for.

Two decisions elsewhere in the kernel consult it, and both would otherwise go wrong. sig_task_ignored() tests sigismember(&t->blocked, sig) || sigismember(&t->real_blocked, sig) before it is willing to conclude that a signal with an ignored disposition can be discarded at generation time — a signal someone is explicitly waiting for must not be optimized away just because no handler is installed for it. complete_signal() makes the same test before treating a signal as fatal to the whole thread group, so a thread sleeping in sigwaitinfo() on SIGTERM receives it as a wait result rather than being killed by it. The right way to read real_blocked is therefore not “the saved mask” but “signals this thread has claimed”: it tells the generation path to keep its hands off.

Signal Actions and Handlers

A process-level disposition answers the question “what should happen if signal N becomes deliverable?” User space sees this through struct sigaction, but the kernel stores each installed action as struct k_sigaction inside the thread group's sighand_struct. The wrapper lets the kernel keep the user ABI layout while attaching architecture-specific details such as a separate restorer slot when needed.

This is a subtle but important modernization over the old 2.6/i386 mental model. In the older text, a handler descriptor was often described as if it primarily mapped one signal number to one function pointer. That is still true at the surface, but in Linux 7.0.12 a disposition also encodes restart policy, alternate-stack use, exposure of tagged fault bits, masking rules while the handler runs, and whether the kernel should pass a full siginfo_t plus ucontext_t. A handler is therefore less like a callback pointer and more like a compact policy object. 



struct sigaction {
    __sighandler_t sa_handler;
    unsigned long  sa_flags;
#ifdef __ARCH_HAS_SA_RESTORER
    __sigrestore_t sa_restorer;
#endif
    sigset_t       sa_mask;
};

struct k_sigaction {
    struct sigaction sa;
#ifdef __ARCH_HAS_KA_RESTORER
    __sigrestore_t ka_restorer;
#endif
};

The sa_flags field in struct sigaction is a bitmask that controls how the kernel delivers the signal, what state it saves, and how it interacts with related subsystems such as syscall restart and child-process notification. The default disposition is represented in-band by SIG_DFL, while complete ignore is represented by SIG_IGN. Linux never stores a separate “kind” field for these cases. Instead, get_signal() compares the installed handler pointer against those sentinel values and then chooses the default, ignore, or user-handler path. That is the same conceptual model as in the older kernel, but today it is wrapped in more policy flags and more architecture-specific return machinery.

One more modern detail is SA_IMMUTABLE, an in-kernel flag used to kill the race between forced fatal signals and concurrent disposition changes. User space cannot request it through the UAPI. It exists because modern Linux has far more internal producers of fatal signals—seccomp, ptrace, kernel threads acting on behalf of user workers, namespace-aware permission paths—so the kernel needs a way to make some default actions stick once the process is already being torn down.

The mechanism that keeps SA_IMMUTABLE unreachable from user space is worth naming, because it also solves an older and more general problem. sa_flags is one 64-bit field shared between the UAPI and the kernel's own private bits, and the kernel draws the line with a single mask, UAPI_SA_FLAGS, built in include/linux/signal_types.h from the seven publicly documented flags plus __ARCH_UAPI_SA_FLAGS — which expands to SA_RESTORER on architectures that define it, such as x86, and to zero on those that do not, such as ARM64. Every action entering or leaving the kernel is intersected with that mask, so SA_IMMUTABLE (0x00800000, deliberately outside it) can never be set by a caller and never appears in a value read back.

Masking on the way out is the part that had to be invented, and SA_UNSUPPORTED is the fossil of the bug it fixes. Kernels older than this rule stored whatever flag bits user space supplied and returned them unchanged through the oldact argument, which meant a program could not tell the difference between a kernel that implemented a new flag and one that had merely preserved a bit it did not understand. Modern kernels clear unknown bits, so a program can install an action with a candidate flag set, read the action back, and check whether the bit survived. That test needs a control, and SA_UNSUPPORTED (0x00000400) is it: a flag defined only to be rejected, so that a bit which does survive proves the kernel is an old one that preserves everything rather than a new one that genuinely supports the flag under test. A BUILD_BUG_ON in do_sigaction() asserts that no architecture ever accidentally adds it to UAPI_SA_FLAGS. Section 5.3 follows the rest of the installation path.

The restorer mechanism is one of the places where the architecture ABI leaks straight into the data structures. On x86_64, SA_RESTORER is effectively mandatory, so glibc's sigaction() wrapper always fills sa_restorer with a trampoline that eventually issues rt_sigreturn. ARM64 can instead use the vDSO entry point __kernel_rt_sigreturn, so user space does not have to supply its own trampoline on every installation. The optional ka_restorer field in k_sigaction exists for architectures that need a kernel-side restorer pointer distinct from the user-visible struct sigaction payload.

Installing a new handler is also intentionally atomic at the shared-table level. The whole of do_sigaction() runs under siglock, so the copy into the action[] slot is indivisible with respect to every other thread in the group: because they all point at the same sighand_struct, a thread inspecting that signal number sees either the old disposition or the new one, never a half-written mixture. The old action is returned to the caller, which is what lets user space chain handlers or restore an earlier policy exactly. Installation does more than write the slot — it can also discard signals that are already pending — but that is delivery policy rather than data-structure layout, and Section 5.3 covers it.

One further structure belongs here even though it is never stored anywhere: struct ksignal, defined alongside k_sigaction in include/linux/signal_types.h. It is a three-field value — a copy of the k_sigaction, a copy of the kernel_siginfo_t, and the signal number — that get_signal() fills in on the stack of the thread that is about to take a handler. 



struct ksignal {
    struct k_sigaction ka;
    kernel_siginfo_t   info;
    int                sig;
};

The copies are the point. By the time architecture code runs, siglock has been dropped and the queue node has been freed, so nothing the frame builder needs can still be reached through current->sighand without re-acquiring the lock — and it must not, because writing a signal frame touches user memory and can sleep. struct ksignal is therefore the exact width of the generic-to-architecture interface described in Section 1.3: everything the two frame builders in Sections 4.4 and 4.5 are allowed to know, snapshotted under the lock and carried out on the stack.

The Signal Handler Descriptor

The structure that ties all per-process signal policy together is sighand_struct. Threads created with CLONE_SIGHAND share one instance, so a handler installation by any thread immediately becomes visible to all threads in the group. This matches the POSIX rule that dispositions are process-wide even though masks and private pending signals are per-thread. The old i386 chapter described the same sharing rule, but Linux 7.0.12 makes the shared ownership more obvious by centering the lock and the signalfd wait queue in the same object.

The companion object is signal_struct. It represents state that is shared by all threads but is not itself the handler table: group-exit progress, group-stop counts, the shared pending queue, the current wakeup target, coredump coordination, and several per-process timer facilities. The split between sighand_struct and signal_struct looks verbose at first. In practice it mirrors the split between “how should signals be handled?” and “what is the process-wide signal state right now?” 



struct sighand_struct {
    spinlock_t          siglock;
    refcount_t          count;
    wait_queue_head_t   signalfd_wqh;
    struct k_sigaction  action[_NSIG];
};

struct signal_struct {
    refcount_t          sigcnt;

    struct core_state  *core_state;
    struct rlimit       rlim[RLIM_NLIMITS];
    ...
};

The presence of signalfd_wqh inside sighand_struct is a good example of Linux 7.0.12's broader view of signals. In the 2.6 era, the dominant question was whether a thread would take a traditional handler on its user stack. Modern Linux still supports that path, but it also lets an event loop consume signals like readable bytes on a file descriptor. The same shared object therefore wakes both the classic return-to-user path and the poll()/epoll() path.

The ellipsis at the end of the signal_struct excerpt hides a great deal, and it is worth knowing roughly what kind of thing lives there: the thread list (thread_head) and the wait_chldexit queue that wait4() sleeps on, the group-exec fields notify_count and group_exec_task, the POSIX interval timers and CPU-time accounting for the process, the controlling terminal, and the whole rlim[] array. That last item explains an oddity a reader will notice elsewhere in this chapter: RLIMIT_SIGPENDING is read out of signal_struct, but the queued signals it limits are charged to a ucounts object instead, because the limit is per-process while the accounting is per-user-namespace.

One hidden field deserves its own explanation, because it exists to close a race that has no other visible trace in the code: struct hlist_head multiprocess. Consider a kill() aimed at a process group, arriving at the instant one of its members is midway through fork(). The child does not yet appear in the process group, so the send skips it; a moment later it is running, having never seen a signal that was, by wall-clock reasoning, sent to it.

Linux closes the window from the fork side. Before copy_process() does anything expensive it puts a stack-allocated struct multiprocess_signals on its parent's multiprocess list — but only for a real fork, not for CLONE_THREAD, since a new thread joins an existing group rather than becoming a new target. From that moment until the child is linked into the process tree, every process-directed send in __send_signal_locked() walks the list and records the signal number in each in-flight fork's private set, taking care not to leave a stop and a SIGCONT recorded at the same time. When the child is finally installed, the accumulated set is assigned straight into its shared_pending.signal bitmap, so the child begins life with those signals already pending.

Two details of that mechanism are instructive. The recording is bitmap-only — no sigqueue node, therefore no siginfo payload — which is the same “deliver at least once, payload optional” bargain the standard signals accept everywhere else. And the fork path itself is signal-aware in the other direction: immediately after registering, copy_process() checks whether the parent has a signal pending and, if so, abandons the fork with -ERESTARTNOINTR rather than creating a child while the parent is about to run a handler. The parent's fork() is then transparently restarted by the machinery described in Chapter 10.

The curr_target field in signal_struct is another modern performance hint. When a process-directed signal is queued, complete_signal() does not want to start its search from thread zero every time. It keeps a rotating preferred target so that repeated sends can spread wakeups across a thread group without repeatedly scanning from the leader. That policy did not exist in the simpler mental models presented by older single-thread-focused texts.

The lifecycle of sighand_struct is almost a miniature ownership case study. Linux allocates one during fork unless the new task is explicitly sharing it through CLONE_SIGHAND, and the embedded refcount records how many task_struct objects still point at that handler table. Each exiting thread drops its reference; when the count reaches zero, the structure can finally be freed. During exec, if the current table is still shared, unshare_sighand() allocates a private copy so the exec'ing task gets its own dispositions without having to coordinate per-exec updates across another thread group or the original parent.

The signalfd_wqh field is what connects the classic signal machinery to the file-descriptor world. When __send_signal_locked() queues a signal on either pending list, it also calls signalfd_notify(), which wakes waiters sleeping on this wait queue head. That is why poll(), select(), and epoll() on a signalfd react immediately when a matching signal arrives. The wait queue lives in sighand_struct because the wakeup behavior is coupled to the same thread-group-wide dispositions and mask coordination that all sharers already observe.

Pending Signal Queues

A pending signal is one that has been generated but not yet delivered. Between generation and delivery, the kernel needs somewhere to remember that the signal exists, which number it carries, and—when the sender provided one—what siginfo payload accompanies it. The pending queues are that storage. They sit at the exact boundary between the send side, which only records intent, and the delivery side, which later interprets it. Understanding their two-layer shape is the key to understanding why standard and real-time signals behave so differently under load.

Concretely, each pending set is represented by struct sigpending, which contains a linked list of queued objects plus a bitmap that says which signal numbers are currently represented in that list. Each queued instance is a struct sigqueue carrying one kernel_siginfo_t payload and one ucounts reference for accounting. Linux keeps both a private pending set in each thread and a shared pending set in the thread group's signal_struct.

This dual-queue model is the most important structural difference between “signal for a thread” and “signal for a process.” Thread-directed signals—faults, tgkill(), ptrace injections—go to task_struct.pending. Process-directed signals—kill() to a thread group, terminal job-control signals, many parent/child notifications—go to signal_struct.shared_pending and are claimed by whichever eligible thread eventually dequeues them. Private and shared pending sets already existed in Linux 2.6, but modern code gives them more work because multithreaded programs are the norm rather than the exception. 



struct sigqueue {
    struct list_head list;
    int flags;
    kernel_siginfo_t info;
    struct ucounts *ucounts;
};

struct sigpending {
    struct list_head list;
    sigset_t signal;
};

These two structures divide the labor cleanly. The signal bitmap inside sigpending answers the fast question—"is any signal of number N pending?"—with a single bit test, which is exactly what the return-to-user path needs before it commits to the more expensive dequeue logic. The list preserves the payload-bearing sigqueue nodes in arrival order, so that when a signal is finally dequeued the kernel can hand back the correct siginfo and, for real-time signals, deliver multiple queued instances in FIFO order. The bitmap and the list are kept consistent under siglock: adding a node sets the corresponding bit, and removing the last node of a given number clears it.

The split between the private set in task_struct and the shared set in signal_struct is what makes the "thread versus process" distinction concrete at the data-structure level. The move from plain struct siginfo to kernel_siginfo_t matters here more than anywhere else, and the difference between the two types is not what the names suggest. Both are generated from the same macro, __SIGINFO, which lays out si_signo, si_errno, si_code, and the _sifields union. The user-visible siginfo_t then wraps that in a second union whose other arm is int _si_pad[SI_MAX_SIZE/sizeof(int)], padding the whole thing out to a fixed 128 bytes so the ABI has room to grow. kernel_siginfo_t is the same layout without that padding — roughly 48 bytes on a 64-bit kernel.

That is a storage decision, not a semantic one, and the pending queues are exactly where it pays off: a sigqueue node embeds its payload by value, so the smaller type shrinks every queued instance by around 80 bytes, and a process at its RLIMIT_SIGPENDING ceiling pins correspondingly less unreclaimable kernel memory. The tail is not lost, only deferred: copy_siginfo_to_user() writes the populated fields and zero-fills the remainder, so user space still receives a full 128-byte siginfo_t. The rule that makes this safe is that the kernel must never copy out a partially initialized payload, which is why producers call clear_siginfo() before filling in the fields they care about.

Queue nodes are the storage points where the kernel keeps provenance: sender credentials, fault address, timer overrun counts, ptrace trap numbers, seccomp system-call metadata, and user payloads from sigqueue(). The old 2.6 code had the same broad idea, but fewer producers needed such rich metadata. As Linux accumulated seccomp, pidfds, and architecture-specific fault annotations, the queue payload became an even more central object.

Each queued sigqueue node also carries a ucounts pointer so Linux can charge that pending instance against a RLIMIT_SIGPENDING budget in the correct user namespace — the receiving task's budget, as Section 6.3 examines. When delivery, flushing, or teardown finally frees the node, the kernel releases the charge through the same accounting object. This namespace-aware accounting replaced the older model of one global per-user counter. As a result, a containerized workload cannot consume the queued-signal budget of a different namespace merely because both environments happen to use the same numeric UID.

Memory pressure exposes the semantic difference between standard and real-time signals. If __send_signal_locked() cannot allocate a new sigqueue—because a GFP_ATOMIC allocation fails or because RLIMIT_SIGPENDING is already exhausted—Linux can still fall back to setting only the bitmap bit for an ordinary standard signal. That preserves “deliver at least once” behavior even when the detailed siginfo payload is lost, whereas a real-time signal send must fail with -EAGAIN if the exact queued instance cannot be created. The SIGQUEUE_PREALLOC flag marks nodes reserved ahead of time, such as timer-owned queue entries; when __sigqueue_free() meets one it drops a reference through posixtimer_sigqueue_putref() and returns, leaving the node to its owner rather than handing it back to the allocator.

It is worth separating the two independent accountings a queue node is subject to, because they are easy to conflate. The ucounts charge is the policy limit: it is taken before the allocation is attempted, in sig_get_ucounts(), and refused when the receiving task's user is already at RLIMIT_SIGPENDING in that user namespace. The refusal is normally silent: print_dropped_signal() exists to log it, but it returns immediately unless the print_fatal_signals sysctl has been turned on, and even then it is rate-limited to ten messages every five seconds. A system quietly losing signal payloads to a resource limit will not say so in dmesg unless an administrator asked it to. The memory itself comes from a dedicated slab cache, sigqueue_cachep, created with SLAB_ACCOUNT so the pages are also charged to the sending process's memory cgroup. A send can therefore fail for two quite different reasons — one process exceeding its own pending-signal quota, one container running out of memory — and only the first of them is visible as -EAGAIN with a comprehensible cause.

Operations on Signal Data Structures

The pending queues introduced in the previous section are not passive containers. Linux continuously repairs, flushes, and sometimes duplicates them so that the bitmaps in struct sigpending, the handler table in struct sighand_struct, and the thread flag TIF_SIGPENDING all describe the same reality. These operations look like background maintenance, but in Linux 7.0.12 they are the glue that keeps signal state coherent across thread exit, fork, and exec.

It helps to group the operations by the life-cycle event that triggers them. Maintenance helpers—flush_signals(), flush_signal_handlers(), and recalc_sigpending()—keep a running task's state self-consistent. Inheritance helpers—copy_sighand(), copy_signal(), and calculate_sigpending()—decide what a child shares or copies at fork. A reset step inside begin_new_exec() normalizes state when a process replaces its image. Finally, teardown helpers free the queues and drop structure references when a thread or thread group exits. The rest of this section walks through each group in that order.

The most direct cleanup helper is flush_signals() in kernel/signal.c. It takes sighand->siglock, clears TIF_SIGPENDING, and empties both the thread-private queue task_struct.pending and the thread-group queue signal_struct.shared_pending by calling flush_sigqueue() on each. Kernel threads and teardown paths use it when a task should not carry any more deferred signal work forward. 

void flush_signals(struct task_struct *t)
{
    unsigned long flags;

    spin_lock_irqsave(&t->sighand->siglock, flags);
    clear_tsk_thread_flag(t, TIF_SIGPENDING);
    flush_sigqueue(&t->pending);
    flush_sigqueue(&t->signal->shared_pending);
    spin_unlock_irqrestore(&t->sighand->siglock, flags);
}

void flush_signal_handlers(struct task_struct *t, int force_default)
{
    int i;
    struct k_sigaction *ka = &t->sighand->action[0];
    for (i = _NSIG ; i != 0 ; i--) {
        if (force_default || ka->sa.sa_handler != SIG_IGN)
            ka->sa.sa_handler = SIG_DFL;
        ka->sa.sa_flags = 0;
        sigemptyset(&ka->sa.sa_mask);
        ka++;
    }
}

void recalc_sigpending(void)
{
    if (!recalc_sigpending_tsk(current) && !freezing(current)) {
        if (unlikely(test_thread_flag(TIF_SIGPENDING)))
            clear_thread_flag(TIF_SIGPENDING);
    }
}

Under the hood, flush_signals() delegates the real work to flush_sigqueue(), which clears the bitmap with sigemptyset() and then walks the list, unlinking every sigqueue node and releasing it through __sigqueue_free(). That free step is where the node's ucounts charge against RLIMIT_SIGPENDING is returned, so flushing is not just forgetting a signal—it is also giving back the accounting budget the sender consumed.

flush_signal_handlers() performs a different kind of reset: it walks the handler table and restores dispositions to SIG_DFL, leaving SIG_IGN entries alone unless the caller passes a force flag. That is exactly what begin_new_exec() wants after unshare_sighand() makes the table private during execve(). The same helper also appears in the fork path when CLONE_CLEAR_SIGHAND asks for copied handler slots to be normalized before the child runs.

recalc_sigpending() is the cheap bookkeeping step that makes deferred delivery work, and it is worth reading carefully because TIF_SIGPENDING means more than "a signal is pending." Its worker, recalc_sigpending_tsk(), sets the flag when there is an unblocked signal in either the private or shared queue, but also when the task carries job-control work (JOBCTL_PENDING_MASK), a pending freeze trap (JOBCTL_TRAP_FREEZE), or a frozen cgroup state. The flag is really a single-bit summary of "the return-to-user path must stop and look," which is why architecture code can gate all of this behind one inexpensive test.

There is a deliberate asymmetry in how the flag is updated. recalc_sigpending_tsk() only ever sets the flag; it never clears it, because clearing it in the wrong context—another thread, or the current thread while a syscall is about to return one of the -ERESTART* codes—would silently drop pending work. Only recalc_sigpending() clears the bit, and only for current when it can prove no work remains. A related helper, calculate_sigpending(), runs early in a freshly forked child under siglock: it optimistically sets TIF_SIGPENDING and then calls recalc_sigpending(), guaranteeing the new task re-examines any signal that arrived during the fork.

Fork and exec split signal state differently. copy_sighand() in kernel/fork.c either shares the parent's sighand_struct by incrementing its refcount when CLONE_SIGHAND is set, or allocates a fresh table and copies every action slot. copy_signal() makes the same choice one layer higher: CLONE_THREAD shares the process-wide signal_struct, while an ordinary fork allocates a new one with its own shared_pending, counters, and timer state. During execve(), begin_new_exec() clears sas_ss_sp and sas_ss_size, unshares the handler table, and flushes handlers back to defaults; pending signals survive the image change, but any signal whose default action is to ignore will simply be discarded when delivery later re-evaluates the new disposition.

Teardown closes the loop that the intro promised. When a thread exits, __exit_signal() in kernel/exit.c detaches it from the thread group and, for the last thread, tears down the shared pending queue. Both the per-thread sighand_struct and signal_struct are reference-counted, so freeing is lazy: __cleanup_sighand() calls refcount_dec_and_test() and only when the count reaches zero does it run signalfd_cleanup() and return the object to sighand_cachep. Because that cache is created with SLAB_TYPESAFE_BY_RCU, a concurrent lookup that raced with the free still sees a validly typed object, which is exactly what lock_task_sighand() relies on when it grabs the lock of a task that may be exiting.

That guarantee is narrower than it first sounds, and the small sighand_ctor() function passed to kmem_cache_create() is what makes it usable. SLAB_TYPESAFE_BY_RCU promises only that freed memory is never handed to a different cache before an RCU grace period elapses; the same memory may be reissued as another sighand_struct immediately. A racing lock_task_sighand() can therefore end up spinning on a lock that now belongs to an unrelated thread group — which is safe, because it re-reads task->sighand under the lock and retries if it changed, but only so long as the bytes it took the lock on are still a validly initialized spinlock_t.

That is precisely what the constructor guarantees. sighand_ctor() performs the two initializations that must survive reuse — spin_lock_init() on siglock and init_waitqueue_head() on signalfd_wqh — and because a slab constructor runs once when the backing page is populated rather than on each allocation, those fields remain valid across free and reallocation. The pattern is worth recognizing: whenever a cache combines SLAB_TYPESAFE_BY_RCU with a constructor, the constructor is not an allocation-time optimization but the invariant that makes the lockless lookup legal.

Signal Generation

Signal generation begins whenever some kernel path decides that a signal should become pending for a task or a thread group. The producer may be a system call such as kill() or tgkill(), an internal helper such as force_sig_info(), a synchronous exception such as a page fault that becomes SIGSEGV, or a subsystem such as POSIX timers, tty job control, or seccomp. The send side therefore needs to do three jobs reliably: validate permissions, decide whether the signal is thread- or process-directed, and queue or collapse it according to signal type.

Linux 7.0.12 funnels most of that work through a compact stack of helpers in kernel/signal.c. For ordinary sends the shape is do_send_sig_info() → send_signal_locked() → __send_signal_locked() → complete_signal(). Compared with Linux 2.6, the interesting change is not the names themselves but the additional policy encoded around them: user-namespace-aware credential rewriting, RLIMIT_SIGPENDING charging through ucounts, pidfd scopes, and tighter integration with signalfd and coredump wakeups.

Before any of that runs, a user-initiated send must clear two gates: target selection and permission. Target selection is where the sign of the pid argument to kill() is interpreted by kill_something_info(): a positive pid targets one thread group through kill_proc_info(); pid == 0 targets the caller's process group; pid < -1 targets the process group -pid; and the broadcast pid == -1 walks every eligible task except init and the caller. The broadcast case is more particular than it sounds: it skips every task whose PID in the caller's namespace is 1 and every member of the caller's own thread group, remembers the last error that was not -EPERM, and returns -ESRCH only when it found no candidate at all. A kill(-1, sig) that was refused for every single target therefore still reports success.

Permission is enforced by check_kill_permission(). Kernel-internal senders skip it outright: si_fromuser() is true only when info is the SEND_SIG_NOINFO sentinel or carries a non-positive si_code, so anything stamped SI_KERNEL—including every forced fault signal described in Section 3.5—is exempt by construction rather than by an explicit privilege test. For a genuine user send, the audit layer sees the attempt first through audit_signal_info(), which may refuse on its own. The credential test then allows the send if the caller and target share a thread group, or if kill_ok_by_cred() matches, or if the caller holds CAP_KILL in the target's user namespace. kill_ok_by_cred() compares four pairs—the caller's effective and real UIDs against the target's saved and real UIDs—and deliberately never consults the target's effective UID. A set-user-ID program that has raised its effective UID therefore gains no protection from the user who started it. SIGCONT gets a small relaxation within the same session, and a final security_task_kill() LSM hook can still veto the operation.

Between those entry points and the queueing core sits send_signal_locked(), a layer with no analogue in Linux 2.6. Its entire job is to compute one boolean—force, the flag that lets a signal past an ignored disposition—and, on the way, to translate the sender's identity into terms the receiver can actually interpret. 

int send_signal_locked(int sig, struct kernel_siginfo *info,
                       struct task_struct *t, enum pid_type type)
{
    /* Should SIGKILL or SIGSTOP be received by a pid namespace init? */
    bool force = false;

    if (info == SEND_SIG_NOINFO) {
        /* Force if sent from an ancestor pid namespace */
        force = !task_pid_nr_ns(current, task_active_pid_ns(t));
    } else if (info == SEND_SIG_PRIV) {
        /* Don't ignore kernel generated signals */
        force = true;
    } else if (has_si_pid_and_uid(info)) {
        struct user_namespace *t_user_ns;

        rcu_read_lock();
        t_user_ns = task_cred_xxx(t, user_ns);
        if (current_user_ns() != t_user_ns) {
            kuid_t uid = make_kuid(current_user_ns(), info->si_uid);
            info->si_uid = from_kuid_munged(t_user_ns, uid);
        }
        rcu_read_unlock();

        /* A kernel generated signal? */
        force = (info->si_code == SI_KERNEL);

        /* From an ancestor pid namespace? */
        if (!task_pid_nr_ns(current, task_active_pid_ns(t))) {
            info->si_pid = 0;
            force = true;
        }
    }
    return __send_signal_locked(sig, info, t, type, force);
}

Three cases set force. A SEND_SIG_PRIV signal is kernel-generated and must not be quietly discarded because user space installed SIG_IGN; a signal carrying SI_KERNEL is treated identically for the same reason. The third case is the one the comment at the top of the function asks about. task_pid_nr_ns(current, task_active_pid_ns(t)) returns zero when the sender has no PID at all in the target's PID namespace, which is precisely the situation of a process signalling into a container. Such a sender lives in an ancestor namespace, is by construction outside the namespace it is signalling into, and is therefore allowed to force the signal past the SIGNAL_UNKILLABLE protection that shields a namespace init from members of its own namespace. That single line is why kill -9 issued on the host works on a container's PID 1 while the identical command issued inside the container does not.

The same block performs the credential rewriting that the send path owes the receiver. When sender and target live in different user namespaces, si_uid is converted back to a kuid in the sender's namespace and then re-expressed with from_kuid_munged() in the target's, so the number a handler eventually reads is meaningful to the process reading it rather than to the process that sent it. When the sender is invisible in the target's PID namespace, si_pid is set to zero rather than reporting an integer the target could not interpret. Identity in a namespaced kernel is not an absolute value carried along with the message; it is a rendering, and this is where the rendering happens.

This send pipeline also explains why the kernel keeps signal generation separate from signal delivery. The send side never builds a user stack frame. Its job ends once the signal is recorded in the right pending set and some thread is woken if necessary. Only later, when a thread is about to resume user mode, does the delivery side interpret that pending state.

The Core Send Path

The real heart of the send side is __send_signal_locked(). By the time this function runs, the caller already holds sighand->siglock and has decided whether the send is private (PIDTYPE_PID) or shared (for example PIDTYPE_TGID). The function first asks prepare_signal() whether the target should accept the signal at all. If the signal is ignored, suppressed for an unkillable init-like task, or overtaken by group-exit state, the helper can return without changing pending state.

prepare_signal() is worth reading closely because it does more than answer yes or no—it also performs state transitions that must happen before the pending bit is set. If the thread group is already exiting (SIGNAL_GROUP_EXIT), it drops the new signal entirely unless a coredump is in progress and the signal is SIGKILL. If the incoming signal is a stop signal, it first flushes any pending SIGCONT from the shared and per-thread queues; if it is SIGCONT, it flushes pending stop signals, clears the stopped state, wakes stopped or traced threads, and records a parent notification. Only after those job-control reconciliations does it apply the final gate, return !sig_ignored(p, sig, force), so that an ignored disposition still short-circuits the send unless force overrides it.

If the signal should proceed, __send_signal_locked() chooses the destination queue, decides whether duplicate standard signals should collapse, and then optionally allocates a sigqueue node. That last step is where modern accounting enters. Allocation goes through sigqueue_alloc(), which charges UCOUNT_RLIMIT_SIGPENDING in the target's user namespace and compares the result against task_rlimit(t, RLIMIT_SIGPENDING). Linux 2.6 charged pending signals to a simple per-user counter; modern Linux makes queued signal memory an explicit, namespace-aware resource. 



static int __send_signal_locked(int sig, struct kernel_siginfo *info,
                                struct task_struct *t,
                                enum pid_type type, bool force)
{
    struct sigpending *pending;
    struct sigqueue *q;
    int override_rlimit;
    int ret = 0, result;

    pending = (type != PIDTYPE_PID) ? &t->signal->shared_pending
                                    : &t->pending;

    if (legacy_queue(pending, sig))
        goto ret;

    if (sig == SIGKILL || (t->flags & PF_KTHREAD))
        goto out_set;

    if (sig < SIGRTMIN)
        override_rlimit = (is_si_special(info) || info->si_code >= 0);
    else
        override_rlimit = 0;

    q = sigqueue_alloc(sig, t, GFP_ATOMIC, override_rlimit);
    if (q) {
        list_add_tail(&q->list, &pending->list);
        switch ((unsigned long) info) {
        case (unsigned long) SEND_SIG_NOINFO:
            clear_siginfo(&q->info);
            q->info.si_signo = sig;
            q->info.si_code  = SI_USER;
            q->info.si_pid   = task_tgid_nr_ns(current,
                                   task_active_pid_ns(t));
            q->info.si_uid   = from_kuid_munged(
                                   task_cred_xxx(t, user_ns),
                                   current_uid());
            break;
        case (unsigned long) SEND_SIG_PRIV:
            clear_siginfo(&q->info);
            q->info.si_signo = sig;
            q->info.si_code  = SI_KERNEL;
            q->info.si_pid   = 0;
            q->info.si_uid   = 0;
            break;
        default:
            copy_siginfo(&q->info, info);
            break;
        }
    } else if (!is_si_special(info) && sig >= SIGRTMIN &&
               info->si_code != SI_USER) {
        result = TRACE_SIGNAL_OVERFLOW_FAIL;
        ret = -EAGAIN;
        goto ret;
    } else {
        result = TRACE_SIGNAL_LOSE_INFO;
    }
out_set:
    signalfd_notify(t, sig);
    sigaddset(&pending->signal, sig);
    complete_signal(sig, t, type);
ret:
    return ret;
}

A small but revealing detail is the call to signalfd_notify() before the pending bit is finalized. Signals are no longer only about stack-based handlers. As soon as the bit is set, any thread watching the shared signalfd_wqh must be able to observe readability. The send path therefore has to notify both the traditional signal-delivery world and the file-descriptor world in one place.

The collapse decision lives in legacy_queue(), a one-line predicate that returns true when sig < SIGRTMIN and that number is already present in the destination bitmap. When it returns true the send jumps straight to the return label without allocating a node, which is exactly why a burst of identical standard signals folds into a single pending instance. Two other cases also skip allocation: SIGKILL and signals aimed at a kernel thread take the out_set shortcut, setting the bit directly because their delivery cannot depend on a possibly failing GFP_ATOMIC allocation.

One more piece of the real function is missing from the excerpt above. Between out_set and the call to complete_signal(), a process-directed send also walks signal->multiprocess, the list of in-flight fork() calls described in Section 2.3, so that a thread group being signalled while it is creating a new thread group cannot lose the signal in the gap between “the child exists” and “the child is reachable.” It is worth knowing that the walk is there, but it is a fork-side concern rather than a send-side one, and it is easier to understand from the copy_process() end.

The other subtlety is the distinction between “must deliver one instance” and “must preserve every payload.” For standard signals sent through paths like kill(), Linux may collapse duplicates and still succeed, even if the second payload is lost. For true queued real-time sends, Linux fails rather than lie. That compromise preserves historical expectations for standard signals while making real-time queues useful for serious event delivery.

The switch on the info argument looks strange until you realize that info is not always a pointer. Two values, SEND_SIG_NOINFO and SEND_SIG_PRIV, are small integer constants cast to struct kernel_siginfo *; they are never dereferenced, and is_si_special() is nothing more than a test for them. They exist so that the overwhelmingly common senders do not have to build a siginfo structure they do not care about. SEND_SIG_NOINFO means “an ordinary user send with no payload,” and the kernel fills in SI_USER plus the sender's PID and UID for it—rendered, once again, in the target's namespaces through task_tgid_nr_ns() and from_kuid_munged(). SEND_SIG_PRIV means “the kernel itself is sending this,” and produces an SI_KERNEL record with zeroed identity fields. Only a real pointer reaches the default arm and is copied verbatim.

The override_rlimit computation immediately above the allocation resolves a conflict between two rules that cannot both hold. RLIMIT_SIGPENDING says a user may not accumulate unbounded queued signals; POSIX says kill() may not fail with -EAGAIN. Linux resolves it by scope: for a standard signal (sig < SIGRTMIN) sent with a special sentinel or with a non-negative si_code—that is, one that did not originate from a queueing interface—the limit is overridden and the allocation is allowed to exceed it. Real-time signals never get the override, which is what makes RLIMIT_SIGPENDING an effective bound on the only queues that can actually grow without limit.

The result variable threaded through the function is not diagnostic clutter. Every exit path assigns one of five outcomes and the epilogue reports it through trace_signal_generate(), giving a tracing tool the ability to distinguish a signal that was ignored from one that was folded into an existing pending instance, and both of those from one that was truly queued. The distinction between the last two outcomes in Table 11-9 is particularly worth having: TRACE_SIGNAL_LOSE_INFO records the case where the kernel could not allocate a queue node but sent the signal anyway with its payload discarded, which is silent by design and otherwise invisible to user space.

Process-Directed vs Thread-Directed Signals

From user space, the difference between a process-directed and a thread-directed signal often looks like a matter of which API you called. Inside the kernel, it is primarily a matter of which pending queue receives the event. A thread-directed signal is deposited in task_struct.pending for one specific task. A process-directed signal is deposited in signal_struct.shared_pending, after which any thread that is both live and unblocked may eventually consume it.

Synchronous faults are almost always thread-directed because they describe the execution of one instruction stream. If thread A dereferences a bad pointer, Linux must report the faulting address to thread A's handler or default action; delivering it to thread B would make the user-space context nonsensical. By contrast, signals like SIGTERM, SIGHUP, or a terminal-generated SIGINT conceptually target the whole program. The kernel therefore queues them as shared pending work and lets one eligible thread claim them.

The old Linux 2.6/i386 discussion already had this distinction, but it mattered less because many examples used single-threaded programs. In Linux 7.0.12 it is central. A modern process may have dozens or hundreds of threads, some blocked in uninterruptible sleep, some masking signals, some acting as dedicated event loops. The process-directed queue gives Linux room to pick a sane delivery point rather than pretending every signal has a natural single-thread owner.

This is also why user programs that care about deterministic receipt often dedicate one thread to signal handling. By blocking a signal in all threads and unblocking it only in the handler thread—or by consuming it through signalfd in exactly one thread—they constrain the generic kernel choice into a predictable design. The kernel still follows the same queueing rules. User space simply arranges the masks so that only one thread is ever eligible.

Choosing a Target Thread

Once a process-directed signal has been queued, Linux still has to decide whether any particular thread should be awakened immediately. That job belongs to complete_signal(). The helper first asks whether the suggested task already wants the signal: it must be alive, not already exiting, not stopped or traced in a way that makes wakeup pointless, and ideally not currently blocking the signal. If so, the kernel wakes that thread directly.

If the suggested task is unsuitable and the thread group has multiple threads, complete_signal() performs a rotating scan starting at signal->curr_target. The scan is deliberately pragmatic rather than “fair” in the formal scheduler sense. It wants the cheapest thread that can make progress on the pending work. That is why Linux may prefer the current thread if it can take the signal, and why it may decline to wake anyone if all eligible threads will naturally notice the pending bit before running again. 



static void complete_signal(int sig, struct task_struct *p, enum pid_type type)
{
    struct signal_struct *signal = p->signal;
    struct task_struct *t;

    if (wants_signal(sig, p))
        t = p;
    else if ((type == PIDTYPE_PID) || thread_group_empty(p))
        return;
    else {
        t = signal->curr_target;
        while (!wants_signal(sig, t)) {
            t = next_thread(t);
            if (t == signal->curr_target)
                return;
        }
        signal->curr_target = t;
    }

    if (sig_fatal(p, sig) && ...)
        ...

    signal_wake_up(t, sig == SIGKILL);
}

The exact test in wants_signal() encodes those intuitions as a short sequence of checks: a thread that has the signal blocked does not want it; a thread with PF_EXITING is already leaving and is skipped; SIGKILL is always wanted; a thread that is stopped or traced is not a useful wakeup target; and otherwise the thread wants the signal only if it is currently running (task_curr()) or does not already have signal work pending. That last clause is the "decline to wake anyone" optimization made concrete—if a runnable thread already has TIF_SIGPENDING set, it will notice the new signal on its own without a second wakeup. When a wakeup is warranted, signal_wake_up_state() sets TIF_SIGPENDING and calls wake_up_state(), falling back to kick_process() to bump a thread already running on another CPU.

The second argument to signal_wake_up() in the excerpt above—sig == SIGKILL—selects between two quite different wakeups. For an ordinary signal the state mask is zero, and signal_wake_up_state() ends up calling wake_up_state(t, TASK_INTERRUPTIBLE): a thread in an interruptible sleep is woken, and a thread that is stopped, traced, or in an uninterruptible sleep is left alone. For a fatal signal the mask becomes TASK_WAKEKILL | __TASK_TRACED and the target's JOBCTL_STOPPED and JOBCTL_TRACED bits are cleared first, so SIGKILL pulls a job-control-stopped or ptrace-stopped thread out of its stop rather than waiting for someone to continue it. The one exception is JOBCTL_PTRACE_FROZEN, where the tracer is mid-operation on the tracee and the stop must not be broken underneath it.

Two details of signal_wake_up_state() repay attention. It never examines t->state before deciding to wake, because the target may be executing on another CPU and entering a stopped state at that very moment; testing the state and then waking would leave a window in which neither branch acts. And when wake_up_state() returns false—meaning the task was not asleep and so was not woken—it calls kick_process() to send a reschedule IPI. That is the mechanism by which a thread spinning in user mode on another CPU is forced through a kernel entry, where it will find the TIF_SIGPENDING flag that was just set for it.

The fatal-signal fast path inside complete_signal() is especially important in modern multithreaded programs. If the signal is fatal to the whole group and is not headed to coredump handling, Linux sets SIGNAL_GROUP_EXIT, stores the exit code, clears stop-related job-control state, injects SIGKILL into sibling threads, and wakes them all. The goal is not elegance; it is containment. Once one thread has a truly fatal signal, Linux wants the whole process to converge on death quickly rather than continue mutating shared state.

That group-wide teardown logic was much less visible in older single-process explanations. Today it is crucial because almost every serious server is multithreaded. A fatal signal is no longer just “the current process dies.” It is “one thread becomes the first observer of a process-wide terminal state, and the kernel uses it to pull every sibling toward the same endpoint.”

Group Stop and Group Exit Signals

Job-control stop signals and fatal group-exit signals deserve separate attention because they do more than queue one pending bit. Signals such as SIGSTOP, SIGTSTP, SIGTTIN, and SIGTTOU can put the whole thread group into a coordinated stop. Linux records this in signal_struct using fields such as group_stop_count and flag bits like SIGNAL_STOP_STOPPED. The mechanics are intentionally distributed across job-control helpers because different threads may notice, consume, and report the stop at different times.

Group exit is the darker mirror image. When Linux decides that a signal should kill the entire process, it sets SIGNAL_GROUP_EXIT, stores a group exit code, and arranges for every sibling to observe a pending SIGKILL or equivalent fatal state. If the terminating signal is coredumping, the kernel coordinates through core_state so that one thread dumps while the rest are frozen and eventually reaped. Compared with Linux 2.6, the same fundamental behavior exists, but the modern kernel is far more explicit about group coordination because threads, ptrace, and coredump handlers all need synchronization.

The reason for this extra machinery is practical. Without it, one thread could be running user code while another already committed the process to a fatal exit or stop state. That would create impossible user-space observations, especially in debuggers and parent wait* callers. Signal generation therefore blends notification with process-state transitions. Signals are not just messages; some of them are distributed state changes for the entire thread group.

This is also why SIGCONT is special when queued. Linux clears stop-related pending state when a continue signal arrives, and stop signals clear pending continue state in the opposite direction. The goal is to preserve the observable semantics of job control rather than naively accumulate contradictory requests. That rule existed in older kernels too, but modern group-stop bookkeeping makes the reason easier to see in the code.

Forced Signals

Most signal-generation paths behave like requests: they check permissions, respect blocked masks, and leave an installed SIG_IGN disposition alone. The forced signal helpers in kernel/signal.c exist for the opposite cases, where the kernel has decided that delivery must happen even if user space tried to ignore or block the signal. They are used for unrecoverable faults, corrupt return frames, and other conditions where “best effort” would leave the task running with broken state. 

void force_sig(int sig)
{
    struct kernel_siginfo info;

    clear_siginfo(&info);
    info.si_signo = sig;
    info.si_code = SI_KERNEL;
    force_sig_info(&info);
}

void force_fatal_sig(int sig)
{
    struct kernel_siginfo info;

    clear_siginfo(&info);
    info.si_signo = sig;
    info.si_code = SI_KERNEL;
    force_sig_info_to_task(&info, current, HANDLER_SIG_DFL);
}

int force_sig_fault_to_task(int sig, int code, void __user *addr,
                            struct task_struct *t)
{
    struct kernel_siginfo info;

    clear_siginfo(&info);
    info.si_signo = sig;
    info.si_code  = code;
    info.si_addr  = addr;
    return force_sig_info_to_task(&info, t, HANDLER_CURRENT);
}

force_sig(int sig) is the baseline helper. It manufactures a kernel-originated siginfo and sends it through force_sig_info(), which makes sure the signal cannot be neutralized by the current blocked mask or by a handler installed as SIG_IGN. If the kernel is forcing a truly fatal outcome, force_fatal_sig(int sig) goes one step further and uses the HANDLER_SIG_DFL mode so the disposition is reset to SIG_DFL before delivery proceeds.

Everything the force helpers do converges on one static function, force_sig_info_to_task(), and its enum sig_handler argument selects among three escalating levels of coercion. HANDLER_CURRENT means “use the installed handler if it is still reachable”; HANDLER_SIG_DFL means “always use default semantics”; and HANDLER_EXIT, reached through force_exit_sig(), means the signal should never be visible to user space at all and should surface only as the process exit code. The distinction matters most for the last one, which is the sole place in the kernel that sets SA_IMMUTABLE on a k_sigaction. That is why the flag discussed in Section 2.2 can never be seen by sigaction(): user space has no way to set it, and a disposition that carries it can no longer be changed.

The reset rule inside the helper is more conditional than “forced signals ignore the handler.” The disposition is rewritten to SIG_DFL only if the signal was blocked, or was set to SIG_IGN, or the caller asked for a mode other than HANDLER_CURRENT; a forced SIGSEGV aimed at a process that installed a genuine handler and left the signal unblocked still runs that handler, which is what makes user-space fault recovery and garbage collectors that trap page faults possible at all. When the signal was blocked, the kernel unblocks it and resets the disposition together, and the comment above the function explains why the two must move as a pair: a handler that user space explicitly blocked must not be invoked behind its back, so the only honest outcome of unblocking is the default action.

The same function is also where a forced signal collides with init protection. SIGNAL_UNKILLABLE marks the init process of a PID namespace, and a forced signal that has arrived at a SIG_DFL disposition clears that flag outright—a namespace init that has genuinely faulted is allowed to die rather than spin forever taking the same trap. The one exception is a traced task, where clearing the flag would let a debugging session accidentally kill init, so the flag survives unless the mode is HANDLER_EXIT, which is fatal unconditionally. Finally, because the target may already have had the signal pending and blocked, the helper ends with an explicit signal_wake_up() for the case where send_signal_locked() found nothing new to do and therefore woke nobody.

The fault-oriented variants attach machine-state detail. force_sig_fault() and force_sig_fault_to_task() package signals such as SIGSEGV, SIGBUS, SIGILL, and SIGFPE together with an si_code and the fault address in si_addr. Architecture trap handlers rely on them so that user space sees the exact address that triggered the exception, even though the signal is still being forced rather than merely requested.

That distinction is the key difference from the normal send path. kill(), tgkill(), and other ordinary interfaces route through permission checks and preserve the target's right to block or ignore most signals until delivery time. The force helpers bypass those policy checks, may rewrite the disposition back to SIG_DFL, and are allowed to override a blocked state. In effect, they say that the kernel's integrity rules outrank the process's preferences.

Common callers make that policy concrete. A bad sigreturn frame leads to force_sig(SIGSEGV); a recursive failure while already trying to report SIGSEGV escalates to force_fatal_sig(SIGSEGV); and architecture exception code uses force_sig_fault() so handlers for page faults, alignment traps, or illegal instructions still get an informative siginfo_t. These are not rare corner cases—they are the last line of defense that turns corrupted control flow back into a controlled process death.

Signal Delivery

Generation records intent; delivery turns that intent into process behavior. Delivery happens when the kernel has a thread in hand and is preparing to return to user mode or to complete a signal-aware wait. The return-to-user machinery in kernel/entry/common.c runs a loop, exit_to_user_mode_loop(), that inspects the thread's work flags; whenever TIF_SIGPENDING or TIF_NOTIFY_SIGNAL is set it calls arch_do_signal_or_restart(). That function asks the generic core whether any signal should be delivered, adjusts interrupted syscall state if necessary, and then asks architecture-specific code to build the user-visible frame.

The two flags are subtly different. TIF_SIGPENDING means a real signal may be deliverable; TIF_NOTIFY_SIGNAL is not a signal at all but a request to run queued task_work callbacks before returning to user space. Both funnel through the same entry because both must break a thread out of a wait and give the kernel a chance to act. That is why get_signal() begins by clearing the notify flag and draining task_work before it ever looks at the pending queues.

The modern delivery pipeline is richer than the Linux 2.6/i386 one for two reasons. First, the generic chooser has to integrate ptrace, freezer hooks, job control, cgroup freezing, coredump initiation, and signalfd-compatible queue semantics. Second, the architecture layer has to save more state. A modern ARM64 task may need FPSIMD, SVE, SME, GCS, TPIDR2, FPMR, or POE records in its frame; a modern x86_64 task may need XSAVE-managed floating-point state and shadow-stack metadata.

The delivery code is therefore where the distance from Linux 2.6 is most visible. The same concepts remain—dequeue a signal, check the disposition, build a frame, jump to the handler, later run rt_sigreturn—but the actual state being preserved and restored is dramatically larger. Signals became a compatibility promise for increasingly complicated machines. The price of that promise is visible in these functions.

Dequeuing Pending Signals

The generic chooser is get_signal(). It is called with no specific signal number in mind; instead it examines the current thread's state and decides whether any unblocked pending signal should be delivered now. Its very first act is to clear TIF_NOTIFY_SIGNAL and drain any queued task_work, because those callbacks must run before the kernel commits to a signal decision. If the thread then has no pending signal work, the function returns false immediately. If pending work exists, Linux calls try_to_freeze() once—it cannot return to user mode while the task is being frozen—and then takes sighand->siglock at the relock label.

The relock label is not decoration; it is the target of five separate restarts, and the shape of the function is a consequence of the fact that almost everything interesting has to drop siglock before it can act. Every thread waking from a stop arrives at relock, which is why the first thing under the lock is the SIGNAL_CLD_MASK test: prepare_signal() encoded a CLD_STOPPED or CLD_CONTINUED notification into those bits when the stop or continue was generated, and the first thread to notice on the way out is the one that reports it to the parent through do_notify_parent_cldstop(). That has to happen under tasklist_lock, not siglock, so the code unlocks, notifies, and jumps back. The same pattern recurs for group stop, for the ptrace job-control traps behind JOBCTL_TRAP_MASK, for the cgroup-v2 freezer trap behind JOBCTL_TRAP_FREEZE, and for cgroup_leave_frozen(). A reader who expects a linear function will find the control flow confusing until they see that the loop exists because state changes and lock ordering, not signal selection, dominate it.

The very first test inside the loop is not about pending signals at all. If SIGNAL_GROUP_EXIT is already set—or group_exec_task is, meaning another thread is in the middle of execve() and this thread must die so the exec can complete—the function fabricates SIGKILL, clears the bit, and jumps straight to the fatal label without dequeuing anything. This is the receiving half of the mechanism described in Section 3.3: complete_signal() set the flag on the sending side and injected SIGKILL into every sibling, and this is where each sibling notices. Because the check precedes dequeuing, a thread group that has committed to dying will not deliver any further signal to any thread, no matter what is queued.

Selection proceeds in an order that is more nuanced than “lowest numbered pending signal.” The kernel first calls dequeue_synchronous_signal(), which gives priority to synchronous fault signals in SYNCHRONOUS_MASK—SIGSEGV, SIGBUS, SIGILL, SIGTRAP, SIGFPE, and SIGSYS—because a signal frame for a fault must describe the exact machine state at the faulting instruction, and its si_addr must match the instruction that trapped. Only if no synchronous fault is queued does the general dequeue_signal() run, taking from the private pending set before the shared pending set. Only after a signal is chosen does Linux consult ptrace and the installed disposition to decide whether the signal should be ignored, transformed, handled, or treated as fatal.

The synchronous priority is narrower than the description above suggests, and the three restrictions are all deliberate. First, dequeue_synchronous_signal() examines only current->pending—the private queue—because a fault belongs to the thread that executed the instruction and can never legitimately arrive through the shared queue. Second, it tests only word zero of the pending bitmap, which is free because every member of SYNCHRONOUS_MASK is below 32 anyway. Third, and most usefully, it requires q->info.si_code > SI_USER. A SIGSEGV that arrived from kill() carries SI_USER and does not jump the queue; only a signal the hardware or the kernel generated as a genuine trap does. The priority exists so that a signal frame describing a fault reports the faulting instruction and a matching si_addr, and a SIGSEGV some other process sent has neither, so it gets no special treatment.

There is one more gate between dequeuing and the disposition test, and it completes a story begun in Section 3.5. A traced thread normally routes every signal except SIGKILL through ptrace_signal(), which lets the tracer inspect, suppress, or substitute it. A disposition carrying SA_IMMUTABLE is exempt: the tracer never sees the signal and cannot cancel it. Since force_exit_sig() is the only thing that sets that flag, the practical statement is that a signal the kernel decided must be fatal cannot be intercepted by a debugger—which is precisely the point of having a mode stronger than “force.”

For queued signals, dequeue_signal() uses the bitmap to find the next number and then collect_signal() to remove one matching queue node, if any, from the linked list. That design avoids linear scans when no candidate of a given number exists. The old i386-era descriptions often treated the queue as a simple list of signal numbers. Modern Linux is deliberately hybrid: bitmap for existence and priority, list for payload and multiplicity.

The fatal default-action path inside get_signal() is where coredump handling begins. If the chosen signal is one for which sig_kernel_coredump(signr) is true, Linux sets PF_SIGNALED, optionally prints diagnostics, calls proc_coredump_connector(), and then enters vfs_coredump(). Only after the coredump work is settled does the thread group exit. So even the seemingly simple question “which signal is next?” can cascade into one of the heaviest control flows in the process life cycle.

Executing the Default Action

Dequeuing a signal does not mean a handler will run. Once get_signal() has picked a pending signal, it immediately inspects the installed disposition in current->sighand->action[]. If the entry names a user handler, delivery continues toward frame construction; if it is SIG_DFL, the kernel must interpret the signal's built-in default action instead. This decision tree is far more than “deliver or kill”.

The easiest branch is sig_kernel_ignore(signr). Signals whose default action is “nothing”—notably SIGCONT, SIGCHLD, SIGWINCH, and SIGURG—are silently skipped when no handler is installed. They may still wake a task, notify a parent, or clear bookkeeping elsewhere in the subsystem, but they do not create a user frame and they do not terminate the process merely because they were dequeued.

Immediately after that branch sits the gate that makes init survivable. If SIGNAL_UNKILLABLE is set on the thread group and the signal is not sig_kernel_only()—that is, not SIGKILL or SIGSTOP—the signal is dropped here, at delivery time, having been queued perfectly normally. This is the rule usually stated as “init gets no signals it does not want”: the global init process and the init of every PID namespace silently discard any default-action signal, which is why a SIGTERM to PID 1 does nothing unless PID 1 installed a handler for it. The complementary half is that a signal that is sig_kernel_only() reaching this point must have been generated internally or forced from an ancestor namespace, so by construction it cannot be dropped. Section 3.5 showed the other side of the same coin: a forced signal that lands on a SIG_DFL disposition clears SIGNAL_UNKILLABLE outright, so an init that genuinely faults is allowed to die.

The stop branch is more involved because it is process-wide. For SIGSTOP, SIGTSTP, SIGTTIN, and SIGTTOU, get_signal() calls do_signal_stop(), which coordinates a group stop across all threads. Job-control stop signals other than SIGSTOP are suppressed for orphaned process groups, because an orphaned group has no session leader left to continue it and stopping it would strand it forever. The check has a cost: is_current_pgrp_orphaned() needs tasklist_lock, which must be taken before siglock, so the kernel drops siglock for the duration. Signals can be posted in that window—including a SIGCONT that invalidates the entire decision—so the code jumps back to relock and re-evaluates rather than committing to a stop it may no longer want. Even when it does call do_signal_stop(), that helper can return false if it lost a race with SIGCONT, in which case the loop simply continues to the next candidate signal.

SIGCONT is special even before delivery reaches this branch. In prepare_signal(), generating SIGCONT flushes all pending stop signals from both private and shared queues, clears job-control stop bits, wakes stopped threads, and sets SIGNAL_CLD_CONTINUED so the parent can later observe a CLD_CONTINUED notification. That behavior is why stop and continue signals feel like state transitions rather than ordinary queued messages: the kernel actively removes contradictory requests instead of letting both accumulate.

Everything else is fatal, but fatal signals still split in two. If sig_kernel_coredump(signr) is true—for signals such as SIGQUIT, SIGILL, SIGABRT, SIGSEGV, SIGBUS, SIGFPE, SIGSYS, SIGTRAP, SIGXCPU, and SIGXFSZ—the kernel sets PF_SIGNALED, enters vfs_coredump(), and only then drives the group through do_group_exit(). For the remaining fatal defaults, Linux simply marks PF_SIGNALED and exits the thread group immediately with that signal number as the exit code.

One class of task is exempt from that final step. A thread carrying PF_USER_WORKER—an io_uring worker, a vhost worker, and similar kernel-managed threads that run inside a user process's address space—must not be terminated by do_group_exit() on the kernel's initiative, because it holds cleanup state the kernel cannot unwind on its behalf. get_signal() therefore jumps past the exit and returns, leaving the worker to observe the fatal condition and tear itself down. This is a comparatively recent accommodation and it exists entirely because Chapter 24's io_uring model put kernel-side worker threads inside ordinary thread groups; the 2.6 kernel had no such category and needed no such exception.

It is worth stating plainly that get_signal() is therefore not a query. Three of its outcomes never return to the caller at all: a group stop parks the thread inside do_signal_stop(), a coredump signal descends into vfs_coredump(), and a fatal signal ends in do_group_exit(). The function returns true only for the handler case and false only for “nothing to deliver.” Reading it as a chooser that reports a decision, rather than as a function that frequently is the decision, makes the architecture code that calls it look far simpler than it is.

Evaluating Signal Flags

Once get_signal() has decided that a user handler should run, the kernel still has to honor the SA_* policy bits stored beside that handler. Some of those flags change the shape of the user-visible frame, some change the temporary blocked mask during handler execution, and some affect entirely different subsystems such as parent-child wait semantics. The important point is that Linux does not evaluate them in one place: signal flags are consumed partly in generic code and partly in architecture-specific frame builders.

SA_SIGINFO is the most visible flag to user space. When it is set, the architecture setup code chooses the real-time frame format and passes three arguments to the handler—(signo, siginfo_t *, ucontext_t *)—instead of the classic single signo. On native x86_64 and ARM64, modern Linux effectively lives in that RT frame world all the time, so SA_SIGINFO mainly decides whether the handler receives the richer calling convention rather than whether the kernel uses an entirely different delivery engine.

SA_ONSTACK redirects delivery to the alternate signal stack if one is configured and currently valid. The actual stack switch happens in helpers such as get_sigframe(), which use sas_ss_sp and sas_ss_size as the top of the alternate stack. SA_RESTART is evaluated in the architecture restart logic rather than in the frame builder itself: when a blocking syscall returns -ERESTARTSYS, Linux converts it to -EINTR unless the chosen handler has SA_RESTART set. Chapter 10, Section 8, covers that restart machinery in detail.

Two flags rewrite signal state immediately around delivery. SA_RESETHAND (also spelled SA_ONESHOT in kernel code) causes get_signal() to reset the handler entry to SIG_DFL before user mode resumes, so the installation is consumed by one delivery. SA_NODEFER changes the temporary blocked mask assembled by signal_delivered(); without it, the delivered signal number is added to the mask for the duration of the handler, while with it the handler remains re-entrant for that signal.

SA_EXPOSE_TAGBITS is the newest flag in the group and the only one evaluated by get_signal() itself, on the very last line before it returns. Unless the handler asked for tag bits, hide_si_addr_tag_bits() runs si_addr through arch_untagged_si_addr() for every fault-shaped siginfo layout. The flag exists because ARM64 Memory Tagging and the Top-Byte-Ignore ABI put non-address bits in the high byte of a pointer, and a handler written before those features existed would compare si_addr against its own untagged pointers and never match. Rather than change the meaning of an existing field, Linux strips the tag by default and lets an aware handler opt back in. Note that the masking happens after the handler was chosen, so two handlers for different signals in the same process can legitimately see the same faulting address with and without its tag.

Once the handler is committed, signal_delivered() performs four distinct pieces of bookkeeping, only one of which is the mask update. It clears the restore-sigmask flag, because the saved mask is now stored in the frame and rt_sigreturn will restore it—the mechanism rt_sigsuspend() depends on, described in Section 5.5. It assembles the new blocked mask from sa_mask plus, unless SA_NODEFER is set, the delivered signal. If the alternate signal stack was registered with SS_AUTODISARM, it resets the stack so that a nested signal cannot reuse it while the handler is running. And if the thread was being single-stepped, it issues a ptrace_notify(SIGTRAP, 0), which is why a debugger stepping through code stops again the moment a handler is entered.

Its sibling signal_setup_done() is the failure path, and it is worth naming because the failure is not rare in badly behaved programs. If the architecture frame builder could not write to the user stack—an exhausted stack, an unmapped alternate stack, a bad sa_restorer—the kernel calls force_sigsegv() on the same signal. That is a forced signal in the sense of Section 3.5, so it resets the disposition to SIG_DFL and cannot itself be caught; a process whose SIGSEGV handler overflows the stack therefore dies rather than recursing forever.

The child-related flags are evaluated later, during process-state bookkeeping rather than at frame setup time. SA_NOCLDSTOP suppresses SIGCHLD notifications for child stops and continues, while SA_NOCLDWAIT tells the exit path to auto-reap children instead of leaving zombies for wait*. They share storage with the delivery flags, but they are really policies for parent-notification code such as do_notify_parent() and group-stop reporting.

Setting Up the Signal Frame (x86_64)

Once get_signal() returns a deliverable signal with a user handler, x86_64 enters handle_signal() in arch/x86/kernel/signal.c. That helper resolves syscall-restart edge cases, saves VM86 quirks for compatibility modes, and then delegates actual frame construction to x64_setup_rt_frame() in arch/x86/kernel/signal_64.c. Linux 7.0.12 always uses the real-time frame format for native 64-bit delivery. The older non-RT frame formats survive only for compat ABIs such as IA32 emulation.

Before any of that, however, setup_rt_frame() does something that has nothing to do with frames and everything to do with a much newer kernel facility: its very first statement is rseq_signal_deliver(ksig, regs). Restartable sequences let user space run a short critical section — a per-CPU counter update, a lock-free list push — without atomics, on the promise that if the thread is preempted or migrated part-way through, the kernel will redirect it to an abort handler rather than let it commit inconsistent state. Signal delivery is the third event that breaks that promise, and it must be handled here because the moment the frame is written the saved instruction pointer no longer refers to the critical section at all. The comment in __rseq_signal_deliver() says exactly that: identity fields can be updated later on the way out to user mode, but the critical section has to be aborted now, because after this point the instruction pointer in regs points to the signal handler.

The abort works by reading the rseq_cs pointer out of the thread's registered struct rseq and, if one is armed, rewriting the saved ip to the sequence's abort address. If that user memory cannot be read — the page is gone, or the pointer is garbage — the kernel cannot know whether the sequence would have committed, and it refuses to guess: force_sigsegv() converts the delivery into an unblockable SIGSEGV using the forced-signal machinery of Section 3.5. A program that unmaps its own rseq area and then takes a signal is therefore killed rather than silently resumed mid-sequence. The wrapper in include/linux/rseq.h makes all of this free for the overwhelming majority of threads, which have never called rseq(): it tests has_rseq (or, for the v2 ABI, user_irq) and returns immediately, and compiles to nothing at all when CONFIG_RSEQ is off.

The x86_64 frame contains three visible components. First comes the restorer pointer, which is the user-space trampoline that will eventually invoke rt_sigreturn. Then comes a full ucontext, including register state, the saved signal mask, alternate-stack metadata, and a pointer to floating-point state. Finally, if SA_SIGINFO is set, Linux copies a siginfo record into the frame and loads the first three argument registers so the handler sees (signo, siginfo_t *, ucontext_t *). 



struct rt_sigframe {
    char __user *pretcode;
    struct ucontext uc;
    struct siginfo info;
    /* fp state follows here */
};

int x64_setup_rt_frame(struct ksignal *ksig, struct pt_regs *regs)
{
    sigset_t *set = sigmask_to_save();
    struct rt_sigframe __user *frame;

    if (!(ksig->ka.sa.sa_flags & SA_RESTORER))
        return -EFAULT;

    frame = get_sigframe(ksig, regs, sizeof(struct rt_sigframe), &fp);
    unsafe_put_user(ksig->ka.sa.sa_restorer, &frame->pretcode, Efault);
    unsafe_put_sigcontext(&frame->uc.uc_mcontext, fp, regs, set, Efault);
    unsafe_put_sigmask(set, frame, Efault);
    copy_siginfo_to_user(&frame->info, &ksig->info);

    regs->di = ksig->sig;
    regs->si = (unsigned long)&frame->info;
    regs->dx = (unsigned long)&frame->uc;
    regs->ip = (unsigned long)ksig->ka.sa.sa_handler;
    regs->sp = (unsigned long)frame;
    return 0;
}

The frame is written to the normal user stack unless SA_ONSTACK and an alternate signal stack are active, in which case get_sigframe() redirects the write to that alternate stack. That part is conceptually unchanged since Linux 2.6. What changed is the amount of architectural state that may trail behind the visible rt_sigframe header. On a machine with XSAVE, x86_64 may append large FPU or vector state regions whose size is computed dynamically.

Another modern wrinkle is control-flow hardening. The x86 code can interact with shadow-stack support when present, and it forcibly clears three EFLAGS bits before entering the handler. DF is cleared because the System V ABI requires the direction flag to be clear on function entry and the handler is, from the compiler's point of view, an ordinary function. RF is cleared because leaving the resume flag set would suppress a debug exception the handler might legitimately need to take. TF is cleared so that a SIGTRAP handler entered because of a trap flag does not immediately trap again and recurse. Signals are effectively indirect function calls manufactured by the kernel, so the architecture code must leave the CPU in a state that obeys the ABI for ordinary function entry. That was always true in spirit; modern security features simply make the requirement more explicit in the code.

One consequence of handle_signal() that surprises people is fpu__clear_user_states(). After the frame is written, x86_64 resets the FPU to its initial state before jumping to the handler. The handler therefore does not inherit the interrupted code's floating-point or vector registers; it starts clean, and the real state lives only in the frame until rt_sigreturn puts it back. This is the correct behavior—the handler is a fresh function call and has no business seeing whatever was in %zmm when the signal arrived—but it means a handler cannot be used to inspect the interrupted floating-point state directly. It has to read the state out of the ucontext it was handed.

Single-stepping is handled on both sides of the frame build. If TIF_SINGLESTEP is set, handle_signal() calls user_disable_single_step() before saving registers, so that the sigcontext the handler sees is not polluted by a trap flag the debugger set rather than the program. It then passes the stepping flag down to signal_setup_done(), which turns it into the ptrace_notify() described in Section 4.3. The tracer therefore observes handler entry as a distinct event, with clean register state, rather than as a mysterious jump.

Setting Up the Signal Frame (ARM64)

ARM64 follows the same broad model but uses a markedly different frame layout. It also opens with the same rseq_signal_deliver() call, placed at the top of its own handle_signal() rather than in a wrapper — the restartable-sequence abort described in Section 4.4 is generic code invoked identically by both architectures, and it is the one part of frame setup that is not architecture-specific at all. In arch/arm64/kernel/signal.c, the user-visible header is struct rt_sigframe { struct siginfo info; struct ucontext uc; }. The simple two-field header is followed by an extensible reserved area that holds optional context records. Linux 7.0.12 uses that space for FPSIMD, fault ESR data, GCS state, SVE, SME, TPIDR2, FPMR, POE, ZA, and ZT records depending on CPU capabilities and task state.

This is one of the clearest places where Linux 7.0.12 differs from Linux 2.6. The old ARM and x86 chapters could treat a signal frame as a mostly fixed block. Modern ARM64 cannot. The architecture deliberately standardized a record-based extension area so that future vector or control-flow features can be preserved across signal delivery without breaking the existing ABI. That is why the code spends so much effort computing sigframe_size() and laying out optional records before writing anything irreversible. 



struct rt_sigframe {
    struct siginfo info;
    struct ucontext uc;
};

static int setup_return(struct pt_regs *regs, struct ksignal *ksig,
                        struct rt_sigframe_user_layout *user, int usig)
{
    __sigrestore_t sigtramp;

    if (ksig->ka.sa.sa_flags & SA_RESTORER)
        sigtramp = ksig->ka.sa.sa_restorer;
    else
        sigtramp = VDSO_SYMBOL(current->mm->context.vdso, sigtramp);

    err = gcs_signal_entry(sigtramp, ksig);
    if (err)
        return err;

    /* We must not fail from this point onwards. */

    regs->regs[0] = usig;
    if (ksig->ka.sa.sa_flags & SA_SIGINFO) {
        regs->regs[1] = (unsigned long)&user->sigframe->info;
        regs->regs[2] = (unsigned long)&user->sigframe->uc;
    }
    regs->sp = (unsigned long)user->sigframe;
    regs->regs[29] = (unsigned long)&user->next_frame->fp;
    regs->regs[30] = (unsigned long)sigtramp;
    regs->pc = (unsigned long)ksig->ka.sa.sa_handler;

    if (system_supports_bti()) {
        regs->pstate &= ~PSR_BTYPE_MASK;
        regs->pstate |= PSR_BTYPE_C;
    }
    regs->pstate &= ~PSR_TCO_BIT;

    if (system_supports_sme()) {
        task_smstop_sm(current);
        current->thread.svcr &= ~SVCR_ZA_MASK;
        write_sysreg_s(0, SYS_TPIDR2_EL0);
    }
    return 0;
}

Note that regs[1] and regs[2] are loaded only when SA_SIGINFO is set. The frame layout itself is unconditional—ARM64 writes a full rt_sigframe containing both siginfo and ucontext for every signal—so what the flag actually controls on this architecture is nothing more than whether the handler is told where those records are. A handler installed without SA_SIGINFO receives one argument and simply never learns that the other two structures are sitting on its stack.

The comment in the middle of the function marks a real design constraint rather than a note of caution. Everything that can fail—including gcs_signal_entry(), which pushes a return address onto the Guarded Control Stack when GCS is enabled—must happen before the first register is modified. Once sp and pc have been rewritten, a failure could no longer be reported by delivering a nested SIGSEGV: the subsequent rt_sigreturn from the nested handler would restore the half-built state of the original delivery. The ordering is what makes signal_setup_done()'s force_sigsegv() path safe.

ARM64 also differs in how it chooses the restorer trampoline. If user space supplied SA_RESTORER, Linux honors that. Otherwise the kernel points the link register at the vDSO-provided sigtramp helper. This is a pleasant contrast with x86_64, where the 64-bit ABI effectively expects SA_RESTORER to be present. The high-level guarantee is identical, but the ABI contract is cleaner on ARM64.

A second ARM64-specific nuance is execution state sanitization, and the three cases in the tail of setup_return() are each worth naming. When BTI is available the kernel sets PSR_BTYPE_C, which makes the CPU behave exactly as if the handler had been reached by a BLR through a register. The effect is that delivering a signal to an address inside a PROT_BTI page that is not a valid function entry point raises SIGILL, just as an indirect call to that address would. PSR_TCO_BIT—the Memory Tagging check-override bit—is cleared unconditionally, so a handler always runs with tag checking in whatever mode the process configured, never with checks suppressed because the interrupted code happened to have suppressed them. And when SME is present the kernel leaves streaming mode, clears the ZA state, and zeroes TPIDR2_EL0, because a handler that knows nothing about SME must not run in streaming mode with a live tile.

The unifying idea is that a signal handler is entered from an unpredictable point in the program, so every piece of ambient processor mode that the interrupted code could have altered has to be normalized to a defined value first. Signals therefore become one of the main points where architecture-specific state must be scrubbed. That is a modern problem created by modern hardware; 2.6-era i386 had far less state to scrub, which is why frame setup there was little more than a memory copy.

The Signal Return Path

A signal handler does not return to the interrupted instruction directly. Instead it returns to a user-space trampoline, and that trampoline issues the rt_sigreturn system call. The kernel then treats the user-built frame as authoritative state to restore: signal mask, alternate-stack state, general registers, floating-point state, and architecture-specific extensions. This separation lets the kernel keep the signal ABI stable even though the interrupted code may have no idea a signal ever happened.

The mask handling forms a clean symmetry with delivery. Just before the handler ran, signal_delivered() added the action's sa_mask—and, unless SA_NODEFER was set, the delivered signal itself—to current->blocked, and it saved the previous mask into the frame's uc.uc_sigmask. On the way out, rt_sigreturn reads that saved mask back and calls set_current_blocked(), so the thread resumes with exactly the mask it had before delivery. The handler's temporary blocking is therefore invisible to the interrupted code, which is precisely the guarantee POSIX requires.

On x86_64, sys_rt_sigreturn() in arch/x86/kernel/signal_64.c reads the frame from the current stack pointer, restores the blocked mask, reinstalls alt-stack state, calls restore_sigcontext(), and repairs shadow-stack metadata if needed. On ARM64, sys_rt_sigreturn() in arch/arm64/kernel/signal.c validates alignment, restores the blocked mask, parses optional extension records through restore_sigframe(), repairs GCS state if enabled, and restores the alt stack. The high-level semantic contract is identical even though the state space is not. 



/* x86_64 */
SYSCALL_DEFINE0(rt_sigreturn)
{
    struct pt_regs *regs = current_pt_regs();
    struct rt_sigframe __user *frame;
    sigset_t set;

    frame = (struct rt_sigframe __user *)(regs->sp - sizeof(long));
    if (!access_ok(frame, sizeof(*frame)))
        goto badframe;
    if (__get_user(*(__u64 *)&set, (__u64 __user *)&frame->uc.uc_sigmask))
        goto badframe;

    set_current_blocked(&set);

    if (restore_altstack(&frame->uc.uc_stack))
        goto badframe;
    if (!restore_sigcontext(regs, &frame->uc.uc_mcontext, uc_flags))
        goto badframe;
    if (restore_signal_shadow_stack())
        goto badframe;

    return regs->ax;

badframe:
    signal_fault(regs, frame, "rt_sigreturn");
    return 0;
}

/* ARM64 */
SYSCALL_DEFINE0(rt_sigreturn)
{
    struct pt_regs *regs = current_pt_regs();
    struct rt_sigframe __user *frame;

    /* Always make any pending restarted system calls return -EINTR */
    current->restart_block.fn = do_no_restart_syscall;

    if (regs->sp & 15)
        goto badframe;

    frame = (struct rt_sigframe __user *)regs->sp;
    if (!access_ok(frame, sizeof(*frame)))
        goto badframe;
    if (restore_sigframe(regs, frame, &ua_state))
        goto badframe;
    if (gcs_restore_signal())
        goto badframe;
    if (restore_altstack(&frame->uc.uc_stack))
        goto badframe;

    restore_user_access_state(&ua_state);
    return regs->regs[0];

badframe:
    arm64_notify_segfault(regs->sp);
    return 0;
}

In older 32-bit discussions, sigreturn and rt_sigreturn often appeared as parallel interfaces. For native x86_64 and ARM64, only rt_sigreturn matters. The old non-RT return path survives only for compatibility ABIs, mirroring the way native 64-bit user space relies almost exclusively on the real-time signal syscalls for installation, masking, and waiting. That simplification is one reason the modern signal ABI is easier to describe even though the underlying hardware state is more complex.

Two small oddities in the excerpts above are worth decoding, because both look like bugs and neither is. On x86_64 the frame is located at regs->sp - sizeof(long) rather than at regs->sp: the restorer trampoline was entered by a ret that popped the pretcode word off the frame, so by the time rt_sigreturn executes, the stack pointer sits one word above where the frame begins. And both handlers end by returning a register they have just restored—regs->ax on x86_64, regs->regs[0] on ARM64—which is the idiom for “this system call has no return value of its own.” The syscall exit path will write the returned value into the result register, so the function returns whatever the restored context already contains, leaving the interrupted code's register untouched.

ARM64 does one thing on the way out that x86_64 does not, and it matters for the restart machinery. Before touching the frame it sets current->restart_block.fn = do_no_restart_syscall, cancelling any pending restart_syscall() continuation. A -ERESTART_RESTARTBLOCK syscall such as nanosleep() stashes its remaining work in the restart block; if a handler ran and then returned, that continuation is stale, and reviving it would resume a sleep the program has already been told was interrupted. Making it return -EINTR instead is the conservative choice. Section 5.9 and Chapter 10, Section 8, cover the restart protocol this belongs to.

The return path is also where the kernel defends itself against malicious or corrupted user frames. The signal frame lives in user memory that the handler was free to modify, so rt_sigreturn is, quite literally, a request to load machine state from untrusted storage. Both architectures therefore funnel every failure into a single badframe label: x86_64 calls signal_fault(), which optionally logs the offending frame, instruction pointer, and stack pointer under the show_unhandled_signals sysctl and then issues force_sig(SIGSEGV); ARM64 calls arm64_notify_segfault() with the offending stack pointer. Both are forced signals in the sense of Section 3.5, so a process cannot install a SIGSEGV handler and use a corrupt sigreturn frame to keep running.

The checks themselves are more than access_ok(). restore_sigcontext() rejects a context whose extended-state area does not describe a valid XSAVE layout, ARM64's parse_user_sigframe() walks the record chain and refuses a record with an unknown magic, a duplicate of one it has already seen, a record describing a feature the CPU does not support, a misaligned offset, or a length that would run past the end of the reserved area, and both architectures validate the alternate-stack descriptor. ARM64 additionally requires the stack pointer to be sixteen-byte aligned before it will even look at the frame. The one thing neither can validate is the restored program counter, which is why sigreturn-oriented programming—forging a frame and calling rt_sigreturn to load arbitrary registers—remains a real exploitation technique. That is the gap the shadow-stack and GCS restore steps close. On delivery, both architectures push a token onto the hardware-protected shadow stack; on return, restore_signal_shadow_stack() and gcs_restore_signal() verify that the token at the current shadow stack pointer is the one this delivery pushed, and ARM64 zeroes it afterwards so it cannot be replayed. The frame is still untrusted, but a forged sigreturn now has to be matched by a token in memory the process cannot write, which it is not.

Signal-Related System Calls

The user-visible API for signals still clusters around the same five jobs as in Linux 2.6: send a signal, install or inspect a disposition, change the blocked mask, suspend until a signal arrives, or synchronously wait for one of several queued signals. What changed in Linux 7.0.12 is the default assumption that the real-time ABI variants are the canonical interfaces. In Linux 2.6 the legacy syscalls still mattered because 32-bit user space used them heavily. For native x86_64 and ARM64, the legacy forms are now mostly historical footnotes.

Two further interfaces sit slightly outside that list and are covered here because nothing else in the chapter accounts for them. sigaltstack() does not send, mask, or wait for anything; it configures the memory a future frame will be built in, and it is the only reason a stack-overflow SIGSEGV can be reported to the program that caused it. restart_syscall() is stranger still: it is a real system call with a real number that no program ever calls, because the kernel injects it into a thread's register state on the way back to user mode. Both are included in Table 11-14 for completeness, and both are discussed at the end of this section.

The system calls are thin wrappers around the generic data structures described earlier. rt_sigaction() copies a user structure into one k_sigaction slot. rt_sigprocmask() edits current->blocked after stripping out unmaskable signals. rt_sigtimedwait() temporarily inverts a mask and then reuses the same dequeue logic that the asynchronous return path uses. In other words, the user ABI is broad, but most of it is different ways of reaching the same core queues and masks.

A pattern repeats across all of them and is worth naming before the details arrive. Each real-time entry point validates sigsetsize against sizeof(sigset_t), copies user memory in and out at the wrapper level, and then delegates every semantic decision to a helper — do_sigaction(), sigprocmask(), do_sigtimedwait(), do_sigaltstack() — that is also reachable from the compat entry points and, in several cases, from the kernel's own internal callers. The consequence for a reader is that the SYSCALL_DEFINE bodies in kernel/signal.c are almost never where the interesting behavior lives; they are marshalling code, and the policy is one call deeper. Every one of them also unconditionally strips SIGKILL and SIGSTOP from whatever set it was handed, which is the single invariant that keeps the two uncatchable signals uncatchable no matter which interface is used.

One major addition since the 2.6 timeframe is pidfd_send_signal(). It addresses a problem old Unix APIs never solved cleanly: a numeric PID can be recycled between lookup and use, while a pidfd remains a stable handle to a particular task or thread group. That is exactly the kind of improvement modern Linux likes to add. It preserves the old API for compatibility and adds a new descriptor-based API for correctness.

Sending Signals: kill, tgkill, and tkill

The oldest sending interface is kill(). Linux packages the request into a kernel_siginfo using prepare_kill_siginfo() and then routes it through kill_something_info(). Depending on the sign of the pid argument, that may mean one thread group, one process group, or a broadcast across all permitted targets. From the signal subsystem's point of view, however, kill() is just a policy-rich front end for ultimately reaching group_send_sig_info() or kill_pid_info_type().

prepare_kill_siginfo() is worth reading closely, because it is where the kernel decides what a handler will be told about the sender. It clears the structure, sets si_errno to zero, and then makes one branch that user space can actually observe: si_code becomes SI_TKILL when the target type is PIDTYPE_PID and SI_USER otherwise. That single bit of provenance is how a handler distinguishes a signal sent with tkill() or tgkill() from one sent with kill(), and it is also what the forgery checks discussed below key on. The other two fields are equally deliberate: si_pid is set from task_tgid_vnr(current), not the sender's thread ID, so a handler can never learn which thread of a multithreaded sender signalled it; and si_uid is first translated into the sender's own user namespace, only to be re-translated into the receiver's namespace later in send_signal_locked() (Section 3.1).

tgkill() and tkill() are both thread-directed interfaces. They exist because a multithreaded process needs a way to direct a signal at one specific thread rather than whichever thread happens to claim a shared pending signal first. The crucial difference is that tgkill() validates both the thread ID and the thread-group ID, which closes the classic race where a dying thread's numeric ID could be reused before the signal is delivered. That is why tgkill() is the interface to prefer in modern code.

Both funnel through do_tkill() into a single helper, do_send_specific(), and the whole of the difference between them is one term in one condition. The helper takes the RCU read lock, resolves the thread with find_task_by_vpid(pid), and then accepts the target only if (p && (tgid <= 0 || task_tgid_vnr(p) == tgid)). tkill() passes tgid = 0 and short-circuits that test; tgkill() passes a real thread-group ID and forces the comparison. Two further details of the helper matter to anyone writing against it. First, sig == 0 is treated as a pure probe: permission and existence are checked and the result returned, but do_send_sig_info() is never called, which is what makes tgkill(tgid, tid, 0) a liveness test. Second, if lock_task_sighand() fails inside the send — meaning the thread was released between the lookup and the send — the resulting -ESRCH is deliberately converted to success, because from the caller's point of view a thread that dies immediately after receiving a private signal is indistinguishable from one that received it and then died. 



SYSCALL_DEFINE2(kill, pid_t, pid, int, sig)
{
    struct kernel_siginfo info;
    prepare_kill_siginfo(sig, &info, PIDTYPE_TGID);
    return kill_something_info(sig, &info, pid);
}

SYSCALL_DEFINE3(tgkill, pid_t, tgid, pid_t, pid, int, sig)
{
    if (pid <= 0 || tgid <= 0)
        return -EINVAL;
    return do_tkill(tgid, pid, sig);
}

SYSCALL_DEFINE2(tkill, pid_t, pid, int, sig)
{
    if (pid <= 0)
        return -EINVAL;
    return do_tkill(0, pid, sig);
}

These syscalls are easy to treat as mere API surface. In Linux 7.0.12 their real significance is how precisely they name a target. If you choose kill(), you are opting into process-directed delivery and the kernel's target-thread selection policy. If you choose tgkill(), you are naming the thread yourself and bypassing that later choice. The queueing code stays mostly the same; the destination queue changes.

These sending syscalls also highlight one of Linux's long-term compatibility strategies. Nothing prevents the kernel from adding a better interface such as pidfd_send_signal(), but the old numeric-PID interfaces keep working because too much software depends on them. The result is an interface family that looks redundant unless you understand the historical accumulation of race fixes and threading requirements.

A related pair of syscalls lets user space attach a payload to the send. rt_sigqueueinfo() and its thread-directed sibling rt_tgsigqueueinfo() accept a full siginfo_t from the caller, which is what makes real-time signals carry a value or pointer to the handler's si_value. The kernel guards this power in do_rt_sigqueueinfo(): a process may not forge kernel-originated metadata or impersonate a kill()/tgkill() send to another process. Concretely, if si_code >= 0 or si_code == SI_TKILL, the target must be the caller itself; otherwise the send is rejected with -EPERM. That check keeps the queued-payload interface from becoming a way to spoof signal provenance.

The two clauses of that test cover two different kinds of lie. Recall from Section 3.1 that a non-negative si_code means “generated by a user process,” so si_code >= 0 blocks the obvious forgery of claiming a send came from somewhere it did not; the explicit SI_TKILL clause exists only because SI_TKILL is negative and would otherwise slip through. Everything else — every negative kernel-originated code such as SI_KERNEL, SI_TIMER, or a fault code like SEGV_MAPERR — is refused outright for any target. Note also that the comparison is task_pid_vnr(current) != pid, the caller's thread ID, so “to yourself” here means the calling thread's TID and not the thread-group ID that kill() would take.

The two entry points then diverge in routing. rt_sigqueueinfo() hands off to kill_proc_info(), and the comment above it explains why there is no negative-pid broadcast form: “POSIX.1b doesn't mention process groups.” rt_tgsigqueueinfo() rejects pid <= 0 || tgid <= 0 up front, repeats the same forgery check, and then reuses do_send_specific(), inheriting the thread-group validation described above. Both also have COMPAT_SYSCALL_DEFINE twins that differ only in running the incoming structure through __copy_siginfo_from_user32(), because the 32-bit siginfo_t layout is not the native one.

pidfd_send_signal — Race-Free Signaling

pidfd_send_signal() is the modern answer to PID reuse races. A pidfd refers to a live process object rather than a naked integer that might later be recycled for some unrelated task. The syscall therefore accepts a file descriptor, resolves it to struct pid, optionally overrides scope with flags such as PIDFD_SIGNAL_THREAD, validates namespace reachability, and then reuses the ordinary kill_pid_info_type() or process-group helpers.

Scope is settled in two stages, and the order matters. The descriptor itself carries a default: pidfd_to_pid() resolves the file — accepting either a real pidfd or, through tgid_pidfd_to_pid(), a /proc/<pid> directory descriptor — and the syscall then reads f_flags & PIDFD_THREAD to decide between PIDTYPE_PID and PIDTYPE_TGID. Only afterwards does do_pidfd_send_signal() let an explicit flag override that inference. Two guards keep the flag space honest: any bit outside PIDFD_SEND_SIGNAL_FLAGS is rejected with -EINVAL, and hweight32() rejects a request that names more than one scope at a time, so PIDFD_SIGNAL_THREAD | PIDFD_SIGNAL_PROCESS_GROUP is an error rather than a silent precedence rule. PIDFD_SIGNAL_PROCESS_GROUP is the interesting one: it is the only way to signal an entire process group without ever naming it by a recyclable number, and it is routed to kill_pgrp_info() rather than kill_pid_info_type().

Namespace reachability is enforced by access_pidfd_pidns(), which walks the parent chain from the target's PID namespace looking for the caller's active namespace. If the caller's namespace is not an ancestor, the call fails. The chosen error is worth noticing: it is -EINVAL, not -EPERM or -ESRCH, because the descriptor is being judged unusable rather than the send being judged forbidden. The same asymmetry appears in the forged-siginfo check, which repeats the rt_sigqueueinfo() rule but adds one clause: type > PIDTYPE_TGID. That means a caller-supplied siginfo can never accompany a process-group send at all, even to a group the caller belongs to, because “this is a signal I sent to myself” has no coherent meaning once the target is a set of processes. A mismatch between the sig argument and kinfo.si_signo is likewise -EINVAL.

Linux 7.0.12 also lets a task use this interface on itself without owning a descriptor at all. Two reserved negative values, PIDFD_SELF_THREAD (-10000) and PIDFD_SELF_THREAD_GROUP (-10001), are recognized by the syscall before any file lookup happens; the UAPI headers expose them under the friendlier names PIDFD_SELF and PIDFD_SELF_PROCESS. They exist because raise() and pthread_kill(pthread_self(), ...) are common enough that forcing a self-signalling program to open, use, and close a pidfd would be pure overhead. The pattern is not specific to signals: the same reserved constants are defined in include/uapi/linux/fcntl.h alongside FD_PIDFS_ROOT and FD_NSFS_ROOT, and they are part of a general convention for descriptor-shaped APIs that need a well-known “self” operand.

The elegance of this interface is that it adds correctness without inventing a new signal-delivery mechanism. Once the pidfd is resolved and policy checks pass, Linux feeds the request into the same send path used by traditional APIs. That means all the familiar semantics—permission checks, standard versus real-time queueing, signalfd wakeups, target-thread selection—still apply. Only the object-identification stage is different, and that is precisely the stage where old Unix APIs were weakest. 



static int do_pidfd_send_signal(struct pid *pid, int sig, enum pid_type type,
                                siginfo_t __user *info, unsigned int flags)
{
    kernel_siginfo_t kinfo;

    switch (flags) {
    case PIDFD_SIGNAL_THREAD:
        type = PIDTYPE_PID;
        break;
    case PIDFD_SIGNAL_THREAD_GROUP:
        type = PIDTYPE_TGID;
        break;
    case PIDFD_SIGNAL_PROCESS_GROUP:
        type = PIDTYPE_PGID;
        break;
    }

    if (info) {
        ret = copy_siginfo_from_user_any(&kinfo, info);
        if (unlikely(ret))
            return ret;
        if (unlikely(sig != kinfo.si_signo))
            return -EINVAL;
        /* Only allow sending arbitrary signals to yourself. */
        if ((task_pid(current) != pid || type > PIDTYPE_TGID) &&
            (kinfo.si_code >= 0 || kinfo.si_code == SI_TKILL))
            return -EPERM;
    } else {
        prepare_kill_siginfo(sig, &kinfo, type);
    }

    if (type == PIDTYPE_PGID)
        return kill_pgrp_info(sig, &kinfo, pid);

    return kill_pid_info_type(sig, &kinfo, pid, type);
}

SYSCALL_DEFINE4(pidfd_send_signal, int, pidfd, int, sig,
                siginfo_t __user *, info, unsigned int, flags)
{
    /* Enforce flags be set to 0 until we add an extension. */
    if (flags & ~PIDFD_SEND_SIGNAL_FLAGS)
        return -EINVAL;
    /* Ensure that only a single signal scope determining flag is set. */
    if (hweight32(flags & PIDFD_SEND_SIGNAL_FLAGS) > 1)
        return -EINVAL;

    switch (pidfd) {
    case PIDFD_SELF_THREAD:
        pid = get_task_pid(current, PIDTYPE_PID);
        type = PIDTYPE_PID;
        break;
    case PIDFD_SELF_THREAD_GROUP:
        pid = get_task_pid(current, PIDTYPE_TGID);
        type = PIDTYPE_TGID;
        break;
    default: {
        CLASS(fd, f)(pidfd);
        if (fd_empty(f))
            return -EBADF;
        pid = pidfd_to_pid(fd_file(f));
        if (IS_ERR(pid))
            return PTR_ERR(pid);
        if (!access_pidfd_pidns(pid))
            return -EINVAL;
        /* Infer scope from the type of pidfd. */
        if (fd_file(f)->f_flags & PIDFD_THREAD)
            type = PIDTYPE_PID;
        else
            type = PIDTYPE_TGID;
        return do_pidfd_send_signal(pid, sig, type, info, flags);
    }
    }

    ret = do_pidfd_send_signal(pid, sig, type, info, flags);
    put_pid(pid);
    return ret;
}

This interface did not exist in Linux 2.6. The kernel added it only after pidfds themselves became a first-class process-management primitive. The broader lesson is that modern Linux increasingly prefers stable kernel objects over ambient global namespaces. Signals followed that trend by gaining a descriptor-based sender just as process waiting and monitoring gained pidfd-based helpers.

For library and runtime designers, pidfd_send_signal() also composes better with event-driven code. The same pidfd can be polled for lifecycle events and later used to signal the target without re-looking it up by number. That unification is not specific to signals, but signals benefit from it as much as any other process-control operation.

Changing Signal Actions: rt_sigaction

rt_sigaction() installs or queries one disposition entry in the shared handler table. The syscall is intentionally thin. It validates that the user supplied a full-width sigset_t, copies the new user struct sigaction into a kernel wrapper, invokes do_sigaction(), and then copies out the old action if requested. All the interesting policy—refusing immutable signals, handling architecture restorer details, resetting flags, and synchronizing with concurrent sends—lives below the syscall wrapper.

The important modernization over Linux 2.6 is not the existence of rt_sigaction() itself; that syscall is old. What changed is that native 64-bit user space effectively treats it as the only real interface. The historical plain sigaction entry point remains for older ABIs, but modern programs, libraries, and runtimes live on the real-time form because only it scales naturally with 64-bit masks and queued payloads. 



SYSCALL_DEFINE4(rt_sigaction, int, sig,
                const struct sigaction __user *, act,
                struct sigaction __user *, oact,
                size_t, sigsetsize)
{
    struct k_sigaction new_sa, old_sa;

    if (sigsetsize != sizeof(sigset_t))
        return -EINVAL;
    if (act && copy_from_user(&new_sa.sa, act, sizeof(new_sa.sa)))
        return -EFAULT;

    ret = do_sigaction(sig, act ? &new_sa : NULL, oact ? &old_sa : NULL);
    if (ret)
        return ret;
    if (oact && copy_to_user(oact, &old_sa.sa, sizeof(old_sa.sa)))
        return -EFAULT;
    return 0;
}

One reason the wrapper stays simple is that dispositions are process-wide and relatively infrequent compared with queue operations. Linux pays a lock and copy cost here without apology. The hot path is delivery, not handler installation. That asymmetry already held in Linux 2.6, and it remains true today.

The real policy lives in do_sigaction(). It rejects any attempt to change the action of a sig_kernel_only() signal—SIGKILL and SIGSTOP can never be caught or ignored—and it refuses to touch an entry marked SA_IMMUTABLE, the in-kernel flag used to protect forced fatal signals. It also masks the incoming flags with UAPI_SA_FLAGS, clearing bits the running kernel does not recognize so that user space can probe for feature support by reading the old action back.

Two ordering details are easy to miss and occasionally surprising. The sig_kernel_only(sig) rejection is written as act && sig_kernel_only(sig), so it fires only on an attempt to change the disposition; a query with act == NULL is legal for SIGKILL and SIGSTOP and returns their permanently-SIG_DFL entries. The SA_IMMUTABLE rejection, by contrast, is unconditional and happens before oact is filled in, so an immutable disposition — one installed by force_exit_sig(), as Section 3.5 described — cannot even be read back. Between those two checks the syscall calls sigaction_compat_abi(), a weak hook that on x86 stamps SA_IA32_ABI or SA_X32_ABI into the stored flags when the installing call came in through a compat entry point; that is how the frame builder later knows which ABI's frame to construct for a signal installed by a 32-bit process.

The flag masking deserves more than a passing mention because it defines a user-space feature-probing protocol. UAPI_SA_FLAGS is the set of flags the running kernel actually understands, and both the incoming and outgoing sa_flags are reduced to it, which means a program can install a flag, read the action back, and see whether the bit survived. That protocol only works on kernels new enough to do the masking at all, so the UAPI reserves one bit — SA_UNSUPPORTED (0x400) — that will never be implemented. A BUILD_BUG_ON in do_sigaction() guarantees it is never accidentally added to UAPI_SA_FLAGS. A program that sets SA_UNSUPPORTED and reads it back still set is talking to a pre-masking kernel and must fall back to version-based assumptions; a program that reads it back clear knows the probe itself is trustworthy.

The most consequential detail is a POSIX requirement that surprises many programmers: changing a disposition can discard already-pending signals. Following POSIX 3.3.1.3, when do_sigaction() installs SIG_IGN—or installs SIG_DFL for a signal whose default action is to ignore, such as SIGCHLD—it flushes every pending instance of that signal from both the shared queue and each thread's private queue, whether or not the signal was blocked. 

if (act) {
    bool was_ignored = k->sa.sa_handler == SIG_IGN;

    sigdelsetmask(&act->sa.sa_mask,
                  sigmask(SIGKILL) | sigmask(SIGSTOP));

    /* POSIX 3.3.1.3: setting SIG_IGN (or SIG_DFL for an
     * ignore-by-default signal) discards pending instances. */
    if (sig_handler_ignored(sig_handler(p, sig), sig)) {
        sigemptyset(&mask);
        sigaddset(&mask, sig);
        flush_sigqueue_mask(p, &mask, &p->signal->shared_pending);
        for_each_thread(p, t)
            flush_sigqueue_mask(p, &mask, &t->pending);
    } else if (was_ignored) {
        posixtimer_sig_unignore(p, sig);
    }
}

The more interesting point for readers is conceptual, and it needs one careful qualification. Installing a real handler does not retroactively transform already-pending signals: the pending queues store occurrences, while the disposition table stores the policy consulted later when those occurrences become deliverable. The exception is precisely the ignore case above—switching to SIG_IGN is defined to erase what is already pending. Linux keeps sends cheap and policy changes explicit, but it honors this one POSIX-mandated interaction where a disposition change reaches back into the queues.

There is a second, less well known interaction, and it runs in the opposite direction. The else if (was_ignored) arm calls posixtimer_sig_unignore() when a signal that had been set to SIG_IGN is given any non-ignoring disposition. The reason is that a POSIX interval timer whose expiry signal is ignored does not simply throw its expiries away — the timer subsystem parks the timer's preallocated sigqueue entry rather than queueing it, precisely because a real-time timer signal is supposed to be a countable event. When the disposition stops ignoring the signal, those parked timers must be requeued so the program does not silently miss the next expiry. This is one of the few places where a signal's disposition table and the timer subsystem are directly coupled, and it exists only because a preallocated queue entry has an identity that survives being ignored, whereas an ordinary send does not. Section 6.4 returns to those preallocated entries.

Blocking and Unblocking Signals: rt_sigprocmask

rt_sigprocmask() edits the calling thread's blocked mask. Like older sigprocmask() interfaces, it supports three operations: add to the mask, remove from the mask, or replace it entirely. The kernel first snapshots the old mask, copies in the new one if present, and then forcibly strips SIGKILL and SIGSTOP from the requested set. No process may block those two signals, because doing so would destroy core Unix control semantics.

The snapshot ordering is a documented behavior, not an accident: old_set is captured before anything is applied, so a caller that passes the same pointer for nset and oset still reads back the mask as it was on entry. Argument validation is split across two levels, which produces one mildly surprising error ordering. The sigsetsize check and the copy_from_user() happen in the syscall wrapper, while the how value is not examined until the switch inside sigprocmask(). A call that passes both an invalid how and an unreadable nset therefore reports -EFAULT, never -EINVAL. sigprocmask() itself is trivial — sigorsets() for SIG_BLOCK, sigandnsets() for SIG_UNBLOCK, plain assignment for SIG_SETMASK — and it reads current->blocked without a lock, justified by a comment stating the invariant the whole design rests on: only the thread itself ever writes its own mask, and never from interrupt context.

The relationship between the blocked mask and pending queues is subtle. Masking a signal never discards it; it only prevents asynchronous delivery for the moment. The pending bit and any queued payload stay recorded until the signal is unblocked or consumed through a synchronous wait interface. That is why the signal subsystem can support patterns such as “block in all threads, then collect through signalfd or rt_sigtimedwait() in one place.”

Unblocking has an asymmetry worth stating plainly. Because a mask change can make an already-pending signal deliverable, __set_task_blocked() ends with a call to recalc_sigpending(), which recomputes TIF_SIGPENDING from the two pending bitmaps and the new mask. A thread can therefore acquire work to do at the next return to user mode without any sender having run at all — the signal arrived earlier and was simply invisible until the mask moved. The write path is also short-circuited: __set_current_blocked() compares the new set against the old with sigequalsets() and returns immediately if nothing changed, so a redundant SIG_SETMASK never takes siglock. 



SYSCALL_DEFINE4(rt_sigprocmask, int, how, sigset_t __user *, nset,
                sigset_t __user *, oset, size_t, sigsetsize)
{
    sigset_t old_set, new_set;

    if (sigsetsize != sizeof(sigset_t))
        return -EINVAL;

    old_set = current->blocked;
    if (nset) {
        copy_from_user(&new_set, nset, sizeof(sigset_t));
        sigdelsetmask(&new_set, sigmask(SIGKILL) | sigmask(SIGSTOP));
        sigprocmask(how, &new_set, NULL);
    }
    if (oset)
        copy_to_user(oset, &old_set, sizeof(sigset_t));
    return 0;
}

On native x86_64 and ARM64 the full-width mask fits naturally in the ABI. On 2.6-era i386 the real-time form needed more explanation, because the legacy 32-bit interfaces carried smaller masks and therefore could not represent the full signal set cleanly. Here the key fact is simpler: the “rt” prefix no longer suggests something exotic. It means “the only mask interface you should care about on 64-bit Linux.”

Blocking policy also interacts with target-thread selection, and in Linux 7.0.12 that interaction is implemented explicitly rather than left to chance. A process-directed signal stays in the shared queue until some thread with that signal unblocked claims it — but Section 3.3 showed that the sender picked and woke a specific thread at generation time. If that thread later blocks the signal, the wakeup it was holding must be handed back, or the signal would sit in the shared queue with nobody scheduled to look at it. __set_task_blocked() handles exactly this case. 

static void __set_task_blocked(struct task_struct *tsk, const sigset_t *newset)
{
    if (task_sigpending(tsk) && !thread_group_empty(tsk)) {
        sigset_t newblocked;
        /* A set of now blocked but previously unblocked signals. */
        sigandnsets(&newblocked, newset, &current->blocked);
        retarget_shared_pending(tsk, &newblocked);
    }
    tsk->blocked = *newset;
    recalc_sigpending();
}

static void retarget_shared_pending(struct task_struct *tsk, sigset_t *which)
{
    sigset_t retarget;
    struct task_struct *t;

    sigandsets(&retarget, &tsk->signal->shared_pending.signal, which);
    if (sigisemptyset(&retarget))
        return;

    for_other_threads(tsk, t) {
        if (t->flags & PF_EXITING)
            continue;
        if (!has_pending_signals(&retarget, &t->blocked))
            continue;
        /* Remove the signals this thread can handle. */
        sigandsets(&retarget, &retarget, &t->blocked);

        if (!task_sigpending(t))
            signal_wake_up(t, 0);

        if (sigisemptyset(&retarget))
            break;
    }
}

The computation is precise about what needs retargeting. sigandnsets(&newblocked, newset, &current->blocked) yields only the signals that are newly blocked — in the new mask but not the old — because signals that were already blocked were never this thread's responsibility. That set is then intersected with shared_pending.signal, so a thread that blocks a signal nobody has sent does no work at all, and the two cheap guards at the top (task_sigpending() and thread_group_empty()) skip the whole exercise for the overwhelmingly common cases of a single-threaded process or a thread with nothing pending.

The loop that follows is a small scheduling decision. It walks the other threads of the group, skips any that are already exiting, and uses has_pending_signals() to ask whether a given thread has one of the orphaned signals unblocked. The line that reads oddly at first — sigandsets(&retarget, &retarget, &t->blocked) — is a narrowing step: after choosing thread t, the signals t can accept are removed from the working set, leaving only the ones still needing a home, and the loop exits early once that set empties. The wakeup is guarded by !task_sigpending(t), so a thread that already has pending work is not woken twice. Note that signal_wake_up(t, 0) is called with resume = 0: this is a re-nomination of an ordinary pending signal, not a fatal one, so there is no reason to break the thread out of an uninterruptible or traced state.

The practical consequence is that the blocked masks across a thread group really do shape Linux's wakeup choices for signal delivery, and program design can steer signal locality without any kernel API beyond rt_sigprocmask(). It also explains the cost model of the popular “block everything in every thread, handle centrally” pattern: the blocking calls themselves are where the retargeting work happens, and they are made once at startup, while the steady-state consumption through signalfd() or rt_sigtimedwait() never touches this code at all.

Waiting for Signals: rt_sigsuspend and rt_sigtimedwait

Signals are asynchronous by default, but Linux also supports synchronous waiting patterns. rt_sigsuspend() temporarily replaces the calling thread's mask and then sleeps until a signal is handled. It is mostly a control-flow helper: install a temporary mask, yield the CPU, and rely on the ordinary delivery path to wake the thread with -ERESTARTNOHAND or handler execution. Programs use it when they want to atomically unblock a set and wait for “something signal-related” to happen.

The implementation is eleven lines and every one of them carries weight. Before installing the temporary mask, sigsuspend() saves the caller's real mask in current->saved_sigmask; after the sleep it calls set_restore_sigmask(), which raises TIF_RESTORE_SIGMASK, and then returns -ERESTARTNOHAND unconditionally. That return value is the whole trick. rt_sigsuspend() has no success path: it cannot return zero, because the only way out of the wait is a signal, and Chapter 10 established that -ERESTARTNOHAND means “restart only if no handler runs.” If a handler runs, the pseudo-error becomes -EINTR and user space sees the familiar failure; if no handler runs — a stop signal, say — the syscall is restarted and the thread goes back to waiting.

The saved mask is then unwound by whichever of two paths applies, both already met in Section 4. When a handler is delivered, signal_delivered() calls clear_restore_sigmask(), because the pre-suspend mask has already been written into the signal frame's uc_sigmask and will be reinstated by rt_sigreturn(). When no handler is delivered, the flag survives and restore_saved_sigmask() on the return-to-user path copies saved_sigmask back into blocked — the right-hand branch of Figure 11-4. The sleep itself is a while (!signal_pending(current)) loop around schedule(), not a single sleep, because a spurious wakeup must not be mistaken for a signal.

rt_sigtimedwait() is more direct. It inverts the caller's interest set into a temporary blocked mask, attempts dequeue_signal() immediately, and if nothing is ready optionally sleeps with those interest signals unblocked so their arrival wakes the task. When a matching signal is obtained, Linux copies a full siginfo_t back to user space and returns the signal number instead of running a handler. This lets a program consume queued signals as ordinary events without ever entering an asynchronous handler.

Section 2.5 already described the real_blocked mechanism this wait depends on, and it is worth recalling the reason it is more than a save slot: while the window is open, real_blocked holds the caller's original mask, which by construction contains the very signals being awaited, and sig_task_ignored() consults it so that a signal someone is explicitly waiting for is never discarded at generation time just because its disposition is SIG_IGN. The comment in do_sigtimedwait() explains why the mask is narrowed by hand rather than through set_current_blocked(): “Unblocking is always fine,” since widening the deliverable set can only create work, never strand a pending signal. Restoration does go through __set_task_blocked(), which is what re-arms the retargeting logic described in the previous section. The sleep uses TASK_INTERRUPTIBLE | TASK_FREEZABLE, so a waiting thread does not obstruct system suspend, and the timeout is honored by schedule_hrtimeout_range() with the task's timer_slack_ns.

The return convention repays careful reading, because two very similar-looking failures mean different things. A positive return is the signal number, with the full siginfo_t copied out only if uinfo was supplied. -EAGAIN means the wait genuinely timed out with nothing in the interest set. -EINTR means the sleep was cut short by a signal that was not in the interest set — one that will be delivered normally once the syscall returns. Two boundary cases follow from the same code. A NULL timeout leaves timeout at KTIME_MAX and waits forever; a timeout of {0, 0} makes the if (!sig && timeout) test fail, so the syscall becomes a non-blocking poll of the pending queues that returns either a signal number or -EAGAIN immediately. A negative or out-of-range tv_nsec is rejected by timespec64_valid() with -EINVAL.

What changed since Linux 2.6 is mostly emphasis. In the 2.6 era, synchronous waits were treated as a specialty next to “real” signal delivery. Modern event-driven applications often prefer synchronous consumption because it is easier to reason about than asynchronous handlers. The kernel accommodates that preference by letting the wait path reuse the same pending queues and metadata rather than inventing a second event mechanism.

The connection to Chapter 10 is also worth remembering. If a blocking syscall is interrupted, the restart rules depend on both the signal disposition and the syscall's restart semantics. Those restart details are covered in the system call chapter so that this chapter can focus on signal selection, frame construction, and user-visible waiting behavior. The interfaces are separate, but the control flows meet at exactly that boundary.

Examining Pending Signals: rt_sigpending

sigpending() looks like a small diagnostic interface, but it remains useful in modern Linux because it exposes exactly what the kernel believes is pending for the current thread. The 64-bit entry point is rt_sigpending() in kernel/signal.c, and its implementation is intentionally short enough that it reads like a specification. 

static void do_sigpending(sigset_t *set)
{
    spin_lock_irq(&current->sighand->siglock);
    sigorsets(set, &current->pending.signal,
              &current->signal->shared_pending.signal);
    spin_unlock_irq(&current->sighand->siglock);

    sigandsets(set, &current->blocked, set);
}

SYSCALL_DEFINE2(rt_sigpending, sigset_t __user *, uset, size_t, sigsetsize)
{
    sigset_t set;

    if (sigsetsize > sizeof(*uset))
        return -EINVAL;
    do_sigpending(&set);
    if (copy_to_user(uset, &set, sigsetsize))
        return -EFAULT;
    return 0;
}

One line of the wrapper is worth pausing on, because it breaks a pattern the rest of this section has established. Every other real-time entry point insists on sigsetsize != sizeof(sigset_t) and rejects anything else, but rt_sigpending() tests sigsetsize > sizeof(*uset) and then copies out exactly sigsetsize bytes. A caller may therefore ask for a truncated view — the low 32 signals only, for instance — and get one, which is how the legacy sigpending() ABI is layered on top without a separate entry point. The relaxation is safe here because the syscall only ever writes to user space; there is no partially-initialized kernel object to worry about.

The helper first ORs together the thread-private bitmap current->pending.signal and the process-wide bitmap current->signal->shared_pending.signal. It then intersects that union with current->blocked, because the POSIX meaning of sigpending() is “signals that are pending but currently masked from delivery.” In other words, the syscall does not dump every queued signal instance; it returns the set that is both pending and blocked at the instant of the call.

The lock discipline is deliberately minimal and the source annotates it. Only the union of the two pending bitmaps is taken under siglock, because shared_pending is written by other threads; the intersection with blocked is performed after the lock is dropped, under the comment “Outside the lock because only this thread touches it.” This is the same invariant that lets sigprocmask() read current->blocked locklessly, and it is worth internalizing as a rule for reading this file: the pending queues are process-wide shared state, while the blocked mask is thread-private and single-writer. An immediate consequence is that the returned set is a snapshot with no atomicity guarantee against a concurrent send — a signal can arrive between the unlock and the caller's inspection — so the result answers “what was blocked and pending a moment ago,” which is precisely what the interface promises and no more.

That design makes rt_sigpending() a good companion to /proc/[pid]/status. The SigPnd field shows the thread-private pending bitmap, ShdPnd shows the shared thread-group bitmap, SigBlk shows the current blocked mask, SigIgn shows signals ignored by disposition, and SigCgt shows signals with user handlers installed. Together they let you answer both “what is queued?” and “why has it not run yet?” without instrumenting the process.

Because the syscall only returns a bitmap, it says nothing about multiplicity or payload. A queued real-time signal with five instances still appears as one bit, and you need rt_sigtimedwait(), a handler, or tracing to inspect individual siginfo_t payloads. Even so, for quick diagnosis of stuck daemons, masked shutdown signals, or surprising job-control state, rt_sigpending() is still one of the simplest windows into the subsystem.

The Alternate Signal Stack: sigaltstack

An ordinary signal frame is built on the thread's current user stack, which is exactly the wrong place to rely on if the signal was caused by stack exhaustion. The alternate signal stack configured by sigaltstack() solves that problem by giving Linux a second stack region for handlers marked with SA_ONSTACK. Without it, a stack-overflow SIGSEGV often cannot even report itself cleanly because there is no safe space left to build the frame. 

int do_sigaltstack(const stack_t *ss, stack_t *oss, unsigned long sp,
                   size_t min_ss_size)
{
    if (oss) {
        oss->ss_sp = (void __user *)t->sas_ss_sp;
        oss->ss_size = t->sas_ss_size;
        oss->ss_flags = sas_ss_flags(sp) |
            (current->sas_ss_flags & SS_FLAG_BITS);
    }
    if (ss) {
        if (unlikely(on_sig_stack(sp)))
            return -EPERM;

        ss_mode = ss_flags & ~SS_FLAG_BITS;
        if (unlikely(ss_mode != SS_DISABLE && ss_mode != SS_ONSTACK &&
                     ss_mode != 0))
            return -EINVAL;

        sigaltstack_lock();
        if (ss_mode == SS_DISABLE) {
            ss_size = 0;
            ss_sp = NULL;
        } else {
            if (unlikely(ss_size < min_ss_size))
                ret = -ENOMEM;
            if (!sigaltstack_size_valid(ss_size))
                ret = -ENOMEM;
        }
        if (!ret) {
            t->sas_ss_sp = (unsigned long)ss_sp;
            t->sas_ss_size = ss_size;
            t->sas_ss_flags = ss_flags;
        }
        sigaltstack_unlock();
    }
}

if (ka->sa.sa_flags & SA_ONSTACK) {
    if (sas_ss_flags(sp) == 0)
        sp = current->sas_ss_sp + current->sas_ss_size;
}

The kernel-side worker is do_sigaltstack(). It reports the old settings through oss, validates any requested new stack, and stores the result in the three task_struct fields sas_ss_sp, sas_ss_size, and sas_ss_flags. One important safety rule appears near the top of the function: if on_sig_stack(sp) says the thread is already running on the alternate stack, Linux refuses to change the configuration and returns -EPERM.

Three further details govern what a request is allowed to say. The mode is extracted with ss_flags & ~SS_FLAG_BITS and must be SS_DISABLE, SS_ONSTACK, or zero; anything else is -EINVAL. Passing SS_ONSTACK on input is accepted for historical symmetry but asserts nothing — it is an output state, computed by sas_ss_flags(), not a property a caller may claim. Next, a request that would change nothing returns success before taking any lock, which keeps the common “save and restore my configuration” idiom cheap. Finally, note where -ENOMEM is assigned rather than returned: a size failure records the error and falls through to the if (!ret) guard, so a rejected request leaves the previous alternate stack completely intact rather than half-installed.

The reporting path deserves its own note because it reads two different things. oss->ss_flags is built as sas_ss_flags(sp) | (current->sas_ss_flags & SS_FLAG_BITS): the first term is computed live from the current stack pointer and yields SS_DISABLE when no stack is configured, SS_ONSTACK when the thread is executing on it, and zero otherwise; the second term carries back the persistent bits such as SS_AUTODISARM. So a query does not simply echo what was installed — it also tells you where the thread is standing right now. on_sig_stack() adds one deliberate lie in the service of robustness: if SS_AUTODISARM is set it returns false without inspecting the stack pointer at all, on the reasoning that an autodisarming stack cannot legitimately be in use, so a corrupted stack pointer that happens to land inside the region will not prevent the signal from being handled.

The flags explain how the alternate stack behaves over time. SS_DISABLE tears the stack down entirely. SS_AUTODISARM is newer and subtler: after a handler is delivered on the alternate stack, Linux temporarily disables that stack so nested signals fall back to the main user stack. That behavior matters for runtimes such as Go that multiplex their own stacks and cannot assume the alternate stack remains valid across arbitrary nested control transfers.

Actual selection happens later during frame construction. When a signal's action has SA_ONSTACK set and sas_ss_flags(sp) says the alternate stack may be entered, helpers such as get_sigframe() switch the frame pointer base to sas_ss_sp + sas_ss_size; otherwise they keep using the current user stack pointer. The configuration is not permanent across an image change, either: begin_new_exec() clears the alternate stack fields during execve(), so a freshly executed program starts with no inherited alternate stack.

The reverse direction is far more forgiving than most of the signal ABI, and the asymmetry is intentional. __save_altstack() writes the configuration into the frame's uc_stack during frame construction, and restore_altstack() reads it back during sigreturn — but it discards the result, with the comment “squash all but EFAULT for now,” and even the -EFAULT is dropped by the caller. A handler that corrupts uc_stack before returning therefore does not take a SIGSEGV; it simply fails to change anything, and the thread keeps the alternate stack it already had. This is the opposite of the strict validation Section 4.6 described for the register context, and the reason is that uc_stack is advisory: getting it wrong cannot corrupt kernel state, only the program's own future frame placement.

The one genuinely modern problem with sigaltstack() is that the right size is no longer a constant. The MINSIGSTKSZ that do_sigaltstack() is called with is a compile-time floor, but the real frame on both of this book's architectures depends on features discovered at runtime: on x86_64 the XSAVE area grows with enabled state components, and on ARM64 the SVE and SME context records scale with the implemented vector length. A program that hardcodes the MINSIGSTKSZ from its libc headers can allocate a stack that was adequate on the build machine and is far too small on the deployment machine — and the failure mode is a corrupted stack during signal delivery, not a clean error.

Linux answers this in two places. At process startup the kernel publishes the true minimum in the auxiliary vector as AT_MINSIGSTKSZ (entry 51), which is what getauxval(AT_MINSIGSTKSZ) returns and what portable code should size against. On x86 the value comes from get_sigframe_size(); on ARM64 it is the boot-time signal_minsigstksz, computed by minsigstksz_setup() by running the real layout builder setup_sigframe_layout() over a maximal context and adding room for a frame record and alignment padding — that is, the number is derived from the same code that will later build the frame, not maintained by hand.

The second answer is a check at installation time, and it exists only on x86. Under CONFIG_DYNAMIC_SIGFRAME, do_sigaltstack() wraps the update in sigaltstack_lock() — which is sighand->siglock — and calls sigaltstack_size_valid(), defined in arch/x86/kernel/signal.c. It compares the requested size against max_frame_size - fpu_default_state_size plus the thread group's permitted user XSAVE size, so a process that has been granted a dynamic feature such as AMX is held to the larger requirement. 

bool sigaltstack_size_valid(size_t ss_size)
{
    unsigned long fsize = max_frame_size - fpu_default_state_size;
    u64 mask;

    lockdep_assert_held(&current->sighand->siglock);

    if (!fpu_state_size_dynamic() && !strict_sigaltstack_size)
        return true;

    fsize += x86_task_fpu(current->group_leader)->perm.__user_state_size;
    if (likely(ss_size > fsize))
        return true;

    if (strict_sigaltstack_size)
        return ss_size > fsize;

    mask = x86_task_fpu(current->group_leader)->perm.__state_perm;
    if (mask & XFEATURE_MASK_USER_DYNAMIC)
        return ss_size > fsize;

    return true;
}

The structure of that function is a compatibility compromise rather than a correctness argument, and the comment above it says so. Plenty of long-standing programs allocate exactly MINSIGSTKSZ bytes and never actually take a signal, and enforcing the true size on all of them would break working software for no benefit. So the check returns true immediately when no dynamic features exist and strict mode is off, and even when the size is too small it only fails for tasks that have asked for and been granted a dynamic feature — unless the strict_sigaltstack_size command-line option is set, in which case everyone is held to the real number. Taking siglock is what makes this race-free against a concurrent permission request: a task either already has the permission when the size is checked, or the later permission request sees the newly installed size.

Syscall Restart and Signal Interaction

Signals and blocking system calls meet at one awkward boundary: a thread may have gone to sleep in the kernel, only to learn at wakeup time that a signal should run first. Linux therefore carries restart-specific pseudo-errors such as -ERESTARTSYS, -ERESTARTNOHAND, -ERESTARTNOINTR, and -ERESTART_RESTARTBLOCK inside the saved register state until signal delivery decides whether to retry the syscall or report -EINTR. Chapter 10, Section 8, covers that contract in detail; this section only sketches where the signal code plugs into it. 

/* handle_signal(): a handler will run */
if (syscall_get_nr(current, regs) != -1) {
    switch (syscall_get_error(current, regs)) {
    case -ERESTART_RESTARTBLOCK:
    case -ERESTARTNOHAND:
        regs->ax = -EINTR;
        break;
    case -ERESTARTSYS:
        if (!(ksig->ka.sa.sa_flags & SA_RESTART)) {
            regs->ax = -EINTR;
            break;
        }
        fallthrough;
    case -ERESTARTNOINTR:
        regs->ax = regs->orig_ax;
        regs->ip -= 2;
        break;
    }
}

/* arch_do_signal_or_restart(): no handler present */
if (syscall_get_nr(current, regs) != -1) {
    switch (syscall_get_error(current, regs)) {
    case -ERESTARTNOHAND:
    case -ERESTARTSYS:
    case -ERESTARTNOINTR:
        regs->ax = regs->orig_ax;
        regs->ip -= 2;
        break;
    case -ERESTART_RESTARTBLOCK:
        regs->ax = get_nr_restart_syscall(regs);
        regs->ip -= 2;
        break;
    }
}

Both halves of that decision are shown above, and putting them side by side makes the shape of the rule obvious: the same four pseudo-errors are evaluated twice, once on the path where a handler is about to run and once on the path where get_signal() returned nothing. Both are guarded by syscall_get_nr(current, regs) != -1, so a signal that interrupted ordinary user code — a page fault, a timer tick — never touches this logic at all; only a thread that was actually inside a system call is eligible for restart. The no-handler path is the more generous of the two: with nothing to run, there is no observable reason to report failure, so every restartable code simply restarts, and it is also the only path that can reach get_nr_restart_syscall().

On x86_64, handle_signal() inspects the saved syscall result before it builds the user frame. If the result is -ERESTARTSYS and the chosen action lacks SA_RESTART, the kernel converts the return value to -EINTR; otherwise it rewinds the instruction pointer and restores the original syscall number so user mode transparently re-executes the call. ARM64 follows the same policy in arch_do_signal_or_restart(), just expressed in terms of pc and orig_x0 rather than ip and orig_ax.

The remaining pseudo-errors refine that rule. -ERESTARTNOINTR always restarts, which is why low-level wait paths such as futex code can depend on it. -ERESTARTNOHAND restarts only if no user handler will run, and -ERESTART_RESTARTBLOCK hands control to restart_syscall() so the kernel can reconstruct more complex restart arguments. The important takeaway for this chapter is that signal delivery does not merely interrupt a syscall—it also decides how much of the syscall should be replayed afterward.

-ERESTART_RESTARTBLOCK is the one that needs a real mechanism rather than a register rewrite, because the calls that use it — nanosleep(), poll(), futex() with a timeout — cannot simply be re-executed with their original arguments. Replaying nanosleep(10s) after nine seconds would sleep nineteen. So instead of restoring the original syscall number, the no-handler path substitutes the number returned by get_nr_restart_syscall(), which is __NR_restart_syscall adjusted for the calling ABI. That syscall is a two-line dispatcher: SYSCALL_DEFINE0(restart_syscall) simply calls current->restart_block.fn(&current->restart_block), letting the original syscall's own continuation function resume with the adjusted state it stashed before sleeping. No program ever invokes it deliberately, which is why it has no libc wrapper.

The default contents of that block are the safety net. restart_block.fn is initialized to do_no_restart_syscall(), which returns -EINTR and nothing else, and several paths reset it to that value on purpose — ARM64's rt_sigreturn() does so as its very first action, as Section 4.6 noted. The effect is that a stale or unarmed restart block can only ever produce a clean -EINTR, never a replay of whatever unrelated syscall happened to use the block last.

Real-Time Signals

Real-time signals are the part of the API where Linux most clearly promises queue semantics rather than bitmap semantics. Every successful send that truly requires queueing should create one queued instance with its own kernel_siginfo_t payload. That is why these signals power POSIX timers, user-level event notifications, and interfaces that need to carry an integer or pointer through sigqueue(). A standard signal can tell you that “something happened.” A real-time signal can tell you that event number three happened after event number two and carried pointer X.

The send side enforces this guarantee in __send_signal_locked(). If Linux cannot allocate a sigqueue for a real-time signal whose producer expects queueing, the call fails with -EAGAIN instead of silently degrading to one pending bit. That is the contract that justifies using real-time signals for reliable event streams. For standard signals, the kernel chooses a more forgiving rule: preserve at least one pending instance even if detailed payload information is lost.

Section 1.2 introduced the real-time range and Table 11-3 summarized its characteristics; this section is about the machinery behind them, so the two tables are complementary rather than redundant. Table 11-3 answers “what does a real-time signal do?”, and Table 11-16 below answers “how does it differ from a standard one?”

Before the details, the central guarantee needs one honest qualification, because the rest of this section is largely a catalogue of where it bends. “One send, one queued instance” is a property of the send path — of __send_signal_locked() declining to collapse and refusing to proceed without a node. It is not a property of every producer that uses real-time numbers. Two documented exceptions matter in practice. A standard signal whose allocation fails still gets its bit set, and Section 6.2 shows what the receiver actually observes in that case, which is not what most readers expect. And a POSIX timer, the single largest consumer of real-time signals, deliberately does not queue one instance per expiry; it queues at most one and counts the rest, as Section 6.4 explains. Understanding both exceptions is what separates using real-time signals correctly from assuming they are a lossless message queue.

A practical consequence is that real-time signals are best when you truly need the signal mechanism but also need lossless queueing semantics. If you only want one wakeup no matter how many identical events occurred, a standard signal is usually sufficient and cheaper. If you need many payload-bearing instances, choose a real-time number and budget for RLIMIT_SIGPENDING. Linux gives both styles first-class support because both styles are useful.

That dual design is one reason the signal subsystem has survived so many alternative event mechanisms. Pipes, eventfds, futexes, io_uring completions, and epoll all overlap with parts of the problem space. Signals remain relevant because they are the only mechanism that can combine process lifecycle semantics, asynchronous faults, default actions, handler delivery, and queued payloads under one old but evolving ABI.

Signal Numbering and the Reserved Range

Real-time signals occupy the numeric range above the standard signals. On both x86_64 and ARM64, SIGRTMIN is 32 and SIGRTMAX is _NSIG, which is 64, so the kernel exposes 33 real-time numbers. Unlike the standard signals, none of these numbers has a predefined meaning: SIGRTMIN + n means whatever the application decides, which is exactly what makes them suitable for user-defined event streams.

There is an important subtlety that trips up many programmers: the SIGRTMIN a program sees from glibc is usually not 32. The NPTL threading implementation privately reserves the first few real-time signals for its own use—thread cancellation, the POSIX timer helper, and the setxid synchronization used by setuid() across a thread group. glibc therefore shifts the public SIGRTMIN upward (commonly to 34) through __libc_current_sigrtmin(). Portable code must always compute real-time numbers as SIGRTMIN + n at run time rather than hard-coding 32, because the kernel's raw range and the C library's usable range deliberately differ.

It is worth being precise about who enforces that reservation, because the answer is nobody. The kernel has no notion of a reserved real-time number. siginmask() range-checks below SIGRTMIN before consulting any mask, so signals 32 through 64 are indistinguishable to every part of kernel/signal.c: same queueing rule, same accounting, same default action of terminating without a core dump. glibc's reservation is a userspace convention implemented entirely by shifting the value that __libc_current_sigrtmin() reports. Nothing stops an unrelated process with the right credentials from calling kill(pid, 32) and injecting a signal into the number NPTL uses for thread cancellation. That is not a defect so much as a consequence of the numbering being a flat, unowned namespace — but it does mean a real-time number is not a private channel, and any protocol built on one should validate si_code and si_pid rather than trusting that only the intended sender knows the number.

The same flatness explains a design choice that surprises people coming from other event systems: because no real-time number carries a predefined meaning, none of them has a useful default action either. An uncaught real-time signal terminates the process, and unlike SIGSEGV or SIGQUIT it does not even leave a core dump behind to explain why. A program that adopts a real-time number for an event stream and then forgets to install a handler before the first event arrives does not lose an event; it exits. Blocking the number at startup, before any producer can reach it, is the usual defense, and it composes naturally with the signalfd() and rt_sigtimedwait() consumption patterns of Sections 5.5 and 7.

Queueing and Delivery Order

Real-time signals promise a specific delivery order, and Linux implements it with the same bitmap-plus-list structure used for every pending set. Global selection still favors lower signal numbers: next_signal() scans the pending bitmap and returns the lowest set bit (after the synchronous-fault priority discussed earlier), so a pending SIGRTMIN outranks a pending SIGRTMIN + 5. Within a single real-time number, delivery is first-in-first-out, which is the property that lets a producer send an ordered stream of events.

Both halves of that sentence need reading carefully, because the guarantee is narrower than “real-time signals arrive in order.” FIFO holds within one signal number, and it holds because __send_signal_locked() appends with list_add_tail() while collect_signal() takes the first match from the head — the ordering is a property of the list, not of any timestamp. Across different numbers there is no temporal ordering at all: selection is by number, so an event sent on SIGRTMIN ten milliseconds after one sent on SIGRTMIN + 5 will be delivered first. A producer that spreads a logically ordered stream across several real-time numbers to “get more queue depth” has therefore given up sequencing without being told so. The correct pattern is one number per independent stream, with ordering carried inside the payload if it must survive across streams.

On x86_64 and ARM64 the selection code is simpler than it looks. Section 2.1 noted that _NSIG_WORDS is 1 on both architectures, so the “handle the first word specially” branch at the top of next_signal() is the only branch that ever executes, and the entire multi-word loop below it is dead code inherited from 32-bit ABIs. The practical consequence is that the SYNCHRONOUS_MASK narrowing described in Section 4.1 is applied to a word that contains every signal, real-time numbers included — not merely to a low word — and that after that narrowing the choice really is a single ffz() over one machine word.

The FIFO guarantee lives in collect_signal(). When a signal number is dequeued, the function walks the pending list in insertion order and takes the first node whose si_signo matches, copying its payload into the caller's siginfo. If a second matching node exists, the bitmap bit is left set so the next dequeue returns the following instance; only when the last matching node is removed does the bit clear. That is how one bitmap bit can front an ordered queue of several payload-bearing instances.

The scan deserves one performance note, since it is the only place in the delivery path with a cost proportional to queue depth. collect_signal() walks the pending list looking for a match and then keeps walking only far enough to answer “is there a second one?”, at which point goto still_pending leaves the loop. That jump is not merely an early exit: it lands past the sigdelset() that would otherwise clear the bitmap bit, which is precisely the mechanism that keeps one bit standing for a queue of several instances. Worst case the scan traverses the whole list, so a process holding thousands of queued real-time signals pays that traversal on every dequeue. This is one of the quieter arguments for RLIMIT_SIGPENDING being a real limit rather than a formality, and it is a reason to consume a real-time stream promptly rather than letting it accumulate while blocked. 

static void collect_signal(int sig, struct sigpending *list,
                           kernel_siginfo_t *info, struct sigqueue **timer_sigq)
{
    struct sigqueue *q, *first = NULL;

    list_for_each_entry(q, &list->list, list) {
        if (q->info.si_signo == sig) {
            if (first)
                goto still_pending;   /* another instance remains */
            first = q;
        }
    }

    sigdelset(&list->signal, sig);     /* last one: clear the bit */

    if (first) {
still_pending:
        list_del_init(&first->list);
        copy_siginfo(info, &first->info);

        if (unlikely((first->flags & SIGQUEUE_PREALLOC) &&
                     (info->si_code == SI_TIMER)))
            *timer_sigq = first;
        else
            __sigqueue_free(first);
    } else {
        /*
         * Ok, it wasn't in the queue.  This must be
         * a fast-pathed signal or we must have been
         * out of queue space.  So zero out the info.
         */
        clear_siginfo(info);
        info->si_signo = sig;
        info->si_errno = 0;
        info->si_code = SI_USER;
        info->si_pid = 0;
        info->si_uid = 0;
    }
}

The else branch is the one worth dwelling on, because it is where the intro's “payload may be lost” becomes something a program can actually observe. Reaching it means the bitmap bit was set but no matching queue node exists, which happens for the two reasons the comment names: a fast-pathed signal that never allocated a node — SIGKILL and sends to kernel threads skip allocation entirely — or a send that ran out of queue space and fell back to setting only the bit, the degradation described in Section 3.1. Linux cannot report a missing payload, and it cannot hand the receiver an uninitialized structure, so it fabricates one.

What it fabricates is specific and slightly misleading: si_code becomes SI_USER, and si_pid and si_uid are both set to zero. A handler examining that siginfo sees a signal that appears to have been sent by kill() from PID 0 — an origin that cannot exist. That combination is in fact the most reliable way to detect the degradation from user space, since no genuine kill() can produce si_pid == 0; prepare_kill_siginfo() always fills in a real task_tgid_vnr(). It also means a program that switches on si_code to distinguish event sources must treat SI_USER with a zero si_pid as “unknown,” not as a legitimate message, because the payload it was expecting is simply gone.

Queue Limits and Accounting

Queueing would be dangerous without limits, so Linux charges each queued instance against RLIMIT_SIGPENDING via the per-user-namespace ucounts mechanism. This is a distinctly modern kernel feature. The old 2.6 discussion could describe signal queue limits more globally. Linux 7.0.12 must account correctly across namespaces and credential changes, so the queue node itself remembers which ucounts object to decrement when freed.

The first question to settle is whose budget is charged, because the intuitive answer is wrong and the manual pages are only accurate in the common case. sig_get_ucounts() is passed the target task and calls task_ucounts(t), which resolves to t's own credentials; the comparison that follows uses task_rlimit(t, RLIMIT_SIGPENDING), again the target's limit. So a queued instance is charged to the process that will receive it, not to the process that sent it. Read as a resource-control mechanism this is defensible — the memory really is held on the receiver's behalf, and it is freed when the receiver consumes it — but it means the limit does not bound how many signals a process may send. It bounds how many may be outstanding for a process, which is why a program that blocks a real-time number and stops consuming it will eventually cause its own senders to fail with -EAGAIN, no matter who those senders are.

The second question is which signals the limit actually restrains, and the answer is narrower than the name suggests. Section 3.1 showed how override_rlimit is computed: it is true for a standard signal carrying a special sentinel or a non-negative si_code, and unconditionally false for every number at or above SIGRTMIN. An override_rlimit allocation still takes the charge — the counter still moves — but skips the comparison against the limit entirely. The practical effect is that RLIMIT_SIGPENDING is, for all ordinary purposes, a real-time-signal limit. No amount of kill() traffic can be refused by it, which is exactly the POSIX requirement that kill() must not fail for lack of resources; the limit exists to bound the one interface that is allowed to fail.

sig_get_ucounts() can return NULL for two different reasons, and only one of them is the interesting one. inc_rlimit_get_ucounts() returning zero signals a failure inside the ucounts machinery itself and is reported without further comment. The ordinary case is the explicit test that follows: if the limit was not overridden and the new count exceeds it, the charge is immediately released with dec_rlimit_put_ucounts(), print_dropped_signal() is called, and NULL is returned. That release-before-return matters, because the counter is incremented optimistically before the comparison; forgetting it would leak a unit of quota on every refusal and slowly strangle a process that merely brushed against the limit.

The reference counting deserves a note as well, since the source flags it explicitly. A pending signal holds a reference on the ucounts object, but the reference is acquired and released only when the pending count transitions to or from zero rather than on every queued instance. That keeps the common path — a burst of signals to a process that already has one pending — free of atomic refcount traffic, at the cost of making the ownership rule less obvious than a naive one-reference-per-node scheme.

The charge is taken during allocation in sigqueue_alloc(), which calls sig_get_ucounts() to increment the pending count in the target's user namespace and compare it against the limit. If the limit is exceeded and the send is not privileged to override it, the allocation returns NULL, which the send path turns into -EAGAIN for a queue-requiring real-time signal. The reciprocal release happens when the node is finally freed, keeping the accounting balanced regardless of whether the signal was delivered, flushed at exec, or discarded when the disposition changed to SIG_IGN.

One consumer of the limit is easy to overlook because it charges at a moment when no signal exists yet. posixtimer_init_sigqueue() calls sig_get_ucounts(current, -1, 0) when a POSIX timer is created, taking a full RLIMIT_SIGPENDING unit for the timer's embedded queue node and passing -1 as the signal number purely because there is no real one to name in a diagnostic. Because override_rlimit is zero, the charge is enforceable, and timer_create() fails when it cannot be taken. RLIMIT_SIGPENDING is therefore also a cap on how many POSIX timers a user may have armed — a coupling that is invisible from either interface's documentation and that occasionally surprises a process that creates many timers and then wonders why an unrelated sigqueue() starts returning -EAGAIN. 

static struct sigqueue *sigqueue_alloc(int sig, struct task_struct *t,
                                       gfp_t gfp_flags, int override_rlimit)
{
    struct ucounts *ucounts = sig_get_ucounts(t, sig, override_rlimit);
    struct sigqueue *q;

    if (!ucounts)
        return NULL;              /* over RLIMIT_SIGPENDING -> caller returns -EAGAIN */

    q = kmem_cache_alloc(sigqueue_cachep, gfp_flags);
    if (!q) {
        dec_rlimit_put_ucounts(ucounts, UCOUNT_RLIMIT_SIGPENDING);
        return NULL;
    }

    __sigqueue_init(q, ucounts, 0);
    return q;
}

The failure path at the bottom mirrors the one inside sig_get_ucounts(): the charge is taken first, so a failed kmem_cache_alloc() must release it before returning. Both callers of the resulting NULL — the ordinary send path and posixtimer_init_sigqueue() — see the same value whether the refusal came from the limit or from the allocator, which is why print_dropped_signal() lives inside sig_get_ucounts() rather than at the call site: only the inner function knows which of the two happened. The trailing zero passed to __sigqueue_init() is the flags word, and it is the single bit of difference between this node and a timer's: the timer's initialization passes SIGQUEUE_PREALLOC instead, which is what tells __sigqueue_free() to drop a reference rather than return the memory to the slab.

Preallocated Entries and POSIX Timers

Real-time signals integrate with POSIX timers in a way that exposes another implementation trick. A timer may fire from interrupt or timer context where a fresh GFP_ATOMIC allocation could fail, yet the timer signal must be delivered reliably. Linux solves this by reserving one sigqueue node when the timer is created and marking it with the SIGQUEUE_PREALLOC flag, so expiration never depends on a late allocation.

“Preallocated” slightly undersells the arrangement. The node is not allocated separately and pointed at; it is a struct sigqueue embedded directly in struct k_itimer as the member sigq, and the send path reaches it as &tmr->sigq. There is exactly one per timer, for the timer's whole lifetime, and posixtimer_init_sigqueue() does nothing but charge the quota and call __sigqueue_init() with the SIGQUEUE_PREALLOC flag set. The consequence is the single most important fact about timer signals, and the section as previously written did not state it: a timer cannot have two notifications outstanding, because it has only one node to queue.

That constraint would be a serious loss of information if the kernel simply dropped the extra expiries, so it counts them instead. Each time an interval timer is rearmed, hrtimer_forward_now() returns how many periods elapsed and the result accumulates into timr->it_overrun. When the queued signal is finally dequeued, that accumulated count is published to the receiver in si_overrun and the counter is reset. Overrun is therefore the timer subsystem's answer to the question real-time signals otherwise answer by queueing: instead of n instances, the receiver gets one instance that says “and n more happened while you were not looking.” The same number is what timer_getoverrun() returns. 

static bool __posixtimer_deliver_signal(struct kernel_siginfo *info,
                                        struct k_itimer *timr)
{
    guard(spinlock)(&timr->it_lock);

    /*
     * Check if the timer is still alive or whether it got modified
     * since the signal was queued. In either case, don't rearm and
     * drop the signal.
     */
    if (timr->it_signal_seq != timr->it_sigqueue_seq ||
        WARN_ON_ONCE(!posixtimer_valid(timr)))
        return false;

    if (!timr->it_interval ||
        WARN_ON_ONCE(timr->it_status != POSIX_TIMER_REQUEUE_PENDING))
        return true;

    timr->kclock->timer_rearm(timr);
    timr->it_status = POSIX_TIMER_ARMED;
    timr->it_overrun_last = timr->it_overrun;
    timr->it_overrun = -1LL;
    ++timr->it_signal_seq;
    info->si_overrun = timer_overrun_to_int(timr);
    return true;
}

Three things in that function are worth reading slowly. The reset is to -1LL rather than zero because hrtimer_forward_now() counts the expiry that produced this notification along with the missed ones, and starting at minus one makes si_overrun mean “additional expiries,” which is what POSIX specifies. The published value goes through timer_overrun_to_int(), which clamps to INT_MAX, because it_overrun is a 64-bit count while si_overrun and the return type of timer_getoverrun() are both int — a timer with a nanosecond interval left unserviced for long enough really can overflow that. And it_overrun_last exists so the value survives the reset: timer_getoverrun() called later, from inside the handler, must report the count for the notification being handled, not for whatever has accumulated since.

The most surprising line is timr->kclock->timer_rearm(timr), because of where it sits. An interval timer is not rearmed when it expires; it is rearmed when the program consumes the resulting signal. Between expiry and dequeue the timer sits in POSIX_TIMER_REQUEUE_PENDING, and only __posixtimer_deliver_signal() moves it back to POSIX_TIMER_ARMED. That is a deliberate flow-control design: a program that stops consuming its timer signals does not accumulate work in the kernel, it simply stops the timer's clock from advancing, and the overrun count tells it afterwards how much it missed. It also explains why the whole rearm path is reachable from dequeue_signal() at all, which otherwise looks like a surprising layering violation.

The two sequence counters guard the window that design opens. it_signal_seq is bumped whenever the timer is modified — rearmed, reset by timer_settime(), deleted — and it_sigqueue_seq records its value at the moment the signal was queued, captured under sighand->siglock specifically to close the race against a concurrent dequeue. If they disagree at delivery time, the queued notification describes a timer configuration that no longer exists, so __posixtimer_deliver_signal() returns false and the signal is discarded. dequeue_signal() handles that with goto again, restarting the whole selection rather than returning a stale event to user space. A program that calls timer_settime() therefore cannot be handed a notification generated under the old settings, which is a stronger guarantee than the queueing model alone would provide.

Lock ordering forces one more piece of structure. timr->it_lock nests outside sighand->siglock, so posixtimer_deliver_signal() drops siglock before calling the inner function and retakes it afterwards, keeping interrupts disabled throughout. It also drops the timer reference that was acquired when the signal was queued. This is the reference counting the next paragraph describes, and it is why the node can be handed back through timer_sigq rather than freed: the queue never owned it.

Because the node is owned by the timer rather than the queue, it must not be freed by the ordinary dequeue path. collect_signal() checks for exactly this case: when the node carries SIGQUEUE_PREALLOC and its si_code is SI_TIMER, it hands the node back to the timer subsystem through the timer_sigq output instead of calling __sigqueue_free(). The timer code can then reuse or release the node under its own reference counting in posixtimer_deliver_signal(). This keeps timer delivery predictable and allocation-free at fire time while still depositing timer notifications in the same generic pending queues as every other signal.

It is the queues that are shared, though, not the send path, and the distinction matters when reading the code. A timer expiry does not call __send_signal_locked(). It calls posixtimer_send_sigqueue(), which performs its own permission-free equivalent of that function: it takes sighand->siglock, consults prepare_signal() for the ignored and group-exit tests, and then hands off to posixtimer_queue_sigqueue() to do the four steps by hand — signalfd_notify(), choosing shared_pending or the thread's private queue from the timer's it_pid_type, list_add_tail() plus sigaddset(), and finally complete_signal() to nominate and wake a thread. The result is indistinguishable from an ordinary send to anything downstream, including signalfd() and the target-thread selection of Section 3.3, but nothing on this path allocates, and nothing checks credentials, because a timer signalling its own creator has no permission question to answer.

The target selection has a small optimization of its own. posixtimer_get_target() resolves the timer's it_pid, and for a process-directed timer — anything other than SIGEV_THREAD_ID, which maps to PIDTYPE_PID and the private queue — it prefers current whenever current is in the same thread group and not exiting. Since a timer very often expires in the context of a thread of the very process it notifies, this avoids waking a potentially idle task merely to deliver a signal that the running thread could take itself.

Finally, the ignored case closes a loop Section 5.3 opened. When prepare_signal() reports that the signal is ignored, an ordinary send simply drops it; a periodic timer instead takes a reference and parks itself on tmr->ignored_list, tracked by it_sig_periodic, which is recorded under siglock precisely so the ignored-signal path can tell a periodic timer from a one-shot one. That list is what posixtimer_sig_unignore() walks when do_sigaction() installs a non-ignoring disposition, requeueing the parked timers so the program does not silently miss its next expiry. The reverse transition is handled too: a timer that was periodic while ignored and is later rearmed as one-shot has its stale entry removed and its reference dropped, because the notification it was holding no longer describes anything real. The bookkeeping is intricate, but the invariant behind it is simple — a preallocated node has an identity that outlives any single expiry, so every state change has to say explicitly what happens to it.

signalfd — Signals as File Descriptors

signalfd lets user space consume signals through the file-descriptor model instead of through asynchronous handlers. A caller supplies a mask, and the resulting file descriptor becomes readable when a matching pending signal exists in either the private or shared queue. A read() returns one or more fixed-size struct signalfd_siginfo records. From the kernel's point of view, this is not a second signal subsystem; it is a second front end onto the same pending queues.

This interface is particularly attractive to event loops. A program can block a set of signals in every thread, create one signalfd, and then watch it with poll() or epoll() alongside sockets, pipes, and timerfds. That avoids re-entrant asynchronous handlers and keeps signal processing inside the same explicit control loop as the rest of the program. The old Linux 2.6 chapter could not emphasize this pattern because signalfd was young and the ecosystem had not yet converged on fd-centric event loops.

The most important structural fact about the implementation is how little of it there is. struct signalfd_ctx has exactly one member — a sigset_t. It holds no reference to a task, no reference to a sighand_struct, and no queue of its own. Every path that needs a task uses current, resolved at the moment of the call rather than at creation. That single design decision explains almost every surprising behavior in this section, including one that catches people out badly: a signalfd is not bound to the process that created it. Inherit it across fork(), or pass it to an unrelated process over a Unix socket with SCM_RIGHTS, and reading it dequeues signals from the reader, using the creator's mask. The descriptor is best understood as a saved query, not as a handle on a subscription.

Consuming Signals from the Pending Queues

Kernel-side, fs/signalfd.c reuses the ordinary pending queues rather than inventing new storage. The poll method registers on the thread group's shared signalfd_wqh wait queue and then, under siglock, tests next_signal() against both current->pending and current->signal->shared_pending using the fd's mask. The read path calls dequeue_signal() with that same mask, so it consumes exactly the queue entries a traditional handler would have consumed. The wakeup side is already familiar from signal generation: every time __send_signal_locked() adds a signal it calls signalfd_notify(), which wakes any waiter parked on signalfd_wqh.

Reusing those two helpers has a consequence that the source states in one line and that nothing in the interface hints at: the mask stored in the context is the complement of the mask the caller passed. Both next_signal() and dequeue_signal() take a mask meaning “signals to skip” — next_signal() computes *s &~ *m, and dequeue_signal()'s parameter is normally &current->blocked. The signalfd() caller, by contrast, supplies the signals it wants to receive. do_signalfd4() reconciles the two by calling signotset(mask) and storing the inverted set, so that “what the user asked for” becomes “what these helpers will not skip.” This is why the fd can be plugged straight into the generic dequeue machinery with no wrapper logic at all, and it is also why signalfd_show_fdinfo() has to run signotset() a second time before printing: the value in /proc/<pid>/fdinfo/<fd> must be re-inverted to look like the set the program originally requested.

The wakeup is deliberately imprecise, and reading signalfd_notify() makes that obvious. It takes a signal number and ignores it. Any queued signal wakes every thread parked on that thread group's signalfd_wqh, regardless of whether the signal matches any particular descriptor's mask, because the wait queue belongs to the sighand_struct and is shared by every signalfd in the process. Each woken sleeper re-runs dequeue_signal() under siglock, finds nothing matching, and goes back to sleep. Filtering, in other words, happens at the reader and never at the waker. For the overwhelmingly common case of one or two descriptors this costs nothing, and the waitqueue_active() test at the top of signalfd_notify() makes the whole thing free for the vast majority of processes that never create a signalfd at all — but a process that creates many descriptors with disjoint masks should expect every one of them to wake on every signal. 



static __poll_t signalfd_poll(struct file *file, poll_table *wait)
{
    struct signalfd_ctx *ctx = file->private_data;
    __poll_t events = 0;

    poll_wait(file, &current->sighand->signalfd_wqh, wait);
    spin_lock_irq(&current->sighand->siglock);
    if (next_signal(&current->pending, &ctx->sigmask) ||
        next_signal(&current->signal->shared_pending, &ctx->sigmask))
        events |= EPOLLIN;
    spin_unlock_irq(&current->sighand->siglock);
    return events;
}

static ssize_t signalfd_dequeue(struct signalfd_ctx *ctx,
                                kernel_siginfo_t *info, int nonblock)
{
    DECLARE_WAITQUEUE(wait, current);

    spin_lock_irq(&current->sighand->siglock);
    ret = dequeue_signal(&ctx->sigmask, info, &type);
    switch (ret) {
    case 0:
        if (!nonblock)
            break;                    /* nothing ready: fall through to sleep */
        ret = -EAGAIN;
        fallthrough;
    default:
        spin_unlock_irq(&current->sighand->siglock);
        return ret;                   /* got one, or SFD_NONBLOCK -> -EAGAIN */
    }

    add_wait_queue(&current->sighand->signalfd_wqh, &wait);
    for (;;) {                        /* block until a matching signal */
        set_current_state(TASK_INTERRUPTIBLE);
        ret = dequeue_signal(&ctx->sigmask, info, &type);
        if (ret != 0)
            break;
        if (signal_pending(current)) {
            ret = -ERESTARTSYS;
            break;
        }
        spin_unlock_irq(&current->sighand->siglock);
        schedule();
        spin_lock_irq(&current->sighand->siglock);
    }
    spin_unlock_irq(&current->sighand->siglock);

    remove_wait_queue(&current->sighand->signalfd_wqh, &wait);
    __set_current_state(TASK_RUNNING);
    return ret;
}

The switch is doing something a plain if would obscure, and it is worth decoding because it is the only place the blocking policy is expressed. Case 0 means the first attempt found nothing. A blocking descriptor breaks out of the switch and proceeds to the sleep loop; a non-blocking one sets -EAGAIN and fallthroughs into default, which is also where a successfully dequeued signal lands. So default is the single exit for “we are not going to sleep,” whether that is because we succeeded or because we are forbidden to wait. The sleep loop itself is a textbook TASK_INTERRUPTIBLE wait, with one detail specific to this subsystem: it re-runs dequeue_signal() before testing signal_pending(), so a signal that satisfies the descriptor's mask is always preferred over aborting the read, even when some other signal is simultaneously trying to interrupt it.

There is one caveat that surprises people, and it follows directly from the use of current in these helpers. A signalfd is bound to the thread group, but a read consumes the reading thread's private queue plus the shared queue. A signal directed specifically at thread A—through tgkill(), a fault, or ptrace—lands in A's private pending and can therefore only be read through the fd by thread A, even though the descriptor could be read from any thread. Process-directed signals live in shared_pending and can be read by whichever thread reads the fd first. For predictable behavior, event-loop designs almost always route only process-directed signals through signalfd.

Reading blocks or not depending on the descriptor's mode. signalfd_read_iter() loops to fill the caller's buffer with as many records as are ready; the first record honors O_NONBLOCK (set by SFD_NONBLOCK), and after that it never blocks again, so a single read() drains the currently available signals without stalling. When no matching signal is pending and the fd is blocking, signalfd_dequeue() sleeps on signalfd_wqh until signalfd_notify() wakes it or a real signal interrupts the wait with -ERESTARTSYS.

Three details of that loop are easy to miss and all of them are observable. The buffer length is converted to a record count with count /= sizeof(struct signalfd_siginfo), and a count of zero is rejected with -EINVAL: a read() of fewer than 128 bytes is an error, not a short read, so a caller cannot discover the record size by probing. Any remainder beyond a whole number of records is simply ignored. The loop then sets nonblock = 1 after the first successful record, which is what makes a single read() drain everything currently available and stop rather than waiting for the buffer to fill. And the return statement is total ? total : ret, so once even one record has been copied the error that terminated the loop is discarded. A reader that asked for eight records, got three, and then hit -EAGAIN sees a successful three-record read; the -EAGAIN surfaces only on the next call, which is precisely the convention an epoll loop already expects from sockets.

The non-blocking decision itself has grown a second input since the interface was designed. nonblock is file->f_flags & O_NONBLOCK || iocb->ki_flags & IOCB_NOWAIT, and the descriptor is created with FMODE_NOWAIT set. That combination is what lets io_uring, described in Chapter 24, submit a read against a signalfd and have the kernel attempt it inline on the submitting thread, falling back to its worker pool only if the read would have blocked. A signalfd created without SFD_NONBLOCK is therefore still capable of a non-blocking read — the per-operation flag overrides the per-file one, and only in the permissive direction.

There is a second, less-known mode of the system call that turns the ufd argument into an input rather than a hint. Passing -1 creates a descriptor; passing an existing signalfd instead replaces its mask in place and returns the same descriptor number. do_signalfd4() validates that the descriptor really is a signalfd by comparing f_op against &signalfd_fops — a plain -EINVAL if not, and -EBADF if the descriptor is closed — then swaps the mask under siglock and calls wake_up() on signalfd_wqh. That final wakeup is the interesting part: widening a mask can make the descriptor readable without any new signal being sent, and a thread already blocked in poll() would otherwise sleep through the change. Note also that the mask is replaced wholesale rather than merged, and that the flags argument is ignored on this path, so SFD_NONBLOCK cannot be toggled this way — fcntl(F_SETFL) is the tool for that.

Both entry points share a strict size check that predates the sigsetsize convention of Section 5: sizemask must equal sizeof(sigset_t) exactly, and anything else is -EINVAL. Unlike the rt_ wrappers, there is no “smaller is acceptable” allowance. The compat entry points substitute compat_sigset_t and get_compat_sigset() for the copy and then converge on the same do_signalfd4(), so a 32-bit process on a 64-bit kernel gets identical semantics with a differently sized mask.

The interface is also intentionally conservative about which signals it will divert. Linux strips SIGKILL and SIGSTOP from the mask because those signals are not meant to be redirected into ordinary user-space event processing, mirroring their unmaskable nature everywhere else in the subsystem. The creation path, signalfd4(), accepts only two flags—SFD_CLOEXEC and SFD_NONBLOCK, defined to equal O_CLOEXEC and O_NONBLOCK—and rejects anything else with -EINVAL. Rather than invent a new VFS object, it backs the descriptor with an anonymous inode and a tiny signalfd_ctx holding just the mask, so the fd slots naturally into epoll and the rest of the kernel's I/O multiplexing infrastructure. The file is opened O_RDWR, but signalfd_fops supplies no write method, so a write attempt is rejected by the VFS; llseek is noop_llseek, making the descriptor a pure stream with no position.

Because the context owns nothing but a mask, signalfd_release() is a single kfree() — there is no reference to drop and no wait queue to unhook, since a reader removes itself from signalfd_wqh before returning. The lifetime hazard runs the other way, and it is the reason for a function that Section 2.5 mentioned only in passing. The wait queue lives in the sighand_struct, which can be freed while a descriptor referencing it is still open and still registered in somebody's epoll set. __cleanup_sighand() therefore calls signalfd_cleanup() immediately before returning the object to its slab, and that function calls wake_up_pollfree() rather than an ordinary wake-up. POLLFREE instructs every registered poll waiter to detach itself synchronously, and the WARN_ON_ONCE(waitqueue_active(wq_head)) that follows asserts that they all did. Without it, an epoll instance could retain a pointer into a freed wait queue head — a use-after-free reachable from unprivileged user space, which is exactly the class of bug wake_up_pollfree() was introduced to close.

Finally, the descriptor is introspectable. With CONFIG_PROC_FS, signalfd_show_fdinfo() prints the mask under a sigmask: key in /proc/<pid>/fdinfo/<fd>, re-inverting it first so the value reads as the set of signals the descriptor accepts. That makes it possible to inspect a running daemon and see exactly which signals its event loop has claimed, which is a genuinely useful debugging affordance when the alternative is inferring the mask from source code.

The signalfd_siginfo Record

Each read() returns one or more fixed 128-byte struct signalfd_siginfo records. The kernel builds each record in signalfd_copyinfo(), which translates the in-kernel kernel_siginfo_t into the stable user layout according to the signal's siginfo layout class. That is why the meaningful fields differ by signal type. A SIL_KILL signal fills only ssi_pid and ssi_uid; a SIL_CHLD signal adds ssi_status along with the child's accumulated ssi_utime and ssi_stime; a SIL_FAULT signal fills ssi_addr, joined by ssi_trapno on architectures that report one and by ssi_addr_lsb for machine-check errors; a SIL_POLL signal from SIGIO fills ssi_band and ssi_fd; a SIL_TIMER notification fills ssi_tid and ssi_overrun beside the payload; a SIL_RT signal from sigqueue() fills ssi_ptr and ssi_int as well as the sender's ssi_pid and ssi_uid; and a SIL_SYS seccomp trap fills ssi_syscall, ssi_arch, and ssi_call_addr. The fixed size and padding keep the record ABI-stable across kernel versions so that binaries reading the fd never need to negotiate a structure size. The source is explicit about the motive: fixed-width members were chosen because the structure “comes out of a read(2) and we really don't want to have a compat on read(2),” and the 128-byte total is enforced at build time by BUILD_BUG_ON(sizeof(struct signalfd_siginfo) != 128) so that adding a member without shrinking the padding fails the compile rather than silently breaking every existing binary.

Two lines at the top of signalfd_copyinfo() carry more weight than their length suggests. The first is memset(&new, 0, sizeof(new)), which zeroes the whole record — including the 28 bytes of tail padding — before any field is filled. The structure is an on-stack local, so without that memset a read() would hand user space whatever the kernel stack happened to contain, and the layout switch below fills only a handful of members for any given signal. This is the routine defense against kernel-memory disclosure, and it is worth noticing because it is what makes the next observation safe. The second is the copy itself: copy_to_iter_full() is all-or-nothing, so a record that cannot be written completely is not written at all and the function returns -EFAULT, leaving the signal already dequeued but undelivered. A caller that passes a bad buffer loses the signal permanently — the record has been consumed from the pending queue and there is no path that puts it back.

The switch is driven by siginfo_layout(), the same classifier copy_siginfo_to_user() consults when flattening a kernel_siginfo onto a user stack in Section 4 — the source carries a comment saying it was copied from there — so the two consumption paths agree by construction about which union member is live. Every class populates a disjoint set of fields and everything else stays zero, which makes the record a deliberately lossy projection: a reader cannot distinguish “this field does not apply to this signal” from “this field applies and its value is zero.” Interpreting ssi_pid or ssi_addr without first switching on ssi_signo and ssi_code is therefore a mistake, and it is the same mistake as reading the wrong union member from a siginfo_t in a handler — the flattening has removed the union, but not the discipline the union demanded.

One arm of the switch is defensive rather than descriptive. SIL_FAULT_BNDERR, SIL_FAULT_PKUERR, and SIL_FAULT_PERF_EVENT fall through into the plain SIL_FAULT case, and the comment explains why: those layouts are only ever produced by faults delivered synchronously to the faulting thread, so they should be impossible to observe through a descriptor. They are handled anyway, reporting just ssi_addr, in case somebody injects such a signal with rt_sigqueueinfo() and it reaches a signalfd. That is a small illustration of a rule that runs through the whole subsystem: any si_code reachable from user space must be assumed to arrive in the wrong context eventually, so every consumer needs a defined answer rather than an assumption.

The SIL_TIMER arm is where this section meets Section 6.4. It fills ssi_tid with the POSIX timer's identity and ssi_overrun with the overrun count computed by __posixtimer_deliver_signal() at dequeue. Because the record is produced by that same dequeue_signal() call, an event loop reading timer notifications from a signalfd gets the missed-expiry count for free, in band, without ever calling timer_getoverrun() — which it could not usefully call anyway, since that interface reports the count for the notification most recently taken by the calling thread. Collecting timer expiries through a descriptor is thus not merely a stylistic alternative to a handler; it is the arrangement in which overrun information is easiest to use correctly.

Deployment Patterns and Masking Discipline

Figure 11-7 shows why signalfd works best when user space first uses rt_sigprocmask() to block the interesting signals in all threads. That forces matching signals to remain pending until the designated consumer thread reads the fd. Without that mask discipline, some other thread could still take the signal asynchronously through the normal return-to-user path before the fd reader gets a chance. The kernel offers both consumption styles simultaneously; user space chooses which one actually wins.

The consequence of getting that wrong is worth stating bluntly, because it is the most common way a first attempt at signalfd fails. Creating a descriptor does not change any signal's disposition. It installs no handler, sets no SIG_IGN, and touches current->blocked not at all. A program that adds SIGTERM to a signalfd mask and then waits in epoll_wait() without having blocked SIGTERM first will simply be terminated by the default action the next time one arrives — the descriptor never becomes readable, because the signal is delivered before anything gets a chance to dequeue it through the fd. sigprocmask() with SIG_BLOCK is not an optimization here, it is the mechanism; the descriptor only ever sees signals that were prevented from being taken any other way. The two masks are also completely independent, so it is entirely possible — and always a bug — to block a signal the descriptor does not select, or to select one the program never blocks.

Threading turns that requirement into a discipline rather than a single call. current->blocked is per-thread and is inherited at creation, so the only reliable arrangement is to block the set in the main thread before spawning anything, letting every worker inherit the mask. Blocking after the fact requires visiting each thread individually, and any thread created in the window between is a thread that can steal the signal. Section 5.4 described the retargeting work that sigprocmask() performs on the way in; doing it once at startup is also what keeps that cost off the steady-state path.

This is also why signalfd is complementary to, not a replacement for, traditional handlers. Fault signals such as SIGSEGV still make the most sense as thread-directed synchronous delivery, while lifecycle signals such as SIGTERM, SIGHUP, or SIGCHLD often fit naturally into an event loop. The same process can even mix the two models. Linux does not impose a universal policy; it exposes both and lets the blocked masks decide which one can run.

A final subtlety is ownership. Because signals are deeply tied to a thread's mask and thread-group shared state, the usefulness of a given signalfd depends on how the program arranges masks across threads. The kernel will happily expose matching pending signals through the fd, but user space must still design who blocks, who waits, and who reads. That is the same discipline required for good traditional signal handling; signalfd simply makes the control flow easier to centralize.

Ownership has a sharper edge than that, though, and it follows from the context holding no task reference at all. The descriptor behaves like any other file descriptor under fork() and SCM_RIGHTS, but its meaning is resolved from current at every read() and poll(). A child that inherits a signalfd across fork() does not share the parent's signal stream; it gets a descriptor that consumes the child's own pending signals through the parent's mask. Since fork() also clears the child's pending queues while preserving the blocked mask, that descriptor starts out silent and then quietly begins answering for the wrong process. Passing one over a Unix socket produces the same effect between unrelated processes. Neither is a security hole — no signal crosses a process boundary — but both are excellent ways to build a supervisor whose shutdown path never fires, and the descriptor gives no indication that anything is wrong. The rule that follows is simple: create the signalfd after fork(), in the process that intends to read it, and set SFD_CLOEXEC so an exec() cannot carry it somewhere it will be misinterpreted.

One last property matters for epoll users specifically. Readability is computed live in signalfd_poll() by testing the pending queues, not latched when a signal arrives, so the descriptor is naturally level-triggered: it stays readable exactly as long as a matching signal remains pending, and stops the moment the last one is dequeued. Registering it with EPOLLET works, but only because signalfd_notify() fires on every send; the safe pattern with edge triggering is the usual one of reading until -EAGAIN, which the drain loop of Section 7.1 already makes a single read() away.

Coredump on Fatal Signals

Some default actions do more than terminate a process: they request a core dump. In Linux 7.0.12, get_signal() recognizes this by calling sig_kernel_coredump(signr) on a fatal signal such as SIGSEGV, SIGABRT, SIGILL, SIGBUS, SIGFPE, or SIGSYS. If a dump is appropriate, the kernel marks the current task as signaled, emits optional diagnostics, notifies connectors, and then calls vfs_coredump() before completing group exit. The coredump path is therefore not an add-on utility; it is baked into the fatal-signal delivery path.

Despite that complexity, the design preserves the essential Unix promise. Fatal signals still produce the same user-visible outcomes: the process dies, the parent can learn which signal was responsible, and a diagnostic image may be produced. Linux 7.0.12 simply wraps those outcomes in safer namespace, credential, and helper orchestration. The coredump subsystem is thus an example of evolutionary compatibility done right: the old behavior remains recognizable while the implementation grows around modern deployment models. The subsections below follow the dump from its trigger, through whole-process coordination, to its destination and the policies that gate it.

One user-visible detail is worth fixing in mind before the mechanics, because it is the only part of this machinery most programs ever observe. A dump that actually happened is reported to the parent by setting bit 0x80 in the group exit code — the bit WCOREDUMP() tests in the status word returned by wait(). coredump_finish() sets it at the very end, and only if the image was really written and the dumper was not itself killed part-way through. Everything else in this section is, from user space's point of view, an elaborate apparatus for deciding whether that one bit gets set.

Triggering the Dump from get_signal()

The trigger lives in the fatal default-action path of get_signal(). When sig_kernel_coredump(signr) is true, the kernel optionally prints a diagnostic through print_fatal_signal(), notifies subscribers via proc_coredump_connector(), and calls vfs_coredump() with the triggering kernel_siginfo_t. Only after the dump work settles does the thread group finish exiting, which is why a coredumping signal can turn the seemingly simple question “which signal is next?” into one of the heaviest control flows in the process life cycle.

vfs_coredump() in fs/coredump.c snapshots everything the dump will need into a struct coredump_params: the triggering siginfo, the RLIMIT_CORE limit, a snapshot of the mm's dumpability flags, and the current CPU. It then runs a fixed sequence—coredump_skip() to decide whether to dump at all, coredump_wait() to quiesce the other threads, do_coredump() to actually write the image, and coredump_cleanup() to release the rendezvous state. Separating the parameter snapshot from the writing stages is what lets the dump run safely even as the rest of the thread group is being torn down.

The snapshot of mm->flags is taken for a reason the source spells out: those bits are not protected by any lock, and a dump that re-read them mid-flight could make inconsistent decisions about which memory regions to include. __mm_flags_get_dumpable() therefore extracts the MMF_DUMP* bits once, and every later test — the dumpability gate, the per-VMA filter, the choice of credentials — consults cprm.mm_flags rather than the live mm. Fixing the CPU number at the same moment serves the same purpose: the note written into the image should record where the crash happened, not where the dumping thread later drifted to.

Two steps sit between the snapshot and coredump_wait() that the sequence above omits, and both matter. The first is audit_core_dumps(), which records the crash in the audit log before any policy is consulted, so a dump that is subsequently refused still leaves a trace. The second is the credential switch, and it is the security core of the whole subsystem. vfs_coredump() takes a fresh copy of the current credentials with prepare_creds(), and if coredump_force_suid_safe() reports that the mm is marked SUID_DUMP_ROOT, it overrides cred->fsuid to GLOBAL_ROOT_UID. do_coredump() then runs inside scoped_with_creds(cred), so the file creation, the helper spawn, and the socket connect all happen under those credentials rather than under whatever the crashing process was running as.

The comment above that override explains the reasoning better than a paraphrase can: the kernel cannot trust fsuid to be the “true” identity of a process that has crossed a privilege boundary, and does not know its entire history — it knows only that the process is tainted. So such a dump is written as root, and, as Section 8.4 describes, only into a destination that an unprivileged user could not have chosen. Note the asymmetry this creates: raising privilege for the dump is safe precisely because the destination is simultaneously constrained; either half without the other would be a vulnerability rather than a mitigation.

Process-Wide Coordination

A core dump must capture a single, consistent address space, so exactly one thread may write it while every sibling stops touching shared memory. Linux arranges this rendezvous through struct core_state, reached from signal_struct.core_state. Inside coredump_wait(), the helper zap_threads() publishes the core_state pointer, marks the dumping task with PF_DUMPCORE, and wakes every other thread in the group with a fatal condition so they head toward exit.

zap_threads() refuses to start under two conditions, and returning -EAGAIN from either one abandons the dump before anything is written. It bails if SIGNAL_GROUP_EXIT is already set, because the group is being torn down by some other decision and there is no coherent address space to capture, and it bails if group_exec_task is set, because a sibling is midway through execve() and the mm is about to be replaced. Both tests happen under siglock together with the publication of core_state, which is what makes “a coredump is in progress” an atomically observable condition — and Section 3.1 already relies on that, since prepare_signal() lets SIGKILL through to a group that is exiting precisely so a stuck dump can still be killed.

zap_process() then does something more forceful than the phrase “wakes with a fatal condition” suggests: it sets SIGNAL_GROUP_EXIT, clears every thread's job-control pending state, and queues a genuine SIGKILL into each sibling's private pending set followed by signal_wake_up(t, 1). The threads are really being killed, not merely nudged. Two exclusions shape the count it returns: current is skipped, because the dumper must survive, and any thread already carrying PF_POSTCOREDUMP is skipped, because it has passed the point where it could still participate. That count is stored in core_state->nr_threads and is exactly what the dumper will wait for. The last act of zap_threads() is to clear TIF_SIGPENDING on the dumper itself — without it, the thread that just made the whole group fatal would immediately notice pending work and abort its own dump.

The siblings do not simply die. As each one runs coredump_task_exit() from kernel/exit.c, it decrements the live-thread count and, when the count reaches zero, completes core_state->startup to release the dumper. Whether it also parks depends on a test the summary above glosses over: only a thread carrying PF_SIGNALED — one that is dying because of the signal — links itself onto the core_state->dumper list and then sleeps in TASK_IDLE | TASK_FREEZABLE until released. A thread that was already exiting for its own reasons sets self.task = NULL, skips the list, and falls straight out of the loop. That distinction matters for the handshake at the end: coredump_finish() walks the list and clears each entry's task pointer before waking its owner, and the sleeping thread's loop condition is precisely if (!self.task) break, so the list membership is the wakeup protocol. A thread that has already passed the point of no return sets PF_POSTCOREDUMP, which tells the zap logic to ignore it.

Waiting for the completion is not the end of the barrier, and the step that follows is easy to overlook but essential on both of this book's architectures. Having been released, the dumper walks the parked list a second time calling wait_task_inactive() on every entry. The comment gives the reason: it must wait for each thread to become genuinely inactive so that all of its context — “extended register state, like fpu etc” — has been written back to memory. A thread that is off-CPU but not yet fully descheduled may still hold live architectural state in registers, and on x86_64 that means the FPU and AVX state, while on ARM64 it means the SVE and SME register files whose variable size Section 4.5 described. Without this second wait the notes in the image could record stale register contents for exactly the threads a debugger most wants to inspect.

The result is a clean barrier: the dumper proceeds only once it knows the address space is frozen and every sibling's register state has landed in memory, and the parked threads are reaped together after the image is written.

This choreography is one of the biggest conceptual gaps between the old single-thread narrative and modern Linux. In 2.6-era teaching it was easy to imagine “the process dumped core” as a direct consequence of one task taking one signal. In Linux 7.0.12 the same outcome coordinates many threads so that helpers and the parent later observe one coherent termination event rather than a half-dozen unrelated thread deaths. The signal subsystem provides the trigger; the coredump code provides the crash choreography.

The teardown half closes the loop and produces the one fact user space sees. coredump_cleanup() closes the output file, drops the pipe-count reservation if one was taken, frees the pattern buffer, and calls coredump_finish(), which runs under siglock to clear signal->core_state and — if the image was written and no fatal signal is pending on the dumper — ORs 0x80 into group_exit_code. That is the bit WCOREDUMP() reports. Its second condition is the interesting one: a dumper that was itself SIGKILLed midway does not claim success, so the parent is not told a usable image exists when the writing was cut short. Only then does the function walk the parked list, clearing curr->task and waking each sibling, with an explicit smp_mb() ensuring the sleeper cannot observe its own task pointer cleared before the dumper has read next — the list is being dismantled by one side while the other side is using it as a wakeup flag.

The dump is also abortable while it runs. dump_interrupted() is consulted between writes and reports true when a fatal signal is pending or the task is being frozen, which lets an administrator kill a process that is dumping a very large address space, and lets suspend proceed without waiting for one. The image left behind is truncated rather than absent, but because the abort prevents core_dumped from being set, WCOREDUMP() will not advertise it as complete.

Destinations: File, Pipe, and Socket

Where the image goes is controlled by the core_pattern sysctl, which do_coredump() parses through coredump_parse() into one of four destination types—COREDUMP_FILE, COREDUMP_PIPE, COREDUMP_SOCK, and COREDUMP_SOCK_REQ. A plain pattern names a regular file; a pattern beginning with | pipes the dump into a usermode-helper program; a pattern beginning with @ streams the dump over an AF_UNIX socket to a listening collector; and a pattern beginning with @@ selects the same socket transport but preceded by a feature negotiation, described below. The socket paths are a distinctly modern addition that let a privileged crash-collection service receive dumps without the fork-and-exec cost of a pipe helper. A read-only kernel/core_modes sysctl advertises which of these the running kernel supports, listing file, pipe, and—only when CONFIG_UNIX is enabled—socket, so a collector can probe rather than guess.

Socket patterns are validated far more strictly than file patterns, in two places. check_coredump_socket() runs when core_pattern is written and rejects the write outright unless the writer is in the initial mount namespace, on the grounds that a socket path resolved in some other namespace would give a misleading impression of what is supported. It also requires an absolute path, forbids .. components, and enforces UNIX_PATH_MAX. coredump_parse() repeats those checks at crash time and adds one more: the path may not contain a space, explicitly reserving whitespace so that future kernels can append parameters to a socket pattern without breaking existing configurations.

Socket patterns also accept no % specifiers at all — the path after the @ is copied verbatim. This is a deliberate design decision rather than an omission, and the source explains it: everything a collector might have learned from an expanded pattern is available more safely from the peer credentials of the connection itself. SO_PEERPIDFD yields a pidfd for the crashing process, and that pidfd can then be used to open /proc/<pid> without any risk of PID recycling — the race that makes a %p-derived path fundamentally untrustworthy. The socket transport thus replaces string interpolation with a handle, which is the same shift Section 5.2 described when pidfd_send_signal() replaced PID-based signaling.

The pattern also carries % specifiers that coredump_parse() expands—among them %p and %P for the namespace-local and global PID, %e and %E for the executable name and path, %s for the fatal signal number, %u/%g for credentials, %t for the crash time, and %h for the hostname. Several more are easy to miss and occasionally exactly what a collector needs: %i and %I give the thread ID rather than the thread-group ID, namespace-local and global respectively, which is the only way a pattern can name the specific thread that faulted; %f gives the executable's full path with its / characters escaped so the result stays a single component; %d reports the dumpability mode; %c the effective RLIMIT_CORE; %C the CPU the crash was noticed on; and %F installs a pidfd for the crashing process, which is meaningful only for a pipe destination. If kernel.core_uses_pid is set, the PID is appended even when the pattern did not request it.

For pipe destinations the kernel.core_pipe_limit sysctl bounds how many crashing processes may have a helper running at once; coredump_pipe() takes its reservation with atomic_inc_return(&core_pipe_count) and coredump_cleanup() releases it. When that gating is active, do_coredump() waits for the helper to finish, which is what lets a collector inspect /proc/<pid> of the crashing task while it is still present rather than racing its disappearance.

The pipe helper receives more than a stream of bytes. umh_coredump_setup() installs the read end of the pipe as file descriptor 0, and—because a usermode helper is always spawned from a workqueue or from kthreadd and therefore starts with a clean descriptor table—it can unconditionally install a pidfs file for the crashing thread-group leader at the fixed descriptor number 3 (COREDUMP_PIDFD_NUMBER). A helper can therefore identify its subject without parsing anything. The same function sets RLIMIT_CORE to the sentinel value 1 in the helper, which is how the kernel traps recursion: if the helper itself crashes, coredump_pipe() sees a limit of exactly 1 and refuses, logging RLIMIT_CORE is set to 1, aborting core. Outside that sentinel, pipes ignore the limit entirely — cprm->limit is reset to RLIM_INFINITY, since nothing is being written to a filesystem.

A file destination is subjected to a long sequence of checks that exist entirely to prevent a crashing process from being tricked into writing through a path an attacker controls. coredump_file() opens with O_CREAT | O_WRONLY | O_NOFOLLOW | O_LARGEFILE | O_EXCL, so an existing file or a symlink at the target aborts the dump rather than being followed. For a normal dump it first unlinks any stale file, but for a SUID_DUMP_ROOT dump it deliberately does not, because it is running as root and must not delete some other user's core file. After the open it verifies that the inode has exactly one link, that the dentry is still hashed, that the file is a regular file, that the owner still matches current_fsuid(), and that the mode is still exactly 0600 — the last two guarding against filesystems such as vfat that silently rewrite ownership and permissions at creation time. Only then does it truncate the file and accept it.

One subtlety in that path is worth drawing out, because it defeats an attack that the “fully qualified path” rule alone would not. An unprivileged user can create a user namespace and pivot current->fs->root to a directory of their choosing, at which point an absolute path is absolute only with respect to a root they control. So for SUID_DUMP_ROOT dumps, coredump_file() ignores the crashing process's root entirely and resolves the name with file_open_root() against init_task's root directory instead. The path in core_pattern therefore always means what the administrator who set it meant.

The @@ form deserves separate treatment, because it is the only destination that can talk back. Ordinary destinations are one-way: the kernel decides everything and either writes the image or does not. A COREDUMP_SOCK_REQ collector, by contrast, is offered a vote. Once coredump_sock_connect() has established the connection, coredump_sock_request() sends a struct coredump_req announcing which policies this kernel understands, reads back a struct coredump_ack naming the one the collector wants, and stores the answer in cn->mask. 

/* include/uapi/linux/coredump.h */
enum {
    COREDUMP_KERNEL    = (1ULL << 0),  /* kernel writes the coredump */
    COREDUMP_USERSPACE = (1ULL << 1),  /* userspace writes it itself */
    COREDUMP_REJECT    = (1ULL << 2),  /* don't generate one at all  */
    COREDUMP_WAIT      = (1ULL << 3),  /* wait for the server        */
};

struct coredump_req {
    __u32 size;        /* size of this structure       */
    __u32 size_ack;    /* size of struct coredump_ack  */
    __u64 mask;        /* features the kernel supports */
};

struct coredump_ack {
    __u32 size;        /* size of this structure       */
    __u32 spare;       /* reserved, must be zero       */
    __u64 mask;        /* features userspace selected  */
};

Both structures carry their own size, and that is what makes the protocol extensible in both directions. Userspace may MSG_PEEK the kernel's size field before deciding how much to read, and the kernel does exactly the same with the acknowledgement: it peeks ack.size, rejects anything smaller than COREDUMP_ACK_SIZE_VER0 or larger than the structure it knows, and only then reads the body. Older userspace talking to a newer kernel reads a prefix it understands; newer userspace talking to an older kernel is told its request is too large.

Rejections are not silent. Before closing the connection the kernel writes a single byte on the socket—an enum coredump_mark value—so the collector learns why it was refused rather than merely observing a hangup. COREDUMP_MARK_MINSIZE and COREDUMP_MARK_MAXSIZE report a bad acknowledgement size, COREDUMP_MARK_UNSUPPORTED reports a flag the kernel never advertised or a non-zero spare field, and COREDUMP_MARK_CONFLICTING reports mutually exclusive choices — the kernel insists via hweight64() that exactly one of COREDUMP_KERNEL, COREDUMP_USERSPACE, and COREDUMP_REJECT be set. A successful negotiation ends with COREDUMP_MARK_REQACK.

The selected mask then steers the rest of do_coredump(), and this is where the collector's vote becomes consequential. COREDUMP_REJECT makes the kernel abandon the dump after the connection is made, letting policy live in userspace where it can consider things the kernel cannot, such as which executable crashed or how many dumps that service has already produced today. COREDUMP_USERSPACE tells the kernel not to write the image itself; the collector will assemble it from the pidfd, and the kernel simply marks core_dumped true so that WCOREDUMP() still reports honestly. COREDUMP_KERNEL, the default that coredump_parse() installs for every other destination type, means the kernel writes as usual. COREDUMP_WAIT is orthogonal and simply asks the kernel to block until the collector is finished — the socket equivalent of wait_for_dump_helpers(), and the flag coredump_parse() sets automatically whenever core_pipe_limit is non-zero.

One further step precedes the writing, and its justification is a piece of kernel history. do_coredump() calls unshare_files(), which the comment describes as almost always a no-op, before invoking the dumper — because the spufs coredump code on Cell reads the crashing task's file descriptor table, and a shared table could be mutated underneath it. When the write finishes, coredump_sock_shutdown() half-closes the socket so the collector sees a clean end-of-stream rather than having to infer completion.

Regardless of destination, the bytes themselves are produced by the binary format's dumper. do_coredump() invokes binfmt->core_dump(cprm), which for ELF executables is elf_core_dump() in fs/binfmt_elf.c. That callback walks the VMAs, writes program headers and notes describing registers and auxiliary state, and emits the memory contents, so the format-specific knowledge stays in the binfmt layer while the generic coredump code handles coordination, naming, and routing.

Dumpability and Resource Limits

Not every fatal signal produces a dump, and the gating is deliberately conservative for security. coredump_skip() refuses in three cases: when no linux_binfmt is registered for the process at all, when the binary format provides no core_dump callback, and when __get_dumpable(cprm->mm_flags) reports the mm is not dumpable. Dumpability is a three-valued flag stored in mm->flags and read through get_dumpable(): SUID_DUMP_DISABLE forbids dumps entirely, SUID_DUMP_USER is the normal case, and SUID_DUMP_ROOT marks a privileged process whose dump must be owned and protected accordingly.

The exec path resets dumpability whenever a program crosses a privilege boundary, so a freshly execve()'d setuid binary is not dumpable by its unprivileged invoker. That prevents an attacker from learning the memory contents of a privileged program simply by crashing it. On top of dumpability, RLIMIT_CORE bounds the size of a file dump, and a format may declare a min_coredump below which a dump is not worth attempting; both are checked before any bytes are written. Together these controls make coredumps useful for debugging without turning them into an information-disclosure channel.

SUID_DUMP_ROOT is not simply “dump as root” — it is a mode that only makes sense in combination with a restricted destination, and the kernel notices when an administrator has configured only half of it. validate_coredump_safety() runs whenever core_pattern or fs.suid_dumpable changes and warns if suid_dumpable is 2 while core_pattern begins with something other than /, |, or @. A relative pattern under that mode would place a root-owned dump of a privileged process's memory into whatever directory the process happened to be running in. The message even tells the administrator the fix — set kernel.core_pattern before fs.suid_dumpable — because the two sysctls are checked independently and the unsafe window exists only between them.

Dumpability decides whether to dump; a separate and much less widely known mechanism decides what. The upper bits of mm->flags, above the two dumpability bits, hold a nine-bit coredump filter that user space can read and write through /proc/<pid>/coredump_filter. vma_dump_size() consults it for every VMA and decides between dumping the region whole, dumping only its first page, or skipping it entirely. The distinction the filter draws is between memory the kernel could reconstruct from elsewhere and memory it could not: private anonymous pages are unique to the process and are dumped by default, while file-backed pages can usually be recovered from the file and are not.

If the inode has any execute bit set, vma_dump_size() returns PAGE_SIZE immediately; otherwise it cannot check for the ELF magic on the spot, since it holds the mmap lock and copy_from_user() is unavailable there, so it returns a placeholder that dump_vma_snapshot() resolves once the lock is dropped. The result is a dump that is a small fraction of the process's resident size yet still fully symbolizable.

Two categories bypass the filter in opposite directions. always_dump_vma() forces the vDSO and vsyscall mappings to be dumped whole regardless of any bit, because a debugger cannot recover them from any file — Chapter 10 described how the vDSO is a kernel-supplied image with no on-disk counterpart. In the other direction, a VMA carrying VM_DONTDUMP — the flag madvise(MADV_DONTDUMP) sets — is skipped unconditionally, as are VM_IO regions, since reading a device mapping during a crash could have side effects or simply hang. Applications holding key material commonly use MADV_DONTDUMP for exactly this reason.

Three further sysctls tune the result. kernel.core_file_note_size_limit caps the total size of the notes segment—registers, auxiliary vectors, file mappings—at 4 MiB by default and 16 MiB at most, bounding what a process with tens of thousands of mappings can force the kernel to assemble. kernel.core_sort_vma asks dump_vma_snapshot() to sort the captured regions by size with cmp_vma_size() before writing, which helps tools that read dumps incrementally. And kernel.core_uses_pid appends the PID to the file name even when the pattern did not ask for it, the oldest of these knobs and the crudest way to keep concurrent dumps from colliding — a job O_EXCL now handles more robustly.

Summary

Signals in Linux 7.0.12 still look familiar from user space: numbers, masks, handlers, default actions, and a handful of classic syscalls. Underneath that familiar shell, however, the subsystem has evolved into a carefully layered engine for per-thread and per-process notifications, payload-bearing queued events, architecture-specific context save and restore, descriptor-based waiting, and synchronized fatal teardown. The old Linux 2.6/i386 chapter taught the vocabulary. This chapter updates the grammar needed to read modern 64-bit kernels fluently.

The most important structural ideas are worth retaining as a compact checklist. A signal occurrence lives first in a pending queue plus bitmap, either private or shared. complete_signal() decides who should notice it. get_signal() decides whether it is ignored, handled, stopped, continued, made fatal, or routed to coredump. Architecture code then translates that generic decision into a concrete user-space frame, and rt_sigreturn later restores the interrupted machine state.

It is also useful to categorize each signal path by the kind of state it manipulates. Some paths mostly touch policy state, such as installing a disposition or changing a blocked mask. Some mostly touch queue state, such as sending a real-time signal or consuming one through signalfd. Some mostly touch machine state, such as building an ARM64 frame with SVE records or restoring an x86_64 XSAVE image through rt_sigreturn. Thinking in those categories makes the otherwise sprawling code much easier to navigate.

  • Read sigset_t operations as fast-path eligibility tests.
  • Read sigqueue objects as payload-preserving event records.
  • Read sighand_struct as the shared policy anchor for one thread group.
  • Read signal_struct as the shared runtime state anchor for that same group.
  • Read complete_signal() as a wakeup policy function, not as a delivery function.
  • Read get_signal() as the one place where pending events become concrete user-visible actions.
  • Read x64_setup_rt_frame() and setup_rt_frame() as ABI translators from generic signal decisions to architecture state.
  • Read rt_sigreturn as a controlled reload of user-supplied machine state guarded by validation.
  • Read force_sig*() as the escape hatch for signals the kernel refuses to let a process ignore, block, or handle away.
  • Read sigqueue_alloc() and SIGQUEUE_PREALLOC as the answer to a question the fast path cannot ask: what happens when an event must be delivered but memory cannot be allocated?
  • Read signalfd as a second reader of the very same pending queues get_signal() drains, not as a parallel mechanism.
  • Read fs/coredump.c as a policy engine that happens to write a file, rather than a file writer that happens to check policy.

That checklist is intentionally mechanical. Signals can feel mysterious when described only in terms of asynchronous control flow, but the implementation becomes much less mysterious once each helper is mapped to one of those jobs. Linux 7.0.12 did not make signals conceptually stranger than Linux 2.6. It mostly made the boundaries between policy, queueing, and ABI restoration sharper and more explicit.

Three themes recur across the sections above often enough to be worth naming, because each one explains a whole family of otherwise arbitrary-looking code. The first is the retreat from PID numbers toward handles: pidfd_send_signal() replaces a racy numeric target with a stable object, and the coredump socket refuses % specifiers entirely because SO_PEERPIDFD gives a collector something better than an interpolated string. The second is preallocation wherever failure is unacceptable: a POSIX timer carries its sigqueue node inside struct k_itimer from the moment it is created, and force_sig() falls back to the statically embedded queue entry, because an expiry or a fault must be reportable even when no memory can be had. The third is the separation of decision from ABI: get_signal() decides, architecture code translates, and the fact that signalfd and coredump can both hook the same decision point without touching a line of arch/ code is the proof that the split is real.

What changed most since Linux 2.6 is not the existence of these stages but the amount of policy and state each one now carries. kernel_siginfo_t is richer. sigqueue objects are namespace-accounted. pidfd_send_signal() eliminates old PID races. signalfd lets event loops consume signals without asynchronous handlers. Coredumping grew from a side effect into a negotiation. ARM64 and x86_64 preserve far more architectural state than the old i386 path ever had to consider — and must now also unwind lock-free user-space state that i386 had no concept of.

Seen together, Table 11-21 and the earlier figures suggest a practical reading strategy for current signal code. Start in kernel/signal.c to understand policy and queue movement. Then switch to the architecture file only when the question becomes “what exact frame or register image does user space see?” That division of labor is far stronger in Linux 7.0.12 than it was in Linux 2.6.

Yet the subsystem remains coherent because Linux kept the central abstraction stable. A signal is still a pending asynchronous event with a number, a disposition, and delivery rules. By keeping that abstraction stable while modernizing the plumbing around it, Linux made signals old enough to be universal and modern enough to remain useful. That tension between historical compatibility and internal evolution is one of the clearest themes in the kernel as a whole.
