The Virtual Filesystem, or VFS, is the layer that lets Linux treat ext4, XFS, tmpfs, procfs, NFS, and device files as members of one coherent namespace. A process issues openat2(),read(),renameat2(), or flock(); the system-call entry code reaches generic VFS routines; and only after permissions, mount traversal, pathname lookup, and descriptor management are settled does the kernel call filesystem-specific methods. The result is not merely an object-oriented wrapper around disk formats. It is the common concurrency contract for names, files, mounts, credentials, and byte ranges.

This chapter follows Linux 7.0.12 rather than the Linux 2.6/i386 implementation. The vocabulary is deliberately familiar—superblocks, inodes, dentries, and files still form the common file model—but the implementation has changed in ways that matter on x86_64 and ARM64. The global dcache_lock is gone, pathname lookup begins in RCU mode, file descriptor tables are RCU-published, mounts use fd-based construction, and file references use file_ref_t rather than the plain atomic_t f_count of Linux 2.6.

Code fragments throughout are focused excerpts, with ... standing for fields or checks that are not relevant to the local point. The reader should treat this chapter as a guided map through the modern kernel: it explains the data structures, then follows the principal operations that allocate, connect, look up, read, write, annotate, watch, lock, and finally release them.

All source-code references in this chapter refer to the Linux 7.0.12 tree. The files the chapter works from are listed by topic in Source Trails.

The Role of the Virtual Filesystem

The VFS exists because Linux supports more than one persistent storage format and more than one kind of object that can be named like a file. A pathname can designate an ext4 regular file, an XFS directory, a tmpfs object backed by memory, a procfs control file synthesized on demand, a socket, a device node, or an automount trigger. User programs should not need to know which of those implementations answered a lookup before they can call statx() or read().

The layer is therefore a narrow waist. Above it are system calls, file descriptors, credentials, namespaces, and the page cache. Below it are concrete filesystems and special filesystems. In the middle are stable object shapes—struct super_block, struct inode, struct dentry, and struct file—plus operation tables that let each implementation provide its own behavior only where necessary.

The narrow-waist design is what lets a single line of application code work everywhere. When a program calls read(), the C library issues one system call regardless of whether the descriptor names an ext4 file, a pipe, a character device, or a synthetic procfs node. The kernel's system-call entry code does not branch on filesystem type; it hands the descriptor to a generic VFS routine, which resolves the current object shapes and then calls exactly one method pointer from the appropriate operations table. The concrete filesystem supplies that method. Everything above the waist is written once; everything below it is written per filesystem.

This inversion is worth stating explicitly because it is the single most important idea in the chapter. In a monolithic design each filesystem would re-implement descriptor management, permission checks, and the page cache. In Linux the VFS owns those concerns and delegates only the medium-specific parts—how to fetch an inode from disk, how to lay out a directory, how to talk to a server—to the filesystem through function pointers. The rest of the chapter is essentially a tour of those object shapes and the points at which the VFS calls down into a specific implementation.

The slogan usually attached to this design—"everything is a file"—is worth stating more precisely, because the kernel does not quite implement it. What Linux actually provides is that everything reachable from a process is reachable through a file descriptor. A socket, a pipe, an eventfd, an epoll set, an io_uring ring, a memfd, a timer, a pidfd, and a mount object all have a struct file with a real f_op table, so read(), poll(), close(), and descriptor inheritance work on them without special cases. Only some of them have a pathname. Sockets and anonymous inodes live on internal mounts—sockfs, pipefs, anon_inodefs—that are pinned by the kernel and never attached to any mount namespace, so no name can ever resolve to them. Section 5 returns to how those internal mounts are built; the point here is that the VFS has two halves that are often confused, and only the descriptor half is truly universal.

The narrow waist is also not a fixed boundary. FUSE moves everything below it into a user process: the kernel-side fs/fuse module implements the operation tables, but each method serializes a request onto a descriptor that a userspace daemon reads and answers. Overlayfs does something structurally similar in the other direction, implementing its methods by calling back into the VFS against a lower filesystem. Both are ordinary filesystems as far as the layer above is concerned, which is the strongest evidence that the waist is defined by the method tables and not by any assumption about what lies underneath them. Filesystem Classes

A useful first classification separates device-backed filesystems from nodev and single-instance filesystems. Device-backed filesystems such as ext4 and XFS need a block device and usually create a superblock with get_tree_bdev(). Memory and synthetic filesystems such as tmpfs, procfs, and sysfs use helpers such as get_tree_nodev(),get_tree_single(), or get_tree_keyed(), because their backing store is not a disk partition.

In 2.6-era terminology proc and devpts are “special filesystems”, and that remains a good user-level phrase. The important Linux 7.0.12 detail is that these filesystems are not exceptions to the VFS. They register a file_system_type, allocate inodes, install dentries, and expose operation tables just like ext4 does. What differs is the implementation hidden behind those callbacks.

Network filesystems form a third practical class. NFS, CIFS, and overlay filesystems can revalidate dentries, translate credentials, or forward operations to another server or lower filesystem. Their presence explains why dentry operations include d_revalidate, why path lookup must sometimes abandon RCU-walk, and why an apparently simple rename() may involve export handles, leases, delegations, and remote cache coherency.

The 2.6-era taxonomy draws the primary line between disk-based, network, and special filesystems, and it is still pedagogically useful. Linux 7.0.12 encodes the disk-based case concretely: a file_system_type that needs a block device sets the FS_REQUIRES_DEV flag, which tells the mount machinery to open and claim a block device before building the superblock. Filesystems without that flag are expected to obtain their store some other way—from anonymous memory, from another mounted tree, or from a remote endpoint—and they use the corresponding get_tree_*() helper instead of get_tree_bdev().

The class of a filesystem also determines the lifetime and sharing rules of its superblock. Two mounts of the same block device normally share one superblock, because the on-disk image is a single source of truth; mounting it twice must not produce two independent caches that could corrupt each other. A nodev filesystem such as tmpfs, by contrast, usually creates a fresh superblock for every mount, because each instance is a distinct, private store. This is why the same word "mount" can mean "attach another view of an existing filesystem" or "instantiate a brand-new filesystem" depending on the class, and why the VFS keys superblock reuse on the filesystem type and its device or key rather than on the mount path. Section 5.2 shows the four get_tree_*() helpers that implement these sharing rules.

It is worth being clear that none of these classes exists as a kernel data structure. There is no enumeration of "disk-based" or "network" filesystems anywhere in the tree; the taxonomy is a reader's aid. What the kernel does encode is a small set of capability bits in the fs_flags field of file_system_type, and each bit answers exactly one question the generic layer needs answered before it can proceed. FS_REQUIRES_DEV tells the mount machinery to expect a block device. FS_USERNS_MOUNT says an unprivileged user namespace may mount this type at all, which is the gate that lets containers mount tmpfs and procfs but not ext4. FS_ALLOW_IDMAP asserts that every method has been audited to translate owner identity through the mount's idmapping rather than using the raw on-disk values. FS_DISALLOW_NOTIFY_PERM refuses fanotify permission events, because a filesystem that can block on a userspace listener while holding VFS locks is a deadlock waiting to happen. Table 12-18 lists the full set.

Three of those bits are recent enough that they did not exist when most VFS documentation was written, and each marks a place where the generic layer had to stop assuming all filesystems behave alike. FS_MGTIME opts a filesystem into multigrain timestamps, in which the kernel keeps a coarse timestamp by default and refines an inode's i_mtime/i_ctime to fine granularity only when someone has actually observed the old value—a compromise between the cost of a high-resolution clock read on every write and the requirement that NFS and inotify be able to tell two writes apart. FS_LBS declares that the filesystem can cope with a block size larger than PAGE_SIZE, which on x86_64 with 4 KiB pages means block sizes of 8 KiB and up; the block layer refuses such a superblock unless the flag is set and CONFIG_TRANSPARENT_HUGEPAGE is enabled, because the page cache must be able to hold a whole block in one folio. Only ext4 and XFS set it in 7.0.12. FS_POWER_FREEZE asks the VFS to freeze the filesystem across suspend and hibernate unconditionally, rather than relying on writeback having quiesced; efivarfs is its only user in 7.0.12.

A fourth class has become important enough to name separately: filesystems whose implementation is a user process. FUSE is the general case, and it is not a stacked filesystem—there is no lower filesystem to forward to—nor a network one, though it can be used to build either. What makes it a distinct class for the VFS is that every method has an unbounded latency and a failure mode that no in-kernel filesystem has, namely that the server can simply stop answering. Much of the awkwardness in the VFS's locking rules, and several of the restrictions expressed through fs_flags, exist because a method may be a round trip to an untrusted process. The Common File Model

The common file model says that every open file descriptor reaches a struct file; every file has a struct path; the path names a mount and a dentry; a positive dentry points at an inode; and the inode belongs to a superblock. The model is independent of the storage medium. A tmpfs inode and an ext4 inode use the same VFS-facing fields even though their private data and allocation rules differ radically.

The common file model consists of four object types, each holding a different slice of the information the kernel needs to service a file operation:

  • The superblock object (struct super_block) stores information about a mounted filesystem as a whole: the filesystem type, block size and size limits, the root dentry, mount flags, the backing block device for disk filesystems, the owning user namespace, and a pointer to filesystem-private data. There is one superblock per mounted instance, and it carries the s_op table of filesystem-wide operations.
  • The inode object (struct inode) stores all the metadata that identifies one file independently of its name: the inode number, type and permission bits, owner and group, size, link count, timestamps, and pointers to the address space (page cache) and to the i_op and i_fop operation tables. One inode exists per file, no matter how many names or open descriptors refer to it.
  • The dentry object (struct dentry) stores the association between one component name and its inode—that is, one directory entry. It caches the name, a pointer to the parent dentry, the target inode, and the d_op table. Because hard links give one inode several names, one inode may have several dentries, and the dentry cache exists to make repeated name lookups fast.
  • The file object (struct file) stores the state of one open file description: the current file position, the access mode and status flags, the credentials captured at open time, the f_path that pins the mount and dentry, and the f_op table. Two descriptors opened on the same file get two file objects with independent positions and flags, which is why the file object—not the inode—is the natural home for per-open state.

A helpful way to remember the split is by lifetime and multiplicity. A superblock is per mounted filesystem; an inode is per file; a dentry is per name; and a file object is per open. Figure 12-2 shows how a descriptor threads through all four before reaching the concrete filesystem.

This is also the point where Linux differs most strongly from simplistic textbook diagrams. A dentry is not “the file,” because hard links can give one inode several dentries. A file is not “the inode,” because two descriptors opened on the same inode can carry different file positions, flags, credentials, and private data. A superblock is not merely an on-disk block; it is the in-memory instance of a mounted filesystem and can describe nodev filesystems with no disk superblock at all.

On x86_64 and ARM64, pointer-sized references make the object graph compact but highly concurrent. VFS paths are copied, refcounted, and validated while other CPUs rename directories, shrink caches, unmount trees, or close descriptors. The modern implementation therefore combines reference counts, RCU grace periods, per-object spinlocks, sequence counters, and namespace locks rather than relying on one global filesystem lock.

The struct path pairing of a mount and a dentry deserves special emphasis because it did not exist as a first-class idea in the oldest VFS descriptions. A dentry alone is ambiguous once bind mounts and mount namespaces enter the picture: the very same directory dentry can be visible at several places in the tree, each reached through a different struct vfsmount. Pairing the dentry with its mount is what lets the kernel answer questions the old model could not—which mount's flags apply, whether this view is read-only, which idmapping to use for owner checks, and whether crossing into a child mount is permitted. Every open file therefore stores a full f_path, not just a dentry.

Polymorphism in the VFS is achieved entirely through the operations tables rather than through any language-level inheritance. A superblock carries an s_op pointer, an inode carries i_op and i_fop, a file carries f_op, and a dentry carries d_op. When generic code needs filesystem-specific behavior it reads the relevant pointer and calls through it, after checking that the method exists. A filesystem that wants the default behavior simply leaves the pointer null, and the VFS substitutes a generic implementation. This is the mechanism that makes the common file model more than a diagram: the objects are shared, but their behavior is late-bound to whichever filesystem that instantiated them.

The other half of that mechanism is how a filesystem attaches its own state to a shared object. It does not allocate a struct inode and hang private data off a pointer; it declares a larger structure that contains the VFS object as a member, and allocates that. ext4 declares struct ext4_inode_info with a struct inode vfs_inode field, and its accessor is a single container_of(): 

/* fs/ext4/ext4.h */
static inline struct ext4_inode_info *EXT4_I(struct inode *inode)
{
        return container_of(inode, struct ext4_inode_info, vfs_inode);
}

This is why super_operations begins with alloc_inode and free_inode rather than letting the VFS call kmalloc() itself: only the filesystem knows the real size of the object and which slab cache it comes from. The VFS calls the method, receives a pointer to the embedded struct inode, and from then on manipulates only the generic fields; the filesystem recovers its own structure with container_of() whenever one of its methods is invoked. The superblock and the dentry use a variation on the theme, providing an untyped s_fs_info and d_fsdata pointer instead of embedding, because their private state is usually allocated at a different moment than the object itself. A struct file gets private_data for the same reason: the object is allocated by the VFS before any filesystem method has had a chance to run.

The consequence for a reader of the source is a habit worth acquiring early. When generic code in fs/ handles a struct inode, that inode is almost always the middle of a larger allocation, and the fields the generic code may touch are exactly the ones declared in include/linux/fs.h. Conversely, when filesystem code receives an inode it immediately converts it with its own FS_I()-style accessor. The boundary between the two is not enforced by the compiler; it is a convention, and it is what lets the common file model work without any language-level inheritance.

Abstraction is only half of the VFS's job; the other half is performance. Because every filesystem is reached through the same object shapes, Linux can attach general-purpose caches to those shapes once and let every filesystem benefit. Two caches matter most, and both live in the generic layer rather than in any single filesystem.

The dentry cache, or dcache, remembers the results of pathname resolution. Walking a path such as /usr/lib/libc.so.6 means resolving each component in turn, and without a cache every component would force the filesystem to read a directory block and match names. The dcache keeps recently used dentries—and, through them, their inodes—in memory, so a repeated lookup of a hot path is satisfied entirely from RAM, often without taking any filesystem lock at all. The dcache even records negative results, remembering that a name does not exist so that repeated failed lookups stay cheap. Section 3 examines this cache and its lockless RCU design in detail.

The second cache is the page cache, the modern successor to the old buffer cache, also known as the "disk cache." Each inode owns an address_space (reached through i_mapping) that holds the file's data pages, nowadays managed as folios. A read() first consults the page cache and copies from memory on a hit; only a miss triggers the filesystem's read_iter path and actual block I/O. A write() usually just dirties a cached page and returns, letting writeback flush it to the backing store later. Because the page cache sits above the filesystem and below the read/write syscalls, one implementation accelerates ext4, XFS, and network filesystems alike, and the same pages serve both ordinary I/O and memory mappings.

These two caches are why the VFS is not merely a compatibility shim. By caching names in the dcache and data in the page cache, the generic layer turns most file operations into memory operations and calls down into a concrete filesystem only when the cache cannot answer. The rest of this chapter repeatedly returns to that pattern: the fast paths stay in the VFS and its caches, and the filesystem methods run only on a cache miss or a modification that must reach stable storage.

System Calls Handled by the VFS

The VFS does not own every system call with a pathname or file descriptor, but it owns the common parts of most of them. Opening, closing, reading, writing, creating, linking, unlinking, renaming, changing attributes, mounting, and locking all pass through generic routines before reaching filesystem-specific operations. The system-call wrappers mostly translate userspace ABI structures into internal flags and names.

This distinction matters for security and observability. Linux security modules, audit, fsnotify, fanotify, idmapped mounts, and mount namespaces hook generic VFS points so that ext4 and procfs cannot accidentally implement incompatible access-control rules. The filesystem still decides many details, but the VFS establishes when credentials are checked, when write access to a mount is acquired, and when a dentry or file must be pinned.

Linux 7.0.12 has also moved several modern interfaces into this shared layer. openat2() centralizes path-resolution constraints; fsopen(), fsconfig(), fsmount(), and move_mount() expose mount construction as file-descriptor state; and copy_file_range(), splice(), and sendfile() are generic data-movement calls that can be accelerated by filesystem methods when available.

It helps to notice that VFS system calls fall into two families by how they name their target. Path-based calls such as openat2() or renameat2() begin with pathname resolution: the VFS walks the name into a struct path, applying the lookup flags and mount rules described later in this chapter, before it can act. Descriptor-based calls such as read() or fcntl() skip resolution because the caller already holds an open file; they begin by translating the integer descriptor into a struct file through the file-descriptor table. The *at() variants unify the two by taking a directory descriptor plus a relative name, with the special value AT_FDCWD meaning "resolve relative to the current working directory." This is why almost every classic call now has an *at() form: it lets threaded programs resolve names relative to a stable directory handle instead of a shared, racy process-wide current directory.

There is a third naming family that is easy to overlook because it has no pathname at all. name_to_handle_at() asks a filesystem to produce an opaque, persistent file handle for an object, and open_by_handle_at() turns that handle back into a descriptor later, possibly after a reboot and possibly without the caller ever having had the ability to resolve the name. The VFS cannot implement this generically—only the filesystem knows what durable identity means for its objects—so it dispatches to the export_operations table, the same table the NFS server uses to identify objects for its clients. Because a handle bypasses pathname resolution, and with it every directory permission check along the way, opening one is privileged. The classic rule was a flat CAP_DAC_READ_SEARCH in the initial user namespace, which made the call unusable inside a container. Linux 7.0.12 adds a second, narrower path: a caller that holds CAP_DAC_READ_SEARCH in its own user namespace and CAP_SYS_ADMIN over the mount it passes as mountdirfd—that is, a caller that could have mounted or bind-mounted that subtree anyway—may decode handles beneath it, provided it opens with O_DIRECTORY and the mount has no locked children hiding part of the subtree. In that mode vfs_dentry_acceptable() walks from the decoded dentry up to the root of the supplied mount, rejecting the handle if any inode along the way is unmapped in the caller's user namespace. The relaxation is deliberately conservative: it grants the ability to reach objects the caller could already have reached by name, not the ability to bypass DAC.

Two newer calls in 7.0.12 close long-standing gaps in this ABI rather than adding new capability. fchmodat2() exists because the original fchmodat() was standardized without a working flags argument, so there was no way to change the mode of a symbolic link or to request AT_EMPTY_PATH; the new call simply takes the flags the old one should have had. statmount() and listmount() replace parsing /proc/self/mountinfo, which was a text format with no way to ask for one mount, no way to extend a field without breaking parsers, and no way to enumerate a mount namespace other than one's own. The new pair takes a struct mnt_id_req naming a mount by its 64-bit ID and a request mask of STATMOUNT_* bits—STATMOUNT_MNT_BASIC, STATMOUNT_FS_TYPE, STATMOUNT_MNT_UIDMAP, and so on—and fills a versioned struct statmount, following the same extensible-structure discipline as statx(). Section 6 uses them when it discusses the mount tree.

Underneath the ABI differences, a typical path-based call follows a recognizable pipeline. The syscall wrapper copies and validates userspace arguments; pathname resolution produces a path; the VFS performs generic permission and mount-writability checks and fires the relevant security and notification hooks; and only then does it call the one filesystem method that does the medium-specific work, such as i_op->create or f_op->write_iter. Descriptor-based calls run a shorter version of the same pipeline: fetch the file, check its mode, dispatch the method. Keeping this pipeline in mind makes the later sections easier to read, because each one is really a detailed account of one stage—resolution in Section 7, the objects and their methods in Section 2, and the concrete open, read, write, and lock implementations in Sections 8 and 9. VFS Objects and Their Operations

The four central VFS objects divide responsibility by lifetime and by semantic level. The superblock describes a mounted filesystem instance; the inode describes one filesystem object; the dentry describes one name in a directory and caches lookup results; and the file describes one open file description. Operation tables hang off these objects, so a generic VFS routine can call inode->i_op->lookup() or file->f_op->read_iter() without knowing whether the underlying object lives on XFS or tmpfs.

The old Linux 2.6 chapter already presented these objects, but many fields and callbacks have changed. Modern superblocks know their user namespace and shrinker state. Inodes store timestamps in split second/nanosecond fields and use idmap-aware inode operations. Files use file_ref_t references and iterator-based I/O. Dentries are RCU-visible objects with sequence counters and lockref reference management. Figure 12-3 shows how the four objects refer to one another, and how a process reaches them.

The Superblock Object

A superblock is the VFS representation of a filesystem instance. For a disk filesystem it corresponds to a mounted device and contains information derived from the on-disk superblock. For nodev filesystems it is still the object that binds a root dentry, a filesystem type, flags, operation methods, inode lists, dentry shrinker lists, and private implementation state.

One piece of bookkeeping surprises readers who go looking for the definition: in Linux 7.0.12 struct super_block and struct super_operations are no longer declared in include/linux/fs.h. They live in include/linux/fs/super_types.h, which include/linux/fs.h pulls in, alongside include/linux/fs/super.h for the superblock helper API. The split is part of a long-running effort to break the monolithic fs.h into type and API headers, and it matters here only because every grep for struct super_block { in the old location now comes up empty.

Linux 7.0.12 superblocks carry fields that did not exist in Linux 2.6.s_user_ns records the user namespace relevant to the filesystem.s_dentry_lru and s_inode_lru place unused objects on per-superblock shrinker lists. Error sequencing with s_wb_err, UUID storage, freeze hooks, and per-filesystem idmapping support all reflect a kernel that must handle containers, writeback errors, and hot-unplugged storage more carefully than 2.6 did.

The super_operations table is where a filesystem supplies superblock-wide behavior. The VFS asks it how to allocate and destroy inodes, how to write dirty metadata, how to evict an inode, how to sync or freeze a filesystem, and how to report statistics. Mount reconfiguration no longer follows the old remount_fs path directly from userspace parsing; the modern mount API carries parameters through fs_context and filesystem context operations.

It is worth being precise about the superblock's lifetime, because it explains why so many of its fields exist. A superblock is created when a filesystem is first mounted—by vfs_get_tree() driving one of the get_tree_*() helpers—and it is destroyed only when the last mount referring to it goes away and its s_count and active reference counts drop to zero. Those two counts are not the same thing, and the difference is worth learning once. s_active counts the mounts that keep the filesystem alive; when it reaches zero the VFS calls put_super and tears the filesystem down, even though the struct super_block may still be pinned. s_count counts transient references taken by code that merely wants to look at the superblock—iterate_supers() walking the global list, for instance—and it is what keeps the memory itself from being freed under such a walker. A third member, the s_umount read/write semaphore, serializes the state changes: it is held for writing across mount, unmount, remount, and freeze, and for reading by anyone who needs a stable view of s_flags and s_root. Between those two events the superblock is the anchor that owns every inode and dentry of the filesystem: the s_inodes list threads all inodes, the two list_lru reclaim lists hold the unused ones, and s_fs_info points at the filesystem's own private control block. When you see a field on the superblock rather than on an inode, it is almost always because the value is shared by the whole mounted instance—the block size, the time-stamp granularity, the maximum file size, the UUID, the writeback-error counter—rather than by one file.

The Inode Object

An inode is the VFS object that represents a filesystem object independently of any particular name. Regular files, directories, symlinks, device nodes, sockets, and FIFOs all have inodes. A hard-linked file has one inode and multiple dentries; a deleted but still-open file has an inode and file objects even when no positive dentry is reachable from a directory.

The inode is the natural home for everything that is true of a file regardless of the name used to reach it. Its type and permission bits live in i_mode; its owner and group live in i_uid and i_gid as kuid_t/kgid_t values that are already resolved into the initial user namespace; its length is i_size; and its link count is i_nlink. Two reference-like counts matter and are easy to confuse: i_nlink counts the names that point at the inode on disk, and reaching zero (with no open file) is what allows the file to be deleted, whereas i_count counts the in-core users of the struct inode and controls when the in-memory object may be freed. A file unlinked while open has i_nlink == 0 but a positive i_count, which is exactly why its blocks are freed only when the last descriptor closes.

The field order in Linux 7.0.12 is deliberate: the members that RCU path lookup reads without any lock—type and permission bits, owner ids, the operation-table pointers, and the superblock and mapping pointers—are grouped near the front so they share the first cache lines, keeping the lockless fast path cheap. Timestamps illustrate a second modern change. They are no longer direct struct timespec64 i_atime members; each is split into a seconds and a nanoseconds field (i_atime_sec/i_atime_nsec, and the mtime and ctime equivalents) and must be read or written through helpers such as inode_get_mtime() and inode_set_ctime(). That split shrinks the structure and lets the kernel evolve the internal representation without touching every filesystem. Concurrency is likewise explicit: i_rwsem serializes directory modifications and larger operations, i_lock protects the small counters, and i_size_seqcount lets readers sample i_size without taking a lock.

The timestamp split is one instance of a broader pattern in 7.0.12: fields that filesystems used to poke directly have been wrapped in types that make direct access awkward on purpose. Two others matter. The link count is declared as a union of a const unsigned int i_nlink and a writable __i_nlink, so a filesystem may read inode->i_nlink but cannot assign to it; changes must go through set_nlink(), inc_nlink(), drop_nlink(), or clear_nlink(), which keep the superblock's s_remove_count of still-referenced zero-link inodes correct. The state word went the same way: i_state is no longer an unsigned long but a one-member struct inode_state_flags wrapping an enum inode_state_flags_enum, and it is read and written through inode_state_read(), inode_state_read_once(), inode_state_set(), and friends. The bits themselves are familiar — I_NEW, I_SYNC, I_DIRTY_SYNC, I_DIRTY_DATASYNC, I_DIRTY_PAGES, I_FREEING, I_CLEAR, I_WILL_FREE, I_REFERENCED, I_DONTCACHE — but wrapping them in a struct means a stray inode->i_state |= I_DIRTY no longer compiles, which is exactly the point: several of these transitions are only legal under i_lock or with the inode-hash lock held.

Two embedded members are worth calling out because they anchor major subsystems. i_mapping points at the inode's address_space (usually the embedded i_data), which is the page cache for this file's contents; this is the field the read, write, and mmap paths follow. And i_fop holds the default file_operations that open() copies into each new struct file, which is how the inode decides what an open descriptor can do before any file object exists. Type-specific unions such as i_cdev for a character device or i_pipe for a FIFO share storage with these, because an inode is only ever one type at a time; the same union also holds i_link for a fast symlink whose target is stored inline, and i_dir_seq for a directory participating in lockless lookup.

The structure is dense with such overlays, and reading them is a good way to see what the kernel considers mutually exclusive. i_dentry, the list of dentries aliasing this inode, shares storage with the i_rcu head used to free the inode after a grace period—an inode being freed has no aliases left. More surprisingly, i_fop itself is unioned with a void (*free_inode)(struct inode *) pointer, because once the inode has entered its RCU teardown nothing will ever dispatch through i_fop again, so the slot can be reused to remember how to free it. And i_devices, the per-device inode list used by block and character nodes, is unioned with i_linklen, the cached length of a fast symlink, since no inode is both a device node and a symlink. The File Object

A struct file is not a disk file. It is the kernel object for an open file description, shared by duplicated descriptors and inherited across fork() when the descriptor table points to the same file. It records the open mode, file flags, current position, credentials, path, mapping, private driver or filesystem state, and operation table used by I/O syscalls.

Linux 7.0.12 uses file_ref_t f_ref for the file reference count. Older explanations that call this an atomic_long_t are now wrong. The helpers get_file(), file_count(), fput(), and the fdget family hide the representation, which lets the kernel optimize file lifetime without exposing refcount internals to drivers.

The distinction between the file object and the inode is the reason per-open state has somewhere to live. The inode is shared by every name and every open of a file; the file object belongs to one open description. That is why the current position f_pos, the status flags f_flags, the opener's credentials f_cred, and the pinned f_path live on the file rather than the inode—two descriptors on the same inode can sit at different offsets, in different modes, opened by different users. The file also carries f_pos_lock, which serializes concurrent updates to the shared position when the same file is read or written from several threads (see FMODE_ATOMIC_POS below).

The primary data path is iterator-based. Although file_operations still contains legacy read and write members, the VFS strongly prefers read_iter and write_iter. These methods receive a kiocb and an iov_iter, so the same filesystem code can handle a single user buffer, a vector, a pipe, a kernel vector, a block-vector, or an xarray-backed transfer.

That listing is not abridged the way the earlier ones are: it is very nearly the whole structure, and its shape is deliberate. A busy machine holds hundreds of thousands of open file descriptions, and every read, write, and poll touches one, so the layout is hand-tuned into exactly three cache lines—192 bytes—with explicit boundary comments in the source. The first line holds everything the hot dispatch path needs (f_op, f_mode, f_mapping, f_inode, private_data); the second holds the path, position, and the position lock; the third holds the writeback-error snapshots, the epoll linkage, the readahead state, and the reference count. The structure is also marked __randomize_layout, so a hardened build reorders the members at compile time and an out-of-tree module cannot rely on offsets.

Three unions in that listing repay a second look, because each records a fact about which uses of a file are mutually exclusive. The f_path/__f_path pair is the same storage viewed twice, once writable for the small amount of code that must install the path and once const for everyone else. The f_pos_lock/f_pipe union works because a pipe has no seekable position to serialize, so it may reuse those bytes for its own state. The four-way union is the most striking: readahead state (f_ra) shares storage with the llist node used to queue a file for deferred fput(), with the task-work head used when the final close must run in task context, and with the slab allocator's free pointer. A file that is being closed has no further use for readahead state, and a file sitting on the slab free list has no use for anything at all—so three code paths that can never overlap in time are allowed to overlap in space.

The Dentry Object

A dentry represents a name in a directory and caches the result of looking up that name. Positive dentries point to inodes. Negative dentries have no inode and remember that a name did not exist at lookup time. This is why repeated failed opens of the same non-existent path do not necessarily call the filesystem every time.

The distinction between a dentry and an inode is the same one that separates a name from the thing it names. A single inode can have many dentries—one per hard link—so the dentry, not the inode, is what the pathname walk manipulates step by step. Each dentry knows its parent (d_parent) and its component name (d_name), and directories form a tree through the parent pointers and the d_children list. Short names are stored inline to avoid a separate allocation, which is a small but frequently exercised optimization given how many dentries a busy system holds. That inline buffer used to be a plain unsigned char d_iname[DNAME_INLINE_LEN]; in 7.0.12 it is a union shortname_store, which overlays the byte array with an unsigned long words[] view of the same storage. The name d_iname survives as a macro for d_shortname.string, so old code still compiles, but the reason for the change is the second view: comparing two short names a machine word at a time is much faster than byte by byte, and the union is what lets dentry_string_cmp() do that without type punning. The inline capacity is chosen so that struct dentry always lands on a clean 64-byte multiple: on the 64-bit architectures this book targets, DNAME_INLINE_WORDS is 5, giving a 40-byte inline buffer and a 192-byte dentry. Names of 40 characters or fewer—which is the overwhelming majority—therefore need no allocation at all.

The modern dentry is built for RCU path walking. Fields touched by lockless lookup—flags, the sequence counter, hash linkage, the parent pointer, the name, and the inode pointer—are grouped at the beginning so a lookup can validate them from cache without a lock. Reference counting and locking are fused into d_lockref, a per-dentry combination of a spinlock and a count in one word, so the common get/put uses a single atomic operation and only falls back to the spinlock under contention. The object also carries LRU linkage for reclaim, sibling and children lists for the directory tree, and a union that holds either an inode alias link, a hash node for a dentry still in the middle of a lookup, or an RCU callback head, because a dentry is in exactly one of those situations at a time. The LRU link is unioned in the same spirit with a wait_queue_head_t *: a dentry that is being looked up is not on any reclaim list, so it may use those bytes to point at the queue where other lookups of the same name wait. Two more names in the structure are macros rather than fields—d_lock expands to d_lockref.lock, and d_name is the const half of a union whose writable half, __d_name, is reserved for fs/dcache.c itself.

The dentry operations table. The dentry_operations table is where a filesystem customizes how a name behaves—how it is validated, hashed, compared, and torn down. A filesystem therefore sets its dentry operations once, at mount time, through set_default_d_op().

There is a fifth table worth naming even though this chapter does not catalog it. address_space_operations, reached through inode->i_mapping->a_ops, is what actually moves file data between the page cache and storage: read_folio, writepages, write_begin/write_end, direct_IO, and the folio migration and invalidation hooks. The division of labour is worth remembering—file_operations decides what an I/O request means for this kind of file, and address_space_operations decides how the bytes reach the device. Chapters 15 and 16 take up that table in detail.

Reading the four together gives a mental map of the whole subsystem. A pathname operation climbs through dentry_operations (is this cached name valid?) and inode_operations (create or look up the target); opening a file freezes a snapshot into a file and thereafter runs on file_operations; and super_operations hovers over all of it, managing the inodes those paths allocate and the writeback those files dirty. The rest of this chapter drills into each environment in turn.

The Dentry Cache

The dentry cache, usually called the dcache, is the performance center of pathname lookup. It remembers directory-to-name-to-dentry mappings, both positive and negative, and lets the common path through open() and stat() avoid calling a filesystem for every component. On large multicore machines, the cache also has to scale under concurrent lookup, rename, unlink, mount traversal, and reclaim.

It helps to see why the cache exists before looking at its machinery. Resolving /usr/lib/libc.so.6 means resolving four components in order. The very first time, each component forces the filesystem to read a directory block and match names, and the kernel builds a dentry for each result. Every subsequent resolution of any prefix of that path—and hot paths are resolved constantly—finds those dentries already in the cache and never touches the filesystem or a disk. The dcache turns repeated path resolution from a series of I/O operations into a series of hash-table probes, which is the single biggest reason filesystem-heavy workloads perform acceptably.

Linux 2.6 protected the dentry cache with a single global dcache_lock. Linux 7.0.12 replaced that design with per-dentry locks, bucket locks, RCU-protected traversal, sequence counters, and lockref reference management. The result is conceptually more complex but radically more scalable: the common lookup path can often read cached names without taking a blocking lock or incrementing a refcount. The three subsections that follow cover the three pieces a developer needs to understand: how names are found (organization and RCU), how a found dentry is safely pinned (lockref), and how the cache is kept from growing without bound (negative dentries and the shrinker).

Cache Organization and RCU

The dcache hash table maps a parent dentry and a child name to a candidate child dentry. The hash computation in fs/dcache.c combines the parent pointer and name hash, then selects a bucket in dentry_hashtable. A matching dentry must still be validated by comparing names, checking parent identity, and confirming sequence counters.

The bucket selection itself has been optimized in a way that says a great deal about how hot this code is. d_hash() needs two values that never change after boot: the base address of dentry_hashtable and the shift d_hash_shift that converts a 32-bit hash into a bucket index. Reading them as ordinary globals would cost two memory loads on what is arguably the most-executed lookup in the kernel. Linux 7.0.12 instead declares them as runtime constants: the values are written into the instruction stream by runtime_const_init() when the hash table is sized at boot, and d_hash() reads them with runtime_const_ptr() and runtime_const_shift_right_32(), which compile to an immediate operand rather than a load. The same trick is applied to the dentry_cache slab pointer. On architectures without the support the macros fall back to a plain variable read, so the code is written once.

__d_lookup_rcu() is the fast RCU-side lookup used by pathname walking. It scans the bucket under RCU, tests candidate dentries, samples the dentry sequence counter, and returns the dentry with sequence information instead of taking a reference. The caller later validates that no rename or dentry mutation invalidated the sample. If validation fails, the pathname walk retries or drops to ref-walk.

The legacy-looking d_lookup() and __d_lookup() still exist for code that needs refcounted dentries. They interact with rename sequence counters to detect concurrent directory moves. The significant point is that modern Linux offers both lockless lookup and traditional referenced lookup, choosing the cheapest safe form for each path.

A dentry enters the cache when a lookup that missed the cache builds it. The VFS allocates a dentry with d_alloc(), calls the parent inode's i_op->lookup to find (or fail to find) the on-disk object, and then attaches the result with d_add()—which sets d_inode and inserts the dentry into the hash bucket under the bucket lock. A successful lookup produces a positive dentry; a lookup that finds nothing produces a negative one. From that moment the entry lives in dentry_hashtable and answers future lookups directly.

The safety of a lockless lookup rests entirely on the sequence counters. __d_lookup_rcu() samples each candidate's d_seq before reading its parent and name, and returns that sample to the caller. Any code that mutates a dentry—renaming it, moving it, or making it negative—bumps d_seq while holding the dentry's d_lock, and directory renames additionally bump the global rename_lock seqlock. The pathname walk therefore proceeds optimistically: it reads cached pointers with no locks, then, before it commits to using them, re-reads the sequence counters. If a counter changed, some concurrent mutation raced the read, and the walk discards its work and retries—or drops out of RCU-walk into the slower ref-walk. This is the crux of how the dcache can be both lockless and correct: it never trusts a cached pointer it has not sequence-validated.

One more coordination problem is worth knowing about: two CPUs looking up the same missing name at the same time must not both call the filesystem and both create a dentry. The dcache solves this with the in-lookup mechanism. The first thread marks a placeholder dentry DCACHE_PAR_LOOKUP via d_alloc_parallel() and puts it on an in-lookup hash with a wait queue; a second thread that arrives finds the in-lookup dentry and waits on that queue instead of starting its own filesystem lookup. When the first thread finishes and calls d_add(), it clears the in-lookup state and wakes the waiters, who then use the now-populated dentry. This is why the cache state table lists an "in-lookup" state distinct from positive and negative. The in-lookup hash is a small fixed array — 1024 buckets, sized by IN_LOOKUP_SHIFT — and is entirely separate from the main dentry hash, because an in-lookup dentry is deliberately not yet findable by ordinary lookups. Note also that the in-lookup dentry reuses d_u.d_in_lookup_hash, the same storage that a hashed dentry uses for d_u.d_alias; the two states are mutually exclusive by construction. 

static inline struct hlist_bl_head *d_hash(unsigned long hashlen)
{
        return runtime_const_ptr(dentry_hashtable) +
                runtime_const_shift_right_32(hashlen, d_hash_shift);
}

struct dentry *__d_lookup_rcu(const struct dentry *parent,
                              const struct qstr *name,
                              unsigned *seqp)
{
        u64 hashlen = name->hash_len;
        const unsigned char *str = name->name;
        struct hlist_bl_head *b = d_hash(hashlen);
        struct hlist_bl_node *node;
        struct dentry *dentry;

        if (unlikely(parent->d_flags & DCACHE_OP_COMPARE))
                return __d_lookup_rcu_op_compare(parent, name, seqp);

        hlist_bl_for_each_entry_rcu(dentry, node, b, d_hash) {
                unsigned seq;

                seq = raw_seqcount_begin(&dentry->d_seq);
                if (dentry->d_parent != parent)
                        continue;
                if (dentry->d_name.hash_len != hashlen)
                        continue;
                if (unlikely(dentry_cmp(dentry, str,
                                        hashlen_len(hashlen)) != 0))
                        continue;
                if (unlikely(d_unhashed(dentry)))
                        continue;
                *seqp = seq;   /* caller re-validates this before trusting the result */
                return dentry;
        }
        return NULL;
}

Three details in that loop are easy to read past. The hash_len test compares the name's hash and its length in a single 64-bit comparison, because qstr packs both into one word for exactly this purpose. The byte comparison then goes through dentry_cmp(), which loads the name pointer with READ_ONCE() and hands off to dentry_string_cmp() — and that helper compares a machine word at a time using load_unaligned_zeropad(), which is why d_shortname is a union with a words[] view and why long names are allocated word-aligned. Finally, the d_unhashed() check cannot be skipped even though it looks redundant: a dentry can be unhashed in the window between being found on the list and having its sequence counter read.

The very first line of the function is a fork in the road. If the parent directory's d_flags has DCACHE_OP_COMPARE — meaning the filesystem supplies its own d_compare method, as case-insensitive and encrypting filesystems do — the lookup diverts to __d_lookup_rcu_op_compare(), a slower variant that must re-read the name and length under a stabilised sequence count before calling out to the filesystem. The fast path exists only for filesystems that compare names byte-for-byte, which is the overwhelming majority.

Names too long to fit inline get their own allocation, and it is not a plain kmalloc(). struct external_name carries an atomic_t count, an rcu_head, and a flexible array declared __aligned(sizeof(unsigned long)). The refcount exists because take_dentry_name_snapshot() lets a caller hold onto a name across operations that might rename the dentry, and the RCU head because a lockless lookup may still be reading the bytes when the name is replaced. The alignment is not cosmetic either: word-at-a-time comparison requires it. Table 12-16 summarizes the states a dentry can be in and what each one means for reclaim.

There is one more thing RCU-walk needs that is not obvious from the lookup loop: it frequently has to know what kind of object a name refers to. Is this component a directory it should descend into, a symlink it must resolve, or a name that does not exist? The obvious answer — look at d_inode->i_mode — is exactly what RCU-walk cannot do, because dereferencing the inode pointer of a dentry it holds no reference to is precisely the unsafe act RCU-walk is built to avoid.

The dcache therefore caches the type in the dentry itself. Bits 19 through 21 of d_flags are not independent flags at all; together they form a small integer field, masked off by DCACHE_ENTRY_TYPE, that records the type of the object the dentry names.

The helpers built on this field are the ones pathname resolution actually calls: d_is_dir(), d_is_reg(), d_is_symlink(), d_is_negative(), d_can_lookup(). Two of the seven values deserve a note. DCACHE_MISS_TYPE is zero, so a freshly allocated dentry with no inode is a negative dentry by default rather than by explicit marking. And DCACHE_AUTODIR_TYPE distinguishes a directory whose inode has no lookup method — the shape an automount trigger takes — from an ordinary directory, so d_is_dir() is the disjunction of d_can_lookup() and d_is_autodir(). The type is set and cleared together with the inode pointer, by __d_set_inode_and_type() and __d_clear_type_and_inode(), which is why attaching or detaching an inode always has to touch d_flags and not just d_inode. The former publishes the new flags with smp_store_release() so that a concurrent RCU walker that observes the type also observes the inode pointer that goes with it.

Reference Counting with lockref

lockref is a small but important scalability mechanism. A dentry needs both a spinlock and a reference count, and the common operations are “take a reference if the object is still usable” and “drop a reference, possibly freeing or moving the object.” Linux combines those fields so uncontended get and put paths can use a single compare-and-exchange fast path.

Under contention, lockref falls back to taking the embedded spinlock. The design avoids global serialization while still giving the kernel a precise place to protect dentry flags, reference counts, and state transitions. It is a direct answer to the 2.6-era scalability problem: one global dcache lock forced unrelated pathnames on different CPUs to wait for each other.

RCU lookup and lockref are complementary, not redundant. RCU-walk avoids taking any reference at all while it can prove the dentry remains stable. When the walk must become ref-walk, or when a caller explicitly needs a pinned dentry, lockref is the mechanism that turns a cached pointer into a counted object safely.

The count carries one special value. When a dentry is being killed, __dentry_kill() calls lockref_mark_dead(), which sets the count to a sentinel negative value so that any concurrent lockref_get_not_dead() fast path fails rather than resurrecting a dying object. This closes the classic race between a lockless lookup that just found a dentry and a dput() on another CPU that is tearing the same dentry down: the finder's cmpxchg sees the dead marker and falls back, and the killer proceeds knowing no new reference slipped in.

Putting a reference shows the fast/slow split concretely. dput() first tries fast_dput(), a single cmpxchg that decrements the count when nothing special is needed. Only if the count would reach zero, or the dentry needs eviction decisions, does it take d_lock and consult retain_dentry() — which may keep the dentry on the LRU for future reuse or hand it to __dentry_kill() for teardown. The everyday case, taking and dropping references on already-cached directories during a walk, therefore stays lock-free; the spinlock appears only at genuine lifecycle transitions.

The mechanics are worth following precisely, because fast_dput() distinguishes three outcomes rather than two. It calls lockref_put_return(), which returns the new count on success and a negative value to mean "the cmpxchg path was unavailable." A negative result sends the caller to the locked path to decrement by hand. A positive result means other references remain and there is nothing more to do. Only a result of exactly zero raises the question of what should happen to a dentry nobody is holding — and that question is retain_dentry()'s to answer.

retain_dentry() takes a bool locked argument, and the reason is instructive. It is first called without d_lock, in the hope of deciding cheaply; if the answer requires the lock, it returns false, which the caller reads as "punt to the locked path and ask again." The policy it applies, in order, is: an unhashed dentry is not worth keeping, because nobody could find it; nor is a DCACHE_DISCONNECTED one; if the filesystem set DCACHE_OP_DELETE its d_delete() method gets a vote, but calling it needs the lock; DCACHE_DONTCACHE is an explicit instruction not to retain. If the dentry survives all of that it is kept — but keeping it may mean adding it to the LRU, or setting DCACHE_REFERENCED on one that is already there, and both of those mutate d_flags and so require the lock too. That is the whole reason for the two-pass structure: the cheap pass handles the case where nothing needs changing, which is the common one. 

#define USE_CMPXCHG_LOCKREF \
        (IS_ENABLED(CONFIG_ARCH_USE_CMPXCHG_LOCKREF) && \
         IS_ENABLED(CONFIG_SMP) && SPINLOCK_SIZE <= 4)

struct lockref {
        union {
#if USE_CMPXCHG_LOCKREF
                aligned_u64 lock_count;
#endif

                        spinlock_t lock;
                        int count;      /* -128 == dead (being killed) */
                };
        };
};

The #if is load-bearing. The single-word member exists only when the architecture has a suitable 64-bit compare-and-exchange, the kernel is SMP, and the spinlock is small enough that a lock and an int together fit in eight bytes. Both of this book's target architectures qualify: x86 selects ARCH_USE_CMPXCHG_LOCKREF if X86_CX8, and arm64 selects it unconditionally. But the size test can fail on a kernel built with lock debugging, where spinlock_t grows — and when it does, the whole fast path compiles away to nothing and every operation simply takes the spinlock. The code is correct either way; only the performance differs. This is a good example of a Linux optimization that is invisible in the source until you notice what the configuration is doing to it.

The fast path itself is the CMPXCHG_LOOP macro in lib/lockref.c, and it is deliberately unambitious. It reads the combined word, and before attempting anything it checks arch_spin_value_unlocked() on the lock half: if any CPU currently holds the spinlock, the loop gives up immediately and falls through to the locked path. It also retries at most a hundred times. lockref never spins waiting for a lock — it either wins the race quickly or admits defeat and does the conventional thing. That bounded, non-blocking character is what makes it safe to use on paths that must not stall.

Negative Dentries and the Shrinker

A negative dentry is a cache entry for failure. If a process tries to open missing in a directory and the filesystem reports that the name does not exist, the VFS can keep a dentry with d_inode == NULL. A second process that looks up the same name can then fail from the dcache instead of calling the filesystem again.

Negative dentries are essential on real systems. Shell completion, library probing, container runtimes, language package managers, and dynamic linkers routinely test for files that are absent. Without negative caching, those misses would repeatedly descend into filesystems and sometimes into remote servers. With negative caching, the VFS can answer many misses locally until a create, rename, or invalidation changes the directory.

A negative dentry is not permanent. If a process later creates the missing name, the create path attaches an inode to the existing negative dentry with d_instantiate() (or d_add()), flipping it to positive in place and bumping d_seq so any racing lockless lookup re-validates. Conversely, an unlink() normally turns a positive dentry negative rather than destroying it outright, so that a program which deletes and immediately re-checks a name still benefits from the cache. This in-place positive/negative flipping is why the same dentry object can serve a name across its whole create-delete lifecycle.

"Normally" is doing some work in that sentence. d_delete() inspects d_lockref.count: only when the caller is the sole holder does it detach the inode and leave a negative dentry behind. If other references exist, it instead calls __d_drop() to unhash the dentry, which makes the name immediately unfindable while the object itself survives until the last reference goes. And the whole behaviour is tunable. The fs.dentry-negative sysctl, backed by dentry_negative_policy, defaults to zero; setting it to one makes d_delete() unhash unconditionally, so deletions never leave negative dentries behind. Workloads that create and delete enormous numbers of short-lived files sometimes prefer that trade: no negative caching benefit, but no accumulation either.

The cost is memory pressure. Linux tracks unused and negative dentries and places reclaimable objects on per-superblock LRU lists such as s_dentry_lru. The dcache shrinker uses list_lru_shrink_walk() in fs/dcache.c to prune unused entries. Flags such as DCACHE_LRU_LIST, DCACHE_SHRINK_LIST, and the entry-type bits describe where a dentry sits in this lifecycle. The shrinker itself is registered per superblock (s_shrink) and is NUMA- and memcg-aware, so reclaim can target the memory node and control group under pressure rather than scanning the whole cache.

The walk is a two-stage affair, and the split matters. prune_dcache_sb() asks list_lru_shrink_walk() to run dentry_lru_isolate() over the LRU; that callback only decides, moving victims onto a local dispose list. The actual destruction happens afterwards in shrink_dentry_list(), outside the LRU lock, because killing a dentry can sleep, can take the parent's lock, and can cascade into freeing an inode. Doing that work inside the LRU walk would be a lock-ordering disaster.

dentry_lru_isolate() implements a second-chance policy. It takes d_lock with spin_trylock() — the LRU lock is already held, so the normal order is inverted and a blocking acquire could deadlock; failing the trylock simply returns LRU_SKIP and the dentry survives this pass. If the dentry has a nonzero reference count it is not a candidate at all and is removed from the LRU outright (LRU_REMOVED), because a referenced dentry has no business occupying a reclaim list. If it is unreferenced but carries DCACHE_REFERENCED — the bit retain_dentry() set the last time somebody released it — the flag is cleared and the dentry is rotated to the tail of the LRU, buying it one more full sweep. Only a dentry that is unreferenced and has not been touched since the previous sweep is moved to the dispose list. This is the classic CLOCK-style approximation of LRU, implemented in one bit.

There is an important knock-on effect that developers debugging memory usage should know: pruning a dentry can release an inode. An in-core inode is normally pinned in the inode cache by the dentries that reference it, so when the shrinker drops the last dentry aliasing an inode, that inode's reference falls to zero and it too becomes eligible for reclaim (its evict_inode eventually runs). The dcache is therefore not just a name cache; it is the controller that keeps the inode cache populated. This is also why an enormous number of negative dentries—easy to generate accidentally with repeated failed lookups—can show up as sustained kernel slab growth until reclaim or a drop_caches pass trims them.

long prune_dcache_sb(struct super_block *sb, struct shrink_control *sc)
{
        LIST_HEAD(dispose);
        long freed;

        freed = list_lru_shrink_walk(&sb->s_dentry_lru, sc,
                                     dentry_lru_isolate, &dispose);
        shrink_dentry_list(&dispose);
        return freed;
}

static enum lru_status dentry_lru_isolate(struct list_head *item,
                                          struct list_lru_one *lru,
                                          void *arg)
{
        struct list_head *freeable = arg;
        struct dentry *dentry = container_of(item, struct dentry, d_lru);

        if (!spin_trylock(&dentry->d_lock))
                return LRU_SKIP;
        if (dentry->d_lockref.count) {
                d_lru_isolate(lru, dentry);
                spin_unlock(&dentry->d_lock);
                return LRU_REMOVED;
        }
        if (dentry->d_flags & DCACHE_REFERENCED) {
                dentry->d_flags &= ~DCACHE_REFERENCED;
                spin_unlock(&dentry->d_lock);
                return LRU_ROTATE;      /* one more pass through the LRU */
        }
        d_lru_shrink_move(lru, dentry, freeable);
        spin_unlock(&dentry->d_lock);
        return LRU_REMOVED;
}

Note that these are members of an enum dentry_flags, not a run of #defines as in earlier kernels, and that the values are no longer free-form: bits 19 through 21 are reserved for the entry-type field described earlier, which is why DCACHE_MISS_TYPE is written as a shift rather than a bit. DCACHE_DONTCACHE is the escape hatch a filesystem uses when it knows an object is not worth keeping; d_mark_dontcache() sets it on an inode and all its aliases, and retain_dentry() honours it on the next release.

All of this is observable. /proc/sys/fs/dentry-state exposes struct dentry_stat_t, whose first, second, and fifth fields are nr_dentry (every dentry allocated), nr_unused (those sitting on an LRU awaiting reclaim), and nr_negative (how many of the unused ones are negative). All three are maintained as per-CPU counters and summed on read, so the numbers are approximate by design — exact accounting would reintroduce the cache-line contention the whole subsystem exists to avoid. When a machine shows unexplained slab growth, the ratio of nr_negative to nr_dentry is usually the first thing worth looking at.

Files Associated with a Process

Everything discussed so far—superblocks, inodes, dentries, and file objects—is shared kernel-wide. This section covers the opposite end: the small, per-process bookkeeping that maps the integer file descriptors a program passes to read(), write(), and close() onto the shared struct file objects they name. When a user program calls read(3, buf, len), the kernel must translate the number 3 into a file pointer as fast as possible, on every single I/O call, so this layer is engineered for lookup speed and for scaling from a shell with three descriptors to a database with a million.

The per-process view of files begins in task_struct, but the VFS-facing data lives in struct files_struct. A file descriptor is just an index into an array hanging off this object; the array element is the struct file * the descriptor refers to. Threads created with CLONE_FILES (as pthread_create() does) share one files_struct, so a descriptor installed by one thread is immediately visible to its siblings and closing it in one closes it for all. A plain fork(), by contrast, gives the child its own copy of the table—same underlying struct file objects (shared offset and status flags), but an independent descriptor-to-file mapping. The object contains a reference count, a lock for descriptor-table changes, an RCU pointer to the active fdtable, the next-descriptor hint, and embedded storage for small descriptor sets.

Linux 7.0.12 separates the descriptor table from the files_struct through an RCU-published struct fdtable. This is the key to lock-free descriptor lookup, and it differs from early 2.6 kernels, where the descriptor array hung directly off files_struct and was protected by file_lock. Growing the table allocates a new fdtable, copies the pointers and bitmaps into it, publishes the new pointer with an RCU assignment, and frees the old table only after a grace period so that any reader still walking the old array finishes safely. A reader that only needs to fetch an existing descriptor can therefore run inside rcu_read_lock() without taking the files lock at all—it is this property that lets read() and write() on unshared descriptors avoid atomics entirely, as the next subsections show.

files_struct and the fdtable

files_struct combines fast small-process storage with scalable growth. The embedded fdtab, the three *_init bitmap words, and fd_array[NR_OPEN_DEFAULT] live inside the files_struct itself and serve the common case where a process has only a handful of descriptors—NR_OPEN_DEFAULT is BITS_PER_LONG (64 on 64-bit), so a typical process never allocates a separate table at all. When a process opens beyond that, expand_files() allocates a larger fdtable and switches files->fdt to point at it.

The growth policy in alloc_fdtable() is keyed to the size of the pointer array, because that array grows far faster than the bitmaps beside it. The new capacity is roundup_pow_of_two() of what was asked for, which makes the sequence of allocations page-tuned: on 64-bit the first separate table holds 128 slots, exactly a 1 KB array, and each subsequent step doubles. Two guards sit on top of that. The capacity is clamped to sysctl_nr_open — /proc/sys/fs/nr_open, default one million — rounded down to a multiple of BITS_PER_LONG so the bitmap arithmetic stays clean. And because distributions routinely raise nr_open to values near INT_MAX, there is an explicit check that the array would not exceed INT_MAX bytes; without it a process reaching for a descriptor near the limit would ask for an eight-gigabyte allocation. Both failures surface to userspace as EMFILE.

It is worth separating the two limits a reader will meet. RLIMIT_NOFILE is the per-process soft limit; it is passed down as the end argument of alloc_fd() and is what returns EMFILE for an ordinary program that opens too many files. sysctl_nr_open is a system-wide ceiling on how large any descriptor table may become, and it bounds the resource limit itself. The two are checked at different places for a reason: the first is policy, the second is a structural bound on the data structure.

The fdtable stores the maximum descriptor number (max_fds), the RCU-protected array of struct file * pointers, the close-on-exec bitmap, the open-fd bitmap, and a second-level full_fds_bits summary. The two-level bitmap is what keeps descriptor allocation fast even with huge tables: open_fds has one bit per descriptor, while each bit in full_fds_bits summarizes one whole BITS_PER_LONG-wide word of open_fds — set only when that entire word is fully allocated.

The order in which find_next_fd() consults the two levels is the opposite of what you might expect, and the source comment says so outright: try to avoid looking at the second level bitmap. It first scans the single open_fds word that contains the starting descriptor, and if that word has a free bit it is done, having touched one cache line. Only when that word is saturated does it fall back to full_fds_bits, using it to skip whole ranges of full words in one test, and then scans open_fds from wherever the summary landed. The summary bitmap is a fallback for the pathological case, not the normal route.

The next_fd field is a further hint: allocation starts there rather than at zero, because POSIX requires the lowest free descriptor and the last allocation is a good guess for where the next free one begins. The hint is maintained conservatively in both directions. alloc_fd() advances it to fd + 1 only when the caller did not ask to start above it — a range request such as fcntl(F_DUPFD) must not push the hint past descriptors that are still free below. And __put_unused_fd() pulls it back down whenever a lower descriptor is released, so the hint never claims that a free slot is taken. It may lag behind reality, but only in the safe direction: the scan starting from it can never skip a free descriptor.

The file-pointer array is RCU-readable, but installing, replacing, and closing descriptors still require careful synchronization so that no reader observes a half-installed file. Growth is the delicate case: because a resize publishes a brand-new array, files_struct carries a resize_in_progress flag and a resize_wait queue. A thread that calls fd_install() while another thread is mid-resize must not scribble its pointer into the old array that is about to be discarded.

The handshake that prevents it is unusual enough to be worth reading closely, because it uses RCU for mutual exclusion rather than for lookup. fd_install() runs its fast path inside rcu_read_lock_sched(), checks resize_in_progress, and if the flag is clear publishes the pointer with rcu_assign_pointer() and no lock at all. expand_fdtable(), on the other side, sets the flag and then calls synchronize_rcu() before switching tables. Waiting for a grace period here is not about freeing anything; it guarantees that every fd_install() already inside its read-side section has finished, and that every one starting afterwards will observe the flag. An installer that does see the flag diverts to fd_install_slowpath(), which simply takes file_lock and installs under it. A paired smp_wmb() in the expander and smp_rmb() in the installer order the flag against the table pointer. Notice that synchronize_rcu() is skipped entirely when atomic_read(&files->count) > 1 is false — an unshared table has no concurrent installer to wait for, so a single-threaded process never pays for this at all.

expand_files() itself is the one that waits on resize_wait: a second thread that also needs to grow the table drops file_lock, sleeps until the first resize completes, retakes the lock and re-evaluates, since the finished resize may already have given it the room it needed. This is why descriptor install is a two-phase operation rather than a single array store.

The VFS descriptor helpers therefore come in pairs. Allocation uses get_unused_fd_flags() to reserve a descriptor number (marking its bit in open_fds under file_lock) without yet publishing any file, then fd_install() stores the struct file * into that slot. Splitting reservation from publication lets the caller run fallible setup—building the file, checking permissions—while holding a stable number, and unwind cleanly with put_unused_fd() if that setup fails, before any other thread can see the descriptor. Close is the mirror image: close_fd() removes the pointer from the table and clears the bitmap bit under the lock, then drops the file reference outside the lock. This two-step structure prevents user-visible descriptor numbers from racing with file-object lifetime.

Three operations act on the table wholesale rather than one descriptor at a time, and each of them explains a field in the structure. fork() without CLONE_FILES calls dup_fd(), which does not blindly copy the source table: sane_fdtable_size() finds the highest descriptor actually open and sizes the copy to that, so a process that once opened ten thousand files and closed them all does not bequeath a ten-thousand-slot table to its children. execve() calls do_close_on_exec(), which walks the close_on_exec bitmap a word at a time, skipping empty words outright, and closes each marked descriptor — dropping file_lock around every filp_close() and calling cond_resched(), because a process with a large table could otherwise hold the lock for a very long time.

The third is close_range(), the syscall that exists because programs had been reading /proc/self/fd in a loop to close inherited descriptors before exec. It closes an inclusive range in one call, and its two flags make it more than a convenience. CLOSE_RANGE_CLOEXEC sets the close-on-exec bits for the range instead of closing anything, which is what a library wants when it must not disturb descriptors the rest of the process may still be using. CLOSE_RANGE_UNSHARE first gives the caller a private copy of the table, so that a thread can drop descriptors before exec without affecting siblings that share it. That combination enables a neat optimization: since the range is about to be closed anyway, dup_fd() is handed a struct fd_range describing it as a punch hole, and the copy skips those descriptors entirely — often allowing a much smaller table to be allocated than the original.

The comments splitting that structure in two are load-bearing. fget, fput, and struct fd

Once a descriptor exists, the kernel needs to convert it back into a struct file * on every I/O call, and this conversion is one of the hottest paths in the whole VFS. The plain fget() interface still exists: it looks the descriptor up under RCU, takes a counted reference on the file, and returns it; the caller later balances that with fput(). Taking a reference means an atomic operation on f_ref, which is unavoidable when the file could be closed concurrently by another thread sharing the table.

That reference count is not an ordinary one, and the reason it is not belongs here rather than with the struct file layout. filp_cachep is created with SLAB_TYPESAFE_BY_RCU, which means a freed struct file can be handed straight back out as a different file without waiting for a grace period. Only the memory is type-stable; the contents are not. A lockless lookup can therefore find a pointer that was valid a moment ago and now names an entirely different open file. file_ref_t is built for that world. It is biased so that FILE_REF_ONEREF is numerically zero, which turns "drop the last reference" into a single subtract-and-test rather than a compare-exchange loop, and it partitions the rest of the value space into a saturation zone (a count that overflowed is pinned rather than wrapping, leaking the object instead of freeing it early) and a dead zone beginning at FILE_REF_RELEASED, so that an acquire attempt on an already-released file fails instead of resurrecting it.

The consequence is visible in __fget_files_rcu(), which is a retry loop rather than a straight-line lookup. It loads the file pointer from the table, calls file_ref_get() — which can fail outright if the file is in the dead zone — and then re-reads the same slot and the table pointer to confirm that neither changed while it was acquiring. If either did, it drops the reference and starts over. Getting a reference first and validating afterwards is the only order that works when the object underneath can be recycled. The loop also applies array_index_mask_nospec() to the descriptor number and masks the loaded pointer with the result, so that a speculatively out-of-bounds descriptor cannot leak a value through a side channel; the mask approach means the bounds check costs no branch on the hot path.

Modern fast paths use fdget() instead, and its payoff is skipping that atomic. It returns a small tagged struct fd whose single word encodes both a struct file * and two low flag bits. Crucially, the shared helper __fget_light() tests atomic_read_acquire(&files->count) == 1: if the descriptor table is not shared (the common single-threaded case, or a child after fork()), no other thread can close the descriptor underneath us, so fdget() returns a borrowed reference — BORROWED_FD(), no refcount taken — and the matching fdput() does nothing. Only when the table is shared does it take a real reference (CLONED_FD()) with the FDPUT_FPUT bit set, so that fdput() knows it must call fput(). This is why so much VFS code is written with the fdget()/fdput() pair rather than fget()/fput(): it makes the overwhelmingly common unshared case allocation- and atomic-free.

The _acquire on that read is not decoration. Consider a thread that calls close_fd() and then put_files_struct(), dropping the sharing count from two to one. If the lookup were allowed to observe the new count of one together with the old table contents, it would conclude the table is private and return a borrowed reference to a file that is being freed. The acquire load pairs with the atomic_dec_and_test() in put_files_struct() to forbid exactly that reordering. This is a good illustration of how much of the fast path's correctness lives in memory ordering rather than in locks.

Note also that when the table is unshared the lookup does not enter an RCU read-side section at all; it reads the slot directly, because nothing else can change the table. The RCU machinery described earlier protects readers against concurrent modification, and the whole point of the count test is to establish that there is none.

The mask argument threaded through this family is how O_PATH descriptors are kept out of ordinary I/O. fdget() passes FMODE_PATH, so a descriptor opened with O_PATH — which refers to a location rather than an open file, and supports no reads or writes — is reported as empty. fdget_raw() passes a mask of zero and accepts it, which is what the handful of syscalls that legitimately operate on O_PATH descriptors, such as fstat() and the *at() family using them as directory anchors, actually call.

The low bits of struct fd.word carry the flags that drive this. FDPUT_FPUT means the caller must drop a reference with fdput(). FDPUT_POS_UNLOCK means fdget_pos() took file->f_pos_lock and fdput_pos() must release it — this lock serializes updates to the shared file offset so that two threads issuing read() on the same struct file cannot interleave and corrupt f_pos. Whether it is taken at all is decided by file_needs_f_pos_lock(), and the test is sharper than "is this a seekable file." The file must have FMODE_ATOMIC_POS; beyond that, the lock is skipped when the file holds exactly one reference (__file_ref_read_raw() equals FILE_REF_ONEREF), because a description nobody else can reach cannot be raced against. The one exception is a directory with an iterate_shared method, which is locked regardless, since getdents() must not have its position moved underneath it. So the ordinary case of a single-threaded program reading its own file takes neither an atomic nor a mutex. The fd_file() accessor masks off both flag bits to recover the pointer, and an empty result is represented by EMPTY_FD (word zero), tested with fd_empty()—that is how a bad descriptor number is reported without a separate error return.

Linux 7.0.12 also uses scope-based cleanup helpers built on DEFINE_CLASS(fd, ...), so new code can write CLASS(fd, f)(fd_num) and have fdput() run automatically at scope exit, including on early return or goto. The semantics are identical to the explicit pattern, but the compiler emits the cleanup, which eliminates a common class of descriptor leaks on error paths. There are three parallel classes — fd, fd_raw, and fd_pos — matching the three lookup variants, so a function that needs the position lock writes CLASS(fd_pos, f) and gets both the mutex release and the reference drop for free.

The allocation side has an equivalent, and it solves a subtler problem. CLASS(get_unused_fd, fd)(flags) reserves a descriptor and arranges for put_unused_fd() to run at scope exit, which is right for every error path — but wrong on success, where the descriptor must survive and be returned to userspace. The idiom for that is take_fd(), which returns the value and sets the variable to -EBADF so the automatic cleanup declines to fire. DEFINE_FREE(fput, ...) plays the same role for a struct file * held in a local. Together these turn the classic reserve-build-install sequence into straight-line code with no goto unwinding at all.

Readers of VFS code should recognize both styles: explicit fdput() remains common in existing code, while newer functions increasingly use the cleanup classes.

Filesystem Types and Registration

The objects in the previous sections describe a filesystem that is already active. This section steps back to ask how the kernel learns that a filesystem implementation exists in the first place, and how a name like ext4 or tmpfs becomes a live superblock. The answer is a two-stage design: a filesystem implementation registers a struct file_system_type once (at boot or module load), and each individual mount() later instantiates that type into a superblock through a per-mount fs_context. Keeping the type (one per implementation) separate from the context (one per mount attempt) is what lets the same ext4 code drive thousands of independently-mounted ext4 volumes.

Before a filesystem can be mounted, it must register a struct file_system_type. Registration places the type on the global filesystem list, records its name, flags, parameter specification, module owner, per-type superblock list, and the callback used to initialize an fs_context. Userspace sees the registered name in calls such as mount -t ext4 or fsopen("tmpfs", 0), and listed in /proc/filesystems.

The modern type object differs sharply from the 2.6-era get_sb model. Linux 7.0.12 expects a filesystem to provide init_fs_context, parse its parameters through the mount-API machinery, and eventually produce a root dentry through one of the get-tree helpers. The VFS still owns registration and lookup with register_filesystem(), unregister_filesystem(), and get_fs_type(); what changed is the per-mount construction path those functions hand off to.

It is worth fixing the shape of the whole section before the details arrive, because three separate lifetimes are in play and they are easy to conflate. The type lives from module load to module unload. A superblock lives from the first mount that creates it until the last mount that referenced it goes away — which is not the same as one per mount, since several mounts may share one superblock. And an fs_context lives only for the duration of a single mount or remount attempt, and is discarded whether it succeeded or failed. The subsections below follow that order: registering the type, constructing a superblock from it, and finally tearing one down.

file_system_type and init_fs_context

file_system_type is small but consequential. name is the ABI string userspace matches against. fs_flags describes broad mount rules, such as whether a block device is required (FS_REQUIRES_DEV) or whether an unprivileged user namespace may mount the filesystem (FS_USERNS_MOUNT). parameters points to the fs_parameter_spec schema that fsconfig() and text option parsing validate against — more on that schema shortly. fs_supers is the hash list linking every superblock created from this type, so the VFS can find an existing superblock to share rather than always creating a new one. kill_sb tears the superblock down when its last mount disappears.

Two things about the declaration are worth noticing. The FS_* flag constants are #defined inside the structure body, immediately after the fs_flags member they describe — unusual style, but it means a reader who jumps to the structure has the flag list in front of them. And most of the structure is not data at all: eight struct lock_class_key members occupy more space than everything else combined. They exist purely for lockdep. Because every ext4 superblock would otherwise share a lock class with every XFS superblock, lock-ordering rules that are perfectly valid within one filesystem would appear to conflict across filesystems. Giving each registered type its own keys for s_umount, i_rwsem, i_mutex_dir_key, the rename lock, and each freeze level lets lockdep reason about them independently. On a kernel built without lockdep these members compile to nothing.

init_fs_context is the entry point into modern mount construction, and understanding the fs_context lifecycle it begins is the key to the whole mount path. When a mount starts, the VFS allocates a struct fs_context, records why it exists in the purpose field (FS_CONTEXT_FOR_MOUNT for a fresh mount, FS_CONTEXT_FOR_SUBMOUNT for an automatic submount, FS_CONTEXT_FOR_RECONFIGURE for a remount), and calls init_fs_context. The filesystem allocates its private context data, installs a fs_context_operations table, and prepares to receive parameters. Options then arrive one at a time through parse_param as fsconfig() is called (or all at once through parse_monolithic when the classic mount() syscall supplies a single option string), and finally vfs_get_tree() invokes the context's get_tree operation to obtain or create the superblock and its root dentry. A remount runs the same object through the reconfigure operation instead.

It is worth being precise about how complete this transition now is, because accounts written during the changeover describe a different kernel. For several releases the VFS carried a compatibility shim: a filesystem could keep its old mount method on file_system_type, and a synthetic legacy context would collect the option string and hand it to that method unchanged. In 7.0.12 both halves of that arrangement are gone. file_system_type has no mount member at all, and there is no legacy context type in fs/fs_context.c. init_fs_context is now the only way a filesystem can be mounted, which is why it is the single method the structure demands. What survives from the old world is the mount() syscall, not the old internal interface: the syscall is translated into a context, and every in-tree filesystem has been converted to receive one.

The context is created by one of three constructors named for the purposes above — fs_context_for_mount(), fs_context_for_submount(), and fs_context_for_reconfigure() — and it accumulates, in one typed object, everything the mount needs: the proposed sb_flags together with a sb_flags_mask recording which of them the caller actually asked to change, the mounter's credentials and target user and network namespaces, the source string, LSM state, the proposed s_fs_info, and a p_log buffer that error messages are written into. That log is the reason the modern API can explain why a mount failed instead of returning a bare -EINVAL: helpers such as errorfc() and warnfc() record a message against the context, and userspace can read it back from the context file descriptor.

Alongside purpose, which never changes, the context carries a phase that does. Because the new mount API exposes the context to userspace as a file descriptor, a program can issue fsconfig() calls in any order it likes, including nonsensical ones — setting a parameter after the superblock has already been created, or asking to create it twice. The phase is what makes those attempts fail cleanly rather than corrupting the context. 

enum fs_context_phase {
        FS_CONTEXT_CREATE_PARAMS,       /* Loading params for sb creation */
        FS_CONTEXT_CREATING,            /* A superblock is being created */
        FS_CONTEXT_AWAITING_MOUNT,      /* Superblock created, awaiting fsmount() */
        FS_CONTEXT_AWAITING_RECONF,     /* Awaiting initialisation for reconfiguration */
        FS_CONTEXT_RECONF_PARAMS,       /* Loading params for reconfiguration */
        FS_CONTEXT_RECONFIGURING,       /* Reconfiguring the superblock */
        FS_CONTEXT_FAILED,              /* Failed to correctly transition a context */
};

A creation context starts in FS_CONTEXT_CREATE_PARAMS, where parameters are accepted; FSCONFIG_CMD_CREATE is refused with -EBUSY unless the context is in exactly that phase. It then moves to FS_CONTEXT_CREATING while get_tree runs and to FS_CONTEXT_AWAITING_MOUNT once a superblock exists, after which parameter-setting is no longer accepted. Any failed transition lands in FS_CONTEXT_FAILED, which is terminal — the context can only be closed. A uapi_mutex serializes the syscalls, so two threads sharing the context fd cannot drive it through conflicting transitions.

Three fields near the top of the structure — cred, user_ns, and net_ns — carry the answer to a question registration raises but does not settle: a filesystem type is visible to the whole system once registered, so who is allowed to instantiate one? All three are captured when the context is allocated, not when the superblock is finally created, and that timing is the whole point of separating the two.

The credentials are those of whoever called fsopen(), and they stay with the context for its whole life. A privileged process can therefore open a context, configure it, and hand the descriptor to a less privileged one to complete — the eventual FSCONFIG_CMD_CREATE is judged against the credentials captured at the start, not against whoever happens to be holding the descriptor. This is what the decomposition of mount() into separate steps buys, and it is not expressible in the old interface at all, where privilege was necessarily evaluated at the single moment the syscall ran.

The user namespace is chosen by purpose, and the two non-mount cases are the interesting ones. A submount and a reconfiguration both take s_user_ns from the superblock they are derived from rather than from the caller, so neither can move a filesystem into a different user namespace: whatever ownership domain the superblock was created in, it keeps. Reconfiguration additionally increments s_active and takes a reference on the root dentry, which is why holding a reconfiguration context keeps the superblock alive even if every mount of it goes away in the meantime.

The check itself is six lines, and it is the entire policy governing which filesystems an unprivileged container may mount. 

bool mount_capable(struct fs_context *fc)
{
        if (!(fc->fs_type->fs_flags & FS_USERNS_MOUNT))
                return capable(CAP_SYS_ADMIN);
        else
                return ns_capable(fc->user_ns, CAP_SYS_ADMIN);
}

The distinction turns on FS_USERNS_MOUNT. Without the flag, capable() demands CAP_SYS_ADMIN in the initial user namespace, which no amount of privilege inside a container can satisfy. With it, ns_capable() accepts the capability in fc->user_ns, so a user namespace root can mount the type. That is the flag's only effect, and it explains why the set of filesystems carrying it is short and conservative: it is a statement that the filesystem is prepared to parse input supplied by someone the kernel does not trust.

Note where the check happens. It runs when the superblock is created, inside the handler for FSCONFIG_CMD_CREATE, not when the context is opened; fsopen() itself is gated only by the weaker may_mount(), which asks for CAP_SYS_ADMIN in the mount namespace's user namespace. Obtaining a context is therefore cheap and widely permitted, while instantiating a superblock from it is not.

That split creates a hole, and it is worth seeing why, because it is the price of the flexibility described above. mount_capable() tests the privilege of whoever is calling now, while fc->user_ns was fixed when the context was opened, possibly by someone else. A globally privileged process handed a descriptor that was opened inside a container therefore passes mount_capable() on the strength of its own capability, while the context still names the container's user namespace. A second check inside sget_fc() closes this, and the source comment states the case precisely: it can happen when fsconfig() is called from init_user_ns with an fs_fd opened in another user namespace. Deferring privilege to creation time is what makes descriptor passing useful; checking the namespace again at the point of allocation is what keeps it safe.

One loose end from the discussion of pseudo filesystems is tied off here. sget_fc() selects the namespace the new superblock will be owned by with 

struct user_namespace *user_ns = fc->global ? &init_user_ns : fc->user_ns;

so the global flag that init_pseudo() sets is what keeps a kernel-internal filesystem owned by the initial user namespace no matter which namespace happened to trigger its creation. A pseudo filesystem is shared by the whole kernel, so allowing the first caller's namespace to claim ownership of it would be a mistake.

The exclusive flag deserves a note because it fixes a long-standing ambiguity. Ordinarily, creating a superblock for a filesystem that already has a matching one silently reuses the existing superblock, which means the options just supplied are quietly ignored — a mount appears to succeed with settings other than the ones requested. FSCONFIG_CMD_CREATE_EXCL sets exclusive, and sget_fc() then refuses to share, returning -EBUSY with the explanatory message reusing existing filesystem not allowed. There is no way to ask for this through the old mount(2) interface; it is one of the capabilities that exists only in the new API.

Registration itself is deliberately unglamorous: file_systems is a singly-linked list threaded through the next member, guarded by a reader-writer lock, and register_filesystem() walks it to reject a duplicate name with -EBUSY. A non-NULL next is itself the test for "already registered," which is why a filesystem must not attempt to register the same static structure twice. A linear list is entirely adequate here: it holds a few dozen entries and is walked only at mount time.

The one substantial thing registration does is validate the parameter schema. If the type supplies parameters, fs_validate_description() checks it for duplicate names and refuses registration with -EINVAL if it finds any. Catching a malformed option table at module load rather than at the first mount that happens to use the ambiguous option is the kind of check that only became possible once options were described declaratively. There is also a BUG_ON() rejecting a dot in the name, because the dot is reserved as the subtype separator described next.

get_fs_type() resolves a name to a referenced type. It first splits the name at a dot, looking up only the part before it, which is how fuse.sshfs finds the fuse implementation; after a successful lookup it verifies that the type actually set FS_HAS_SUBTYPE and fails if it did not, so a subtype cannot be smuggled past a filesystem that does not expect one. If no match is found it triggers module autoloading using the fs-<name> alias convention (request_module("fs-%.*s", len, name), using the pre-dot length), then retries the lookup. The reference it returns is a try_module_get() on the owning module, taken under the list lock, which is what lets mount code call into a filesystem implementation without its module being unloaded mid-mount.

The registered list is what userspace reads from /proc/filesystems. The format is two tab-separated columns: the first is the literal string nodev for types without FS_REQUIRES_DEV and empty otherwise, the second is the name.         fsparam_uid     ("uid",      Opt_uid),
        fsparam_enum    ("errors",   Opt_errors, my_error_actions),
        fsparam_fd      ("fd",       Opt_fd),
        {}
};

The type functions do the conversion and range checking, so parse_param receives an already-validated value and only has to record it. Several of the types have no equivalent in the old comma-separated string world at all: fsparam_fd takes a file descriptor, fsparam_blob takes binary data, and fsparam_path takes a pathname resolved relative to a dirfd. That is what the fs_value_type tag on struct fs_parameter is discriminating between, and it is the concrete reason the new API is more than a cosmetic rearrangement of the old one: an option value can now be a capability-bearing object rather than text that the filesystem must re-resolve itself, with all the ambiguity that re-resolution invites.

The schema says what a parameter may be; it does not say who gets to handle it. That is decided by vfs_parse_fs_param(), which every parameter passes through no matter which syscall delivered it, and which is worth reading because it is a chain of responsibility built out of a single return value. 

int vfs_parse_fs_param(struct fs_context *fc, struct fs_parameter *param)
{
        int ret;

        if (!param->key)
                return invalf(fc, "Unnamed parameter\n");

        ret = vfs_parse_sb_flag(fc, param->key);
        if (ret != -ENOPARAM)
                return ret;

        ret = security_fs_context_parse_param(fc, param);
        if (ret != -ENOPARAM)
                /* Param belongs to the LSM or is disallowed by the LSM; so
                 * don't pass to the FS.
                 */
                return ret;

        if (fc->ops->parse_param) {
                ret = fc->ops->parse_param(fc, param);
                if (ret != -ENOPARAM)
                        return ret;
        }

        /* If the filesystem doesn't take any arguments, give it the
         * default handling of source.
         */
        ret = vfs_parse_fs_param_source(fc, param);
        if (ret != -ENOPARAM)
                return ret;

        return invalf(fc, "%s: Unknown parameter '%s'",
                      fc->fs_type->name, param->key);
}

-ENOPARAM is the convention that makes this work. It means not mine, keep going; every other return value, including zero, ends the chain. It is defined in include/linux/errno.h as 519, in the block of codes that the header's comment says should never be seen by user programs — it is a purely internal signal, not an error a mount can fail with.

The order of the four handlers is the part with observable consequences. vfs_parse_sb_flag() runs first, and it recognises a small fixed set of names against two tables: dirsync, lazytime, mand, ro, and sync set a superblock flag, while async, nolazytime, nomand, and rw clear one. Because this runs before anything else, these names are reserved: a filesystem cannot give ro its own meaning, and never sees it. The LSM comes second, which is equally deliberate — options such as SELinux's context= are consumed before the filesystem is consulted, so a filesystem cannot accidentally claim them or leak them into its own private state.

Only then does the filesystem's own parse_param run, and only if it too answers -ENOPARAM does vfs_parse_fs_param_source() get a chance. That last fallback is the reason a filesystem which takes no options at all still handles source correctly without writing any code: the default implementation accepts a single string, rejects a second one with Multiple sources, and takes ownership of it. A filesystem that needs to do something unusual with source simply handles it in parse_param and the fallback never runs.

The flag handler does one more thing that only matters later. Alongside setting or clearing a bit in fc->sb_flags, it records the bit in fc->sb_flags_mask, which accumulates the flags the caller actually mentioned. Reconfiguration then applies 

WRITE_ONCE(sb->s_flags, ((sb->s_flags & ~fc->sb_flags_mask) |
                         (fc->sb_flags & fc->sb_flags_mask)));

so a remount changes exactly the flags that were named and leaves every other flag alone. Without the mask a remount would have to carry the complete flag state, and any flag the caller did not know about would be silently reset. This is also where MS_RMT_MASK is enforced: a reconfigure that names a flag outside the remountable set is rejected rather than partially applied.

The classic mount() syscall does not deliver parameters one at a time; it hands over a single page of text. That page is turned into individual parameters by parse_monolithic_mount_data(), which calls the filesystem's parse_monolithic method if it has one and generic_parse_monolithic() otherwise. The generic version splits on commas with strsep(), breaks each fragment at the first =, and feeds the pieces to the same vfs_parse_fs_param() chain described above. The two syscall families therefore converge immediately: after this point nothing downstream can tell whether an option arrived from mount() or from a sequence of fsconfig() calls.

The splitting itself is a callback rather than fixed code, because comma-splitting is not universal. generic_parse_monolithic() is a one-line wrapper that passes a comma splitter to vfs_parse_monolithic_sep(); overlayfs passes its own splitter instead, one that honours a backslash escape, because a lowerdir= value is a list of pathnames and a pathname may legally contain a comma. That is the kind of ambiguity the typed parameters of the new API exist to eliminate, and it is instructive that the one filesystem which most needed an escape mechanism in the old syntax is the one that had to supply its own parser.

The counterpart to all of this construction is kill_sb, and it is worth following because the ordering it imposes is not obvious. A superblock is not destroyed when a mount goes away; it is destroyed when s_active reaches zero, which deactivate_locked_super() detects with atomic_dec_and_test(). Only then does it free the shrinker, call the type's kill_sb, destroy the two LRU lists, and finally drop both the module reference taken by get_fs_type() and the last superblock reference. Note the order: the filesystem's teardown runs before put_filesystem(), so the module cannot be unloaded out from under its own destructor.

Almost every kill_sb implementation is a thin wrapper around generic_shutdown_super(), which does the VFS-generic work in a strict sequence: prune the dentry tree with shrink_dcache_for_umount(), flush with sync_filesystem(), clear SB_ACTIVE so no new references can be taken, evict every inode with a zero refcount, and only then call the filesystem's own put_super(). Each step depends on the previous one having completed — inodes cannot be evicted while dentries still pin them, and the filesystem's private teardown cannot run until the VFS has finished with its inodes. If inodes remain after all that, the condition is reported through CHECK_DATA_CORRUPTION() and the surviving inodes have their i_op, i_sb, and i_mapping pointers overwritten with VFS_PTR_POISON, so that a later use crashes immediately and legibly rather than corrupting freed memory.

The two common wrappers differ only in what kind of device backs the superblock. kill_anon_super() releases the anonymous block-device number that set_anon_super_fc() allocated for a filesystem with no real device; kill_block_super() instead syncs the block device and releases it. Filesystems needing more do their own work around a call to one of these — procfs and sysfs both wrap them to release namespace and kernfs state first.

One subtlety in that sequence has a comment of its own in the source. generic_shutdown_super() sets SB_DYING and broadcasts it before kill_sb runs, but deliberately leaves the superblock on fs_supers until afterwards. That means a concurrent sget_fc() can still find it, which is intentional — the flag is what tells every other walker of fs_supers to treat it as dead and skip it, while sget_fc() retains the ability to observe and wait on the dying superblock rather than racing to create a duplicate alongside it.

Unregistration is correspondingly simple. unregister_filesystem() unlinks the type from file_systems, sets next back to NULL so the structure can be registered again, and then calls synchronize_rcu() before returning — ensuring that any lookup already walking the list has finished before the module that owns the memory can be unloaded. It does not and cannot check whether mounts still exist; that is what the module reference held by every live superblock is for.

Special (Pseudo) Filesystems

Not every filesystem is backed by a disk. A large and important class of pseudo (or special) filesystems are ordinary VFS citizens with unusual backing stores: they present the same inode/dentry/file interface, but their contents are synthesized on demand rather than read from blocks. This is the mechanism behind much of the kernel's userspace API. Procfs synthesizes process and kernel state under /proc. Sysfs exposes device-model objects and their attributes under /sys. Tmpfs, implemented by shmem, stores file contents in the page cache and swap rather than on a block device, which is why it is used for /tmp, /run, and POSIX shared memory. Devtmpfs creates device nodes directly from the driver core so early userspace has a populated /dev. Each registers a file_system_type and supplies VFS operations exactly like a disk filesystem; the difference is entirely in where the data comes from.

The internal-mount pattern is common for pseudo filesystems. A kernel subsystem that needs VFS objects but no user-visible mount point calls kern_mount() to obtain a private mount pinned by the subsystem itself, living outside any process's mount namespace. This is how sockets, pipes, and anonymous inodes get real struct file and inode objects even though no path ever led to them: they are created on an internal mount of a tiny pseudo filesystem (for example sockfs or pipefs), so the rest of the VFS — reference counting, fput(), poll() dispatch — treats them uniformly with ordinary files.

Those tiny internal filesystems are so nearly identical that the VFS supplies a shared implementation of them. init_pseudo() attaches a struct pseudo_fs_context to the fs_context and installs a ready-made operations table; the filesystem passes only its magic number and, optionally, its super_operations and dentry_operations. Everything else — a root inode numbered 1, PAGE_SIZE blocks, a d_make_root() call — is done by pseudo_fs_fill_super(). Sockfs, pipefs, and anon_inodefs are each a few dozen lines on top of it.

Two flags init_pseudo() sets deserve attention. SB_NOUSER marks the superblock as one that must never appear in a namespace, so an attempt to mount it from userspace fails rather than exposing kernel plumbing at a path. And fc->global = true forces the superblock into the initial user namespace, which is correct precisely because these filesystems are never user-mountable and therefore have no namespace of their own to belong to. 

struct pseudo_fs_context {
        const struct super_operations *ops;
        const struct export_operations *eops;
        const struct xattr_handler * const *xattr;
        const struct dentry_operations *dops;
        unsigned long magic;
        unsigned int s_d_flags;
};

/* net/socket.c, in sockfs's init_fs_context: */
struct pseudo_fs_context *ctx = init_pseudo(fc, SOCKFS_MAGIC);

if (!ctx)
        return -ENOMEM;
ctx->ops = &sockfs_ops;
ctx->dops = &sockfs_dentry_operations;
ctx->xattr = sockfs_xattr_handlers;
return 0;

kern_mount() completes the picture. It mounts the type with SB_KERNMOUNT and then sets the mount's namespace pointer to MNT_NS_INTERNAL, which is not a namespace at all but the poisoned value ERR_PTR(-EINVAL), chosen so it can never compare equal to any real mnt_namespace. The mount is thereby invisible to every namespace-walking operation, and it is a longterm mount: it is pinned for as long as the subsystem is loaded, which is what keeps the superblock alive even though no process ever references it by path.

The implementation difference between these filesystems shows up mainly at get-tree time, in how many superblocks a type is allowed to have. A nodev filesystem that wants a fresh superblock per mount uses get_tree_nodev(). A singleton filesystem that must have exactly one superblock no matter how many times it is mounted uses get_tree_single() (this is how a second mount -t sysfs reuses the existing tree). Filesystems that key superblocks on some distinguishing value—so that mounts with the same key share a superblock while different keys get different ones—use get_tree_keyed(). Disk filesystems instead use get_tree_bdev(), which locates or opens the block device and shares a superblock when the same device is mounted twice. These helpers replaced the older get_sb_nodev-style interfaces and slot directly into the get_tree operation of fs_context_operations described above.

The first three of those are not three functions but one. All of them call vfs_get_super(), which calls sget_fc() with a test callback and then runs the filesystem's fill_super only if the superblock it got back has no root yet. The entire difference between them is that callback. get_tree_nodev() passes NULL, so sget_fc() skips the search loop and always allocates: every mount gets its own superblock. get_tree_single() passes a function whose body is return 1, so the first candidate examined always matches and there can only ever be one superblock. get_tree_keyed() passes a comparison of sb->s_fs_info against fc->s_fs_info, so mounts agreeing on the key share and others do not. Never, always, and sometimes — expressed as three one-line predicates over the same machinery.

That machinery is sget_fc(), and it is worth knowing what it does beyond the search, because it enforces rules the helpers above do not mention. It refuses outright to create a superblock from a non-initial user namespace for a type that did not set FS_USERNS_MOUNT, failing with -EPERM and the message VFS: Mounting from non-initial user namespace is not allowed; this is the second of the two namespace checks discussed earlier, and the one that catches a context opened in one namespace and driven from another. It declines to share an existing superblock across user namespaces even when the test callback says the two match, because the credentials that superblock was created under are baked into it. And it allocates a candidate superblock before taking sb_lock — allocation can sleep, the lock is a spinlock — then retries the search with the lock held and throws the candidate away with destroy_unused_super() if the race was lost. This allocate-then-retry shape recurs throughout the VFS wherever a lookup under a spinlock may need to insert.

get_tree_bdev() stands apart from the other three because its key is not a pointer but a device. It resolves fc->source to a dev_t with lookup_bdev() and keys the superblock on that, so mounting the same device twice reaches the same superblock regardless of which of its names was used. Two behaviours there are worth knowing. It sets SB_NOSEC unconditionally, and when it does find an existing superblock it explicitly refuses to change the read-only state, failing with -EBUSY and the message Can't mount, would change RO state — which is why mounting an already-mounted device with a different ro/rw setting fails rather than silently succeeding or, worse, flipping the mode for everyone already using it. Changing that state is what reconfigure is for. Table 12-20 lists the pseudo filesystems most likely to be encountered and what each exists to provide.

procfs, seq_file, and /proc/sys

Procfs is the oldest of the pseudo filesystems and still the largest, and it is really three filesystems sharing one mount. Under /proc/<pid> it synthesizes a directory per process from the task and its memory map. Beside those directories it keeps a registry of entries that kernel code creates explicitly — /proc/meminfo, /proc/interrupts, and hundreds more. Under /proc/sys it exposes the sysctl tunables. All three share one problem that a disk filesystem never has: the "file" is a view of live kernel state, often larger than one read() buffer, that has to be turned into text on demand and stay sensible when the reader reads it in pieces.

The kernel's answer is seq_file (fs/seq_file.c), an iterator interface that every pseudo filesystem in this section uses. Linux 2.6.11 already had it, but it then lived alongside the older create_proc_entry() interface, whose read_proc callback was handed a single page to fill and had to invent its own offset arithmetic for anything larger. Both create_proc_entry() and create_proc_read_entry() were deleted in 3.10. A text file in procfs, debugfs, or sysfs is now produced through seq_file or through a custom read method, with no third option. 

struct seq_file {                       /* include/linux/seq_file.h */
        char *buf;              /* output buffer, PAGE_SIZE and growing */
        size_t size;
        size_t from;            /* first unread byte in buf */
        size_t count;           /* bytes in buf */
        size_t pad_until;
        loff_t index;           /* record cursor, not a byte offset */
        loff_t read_pos;        /* byte offset the reader has reached */
        struct mutex lock;
        const struct seq_operations *op;
        int poll_event;
        const struct file *file;
        void *private;
};

struct seq_operations {
        void * (*start) (struct seq_file *m, loff_t *pos);
        void (*stop) (struct seq_file *m, void *v);
        void * (*next) (struct seq_file *m, void *v, loff_t *pos);
        int (*show) (struct seq_file *m, void *v);
};

The file's author supplies four callbacks over a sequence of records. start() takes whatever lock protects the data and returns a cursor for record *pos, or NULL at the end. show() formats one record into the buffer with seq_printf(), seq_puts(), and their relatives. next() advances the cursor and the index. stop() drops the lock. The author never sees a byte offset or a user pointer; seq_read_iter() owns both.

seq_read_iter() is worth reading in full, because its loop encodes the contract. On the first read it allocates a PAGE_SIZE buffer. It then calls start() and show() for the current record. If the record did not fit — seq_has_overflowed() — it calls stop(), frees the buffer, allocates one twice the size, and calls start() again at the same index, repeating until the record fits. One record is therefore always generated whole, never torn across two buffers. Once one record is in, the loop keeps calling next() and show() until the user's buffer would be full, rolls back the partial record that overflowed, calls stop(), and copies out. Bytes that did not fit stay in m->buf and are copied out by the next read() before any new record is generated. A show() that returns SEQ_SKIP discards its record. A next() that forgets to advance the index gets a rate-limited "buggy .next function" warning, and the loop advances the index itself rather than spinning.

The consequences are visible from userspace. Each read() call sees a consistent batch of records, generated between one start() and one stop() under whatever lock those take. A file read in several calls can still change between calls, so a listing such as /proc/self/mountinfo may show a mount appear or disappear at a read boundary. Because the cursor is a record index, a read at an offset other than where the last one stopped cannot seek directly: traverse() regenerates records from index 0 and discards their output until it reaches the requested byte offset. A read at offset 0 always restarts the iterator. seq_read_iter() arrived in 5.10 so that seq_file files could offer read_iter and therefore splice. The older seq_read() is now a three-line wrapper that builds an iov_iter and calls it.

Most files have only one record — a block of statistics, a single value — and for those the four-callback interface is overkill. single_open() wraps a lone show function in an operations table whose start() returns a token only for position 0. A family of macros then removes the remaining boilerplate. DEFINE_SHOW_ATTRIBUTE(foo) generates foo_open() and a file_operations named foo_fops around foo_show(); DEFINE_SEQ_ATTRIBUTE does the same around a full foo_sops table; and DEFINE_PROC_SHOW_ATTRIBUTE produces the procfs flavour. Procfs goes one step further: proc_create_single() and proc_create_seq() store the show function or the operations table in the procfs entry itself and need no open function at all. 

static int foo_show(struct seq_file *m, void *v)
{
        struct foo_stats *s = m->private;       /* the data pointer below */

        seq_printf(m, "requests: %llu\n", s->requests);
        seq_printf(m, "errors:   %llu\n", s->errors);
        return 0;
}

/* /proc/driver/foo: one record, no open or release function to write */
proc_create_single_data("driver/foo", 0444, NULL, foo_show, &foo_stats);

Behind those helpers is the procfs registry. Every explicitly created entry is a struct proc_dir_entry (fs/proc/internal.h), and a directory keeps its children in a red-black tree keyed by name. The general constructor is proc_create(name, mode, parent, proc_ops); proc_mkdir() creates a directory and remove_proc_entry() or remove_proc_subtree() takes entries away again. The method table is struct proc_ops, introduced in 5.6 to cut procfs loose from struct file_operations. Its methods are named proc_open, proc_read_iter, proc_write, proc_lseek, and so on, and it has no owner field, for a reason the next paragraph explains. Its proc_flags word carries PROC_ENTRY_PERMANENT, which built-in code sets for entries that are never removed so that they can skip the removal bookkeeping entirely. 

struct proc_dir_entry {                 /* fs/proc/internal.h, abridged */

The interesting field is in_use, because it solves a problem every pseudo filesystem has: a module can remove an entry, and unload its code, while a process still has the file open. Procfs installs its own file_operations on every regular entry, and each of those — proc_reg_read(), proc_reg_write(), and the rest — brackets the call into the entry's proc_ops with use_pde() and unuse_pde(), which increment and decrement in_use. Removal calls proc_entry_rundown(). It adds a large negative bias to in_use, so every later use_pde() fails, waits for the callers already inside to leave, and then calls the entry's release method on behalf of every file still listed in pde_openers. After that the module can go. A process that still holds the descriptor gets -EIO from its next read, never a jump into unloaded code. Because the entry itself guarantees this, proc_ops needs no owner field for module reference counting.

The per-process directories are not registry entries at all. proc_pid_lookup() resolves a numeric name to a task. The directory's contents come from static pid_entry tables such as tgid_base_stuff[] in fs/proc/base.c, built from REG, ONE, DIR, and LNK macros: ONE("status", S_IRUGO, proc_pid_status) is a seq_file single-show file, and LNK("exe", ...) a magic symlink. The task can exit while its dentries are cached, so they carry pid_revalidate() as their d_revalidate. Procfs also uses get_tree_nodev(), which gives each mount its own superblock. That is what lets hidepid= and subset=pid differ between mounts: a container can be handed a /proc that shows only process directories and hides the rest of the kernel.

/proc/sys is implemented separately, in fs/proc/proc_sysctl.c, on top of tables of struct ctl_table. A subsystem describes each tunable — a name, a data pointer, a length, a mode, and a handler — and registers the array under a path string. Two changes since Linux 2.6 shape what such a table looks like. Since 6.6, register_sysctl() takes the array length from ARRAY_SIZE(), so tables no longer end in an empty sentinel entry. Since 6.11 every handler takes a const struct ctl_table *, so tables can be const and live in read-only memory.

debugfs, tracefs, and kernfs

Procfs shows one way to build a pseudo filesystem: keep a private registry and create dentries and inodes from it on lookup. The kernel has two other designs, and the difference between the three is mostly about what the source of truth is.

Kernfs (fs/kernfs/), behind sysfs, both cgroup hierarchies, and resctrl, takes the registry approach further. Its struct kernfs_node tree is a complete filesystem model in its own right, independent of the dcache. Dentries and inodes are made on lookup and can be reclaimed like any other cached object. Each node carries an active count that every file operation takes with kernfs_get_active(), and removal drains it in kernfs_drain() — the same "count the callers in, then wait them out" idea as procfs's in_use. Each node also carries a namespace tag, which is how /sys/class/net shows a different set of interfaces in each network namespace. Chapter 13 describes sysfs from the device-model side.

Debugfs (fs/debugfs/) takes the opposite approach and has no shadow tree at all: the dentries are the filesystem. Each create call allocates a dentry and an inode and instantiates them with d_make_persistent(), a 6.19 helper that marks the dentry DCACHE_PERSISTENT and takes an extra reference, so the dentry never leaves the dcache until the file is removed. Removal is simple_recursive_removal() from fs/libfs.c, and everything in between is built from the same libfs simple_* helpers that ramfs uses. This is the cheapest possible design to write, and it suits the purpose stated at the top of fs/debugfs/inode.c: "debugfs is for people to use instead of /proc or /sys". Sysfs's one-value-per-file rule does not apply, and nothing in debugfs is ABI.

The API is a set of one-line constructors. debugfs_create_dir() returns the new directory's dentry. Typed files such as debugfs_create_u32(), debugfs_create_bool(), debugfs_create_x64(), and debugfs_create_regset32() return nothing at all; they disappear with their parent directory. debugfs_create_file() returns a dentry and, since 6.13, is a _Generic macro. Passed a full file_operations, it creates a file with all methods. Passed the new struct debugfs_short_fops (only read, write, and llseek), it creates a file with a much smaller proxy. DEFINE_DEBUGFS_ATTRIBUTE(fops, get, set, fmt) builds a get/set pair into a file of one formatted number. The error policy is deliberately inverted. The source tells callers to ignore the return value of the create functions. Every debugfs function accepts an error pointer as its parent and simply passes it back (or, for the helpers that return nothing, does nothing), so a failure early in the tree flows harmlessly through every later call. A driver whose debug files failed to appear should still work, so it should not carry error paths for them.

Debugfs faces the same removal race as procfs and solves it the same way, through a proxy. debugfs_create_file() does not install the caller's file_operations on the inode. It installs debugfs_full_proxy_file_operations (or the short proxy), whose methods call debugfs_file_get() to take an active-user reference on the dentry, call the real method, and drop the reference with debugfs_file_put(). debugfs_remove() waits for the active users to drain before returning, so the module that owned the methods can then be unloaded safely. Debugfs is mounted at /sys/kernel/debug. Its init code creates that directory as an empty sysfs mount point, and while files exist the filesystem is pinned internally with simple_pin_fs(), so drivers can create files before userspace has mounted anything. Because debugfs exposes raw kernel internals, access is policy-controlled: the debugfs=on|off boot parameter and the CONFIG_DEBUG_FS_ALLOW_* choices decide whether it registers at all, and kernel lockdown restricts it further.

Tracefs (fs/tracefs/) was split out of debugfs in 4.1, so that a system could use ftrace without also exposing every driver's debug files. It is mounted at /sys/kernel/tracing. For older tools it is still auto-mounted at /sys/kernel/debug/tracing, under CONFIG_TRACEFS_AUTOMOUNT_DEPRECATED, which still defaults to y but was marked deprecated in 6.17. Tracefs inherits debugfs's dentries-as-truth design, with two additions. Its instances directory accepts mkdir and rmdir, each of which creates or destroys a complete, independent trace buffer. And its events subtree, which holds one directory per tracepoint with enable, filter, format, id, and trigger files in each, is too large to keep as persistent dentries: on a typical kernel that is thousands of directories and tens of thousands of files. Since 6.6 that subtree is eventfs (fs/tracefs/event_inode.c). It keeps lightweight eventfs_inode metadata and creates dentries and inodes "just-in-time" when a path is looked up, freeing them when they are no longer referenced. For its largest subtree, tracefs has therefore moved from debugfs's design to kernfs's. Table 12-23 sets the three designs side by side, with procfs's two halves for comparison.

Mounting Filesystems

A superblock and its root dentry describe a filesystem in isolation; mounting is what grafts that root onto a position in the directory tree a process actually sees. The result is that the visible tree is not a single dentry hierarchy but a graph of mounts layered over dentry trees—each mount splicing one filesystem's root over a directory (the mountpoint) in another. This is why the same directory can show completely different contents to two processes, and why df and /proc/self/mountinfo report a structure the plain directory listing never reveals.

Because mounts form their own layer, crossing a mount point during pathname lookup changes the active vfsmount—and usually the active superblock—even though the textual pathname simply advances to the next component. A single dentry can be a mountpoint for one mount and the root of another; the lookup code detects these transitions and steps from the covering mount's root onto the covered directory (or vice versa on the way out). The following section on pathname lookup depends on this: a path walk is simultaneously a walk over dentries and over the mount graph.

Linux 7.0.12 has two user-visible mount APIs. The classic mount(2) syscall remains for compatibility, but the new fd-based API lets userspace construct a filesystem context, configure it in discrete steps, create a detached mount that exists as a file descriptor before it is attached anywhere, and then splice it into a namespace atomically. Despite the very different front ends, both routes converge on vfs_get_tree() and the same superblock and mount infrastructure, as Figure 12-4 shows.

struct mount and struct vfsmount

The mount object is deliberately split in two. struct vfsmount is the small public part—the mounted root dentry (mnt_root), the superblock (mnt_sb), the mount flags (mnt_flags), and the idmap pointer (mnt_idmap). It is exactly the information a struct path needs to say "a lookup currently stands at this dentry, reached through this mount." The much larger struct mount embeds that vfsmount as its mnt member and surrounds it with all the namespace bookkeeping: parent pointer, mountpoint dentry, child list, propagation links, peer/slave lists, namespace membership, and per-mount writer accounting. Code that only needs the public view holds a vfsmount; namespace code recovers the full object with real_mount(), which is just a container_of() back to the enclosing struct mount.

This split is a scalability and encapsulation detail absent from the Linux 2.6 model, and it exists because the two halves are touched on very different paths. Every pathname lookup dereferences the tiny vfsmount constantly, so keeping it small keeps it cache- friendly; the heavyweight tree-management fields in struct mount are touched only when the mount topology itself changes. A related piece is per-mount writer accounting: struct mount carries mnt_writers (and a per-CPU mnt_pcp counter) so the kernel can answer "does this mount have open writable files?" without a global lock. mnt_want_write() takes a writer reference and is what makes a read-only remount (or read-only bind mount) fail cleanly with -EBUSY while a file is still open for writing.

A mount is emphatically not the same thing as a superblock. Several mounts can reference one superblock—every bind mount and every member of a shared subtree does exactly that—so the superblock's fs_supers-linked mounts share on-disk state while presenting independent locations, flags, and idmaps. Conversely, a single namespace can hold many mounts of the same filesystem type, and an internal (kern_mount()) mount may exist while being reachable from no process namespace at all. Each mount also carries identifiers: the reused mnt_id visible in /proc/self/mountinfo and the mnt_id_unique value that is never recycled for the life of the boot. One field in that table deserves more than a line, because it is what makes the mount tree usable during pathname resolution. A mount is not reached by searching a list of mounts; it is found by hashing the pair that identifies where it is attached. 

static inline struct hlist_head *m_hash(struct vfsmount *mnt, struct dentry *dentry)
{
        unsigned long tmp = ((unsigned long)mnt / L1_CACHE_BYTES);
        tmp += ((unsigned long)dentry / L1_CACHE_BYTES);
        tmp = tmp + (tmp >> m_hash_shift);
        return &mount_hashtable[tmp & m_hash_mask];
}

struct mount *__lookup_mnt(struct vfsmount *mnt, struct dentry *dentry)
{
        struct hlist_head *head = m_hash(mnt, dentry);
        struct mount *p;

        hlist_for_each_entry_rcu(p, head, mnt_hash)
                if (&p->mnt_parent->mnt == mnt && p->mnt_mountpoint == dentry)
                        return p;
        return NULL;
}

The key is a pair, and that single design decision is what makes mount namespaces work. A dentry is shared by every namespace that has the filesystem mounted, but each namespace has its own vfsmount objects, so the same directory hashes to different buckets depending on which mount it was reached through. A mount attached in one namespace is therefore simply not found from another — not filtered out afterwards, but never a candidate in the first place. The per-namespace view of the filesystem tree falls out of the hash key rather than being enforced by a check.

Because pointers are hashed, both are divided by L1_CACHE_BYTES first. Structures allocated from a slab cache are cache-line aligned, so their low bits are always zero and would waste the width of the table; shifting them out spreads real allocations across the buckets instead of piling them into every nth one.

Consulting even a hash table on every path component would be wasteful, since the overwhelming majority of directories are not mount points, so the lookup is gated by a bit on the dentry itself. DCACHE_MOUNTED is one of the dentry_flags discussed earlier in this chapter, and the walker in fs/namei.c tests it before doing anything else: 

if (flags & DCACHE_MOUNTED) {   // something's mounted on it..
        struct vfsmount *mounted = lookup_mnt(path);
        if (mounted) {          // ... in our namespace
                dput(path->dentry);
                if (need_mntput)
                        mntput(path->mnt);
                path->mnt = mounted;
                path->dentry = dget(mounted->mnt_root);
                ...
                continue;
        }
}

Crossing a mount point is thus a substitution: the path keeps moving, but both of its halves are replaced, the vfsmount by the mounted one and the dentry by that mount's root. The continue matters as much as the substitution. Having crossed, the loop tests the new dentry again, because something may be mounted on the root of the filesystem just entered; a stack of mounts on one directory is traversed by going around this loop once per layer rather than by any special case.

The two comments in that fragment are worth reading together, since they mark the two independent questions being asked. The dentry flag answers is anything mounted here at all, and it is a property of the dentry, which is shared across namespaces. lookup_mnt() answers is anything mounted here for us. A dentry can therefore have DCACHE_MOUNTED set and still yield NULL, which is exactly the case of a directory that some other namespace has mounted over and this one has not. The flag is a fast filter, not the answer.

lookup_mnt() wraps the hash lookup in the standard RCU-plus-seqlock retry: it reads mount_lock's sequence counter, performs the lockless search, and then calls legitimize_mnt() to take a reference and confirm nothing changed. If the counter moved, the whole attempt is discarded and repeated. Mount-point crossing therefore takes no locks at all in the common case, which matters because it happens on almost every pathname resolution on a modern system.

The Classic mount() Path

The classic syscall enters SYSCALL_DEFINE5(mount) in fs/namespace.c with five arguments: source device, target directory, filesystem type, a flags word, and an opaque data pointer. The kernel copies the userspace strings and the option data into kernel memory, then calls do_mount(), which resolves the target path and hands off to path_mount(). The reason this one syscall is so overloaded is historical: the single flags word selects among fundamentally different operations, and path_mount() is essentially a dispatcher on those flag bits.

path_mount() inspects the flags in a fixed priority order and branches to a dedicated handler: MS_REMOUNT changes an existing mount's flags and options, MS_BIND makes a second mount of an existing subtree, the propagation flags (MS_SHARED/MS_PRIVATE/MS_SLAVE/MS_UNBINDABLE) change how a mount propagates events through do_change_type(), MS_MOVE relocates a mount, and everything else falls through to do_new_mount() for a genuinely new mount. Only one of these operations happens per call, which is why the flags are checked in order rather than combined.

The order is not arbitrary, and the first test is the one most easily missed: MS_REMOUNT and MS_BIND together do not mean “remount, and also bind.” They select a fourth operation, do_reconfigure_mnt(), which changes only the per-mount flags of an existing bind mount and deliberately does not touch the superblock. That distinction is what makes it possible to have one directory visible read-write at its original location and read-only through a bind mount elsewhere, since the read-only-ness belongs to the mount rather than to the filesystem. Because this case is tested before the plain MS_REMOUNT case, a program that sets both bits never reaches do_remount(). Notice also that do_remount() receives sb_flags and mnt_flags as separate arguments rather than the raw flags word: by this point the syscall's single flags value has already been split into the bits that belong to the superblock and the bits that belong to this mount, which is exactly the distinction the next paragraph draws.

A new classic mount reaches do_new_mount(), which resolves the filesystem type with get_fs_type(), allocates an fs_context, feeds the legacy comma-separated options into it through parse_monolithic, calls vfs_get_tree() to obtain the superblock, and then grafts the resulting mount onto the target path under the namespace lock. This is the concrete reason even unmodified old userspace benefits from the new internal model: the ABI is still a single syscall, but underneath it is the same context-driven path the fd-based API uses, not a direct call into the retired get_sb_* helpers. The classic path's weakness is precisely that it multiplexes construction, configuration, and attachment into one uninterruptible call, so a bad option is only discovered after the kernel has already begun building the mount—one of the problems the new API was designed to fix.

The New Mount API

The new mount API turns mount construction into explicit file-descriptor state, so that each phase is a separate, restartable, permission-checkable syscall. fsopen() creates an fs_context and returns an fd that refers to it. fsconfig() then feeds that fd one parameter or command at a time: it takes a command selector such as FSCONFIG_SET_STRING or FSCONFIG_SET_FLAG to set an individual option, and FSCONFIG_CMD_CREATE to finally create (or reuse) the superblock once all options are set. fsmount() converts the now-configured context into a detached mount and hands back a mount fd; move_mount() attaches that detached mount to a location in the namespace. open_tree() can open or clone an existing subtree into a mount fd, and mount_setattr() changes attributes—read-only, nosuid, idmap—on an existing mount.

The internal object behind the fd is struct fs_context, the same object init_fs_context populates and the same one whose fields and phase machine were laid out earlier in this chapter. What the descriptor adds is that userspace now drives those phase transitions directly, one syscall at a time. Because options are parsed into this typed object one at a time rather than handed over as an opaque void * blob at mount time, a rejected option is reported at the fsconfig() call that set it, with the context left intact so userspace can correct it and retry. vfs_get_tree() is still the point where the filesystem is asked to produce the root and superblock, exactly as on the classic path.

The practical advantage is composability. A container runtime can open a context, set every option with individual checked calls, create the superblock, apply an idmap and other attributes to the still-detached mount, and only splice it into a namespace with move_mount() once the whole operation has succeeded—so a partially-built mount is never visible to other processes. Error reporting is sharper because parameter parsing is separated from attachment, and security is easier to reason about because a file descriptor represents an in-progress or detached mount with a well-defined lifetime and owner.

The object behind the context file descriptor is the fs_context introduced in the previous section, and the three fields discussed there govern this workflow directly: phase is what rejects an fsconfig() issued out of order, cred is captured when fsopen() runs rather than when the superblock is created, and user_ns is what mount_capable() consults. The sequence below is the canonical one, and Table 12-26 lists the syscalls it uses.

The last two complete the API in the direction nobody thought to address at first. fsopen() and its relatives replaced the mount syscall, but examining the resulting mounts still meant parsing /proc/self/mountinfo, which has every weakness the old option string had and a few of its own: it is a single text blob that must be read and reparsed in full to answer a question about one mount, its fields are positional, and separators inside a path are escaped rather than avoided. Worse, it is inherently racy — by the time a program has parsed the line describing a mount, that mount may be gone, and nothing in the file identifies whether the entry now at the same position is the same object.

listmount() and statmount() replace it with the same two-step pattern that getdents() and statx() use for directories: enumerate identifiers first, then ask about one identifier at a time. Both take a struct mnt_id_req, and both work in terms of mnt_id_unique rather than the mnt_id that mountinfo reports. That distinction is the point of having two ids in struct mount: the small id is recycled when a mount goes away, so a program that observes id 42 twice cannot tell whether it saw one mount or two, while the 64-bit unique id is never reused for the lifetime of the boot. An answer about a departed mount is reported as such rather than silently becoming an answer about a different one.

statmount() follows the statx() design in the other respect too. The caller sets a request mask of STATMOUNT_* bits — STATMOUNT_SB_BASIC, STATMOUNT_MNT_POINT, STATMOUNT_FS_TYPE, STATMOUNT_MNT_OPTS, STATMOUNT_MNT_UIDMAP and others — and the kernel reports in a matching mask which of them it actually supplied. Attributes that are expensive to compute are not computed unless asked for, and a kernel that does not know a bit says so instead of returning a plausible zero. Variable-length values such as the mount point path and the options string are written into a buffer after the fixed structure and referenced by offset, so a single call returns them without the caller having to guess at sizes in advance.

listmount() enumerates the children of a mount, or with mnt_ns_id the mounts of an entire namespace, returning unique ids into a caller-supplied array. It is resumable: passing the last id received as param continues the enumeration, which is how a large namespace is walked without an unbounded buffer. LISTMOUNT_REVERSE walks the other way. Together the two calls let a program inspect the mount table incrementally and with defined behaviour under concurrent change, neither of which parsing mountinfo can offer.

Mounting the Root Filesystem

Every mount discussed so far is spliced onto a directory that already exists in the tree—but that raises a bootstrap question: what does the very first mount attach to, before any filesystem has been mounted? The answer is rootfs, a small in-memory filesystem the kernel mounts as / before any userspace runs and before any block device is available. rootfs guarantees there is always a valid root to graft onto, so the code paths above never face an empty tree.

rootfs is registered as its own file_system_type in init/do_mounts.c. It is not a filesystem in its own right; its init_fs_context forwards to either ramfs or, when tmpfs is configured and requested, shmem (tmpfs). Both are memory-backed, so rootfs needs no device. The choice is fixed early by init_rootfs() setting is_tmpfs. 

static int rootfs_init_fs_context(struct fs_context *fc)
{
        if (IS_ENABLED(CONFIG_TMPFS) && is_tmpfs)
                return shmem_init_fs_context(fc);   /* tmpfs-backed rootfs */
        return ramfs_init_fs_context(fc);           /* ramfs-backed rootfs */
}

struct file_system_type rootfs_fs_type = {
        .name            = "rootfs",
        .init_fs_context = rootfs_init_fs_context,
        .kill_sb         = kill_anon_super,
};

The initial mount tree is built by init_mount_tree() in fs/namespace.c, called from mnt_init() during early boot. In Linux 7.0.12 this creates two mounts: a nullfs mount (mount id 1) that serves as the namespace's fixed anchor, and the mutable rootfs (mount id 2) stacked on top of it. The initial mount namespace init_mnt_ns is populated with both, and the init task's root and working directory are set to point at the mutable rootfs. From this moment on there is a live struct path for /, and every later mount—whether from userspace mount(2) or the fd-based API—hangs off this tree. 

static void __init init_mount_tree(void)
{
        struct vfsmount *mnt, *nullfs_mnt;
        ...
        nullfs_mnt = vfs_kern_mount(&nullfs_fs_type, 0, "nullfs", NULL);
        mnt        = vfs_kern_mount(&rootfs_fs_type, 0, "rootfs", initramfs_options);

        /* nullfs (id 1) is the namespace root; rootfs (id 2) is mounted on it. */
        init_mnt_ns.root = real_mount(nullfs_mnt);
        ...
        /* root and pwd of the init task point at the mutable rootfs. */
        root.mnt = mnt;
        root.dentry = mnt->mnt_root;
        set_fs_pwd(current->fs, &root);
        set_fs_root(current->fs, &root);
}

Once rootfs exists it is populated: the initramfs—a cpio archive either embedded in the kernel image or supplied by the bootloader—is unpacked directly into rootfs, giving an early userspace root that normally contains an /init program. What happens next determines how the real root filesystem is reached, and there are two paths.

The initramfs path (the modern default). If the unpacked rootfs contains an executable /init, kernel_init() runs it directly as PID 1 and never calls prepare_namespace(). That early userspace is then responsible for locating the real root device, mounting it, and switching to it—typically with switch_root, which moves the new mount to /, performs a chroot into it, and executes the final /sbin/init. rootfs is never explicitly unmounted; it is simply left behind and reclaimed.

The legacy path. If there is no /init, kernel_init() falls back to prepare_namespace(), shown below. It waits for the root device named by the root= boot parameter to finish probing, calls mount_root() to mount that real filesystem on /root, and then uses init_pivot_root(".", ".") to pivot the real filesystem into place and unmount the old rootfs underneath. Only afterward does the kernel exec the userspace /sbin/init. 

void __init prepare_namespace(void)
{
        wait_for_device_probe();
        ...
        if (saved_root_name[0])
                ROOT_DEV = parse_root_device(saved_root_name);
        initrd_load();
        if (root_wait)
                wait_for_root(saved_root_name);

        mount_root(saved_root_name);        /* mount root= device on /root */
        devtmpfs_mount();

        init_pivot_root(".", ".");          /* pivot real root into place */
        init_umount(".", MNT_DETACH);       /* detach the old rootfs */
        pr_info("VFS: Pivoted into new rootfs\n");
}

Two properties make rootfs special compared with an ordinary mount. It is created by the kernel itself rather than by a syscall, so it has no source device and a fixed mount id; and in the legacy path it is never unmounted in the normal sense—the kernel pivots away from it. This is also why the picture of a kernel that mounts the real root filesystem directly no longer matches reality: modern boots almost always go through an initramfs mounted on rootfs first.

Mount Namespaces and Propagation

A mount namespace is a private view of the mount tree—the set of mounts a process can see and traverse. Creating a process with CLONE_NEWNS (or calling unshare(CLONE_NEWNS)) drives copy_mnt_ns(), which clones the caller's mounts into a fresh namespace, preserving or adjusting propagation relationships as it goes. From then on, processes in different namespaces can have different roots, different bind mounts, and different visibility of the very same underlying superblocks; a mount added in one namespace is invisible in another unless propagation deliberately carries it across.

Propagation is what governs whether mount and unmount events flow between related mounts, and it is the mechanism that makes containers both isolated and manageable. A shared mount propagates events to every peer in its group, so a new mount under it appears under all of them. A private mount propagates in neither direction. A slave mount receives events from its master but never sends any back—the asymmetry a container runtime wants when it needs host mounts (say, a newly inserted USB disk) to appear inside a container while guaranteeing that mounts created inside the container cannot leak out to the host. An unbindable mount is private and additionally refuses to be bind-mounted, which prevents accidental recursive duplication of large subtrees. These states are set with the MS_SHARED, MS_PRIVATE, MS_SLAVE, and MS_UNBINDABLE flags and are recorded in the mnt_share, mnt_slave_list, and mnt_master links of struct mount.

Idmapped Mounts

Idmapped mounts let a single mounted view reinterpret inode ownership through a per-mount UID/GID mapping, without touching the bytes on disk. The same on-disk inode can therefore appear owned by one id through one mount and by a different id through another mount of the same filesystem. This solves a real container and sandbox problem: a host directory owned by UID 1000 can be exposed to a container that expects it owned by UID 0, or a shared build tree can be presented under each user's own id, all without the expensive and destructive chown -R that changing on-disk ownership would require.

The mapping lives on the mount, not the inode: the public struct vfsmount carries mnt_idmap, retrieved with the mnt_idmap() accessor under the required memory ordering. The VFS translates on the fly between the filesystem's on-disk ids and the caller-visible ids using the vfsuid/vfsgid types, which are deliberately distinct from raw kuid_t/kgid_t so the compiler helps catch a missed translation. The key API consequence—and the reason so many prototypes in this chapter begin with a struct mnt_idmap *—is that every inode operation that creates, changes, or reports ownership now receives the idmap explicitly, so the filesystem applies the mapping consistently at exactly the points where ownership is interpreted.

Userspace installs an idmap by pointing mount_setattr() at a user namespace with MOUNT_ATTR_IDMAP. A filesystem must opt in by setting FS_ALLOW_IDMAP in its file_system_type, because supporting the feature means every permission check, ownership report, quota account, and on-disk id operation has been audited to route through the mapping rather than around it. Idmapped mounts are a good illustration of how Linux 7.0.12 generalizes the classic VFS model for container workloads by threading one extra parameter through the existing inode operations, instead of inventing a parallel namespace of file objects.

Pathname Lookup

Pathname lookup—turning a string like /usr/lib/libc.so.6 into the dentry and inode it names—is the most intricate operation in the VFS, because a single walk has to combine string parsing, dcache lookup, permission checks, symlink following, mount-point crossing, RCU, rename races, automounts, and special final-component semantics (create, exclusive-create, trailing-slash, "must be a directory"). The implementation lives primarily in fs/namei.c. Its central state object is struct nameidata, and its central optimization is to begin every walk in lockless RCU-walk whenever the operation permits.

Linux 2.6 resolved symbolic links recursively and used a much more lock-heavy dentry lookup. Linux 7.0.12 instead uses an iterative stack for symlinks and a two-mode walk. The mode choice is expressed as a three-attempt escalation in filename_lookup(): the walk is first tried with LOOKUP_RCU; if RCU-walk gives up it returns -ECHILD and the walk is retried in ref-walk; and if a filesystem's revalidation reports stale cache it returns -ESTALE and the walk is retried once more with LOOKUP_REVAL to force fresh revalidation. Each attempt runs the same component loop, so understanding one walk explains all three. 

/* fs/namei.c — the mode escalation that drives every lookup */
retval = path_lookupat(&nd, flags | LOOKUP_RCU, path);
if (unlikely(retval == -ECHILD))          /* RCU-walk bailed out */
        retval = path_lookupat(&nd, flags, path);           /* ref-walk */
if (unlikely(retval == -ESTALE))          /* cached dentry was stale */
        retval = path_lookupat(&nd, flags | LOOKUP_REVAL, path);

Within a single attempt, the walk is a small pipeline: path_init() establishes the starting point (root, cwd, or a directory fd) and samples the sequence counters; link_path_walk() loops over the "/"-separated components; walk_component() resolves one name, usually via lookup_fast() against the dcache; and step_into() descends into the result, crossing any mount stacked on it and following any symlink; and every attempt ends in either complete_walk() or terminate_walk(). When lookup cannot proceed losslessly in RCU mode, it calls try_to_unlazy() to legitimize the path and continue in ref-walk, or bails out with -ECHILD to trigger the ref-walk retry above.

Two things about that pipeline are easy to miss and are taken up in turn below. The loop is not only resolving names: before it can search a directory it must check that the caller may search it, and the shape of that check is dictated by the same RCU constraints as everything else. And two of the components it meets, . and .., are not resolved by lookup at all—the second of them is where the walk's containment guarantees are won or lost. Figure 12-5 contrasts the two modes of the walk and the point at which one becomes the other.

nameidata and the Two Walk Modes

struct nameidata is far more than a parser cursor. It records the current path (path), the component being resolved (last) and its type (last_type: normal, dot, dotdot, or root), the resolution root (root), the current inode, the lookup flags and internal state, the starting descriptor (dfd), the symlink depth, and the saved symlink frames. Crucially, it also carries four sequence snapshots that constitute the correctness proof for a lockless walk: seq and next_seq for the current and next dentry, m_seq for the mount hierarchy (mount_lock), and r_seq for the rename sequence. The same object thus holds the concurrency proof for an RCU walk and the pinned references for a ref-walk.

The symlink stack is embedded to avoid allocation on the common path: internal[EMBEDDED_LEVELS] holds the first two nested links (EMBEDDED_LEVELS is 2), and only a deeper nest allocates a larger stack. Each frame saves the link's path, its get_link cleanup state (a delayed_call), and the sequence number captured when the link was picked, so the walk can resume the parent component after the link body is consumed.

The two walk modes are documented at the top of fs/namei.c. RCU-walk is lockless and validates every sampled pointer against the sequence counters before trusting it; ref-walk takes real references and locks as needed. A single lookup can start in RCU mode, drop to ref-walk mid-walk via try_to_unlazy(), or restart entirely from the top if a concurrent mutation invalidates the sampled state before it can be legitimized—exactly the -ECHILD path shown in the section introduction.

Lookup flags in include/linux/namei.h steer the walk. Some are the classic behaviors inherited from traditional syscalls, such as LOOKUP_FOLLOW (follow a trailing symlink) and LOOKUP_DIRECTORY (require the result to be a directory). Others come from the modern containment interfaces exposed by openat2(), such as LOOKUP_BENEATH, LOOKUP_IN_ROOT, LOOKUP_NO_XDEV, and LOOKUP_CACHED. The RCU/ref distinction itself is carried by LOOKUP_RCU, cleared the moment the walk unlazies.

Two fields hold what looks like one kind of information, and the split is deliberate. flags holds the LOOKUP_* bits, which are policy—supplied by the caller, largely constant for the whole walk, and meaningful outside fs/namei.c. state holds the three ND_* bits, which are bookkeeping—set by the walk about itself, private to the file, and meaningful only until the walk ends. ND_ROOT_PRESET records that the caller supplied the resolution root, so the walk must not clear or free it; ND_ROOT_GRABBED records the opposite, that the walk took its own reference on the root and owes a path_put(); and ND_JUMPED records that the walk moved somewhere other than by stepping into a child, which matters at the very end of the lookup for reasons taken up under ref-walk. Older kernels carried the last of these as a LOOKUP_JUMPED flag mixed in with the caller's policy bits; separating them made both sets easier to reason about, and LOOKUP_JUMPED no longer exists.

root_seq is the sequence number of the resolution root, sampled when the root was chosen. It exists for the same reason seq does: in RCU-walk the root is a borrowed pointer like any other, and if the walk later needs a real reference to it, that reference is only trustworthy if the root has not changed in the meantime. saved is a different kind of field again—it links to the nameidata of an outer lookup, because current->nameidata is a stack. RCU-Walk

RCU-walk begins in path_init() when the requested operation permits it. The function enters an RCU read-side critical section and snapshots the relevant sequence counters—the starting dentry's d_seq into nd->seq and the mount sequence into nd->m_seq. link_path_walk() then iterates over components, and walk_component() asks lookup_fast() to search the dcache with __d_lookup_rcu(), the lockless variant described in the dentry-cache section.

Two details of that function repay attention. A cache miss is not simply reported upward: because resolving a name that is not cached means calling the filesystem, which may block, lookup_fast() unlazies on the spot and returns NULL to mean not found in cache, and you are now in ref-walk. The failure to unlazy, not the miss, is what produces -ECHILD. And the comment at the top explains an omission rather than a check—the rename seqlock is deliberately not consulted here, because the worst a concurrent rename can cause is a false negative, and a false negative merely sends the walk down the slow path that would have been taken anyway. That is a useful contrast to hold against the .. case discussed later, where the rename counter genuinely is required, because there a stale answer would not be a missed cache hit but a wrong parent.

The crucial property is that RCU-walk takes no reference count on any dentry or mount it passes through. Two guarantees make that safe. First, RCU deferral: a dentry freed by another CPU cannot be recycled until a grace period ends, and the walk holds rcu_read_lock(), so a pointer it sampled cannot point at reused memory. Second, sequence validation: before the walk trusts a sampled parent, child, name, mount, or rename state, it re-reads the matching seqcount and confirms it did not change. If any check fails, the sampled data might be inconsistent, and the walk aborts back to the caller with -ECHILD rather than risk acting on it.

A successful RCU-walk is extremely cheap for hot paths such as /usr/lib/libc.so.6 or a server repeatedly statting files in its working directory: no atomics, no locks, no cache-line ping-pong on shared dentries. The price is that RCU mode cannot do anything that sleeps, takes a lock, or needs a stable reference—reading a slow symlink, allocating a missing dentry, calling a non-RCU d_revalidate, or triggering an automount. Any of those forces the walk either to legitimize its state with try_to_unlazy() and continue, or to give up with -ECHILD. That transition is a designed part of the algorithm, not a failure.

One thing the walk must do at every single component has no place in the pipeline as described so far: check that the caller is allowed to search the directory. That is may_lookup(), and its structure is governed entirely by the RCU problem. Search permission on a directory is the execute bit, so the mask is MAY_EXEC—which is why a directory with x but not r can be traversed by anyone who knows a name inside it but cannot be listed. The check is per component, so a path is walkable only if every directory along it grants search.

In RCU mode the check is asked to run with MAY_NOT_BLOCK, and the interesting case is failure. A permission check that fails in RCU mode has not necessarily decided anything: it may have been unable to consult an ACL, or a security module may have needed to sleep. So a non-RCU failure is final and returned as-is, while an RCU failure is treated as provisional. The walk unlazies and, if the error was -ECHILD, runs the check again for real. Once more an errno is doing duty as an internal signal rather than as a result—-ECHILD here means I could not answer without blocking, in the same way -ENOPARAM means this parameter is not mine in the mount dispatcher. Both are values a caller inside the kernel is expected to interpret and act on, and neither ever reaches userspace. 

static inline int may_lookup(struct mnt_idmap *idmap,
                             struct nameidata *restrict nd)
{
        int err, mask;

        mask = nd->flags & LOOKUP_RCU ? MAY_NOT_BLOCK : 0;
        err = lookup_inode_permission_may_exec(idmap, nd->inode, mask);
        if (likely(!err))
                return 0;

        // If we failed, and we weren't in LOOKUP_RCU, it's final
        if (!(nd->flags & LOOKUP_RCU))
                return err;

        // Drop out of RCU mode to make sure it wasn't transient
        if (!try_to_unlazy(nd))
                return -ECHILD; // redo it all non-lazy

        if (err != -ECHILD)     // hard error
                return err;

        return lookup_inode_permission_may_exec(idmap, nd->inode, 0);
}

The helper it calls is a lookup-specific shortcut rather than the general inode_permission(), and its comment explains the reasoning in a way worth repeating, because it is a good example of how a hot path is optimized in the kernel. Two facts are known for free at this call site—the object is a directory, and no write access is being requested—so the general routine does work that cannot matter here. More usefully, the comment observes that the overwhelming majority of real traversals happen through directories that grant search to everybody. So the fast path tests exactly that, (inode->i_mode & 0111) == 0111 together with the absence of POSIX ACLs, and on success calls only the security-module hook. Anything else—a restrictive mode, an ACL, or an inode whose filesystem has not opted in via IOP_FASTPERM or IOP_FASTPERM_MAY_EXEC—falls back to the full check. The optimization is not a different policy, only a cheaper way of reaching the same answer in the common case.

Ref-Walk and unlazy

try_to_unlazy() and try_to_unlazy_next() are the bridge from RCU-walk to ref-walk. Rather than restart, they attempt to convert the walk's sampled state into pinned references in place. The correctness argument lives one level down, in __legitimize_path(), and its order of operations is the whole idea: it first legitimizes the mount against nd->m_seq, then takes a live reference on the dentry with lockref_get_not_dead() (which fails if the dentry is already dying), and only then re-checks read_seqcount_retry() on d_seq to prove the dentry did not change while the reference was being taken. The re-check must come last. Taking a reference is not an act of observation, and a reference taken on the wrong object is worse than useless; the sequence number is what certifies, after the fact, that the object referenced is the object that was sampled.

What try_to_unlazy() adds on top is the list of things that have to survive the transition, and that list is longer than the current position. The walk may be several symlinks deep, and every saved frame holds a borrowed path of its own, so legitimize_links() walks the stack and legitimizes each one—a failure part-way through carefully sets nd->depth so that terminate_walk() releases exactly the frames that were pinned. Then the current path, then the resolution root via legitimize_root(), which is where root_seq is finally spent and where ND_ROOT_GRABBED is set to record that the root now carries a reference the walk owes back. Only after all of those does leave_rcu() clear LOOKUP_RCU, zero the stale sequence numbers, and drop the RCU read lock. If any step fails, the whole walk returns -ECHILD and is retried from the top in ref-walk mode.

The first test in the function is not part of that argument at all. If LOOKUP_CACHED is set, unlazying is refused outright, because the caller asked for a resolution that does no uncached work and dropping to ref-walk is precisely the beginning of such work. This is the kernel side of RESOLVE_CACHED, and it is the reason that flag can be honoured cheaply: rather than being checked at each blocking operation, it is enforced at the one door every blocking operation must pass through.

Once in ref-walk, the walk is the traditional stable-reference mode: dentries and mounts are pinned, locks may be taken, and filesystem callbacks may sleep. This is required whenever lookup hits a dcache miss and must allocate and populate a dentry, calls a non-RCU d_revalidate, follows a symlink that needs filesystem I/O, triggers an automount, or reaches a final component that must hold a stable reference for the caller (such as the file that open() will attach to a descriptor).

This optimistic-then-conservative retry is a recurring pattern in Linux lockless algorithms. The fast path assumes stability and validates the assumption; the slow path pays for references and locks only when the assumption breaks or the semantics demand it. From userspace the lookup is a single atomic operation; internally it may be an RCU attempt, an in-place unlazy, and—if that loses—a full ref-walk restart, exactly the three-attempt escalation in filename_lookup(). 

/* path_put is needed afterwards regardless of success or failure */
static bool __legitimize_path(struct path *path, unsigned seq, unsigned mseq)
{
        int res = __legitimize_mnt(path->mnt, mseq);
        if (unlikely(res)) {
                if (res > 0)
                        path->mnt = NULL;
                path->dentry = NULL;
                return false;
        }
        if (unlikely(!lockref_get_not_dead(&path->dentry->d_lockref))) {
                path->dentry = NULL;
                return false;
        }
        return !read_seqcount_retry(&path->dentry->d_seq, seq);
}

static bool try_to_unlazy(struct nameidata *nd)
{
        struct dentry *parent = nd->path.dentry;

        VFS_BUG_ON(!(nd->flags & LOOKUP_RCU));

        if (unlikely(nd->flags & LOOKUP_CACHED)) {
                drop_links(nd);
                nd->depth = 0;
                goto out1;
        }
        if (unlikely(nd->depth && !legitimize_links(nd)))
                goto out1;
        if (unlikely(!legitimize_path(nd, &nd->path, nd->seq)))
                goto out;
        if (unlikely(!legitimize_root(nd)))
                goto out;
        leave_rcu(nd);
        BUG_ON(nd->inode != parent->d_inode);
        return true;

out1:
        nd->path.mnt = NULL;
        nd->path.dentry = NULL;
out:
        leave_rcu(nd);
        return false;
}

Every walk ends in one of two functions, and the asymmetry between them is instructive. terminate_walk() is the unconditional cleanup: it releases any symlink frames still on the stack, and then, if the walk is in ref-walk, drops the current path, each saved link, and the root if ND_ROOT_GRABBED says the walk took one—or, if the walk is still in RCU mode, simply leaves the read-side critical section, since nothing was pinned and nothing needs releasing. That single branch is the clearest statement of what the two modes cost: unwinding a failed RCU-walk is free.

complete_walk() is the successful exit, and it has one more job than it appears to. First it must leave RCU mode, because the caller is about to be handed a result it will hold onto; a walk that cannot unlazy here has not failed to find the file, it has merely failed to finish cheaply, and returns -ECHILD for the ref-walk retry. Then comes the answer to a question the section opened with and did not settle: where the -ESTALE in the three-attempt escalation comes from. If ND_JUMPED is set—that is, if the walk arrived at its result by some means other than stepping into a child, such as jumping to the root or following a magic link—then the ordinary per-component revalidation never ran on the way here, and a filesystem that wants to be asked is given a last chance through d_weak_revalidate. A filesystem that answers no turns the whole lookup into -ESTALE, which the caller converts into a third attempt with LOOKUP_REVAL set. This is why ND_JUMPED is worth a bit of its own: it is not a curiosity about how the walk travelled, it is the condition under which the result has not been checked. 

static int complete_walk(struct nameidata *nd)
{
        struct dentry *dentry = nd->path.dentry;
        int status;

        if (nd->flags & LOOKUP_RCU) {
                ...
                nd->flags &= ~LOOKUP_CACHED;
                if (!try_to_unlazy(nd))
                        return -ECHILD;
        }
        ...
        if (likely(!(nd->state & ND_JUMPED)))
                return 0;

        if (likely(!(dentry->d_flags & DCACHE_OP_WEAK_REVALIDATE)))
                return 0;

        status = dentry->d_op->d_weak_revalidate(dentry, nd->flags);
        if (status > 0)
                return 0;

        if (!status)
                status = -ESTALE;

        return status;
}

Dot, Dot-Dot, and Scoped Resolution

Not every component is a name to be looked up. . and .. are parsed into last_type values—LAST_DOT and LAST_DOTDOT—and handled by handle_dots() instead of going anywhere near the dcache hash. . is trivially nothing. .. is the hardest single component in the walker, and it is worth understanding why, because almost every containment escape that pathname resolution has to defend against is an escape through ...

The difficulty is that .. is not a lookup at all. There is no entry named .. to find; the parent is reached by following dentry->d_parent, or, if the current dentry is the root of a mounted filesystem, by first stepping out of that mount to the directory it was mounted on. That is the mirror image of the crossing described under mounting: lookup_mnt() answers what is mounted here on the way down, and choose_mountpoint() answers where was this mounted on the way up. Both directions have to be blocked when the caller asked not to cross device boundaries, which is why LOOKUP_NO_XDEV appears in the .. path as well as in the descent.

The most surprising line in the function is the one that does nothing. When the current path already equals the resolution root, .. does not fail and does not move—it returns the same dentry. This is the kernel implementing the rule that /.. is /, and it is the reason a chain of .. components can never walk off the top of a tree by accident. The importance of that clamp is what makes the next line make sense: LOOKUP_BENEATH does not add a check, it changes what the existing clamp does. Instead of silently staying put, an attempt to go above the starting point becomes -EXDEV. The difference matters to a sandbox, which needs to know that a path tried to escape rather than being quietly given a path that means something else than it says.

The twin comments reading makes sure that non-RCU pathwalk could reach this state state the discipline that RCU-walk works under. The lockless walk is not allowed to reach conclusions a careful, reference-taking walk could not have reached; where it cannot prove that, it must abandon the attempt rather than produce a plausible answer. Both checks here are of that kind, and both bail with -ECHILD.

path_connected() guards a subtler case. A bind mount can expose a subtree of a filesystem, and a rename elsewhere in that filesystem can move a directory out from under the bind mount while a walk is inside it. Following d_parent would then lead somewhere the mount never made visible. The check confirms the parent is still below mnt->mnt_root, and, in ref-walk, reports -ENOENT—the honest answer, since the path the caller named no longer exists in the tree the caller can see. The function returns early for a mount whose root is the filesystem root, because that case cannot arise there.

The last part of handle_dots() is the one place in the walker where per-step checks are admitted to be insufficient, and it is what nd->r_seq exists for. Each .. is verified as it is taken, but a scoped lookup is a statement about the path as a whole, and a rename racing with the walk can move a directory so that a sequence of individually valid parent steps ends up above the root. No local check can see this. So a scoped lookup, on completing a .., re-reads the global mount and rename sequence counters it sampled at the start, and if either has advanced it gives up with -EAGAIN.

This is a conservative test, and deliberately so: any rename anywhere in the system, on any filesystem, will trip it, not merely one along the path being walked. The counters are global. But the cost falls only on scoped lookups, which are rare compared to ordinary ones, and the alternative—tracking which renames could have affected this walk—would be far more expensive than occasionally telling a sandbox to try again. It is also worth noticing what kind of answer -EAGAIN is. Most syscalls do not ask userspace to retry; here the kernel is saying that it cannot make the guarantee that was requested, and would rather say so than weaken the guarantee. A caller that cannot retry has learned something real, which is that the tree it is resolving against is being changed underneath it.

The same conservatism appears once more at the end. complete_walk() finishes a scoped lookup by calling path_is_under() on the result, and the comment is candid about why: the guarantee should already follow from everything above, but a bug in the walker would hand userspace a descriptor outside the requested root, so the cheap check is made anyway. The same comment answers the obvious objection—that the path could be moved out of the root immediately afterwards—and in doing so states precisely what RESOLVE_IN_ROOT promises. Not that the file will remain inside the root, which no kernel could promise, but that it was inside the root at the moment it was resolved.

Symbolic Links

Linux 7.0.12 resolves symbolic links iteratively rather than by the recursion used in Linux 2.6. Instead of the walk calling itself for each nested link, the current component is pushed onto the nameidata symlink stack and the loop simply continues with the link's body as the new input. reserve_stack() holds both limits. Its first line increments nd->total_link_count and refuses at MAXSYMLINKS (40) with -ELOOP, which is a budget on the total number of links a single resolution may follow, not on how deeply they nest. That distinction is what makes the limit an effective defence: a path can loop through forty links without ever nesting more than one deep, and counting nesting alone would not stop it.

The rest of the function is allocation, and its shape is dictated by RCU. If the two embedded frames are exhausted, nd_alloc_stack() allocates a full MAXSYMLINKS frames in one go—there is no point growing incrementally when the ceiling is both small and known—using GFP_ATOMIC in RCU mode. If that atomic allocation fails, the walk must unlazy and retry with GFP_KERNEL, and the ordering here repays reading. The link has to be legitimized before the unlazy, because after leaving RCU mode the sampled pointer can no longer be validated; and the unlazy has to happen even when that fails, because terminate_walk() needs the walk to be in a consistent mode in order to clean up. The comment in the source says exactly this, in two lines.

Resolving one link means calling the inode's get_link method. pick_link() invokes it, saves the returned body and a delayed_call cleanup handle in the stack frame (so the filesystem can free or unpin the link buffer once the walk has consumed it), and hands the body back to the component loop. This structure both prevents kernel-stack exhaustion and lets symlink following cooperate with RCU-walk: a "fast" symlink whose target is stored inline in the inode can be read without blocking and stays in RCU mode, while a link that needs filesystem I/O or allocation forces the walk to unlazy to ref-walk first.

Magic links—the special procfs entries such as /proc/<pid>/fd/N or /proc/<pid>/root that behave like direct kernel references to an open file rather than textual targets—are handled separately, because following one can jump the walk to an object outside the visible tree. They do not go through get_link at all in the usual sense: the filesystem calls nd_jump_link(), handing the walker a fully formed path and telling it to continue from there. That function is where the policy is enforced, and it is short enough to enumerate— LOOKUP_NO_MAGICLINKS refuses outright with -ELOOP, LOOKUP_NO_XDEV refuses if the jump would land on a different mount, and a scoped lookup refuses unconditionally, because a jump has no parent chain to check against the root and so cannot be shown to stay beneath it. On success it sets ND_JUMPED, which is what later obliges complete_walk() to offer the result for weak revalidation.

Notice that the refusal for scoped lookups is not configurable. A caller cannot opt into magic links under RESOLVE_IN_ROOT, because there would be nothing left of the guarantee. This is one more place where modern pathname lookup is a security boundary rather than a string parser: the decision to cross such a link is made inside the walk, under the caller's resolve policy, at the moment the crossing would happen.

openat2 and RESOLVE Flags

openat2() exposes pathname-resolution policy that older interfaces could only approximate. Where open() and openat() take a bare flags integer, openat2() takes a versioned struct open_how with separate flags, mode, and resolve fields, passed together with its size. The kernel checks that size (so old binaries and new kernels stay compatible), validates the flag combinations, and maps the resolve bits into the corresponding LOOKUP_* flags before handing off to the normal do_filp_open() path—so the new policy reuses the same walker, it does not fork it.

The resolve flags exist for race-resistant sandboxing. RESOLVE_BENEATH forbids the walk from escaping above the starting directory, and RESOLVE_IN_ROOT makes the starting directory behave like a temporary / (so absolute paths and .. are pinned to it, the building block of a userspace chroot without the syscall). RESOLVE_NO_XDEV refuses to cross mount points, RESOLVE_NO_SYMLINKS rejects every symlink, and RESOLVE_NO_MAGICLINKS rejects only the proc-style magic links. RESOLVE_CACHED asks the kernel to fail with -EAGAIN rather than perform any blocking lookup work, letting an event loop keep a fast path fully non-blocking and hand the slow case to a worker thread. Notice that RESOLVE_CACHED is the only one of the six that is not a plain translation into a LOOKUP_* bit. It is refused before the walk even starts if the open would create, truncate, or make a temporary file, since no amount of caching can satisfy a request that must modify the filesystem.

Past that point the flag becomes LOOKUP_CACHED and is enforced in just two places, both already seen: path_init() rejects it up front if the walk is not being attempted in RCU mode at all, and try_to_unlazy() refuses to leave RCU mode once the walk is under way. Everything in the walker that could block lies downstream of one of those two doors, so no third check is needed—a good illustration of how much cheaper a guarantee becomes when the code has a single chokepoint to attach it to.

The underlying lesson is that pathname lookup cannot be made safe by filtering strings in userspace. Between one lstat() check and the following open(), a rename, a new mount, or a swapped symlink can change what a path means—the classic time-of-check/time-of-use race. openat2() closes that gap by moving the constraints into the same state machine that resolves the path, so every component is checked against the policy as it is walked, atomically with the resolution itself. Implementation of VFS System Calls

Everything the chapter has built—objects, caches, mounts, and the pathname walker—exists to serve a handful of file system calls. This section follows four of them (open, read/write, close, and the zero-copy transfer calls) from the userspace ABI down to the filesystem method, so the pieces connect. Every one of them follows the same four-step shape: validate userspace input (copy the filename, translate flags, check the descriptor), acquire the VFS objects (path lookup, a referenced struct file), run generic helper logic (permission and mode checks, position handling, security hooks), and only at the very bottom dispatch to a filesystem method through an operations table. Keeping the filesystem-specific call at the boundary is what lets one syscall implementation serve ext4, tmpfs, NFS, and a pseudo filesystem identically.

The second theme is that modern Linux treats data movement as an iterator problem. The 2.6-era read/write function-pointer model still exists for compatibility, but the preferred methods are read_iter and write_iter, driven by a kiocb (which carries the file, the offset, and I/O flags such as non-blocking or O_SYNC) and an iov_iter (which describes where the bytes are). Collapsing every data path onto this pair means a single filesystem implementation covers blocking synchronous I/O, vectored readv()/writev(), in-kernel buffers, splice and sendfile transfers, and io_uring submissions, with the generic accounting and permission logic written exactly once.

Opening a File

Opening begins with SYSCALL_DEFINE4(openat) or SYSCALL_DEFINE4(openat2). Both routes normalize their arguments into a struct open_how and reach do_sys_openat2(), which turns the open flags and resolve policy into an internal open_flags structure with build_open_flags() and then calls do_file_open(). That hands off to the namei code, which runs path_openat()—the open-aware variant of the pathname walk—driving path_init(), link_path_walk(), the final-component lookup (including O_CREAT/O_EXCL creation), and finally do_open().

The whole function is now six lines, and the reason is worth dwelling on because it is one of the clearest examples of a change that has been working its way through the kernel. The two resources this syscall handles—the copied-in filename and the reserved descriptor number—are no longer released by hand on each error path. The filename is a scope-bound object declared with CLASS(filename, name)(filename), whose destructor calls putname() automatically when the variable goes out of scope, however the function leaves. The descriptor and file are handled the same way by FD_ADD().

The file object is allocated by alloc_empty_file() in fs/file_table.c, which also enforces the system-wide open-file limit. Final opening runs vfs_open()/finish_open(), which sets the file's operations from the inode's i_fop and invokes the filesystem's open method if it has one. The file's mode bits (FMODE_READ, FMODE_WRITE, FMODE_ATOMIC_POS, and so on) are settled here, so that by the time the file is published every later read/write can trust them without re-deriving them. Only after the file object is fully initialized does fd_install() publish it into the descriptor table.

This ordering is the reserve-then-publish invariant from the descriptor-table section, seen end to end. If anything fails during lookup or the filesystem open—a missing file, a permission denial, an allocation failure—the reserved descriptor is returned with put_unused_fd() and userspace never sees a half-open file. If the open succeeds, publication is a single store that makes the fully formed file atomically visible to close, dup, and exec. That strict separation of descriptor allocation from file publication is one of the small invariants that keeps multithreaded descriptor tables correct.

What has changed is not the invariant but who is responsible for it. Older kernels wrote the unwinding by hand at each exit, and that is the shape most descriptions of open() still show: reserve, attempt, and on any failure remember to call put_unused_fd(). The trouble with hand-written unwinding is that it is correct only as long as nobody adds an early return, and file descriptors are an unusually unforgiving thing to leak, because a stale reservation is invisible until the process runs out of descriptors much later. FD_ADD() removes the possibility. The reservation is made inside a scope-bound struct fd_prepare whose destructor releases both the descriptor and the file if they are still held; every early return therefore unwinds correctly by construction.

Success is expressed as disarming that destructor rather than as skipping it. fd_publish() calls fd_install() and then retain_and_null_ptr() and take_fd(), which clear the file pointer and the descriptor number out of the guard so the destructor finds nothing to release. Reading this idiom for the first time is easier if the guard is understood as owning the resources until ownership is explicitly taken away from it, which is the opposite of the usual convention that a function owns what it allocated until it says otherwise. The single-source-of-truth err field is part of the same design: rather than each caller re-deriving whether the descriptor or the file failed, the error is recorded once when the guard is initialized.

Two things happen at the end of the walk that the account so far has skipped, and the first is permission. The check that a component may be searched was covered under pathname lookup; the check that the final file may be opened is may_open(), and it is worth reading because almost every puzzling open() error a programmer meets originates in its one switch statement. Opening a symlink is -ELOOP, which is where O_NOFOLLOW's error code comes from. Opening a directory for writing is -EISDIR. A device node on a filesystem mounted nodev is -EACCES, and a regular file on a noexec mount is the same when execute access was asked for. For fifos, sockets and device nodes O_TRUNC is not an error but is silently cleared, because truncation is meaningless for objects that have no length. An append-only file refuses to be opened for writing without O_APPEND, and refuses O_TRUNC outright. O_NOATIME is allowed only to the owner or to a sufficiently privileged caller, since suppressing access-time updates on somebody else's file would hide the fact that it had been read.

Underneath the switch is a single inode_permission() call with MAY_OPEN added to the access mode. That extra bit is not a permission in the file-mode sense—no inode grants or denies it—but a signal to security modules that this particular check is an open rather than an incidental access, which is the kind of distinction an LSM policy needs and the traditional mode bits cannot express.

The second thing is that on some filesystems the last component is not looked up, created and opened as three separate operations. A network filesystem that did so would pay three round trips and still not be atomic. So the VFS offers atomic_open, a method that is handed the parent directory, the name, and the open flags, and is asked to do whatever combination of lookup, creation and opening it can manage in one exchange. It reports back through finish_open() if it opened the file, or finish_no_open() if it only resolved the name and wants the VFS to continue in the ordinary way. Filesystems that gain nothing from this simply do not implement the method. The pattern is the same narrow-waist bargain the chapter began with: the VFS defines the sequence, and offers an optional escape hatch for filesystems that can do better than the sequence allows.

Reading and Writing with iov_iter

read() enters ksys_read(), which fetches the file with fdget_pos(), reads the current offset if the file is seekable, and calls vfs_read(); write() takes the analogous path through vfs_write(). The fdget_pos() step is what serializes the shared offset: if the file has FMODE_ATOMIC_POS (a normal seekable file that may be shared), fdget_pos() takes f_pos_lock so that two threads issuing read() on the same open file description cannot interleave and corrupt f_pos. It is released by fdput_pos() when the call returns.

vfs_read() and vfs_write() do the generic gatekeeping before any filesystem code runs: they confirm the file was opened in the right mode (FMODE_READ/FMODE_WRITE), check the user buffer, and call rw_verify_area(), which validates the offset/length range and invokes the security_file_permission() LSM hook. They then prefer the iterator method: new_sync_read() builds a synchronous kiocb and wraps the single user buffer in a one-segment iov_iter (tagged ITER_DEST for a read, ITER_SOURCE for a write) and calls filp->f_op->read_iter(). The legacy read/write callbacks are only a fallback for filesystems that have not been converted.

struct iov_iter is the unifying abstraction that makes this work. One iterator can describe a single user buffer (ITER_UBUF), a user iovec array (ITER_IOVEC), an in-kernel vector (ITER_KVEC), a page-backed block vector (ITER_BVEC), or an xarray range. The filesystem never inspects which kind it is; it just copies or maps bytes and calls iov_iter_advance(), and the iterator hides whether the destination is user memory, kernel memory, or page cache. That is precisely why the same read_iter implementation serves read(), readv(), preadv2(), splice, and many in-kernel data paths without special-casing any of them. 

static ssize_t new_sync_read(struct file *filp, char __user *buf,

{

The kiocb is where per-call behaviour lives, and it is the reason preadv2() and pwritev2() exist at all. Their predecessors could only be modified through f_flags, which belongs to the open file description and is therefore shared by every thread and every descriptor derived from it; changing it to make one write synchronous changes it for everybody. The flags argument added by the v2 calls applies to a single operation, and kiocb_set_rw_flags() translates it into IOCB_* bits on the kiocb that carries just that one request.

The translation is a masked copy rather than a switch, because the IOCB_* constants are literally defined as the corresponding RWF_* values, and the flags the kernel keeps to itself begin at bit 16 where no userspace flag can reach. A BUILD_BUG_ON asserts that the two sets do not overlap, so the arrangement cannot be broken silently by adding a flag. It is a small thing, but it is the difference between a translation layer that must be maintained and one that cannot drift.

Several of these flags are refused rather than ignored when the target cannot honour them, which matters more than it sounds. RWF_NOWAIT requires FMODE_NOWAIT on the file, RWF_ATOMIC requires a write to a file whose filesystem advertises FMODE_CAN_ATOMIC_WRITE, and RWF_DONTCACHE requires FOP_DONTCACHE and rejects DAX mappings. Each unsupported case returns -EOPNOTSUPP. A caller asking for a non-blocking or atomic write is making an assumption its correctness depends on, so silently downgrading the request would be worse than refusing it—the same reasoning that makes RESOLVE_CACHED return -EAGAIN rather than quietly blocking. Asking for RWF_APPEND and RWF_NOAPPEND together is -EINVAL, since the pair exists precisely so that a single write can override the file's O_APPEND setting in either direction. Closing a File

Closing a descriptor separates two actions: removing the descriptor-table entry and dropping the file reference. close_fd() takes file_lock, plucks the struct file * out of the fdtable slot and clears the bitmaps with file_close_fd_locked(), then calls filp_close(), which runs the filesystem flush method and calls fput(). From userspace the descriptor number is free for reuse the instant close() returns, even though the file's final teardown may still be pending.

fput() is deliberately lightweight at the call site: it just releases one reference, and only when that was the last one does it hand the real work to __fput_deferred(). The last-reference teardown is heavy—it may run the filesystem release method, flush writeback, drop POSIX locks and leases, tear down fsnotify marks, and release the module and mount references—and much of it can sleep or take locks, so it must not run deep inside an arbitrary syscall. For a normal task, __fput_deferred() queues ____fput() as task work that runs at the safe boundary when the task returns to userspace; for kernel threads and interrupt context, where there is no such boundary, it falls back to the delayed_fput workqueue.

The reference count itself is no longer a plain atomic_long_t. struct file carries a file_ref_t, a counter biased so that zero means one reference: FILE_REF_ONEREF is 0, and the values below it, reached by decrementing past the last reference, form labelled dead and saturation zones rather than wrapping. The point of the bias is that the common operations become a plain decrement whose sign tells the caller what happened, with no compare-and-swap loop in the fast path, and an over- or under-count lands in a zone that can be recognised and reported instead of corrupting memory.

Closing a descriptor gets its own entry point for a related reason. fput_close() first tests for exactly one outstanding reference and, in that case, swaps the counter straight to FILE_REF_DEAD—which is the overwhelmingly common case, since most files are opened, used and closed by one thread that shares them with nobody. Only when the guess is wrong does it fall back to the general file_ref_put(). The close path is the hottest place in the kernel where a file's last reference is dropped, so it is worth a specialization that the generic fput() cannot make.

The split between flush and release follows from all this and is easy to get backwards. filp_close() calls filp_flush(), which invokes the filesystem's flush method, on every close()—once per descriptor, even when other descriptors for the same file remain open—which is why close() can report a writeback error that a previous write() returned success for. The release method runs from __fput(), once, when the final reference goes away, and may run long after the close() that triggered it. One is a per-descriptor notification; the other is the object's destructor.

Descriptor lifetime and file lifetime are therefore related but distinct. dup(), a fork() that shares the files table, passing a file over a socket with SCM_RIGHTS, registering it with epoll, and in-kernel references can all keep the struct file alive after one descriptor is closed. Conversely, closing the last descriptor does not necessarily free the memory immediately, because deferred fput processing (or RCU protecting a concurrent lockless fdget()) may still hold it. The descriptor is an index; the file is the reference-counted object it points to.

copy_file_range, sendfile, and splice

Linux provides several ways to move bytes without forcing userspace to bounce data through its own buffers, and all of them are VFS operations rather than filesystem-private tricks. sendfile() moves data from a file to another descriptor—historically a socket, which is how web servers stream files to the network without a user-space copy. splice() moves data between a pipe and a file (or between two pipes), using the pipe as an in-kernel conduit. copy_file_range() asks the kernel or filesystem to copy bytes directly between two files, potentially without moving the data at all.

The VFS mediates these paths because permissions, current offsets, append semantics, file-type restrictions, and per-filesystem capabilities still have to be enforced. Accordingly, file_operations carries dedicated methods—splice_read, splice_write, copy_file_range, and remap_file_range. The last two enable the real optimization: a filesystem that can share disk extents (a reflink, as on Btrfs or XFS) or offload the copy to a server (as with NFS or SMB server-side copy) implements copy_file_range/remap_file_range and completes a whole-file copy by manipulating metadata instead of reading and rewriting every block.

vfs_copy_file_range() tries three things in order, and the order is the interesting part. A filesystem's own copy_file_range is preferred, because it is the only one of the three that can offload the work to a server. Failing that, and only when both files live on the same superblock, remap_file_range is tried, which is the reflink path: the two files are made to share the same extents on disk, so the copy costs a metadata update and nothing else. If the remap returns zero or an error the code does not give up but sets splice and continues, because a filesystem may be able to share some ranges and not others. Only then does the generic splice-based copy run, which still avoids the userspace round trip but does move the data.

That last fallback is narrower than it looks. It is taken only for files on the same superblock, and the comment says why in three words: backward compatibility. A cross-filesystem copy_file_range() with no method to serve it is -EXDEV, and userspace is expected to fall back to reading and writing itself. The cross-filesystem rule has one deliberate exception that repays reading, since it explains an otherwise baffling comparison in the source. Two files on different superblocks are permitted if their copy_file_range pointers are the same function. NFS and SMB register several file_system_type structures and several sets of file_operations, but all of them share one copy implementation, so pointer equality is a cheap and exact test for the question actually being asked: were these two files produced by the same driver? Comparing superblocks would answer a narrower question and refuse server-side copies that work perfectly well.

These calls are also the clearest justification for the iterator-based model. A pipe buffer, a page vector, an xarray range, and a user iovec are all just different carriers of bytes, but the VFS wants one place that applies offset, permission, and accounting logic to all of them. The iov_iter and kiocb abstractions provide exactly that common seam, so this logic is written once in the VFS rather than re-implemented—and re-broken—in every filesystem.

Extended Attributes and File Notification

Two VFS facilities sit beside the main path of open(), read(), and write() rather than on it. Extended attributes attach named values to an inode beyond the fixed fields that stat() reports. They carry security labels, POSIX ACLs, file capabilities, and arbitrary user metadata. fsnotify lets an observer learn that VFS operations happened — or, for fanotify, approve them before they happen. Both are generic layers with many back ends or front ends, and both have grown well beyond what Linux 2.6.11 offered; that kernel predates even inotify, which arrived in 2.6.13.

Extended Attributes

An extended attribute is a name/value pair attached to an inode. The name is a string with a namespace prefix; the value is an opaque byte string. Four prefixes are defined for general use, and the VFS applies a different access policy to each in xattr_permission(). user. attributes are governed by the file's ordinary permission bits. They are allowed only on regular files and directories, because the permission bits of a device node or symlink say nothing about who may annotate it. In a sticky directory, only the owner may write them. trusted. attributes require CAP_SYS_ADMIN; to anyone else they are invisible, and a read fails with ENODATA as if they did not exist. security. and system. are left entirely to the LSM and the filesystem: SELinux labels and file capabilities live in the first, POSIX ACLs in the second. Every write is also refused on an immutable or append-only inode, and on an idmapped mount where the inode's owner has no mapping.

The system-call family is a four-by-four grid, shown in Table 12-33. There are four operations — set, get, list, and remove — and four ways to name the file: by path following symlinks, by path not following them (the l forms), by descriptor (the f forms), and since 6.13 relative to a directory descriptor (the *at forms). The *at calls take AT_SYMLINK_NOFOLLOW and AT_EMPTY_PATH, so each of them subsumes all three older variants. POSIX ACLs are xattrs only at the system-call boundary. Individual filesystems are often stricter; on ext4, for example, all of a file's attributes together must fit in one block plus the in-inode area.

fsnotify: dnotify, inotify, and fanotify

Linux 2.6.11 had one notification interface, dnotify. A process called fcntl(fd, F_NOTIFY, mask) on an open directory and received a signal when something in it changed — without being told what changed, and only by holding the directory open. inotify (2.6.13) replaced the signal with a descriptor: watches on individual files or directories, events read as records that carry the affected name. In 2.6.31 both were rebuilt on a common back end, fsnotify (fs/notify/), and fanotify (2.6.37) became the third front end on top of it. All three share one set of VFS hooks and one data model.

The hooks are inline functions in include/linux/fsnotify.h, called at the points where VFS operations complete. fsnotify_access() and fsnotify_modify() are called from the read and write paths in fs/read_write.c; fsnotify_open() and fsnotify_close() from open and the final fput(); fsnotify_create(), fsnotify_mkdir(), fsnotify_unlink(), fsnotify_link(), and fsnotify_move() from the namespace operations; fsnotify_change() after setattr; and fsnotify_xattr() from the code above. These calls run on every write of every file, so the cost when nobody is watching is what matters. The first test, in fsnotify_parent(), is fsnotify_sb_has_watchers(), a single read from the superblock. On a filesystem with no watchers at all, that test is the whole cost.

Past that test, the data model is three objects, shown in Figure 12-6. A struct fsnotify_group is one listener — one inotify or fanotify descriptor. It holds the queue of events not yet read (notification_list), its limit max_events, a preallocated overflow_event, the front end's fsnotify_ops, and a priority. A struct fsnotify_mark is one group's interest in one object: an event mask, an ignore mask, and a pointer back to the group. Each mark is on two lists, the group's marks_list and the watched object's mark list. That object-side list hangs from a struct fsnotify_mark_connector, which can be attached to four kinds of object, each with a typed slot of its own: inode->i_fsnotify_marks, mount->mnt_fsnotify_marks, the superblock's sb_marks, and since 6.15 a mount namespace's n_fsnotify_marks.

Every watched object also caches the OR of its marks' masks (i_fsnotify_mask, mnt_fsnotify_mask, s_fsnotify_mask, n_fsnotify_mask), and fsnotify() uses those masks for its second fast exit. It collects the inode, the parent directory (for an event on a child), the mount, the superblock, and the mount namespace involved in the event. If none of them has a mark list it returns at once, and if the event bit is in none of their masks it returns too. Only then does it enter an SRCU read section on fsnotify_mark_srcu and walk the lists. The walk is not a simple concatenation. fsnotify_iter_select_report_types() steps through all the lists together in group-priority order, so that a group with marks on both an inode and its mount gets the event once, and so that an inode mark's ignore mask can suppress an event that the same group's mount mark would otherwise report. That is mark B's role in Figure 12-6. For each group selected, send_to_group() calls the front end's handle_event or handle_inode_event method.

Events on a file are also reported to a watching parent directory, which is how a watch on a directory sees writes to the files inside it. To keep that cheap, a directory with such a watch sets DCACHE_FSNOTIFY_PARENT_WATCHED on its children's dentries, so fsnotify_parent() climbs to the parent only when the flag says someone there is listening. Queued events go through fsnotify_insert_event(). It first offers the new event to the front end's merge callback, which can coalesce it with an identical queued event: inotify compares against the last event, and fanotify searches a hash of recent ones. When the queue already holds max_events, the group's preallocated overflow event (IN_Q_OVERFLOW or FAN_Q_OVERFLOW) is queued instead, once. Events are lost under pressure, but the listener is always told that they were.

The inotify interface is three calls. inotify_init1(flags) returns a descriptor for a new group. inotify_add_watch(fd, path, mask) places an inode mark and returns a watch descriptor; the inotify_rm_watch() call removes it. read() on the group descriptor returns a sequence of struct inotify_event records, each carrying the watch descriptor, the event mask, a cookie that pairs IN_MOVED_FROM with IN_MOVED_TO, and the affected name if the event came from a watched directory. Inotify can watch only inodes, and each watch pins its inode in memory, so watches are a per-user resource. /proc/sys/fs/inotify/max_user_watches defaults to about 1% of low memory divided by the cost of one watch, clamped to between 8192 and 1048576. max_user_instances defaults to 128, and max_queued_events, the per-group queue limit, to 16384.

Fanotify was designed for a different user: an anti-malware scanner, an indexer, or a hierarchical storage manager that must see every file on a mount and may need to rule on access. fanotify_init(flags, event_f_flags) creates the group. fanotify_mark(fd, flags, mask, dirfd, path) places a mark whose scope is chosen by FAN_MARK_INODE, FAN_MARK_MOUNT, FAN_MARK_FILESYSTEM, or — since 6.15, with mount attach and detach events — FAN_MARK_MNTNS. In the classic mode, each event read from the descriptor carries an open file descriptor for the object instead of a name. The kernel opens it with dentry_open_nonotify(), which sets FMODE_NONOTIFY so that the listener's own reads of the file do not generate more events. That design cannot describe directory-entry events such as create or rename, so 5.1 added FAN_REPORT_FID and 5.9 FAN_REPORT_DFID_NAME, which report file handles and names instead of descriptors. Later releases added FAN_REPORT_PIDFD (5.15), FAN_FS_ERROR (5.16), and FAN_RENAME (5.17). FID reporting is also what made fanotify safe to open to unprivileged users in 5.13. Without CAP_SYS_ADMIN, a process may create only a notification-class group that reports FIDs and may place only inode marks.

Permission events are the feature that no other notification interface has. A group created with FAN_CLASS_CONTENT or FAN_CLASS_PRE_CONTENT (both privileged) can ask for FAN_OPEN_PERM, FAN_OPEN_EXEC_PERM, and FAN_ACCESS_PERM. A pre-content group can also ask, since 6.14, for FAN_PRE_ACCESS, which is raised before a range of a file is read, written, mapped, or truncated on a filesystem that opts in with SB_I_ALLOW_HSM, so that a storage manager can fill in content that has not been fetched yet. The task performing the operation queues the event and then sleeps in fanotify_get_response(), in a killable, freezable wait, until the listener writes a struct fanotify_response naming the event's descriptor and FAN_ALLOW or FAN_DENY. A deny fails the operation with EPERM, or with a custom errno for pre-content events. Groups are ordered by priority — FSNOTIFY_PRIO_PRE_CONTENT, then FSNOTIFY_PRIO_CONTENT, then ordinary listeners — so the storage manager supplies the data before the scanner inspects it. This blocking is why a filesystem whose methods cannot safely wait on a userspace listener sets FS_DISALLOW_NOTIFY_PERM, as Section 1.1 noted. To keep the cost off read and write, fsnotify_open_perm_and_set_mode() checks at open time whether the superblock has any permission watchers and records the answer in the file's FMODE_NONOTIFY* bits. File Locking

File locking lets cooperating processes coordinate access to a file's contents, and on Linux it is advisory: a lock only has effect on processes that also check for it, never on a process that simply reads or writes. This is worth stating flatly, because Linux 2.6 offered advisory locking as the default and mandatory locking — where the kernel itself refuses a conflicting read() or write() — as a second mode available with a mount option. In 7.0.12 there is no second mode. The enforcement code has been deleted, and what remains is only its skeleton: the mand mount option is still parsed into SB_MANDLOCK and still printed in /proc/mounts, and IS_MANDLOCK() is still defined in include/linux/fs.h — with no callers anywhere in the tree. A filesystem can therefore still be mounted mand, still report itself as mounted mand, and enforce nothing. The kernel is at least candid about it at mount time: path_mount() and the fsconfig() path both call warn_mandlock(), whose boxed message says the option “has been deprecated and is ignored by this kernel.” The complication the VFS must manage is that "a lock" is not one thing—Linux supports four distinct lock families with different ownership and conflict rules: POSIX byte-range locks (fcntl), BSD whole-file locks (flock), leases, and the modern open file description (OFD) locks. Linux 7.0.12 keeps all of this in a single per-inode file_lock_context.

This is a substantial update from Linux 2.6's single inode->i_flock list. The inode now holds an i_flctx pointer, installed lazily by locks_get_lock_context() so that inodes which are never locked pay nothing. The context holds three separate lists—one per family class—which keeps families with incompatible ownership rules from being tangled together on a single list, as Figure 12-7 shows.

A second modernization is in the lock object itself. What used to be one fat struct file_lock is now split around a shared struct file_lock_core (the owner, flags, type, pid, blocker and blocked-request lists, wait queue, and file). Byte-range and whole-file locks embed that core in struct file_lock and add a fl_start/fl_end range; leases embed the same core in a distinct struct file_lease with lease-break timers. The split makes the "a lease is not a byte-range lock" distinction explicit in the type system rather than by convention.

The file_lock_context

struct file_lock_context is allocated only when an inode first needs locking state, by locks_get_lock_context(). That lazy installation matters at scale: a system may hold millions of cached inodes, and the overwhelming majority never take an advisory lock, so embedding the lists unconditionally would waste memory on every one of them. The context is guarded by its own flc_lock spinlock and carries three lists: flc_flock, flc_posix, and flc_lease.

The struct file_lock/struct file_lease objects on those lists record, through their shared file_lock_core, the owner, type (F_RDLCK/F_WRLCK/F_UNLCK), owning pid, file, wait queue, and the blocker/blocked-request relationships used to build the dependency graph for blocking waits. Two callback tables let filesystems hook in: fl_ops for filesystem-private setup and teardown, and fl_lmops for a lock manager—the seam through which NFS, AFS, and Ceph project locks onto a server. The generic VFS layer still owns the system-call semantics: how a request maps to list insertion, conflict testing, blocking, waking, and close-time cleanup.

Splitting the state into three lists is easier to reason about than the old inode-wide list precisely because each family obeys different rules. BSD flock locks are whole-file and tied to the open file description. POSIX locks are byte ranges owned by a (process, inode) pair. OFD locks are byte ranges too, but owned by the open file description. Leases are not exclusion locks at all but notification promises. };

struct file_lock_context {
        spinlock_t       flc_lock;
        struct list_head flc_flock;     /* BSD flock() locks */
        struct list_head flc_posix;     /* POSIX and OFD byte-range locks */
        struct list_head flc_lease;     /* leases (struct file_lease) */
};

Which family a lock belongs to is not recorded as an enumerated type but as a bit in flc_flags, and the same word carries request modifiers alongside the family bit. This is worth pausing on, because it explains how one set of routines serves several user-visible interfaces. A request is not dispatched by its origin; it is dispatched by its flags. FL_POSIX and FL_FLOCK select the family, FL_OFDLCK changes only whose identity counts as the owner, FL_SLEEP distinguishes F_SETLKW from F_SETLK, and FL_CLOSE marks a request the VFS generated on the close path rather than one a process asked for. The per-inode context is not the only place locks are recorded. Every lock is also threaded onto a global list through flc_link, and because a single global list would be a contention point on a large machine, that list is per-CPU: locks_insert_global_locks() adds the lock to the current CPU's list and remembers which one in flc_link_cpu so the removal can find it again. Blocked requests are additionally indexed in a hash, blocked_hash, keyed by owner. These structures exist for two consumers. One is /proc/locks, which walks the per-CPU lists to report every lock on the system — family, mode, holder pid, device and inode number, and byte range — and is the first thing to look at when two programs are fighting over a file. The other is deadlock detection, which needs to ask which lock a given owner is currently waiting for; that question is answered by the hash rather than by searching. It is a small but telling detail that /proc/locks now prints the word ADVISORY for every POSIX and flock entry: the field once distinguished advisory from mandatory, and the string MANDATORY no longer appears in fs/locks.c at all.

POSIX (fcntl) Locks

POSIX locks are byte-range locks set through fcntl() with F_SETLK (non-blocking), F_SETLKW (blocking wait), and queried with F_GETLK. Each lock covers an arbitrary [start, len) range of the file and is a read (shared) lock, a write (exclusive) lock, or an unlock. F_SETLKW blocks until the conflicting lock is released or a signal interrupts the wait, in which case the call returns -EINTR. A read lock is compatible with other read locks on the same range but conflicts with a write lock; two write locks always conflict.

Their ownership rule is the famous POSIX pitfall: a classic POSIX lock is owned by the (process, inode) pair, not by the file descriptor that created it. Two consequences follow, and both bite real programs. First, closing any descriptor the process holds for that inode drops all of the process's POSIX locks on it—so a library that opens a file, locks it, and closes its own descriptor silently releases locks another part of the program is relying on. Second, locks are not shared across a fork() and do not accumulate by reference. Linux preserves this behavior for standards compliance, which is exactly why the VFS close path must run POSIX lock cleanup for the inode even when the descriptor being closed never took a lock.

That cleanup is worth seeing, because it shows the rule being implemented rather than merely asserted. locks_remove_posix() does not walk the list picking out the locks this descriptor created — it cannot, because a POSIX lock does not remember which descriptor created it. Instead it builds an unlock request covering the entire file and pushes it through the ordinary locking path. 

void locks_remove_posix(struct file *filp, fl_owner_t owner)
{
        ...
        ctx = locks_inode_context(inode);
        if (!ctx || list_empty(&ctx->flc_posix))
                return;

        locks_init_lock(&lock);
        lock.c.flc_type = F_UNLCK;
        lock.c.flc_flags = FL_POSIX | FL_CLOSE;
        lock.fl_start = 0;
        lock.fl_end = OFFSET_MAX;
        lock.c.flc_owner = owner;
        lock.c.flc_pid = current->tgid;
        lock.c.flc_file = filp;
        lock.fl_ops = NULL;
        lock.fl_lmops = NULL;

        error = vfs_lock_file(filp, F_SETLK, &lock, NULL);
        ...
}

The range [0, OFFSET_MAX] is the whole file, and the owner is the process's files_struct, so the request means precisely “release every POSIX lock this process holds on this inode” — which is the surprising POSIX rule, expressed as one ordinary unlock. Two details follow from this. The function returns immediately if the inode has no context or an empty flc_posix list, so the overwhelming majority of closes, which involve no locks at all, cost one pointer test. And the FL_CLOSE bit tells a network filesystem's lock manager that this unlock came from the close path, which matters because such an unlock must not be allowed to fail and leave the server holding state the client has forgotten about.

The caller is filp_flush(), the same function the previous section described as running on every close() rather than only on the last one — and that is exactly the behavior the POSIX rule requires, since the locks must go away when any of the process's descriptors for the inode is closed, not when the last one is. The one exception is a descriptor opened with O_PATH: filp_flush() skips both dnotify_flush() and locks_remove_posix() when FMODE_PATH is set, because such a descriptor refers to a location rather than to opened file contents and was never able to take a lock.

The generic helper posix_lock_file() implements the range algebra: it tests for conflicts across the flc_posix list, merges adjacent compatible locks held by the same owner, splits a range when an unlock or a different-type lock covers only part of it, and queues blocked waiters on the dependency graph. The graph itself is built from the file_lock_core fields shown earlier: a blocked request points at what it is waiting for through flc_blocker and hangs off that blocker's flc_blocked_requests list through flc_blocked_member. Filesystems that need remote coordination plug in through fl_lmops, but the user-visible semantics are defined by this VFS layer.

posix_locks_deadlock() walks that graph before any process is put to sleep, rejecting a request that would close a cycle with -EDEADLK rather than letting it hang. It is worth being precise about how much this guarantee is worth, because it is easy to over-read. The walk follows the chain of waiters from the prospective blocker, asking at each step which lock that owner is itself waiting for, and stops with a positive answer if it arrives back at the caller. But it gives up after MAX_DEADLK_ITERATIONS, which is ten, and returns “no deadlock.” The bound is deliberate: the argument that the chain must be finite assumes every waiter is a distinct owner making one request at a time, and that assumption fails for a misbehaving NFS client or for threads sharing one file table. So the detector is a best-effort courtesy that catches the simple mutual-wait mistakes programs actually make, not a proof of freedom from deadlock. A program that deadlocks past ten hops deadlocks.

BSD flock Locks

BSD locks are whole-file locks requested through the flock() syscall, in shared (LOCK_SH) or exclusive (LOCK_EX) mode, released with LOCK_UN, and made non-blocking by adding LOCK_NB, which turns a wait into -EWOULDBLOCK. Their defining property is that a flock lock belongs to the open file description, not the process and not the descriptor number. This is what makes their semantics more intuitive than POSIX locks: because dup() and a shared-table fork() produce descriptors that refer to the same open file description, they all share one flock lock, and the lock is released only when the last of those descriptors is closed—not when any one of them is.

The VFS routes these through flock_lock_inode(), or the filesystem's flock file operation when it provides one (network filesystems use this to reach a server). Because flock locks are whole-file, they need none of the range-splitting and merging machinery POSIX locks require; a request either converts the description's existing mode or waits. They still conflict with other flock locks by the shared/exclusive rule and must wake blocked waiters when released or downgraded.

A common source of bugs is assuming POSIX and BSD locks interact. On Linux they occupy separate lists and, on local filesystems, do not block each other—a POSIX write lock and an exclusive flock can coexist on the same bytes. (Some network filesystems emulate one in terms of the other, so the interaction is filesystem-dependent.) Portable programs should therefore pick one family per file rather than mixing them and expecting mutual exclusion.

flock() also carries the clearest trace of the removal of mandatory locking. There was once a LOCK_MAND mode, and the constant is still defined in include/uapi/asm-generic/fcntl.h because removing a UAPI value would break compilation of programs that merely mention it. The implementation is gone. A request carrying LOCK_MAND is now recognized at the top of the syscall, logged once with a warning, and succeeds without doing anything — flock() returns 0 and no lock exists. Returning success for an unimplemented request looks indefensible until you read the reasoning in the source: LOCK_MAND locks had been broken for years, never conflicting with one another and never preventing any open, read, or write, so programs using them had always been getting nothing while being told they had succeeded. Returning an error now would break those programs without making them any safer. The behavior is preserved deliberately, and the warning exists to tell the operator what the program does not know. It is a good illustration of a rule that governs a great deal of kernel change: the interface that must not break is the one user space actually observed, not the one that was documented.

Leases

A lease is a different kind of promise: the kernel guarantees to notify a lease holder before another process performs an operation that would break the holder's assumptions about the file. Userspace requests one with fcntl(F_SETLEASE) passing F_RDLCK (read lease), F_WRLCK (write lease), or F_UNLCK. A read lease can be held while no one is writing; a write lease requires the holder be the only one with the file open. When another process then opens the file (for a read lease, opens it for writing; for a write lease, opens it at all) or truncates it, the kernel signals the holder—by default SIGIO—and starts a timer (lease_break_time, default 45s). The conflicting operation is held until the holder downgrades or releases the lease, or the timer expires and the kernel breaks the lease forcibly.

This makes leases the building block for coherent caching by a user-space server. Samba uses them to implement SMB oplocks/leases, and the kernel's own NFS server uses them for delegations: a client can cache a file's contents locally and trust the cache because it will be told the moment another node wants to change it. The lease is about notification and cache invalidation, not indefinite exclusion. Filesystems participate through the setlease file operation, and lease managers hook the break path through lock_manager_operations.

Leases live on the flc_lease list as struct file_lease objects, kept separate from POSIX and flock locks because their break mechanics are unique: a break may deliver a signal, wait for acknowledgement within the grace period, and only then let the conflicting open or truncate proceed—an interaction no byte-range lock has. The dedicated file_lease type (with its fl_break_time/fl_downgrade_time fields) is what the 7.0.12 file_lock_core split introduced to model this cleanly.

The question the description above leaves open is how a conflicting operation ever reaches the lease code, since nothing in open() or truncate() looks like locking. The answer is break_lease(), and there are only two call sites in the core VFS. do_dentry_open() calls break_lease(file_inode(f), f->f_flags) just before it invokes the filesystem's open method, and do_truncate() calls break_lease(inode, O_WRONLY) before shortening the file. Both sit on paths the previous section walked through without the lease step being visible, and both can fail, which is the part worth noticing: an open() can block for the lease-break period and can return an error because of a lease held by an entirely different process. When do_dentry_open()'s call fails it jumps to the same cleanup label as every other failure there, so the scope guard described in the previous section releases the descriptor and the file.

break_lease() is written to cost as close to nothing as possible on the enormous majority of opens, where no lease exists. It reads i_flctx, returns immediately if there is none, and otherwise tests flc_lease with list_empty_careful() — taking no lock at all in the common case. The smp_mb() between the two is not decoration: the check is lockless, so the barrier orders the reference the caller has already taken against the read of the lease list, without which the open could race with a setlease() installing a lease it should have broken. Only when the list is non-empty does __break_lease() run and take the locks. The open access mode is translated into LEASE_BREAK_OPEN_RDONLY and LEASE_BREAK_NONBLOCK, so a read-only open breaks only a write lease, and an O_NONBLOCK open declines to wait out the grace period and fails instead.

Delegations are the same mechanism with a different caller and one extra complication. An NFSv4 delegation is a lease carrying FL_DELEG, and it must be broken not only by opens and truncates but by operations that change a file's metadata or its name: unlink, rename, setattr, and the extended-attribute and POSIX-ACL paths all break delegations. Those callers cannot simply wait, because they reach the break while holding i_rwsem on a directory, and sleeping there for up to the lease-break time would block every other lookup and creation in that directory. The kernel therefore uses a drop-and-retry dance: try_break_deleg() attempts a non-blocking break, and if it returns -EWOULDBLOCK it pins the inode with ihold() and hands it back through a struct delegated_inode. The caller unwinds and releases its locks, calls break_deleg_wait() outside them — which waits, drops the reference, and clears the field — and then retries the whole operation from the beginning. The extra inode reference is what makes the retry safe: the inode cannot be freed in the window when no lock is held. This is the standard shape for “I must sleep but I am holding a lock I must not sleep under,” and it is why unlink() on a delegated file can legitimately do its pathname walk twice.

Open File Description Locks

Open file description locks are the modern fix for the worst of the POSIX lock semantics. They are requested through fcntl() with F_OFD_SETLK, F_OFD_SETLKW, and F_OFD_GETLK. Like POSIX locks they are byte-range locks and use the same range algebra; unlike POSIX locks they are owned by the open file description—identified by the struct file—rather than by the process.

That single change of owner removes both POSIX foot-guns. Because the owner is the open file description, an OFD lock is shared across a fork() when the child inherits the same description, and it is not released by closing some unrelated descriptor for the same inode—only when the last reference to that open file description goes away (or it is explicitly unlocked). It also means two threads that each open() the file get independent descriptions and can hold their own OFD locks without clobbering each other. This is what makes OFD locks the right choice for multithreaded programs and for libraries that must not interfere with the rest of the process.

Internally, OFD locks are stored on the same flc_posix list as POSIX locks, because their conflict and range mechanics are identical. Only the owner identity differs: conflict testing and release compare the owning struct file instead of the (process, inode) pair. This is a recurring VFS design move—reuse the generic machinery wherever the shape is the same, and make ownership an explicit field so the semantics stay correct.

The reuse is cheaper than it sounds, because the comparison the generic code performs is not a structured test but a single pointer equality: posix_same_owner() returns fl1->flc_owner == fl2->flc_owner and nothing more. fl_owner_t is an opaque pointer, so making a lock an OFD lock is simply a matter of storing the struct file in flc_owner instead of the files_struct, and setting FL_OFDLCK so the rest of the kernel can tell which kind of token it is looking at. Everything else — merging, splitting, conflict detection, waking waiters — is untouched. The close path reuses itself in the same way: locks_remove_file() releases a description's OFD locks by calling the very function shown earlier, as locks_remove_posix(filp, filp), passing the file as its own owner token.

One consequence of that choice is a genuine loss, and it deserves stating alongside the gains. Because an OFD lock's owner is a file rather than anything tied to a thread of execution, the question the deadlock detector asks — which lock is this owner waiting for? — has no well-defined answer, and posix_locks_deadlock() therefore returns false immediately for any request carrying FL_OFDLCK. Two processes that block on each other's OFD locks are not rescued with -EDEADLK; they simply hang. The trade is deliberate and, for the programs OFD locks were designed for, sound: the detector was never reliable past ten hops anyway, and a multithreaded program that could not use POSIX locks correctly in the first place gains more from safe ownership than from a partial deadlock check. But a program moving from F_SETLKW to F_OFD_SETLKW should know it has given up its last automatic warning. Table 12-37 contrasts all four families.

Summary

The Linux 7.0.12 VFS keeps the elegant shape of the classic common file model while replacing many of its 2.6-era implementation assumptions. Superblocks, inodes, dentries, and files still provide the common vocabulary. What changed is the concurrency architecture around them: RCU, lockref, fdtable indirection, sequence counters, per-superblock reclaim lists, and deferred file cleanup are now ordinary parts of the design.

Mounting is no longer just mount(2) calling a filesystem-specific superblock helper. The fd-based mount API exposes fs_context, detached mounts, subtree file descriptors, idmapped mounts, and attribute updates. Pathname lookup is no longer a lock-heavy recursive walk. It is an optimistic RCU state machine that can unlazy into a conservative referenced walk. File I/O is no longer primarily a pair of byte-buffer methods. It is iterator-based and integrated with modern zero-copy and async interfaces. File locking is no longer one list on the inode; it is a lazily allocated per-inode context holding three lists, one per family, with ownership made an explicit field so that the same range algebra can serve both process-owned POSIX locks and description-owned OFD locks.

The pseudo filesystems that make up much of the kernel's userspace API have converged on a few shared mechanisms. Text files are produced by the seq_file record iterator rather than by page-filling callbacks. Procfs entries use struct proc_ops, and sysctls use const ctl_table arrays reached only through /proc/sys. Debugfs and tracefs build on libfs and keep their dentries as the filesystem, while kernfs keeps a tree of its own. Each guards against a file being removed while it is open by counting the callers inside its methods and waiting them out. Beside the main I/O path, extended attributes gained the *xattrat calls and lost POSIX ACL parsing to the VFS, and file notification grew from dnotify's signals into the fsnotify back end. There, inotify and fanotify share marks on inodes, mounts, superblocks, and mount namespaces, and fanotify can hold an access until a listener rules on it.

A theme that runs through the chapter and is easy to overlook is how much has been removed. The global dcache_lock is gone. The remount_fs superblock method is no longer how a remount is driven. The get_sb_* helpers have been replaced wholesale by fs_context. LOOKUP_JUMPED no longer exists as a lookup flag, its bit having moved to a separate state word. Mandatory locking has been deleted outright. Removals matter to a reader for a reason additions do not: the code that remains often keeps the shape of what it replaced, so a name that survives may no longer mean what it once did. The clearest example in this chapter is the mand mount option, which is still parsed, still stored in the superblock flags, and still printed in /proc/mounts, while enforcing nothing at all. When reading VFS code against older documentation, the dangerous cases are not the mechanisms that were renamed but the ones that were hollowed out.

The most important habit for reading modern VFS code is to ask which lifetime proof is active. Is this pointer protected by RCU, by a refcount, by a sequence counter, by a namespace lock, by an inode semaphore, by a mount writer count, or by descriptor-table locking? The VFS remains Linux’s promise that “everything is a file” can be useful without being simplistic. It gives user programs one descriptor and pathname model, while allowing filesystems, devices, memory objects, network clients, and kernel pseudo files to implement only the methods they actually need. Understanding that contract is the foundation for the storage, namespace, and I/O chapters that follow.
