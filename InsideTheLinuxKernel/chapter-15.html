Chapter 14 followed a block transfer from the filesystem down to the disk and noted, repeatedly, that most accesses never reach the device at all. This chapter is about the layer that makes that true: the page cache, the kernel's main in-memory cache of disk data. Nearly every read and write a process performs passes through it, and the kernel's overall I/O performance depends more on the page cache than on any single device driver. The chapter builds the page cache from its central object—the address_space—up through the units it caches (folios), the structure that indexes it (the XArray), the paths that read and write it, the buffer heads and iomap that map it to disk blocks, the writeback machinery and the sync family of system calls that push its dirty contents back to storage, and finally the truncation, invalidation, and reclaim that remove folios from it again. The organization follows the life of a cached folio: what holds it, what it is, how it is found, how it is filled and dirtied, how it maps to disk, how it is written back, and how it leaves.

Two changes since Linux 2.6 dominate this chapter and are worth flagging at the outset. The cache is no longer indexed by a radix tree but by the XArray, and it no longer caches bare pages but folios. Both are described in detail below; wherever 2.6-era code and documentation say "radix tree" read "XArray," and wherever they say "a page in the cache" read "a folio."

The Role of the Page Cache

The page cache exists because storage is slow and access to it is repetitive. When a process reads a file, the kernel keeps the data it fetched in memory; a later read of the same bytes—by the same process or another—is served from RAM without touching the disk. When a process writes, the kernel usually stores the new data in memory and marks it dirty, deferring the slow disk update. This section frames why the cache pays off, what it holds, and the unit it now works in.

Before the details, it helps to see the page cache as a subsystem rather than a single data structure. Figure 15-1 gives that architectural view. At its center is the cached data itself—folios held in each address_space's XArray—surrounded by the machinery that fills, tracks, and drains it. Above, three access paths reach the same cached folios: buffered read()/write(), memory-mapped access through page faults, and O_DIRECT, which deliberately bypasses the cache. Below, the filesystem's address_space_operations move folios to and from the block layer. To the sides sit the two subsystems that manage a folio's life: reclaim, which evicts clean folios under memory pressure, and writeback, which flushes dirty ones to disk. The rest of this chapter is essentially a tour of these components, and it is worth keeping the whole picture in view as each is examined in turn.

Why a Page Cache

Repeated access to the same disk data is the common case, not the exception. A shell pipeline reads a file that was just written; a compiler reads the same headers for every source file; a database touches its hot pages constantly. Caching that data in memory turns the second and subsequent accesses from device operations into memory accesses, and the gap is not marginal: a rotating disk answers in milliseconds and even an NVMe SSD needs tens of microseconds, while DRAM answers in tens of nanoseconds. Three or more orders of magnitude separate a cache hit from a cache miss, which is why the hit rate matters far more to observed I/O performance than any tuning of the layers below. The gain on writes is just as large but comes from a different mechanism: deferred writes. Rather than sending each write() to the disk immediately, the kernel collects modifications in cache and writes them back later, in bulk. A file written in many small pieces becomes a few large, well-ordered transfers—exactly the merging and batching Chapter 14 described—and data that is overwritten or deleted before writeback never reaches the disk at all.

Deferred writes carry a risk: data held only in memory is lost if power fails before writeback. The kernel bounds that exposure with time and volume limits (a dirty folio is normally written within tens of seconds) and gives applications explicit control through fsync() and its relatives, covered at the end of this chapter. The page cache is thus a deliberate trade of durability latency for throughput, with knobs to tune the balance.

Two properties of real workloads are what make the cache effective, and both are worth naming because the rest of the chapter's design follows from them. The first is temporal locality: data accessed once is likely to be accessed again soon, so keeping it resident pays off repeatedly. The second is the read/write asymmetry: a read is usually synchronous—a thread is blocked waiting for the data, so latency matters enormously—whereas a write is usually asynchronous, with no one waiting for it to reach the disk, so it can be safely deferred and batched. The cache exploits both: it holds recently used data to satisfy future reads from memory, and it absorbs writes so the device sees far fewer, larger, better-ordered transfers than the application issued. On a busy system the vast majority of file I/O is serviced entirely within the cache; the device is reached only for cold reads and for eventual writeback, which is exactly why the elaborate lower layers of Chapter 14 can afford to be elaborate—they run comparatively rarely.

It is worth noting that this single cache is unified. Older Unix systems, and Linux before 2.4, kept two separate caches: a page cache for file contents and a distinct buffer cache for raw disk blocks. Those were merged long ago, so today one page cache holds both, and a block accessed as filesystem metadata and the same block accessed through the block-device file resolve to the same cached data. The cache also has no fixed size: it grows to fill otherwise-free memory and shrinks under pressure as reclaim (Figure 15-1) evicts clean folios, so idle memory is never wasted—it becomes cache—yet the cache never starves a process that needs the memory back.

That elasticity has a consequence worth stating plainly, because it is the single most common source of confusion about Linux memory: a system with almost no free memory is usually a healthy system, not one about to run out. Memory occupied by clean page cache is available on demand—the allocator reclaims it without any I/O—so the number that matters is MemAvailable rather than MemFree. The cache is also not a single global pool in the accounting sense: every cached folio is charged to a memory cgroup when it is added, so a container with a memory.max limit reclaims its own cache when it approaches that limit rather than pushing on the rest of the system, and the writeback machinery of section 7 is cgroup-aware for the same reason.

The cache is directly observable, which makes it easy to check any of the claims in this chapter on a running system. /proc/meminfo (fs/proc/meminfo.c) reports the totals, and /proc/vmstat exposes the underlying counters; the per-cgroup equivalents appear in each cgroup's memory.stat. What the Page Cache Holds

The page cache is not one cache but many, unified by a single mechanism. Anything the kernel identifies by an (address_space, index) pair lives in it. In practice that means the data of regular files; the contents of directories, which Linux stores and caches much like files; data read directly from block-device files, such as a superblock or a filesystem's metadata blocks; and the pages of memory-mapped files, which share the very same cached folios as ordinary reads and writes of the file. It also holds the pages of tmpfs and shared anonymous memory, which have address_space objects like any other file even though nothing backs them but swap. Table 15-2 lists the kinds of data in the cache and the object that owns each.

The swap cache is the one entry in that table that needs a caveat, and it has changed. Older kernels genuinely indexed swapped pages in per-area address_space objects, so it was fair to say that anonymous memory and the page cache shared one indexing mechanism. In 7.0.12 they no longer do: a single global struct address_space swap_space (mm/swap_state.c) survives only so that reclaim and the other paths that expect a folio to have a mapping keep working—the source calls it "a fiction"—while the real index is a per-cluster flat array, struct swap_table, whose slots hold a folio pointer, a shadow value, or nothing. Swap and the page cache are therefore cousins in 7.0.12 rather than the same machinery, and the rest of this chapter is about the file side.

The (address_space, index) key is the unifying idea and deserves a second look. The address_space identifies which cache—one file, one directory, one block device—and the index identifies which folio-sized slice of it, counted in pages from the start of the object. Every distinct cacheable thing has its own address_space, so the same page index means different data in different objects, and there is never any ambiguity about what a cached folio contains. This is why the cache can serve so many roles with one mechanism: a regular file, a directory, and a raw disk are all just address_space objects with folios indexed inside them, and the read, write, writeback, and reclaim machinery treats them identically. What it deliberately does not cache is data that has no backing store to be consistent with—kernel text and most kernel data structures live in memory permanently and are never part of the page cache. Nor does it hold everything that looks like file I/O. Two paths deliberately step around it. O_DIRECT reads and writes build bios straight from the user's own pages, trading the cache's benefits for control over when data reaches the device, which is what a database that manages its own buffer pool wants; the kernel invalidates any cached copies of the range so the two views cannot disagree. DAX, used on persistent memory and on some virtio-pmem devices, goes further: because the storage is byte-addressable and already in the physical address space, there is nothing to copy into RAM, so a DAX mapping points straight at the device and the page cache is bypassed entirely. Both are exceptions that prove the rule—they exist precisely because the default is to go through the cache.

Figure 15-2 places the cache in the I/O stack. It sits directly beneath the system-call and VFS layers and above the filesystem's mapping layer and the block layer of Chapter 14. A read() that hits returns from the cache without descending further; a miss, or the writeback of dirty folios, is what generates the bios that the lower layers carry to the device.

Pages, Folios, and the Cache

Historically the page cache cached individual struct page objects, one per hardware page. That page is 4 KB on x86_64 and on the usual ARM64 build, but ARM64 can also be configured with a 16 KB or 64 KB translation granule, so "page" is a per-configuration quantity rather than a universal 4 KB and the code must never assume otherwise. Modern kernels cache folios instead. A folio is a run of one or more physically contiguous pages managed as a unit, and it is now the natural currency of the page cache: a lookup returns a folio, a read fills a folio, and dirty tracking and writeback operate on folios. A single-page folio behaves exactly like the old per-page cache entry, so the concept subsumes the old model rather than replacing it wholesale; larger folios let one cache entry, one lookup, and one I/O cover many pages at once, which is a significant efficiency gain on modern high-throughput storage. Folios are the subject of their own section below; for now it is enough to read "the unit stored in the page cache" wherever the text says folio.

The shift matters even at this framing stage because it changes what a "cache entry" costs. In the page-at-a-time model, a one-megabyte file occupied 256 separate 4 KB entries, each with its own XArray slot, its own lock, its own dirty and writeback bookkeeping, and—when written—its own small I/O. With folios the same file can be held in far fewer, larger entries, so a sequential read or write touches one folio where it once touched sixteen, and the per-entry overhead that used to dominate large-file workloads largely disappears. The cache still falls back to single-page folios when memory is fragmented or a file is accessed in small scattered pieces, so nothing is lost in the small case; the folio simply lets the common large-file case be handled far more cheaply. This is the single most important structural change in the page cache since Linux 2.6, and it is why the chapter is organized around folios rather than pages from here on.

There is a ceiling on how large a page-cache folio may be, and it is worth knowing where it comes from. MAX_PAGECACHE_ORDER (include/linux/pagemap.h) is the smaller of two limits: a preferred maximum, which is the PMD order when transparent huge pages are configured and order 8 otherwise, and MAX_XAS_ORDER, which is what the XArray can split in one step. On the common 4 KB-page build with transparent huge pages that works out to order 9—a 2 MB folio—so the practical range of a page-cache entry spans from a single page up to a huge page. Which order is actually used within that range is decided dynamically, mostly by readahead, and a filesystem opts into anything above order 0 explicitly; sections 3 and 5 return to both.

The address_space Object

The address_space is the object at the center of the page cache. Every cache—each file, each directory, each block device—has one, and it ties together the cached folios, the operations that fill and flush them, and the owner they belong to. Where the 2.6 object embedded a radix tree, the modern object embeds an XArray, but its role is unchanged: it is the page cache for one cacheable thing.

The name is something of a misnomer worth clearing up at the outset: a struct address_space has nothing to do with a process's address space or with virtual-memory mappings in the sense of page tables. Rather, it is the bridge between the two subsystems that meet at the page cache—the Virtual File System above, which knows files and inodes, and the memory-management subsystem below, which knows folios and physical pages. If the inode describes a file's on-disk metadata, its address_space describes the RAM currently caching that file's contents, and it is what turns "byte offset N of file X" into "this folio in memory," so a read() can be satisfied without touching the disk. The sections that follow open up the three things inside it that make that possible: the XArray that indexes cached folios by offset, the host back-pointer to the owning inode, and the a_ops vector through which the filesystem fills and flushes them.

struct address_space

struct address_space (include/linux/fs.h) is compact. Its host points at the owning inode (or block device); i_pages is the XArray that holds the cached folios keyed by index; a_ops is the table of operations that read, write, and manage those folios; nrpages counts the cached pages; writeback_index records where cyclic writeback should resume; gfp_mask is the allocation mask for new folios; flags carries AS_* state bits; and i_mmap plus its lock track the memory mappings of this object. The excerpt below is the whole structure apart from one configuration-dependent counter, nr_thps; twenty or so bytes of pointers and counters are all the page cache needs per cacheable object, which is what makes it affordable to give one to every inode in the system. The flags word repays a closer look, because it is doing two unrelated jobs. Its low bits are the AS_* state flags (include/linux/pagemap.h) listed in Table 15-4, which record error state and per-mapping policy: whether folios may be evicted, whether writes must wait for in-flight writeback, whether release_folio should be called even when a folio has no private data. Its high bits, 16 through 25, are not flags at all but two packed 5-bit fields holding the minimum and maximum folio order this mapping allows. That is where mapping_set_large_folios() and mapping_set_folio_order_range() write, and where mapping_max_folio_order() reads, so the folio-size ceiling of section 1 is quite literally stored in this one unsigned long. A detail that catches people out: those helpers compile to nothing unless CONFIG_TRANSPARENT_HUGEPAGE is enabled, and mapping_max_folio_order() then returns zero, so large folios in the page cache depend on the huge-page configuration even for filesystems that never use huge pages directly.

Error state is the one field with genuine historical baggage. mapping_set_error() records a writeback failure in three places at once: the mapping's wb_err sequence, the superblock's s_wb_err, and, for callers that have not been converted, the old AS_EIO or AS_ENOSPC bit. Only the first gives the exactly-once-per-opener guarantee that section 8 describes; the flag bits are a fallback kept for code that still tests them.

An address_space is rarely allocated on its own; it is embedded in an inode as the i_data field and initialized when the inode is created. At inode allocation (inode_init_always(), fs/inode.c) the kernel sets the mapping's host to the inode, points inode->i_mapping at it, gives it a placeholder a_ops of empty_aops, and initializes its XArray and default gfp_mask (GFP_HIGHUSER_MOVABLE, so cached folios may live in high memory and be migrated). A filesystem then finishes the setup as it fills in the inode: it installs its own operations table—for example inode->i_mapping->a_ops = &ext4_aops—and may adjust the allocation mask with mapping_set_gfp_mask() (a block-device or DMA-backed inode, for instance, restricts folios to a usable memory zone). From that point the address_space is the file's page cache, and every read, write, fault, and writeback of the inode flows through it.

The object is a hub that links several others, and understanding those links is the key to how the cache is used. The relationship with the inode is bidirectional: mapping->host points down to the inode, and inode->i_mapping points back to the mapping, so code holding either can reach the other—folio->mapping->host is the standard way writeback and reclaim get from a cached folio to the inode whose size, mtime, and filesystem they need. The relationship with folios is ownership: the i_pages XArray holds every cached folio of the object, and each folio's mapping and index point back into it, so a folio always knows which cache it belongs to and where. The relationship with the filesystem is through a_ops: whenever the generic page cache needs to fill, flush, or release a folio it calls one of these methods, which is how one body of caching code drives dozens of different filesystems. And the relationship with memory mappings is through i_mmap: every vm_area_struct that maps the file is linked into this tree, so operations that must reach all mappers of a file—truncation unmapping the tail, or the reverse-mapping code during reclaim—walk i_mmap to find them. Figure 15-3 draws the hub and these four relationships.

Most driver and filesystem code touches the address_space through a small set of helpers rather than its fields directly. To flush a file's cache a caller uses filemap_write_and_wait(); to discard cached data it uses truncate_inode_pages() or invalidate_mapping_pages(); to read a single cached block through a block-device inode's mapping it uses the buffer helpers of a later section. Block drivers seldom manipulate an address_space directly, but they benefit from one indirectly: a block-special inode's i_mapping is redirected to the underlying block_device's mapping (Chapter 14), so all raw access to a disk shares one page cache and one set of dirty folios, which is why sync can flush a device and why two openers of /dev/sda see coherent data. Concurrency is managed by three locks visible in the struct: the XArray's internal xa_lock guards insertion and lookup, invalidate_lock serializes truncation and hole-punching against faults and reads, and i_mmap_rwsem protects the mapping tree—so the page cache can be walked and modified from many CPUs at once without a single global lock.

address_space_operations

The address_space_operations table is how the generic page cache calls into a specific filesystem to move data between a folio and its backing store. In the modern kernel these methods are folio-based: the 2.6-era readpage is now read_folio, set_page_dirty is now dirty_folio, and invalidatepage/releasepage are invalidate_folio/release_folio. The most important methods are read_folio (fill one folio from disk), readahead (fill several folios ahead of demand), writepages (flush a range of dirty folios), dirty_folio (mark a folio dirty), and write_begin/write_end (bracket a buffered write). Table 15-5 lists the ones a filesystem most commonly implements.

One 2.6-era entry is conspicuously absent, and its absence is one of the larger changes in this chapter. There is no writepage method in 7.0.12. The 2.6-era interface asked the filesystem to write back one page at a time, and both reclaim and the flusher threads called it directly; the whole method was removed once the last filesystems were converted, leaving writepages as the only way the kernel asks for dirty data to be written. The reason is the same one that motivated folios: writing a single page at a time gave the filesystem no opportunity to build a large, well-ordered transfer, and it forced memory reclaim into the filesystem's allocation paths at exactly the moment memory was scarce. A range-based writepages lets the filesystem see the whole run of dirty folios at once and emit one bio for it, and reclaim no longer writes file data itself — it kicks writeback and moves on, as section 9 describes.

Which Inodes Own an address_space

Every inode embeds one address_space directly, its i_data field, and its i_mapping pointer normally points at that embedded object. Code throughout the VFS and page cache reaches the cache through inode->i_mapping, which is why the same folios back a file whether it is read with read(), written with write(), or accessed through a memory mapping. Redirecting the pointer is rare in 7.0.12, and every remaining case has the same motive — making two inodes share one set of cached folios instead of keeping two copies that could drift apart. Coda points a cached inode's i_mapping at the local container file it is backed by (fs/coda/file.c); a device-DAX inode is pointed at the mapping of the DAX device's own internal inode (drivers/dax/device.c), which is undone by cd_forget() when the character device goes away; and the swap cache uses a standalone address_space of its own, the global swap_space that section 1 described as a placeholder. The rule of thumb is that i_data is where an inode's own cache lives and i_mapping is where its I/O is directed—usually the same object, occasionally another.

The consequence of embedding rather than allocating is that every inode has an address_space, whether or not it will ever cache anything. A pipe, a socket, an eventfd, and an anonymous inode from anon_inode_getfd() all carry a fully initialized but permanently empty one: i_pages is an empty XArray, nrpages stays zero, and a_ops is the do-nothing empty_aops that inode_init_always() (fs/inode.c) installs. Their read and write paths never go through the page cache at all, so nothing ever consults the object. Character devices are the same: unless the driver deliberately redirects it, i_mapping keeps pointing at the inode's own i_data, and a character driver's read and write methods talk to the device directly without ever touching it. Paying a few dozen bytes per inode to avoid a conditional allocation and a NULL check on every cache lookup is a trade the kernel makes gladly.

Block devices deserve a note of their own, because 7.0.12 solves the same problem one level higher up. A block-special file has an inode in whatever filesystem holds the device node — usually devtmpfs — and there may be several such nodes for one disk, on different mounts, in different mount namespaces. Rather than redirect each of those inodes, blkdev_open() overrides the open file: it sets file->f_mapping to bdev->bd_mapping (block/bdev.c), which is the i_data of a private inode living in the kernel-internal bdev pseudo-filesystem, one per block_device. Because the read and write paths reach the cache through file->f_mapping rather than file_inode(file)->i_mapping, every opener of a disk ends up on the same folios no matter which device node it went through, and the device-node inodes keep their own untouched i_data. Chapter 14 describes the bd_mapping field from the block layer's side; this is the page cache's half of that arrangement.

Folios

The folio is the modern unit of the page cache and one of the two headline changes since Linux 2.6. This section explains what a folio is, why it was introduced, the structure that represents it, and how large folios let a single cache entry span many pages. Although this chapter meets folios in the page cache, they are a general memory-management concept: anonymous memory, shmem, and other kernel allocations are described by folios too, so the abstraction reaches well beyond caching.

From Pages to Folios

For most of Linux's history the page cache dealt in struct page, one per hardware page. That worked, but it created a persistent ambiguity: when the kernel began using compound pages—groups of contiguous pages managed together, as for transparent huge pages—a struct page * might point at the head of such a group or at a tail page, and huge amounts of code had to check which. A folio resolves the ambiguity by definition: a struct folio always refers to the head page of a page group and never to a tail, so a function that takes a struct folio * knows it is holding the whole object. In the words of the source, a folio is a physically, virtually, and logically contiguous set of bytes, a power-of-two in size, aligned to that same power-of-two, and at least one page in size (include/linux/mm_types.h). The name is deliberately ordinary—a folio is a sheet or leaf—chosen precisely because it carries no baggage from "page."

The ambiguity was not academic; it was a steady source of bugs. Before folios, a function handed a struct page * could not tell whether it owned a whole huge page or one 4 KB slice of one, so it had to call compound_head() or check PageTail() almost everywhere, and forgetting to do so produced subtle corruption—dirtying the wrong page, miscounting references, or freeing a page still in use. Because a folio is defined to be a head page, an entire class of these checks simply disappears: the type system now encodes what used to be a runtime invariant. When code does need to cross between the two views it does so explicitly and cheaply—page_folio(page) returns the folio that owns a page, and folio_page(folio, n) returns the n-th page of a folio—so the conversion is a pointer adjustment, not a data copy.

Practically, the conversion means the page-cache API is now expressed in folios. Where code once called find_get_page() it now calls filemap_get_folio(); where a filesystem implemented readpage it now implements read_folio. Because a single-page (order-0) folio is bit-for-bit the old per-page entry, the transition has been incremental and is still ongoing—much of the kernel has been converted function by function, and page-based wrappers remain for code that has not—yet for the page cache the folio is now unambiguously the primary abstraction. There is also a longer-term motive behind the change: separating the folio's per-object state from the raw struct page is a step toward shrinking the memory the kernel spends on page metadata, since one folio descriptor can stand in for many pages. Figure 15-4 shows the relationship between a folio and its pages.

That long-term motive has become visible in 7.0.12. The work travels under the name memory descriptors: the goal is a small struct page that says only what kind of thing a page frame is being used for, with the substantial per-object state living in a separate descriptor — a folio for cache and anonymous memory, a struct slab for the slab allocator, a page-table descriptor for page tables. The first externally visible step is a type change. A folio's flags field is no longer a bare unsigned long but a memdesc_flags_t, a one-member struct wrapping that word (include/linux/mm_types.h), so that code cannot silently mix a descriptor's flags with an integer while the flags are being moved. Readers comparing this chapter with a 6.x kernel will notice the change immediately; nothing in the page cache's behavior depends on it, but it is a useful signpost for where the abstraction is heading.

It is worth being clear about what a folio is not. It is not a new kind of memory and not a new allocator: a folio is still backed by ordinary page frames from the buddy allocator, and an order-n folio is exactly the order-n allocation the buddy system has always returned. Nor does a folio imply a huge page in the hardware sense; a 2 MB folio may perfectly well be mapped by 512 ordinary PTEs. What the folio adds is a name for the whole run and a guarantee about which end of it you are holding. Everything else — contiguity, alignment, the power-of-two size — was already true of compound pages; the folio simply made it possible to say so in a function signature.

The overlay with struct page is worth understanding because it is what made the transition affordable. A folio and a page occupy the same memory: struct folio is laid out so its fields line up with the head struct page's fields, and static assertions in the header enforce the alignment, so converting a page pointer to a folio pointer is a cast, not an allocation. This means folios added no per-page memory cost—the folio is the head page, viewed through a type that guarantees it is not a tail. The accessors in Table 15-6 exist for the same reason: reading folio->flags directly would work, but going through folio_test_dirty() and its siblings keeps callers from accidentally operating on a tail page's flags, the very bug the folio was designed to prevent. Figure 15-5 shows the two type views over the same bytes.

The consequence of overlaying is that a folio has no spare room, and the structure is unusually crowded as a result. Several fields are unions that mean different things depending on what the folio is being used for: index shares its word with share for hugetlbfs, private shares its word with swap for a swap-cache folio, and the lru link shares its space with mlock_count for an unevictable folio and with pgmap for device memory. Reading any of these without knowing which kind of folio you hold is a bug, which is another reason the accessors are not optional decoration.

A large folio solves the space problem differently: it borrows the memory of its own tail pages. Because the tail struct pages of a compound allocation carry almost no state of their own, struct folio declares three further unions — __page_1, __page_2, and __page_3 — that overlay them, and the fields a large folio needs live there. The order is the low byte of _flags_1, in the first tail page, alongside the mapcounts and pin count; _deferred_list lives in the second; hugetlb's four private pointers occupy the third. This is why folio_order() begins with a folio_test_large() test and returns a constant zero for a single-page folio: there is no tail page to read the order from, and the fast path therefore touches no extra memory at all. It is also why 7.0.12 caches a large folio's page count in an explicit _nr_pages field on 64-bit builds rather than recomputing 1 << order — folio_nr_pages() is called often enough for the shift to matter. Twenty-seven FOLIO_MATCH() static assertions at the bottom of include/linux/mm_types.h hold this entire arrangement in place; if anyone reorders struct page, the build breaks rather than the kernel.

A folio's lifetime is governed by two mechanisms visible in the table. The _refcount is a pin count: folio_get() takes a reference and folio_put() drops one, and the folio cannot be freed or migrated while any reference is held—this is how a reader keeps a cached folio alive while copying from it, and how the page cache keeps a folio present between lookup and use. Separately, the folio lock (the PG_locked flag, taken with folio_lock() and released with folio_unlock()) serializes operations on the folio's contents: a folio is locked while it is being filled by read_folio, while a write is prepared in it, and while it is handed to writeback, so that concurrent accessors wait rather than see half-written data. The distinction matters—a reference keeps the folio existing, the lock keeps its contents consistent—and page-cache code routinely holds a reference without the lock (to keep a folio around after unlocking it) or takes the lock briefly under a reference it already holds. Reclaim and memory-cgroup accounting also hang off the folio: the lru link places it on a per-node LRU list, and the folio records which memory cgroup it is charged to, so eviction and accounting both operate at folio granularity.

Large Folios in the Page Cache

The payoff of the folio abstraction is the large folio: a cache entry of order greater than zero that holds several contiguous pages. When a filesystem opts in—mapping_set_large_folios() on the address_space—the page cache may allocate multi-page folios for a file, so a large sequential read fills one 64 KB folio instead of sixteen 4 KB pages. The benefits compound down the stack: one XArray entry instead of sixteen, one folio lock instead of sixteen, one dirty/writeback mark instead of sixteen, and one large bio instead of many small ones. On ARM64 large folios also enable contiguous PTE hardware optimizations, and on both architectures they cut per-page bookkeeping dramatically for large files.

Large folios are not unconditional. The cache chooses an order based on the file's access pattern and the address_space's configured minimum and maximum order (mapping_max_folio_order() and related helpers), falling back to smaller folios under memory fragmentation. Code that walks a folio's contents must therefore never assume a single page: it uses folio_nr_pages() and folio_size() and iterates, which is exactly why the folio accessors exist. This is the mechanism behind much of the read/write throughput improvement over the 2.6-era page-at-a-time cache.

The order is chosen dynamically, mostly by readahead. When a file is opened and read sequentially, the readahead code grows the folio order as the sequential run lengthens—raising ra->order step by step and clamping it to the mapping's maximum—so the first accesses use small folios and a sustained streaming read settles into large ones. A random or small-strided access pattern keeps the order low, because a large folio there would read in data the caller never touches. The mapping's minimum and maximum orders bound the range: a filesystem sets them with the mapping_set_large_folios() / mapping_set_folio_order_range() helpers, and some devices require a minimum order greater than one page (for instance to match a hardware block size larger than the page size). Because a large folio must be physically contiguous and size-aligned—when cached, it sits at a file offset that is a multiple of its size—the allocator cannot always satisfy the requested order under fragmentation, so the cache gracefully falls back to a smaller folio rather than failing the I/O.

The minimum order deserves more than a passing mention, because it is what made a long-standing limitation go away. Until recently Linux could not mount a filesystem whose block size exceeded the page size: a filesystem block had to fit in one cached page, so a 16 KB-block filesystem was unmountable on a 4 KB-page x86_64 machine even though it mounted happily on a 64 KB-page ARM64 one. A minimum folio order removes the restriction. If the mapping guarantees that every folio is at least 16 KB, a 16 KB block always fits in exactly one folio and the old assumption holds again at a different granularity. That is what mapping_set_folio_min_order() is for, and the block layer uses it too: set_blocksize() in block/bdev.c raises the block device mapping's minimum order to match the logical block size, so a disk with 16 KB sectors is cached in folios no smaller than a sector. The minimum is a promise the page cache must keep, not a hint, which is why it constrains splitting as well as allocation.

Large folios are not permanent, either. A folio can be split into smaller folios when an operation must act on part of it at finer granularity—a partial truncation, a hole punch, or memory reclaim that wants to free only some of its pages—so the cache can create large folios optimistically and break them up when necessary. There are two forms. split_folio() is the uniform split: it turns one order-n folio into 2n order-0 folios, which is simple but throws away every benefit of the large folio at once. folio_split() (include/linux/huge_mm.h) is the non-uniform variant added for exactly this case: it splits down to the requested order only around the page that needs finer treatment, leaving the rest of the run in large folios. Neither may split below the mapping's minimum order, and min_order_for_split() is the function that says how far down a caller may go. Splitting also does not have to happen immediately: a large folio that reclaim would like to break up is queued on _deferred_list and split later under memory pressure, so the common case pays nothing.

Taken together, the order chosen by readahead, the bounds set by the mapping, and the splitting that trims a folio when something needs part of it are what make large folios usable as a default rather than as a tuning option. The savings listed at the head of this section — one slot, one lock, one mark, one bio — are collected automatically for the workloads that benefit, and quietly given back for the workloads that do not. That is the difference between a large folio and the huge pages of earlier kernels, which had to be requested, were all-or-nothing, and could not be broken up when a caller wanted a single page of one.

The folio API

Working with folios means working through a family of accessor functions rather than touching fields directly, and the names follow a consistent convention: nearly every one is prefixed folio_ and takes a struct folio * as its first argument. The functions fall into a handful of groups—conversion between pages and folios, state and flag tests, geometry queries, reference and lock management, content access, and dirty/writeback transitions—and knowing the groups is enough to read most page-cache code. Two conventions in this table are worth internalizing. First, the state tests and transitions come in matched pairs—folio_test_dirty() reads the bit that folio_mark_dirty() sets, folio_test_writeback() reads what folio_start_writeback()/folio_end_writeback() toggle—so a folio's progress through its lifecycle is entirely expressed through these calls. Second, content access goes through kmap_local_folio() rather than a raw pointer, because a folio's pages may live in high memory that is not permanently mapped into the kernel's address space; the mapping is established for the duration of the access and torn down with kunmap_local(). On 64-bit architectures like x86_64 and ARM64 all memory is directly mapped, so this is effectively free, but using the helper keeps the same code correct on 32-bit systems and is the required idiom.

A third convention is easy to miss and worth stating: almost every one of these functions takes an order or reports one, and the ones that do not have been quietly deleted. filemap_alloc_folio() takes a gfp_t and an order, not just a mask; folio_size() is a real runtime value rather than PAGE_SIZE; and the folio_end_read() helper exists because marking a folio uptodate and unlocking it are done together at the end of almost every read, and doing them separately costs two atomic read-modify-write operations on the same word; folio_end_read() flips both bits with a single atomic XOR and wakes any waiter only if there was one. Code written against this API is size-agnostic by construction, which is precisely the property that let large folios be turned on for filesystem after filesystem without rewriting the page cache each time. The lookup and insertion functions that find folios in the cache (filemap_get_folio() and friends) belong to the page cache proper and are covered with the XArray in the next section.

Indexing the Cache: The XArray

Given an address_space and a page index, the kernel must find the cached folio quickly—or determine that there is none. The structure that answers that lookup is the XArray, the second headline change since Linux 2.6. This section explains the move from the radix tree, the folio lookup and insertion API built on the XArray, and the per-folio tags the cache keeps in it.

From the Radix Tree to the XArray

Linux 2.6 indexed the page cache with a radix tree, the data structure that mapped a page index to a cached page. The XArray (include/linux/xarray.h) is its successor: introduced by Matthew Wilcox and merged in 2018 (Linux 4.20), it is an array-like abstraction, indexed by an unsigned long, implemented internally as the same kind of wide radix tree but wrapped in a cleaner API with built-in locking and per-entry marks. It was not a change of data structure so much as a change of interface: the old radix-tree API had grown organically for two decades and become error-prone—callers had to preallocate tree nodes with radix_tree_preload(), bring their own RCU and spinlock discipline, and handle node allocation edge cases by hand—so the XArray encapsulated all of that plumbing behind simple operations. The page cache's address_space.i_pages is an struct xarray, keyed by folio index. A simple lookup is xa_load() and a simple store is xa_store(); the page cache's hot paths use the advanced xa_state cursor API (xas_load(), xas_store(), xas_find()) to walk and update the array while holding its lock, and to handle a large folio that occupies a range of indices as a single entry.

The XArray also stores non-folio values, a capability the page cache relies on. An entry can be a tagged value rather than a pointer (xa_is_value()): the cache uses this for shadow entries that remember a recently evicted folio's position for reclaim accounting, for the swap entries of shmem/tmpfs, and for DAX entries. A lookup therefore returns either a folio, a value entry, or nothing, and callers such as filemap_get_entry() distinguish the cases. Figure 15-6 shows the address_space, its XArray, and the folios and marks it holds.

It helps to know a little of the internal shape, because it explains why the lookups are fast. An XArray is a tree of nodes, and each node holds a wide fan of slots—XA_CHUNK_SIZE, which is 64 on a normal build (XA_CHUNK_SHIFT of 6). A 64-way fan-out keeps the tree very shallow: a few levels index billions of entries, so reaching a folio from its index is a handful of pointer dereferences, not a long walk. A value entry is distinguished from a folio pointer by its low bit—xa_mk_value() shifts a small integer left and sets that bit, and xa_is_value() tests it—so the array can hold folios and values interchangeably without a separate type field. And a large folio is stored as a multi-index entry: the same folio pointer occupies the whole contiguous range of slots its pages cover, so a lookup at any index in the range returns it and the layer naturally treats the folio as one object.

Two properties made the XArray a better foundation than the bare radix tree of Linux 2.6. First, the read side is lockless: a lookup runs under RCU with no lock at all, retrying (xas_retry()) only if it races with a concurrent structural change, which is what lets many CPUs probe the page cache at once. Writers serialize on the array's own xa_lock (the page cache takes it with interrupts disabled, since completion handlers touch the cache). Second, the API is self-contained: the same structure provides the cursor iterator (xa_state), the value entries, and the per-entry marks, where the old radix tree needed separate helper layers bolted on top. The page cache uses all three features heavily, so the move cleaned up a great deal of code even though the underlying tree shape is much the same. The folio lookup API lives in mm/filemap.c and include/linux/pagemap.h. The workhorse is __filemap_get_folio(), usually reached through the thin wrappers filemap_get_folio() (find an existing folio), filemap_lock_folio() (find and lock it), and filemap_grab_folio() (find or create one). The last row of Table 15-9 is not a flag at all, and it answers a question section 3 left open: when the cache creates a folio, how does it know what size to create? The flags word is a distinct type, fgf_t, and its top six bits carry a folio order. A caller that knows how much it is about to write ORs in fgf_set_order(size), and __filemap_get_folio() allocates a folio of that order if it can, clamped to the mapping's minimum and maximum and falling back to smaller orders under fragmentation. This is the mechanism behind large folios in the write path, the counterpart to readahead's growing order in the read path: a filesystem's write_begin passes the length of the write, and the cache creates a folio big enough to hold it rather than a page at a time. The order is only ever a suggestion — if a folio already exists at the index it is returned whatever its size.

FGP_DONTCACHE deserves its own note, because it is the visible end of a mechanism Linux 2.6 had no equivalent for: uncached buffered I/O. An application that streams through a very large file gets no benefit from caching it — it will never read those bytes again — but it does get the harm, because its data evicts everything else. The traditional answers were O_DIRECT, which is awkward because of its alignment rules, and a POSIX_FADV_DONTNEED call after the fact, which is a second pass over the data. Linux now offers a third: RWF_DONTCACHE on a preadv2() or pwritev2(), which sets IOCB_DONTCACHE on the kiocb, which becomes FGP_DONTCACHE on the lookup, which sets PG_dropbehind on the folio. A folio so marked is dropped as soon as the kernel is finished with it — right after the read completes, or after writeback finishes for a write — by folio_end_dropbehind() in mm/filemap.c. The caller gets ordinary buffered I/O semantics, with readahead and no alignment requirements, and the page cache gets its memory straight back. A filesystem must advertise FOP_DONTCACHE for the flag to be accepted. The mark is also polite: if an ordinary caller — one without FGP_DONTCACHE — looks up a folio that was marked dropbehind, the mark is cleared, because someone now wants the data cached after all.

The older page-oriented names still appear in the tree—find_get_page(), find_lock_page(), pagecache_get_page()—but they are now thin wrappers over the folio functions, returning the page that begins the folio. New code uses the folio API directly.

The lookup itself is subtler than a plain tree walk because it runs without a lock. filemap_get_entry() descends the XArray under RCU and, when it finds a folio, must take a reference before the folio can be used —but a folio found locklessly might be freed the instant after it is seen. The code handles this with a speculative reference: it tries to bump the folio's refcount with folio_try_get(), then rechecks that the folio is still at the same index in the same mapping; if either changed, it drops the reference and retries. This is what lets a hot read path find a cached folio with no lock and no contention, while still being safe against concurrent eviction. Insertion, by contrast, takes xa_lock: filemap_add_folio() walks an xa_state cursor to the target index, stores the folio into all the slots a large folio spans, updates nrpages, and—if a shadow entry was sitting at that index—hands it to the workingset code, which decides from the recorded eviction time whether the folio is a refault that should be activated immediately rather than placed on the inactive list.

Bulk operations use a batched form of the same lookup. filemap_get_folios() and its tag- and range-restricted variants fill a folio_batch (up to thirty-one folios) in one locked descent of the XArray, which is how readahead, truncation, and writeback amortize the cost of walking the array over many folios instead of paying it per folio. Callers that need to see value entries—reclaim scanning for shadow entries, or the DAX path—use filemap_get_entry() and check xa_is_value() themselves; callers that only want present folios let the higher-level helpers skip value entries for them.

The Page-Cache Tags

Writeback must be able to find the dirty folios of a huge file without walking every cached folio, and the XArray's per-entry marks make that possible. The page cache defines three (include/linux/fs.h), and the definitions are one line each because a page-cache tag is an XArray mark: PAGECACHE_TAG_DIRTY is literally XA_MARK_0, PAGECACHE_TAG_WRITEBACK is XA_MARK_1, and PAGECACHE_TAG_TOWRITE is XA_MARK_2. The names exist to say what the cache means by each mark, not to add machinery. Folios that have been modified and need writing carry the first; PAGECACHE_TAG_WRITEBACK marks folios whose write is currently in flight; and PAGECACHE_TAG_TOWRITE marks the folios a given writeback pass has selected, so that concurrent dirtying does not extend the pass indefinitely. Because a mark propagates up the XArray's internal nodes, a search for tagged entries skips whole subtrees that contain none, turning "find the next dirty folio after index N" into a fast operation even on a multi-gigabyte file. The number three is not a coincidence: the XArray provides exactly XA_MAX_MARKS marks per node—three—and the page cache uses all of them for these tags. Each mark is a bitmap stored inside every node, one bit per slot, and the crucial property is that a node's bit in its parent is set whenever any of its slots carries the mark. This makes marked iteration hierarchical: when xas_find_marked() looks for the next dirty folio, it descends only into subtrees whose parent bit is set and skips entire branches that contain nothing dirty. On a multi-gigabyte file with a few scattered dirty folios, finding them costs time proportional to the number of dirty folios, not to the size of the file —which is exactly what writeback, sync, and reclaim need when they ask "what in this cache still needs writing?"

Two consequences of storing the tags in the index rather than on the folio are worth drawing out. First, a folio's dirty state is recorded twice, in two places that must agree: the PG_dirty flag on the folio itself and the DIRTY mark in its mapping's XArray. This is why folio_mark_dirty() is not a simple bit set — it must take the i_pages lock to update the mark as well, which is what __folio_mark_dirty() does, and why the address_space rather than the folio is the thing you lock. It is also why AS_NO_WRITEBACK_TAGS from section 2 exists: a mapping whose folios are never written back, such as the one behind a ramdisk, opts out of maintaining marks it would never query. Second, a mark applies to an XArray slot, and a large folio occupies many slots as a single multi-index entry, so the mark covers the whole folio at once. A 2 MB folio is one dirty mark, not 512 — which is the same economy section 3 claimed for large folios, seen from the index side.

The TOWRITE tag deserves a note because it solves a subtle livelock. A writeback pass wants to write every folio that is dirty now, but if it simply looped on DIRTY a process dirtying the file as fast as the pass writes it could keep the pass running forever. So at the start of an integrity writeback, tag_pages_for_writeback() snapshots the current dirty set by copying the DIRTY mark to TOWRITE across the range; the pass then writes only the TOWRITE folios and finishes when that fixed set is done, even if new folios are dirtied meanwhile. The three tags thus divide a folio's writeback life cleanly: DIRTY while it waits, TOWRITE once a pass has claimed it, and WRITEBACK while its I/O is in flight—each a fast, hierarchical query away. The writeback section returns to how the passes that use them are scheduled.

Reading and Writing Through the Cache

With the cache's object, unit, and index in place, we can follow an actual read() and write() through it. Both are implemented generically in mm/filemap.c and call into the filesystem only through the address_space operations, which is why so many filesystems share the same buffered-I/O code. This section traces the read path that fills the cache, the write path that dirties it, and the fault path that maps it. The recurring theme is the read/write asymmetry from the start of the chapter: reads block the caller and so are optimized for latency and prefetching, while writes return as soon as the data is cached and defer the real device I/O to writeback. Only O_DIRECT steps outside this entirely, building bios straight from user pages and bypassing the cache.

The Read Path

A buffered read enters through the file operation read_iter, which for most filesystems is generic_file_read_iter(), and reaches filemap_read(). The core is filemap_get_pages(): it looks up the target folios in mapping->i_pages, and for each index either finds a cached folio or handles the miss. On a hit the data is copied straight to the user buffer. On a miss the kernel allocates a folio, adds it to the cache, and calls the filesystem's read_folio (or readahead) to fill it from disk—which produces the bios of Chapter 14—then waits for the folio to become uptodate before copying. Readahead runs alongside: sequential access triggers page_cache_sync_ra()/page_cache_async_ra() to fetch folios ahead of demand, so later reads hit. Figure 15-8 shows the decision.

The loop inside filemap_read() is worth following once because it explains why streaming reads are fast. filemap_get_pages() first tries a batch lookup of the folios covering the requested range; if the range is not fully cached it kicks synchronous readahead (page_cache_sync_ra()) to fetch the miss and a window of folios past it, then retries the lookup. Once it has a folio it may still need to wait for an in-flight read to finish (filemap_update_page() waits on the folio lock and rechecks folio_test_uptodate()). Only then does filemap_read() copy out of the folio into the user iterator, honoring large folios by copying across all their pages and stopping cleanly at end-of-file with a short read. Because a single large folio can cover a 64 KB span, one lookup and one copy can satisfy what used to take sixteen.

Three details of that loop are easy to miss and each guards against a real hazard. First, filemap_read() re-reads i_size after the folios are known to be uptodate, not before: a concurrent truncation could have shrunk the file while the read was waiting for I/O, and checking the size last is what keeps the zero-filled tail of the final folio from being copied out as though it were data. Second, before copying from a folio the loop calls flush_dcache_folio(), but only if mapping_writably_mapped() says the file has shared writable mappings — the i_mmap_writable counter from section 2, used here to decide whether a virtually-indexed CPU cache might hold a userspace alias of these bytes that the kernel's view has not seen. On x86_64 and ARM64, whose caches are physically indexed, the call compiles to nothing; the test exists so that architectures where it does not are correct without slowing down the ones where it is free. Third, folio_mark_accessed() is called once per folio, not once per copy: pos_same_folio() checks whether this read began in the same folio the previous one ended in, so a program issuing a thousand four-byte reads inside one 64 KB folio does not bang on that folio's LRU state a thousand times. The batch is released at the bottom of the loop, and it is there that filemap_end_dropbehind_read() throws away the folios of an RWF_DONTCACHE read.

The read path is also where the page cache meets asynchronous I/O, and the kiocb carries three distinct flags for it that are worth separating. IOCB_NOIO means "return what is already cached and start no I/O at all." IOCB_NOWAIT means "do not sleep": the invalidate lock is taken with a trylock, the folio lock with a trylock, and anything that would block returns -EAGAIN — and while readahead is allowed, it runs inside memalloc_noio_save() so that allocating for it cannot recurse into the filesystem and sleep there. IOCB_WAITQ, which io_uring uses, is the interesting one: rather than fail, __folio_lock_async() attaches the caller's wait queue entry to the folio and returns -EIOCBQUEUED, so the submitting thread goes back to work and the operation is retried from a completion callback when the folio unlocks. Ordinary blocking reads take none of these paths and simply wait in folio_put_wait_locked(). One shared subtlety: a folio can be truncated out of the cache while the reader waits for it, in which case the helpers return AOP_TRUNCATED_PAGE and the whole lookup restarts rather than returning stale data.

Truncation is kept at bay more directly, too. filemap_update_page() takes the mapping's invalidate_lock in shared mode for the duration of a fill, which is the read side of the lock section 2 introduced and section 9 uses: a reader that is bringing a folio up to date holds off the exclusive holder that truncation and hole punching need, so a folio cannot be removed from the cache halfway through being filled. Readahead interacts with the folio size as well — the range a read requests is rounded up by mapping_min_folio_nrbytes() before the lookup, because a mapping with a minimum folio order cannot return anything smaller, and page_cache_ra_order() is what actually chooses the order of the folios readahead allocates.

Readahead itself is adaptive and hinges on a per-folio marker. When the kernel prefetches a window, it sets the readahead flag (PG_readahead, tested with folio_test_readahead()) on one folio near the end of that window. When a later read reaches that marked folio, page_cache_async_ra() fires asynchronously—launching the next window while the current data is still being consumed—so a steady sequential reader always has folios arriving ahead of it and never stalls on a miss. The window grows as the sequential run lengthens and collapses back to a single folio when the access pattern turns random, which is the same signal that drives the large-folio order decision of the previous section. A read served entirely from already-cached folios does none of this: it finds every folio present and copies, touching neither the filesystem nor the device.

The Write Path

A buffered write is the mirror image. generic_perform_write() walks the user data folio by folio, and for each one calls the filesystem's write_begin to obtain a locked, up-to-date folio (creating it in the cache if necessary, reading in surrounding data for a partial write), copies the user bytes into it with copy_folio_from_iter_atomic(), and calls write_end to finalize. The loop is not really page-by-page: its chunk size is mapping_max_folio_size(mapping), so on a filesystem with large folios enabled a single iteration asks write_begin for as much as the mapping's maximum order allows and copies that much at once. This is the write-side counterpart to readahead's growing order, and it is what fgf_set_order() from the previous section carries into __filemap_get_folio(). write_end marks the folio dirty—setting PAGECACHE_TAG_DIRTY in the XArray and adding the inode to its writeback list—and returns. Crucially, no disk I/O has happened yet: the write returns as soon as the data is in cache, and the actual device write is deferred to writeback. Many filesystems now implement this path through the iomap framework rather than by hand, but the shape—prepare a folio, copy in, mark dirty—is the same.

Two details of write_begin/write_end deserve emphasis. First, a partial write—one that does not cover a whole folio—forces a read-modify-write: write_begin must bring the rest of the folio up-to-date from disk before the copy, because the folio will be written back in full and the untouched bytes must be correct. A write that happens to cover an entire folio skips this read, which is why aligned, folio-sized writes are markedly cheaper. Second, the copy can come up short—the user buffer might be partly unmapped and fault mid-copy—so the loop is written to handle a short copy, tell write_end how many bytes actually landed, and retry the remainder, rather than assuming the whole folio was filled.

The reason the copy must be able to come up short is worth spelling out, because it is a deadlock and not merely an inconvenience. At the moment of the copy the folio is locked and the filesystem may hold transaction locks underneath it. If the source buffer is itself a memory-mapped file — perfectly legal, and exactly what cp does with mmap — then touching it can take a page fault that re-enters the filesystem while all of those locks are held. So the copy is done with copy_folio_from_iter_atomic(), which refuses to fault and simply stops at the first inaccessible byte. The loop then unlocks the folio, calls fault_in_iov_iter_readable() to fault the user buffer in with no locks held, and tries again. If even that makes no progress it returns -EFAULT rather than spinning. There is one more adaptive touch: if write_end rejects an iteration outright, the loop halves its chunk size before retrying, so a write that cannot be satisfied at a large folio size degrades toward page-sized work instead of failing.

The write path also flushes the data cache around the copy, twice and for different reasons: once before, if mapping_writably_mapped() indicates a userspace alias might hold dirty lines for these bytes, and once unconditionally afterward, so that a userspace mapping of the file sees what the kernel just wrote. As in the read path this is free on x86_64 and ARM64 and matters only on virtually-indexed architectures.

The write path is also where dirty-page pressure is applied. generic_perform_write() calls balance_dirty_pages_ratelimited() at the top of each iteration, before it asks the filesystem for a folio (the iomap path calls the same function in the same place), which is the throttle from the writeback section: if the process is dirtying faster than the disk can absorb, this is where it is made to wait so memory does not fill with unwritten data. A plain write() otherwise returns immediately, but the open flags can change that—O_SYNC or O_DSYNC turn each write into an implicit fsync, forcing the just-written folios to disk before the call returns, and O_DIRECT bypasses the cache to write straight from user pages. The common case, though, is the deferred one: the data sits dirty in cache and the device is not touched until writeback runs.

Faulting Mapped Files

A memory-mapped file reaches the same folios by a third route. When a process touches an address backed by a file mapping and the page is not present, the fault handler calls the vma's fault operation, which for file mappings is filemap_fault(). It performs the identical cache lookup—find the folio in i_pages, or allocate, add, and fill it via read_folio—and installs the folio's page in the process's page tables. Because the mapping and the read/write paths share one cache, a change made through write() is visible through the mapping and vice versa, without a second copy. Writes to a shared mapping dirty the folio just as write_end does, so they too are captured by writeback. This unity of the mmap and read/write views of a file is a direct consequence of the single address_space per inode described earlier.

Whether a fault is cheap or expensive depends on the cache. A minor fault finds the folio already cached and only needs to install a page-table entry; a major fault misses in the cache and must read the folio from disk, blocking the thread. To make the common minor case cheaper still, filemap_fault() is paired with a map_pages operation, filemap_map_pages(), that the fault handler calls to install page-table entries for several already-cached folios around the faulting address in one go—"fault-around"—so a program walking a mapped file takes far fewer faults than it has pages. The readahead marker works here too: touching a folio tagged for readahead launches the next window asynchronously, exactly as in the read path.

A major fault has a problem the read path does not: it is holding mmap_lock, the lock that serializes every mapping change in the address space, and it is about to wait for a disk. Sleeping there would stall every other thread in the process that wants to mmap, munmap, or fault. So filemap_fault() gives the lock up. maybe_unlock_mmap_for_io() takes a reference on the file (the fault handler's fpin, so the vm_area_struct may be torn down while the I/O is in flight), drops mmap_lock, and the handler returns VM_FAULT_RETRY. The fault is then taken again from the top, this time with FAULT_FLAG_TRIED set and, in the common case, with the folio already in the cache — so the retry is a minor fault. The same dance happens in lock_folio_maybe_drop_mmap() when the folio is present but locked by somebody else. This is why the code is careful never to return VM_FAULT_RETRY together with an error bit: the two answers mean incompatible things to the caller.

Fault-around and mmap readahead are both tuned by heuristics that are worth knowing when a workload behaves unexpectedly. The fault-around window is 64 KB by default — sixteen pages with a 4 KB page size — and is exposed through debugfs as fault_around_bytes, rounded down to a power of two; setting it to one page disables fault-around entirely, which is occasionally a useful thing to try when a program touches a mapping very sparsely. Readahead on mapped files is governed by a miss counter, mmap_miss in the file's file_ra_state. A fault that misses the cache increments it, in do_sync_mmap_readahead(); a fault that finds an unlocked folio already there decrements it, in do_async_mmap_readahead(). Once the counter exceeds MMAP_LOTSAMISS (100) — that is, once misses have run 100 ahead of hits — mmap readahead switches off for that file, on the theory that a mapping being accessed randomly is only harmed by reading ahead. The madvise() hints short-circuit the heuristic from both ends: MADV_SEQUENTIAL sets VM_SEQ_READ and skips the miss accounting so readahead is never disabled, while MADV_RANDOM sets VM_RAND_READ and suppresses asynchronous readahead outright.

The kind of mapping decides what a write fault does. In a private (MAP_PRIVATE) mapping, writing triggers copy-on-write: the faulting process gets a private anonymous copy of the folio and its changes never reach the file. In a shared (MAP_SHARED) writable mapping, the write must reach the file, so the first write to a clean folio takes a write-notify fault that calls the filesystem's page_mkwrite hook (to let it allocate backing blocks or extend the file), then marks the folio dirty so writeback carries the change to disk. This is how an mmap-based write, with no write() call at all, still flows through the same dirty folios, tags, and flusher threads as every other write in this chapter.

Storing Blocks: Buffer Heads and iomap

In Linux 2.6, storing blocks in the page cache was built entirely around the buffer_head—the descriptor that located an individual disk block inside a cached page. Buffer heads still exist in 7.0.12, but their role has narrowed sharply: the page cache itself is folio-based, and modern filesystems handle file data through the iomap framework rather than buffer heads. This section covers what survives, the block-lookup functions that remain, and the iomap mechanism that has largely replaced them.

The unification section 1 described is what explains why buffer heads exist at all. Once the separate buffer cache was merged into the page cache, block buffers stopped being allocated on their own: they live inside ordinary page-cache pages, now folios, historically called buffer pages. The reason a folio needs per-block descriptors at all is that the blocks it holds are not necessarily contiguous on disk: a single 4 KB folio might hold four 1 KB filesystem blocks that map to four scattered disk locations, and something must record where each one lives and whether it is up to date or dirty. That something is the buffer head.

Buffer Heads Today

A buffer head (struct buffer_head, include/linux/buffer_head.h) describes one disk block that lives inside a cached folio. Its b_blocknr and b_bdev give the block's device address, b_size its size, b_data its location within the folio, b_state a set of BH_* flags, and b_this_page links all the buffer heads of one folio into a ring. A notable modernization: the descriptor now points at its folio through b_folio (with b_page kept in a union for compatibility), and the buffer heads of a folio hang off folio->private, reached with folio_buffers()—the folio-era replacement for the old page->private/page_buffers(). The relationship between a folio's state and its buffers' states is the subtle part. A buffer page's folio carries the overall dirty and uptodate flags, but each block within it also has its own BH_Dirty and BH_Uptodate bits: the folio is uptodate only when every one of its buffers is, and it is dirty if any buffer is dirty. When writeback picks such a folio, it consults the buffer heads and writes only the blocks whose BH_Dirty is set, then clears the folio's dirty flag once they are all clean. Buffer heads have their own slab cache and are obtained and released with alloc_buffer_head()/free_buffer_head(); the b_count reference must be held while a buffer is in use (the lookup helpers take it automatically) and dropped with brelse(), and only a buffer with a zero count is reclaimable.

Two fields deserve more than a table row. b_uptodate_lock solves a problem created by folios holding many blocks: when several buffers of one folio are read asynchronously, each completion must ask "am I the last?" before it can mark the whole folio uptodate, and those completions run in interrupt context on different CPUs. Rather than give every buffer head a lock, the buffers of a folio all use the lock in the first one, which folio_buffers() can always find. And b_assoc_map with b_assoc_buffers is the other end of the i_private_list field that section 2 left unexplained: a filesystem that calls mark_buffer_dirty_inode() on a metadata block — an indirect block, say — links that buffer onto the owning inode's private list, so that sync_mapping_buffers() can flush those blocks when the file is fsynced even though they live in the block device's mapping and not in the file's. It is a small mechanism, but it is the reason an ext2-style filesystem can make fsync() mean something for the metadata a file depends on.

It is also worth correcting an impression the previous paragraphs might leave: buffer heads are not only for metadata. fs/buffer.c still supplies a complete set of address_space operations that any unconverted filesystem can adopt wholesale — block_read_full_folio(), block_write_begin() with block_write_end() and generic_write_end(), block_dirty_folio(), block_truncate_page(), and create_empty_buffers() (which, like everything else here, now takes a folio rather than a page). Roughly two dozen filesystems in the tree still use them for file data.

The clearest measure of how far the separation has gone is that buffer heads are now a build option. CONFIG_BUFFER_HEAD can be turned off, and a kernel configured with only iomap-based filesystems leaves fs/buffer.c out of the image entirely — which is why IOMAP_F_BUFFER_HEAD, the flag by which a filesystem tells iomap it still wants buffer heads underneath, is #defined to zero when the option is absent. In 2.6 the buffer head was a structure the kernel could not function without; in 7.0.12 it is a subsystem you can decline.

One of those helpers connects directly to section 2's observation that writepage has been deleted from address_space_operations. The buffer-head writeback function is block_write_full_folio(), and it is still very much alive — what changed is who calls it. It is no longer installed as a per-folio method the kernel invokes; a filesystem's own writepages implementation now walks the dirty folios itself and calls block_write_full_folio() on each. The work is the same; the control flow inverted, which is precisely what removing writepage was meant to achieve.

Why do buffer heads survive at all in a folio-and-iomap world? Because some jobs still need per-block state that is separate from file data. Filesystem metadata—superblocks, inode tables, allocation bitmaps, directory blocks—is naturally addressed one block at a time, and the buffer cache is exactly the right tool for it. Journaling makes this essential: the jbd2 layer used by ext4 tracks each metadata change as a buffer head, ordering and committing them through the journal, and there is no folio-level equivalent for that. So buffer heads remain the currency of metadata and of filesystems that predate the iomap conversion, while file data has largely moved on—the division the rest of this section describes.

Finding and Reading Blocks

The functions that locate and read a single block through the buffer cache survive from the 2.6 era, mostly under the same names. __find_get_block() looks up a block that is already cached (with a companion __find_get_block_nonatomic() for callers that may sleep); bdev_getblk(), which replaced the old __getblk(), finds a block or creates a mapped buffer for it; __bread() returns an uptodate buffer, reading it from disk if necessary; and filesystems usually reach these through the superblock helpers sb_bread() and sb_getblk(), which supply the device and block size automatically. A dirty buffer is marked with mark_buffer_dirty() and released with brelse() (or bforget() to discard pending changes). Submitting a buffer for I/O is submit_bh(), which builds a one-block bio and hands it to submit_bio()—the bridge from the buffer cache into the block layer of Chapter 14.

One prominent 2.6-era function is gone: ll_rw_block(), the 2.6 interface for submitting several buffers at once, has been removed entirely. Its callers now use submit_bh() directly or the higher-level helpers bh_read(), bh_readahead(), and bh_read_nowait(). Table 15-13 maps the 2.6-era block functions to their current status.

It is worth seeing where these buffers actually live, because it ties the buffer cache back to Chapter 14. The blocks read by sb_bread() are cached in the page cache of the block device's own inode—the mapping a block-special file's i_mapping points at—so a filesystem's metadata blocks and the raw device share one cache, keyed by block number. When a filesystem calls sb_getblk(), the buffer's b_size comes from the superblock's block size (s_blocksize) and the folio that backs it is allocated in that device cache if not already present; __bread() then issues the read through submit_bh() if the buffer is not yet uptodate. Because these buffers are just folios in the device's page cache, they are flushed by the same writeback machinery as everything else, which is why sync writing a device (Chapter 14) also commits a filesystem's dirty metadata buffers. A per-CPU LRU of recently used buffer heads (bh_lru) makes the repeated lookups a filesystem does for hot metadata —the same inode-table or bitmap block again and again—cheap. That LRU holds sixteen buffer heads per CPU (BH_LRU_SIZE), and the difference between __find_get_block() and __find_get_block_nonatomic() is exactly how they touch it: the first assumes it may not sleep and so takes the per-CPU list with preemption disabled, while the second is for callers that can block. Missing in the LRU is not an error — it simply falls through to a page-cache lookup in the device mapping and installs the result in the LRU for next time.

The iomap Alternative

For file data, most modern filesystems have moved off buffer heads entirely and onto the iomap framework (fs/iomap/, include/linux/iomap.h). Instead of attaching a buffer head to every block, iomap asks the filesystem once—through an iomap_begin callback—to describe a whole extent (a contiguous run of blocks) with a single struct iomap, then drives the folio's I/O directly against that description. Where sub-page block state is still needed, iomap keeps a compact iomap_folio_state bitmap on folio->private rather than a chain of buffer heads. The generic helpers iomap_read_folio(), iomap_readahead(), and iomap_writepages() implement the address_space operations on top of this, so a filesystem supplies only its extent-mapping callback and inherits the buffered-I/O machinery. It is worth being precise about who uses it, because "modern filesystem" and "iomap filesystem" are not the same set. For buffered file data the users are XFS, gfs2, erofs, zonefs, ntfs3, fuse, and the raw block-device cache (blkdev_iomap_begin(), from Chapter 14). ext4 and btrfs, despite being thoroughly modern, still have their own buffered read and writeback paths and use iomap only for direct I/O (and, for ext4, DAX and fiemap) — a reminder that the conversion is a long-running migration rather than a finished one. Buffer heads remain the mechanism for filesystem metadata and for filesystems that have not converted, so the two coexist: iomap for the bulk of file data, buffer heads for metadata and legacy paths.

The heart of the framework is the struct iomap the filesystem returns. It gives the mapping's disk address (addr), the file offset and length it covers, the target device (bdev), and—critically—a type that says what kind of extent it is. It also carries a flags word, an optional dax_dev for DAX mappings, a private pointer the filesystem may use, and a validity_cookie discussed below. The types matter because they let iomap handle whole ranges without touching the disk: an IOMAP_HOLE is an unallocated region that reads as zeros, IOMAP_UNWRITTEN is allocated-but-never-written space that also reads as zeros without I/O, IOMAP_DELALLOC is a delayed-allocation range not yet assigned a disk block, IOMAP_MAPPED is a real run of blocks at addr, and IOMAP_INLINE is small data stored directly in the inode. A single iomap_begin call can thus describe megabytes of a file, and iomap issues one large bio for a mapped extent or fills a hole with zeros in memory—work that the one-buffer-head-per-block model did block by block.

The contrast with buffer heads is sharpest if you put the two callbacks side by side. The buffer-head world's mapping callback is get_block_t (include/linux/fs.h): given an inode and one logical block number, fill in one buffer head. It is called once per block, and a filesystem that knows perfectly well that the next ten thousand blocks are contiguous has no way to say so — the most it can do is set BH_Boundary on the last block before a discontinuity. iomap_begin() is the same question asked once for a range, and the answer, iomap->length, is however much the filesystem can describe in one go. That single change of shape is what the rest of the framework is built on.

Callers do not invoke iomap_begin directly; they run an iomap_iter loop. The iterator holds the inode, the current position and remaining length, the operation flags, and — for copy-on-write filesystems — both a destination iomap and a srcmap describing where the old data is to be read from. Each turn of iomap_iter() calls the filesystem's iomap_begin, the body of the loop consumes as much of the returned extent as it can and reports progress with iomap_iter_advance(), and iomap_end commits or releases whatever iomap_begin reserved. This is what makes the framework composable: buffered writes, direct I/O, fiemap, SEEK_HOLE, swapfile activation, and page-fault handling are all the same loop with different bodies, which is why fs/iomap/ is a directory of small files rather than one large one.

A cached extent map raises an obvious hazard: a long buffered write may hold one struct iomap across many folios while the filesystem's real extent tree changes underneath it. iomap handles this with a validity cookie. The filesystem stores a sequence number in iomap->validity_cookie when the mapping is created, and iomap calls the optional iomap_valid() hook — with the folio locked — before trusting the cached mapping again; if the cookie no longer matches, the mapping is marked IOMAP_F_STALE and the iteration re-maps that range. Several other flags in the same word carry information back to the generic code: IOMAP_F_NEW says the blocks were just allocated and must be zeroed, IOMAP_F_DIRTY that the inode has uncommitted metadata so a write needs an fsync, IOMAP_F_SHARED that the extent is shared and a write must copy it first, and IOMAP_F_BUFFER_HEAD that the filesystem is using iomap while still wanting buffer heads underneath.

The iomap_folio_state that iomap attaches to a large folio is the other half of the efficiency story: it is a small array with two bits per block—one for uptodate, one for dirty—so a 2 MB folio tracks the state of its hundreds of blocks in a handful of words instead of hundreds of buffer-head structures. The arithmetic is worth doing: at a 4 KB block size that folio holds 512 blocks, which as buffer heads would be 512 separate slab allocations threaded on a b_this_page ring, versus 128 bytes of bitmap in a single flexible array. Alongside the bitmap the structure keeps a state_lock guarding it and two pending-byte counters, one for reads and one for writes, so completion can tell when the last outstanding transfer against the folio has finished without walking anything. This is what lets iomap support the large folios of this chapter cheaply, and it is the main reason the high-throughput filesystems have adopted it. The direction of travel is clear: file data on iomap and large folios, metadata on buffer heads, with the buffer cache steadily confined to the role the merged buffer cache was always best at.

Writing Dirty Pages Back

Deferred writes are only half a mechanism; the other half is the machinery that eventually moves dirty folios to disk. Linux 2.6 used the pdflush kernel threads for this. pdflush is gone—removed back in 2.6.32—and this section describes what replaced it: per-device flusher threads driven by the writeback infrastructure, together with the dirty-page throttling that keeps a fast writer from filling memory with unwritten data.

Marking Folios Dirty

Writeback begins the moment a folio is dirtied. folio_mark_dirty() calls the address_space's dirty_folio operation, generically filemap_dirty_folio() (mm/page-writeback.c). That does two things: it sets the folio's dirty flag and its PAGECACHE_TAG_DIRTY mark in the XArray (so writeback can find it), and it calls __mark_inode_dirty(mapping->host, I_DIRTY_PAGES) to record that the inode has dirty data. Marking the inode dirty puts it on a per-device writeback list and, if it is the first dirty inode on that device, wakes the device's flusher work. Dirtying is thus what links a folio to the inode, the inode to its device's writeback queue, and the queue to the flusher thread that will drain it.

The inode's dirty state is finer-grained than a single bit, and the distinctions matter for the sync family later in the chapter. __mark_inode_dirty() takes a mask of I_DIRTY_* flags: I_DIRTY_PAGES means the inode has dirty data folios; I_DIRTY_SYNC and I_DIRTY_DATASYNC mean its metadata is dirty, the latter specifically metadata needed to read the data back (such as a new size or newly allocated blocks); and I_DIRTY_TIME means only timestamps changed, which the kernel can defer especially lazily via the b_dirty_time list. This is exactly the split fdatasync exploits—it must flush the data and I_DIRTY_DATASYNC metadata but may skip a pure I_DIRTY_SYNC timestamp update. Dirtying through a shared memory mapping reaches the same place: the write-notify fault's page_mkwrite path ends in folio_mark_dirty(), so an mmap store, a write(), and a metadata change all funnel into the one per-inode dirty state and the one per-device writeback queue.

Dirtying also has to be accounted, because the throttle below can only work from numbers. filemap_dirty_folio() ends in __folio_mark_dirty(), which takes the mapping's XArray lock, sets the tag, and bumps the folio's page count into NR_FILE_DIRTY, the memory cgroup's dirty counter, and the backing device's WB_RECLAIMABLE statistic all at once. The folio-aware part matters: a large folio adds folio_nr_pages() to each of those, so one 2 MB folio counts as 512 against the dirty limit rather than as one item. A filesystem that does not want any of this — one with no writeback at all, such as a purely in-memory or read-only filesystem — installs noop_dirty_folio() instead, which sets the flag and accounts nothing.

The Flusher Threads

Modern writeback is organized per backing device. Each backing_dev_info (bdi)—roughly, each disk or backing store—owns one or more struct bdi_writeback (a "wb") objects, and each wb has its own dirty-inode lists (b_dirty, b_io, b_more_io) and a delayed work item (dwork) that runs on a shared workqueue. The work function wb_workfn() (fs/fs-writeback.c) is the heart of writeback: it drains any explicitly queued work, then performs periodic and background writeback as needed. This is the direct replacement for pdflush's pool of generic threads—instead of a handful of shared threads scanning all caches, each backing device has its own writeback context, which scales better and lets a slow device's writeback not stall a fast one. With cgroup writeback enabled, a bdi has a wb per memory cgroup, so writeback can also be attributed and throttled per container.

Cgroup writeback raises a question the single-threaded model never had to answer: which cgroup owns an inode that two of them are writing? The kernel resolves it by observation rather than by rule. wbc_attach_fdatawrite_inode() associates a writeback pass with the wb it believes owns the inode, wbc_account_cgroup_owner() records, folio by folio, which cgroup the bytes actually came from, and wbc_detach_inode() compares the totals at the end of the pass. If a different cgroup has been doing most of the writing consistently — the decision is smeared over a sixteen-slot history in inode->i_wb_frn_history, so a single burst cannot flip it — the inode is switched to that cgroup's wb. Ownership is therefore a moving average of who writes, which is the only workable answer for a file that several containers share.

The evolution is worth noting because it is a recurring theme of this chapter. The 2.4 kernel used two dedicated threads, bdflush (scan for dirty buffers) and kupdate (age out old ones); Linux 2.6 replaced them with the pdflush pool, a set of general threads dynamically grown and shrunk; and 2.6.32 replaced that with the per-bdi model here. The threads themselves are now ordinary workqueue items: the writeback work runs on a shared, memory-reclaim-safe workqueue (bdi_wq), scheduled through each wb's dwork. When an inode is first dirtied, wb_wakeup_delayed() arms that work to fire after dirty_writeback_centisecs, so periodic writeback is simply the delayed re-arming of the same work item rather than a thread spinning on a timer. Each wb also tracks its own achieved write bandwidth (dirty_ratelimit), which the throttling code below uses to pace writers to what the device can actually absorb.

Three conditions trigger writeback, as in Linux 2.6, but implemented through this per-bdi machinery. Periodic (kupdate) writeback runs every dirty_writeback_centisecs and writes folios that have been dirty longer than dirty_expire_centisecs, bounding how long data sits unwritten. Background writeback starts when the total dirty memory crosses the background threshold and runs until it falls back below. Synchronous writeback is forced by memory pressure or by the sync family of calls. Figure 15-9 traces the flow from a dirty folio to the device.

A fourth 2.6-era trigger has quietly been retired. Laptop mode — the arrangement whereby any disk I/O caused a batch flush of everything else, so that the drive could then spin down for minutes at a time — was written for rotating media and makes no sense on flash. The vm.laptop_mode sysctl still exists in 7.0.12, but writing to it only prints a deprecation warning and the value is ignored.

Dirty Throttling and Limits

If a process could dirty folios faster than the disk drains them, memory would fill with unwritten data. The kernel prevents this by throttling writers. As it writes, balance_dirty_pages_ratelimited() periodically checks the amount of dirty memory against a limit; when a writer runs ahead, balance_dirty_pages() (mm/page-writeback.c) makes it sleep briefly (io_schedule_timeout()) so writeback can catch up, and kicks background writeback if it is not already running. The limits are configurable through /proc/sys/vm/, listed in Table 15-15: a process is throttled hard at the foreground dirty limit and background writeback begins at the lower background limit, with the ratio-based knobs expressed as a percentage of available memory and the byte-based knobs as absolute amounts. The throttling is more refined than a single hard limit, and two ideas make it work smoothly. First, checking the global dirty total on every dirtied page would be far too expensive, so each task keeps a per-CPU count of pages it has dirtied (current->nr_dirtied) and only calls into balance_dirty_pages() after a small budget (current->nr_dirtied_pause) is spent—the ratelimiting the function's name refers to. Second, the throttle does not simply block at the limit; it computes a target rate. Below a lower "freerun" threshold a writer is not delayed at all; between there and the hard limit it is paused for an interval calculated from how far dirty memory is above the setpoint and how much write bandwidth the device is actually achieving (dirty_ratelimit), so a writer to a fast SSD is barely slowed while a writer to a slow USB stick is paced to match it. On a system with many backing devices each wb gets a proportional share of the global limit (wb_calc_thresh()), so a slow device cannot monopolize the dirty budget and stall writers to a fast one. The effect is that writers are smoothly metered to aggregate writeback bandwidth rather than lurching between running free and blocking hard.

There is one important exception to the proportional-share scheme. The global limit assumes every backing device is trustworthy: if one of them stops completing writes, the dirty pages piled up against it are still counted globally and every other writer eventually feels it. That is an unacceptable risk when the "device" is a userspace process, so a filesystem may set BDI_CAP_STRICTLIMIT on its bdi, which makes the throttle enforce the limit against that device alone rather than letting it borrow from the global pool. FUSE sets it, and it is the reason a hung or malicious FUSE daemon can no longer take the whole machine's dirty budget hostage. The strictlimit attribute is also exposed per device as strict_limit under /sys/class/bdi/.

writeback_control and the Writeback Flow

Each writeback operation is described by a struct writeback_control (include/linux/writeback.h) passed down through the flow. Its nr_to_write caps how many pages the pass should write, range_start/ range_end restrict it to a file range, range_cyclic asks it to resume from writeback_index and wrap, and—most importantly—sync_mode selects between WB_SYNC_NONE (best-effort, don't block on locked or in-flight folios) and WB_SYNC_ALL (integrity: write everything and wait). Flags such as for_kupdate, for_background, and for_sync tell the filesystem why the writeback is happening. Table 15-16 lists the key fields.

The structure is no longer purely a set of instructions from caller to callee. It now also carries the state of the writeback loop — an embedded folio_batch, the index reached so far, and a saved error — which is what lets the iteration described below be a plain for loop in the filesystem rather than a callback. A second group of fields, present only under CONFIG_CGROUP_WRITEBACK, holds the wb and inode this pass is attached to along with the byte counters that decide inode ownership. So a writeback_control is really three things at once: what to write, where the loop has got to, and who is being charged.

The flow ties the pieces together. wb_workfn() calls wb_do_writeback() → wb_writeback(), which moves inodes from the wb's b_dirty list to its b_io list and calls writeback_sb_inodes(); that loops over inodes, building a writeback_control and calling __writeback_single_inode() → do_writepages(), which invokes the filesystem's writepages operation (iomap's iomap_writepages(), or a hand-written one). Those walk the folios tagged PAGECACHE_TAG_DIRTY in the XArray—using PAGECACHE_TAG_TOWRITE to fix the set for this pass—and issue the bios that carry the data to the device, marking each folio PAGECACHE_TAG_WRITEBACK until its I/O completes.

The generic helper that does the walking has changed shape, and the old name is worth retiring explicitly. write_cache_pages(), which writeback documentation long described as the function a filesystem hands a per-page callback to, no longer exists; the last copies of it in the tree are private forks inside f2fs and btrfs. What replaced it is writeback_iter() (mm/page-writeback.c), an iterator rather than a callback, used as an ordinary loop: 

struct folio *folio = NULL;
int error;

while ((folio = writeback_iter(mapping, wbc, folio, &error)))
        error = write_one_folio(folio, wbc);

return error;

The inversion is the point. With a callback, everything the filesystem wanted to carry across pages had to travel in an opaque void *, errors had to be smuggled out through it, and the loop could not be broken out of naturally. As a loop, the filesystem keeps its state in local variables and the shared bookkeeping lives in the writeback_control itself: the first call initializes fbatch and index and, for an integrity pass, tags the dirty set; each subsequent call charges folio_nr_pages(folio) against nr_to_write and fetches the next folio. That accounting is folio-accurate, so one 2 MB folio spends 512 of the pass's budget rather than one.

The loop's exit rule differs by sync mode in a way that is easy to get backward. A background (WB_SYNC_NONE) pass stops at the first error or as soon as nr_to_write is exhausted — it is best-effort, and there will be another pass. An integrity (WB_SYNC_ALL) pass does neither: it keeps going until every folio it tagged has been dealt with, past the nr_to_write budget and past errors, stashing only the first error in saved_err and returning it at the end. It has to, because the filesystem may still have per-folio state to release, and because stopping early would break the promise that fsync() covers everything dirty at the time of the call.

The inode lists on each wb encode the progress of a pass. Dirty inodes wait on b_dirty, ordered by the time they were dirtied; when a pass starts, queue_io() moves those old enough onto b_io, the queue the pass actually drains. An inode whose folios could not all be written this time—because some were locked, under writeback, or the nr_to_write budget ran out—is requeued onto b_more_io to be retried in the next pass rather than blocking the current one. This is why a single huge dirty file cannot starve the others: each pass writes a bounded nr_to_write and rotates on. The sync_mode field is what makes a sync-triggered pass different from a periodic one—an integrity (WB_SYNC_ALL) pass, marked tagged_writepages, first snapshots the dirty set into PAGECACHE_TAG_TOWRITE and then waits for every one of those folios, guaranteeing all data present at the call is on disk, while a background (WB_SYNC_NONE) pass writes what it easily can and moves on. For a range-cyclic pass, writeback_index remembers where the last one stopped so successive periodic passes sweep the whole file over time instead of always restarting at the front. A fourth list, b_dirty_time, holds inodes whose only dirty state is a timestamp; they are not written with the others but are aged out separately after dirtytime_expire_seconds, which is how a relatime update on a file nobody has otherwise touched eventually reaches disk without costing a write every few seconds.

Finally, the pass does not end when the bios are submitted. Each folio stays marked for writeback until its I/O completes, at which point folio_end_writeback() clears the flag, clears PAGECACHE_TAG_WRITEBACK, and wakes anyone sleeping in folio_wait_writeback() — which is what an integrity sync is doing while it waits. A failure at this point has nowhere to be reported synchronously, so it is recorded on the mapping with mapping_set_error(), the mechanism section 2 described, to be collected by the next fsync() or close(). Writeback is thus the one place in the chapter where an error is deliberately stored rather than returned, and the sync family in the next section is what finally returns it.

Forcing Writeback: sync, fsync, and fdatasync

Deferred writeback is invisible until an application needs a guarantee that its data is on disk—a database committing a transaction, an editor saving a file. The sync family of system calls provides that guarantee. This section covers sync, fsync, and fdatasync, plus syncfs, and the cache-flushing primitives beneath them.

The key point these calls exist to make is that a successful write() does not mean the data is on disk—only that it is in the page cache and will be written eventually. For most programs that is exactly what they want, but any program that must survive a crash with its data intact—a database, a mail server, a package manager—needs a stronger promise, and only the sync family delivers it. These calls are also where the durability chain that runs through the whole book is finally closed: they push dirty folios through writeback into bios (Chapter 14), down to the device, and then force the device to commit its own volatile cache, so that when the call returns the data will still be there after a power loss.

sync and syncfs

sync() flushes everything. Its implementation, ksys_sync() (fs/sync.c), wakes the flusher threads to write back all dirty inodes, calls each mounted filesystem's sync_fs method, and then flushes the block devices. As in Linux 2.6, it works in two passes—an initial asynchronous sweep to start I/O everywhere, then a synchronous sweep that waits for it—so that independent devices write in parallel rather than one at a time. syncfs(fd) narrows this to the one filesystem containing the referenced file, via sync_filesystem(), which performs the same async-then-sync pair for a single superblock. Both are about whole filesystems, not individual files.

The two-pass structure is worth following literally, because the two calls arrange it differently. ksys_sync() starts with wakeup_flusher_threads(WB_REASON_SYNC), which kicks asynchronous writeback on every backing device at once and does not wait; only then does it walk the mounted filesystems with iterate_supers(), calling sync_inodes_sb() on each to wait for the data, then sync_fs twice — once with wait = 0 and once with wait = 1 — and finally sync_bdevs(false) followed by sync_bdevs(true). Every stage is thus a start-everything pass followed by a wait-for-everything pass, so that on a system with several disks the writeback overlaps instead of serializing.

sync_filesystem(), which syncfs uses, does the same dance within one superblock and is the clearest place to read it: writeback_inodes_sb() to start the I/O, sync_fs(sb, 0), sync_blockdev_nowait(), and then the waiting halves — sync_inodes_sb(), sync_fs(sb, 1), sync_blockdev(). The sync_fs method is the filesystem's own hook, and the reason it is called twice is that a journaling filesystem such as ext4 uses the first call to start a journal commit and the second to wait for it, so the metadata it has been batching is made durable together with the data. A read-only filesystem short-circuits the whole thing, and a filesystem that sets SB_I_SKIP_SYNC — typically a virtual one with nothing to write — is skipped by the global sync() as well.

The two calls differ in one respect that matters more than it looks: error reporting. sync() discards errors entirely — the system call is literally ksys_sync(); return 0;, so a failed writeback during a sync() is invisible to the caller, and a shell script that runs sync && echo safe has learned nothing. syncfs() was given a way out: each superblock keeps its own writeback error sequence in s_wb_err, each open file remembers where it last looked in f_sb_err, and syncfs returns the first error recorded anywhere on that filesystem since the file was opened. Unlike the 2.6 sync(), which historically returned before I/O completed, both calls now wait; only one of them will tell you how it went.

fsync and fdatasync

fsync(fd) flushes just the one open file and waits for it. It reaches vfs_fsync_range(), which calls the file's fsync operation; that writes the file's dirty folios with an integrity (WB_SYNC_ALL) pass and, for a real disk, follows them with a device cache flush so the data is durable even against the drive's own volatile write cache. fdatasync(fd) is the same but omits metadata that is not needed to read the data back: it still writes the file's data and any metadata required to locate it (a size extension, newly allocated blocks) but skips a pure timestamp update. For a workload that appends to a file and calls fdatasync after each record, this avoids an inode write per record while still guaranteeing the data is recoverable. Table 15-17 contrasts the four calls.

The difference between the two is drawn in exactly one place at the VFS level, and it is a satisfying one to find: vfs_fsync_range() calls sync_lazytime(inode) only when datasync is zero. That is the I_DIRTY_TIME state of the previous section — the lazily deferred timestamp parked on the wb's b_dirty_time list, which would otherwise wait up to twelve hours. fsync forces it out; fdatasync leaves it there. Everything else is delegated to the filesystem's own fsync method, which receives the datasync flag and decides for itself which of its metadata is needed to read the data back. Both are passed a byte range, incidentally, even though the system calls do not expose one: fsync(2) supplies 0 to LLONG_MAX.

That range argument exists because there is a fifth member of the family the table does not list, and it is the one most databases actually use. Opening a file with O_SYNC or O_DSYNC — or setting RWF_SYNC or RWF_DSYNC on an individual pwritev2() — makes every write durable by itself. The mechanism is not a separate path: generic_write_sync(), which the buffered and direct write paths both call on the way out, simply invokes vfs_fsync_range() over the bytes just written, with datasync set from whether the flag was the SYNC or the DSYNC variant. So O_DSYNC is precisely "call fdatasync on this range after every write," which is also why it is expensive and why databases that can batch their own fdatasync calls usually do. The same function carries one more errand: on an RWF_DONTCACHE write it starts writeback over the range immediately, since folios marked for dropbehind cannot be dropped until they are clean.

Two practical points about fsync trip up application authors often enough to be worth stating. First, ordering: fsync writes the file's data and then issues the device cache flush, so that when it returns the bytes are genuinely on stable media, not merely accepted by the drive's volatile buffer. A program that needs write A durable before write B therefore calls fsync between them; the page cache alone makes no such ordering promise. Second, directory durability: fsync on a file makes the file's contents durable, but the directory entry that gives the file its name is a property of the parent directory, so a program that creates a new file and wants both the data and the name to survive a crash must fsync the file and then fsync the parent directory. This is the classic write-a-temp-file-and-rename pattern's hidden requirement. For memory-mapped files there is a parallel call, msync() with MS_SYNC, which flushes a mapped range's dirty folios the same way, since mmap writes never pass through write() at all.

filemap_write_and_wait and Cache Flushes

Underneath these calls are two page-cache primitives. filemap_fdatawrite() starts writeback of a mapping's dirty folios with WB_SYNC_ALL, and filemap_fdatawait() waits for the in-flight writeback (the folios tagged PAGECACHE_TAG_WRITEBACK) to finish and collects any I/O error; filemap_write_and_wait_range() combines the two over a byte range and is what fsync uses. Error reporting is careful: a writeback error is stored in the mapping's wb_err field and sampled per open file, so each fsync caller is told about an I/O failure exactly once rather than having the error silently lost or reported repeatedly. Finally, durability against a device's own write cache requires more than reaching the device: fsync issues a cache flush (blkdev_issue_flush(), a REQ_PREFLUSH request from Chapter 14) so the drive commits the data to stable media before the call returns. All of these open with the same cheap test: mapping_needs_writeback() asks only whether the mapping holds any folios at all, so fsync on a file with nothing cached costs a single load and returns.

The error-reporting mechanism deserves a closer look because it fixed a long-standing hazard. Writeback errors are recorded in the mapping's wb_err as an errseq_t—a value that packs an error code with a sequence counter—and each open file remembers, in its f_wb_err, the point in that sequence it last observed. When fsync calls file_check_and_advance_wb_err(), it reports an error only if the mapping's sequence has advanced past the file's saved point, then updates the file's point. The effect is that every opener of the file is guaranteed to see a writeback failure exactly once, even if the folios that failed were long since evicted—closing the old "lost write error" hole where an fsync could return success after an earlier asynchronous writeback had already failed and been forgotten.

The encoding is worth a sentence because it explains the guarantee. An errseq_t is a single word: the low bits hold an errno, one bit above them is a seen flag, and everything above that is a counter. Recording an error stores the code and clears seen; the counter is incremented only when the error being replaced had already been observed. So a burst of identical failures that nobody has looked at does not advance the sequence, while a failure that has been reported and then recurs does — which is exactly the distinction "tell each observer once" requires, in one word and with no allocation.

There is a boundary condition here that catches people out. A file's f_wb_err is not initialized to zero but sampled from the mapping at open time, so a newly opened file starts level with whatever errors have already been recorded and will never report them. The guarantee is therefore "each open file description is told about every writeback error that happens after it was opened, exactly once" — not "every error ever." Reopening a file after a failed fsync and calling fsync again will report success, which is why the durability advice is to treat a failed fsync as unrecoverable for that data rather than to retry it.

The older mechanism has not gone away, and the two coexist for a reason. mapping_set_error() still sets AS_EIO or AS_ENOSPC in the mapping's flags alongside advancing wb_err. filemap_check_errors() reads those bits with a test-and-clear, which is the old lossy behavior — the first caller to look consumes the error and every other waiter sees success — while filemap_check_and_keep_errors() peeks without consuming, and is what the paths that must not swallow an error use. The flags survive because callers that have no struct file to carry an f_wb_err, such as writeback and truncation, still need somewhere to look.

Two finer controls round out the family. sync_file_range() lets a program start or wait on writeback for a specific byte range of a file without the full durability guarantee of fsync—useful for pacing a large streaming write so dirty data does not pile up—though it does not issue a device cache flush and so is not a durability primitive on its own. Its three flags can be combined into any of the useful shapes: SYNC_FILE_RANGE_WAIT_BEFORE waits for writeback already in flight over the range, SYNC_FILE_RANGE_WRITE starts writeback of the dirty folios in it without waiting, and SYNC_FILE_RANGE_WAIT_AFTER waits for what it started; the combination of all three has a name of its own, SYNC_FILE_RANGE_WRITE_AND_WAIT. The classic use is SYNC_FILE_RANGE_WRITE alone, issued periodically behind a large sequential write so that dirty data trickles out steadily instead of accumulating until the throttle of the previous section forces a stall. And at the very bottom, the device flush comes in two forms from Chapter 14: REQ_PREFLUSH tells the drive to commit its existing cache before the write, while REQ_FUA (force unit access) asks that a specific write bypass the volatile cache and land on stable media directly. Filesystems and fsync use these to build the exact ordering and durability guarantees a crash-safe application depends on, completing the path from a dirtied folio all the way to permanent storage.

Removing Folios from the Cache

Everything so far has put data into the cache or moved it back to disk while leaving it cached. The last question is how a folio leaves. There are two answers, and the difference between them runs through this section. A folio is invalidated when its contents have become wrong or unwanted—the file was truncated, a hole was punched, the filesystem was unmounted, an application said it would not read the data again—and it is reclaimed when its contents are still perfectly valid but the memory is needed for something else. Invalidation is a correctness operation and must succeed; reclaim is an optimization and is free to give up on any folio that is inconvenient. Both funnel into the same low-level removal, filemap_remove_folio(), which deletes the folio from mapping->i_pages, clears its mapping and index, and decrements nrpages. The section ends with the two system calls that let user space ask what is still cached.

Truncation and Invalidation

Truncation is the correctness case. When a file shrinks, the cached data beyond the new end of file is no longer part of the file and must not be visible to a later read, so truncate_inode_pages_range() (mm/truncate.c) removes it. The function works in folio batches and takes two passes over the range: the first is non-blocking and skips any folio it cannot immediately lock or that is under writeback, which clears out the great majority cheaply; the second pass revisits what remains and waits. Doing the easy work first means the expensive pass has little left to do, and it avoids starting I/O in a region that is about to be discarded anyway. Partial folios at the two ends of the range are not removed but zeroed—truncate_inode_partial_folio() clears the part that falls inside the truncated range and leaves the rest cached—which is why a truncate to a non-folio-aligned offset still leaves a valid folio behind. Before any of this, the filesystem's invalidate_folio operation is called so it can release the folio's private state, the buffer heads or iomap_folio_state of section 6.

Several details of that outline are worth making concrete. The whole function opens with mapping_empty(), so truncating a file with nothing cached costs one test. The first pass uses find_lock_entries(), which fills a batch with folios it managed to trylock, and then delete_from_page_cache_batch(), which removes the entire batch under one acquisition of the XArray lock rather than one per folio. It also calls truncate_folio_batch_exceptionals() to clear the shadow entries in the range — the eviction markers of the next subsection, which are just as much stale information about the truncated region as the folios were. The second pass is where the "must succeed" property lives: after waiting for each remaining folio's writeback it checks whether it found everything, and if not it goes back to the start of the range and sweeps again, so the function does not return until the range is genuinely empty.

The partial folios at the ends get more careful treatment in 7.0.12 than "zero and keep" suggests, because a large folio at the edge of a truncation can be mostly wasted memory. truncate_inode_partial_folio() zeroes the part inside the range and then, if the folio is large, tries to split it with try_folio_split_or_unmap() — respecting the mapping's minimum order from section 3, since it cannot produce folios smaller than the filesystem's block size. If the split succeeds and the folio is clean, the piece inside the truncated range is genuinely freed rather than merely blanked; a second split is attempted at the far edge for the same reason, which matters most for shmem, where the zeroed remainder would otherwise occupy memory forever. Only when the split fails does the old zero-the-whole-folio behavior stand. One exception: if the mapping is marked AS_INACCESSIBLE — the guest-memory case from section 2 — the zeroing is skipped entirely, because the kernel may not touch those bytes at all.

Truncation is serialized against readers and faults by the invalidate_lock in the address_space, one of the three locks noted in section 2. Without it a fault could look up a folio, find it present, and install it in a page table just as truncation removed it, leaving a process with a mapping of data that is no longer in the file. Holding invalidate_lock for writing across the truncate and for reading across the fault closes that window. A related entry point, truncate_inode_pages_final(), is what a filesystem calls from evict_inode when an inode is being destroyed: it first marks the mapping AS_EXITING so that reclaim running concurrently does not install eviction bookkeeping into a cache that is about to disappear, then truncates everything.

Invalidation proper is the softer relative. invalidate_mapping_pages()—a thin wrapper over mapping_try_invalidate()—drops only the folios that are clean, unmapped, unlocked, and not under writeback, and it never blocks on I/O. Anything dirty or in use is simply left alone, because the caller is expressing a preference, not a requirement. The strict variant, invalidate_inode_pages2_range(), is for callers that need the cache range genuinely gone: it unmaps the folios from every process that has them mapped, writes back or launders dirty ones through the filesystem's launder_folio operation, and returns -EBUSY if it still cannot remove a folio. Direct I/O uses it to discard cached copies of a range it is about to write behind the cache's back, so a later buffered read does not return stale data. Table 15-18 contrasts the three.

Reclaim and Shadow Entries

Reclaim is the other exit, and it is the one that governs the cache's size. The page cache has no fixed limit: it grows until memory runs short, at which point the memory-management subsystem begins evicting folios to make room. Cached file folios sit on per-node LRU lists through the lru field of section 3, and shrink_folio_list() (mm/vmscan.c) walks the inactive list deciding what to drop. A clean folio can be freed immediately, since the copy on disk is authoritative; a dirty one must be written first, which is why reclaim under pressure also kicks writeback rather than waiting on the folio itself. The actual detachment is __remove_mapping(), which takes the folio lock and xa_lock, rechecks that nobody has taken a reference or dirtied the folio in the meantime, and only then removes it—the same reference-versus-lock distinction of section 3, now used to decide whether a folio is safe to destroy.

The recheck is done with folio_ref_freeze(), an atomic compare-and-swap that succeeds only if the reference count is exactly the expected value and, in the same operation, drives it to zero so that no one else can acquire one afterwards. The order of the two tests that follow is deliberate and documented at length in the source: the dirty flag is examined after the freeze, because a thread that still held a reference could have dirtied the folio between the two, and a reclaim that dropped a dirty folio would lose a user's data. If the freeze fails, or the folio turns out to be dirty, the reference count is restored and reclaim moves on to the next candidate — the "free to give up" half of the distinction this section opened with.

Reclaim does not always leave the XArray slot empty. When a file folio is evicted, workingset_eviction() (mm/workingset.c) returns a small value that encodes when, in the LRU's own notion of time, the eviction happened, and __remove_mapping() stores that value into the slot the folio occupied. These are the shadow entries the XArray section described: not folios, but xa_is_value() markers that remember a folio used to be here. Their purpose is refault detection. If the same index is read again and the kernel finds a shadow entry, workingset_refault() compares the recorded eviction time against how much LRU activity has happened since; a short refault distance means the folio was thrown away too early—it was part of the workload's working set—and the new folio is placed directly on the active list rather than starting at the bottom of the inactive one. This is how the kernel distinguishes a file being streamed through memory once from a file being used repeatedly, without any hint from the application.

Shadow entries cost memory of their own, so they are themselves reclaimable: workingset_update_node() tracks XArray nodes that hold nothing but shadows, and a shrinker frees them under pressure. An inode whose mapping has been reduced to shadow entries is likewise put back on the superblock's inode LRU (mapping_shrinkable()) so the inode itself can eventually be reclaimed. On kernels built with the multi-generation LRU (CONFIG_LRU_GEN), which is the default on many distributions, the eviction and refault bookkeeping is handled by the generational equivalents lru_gen_eviction() and lru_gen_refault(), but the idea is the same: remember enough about an evicted folio to tell a genuine working-set member from a one-time read.

Two cases deliberately get no shadow at all, and one of them closes a loop opened above. A mapping marked AS_EXITING — set by truncate_inode_pages_final() when an inode is being destroyed — is skipped, and the comment in __remove_mapping() explains that this is a correctness requirement rather than a saving: inode reclaim needs to find the XArray empty, and a shadow planted behind its back would strand the nodes. DAX mappings are skipped too, since their exceptional entries would be confused with shadow ones. When the removal does empty a mapping down to nothing but shadows, mapping_shrinkable() notices and inode_lru_list_add() puts the inode back on the superblock's LRU, so the inode can eventually follow its folios out of memory. Reclaim also gives the filesystem a last word here: the free_folio operation, if the address_space defines one, is called after the folio has left the XArray.

Dropping the Cache on Request

Applications and administrators can also ask for cached data to be dropped, and every such interface lands on the invalidation functions above. posix_fadvise() with POSIX_FADV_DONTNEED (mm/fadvise.c) first starts writeback of the range so dirty data is not lost, then calls invalidate_mapping_pages() on the whole folios inside it—deliberately preserving the partial folios at each end, on the theory that it is better to keep a little unneeded memory than to discard memory something else still wants. It is the right tool for a backup or copy program that streams a huge file once and should not evict everyone else's cache to do it.

It is a hint, though, and it fails more often than its users expect. The writeback it starts is filemap_flush_range(), which only begins the I/O; a program that writes a chunk and immediately advises it away usually finds the folios still under writeback and therefore not droppable. Even for clean data there is a subtler obstacle: a folio just read or written is likely to be sitting in a per-CPU LRU staging batch, which holds a reference and defeats the invalidation. The kernel goes to some trouble about this — it calls lru_add_drain() to flush the local CPU's batch first, then invalidates through mapping_try_invalidate() asking it to count the folios it could not remove, and if any failed it drains every CPU's batch and tries the range once more. Two attempts and a cross-CPU drain is as hard as the kernel will try; anything still referenced stays.

The two neighboring hints are narrower than they look. POSIX_FADV_NOREUSE sets FMODE_NOREUSE on the file, but the only thing that reads that flag is vma_has_recency(), so it changes reclaim's behavior for mapped pages of the file — telling it not to treat references through such a mapping as evidence of a working set, alongside the MADV_SEQUENTIAL and MADV_RANDOM hints from section 5 — and does nothing at all for folios reached only through read() and write(). And madvise() with MADV_DONTNEED is not the mapped equivalent of POSIX_FADV_DONTNEED: on a file-backed mapping it removes the page-table entries and nothing more, leaving every folio in the page cache, so the next access is a cheap minor fault. It frees memory only for anonymous mappings, where the page table was the only reference.

The blunt instrument is /proc/sys/vm/drop_caches (fs/drop_caches.c). Writing 1 walks every superblock's inodes calling invalidate_mapping_pages() on each mapping; writing 2 asks the slab shrinkers to free reclaimable kernel objects, chiefly dentries and inodes; writing 3 does both. Because it uses the non-blocking invalidation path it drops only clean folios, so the conventional advice is to run sync first if the intent is to empty the cache completely — and, since sync() is the one call in the previous section that cannot report failure, to not read too much into its having returned. It is a diagnostic and benchmarking aid rather than a tuning knob—the cache is supposed to fill memory, and dropping it merely guarantees that the next round of work will be served from disk.

Asking What Is Cached: mincore and cachestat

The interfaces above remove folios from the cache. Two system calls do the opposite and only report what is there. The older one is mincore(), described in Chapter 9, which asks about a range of the caller's address space. It walks the page tables under mmap_lock, and where it finds no PTE for a file-backed page, mincore_page() (mm/mincore.c) looks the file index up with filemap_get_entry() and reports the page as resident if the folio there is up to date. From the page cache's point of view this answer has three limits. The file has to be mapped before it can be asked about. The result is one byte per page, which the caller must add up itself. And the only answer is “resident” or “not resident”: mincore() cannot tell whether a page is dirty, or whether a page that is absent was evicted a moment ago or was never read.

cachestat(), added in Linux 6.5 (cf264e1329fb), asks the page cache directly. It is system call 451 on every architecture and is built unless CONFIG_CACHESTAT_SYSCALL, which defaults to y and is visible only with CONFIG_EXPERT, is turned off: 

/* include/uapi/linux/mman.h */
struct cachestat_range {
        __u64 off;                      /* byte offset */
        __u64 len;                      /* bytes; 0 means to end of file */
};

struct cachestat {                      /* all counts are in pages */
        __u64 nr_cache;
        __u64 nr_dirty;

};

long cachestat(unsigned int fd, struct cachestat_range *range,

The system call in mm/filemap.c turns the byte range into page indices and returns five counts for the whole range. A len of zero extends the range to the largest possible index, which covers the rest of the file. flags must be zero, and the call fails with EOPNOTSUPP on a hugetlbfs file. It also fails with EPERM if can_do_cachestat() rejects the caller. That check repeats the rule mincore() applies and was added only in 6.14, as Chapter 9 explains. Because the call works on file->f_mapping, not on the inode, a descriptor for a block device reports on the device's own bd_mapping, the mapping that section 2.3 showed blkdev_open() installing.

All of the work happens in filemap_cachestat(), a single xas_for_each() walk over mapping->i_pages under rcu_read_lock(). The walk never dereferences a folio. It takes no reference and no lock, and it reads everything it needs from the XArray itself. xas_get_order() gives the size of a multi-index entry, so a large folio counts as 1 << order pages, minus any part that lies outside the requested range. The PAGECACHE_TAG_DIRTY and PAGECACHE_TAG_WRITEBACK marks of section 4.3 supply nr_dirty and nr_writeback. The first version of the call did look at the folio. It tested the folio's flags without holding a reference, and Jann Horn pointed out that the folio could be freed and reused as something else while it was being read. Linux 6.8 (3a75cb05d53f) changed the walk to read only the XArray, which had two consequences. Any folio entry now counts as cached, including one that readahead has inserted but whose read has not yet finished, which mincore() would report as absent. And a tmpfs file always reports zero dirty and zero writeback pages, because shmem's dirty_folio operation is noop_dirty_folio(), which never sets the tag. A tmpfs folio is “cleaned” only by being swapped out. On a long range the loop calls xas_pause() and cond_resched_rcu() whenever a reschedule is due, so a query over a huge file does not hold up the CPU.

The two eviction counts come from value entries. A shadow entry that reclaim left behind (section 9.2) adds its pages to nr_evicted. workingset_test_recent() (mm/workingset.c) then applies the test that workingset_refault() would apply if the page were read now. The classic LRU checks whether the refault distance is within the current working-set size. The multi-generation LRU checks whether the shadow's generation is still within MAX_NR_GENS of the newest one. A page that passes is also counted in nr_recently_evicted: it was pushed out by memory pressure and would be treated as part of the working set if it came back. A high recently-evicted count is therefore a cheap, per-file sign that a workload's data does not fit in memory, which a program can read without parsing /proc/vmstat or knowing which cgroup owns the pages. For tmpfs the value entry is a swap entry instead. Since 6.9 (d5d39c707a4c) the call follows it to the swap cache with swap_cache_get_shadow() and tests that shadow instead. An entry poisoned by a swap-in error counts as evicted but never as recent. The recency test can need fresh memory-cgroup statistics, and flushing them may sleep, which is not allowed inside an RCU read-side section. Since 6.10 (5a4d8944d6b1) the call therefore flushes once, rate-limited, before taking rcu_read_lock(), and passes flush = false to each recency test.

Nothing in the walk is locked or pinned, so the five numbers are a snapshot that may already be out of date when the call returns. The source comment says so, and like mincore() the result should be treated as a hint. In exchange, the call is cheap enough to use routinely. A database can decide whether to prefetch a file, a cache warmer can check how much of a file survived a restart, and a monitor can watch dirty and recently-evicted counts for the files it cares about. Summary

This chapter examined the page cache, the kernel's in-memory cache of disk data through which nearly all file I/O passes. The cache exists to turn repeated reads into memory accesses and to defer and batch writes; its central object is the address_space, one per file, directory, or block device, tying together the cached data, the operations that fill and flush it, and the owning inode. The unit it caches is now the folio—a run of one or more contiguous pages named by its head page—so a single large folio can hold, lock, dirty, and write many pages at once, replacing the page-at-a-time model of Linux 2.6. The folio also turned a runtime invariant into a type: a struct folio * is by definition a head page, which is what let the conversion proceed filesystem by filesystem without rewriting the cache each time.

The cache is indexed by the XArray in address_space.i_pages, keyed by folio index, with per-entry marks that let writeback find dirty folios without scanning; it also holds value entries—shadow entries, the swap entries of tmpfs, and DAX entries. A large folio occupies a whole range of slots as one multi-index entry, so a 2 MB folio is one lookup and one dirty mark rather than 512. Reads fill folios through read_folio and readahead, which grows both its window and its folio order as a sequential run lengthens; writes dirty them through write_begin/write_end in chunks as large as the mapping allows, copying without faulting so that a memory-mapped source buffer cannot deadlock the filesystem; and memory mappings share the very same folios through filemap_fault, which drops mmap_lock and retries rather than sleeping on a disk read while holding it. Individual disk blocks are still described by buffer_head structures—now hanging off a folio's private data, and confined largely to metadata, journaling, and unconverted filesystems—while the high-throughput filesystems handle file data through the extent-based iomap framework, which asks the filesystem to describe a whole extent once instead of a block at a time and tracks sub-folio state in a bitmap rather than a chain of descriptors. Buffer heads have become optional enough to be a build option.

Dirty folios are written back by per-backing-device flusher work (wb_workfn), the successor to pdflush, paced by a throttle that meters each writer against the bandwidth its device is actually achieving; the per-folio walk that used to be the callback-driven write_cache_pages() is now the writeback_iter() loop, and its budget is charged in pages so that one large folio spends what it is worth. Because writeback happens long after the write() that caused it, an I/O failure has nowhere to be returned and is instead recorded on the mapping, which is why the sync family is where durability and error reporting meet: fsync and fdatasync flush one file and issue the device cache flush that makes the data survive a power loss, and each reports every writeback error that occurred after the file was opened exactly once through the errseq_t mechanism—while sync(), alone in the family, cannot report an error at all. Folios leave the cache by two routes: invalidation, when their contents have become wrong or unwanted, and reclaim, when the memory is needed elsewhere—the former obliged to succeed and therefore willing to loop and wait, the latter free to skip any folio that is inconvenient, and leaving a shadow entry behind so that a quick refault can be recognized as a working-set member rather than a first read. cachestat() reads that same state back for user space: cached, dirty, under writeback, and evicted pages, counted straight from the XArray's entries and marks without touching a folio. The through-line is that the page cache has been generalized and scaled. Folios let one cache entry cover many pages, the XArray gives a cleaner and faster index, and per-device writeback replaces a shared thread pool— each change trading the page-at-a-time assumptions of the 2.6 era for structures that suit multi-gigabyte files, many-core systems, and modern storage. A second, quieter through-line is that the interfaces have been turned inside out. writepage became writepages, a per-page callback became a loop, one block at a time became one extent at a time, and an all-or-nothing huge page became a folio of whatever order fits — in every case the kernel stopped asking the filesystem the same small question repeatedly and started asking it one large question instead. It also closes the durability story of the last few chapters: a write() only reaches the cache, and it is writeback and the sync family that carry data through the block layer to stable storage.
