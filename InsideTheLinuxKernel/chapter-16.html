Reading and writing a file draws on everything the last several chapters built: the VFS abstraction of Chapter 12, the block layer of Chapter 14, and the page cache of Chapter 15. This chapter is about the layer where a process's read() and write()—and its memory mappings, direct I/O, and asynchronous submissions—meet those facilities. It picks up after the VFS has resolved which file's methods to call, and follows each access down to the point where a read has delivered data to the process and a write has left data ready for the device. What happens below that point is the writeback and block-layer work of the previous two chapters.

The mechanisms have changed more than the concepts since Linux 2.6. The unifying interface is no longer read/write plus a separate aio_read/aio_write, but a single pair of iterator methods, read_iter and write_iter, that every access mode funnels through; memory mappings now store their regions in a maple tree rather than a red-black tree; direct I/O runs through the iomap framework; and the asynchronous story is dominated by a facility that did not exist in 2.6—io_uring. Two structures carry that unification and recur on every page of this chapter: struct kiocb, which says what kind of I/O this is and where in the file it lands, and struct iov_iter, which says where the bytes are without committing to whether that is user memory, kernel memory, a list of pages, or a pipe. A filesystem that implements read_iter and write_iter correctly gets buffered I/O, direct I/O, memory-mapped writeback, splice, and both asynchronous interfaces at once, because all of them arrive as some combination of those two structures.

One family of interfaces stands slightly apart and is easy to overlook. splice(), sendfile(), and copy_file_range() move file data without it ever appearing in the calling process's address space, and for a program that only forwards bytes from one descriptor to another they are not an optimization but the natural expression of the task. Section 7 takes them up, and shows that even there the destination is reached by a write_iter call. This chapter covers each mode in turn and shows how they all reduce to the same small interface underneath.

The Ways to Access a File

Chapter 15 built the page cache; this chapter is about the operations that drive it. A process can reach the bytes of a file in several ways, and choosing among them is really choosing how much of the kernel's machinery to use. At one extreme a plain read() leans on everything the kernel offers—caching, read-ahead, and deferred writeback; at the other, direct I/O strips almost all of it away and hands the application the raw transfer. This section lays out the modes at a glance; the rest of the chapter takes each in depth. Figure 16-1 shows how they relate.

It helps to see the choices as two independent axes rather than a single menu. The first axis is where the data lives on its way to and from the device: through the page cache, which buffers it in kernel memory and lets many processes share it, or around the cache with direct I/O, which moves bytes straight between the device and the application's own buffers. The second axis is when the call returns: synchronously, when the work is finished, or asynchronously, immediately, with the result reaped later. The two axes are orthogonal—one can do cached asynchronous I/O or direct synchronous I/O—which is exactly why the kernel funnels every combination through a single pair of methods, read_iter and write_iter, rather than a separate code path per mode. The mode is selected partly at open() time through flags such as O_DIRECT and O_SYNC, and partly by which system call or interface a program uses to issue the request. A third axis, less often drawn because it applies only to transfers between two descriptors, is whether a user buffer is involved at all: the zero-copy and copy-offload calls of section 7 remove it, and in the reflink case remove the data movement with it. The sections below walk the modes in that order; Table 16-1 collects them.

Two qualifications keep that picture honest. The first is that the caching axis is no longer the two-valued choice it was in 2.6. Between full caching and O_DIRECT sits uncached buffered I/O—ordinary buffered reads and writes, with no alignment rules, whose folios are marked to be dropped as soon as the transfer is done—requested per call with RWF_DONTCACHE and described in section 6.1. Beyond O_DIRECT sits DAX, where a filesystem on byte-addressable persistent memory has no cache to bypass because the storage is memory: ext4_file_read_iter() and its peers test IS_DAX() before anything else and route the transfer to dax_iomap_rw(), which copies straight out of the medium with no page cache, no bio, and no block layer beneath it. A mapping of such a file maps the persistent memory itself, which is why vm_operations_struct needs a pfn_mkwrite method at all.

The second qualification is that a mode is requested by the caller but must be supported by the file. Since 6.x that support is declared, not inferred: struct file_operations carries a fop_flags field whose bits—FOP_BUFFER_RASYNC, FOP_BUFFER_WASYNC, FOP_DIO_PARALLEL_WRITE, FOP_MMAP_SYNC, FOP_DONTCACHE—name the optional behaviours a filesystem can honour. Of the major filesystems, XFS and ext4 set most of them, btrfs and f2fs fewer. This matters when reading the sections that follow, because several of the capabilities they describe are not properties of the kernel at all but of the particular filesystem the file happens to live on, and a request the file cannot honour is either rejected with -EOPNOTSUPP or quietly downgraded to the synchronous, cached default.

Buffered and Synchronous Access

The default is buffered access through read() and write(). A read copies data from the page cache into the process, filling the cache from disk on a miss and reading ahead for sequential patterns; it blocks until the requested bytes are available (though the kernel may return fewer than asked). A write copies data into the cache, marks it dirty, and returns immediately—the deferred write of Chapter 15—so the device is not touched inline. This is the mode almost every program uses and the one the next two sections dissect.

Buffered access is the default because the page cache pays for itself. A second process opening the same file finds its data already in memory; a re-read is served without touching the disk; sequential reads are anticipated by read-ahead so the data arrives before it is asked for; and a burst of small writes is coalesced in the cache and written back once, in large contiguous chunks, instead of one device transfer per call. The cost is a copy—the bytes pass through kernel memory on their way between the device and the process—and a window during which written data lives only in volatile RAM. For the overwhelming majority of programs that trade-off is invisible and favourable, which is why read() and write() remain the interface most code ever uses.

Two details of the buffered contract matter throughout the chapter. First, transfers can be partial: read() may return fewer bytes than requested (it has reached end-of-file, or only some pages are ready), and write() may accept fewer than offered (a signal arrived, or a limit was hit). Correct programs treat the return value as the count actually transferred and loop. Second, each call advances the open file's position (ki_pos, drawn from the file's f_pos) by that count, so successive calls walk through the file; the positional variants pread()/pwrite() instead carry an explicit offset and leave f_pos untouched.

That second point deserves more precision than it is usually given, because the position is shared state and the kernel protects it. When a descriptor may be reached from more than one thread, fdget_pos() in fs/file.c takes the file's f_pos_lock mutex for the duration of the call, and file_needs_f_pos_lock() shows exactly when: the file must have FMODE_ATOMIC_POS (which open() sets for regular files and directories) and must either be shared—its reference count is more than one—or be a directory. So two threads issuing read() on the same descriptor do not race on f_pos; they serialize on a mutex, and each gets a distinct, correctly ordered slice of the file. The real argument for pread()/pwrite() is therefore not correctness but concurrency: they take no position lock, so many threads can read one descriptor in parallel instead of queueing behind each other. The same test is why an unshared descriptor pays nothing at all—the common single-threaded case never touches the mutex.

The buffered family is also wider than read() and write(). readv() and writev() take an array of iovec segments and scatter or gather across them in one call; preadv() and pwritev() add an explicit offset; and preadv2() and pwritev2() add a per-call flags argument. That last pair matters out of proportion to how often it is used, because it is the only way to change the behaviour of a single request without changing the open file: RWF_NOWAIT, RWF_HIPRI, RWF_SYNC, RWF_DSYNC, RWF_APPEND, and RWF_DONTCACHE all arrive this way and become IOCB_* bits, as section 2.2 describes. O_APPEND is the instructive counter-example: it is fixed at open(), becomes IOCB_APPEND, and causes the write path to resolve the position from i_size while holding the inode lock rather than from f_pos—which is what makes appending from several processes atomic, and why an append cannot simply be expressed as a seek followed by a write.

Opening the file with O_SYNC or O_DSYNC changes only the write side: each write then blocks until its data reaches stable storage before returning, so the deferred-write window closes. Note what does not change—the data still passes through the page cache and is still there afterwards, so this is a write-through mode rather than a way of bypassing the cache, which is the distinction section 3.3 draws out once the buffered write path has been traced.

Memory-Mapped and Direct Access

Memory mapping with mmap() makes a file appear as an array of bytes in the process's address space; the program then reads and writes the file simply by dereferencing pointers, and the kernel pages data in on demand through faults and writes dirty pages back through the same writeback path. It shares the page cache with read()/write(), so the two views of a file stay coherent: a page faulted in by a load is the very same cache folio a concurrent read() would copy from. Because the mapping is demand-paged, only the parts a program actually touches are ever brought in, and no read()/write() system call stands between the process and its data—the fault handler runs instead. A shared mapping (MAP_SHARED) propagates stores back to the file; a private one (MAP_PRIVATE) keeps them process-local through copy-on-write. Mapping is the mechanism behind loading executables and shared libraries as well as an explicit tool for random access to large files, and it is the subject of its own section later in the chapter.

Direct I/O, selected with the O_DIRECT open flag, goes the other way: it bypasses the page cache entirely, transferring data straight between the device and the process's own buffers. It exists for applications—databases above all—that maintain their own cache and would only be slowed by a second copy in the kernel's; for them the page cache is wasted memory and an unwanted extra copy, and direct I/O gives them a predictable transfer whose caching policy they control themselves. The freedom is not free. Direct I/O demands aligned transfers, and it gives up read-ahead and deferred writes, so every access is a real device round-trip. It also gives up the automatic coherency that the shared cache provides: the kernel must flush and invalidate any cached pages that overlap a direct transfer so the two paths do not disagree, a subtlety the direct-I/O section returns to.

The alignment requirement is worth flagging here because the familiar summary—"everything must be a multiple of the block size"—is not what 7.0.12 enforces. There are two independent alignments, one for the user buffer and one for the file offset, and they are usually different numbers; getting either wrong yields -EINVAL with no indication of which. A program should not guess at them, and does not have to: statx() reports both in the STATX_DIOALIGN fields. Section 6.3 gives the derivation.

One long-standing cost of direct I/O has been reduced rather than removed. Because a direct write bypasses the page cache, filesystems historically serialized direct writers against each other with the inode's exclusive lock, which turned O_DIRECT into a bottleneck for exactly the many-threaded database workloads it was built for. A filesystem that can guarantee correctness without that lock now says so by setting FOP_DIO_PARALLEL_WRITE in its fop_flags; XFS and ext4 both do, so non-overlapping direct writes from many threads to one file proceed concurrently. It is a good illustration of the qualification made above: the mode is the same, but what it costs depends on the filesystem.

Asynchronous Access

All the modes above are, by default, synchronous: the system call returns only when the data has been copied (a read) or at least cached (a buffered write). That is fine when a program has nothing better to do than wait, but a server juggling thousands of connections cannot afford a blocked thread per outstanding I/O. Asynchronous access lets a program submit an I/O and continue running, collecting the result later; the completion axis is orthogonal to the caching axis, so an asynchronous request can be buffered or direct just as a synchronous one can. Under the hood asynchrony is simply a property of the kiocb: when its completion callback (ki_complete) is set, the lower layers may return before the transfer finishes and invoke the callback when it does.

That last sentence understates one difficulty, and the difficulty is the reason the older interface disappointed. Setting a callback lets a path return early, but it does not by itself give the path anywhere to return early from. Direct I/O has an obvious such point: the bio is submitted, and the completion arrives as an interrupt. The buffered read path does not—when it finds a folio that is not uptodate it simply sleeps on the folio lock, and a sleeping thread is precisely what asynchrony is meant to avoid. This is why POSIX AIO on a buffered file usually completed inline: there was no way to hand back an unfinished buffered read. The fix is IOCB_WAITQ, a flag that tells the read path to attach a wait-queue entry to the folio and return -EIOCBQUEUED instead of sleeping, so that unlocking the folio later wakes a callback rather than a thread. It works only where the filesystem has been audited for it, which is what FOP_BUFFER_RASYNC and FOP_BUFFER_WASYNC declare; io_uring checks the flag before it will even try, and generic_write_checks() rejects an IOCB_NOWAIT write outright unless the request is direct or the filesystem advertises FOP_BUFFER_WASYNC. Asynchronous buffered I/O, in other words, is not a property of io_uring but a capability io_uring was finally able to ask for.

Linux has two facilities for this. The older is the POSIX-style AIO built on io_submit() and a kernel aio context—the interface Linux 2.6 provided—which in practice is only truly asynchronous for direct I/O (a buffered request usually completes inline) and is heavy on system calls, one per submission and one per reaping. The newer, and now dominant, is io_uring: a pair of shared-memory ring buffers through which a program submits requests and reaps completions with few or no system calls, asynchronous for buffered and direct I/O alike and for network as well as storage. Neither, however, is a separate I/O path: both are submission-and-completion frames fitted around the machinery of the earlier sections, a point section 8.3 returns to once the details are in hand. The File Access Interface

Beneath every mode is one small interface. A filesystem exports two methods for moving file data—read_iter and write_iter—and each call to them carries two objects: a kiocb describing the I/O in progress and an iov_iter describing the memory buffer. Understanding these three is the key to the whole chapter, because buffered, direct, and asynchronous access differ only in how they set them up.

The shape of the chapter follows from that. Every access mode first converges on this interface—a read(), a readv(), an io_submit(), and an io_uring read all end up calling the same read_iter—and only then diverges again inside the method, according to the flags in the kiocb, into the cached path or the direct path. The three objects are the seam between those two halves: the sections that follow trace each one in turn, and the rest of the chapter is largely the story of how the different modes populate them.

read_iter and write_iter

In Linux 2.6, file_operations had four data methods: read and write for synchronous I/O, and aio_read/aio_write for asynchronous. Modern kernels collapse them into two iterator methods (include/linux/fs.h): 

struct file_operations {
        ...
        ssize_t (*read)(struct file *, char __user *, size_t, loff_t *);
        ssize_t (*write)(struct file *, const char __user *, size_t, loff_t *);
        ssize_t (*read_iter)(struct kiocb *, struct iov_iter *);
        ssize_t (*write_iter)(struct kiocb *, struct iov_iter *);
        int     (*mmap)(struct file *, struct vm_area_struct *);
        int     (*mmap_prepare)(struct vm_area_desc *);
        ssize_t (*splice_read)(struct file *, loff_t *,
                               struct pipe_inode_info *, size_t, unsigned int);
        ssize_t (*splice_write)(struct pipe_inode_info *, struct file *,
                                loff_t *, size_t, unsigned int);
        ssize_t (*copy_file_range)(struct file *, loff_t, struct file *,
                                   loff_t, size_t, unsigned int);
        loff_t  (*remap_file_range)(struct file *, loff_t, struct file *,
                                    loff_t, loff_t, unsigned int);
        int     (*uring_cmd)(struct io_uring_cmd *, unsigned int);
        fop_flags_t fop_flags;      /* FOP_* capabilities, see section 1 */
        ...
};

The plain read/write members still exist for simple character drivers, but regular files implement read_iter and write_iter—generically generic_file_read_iter() and generic_file_write_iter(). The change is more than cosmetic: because both take a kiocb (which can request asynchronous completion) and an iov_iter (which can describe any kind of buffer), the same method serves a synchronous read(), an O_DIRECT transfer, a scatter-gather readv(), an io_submit(), and an io_uring request. There is no longer a separate asynchronous entry point; asynchrony is a property of the kiocb, not of the method.

The excerpt above is deliberately wider than the two methods this section is named for, because the data methods a filesystem may implement are more than two and it is easy to come away believing otherwise. mmap (or, on filesystems converted to the newer form, mmap_prepare) is how section 5 reaches the same bytes through page faults; the splice_read/splice_write pair and copy_file_range/remap_file_range are the zero-copy and copy-offload entry points of section 7; and uring_cmd is a passthrough channel by which io_uring can hand a device-specific command to a driver without an equivalent system call existing at all. What unifies them is not that they share a signature—plainly they do not—but that all of them either take an iov_iter or, as with splice, are implemented by building one. The last member shown, fop_flags, is the capability declaration section 1 introduced: the same table that says what a filesystem can do also says how well it can do it.

Even a bare read() reaches the file through this iterator interface. The VFS dispatcher vfs_read() prefers read_iter whenever a file provides it, and the wrapper new_sync_read() (fs/read_write.c) does the adaptation on the fly: 

static ssize_t new_sync_read(struct file *filp, char __user *buf,
                             size_t len, loff_t *ppos)
{
        struct kiocb kiocb;
        struct iov_iter iter;
        ssize_t ret;

        init_sync_kiocb(&kiocb, filp);      /* synchronous: ki_complete stays NULL */
        kiocb.ki_pos = (ppos ? *ppos : 0);
        iov_iter_ubuf(&iter, ITER_DEST, buf, len);   /* wrap the user buffer */

        ret = filp->f_op->read_iter(&kiocb, &iter);
        BUG_ON(ret == -EIOCBQUEUED);        /* a sync call must not queue */
        if (ppos)
                *ppos = kiocb.ki_pos;       /* publish the advanced position */
        return ret;
}

So the "old" system call is now just the "new" interface with a throwaway kiocb and a one-segment iov_iter built around the user's buffer. The symmetry is exact on the write side (new_sync_write() uses ITER_SOURCE). Two things in this snippet recur below: the call is synchronous precisely because init_sync_kiocb() leaves ki_complete unset, which is why the queued-completion return -EIOCBQUEUED can never appear here; and the file's current offset is copied into ki_pos before the call and read back afterward, because the method advances ki_pos by the number of bytes it moved.

struct kiocb

A kiocb ("kernel I/O control block," include/linux/fs.h) is the state of one in-flight I/O. It names the file (ki_filp), the position (ki_pos), the flags that select the mode (ki_flags), an I/O priority, and—crucially—an optional completion callback (ki_complete). When ki_complete is set, the I/O is asynchronous: the method may return -EIOCBQUEUED and call the callback later; when it is NULL, the caller waits. The flags in ki_flags are how each mode announces itself.

It is worth being clear about what the object is not. A kiocb is not the open file; it is the description of a single transfer against that file, created fresh for each call and discarded when the call completes. For a synchronous access it lives on the caller's stack, as new_sync_read() showed; for an asynchronous one libaio or io_uring keeps it alive inside a larger request structure until the completion callback fires. Its ki_flags are not recomputed on every call either: open() folds the file's O_DIRECT, O_SYNC, and O_APPEND bits into a precomputed file->f_iocb_flags, and init_sync_kiocb() simply copies that snapshot into ki_flags, so the per-call setup stays cheap. Higher layers may add per-request flags—IOCB_NOWAIT and IOCB_HIPRI come from RWF_* modifiers or from io_uring rather than from the open flags. 

struct kiocb {
        struct file        *ki_filp;      /* the file being accessed */
        loff_t             ki_pos;        /* file offset of this I/O */
        void (*ki_complete)(struct kiocb *iocb, long ret); /* async completion */
        void               *private;      /* scratch for the lower layers */
        int                ki_flags;      /* IOCB_* mode flags */
        u16                ki_ioprio;     /* I/O priority */
        u8                 ki_write_stream; /* placement hint for the device */

        /* async buffered reads only; valid IFF IOCB_WAITQ is set */
        struct wait_page_queue *ki_waitq;
};

Two fields carry more weight than their size suggests. ki_pos is the transfer's own offset: the VFS seeds it from the open file's f_pos (or, for pread()/pwrite() and every asynchronous request, from an explicit argument), and the method updates it in place as it consumes bytes, which is what lets short transfers resume correctly. ki_complete is the single switch between synchronous and asynchronous behaviour for the entire stack below: the same generic_file_read_iter() either blocks or returns -EIOCBQUEUED based only on whether this pointer is set. The private field is scratch space for the lower layers—iomap's direct-I/O code, for instance, hangs its per-I/O state off it.

The excerpt above is the whole structure, and its brevity is the point: eight members is the entire vocabulary in which every access mode in this chapter describes itself. Two of them are recent enough that Linux 2.6 had no counterpart. ki_waitq is the mechanism behind the asynchronous buffered I/O of section 1.3: it is valid only when IOCB_WAITQ is set, and it points at the wait-queue entry the read path attaches to a folio so that unlocking the folio later completes the request instead of waking a blocked thread. ki_write_stream is newer still and points the other way, down rather than up. It is a placement hint that the block layer copies verbatim into bio->bi_write_stream, letting a device that supports data placement—an NVMe drive with flexible data placement, for instance—group writes that are expected to be overwritten or deleted together into the same erase unit, which reduces the write amplification the drive would otherwise incur. io_uring exposes it directly as sqe->write_stream. Neither field changes the shape of the interface; both are evidence of what a stable, narrow interface buys you, since adding a capability that reaches from a system call to a device firmware feature cost one byte and no new method.

struct iov_iter

An iov_iter ("I/O vector iterator," include/linux/uio.h) is the universal description of the memory a transfer moves bytes to or from. It abstracts where the buffer lives behind a small set of operations, so one body of code can copy into a user buffer, a kernel buffer, a list of pages, or a discard sink without caring which. Its iter_type selects the backing: ITER_UBUF and ITER_IOVEC for user buffers, ITER_KVEC for kernel buffers, ITER_BVEC for pages (the form used by the block layer and direct I/O), ITER_FOLIOQ and ITER_XARRAY for folios held in a network filesystem's own structures, and ITER_DISCARD. Code moves data through it with copy_to_iter()/copy_from_iter() (and folio variants such as copy_folio_to_iter()), queries the remaining bytes with iov_iter_count(), and advances it with iov_iter_advance(). Figure 16-2 shows why this matters: the same read_iter serves every access mode because the mode only chooses which kind of iov_iter it hands in.

Two properties make the abstraction work. First, an iov_iter carries a direction as well as a shape: it is built with ITER_DEST for a read (bytes flow into the buffer) or ITER_SOURCE for a write, so a single descriptor type expresses both halves of I/O and the copy helpers refuse to move data the wrong way. Second, it is a cursor, not a static description: every copy_to_iter() or copy_from_iter() both transfers bytes and advances the iterator past them, decreasing the count it reports. A transfer therefore drains its iov_iter as it proceeds, and a partial copy leaves the cursor sitting exactly where the next byte should go—which is how the read and write loops of the next section resume cleanly after a page-at-a-time copy.

The shape ranges from trivial to fully scattered. The common case is a single contiguous user buffer, which ITER_UBUF represents in one pointer-and-length pair with no array to walk—the form new_sync_read() built above. A scatter-gather readv()/writev() instead imports its array of user iovec structures into an ITER_IOVEC iterator that steps across the segments in order. Kernel-internal callers use ITER_KVEC, and—importantly for direct I/O and the block layer—ITER_BVEC describes memory as an array of bio_vec entries, i.e. already-pinned physical pages, so data can be transferred by DMA without any intermediate copy at all. Whichever shape a mode chooses, the code below it calls the same handful of iterator operations, which is precisely what lets one read_iter body cover them all.

The two folio-backed types deserve a note, because they are the newest and the least obvious. ITER_XARRAY describes folios sitting in an XArray indexed by file offset—in practice, a network filesystem's own cache laid out like the page cache of Chapter 15. ITER_FOLIOQ describes a struct folio_queue, a linked list of folio_batch-sized segments each carrying up to thirty-one folios, their orders, and two bits of per-folio marks. The queue form was added for the netfs library because a network read assembles its buffer incrementally as replies arrive, and an XArray insert per folio is more machinery than that needs; a linked list of small batches can be appended to and consumed from the front without allocating an index. Both exist for the same underlying reason: once a subsystem holds data as folios rather than as an address, handing those folios to write_iter should not require copying them into a buffer first.

The structure itself is worth opening, because it is remarkably small for what it does—a type byte, two booleans, a byte offset into the current segment, a union of one pointer per backing type, and a union holding either a segment count or a slot index: 

struct iov_iter {
        u8       iter_type;      /* ITER_UBUF, ITER_IOVEC, ITER_BVEC, ... */
        bool     nofault;        /* copies must not fault */
        bool     data_source;    /* ITER_SOURCE (write) or ITER_DEST (read) */

Three details in that declaration explain behaviour described elsewhere in the chapter. The outer union is an overlay the source calls a "hack alert": a one-segment ITER_UBUF is laid out so that its buffer and length line up with the first entry of an ITER_IOVEC array, which lets the same code path serve both without a branch—the reason the common single-buffer case costs nothing extra despite the general machinery. data_source is the direction discussed above, stored as one bool rather than encoded in the type, which is why ITER_DEST and ITER_SOURCE are arguments to the constructors rather than separate types. And nofault is a deadlock guard with a narrow but instructive use. Setting it adds FOLL_NOFAULT to the page-lookup flags used when the iterator is turned into pages, so the lookup fails with -EFAULT rather than servicing a page fault. Only a handful of callers set it, and they are all direct-write paths—btrfs and gfs2 set it around their iomap direct-I/O call, then clear it, and retry after faulting the buffer in explicitly. The scenario they are defending against is a program issuing an O_DIRECT write whose source buffer is a mapping of the very range being written. Faulting that buffer in while the direct-write path holds the inode lock and an ordered extent would deadlock against itself; failing fast, dropping the locks, faulting the pages in, and retrying breaks the cycle. It is a good example of a field that looks like a performance knob and is in fact a correctness one.

One question the type list leaves open is how a transfer gets from an ITER_UBUF naming a user address to the pinned pages that a bio requires. The answer is iov_iter_extract_pages(), the successor to the older iov_iter_get_pages2(), and the distinction between the two names is the substance. Extraction asks the iterator not merely for pages but for the right retention policy: iov_iter_extract_will_pin() reports whether the pages will come back with a pin the caller must later drop, and it answers true exactly for user-backed iterators. That matters because a page targeted by in-flight DMA must be pinned rather than merely referenced, so that a concurrent fork() is forced to copy it for the child and leave the original where the device is writing (Chapter 9, Section 11 covers pinning in detail). A kernel-backed or folio-backed iterator needs no such treatment, and extraction says so instead of pinning defensively. bio_iov_iter_get_pages() in block/bio.c consults exactly this predicate to decide whether to mark the bio BIO_PAGE_PINNED, which is how the policy travels from the iterator all the way to the completion path that must undo it.

Iterators are constructed rather than assembled by hand. import_ubuf() builds the single-buffer form from a user pointer and length; import_iovec() copies and validates a user iovec array, using a small on-stack array for the common short case and allocating only when the vector is long; and iov_iter_bvec(), iov_iter_kvec(), iov_iter_folio_queue(), and iov_iter_xarray() build the kernel-side forms. Every system call in this chapter begins by calling one of them, and everything below that point sees only the result.

Buffered Reads and Writes

The default access mode is worth following in detail because it is both the common case and the foundation the other modes vary from. A buffered read moves data from the page cache into the process; a buffered write moves it the other way and leaves it dirty for later writeback. Both are implemented generically on top of the page cache of Chapter 15, so this section is largely about how the syscall layer drives that cache. Figure 16-3 sketches the two paths.

Two things are worth keeping in view as the paths unfold. First, the generic implementations—generic_file_read_iter() and generic_file_write_iter()—do the work for almost every disk filesystem; a filesystem supplies only the small address_space_operations hooks (read_folio, write_begin/write_end or an iomap description) that Chapter 15 introduced, and inherits the rest. Second, both paths are structured as a loop over folios: neither moves the whole request in one step, because the cache is organized in folio-sized units and a large request simply walks across as many of them as it spans, copying through the iov_iter one folio at a time.

That second point has grown teeth since large folios arrived. The unit of both loops is not a page but a folio whose size the mapping chooses: generic_perform_write() sets its chunk size from mapping_max_folio_size(), so on a filesystem that allows order-4 folios a single iteration can absorb 64 KB of user data with one write_begin/write_end pair instead of sixteen. The loop still exists—a request larger than the maximum folio still spans several—but it turns far fewer times, and the per-folio costs (locking, dirty accounting, extent lookup) are amortized over much more data. Chapter 15 explained where those large folios come from; this chapter is where the saving is collected.

One clarification about "generic," because the function names are slightly misleading in 7.0.12. Very few filesystems still install generic_file_write_iter() directly as their write_iter; they need to do their own locking, allocation, and journalling around the data copy. But they all reach the same core. ext4's ext4_buffered_write_iter() takes the inode lock, runs its own checks, and then calls generic_perform_write() unchanged. XFS and btrfs go through iomap_file_buffered_write(), whose iomap_write_iter() is a near-copy of the same loop with iomap_write_begin() and iomap_write_end() in place of the address_space_operations hooks. So the loop described below is the loop that runs on essentially every Linux filesystem, even when the entry point above it has a filesystem-specific name.

The Read Path

A read() on a regular file calls its read_iter, which for most filesystems is generic_file_read_iter() (mm/filemap.c). It first checks ki_flags: if IOCB_DIRECT is set the call detours to the direct path described in section 6; otherwise it enters filemap_read(), the buffered core. The detour is worth two remarks even here, because it is not the clean separation the two names suggest. Before issuing the direct read the kernel calls kiocb_write_and_wait(), which writes back and waits on any dirty cached folios overlapping the range—without that step a direct read could legitimately return stale bytes from the device while newer bytes sat dirty in memory. And the detour can come back: if the filesystem's direct_IO method returns a short count (btrfs does this when it meets a compressed extent, and any filesystem may when it meets a hole), generic_file_read_iter() falls through to filemap_read() to finish the remainder through the cache. Only a DAX inode is exempt, because for DAX there is no buffered path to fall back to. As Chapter 15 detailed, filemap_read() looks up the target folios in the mapping's XArray, triggers read-ahead, fills any miss through the filesystem's read_folio, waits for each folio to become uptodate, and copies its bytes into the caller's buffer with copy_folio_to_iter(). Copying through the iov_iter is what makes the same code serve a plain read(), a scatter-gather readv(), or an io_uring read: the destination is whatever the iov_iter describes. The call returns the number of bytes copied, which may be fewer than requested—at end-of-file, or when only part of the range was cached and the caller cannot block—so every correct program loops on short reads.

It is worth seeing the loop that filemap_read() runs, because it explains both the performance and the corner cases. Each pass gathers a batch of folios covering the current offset with filemap_get_pages(): folios already present are taken from the cache; a gap starts read-ahead and, if the data still is not there, an on-demand read through read_folio. The function then walks the batch, and for each folio confirms it is uptodate, maps the portion that overlaps the request, and hands it to copy_folio_to_iter(). Because the iov_iter is a cursor, a folio that is only partly consumed—say the read ends in its middle—leaves the iterator positioned exactly at the next byte, and ki_pos is advanced by whatever was copied, so the next call resumes seamlessly. A read that finds its data entirely in cache never blocks and never touches the disk; that common case is the whole reason the page cache exists.

Batching is the point of filemap_get_pages(), and it is why the loop is structured as two nested walks rather than one folio at a time. A single XArray lookup under RCU (filemap_get_read_batch()) collects every consecutive present folio up to the end of the request, so a large read that hits entirely in cache pays one tree descent and then does nothing but copy. The slow paths are the arms taken when that batch comes back empty or incomplete: an empty batch starts synchronous read-ahead and looks again, and a still-empty batch means the folio must be created and read (filemap_create_folio()). If the last folio of the batch carries the read-ahead mark, asynchronous read-ahead for the following window is kicked off before any copying begins. And if a folio in the batch is not uptodate, the batch is trimmed to that one folio and filemap_update_page() waits for it—the loop would rather return early with what it has than hold a batch of folio references across a disk wait.

Several small pieces of bookkeeping in the copy loop have consequences well outside this section. The first folio of each batch is passed to folio_mark_accessed() only if the previous call did not already end inside it, which pos_same_folio() decides by comparing shifted offsets; a program reading a large file 4 KB at a time therefore ages the folio once rather than sixteen times, which keeps the LRU accounting of Chapter 17 proportional to data touched rather than to syscalls issued. If the mapping is writably mapped by some process—mapping_writably_mapped()—each folio is passed through flush_dcache_folio() before the copy, because on an architecture with virtually-indexed caches the writer's alias may hold bytes the kernel's alias cannot see. The final position is stored in ra->prev_pos, which is the state the read-ahead heuristics of section 4 consult to decide whether this call continued a sequential run. And any folio that came back marked dropbehind—the RWF_DONTCACHE case of section 1—is handed to filemap_end_dropbehind_read() as soon as its bytes are copied, so the cache returns to its previous size instead of growing.

Three behaviours of this path deserve emphasis. A read that begins a sequential run leaves behind a read-ahead marker (PG_readahead) on a folio further along, so that reaching it later kicks off the next window asynchronously—the subject of the following section. A read issued with IOCB_NOWAIT (from preadv2(RWF_NOWAIT) or io_uring) refuses to sleep: if a needed folio is missing or not yet uptodate it returns -EAGAIN rather than waiting for the disk, letting an event loop fall back to an asynchronous submission instead of stalling its thread. The kernel is careful about the meaning of that promise: while IOCB_NOWAIT is set the read-ahead call is wrapped in memalloc_noio_save(), so even the memory allocations made on the way cannot be satisfied by reclaim that would itself issue I/O. There is also a stricter sibling, IOCB_NOIO, which is not a user-visible flag at all—it means "look in the cache and nowhere else," so a missing folio fails immediately rather than starting read-ahead—and it is what an asynchronous submission path uses to probe whether a read can be served inline.

The third behaviour is IOCB_WAITQ, the flag section 1.3 introduced as the answer to asynchronous buffered reads and section 8.2 follows from the caller's side. What belongs here is the read loop's own constraint on it. Returning -EIOCBQUEUED is a promise that nothing has happened yet, and the loop can only make that promise before any bytes have moved: once it has copied part of the request it cannot honestly say the whole operation was queued, so it converts itself back to IOCB_NOWAIT and returns the short count. That is the mechanism behind the ordinary advice to loop on short reads, seen from the other side—a short read is not just an end-of-file artifact but the kernel's standard way of declining to block for the rest.

A last detail explains an error code that surprises people. The copy is copy_folio_to_iter(), and it can come up short—not because the file ran out, but because the destination is not resident. There is no fault-in retry on the read side, so the loop simply stops with -EFAULT; if bytes were already copied that error is discarded and the short count is returned instead, which is why a read() into a partly bad buffer reports success for the good prefix and only fails outright if nothing at all could be copied.

The Write Path

A write() calls write_iter, generically generic_file_write_iter(), which does the bookkeeping a write needs before touching data: it takes the inode lock, runs generic_write_checks() to enforce the file size limit and apply O_APPEND, strips any set-user-ID and set-group-ID bits with file_remove_privs(), and updates the modification time. It then calls generic_perform_write() (or, for O_DIRECT, the direct write path). Two structural points about that wrapper are easy to miss. The inode lock is exclusive, which is why concurrent buffered writers to one file serialize while concurrent readers do not, and it is precisely what FOP_DIO_PARALLEL_WRITE in section 1 lets the direct path escape. And the lock is dropped before generic_write_sync() runs, deliberately: a synchronous write must not hold i_rwsem across a device round-trip, or one slow flush would stall every other writer to the file. As Chapter 15 covered, generic_perform_write() walks the data folio by folio: write_begin obtains a locked, up-to-date folio (reading in surrounding data for a partial write), copy_folio_from_iter_atomic() copies the user bytes from the iov_iter into it, and write_end marks it dirty. The call returns as soon as the data is in cache; the device is reached only later, by writeback. This is the deferred write that makes ordinary writing fast, and it is why a program that needs durability must ask for it explicitly.

The heart of the write is a single loop in generic_perform_write(), and its shape is worth reading closely: 

size_t chunk = mapping_max_folio_size(mapping);   /* a folio, not a page */

do {
        bytes = iov_iter_count(i);
retry:
        offset = pos & (chunk - 1);
        bytes  = min(chunk - offset, bytes);
        balance_dirty_pages_ratelimited(mapping);   /* throttle a fast writer */

        status = a_ops->write_begin(iocb, mapping, pos, bytes, &folio, &fsdata);
        if (unlikely(status < 0))
                break;
        offset = offset_in_folio(folio, pos);       /* fs may hand back a
                                                       different folio size */
        bytes  = min_t(size_t, bytes, folio_size(folio) - offset);

        if (mapping_writably_mapped(mapping))
                flush_dcache_folio(folio);
        copied = copy_folio_from_iter_atomic(folio, offset, bytes, i);
        flush_dcache_folio(folio);

        status = a_ops->write_end(iocb, mapping, pos, bytes, copied, folio, fsdata);
        if (unlikely(status != copied))             /* fs accepted less */
                iov_iter_revert(i, copied - max(status, 0L));

        if (unlikely(status == 0)) {                /* write_end rejected it */
                if (chunk > PAGE_SIZE)
                        chunk /= 2;                 /* back off and retry */
                if (copied) {
                        bytes = copied;
                        goto retry;
                }
                if (fault_in_iov_iter_readable(i, bytes) == bytes) {
                        status = -EFAULT;           /* nothing can be faulted in */
                        break;
                }
        } else {
                pos += status; written += status;
        }
} while (iov_iter_count(i));

iocb->ki_pos += written;

Four details in that loop matter. First, balance_dirty_pages_ratelimited() is the throttle of Chapter 15 applied at its source: a process that dirties pages faster than writeback can clean them is made to wait here, so a runaway writer cannot fill memory with dirty data. Note where it sits—at the top of the iteration, before the folio is locked—so the sleeping is done with no filesystem state held. Second, the loop's unit is a folio and its size is negotiated twice: chunk starts as the mapping's maximum folio size, but write_begin may return a folio of a different order, so offset and bytes are recomputed from the folio the filesystem actually handed back before any bytes are copied.

Third, the copy uses the atomic helper copy_folio_from_iter_atomic(), which runs with page faults disabled so it cannot sleep while holding the folio locked. If the user buffer is not resident the copy simply comes up short. The reason for the restriction is a genuine deadlock rather than mere tidiness: the source buffer may be a mapping of the very file being written, so servicing its fault would re-enter the filesystem and try to lock a folio this thread already holds. The recovery is more interesting than it first looks, because the loop distinguishes two failures. If write_end accepted only part of what was copied, the iterator is rewound over the difference with iov_iter_revert() and the write continues from the new position. If write_end rejected the folio entirely—a zero return—the loop first halves its chunk size and retries at retry:, on the theory that a large folio was too ambitious for whatever went wrong; only when even that copied nothing does it call fault_in_iov_iter_readable(), now with the folio unlocked, to fault the user pages in. That call returning the full byte count means nothing could be faulted in, and the loop gives up with -EFAULT; any other result means progress is possible and the outer loop tries again. Note that this recovery is reactive—the iomap version of the same loop faults the source in before calling write_begin instead, paying an extra probe per iteration to avoid ever taking the short-copy path.

Fourth, flush_dcache_folio() keeps CPU caches coherent on architectures with virtually-indexed caches, a portability detail x86-64 does not need but ARM64 can. It appears twice for a reason: once before the copy, and only when mapping_writably_mapped() says some process has the file mapped writably, to make that process's dirty alias visible to the kernel's; and once unconditionally after, to push the kernel's newly written bytes out where a user alias will see them. Only after all this does write_end mark the folio dirty; the bytes now live in cache, and the syscall returns without a device transfer. ki_pos is advanced once, at the end, by the total—so a write that fails partway still leaves the file position consistent with the bytes it reports.

Two consequences of this design show up at the interface. Because generic_perform_write() can block in three places—dirty throttling, write_begin reading in a partial folio, and journal or allocation work inside the filesystem—a buffered write is much harder to make non-blocking than a buffered read, which is why FOP_BUFFER_WASYNC in section 1 is set by so few filesystems and why ext4's buffered write path simply returns -EOPNOTSUPP when it sees IOCB_NOWAIT. The iomap version does support it, by passing BDP_ASYNC to the throttle so that a writer who would have been made to wait gets -EAGAIN instead. And because a direct write may also stop short—writing into a hole, for instance—__generic_file_write_iter() finishes the remainder buffered through direct_write_fallback(), which then has to flush and invalidate the range it just dirtied so that the two halves of the write are not left in different places.

O_SYNC and Write-Through

Opening a file with O_SYNC or O_DSYNC sets IOCB_SYNC or IOCB_DSYNC on every write's kiocb, and generic_file_write_iter() finishes such a write by calling generic_write_sync(), which flushes the just-written range to stable storage before returning—exactly the fdatasync/fsync machinery of Chapter 15, applied inline to each write. O_DSYNC flushes the data and the metadata needed to read it back; O_SYNC flushes all metadata too. The same effect is available per-call without changing the open flags through the pwritev2() flags RWF_SYNC and RWF_DSYNC, which the kernel turns into the identical IOCB_* bits. Synchronous writes trade throughput for durability on every call, so they are used only where an application must know its data survived—journals, databases, and the like—rather than as a default.

The flag encoding repays a moment's attention, because it is why the two levels nest correctly. O_SYNC is not a single bit: it is defined as __O_SYNC|O_DSYNC, so opening with it sets both IOCB_SYNC and IOCB_DSYNC. generic_write_sync() then tests only the weaker bit to decide whether to flush at all, and uses the stronger one solely to choose the datasync argument it passes down—1 for O_DSYNC, 0 for O_SYNC. The per-call flags follow the same rule, with RWF_SYNC implying IOCB_DSYNC. There is also a third way to arrive here that no application flag controls: iocb_is_dsync() returns true if IS_SYNC() holds for the inode, which it does when the filesystem is mounted with -o sync or when the individual file carries the S_SYNC attribute set by chattr +S. Every write to such a file is synchronous whether or not the program asked, which is worth knowing when a program that seemed fast on one machine crawls on another.

The name "write-through" is precise, and it is worth distinguishing from "write-around." A synchronous write still goes through the page cache: generic_perform_write() runs exactly as before, copying the bytes into a folio and marking it dirty, and only then does generic_write_sync() force that range out. The data therefore stays in the cache after the call, available to a later read without a disk access; durability is added on top, not substituted for caching. This is the opposite of O_DIRECT, which writes around the cache and leaves nothing behind. The flush is also scoped: generic_write_sync() passes the exact byte range just written to vfs_fsync_range(), so a synchronous write forces out only its own data, not the whole file. The cost is nonetheless a real device round-trip per call—often a cache-flush or FUA write at the block layer, as Chapter 15 described—which is why even durability-sensitive programs usually prefer to batch many ordinary writes and call fsync() once rather than open with O_SYNC and pay the price on every one.

generic_write_sync() has acquired a second job that is not about durability at all. If the write carried IOCB_DONTCACHE—the uncached buffered mode of section 1—and is not synchronous, the function instead calls filemap_flush_range() on the range just written. That does not wait for anything; it merely starts writeback so the dropbehind folios become clean and can be reclaimed promptly, which is the whole point of the mode. The three outcomes are worth holding apart: an ordinary write leaves dirty folios for the writeback threads to find later, a RWF_DONTCACHE write starts their writeback immediately but does not wait, and an O_DSYNC write starts it and waits for completion. They differ only in how long the syscall stays around to watch, and all three leave the data in the cache—which remains the distinction from O_DIRECT.

Read-Ahead

Read-ahead is the optimization that makes sequential reading fast: the kernel fetches folios before the program asks for them, so that a streaming reader finds its data already cached and never stalls on the disk. Linux 2.6 implemented this through page_cache_readahead() and a handle_ra_miss() helper; the modern kernel has a cleaner read-ahead framework around a readahead_control and an adaptive window. This section covers why it pays off, the window it maintains, and how it adapts.

The framework lives in mm/readahead.c and sits inside the buffered read path: filemap_read() and the fault handler call into it rather than the filesystem driving it. Its state is kept per open file (in file->f_ra) so two descriptors on the same inode read ahead independently, and its cap comes from the backing device (the bdi's ra_pages), so a fast device is allowed a larger window than a slow one. That cap is a floor as much as a ceiling: ractl_max_pages() raises it when the request itself is bigger than the window and the device advertises a larger optimal transfer size (bdi->io_pages), so a program that asks for a megabyte in one read() is not chopped into 128 KB pieces merely because that is the default window. Everything below is automatic; the only knobs a program has are the advice calls at the end of the section.

Read-ahead also knows when to stay out of the way. Every entry point begins by checking blk_cgroup_congested(), and if the calling cgroup's block device is already backed up the speculative fetch is simply skipped—there is no point queueing guesses behind requests someone is actually waiting for. A file whose ra_pages is zero, likewise, still reaches the read-ahead code, but only so that the machinery can issue the one folio the reader genuinely asked for; the framework is the sole path into the cache for a buffered read, so "disabled" means a window of one rather than a different code path.

Why Read-Ahead

Disk and even flash storage are far more efficient at large, sequential transfers than at small, scattered ones, and most file access is sequential—a program reading a file from start to end, a loader mapping an executable, a copy streaming bytes. If the kernel fetched only the exact folio each read() asked for, a sequential reader would issue one small synchronous I/O after another, stalling on each. Read-ahead breaks that pattern by noticing the sequential access and issuing large, asynchronous reads that run ahead of the program, so the folios are present by the time they are wanted. It is invisible to the application— no API, no flag—yet it is responsible for much of the throughput of ordinary reading, which is why it is built into the buffered read path rather than left to the filesystem.

The win has two independent parts. One is amortization: a single large request pays the per-request overheads—block-layer queueing, a seek or a flash command, request setup—once for many folios instead of once per folio, and a rotating disk in particular turns a scatter of small seeks into one long streaming read. The other is overlap, or pipelining: by launching the next batch asynchronously while the application is still consuming the current one, read-ahead hides disk latency behind the program's own compute time, so a well-behaved sequential reader spends almost no time blocked. The source calls this "readahead pipelining," and it is the reason the window carries an asynchronous trigger rather than simply prefetching on every miss.

The gamble is cheap even when it is wrong. Folios fetched speculatively are ordinary clean cache pages; if the program never reads them, the reclaim machinery of the next chapter simply drops them, at no cost beyond the bandwidth already spent. That asymmetry—large upside on a correct guess, small downside on a wrong one—is what lets the kernel read ahead aggressively by default. It also explains the one place it must be careful: read-ahead applies only to buffered reads. Direct I/O bypasses the cache and so has no window at all, and a mapping or descriptor marked as random access has its window collapsed, precisely because there the speculation would usually be wrong.

The Read-Ahead Window

The kernel tracks read-ahead per open file in a struct file_ra_state (include/linux/fs.h) and drives a pass with a struct readahead_control (include/linux/pagemap.h). The state is essentially a sliding window: start and size describe the range currently being read ahead, and async_size marks how far into that range a trigger sits. When a read enters the window's synchronous part it fetches the whole window at once (page_cache_sync_ra()); one folio near the end—size minus async_size—is tagged with the PG_readahead marker, and when a later read reaches that marked folio, page_cache_async_ra() launches the next window asynchronously while the current data is still being consumed. A steady sequential reader therefore always has a window's worth of folios arriving ahead of it. Table 16-4 lists the state fields.

Where exactly the trigger sits is worth working out, because it changes as the reader settles down. The marker goes on the folio at index start + size - async_size, so async_size is really "how much of this window is still unread when the next one should start." On the very first window the kernel sets it to whatever the window exceeds the request by, so the trigger lands immediately past the bytes the caller asked for. Once the reader is confirmed sequential, though, page_cache_async_ra() sets async_size equal to size—putting the marker on the first folio of the new window. That is the steady state: the moment the reader touches the first byte of the window it just triggered, the window after that is already being fetched, and the reader stays a full window ahead of the disk indefinitely. The marker itself is PG_readahead, which shares a page-flag bit with PG_reclaim; that is why page_cache_async_ra() checks for writeback before believing the flag, since on a folio under writeback the same bit means something else entirely.

The window's size is not a constant but the output of two small ramp functions in mm/readahead.c. The first window is sized by get_init_ra_size(), which rounds the request up to a power of two and then multiplies it—by four for a small request (up to ra_pages/32), by two for a medium one, and to the full cap for a large one—so even the opening read of a stream fetches several times what was asked. Every window after that is sized by get_next_ra_size(), which ramps the previous size up geometrically: it quadruples while the window is still small (below ra_pages/16), then doubles, until it saturates at the device's ra_pages cap. A long sequential read therefore climbs quickly to the maximum window and stays there, issuing steady, cap-sized asynchronous fetches. The cap itself defaults to a modest amount (VM_READAHEAD_PAGES, 128 KB) and is a per-backing-device value, so it can be tuned per disk.

Fetching a window is the job of page_cache_ra_order(), which allocates the folios, links them into the mapping's XArray, and submits the underlying reads through the filesystem's readahead or read_folio operation. It is also where large folios enter: as the window grows the kernel raises the folio order it asks for, so a saturated sequential read ends up fetching large folios in large bios—the same order-selection signal Chapter 15 described, driven here by read-ahead. A filesystem that needs a wider transfer than the reader asked for—for alignment, compression, or a large-folio boundary—can enlarge the pass itself with readahead_expand().

The order is not chosen freely. page_cache_ra_order() clamps the state's order three ways before allocating anything: down to the mapping's maximum folio order, down to ilog2(ra->size) so a folio can never be larger than the window that asked for it, and up to the mapping's minimum order, which is how a filesystem with a block size larger than the page size gets folios it can actually use. Then the allocation loop makes two further concessions to reality. A folio of order n must sit at an index that is a multiple of 2n, so a window starting at an unaligned index begins with smaller folios—the order drops to __ffs(index)—and grows to the target as the loop reaches aligned boundaries. And the order is reduced again near the end of the file, because allocating a large folio that extends past EOF would waste most of it. The window's end is likewise rounded down to an order boundary when the state is advanced, so consecutive windows meet on an alignment the next pass can use.

Submission happens once, at the end, in read_pages(), and its shape matters for throughput. The whole window is bracketed in a blk_start_plug() / blk_finish_plug() pair, so the bios the filesystem generates accumulate on the plug list and are merged into a few large requests rather than issued one at a time—this is where the amortization argument of section 4.1 is actually collected. If the filesystem provides a readahead operation it is handed the whole readahead_control and may consume the folios in whatever batches suit its extent layout; if it only provides read_folio, the loop falls back to calling it once per folio. The pass runs under filemap_invalidate_lock_shared(), which keeps a concurrent truncate or hole punch from removing the range underneath it, and inside memalloc_nofs_save(), so the folio allocations cannot recurse into the filesystem that is about to be asked to fill them. One last touch: if any folio in the window was a workingset folio—one being refaulted after reclaim evicted it—the pass is accounted as memory stall time through psi_memstall_enter(), so pressure-stall information can tell the difference between reading new data and re-reading data the system should not have dropped.

Adapting to the Access Pattern

The window is not fixed; it grows and shrinks with the observed pattern. On a detected sequential run the kernel enlarges size up to the device's ra_pages cap, so a long streaming read settles into big asynchronous fetches; a read that lands where the previous one ended (prev_pos) confirms the sequential guess and keeps the window growing. When access looks random—reads that jump around, or an mmap fault pattern that keeps missing (mmap_miss)—the kernel shrinks the window back toward a single folio, because reading ahead there would only fetch data the program never touches and waste memory and bandwidth. This is the same signal that chooses the folio order (Chapter 15): a strong sequential run both widens the window and raises the folio order, so large sequential reads end up fetching large folios in large bios. Figure 16-4 shows the window and its asynchronous trigger.

The interesting part is what happens when prev_pos does not match. That is not rare: two threads reading the same descriptor interleave, a program seeks and resumes, a server hands the file to a different worker, and in each case the per-file state describes somebody else's position. Rather than declare the access random, page_cache_sync_ra() asks the page cache what happened. page_cache_prev_miss() scans backwards from the folio before the current one, looking for the first index that is not cached; the distance to that hole is how many consecutive folios preceding this read are already in memory—which is exactly the trail a sequential stream leaves behind. The cache is used as a history buffer, and no extra state has to be maintained to get it.

Three conclusions follow from that measurement. If the trail is no longer than the request itself, this looks like an isolated random read: the kernel fetches precisely what was asked and, importantly, does not touch the read-ahead state at all, so one seek in the middle of a stream cannot destroy a window that other reads are still using. If there is a trail, the new window is sized to the trail plus the request, capped at the maximum—so an interleaved reader is credited with the history it has actually accumulated and resumes at roughly the size it had earned. And if the backwards scan finds no hole at all, meaning the file is cached continuously from its beginning, that is taken as strong evidence of a whole-file read and the count is doubled. The same trick runs on the asynchronous side: a marked folio reached without matching state makes page_cache_next_miss() scan forwards to find where the previously fetched run ends, and the window is rebuilt from there.

The folio order ramps on its own schedule. It is reset to zero whenever a synchronous pass starts a fresh window—a new stream begins with small folios, since nothing yet justifies large ones—and then increases by two on every asynchronous pass. Two, not one, so the folio size quadruples per window and catches up with the window's own geometric growth; a stream that stays sequential is soon fetching order-8 folios inside cap-sized bios, while a stream that stops being sequential falls back to a fresh order-zero window without any explicit decay logic.

An application that knows its own pattern can override the heuristic through advice calls, which the kernel folds into the same state. The posix_fadvise() hint POSIX_FADV_SEQUENTIAL doubles the file's ra_pages cap so the window ramps to twice the default; POSIX_FADV_RANDOM sets FMODE_RANDOM, which disables adaptive read-ahead entirely so each read fetches only what it needs; and POSIX_FADV_WILLNEED—like the readahead(2) system call—forces an immediate prefetch of a named range through force_page_cache_ra(), bypassing the adaptive logic to pull data in before it is asked for. The madvise() counterparts MADV_SEQUENTIAL, MADV_RANDOM, and MADV_WILLNEED do the same for a memory mapping. These hints are the only application-visible controls over a mechanism that is otherwise entirely automatic.

Read-Ahead for Mapped Files

Everything so far assumed a reader with a direction. A memory mapping does not have one: the kernel sees an isolated page fault at some offset, with no request size, no previous position, and no promise that the next fault will be anywhere nearby. The framework is the same—faults call into do_sync_mmap_readahead() and do_async_mmap_readahead(), which drive the same file_ra_state—but the default policy is different enough to have its own name. It is read-around rather than read-ahead: the window is centred on the faulting page, starting half a window before it and extending ra_pages beyond, on the reasonable theory that a program touching one part of a mapping will touch its neighbours in either direction. A sequential reader is fetched ahead of; a mapping is fetched around.

Because read-around is a much weaker guess than sequential read-ahead, it needs a way to give up, and that is the mmap_miss field of Table 16-4. The counter rises by one on every fault that had to fetch and falls by one on every fault that found its folio already present, so it measures the ratio of misses to hits rather than a raw miss count. Above MMAP_LOTSAMISS—100—the kernel stops reading around this file entirely and services faults one folio at a time; the counter keeps climbing to ten times that before saturating, so a file that has been genuinely random for a long time needs a correspondingly long run of hits to earn read-around back. Note that this is a per-open-file counter like the rest of the state, so one process's random access to a shared library does not disable read-around for another's.

Two kinds of mapping are singled out. madvise() is the loudest signal: MADV_RANDOM (VM_RAND_READ) skips read-around altogether, MADV_SEQUENTIAL (VM_SEQ_READ) abandons read-around in favour of the ordinary page_cache_sync_ra() ramp of the previous sections, and MADV_HUGEPAGE (VM_HUGEPAGE) forces PMD-order folios and fetches two of them, so that there is something left to trigger on. The other case is executable mappings, and it is a good illustration of how specific this tuning has become. Code is accessed in a scattered way as calls jump between functions, so VM_EXEC mappings are read with async_size set to zero—no trigger, no pipelining—and the range is clamped to the VMA's own bounds so that the padding between ELF sections is never pulled in. What the kernel does ask for is a particular folio order, from the architecture hook exec_folio_order(). It is zero generically, but ARM64 defines it as 64 KB worth of pages, because a 64 KB-aligned folio can be mapped with contiguous PTEs and consume a single TLB entry instead of sixteen. Read-ahead here is not fetching data the program will need sooner; it is arranging the data so the MMU can describe it more cheaply.

One mechanism that is often confused with this one is fault-around, which section 5.3 covers. The distinction is worth stating plainly: read-around decides which folios to fetch from disk near a fault, while fault-around decides how many page-table entries to install for folios that are already cached. They are complementary—read-around populates the cache, fault-around saves the faults that would otherwise be needed to map what read-around brought in—and a mapping being streamed benefits from both at once. Finally, all of these paths call maybe_unlock_mmap_for_io() before submitting anything, dropping mmap_lock for the duration of the I/O so that a slow read does not block every other fault and mapping operation in the address space.

Memory-Mapped Files

Memory mapping is the third way to reach a file, and in some ways the most elegant: instead of calling read() and write(), a program maps the file into its address space with mmap() and then accesses the file as an array of bytes, letting the page-fault machinery move data in and out on demand. This is how executables and shared libraries are loaded, how many databases access their files, and how processes share memory. This section covers the structures that describe a mapping, how one is created, how faults page it in, and how its dirty pages reach disk.

The appeal over read()/write() is twofold. It is zero-copy: the folios that a mapping exposes are the page-cache folios themselves, mapped straight into the process's page tables, so there is no copy into a separate user buffer and no system call per access—the CPU touches the cache directly. And it is convenient: the file becomes ordinary memory, so pointer arithmetic, structure overlays, and library routines that expect memory all work on it unchanged. Because a shared mapping exposes the very same folios that read() and write() use, the two interfaces are perfectly coherent on one file. The costs are that access happens a page at a time through faults rather than in large batched transfers, and that errors surface as signals (SIGBUS, SIGSEGV) at access time rather than as a return value—trade-offs the rest of the section makes concrete.

How a process's VMAs are organized is one of the larger changes since Linux 2.6, which kept a red-black tree of VMAs plus a linked list, both threaded through fields in each VMA. Modern kernels store the VMAs in a maple tree—mm->mm_mt, an RCU-friendly B-tree built for storing ranges—and the VMA no longer carries tree or list links at all. The maple tree answers the central question of the fault handler—"which VMA contains this faulting address?"—in a few cache- friendly steps, and its RCU design allows lookups without taking the address-space lock, which is what enables the newer per-VMA locking that lets faults on different regions proceed in parallel. Code walks the tree through a VMA iterator (VMA_ITERATOR, for_each_vma()) or looks up a single region with find_vma(); the whole address space is protected by mm->mmap_lock (the read/write semaphore called mmap_sem before Linux 5.8). Figure 16-5 shows the arrangement.

The maple tree's RCU design is what makes the newest scalability work possible. On a fault the handler first tries lock_vma_under_rcu(), which finds the VMA and takes a lightweight per-VMA lock without acquiring the address space's mmap_lock at all; the fault then runs with the FAULT_FLAG_VMA_LOCK flag set, so faults on unrelated regions of the same process proceed fully in parallel—a large gain for many-threaded programs that used to serialize on the single mmap_lock. The fast path is not always available: when a fault needs an operation the speculative path cannot safely perform, it returns VM_FAULT_RETRY and the handler falls back to taking mmap_lock and retrying the classic way. The vm_page_prot field is a small but load-bearing detail here: it is the page-table protection value derived once from vm_flags, so that installing a PTE for a faulted folio is a cheap copy rather than a re-computation of permissions on every fault.

Two implementation details make that fast path safe, and both are visible in the structure. The per-VMA lock is not a separate allocation but the vm_lock_seq and vm_refcnt fields embedded in the VMA itself, the second of which doubles as the attached/detached indicator—a refcount of zero means the VMA has been removed and no reader may take it. More subtly, VMAs are allocated from a SLAB_TYPESAFE_BY_RCU cache, which is why vm_start and vm_end share a union with a freeptr_t. Type-safe-by-RCU means a freed VMA may be reused for another VMA immediately, but the memory never becomes something else, so an RCU reader that follows a stale pointer reads a plausible vm_area_struct rather than garbage; it can then check the sequence number and the address range and retry if it lost the race. Without that guarantee the lockless lookup would have to wait for a grace period on every munmap(). The flags word has been tightened for similar reasons: vm_flags is now declared const, overlaid with a writable vma_flags_t, so that modifying a VMA's flags has to go through the vm_flags_set() family of helpers that take the write lock rather than through a stray assignment.

One thing the address-space view hides is that a file-backed VMA belongs to two trees at once. The maple tree indexes it by virtual address for the owning process, which is what a fault needs. The shared.rb node links it into the i_mmap interval tree of the address_space that Chapter 15 described, which indexes every mapping of the file by file offset, across all processes. That second tree answers the opposite question—"who has this part of this file mapped?"—and it is what makes truncation work: shrinking a file calls unmap_mapping_range(), which walks i_mmap and tears the doomed page-table entries out of every process that mapped the range, so that a subsequent access takes a fault and receives SIGBUS instead of quietly reading a stale folio. A private mapping additionally acquires an anon_vma the first time it copies a page, because from then on it owns anonymous memory that reclaim must be able to find its way back from.

Creating a Mapping

An mmap() system call descends vm_mmap_pgoff() → do_mmap() (mm/mmap.c) → mmap_region() (mm/vma.c, which now holds the VMA manipulation code that used to live alongside do_mmap()), which finds a free range of addresses, allocates and initializes a VMA, inserts it into the maple tree, and—for a file mapping—asks the file how it wants to be mapped. The generic answer installs the file fault handlers and nothing else: vma->vm_ops = &generic_file_vm_ops. No data is read at this point; the mapping is a promise, and the folios are brought in lazily by faults. The MAP_SHARED versus MAP_PRIVATE choice made here decides what writes mean: a shared mapping's writes go back to the file (and are visible to other mappers), while a private mapping's writes are kept process-local through copy-on-write and never reach the file. Tearing a mapping down (munmap(), or process exit) removes the VMA from the tree, unmaps its page-table entries, and drops its reference on the file.

Several details of that path matter in practice. The free range is chosen by get_unmapped_area(), which consults the architecture's address-space layout (and the randomized mmap base that ASLR provides) unless the caller pins an address with MAP_FIXED. Before a fresh VMA is committed, do_mmap() tries to merge it with an immediately adjacent VMA that has identical properties—same file, contiguous offset, same flags—so a process that maps many adjacent regions does not accumulate a VMA per call; this is why the count of VMAs is usually far smaller than the count of mmap() calls. The mapping also takes a reference on the open file (vm_file), so the underlying inode and its page cache stay alive for as long as the mapping exists, even if the program closes its descriptor. And while faulting is lazy by default, MAP_POPULATE asks the kernel to prefault the whole mapping up front, trading a slower mmap() for the absence of later fault stalls.

How the filesystem is asked has changed in 7.0.12, and section 2.1's file_operations excerpt showed both forms. The original hook is mmap, which receives a fully built vm_area_struct and may modify it; the generic implementation is generic_file_mmap(). The newer hook is mmap_prepare, which is called before the VMA exists and receives a struct vm_area_desc—a plain description of the mapping being requested, with the range and flags as mutable fields and vm_ops as a write-only one—so the filesystem states what it wants without ever touching a live VMA. The two are mutually exclusive; can_mmap_file() warns if a filesystem supplies both. ext4, XFS, and btrfs have all moved to mmap_prepare, and generic_file_mmap_prepare() is the generic form.

The motivation is that the old interface handed out a half-initialized VMA that was not yet in any tree, which made a long list of things a driver might plausibly do either racy or outright wrong, and made it impossible for the VMA-manipulation code to reason about what a callee had changed. Restricting the filesystem to a descriptor means the kernel can validate the result before committing anything, and it is what allows the mapping to be merged with a neighbour after the filesystem has spoken rather than before. Callers that genuinely hold a VMA and need to drive a mmap_prepare filesystem go through a compatibility bridge, vfs_mmap(), which builds a descriptor from the VMA, calls the new hook, and applies the result—so both worlds keep working while the remaining mmap implementations are converted.

The flags argument to mmap() carries these choices, and the kernel translates each into a VMA attribute during do_mmap()—the sharing flags into vm_flags bits by the case analysis above, and the modifier flags into further vm_flags bits by calc_vm_flag_bits(). Demand Paging and Fault-Around

Because mmap() reads nothing eagerly, the real work happens on the first access to each page—a page fault. The fault handler handle_mm_fault() looks up the faulting address's VMA in the maple tree and, for a file-backed region, routes to do_fault() (mm/memory.c), which splits by fault type: do_read_fault() for a read, do_cow_fault() for a write to a private mapping, and do_shared_fault() for a write to a shared one. All of them call the VMA's fault operation, which for a file mapping is filemap_fault(): it looks the folio up in the page cache, and on a miss allocates, adds, and fills it through read_folio—exactly the lookup of Chapter 15—then hands it back to be installed in the page tables. A fault satisfied from cache is a minor fault; one that had to read from disk is a major fault, reported as VM_FAULT_MAJOR. Figure 16-6 traces the path.

Two optimizations make faulting cheap. Fault-around: rather than installing only the one faulted page, the handler calls the VMA's map_pages operation, filemap_map_pages(), which installs page-table entries for a batch of already-cached folios around the faulting address, so a program walking a mapped file takes far fewer faults than it has pages. The ordering is the reverse of what one might guess: do_read_fault() tries map_pages first and only falls back to the fault operation if the batch did not happen to cover the faulting address, so on hot data the expensive handler is never reached at all. And read-ahead: the same PG_readahead marker used by read() works for mmap, so touching a marked folio launches the next window. The result is that sequentially reading a large mapped file is about as efficient as reading it with read()—both ride the page cache and its read-ahead.

It is worth being precise about the split. The three sub-handlers differ only in what they do with the folio filemap_fault() returns. do_read_fault() maps it read-only and shared—many readers of the same file page point at the one cache folio. do_cow_fault(), taken on a write to a MAP_PRIVATE region, copies the cache folio into a fresh anonymous page and maps that, so the process's change is private and the file is never touched. do_shared_fault(), taken on a write to a MAP_SHARED region, is the one that must arrange write-back, and it does so through page_mkwrite, described next. Fault-around is deliberately restrained, in four separate ways. Its window is fault_around_bytes, 64 KB by default and adjustable only through debugfs, and it is rounded down to a power of two so the window can be aligned cheaply. filemap_map_pages() maps only folios already present in the cache—it never triggers I/O—so it speeds up re-faulting hot data without gambling on cold reads. The window is clamped to the faulting VMA and to the enclosing page-table page, so fault-around never allocates a second PTE table or maps memory the VMA does not cover. And it is attempted only on do_read_fault(): a write fault, private or shared, has real work to do per page and cannot be batched this way. All three handlers come from one binding: generic_file_vm_ops wires fault to filemap_fault, map_pages to filemap_map_pages, and page_mkwrite to filemap_page_mkwrite.

filemap_fault() itself has more to do than the page-cache lookup suggests, and its extra work is where several user-visible behaviours come from. It begins by comparing the faulting index against the file size and returning VM_FAULT_SIGBUS if the fault is past the end—this is the concrete source of the SIGBUS the introduction promised, and the check is repeated later under the folio lock, because a concurrent truncate can shrink the file in between. A folio found in the cache is also re-validated after it is locked, since it may have been removed while the fault waited. Most interesting is what happens when the fault must block: lock_folio_maybe_drop_mmap() takes a reference on the file, releases mmap_lock, waits for the folio outside it, and then returns VM_FAULT_RETRY so the whole fault is re-taken from the top. A fault that reads from disk therefore does not hold the address-space lock across the I/O, which is what keeps one slow major fault from freezing every other thread's mapping activity—at the cost of the fault being executed twice, which is why FAULT_FLAG_TRIED exists to stop the second attempt from repeating the read-ahead. The major-fault accounting happens on the branch where the folio was absent from the cache entirely, so VM_FAULT_MAJOR and the PGMAJFAULT counter measure cache misses rather than completed disk reads.

Dirtying and Flushing Mapped Pages

Writing through a shared mapping needs care, because a store to memory does not obviously "dirty" a file. The mechanism is the write fault. When a program first writes to a clean page of a MAP_SHARED writable mapping, the page-table entry is kept read-only so that the store traps; the handler calls the filesystem's page_mkwrite (to let it allocate backing blocks or extend the file), marks the folio dirty—setting its PAGECACHE_TAG_DIRTY tag exactly as write_end does—and makes the entry writable so subsequent stores proceed freely. From that point the folio is an ordinary dirty page-cache folio, written back by the flusher threads of Chapter 15 with no mmap-specific path. A program can force those dirty pages out with msync(): MS_SYNC flushes the mapped range synchronously (through vfs_fsync_range()), while MS_ASYNC is now essentially a no-op, since the pages are already tracked as dirty and will be written by normal writeback. This is why a shared mmap and a write() to the same file are fully coherent and share one durability story.

The read-only-until-first-write trick is the whole basis of dirty tracking for mappings, and it is worth seeing why it is necessary. Once a page is mapped writable, the CPU updates it silently—no kernel code runs on each store—so the kernel would have no way to know the file had changed. By leaving the PTE read-only until the first write, it forces exactly one trap per clean page, uses that trap (via filemap_page_mkwrite()) to let the filesystem reserve blocks and to mark the folio dirty, and only then grants write access; further stores run at full speed until writeback cleans the folio and re-arms the trap. From that moment the folio is indistinguishable from one dirtied by write(): it carries the same PAGECACHE_TAG_DIRTY tag, counts toward the same dirty-memory limits, and is subject to the same balance_dirty_pages throttling—so a process dirtying a mapping fast is throttled just as a fast write() is. The only mmap-specific control is msync(), and the modern behaviour is simple: MS_SYNC forces the range out now, and MS_ASYNC need do nothing because the pages are already queued for the flusher threads. A third flag, MS_INVALIDATE, asks for other mappings of the range to be invalidated; it fails with -EBUSY if any of them is locked into memory. Because msync() works from addresses rather than file offsets, it walks the VMAs covering the range and translates each to a file range through vm_pgoff, which is why an msync() spanning a hole in the address space still flushes the mapped parts and reports -ENOMEM at the end.

Three further things filemap_page_mkwrite() does on that first write fault have consequences that surprise people. It calls file_update_time(), so a mapped file's modification time is stamped when a page is first dirtied—not on every store, which no kernel code sees, and not at msync() time. A program that mutates a mapping for an hour after its first write leaves an mtime an hour stale, which is a real hazard for build systems and backup tools. It calls folio_wait_stable(), which blocks the faulting thread if the folio is currently under writeback on a device that requires stable pages, so that a checksum or integrity tag computed by the storage stack cannot be invalidated by a store landing mid-flight. And the whole handler is bracketed by sb_start_pagefault() and sb_end_pagefault(), which enrol it in the filesystem freeze protocol: freezing a filesystem blocks new write faults here and waits for the ones in flight, so fsfreeze genuinely quiesces mmap writers rather than only write() callers. If the folio turns out to have been truncated away while the handler waited for its lock, the fault returns VM_FAULT_NOPAGE and the access is retried from scratch. On a kernel built without the block layer the generic page_mkwrite is a stub that returns SIGBUS, which is the honest answer when no writable file mapping can be supported at all.

Direct I/O

Every mode so far runs through the page cache. Direct I/O is the mode that deliberately does not. Section 1.2 introduced it in a sentence; this section asks the three questions that sentence leaves open—why an application would give up the cache, what the kernel actually builds in its place, and what the application owes in return.

Why Bypass the Cache

The page cache is a benefit for most programs but a cost for a few. A database, or any application that maintains its own carefully tuned cache, gains nothing from a second copy of its data in the kernel—and pays for it three times over: the duplicated pages waste memory, the extra copy between the kernel buffer and user memory wastes CPU and bandwidth, and the kernel's read-ahead and write-back heuristics work against an access pattern the application understands better than the kernel does. Direct I/O lets such a self-caching application take control: reads and writes transfer directly to and from its buffers, with no kernel caching, read-ahead, or deferred write in the way. In exchange it gives up all of those conveniences and must manage its own buffering, alignment, and concurrency. Table 16-8 contrasts the two.

Two of these costs are worth drawing out, because they are why the mode exists at all. The first is double caching: a database that keeps its own buffer pool sized to most of RAM does not want the kernel to keep a second copy of the same blocks in the page cache, doubling memory use and evicting pages the application would rather keep. The second is latency predictability: buffered writes accumulate as dirty pages and are flushed in bursts, and a writer can be blocked in balance_dirty_pages at an unpredictable moment; direct writes reach the device as they are issued, giving the steady, bounded latency that transactional systems need to honour their own durability guarantees. This is why the heavy users of O_DIRECT are databases, virtual-machine disk backends, and large-file media tools—programs that manage caching and I/O scheduling themselves and treat the kernel purely as a path to the device.

Whether the mode is available at all is decided at open() time and is easy to overlook. do_dentry_open() sets FMODE_CAN_ODIRECT only when the address space actually supplies a direct_IO method (filesystems that use iomap set the mode bit themselves), and then rejects the open with -EINVAL if O_DIRECT was requested without it. So O_DIRECT on tmpfs, on most network filesystems in their default configuration, or on any filesystem that never implemented the path fails immediately rather than degrading quietly—which is the behaviour a portable program should be prepared for, since the flag has never been part of POSIX.

Between these two extremes 7.0.12 offers a middle ground Linux 2.6 had no equivalent of. A program that wants the convenience of buffered I/O (no alignment rules, ordinary short reads, the kernel doing the block mapping) but does not want its data to linger in the cache afterwards can pass RWF_DONTCACHE to preadv2() or pwritev2(), or set the corresponding io_uring flag. The kernel turns it into IOCB_DONTCACHE, and the effect inside the buffered path is small and precise: every folio the call allocates is marked with __folio_set_dropbehind(), and any read-ahead the call triggers is issued with ractl.dropbehind = 1, so the folios are reclaimed as soon as the read completes or the write is written back rather than competing with the rest of the working set. The flag is not universally available—kiocb_set_rw_flags() rejects it with -EOPNOTSUPP unless the file operations advertise FOP_DONTCACHE—but where it is, it is the right answer for the streaming case that historically reached for O_DIRECT only to escape cache pollution, not to escape the copy.

The Direct I/O Path

When generic_file_read_iter() or generic_file_write_iter() sees IOCB_DIRECT in the kiocb, it detours from the buffered core to the mapping's direct_IO operation. Most modern filesystems—XFS, ext4, btrfs— implement it through the iomap framework's iomap_dio_rw() (fs/iomap/direct-io.c), the descendant of the 2.6-era __blockdev_direct_IO() that older filesystems still use. The iomap path does what the buffered path does not: it pins the user pages of the iov_iter directly (with bio_iov_iter_get_pages()) and builds bios that point at those very pages, so the device DMAs to and from user memory with no kernel copy. Because the transfer names user pages, the kernel must keep them present and accessible for its duration—the pins prevent them from being reclaimed or migrated. This is the ITER_UBUF/ITER_IOVEC case of section 2.3 taken to its conclusion: the block layer records on the bio that its pages are pinned rather than merely referenced, by setting BIO_PAGE_PINNED, and releases them on completion. A bio built from an iterator that already describes kernel memory—ITER_BVEC, as io_uring's registered buffers and the loop device produce—skips the pinning entirely, which is one of the reasons registered buffers are faster than ordinary ones. When the I/O completes, a synchronous caller is woken; an asynchronous one (io_uring or libaio) has its ki_complete invoked. Figure 16-7 contrasts the direct and buffered data paths.

That description is the common case, not a definition, and 7.0.12 has three exits from it that are worth knowing. A range that the iomap describes as a hole, or as an unwritten extent being read, is not sent to the device at all: iomap_dio_hole_iter() simply zeroes that part of the user buffer, so a direct read of a sparse file costs no I/O for the sparse parts. A range held as inline data in the inode is transferred with an ordinary copy_to_iter() or copy_from_iter()—a memcpy, not a DMA, because there is no block to point a bio at. And most interestingly, the caller can ask for IOMAP_DIO_BOUNCE, which makes the transfer go through a kernel bounce buffer rather than the user's pages. That exists because zero-copy and stable data are in tension: a device that computes a checksum or generates RAID parity over the buffer needs the bytes to hold still, and nothing stops another thread in the calling process from modifying its own memory while the DMA is in flight. Copying into a private buffer restores the guarantee at the price of the copy direct I/O exists to avoid. The lesson is that O_DIRECT names a cache bypass; whether it is also a copy bypass depends on the filesystem, the layout, and the device.

Two flags on the submission side connect back to earlier sections. IOMAP_DIO_OVERWRITE_ONLY is the mechanism behind FOP_DIO_PARALLEL_WRITE from section 1: a direct write that merely overwrites already-allocated blocks changes no metadata, so it can run under a shared inode lock alongside other writers. The filesystem takes the shared lock, submits with this flag, and iomap returns -EAGAIN the moment it discovers the range would need allocation or partial-block zeroing; the caller then retries the whole thing under the exclusive lock. The optimistic attempt costs almost nothing when it fails and removes the single-writer bottleneck when it succeeds, which is why databases see so much more concurrency on XFS and ext4 than the i_rwsem discussion of section 3.2 would suggest. IOMAP_DIO_PARTIAL is the other half of the nofault story from section 2.3: a filesystem that has disabled page faults to avoid deadlocking on a source buffer that maps the file returns a partial result instead of an error, and the caller faults the rest in outside its locks and resubmits with done_before set, so that the final completion still reports one correct total.

The completion side is where direct I/O's asynchrony and durability are resolved, in iomap_dio_complete(). A synchronous caller simply waits for the bios and collects the byte count; an asynchronous one has its ki_complete invoked—sometimes directly from the bio's completion, but for a write that still needs blocking work (converting unwritten extents, updating the inode size) the completion is handed to a workqueue (IOMAP_DIO_COMP_WORK) so that ki_complete runs in a context that can sleep. If the file was opened O_DSYNC/O_SYNC, completion also runs generic_write_sync() to force the data durable, and iomap can fold that into the transfer itself: a pure overwrite can be issued as a write-through (FUA) bio, making the data durable in the same device operation instead of a separate cache flush. Throughout, the inode's inode_dio_begin()/inode_dio_end() counter keeps direct I/O in flight serialized against truncate, so a shrinking file cannot pull the ground out from under an outstanding transfer.

The write-through optimization is more careful than that summary suggests, and the care is instructive. It is attempted only for O_DSYNC, never for O_SYNC, because a full sync must also push metadata and no device flag can express that. It is optimistic: IOMAP_DIO_WRITE_THROUGH is set speculatively at submission, but one request can map to several disjoint extents and only some of the resulting bios may qualify for REQ_FUA—so any bio issued without it clears the flag. By the time the last bio is submitted the kernel therefore knows, without asking the device anything, whether every byte went through to the media. If the flag survived, the IOMAP_DIO_NEED_SYNC obligation is simply dropped and no flush is issued at all; if it did not, the completion is forced onto the workqueue, because issuing a cache flush needs a context that can sleep. The same reasoning governs IOMAP_DIO_COMP_WORK generally: a write that extends the file must update i_size from process context, so it can never complete inline from the bio's interrupt-time callback.

Two more behaviours round out the path. A direct read or write issued with IOCB_HIPRI—from preadv2(RWF_HIPRI) or io_uring—marks its bio for polling, so the submitting thread spins on completion instead of waiting for an interrupt; on a fast NVMe device that removes an interrupt and a context switch from the critical path. The kernel withdraws the flag as soon as the request turns out to need more than one bio, or is synchronous, because polling only pays when there is exactly one thing to poll for. Finally, if the post-write invalidation of the page cache fails, iomap returns -ENOTBLK rather than an error to the application, and the caller falls back to the buffered path—the concrete form of the claim, made below, that O_DIRECT is a request rather than a contract.

Alignment and Coherency

Bypassing the cache imposes two obligations. The first is alignment: because the transfer becomes a bio built directly on user pages and sent to the device, both the buffer and the range must satisfy constraints the buffered path would have absorbed. As section 1.2 introduced, there are two separate constraints rather than one. The memory alignment governs the address of the user buffer and derives from what the device's DMA engine can address—ext4 and XFS both compute it as bdev_dma_alignment(bdev) + 1, which on ordinary hardware is a few hundred bytes at most, not a block. The offset alignment governs the file offset and the length and derives from the filesystem's own block accounting: ext4 reports the device's logical block size, while XFS reports its allocation unit size for force-aligned and realtime inodes. Getting either wrong yields -EINVAL, with nothing to say which one was violated. Applications typically allocate their buffers with posix_memalign() and round their ranges to the reported offset alignment. The second is coherency with any cached copy of the same data: if some of the range is present in the page cache from earlier buffered access, a direct write would leave the cache stale and a direct read might miss recent buffered writes. The kernel keeps the two consistent by flushing and invalidating the overlapping cached folios around each direct operation—filemap_write_and_wait_range() before, and invalidate_inode_pages2_range() after a direct write—so that direct and buffered access to the same file, while discouraged, remain correct. Direct I/O is synchronous unless issued through an asynchronous interface, which is the subject of the next section.

The alignment requirement is a consequence of the DMA path, not an arbitrary rule: the device transfers whole blocks by bus address, so a sub-block offset or an oddly-placed buffer has nowhere to land. Because the alignment a device demands is not fixed—an NVMe drive behind a filesystem may allow finer alignment than the raw block size suggests—the kernel exposes the actual requirements through statx() in the STATX_DIOALIGN fields (stx_dio_mem_align and stx_dio_offset_align), so a program can query them rather than guess. It is also why O_DIRECT is best understood as a strong hint: the kernel makes a genuine direct transfer when it can, but a filesystem is free to fall back to the buffered path for a request it cannot serve directly (a hole, a compressed extent, an unaligned tail), and the application sees only correct data either way.

The coherency dance is worth reading in order. Before a direct operation, filemap_write_and_wait_range() pushes any dirty cached folios in the range out to the device and waits, so the direct read or write sees the latest data. After a direct write, the kernel invalidates the clean cached folios that overlap the range, dropping stale copies that read-ahead—or a get_user_pages() of an mmap of the same file—might have left behind; the source comment fairly calls mixing the two "a pretty crazy thing to do," and supports it only far enough to keep results correct, not fast. Crucially this invalidation happens after the filesystem's end_io, because converting unwritten extents to real allocations must finish first, or a racing buffered read could cache zeros from a not-yet-converted extent. The practical advice is simply not to mix direct and buffered access to the same region concurrently; the kernel guarantees correctness, but the overhead of the flush-and-invalidate on every direct operation is exactly what direct I/O was meant to avoid.

There is one place where the guarantee runs out, and 7.0.12 says so out loud. Direct I/O is not serialized against mmap() at all. If a page_mkwrite fault lands between the flush and the iomap_iter() call that maps the range, the direct path can find a delayed-allocation extent—a range the buffered path has reserved but not yet given a block—where it expected either a hole or a real mapping. There is nothing sensible to do with it, so iomap_dio_iter() prints "Direct I/O collision with buffered writes!" with the offending file and command name and returns -EIO. That message is worth recognising in a log: it is not a hardware fault or a filesystem bug but an application writing the same range through both a mapping and O_DIRECT at the same time.

Alignment also underpins a guarantee that direct I/O alone can offer. Atomic writes, requested with the RWF_ATOMIC flag to pwritev2() or io_uring, promise that a write of a supported size either reaches the media whole or not at all—no torn write, even across a power loss. The kernel cannot synthesize this; it can only pass through a capability the device already has, so the flag is rejected with -EOPNOTSUPP unless the file was opened on a filesystem and device that support it (ext4 and XFS set FMODE_CAN_ATOMIC_WRITE at open time when the inode qualifies), and it is valid on writes only. As with alignment, the limits are not guessable, so statx() reports them: STATX_WRITE_ATOMIC fills in stx_atomic_write_unit_min, stx_atomic_write_unit_max, and stx_atomic_write_unit_max_opt, the last being the largest size the device handles without an internal penalty. For a database that has historically paid for torn-page protection with a doubled write—a full-page journal before every page update—this removes an entire copy of every write from the I/O path.

Moving Data Without a User Buffer

Every access mode described so far ends, one way or another, at a user buffer. A buffered read copies out of a page-cache folio into it; a write copies in from it; direct I/O maps it and lets the device write into it; io_uring changes only who waits for the copy, not that a copy happens. The buffer is so nearly universal that it is easy to mistake it for part of the definition of I/O. It is not. A program that only wants to move bytes from one file descriptor to another never needs to see them, and for that case the kernel offers a third family of interfaces in which the user address space does not appear at all.

These are the zero-copy and copy-offload paths: splice(), sendfile(), and copy_file_range(). They are not optimizations bolted onto the interfaces of section 2 but distinct file_operations methods—splice_read, splice_write, splice_eof, copy_file_range, and remap_file_range, all declared alongside read_iter and write_iter in include/linux/fs.h. Yet, as this section shows, underneath them the machinery is the machinery already described: the read side is the page-cache loop of section 3 with the copy replaced by a reference, and the write side is literally write_iter called with an ITER_BVEC iterator—the iterator flavor Table 16-3 attributed to "splice" without saying what splice was.

splice() and the Pipe as a Conduit

The splice system call moves up to len bytes between two file descriptors, at least one of which must be a pipe. The pipe is not an accident of the interface; it is the whole design. A pipe in Linux is a small ring of struct pipe_buffer entries, and each entry is a reference to a page plus an offset and a length. Moving data into a pipe therefore need not mean copying it. It can mean taking a reference on a page that already holds the data and installing that reference in a pipe buffer. Once the bytes are described by page references rather than by an address in some address space, they can be handed to a second file descriptor without ever being materialized anywhere.

The read half is vfs_splice_read(), which dispatches to the file's splice_read method. Almost every page-cache-backed filesystem sets that method to filemap_splice_read(), and reading it next to filemap_read() is the most economical way to understand splice at all: it is the same function. It initializes a synchronous kiocb, calls filemap_get_pages() in a loop—so read-ahead is triggered exactly as in section 4—re-reads i_size after the folios are known uptodate for the same truncation race described in section 3.1, calls folio_mark_accessed() so the folios age like any other cache hit, and calls flush_dcache_folio() when mapping_writably_mapped() reports a writable mapping exists. Only the last step differs. Where filemap_read() calls copy_folio_to_iter(), filemap_splice_read() calls splice_folio_into_pipe(), which takes a reference on the folio and stores it in the next pipe buffer. The data does not move.

The substitution is not quite one buffer per folio. splice_folio_into_pipe() walks the folio a page at a time, filling one pipe_buffer per page and taking a separate folio_get() for each, because a pipe buffer names a struct page, not a folio. Large folios therefore consume pipe slots in proportion to their size, and pipe slots are scarce: a pipe is created with PIPE_DEF_BUFFERS, which is 16, so the default capacity is 64 KB on a 4 KB-page machine and a single splice() can move no more than that however large len is. A program that moves bulk data should raise the capacity with fcntl(F_SETPIPE_SZ), which is permitted up to /proc/sys/fs/pipe-max-size (1 MB by default) and beyond that only with CAP_SYS_RESOURCE. This, and not any property of the filesystem, is the usual reason a splice loop makes more syscalls than its author expected.

Two consequences follow from that single substitution. First, the transfer length is clamped up front to the free space in the pipe, computed as pipe->max_usage - pipe_buf_usage(pipe) pages: a splice can be short simply because the pipe is full, and a program that treats a short splice as an error is wrong. Second, splice is only zero-copy when there is a cached folio to take a reference on. do_splice_read() tests O_DIRECT and IS_DAX() before dispatching, and for either it substitutes copy_splice_read(), which allocates pages, performs an ordinary read into them, and splices those. Asking for O_DIRECT and splice together does not compose—it produces a copy that neither interface would have made alone.

The write half is the more surprising one. iter_file_splice_write(), the method almost every filesystem installs, walks the pipe's occupied buffers, calls pipe_buf_confirm() on each, and fills a struct bio_vec array with their page, offset, and length. It then builds an iterator over that array with iov_iter_bvec(&from, ITER_SOURCE, array, n, len), initializes a kiocb on the output file, and calls out->f_op->write_iter(&kiocb, &from). That is the same write_iter method section 2 introduced and section 3.2 traced; the filesystem cannot tell, and does not need to know, that the source pages came from a pipe rather than from user space. Only after the write returns does the function release the consumed buffers and advance pipe->tail. This is the clearest possible demonstration of the claim made throughout this chapter: the iterator is the interface, and what is on the far side of it is not the filesystem's business.

Two details of that loop are worth noticing. The bio_vec array is sized to pipe->max_usage and reallocated if the pipe grew while the loop slept, since F_SETPIPE_SZ can change the capacity underneath it. And a file whose operations supply no splice method at all does not fall back to anything: warn_unsupported() logs the file and command at debug level and returns -EINVAL, which is worth knowing when a splice fails for no visible reason.

The canonical splice destination, however, is not a file—it is a socket, and sockets take a different route. socket_file_ops installs splice_to_socket() as its splice_write, so the file-to-socket case never reaches iter_file_splice_write(). The function does something more direct: it fills a small on-stack array of sixteen bio_vec entries from the pipe's buffers, builds an ITER_BVEC iterator over them, and calls sock_sendmsg() with MSG_SPLICE_PAGES set in msg_flags. That flag is the network stack's half of the bargain: it tells the transport to attach the pages to the outgoing sk_buff by reference rather than copying them into skb fragments, so the same page-cache folio that the filesystem read into is what the network card eventually DMAs from. This is the path that makes the classic file server zero-copy end to end, and it is why the section 3 discussion of write_iter does not by itself explain sendfile() performance.

MSG_MORE is set on every send that does not exhaust the pipe, not just when the caller asked for SPLICE_F_MORE, so a multi-segment transfer naturally coalesces without the application saying anything. That optimization creates the problem the splice_eof method exists to solve. If the transfer ends—at end of file, or on an error partway through—the last send has already told the transport that more is coming, and TCP will sit on the final partial segment waiting for it. direct_file_splice_eof() therefore calls the output file's splice_eof, which for a TCP socket is tcp_splice_eof(), and that simply runs tcp_push() to flush the write queue. It is the only purpose the method has, and no filesystem implements it—only sockets do.

Each pipe buffer also carries a pipe_buf_operations vector, and its four methods explain several behaviours that would otherwise look arbitrary. confirm() is called before the contents are used and is where a reader waits if the page is not yet uptodate—it is the hook through which an I/O error on a page spliced earlier is finally reported to whoever drains the pipe. release() drops the reference when a buffer is fully consumed. get() takes an additional one, which is all tee() needs to do. And try_steal() attempts to take exclusive ownership of the page so it can be moved into another address space rather than copied; the page-cache implementation succeeds only for a clean, unshared, non-mapped page. Which brings us to the flags.

Four flags modify the operation, all defined in include/linux/splice.h. SPLICE_F_NONBLOCK makes the pipe side non-blocking without changing the file descriptors' own O_NONBLOCK state. SPLICE_F_MORE tells the output that more data is coming, which is what lets a web server splicing a file into a TCP socket avoid pushing a half-full segment. SPLICE_F_MOVE is a historical request to move pages rather than copy them—the try_steal() path above—and is today effectively advisory: the only code in 7.0.12 that still inspects it is the FUSE device's write path. SPLICE_F_GIFT belongs to vmsplice(), the companion call that splices pages of the calling process' own memory into a pipe; the gift flag promises the kernel may take the pages rather than referencing them, and it is the reason vmsplice() demands care—the caller must not touch the gifted pages again. A third companion, tee(), duplicates the contents of one pipe into another by taking additional references without consuming the source, which is how a stream can be forked to two destinations with no copy at all.

sendfile() and the Hidden Pipe

The sendfile system call predates splice and is older than most of the machinery it now rides on. Its promise is narrower and therefore simpler: copy count bytes from one descriptor to another inside the kernel. It was created for exactly one workload—a server sending a static file to a socket—and it remains the shortest way to express that.

In 7.0.12 sendfile() is a thin front end. do_sendfile() in fs/read_write.c checks whether the output descriptor is itself a pipe. If it is, the call becomes splice_file_to_pipe() and behaves exactly as splice() would. If it is not—the common case, a socket or a file—the call becomes do_splice_direct(), which allocates an internal pipe the caller never sees, splices the input into it, and drains it into the output. The pipe is present in every sendfile; the only difference is whether userspace supplied it. Understanding that removes most of the folklore around which of the two calls is faster: they are the same path, and sendfile() merely spares the caller the two extra descriptors and the loop.

The input descriptor must support splice_read, which in practice means a regular file or anything else backed by a page cache. The old rule of thumb that a socket cannot be the source needs qualifying in 7.0.12: sockets do install a splice_read method, sock_splice_read(), which delegates to the protocol's own or falls back to copy_splice_read(). What still constrains sendfile() is its interface rather than the mechanism—when an explicit offset is supplied the input must have FMODE_PREAD, or the call fails with -ESPIPE, because a descriptor with no seekable position has nothing for the offset argument to mean. The output has no comparable restriction, because the output side is a splice_write or write_iter call and nearly everything implements one. That asymmetry, rather than any policy decision, is why sendfile() is described as file-to-socket rather than the reverse, and why the reverse direction is written with two splice() calls and an explicit pipe—the case that keeps splice() from being redundant.

copy_file_range() and Copy Offload

Splice removes the user buffer but not the data movement—bytes still travel from the source storage into memory and back out to the destination. copy_file_range, added long after splice, asks a more ambitious question: can the copy be delegated to something that need not move the data at all? For two files on the same modern filesystem the answer is usually yes, because a copy of a file is describable as a second set of references to the same extents.

vfs_copy_file_range() in fs/read_write.c encodes the resulting preference order, and it is worth reading because the order is not obvious. First, if the output file's copy_file_range method exists, it is called. This is the network-filesystem case: NFS and SMB can ask the server to perform the copy, so no byte crosses the wire in either direction. Second, if both files live on the same superblock and the input file has a remap_file_range method, that is called with REMAP_FILE_CAN_SHORTEN. This is the reflink case—btrfs and XFS share the extents between the two inodes and mark them copy-on-write, so a gigabyte "copy" costs a metadata update and no data I/O whatsoever. Third, if neither applies, or if the reflink attempt returns zero or an error because the request was not aligned to the filesystem's requirements, the kernel falls back to do_splice_direct()—an ordinary splice through a hidden pipe. The same fallback catches the plainest case of all: two files on one superblock whose filesystem implements neither method.

The preference order is preceded by a gate that the interface's reputation tends to obscure. generic_copy_file_checks() refuses a copy between different superblocks with -EXDEV unless both files happen to reach the same copy_file_range function pointer—which is how NFS and SMB, each of which registers several file_system_type structures sharing one implementation, remain able to copy between two of their own mounts. So copy_file_range() always works within a filesystem, not everywhere; a program copying across mount points must still be prepared to fall back to a read-write loop itself. The same function shortens the request to the end of the input file, so a short return is ordinary rather than an error, and it rejects a few cases outright: overlapping ranges within one file give -EINVAL, an immutable destination gives -EPERM, and a swapfile on either side gives -ETXTBSY.

That fallback is a deliberate design choice rather than a convenience, and the comment above it says so: it exists so that userspace can be told copy_file_range() always works, instead of having to discover per filesystem whether it does. The COPY_FILE_SPLICE flag, which is internal to the kernel and not available to applications, forces the fallback directly; the NFS server uses it to implement server-side copy between two different filesystems, and it is also what lifts the -EXDEV gate just described. The fallback splice is deliberately issued outside the file_start_write() region that guards the other two branches, because holding freeze protection on the output superblock while reading from a different one is a recipe for deadlock. Note also that a reflink is not merely an optimization with the same semantics as a copy—it makes the two files share storage until one is written, so the second file consumes almost no space until it diverges. The same remap_file_range method backs the FICLONE, FICLONERANGE, and FIDEDUPERANGE ioctls, which expose sharing explicitly rather than disguising it as a copy.

Asynchronous I/O

Every mode so far blocks the calling thread until the data is at least cached. Asynchronous I/O lets a program submit a request and keep running, collecting the result later—essential for a server juggling thousands of connections or a database issuing many overlapping disk operations. Linux has two facilities: the older POSIX-style AIO, and io_uring, the modern interface that has largely superseded it.

The motivation is a scaling wall. The obvious way to overlap I/O is a thread per outstanding operation, blocked in read() or write(), but thousands of threads cost memory for stacks and load the scheduler with context switches, and the classic readiness interfaces (select, poll, epoll) only tell a program that a descriptor can be operated on without blocking—they do not perform the operation. True asynchronous I/O closes that gap: the program hands the kernel a complete request and is told later that it finished, so one thread can keep an arbitrary number of transfers in flight. Recall from the first section that completion is orthogonal to caching; an asynchronous request is still a kiocb and an iov_iter, so everything below is about how these two interfaces submit that work and deliver its result, not about a different I/O path.

The Legacy AIO Interface

The original kernel AIO (fs/aio.c) is built on five system calls— io_setup(), io_submit(), io_getevents(), io_cancel(), and io_destroy()—around a kernel aio context (struct kioctx). A program creates a context, fills submission blocks (struct iocb) describing reads and writes, submits a batch with io_submit(), and later reaps completions (struct io_event) with io_getevents(). Internally each submission becomes a kiocb whose ki_complete posts an io_event when the I/O finishes—so even this old interface funnels into the same read_iter/ write_iter methods as everything else. Its limitations are what motivated a replacement: it is only reliably asynchronous for O_DIRECT (buffered AIO often blocks), it needs a system call to submit and another to reap, and it never covered network sockets. It remains in the kernel for compatibility, but new code rarely uses it.

The reason buffered AIO "often blocks" is worth understanding, because it is the exact weakness io_uring fixes. When io_submit() issues a buffered read, the request runs through the same filemap_read() path as a synchronous one; if the data is not cached there is no lightweight way to step aside and be called back, so the submitting thread simply sleeps waiting for the folio—inside the "asynchronous" io_submit() call. Only direct I/O, whose bios naturally complete via an interrupt, was ever truly non-blocking. That, plus the two system calls per operation and the storage-only scope, made legacy AIO useful to a narrow set of direct-I/O databases and little else. Understanding its shape still matters, though: its struct iocb submission block and struct io_event completion are the direct ancestors of io_uring's SQE and CQE, and the per-context design is the seed of io_uring's per-ring context.

The interface has not stood entirely still, and two of its later additions are worth knowing because they are what makes it usable at all in an event loop. The first is IOCB_FLAG_RESFD: a submission block may name an eventfd, and the completion path calls eventfd_signal() on it. Since an eventfd is pollable, an application can put AIO completions into the same epoll loop as its sockets rather than dedicating a thread to io_getevents(). Without it, the only way to learn of a completion is to block in a syscall, which defeats the purpose. The second is io_pgetevents(), a sixth system call that takes a signal mask and applies it atomically for the duration of the wait, exactly as ppoll() does for poll()—closing the classic race in which a signal arrives after the handler decides to wait but before the wait begins. Two smaller flags round out the set: IOCB_FLAG_IOPRIO attaches an I/O priority to an individual request, and aio_rw_flags is passed through kiocb_set_rw_flags(), so the RWF_* vocabulary of section 2.2 is available per request here too. The opcode list also grew an IOCB_CMD_POLL, which lets a context wait for descriptor readiness rather than perform a transfer.

One line in aio_prep_rw() tells the rest of the story. Having built the kiocb, it clears IOCB_HIPRI with the comment that no one is going to poll for this I/O. Legacy AIO cannot use the polled completion path of section 6.2, because there is no thread positioned to spin: the submitter has already returned to userspace and the reaper is asleep in io_getevents(). That single restriction captures why the interface reached its ceiling. It is not that its authors chose badly; it is that a design in which submission and completion are separate system calls has nowhere to put the work that a modern fast path wants to do inline.

io_uring

io_uring (io_uring/) is the headline addition to Linux I/O since 2.6, and it rethinks asynchronous I/O around shared-memory ring buffers. A program calls io_uring_setup(), which creates a context (struct io_ring_ctx) and two queues that it then maps into its address space: a submission queue (SQ) of submission entries (struct io_uring_sqe) and a completion queue (CQ) of completion entries (struct io_uring_cqe). To issue I/O, the program writes SQEs describing the operations—each names an opcode, a file descriptor, a buffer, a length, an offset, and a user_data tag it will get back—into the SQ ring and advances the tail. To collect results it reads CQEs, each carrying the matching user_data, a result res, and flags, from the CQ ring. Figure 16-8 shows the two rings.

The power of the design is in how little the kernel and application have to talk. In the simplest use the program batches many SQEs and makes one io_uring_enter() call to submit them and, optionally, wait for completions; with the SQPOLL option a kernel thread polls the submission ring so the program submits work by writing memory alone, with no system call at all, and reaps completions the same way—the zero-syscall fast path. Each SQE is issued through the ordinary read_iter/write_iter path with an asynchronous kiocb; if an operation cannot complete without blocking, io_uring hands it to a pool of worker threads (io-wq) rather than stalling the submitter, which is why io_uring is genuinely asynchronous for buffered and direct I/O, unlike the old AIO. That last sentence is true but skips the interesting part, which the next paragraphs take up. io_uring_register() lets a program pre-register buffers and file descriptors so that repeated operations skip the per-call setup, and requests can be linked so one starts only when the previous finishes. Handing the request to a worker thread is in fact io_uring's last resort, not its first, and the mechanism it prefers is the one that makes buffered asynchronous reads genuinely work. The sequence in io_read() (io_uring/rw.c) is worth following because it ends inside a function section 3.1 already described. The first attempt sets IOCB_NOWAIT and calls read_iter; if the data is cached, the read completes inline and a CQE is posted without anything having blocked. If it returns -EAGAIN, io_uring does not punt. io_rw_should_retry() builds the struct wait_page_queue that section 1.3 described in the abstract, points its callback at io_async_buf_func(), swaps IOCB_NOWAIT for IOCB_WAITQ, and issues the read again—whereupon __folio_lock_async() registers on the folio's waitqueue and hands back -EIOCBQUEUED, and the whole call unwinds to userspace with nothing blocked. The part not yet said is what happens next: the waitqueue callback does not complete the request, it queues task work that re-runs the read from the owning task, which now finds the folio uptodate and copies it out. Only when the retry cannot be armed at all—a pollable file, a filesystem that does not set FOP_BUFFER_RASYNC, an explicit RWF_NOWAIT—does the request go to io-wq. The worker pool exists for the cases the page cache cannot describe, not for the common one.

A few mechanisms make the rings efficient and are worth naming. The submission ring does not hold SQEs directly; it holds an array of indices into a separate SQE array, so an application can fill entries ahead of time and submit them in any order—though a program that does not want that freedom can now ask for IORING_SETUP_NO_SQARRAY and have the indirection removed. The SQE itself can be extended (the 128-byte IORING_SETUP_SQE128 form) for opcodes that need more arguments, and the CQE likewise (IORING_SETUP_CQE32). Registered buffers address direct I/O's per-call cost: normally each transfer must extract and pin the user pages, as section 2.3 described, and release them at completion, but a buffer registered once with io_uring_register() is pinned once and reused, and the _FIXED opcodes transfer into it with no per-I/O pinning at all. For completions, IORING_SETUP_IOPOLL lets the kernel busy-poll a fast NVMe device instead of taking an interrupt, trimming latency further; it is the ring-wide form of the IOCB_HIPRI flag section 6.2 described, and like that flag it applies to direct I/O only—a request without IOCB_DIRECT, or on a file whose operations have no iopoll method, is refused with -EOPNOTSUPP. The flip side of putting so much power behind a pair of mmap'd rings is a large kernel attack surface, so some hardened and container environments restrict or disable io_uring outright—a real deployment consideration, not just a performance one.

Three further ideas have arrived since the interface settled, and they are what a program written against 7.0.12 actually looks like. The first is multishot operations. An ordinary SQE produces one CQE and is done; a multishot one stays armed and produces a CQE each time it has something to report, marking each with IORING_CQE_F_MORE to say the request is still alive. A multishot IORING_OP_ACCEPT delivers every incoming connection from a single submitted request, and a multishot RECV delivers every arriving message—so a server's steady state involves no submissions at all, only reading CQEs.

Multishot forces the second idea, because a request submitted long before the data arrives cannot name a buffer: the application does not know how many will be needed or how large. Provided buffers invert the ownership. The program registers a buffer ring with IORING_REGISTER_PBUF_RING, publishing a pool of buffers the kernel may draw from, and the completion reports which one was used by setting IORING_CQE_F_BUFFER and packing the buffer ID into the upper 16 bits of cqe->flags. The application consumes it and hands it back by advancing the buffer ring's tail—again without a system call. This is what lets one thread service tens of thousands of sockets with a bounded, shared pool of memory rather than a buffer per connection.

The third is the completion-side counterpart of SQPOLL. IORING_SETUP_DEFER_TASKRUN, used together with IORING_SETUP_SINGLE_ISSUER, stops the kernel from running the request's task work at every opportunistic transition into the owning task and instead defers it to the moment the application asks for events. A ring that promises only one thread will ever submit to it also gives up the internal locking that supported the general case. The pair is now the recommended configuration for a dedicated I/O thread, and it illustrates a theme worth naming: io_uring's later performance work has been less about doing I/O faster than about removing interruptions, locks, and transitions that the general-purpose design had to assume were necessary.

The opcode list has grown accordingly, past sixty entries, and two families stretch the framing of this chapter. IORING_OP_URING_CMD is a passthrough: rather than naming a read or a write, the SQE carries a device-specific command that the file's uring_cmd method interprets, which is how NVMe passthrough submits raw commands to a drive through the same ring as everything else. And IORING_OP_SEND_ZC and SENDMSG_ZC bring the zero-copy story of section 7 into the ring, sending directly from registered buffers and posting a second, IORING_CQE_F_NOTIF-marked CQE later to say the network stack has finished with the pages and the application may reuse them. One Interface Underneath

For all their differences at the top, the two asynchronous interfaces—and the synchronous ones—end in the same place. A blocking read(), an io_submit(), and an io_uring IORING_OP_READ all build a kiocb and an iov_iter and call the file's read_iter; they differ only in whether the kiocb carries a completion callback and how the result is delivered— returned inline, posted as an io_event, or written as a CQE. This is the quiet unification the chapter has been building toward: the four data methods of Linux 2.6 became two iterator methods, and asynchrony, direct I/O, and vectored I/O became flags and buffer types on those two methods rather than separate code paths. Table 16-11 summarizes the asynchronous choices.

io_uring widens that seam without breaking it. Beyond the data opcodes it also carries operations that are not read_iter/write_iter at all— IORING_OP_OPENAT, CLOSE, FSYNC, the socket verbs, and even futex waits and waitid()—so a program can run an entire chain of file and network steps through one ring, linking them so each begins when the last completes. With IORING_OP_URING_CMD it goes further still and leaves the VFS behind altogether, handing a command to a driver. It is fair to say the ring has stopped being an asynchronous file interface and become a general mechanism for asking the kernel to do things. But for the operations this chapter is about, the picture is exactly the one Figure 16-1 opened with: the ring is a submission-and-completion frame wrapped around the same kiocb and iov_iter that a plain read() builds on its own stack. Learn those two objects and the read_iter/write_iter pair, and every access mode in the chapter—buffered, synchronous, memory-mapped, direct, and asynchronous—is a variation on a single theme rather than five separate subsystems to master.

Summary

This chapter followed a process's file access from the system call down to the point where data is delivered or queued for the device. The overarching change since Linux 2.6 is unification: the separate read/write/aio_read/aio_write methods collapsed into two iterator methods, read_iter and write_iter, each carrying a kiocb that holds the I/O's state and flags and an iov_iter that describes the buffer. Every access mode is a way of setting those two objects up: buffered access copies through the page cache; O_SYNC makes writes durable inline; read-ahead prefetches folios along the buffered read path; memory mapping brings data in through faults on VMAs now stored in a maple tree; direct I/O sets IOCB_DIRECT and builds bios straight on pinned user pages; and asynchronous I/O sets a completion callback. Because the flags live in the kiocb rather than in the file, most of them can now be chosen per request through preadv2() and pwritev2()— RWF_NOWAIT, RWF_HIPRI, RWF_DSYNC, the newer RWF_DONTCACHE, which keeps the buffered path but drops the folios behind it, and RWF_ATOMIC, which asks the device for a write that cannot tear. The rules that cannot be guessed are no longer folklore either: statx() reports the two direct-I/O alignments through STATX_DIOALIGN and the atomic-write limits through STATX_WRITE_ATOMIC.

Two of the chapter's findings are worth restating because they cut against the names of the things they describe. The first is that O_DIRECT names a cache bypass and not necessarily a copy bypass: a hole is zeroed without touching the device, inline data is transferred with a memcpy, and IOMAP_DIO_BOUNCE routes the whole transfer through a kernel buffer when the device needs data that will hold still long enough to be checksummed. The second is that the page cache and direct I/O are kept coherent by flushing and invalidating around every direct operation. The result is correct, and it is expensive in exactly the way direct I/O exists to avoid; it also has one hard edge, since direct I/O is not serialized against mmap() at all and a collision is reported rather than resolved.

Section 7 added a family that the unification argument might otherwise have hidden. splice(), sendfile(), and copy_file_range() move data between descriptors without it entering the process's address space, and they have their own file_operations methods to do it. Even so, the pattern holds: filemap_splice_read() is filemap_read() with copy_folio_to_iter() replaced by a reference into a pipe buffer, and iter_file_splice_write() is nothing but a write_iter call over an ITER_BVEC iterator built from the pipe—though the destination that matters most, a socket, takes its own route through splice_to_socket() and MSG_SPLICE_PAGES, which is what carries the zero-copy property across the boundary into the network stack. sendfile() is a splice through a pipe the caller never sees, and copy_file_range() goes further still, preferring a server-side copy or a same-superblock reflink that moves no data at all, and falling back to that same hidden-pipe splice when neither is possible—within one filesystem, that is, since a copy across superblocks is still refused with -EXDEV.

The asynchronous story is where the kernel has moved furthest. The POSIX-style AIO of Linux 2.6 survives but is eclipsed by io_uring, whose shared-memory submission and completion rings let a program issue and reap I/O with few or no system calls, asynchronously for buffered and direct I/O and for storage and network alike. The buffered half of that promise deserves the credit it usually does not get, because it was not won with worker threads: IOCB_WAITQ lets a read register a callback on a folio and return -EIOCBQUEUED, and the worker pool is what happens when that cannot be arranged. Around this core the interface has grown a vocabulary of its own—multishot requests that stay armed, buffer rings the kernel draws from, and a passthrough opcode that leaves the VFS behind entirely—so that io_uring is no longer only an asynchronous file interface. Yet for the operations this chapter is about it still bottoms out in the same read_iter/write_iter path as a plain read()—the theme of the whole chapter. The through-line is that file access has been generalized into a single, flag-driven interface and then made asynchronous end to end. One pair of iterator methods now serves every mode; the page cache, read-ahead, and writeback of the previous chapter sit beneath the buffered and mapped paths; the zero-copy paths reach the same methods from the other side; and io_uring finally makes the whole stack asynchronous without a separate code path. Seen together, the two structures of section 2 are what made all of this possible: once the question "where are the bytes?" has a single answer of its own, a filesystem stops needing to know who is asking.
