The previous chapters filled memory up: the page cache of Chapter 15 grows to hold file data, processes fault in anonymous pages, and the kernel's own caches of dentries, inodes, and slab objects expand as the system runs. None of these give memory back on their own. This chapter is about the machinery that takes it back—page frame reclaiming: how the kernel decides which pages are worth keeping, how it finds and frees the rest, and what it does when even that is not enough. It completes the memory story begun in the addressing and allocation chapters.

The reclaim subsystem has changed more since Linux 2.6 than almost any other part of the kernel. The LRU lists that were per-zone in 2.6 are now per-node and, under memory control groups, per-cgroup; a whole new aging algorithm, Multi-Gen LRU, sits alongside the classic active/inactive scheme; reverse mapping was rebuilt around anon_vma chains and interval trees; reclaim operates on folios rather than single pages; the shrinker interface for kernel caches was modernized; the out-of-memory killer gained an asynchronous reaper; and swapping acquired clusters, compression, and solid-state awareness. Three additions go further than modernizing a mechanism and change what reclaim is. Reclaim became scoped: a memory control group has its own LRU lists, its own limits, and its own out-of-memory killer, so reclaim can be aimed at one container instead of the whole machine. It became self-observing: refault detection measures whether an eviction was a mistake, and pressure stall information measures what reclaim is costing the workload, so the subsystem now has evidence about its own decisions and userspace can act on that evidence before the kernel has to. And on machines with more than one speed of memory it acquired a step short of eviction, demotion, which moves a cold folio to slower memory rather than freeing it. The concepts—LRU approximation, reverse mapping, watermarks, swapping—are the same as in Linux 2.6, but nearly every mechanism beneath them is new, and reclaim is no longer only a reaction to shortage: it is also a tool a controller can drive deliberately. The chapter takes these topics in order: what can be reclaimed, how pages are aged, how they are found and freed, when reclaim runs, how kernel caches shrink, what happens when reclaim fails, and swapping. It ends with mechanisms Linux 2.6.11 did not have: page migration, which reuses the reverse-mapping machinery to move a page instead of evicting it, and the memory hot-remove and memory-failure handling that depend on it.

The Reclaim Problem

Linux deliberately allows memory to be overcommitted: it hands out page frames freely and places few hard limits on how much a process or a cache may accumulate, because the most useful thing to do with free RAM is to fill it—with cached file data, with process pages, with kernel object caches—rather than leave it idle. The consequence is that memory inevitably runs low, and when it does the kernel must reclaim frames faster than they are consumed. Reclaim is not an occasional emergency but a continuous background activity on any busy system, quietly recycling the least valuable pages so that allocation almost always finds a frame ready.

How far the kernel is willing to overcommit is itself a policy, set by vm.overcommit_memory (sysctl_overcommit_memory in mm/util.c) and enforced by __vm_enough_memory(). The default, OVERCOMMIT_GUESS, is far looser than its name suggests: it compares each individual request against totalram_pages() plus total_swap_pages and rejects only a single allocation larger than all memory put together, keeping no running total of what has already been promised. A thousand processes may therefore each be promised a gigabyte on a machine with eight. OVERCOMMIT_ALWAYS drops even that check, betting that most allocated memory is never touched. Only OVERCOMMIT_NEVER does real accounting, comparing the running vm_committed_as counter against vm_commit_limit()—all of swap plus overcommit_ratio percent of RAM (50 by default, or an absolute figure in overcommit_kbytes)—and it holds back two reserves from that limit so a runaway process cannot make the machine unrecoverable: admin_reserve_kbytes for a privileged user to log in and intervene, and a slice of user_reserve_kbytes so the offending process cannot consume the last of its own user's budget. The two figures are visible as CommitLimit and Committed_AS in /proc/meminfo, and a refusal is logged rather than silent.

These controls only bound how much virtual memory may be promised—they do not free physical frames, and under the default policy they barely bound anything at all. Because most workloads touch far less memory than they map, the promises routinely exceed RAM, and the physical shortfall that results is what page frame reclaiming exists to manage. It is worth being precise about the division of labour, because the two mechanisms are often confused: overcommit accounting decides whether an mmap() or brk() may succeed, and it operates on address space that may never be touched; reclaim operates on frames that have actually been allocated and must now be recycled. A machine can pass every overcommit check and still run out of memory, and a machine with overcommit disabled entirely still needs reclaim—because a promise that is kept still has to be paid for in frames. This section explains why reclaim must run proactively, what it can and cannot free, and the overall shape of the subsystem.

Why the Kernel Reclaims

The reason reclaim cannot simply wait until memory is exhausted is a long-standing deadlock hazard that remains real. Freeing a dirty page requires writing it to disk, and writing it requires memory—for a bio, for buffer structures, for the driver's own allocations. If the kernel let free memory reach zero before reclaiming, it could find itself unable to free anything because it could not allocate the means to do so. Reclaim therefore keeps a reserve: it starts well before memory is gone, maintains a floor of free pages that only the most critical allocations may dip into, and escalates its effort as the reserve shrinks. The watermarks that encode this floor are the subject of a later section; the point here is that reclaim exists to keep the system out of the corner where it can neither allocate nor free.

Two mechanisms protect reclaim from recursing into the very shortage it is resolving. First, a thread doing reclaim marks itself with PF_MEMALLOC (through memalloc_noreclaim_save()): its own small allocations—for the bios and structures needed to write pages out—are allowed to dip into the emergency reserve and are exempted from triggering nested reclaim, so the act of freeing memory cannot itself block on a lack of memory. Second, allocations carry flags that tell reclaim what it may safely do on their behalf: an allocation issued from inside a filesystem or block driver clears __GFP_FS or __GFP_IO, and reclaim honoring such a request will not re-enter the filesystem or start I/O to free a page, because doing so could deadlock on a lock the caller already holds. These constraints are why reclaim is careful about which pages it frees in a given context, not just how many.

The way that second constraint is expressed has changed, and the change is worth understanding because the old way did not really work. Clearing __GFP_FS at the allocation site requires every allocation made anywhere inside a filesystem's critical section to be found and corrected, including allocations made by helper code and by libraries that have no idea which context they were called from—and a single missed call site reintroduces the deadlock. Modern code therefore marks the scope rather than the call: memalloc_nofs_save() sets PF_MEMALLOC_NOFS on the current thread, and from then until the paired memalloc_nofs_restore(), current_gfp_context() strips __GFP_FS from every allocation the thread makes, whether or not that allocation's author knew about the constraint. memalloc_noio_save() does the same for __GFP_IO, which is how a block driver or a suspend/resume path protects itself. The family extends further—memalloc_pin_save() clears __GFP_MOVABLE so that pages about to be pinned for DMA are not allocated somewhere migration would later want to move them—and all of them share the same memalloc_flags_save() mechanism, returning only the bits they actually set so that nested scopes restore correctly.

The deadlock this guards against is subtle enough that the kernel now checks for it automatically rather than trusting review. Lockdep models reclaim as a notional lock: an allocation that permits filesystem re-entry acquires fs_reclaim for the duration of might_alloc(), and reclaim itself acquires the same token when it calls into a filesystem. If any real filesystem lock is ever held across an allocation that could re-enter the code holding it, lockdep reports the inversion on a kernel that has never actually deadlocked and may never have come close. The check runs on every allocation on a debug kernel, which is why a class of bug that once required a production hang to discover is now usually caught during development.

The reserve those flags gate is not a single door but a graded series of them. An ordinary allocation must leave the low watermark intact; one marked __GFP_HIGH gets ALLOC_MIN_RESERVE and may consume half of what remains below the minimum; an atomic allocation that cannot block gets ALLOC_NON_BLOCK; and only ALLOC_NO_WATERMARKS—granted to PF_MEMALLOC threads and, briefly, to a task chosen by the OOM killer so it can exit—ignores the watermarks entirely. Reclaim's own allocations therefore sit at the innermost level precisely because everything else depends on them completing.

Reclaim also serves a subtler goal than avoiding exhaustion: it keeps the right pages resident. Memory that holds frequently-used file data or a process's hot working set is far more valuable than memory holding a page read once and never touched again. A good reclaim policy is really a good guess about which pages will be used again soon, so that the pages it evicts are the ones least likely to be missed. The cost of a wrong guess is a refault—a page evicted just before it is needed, then faulted straight back at the price of a disk read—and in the worst case a system that spends all its time paging the same working set in and out, called thrashing. Most of this chapter is about how the kernel makes that guess—through LRU approximation and refault feedback—and how it acts on it.

That last point marks the most important difference from 2.6-era reclaim. The 2.6 reclaimer chose victims and moved on; it had no way to learn whether its choices had been good ones, so a policy that was evicting exactly the wrong pages looked, from inside the kernel, identical to one that was working perfectly. Modern reclaim observes itself. Every refault of a page the reclaimer recently evicted is recorded and compared against how much the lists have aged in the meantime, which turns a wrong guess into a measurement that feeds back into the next decision. Alongside it, pressure stall information accumulates the time threads actually spend waiting on memory, so that "the machine is thrashing" becomes a number a scheduler or a userspace supervisor can act on rather than an inference drawn from a rising page-fault rate. Both mechanisms appear later in the chapter; what matters here is that reclaim in 7.0.12 is a feedback loop, and much of its apparent complexity is the machinery of that loop.

What Can Be Reclaimed

Not every page can be freed, and those that can are freed in different ways. The kernel sorts pages by what reclaiming them costs. A page backing a clean, up-to-date copy of file data is the cheapest: its contents are already on disk, so it can simply be dropped and re-read later if needed. A dirty file page must first be written back before it can be dropped. An anonymous page—process heap, stack, or private mapping—has no file behind it, so to evict it the kernel must first copy it to a swap area. And some pages cannot be touched: kernel stacks, pinned pages, reserved pages, and pages in memory regions locked with mlock are unevictable and set aside entirely. Table 17-1 groups the page types the way the reclaimer treats them.

Two long-standing statements of that taxonomy need qualifying in 7.0.12. The first is "anonymous memory cannot be reclaimed without swap." It remains true on an ordinary machine, but on one with tiered memory the reclaimer has a second option: rather than write an anonymous folio to swap it can demote it to a slower node, freeing the fast frame without any swap area existing at all. Section 4.3 covers this; the consequence for the taxonomy is that "swappable" and "reclaimable" are no longer the same predicate. The second is that anonymous memory always needs writing somewhere. An application that has finished with a buffer but wants to keep the mapping can call madvise(MADV_FREE), which tells the kernel the contents are expendable. The folio's PG_swapbacked flag is cleared, and the reclaimer may then simply drop it—no swap slot, no I/O, no writeback—making it the cheapest page in the system to reclaim, cheaper even than a clean file page, because nothing has to be re-read afterwards. What makes the mechanism lazy rather than an immediate free is that the pages stay mapped and readable until pressure actually arrives; if the application writes to one first, try_to_unmap_one() notices the folio is dirty, sets PG_swapbacked again, and aborts the unmap, quietly returning the page to the ordinary swappable population. The application learns of the discard only by finding zeroes, which is why MADV_FREE is safe for caches and allocator free lists and wrong for anything that must survive. A mapping created with MAP_DROPPABLE takes the idea to its conclusion: its pages are discarded under pressure even when dirty, which is what lets the kernel hand a process a piece of writable state—the vDSO random-number state, for instance—that it can reclaim unilaterally without ever needing to preserve.

This classification is not merely descriptive; it is built into where a page lives. Evictable pages sit on the anonymous or file LRU lists according to whether they have a file behind them, and the reclaimer scans those two families at independently chosen rates—the subject of the next section. Unevictable pages are deliberately kept off the scannable lists, on LRU_UNEVICTABLE, so the reclaimer never wastes effort examining a page it could not free anyway. The test that decides this, folio_evictable(), is narrower than the informal list above suggests: it asks only whether the folio's mapping has been marked unevictable—as ramfs does for its whole address space, and as shmctl(SHM_LOCK) does for a locked segment—and whether PG_mlocked is set because some VMA mapping the folio has VM_LOCKED. Kernel stacks and slab do not appear in that test because they are not on any LRU list in the first place; they are unreclaimable rather than unevictable, a distinction worth keeping because unevictable folios are still aged, still accounted, and can still come back. The placement is a cache of a condition that may change, not a permanent verdict: when a segment is unlocked or the last VM_LOCKED mapping goes away, check_move_unevictable_folios() walks the affected folios and moves those that now pass the test back onto the evictable lists, incrementing UNEVICTABLE_PGRESCUED as it goes. One category blurs the file/anonymous line: tmpfs and shared-memory pages have no backing file yet are not truly anonymous either, so the kernel treats them as swap-backed—they are reclaimed by writing to swap, exactly like anonymous memory, which is why a system with no swap cannot shrink its tmpfs usage. The dirty-versus-clean distinction, meanwhile, is not fixed: a clean file page becomes dirty the moment it is written, and writeback turns a dirty page clean again, so a page can move between the cheap and expensive categories over its lifetime.

The Shape of Reclaim

Before the details, it helps to see the whole subsystem at once. Reclaim is driven from two directions. In the background, per-node kswapd threads wake when free memory drops below a watermark and reclaim until it rises comfortably above one, so that most allocations never wait. In the foreground, an allocation that cannot be satisfied performs direct reclaim in the calling thread, and a memory control group that exceeds its limit reclaims within its own scope. All of these paths converge on the same core: a scan of the LRU lists that ages pages and evicts the coldest, assisted by reverse mapping to unmap shared pages and by per-subsystem shrinkers to trim kernel caches. When every path has failed and memory is still not available, the out-of-memory killer is the last resort. Figure 17-1 shows how these pieces fit together, and the rest of the chapter takes them one at a time. Table 17-2 summarizes the triggers—when each fires, who runs it, and what it reclaims.

To those two directions 7.0.12 adds a third that has no shortage behind it at all. Proactive reclaim is reclaim requested by userspace: writing a byte count to a cgroup's memory.reclaim file, or to /sys/devices/system/node/nodeN/reclaim, drives the same machinery on demand, and both paths land in the same user_proactive_reclaim(). The motivation is that a supervisor often knows things the kernel cannot: that a batch job has finished and its page cache is now worthless, that a machine is about to be given a latency-sensitive tenant and should have free memory before that tenant arrives rather than after it stalls. Because the caller may want different policy than the kernel would choose—a one-off sweep of a finished job's anonymous memory to swap, say—the request accepts a swappiness= override that applies only to that invocation. An older and much blunter relative of the same idea survives in node_reclaim_mode (vm.zone_reclaim_mode), which makes an allocation reclaim locally rather than fall back to another NUMA node; it is off by default, because on most workloads the cost of reclaiming beats the cost of a remote access it was trying to avoid.

Three properties of this design are worth fixing in mind before the details. Reclaim is scoped: it operates per NUMA node, so freeing memory on a busy node does not disturb a quiet one, and under memory control groups it can be aimed at a single container. It is graduated: rather than freeing everything at once, each attempt scans only a fraction of the lists, and that fraction is widened—by stepping the reclaim priority counter down toward zero, as section 4.1 describes—only if the gentler pass did not free enough. A system under mild pressure therefore does a little quiet background work, while one under severe pressure escalates through direct reclaim, cache shrinking, and finally the OOM killer. And it is bounded: no path retries forever. MAX_RECLAIM_RETRIES, sixteen, caps how many fruitless rounds an allocation, a cgroup charge, or a proactive request will make before giving up, and the same count of consecutive failures is what marks a node's kswapd as unable to make progress. That bound is what turns an unwinnable shortage into a decision—a failed allocation, a -EAGAIN, or the OOM killer—instead of a machine that spins in reclaim forever, which is the failure mode the bound exists to prevent. The sections that follow trace this progression: first how pages are aged and found (the LRU lists, reverse mapping, and the eviction pipeline), then what sets reclaim in motion (watermarks, kswapd, direct reclaim, and cgroups), then the shrinking of kernel caches, the last-resort killer, and finally swapping—the backing store that makes most anonymous reclaim possible at all.

The LRU Lists and Folio Aging

The kernel cannot afford true least-recently-used bookkeeping—stamping every page on every access would be far too expensive—so it approximates LRU with a small number of lists and a cheap per-access hint. This section describes those lists, how a folio ages across them, how the kernel splits its effort between file and anonymous memory, and the newer Multi-Gen LRU that reorganizes the whole scheme.

The approximation is a descendant of the classic clock algorithm: instead of ordering pages by exact access time, the kernel keeps them in coarse buckets and moves a page between buckets based on a single "was it touched recently" bit, sweeping the buckets in order when it needs to free something. What follows is that idea made concrete—which buckets exist, what moves a page between them, and how the whole structure is replicated per node and per cgroup so that reclaim can be aimed precisely.

The Five LRU Lists and the lruvec

Reclaim tracks evictable memory on LRU lists. There are five, enumerated by enum lru_list (include/linux/mmzone.h): an active and an inactive list each for anonymous and for file-backed memory, plus a single unevictable list for pages that must not be reclaimed. Splitting anonymous from file memory lets the kernel reclaim the two at different rates; splitting active from inactive is the LRU approximation itself, with the inactive list holding eviction candidates and the active list holding the working set. The unevictable list keeps folios locked with mlock and other non-reclaimable folios off the scan entirely, so the reclaimer never wastes time examining them. Table 17-3 lists the five.

A folio records which list it is on in its own flags—PG_lru marks it as being on some LRU list at all, PG_active distinguishes active from inactive, and PG_unevictable marks the unevictable list—so the reclaimer can tell a folio's status without consulting the lists themselves. Adding a folio to a list is deferred and batched: folio_add_lru() (mm/swap.c) does not take the list lock immediately but queues the folio on a per-CPU folio batch that is flushed in bulk (or drained explicitly by lru_add_drain()), which keeps the hot lru_lock from being contended on every single page. Reclaim itself works in batches too, isolating up to SWAP_CLUSTER_MAX (32) folios from a list at once so that the lock is held briefly and the freed folios can be processed without it.

The deferral is more thorough than the word "batch" suggests, because it is not only additions that are queued. struct cpu_fbatches (mm/swap.c) holds six separate per-CPU batches, one for each kind of list movement that ordinary code performs: lru_add for newly added folios, lru_activate for promotions, lru_deactivate for folios an application has declared cold with madvise(MADV_COLD), lru_deactivate_file for cache folios that invalidate_mapping_pages() could not free outright, lru_lazyfree for folios released with MADV_FREE, and lru_move_tail for the rotations that folio_rotate_reclaimable() performs when writeback finishes on a folio reclaim had already given up on. Nearly every LRU state change outside reclaim is therefore recorded in a folio's flags immediately and reflected in the lists only later, in bulk, under a single acquisition of lru_lock. The structure is split by locking discipline rather than by purpose: the first five batches are protected by a local_lock_t that merely disables preemption, while lru_move_tail needs a second, interrupt-disabling lock, because that last case runs from a block-layer completion in interrupt context. Draining is expensive enough—lru_add_drain_all() must schedule work on every CPU that has anything pending—that the kernel checks each CPU's batches first and skips the ones that are already empty.

The consequence worth remembering is that a folio's flags are the truth and the lists lag behind them. A folio may carry PG_active while still sitting on the inactive list because its promotion has not been drained yet, and folio_add_lru() may be handed a folio that is not yet on any list at all. Code that must see an accurate list, such as memory hotplug or the migration paths that need a page frame vacated, calls lru_add_drain_all() first for exactly this reason. Reclaim itself tolerates the lag: a folio it fails to isolate because someone else holds it is simply put back, and the counter SWAP_CLUSTER_MAX_SKIPPED bounds how many folios a scan will step over before it gives up rather than continuing to search a list that is mostly ineligible.

The larger structural change since Linux 2.6 is where these lists live. In 2.6 the LRU lists were global, then per-zone. Now they are gathered in a struct lruvec (include/linux/mmzone.h) that exists per NUMA node—pglist_data.__lruvec—and, when memory control groups are configured, per (node, cgroup), embedded in each mem_cgroup_per_node. This is what lets a cgroup's memory be aged and reclaimed as its own pool, independent of the rest of the system. The move from per-zone to per-node lists also fixed a real problem of the older design: with lists split by zone, a page's age depended on which zone it happened to land in, and reclaim could evict a recently-used page from one zone while an idle page sat in another. A single per-node list ages all of a node's memory together, and zone eligibility is applied only when folios are picked for eviction. Besides the five lists[], the lruvec carries the state that drives aging: anon_cost and file_cost (the running reclaim cost of each side), nonresident_age (a clock used for refault detection), and, when Multi-Gen LRU is built in, an embedded lru_gen_folio. Active, Inactive, and the Second Chance

A folio's position between the active and inactive lists is the kernel's estimate of how likely it is to be used again. New folios generally enter the inactive list; a folio that is referenced again while inactive is promoted to the active list, and a folio on the active list that survives a scan without recent references is demoted back toward inactive. Reclaim always takes its victims from the inactive end, so this movement is what protects the working set: pages that keep getting touched climb to safety, while pages that fall quiet drift toward eviction.

The cheap per-access hint that drives this is the PG_referenced flag, combined with the hardware "accessed" bit in page tables. When code touches a file page through the cache, folio_mark_accessed() (mm/swap.c) applies a second-chance rule: an unreferenced folio is merely marked PG_referenced; a folio that is already referenced when touched again is promoted to the active list and its flag cleared. During a scan, shrink_active_list() (mm/vmscan.c) consults reverse mapping through folio_referenced() to see whether any page table still has the folio's accessed bit set; an unreferenced active folio has its PG_active cleared, gains PG_workingset, and moves to the inactive list, while a referenced executable file page is kept active so that program text is not evicted under momentary pressure. A folio therefore needs to be missed twice—once by losing its referenced status and again by reaching the inactive tail without being touched—before it is evicted, which filters out one-off accesses like a single streaming read.

The transitions folio_mark_accessed() performs are worth stating exactly, because the function is doing less than its name implies. An inactive, unreferenced folio becomes inactive and referenced; an inactive, referenced folio becomes active and unreferenced, with workingset_activation() recording the promotion for the refault machinery; and an active folio merely becomes referenced again, since it is already as safe as it can be. A folio on the unevictable list is skipped outright, because that list is never rotated and marking it would accomplish nothing. Even the promotion is deferred: if the folio is on an LRU list, folio_activate() queues it on the lru_activate batch, and if it is not—because it is still sitting in an undrained lru_add batch—__lru_cache_activate_folio() reaches into that batch and sets PG_active in place, so the folio lands directly on the active list when the batch is finally flushed and never touches the inactive list at all.

Two escape hatches bypass the aging machinery entirely, one at each end of the value scale. The first is for data the caller knows is worthless: a folio carrying PG_dropbehind, set when a file is read or written with RWF_DONTCACHE, causes folio_mark_accessed() to return immediately without recording anything. This is a more direct answer to cache pollution than the second-chance rule, which only limits the damage a streaming read does; the dropbehind hint prevents the folio from ever competing for residency in the first place, so a backup or a media-transcoding pass can move terabytes through the page cache without displacing a single page of anyone's working set. The second is idle page tracking: the accompanying PG_idle flag, set by a userspace profiler writing to /sys/kernel/mm/page_idle/bitmap, is cleared on any access, which lets a monitoring tool measure which pages a workload actually touches without perturbing the reclaimer's own decisions. And when Multi-Gen LRU is enabled the whole function short-circuits to lru_gen_inc_refs(), since that ager replaces the single PG_referenced bit with a small saturating counter, as the last part of this section describes.

The two hints play different roles because they capture different things. The page-table accessed bit is set by hardware on any access to a mapped page and is harvested only lazily, during a scan, through reverse mapping; it is how the kernel notices that a mapped page is still hot without trapping every access. The PG_referenced flag, by contrast, is set by software on cache accesses—reads and writes that go through read/write rather than a mapping—and is the memory of "this was touched since the last time we looked." Together they let the same active/inactive machinery age both mapped and unmapped pages. The distinction the executable case draws is deliberate: dropping a page of program text forces a hard page fault and a disk read the instant the code runs again, so file pages in VM_EXEC mappings are given an extra reprieve, which keeps a busy system's hot code resident even when its data cache is churning.

The size relationship between the two lists matters as much as the movement between them. The inactive list must be large enough to act as a genuine staging area—if it were tiny, a folio would race from promotion to the evict end before it had a chance to prove itself, and the second-chance filter would collapse. The reclaimer therefore aims to keep enough folios inactive relative to active, deactivating from the active list when the inactive side runs low, so that a page demoted from active always spends some observable time as an eviction candidate before it is actually freed. The PG_workingset flag set during that demotion is what later lets refault detection recognize a page that was part of the working set when it was evicted, closing the loop described in the pipeline section.

What counts as "enough" is not a fixed fraction, and the way it varies is instructive. inactive_is_low() (mm/vmscan.c) computes a target ratio of active to inactive as int_sqrt(10 * gb), where gb is the size of the two lists together in gigabytes, and reports the inactive side as too small when inactive * ratio < active. On a small lruvec the ratio is 1, so half the folios are kept inactive; at a gigabyte it is 3, or a quarter; at a terabyte it is 101, barely one percent. The target shrinks because what the inactive list really has to provide is time—a window long enough for a folio that is still wanted to be touched again before it reaches the end—and on a large machine a small percentage is already an enormous number of folios and a long window. Holding half a terabyte inactive would not lengthen that window usefully; it would only shrink the protected working set.

The active list is not always scanned, and the condition that decides is a nice illustration of reclaim watching itself. Before scanning a node, prepare_scan_control() sets DEACTIVATE_ANON and DEACTIVATE_FILE in sc->may_deactivate only if the corresponding inactive list is low or the WORKINGSET_ACTIVATE_ANON and WORKINGSET_ACTIVATE_FILE counters have moved since the last time reclaim looked—that is, only if folios have been refaulting and re-activating, which means a new working set is establishing itself and the current active list may be full of stale survivors of the old one. On a machine in steady state with a healthy ratio, neither condition holds, and reclaim takes its victims from the inactive lists without ever disturbing the active ones. This is why shrink_active_list() can be an expensive operation and still not show up on a well-behaved system: it runs when the evidence says the aging itself has gone stale, not on every pass.

Balancing Anonymous and File Reclaim

Because anonymous and file pages sit on separate lists, the reclaimer must decide how to divide its scanning between them. Two inputs govern the split. The first is swappiness, the tunable vm_swappiness (default 60, also settable per cgroup), which expresses how willing the kernel is to reclaim anonymous memory by swapping versus reclaiming file pages by dropping or writing them back; a low value steers pressure toward the file lists, a high value toward swapping. The second is measured cost: the lruvec tracks anon_cost and file_cost, updated as reclaim actually does work, so that the side which has recently been more expensive to reclaim (because it needed more I/O or rotated more pages) receives proportionally less pressure. get_scan_count() (mm/vmscan.c) combines these into the number of folios to scan from each list.

Anonymous reclaim has a hard precondition the file side does not: there must be somewhere to put the pages. can_reclaim_anon_pages() gates it on available swap space—total_swap_pages for global reclaim, the cgroup's swap allowance for cgroup reclaim—so on a system with no swap the anonymous lists are simply never scanned, and all reclaim pressure falls on file pages. This is why a swapless server under memory pressure evicts its page cache aggressively while process memory stays put: with no swap, the kernel has no choice. The one exception is a machine with more than one tier of memory, where can_reclaim_anon_pages() falls through to a second question—whether the folio could be moved to slower memory instead of being freed—which section 4.3 takes up.

The cost feedback deserves a closer look because it is what makes the balance self-correcting. Each time reclaim does work on a list it calls lru_note_cost() (mm/swap.c), which adds to that side's running cost a figure reflecting both the I/O it caused and the folios it had to rotate—move back to the head rather than evict, because they turned out to be in use. get_scan_count() then divides scan pressure between the two lists in inverse proportion to their costs, so a side that keeps forcing expensive writeback or that keeps rotating still-hot pages is scanned less, and pressure shifts to the side that yields reclaimable pages more cheaply. Swappiness enters as a bias on top of this measured cost rather than a fixed ratio. The weights are computed in calculate_pressure_balance() as swappiness for the anonymous side and MAX_SWAPPINESS - swappiness for the file side, and since MAX_SWAPPINESS is 200 the two are balanced not at the default but at 100: at 60 the file lists already receive well over twice the weight of the anonymous ones before measured cost is applied at all. The scale therefore runs from 0, which avoids swapping until file reclaim alone cannot keep up, through 100, where the kernel treats a swap-in and a page-cache reload as equally expensive, to 200, which pushes pressure strongly toward anonymous memory. A subtlety guards the extremes: the costs are folded in as total_cost + anon_cost and total_cost + file_cost rather than the raw figures, which caps how far measured cost can skew the split and guarantees that at least a third of the pressure reaches each side before swappiness is applied, so neither list can be starved of scanning entirely and left with an age that has stopped advancing.

Zero and maximum are not merely the ends of that scale; both have separate, explicit meanings. A swappiness of 0 set on a cgroup disables anonymous reclaim for that group outright, because the memory controller's users want the knob as a switch, but the same value in global reclaim does not: the kernel will still swap rather than let the machine go out of memory, on the principle that a tuning preference should not be allowed to cause a kill. At the other end, proactive reclaim can pass SWAPPINESS_ANON_ONLY—one past the maximum, spelled swappiness=max when written to memory.reclaim—which is not an extreme bias but a different instruction altogether: scan only the anonymous lists and leave the page cache untouched. It exists because the most common reason to ask for reclaim explicitly is to push a finished job's anonymous memory out to swap while deliberately preserving the cache that the next job will want.

Several corner cases override the smooth proportional split when the situation is clear-cut. get_scan_count() picks one of four modes, tested in a fixed order so that the strongest constraint wins. SCAN_FILE comes first, for a system with no usable swap or a cgroup whose swappiness has been set to zero. SCAN_ANON follows, for the anon-only proactive request just described and for file_is_tiny, the case where the file lists have shrunk so far that scanning them would barely help. SCAN_EQUAL takes over at priority 0, when memory is critically short and the reclaimer should take whatever it can get rather than optimize. SCAN_FILE appears a second time for cache-trim mode—plenty of inactive file pages that are not thrashing, so there is no reason to disturb anonymous memory at all. Only when none of these apply does the mode fall through to SCAN_FRACT and the proportional calculation, which is the common, non-extreme case.

The file_is_tiny case is worth dwelling on, because it exists to break a feedback loop the proportional scheme would otherwise walk into on its own. New page-cache folios start on the inactive file list, so every cache miss adds weight to the file side and tips the balance further toward file reclaim. As the file lists shrink under that pressure, the window in which a folio might be referenced and rotated shrinks with them, so fewer file folios prove themselves useful, so the measured file cost falls, so the file side looks cheaper still. Left alone, a file cache that is thrashing badly enough looks arbitrarily attractive next to anonymous memory that is doing fine—the kernel's own comment calls it a runaway feedback loop, and the ordinary refault machinery cannot see it because the pages it would learn from are being evicted faster than they can refault. The kernel therefore checks the raw size directly: if the file lists plus free memory together fall below the sum of every zone's high watermark, while the active file list is not even being deactivated and some anonymous memory remains, it declares the file side tiny and forces the scan to anonymous. The check is deliberately outside the cost machinery, because a measurement that is itself corrupted cannot be used to detect its own corruption.

Multi-Gen LRU

The active/inactive scheme approximates LRU with just two levels of age, and its accuracy suffers on large modern machines. Multi-Gen LRU (MGLRU), controllable through CONFIG_LRU_GEN and a runtime switch, is a newer aging algorithm—absent entirely from Linux 2.6—that replaces the two lists with several generations. Each folio belongs to a generation numbered by a sequence counter; the youngest generation is max_seq and the oldest evictable one is min_seq, which is kept separately for anonymous and for file memory so the two types can age at their own rates without needing the explicit cost balancing the classic scheme requires. Reclaim proceeds in two motions: aging creates a new youngest generation and, by scanning page tables for accessed bits, works out which folios are still in use; eviction frees folios from the oldest generation. The per-lruvec state lives in struct lru_gen_folio (include/linux/mmzone.h), with up to MAX_NR_GENS (four) generations and per-generation, per-type, per-zone lists.

Two ideas make MGLRU more accurate than the classic scheme. First, it ages by walking page tables rather than only inspecting individual folios, which lets it harvest the accessed bits of many pages at once and identify the working set more cheaply on large address spaces. Second, it ranks folios within a generation by how often they have been referenced and feeds refault statistics back through the working-set machinery, so that protection is graduated rather than all-or-nothing—the tiers described below. When MGLRU is enabled, shrink_lruvec() and shrink_node() dispatch to lru_gen_shrink_lruvec()/lru_gen_shrink_node() instead of the classic shrink_list() path; the surrounding reclaim triggers, reverse mapping, and swapping are unchanged. The two algorithms are alternative agers under the same reclaim framework, which is why the rest of this chapter applies whichever one is in force.

The generational structure is what gives MGLRU its finer resolution. Between MIN_NR_GENS (2) and MAX_NR_GENS (4) generations exist at once, so a folio's age is placed on a scale of several steps rather than the two of active/inactive, and a folio that survives an aging pass simply carries into a younger generation instead of being coarsely reclassified. Aging is driven by inc_max_seq(), which creates a new youngest generation and walks the page tables of the address spaces on the node to find which pages were accessed—using the same accessed bits as before, but sampled in bulk and, where the hardware supports it, guided so that large unchanged regions are skipped rather than walked entry by entry. Eviction, in evict_folios(), takes folios from the oldest generation (min_seq); a folio found still in use during eviction is moved forward instead of freed. The tiers add a second dimension: within a generation, folios are ranked by how many times they have been referenced, and the refault feedback decides how many of each tier to protect, so a page read many times is far likelier to be carried forward than one read once. Figure 17-3 shows the generations and the two motions that move folios through them.

Both dimensions are stored in space the kernel already had. A generation number needs only the bits to index MAX_NR_GENS plus a zero meaning "not on the multi-gen lists," and a tier needs MAX_NR_TIERS of them; both are packed into spare bits of the folio's flags word as LRU_GEN_MASK and LRU_REFS_MASK, so neither generations nor tiers cost a folio a single extra byte. Only the per-lruvec lru_gen_folio grows, and what it holds is mostly statistics rather than state: evicted and refaulted counters per generation, type, and tier, from which avg_refaulted and avg_total are maintained as exponential moving averages. Those averages are the decision input—before evicting a tier, MGLRU compares how much of it historically refaulted against how much was evicted, and protects the tier by carrying it into the next generation if the answer says the last eviction was a mistake. The tier count itself is a saturating reference counter rather than a bit, which is the substantive difference from PG_referenced: the classic ager cannot distinguish a page touched twice from one touched two hundred times, and MGLRU can.

The page-table walk is the part that most needed engineering, because walking every address space on a large machine would cost more than the aging is worth. Three mechanisms keep it affordable. The first is that MGLRU iterates over mm_structs rather than folios, through a per-cgroup list traversed by iterate_mm_list(), so the work is proportional to the address spaces in use rather than to the memory installed, and a process that has exited stops costing anything the moment it is removed from the list. The second is a pair of double-buffered Bloom filters per generation: when a walk finds young entries under a page-middle-directory entry it records that entry in the filter for the next generation, and the next walk consults the filter before descending, so regions that were cold last time are skipped without being examined. Two filters are needed rather than one because the current generation is being read while the next is being written. The third is hardware: where the architecture sets an accessed bit on non-leaf page-table entries—x86 does, and arm64 does when FEAT_HAFT is present, both tested through arch_has_hw_nonleaf_pmd_young()—a single clear bit on a page-middle-directory entry proves that nothing in the two megabytes below it has been touched, and the entire subtree is skipped on one read. Each of the three can be disabled independently, which is what the bits of the runtime switch described next control.

MGLRU also changes how global reclaim chooses which cgroup to reclaim from, which is a decision the classic path makes by walking the cgroup tree in order. Instead, each lru_gen_folio is itself an element of a per-node LRU of memory cgroups, carrying a generation in its gen field and a position in seg, and reclaim visits cgroups in that order. A group is moved within the list by the outcome of reclaiming it: one that has just been aged is rotated to the young end, one that is offlined or has little left to reclaim is moved toward the old end and then aged out, and one that has exceeded its soft limit is moved to the head so it is visited first. The effect is that a machine running thousands of containers does not pay to walk a tree of thousands of mostly-empty groups on every reclaim pass—it goes straight to the ones that recently yielded memory, and lets the ones that did not drift out of the way.

MGLRU is not a compile-time-only choice. It is selected with CONFIG_LRU_GEN and can be turned on or off at run time by writing to /sys/kernel/mm/lru_gen/enabled, whose bits separately enable the core algorithm, the page-table walking, and the hardware young-bit clearing, so an administrator can switch a live system between the two agers and even tune how aggressively MGLRU walks page tables. A companion file, min_ttl_ms, sets a minimum age the youngest generation must reach before reclaim is allowed to fall back on the OOM killer, which lets an operator trade a kill for the thrashing that would otherwise precede it. A third interface goes further still: /sys/kernel/debug/lru_gen accepts commands that run aging or eviction on a named cgroup and node on demand, exposing MGLRU's two motions as primitives a userspace policy agent can drive itself. That is proactive reclaim taken to its conclusion—not merely asking the kernel to free a byte count, but implementing the aging policy outside the kernel entirely, which is how the mechanism is used on fleets whose operators know more about their workloads than any in-kernel heuristic could. It was introduced to serve workloads the two-list scheme handles poorly—very large memories, heavily overcommitted cloud hosts, and containers with tight limits—where its cheaper working-set identification and more graduated protection translate into fewer wrong evictions and less thrashing. On a small or lightly loaded system the classic active/inactive lists remain perfectly adequate, which is why both agers ship side by side.

Reverse Mapping

When the reclaimer decides to evict a page, it faces a problem the forward page tables cannot solve. A single physical page may be mapped by many processes at many virtual addresses—shared libraries, forked heaps, shared memory—and before the page can be freed every one of those mappings must be torn down. Forward page tables translate virtual to physical; reclaim needs the reverse. Reverse mapping (rmap) is the machinery that, given a folio, finds all the page-table entries that point at it. It is also what lets the ager consult every mapping's accessed bit. This section covers the two kinds of rmap—anonymous and file—and the unified walk over them.

The reason the kernel needs rmap at all has not changed since Linux 2.6. Without it, evicting a shared page would require finding its mappers by brute force—scanning every process's page tables for entries that point at the page—which would make reclaim's cost proportional to the size of every address space in the system. Rmap replaces that search with a direct lookup: each folio carries enough information to enumerate its mappers in time proportional to how many there actually are. The design has been rebuilt twice since—first from a per-page linked list of PTE pointers to the object-based scheme of Linux 2.6.11, then again into the anon_vma-chain and interval-tree forms described here—but the purpose is unchanged: make "who maps this page?" a cheap question so that reclaim can afford to ask it for every page it considers.

Finding Every Mapper of a Folio

A folio records what kind of memory it is, and therefore how to reverse-map it, in its mapping field. For a file folio, folio->mapping points directly at the file's address_space; for an anonymous folio, it points at an anon_vma with the low PAGE_MAPPING_ANON bit set, which folio_anon_vma() masks off; a folio that memory deduplication has merged carries PAGE_MAPPING_KSM in the same two bits and is routed elsewhere again. Reclaim uses this to route to the right walk. Linux 2.6.11 used an object-based rmap that had just replaced an earlier per-page list of PTE pointers; the modern kernel keeps the object-based idea but has rebuilt both halves—anonymous mapping around anon_vma chains, and file mapping around an interval tree—and folded them under one interface, rmap_walk().

Two counters on the folio complement the structural rmap and decide when a page is a reclaim candidate at all. The map count (folio_mapcount()) records how many page tables currently map the folio; a folio with a map count of zero is mapped by no one and can be reclaimed without any unmapping at all—the common case for page-cache pages that are cached but not mmapped. The reference count (_refcount) records all holders, including the LRU list, the page cache, and any transient pins; reclaim can only free a folio once every reference but its own is gone, which is why __remove_mapping() at the end of the pipeline checks the count under a lock before committing. Rmap and these counters work together: rmap drives the map count to zero by unmapping, and only then can the reference count fall to the point where the folio is freed.

Large folios complicate the map count in a way worth understanding, because the question reclaim and migration actually want to ask is not "how many mappings" but "is this mapped by more than one process." For a small folio the two are the same—a non-KSM anonymous page can be mapped at most once per address space, so a map count above one means sharing. A large folio can be mapped partially, by different processes at different offsets and through a mixture of huge and ordinary entries, so its map count says nothing directly about how many address spaces are involved, and answering the real question by walking the rmap would be far too expensive for a check made on every page fault and every migration decision.

7.0.12 answers it from the folio itself. A large folio carries two slots, _mm_id[0] and _mm_id[1], each holding the identifier of an address space that maps it together with that address space's own count of mappings, plus a flag bit meaning "more than these two have been seen." folio_maybe_mapped_shared() reads the flag and answers in constant time. The hedge in the name is deliberate and is the interesting part of the design: once a third address space has ever mapped the folio the flag is set and never cleared, so the answer can be a false positive long after the sharing ended. The kernel accepts that because the error is one-directional—a folio reported as possibly shared is merely treated more conservatively, while one reported exclusive really is exclusive—and because a cheap conservative answer on the fault path is worth far more than an exact answer that costs an rmap walk. The reference count has a similar companion: folio_expected_ref_count() computes how many references a folio ought to have from the page cache, the swap cache, its private data, and its page tables, so that comparing it against the actual count reveals whether some unaccounted holder—a get_user_pages() pin, most often—is keeping the folio alive. Several of the decisions in the reclaim pipeline are made on exactly that comparison.

Anonymous Reverse Mapping

Anonymous memory has no file to hang mappings off, so the kernel introduces an anon_vma (include/linux/rmap.h) to serve as the anchor: all the VMAs that map a given set of anonymous pages are reachable from one anon_vma, and each anonymous folio points back to it. The complication is fork(). When a process forks, parent and child share the same physical anonymous pages copy-on-write, so a page created before the fork may belong to both address spaces, while a page created after the fork by either process belongs only to that one. A naive design that linked each anon_vma straight to its VMAs could not express this cleanly.

The solution is a layer of indirection: the anon_vma_chain (AVC). Each AVC links one VMA to one anon_vma, and a VMA holds a list of AVCs connecting it to its own anon_vma and to those it inherited from ancestors at fork time. On fork(), anon_vma_clone() and anon_vma_fork() (mm/rmap.c) give the child its own new anon_vma but also chain it to the parent's, so a pre-fork page reached through the parent's anon_vma is still found in the child, while post-fork pages are kept separate. The AVCs of each anon_vma are held in an interval tree keyed by virtual-address range, so a walk can skip VMAs that do not cover the folio's offset. Figure 17-4 shows the arrangement across a fork.

The reason the chain must exist, rather than simply re-pointing the child's pages at a shared anon_vma, is correctness under aging over time. The alternative—one anon_vma shared by parent and child—would work, but it would grow monotonically: every fork would add its VMAs to the same anon_vma, so reverse-mapping a page that in fact belongs to only one descendant would still walk the VMAs of every relative, and the set could never shrink even as processes exited. The chained design bounds this. A folio is anchored to the specific anon_vma of the generation that created it, and only the ancestors that could genuinely share it are reachable, so the walk visits the processes that might map the page and not an ever-growing crowd that merely shares a lineage. The anon_vma also carries a lock (a reader/writer semaphore) that the walk takes to keep the VMA set stable while it iterates, since a concurrent fork() or munmap() could otherwise change the tree underneath it.

That lock needs one refinement to be workable, because a chain is a hierarchy and locking each anon_vma in it separately would invite deadlock between two walks approaching the same family from different generations. Every anon_vma therefore carries a root pointer to the oldest ancestor of its chain, and all locking is done on that single root: folio_lock_anon_vma_read() follows the folio to its anon_vma, takes the root's semaphore for reading, and re-checks that the folio is still anonymous and still points where it did—a necessary re-check, because the folio is not pinned by anything at the moment the pointer is read. One lock per family gives a total order, and the cost of the coarser granularity is small in practice because rmap walks are reads and the semaphore admits any number of them.

The map counts that all of this maintains are themselves kept in batches now, matching the way large folios are mapped. Rather than a call per page, the kernel exposes folio_add_anon_rmap_ptes() and folio_remove_rmap_ptes() (include/linux/rmap.h), which take a run of consecutive pages within a folio and adjust the folio's counters once for the whole run, with single-page and PMD-sized wrappers layered on top. A fault that maps sixteen consecutive pages of a large folio and the unmap that later tears them down each touch the shared counters a single time instead of sixteen, which matters because those counters are atomics on a line every mapper of the folio contends for. The flag RMAP_EXCLUSIVE, passed when the mapping is known to be the folio's only one, is what lets the fault handler record that a page may be written without a copy—the anonymous-memory counterpart of the sharing question section 3.1 describes, resolved at map time rather than looked up later.

File Reverse Mapping

File-backed memory is simpler because the file itself is the natural anchor. Every address_space has an i_mmap field holding all the VMAs that currently map the file, and a file folio points straight at that address_space, so the walk starts from the folio with no extra indirection. The change since Linux 2.6 is the data structure: 2.6-era kernels stored the VMAs in a priority search tree, whereas the modern i_mmap is a interval tree (an augmented red-black tree, rb_root_cached) keyed by the file-page range each VMA covers. Given a folio at some file offset, vma_interval_tree_foreach() visits exactly the VMAs whose ranges include that offset, skipping the rest. Because a gigabyte file may be mapped by hundreds of processes each mapping a different window, this range-indexed walk is far cheaper than examining every mapper, and it is the same interval-tree idea used for the anonymous AVCs. Figure 17-5 shows the layout.

The interval tree earns its keep precisely because file mappings are so often partial and overlapping. Consider a shared library: hundreds of processes map it, but each maps only the portions it uses, and the pages of its code, data, and read-only sections fall at different file offsets. When reclaim wants to evict one page of that library, a flat list of mappers would force it to examine every process that mapped any part of the file and check whether each one covers the page; the interval tree, keyed by range, returns in one indexed descent only the VMAs whose window actually contains the page. The augmentation that makes this possible is a per-subtree maximum-offset field maintained in the red-black tree, which lets a range query prune whole subtrees that cannot overlap—the standard augmented-tree technique, and the same one underlying the anonymous AVC tree, so both halves of rmap share a single range-lookup mechanism guarded, on the file side, by the i_mmap_rwsem.

File rmap has a second consumer that has nothing to do with reclaim, and noticing it explains why the machinery is shaped as it is. folio_mkclean() uses the same interval-tree walk to write-protect every mapping of a folio, which is what makes writeback of a mapped file correct: once the folio has been marked clean and queued for I/O, any further write through a mapping must trap so the folio can be marked dirty again rather than being modified silently behind the writeback that is already in flight. The forward page tables cannot express this; only a walk from the folio outward can find every mapping that needs its write permission removed. Reclaim's try_to_unmap() and writeback's folio_mkclean() are the same traversal carrying different verbs, which is why both live in mm/rmap.c and why the interval tree was worth building.

The rmap Walk

Both kinds of rmap are consumed through one interface. A caller fills a struct rmap_walk_control (include/linux/rmap.h) with a callback, rmap_one, and rmap_walk() (mm/rmap.c) invokes it for every mapping of the folio—dispatching to the anonymous interval-tree walk or the file interval-tree walk according to the folio's mapping. (A third case, handled first, is a KSM page—one that memory deduplication has merged from several identical pages—which has its own rmap_walk_ksm() to reach all the originally distinct mappers.) Two reclaim operations are built on this walk. folio_referenced() runs it to count how many of the folio's mappings have their accessed bit set, which is the input the ager uses to promote or demote the folio. try_to_unmap() runs it to tear every mapping down when the folio is being evicted: try_to_unmap_one() is called for each PTE and clears it, and here the two page types diverge—for an anonymous folio it writes a swap entry into the PTE so the page can be found again in the swap area, while for a file folio it simply clears the PTE, since the data can be re-read from the file. A third operation shares the walk and is easy to mistake for the second. try_to_migrate() also tears down every mapping, but where try_to_unmap() leaves a swap entry or nothing at all, it installs a migration entry—a special non-present entry that causes any thread faulting on the address to block until the move is finished and then resume against the new page frame. The distinction matters here because the demotion stage of section 4.3 uses this path rather than the unmapping one: a demoted folio is not being evicted, it is being relocated, and its mappers must end up pointing at the copy on the slower node rather than being sent to swap. Compaction and NUMA balancing enter the same way, and The Migration Protocol follows the whole move.

Between rmap_walk() and the callback sits page_vma_mapped_walk(), which answers a question the interval tree only narrows down: given that this VMA covers the folio's range, where and how is it actually mapped? A folio may be reached through a single huge PMD entry, through a run of ordinary PTEs, through only part of a run if it was partially unmapped, or through a migration entry left by an operation still in progress. The helper iterates over each mapping it finds and hands the callback one at a time, which is why the callback is written as a loop rather than a single test. On the unmap side this pairs with folio_unmap_pte_batch(), which recognizes a run of consecutive PTEs belonging to the same large folio and clears the whole run in one step, so that tearing down a two-megabyte folio mapped by ordinary entries does not cost five hundred and twelve separate rounds of lock, clear, account, and flush.

One step inside try_to_unmap_one() is easy to overlook but essential for correctness: as it clears each PTE it reads the entry's dirty bit, and if the hardware had marked the page modified through that mapping it calls folio_mark_dirty() before discarding the PTE. This transfers the "modified" state from the page table, where it is about to be destroyed, onto the folio, where the pipeline will see it and write the page back rather than dropping it. Without this transfer a page dirtied only through a memory mapping—never through a write() call—could be silently lost when it was unmapped. The walk also flushes the TLB entries for the mappings it tears down, batching those flushes (with TTU_BATCH_FLUSH, one of the Table 17-4 flags) across many pages so that a single, expensive cross-CPU TLB shootdown covers a whole batch of unmapped folios rather than one per page.

Deferring those flushes is not free of risk, and the way the risk is closed is instructive. Between clearing a PTE and flushing the TLB there is a window in which another CPU still holds a valid translation and can reach a page the kernel believes it has unmapped; if the folio were freed and reused in that window, the stale entry would expose one process's data to another. Tracking which address spaces have flushes outstanding would cost more than the batching saves, so the kernel instead records only that batching has happened, and the operations that could be hurt by it—mprotect(), munmap(), and their relatives—call flush_tlb_batched_pending() under the page-table lock before they proceed. The cost is one extra flush per reclaim cycle, paid by whichever of those operations happens first, in exchange for removing a per-page shootdown from the reclaim path. The optimization is architecture-gated on CONFIG_ARCH_WANT_BATCHED_UNMAP_TLB_FLUSH, which x86, arm64, and RISC-V select; elsewhere should_defer_flush() always returns false and each unmap flushes as it goes.

Two decisions the walk makes have nothing to do with unmapping and everything to do with reclaim being careful. The first is that reclaim never waits on rmap. folio_referenced() sets try_lock in its walk control, so a walk that finds the anon_vma or i_mmap lock already held gives up rather than blocking, sets contended, and returns −1; the caller reads that as FOLIOREF_KEEP and rotates the folio to be considered again later. The same applies one level up: if reclaim cannot even take the folio lock, folio_referenced() returns 1, claiming a reference it never verified. Both are the same principle—when in doubt, keep the folio—and both exist because a reclaimer that blocked on a lock held by a process doing real work would convert a memory shortage into a stall for everyone. Wrongly keeping a page costs one more pass over the list; wrongly waiting costs latency the system cannot get back.

The second is that the walk is where the unevictable classification is repaired. Section 1.2 described LRU_UNEVICTABLE as a cache of a condition rather than a verdict, and this is the mechanism that keeps the cache honest: when folio_referenced_one() finds the folio mapped by a VMA carrying VM_LOCKED, it calls mlock_vma_folio() to set PG_mlocked, reports VM_LOCKED back through the walk control, and stops early, and folio_check_references() turns that into FOLIOREF_ACTIVATE so the folio is moved onto the unevictable list instead of being reclaimed. The kernel therefore does not have to find every folio at mlock() time and guarantee it is marked; it can afford to be lazy, because the reclaim scan is a sweep that will eventually visit every folio and fix any that were missed. The walk also declines to work on a folio whose only mapper is an address space that is exiting or has been emptied by the OOM reaper—writing such a page to swap would be wasted I/O for memory that is about to be freed outright.

When Multi-Gen LRU is in force this walk becomes a two-way channel rather than a query. On finding a young PTE, lru_gen_look_around() examines the neighbouring entries in the same page-table page, on the reasoning that pages adjacent in an address space are usually touched together, and promotes the hot neighbours it finds—so a folio can be rescued by the eviction scan of a different folio near it. If the surrounding scan was productive, the walk also records the page-middle-directory entry in the Bloom filter that the next aging pass will consult, so that eviction tells aging where to look next time. The kernel's own comment calls this a feedback loop between the eviction and the aging, and it is a good illustration of why MGLRU can afford to walk page tables at all: much of the walking is paid for by work reclaim was doing anyway.

The Reclaim Pipeline

With the lists and reverse mapping in place, the actual work of reclaim is a pipeline that descends from a whole node to a single folio and either frees it or puts it back. This section follows that descent, looks closely at what it takes to evict one folio, describes the stage that moves a folio to slower memory instead of evicting it at all, and explains the refault feedback that makes the next round smarter. A theme runs through all four: at every stage the pipeline would rather give up on a folio than block, because a reclaimer that waits is a reclaimer that is not freeing memory.

From Node to Folio List

Reclaim is organized as a series of nested scans, each narrowing the scope. shrink_node() (mm/vmscan.c) reclaims from one NUMA node; it walks the memory cgroups that have memory on that node and calls shrink_lruvec() for each, so global reclaim and cgroup reclaim share the same code. shrink_lruvec() uses get_scan_count() to decide how many folios to take from each of the four evictable lists—the anon/file balance of an earlier section—and calls shrink_list() on each. An active list is handled by shrink_active_list(), which moves unreferenced folios down to the inactive list; an inactive list is handled by shrink_inactive_list(), which isolates a batch of folios and hands them to the function that does the real reclaiming, shrink_folio_list().

The nesting matters because it is where the two kinds of scope apply. shrink_node() iterates the node's cgroups with mem_cgroup_iter(), so a global reclaim visits every cgroup's lruvec on the node while a cgroup-targeted reclaim visits only the target and its descendants—the same loop, differing only in where it starts. That loop is also where a cgroup's memory reservations take effect: mem_cgroup_calculate_protection() is consulted for each group, and one below its memory.min is skipped outright while one below memory.low is skipped only on the first attempt—the fact that it was passed over is recorded in memcg_low_skipped, and if the whole node yields nothing the scan is repeated with memcg_low_reclaim set, which is what makes memory.low a soft guarantee rather than a hard one. The iteration itself differs by caller: a direct reclaimer resumes the cgroup walk from a persistent cursor rather than starting over, so that one thread does not repeatedly pay to traverse the whole tree, while kswapd always makes a complete pass, because reliable progress matters more for it than a quick return. And the isolation step in shrink_inactive_list() is deliberately brief: it takes the lru_lock, moves up to SWAP_CLUSTER_MAX folios off the list into a private list, and drops the lock, so that the expensive per-folio work in shrink_folio_list()—reference checks, unmapping, writeback—runs without any lock held and without blocking other CPUs from touching the same LRU. The isolated folios are pinned by an elevated reference count while off the list, and whatever is not freed is spliced back at the end.

The whole descent is repeated at increasing urgency. A struct scan_control carries the parameters of one reclaim attempt—how many pages to reclaim, the allocation's gfp flags, whether writing and swapping are permitted, the target cgroup—and a priority field that controls how much of the lists one pass examines, starting with a small fraction and widening if not enough was freed. Table 17-5 lists the principal scan_control fields.

Within one lruvec, shrink_lruvec() does not drain one list before starting the next. It loops over the four evictable lists round-robin, taking at most SWAP_CLUSTER_MAX folios from each per turn, so that the anon/file proportions get_scan_count() chose are respected continuously rather than only in aggregate. The whole loop runs inside a block-layer plug, which is what allows the writeback that reclaim submits along the way to be merged and issued in batches rather than one request at a time. Stopping is a decision in its own right: reaching nr_to_reclaim ends the loop for kswapd and for cgroup reclaim, but a global direct reclaimer at DEF_PRIORITY deliberately keeps going past its target, on the reasoning that a thread which had to reclaim for itself has already proved kswapd is not keeping up, so it may as well do a useful batch of work while it is here. When the loop does stop early it first makes a single adjustment to whichever side has more scanning left, reducing it in proportion to its original target, so that an early exit does not silently turn a balanced plan into a lopsided one.

One more limit governs how many threads may be in this part of the pipeline at once. Because shrink_inactive_list() moves folios onto a private list, a crowd of direct reclaimers could between them isolate an entire inactive list, leaving later arrivals scanning a list that appears empty while the memory they want is held privately by their peers. too_many_isolated() detects this by comparing the node's NR_ISOLATED_FILE or NR_ISOLATED_ANON count against the corresponding inactive list, and a thread that finds more isolated than remaining throttles under VMSCAN_THROTTLE_ISOLATED until someone finishes. The threshold is deliberately eight times looser for a caller that cleared __GFP_FS or __GFP_IO, because such a caller is often the one holding the filesystem lock the ordinary reclaimers will eventually need; throttling it behind them would close the circle into a deadlock.

The priority field is the mechanism behind reclaim's graduated response. It starts at DEF_PRIORITY (12) and is used as a right-shift on the list size, so the first pass scans only 1/4096 of a list; if that frees too little, the priority is decremented and the next pass scans twice as much, down to priority 0, which scans the entire list. A lightly pressured system thus does a small, cheap scan and stops, while a desperately short one works its way down to examining everything. The may_* flags encode the caller's constraints from an earlier section: a reclaim invoked from a context that must not recurse into the filesystem clears may_writepage or may_unmap, and one for an allocation that cannot swap clears may_swap. Reclaim therefore does only what its caller's context permits, which is why the same pipeline behaves differently depending on who invoked it.

Evicting a Folio

shrink_folio_list() is the heart of reclaim: it takes a list of isolated folios and, for each, decides whether it can be freed and does the work. The steps, in order, are roughly these. It locks the folio and skips any that became unevictable. It checks the folio's dirty and writeback state; a folio already under writeback is left alone (and the scan may throttle rather than spin). Unless told to ignore references, it calls folio_check_references()—reverse mapping again—and returns strongly referenced folios to the active list rather than evicting them. For an anonymous folio not yet backed by swap, it allocates a swap slot with folio_alloc_swap(), adding the folio to the swap cache. It then unmaps the folio from every page table with try_to_unmap(). If the folio is dirty it is written back with pageout()—to the filesystem for a file folio, to the swap device for an anonymous one. Finally, a folio that is now clean and unmapped is detached from its mapping by __remove_mapping() and freed; one that could not be reclaimed is activated or kept for a later pass. Figure 17-6 lays out the pipeline.

Before any of that, the loop asks a question 2.6 reclaim treated as a single yes-or-no: what to do about a folio that is already under writeback. Waiting for the disk is the obvious answer and almost always the wrong one, and the code says why in as many words—waiting for a disk write is more expensive than possibly having to read the folio back later. So there are three outcomes. If kswapd finds a folio that is under writeback and already carries the PG_reclaim flag on a node flagged PGDAT_WRITEBACK, the folio has travelled all the way around the inactive list a second time without its I/O finishing; that is the kernel's working definition of congestion, and rather than wait on storage that may be broken or disconnected, the folio is activated and the caller throttles after the batch. If the folio is not yet marked, or the caller's gfp flags forbid entering the filesystem, it is marked with PG_reclaim and activated, so that when the write does complete folio_rotate_reclaimable() drops it at the inactive tail where the next scan will meet it immediately. Only a cgroup on the legacy hierarchy, which has no dirty-page throttling of its own and could therefore be driven to a needless out-of-memory kill by writeback alone, actually unlocks and waits. The filesystem check in that second case is not hypothetical: the loop device issues its writes through another filesystem, so a reclaimer waiting on a loop device's writeback can end up waiting on itself, which is exactly why the loop driver masks __GFP_IO and __GFP_FS out of its allocations.

The final step, __remove_mapping(), is where reclaim commits and where a subtle race is closed. Detaching a folio from its mapping and freeing it is safe only if no one else is about to use it, and another CPU could be looking the folio up in the page cache at that very moment. The function therefore takes the mapping's lock and freezes the reference count: it atomically checks that the count equals exactly the expected value—one for the reclaimer plus the mapping's own references—and, if so, sets it to zero in the same operation, so a concurrent lookup that raised the count is detected and the eviction is abandoned. The order of that test and the dirty check after it is not arbitrary. Something holding a pin obtained through get_user_pages() can write to the folio long after every page table entry mapping it is gone, and then drop its reference; had reclaim looked at the dirty flag first and the refcount second, it could observe a clean folio, miss the store that arrived a moment later, and then find the reference dropped and discard the data. Freezing first and re-examining PG_dirty afterwards closes that window, and the atomic compare-and-exchange inside the freeze supplies the memory barrier that makes the second load meaningful. Only after both tests pass is the folio removed from the page cache (or, for an anonymous folio, from the swap cache) and freed—and it is here, in the same critical section, that the shadow entry described shortly is planted in the slot the folio is vacating. This is what makes lockless page-cache lookups safe to coexist with reclaim: a racing filemap lookup either grabs its reference before the freeze, forcing reclaim to back off, or arrives after the folio is gone and retries.

The throttling those cases defer to is itself a small state machine. reclaim_throttle() puts the scanning thread to sleep for a bounded interval, and the reason it records says what the scan was waiting for: writeback that has not completed, too many folios isolated by other reclaimers, a scan that has stopped making progress at all, or a backing device that cannot absorb more requests. Sleeping is what turns a scan that is outrunning the storage into one that paces itself, and because each wait is bounded and the sleepers are woken as soon as the condition clears, a reclaimer is never parked indefinitely on a device that has stopped responding. The accounting that feeds these decisions is gathered per batch in a struct reclaim_stat—dirty folios seen, dirty folios not yet queued, congested ones, ones kept because they were referenced, ones whose unmapping failed—and it is what lets the caller decide, after the batch, whether the node as a whole should be flagged as writeback-bound. Writing dirty file pages from within reclaim is also discouraged in general—it produces scattered, seek-heavy I/O—so reclaim prefers to let the dedicated writeback threads of Chapter 15 clean pages in large, ordered batches and to reclaim them on a later pass, writing back from the scan itself only when memory is critically short.

Demotion and Memory Tiering

The pipeline just described has one more stage than its 2.6 counterpart, and it sits before all the expensive ones. On a machine where not all memory is equally fast, evicting a cold folio outright is not the only option: it can be moved to the slower memory instead, and left resident. That is demotion, and the arrangement of memory it presupposes is memory tiering.

The premise is hardware that has stopped being uniform. A modern server may combine ordinary DRAM with high-bandwidth memory, with persistent memory, or with memory attached over CXL, and the differences between them are large enough that treating all of it as one interchangeable pool wastes the fast part. The kernel therefore sorts memory nodes into tiers by an abstract distance, a single number that stands in for how far a node is from the CPU: smaller means faster, plain DRAM is anchored at MEMTIER_ADISTANCE_DRAM, and each tier spans a chunk of the scale (include/linux/memory-tiers.h). What matters for reclaim is the ordering this produces, because it defines what "slower" means: each node gets a set of allowed demotion targets, and next_demotion_node() (mm/memory-tiers.c) answers the only question the reclaimer asks, which is where a folio evicted from this node should go instead.

Inside shrink_folio_list() the stage is placed deliberately. After the reference check has decided a folio is reclaimable, and before the folio is given a swap slot or unmapped, do_demote_pass diverts it onto a separate list; at the end of the loop demote_folio_list() hands that list to migrate_pages() with MR_DEMOTION. The placement is the whole point. Demotion is cheaper than eviction for a folio that is merely cold rather than dead: nothing is written to swap, nothing is dropped from the page cache, and the next access is a slow memory reference instead of a page fault and a disk read. The allocation for the target node is made deliberately timid (GFP_NOWAIT with __GFP_NOMEMALLOC and reclaim cleared), so if the slower tier is itself under pressure the migration simply fails and the folio falls back to being reclaimed the ordinary way—literally so, since whatever migrate_pages() could not move is spliced back onto the working list and the loop runs a second time with demotion switched off. The target allocation is also pinned to the chosen node rather than merely preferring it, so a folio demoted from fast memory lands on the next tier down instead of drifting to the slowest node in the machine on its first move. The unmapping itself is the migration path of the reverse-mapping section, try_to_migrate(), which leaves migration entries behind so that a process touching the folio mid-move simply waits rather than faulting on nothing. Demotion also ignores cpuset and memory-policy restrictions on purpose: the folio is not being placed somewhere the process asked for, it is being spared from eviction, and the alternative is losing it entirely.

Two consequences reach back into earlier sections. The first is that can_reclaim_anon_pages() no longer means what it did: an anonymous folio on a tiered system can be reclaimed without any swap at all, by demotion, so the flat rule that a swapless machine never scans the anonymous lists holds only where there is no lower tier to demote to. The second is that WMARK_PROMO, the extra watermark named in the watermarks section, exists for the other direction. Demotion has a counterpart in promotion: with NUMA balancing in NUMA_BALANCING_MEMORY_TIERING mode, a page on a slow tier that keeps being accessed is migrated back up by migrate_misplaced_folio(), and WMARK_PROMO is what reserves the headroom on the fast tier for those arrivals to land in. Reclaim maintains that headroom, which is why kswapd on a tiered system aims at a slightly higher mark than WMARK_HIGH. Demotion and promotion together turn the tier hierarchy into a cache: hot pages drift up, cold pages drift down, and only what is cold on the slowest tier is finally evicted.

Because moving pages between tiers costs bandwidth and can misfire, the whole mechanism is off by default and enabled with /sys/kernel/mm/numa/demotion_enabled, with promotion gated separately behind the NUMA balancing mode. This is the one part of the reclaim pipeline that most systems never execute: on a machine with a single kind of memory can_demote() returns false immediately and the stage costs nothing. It is described here because it changes the shape of the pipeline for the class of machine that increasingly matters, and because it is the reason several constants and code paths elsewhere in reclaim look more complicated than a uniform-memory system would require.

Refault Detection

Evicting a folio is a bet that it will not be needed soon. The kernel checks that bet and learns from it through refault detection (mm/workingset.c). When a file folio is evicted, the page cache does not simply forget it: workingset_eviction() stores a small shadow entry in the same XArray slot the folio occupied, recording the value of the lruvec's nonresident_age clock at eviction time. If that page is read again later and a fresh folio is brought in, workingset_refault() compares the clock's current value with the stored one to compute a refault distance—how much other memory was evicted in the interval. A short distance means the page was evicted too soon and belongs in the working set, so the refaulting folio is placed directly on the active list rather than the inactive one; a long distance means the eviction was justified.

Nothing in that scheme is specific to files. An anonymous folio leaving memory passes through the same workingset_eviction() call in __remove_mapping(), and the shadow it produces is stored in the swap table entry that the folio's slot occupies—the same slot that would otherwise hold a pointer to the cached folio, as the swapping section describes. A later swap-in retrieves it and evaluates the same distance. Refault detection therefore covers both halves of the LRU, which matters because the two compete: the comparison is not against the folio's own list but against everything that could have been kept instead. A refaulting file folio is measured against the active file pages plus, when there is swap, the anonymous lists, and an anonymous refault is measured against the file lists plus the active anonymous ones. The question being asked is not "was this page recently used" but "would this page have survived if the working set had been given the memory that other pages consumed in the meantime," and only pages that would have survived are promoted.

The mechanism is elegant because it reuses storage that would otherwise sit empty. When a folio is evicted, its slot in the page cache's XArray is not removed; it is replaced by a shadow entry, a special value (not a folio pointer) that the XArray can hold in the same slot, encoding the nonresident_age timestamp along with the memory cgroup and node the folio belonged to. The slot thus keeps a memory of the evicted page at no extra allocation. The nonresident_age clock it records is not wall-clock time but a count that advances each time a page is evicted or an active page is rotated, so the "distance" between eviction and refault is measured in pages reclaimed—exactly the quantity that determines whether the page could have fit had the working set been a little larger. If that distance is smaller than the number of active pages, the page would have been a hit under a slightly larger memory, so it is treated as part of the working set. The clock value is stored coarsened, shifted down by a scale chosen at boot so that the timestamp still fits alongside the cgroup identifier and node number in a single machine word; the resolution lost is far below the granularity at which the comparison is meaningful. Shadow entries are themselves reclaimable: a dedicated shrinker prunes them when they accumulate, so a workload that streams through more files than memory can hold—and thereby manufactures shadows faster than they are ever consulted—does not accumulate them without bound.

The shadow carries one more bit than the timestamp: whether the folio was on the active list when it was evicted. That distinction separates two rather different events. A folio that was merely cached and comes back soon is a refault, counted in WORKINGSET_REFAULT_FILE or its anonymous counterpart, and a recent one is activated. A folio that had already earned active status, was evicted anyway, and has now been demanded again is a restore, counted separately, and it is the one that gets PG_workingset set on its replacement. Refaults also feed back into the anon/file cost balance through lru_note_cost_refault(), so a type that keeps refaulting makes itself more expensive to reclaim from—the accounting the balance section described, driven from the far end of the pipeline.

This feedback closes the loop that plain LRU lacks. Without it, a working set slightly larger than memory would thrash—each page evicted just before it is needed and faulted straight back—while the reclaimer kept believing it was making progress. With refault distance, repeated early evictions push the pages back onto the active list and shift pressure elsewhere. The PG_workingset bit is also what makes pressure-stall accounting mean something. A process waiting for a folio to be read from disk is doing ordinary I/O and should not be reported as starved of memory; but a process waiting on a folio that carries PG_workingset is waiting for something the kernel had already judged part of its working set and then threw away, which is the definition of thrashing. So the wait is wrapped in psi_memstall_enter() only in that case, in the page-cache read path and in the swap-in path alike, and the memory pressure a system reports is built from exactly those waits rather than from I/O in general. Multi-Gen LRU uses the same shadow entries through its own lru_gen_eviction()/lru_gen_refault() hooks, so refault detection informs whichever ager is in use.

When Reclaim Runs

Everything so far describes how reclaim frees memory; this section is about when it starts and who runs it. Three of the answers are reactions to a shortage—a background daemon, the allocating thread itself, and a cgroup hitting its limit—governed by thresholds called watermarks, and a fourth is no reaction at all but a deliberate request from user space. The order in which they engage is the order of increasing cost, and most of the design effort in this part of the kernel goes into keeping the cheap ones sufficient.

Watermarks

Each memory zone carries three watermarks—WMARK_MIN, WMARK_LOW, and WMARK_HIGH (enum zone_watermarks, include/linux/mmzone.h)—that mark levels of free memory and drive reclaim's escalation. They are derived from the min_free_kbytes tunable, itself scaled from total memory (roughly proportional to its square root), and recomputed by __setup_per_zone_wmarks() (mm/page_alloc.c). As free memory falls past each watermark the kernel responds more forcefully: crossing WMARK_LOW wakes the background reclaimer, reaching WMARK_MIN forces the allocator to reclaim before it may proceed, and reclaim continues until free memory climbs back above WMARK_HIGH. A newer refinement, watermark boosting, temporarily raises the watermarks after an allocation causes fragmentation, so that a burst of reclaim and compaction restores contiguous free memory. The gap between the watermarks is what gives reclaim room to work. The distance from WMARK_MIN up to WMARK_HIGH is the buffer kswapd tries to keep free, and it is sized so that a background reclaim started at the low watermark has time to refill memory before demand can drain it to the minimum—so allocations rarely have to reclaim inline. The reserve below WMARK_MIN is not wasted: it is graded access, released to progressively more critical requests through allocation flags, so that an ordinary allocation fails and reclaims while a reclaim-critical one (writing a dirty page out, or a dying OOM victim) may dip into the reserve to make forward progress. Two extra watermarks refine the picture in the modern kernel: the per-zone watermark_boost (governed by watermark_boost_factor, default 15000) lifts all three temporarily to trigger compaction after a fragmenting allocation, and WMARK_PROMO, a further full step above high, reserves headroom on a fast memory tier for pages promoted into it from a slower one, the mechanism section 4.3 describes. Only the boost is temporary; WMARK_PROMO is a permanent member of the enum, computed alongside the other three, and left unused wherever no tier is faster than another.

Which knob controls which part of that picture is worth being precise about, because the two are often confused. min_free_kbytes sets only WMARK_MIN, the floor; the steps from there up to low and up again to high are computed separately, each equal to a fraction of the zone's own managed pages given by watermark_scale_factor, with a floor of a quarter of the minimum. The factor is expressed in ten-thousandths and defaults to 10, which is to say the gaps are a tenth of one percent of the zone; it can be raised to 3000, or thirty percent. The default is generous on a small machine and can be far too tight on a large one, because the gap is what buys kswapd time: a terabyte of memory with a 0.1 percent gap gives the background reclaimer about a gigabyte of runway, which a few threads allocating hard will cross in milliseconds. The symptoms are visible in /proc/vmstat—a high allocstall count means threads are reclaiming inline, and kswapd_low_wmark_hit_quickly means kswapd is being woken again almost as soon as it sleeps—and raising watermark_scale_factor rather than min_free_kbytes is the response, since widening the gaps is what was wanted and raising the floor merely holds more memory permanently idle.

One caution about reading a watermark as the whole admission test: it is not. zone_watermark_ok() subtracts more than the watermark from the free count before deciding. It also requires that a free block of the requested order actually exist, since a zone with ample free pages scattered as single frames cannot satisfy an order-4 request no matter how far above its high watermark it sits—which is why watermark boosting exists at all, and why kswapd hands off to kcompactd. And it subtracts the zone's lowmem_reserve entry for the requesting allocation's own zone index, a per-pair reserve that stops a request which could equally have been served from a higher zone from consuming the scarcer lower ones that restricted callers depend on. A watermark, in other words, answers a question about one zone; the full test answers a question about that zone relative to who is asking.

kswapd: Background Reclaim

The background reclaimer is kswapd (mm/vmscan.c), one kernel thread per NUMA node. When an allocation finds a zone below its low watermark it calls wakeup_kswapd(), which records the needed order and zone in the node's pglist_data and wakes the thread. kswapd then runs balance_pgdat(), reclaiming across the node's zones at rising priority until every zone is balanced—free above its high watermark—after which it sleeps again on pgdat->kswapd_wait. Because it runs asynchronously and aims for the high watermark rather than merely the minimum, kswapd keeps a cushion of free memory ahead of demand, so most allocations are served immediately without any thread having to reclaim inline. Before sleeping it also wakes kcompactd, the companion per-node thread that defragments free memory so that higher-order allocations can be satisfied.

Going to sleep is a two-stage affair, and the staging is deliberate. Having balanced the node, kswapd first sleeps for only a tenth of a second; if a new wakeup arrives in that window—which on a busy machine it very often does—the thread resumes without paying for a full sleep and wakeup, and without the scheduler having to migrate it. Only if the short sleep expires undisturbed does it settle into the indefinite wait on pgdat->kswapd_wait. The short sleep is also the point at which the compaction handoff happens: kcompactd is woken and compaction's record of page blocks it recently failed to isolate from is cleared, on the reasoning that memory has just been freed so blocks previously written off are worth trying again. Both are done only on the path where the short sleep was affordable, because if reclaim could not balance the node then compaction is unlikely to achieve anything either and there is no point waking a second thread to find that out. Before any of this, each pass calls kswapd_age_node(), which ages the active lists regardless of which zone the allocation wanted, so that the reference bits section 2.2 relies on keep being sampled even on a node whose pressure is confined to one zone.

Watermark boosting gives kswapd a second mode that is easy to mistake for the first. When boosting has raised a zone's watermarks after a fragmenting allocation, balance_pgdat() notes how much of its target is boost rather than genuine shortage, and treats that portion quite differently: it clears may_writepage and may_swap for the duration, refuses to descend more than two priority steps, and abandons the attempt entirely the moment a pass frees nothing. The reasoning is that boosted reclaim is not trying to free memory—the real watermarks are already satisfied—but to free contiguous memory so compaction has something to work with, and paying for scattered writeback and swap I/O to achieve that would cost more than the fragmentation does. Ordinary reclaim frees whatever it must; boosted reclaim takes only what is cheap and gives up quickly.

kswapd is also where the system decides that background reclaim has failed. Each pass of balance_pgdat() that cannot restore balance increments pgdat->kswapd_failures; the counter is reset to zero as soon as a pass succeeds. Once it reaches a threshold (the same MAX_RECLAIM_RETRIES limit the allocator uses), kswapd concludes that the node is genuinely unreclaimable and stops spinning, leaving further attempts to direct reclaim and ultimately the OOM killer rather than burning a CPU on scans that free nothing. This split of labor is deliberate: kswapd handles the steady, common case efficiently and quietly, and hands off to the more drastic foreground paths only when it provably cannot keep up. Its work is throttled the same way the pipeline's is—if it keeps meeting folios under writeback it sleeps rather than spins—so on a healthy system kswapd spends most of its time asleep on pgdat->kswapd_wait, waking only when an allocation drives a zone below its low watermark.

Direct Reclaim and Pressure

When demand outruns kswapd and an allocation cannot be satisfied even at the minimum watermark, the allocating thread reclaims for itself—direct reclaim. In __alloc_pages_slowpath() (mm/page_alloc.c) the failing allocation calls try_to_free_pages() (mm/vmscan.c), which sets up a scan_control and runs do_try_to_free_pages(), looping over the reclaim priorities until enough is freed or the scan is exhausted. Direct reclaim is what makes an allocation block: the thread pays for its own memory by doing reclaim work before its request returns. Because that stall is a real source of application latency, the kernel accounts for it as pressure stall information (PSI): reclaim is bracketed by psi_memstall_enter() and psi_memstall_leave(), and the accumulated time appears in /proc/pressure/memory, giving operators a direct measure of how much the system is thrashing—information Linux 2.6 could not report. Much of that measured time is not scanning at all but the refault waits section 4.4 describes, which is why the two mechanisms report the same quantity from opposite ends.

Before a thread is allowed to reclaim, though, it may be told to wait instead. A shortage that kswapd has not yet caught up with will be noticed by every allocating thread at once, and a hundred threads each entering the pipeline to free thirty-two folios is worse than one thread doing the work while the others stand still. throttle_direct_reclaim() is the herd control: a thread whose node has less free memory than half the sum of its zones' minimum watermarks does not begin reclaim but sleeps on pgdat->pfmemalloc_wait until kswapd has restored enough, an event counted as PGSCAN_DIRECT_THROTTLE. The exceptions are as instructive as the rule. Kernel threads are never throttled, because one of them may be the thread that cleans the pages reclaim is waiting for—a journalling daemon blocked here would stall every process waiting on its transaction. A thread with a fatal signal pending is not throttled either, since letting it die frees its memory faster than reclaiming would. And a caller that cleared __GFP_FS waits at most one second rather than indefinitely, because such a caller is likely holding a filesystem lock that kswapd itself will need, and an unbounded wait would be a deadlock rather than a throttle.

A thread that does proceed runs with PF_MEMALLOC set, which exempts its own allocations from the watermark checks for as long as it is inside reclaim. That is not a privilege but a necessity: freeing memory consumes memory—a writeback needs a bio, an unmap may need a page table page—and a reclaimer that could not allocate would deadlock against the shortage it was summoned to fix. The flag also silences the allocator's own attempts to recurse into reclaim, so the pipeline cannot re-enter itself.

Direct reclaim is the path the kernel most wants to avoid, because it turns a memory shortage into user-visible latency: every thread that allocates while memory is tight stops to do reclaim work, so a shortage that kswapd cannot outpace spreads slowdown across the whole workload. It is bounded rather than unlimited—do_try_to_free_pages() gives up after working through the reclaim priorities without success, returning failure to the allocator, which then retries, wakes kswapd again, or falls through to the OOM path—so a thread cannot loop forever in reclaim. The allocator's half of that bargain is a retry loop with a counter: should_reclaim_retry() allows another round only while progress is still being made or the reserves still look like they might be enough, and after MAX_RECLAIM_RETRIES fruitless passes it stops and the request falls through to compaction or to the OOM path. Callers steer that loop with allocation flags rather than by looping themselves: __GFP_NORETRY asks to fail fast and try something else, __GFP_RETRY_MAYFAIL asks for heavy effort but accepts failure, and __GFP_NOFAIL declares that the caller has no error path at all and the allocator must keep trying indefinitely. For an order above zero the loop alternates with compaction, since moving pages together may produce the contiguous block that freeing them individually never will. PSI quantifies exactly this cost, and it distinguishes two degrees: some pressure (PSI_MEM_SOME) is the fraction of time at least one task was stalled waiting on memory, while full pressure (PSI_MEM_FULL) is the fraction during which every runnable task was stalled and the CPU did no useful work at all. Because full pressure is the signature of genuine thrashing, userspace managers watch it to act early—shedding load or triggering a controlled kill—before the kernel's own OOM killer has to, which is the modern, proactive alternative to letting the system grind to the edge of collapse. They do not poll for it, either: a manager writes a stall threshold and a window to /proc/pressure/memory and then waits on the resulting file descriptor, so the kernel wakes it the moment the threshold is crossed. That turns memory pressure from something inspected after the fact into an event a supervisor can be scheduled on, which is what makes userspace out-of-memory management practical at all.

Cgroup-Scoped Reclaim

The third trigger is entirely new since Linux 2.6: a memory control group exceeding its limit. A cgroup's memory usage is tracked by a page counter with configurable thresholds, chiefly memory.high (a soft cap that triggers reclaim and throttling) and memory.max (a hard cap). When a charge would push usage over memory.high, try_charge_memcg() (mm/memcontrol.c) calls try_to_free_mem_cgroup_pages(), which runs the very same shrink_node()/shrink_lruvec() pipeline but with scan_control.target_mem_cgroup set, so only that cgroup's per-node lruvec lists are scanned. If usage stays above the limit the offending task is throttled on return to user space. This is why the LRU lists had to become per-cgroup: reclaim can be aimed at one container's memory without disturbing the rest of the system, and a runaway workload is contained to its own budget rather than evicting everyone else's pages. Reaching memory.max with reclaim unable to help invokes a cgroup-scoped out-of-memory kill, the subject two sections ahead.

The two caps play different roles worth separating. memory.high is a throttling cap: exceeding it does not fail the allocation but forces the charging task to reclaim and, if usage stays high, to sleep before returning to user space, so a cgroup over its high mark is slowed in proportion to how far over it is—applying steady back-pressure without ever killing anything. Two details make it work in practice. The penalty is applied on the way back to user space rather than at the point of the charge, so the sleeping task is holding no kernel locks and cannot block anyone else while it serves its sentence. And the curve is steep rather than linear: with a high mark of a hundred megabytes, a cgroup one megabyte over pays a handful of milliseconds per allocation, ten megabytes over pays a little over half a second, and the penalty saturates at two seconds. A workload that overshoots slightly barely notices; one that ignores the cap is slowed until it cannot overshoot further. memory.max is a hard cap: a charge that would exceed it triggers reclaim inline and, if that fails, the cgroup OOM killer. Below these there is also protection: memory.low and memory.min mark amounts of memory the reclaimer should avoid, or must refuse, to take from a cgroup even under global pressure, so a critical container's working set is shielded from reclaim driven by activity elsewhere. Together these turn the single global reclaim policy of Linux 2.6 into a per-container one, with guaranteed floors, throttled ceilings, and hard limits. The protections are not enforced at the charge at all but inside the reclaim scan itself, at the cgroup walk section 4.1 describes; the controls here are the interface, and that loop is where they take effect. Parallel limits exist for the other resources a cgroup can consume on its way out of memory—memory.swap.max and memory.swap.high bound how much of a cgroup may be pushed to swap, and memory.zswap.max bounds what it may hold compressed—so that one container cannot exhaust a shared swap device by being reclaimed aggressively.

All of it is observable, which is arguably the point. Each cgroup's memory.events file counts the number of times its memory.low protection was breached under pressure, its memory.high mark was exceeded, its memory.max was reached, an out-of-memory condition was declared, and a process was actually killed; a separate count records kills made as a group. A container manager reads these rather than inferring distress from timing, and together with the cgroup's own pressure-stall files they give a per-container version of the signals the previous section described for the system as a whole. A limit that is never hit produces no events, so a cgroup whose counters stay at zero is one whose budget is genuinely sufficient—a far more useful statement than any instantaneous usage figure.

The same machinery also enables proactive reclaim. Because reclaim can be scoped to a cgroup and driven to a target, writing to a cgroup's memory.reclaim control asks the kernel to free a specified amount from that cgroup on demand, independent of any watermark—used by userspace managers to trim idle containers, reclaim cold memory ahead of a new workload, or measure a job's true working set by pushing pages out and watching what refaults. This inverts the classic model: rather than reclaim being purely a reaction to shortage, a controller can drive it deliberately as a tool, which is one of the larger conceptual shifts in memory management since Linux 2.6.

Shrinking Kernel Caches

LRU reclaim frees user pages, but a large share of memory on a busy system is held by the kernel's own reclaimable caches—above all the dentry and inode caches that speed up path lookup. These are not on any LRU list, so the reclaimer cannot free them directly; instead it asks each owning subsystem to give some back through a shrinker.

The arrangement exists because the kernel cannot reach inside another subsystem's private data structures to free objects safely—only the subsystem knows which of its cached objects are idle, how they are locked, and what must happen before one is released. So reclaim and the caches meet at a narrow contract: reclaim says "memory is tight, please free about this many objects," and each subsystem obeys in its own way. Dozens of caches register shrinkers—not only the filesystem's dentry and inode caches but also XFS's internal caches, the GPU and DRM object caches, the network route cache, and many more—so this one interface lets the page reclaimer apply pressure across the whole kernel without knowing anything about what it is pruning.

The Shrinker Interface

A shrinker (struct shrinker, include/linux/shrinker.h) is a pair of callbacks a subsystem registers so reclaim can prune its cache. count_objects() reports how many reclaimable objects the cache holds, and scan_objects() is asked to free a specified number. During reclaim, shrink_slab() (mm/shrinker.c) calls each registered shrinker; the number it asks a shrinker to scan is computed in do_shrink_slab() from the reported object count, scaled down by the reclaim priority and weighted by the shrinker's seeks value—an estimate of how costly the objects are to recreate—so caches whose contents are expensive to rebuild are pruned more gently. This count-and-scan interface (replacing the single callback of Linux 2.6) also carries scope: a shrinker flagged SHRINKER_NUMA_AWARE is asked per node, and one flagged SHRINKER_MEMCG_AWARE is asked per cgroup, so kernel-cache reclaim can be aimed at a node or a container just as page reclaim can. The scan count is worth seeing in a little more detail, because it is what keeps kernel-cache reclaim proportional and fair. For a shrinker reporting freeable objects at reclaim priority, do_shrink_slab() computes a base amount of roughly freeable >> priority, then scales it by 4 / seeks, so a cache of cheap-to-refill objects (low seeks) is scanned harder than one whose objects cost several disk seeks to rebuild. The work is issued in chunks of SHRINK_BATCH (128) and, crucially, any shortfall is deferred: whatever a shrinker was asked to scan but did not (because its objects were momentarily locked or in use) is accumulated in a per-shrinker, per-node nr_deferred counter. That backlog is not simply added to the next round, though—it too is shifted right by the reclaim priority, so a cache that resisted once contributes only a fraction of its debt to a gentle pass and pays the whole of it only when pressure has become severe. The running total is swapped out of the counter rather than read from it, so that two CPUs shrinking the same cache at once do not each take on the same deferred work. A final clamp holds the target to twice the number of objects the cache says it has, which keeps a long-accumulated backlog from turning one pass into an attempt to free more than exists.

Two special cases in that arithmetic are worth knowing. A shrinker may declare seeks of zero, which is not a division by zero but a statement that its objects cost no I/O at all to recreate; such a cache is scanned at half its size on every pass, far harder than any weighted shrinker, on the reasoning that keeping cheap objects around only displaces memory that could hold something expensive. And the batching loop normally stops once fewer than a batch remains, to avoid calling a shrinker repeatedly for a handful of objects; but when the computed target exceeds the cache's entire population—which can only happen at high priority—the loop keeps going until the cache is drained, because at that point failing an allocation while reclaimable objects sit scattered across many under-full slabs is the worse outcome. A shrinker that finds nothing to free returns the sentinel SHRINK_EMPTY, letting the reclaimer skip it cheaply. Registration uses the modern shrinker_alloc()/shrinker_register() API, which allocates the shrinker and its per-node, per-memcg bookkeeping before it goes live—a safer two-step replacement for the single register_shrinker call.

Making shrinkers cgroup-aware created a scalability problem that shaped the data structures. A machine running thousands of containers, each nominally subject to hundreds of registered shrinkers, presents reclaim with millions of cgroup-and-shrinker pairs, and the overwhelming majority of them are empty—a given container has no objects in most filesystems' caches, let alone in the GPU's. Walking all of them to ask would cost more than the reclaim is worth. So each cgroup carries, per node, a shrinker_info: a bitmap with one bit per registered shrinker, set the first time that cgroup puts an object into that cache, with the deferred counts stored in the same units as the bits. Reclaim iterates set bits rather than shrinkers, so the cost of a cgroup-scoped slab scan is proportional to the caches the cgroup actually uses. Shrinker lifetime is managed around that indirection with RCU and a reference count: a scan looks the shrinker up under RCU, takes a reference, and drops the RCU lock before calling into code that may sleep, while shrinker_free() clears the registered flag and then waits for the last reference to be returned, so unregistering a shrinker never races with a scan already in progress.

All of this is observable and can be driven by hand. Each registered shrinker gets a directory under /sys/kernel/debug/shrinker containing a count file, which reports the freeable objects it currently holds broken down by node and cgroup, and a scan file that triggers a scan on demand—the slab-cache equivalent of the proactive reclaim controls section 1.3 describes, and the practical way to find out which cache on a machine is holding the memory. The blunter instrument is /proc/sys/vm/drop_caches, whose second bit runs every shrinker repeatedly until none of them frees anything more. It is a diagnostic rather than a tuning knob: emptying caches that took hours of work to populate makes the next hour slower, and the only sound use is to establish a clean baseline before a measurement.

The dentry and inode Caches

The most important shrinker is the one every mounted filesystem registers for its superblock. super_cache_count() and super_cache_scan() (fs/super.c) count and prune the superblock's dentry and inode caches together; a scan calls prune_dcache_sb() and then prune_icache_sb(), because a dentry pins its inode and so dentries must be released first. The lists these operate on are list_lru structures (include/linux/list_lru.h)—per-node and cgroup-aware LRU lists of objects—so unused dentries and inodes are themselves aged least-recently-used and reclaimed coldest-first, and the reclaim can be scoped to a node or cgroup like everything else. This is the modern form of the 2.6 code that reclaimed pages of shrinkable disk caches; the caches and their purpose are the same, but the mechanism is now the general, scope-aware shrinker and list_lru infrastructure rather than bespoke per-cache code.

super_cache_scan() begins by refusing to work in two situations, and both refusals matter more than the work itself. If the allocation that triggered reclaim cleared __GFP_FS, the shrinker returns SHRINK_STOP immediately: the caller may be holding filesystem locks, and freeing an inode calls back into the filesystem through clear_inode(), so proceeding would risk re-entering the very code that is waiting for memory. It then tries, without blocking, to take a shared reference on the superblock, and gives up if it cannot—a shrinker that waited for a superblock being unmounted would hold up reclaim for the whole system on behalf of one filesystem. Having decided to proceed, it splits its budget three ways rather than two. The superblock's dentries, its inodes, and any objects the filesystem caches privately through s_op->nr_cached_objects—XFS's internal caches being the usual example—each receive a share of the requested scan in proportion to how many objects they hold, so a filesystem with a huge dentry cache and few inodes has its dentries pruned correspondingly harder. Each share is rounded up by one so that every cache is always scanned at least a little, which is what allows a dying cgroup's kernel-memory accounting to drain to zero rather than stalling just short of empty.

The ordering constraint is stricter than it first appears and shapes the whole design. An inode cannot be freed while any dentry still refers to it, and a dentry in use (its reference count above zero, because a process has the file open or the directory as its working directory) cannot be freed at all—so pruning walks the list_lru and, per object, decides via a callback that returns one of a small set of verdicts: remove it, rotate it to the tail because it was referenced and deserves another pass, or retry later because it is temporarily locked. The rotation verdict is more than politeness. A dentry carries a DCACHE_REFERENCED flag and an inode an I_REFERENCED state bit, set when the object is used and cleared by the first shrinker pass that meets it, which is rotated rather than freed; only a second pass that finds the bit still clear will evict. These caches therefore implement in miniature exactly the two-chance structure the inactive and active lists give user pages, using a single bit and the LRU order in place of two lists. Only unreferenced dentries are dropped, which then releases their hold on the inodes, so a second shrinker pass (or the prune_icache_sb() half of the same one) can reclaim those inodes. Freeing a dentry or inode returns its slab memory to the allocator, which is what actually gives pages back—so shrinking these caches is usually a step removed from freeing pages, reclaiming objects whose aggregate frees the underlying slabs. The inode shrinker is the exception, and an instructive one. An inode that still owns cached pages or buffer heads is not freed at all; instead the shrinker drops that page cache outright with invalidate_mapping_pages(), counts the result as PGINODESTEAL (or KSWAPD_INODESTEAL when kswapd is the one doing it), and leaves the inode to be retried once it is empty. Here the slab shrinker is freeing page-cache pages directly, which is why the two kinds of reclaim cannot be reasoned about entirely separately: pressure applied to the inode cache comes out, at least in part, as pages of the file data of Chapter 15. Because path-name lookup leans so heavily on these caches, the reclaimer treats them gently by default (a comparatively high seeks weight), pruning them only in proportion to the pressure on ordinary pages rather than emptying them at the first sign of shortage. That balance is adjustable through vfs_cache_pressure, which is worth understanding precisely because it does not do what its name suggests: it scales the object count the superblock shrinker reports, not the scan it performs. At the default of 100 the count is truthful; above it the caches are made to look larger than they are and so attract proportionally more scanning, and below it smaller. The value zero is a trap rather than a setting—a cache that always reports nothing freeable is never pruned, and dentries and inodes accumulate until the machine runs out of memory with no reclaimable pages to show for it.

Writing a Shrinker

A subsystem that caches reclaimable objects registers a shrinker so the reclaimer can prune it under pressure. The modern API (include/linux/shrinker.h) is a three-step pattern: allocate the shrinker with shrinker_alloc(), fill in its callbacks and parameters, then publish it with shrinker_register(). Splitting allocation from registration is deliberate—the object is fully set up, including its per-node and per-memcg deferred-count bookkeeping, before it becomes visible to reclaim, which closes a race the old one-step register_shrinker() could hit. A minimal shrinker for a cache of objects kept on a list_lru looks like this: 

/* Count: how many objects could be freed right now. */
static unsigned long myc_count(struct shrinker *shrink,
                               struct shrink_control *sc)
{
        struct my_cache *c = shrink->private_data;
        unsigned long n = list_lru_shrink_count(&c->lru, sc);

        return n ? n : SHRINK_EMPTY;   /* SHRINK_EMPTY: nothing to do */
}

/* Scan: try to free about sc->nr_to_scan objects. */
static unsigned long myc_scan(struct shrinker *shrink,
                              struct shrink_control *sc)
{
        struct my_cache *c = shrink->private_data;

        /* walk the list_lru, calling myc_isolate() on each candidate */
        return list_lru_shrink_walk(&c->lru, sc, myc_isolate, NULL);
}

int my_cache_init(struct my_cache *c)
{
        c->shrink = shrinker_alloc(SHRINKER_NUMA_AWARE | SHRINKER_MEMCG_AWARE,
                                   "my-cache");
        if (!c->shrink)
                return -ENOMEM;

        c->shrink->count_objects = myc_count;
        c->shrink->scan_objects  = myc_scan;
        c->shrink->seeks         = DEFAULT_SEEKS;  /* cost to recreate an object */
        c->shrink->private_data  = c;

        list_lru_init_memcg(&c->lru, c->shrink);
        shrinker_register(c->shrink);             /* now live */
        return 0;
}

The two callbacks honor a simple contract. count_objects() must be cheap and side-effect-free—it is called on every reclaim pass just to size the work—and returns the number of freeable objects, or the sentinel SHRINK_EMPTY when there are none so the reclaimer can skip the cache. Its count should reflect only objects that can actually be freed; counting pinned or in-use objects would make the reclaimer expect memory that never materializes. scan_objects() is then asked to free about sc->nr_to_scan objects and returns how many it actually freed—or SHRINK_STOP if it cannot make progress right now (for instance because the allocation context in sc->gfp_mask forbids the I/O a free would require). Whatever it is asked to scan but does not free is carried forward automatically in the shrinker's deferred count, so a busy cache is pressed harder on later passes rather than escaping reclaim. The distinction between the two sentinels is easy to get wrong and worth stating plainly: SHRINK_EMPTY comes from the count callback and means there is nothing here, while SHRINK_STOP comes from the scan callback and means there is something here but now is not the time. Returning plain zero from a scan is a third thing again—it says the scan ran and freed nothing—and it leaves the unfulfilled work in the deferred counter, whereas SHRINK_STOP abandons the batch loop at once.

Two knobs are worth setting deliberately. The seeks weight is the shrinker's declaration of how expensive its objects are to rebuild, measured in notional disk seeks; DEFAULT_SEEKS is 2, a cache of objects that must be read from storage should say more, and a cache that can regenerate its contents from memory should say zero, which as the earlier section describes puts it on a far more aggressive schedule. The batch field overrides the default chunk of 128 objects per call into scan_objects(), and is worth raising for a cache whose per-call overhead is high—one that must take an expensive lock or walk a tree to reach its objects—so the fixed cost is amortized over more work. A new shrinker can be exercised without waiting for genuine memory pressure by reading its count file and writing to its scan file under /sys/kernel/debug/shrinker, which is the practical way to check that the count callback agrees with what the scan callback can actually deliver.

Three rules keep a shrinker safe. It must not allocate memory on the scan path in a way that could recurse into reclaim—it is already running inside reclaim, so it must respect sc->gfp_mask and avoid blocking allocations. It should honor scope: a SHRINKER_NUMA_AWARE shrinker frees objects on the node in sc->nid, and a SHRINKER_MEMCG_AWARE one restricts itself to the cgroup in sc->memcg, which is automatic when its objects live on a memcg-aware list_lru as above. And it must tear down cleanly: shrinker_free() unregisters and releases the shrinker, waiting out any scan already in flight, so it is safe to call while reclaim is active. Getting these right lets any subsystem participate in memory reclaim on equal footing with the page cache—the reclaimer applies proportional pressure, and the subsystem decides exactly what that means for its own objects.

The Out-of-Memory Killer

Reclaim usually keeps up, but it can fail: if almost all memory is anonymous with no swap, or dirty and un-writable, or genuinely in use, a scan may free nothing. When even repeated, highest-priority reclaim cannot satisfy an allocation, the kernel's last resort is to kill a process and take its memory. This section covers when that happens, how the victim is chosen, and the asynchronous reaper that makes the kill effective.

When the Killer Fires

The out-of-memory killer is invoked from out_of_memory() (mm/oom_kill.c), reached from __alloc_pages_may_oom() only after direct reclaim and its retries have all failed to make progress—it is deliberately the very last step of the allocation slow path. A parallel entry exists for memory cgroups: when a cgroup hits memory.max and reclaim cannot help, mem_cgroup_out_of_memory() runs the same killer scoped to that cgroup. The context of an OOM event is gathered in a struct oom_control (include/linux/oom.h)—the allocation's constraints, the target cgroup, and the eventual victim—and constrained_alloc() classifies whether the shortage is system-wide or confined to a cpuset, memory policy, or cgroup, which narrows the set of tasks eligible to be killed.

The constraint classification matters because an OOM event is often not a whole-system shortage at all. A process bound by mbind() or a cpuset to a subset of NUMA nodes can exhaust those nodes while the rest of the machine has memory to spare; the killer must then choose a victim that actually uses the constrained nodes, not merely the biggest process on the system. So constrained_alloc() returns one of CONSTRAINT_NONE (a true global shortage), CONSTRAINT_CPUSET, CONSTRAINT_MEMORY_POLICY, or CONSTRAINT_MEMCG, and the constrained cases restrict both the eligible victims and the meaning of "total memory" used to normalize scores. The killer also fires only after being careful that nothing else can help: the allocator retries reclaim up to its limit, and before killing, out_of_memory() checks for freeing already in flight—if another task is exiting or a previous victim's memory is still being reaped, it holds off rather than killing a second process needlessly.

In fact out_of_memory() has several ways to return without killing anything, and they run before any scoring. It first consults a notifier chain, which is how a balloon driver in a virtual machine gets a chance to hand memory back before a guest starts killing processes; if a notifier frees anything, the event is abandoned. It then checks whether the allocating task is itself already dying, in which case that task is made the victim of record—marked, granted reserves, and queued for reaping—so it can finish exiting rather than have some innocent third process killed on its behalf. And a global allocation that cleared __GFP_FS is refused an OOM kill outright, on the principle that the killer does not compensate for I/O-less reclaim: such a caller has not demonstrated that memory is gone, only that it was not permitted to look properly, so it is sent back to retry rather than allowed to kill. A cgroup OOM is deliberately exempt from that last rule, because a cgroup at its limit will never make progress by retrying no matter what its gfp flags say. The killer can also be switched off wholesale while the system hibernates, when processes are being frozen and killing one would be meaningless.

Choosing a Victim

The killer aims to free the most memory while killing the fewest, most expendable processes. oom_badness() scores each candidate by its memory footprint—resident set, swap usage, and page-table size—so the process using the most memory is the most likely victim, and killing it frees the most. The score is adjusted by each task's oom_score_adj, a value in /proc/<pid>/oom_score_adj ranging from −1000 to +1000 that lets administrators bias the choice; the special minimum makes a process ineligible entirely by an explicit test rather than by arithmetic, protecting critical services. (This replaces the older oom_adj, still present but deprecated and remapped onto the new scale.) select_bad_process() scans the eligible tasks—all processes for a global event, or the cgroup's tasks for a cgroup event—and picks the highest score. Figure 17-8 shows the flow.

The score is deliberately simple, and its exact form explains how oom_score_adj behaves. The base points are the sum of the process's resident pages, its swap entries, and its page-table pages—everything killing it would return to the system—so a big memory hog scores high regardless of how long it has run or how much CPU it has used. The adjustment is scaled to that same currency: oom_score_adj is multiplied by totalpages / 1000 and added, so the full ±1000 range corresponds to ±100% of total memory. Setting a service's oom_score_adj to −500 therefore discounts its footprint by half of RAM when comparing it against others, and the minimum is not merely the far end of that scale. oom_badness() tests for it before computing anything and returns the lowest possible score, so a process at −1000 is excluded categorically rather than merely made expensive to choose—a distinction that matters, because at −999 the arithmetic still applies and a large enough process remains a candidate. Two other conditions take the same categorical exit: a task whose memory has already been reaped carries MMF_OOM_SKIP and would yield nothing if killed again, and a task in the middle of a vfork() is borrowing its parent's address space, so killing it would destroy memory belonging to a process that was never chosen. This design means the knob expresses a bias in units of memory, not an arbitrary priority, which is why it composes predictably: a process is picked when its real footprint minus its adjustment exceeds every other candidate's. The scan skips the unkillable—kernel threads, the global init process, and tasks already marked as OOM victims. Once it has a winner, the kill is wider than one process: __oom_kill_process() signals every task that shares the victim's mm_struct, not merely its thread group, because an address space stays alive as long as any of its users does and killing one sharer of it would free nothing at all. Older kernels also tried to redirect the kill to a child that would free enough on its own; that heuristic has since been removed, because a score computed for the parent says nothing about which descendant actually holds the memory, and the indirection produced kills that were both unpredictable and frequently useless.

Killing and the OOM Reaper

oom_kill_process() sends the victim a SIGKILL and marks it with TIF_MEMDIE, which grants the dying task access to memory reserves so it can run its own exit path and release memory. Marking a victim also thaws it if it happens to be frozen, whether by system suspend or by a cgroup freezer, since a frozen process can never act on its SIGKILL and a killer waiting on one would deadlock the machine it was trying to rescue. The problem the 2.6 killer had is that a victim can be slow or unable to die—blocked in uninterruptible sleep, or stuck trying to allocate the very memory that is exhausted—so the kill alone did not guarantee timely relief. The modern kernel adds the OOM reaper, a kernel thread (oom_reaper) that oom_kill_process() hands the victim to. The reaper does not wait for the process to exit: it walks the victim's address space and unmaps its anonymous, non-shared memory itself with __oom_reap_task_mm(), freeing the bulk of its pages without the victim's cooperation. This makes the OOM killer reliable—memory is recovered promptly even from a wedged victim—which is why an out-of-memory event now resolves quickly instead of risking a stall.

The reaper is not, however, dispatched immediately. Queuing a victim arms a timer two seconds out, and only when it expires is the thread woken. That delay is deliberate: a healthy victim will normally take its SIGKILL, run exit_mmap(), and release everything well inside two seconds, and a process tearing down its own address space is both faster and simpler than a second thread doing it concurrently, with no lock contention and no window in which half-unmapped memory is visible. The reaper exists for the victim that does not manage this, so it costs nothing to let the ordinary case finish first. The two paths meet at the same flag: exit_mmap() sets MMF_OOM_SKIP itself once it has unmapped the address space, so a victim that dies normally reports its own completion and the reaper, arriving late, finds nothing left to do.

The reaper and the kill interlock through flags on the victim's mm_struct. Queuing the victim sets MMF_OOM_REAP_QUEUED so it is reaped only once; the reaper takes the mmap_lock in read mode and, if it cannot, retries ten times at tenth-of-a-second intervals rather than block forever behind whatever wedged the victim. Should all ten attempts fail it gives up loudly, logging the stuck task's stack and every lock held on the system—a victim that cannot be reaped is almost always evidence of a deadlock worth reporting—and then sets MMF_OOM_SKIP anyway, so that a permanently wedged address space cannot prevent the killer from moving on to a different process. Before unmapping it sets MMF_UNSTABLE to warn other subsystems that the address space is being torn down out from under the process, so that a concurrent get_user_pages() or copy_from_user() knows the contents it reads are no longer trustworthy. It then walks the victim's mappings from the highest address downwards, precisely because the dying task unmaps from the bottom up: starting the two teardowns at opposite ends of the address space keeps them from contending for the same page table locks. When done—or if the memory is shared and cannot be safely reaped—it sets MMF_OOM_SKIP, which tells the killer this victim's memory has been dealt with and it may, if the shortage persists, choose another. The reaper deliberately touches only private anonymous memory, and skips huge-page and raw-PFN mappings outright since neither can be torn down cheaply: file-backed pages can be reclaimed normally, and shared memory might still be in use by a survivor, so leaving them is both safe and sufficient, since a process's private anonymous pages are usually the bulk of what it holds. This is why the TIF_MEMDIE reserve grant is now a backstop rather than the main mechanism: the reaper frees memory proactively, so the dying task no longer has to win an allocation race just to release its own pages.

Two policy controls surround the mechanism. For memory cgroups, memory.oom.group turns the kill into a group operation—when set, the whole cgroup is killed together, so a multi-process workload is stopped as a unit rather than losing one member and continuing in a broken state. The scope of that widening deserves care. The kernel does not simply kill the cgroup that hit its limit; it walks from the victim's own cgroup upwards as far as the cgroup whose limit was breached, and kills the highest ancestor along that path with the flag set. A container runtime that sets the flag near the top of its hierarchy therefore turns one task's overrun into the loss of everything beneath it, which is usually the intent but rarely the first guess. Within the doomed subtree two kinds of member are still spared: processes pinned at the minimum oom_score_adj, and the system's init. And the panic_on_oom sysctl makes a system-wide OOM event deliberately crash the machine instead of killing a process, which some deployments prefer so that a supervisor can restart from a known state. Barring those, the OOM killer is a targeted last resort: it kills one process, the reaper frees its memory, and the system continues.

Several other sysctls tune the killer's behavior, and they are worth knowing because the default is not always what an operator wants. oom_dump_tasks (on by default) makes the kernel log a table of every eligible task and its score when it fires, invaluable for understanding why a particular victim was chosen after the fact. oom_kill_allocating_task changes the policy from "scan and pick the worst" to "just kill whoever triggered the OOM," which is cheaper and more predictable on systems with huge numbers of tasks but sacrifices the fairness of scoring. And panic_on_oom has a middle setting (2) that panics even on a constrained or cgroup-local OOM, not just a global one. Together with oom_score_adj these turn the killer from the fixed, opaque mechanism of Linux 2.6 into something an administrator can shape—biasing which processes are chosen, deciding whether to kill or panic, and getting a full record of each decision.

Swapping

Reclaiming a clean file page is easy because its data already exists on disk. Anonymous memory—heap, stack, private mappings—has no such backing, so to reclaim it the kernel must first save it somewhere. Swapping is that facility: a set of swap areas on disk (or in compressed memory) that hold anonymous pages while they are out of RAM, and the machinery to move pages out and back. It is the largest and most self-contained part of the reclaim subsystem, almost a chapter of its own, and this section covers its structures and flows in turn.

A word on terminology, because the modern role of swap differs from its role in Linux 2.6. Swap is not a way to run with less RAM at the same performance—paging to disk is orders of magnitude slower than memory—but a pressure-relief valve and a place to put memory that is genuinely cold. Its value is that it lets the reclaimer treat anonymous and file pages uniformly: with swap present, a rarely-touched heap page is just another cold page that can be evicted to make room for hot data, whereas without swap it is pinned in RAM no matter how idle it is. Compression (covered below) has sharpened this further, turning swap from a last-ditch disk overflow into a routine tier between RAM and storage. The pieces that follow are the same as in Linux 2.6—areas, entries, the cache, the I/O paths, and swapoff—but each has been reworked for concurrency, SSDs, large folios, and compression.

Swap Areas

A swap area—a partition or a file activated with swapon—is described by a struct swap_info_struct (include/linux/swap.h). Its heart is swap_map, an array of small usage counters with one entry per page-sized slot in the area, recording how many references each swapped page has (a page shared by several processes has a count above one). Other fields give the area its priority, its backing file or block device, and its flags. The system can have several swap areas at once; they are kept on a priority-ordered list, and allocation prefers higher-priority areas, spreading across equal-priority ones. The scalability of slot allocation is a notable change since Linux 2.6. Rather than scanning swap_map linearly for a free slot, the modern allocator divides the area into clusters (swap_cluster_info) and keeps a per-CPU cluster so concurrent swap-outs on different CPUs do not contend, and so a process's pages tend to land in contiguous slots—which matters both for read-ahead and for issuing large, aligned writes. On an SSD (SWP_SOLIDSTATE) the allocator also arranges to discard freed clusters so the drive can reclaim them. Large folios are swapped as a unit into a cluster when transparent-huge-page swap is configured.

The clusters themselves are kept on lists by how full they are, and the shape of those lists is what makes large-folio swap-out practical. Besides a list of wholly free clusters and one of wholly full ones, the area keeps per-allocation-order lists of partially used clusters, split into those that still have a run of the right size and those that have become too fragmented to serve one. An order-4 folio looking for sixteen aligned contiguous slots therefore consults the list for its own order and finds a candidate immediately, instead of scanning clusters that could only ever satisfy a single-page request. A cluster is a substantial unit—512 slots where transparent huge pages are configured, 256 otherwise—so this indexing is the difference between large-folio swap being routine and being a lucky accident, and it is why a fragmented swap area degrades by silently falling back to splitting folios rather than by failing outright.

Priority is the knob that lets an administrator build a swap hierarchy. Each area gets a priority at swapon time (explicit, or assigned in decreasing order of activation), and the allocator always draws from the highest-priority area that has free slots, falling back to lower ones only when it fills; areas of equal priority are used round-robin so their I/O is spread across devices. This is what makes a fast-then-slow arrangement work—a small high-priority zram or NVMe area absorbs the common case, and a larger, slower disk area of lower priority catches the overflow—without the kernel needing any policy beyond "prefer the highest priority with room." The SWP_SYNCHRONOUS_IO flag marks the fast end of that spectrum: for a device quick enough that the latency of an interrupt-driven completion outweighs the read itself, the swap-in path reads the page synchronously in the fault handler and skips the swap cache entirely, which is a meaningful win for zram and fast NVMe and a case the flag exists specifically to enable.

Swap Entries

When a page is swapped out its physical frame is freed, but the page-table entries that mapped it must still record where it went so a later access can bring it back. That is the job of a swap entry, swp_entry_t (include/linux/swapops.h): a compact value encoding which swap area (the type) and which slot within it (the offset) holds the page. During eviction, try_to_unmap_one() replaces each present PTE that mapped the folio with a non-present PTE carrying the swap entry (swp_entry_to_pte()). A later access to that address faults, the fault handler reads the swap entry back out of the PTE, and it knows exactly where to find the data. Figure 17-9 shows a swapped page's PTE alongside the swap area and cache.

The swap_map counter the entry points at is what makes shared anonymous pages work across swap. A page mapped by several processes—because they forked and share it copy-on-write—has one swap slot but a usage count above one, so swapping it out does not immediately free the slot; each process's PTE holds the same swap entry, and the slot is released only when the last of them has either faulted the page back in or exited. That count has a limited width—six bits, so it saturates at 62 references—and a page shared by more processes than that uses a continuation (the SWP_CONTINUED mechanism), a chain of extra pages each contributing seven more bits to the count. The arrangement is unapologetically optimized for the common case: the overwhelming majority of slots are referenced once or twice, so paying a byte per slot and handling the rare deeply-shared page by exception costs far less memory than sizing every counter for the worst case. Freeing works in reverse: swap_free() drops one reference as each mapping is restored or torn down, and when the count reaches zero the slot returns to its cluster's free pool (and is discarded to an SSD if the area is SWP_DISCARDABLE).

The same non-present-PTE encoding is multiplexed for several other special states—migration entries (a page being moved; see Migration Entries), device-private entries, hardware-poison markers (see Memory Failure and HWPoison), and PTE markers—so the fault handler first classifies the entry before treating it as a swap-in. This shared encoding is why the swap-entry machinery underpins more of modern memory management than swapping alone, though the reclaim path uses it strictly for anonymous pages saved to swap.

The multiplexing is not free, and the cost lands in an unexpected place. The type field is five bits wide, so there are thirty-two type numbers in existence—and every special encoding claims one or more of them from the top of the range. Page migration reserves three (read, write, and exclusive-read), device-private memory another three, hardware poison one, and PTE markers one, which leaves a kernel configured with all of them supporting twenty-four swap areas rather than thirty-two. The limit is generous enough that few installations notice, but it explains a number that otherwise looks arbitrary, and it is a good illustration of how the page-table entry—the one structure the hardware forces the kernel to share—ends up as contested real estate.

The Swap Cache

Moving a page to or from swap is full of races: two processes sharing an anonymous page might fault on it at the same time, or a page might be faulted back in while it is still being written out. The swap cache serializes these. It is an index from swap entry to folio, consulted by everyone who touches a slot, in which a folio being swapped lives while it is in transit. Because all parties look the folio up in the swap cache by its swap entry, a second faulter finds the in-flight folio and waits on it rather than starting a duplicate transfer, and a swap-in that races with swap-out finds the still-cached folio and skips the disk read entirely. A folio's membership is testable with folio_test_swapcache(), and swap_cache_add_folio() / swap_cache_get_folio() add and look up entries.

What that index actually is has changed, and the change is recent enough to be worth stating plainly, because every older account of the swap cache describes it as a use of the page cache: a fake address space, swapper_space, whose XArray was keyed by swap entry exactly as a file's is keyed by offset. In 7.0.12 that is no longer the mechanism. The index is now a flat array per swap cluster, struct swap_table (mm/swap_table.h), holding one word per slot; because a cluster's slots are contiguous and the array is a 1:1 map of them, a lookup is an offset computation rather than a tree descent, and there is no shared lock for concurrent swap-outs to contend on. swap_cache_get_folio() is the whole of it: compute the cluster from the entry, read the word, and take a reference if it holds a folio. The old address_space still exists as swap_space in mm/swap_state.c, but the comment above it now calls it "a fiction, retained to simplify the path through vmscan's shrink_folio_list"—it survives only so that code which reaches for folio->mapping finds something valid there.

The new table also carries more than folio pointers. Each word is one of three things: null, a pointer to a folio in the cache, or a shadow entry—the same encoding section 4.4 describes for the page cache. Swap thus gained its own refault detection, so a swapped-out anonymous page that is faulted straight back is recognized as having been evicted too soon, exactly as an evicted file page is. The two halves of reclaim, which Linux 2.6 treated as quite different problems, now feed the same working-set estimator.

The swap cache is really the swap subsystem's answer to a page cache's identity problem: an anonymous page has no file and offset to name it, so while it is in transit to or from swap the kernel gives it a temporary identity—its swap entry—and indexes it by that, exactly as a file page is indexed by its file offset. Two consequences follow. A page shared by several processes is swapped out once and swapped back in once no matter how many of them fault on it: the first faulter installs the folio in the swap cache, and the others find it there and simply re-point their PTEs, so the disk read is never duplicated. And a folio that has been read back in can linger in the swap cache, still associated with its swap slot, so if it is reclaimed again without having been modified it need not be rewritten—the copy on disk is still valid. The cost is that the swap cache holds references that must be cleaned up, which is why SWP_SYNCHRONOUS_IO devices deliberately bypass it: when a page is mapped by only one process and the device is fast, the fault handler reads the page directly and never puts it in the cache, avoiding the bookkeeping for the common private-page case.

Swapping Out and Back In

Swapping out begins inside the reclaim pipeline. When shrink_folio_list() reaches a reclaimable anonymous folio it calls folio_alloc_swap(), which reserves a slot in a swap area and adds the folio to the swap cache; try_to_unmap() then rewrites the mapping PTEs to swap entries, and the dirty folio is written to the device by swap_writeout() and __swap_writepage() (mm/page_io.c), which builds a bio straight on the folio's pages—the same block-layer path as file writeback. Once the write completes and no one holds the folio, its frame is freed. Swapping in happens on a fault: do_swap_page() (mm/memory.c) extracts the swap entry from the faulting PTE, looks for the folio in the swap cache, and on a miss reads it from the area with swap_read_folio()—optionally reading ahead neighboring slots—then locks it, restores a present PTE pointing at the new frame, and lets the faulting instruction retry. Figure 17-10 traces both directions.

The swap-in path has more nuance than the fault-and-read sketch suggests, because a single disk read is wasteful if the pages around it will be wanted too. So do_swap_page() usually calls swapin_readahead(), which fetches a cluster of nearby pages in one go on the guess that a process swapping in one page will soon touch its neighbors. How many neighbors is where measurement does enter: both policies share one window calculation that doubles the batch when the previous batch was actually used, collapses it to a single page the moment a fault lands somewhere not adjacent to the last one, and then refuses to shrink below half the previous window so that one stray access does not throw away a working prefetch pattern. The ceiling is /proc/sys/vm/page_cluster as a power of two, defaulting to three and therefore eight pages; setting it to zero disables swap read-ahead altogether, which is the standard recommendation for zram, where a decompression is cheap enough that guessing wrong costs more than it saves. Two policies choose which neighbors: cluster read-ahead reads slots physically adjacent in the swap area (good when a process's pages were written out together into one cluster), while VMA read-ahead reads pages adjacent in the faulting process's virtual address space (better when swap slots are scattered). The kernel does not choose between them by measuring which works better; it chooses by device. VMA read-ahead is the default, and the kernel falls back to cluster read-ahead for as long as any rotating swap device is active, on the reasoning that a seek dominates everything else on such a device, so reading slots that are physically adjacent is worth far more than reading pages the process is more likely to want. On an SSD, where position carries no cost, virtual-address locality is simply the better predictor of what will be touched next. The policy can also be forced off through /sys/kernel/mm/swap/vma_ra_enabled. The exception is again the SWP_SYNCHRONOUS_IO fast path: for a single-mapped page on a fast device the handler skips both the read-ahead and the swap cache and reads just the one page synchronously, because the latency saved by not setting up asynchronous completion outweighs any benefit from prefetching. On the way out, the reverse-SWP_CONTINUED accounting and the deferred freeing of the frame mean a swapped page can briefly exist in three places at once—its PTE (as a swap entry), the swap cache (as a folio), and the swap area (as saved data)—which is exactly the state Figure 17-9 depicts.

Compressed Swap

The most consequential swap addition since Linux 2.6 is compression. zswap (mm/zswap.c) is a compressed cache that sits in front of the real swap device: when a folio is swapped out, swap_writeout() first offers it to zswap_store(), which compresses it and keeps it in a pool of memory rather than writing to disk; a later swap-in calls zswap_load() to decompress it directly, avoiding the device entirely. Because compressed anonymous data typically occupies a fraction of its original size, zswap effectively enlarges memory and turns most swap traffic into fast in-memory compression instead of slow disk I/O, only spilling to the backing device when the compressed pool itself fills. The pool is capped as a percentage of total memory, twenty by default, and the cap is enforced with deliberate hysteresis: once the pool is full zswap stops accepting stores entirely and does not resume until writeback has drained it back to ninety percent of the cap, so a system sitting exactly at the boundary alternates between two clean regimes instead of thrashing on every page. A related tool, zram, presents a compressed block device that can be used as a swap area in its own right—common on memory-constrained and disk-less systems. Both reflect a shift in what swapping is for: no longer only an overflow to slow disk, but a way to trade CPU cycles for effective memory capacity.

The two tools differ in where they sit, and the distinction matters. zram is a compressed block device: it looks like an ordinary swap device to the rest of the kernel, so a page written to it goes through the normal swap_writeout() path and is compressed inside the driver, and there is no disk behind it at all—when zram fills, swap-out simply fails and pressure builds. zswap, by contrast, is a cache in front of a real swap device: swap_writeout() offers each page to zswap_store() first, and only pages that compress poorly, or that overflow the pool, or that zswap later decides to evict are written through to the backing device in their uncompressed form. That last category is not an afterthought: zswap keeps its compressed entries on an LRU of their own and registers a shrinker against it, so the ordinary reclaim machinery of section 6 reaches into the compressed pool and writes its coldest entries through to disk before the pool is full, rather than waiting for the cliff. That list is per-cgroup like the folio LRUs, which means a container's compressed footprint is aged against its own pressure and not the machine's; a cgroup can also be forbidden to write through at all with memory.zswap.writeback, confining it to compression alone. This gives zswap a property zram lacks—it has somewhere to spill—so it degrades gracefully under sustained pressure while still keeping the hot, compressible majority of swap traffic in fast memory. Both rely on the observation that anonymous memory is usually compressible (zeroed pages, sparse structures, text) and on modern CPUs being able to compress a page far faster than a disk can store it; on a memory-constrained system the effect is that the machine behaves as though it had noticeably more RAM, at a cost in CPU that is usually a good trade.

Turning Swap Off

A swap area can be removed at run time with swapoff, and doing so is the mirror image of swapping: every page currently in the area must be brought back into memory before the area can be released. The syscall calls try_to_unuse() (mm/swapfile.c), which walks every process's page tables and the swap cache, faulting each of the area's pages back in and rewriting the swap entries to present PTEs, until the area's usage counts reach zero. Only then is the area detached. Because this can require faulting in a great many pages, swapoff on a heavily used area is slow and can itself create memory pressure—the reason it is an administrative operation rather than an automatic one. The complementary swapon path validates the area's header and threads it into the priority list so the reclaimer can begin using it.

swapoff is genuinely one of the harder operations in the subsystem, and it can fail, which is worth understanding. Pulling every page of an area back into RAM can require more memory than is free—so try_to_unuse() proceeds incrementally, faulting pages in a few at a time and letting normal reclaim push other pages out to remaining swap areas as it goes, but if there is simply nowhere to put the returning pages the call fails with -ENOMEM and the area stays active. It must also cope with a moving target: while it scans, running processes continue to fault their pages back in on their own, and new swap-outs (to other areas) proceed, so try_to_unuse() loops until the area's in-use count truly reaches zero rather than making a single pass. It walks three populations to get there—the swap cache, whose folios it can detach directly; every process's page tables via the mm list, whose swap entries it must fault back to present PTEs; and the shared-memory objects, whose swapped pages are reached through no page table at all, since a shmem page's swap entry is parked in the page cache where the folio used to be and so persists even when no process has the segment mapped. The difficulty is the price of a feature Linux 2.6 also had: swap can be reconfigured on a live system, added or removed without a reboot, which demands exactly this careful, restartable drain.

Page Migration and Memory Failure

Everything so far in this chapter has been about getting rid of a page's contents. A closely related problem is moving them: keeping the data and the virtual addresses that reach it, but changing the physical frame underneath. The kernel does this constantly—to defragment memory for huge pages, to bring memory closer to the CPU that uses it, to demote cold folios, to empty a block of RAM before it is unplugged, and to evacuate a page that the hardware has reported as failing. All of these share one engine, migrate_pages() (mm/migrate.c), and the reverse-mapping walk this chapter already met. This part explains who calls it, the protocol it follows, the migration entries that keep the move invisible to the process, the hooks that let pages outside the LRU move too, and memory hot-remove, the client that depends on it most. A final section covers the memory-failure handler, which deals with RAM that has actually gone bad. It migrates pages that can still be read, and for the rest uses the same unmap machinery and a special entry left in the page table.

None of this existed in Linux 2.6.11. Page migration arrived in 2.6.16 (2006), first to support NUMA memory policies and then memory hot-remove; the memory-failure handler, mm/memory-failure.c, arrived in 2.6.32 (2009). In 2.6.11 a physical page stayed where it was for its whole life unless it was evicted, and an uncorrectable memory error was a machine check that ended in a panic. Both assumptions are now wrong, and much of the folio and reverse-mapping machinery in this chapter is shaped by the need to support relocation.

Compaction and its compaction_alloc() destination callback are described in Chapter 8 (Memory Compaction), as are CMA and the gigantic HugeTLB pages that need alloc_contig_range(). The modes form a ladder. MIGRATE_ASYNC never blocks: it gives up on a folio that is locked or under writeback, and it is what latency-sensitive callers such as NUMA balancing and the first pass of direct compaction use. MIGRATE_SYNC_LIGHT will wait for a folio lock but not for I/O, and it is the mode used by kcompactd and by direct compaction once the cheap attempt has failed. MIGRATE_SYNC waits for anything, including writeback, and it is reserved for callers that must empty a specific range and have no alternative.

The callers also differ in how they treat failure, and that difference explains much of the engine's design. To compaction, a folio that will not move is an inconvenience: it skips the pageblock and tries elsewhere. To alloc_contig_range(), memory offlining, or a long-term pin into ZONE_MOVABLE, one stuck folio fails the whole operation. The engine therefore retries, splits large folios it cannot place whole, and reports exactly how many folios it could not move, and it leaves the decision about what that means to the caller.

The Migration Protocol

Moving a page that other CPUs may be reading and writing at that moment has the same difficulty as unmapping one for reclaim, with an additional requirement: when the move is over, every mapping must point at the new frame, and no write may have landed in the old frame after its contents were copied. The kernel meets that requirement with four phases, and Figure 17-11 shows how they connect.

Isolate. The caller removes each folio from wherever it normally lives, so that reclaim, compaction, and other migrators cannot also take it. For an LRU folio this is folio_isolate_lru(), the same isolation reclaim uses. For a page with movable_ops (described in section 9.4) it is isolate_movable_ops_page(). isolate_folio_to_list() chooses between the two. Isolation takes a folio reference, and the isolated folios are chained through folio->lru onto a private list that is handed to migrate_pages(). Whatever the engine cannot move is left on that list, and the caller returns it with putback_movable_pages().

Unmap. For each folio, migrate_folio_unmap() calls the caller's get_new_folio callback to allocate the destination and locks the source folio. In async mode it gives up if the source is already locked. It then waits for or rejects writeback according to the mode, pins the folio's anon_vma so the reverse map cannot vanish while the folio is unmapped, and calls try_to_migrate(). That rmap walk replaces every PTE (or PMD, for a PMD-mapped THP) that maps the folio with a migration entry. From this point on, no process can reach the old frame through its page tables.

Move. migrate_folio_move() transfers the folio's identity to the destination. It calls the owning address_space's migrate_folio method or, for an anonymous folio not in the swap cache, the generic migrate_folio(). The critical step is the reference check. The engine computes how many references the folio should have once all of its mappings are gone: one for each page-cache or swap-cache slot, one for any private data, and one for the isolation. __migrate_folio() compares the count with that figure before doing any work, copies the data with folio_mc_copy(), and then __folio_migrate_mapping() freezes the count at exactly that value with folio_ref_freeze() while holding the mapping's xarray lock. If anyone else holds a reference—an in-flight get_user_pages(), a direct I/O, a speculative page-cache lookup—the check or the freeze fails, the move returns -EAGAIN, and the still-unmapped folio is tried again on the next pass. If the freeze succeeds, nobody else can take a new reference, and the code says so: no turning back from here. Copying before the freeze is safe because the folio is locked and has no mappings left, and anyone who could still write to it—a pinned direct-I/O buffer, say—holds a reference that makes the freeze fail. The xarray slot is switched to the new folio, and the dirty bit and the per-node and per-memcg statistics follow it. folio_migrate_flags() then carries over the remaining state: referenced, active or unevictable, workingset, the idle and young bits, the NUMA-balancing last-access CPU and PID, the KSM stable-node link, and the memcg binding.

Remap. remove_migration_ptes() walks the reverse map of the new folio and turns each migration entry back into a present PTE that points at the corresponding page of the destination. It restores writability and the young and dirty state recorded in the entry. Each restored mapping adds the mapcount and folio reference it would have had in the old frame. The folio locks are released, which wakes anyone who faulted during the move. The source folio, now with no mappings and no cache slot, drops its last reference and returns to the buddy allocator.

Unmapping and moving are deliberately separate phases, and since 6.3 the engine exploits the gap. migrate_pages() carves the caller's list into batches of up to NR_MAX_BATCHED_MIGRATION base pages—HPAGE_PMD_NR, 512 on a 4 KiB-page system with THP—and migrate_pages_batch() first unmaps every folio in the batch, then issues a single try_to_unmap_flush(), and only then moves them. Unmapping a folio requires a TLB shootdown on every CPU that might cache the old translation. Batching the shootdowns turns hundreds of inter-processor interrupts into one, which is a large saving for compaction and NUMA balancing, the callers that move pages in bulk.

Each batch is attempted up to NR_MAX_MIGRATE_PAGES_RETRY (ten) times. A synchronous request is first tried as an asynchronous batch for three passes, and only the folios that are left over are retried one at a time in the caller's synchronous mode for the remaining seven. This order keeps the expensive blocking work for the folios that actually need it. Large folios add one more fallback. If a THP cannot be migrated whole—the architecture lacks THP migration, the destination allocation failed, or the folio was already partially unmapped—try_split_folio() splits it and the pieces are retried with one asynchronous pass at the end. A folio whose move still returns -EAGAIN after the last pass is not left stranded behind its migration entries: migrate_folios_undo() runs remove_migration_ptes() with the source as its own destination, so the original mappings come back exactly as they were. NUMA balancing is the exception: it sets nosplit because breaking up a hot THP to move it closer would cost more than leaving it where it is. HugeTLB folios cannot be split, so migrate_hugetlbs() handles them separately before the batching begins.

The return value counts the folios that did not migrate, with a split large folio counted as one failure however many of its pieces moved. A negative value means the engine stopped early: -ENOMEM when the destination callback failed, which the callers treat as a reason to stop rather than retry. The counters pgmigrate_success and pgmigrate_fail, together with thp_migration_success, thp_migration_fail, and thp_migration_split, are exported in /proc/vmstat. The mm_migrate_pages tracepoint reports the same figures per call, together with the reason.

Migration Entries

A migration entry is one of the non-present PTE encodings described under swap entries in section 8.2. It uses one of the type numbers reserved at the top of the swap-type range, and its offset field holds not a swap slot but the page frame number of the page being moved. In 7.0 these special encodings are handled through the softleaf helpers in include/linux/leafops.h. softleaf_type() classifies a non-present entry as a swap entry, one of three migration kinds, a device-private entry, a hardware-poison entry, or a PTE marker, and the fault handler acts on that classification before it ever considers swap-in.

There are three migration kinds because the entry must remember how the page was mapped, so that the remap phase can rebuild an equivalent PTE. SOFTLEAF_MIGRATION_WRITE records that the PTE was writable. SOFTLEAF_MIGRATION_READ_EXCLUSIVE records a read-only mapping of an anonymous page that belonged exclusively to this process. This is the PageAnonExclusive state that Chapter 9 relies on to keep copy-on-write correct under pinning, and it must survive the move. SOFTLEAF_MIGRATION_READ covers everything else. Where the architecture has spare bits in the swap-entry format (migration_entry_supports_ad()), the entry also carries the old PTE's young and dirty bits. Without them, every migrated page would come back looking freshly accessed and clean, which would mislead reclaim's aging and could even lose a dirty bit on a file page. Soft-dirty and userfaultfd write-protect state ride along in the swap-PTE bits as they do for an ordinary swap entry.

The other half of the design is what happens when a thread touches the address during the move. do_swap_page() sees the migration entry and calls migration_entry_wait(), which re-reads the PTE under its page-table lock and, if the entry is still there, calls softleaf_entry_wait_on_locked() (mm/filemap.c). That function sleeps on the source folio's PG_locked bit in the same hashed page wait queue that folio_lock() uses—without taking a reference to the folio, which would make the migrator's reference freeze fail. When the migrator unlocks the folio at the end of the remap phase the thread wakes up and returns from the fault, and the instruction faults again, this time finding a present PTE for the new frame. PMD-mapped THPs use pmd_migration_entry_wait(), and HugeTLB uses migration_entry_wait_huge(). GUP and other page-table walkers that find a migration entry wait the same way or retry. The result is that migration is invisible to the process apart from a short sleep, which shows up only in the wait-time accounting.

Teaching the Kernel to Move a Page

The generic engine knows how to move the bytes, but it cannot know every place that refers to a page. For page-cache folios that knowledge lives in the filesystem and is exported through address_space_operations->migrate_folio. Most filesystems use one of three library implementations: filemap_migrate_folio() (for example XFS and most iomap-based filesystems) moves the cache slot and any private pointer; buffer_migrate_folio() (ext4 data, block-device mappings) also re-points each buffer_head attached to the folio; and migrate_folio() itself serves anonymous swap cache and shmem. A mapping that provides no method falls back to fallback_migrate_folio(), which refuses a dirty folio and otherwise asks the filesystem to release its private data first, and warns that the mapping should implement the method. Some mappings refuse on purpose: secretmem returns -EBUSY because its pages are removed from the kernel's direct map, and a mapping marked inaccessible (guest memory for confidential VMs) is rejected with -EOPNOTSUPP.

Pages that are not folios on the LRU are a harder case. For years the kernel let any driver make its pages movable by storing a pointer to its movable_operations in page->mapping, tagged with the low PAGE_MAPPING_MOVABLE bit. Linux 6.17 replaced that with a closed registry. A page type that wants to be movable provides a struct movable_operations (include/linux/migrate.h) and registers it with set_movable_ops(), and the page carries the PG_movable_ops flag—an alias of PG_uptodate, which such pages do not otherwise use—tested by page_has_movable_ops().

The three callbacks correspond to the protocol's phases. isolate_page takes the page out of the owner's own structure, as LRU isolation does for a folio. migrate_page copies the page and updates the owner's internal pointers. Memory Hot-Remove and ZONE_MOVABLE

Chapter 2 (Adding and removing memory) described the lifecycle of hotplugged memory: add_memory() creates the struct page array, online_pages() gives the pages to a zone and the buddy allocator, and removal runs in the opposite order. Adding memory is easy, because the new pages are free. Removing it is hard, because the pages to be removed are in use, and the operation succeeds only if every one of them can be moved. Memory offlining is therefore migration's most demanding caller.

Memory is added and removed in memory blocks, each one or more sparsemem sections (128 MiB on x86_64 and on ARM64 with 4 KiB pages, though x86_64 uses blocks of up to 2 GiB on large machines), and each block appears as /sys/devices/system/memory/memoryN. Writing offline to a block's state file runs offline_pages() (mm/memory_hotplug.c), whose structure explains why removal so often fails:

  1. Fence the range. The zone's per-CPU free lists and the per-CPU LRU caches are disabled, and start_isolate_page_range() (mm/page_isolation.c) changes every pageblock in the range to MIGRATE_ISOLATE. Pages freed inside the range now stay out of the allocator, and new allocations cannot land there. Before isolating a pageblock, has_unmovable_pages() checks it for pages that can never move—reserved pages and, outside ZONE_MOVABLE, any in-use page that is neither on the LRU nor a movable_ops page, such as slab, page tables, or kernel stacks. If it finds one, the offline fails at once with failure to isolate range. Memory notifiers (MEM_GOING_OFFLINE) give drivers such as balloons a chance to object or to release what they hold.
  2. Drain. The kernel repeatedly scans for in-use pages with scan_movable_pages() and passes each run to do_migrate_range(), which isolates the folios and calls migrate_pages() with MIGRATE_SYNC and MR_MEMORY_HOTPLUG. Its destination callback prefers any node other than the one losing memory. Pages already marked as hardware-poisoned are unmapped instead of moved. A folio that fails to migrate is not fatal: it may have been under writeback or briefly referenced, so the loop simply tries again. Because it checks for pending signals on every pass, an offline that can never finish can still be interrupted.
  3. Confirm and remove. Free HugeTLB pages in the range are dissolved back into base pages, and test_pages_isolated() checks that every page is now free and isolated, repeating the drain if a page was freed late or reappeared. __offline_isolated_pages() then takes the pages out of the buddy allocator, and the zone's managed and present counts, the watermarks, and if necessary the node's N_MEMORY state and the zonelists are updated.

Both checks look for the same thing: one unmovable page anywhere in the block blocks the offline. In ZONE_NORMAL such pages are everywhere, because the kernel's own allocations—slab, page tables, kernel stacks—are spread across all of it, so the isolation check usually fails at once. A page that is movable in principle can also block the drain. A long-term pinned buffer, for example, fails migration on every pass, and the offline keeps retrying until whoever started it gives up with a signal or a timeout. That is why ZONE_MOVABLE exists. Memory placed in it accepts only movable allocations (user pages and page cache), so the isolation check trusts every non-reserved page in it without looking further. Long-term GUP refuses to pin pages there and migrates them out first (the MR_LONGTERM_PIN row of Table 17-10). A block onlined to ZONE_MOVABLE can therefore almost always be offlined later. The cost is that the kernel cannot use that memory for its own data structures: a machine whose memory is mostly ZONE_MOVABLE can run out of memory for slab and page tables while gigabytes of movable memory are still free. Memory Failure and HWPoison

Server memory carries error-correcting codes. A single flipped bit is corrected on the fly and only counted. An error the code cannot correct is different: the memory controller marks the affected cache line as poisoned and raises an error when something actually consumes it, or when a patrol scrubber finds it first. Chapter 4 described the machine check as an abort (see Vector 18: Machine Check). This section follows what happens after it. The kernel's job is to work out who owns the bad frame, keep anyone from reading the corrupt data as if it were valid, and take the frame out of service for good. Linux calls this HWPoison. The central function is memory_failure() (mm/memory-failure.c), and the mark it leaves is the PG_hwpoison page flag.

How the error reaches memory_failure() depends on the architecture, but both follow the same rule: real work is never done in the exception handler itself. On x86, an uncorrected error that the CPU consumed raises #MC, and do_machine_check() (arch/x86/kernel/cpu/mce/core.c) runs on its own IST stack in a context where it cannot sleep or take locks. If the error was consumed in user mode at a usable physical address, it queues task work, kill_me_maybe(), that runs just before the task returns to user space and calls memory_failure(pfn, MF_ACTION_REQUIRED). It adds MF_MUST_KILL when the CPU reports that the interrupted instruction cannot be restarted. If the kernel itself consumed poison while copying from a user buffer, the exception-table fixup lets the copy return an error, and kill_me_never() later poisons the page without signaling anyone. Kernel consumption anywhere else is a panic. Errors found asynchronously—by the scrubber, or deferred by the hardware—reach memory_failure(pfn, 0) through the MCE decoder chain.

On ARM64 the same error arrives as a synchronous external abort (SEA). The fault_info[] table routes it to do_sea() (arch/arm64/mm/fault.c), which offers it to the firmware first through apei_claim_sea(). On servers with ACPI firmware-first error handling, the firmware has already logged a CPER record in a GHES error source, and ghes_do_memory_failure() (drivers/acpi/apei/ghes.c) does what x86 does: for a synchronous error in a user task, it adds task work, memory_failure_cb(), with MF_ACTION_REQUIRED. If the firmware does not claim the abort, do_sea() just sends SIGBUS, or dies if the abort came from the kernel. Asynchronous reports on either architecture go through memory_failure_queue(), a 16-entry per-CPU FIFO that can be filled from interrupt or NMI context and drained by a workqueue. The same queue carries the opposite case: when a page has produced too many corrected errors (the x86 correctable-error collector in drivers/ras/cec.c, or a GHES threshold record), it is queued with MF_SOFT_OFFLINE so that it is retired before it fails outright.

memory_failure() itself, shown with its delivery paths in Figure 17-12, runs under a global mutex. If vm.memory_failure_recovery has been cleared, it panics at once. Otherwise it works through five steps:

  1. Mark the frame. TestSetPageHWPoison() sets PG_hwpoison. From now on the allocator will never hand this page out again, and every path that might map or read it checks the flag. If the flag was already set, the error is a repeat: the accessing process is killed and the function returns -EHWPOISON. Pages without a normal struct page—device memory (ZONE_DEVICE) and raw PFN mappings—branch off to their own handlers, and hugetlb pages go to try_memory_failure_hugetlb().
  2. Pin and classify. get_hwpoison_page() tries to take a reference. A free page in the buddy allocator is simply removed from the free lists by take_page_off_buddy(), the best outcome. A page the handler cannot deal with—slab, page tables, other kernel memory—is left marked but otherwise ignored. Its owner will find out only if it touches the data again.
  3. Split. A large folio is split so that only the bad 4 KiB page is lost, after folio_set_has_hwpoisoned() records the problem for any later fault. If the split fails, every process that maps the folio is killed.
  4. Unmap. hwpoison_user_mappings() first collects every process that maps the page, using the same reverse map that reclaim and migration use, and then calls try_to_unmap() with TTU_HWPOISON. Each PTE is replaced by a hwpoison entry—another kind of non-present software entry, alongside the migration entries described earlier in this part. If the folio is clean file data, it can be read back from disk, so TTU_HWPOISON is dropped and the PTEs are simply cleared. The processes are then signaled if the page was dirty, if the caller insisted, or if unmapping failed. If the page was clean and every mapping is gone, no one is signaled at all: even the task that hit the error just faults the data in again from disk.
  5. Handle by page state. identify_page_state() matches the page flags, as they were saved before unmapping, against the error_states[] table and calls the matching handler. Signals are how the damage is reported to user space, and there are two kinds. The task whose access triggered the error gets SIGBUS with si_code BUS_MCEERR_AR (action required) through force_sig_mceerr(). It cannot block or ignore it, because returning to the faulting instruction would only consume the poison again. si_addr holds the virtual address, and si_addr_lsb gives the size of the lost region as a power of two: PAGE_SHIFT for a base page, more for a huge page. Other processes that map the same page get BUS_MCEERR_AO (action optional) only if they have asked to be told early, with prctl(PR_MCE_KILL, PR_MCE_KILL_SET, PR_MCE_KILL_EARLY) or the system-wide vm.memory_failure_early_kill sysctl. Everyone else is a late kill: the hwpoison entry stays in the page table, and if the process ever touches the address, do_swap_page() sees the entry and returns VM_FAULT_HWPOISON. The architecture's fault handler then turns that into the same BUS_MCEERR_AR signal. In the rare case that the kernel cannot work out at which address a process maps the page, there is nothing to put in si_addr, and that process gets SIGKILL instead. A program that never looks at the page again never notices that it was lost. Hypervisors are the main users of these signals. QEMU catches SIGBUS, decodes si_addr back to a guest-physical address, and injects a virtual machine check, so the error is contained in the guest and the guest kernel runs its own memory_failure() on the page.

After a successful recovery, x86 also calls set_mce_nospec(), which removes the page from the kernel's direct map so that not even a speculative access can touch it again. That still leaves the case where the kernel itself is copying the page when it touches poison. Migration is the obvious example, because soft offline and compaction may both copy a page that has gone bad. Since Linux 6.11 the copy step uses folio_mc_copy(), built on the machine-check-safe copy_mc_highpage(), so a poisoned source makes migrate_pages() fail that folio with -EHWPOISON instead of crashing the machine. Memory hot-remove likewise skips frames already marked poisoned, and unmaps them if they are still mapped.

Soft offline is the preventive counterpart. soft_offline_page() retires a page whose contents are still correct but whose cell has produced too many corrected errors. Nothing is lost, so no one is signaled. A free page is taken off the buddy lists. A clean page-cache page is invalidated. Any other in-use page is moved elsewhere with migrate_pages(), using MIGRATE_SYNC and MR_MEMORY_FAILURE, and the old frame is then marked PG_hwpoison. vm.enable_soft_offline (default 1) can turn it off, for example on systems where splitting huge pages to retire one base page costs more than the error risk. Administrators and tests can drive both paths: madvise() with MADV_HWPOISON or MADV_SOFT_OFFLINE (root only) injects an error into a range of the caller's own memory; hwpoison/corrupt-pfn and hwpoison/unpoison-pfn in debugfs do the same by physical frame number; and the results show up as HardwareCorrupted: in /proc/meminfo and as per-node counters under /sys/devices/system/node/nodeN/memory_failure/ (total, ignored, failed, delayed, recovered).

Summary

This chapter followed page frame reclaiming from the pressure that starts it to the last resort that ends it. The kernel overcommits memory on purpose and so must continuously recycle page frames, keeping a reserve ahead of demand so it never reaches the corner where it can neither allocate nor free. It reclaims by approximating LRU: evictable memory sits on active and inactive lists—now five lists gathered in a per-node, per-cgroup lruvec—and a cheap referenced-bit hint ages folios so that the coldest are evicted first, with an optional Multi-Gen LRU offering a more accurate, generational alternative. Reverse mapping, rebuilt around anon_vma chains and interval trees, lets the reclaimer find and tear down every mapping of a folio, and refault detection feeds back which evictions were mistakes.

Reclaim runs from three directions—background kswapd woken at a watermark, foreground direct reclaim in a stalled allocation, and cgroup-scoped reclaim when a container exceeds its limit, plus proactive reclaim asked for by userspace with nothing wrong at all—all converging on the same shrink_folio_list() pipeline, and all accounted as pressure through PSI. A recurring theme along the way is that reclaim would rather wait than spin: a thread whose node is too depleted to reclaim from sleeps in throttle_direct_reclaim() instead of scanning, and the pipeline backs off on writeback, on isolation, and on lack of progress rather than burning CPU it could leave to the threads that would actually free something. Kernel object caches shrink through the modern, scope-aware shrinker interface, chiefly the dentry and inode caches on their list_lru lists—and that path reaches further than its name suggests, since freeing an inode invalidates the page cache hanging off it, so the object shrinkers return page frames and not merely slab. When reclaim cannot keep up, the out-of-memory killer chooses a victim by memory footprint and oom_score_adj, kills everything sharing that victim's address space, and hands it to the OOM reaper so memory is recovered even from a process too wedged to die. And swapping—with clusters indexed by allocation order so large folios can be written as a unit, a swap cache that is now a flat per-cluster table rather than a borrowed address space, compression through zswap and zram, and enough solid-state awareness to pick a read-ahead policy by device type—gives anonymous memory the backing that lets it be reclaimed at all.

The same reverse-mapping walk that unmaps a folio for eviction also moves folios. migrate_pages() isolates a folio, replaces each of its PTEs with a migration entry, copies the data, and points the entries at the new frame. Callers include compaction, NUMA balancing, demotion, CMA, long-term GUP, and memory hot-remove, which depends on ZONE_MOVABLE to keep the memory it wants to unplug free of pages that cannot move. When RAM goes bad, memory_failure() uses the same unmap path to replace each mapping with a hwpoison entry, so that the task that consumed the error gets SIGBUS with BUS_MCEERR_AR and every other process finds out only if it touches the page again.

Two of the chapter's themes are worth naming separately, because they are changes of kind rather than of degree. The first is that eviction is no longer the only outcome of reclaim. On a machine with more than one speed of memory, a cold folio can be demoted to a slower tier and stay resident, and a folio that turns hot again can be promoted back, so that eviction is reserved for what is cold even by the standards of the slowest memory available. That stage sits ahead of swap allocation and unmapping in the very same pipeline, and it is the reason an anonymous page can now be reclaimed on a system with no swap at all. The second is that reclaim has acquired evidence about itself. Refault distance says whether an eviction was premature; PSI says what the stalls are costing the workload; and both are readable from user space, which is what makes it possible to drive reclaim deliberately—through a cgroup's memory.reclaim control—rather than only waiting for a watermark to be crossed. The through-line is that reclaim has become both finer-grained and more self-observing. It works on folios and per-cgroup pools rather than single pages and one global list; it measures its own cost through refault distance and PSI and steers pressure accordingly; and it recovers reliably from failure through the OOM reaper. If there is a single habit to carry away from the chapter, it is that almost every number in this subsystem is a deliberate refusal to be exact—a folio's age is two bits or four, a shared slot's reference count saturates at sixty-two, a sharing test answers "maybe," a scan gives up rather than wait for a lock, and a victim is chosen by a score nobody claims is correct. Reclaim runs on the hot path of every allocation on the machine, so an approximation it can compute now is worth more than a truth it would have to stop and derive; the art of the subsystem lies in choosing errors that are cheap to make and safe to be wrong about. With reclaim understood, the memory-management story is complete; the next chapters turn from how memory is managed to how a real filesystem puts all of it to work on disk.
