This chapter explains how User Mode processes synchronize their actions and exchange data. Chapter 5 covered synchronization too, but the actors there were kernel control paths; here they are ordinary processes, which must rely on the kernel to communicate because each runs in its own address space and cannot simply touch another's memory. Linux 2.6 offered pipes, System V IPC, and POSIX message queues. Those all still exist and this chapter covers them—but the center of gravity has shifted. The mechanisms a new Linux program reaches for today are as likely to be file descriptors—pipes, eventfd, signalfd, timerfd, memfd, pidfd—multiplexed with epoll, and the fast synchronization underneath threads and POSIX semaphores is the futex, which was still minimal in Linux 2.6.11. This chapter opens with a map of the whole landscape—the families of mechanisms and the two questions that really decide among them—then covers pipes and FIFOs, System V IPC, and POSIX IPC, before adding the futex, the file-descriptor primitives that define modern Linux IPC, and the Unix-domain socket that carries those descriptors between unrelated processes, noting at each step what carried over from Linux 2.6 and what changed by Linux 7.0.12.

One family is only partly in scope: sockets. Sockets that actually carry traffic between machines are the subject of network programming—they belong with the networking stack of Chapter 22, not with the local-process mechanisms collected here. Unix-domain sockets are a different matter. They share the socket API but never touch a protocol, a checksum, or a wire; they are purely a local mechanism, they are the transport under most service interfaces on a modern Linux system, and they are the only way one process can hand a file descriptor to another—a fact several of the arguments below depend on. They are covered in §7.

The IPC Landscape

Before the individual mechanisms, it helps to see why there are so many and how they divide up the problem. Every one of them exists because processes are isolated: the memory-management chapters showed that each process has its own address space, so one process cannot read another's variables or wait on another's lock without the kernel building a shared object between them. The kernel therefore offers a toolbox, and the right tool depends on what is being shared—a stream of bytes, a block of memory, or merely the knowledge that an event has happened.

There is a second question that matters as much as what is shared: how the handle behaves. A mechanism can be reached through a file descriptor—inherited, closed on exit, waitable—or through a free-standing name that persists on its own; it can live only as long as the processes using it or outlast them all; it can be confined to one container or visible system-wide. These properties, not just raw throughput, are usually what decides which mechanism a program picks, and they are where Linux has changed most since 2.6.11. The rest of this section sets up those two axes—what is shared and how the handle behaves—so that the detailed mechanisms in the sections that follow fall into a clear picture rather than arriving as an unordered list of system calls. It is also worth recalling that Chapter 5 already covered synchronization within the kernel; the concern here is synchronization and communication between User Mode processes, which can share nothing implicitly and so must ask the kernel for every channel.

It is worth asking at the outset why there are so many mechanisms rather than one good one, because the answer shapes everything that follows. Linux has never removed an IPC facility. Each generation added a family beside the previous one rather than in place of it, because by the time the newer design existed the older one had users whose programs could not be broken—System V IPC arrived with AT&T Unix and outlived the operating system that defined it, POSIX IPC was standardized to correct System V's naming without displacing it, the futex was invented for thread libraries that could not afford a system call per lock, and the file-descriptor primitives grew one at a time as event-driven servers found each new thing they wanted to wait on. The result is less a designed toolbox than a geological section, and reading it that way makes the oddities legible: System V's numeric identifiers are not a mistake but an artifact of a decade before "everything is a file" had been settled, and eventfd is not redundant with a pipe but a pipe with everything removed that an event-loop wakeup does not need.

The Families of IPC

The mechanisms fall into a few families by purpose. Data transfer mechanisms move bytes from one process to another through a kernel-held buffer: pipes and FIFOs carry an unstructured byte stream, while message queues (System V and POSIX) carry discrete, typed or prioritized messages. Shared memory mechanisms instead give two processes a common region of pages they both map, so that after setup they exchange data at memory speed with no system call at all—the fastest way to share bulk data, at the cost of needing separate synchronization. Synchronization mechanisms carry no payload but coordinate access: semaphores (System V and POSIX) and, underneath most user-space locking, futexes. Finally, a group of notification primitives exist only to tell a process that something happened—a counter was posted (eventfd), a signal arrived (signalfd), a timer fired (timerfd), or a process exited (pidfd). Sitting across several of these is the Unix-domain socket, which transfers data in both directions like a pipe but can also carry a file descriptor or the sender's identity, and so belongs to no single family. One thing the table cannot show is how much the ceilings have moved. The System V limits were, for two decades, the single most common piece of Linux tuning advice: every database installation guide began by telling the administrator to raise kernel.shmmax above its 32 MB default. In Linux 7.0.12 the default is ULONG_MAX less a small margin, chosen only to stop a program that reads the limit, adds to it, and writes it back from overflowing (include/uapi/linux/shm.h); MSGMNI and SEMMNI have gone from 16 and 128 to 32,000 apiece, and SEMOPM from 32 to 500. The identifier space itself is the remaining hard bound, 32,768 objects of each type, raisable to about sixteen million with the ipcmni_extend boot option. For practical purposes the System V limits are no longer something a program has to be designed around, which quietly removed one of the mechanism's real disadvantages even as newer mechanisms displaced it for other reasons.

The families are not rigid, and the choice among them is really a set of tradeoffs. The two data-transfer families differ in framing: a pipe delivers an undifferentiated byte stream in which the reader must find its own record boundaries, whereas a message queue preserves message boundaries and, in the System V case, lets a reader select by type—so a pipe suits a continuous flow while a queue suits discrete requests. Shared memory is the fastest family because after setup it needs no system call at all, but it is also the most demanding: the pages carry no boundaries, no flow control, and no built-in mutual exclusion, so shared memory is almost always paired with a synchronization mechanism—classically a semaphore, today usually a futex—to coordinate who writes when. This pairing is the norm rather than the exception; real programs combine families, using shared memory for bulk data, a semaphore or futex to guard it, and perhaps an eventfd to signal that new data is ready.

A third property separates the families in practice, and it follows from where the data sits: flow control. Every mechanism that buffers data inside the kernel must bound how much it will hold, and the bound is what makes the mechanism self-regulating. A pipe holds sixteen page-sized buffers by default (PIPE_DEF_BUFFERS), or 64 KB, and can be resized up to /proc/sys/fs/pipe-max-size, one megabyte unless an administrator raises it, with a further per-user page budget so that one process cannot claim the kernel's pipe memory by opening thousands of them. A System V queue holds MSGMNB bytes, 16 KB by default, of messages no larger than MSGMAX. A POSIX queue is stricter still: it reserves its entire worst-case size at mq_open and charges it against RLIMIT_MSGQUEUE then and there, so it can never grow into memory the creator was not entitled to. When any of these fills, the writer blocks or gets EAGAIN, and that is precisely the back pressure that lets a shell pipeline run a slow wc behind a fast cat without either an unbounded buffer or a dropped byte.

Shared memory is the exception that proves the point. A mapped region has a fixed size and no notion of full or empty at all, so there is nothing to block on and no back pressure to be had: a writer that outruns its reader simply overwrites data the reader has not looked at yet, and neither side finds out. This is the deeper reason shared memory is never used alone, beyond the obvious need for mutual exclusion—it supplies capacity but not pacing, so the partner mechanism has to supply both. Recognizing which of the two a mechanism gives you is often enough to predict the shape of the code that will have to be written around it.

The families also differ in lifetime, which often settles the choice on its own. A pipe and the notification descriptors exist only as long as some process holds them open; when the last descriptor closes, the object vanishes automatically. System V objects and named POSIX objects go the other way: they persist in the kernel until explicitly removed, surviving the death of every process that used them—convenient for a server that should find its shared segment still present after a restart, but a leak hazard when a program forgets to clean up (the reason the ipcs and ipcrm tools exist). The two persistence rules are not quite the same, and the difference shows up when a program gets it wrong. Removing a System V message queue or semaphore array takes effect at once, and processes still using it get EIDRM on their next operation; removing a shared-memory segment only marks it destroyed, and the pages survive until the last process detaches. A named POSIX object behaves like the file it is: mq_unlink or shm_unlink removes the name immediately, but the object lives on for anyone still holding a descriptor, exactly as an unlinked file does.

Linux eventually conceded that System V's persistence is more often a bug than a feature, and added a way to switch it off. Setting the kernel.shm_rmid_forced sysctl makes the kernel treat every shared-memory segment as though IPC_RMID had been issued on it at creation, so a segment is destroyed as soon as its last attachment goes away (ipc/shm.c). That is the file-descriptor lifetime rule retrofitted onto a mechanism designed without it, and it is a useful thing to know exists: on a machine where processes are killed and restarted constantly, it converts the classic System V leak into a non-problem. When a program does leak, the objects are visible under /proc/sysvipc/, which is exactly where ipcs reads them from. Keeping the axes in mind—what shape of data, whether the mechanism paces its writers, and how long the channel should live—narrows the toolbox to usually one obvious answer for a given problem.

File Descriptors, Namespaces, and Scope

Two themes cut across the families and mark the biggest changes since Linux 2.6.11. The first is the rise of the file descriptor as the universal IPC handle. System V IPC identifies its objects by a numeric identifier that is not a file descriptor, cannot be waited on with select or poll, and is not closed automatically when a process dies. Nearly every mechanism added since does the opposite: it is represented by a file descriptor, so it is inherited across fork, closed automatically on exit, passed to another process over a Unix socket, and—crucially—waited on together with every other descriptor in a single epoll loop. This is why an event-driven server can wait for a socket, a timer, a signal, a child's death, and a wakeup posted by one of its own threads in one place: they are all file descriptors. The one family that stayed outside this model is the semaphore. Neither a System V semaphore nor a POSIX one can be polled—there is no descriptor for either, and a POSIX semaphore is not even a kernel object—which is why a program that wants a semaphore-like post to wake an event loop reaches for an eventfd instead. Figure 19-1 maps the mechanisms onto their families and marks which are file descriptors.

The move to file descriptors is not cosmetic; it changes what a program can do. Because a descriptor is closed automatically when a process exits, an fd-based channel cannot leak the way a System V object can—the kernel reclaims it as part of ordinary process teardown, so there is nothing to forget to delete. Because a descriptor can be sent to an unrelated process over a Unix-domain socket (with SCM_RIGHTS), two processes can be handed a private channel by a third without sharing any name, which is the basis of the capability-style sandboxing modern desktops and browsers rely on. And because a descriptor is charged to the process's open-file limit, the kernel already accounts for it. System V's numeric identifiers have none of these properties—they are global within a namespace, survive the creating process, and must be hunted down with ipcs and removed with ipcrm when a program crashes—which is precisely why the newer mechanisms abandoned them for the file-descriptor model.

What makes this pattern so easy to repeat is that becoming a file descriptor costs the kernel almost nothing. There is no need for a filesystem, a name, or an inode anyone can look up: the anonymous-inode helpers in fs/anon_inodes.c hand back a struct file attached to an inode in a single shared internal filesystem, and the new mechanism supplies a struct file_operations with the two or three methods that actually mean something for it. In fs/eventfd.c, fs/signalfd.c, and fs/timerfd.c those are a read method that consumes the pending state, a poll that reports whether any is pending, and a release that tears the object down. That last one is the whole of the no-leak guarantee: because release runs when the final reference drops, and the final reference always drops when the process exits, the cleanup a System V program has to remember is something an fd-based program cannot forget. The poll method is the whole of the epoll integration. A new notification primitive is therefore a few hundred lines rather than a subsystem, which is a large part of why Linux acquired five of them in the years after 2.6.11.

The second cross-cutting theme is the IPC namespace. System V objects and POSIX message queues live in a namespace (struct ipc_namespace, include/linux/ipc_namespace.h) so that containers can each have their own independent sets of semaphores, message queues, and shared-memory segments, with their own limits, invisible to one another. A process created with CLONE_NEWIPC gets a fresh IPC namespace, and copy_ipcs() (ipc/namespace.c) builds a new one with empty object tables. This is the mechanism that keeps two containers' IPC from colliding even when they pick the same key, and it did not exist in Linux 2.6.11.

Two details about that structure are worth drawing out, because they explain behavior that otherwise looks impossible. The first is that one ipc_namespace covers both standards: it holds the three System V object tables and the mount of the mqueue filesystem, so entering a new IPC namespace changes which POSIX message queues exist as well as which System V objects do. The second is that the namespace carries its own sysctl tables, built by setup_ipc_sysctls() and setup_mq_sysctls(), rather than merely its own values. A process inside a container that reads /proc/sys/kernel/shmmax is not reading the host's file at all; it is reading its own namespace's, and writing it changes nothing outside. The namespace is also owned by a user namespace and counted against that user's ucounts budget, which is what allows an unprivileged process to create one by way of a user namespace while still bounding how many it can create. Joining an existing IPC namespace with setns remains privileged: it requires CAP_SYS_ADMIN in both the target namespace's user namespace and the caller's.

Finally, it is a mistake to think of IPC scope as governed by one namespace, and the mistake is easy to make because only one of them is named after IPC. Four are involved, and which applies depends entirely on how the mechanism names its objects. The System V families and POSIX message queues take the IPC namespace. FIFOs and POSIX shared-memory objects are named by paths, so they are scoped by the mount namespace—two containers with separate /dev/shm mounts are isolated, and two sharing one are not, whatever their IPC namespaces say. Abstract Unix-domain sockets are scoped by the network namespace, as §7.1 explains, even though they never touch a network. And a pidfd is meaningful across PID namespaces precisely because it does not name a number that a namespace could reinterpret. Scope, then, is the other axis to keep in mind alongside the file-descriptor question: an object is visible within one of those namespaces, to any process that can open a path, or only to processes that inherit or are passed the descriptor—and the last of those three, which needs no namespace at all, is the one the newer mechanisms chose.

Pipes and FIFOs

Pipes and FIFOs are the oldest and simplest form of Unix interprocess communication, and still the most widely used. Both provide the same thing: a unidirectional byte stream in which whatever one process writes another reads back in order, with the kernel holding the bytes in between. This is the classic producer/consumer channel, and its enduring appeal is that the synchronization comes for free—a reader that outruns the writer simply blocks until more data arrives, and a writer that outruns the reader blocks until the buffer drains, so neither side needs an explicit lock. Every shell pipeline, ls | wc -l, is two processes joined by such a channel, and the mechanism has survived unchanged in its interface since the earliest Unix while being substantially rebuilt underneath.

A pipe is anonymous: it has no name anywhere, so only processes that inherit its descriptors—a parent and the children it forks— can share it. A FIFO, or named pipe, is the same channel given a name in the filesystem, so that any two processes able to open that name can connect even with no common ancestor. The distinction is only in naming and creation; once open, both are the same in-kernel pipe object and behave identically, down to a shared implementation that differs in one small respect noted below. This section builds up from that object: first its structure, the buffer ring; then the rules that govern reading and writing it; then the extra open-time behavior that is all a FIFO really adds; and finally the splice family, which exploits the object's design to move data without copying it.

The Pipe Object

Everything in this section rests on one kernel object, so we start there. The pipe2 system call (fs/pipe.c) returns two file descriptors—fd[0] for reading and fd[1] for writing—backed by a single in-kernel pipe object; the plain pipe call is now just do_pipe2(fildes, 0). Because the endpoints are file descriptors, the classic idiom still works: a process calls pipe, then fork, and parent and child inherit the shared pipe, one writing and one reading.

A pipe is strictly half-duplex: data flows one way only, from the write end to the read end. Two processes that need to talk in both directions create two pipes, or use a socketpair, which is a bidirectional relative. The half-duplex rule is why a pipeline is set up so carefully: to build ls | wc, the shell creates a pipe, forks both commands, and in each child uses dup2 to attach the correct end to the right standard descriptor—the writer's fd[1] becomes its standard output, the reader's fd[0] becomes its standard input—then closes every original descriptor. Closing the unused ends is essential: a reader only sees end-of-file when all write descriptors are closed, so a forgotten open write end would leave the reader waiting forever. The pipe object itself has no name in any directory; it is an anonymous inode living in the internal pipefs filesystem, reachable only through the descriptors, which is exactly what makes it private to the processes that inherit it.

The kernel object is struct pipe_inode_info (include/linux/pipe_fs_i.h). Its heart is a ring of buffers: the bufs field points at an array of struct pipe_buffer slots, and two counters, head (where the next write lands) and tail (where the next read comes from), index into it modulo ring_size. Each pipe_buffer does not hold the data inline; it references a struct page (with an offset and len) plus a pointer to a pipe_buf_operations table—for an ordinary pipe, the anon_pipe_buf_ops methods (release, try_steal, get). This page-referencing design is what makes the splice family of §2.5 possible. This is the first big change from Linux 2.6.11, which used a fixed array of exactly 16 buffers: the modern ring is resizable. It starts at PIPE_DEF_BUFFERS (16) pages but can be grown or shrunk, and ring_size is always a power of two so that indexing is a cheap mask (slot & (ring_size - 1)). Figure 19-2 shows the layout.

Two details of the modern ring repay a close look. The first is that ring_size and max_usage are separate fields: the first is how many slots were allocated, the second how many a writer is allowed to fill. They are normally equal, and they diverge when a pipe is shrunk with unread data still in it, or when a notification pipe pins its own smaller budget. It is max_usage that pipe_full() tests, so that is the number a program actually feels. The second is that head and tail are not two independent words but the two halves of a union pipe_index overlaid on a single unsigned long named head_tail. That is deliberate: the predicates pipe_readable() and pipe_writable(), which a waiting process evaluates without holding the pipe lock, can sample both indices in one READ_ONCE and so can never see a head from before an update paired with a tail from after it. Packing the pair into one word is what makes the lockless wait condition correct.

Pipes have no name in the filesystem; the object lives in a special internal filesystem, pipefs, mounted only inside the kernel (init_pipe_fs, get_pipe_inode). Because pipe memory is a kernel resource a program could try to exhaust, the ring size is bounded and charged to the user: the pipe-max-size sysctl caps a single pipe (default 1 MiB), and pipe-user-pages-soft/-hard limit the total pages one user's pipes may pin. A process can resize a pipe within those limits through the F_SETPIPE_SZ and F_GETPIPE_SZ operations of fcntl, which round_pipe_size rounds up to a power-of-two number of pages—useful for a high-throughput pipeline that would otherwise block often on a small buffer. Raising a pipe above pipe-max-size, or past the hard per-user page budget, requires CAP_SYS_RESOURCE.

One behavior of the ring is easy to miss and explains a great deal about how pipes perform: a buffer is not necessarily one write. An ordinary write marks the buffer it fills with PIPE_BUF_FLAG_CAN_MERGE, and the next write will, if the last buffer has room, copy its bytes into the slack after the data already there rather than consuming a fresh slot. This write merging is why a program that writes a few bytes at a time does not exhaust a sixteen-slot ring after sixteen calls. The implementation is cleverer than it first appears: the merge step copies only the sub-page remainder of the incoming write, total_len & (PAGE_SIZE - 1), so that whatever is left of a large write starts at a page boundary and lands one page per slot. Two things suppress merging, and both are deliberate. A packet-mode write sets PIPE_BUF_FLAG_PACKET instead of CAN_MERGE, which is precisely the mechanism that keeps packets distinct. And fs/splice.c clears CAN_MERGE on every buffer it splices in, because those pages may belong to a page cache or to another process and must never be written into behind their owner's back.

Reading and Writing a Pipe

Reading and writing a pipe is governed by the producer/consumer rules the ring implies, implemented in anon_pipe_read and anon_pipe_write (fs/pipe.c). A reader that finds the pipe empty blocks—but only if there is still at least one writer (pipe->writers > 0); if the last writer has closed, an empty pipe returns 0, the end-of-file indication. This is why a shell pipeline's reader sees EOF exactly when the writer exits. Symmetrically, a writer that fills the ring blocks until a reader drains a buffer, and a write to a pipe with no readers left raises SIGPIPE (and returns EPIPE). Either side can opt out of blocking with O_NONBLOCK, which turns a would-be wait into EAGAIN. When one side makes progress it wakes the other with wake_up_interruptible_sync_poll, a targeted wakeup that also notifies any epoll watcher.

Those wakeups are issued with more care than the description suggests, because on a busy pipeline they are the dominant cost. A reader wakes writers only if the pipe was full when it started and is no longer full now; a writer wakes readers only if the pipe was empty when it started. In the common case where both ends are keeping pace, neither side is ever blocked and no wakeup is sent at all. The exception is a pipe someone is watching with epoll, which the kernel notices by setting poll_usage in pipe_inode_info the first time pipe_poll runs on it. An epoll watcher has to be told that data arrived even though the pipe was not empty, so for those pipes the writer wakes unconditionally. All the wakeups are also issued after the pipe mutex is dropped, so the woken process does not immediately block on the lock its waker still holds. One further subtlety concerns SIGPIPE: a write to a readerless pipe normally raises it, but a caller that sets IOCB_NOSIGNAL gets the EPIPE return with no signal, which is what lets io_uring report the condition to a submitter that never issued the write on the thread that would receive the signal.

The pipe honors one atomicity guarantee that programs rely on: a write of no more than PIPE_BUF bytes (4096 on Linux) is atomic—its bytes are never interleaved with those of a concurrent writer. Larger writes may be split and interleaved. This is what lets several processes write short records to one pipe (a classic logging pattern) without a lock. Two flag-driven variants extend the basic behavior: opening the write end with O_DIRECT puts the pipe in packet mode (PIPE_BUF_FLAG_PACKET), where each write becomes a distinct packet that a read returns without merging; and the notification-pipe feature (O_NOTIFICATION_PIPE, which is O_EXCL reused as a pipe2 flag, built on the same ring via kernel/watch_queue.c) lets the kernel post event records into a pipe a process then reads—a modern use of the pipe as a kernel-to-user event channel. Every pipe is also pollable through pipe_poll, so it drops naturally into an epoll event loop alongside sockets and the notification descriptors of §6.

Packet mode is worth a second look, because its read semantics are not the stream semantics the rest of the section describes. A packet buffer is never merged with the next write, so each write is a distinct record—but a read smaller than the record does not leave the remainder for the next read. It consumes the whole buffer and discards what did not fit, exactly as a datagram socket does. A program using O_DIRECT pipes must therefore size its reads for the largest record it can receive, or lose data silently. The notification pipes built on kernel/watch_queue.c take the opposite approach to the same problem: their buffers carry PIPE_BUF_FLAG_WHOLE, and a read too small for the pending record returns ENOBUFS rather than truncating it. Notification pipes are also read-only to user space—only the kernel may post to them, and an attempted write fails with EXDEV—and when the ring overflows the kernel sets note_loss so that the next read is prefixed with an explicit message-lost record. A watcher is never silently lied to about having seen everything.

Two consequences follow from a pipe being a raw byte stream rather than a message channel. First, it preserves no record boundaries: a reader asking for N bytes receives whatever is available up to N, so several small writes may be returned by one read, or one large write split across several reads. A program that needs discrete records must frame them itself—with a length prefix or a delimiter—which is exactly the service a message queue provides and a pipe does not. Second, the default response to writing to a pipe whose read end is closed is not an error return but the SIGPIPE signal, whose default action terminates the writer. That is convenient in a shell pipeline—when head has read enough and closes the pipe, the upstream producer is killed rather than running on—but a hazard in a long-lived server, which therefore usually ignores SIGPIPE and handles the EPIPE error return from write instead.

Creating and Opening a FIFO

The data in a FIFO never travels through the filesystem; it flows through the very same pipe object just described, and once the channel is open the two mechanisms behave alike in everything a program can observe. A FIFO's whole character is therefore concentrated in how it is created and opened, which is what this section covers. A FIFO is created with the mkfifo command or library call, which makes a special inode of type S_IFIFO—the same node type the mknod call can produce. This inode takes a name in a directory but holds no data blocks of its own; it is purely a marker that tells the kernel "opening this path yields a pipe." The node is therefore tiny and persistent: it stays in the directory after every process using it has exited, and it is removed only by unlink (for example, the rm command), exactly like an ordinary file. Nothing is buffered in the node itself—it is only a rendezvous name.

Having a real inode buys a FIFO one thing an anonymous pipe cannot have: permissions. The node carries an owner, a group, and a mode like any other file, so a service can publish a FIFO that only members of one group may write, and the ordinary open permission check does the enforcement before any pipe machinery is reached. An anonymous pipe has no such control and needs none—the only way to reach it is to be handed the descriptor. What the inode does not buy is storage. The pipe_inode_info is allocated lazily on the first open and hung off inode->i_pipe, and put_pipe_info() frees it when the last opener closes. Bytes still sitting in the ring at that moment are discarded with it. A FIFO is a rendezvous with a persistent name, never a persistent mailbox: nothing written before a reader arrives will be waiting for one that arrives later, because there is no FIFO object in memory in between.

Opening a FIFO is where its distinctive behavior lives, in fifo_open (fs/pipe.c). The guiding rule is that a FIFO joins two independently started programs, so by default an open blocks until both ends are present: a process opening the FIFO read-only waits until some process opens it for writing, and a process opening it write-only waits until a reader appears. This blocking is a deliberate rendezvous—it guarantees that neither side begins transferring data before the other is ready, so a writer cannot push bytes into a FIFO that no one is reading, and a reader does not immediately see end-of-file merely because it happened to open first. The two escapes from blocking cover the cases where a program cannot wait. Passing O_NONBLOCK makes a read-open succeed at once even with no writer present—useful for a server that wants to open its FIFO and then wait for clients with poll rather than blocking in open—while a nonblocking write-open with no reader fails with ENXIO rather than waiting, so a client can detect that no service is listening. Opening with O_RDWR is a third escape, non-portable but common on Linux: it never blocks, because the descriptor is simultaneously a reader and a writer, so the rendezvous condition is trivially met. Internally the rendezvous is implemented by wait_for_partner and wake_up_partner, which park an opener until the counterpart increments the FIFO's reader or writer count and wakes it.

The counters those functions watch are not the ones that count current openers. pipe_inode_info carries both readers and writers, which rise and fall, and r_counter and w_counter, which only ever increase. wait_for_partner samples the relevant monotonic counter and sleeps until its value changes, not until the live count is nonzero, and that choice closes a race the obvious implementation would lose: a writer that opens the FIFO and closes it again before the sleeping reader is scheduled would leave writers back at zero, and a reader testing the live count would go back to sleep having missed its partner entirely. Testing a generation counter cannot miss it. The wait is interruptible, so a signal makes the open itself return ERESTARTSYS—a blocked FIFO open is not an uninterruptible state, and a program can be killed out of one.

Two smaller details of fifo_open are worth knowing because they surprise people. The first is that a nonblocking read-open, which succeeds with no writer present, records the current w_counter in the file. Until that counter moves—that is, until some writer has actually appeared—poll suppresses EPOLLHUP on the descriptor. Without this, a server that opened its FIFO early would see a spurious hangup immediately and conclude its clients had all vanished before any had arrived. The second is that fifo_open calls stream_open, which marks the file non-seekable and tells the VFS not to take the file-position lock. A FIFO has no position to protect, and skipping the lock means two threads sharing one descriptor do not serialize against each other in the VFS before they reach the pipe mutex.

Using a FIFO

Once open, a FIFO is a pipe in very nearly every respect: it blocks a reader on an empty buffer and a writer on a full one, delivers end-of-file when the last writer closes, and preserves the same PIPE_BUF atomicity for writes up to 4096 bytes. The single exception is the one mentioned in §2.1, and it is worth stating plainly. Linux 7.0.12 uses two file_operations tables, not one: pipefifo_fops for FIFOs and pipeanon_fops for anonymous pipes. They share pipe_poll, pipe_release, and the same read and write machinery, and the only difference is that the FIFO's methods wrap anon_pipe_read and anon_pipe_write in calls to file_accessed() and file_update_time(). A FIFO has a real inode in a real filesystem, so its access and modification times have to be maintained; an anonymous pipe's pipefs inode is visible to nobody, so the kernel does not pay for timestamps it could never be asked about. The write-side update is even guarded by sb_start_write_trylock(), so a FIFO on a frozen filesystem still transfers data and merely skips the timestamp. Because the channel has a well-known name, its natural use is letting an unrelated client hand work to a long-running service: the service opens a fixed path such as /run/myservice.fifo for reading, and any client opens the same path for writing. More than two processes may hold a FIFO open at once— several writers, and even several readers—and their bytes interleave in arrival order, with PIPE_BUF atomicity ensuring that each short write from each client arrives intact rather than shredded across others, so many clients can feed one service through a single FIFO without a lock. The one lasting difference from an anonymous pipe is cleanup: the FIFO's name outlives the processes, so a program that creates a private FIFO is responsible for unlinking it when done, or it will linger in the directory indefinitely.

Splice, Tee, and Zero-Copy

Because a pipe buffer references a page rather than owning a private copy of the data, the kernel can move data through a pipe without copying it. The splice family (fs/splice.c) exposes that capability to user space. splice moves data between a file and a pipe by transferring page references: on the read side, splice_to_pipe links a file's page-cache pages directly into pipe buffers; on the write side, iter_file_splice_write hands those same pages to the destination file. No bytes are copied into or out of user space, which is why splice is the foundation of high-throughput data movement such as a web server sending a file to a socket. The pipe is not incidental here but the mandatory conduit—it is the object whose buffers hold the page references being shuffled—so moving data from one file straight to another goes file → pipe → file as two splices. Flags tune the transfer: SPLICE_F_NONBLOCK makes it return rather than wait, SPLICE_F_MORE hints that further data will follow (so a socket can hold back a partial network segment), and SPLICE_F_GIFT lets a vmsplice caller donate its pages outright. SPLICE_F_MOVE is the interesting one, because it does nothing. It was meant to ask that pages be moved rather than copied, was found to be able to corrupt data, and has been ignored by the generic splice paths ever since; the only code in the tree that still reads it is the FUSE device, which gives it a meaning of its own. Programs still pass it—the kernel's own selftests do—and it has no effect. It is a good reminder that a flag defined in a header is not a feature. The payoff is the elimination of the two copies that a naive read into a user buffer followed by a write would incur; on a server streaming files to the network, removing that traffic across the user/kernel boundary is a substantial saving, which is why splice and sendfile underlie high-performance file serving.

Two relatives round out the family. tee duplicates data from one pipe to another without consuming it—both pipes end up referencing the same pages—so a stream can be forked, for example to log it and process it at once. vmsplice goes the other way, mapping a range of a process's own memory into a pipe; with SPLICE_F_GIFT the process donates the pages outright. And the familiar sendfile, which copies between two descriptors, is now implemented on top of this machinery: do_sendfile routes through splice_direct_to_actor using a hidden per-task pipe as the intermediary. The unifying idea is that the pipe is not just a channel between two processes but the kernel's general conduit for moving pages by reference—a role the fixed 16-buffer pipe of Linux 2.6.11 could not play.

The internal pipe behind sendfile and copy_file_range is not created per call. splice_direct_to_actor caches one on the task itself, in current->splice_pipe, allocating it the first time and reusing it thereafter, so a server issuing a sendfile per request pays the setup once for the life of the thread. The pipe never becomes visible: no descriptor names it, and the loop empties it before returning. What actually happens inside it depends on the destination. A socket that can hold a page reference keeps one, and no copy occurs; a destination that needs to own its pages calls pipe_buf_try_steal, which for an anonymous pipe buffer succeeds only when the page is not shared, and otherwise falls back to a copy. Zero-copy is therefore a best effort rather than a guarantee, which is why splice reports how many bytes it moved and not how it moved them.

Passing pages by reference also has a sharp edge, and it is exactly the one the design implies: the data is not snapshotted. If a process vmsplices its own memory into a pipe and then modifies that memory before the reader has consumed it, the reader sees the modification, because both are looking at the same page. With SPLICE_F_GIFT the situation is worse, since the process has given the pages away and must not touch them again at all. The same property in reverse is what makes splicing from a file fast—the pipe holds the page-cache page itself, not a copy of it—and it is why fs/splice.c clears PIPE_BUF_FLAG_CAN_MERGE on everything it inserts. A page that belongs to someone else is a page nothing may append to.

System V IPC

System V IPC is the classic Unix interprocess toolkit, introduced in AT&T's System V Unix (with roots in an earlier variant called Columbus Unix) and bundling three mechanisms—semaphores, message queues, and shared memory—under one shared design. For two decades it was the portable way for unrelated Unix processes to synchronize and share data, and it remains widely used by long-lived software: databases and enterprise servers still reach for System V shared memory and semaphores, and a great deal of existing code depends on them, so the mechanisms endure even as newer designs surpass them.

System V IPC also shows its age, and understanding why is the key to the whole section. Its objects are kernel-global within a namespace, named by a numeric key and identifier rather than a file descriptor, and they persist beyond the process that created them—so they are neither inherited, nor closed on exit, nor waitable with poll, and a program that forgets to delete one leaves it lingering until an administrator removes it with ipcrm. These traits are exactly the ones the file-descriptor mechanisms of §5 and §6 were designed to avoid. This section first describes the common framework the three mechanisms share—how a key becomes an identifier, how permissions and namespaces work—and then treats semaphores, message queues, and shared memory in turn.

Keys, Identifiers, and Namespaces

The naming and permission framework the three mechanisms share is worth understanding once, because all three use it identically. A program names a resource by an integer key (often derived from a pathname with ftok), and calls semget, msgget, or shmget with that key and flags. The kernel translates the key into an internal identifier, the small integer that later semop, msgsnd, or shmat calls use to reach the object. Two steps, then, and each answers a different need: the key is the agreed name two unrelated programs can compute independently, while the identifier is the efficient handle the kernel actually looks up. The key deserves a closer look, because it is how unrelated processes find the same object. Programs that share source can agree on a fixed key number, but the portable convention is to derive one from a file both processes can name, with ftok, which hashes a pathname and a project byte into a key. The special key IPC_PRIVATE asks instead for a brand-new object with no key at all, suitable when the identifier will be shared some other way—for example, passed to a child across fork. The *get calls combine the key with flags that mirror open: IPC_CREAT creates the object if the key is not yet bound, and IPC_CREAT | IPC_EXCL insists on creating it, failing with EEXIST if another process already did—the standard idiom for deciding who is the creator. Every object also carries a permission mode in the low nine bits, checked by ipcperms against the caller's credentials just as file permissions are, though only the read and write bits are meaningful for IPC. Finally, the *ctl calls administer an object: IPC_STAT reads its metadata, IPC_SET changes its owner or mode, and IPC_RMID marks it for destruction—the only way a System V object is ever removed.

Two of those control commands have acquired variants for the benefit of the tools that inspect IPC. SEM_STAT, MSG_STAT, and SHM_STAT exist so that ipcs can walk the object tables by array index rather than by identifier, but each one applies the ordinary read-permission check, so a listing tool running as an unprivileged user simply lost every object it could not read. The newer SEM_STAT_ANY, MSG_STAT_ANY, and SHM_STAT_ANY skip the ipcperms check entirely, record the access with audit_ipc_obj, and leave the decision to the security module—which is the right shape for the problem, since whether an administrator may enumerate objects is a policy question rather than a file-permission one. None of the three existed in Linux 2.6.11.

Both halves of that scheme have sharp edges. ftok is not a hash of the pathname at all: it stats the file and folds the low sixteen bits of the inode number, the low eight bits of the device minor number, and the project byte into a 32-bit key. Two unrelated files can therefore collide, and—more often the real problem—deleting and recreating the file a program uses as its ftok argument changes the key, so an upgrade that rewrites a configuration file in place with a new inode silently moves the whole application to a different IPC object. On the permission side, kern_ipc_perm records two identities rather than one: the creator (cuid, cgid) and the current owner (uid, gid). The mode bits govern ordinary use, but IPC_SET and IPC_RMID are restricted to the owner, the creator, or a process holding CAP_SYS_ADMIN—so giving an object's ownership away does not give away the creator's standing right to destroy it.

Under the surface, the common code lives in ipc/util.c, and its data structures reveal a substantial modernization since Linux 2.6.11. Each resource type keeps a struct ipc_ids (include/linux/ipc_namespace.h) holding two lookup structures: an IDR (ipcs_idr, a radix-tree-based integer-to-pointer map) that resolves an identifier to its object, and a resizable hash table (key_ht, an rhashtable) that resolves a key to its object for the *get calls. Linux 2.6.11 used a hand-rolled resizable array, ipc_id_ary; that is gone, replaced by these general kernel data structures. Every IPC object begins with an embedded struct kern_ipc_perm (include/linux/ipc.h) carrying the key, owner and creator credentials, mode bits, a sequence number, and the object's own spinlock and refcount—so the common code can manipulate any object through its kern_ipc_perm and recover the full structure with container_of. Figure 19-4 shows how the pieces connect.

This structure explains the framework's two subtle behaviors. The identifier returned to user space is not the raw slot index but a 31-bit value composed as (seq << shift) + index, so that a program holding an old identifier for a removed-and-recreated object is rejected rather than silently misdirected. How the two halves move is worth being precise about, because the obvious guess is wrong. Indices come from idr_alloc_cyclic over a window of max(in_use * 3 / 2, ipc_min_cycle) slots, so the allocator deliberately walks forward rather than reusing the lowest free slot, and an index is not issued again until it has cycled all the way around. The sequence number is kept per resource type, not per slot, and is bumped only when that cycle wraps. Two objects created within one cycle therefore share a sequence number; what separates them is their indices, and what separates a stale identifier from a live one at the same index is that a wrap must have happened in between. The split between the two fields is also where the ipcmni_extend option mentioned in §1 shows its price: by default an identifier is 15 bits of index and 16 bits of sequence, but under the extension it becomes 24 bits of index and just 7 of sequence, dropping the number of distinguishable generations from 65,536 to 128. A larger identifier space is bought with weaker stale-identifier detection. One smaller behavior belongs here too: /proc/sys/kernel/sem_next_id, and its msg and shm siblings, pin the identifier the next object created will receive—a facility that exists so a checkpoint/restore tool can bring a process back holding the identifiers it had before. And the locking is now fine-grained: a lookup takes rcu_read_lock, finds the object in the IDR, and takes that object's own spinlock (ipc_lock_object), so operations on unrelated semaphores or queues no longer serialize on one global lock as they did in Linux 2.6.11. Creation and destruction serialize per resource type on ids->rwsem, and freed objects are released through call_rcu so a concurrent reader never dereferences freed memory. There is also a legacy ipc multiplexer system call (ipc/syscall.c) that dispatches all of these by a subcommand number—a relic of early Linux that some architectures still use, though the individual calls are now the norm.

Semaphores

A System V semaphore resource is not a single counter but an array of them, represented by struct sem_array (ipc/sem.c) with its per-semaphore struct sem entries. A process operates on them with semop, which takes a list of operations—each adding to, subtracting from, or waiting for zero on one semaphore of the array—and applies the whole list atomically: either every operation can proceed and all are applied, or the caller blocks with none applied, so a process can acquire several resources at once without deadlocking halfway. perform_atomic_semop is the routine that tests and applies a batch; if it cannot proceed, the request is queued on the array's pending_alter or pending_const list until another operation makes it satisfiable. semtimedop adds a timeout, so a process can bound how long it waits; it is older than it looks, having already been present in Linux 2.6.11, and today it is the real implementation—semop is a thin wrapper that passes a null timeout.

Each element of the operation list is a struct sembuf naming one semaphore of the array (sem_num), an operation (sem_op), and flags (sem_flg). A positive sem_op adds to the semaphore—releasing that many units of a resource; a negative sem_op subtracts, blocking if the semaphore would go below zero until enough is released; and a zero sem_op is a wait-for-zero, blocking until the semaphore is exactly zero. Those three forms cover the classic uses: a counting semaphore initialized to N guards a pool of N interchangeable resources, a binary semaphore (0 or 1) is a mutex, and wait-for-zero lets a process block until a count of outstanding work drains. This split is also why each semaphore keeps two pending lists internally—pending_alter for operations that change the value and pending_const for wait-for-zero operations that only read it—so a value change need only re-examine the operations that its new value could newly satisfy. The semctl call supplies the out-of-band operations a program needs to manage the array: SETVAL and SETALL initialize values, GETVAL and GETALL read them, and GETNCNT/GETZCNT report how many processes are waiting. GETPID returns the process that last operated on a semaphore, and IPC_STAT reports sem_otime, the time of the last semop—between them the only forensic trail a stuck semaphore leaves.

Two boundaries constrain what an operation list may ask for. A semaphore's value is capped at SEMVMX, 32,767, and an operation whose result would exceed it fails the whole list with ERANGE rather than saturating. Separately, an operation carrying SEM_UNDO must keep the accumulated undo adjustment within the same range, because the adjustment is stored as a short; a program that repeatedly acquires without releasing can therefore be refused not because the semaphore is exhausted but because its undo bookkeeping would overflow. There is also a size boundary in the implementation rather than the interface: lists of up to SEMOPM_FAST (64) operations are copied into an array on the kernel stack, and only longer ones take an allocation—which is why the great majority of real semop calls, which name one or two semaphores, allocate nothing at all.

Two aspects received major reworking after Linux 2.6.11. The first is locking. A single global lock per array would serialize every operation on a busy array, so sem.c now uses fine-grained locking: an operation on a single semaphore takes only that semaphore's own spinlock (the fast path), while an operation spanning several semaphores of the array takes the whole-array lock and sets use_global_lock to force simple operations to wait. Switching between the two modes is not free, so the kernel damps it: after a complex operation completes, use_global_lock is set to USE_GLOBAL_LOCK_HYSTERESIS (10) and counts down one per simple operation, keeping the array in global-lock mode for a short while rather than flapping between regimes on a workload that mixes the two. The pending-operation lists are doubled for the same reason: every semaphore has its own pending_alter and pending_const lists and the array has a pair of its own, and merge_queues folds the per-semaphore lists into the array's when a complex operation appears, while unmerge_queues splits them back out when complex_count returns to zero. That is what preserves first-in, first-out wakeup order across a mix of simple and complex waiters without forcing every value change to walk every waiter. This lets independent single-semaphore operations on the same array run in parallel, a large scalability gain for programs that use big semaphore arrays.

The second reworked aspect is the undo mechanism. A process can flag an operation with SEM_UNDO, and the kernel records the reverse adjustment in a struct sem_undo; if the process dies while holding the semaphore, exit_sem replays the undo so the resource is released rather than left permanently locked by a crashed program. Undo is what makes System V semaphores usable as robust locks between processes that might crash.

Who exactly owns that undo state is easy to get wrong, and it matters. A sem_undo is not per process and per semaphore but per undo list and per array, and the list—a sem_undo_list—is shared by every task cloned with CLONE_SYSVSEM, which is precisely what the threads of one program are. All the threads of a process therefore share one set of adjustments, so a thread that exits does not trigger any undo at all; only when the last sharer of the list goes away is exit_sem run. That is almost always what a threaded program wants, and it is why a crashed worker thread does not mysteriously release a lock its siblings still hold. Each sem_undo is threaded onto two lists at once, one per owning process and one per semaphore array, because both directions have to be walked: process exit must find every array the process touched, and IPC_RMID must find and invalidate every undo record referring to the array being destroyed.

Message Queues

A System V message queue (struct msg_queue, ipc/msg.c) is a kernel-held list of typed messages. A sender calls msgsnd with a message whose first field is a positive type, and a receiver calls msgrcv selecting by type: a positive msgtyp asks for the first message of exactly that type, a negative one for the first message of the lowest type ≤ its absolute value, and zero for the first message regardless of type. This type selectivity—one queue serving as several logical channels distinguished by type—is the feature that distinguishes System V messages from a plain byte pipe. Flags refine it: MSG_EXCEPT inverts the match, MSG_NOERROR truncates an over-large message instead of failing, and MSG_COPY peeks a message without removing it. That last one is not a general-purpose facility: it is compiled in only under CONFIG_CHECKPOINT_RESTORE, returns ENOSYS otherwise, and reinterprets msgtyp as an index into the queue rather than a type, because its purpose is to let a checkpointing tool walk a queue and copy out every message without disturbing it. Ordinary code should not use it.

Each message is a struct msg_msg (include/linux/msg.h) whose body, if larger than a page, is chained across msg_msgseg segments—so a message is not limited to one page. A queue has a capacity in bytes (q_qbytes); a msgsnd that would exceed it blocks until a receiver drains space, unless IPC_NOWAIT is set, and a msgrcv on an empty queue blocks likewise. The kernel optimizes the common rendezvous with pipelined send: if a receiver is already waiting for the type being sent, pipelined_send hands the message straight to it and wakes it, skipping insertion into the queue entirely. Per-namespace limits (msg_ctlmax, msg_ctlmnb, msg_ctlmni) bound message size, per-queue bytes, and queue count.

The segmenting deserves a number, because it explains the queue's memory behavior. The first chunk of a message shares a page with its msg_msg header, so it holds PAGE_SIZE less that header; each further segment holds PAGE_SIZE less a small msg_msgseg link. A message is thus a chain of single pages rather than one contiguous allocation, which is why the 8 KB default ceiling on message size is a policy choice and not a structural limit—nothing in the code would break at a megabyte. It also means a queue's memory is allocated a page at a time and charged to the sending process's memory cgroup, through SLAB_ACCOUNT on the header and GFP_KERNEL_ACCOUNT on the segments. The allocation is also deliberately segregated: init_msg_buckets() gives msg_msg its own set of slab buckets rather than letting it share the general-purpose kmalloc caches. That is a hardening measure with a specific history. A message body is attacker-sized, attacker-filled, and kept alive for exactly as long as the attacker likes, which made msg_msg one of the most convenient heap-grooming primitives in the kernel; private buckets keep it away from the objects an exploit would want to land beside.

The send and receive paths share a discipline with the pipe code of §2: the copy in from user space happens before the queue lock is taken, and every wakeup is accumulated in a wake_q and delivered after the lock is dropped. Pipelined send takes this one step further. Rather than waking a receiver and letting it re-acquire the lock to find its message, the sender writes the message pointer into the waiting receiver's msg_receiver structure and publishes it with a release barrier; the receiver wakes, reads the pointer with the matching acquire, and returns without touching the queue at all. The message never enters the queue, and the handoff costs one wakeup rather than a wakeup plus a lock round trip.

Laid out for the programmer, a message is simply a positive long type followed by an arbitrary payload—the familiar { long mtype; char mtext[]; } shape. The type is what gives a single queue the flexibility of many channels: a server can read type 1 for incoming requests while each client waits for replies tagged with its own process id as the type, so one queue routes a whole request/response protocol. Within any one type, messages are delivered in first-in, first-out order. Compared with a pipe, a message queue therefore adds three things a byte stream lacks—message boundaries (each msgrcv returns exactly one message), selective receipt by type, and independence from the processes using it (the queue and its unread messages persist until removed). The costs are the System V costs: a queue cannot be polled, its total size is capped by the namespace limits, and it must be cleaned up explicitly.

Shared Memory

System V shared memory is the fastest IPC because, once set up, it involves no system calls at all: two processes map the same pages and read and write them as ordinary memory. A process creates or looks up a segment with shmget and then attaches it with shmat, which returns a pointer into the process's address space; shmdt detaches it. The kernel object is struct shmid_kernel (ipc/shm.c), and here one implementation detail is important: the segment is backed by a real file. newseg creates an unlinked file in the kernel's internal tmpfs instance (shmem_kernel_file_setup), or in hugetlbfs when SHM_HUGETLB is requested, and shmat simply maps that file into the process with do_mmap, creating a new VMA. The pages are then demand-faulted from the shmem file through shm_fault—so two processes attaching the same segment map the same shmem pages and genuinely share them, rather than the segment being a special dummy-page region.

It is worth seeing how thin that layer is. shm_vm_ops defines fault, may_split, pagesize, and the NUMA policy hooks, and every one of them does nothing but forward to the corresponding method of the underlying shmem or hugetlbfs mapping, which shm_file_data keeps a pointer to. The System V layer interposes on only two operations for its own purposes, open and close, and it interposes on those because they are how the attach count is maintained. That is a point the interface hides: shm_nattch is not incremented by shmat and decremented by shmdt, it is maintained by the VMA callbacks. A fork duplicates the attached region and the kernel calls shm_open on the copy, so the child counts as an attachment without having called shmat; an exit or a plain munmap of the region calls shm_close and decrements it. The count tracks mappings, not calls, which is exactly what a deferred destruction rule needs it to mean.

The backing file also leaks pleasantly into the interfaces an administrator uses. newseg names it SYSV followed by the key in hexadecimal, which is why a System V segment shows up in /proc/<pid>/maps as something like /SYSV0000162e (deleted)—deleted because the file was never linked into any directory. Better still, newseg then overwrites the inode number of that file with the IPC identifier, with a comment in the source warning that process tools depend on it. The inode number a program sees for a shared segment is its shmid, which is what lets ipcs output and /proc/<pid>/maps be correlated at all. A small hack, decades old, and load-bearing.

Backing the segment with a shmem file unifies shared memory with the page cache and swapping machinery of the earlier chapters: a shared segment's pages can be swapped out under pressure like any other anonymous-tmpfs pages, and SHM_LOCK exists to pin them when that is not wanted. Lifetime follows the System V convention rather than the file convention: a segment persists until it is explicitly removed with IPC_RMID, and even then, if processes still have it attached (shm_nattch > 0), destruction is deferred until the last detach—shm_destroy runs when the attach count reaches zero on a segment marked for removal. The mark itself is visible: IPC_RMID on an attached segment sets SHM_DEST in the mode word, which is the dest flag ipcs prints, so an administrator can tell a segment that is merely waiting for its last user from one that has been forgotten. The same call resets the object's key to IPC_PRIVATE and drops it from the key hash (ipc_set_key_private), so the key becomes available for a new segment at once even while the old pages are still mapped—a restarted server gets a fresh segment rather than inheriting the dying one. This is why a shared-memory segment can outlive its creator, and why a leaked segment lingers (visible in ipcs) until explicitly deleted. The optional shm_rmid_forced namespace setting forces segments to be destroyed on last detach regardless, closing that leak in container environments.

The shmat call gives some control over how the segment is mapped. Passed a null address it lets the kernel choose where to place the segment—the usual and most portable choice—while a supplied address with SHM_RND is rounded down to a SHMLBA boundary the hardware requires. SHM_RDONLY maps the segment read-only (useful for a publisher/subscriber split where consumers may not write), SHM_EXEC permits executing code from it, and SHM_REMAP replaces any existing mapping at the target address. The essential point, though, is what shared memory does not provide: the shared pages carry no boundaries, no flow control, and no mutual exclusion, so shared memory is almost never used alone. The standard pattern is to pair it with a synchronization mechanism—historically a System V semaphore, today often a futex placed inside the shared region itself—so one process signals another that data is ready and readers and writers do not collide. Shared memory supplies the fast bulk channel; something else must supply the coordination. Rounding out the control surface, shmctl offers SHM_LOCK and SHM_UNLOCK to pin a segment against swapping and SHM_INFO/SHM_STAT to report system-wide usage.

POSIX IPC

The System V mechanisms were standardized before Unix settled on the "everything is a file" philosophy, and their unpollable numeric identifiers show it. The POSIX standard defined a second generation of the same three facilities—message queues, semaphores, and shared memory—that keeps the capabilities but fits them to the file model. A POSIX object is named by a pathname that looks like a file path (a string beginning with a slash, such as /myqueue) and is handled through a file descriptor, so it inherits across fork, closes automatically on exit, can be passed to another process over a socket, and—for message queues—waited on with poll and epoll. Removal is by an unlink-style call rather than a control command, and lifetime follows the same persistence rule as a file: the object survives until its name is unlinked and the last descriptor closes. There is no shm_open system call, no sem_open, no sem_wait, and no sem_post. Those four are library functions built from calls the kernel already had, and that is not an implementation detail to be corrected later but the design: the POSIX interfaces were specified in terms of files and memory, and once Linux had tmpfs and futexes there was nothing left for a dedicated subsystem to do. The practical consequence is that two of the three facilities in this section are invisible to the kernel as IPC. They leave no entry in /proc/sysvipc, nothing for ipcs to print, and no object for an administrator to remove—only files, which rm handles.

Message Queues

A POSIX message queue is opened with mq_open, which returns a descriptor (an mqd_t, really a file descriptor) referring to an inode in a dedicated kernel filesystem, mqueue (ipc/mqueue.c), mountable at /dev/mqueue so queues are even visible with ls. Because the handle is a descriptor, a queue can be waited on with poll, select, or epoll—something a System V queue cannot do—so it drops into an event loop naturally. Messages are sent and received with mq_timedsend and mq_timedreceive, both carrying an explicit priority and an optional timeout. The defining behavior is that delivery is ordered strictly by priority: a receive always returns the highest-priority message currently queued, and among equal priorities the oldest. The kernel implements this with a red-black tree (struct posix_msg_tree_node) keyed by priority, each node holding a list of same-priority messages, with a cached pointer to the rightmost (highest) node so the next message to deliver is found in constant time. Figure 19-5 shows the structure.

The tree is built to make sending cheap and, more importantly, unable to fail halfway. A priority is an unsigned int bounded by MQ_PRIO_MAX, which is 32768, so the usable range is 0 through 32767 and mq_timedsend rejects anything larger outright. That bound also limits how many nodes a tree can ever hold, since a node exists per distinct priority rather than per message. Since a node has to be linked while the queue's spinlock is held, do_mq_timedsend allocates one before taking the lock and parks it in the queue's node_cache field, so the insertion itself only has to unhook a pointer; the GFP_ATOMIC allocation inside msg_insert is a fallback that a well-behaved send never reaches. The cache is one deep and is refilled from the other direction as well: when a receive empties a priority level, msg_tree_erase keeps the node instead of freeing it if the slot is vacant. A queue whose messages all carry the same priority—which is to say most queues—therefore allocates a single node when the first message is sent and then recycles it forever, never touching the allocator again.

A queue's shape is fixed when it is created: mq_open with O_CREAT takes an mq_attr giving the maximum number of messages (mq_maxmsg) and the maximum size of each (mq_msgsize), and those bounds hold for the queue's life. A process can read them back, and query how many messages are currently queued, with mq_getattr, and toggle the non-blocking flag with mq_setattr—but not resize the queue. The kernel charges the queue's worst-case memory against the creating user's resource limit at open time, so a queue cannot lazily grow past what was reserved. The charge is not merely the payload: mqueue_get_inode computes mq_maxmsg × mq_msgsize and then adds a tree size of mq_maxmsg × sizeof(struct msg_msg) plus min(mq_maxmsg, MQ_PRIO_MAX) × sizeof(struct posix_msg_tree_node), so the per-message header and the priority nodes are paid for too. A queue of ten thousand one-byte messages is charged for hundreds of kilobytes rather than ten thousand bytes, which is the honest answer, because that is what the queue will actually consume when full. The total is accumulated through the ucounts mechanism as UCOUNT_RLIMIT_MSGQUEUE and compared against RLIMIT_MSGQUEUE, so the limit follows the user across the user-namespace hierarchy rather than being a flat per-uid counter; exceeding it fails mq_open with EMFILE rather than the ENOMEM one might expect. Send and receive block by default—mq_timedsend waits while the queue is full, mq_timedreceive while it is empty—unless the descriptor was opened O_NONBLOCK or the per-call timeout expires, in which case they fail rather than wait. As with the other blocking IPC paths, the kernel optimizes the rendezvous: if a receiver is already waiting when a message is sent, the send hands it over directly instead of inserting into the tree.

That handoff runs in both directions and uses the same trick the System V pipelined send does. pipelined_send hands a message straight to a waiting receiver, and pipelined_receive does the mirror image: a receiver that has just freed a slot in a full queue passes the vacancy to a waiting sender, whose message is deposited on its behalf. In each case the waiter's state is set to STATE_READY with smp_store_release and the task is woken through a wake_q after the queue lock is dropped. The woken task reads its state with READ_ONCE, sees STATE_READY, and returns without ever reacquiring the lock—so a busy queue with waiters on both sides passes messages with one lock acquisition per operation rather than two. The comment block at the head of ipc/mqueue.c spells out the memory ordering this depends on, including the reordering hazard that forces the release barrier, and is worth reading as a compact example of how the kernel documents a lockless handoff.

POSIX message queues add one capability System V lacks entirely: asynchronous notification. A process can register with mq_notify to be told when a message arrives on a previously empty queue, either by delivery of a signal (SIGEV_SIGNAL) or by the kernel spawning notification into a thread (SIGEV_THREAD, delivered via a netlink message). The netlink path is worth spelling out, because it turns on a sigevent field that is not what it claims to be: for SIGEV_THREAD, glibc opens a netlink socket, hides its descriptor in sigev_signo, and the kernel resolves it with netlink_getsockbyfd. At registration time—not at delivery time—the kernel allocates a small cookie message and attaches it to that socket with netlink_attachskb, reserving the queue space up front so the eventual notification can never fail for want of memory. When a message then arrives, netlink_sendskb pushes the pre-allocated cookie with its last byte set to NOTIFY_WOKENUP; if instead the queue is unlinked or the registration is cancelled while it is live, the same cookie goes out carrying NOTIFY_REMOVED. That one byte is how glibc's helper thread distinguishes "a message is waiting for you" from "stand down and exit," which is why a program that unlinks a queue under a SIGEV_THREAD registration does not leak the helper. Only one process may be registered at a time, and the registration is one-shot—it fires once and must be re-armed—which suits the common pattern of a mostly idle queue that a process wants to react to without a dedicated blocking thread. Per-namespace limits under /proc/sys/fs/mqueue/ (queues_max, msg_max, msgsize_max) bound how many queues exist and how large messages may be, and because the mqueue mount is per IPC namespace, containers again get independent sets.

One small convenience follows from queues being files in a real filesystem. Reading a queue file directly—plain cat on /dev/mqueue/myqueue—does not dequeue anything; mqueue_read_file instead synthesizes a single status line reporting QSIZE, the total bytes currently held, along with NOTIFY, SIGNO, and NOTIFY_PID describing any active notification registration. It is the POSIX answer to ipcs -q, and unlike ipcs it needs no special tool: the ordinary file permissions on the queue decide who may look. The inode behind it is a struct mqueue_inode_info with a VFS inode embedded at its head, carved from a dedicated slab cache, which is the same embedding pattern the filesystem chapters described for every other special-purpose filesystem.

Shared Memory

A POSIX shared-memory object is opened with shm_open, which is essentially open on a file in a tmpfs instance mounted at /dev/shm; the returned descriptor is sized with ftruncate and mapped with mmap. There is no special IPC object at all—POSIX shared memory is a mapped tmpfs file, which is why a segment appears as a file under /dev/shm and is removed with shm_unlink. This makes it the same shared-page mechanism as System V shared memory (which, as §3.4 showed, is also tmpfs-backed) but named by path and handled by descriptor, so it inherits, closes, and passes like any file.

It is worth being exact about how little the kernel contributes here, because the answer is nothing. A search of the system-call table finds no shm_open: the function lives entirely in the C library, where it validates that the name is a single component beginning with a slash, prepends the mount point, and calls open with O_CLOEXEC added. shm_unlink is unlink with the same prefix. The kernel never learns that the resulting file is meant to be shared memory, which has one practical consequence worth knowing before debugging a container: /dev/shm is mounted by the distribution's startup, not created by the kernel, so an image built without it fails every shm_open with ENOENT for a reason no message mentions. Because the mount point is resolved in the caller's mount namespace rather than its IPC namespace, two processes in the same IPC namespace but different mount namespaces do not share POSIX shared memory, while two in different IPC namespaces that share a mount namespace do—exactly the reverse of how System V segments behave.

The descriptor-based interface makes POSIX shared memory considerably more flexible than its System V counterpart. Because the handle is an ordinary file descriptor, two processes need not both know a path: one can create the object, map it, and pass the descriptor to the other over a Unix socket, which maps the same pages without ever seeing the name—the same pattern memfd generalizes in §6.3. Resizing is a plain ftruncate, mapping is a plain mmap with the protection and sharing flags the memory-management chapters described, and unmapping is munmap; there is no separate attach/detach vocabulary to learn. And because the object is a file, its lifetime follows the file rule: shm_unlink removes the name, but the pages persist until the last mapping and descriptor are gone, so a segment can be created, unlinked immediately, and still shared safely by processes already holding it—a clean way to avoid the leaked-segment problem that dogs System V shared memory. Table 19-6 sets the two side by side.

Being an ordinary file also means the whole file toolbox applies without anyone having taught it about IPC. A region can be grown or shrunk with ftruncate after the fact, sparsely populated, or punched full of holes with fallocate and FALLOC_FL_PUNCH_HOLE to hand pages back while keeping the mapping valid. The tmpfs size limit—half of RAM by default, and visible through statfs or df—caps the total, and because the pages are shmem pages they may be swapped or, as Chapter 17 described, compressed into zswap under pressure, which is not true of System V segments locked with SHM_LOCK. The one thing shm_open cannot do is produce an object with no name at all, however briefly; a program that wants that reaches for memfd_create instead, which §6.3 covers along with the sealing that makes a received descriptor safe to trust.

Semaphores

POSIX semaphores come in two forms. A named semaphore (sem_open) is, like shared memory, a small tmpfs-backed object named by path; an unnamed semaphore (sem_init) is just a variable the program places in memory it already shares—often inside a POSIX shared-memory region, which is how two processes share one. In both cases the interesting point is what happens on the fast path: the semaphore's value is an ordinary word in shared memory, and the common sem_wait/sem_post operations that do not have to block are performed entirely in user space with an atomic instruction, never entering the kernel. The kernel is involved only when a thread must actually wait or wake a waiter, and then through the futex mechanism of the next section.

The consequence deserves stating plainly, because the symmetry of the names hides it: there is no sem_open system call, no sem_wait, and no sem_post. Unlike message queues, which have a subsystem, and unlike POSIX shared memory, which at least produces an inode the kernel can see, a POSIX semaphore has no kernel object whatsoever. The sem_t a program declares is a small structure in its own memory holding a counter, a waiter count, and a flag recording whether it was initialized for cross-process use; a named semaphore is that same structure living in a file under /dev/shm that sem_open creates and maps on the caller's behalf, so it inherits the mount namespace caveat of the previous section exactly. This explains several otherwise puzzling facts at once: a POSIX semaphore appears in no /proc file and no ipcs listing; it cannot be waited on with epoll, because there is no descriptor to wait on and no kernel state to report readiness; a leaked named semaphore is not a leak the kernel can be asked to clean up, merely a stale file that rm removes; and the pshared argument to sem_init matters, because it decides whether the library issues private or shared futex operations, and a semaphore initialized with it zero will silently fail to synchronize processes that map it.

This is the sharpest contrast in the chapter. A System V semaphore operation is always a system call—every semop, contended or not, crosses into the kernel, takes locks, and walks pending lists—whereas a POSIX semaphore that is uncontended costs a single atomic instruction and no system call at all. For the overwhelmingly common case of a lock that is free when a thread wants it, that is the difference between tens of nanoseconds and a full syscall round trip. POSIX semaphores, POSIX mutexes, and condition variables are thus best understood as thin glibc wrappers over futexes—which is why the futex, still minimal in Linux 2.6.11, is the real foundation of modern user-space synchronization, and the subject of the next section. Futexes

The futex is the piece of machinery that ties this chapter's synchronization threads together. It is not a user-facing IPC object like a semaphore or a message queue—few programs call it directly—but it is the kernel primitive on which the entire user-space locking library is built. Every pthread mutex, condition variable, read-write lock, and barrier, and every POSIX semaphore, is a futex underneath. Understanding it explains a fact stated repeatedly in the earlier sections: that an uncontended POSIX lock costs no system call. The futex existed in a minimal form in 2.6.11, but the priority-inheritance, robust-list, and multi-wait facilities that make it the foundation of modern threading were all added later.

The design rests on one observation about how locks are actually used: the vast majority of lock operations are uncontended. When a thread acquires a mutex that no one else holds, or releases one that no one is waiting for, nothing needs to sleep or wake—the operation is logically just a change to a variable. Paying for a system call on every such operation, as older kernel-based locks did, is pure waste. The futex removes that waste by splitting a lock into two halves: a fast half in user space that handles the uncontended case with a single atomic instruction, and a slow half in the kernel, reached only when a thread genuinely must block or wake another. This section covers the idea, then the futex system call that implements the slow half, then the priority-inheritance and robust extensions that make it safe for real programs.

Fast Userspace Locking

A futex—fast user-space mutex—is the primitive that makes user-space locking cheap. The problem it solves is that a traditional lock built on a system call pays the cost of entering the kernel on every acquire and release, even when the lock is uncontended and the operation is really just flipping a bit. Most locks, most of the time, are uncontended. The futex insight is to keep the lock's state in an ordinary 32-bit word in user memory and touch the kernel only when a thread actually has to wait. Acquiring an uncontended lock is a single atomic compare-and-swap on that word, done entirely in user space with no system call; only when a thread finds the lock already held—and must block—does it call the futex system call to sleep, and only a thread releasing a lock that has waiters calls futex to wake one. Figure 19-6 contrasts the two paths.

What makes the split correct rather than merely fast is that the fast and slow halves agree on the meaning of the futex word. In a typical mutex the word encodes the lock's whole state: zero means unlocked, a thread id means locked by that thread, and a separate "waiters" bit means at least one thread is blocked in the kernel. The critical rule is that a thread releasing a lock must fall into the kernel to issue a wake only when that waiters bit is set; otherwise it clears the word in user space and returns without a system call. So the kernel is entered exactly twice per contended lock—once by the waiter to sleep, once by the owner to wake it—and not at all when the lock is uncontended. This is why a benchmark of an uncontended pthread mutex shows no system calls whatsoever, while the same lock under contention shows the expected futex pair. The FUTEX_WAIT operation is what makes the sleep safe: it rechecks the word against an expected value inside the kernel, atomically with respect to enqueuing, so a thread that was about to sleep but whose lock was released in the interval is not lost—it sees the value has changed and returns instead of blocking forever.

The futex System Call

The futex system call (kernel/futex/) is an operation multiplexer; its second argument selects what to do. The two fundamental operations are FUTEX_WAIT, which atomically checks that the futex word still equals an expected value and, if so, sleeps (closing the race where the value changes between the user-space test and the syscall), and FUTEX_WAKE, which wakes a given number of waiters on a word. Around these the kernel provides higher-level operations—requeuing waiters from one futex to another (FUTEX_CMP_REQUEUE, used to implement condition variables without a thundering herd), a combined wake-and-modify (FUTEX_WAKE_OP), and bit-masked variants—listed in Table 19-8.

To act on a futex the kernel must identify it, and it does so with a struct futex_key computed by get_futex_key, which derives an identity for the word that every participating process will agree on—how it does so depends on the private-versus-shared distinction taken up below. The key hashes to a futex_hash_bucket, on whose wait list the blocked thread parks as a struct futex_q. A newer syscall, futex_waitv, lets a thread wait on several futexes at once—up to FUTEX_WAITV_MAX, which is 128—and wake on any of them, which is what a user-space scheduler or an emulator translating another system's wait primitive needs. Linux 2.6.11 had only the bare wait/wake core.

The interface has since grown past the multiplexer that gave it its shape. Linux 7.0.12 has five futex system calls, not one: the original futex, futex_waitv, and a trio of futex_wake, futex_wait, and futex_requeue that give the three core operations entry points of their own. The reason is that the old encoding ran out of room. Every option had to be packed into the operation word alongside the command—FUTEX_PRIVATE_FLAG and FUTEX_CLOCK_REALTIME are bits stolen from that word—and there was nowhere left to put per-futex attributes. The newer calls take a struct futex_waitv descriptor per futex, each carrying its own flags, which is why futex_requeue takes an array of two descriptors rather than two pointers. The flags themselves moved to a separate FUTEX2_ family whose futex2_to_flags helper translates them into the internal FLAGS_ set that both interfaces share.

It is worth reading the FUTEX2_ list carefully, because the interface is more general than the implementation. Four size flags are defined— FUTEX2_SIZE_U8, U16, U32, and U64—but futex_flags_valid in kernel/futex/futex.h rejects every one of them except U32, under a comment saying plainly that only 32-bit futexes are implemented for now. A program that asks for an 8-bit or 64-bit futex gets EINVAL, and the futex_requeue implementation carries a matching note explaining that its requirement for both descriptors to have identical flags can be relaxed once variable-sized futexes land. The flags are reserved interface, not working feature. What does work is FUTEX2_NUMA, which makes the futex word a pair of words: the second holds the NUMA node whose hash table should hold the waiter, so a lock shared across a large machine does not force every waiter through one node's memory. The kernel refuses the flag if nr_node_ids cannot be represented in a word of the requested size. Its companion FUTEX2_MPOL derives the node from the mapping's memory policy instead of from an explicit number.

The hash table the key lands in has changed more than anything else in this section, and for a reason that has nothing to do with correctness. Historically there was exactly one global table, and because a private futex is keyed on (mm, address), two unrelated processes could hash their entirely private locks into the same bucket and contend on its spinlock—a noisy neighbor effect invisible to both. Linux now gives each process its own table, hanging off mm->futex_phash, and falls back to the global one (which is itself split per NUMA node) only for shared futexes and for processes that have not needed a private table yet. The allocation happens in kernel/fork.c when a process first creates a thread, is sized roundup_pow_of_two(4 × min(threads, online CPUs)) clamped between 16 buckets and the size of the global table, and is grown as the thread count rises, with existing waiters rehashed into the new table under RCU. A program that knows its own locking pattern can override the heuristic with prctl(PR_FUTEX_HASH, PR_FUTEX_HASH_SET_SLOTS, ...), and read back what it has with PR_FUTEX_HASH_GET_SLOTS, where a returned zero means the process is still using the global table.

The private-versus-shared distinction is worth dwelling on because it is a real performance lever. A private futex is the common case—a lock shared only among threads of one process, which all see the same virtual address—so the kernel can key it on (mm, address) without touching the page tables at all, and can skip the reference counting that shared keys need. A shared futex sits in memory mapped by several processes (a POSIX shared-memory region, for instance), where the same lock has different virtual addresses in each, so the kernel must resolve the address to the underlying page and key on (inode, page offset) to give every process the same identity for that word. Glibc picks the private variant automatically whenever a lock is not process-shared, which is why thread locks are even cheaper than cross-process ones. The FUTEX_CMP_REQUEUE operation deserves its own note: it exists to make pthread_cond_broadcast efficient. Waking every waiter on a condition variable would send them all racing for the associated mutex—a thundering herd—so instead the kernel wakes one and requeues the rest directly onto the mutex's futex, where they wait their turn in order, one wakeup at a time.

Priority-Inheritance and Robust Futexes

Two extensions make futexes safe for demanding uses. A plain futex lock is vulnerable to priority inversion: a high-priority thread can block on a lock held by a low-priority thread that never gets scheduled to release it. Priority-inheritance futexes (FUTEX_LOCK_PI, kernel/futex/pi.c) fix this by tying the futex to a kernel rt_mutex that temporarily boosts the lock holder to the waiter's priority until it releases. These PI futexes use a defined protocol in the futex word itself: the word holds the owner's thread id, the FUTEX_WAITERS bit signals that the kernel must be told on release, and the FUTEX_OWNER_DIED bit records that an owner died holding the lock. Glibc's priority-inheriting mutexes are built directly on this.

The second extension addresses a crash while holding a lock. If a thread dies with a normal lock held, any waiter blocks forever. Robust futexes let a thread register a robust list (set_robust_list) of the locks it currently holds, kept in user memory. When the thread exits—cleanly or by crashing—the kernel walks that list (exit_robust_list), and for each still-held lock it sets the FUTEX_OWNER_DIED bit and wakes a waiter, so surviving threads learn the lock's owner died and can recover rather than hang, typically by taking the lock and calling pthread_mutex_consistent to declare the protected data repaired. Together, PI and robust futexes turn the bare fast-path primitive into something robust enough to underlie the full pthread synchronization API—mutexes, condition variables, read-write locks, and barriers—which is why nearly every threaded Linux program depends on futexes without ever calling one directly.

It is worth being precise about how each extension does its job, because both rely on the kernel and user space sharing the futex word's format. A priority-inheritance lock cannot be taken purely in user space the way a plain mutex can: acquiring it goes through FUTEX_LOCK_PI so the kernel can build the rt_mutex chain that implements the priority boost, and releasing it uses FUTEX_UNLOCK_PI. The kernel reads the owner's thread id straight out of the word to know whom to boost, which is why the protocol fixes the word's low bits as the TID and reserves the high bits for the FUTEX_WAITERS and FUTEX_OWNER_DIED flags. The robust mechanism leans on the same FUTEX_OWNER_DIED flag but is driven differently: the thread itself maintains the robust list as it locks and unlocks, and registers only the list's head with the kernel through set_robust_list, so the per-lock bookkeeping stays in user space and costs nothing until the thread dies. Only at exit does the kernel walk the list. The two extensions compose—a lock can be both priority-inheriting and robust—and together they let glibc offer the full range of mutex types the pthreads standard defines, all resting on this one primitive.

The robust list repays a closer look, because the obvious design does not work and the fix is instructive. A thread registers only the head of the list, so the kernel must walk a linked structure that lives entirely in the dying thread's memory and was maintained by code that may have been in the middle of anything when it died. The kernel therefore treats it as untrusted: the walk in exit_robust_list is bounded by ROBUST_LIST_LIMIT, so a corrupted list that loops back on itself stops the walk rather than the machine, and a faulting read simply ends it. The head also carries a futex_offset, a signed displacement from each list entry to the futex word it describes, because the list node is embedded in glibc's mutex structure at a position the kernel must not assume. The subtle part is the third field, list_op_pending: a thread adding a lock to the list or removing it is momentarily in a state where the lock is held but not listed, or listed but no longer held, and dying in that window would strand a waiter. Glibc closes the gap by publishing the futex it is about to operate on in list_op_pending before touching either the word or the list, and the kernel processes that entry last, after the list proper. For each candidate, handle_futex_death sets FUTEX_OWNER_DIED and wakes a waiter only if the thread id in the word is in fact the dying thread's, so an entry that was already cleaned up is skipped.

One asymmetry between the two extensions is easy to miss. A robust lock is still an ordinary futex, so its uncontended path stays in user space and the list bookkeeping is a few stores; robustness is close to free until something dies. A priority-inheriting lock gives that up. Because the kernel must own the rt_mutex chain that implements the boost, even an uncontended FUTEX_LOCK_PI enters the kernel, and so does every unlock of a lock the kernel knows about—the fast path that justifies the futex in the first place does not apply. Priority inheritance is therefore something to ask for when inversion is a real hazard, not a safe default. The operation also carries a historical wart: FUTEX_LOCK_PI forces its timeout to be an absolute CLOCK_REALTIME deadline, which moves when the administrator sets the clock, so a second operation, FUTEX_LOCK_PI2, was added that behaves identically except for honoring CLOCK_MONOTONIC. New code should use it. The priority-inheriting variants of requeue, FUTEX_WAIT_REQUEUE_PI and FUTEX_CMP_REQUEUE_PI, exist so that a PI-aware condition variable can move waiters onto a PI mutex without losing the ownership tracking on the way across.

File-Descriptor IPC and Notification

The mechanisms in this final section share a design philosophy rather than a purpose: each turns some event or resource into a file descriptor. That is a powerful unification, because a descriptor can be waited on with epoll. A single-threaded event loop can therefore block in one epoll_wait and be woken by a network socket, a countdown timer, an incoming signal, a child's death, or another thread's post—each arriving as a readable descriptor. This is the architecture behind essentially every modern high-performance Linux server and language runtime, and most of these primitives were added after Linux 2.6.11. eventfd

The simplest of the family, eventfd (fs/eventfd.c), is a descriptor wrapping a single 64-bit counter (struct eventfd_ctx). Writing adds a value to the counter; reading returns the accumulated total and resets it to zero, or, in semaphore mode (EFD_SEMAPHORE), returns 1 and decrements by one. A read blocks while the counter is zero, so an eventfd is a minimal, countable wakeup: one thread posts, another wakes. Its real importance is as a bridge from the kernel to user space—the in-kernel eventfd_signal lets subsystems such as KVM, asynchronous I/O, and io_uring notify a waiting process through an ordinary descriptor it can epoll. It is the lightest-weight way to say "something happened" across a thread or kernel/user-space boundary.

The two read modes suit different roles. In the default mode a read collapses however many posts have accumulated into one total and clears the counter, which fits a "wake me if there is work" signal where the exact count does not matter—a reader that wakes once and drains all pending work. In semaphore mode each read returns exactly 1 and leaves the rest, so N posts wake N reads, which turns the eventfd into a simple counting semaphore usable across an epoll loop. The flags follow the family convention: EFD_NONBLOCK makes a read of a zero counter return EAGAIN rather than block, and EFD_CLOEXEC closes the descriptor across exec. Because an eventfd is only an 8-byte counter with a wait queue, it is far cheaper than a pipe for the pure signaling job a pipe is often misused for—no buffer, no byte stream, just a number and a wakeup—which is why the kernel's own asynchronous interfaces adopted it as their notification handle.

The implementation is deliberately tiny. eventfd2 allocates a struct eventfd_ctx—a reference count, a wait-queue head, the 64-bit count, and the flags—and hands back a descriptor over an anonymous inode (there is no file on any filesystem, just an in-kernel [eventfd] inode with the eventfd_fops methods). All access goes through fixed 8-byte transfers: a read or write of anything other than sizeof(u64) is rejected with EINVAL, so the descriptor carries a single integer, never a stream. A write adds its value to count under the wait-queue's spinlock and wakes any reader; if the addition would overflow, the writer blocks (or returns EAGAIN) until a read makes room, because the counter saturates just below ULLONG_MAX, which is reserved as an overflow sentinel. A read blocks while count is zero, then returns the whole count and zeros it—or, in semaphore mode, returns 1 and decrements by one. And eventfd_poll reports EPOLLIN whenever the count is nonzero, which is what lets the object sit in an epoll set.

The in-kernel posting path is close to the userspace one but not identical, and the differences are instructive. eventfd_signal takes only the context: it adds exactly one, where a write adds whatever value the caller supplied. The count argument it once had was removed because essentially every caller passed one, and the handful that did not were relying on behavior the function could not actually deliver—a partial add on overflow—so the interface was narrowed to the operation that was always meant. More importantly, eventfd_signal exists to be called from contexts that cannot sleep, such as interrupt handlers and completion paths, so it cannot block the way a full-counter write does. It therefore permits the count to reach ULLONG_MAX—the value userspace writes are held below—and reports that saturation to the waiter as EPOLLERR from poll rather than by refusing the post. A reader that sees an error on an eventfd is being told that notifications were lost, which for a counter is the only honest thing to say.

One hazard is worth naming because the kernel warns about it explicitly. Waking a waiter can run that waiter's custom wake function, and if the wakee is itself holding or signaling an eventfd, the chain can recurse into eventfd_signal and deadlock on the wait queue's own spinlock, or exhaust the stack. The kernel guards against this with a per-task in_eventfd flag set across the post; a nested call trips a warning and is dropped instead of deadlocking. Code that can legitimately find itself in such a nest—the classic case is an eventfd registered with epoll whose readiness is signaled from inside another epoll callback—is expected to test eventfd_signal_allowed first and defer the post to a workqueue if the answer is no.

For a developer the object is almost trivial to use, and that is the point. One thread or subsystem creates the eventfd and shares the descriptor—inherited across fork, passed over a socket, or simply used by sibling threads—then producers signal by writing an 8-byte value (usually 1) and the consumer waits by reading, or, more commonly, by adding the descriptor to an epoll set and treating a readable eventfd as "wake up, there is work." A worker pool, for instance, can post to one eventfd to nudge an idle dispatcher; a thread finishing background I/O can signal the main loop without a pipe or a condition variable. The pattern the object was designed for, though, is kernel-to-userspace notification: KVM signals a guest's virtual interrupt through an eventfd (irqfd), the POSIX AIO and io_uring interfaces can post completions to one, and a program registers that single descriptor in the same epoll_wait that watches its sockets and timers—so a kernel event and a network event arrive through one uniform readiness interface.

signalfd and timerfd

These two fold classically asynchronous events into the synchronous descriptor model. signalfd (fs/signalfd.c) turns signal delivery into a readable stream: after a process blocks a set of signals and creates a signalfd for them, each signal that would have interrupted a handler instead becomes a fixed-size signalfd_siginfo record the process reads from the descriptor at a moment of its choosing. This escapes the notorious constraints of asynchronous signal handlers—which may call only async-signal-safe functions—by letting a program handle signals in its normal control flow, inside its event loop. timerfd (fs/timerfd.c) does the same for timers: timerfd_create and timerfd_settime arm a timer whose expirations become readable events, the read returning a count of how many times it fired since the last read. Because both are descriptors, a program waits for signals and timers in the same epoll_wait that waits for its sockets, rather than juggling handlers and SIGALRM.

Both solve a real awkwardness of the older interfaces. A traditional signal handler runs asynchronously on some thread's stack at an arbitrary point, so it may call only async-signal-safe functions—it cannot safely take a lock, allocate memory, or call most of the C library—which makes non-trivial signal handling notoriously error-prone. Reading signals from a signalfd removes that hazard entirely: the work happens synchronously in ordinary code, so it may do anything. The one requirement is that the signals be blocked with sigprocmask first, so the kernel queues them for the descriptor instead of delivering them the old way. timerfd likewise improves on setitimer and SIGALRM: a timer that delivers through a descriptor does not interrupt anything, several independent timerfds can coexist in one process (where there was only one SIGALRM), and the read's count of missed expirations makes overrun explicit rather than silently coalesced. timerfd_settime accepts TFD_TIMER_ABSTIME for absolute deadlines and can arm a repeating interval, and a timerfd built on CLOCK_REALTIME can even be set to report when the wall clock is stepped.

That last flag repays being stated precisely, because it solves a problem absolute deadlines otherwise have no answer for. An absolute CLOCK_REALTIME deadline is a promise about a wall-clock reading, and an administrator or an NTP step can move the wall clock underneath it, leaving the timer due years early or years late. Arming with TFD_TIMER_CANCEL_ON_SET alongside TFD_TIMER_ABSTIME tells the kernel to abandon the timer if that happens: the pending read fails with ECANCELED instead of returning an expiration count, and the program knows to recompute its deadline from the new clock rather than trust a stale one. It is the descriptor-shaped version of the same discontinuity problem the futex section met in FUTEX_LOCK_PI, and the same answer—tell the caller the clock moved—rather than pretending it did not.

memfd and File Sealing

memfd_create (mm/memfd.c) creates an anonymous file that lives in tmpfs and has no name in any directory—it exists only as a descriptor. The sharing pattern is the one §4.2 described for a shm_open object with the path step removed: the descriptor itself is the only thing the second process ever receives, usually over a Unix-domain socket (§7.2). That is what suits sandboxed and privilege-separated designs, where the receiver may have no filesystem in which an agreed-upon name could exist. Its distinctive feature is file sealing: through fcntl a process can apply seals—F_SEAL_WRITE, F_SEAL_SHRINK, F_SEAL_GROW, F_SEAL_FUTURE_WRITE, F_SEAL_EXEC, and F_SEAL_SEAL (which forbids further sealing)—that irreversibly restrict how the file may be changed. A receiver can verify the seals and then trust the shared buffer: once it is sealed against writing and shrinking, a malicious sender cannot pull the memory away or alter it mid-use. This is what makes memfd safe for zero-copy sharing between mutually distrusting processes, as in graphics buffers (dma-buf) and the Wayland display protocol—a guarantee System V shared memory never offered.

Sealing has to be enabled deliberately: a memfd accepts seals only if it was created with MFD_ALLOW_SEALING, and once F_SEAL_SEAL is applied no further seals can be added, so the set of restrictions becomes permanent. The reason a seal can be trusted is that the kernel enforces it against every path to the file—not just the sealing process's own writes but any other descriptor, any shared mapping, and any future reopen—so a producer that seals a buffer against writing and shrinking has made a promise the kernel keeps on its behalf. That is precisely what a consumer needs before it maps a buffer it did not create and reads from it without copying: without sealing it would have to defensively copy the data in case the sender changed the size or contents underneath it, and the copy would defeat the zero-copy purpose. Beyond shared buffers, memfd_create is also the modern way to hold a block of anonymous memory as a passable, mappable object—used for cross-language runtimes, for handing a region to a child with a known descriptor number, and (with MFD_HUGETLB) for huge-page-backed shared regions.

One seal in that list is not about sharing at all. A memfd was originally created with its execute bits set, which made it a convenient vehicle for fileless execution: an attacker who could get code into a process could write a payload into a memfd and then execute it through /proc/self/fd/N, leaving nothing on disk for a scanner to find. F_SEAL_EXEC closes that by freezing the file's mode bits, so the execute permission can be neither added later nor, once absent, restored. The flag MFD_NOEXEC_SEAL asks for the safe combination in one step: create the file non-executable and apply F_SEAL_EXEC immediately, which is what essentially every legitimate user of a memfd wants. Its counterpart MFD_EXEC requests the old behavior explicitly, and passing both is rejected.

Because existing programs pass neither flag, the kernel needed a way to change the default without breaking them, and the mechanism it chose is worth noting for its shape. A sysctl, vm.memfd_noexec, selects among three policies— leave the old behavior alone, quietly add MFD_NOEXEC_SEAL to callers that did not choose, or refuse outright any memfd_create that does not ask for it—and a call that omits both flags is logged so an administrator can find the code that needs updating. The setting lives per PID namespace rather than system-wide, and a namespace may only tighten what it inherited, so a container runtime can enforce the strict policy on the workloads it starts without needing the host to agree and without a nested container being able to relax it again.

pidfd

The last primitive references not an event or a buffer but a process. Traditional Unix names a process by its numeric pid, which is unsafe: pids are recycled, so between learning a pid and acting on it, that pid may have been reused by an unrelated process—a signal or wait can hit the wrong target. A pidfd is a stable, race-free descriptor for a specific process, obtained with pidfd_open or at creation time with clone(CLONE_PIDFD). It never refers to any other process even after the original exits and its pid is recycled. pidfd_send_signal signals the exact process with no reuse race; polling a pidfd reports when the process exits, letting a supervisor wait on children in its event loop alongside every other descriptor; and pidfd_getfd can even retrieve a descriptor from another process. The pidfd rounds out the theme of the section—by making even "a process" into a file descriptor, Linux lets process supervision join the same uniform, pollable model as every other kind of event. (A related descriptor, userfaultfd, turns page faults into user-space events for live migration and user-space paging; it belongs to the memory-management machinery of the earlier chapters but shares this fd-centered design.)

The pid-reuse race the pidfd closes is not hypothetical: a classic bug is a supervisor that records a child's pid, and later—after the child has exited and the kernel has recycled that number for an unrelated process—sends a signal to "the child" and kills the wrong process. Holding a pidfd from the moment of creation eliminates the window, because the descriptor is bound to the specific process, not to a number that can be reassigned. This is why clone gained CLONE_PIDFD, which hands back a pidfd for the new child atomically with its creation, and why container managers, service supervisors like systemd, and language runtimes now track their children by pidfd. The pollability matters as much as the safety: a supervisor adds each child's pidfd to its epoll set and is notified the instant a child exits, in the same loop that handles its sockets and timers, without the traditional SIGCHLD-handler-plus-waitpid dance. And pidfd_getfd, which pulls a descriptor out of another process, lets a supervisor or debugger reach into a target it holds a pidfd for—the inverse of passing a descriptor over a socket, and the last way in which the file descriptor has become Linux's universal handle, here even for another process's open files.

The pidfd has grown well past that original sketch, and the change with the widest consequences is that a pidfd is no longer an anonymous inode. Pidfds now come from a small internal filesystem of their own, pidfs (fs/pidfs.c), which gives each one a distinct inode number drawn from a 64-bit counter and paired with a generation number. That sounds like bookkeeping, but it answers a question that was previously unanswerable: whether two descriptors refer to the same process. While every pidfd shared the one anonymous inode, comparing them with stat told a program nothing at all. Now the inode number and generation identify the process as durably as the descriptor does, which lets a supervisor holding pidfds from several sources deduplicate them. Pidfs also implements the export operations, so a pidfd can be turned into a file handle with name_to_handle_at, written down, and later reopened with open_by_handle_at—a process identity that can be stored in a database and still refuses to be confused with a recycled pid.

The other additions fill in what a supervisor actually needs. A pidfd normally refers to a thread group, and polling it fires when the last thread exits; opening with PIDFD_THREAD narrows it to one thread, so a runtime can watch an individual thread the way it watches a process. The magic values PIDFD_SELF and PIDFD_SELF_PROCESS let a program name itself without opening anything, which matters for calls that take a pidfd in a context where opening a descriptor would be awkward. pidfd_send_signal takes flags choosing whether the signal goes to the one thread, the whole thread group, or the process group, extending the race-free guarantee to targets that previously had to be named by a negative pid. And a family of ten PIDFD_GET_X_NAMESPACE ioctls hands back a descriptor for any of the target's namespaces ready for setns, so entering a container's network or mount namespace no longer requires reading /proc/<pid>/ns/ and thus no longer depends on /proc being mounted or on the pid still meaning what it did.

The most useful of the new operations, though, is PIDFD_GET_INFO. It fills a struct pidfd_info with whatever the caller asks for and the kernel can supply: the target's pid as seen from the caller's namespace, its credentials, its cgroup id, and—with PIDFD_INFO_EXIT—how it exited. That last item closes the final gap in the pidfd story. A supervisor could already learn that a child had exited by polling, but to learn how it had exited it still needed waitid, which is the one operation that consumes the zombie and so can be performed exactly once by exactly one caller. Reading the exit status from the pidfd instead lets several interested parties each discover the outcome independently, in their own event loops, which is what a service manager, a supervising library, and a language runtime living in the same process all need at once. The structure is versioned by size and carries a supported_mask, so a program can discover at runtime which fields the running kernel knows how to fill—the same extensible-struct convention the newer system calls in earlier chapters used.

epoll: Waiting on Many Descriptors

Every primitive in this section ends the same way: the descriptor is handed to epoll. The mechanism that makes that work lives in fs/eventpoll.c, and it is worth opening, because it is what turns a pile of descriptors into one event loop. The older select and poll calls in fs/select.c take the whole list of descriptors on every call, walk every one of them through its file's poll method (Chapter 13 shows a driver implementing one), and then throw the work away. Their cost grows with the number of descriptors watched, not the number that are ready. epoll splits the operation in two: a program registers its interest once, the kernel remembers it, and each wait then costs in proportion to the number of descriptors that actually have something to report.

epoll_create1 builds a struct eventpoll and returns it as an anonymous file named [eventpoll], so the epoll instance is itself a descriptor—closed on exit, inherited across fork, and pollable. The structure holds the interest set as a red-black tree (rbr), a ready list (rdllist) of items with pending events, the wait queue wq on which epoll_wait callers sleep, a mutex that serializes control operations and event collection, and a spinlock that guards the ready list. Each watched descriptor is a struct epitem, keyed in the tree by the pair (struct file pointer, descriptor number), carrying the struct epoll_event the caller asked for, and linked onto the target file's f_ep list so the file knows who is watching it.

The interesting work happens in epoll_ctl(EPOLL_CTL_ADD). After checking that the target supports poll at all (a regular file does not, and is refused with EPERM), ep_insert allocates the epitem, inserts it in the tree, and then calls the target's poll method exactly once with a special poll_table. Where select uses the poll table only to park the current task on the file's wait queue for one call, epoll's queueing callback, ep_ptable_queue_proc, installs a permanent wait-queue entry whose wake function is ep_poll_callback. From then on, whenever the socket, pipe, eventfd, or timerfd wakes its wait queue—as it would for any blocked reader—ep_poll_callback runs in the waker's context, puts the epitem on the ready list if it is not already there, and wakes one sleeper on ep->wq. Readiness is therefore pushed to epoll by the event source rather than pulled by repeated scanning; that is the entire source of its scalability. If the descriptor is already ready when it is added, ep_insert queues it at once.

epoll_wait, epoll_pwait, and epoll_pwait2 (Linux 5.11, which takes a timespec timeout instead of milliseconds) all end in ep_poll. If the ready list is empty it adds the caller to ep->wq as an exclusive waiter and sleeps on a high-resolution timeout, so a burst of events on one instance wakes one thread rather than every thread blocked on it. When there is work, ep_send_events takes the mutex, splices the ready list onto a private list, and re-polls each item before copying its event to user space—so a descriptor that became ready and then drained in between is not reported. While that scan runs, new events arriving from ep_poll_callback are chained on a separate overflow list (ovflist) and merged back afterward, which lets wakeups proceed under the spinlock without disturbing the list being walked.

That re-queueing step is where the three reporting modes differ. In the default level-triggered mode, an item that is still ready after being reported is put straight back on the ready list, so the next epoll_wait reports it again until the program drains it—the same contract as poll. With EPOLLET, edge-triggered mode, the item is not re-queued; it reappears only when ep_poll_callback fires again for new activity, so the program must read until EAGAIN or risk waiting forever on data already present. With EPOLLONESHOT the item's event mask is cleared after one report and nothing more is delivered until the program re-arms it with EPOLL_CTL_MOD, which is how a thread pool guarantees that only one worker handles a given connection at a time. A related flag, EPOLLEXCLUSIVE (Linux 4.5), attacks the thundering herd from the other side: when many epoll instances watch the same listening socket, it registers each one's wait entry as exclusive so a single incoming connection wakes only one of them.

Because an epoll descriptor is pollable, it can itself be added to another epoll set, and the kernel must stop that from becoming a cycle. do_epoll_ctl refuses to add an instance to itself, and when the target is another epoll file it takes a global mutex and runs ep_loop_check, which fails the call with ELOOP if the addition would close a loop or nest instances more than EP_MAX_NESTS (four) deep; a reverse-path check additionally bounds how many wakeup paths can lead to any one file. Memory is bounded too: each watch costs an epitem plus a wait-queue entry, and the per-user total is capped by /proc/sys/fs/epoll/max_user_watches, which defaults to about four percent of low memory divided by that cost; exceeding it returns ENOSPC.

The (file, descriptor) key explains epoll's best-known surprise. A watch belongs to the open file description, not to the descriptor number: the kernel removes it automatically only when __fput drops the file's last reference and calls eventpoll_release. If a program dups a descriptor, or a child inherits it across fork, and the original number is then closed, the watch survives and keeps reporting events for a descriptor number that may no longer exist or may now name something else. The safe idiom is to issue EPOLL_CTL_DEL before close. Three later additions round out the interface: EPOLLWAKEUP, which holds a power-management wakeup source from the moment an event is queued until the next epoll_wait, so a system cannot suspend between a device event and the program collecting it, and which is silently ignored unless the caller has CAP_BLOCK_SUSPEND; the EPIOCSPARAMS and EPIOCGPARAMS ioctls (Linux 6.9), which set per-instance network busy-poll parameters so epoll_wait can spin on a NIC queue instead of sleeping; and the IORING_OP_EPOLL_CTL and IORING_OP_EPOLL_WAIT io_uring operations (the latter in Linux 6.15), which let an io_uring-based program (Chapter 24) drive an existing epoll set asynchronously.

Unix-Domain Sockets

One local mechanism has been deferred until now, and the previous section explains why it can be deferred no longer. Everything in this chapter since System V IPC has turned on the file descriptor as the universal handle, and twice already the argument has leaned on a fact not yet established: that a descriptor can be handed to an unrelated process. There is exactly one mechanism in Linux that can do that, and it is the Unix-domain socket. It is a socket by API—created with socket(AF_UNIX, ...), bound, listened on, connected to, read and written with the socket calls—but nothing about it touches the networking stack. There is no protocol, no checksum, no packet ever built; net/unix/af_unix.c simply moves socket buffers from one endpoint's queue to the other's inside one kernel. That is why it belongs here with the local mechanisms rather than with the network stack, and why it is the transport under nearly every service interface on a modern Linux system: systemd's control channel, the D-Bus and Wayland protocols, the container runtimes' sockets, and the journal are all Unix-domain sockets.

Local Sockets

A Unix-domain socket comes in three types, and the third is the one no other mechanism in this chapter offers. SOCK_STREAM is a reliable, ordered byte stream, like a pipe but bidirectional over a single descriptor; SOCK_DGRAM carries discrete datagrams and, unlike its UDP namesake, is reliable and ordered, because there is no network to lose anything—a datagram is dropped only if the receiver's queue is full, in which case the sender blocks or gets EAGAIN rather than silently losing it. SOCK_SEQPACKET combines the two: a connection, like a stream, but one that preserves message boundaries, like a datagram. That combination is genuinely unavailable elsewhere here—a pipe gives a connection but no boundaries, a System V queue gives boundaries but no connection and no notification of the peer's death—and it is why protocols that need framed request/response over a supervised connection reach for it.

Addressing is where the local nature shows. A struct sockaddr_un holds a sun_path, and how that path is interpreted depends on its first byte. An ordinary path names a socket inode of type S_IFSOCK created in the filesystem by bind, which means the usual directory permissions govern who may connect, and which also means the node persists after the server exits and must be unlinked—the reason a daemon that crashed often refuses to restart until its stale socket file is removed. If the first byte is instead a null, the name is an abstract socket: it lives only in a kernel hash table, has no filesystem presence, no permission bits, and vanishes automatically when the last reference goes away. The trade is that any process in the same network namespace can connect to it, because—a detail that surprises people—abstract names are scoped by the network namespace (unix_find_abstract is passed a struct net), not by the IPC namespace that governs the System V families. A socket that is never bound gets an address anyway the first time it needs one: unix_autobind invents a random five-hex-digit abstract name, retrying until it finds a free one—and, since it starts from a random point and then scans sequentially, it gives up with ENOSPC only after it has wrapped all the way back to where it began, having found all 1,048,576 possible names in use. Finally, socketpair creates a connected, unnamed pair directly—the full-duplex answer to pipe, mentioned in passing in §2.1 and the usual way a parent hands a child a two-way channel.

Two further details matter more than their obscurity suggests. The first is flow control on datagrams: a SOCK_DGRAM receive queue is bounded by net.unix.max_dgram_qlen, a sysctl that is per network namespace like the abstract namespace it accompanies, and a sender that fills the queue blocks or takes EAGAIN. This is the same producer/consumer back pressure a pipe provides, applied to messages instead of bytes, and it is why a Unix datagram socket can be used as a reliable work queue in a way UDP cannot. The second is that a SOCK_STREAM Unix socket is a full participant in the machinery of §2.5: unix_stream_splice_read means a local socket can be spliced to a pipe, so the zero-copy paths that move data between a file and a pipe extend to the local socket that most services actually listen on. A Unix stream even carries one byte of out-of-band data if asked, which exists chiefly so that protocols ported from TCP do not have to give up MSG_OOB.

Passing Descriptors and Credentials

The socket's defining capability is that it can carry things a byte stream cannot: kernel objects. Alongside ordinary data, sendmsg can attach a control message of type SCM_RIGHTS holding an array of file descriptors. What crosses is emphatically not the numbers—a descriptor number is meaningless outside its own process. The kernel takes a reference on each underlying struct file, carries that reference in the queued socket buffer, and at recvmsg installs it into the receiver's descriptor table at whatever index happens to be free, reporting the new numbers back in the control message. The two processes end up sharing one open file description, with its shared file offset and status flags, exactly as a fork would have left them—except that these two processes need have no relationship at all. At most SCM_MAX_FD, which is 253, descriptors travel in one message (include/net/scm.h), and MSG_CMSG_CLOEXEC on the receive makes the arriving descriptors close-on-exec, which a careful receiver always sets because there is no other moment at which it could close the window before an exec.

What happens when the receiver's control buffer is too small deserves to be stated exactly, because the comfortable assumption is wrong and the consequence is silent. The kernel does not refuse the message and it does not defer the surplus. scm_detach_fds computes how many descriptors the supplied buffer can hold, installs exactly that many, and then drops the remaining struct file references on the floor. The receiver is told only by the MSG_CTRUNC flag in msg_flags, which a program that never inspects msg_flags will never see. So a sender can transfer eight descriptors, the receiver can collect three, and both can believe the exchange succeeded while five open files are quietly closed. This is the one place in the descriptor-passing design where the kernel's behavior is lossy, and the only defense is the unglamorous one: size the control buffer with CMSG_SPACE for the maximum the protocol allows, and treat MSG_CTRUNC as a fatal protocol error rather than a warning.

It is also worth knowing where the security decision is made, because the answer is once, at the receiving end. Installing each arriving descriptor goes through receive_fd, which calls the security_file_receive hook before it allocates a slot, so a module such as SELinux can refuse a transfer that its policy forbids. Nothing else is rechecked: the kernel does not ask whether the receiver could have opened the underlying file itself, and it does not consult the permissions on the file at all. That is precisely what makes the mechanism a capability rather than a shortcut—the authority travels with the object, and the receiver's own rights are irrelevant to what it may now do with it. The same control-message channel carries security labels in their own right, through SO_PASSSEC and its SCM_SECURITY messages or the one-shot SO_PEERSEC, and SO_PEERGROUPS returns the peer's supplementary groups, which a server needs when its access rules are written in terms of group membership rather than uid.

This descriptor passing is what makes capability-style design possible on Linux, and it is the concrete mechanism behind claims made earlier in this chapter. A privileged helper can open a file, a memfd, or a listening socket and hand the descriptor to a sandboxed process that has no path to it, no permission to open it, and possibly no filesystem at all; the sandbox receives the authority to use that one object and nothing more. It is how a browser's renderer gets its shared buffers, how a container manager hands a runtime its namespaces and its terminal, and how socket activation lets a service inherit an already-bound listening socket from its supervisor.

A socket can also carry the identity of its peer, which matters because the receiver of a request usually needs to know who is asking. With SO_PASSCRED set, each message arrives with an SCM_CREDENTIALS control message giving the sender's pid, uid, and gid, translated into the receiver's user namespace so that a container's root is not mistaken for the host's; the kernel fills these in itself, so they cannot be forged. SO_PEERCRED answers the simpler question once, returning the credentials the peer had at connect time, which is what a daemon typically wants for an access-control decision. The pid in those structures, though, is a raw number, and §6.4 explained precisely what is wrong with raw numbers: by the time the receiver acts on it, the sender may have exited and the pid been recycled. Linux therefore added peer credentials that are not numbers at all— SO_PASSPIDFD delivers an SCM_PIDFD control message carrying a pidfd instead of a pid, and SO_PEERPIDFD returns one for the connected peer. The receiver then holds a handle that can never refer to a different process, and the oldest identity-passing mechanism in Unix IPC is closed under the newest descriptor primitive in the chapter.

In-Flight Descriptors and Garbage Collection

Descriptor passing creates a problem with no counterpart anywhere else in this chapter, and solving it is the reason AF_UNIX is the one place in the kernel with a garbage collector of its own. A descriptor that has been sent but not yet received is in flight: its struct file reference is held by a socket buffer sitting in a receive queue. If the file in question is itself a Unix-domain socket, that reference is one socket holding another. Nothing prevents the references from forming a cycle—in the simplest case a socket sending its own descriptor to itself, in the general case a ring of sockets each holding the next. Every socket in such a ring has a nonzero reference count and so is never freed by fput, yet no process holds a descriptor for any of them, so the ring is unreachable. Reference counting alone cannot recover it; the memory and the descriptors leak until reboot. This is the classic cycle problem, arriving in the kernel by way of a feature that lets one object contain a reference to another.

net/unix/garbage.c exists to break those cycles, and the way it does so was rebuilt in recent kernels. The collector now maintains an explicit graph alongside the sockets: every socket with descriptors in flight is a vertex, every in-flight socket reference an edge, and unix_add_edges and unix_del_edges keep the graph current as messages are sent and received. Finding the garbage is then a standard problem—__unix_walk_scc runs Tarjan's algorithm to identify strongly connected components, and a component that is cyclic and whose vertices carry no references from outside it is unreachable by definition; its queued buffers go onto a hit list and are purged, dropping the file references and letting the sockets die. The rebuild replaced an older mark-and-sweep that scanned every in-flight socket on every run, and it brought a shortcut worth more than the algorithm: the graph records whether any cycle exists at all, so unix_schedule_gc can return immediately when the state is UNIX_GRAPH_NOT_CYCLIC. Since ordinary descriptor passing—a supervisor handing out a file, a sandbox receiving a memfd—never creates a cycle, the overwhelmingly common case pays nothing, and the collector runs only for the rare programs that actually build one.

Two further precautions surround the collector, and both are aimed at the same abuse: a process that sends descriptors and arranges for no one to receive them, pinning kernel memory indefinitely. The first is a hard cap. too_many_unix_fds compares the sending user's count of in-flight descriptors against that user's RLIMIT_NOFILE and fails the sendmsg with ETOOMANYREFS when it is exceeded, which is a rare enough errno that encountering it is usually a bug rather than a limit; CAP_SYS_RESOURCE or CAP_SYS_ADMIN lifts it. The second is a piece of deliberate unfairness in unix_schedule_gc. Beyond skipping the collection entirely when no cycle can exist, it also skips it for any user with fewer than SCM_MAX_FD × 8 descriptors in flight, so a normal program never triggers a scan at all; and for a user above that threshold it does not merely queue the work but waits for it with flush_work. The cost of collecting the garbage is charged to the process that is generating it, in the send path, rather than spread over every other user of the system. The comment in the source is blunt about the intent, and the design is a good example of a general principle: when a mechanism can be abused, make the abuser pay for the cleanup.

Summary

This chapter surveyed how User Mode processes communicate, starting from the classic mechanisms—pipes and FIFOs, System V IPC, POSIX message queues—and then extending the survey to the mechanisms that define modern Linux IPC. The oldest mechanisms endure but have been rebuilt underneath. The pipe kept its producer/consumer semantics and its PIPE_BUF atomicity, but its fixed 16-buffer ring became a resizable one whose page-referencing buffers turned the pipe into the kernel's general zero-copy conduit, exposed through the splice, tee, and vmsplice calls that did not exist before. System V IPC kept its key-and-identifier API but was re-implemented on an IDR and an rhashtable under RCU and per-object locks in place of a global lock, its semaphores given fine-grained per-semaphore locking, and its shared memory revealed as ordinary tmpfs files mapped and demand-faulted like any other. IPC namespaces, entirely new, let containers hold independent object sets.

The larger story is a shift in what a communication handle is. System V names its objects by an integer that is not a file descriptor—unpollable, uninherited, persistent until explicitly removed—and nearly everything added since has moved the other way. POSIX message queues are descriptors ordered by a red-black priority tree and can be epolled and notified asynchronously. POSIX shared memory and POSIX semaphores went further and dispensed with the kernel object altogether: of the whole POSIX IPC surface only the six mq_* calls are system calls at all, while shm_open, sem_open, sem_wait and sem_post are library functions built over tmpfs and futexes. The futex moved the common, uncontended case of a lock entirely into user space, touching the kernel only under contention, and became the foundation beneath every pthread mutex and POSIX semaphore, with priority-inheritance and robust variants for demanding uses; its own interface has since outgrown the single multiplexing call it began as, and its hash table has moved from one global array to a table per process. And a family of descriptor primitives— eventfd, signalfd, timerfd, memfd with sealing, and pidfd—turned counters, signals, timers, shared buffers, and even whole processes into file descriptors, so that one epoll loop can wait on all of them at once. The pidfd has outgrown notification in its turn: living on a filesystem of its own rather than on an anonymous inode, it can be compared with another pidfd, stored as a file handle, and asked for a child's exit status without consuming the zombie that waitid would. The Unix-domain socket completes that picture, because it is the one mechanism that can move a descriptor between unrelated processes, and it has followed the same trajectory itself: the identity it passes alongside the data is no longer only a pid but, with SO_PASSPIDFD, a pidfd. Its garbage collector is the price of that power, and the rebuilt collector's real achievement is that programs which never create a reference cycle now pay nothing for it. The through-line is unification: where Linux 2.6.11 treated process communication as a set of separate subsystems each with its own naming and waiting model, modern Linux has drawn them toward two organizing ideas—the file descriptor as the universal, epoll-able handle, and the futex as the universal user-space wait. Between them they explain nearly every design decision in this chapter: why the newer mechanisms are all descriptors, why the older ones look increasingly out of place, and why the one genuinely new capability that descriptors bring—passing a descriptor to a process that could not otherwise obtain it—turned out to matter more than any improvement in throughput. This chapter also closes the book's account of the kernel's classical core, which has run from memory addressing and process scheduling through interrupts, the virtual filesystem, the page cache, and the block and filesystem layers to the ways processes finally talk to one another. The chapters that follow turn to how a program is loaded and run, and then to the newer machinery that is reshaping the kernel from the outside in—eBPF, io_uring, the namespace and cgroup foundations of containers, and Rust.
