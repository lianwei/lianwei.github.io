Chapter 3 introduced the process as the kernel's unit of a running program; this chapter closes that loop by asking where a running program comes from. A program lives on disk as an inert executable file—a structured bundle of machine code, initial data, and metadata—and turning it into a live process is the job of the exec family of system calls. It sounds simple: load some instructions into memory and jump to them. But the kernel must cope with several kinds of flexibility at once. It supports more than one executable format, and can even run binaries built for other systems. Most programs are not self-contained but pull in shared libraries at run time. Every program expects its command-line arguments and environment to be waiting for it. And every exec is a privilege boundary—the moment a process may gain or shed authority, which the modern kernel guards with credentials, capabilities, and a stack of security frameworks.

This chapter covers executable files, their formats, and the exec functions in Linux 7.0.12. After an overview of what exec must accomplish, it covers the binary-format framework and the ELF format that now dominates; the execve/execveat pipeline that drives a file through that framework; the process memory layout it builds and the address-space randomization that protects it; libraries and the dynamic linker; the credential and capability model that governs privilege; and the security and sandboxing frameworks—LSM, seccomp, and Landlock—that increasingly define what a newly executed program is allowed to do. With a program becoming a process, the tour of the classic kernel is complete. The two chapters that follow close Part III with power management and networking, both already present in 2.6.11, and the seven chapters of Part IV—eBPF, io_uring, containers, Rust, the security infrastructure, KVM, and tracing and diagnostics—cover subsystems that did not exist, or barely existed, in 2.6.11.

From File to Process

The distinction between a program and a process is the starting point for everything in this chapter. A program is passive: a file on disk, a fixed sequence of bytes describing code and data that does nothing until something runs it. A process is active: a program in motion, with its own address space, registers, open files, and place in the system. The bridge between the two is the exec family of system calls, and this first section looks at that bridge from two angles before the later sections dig into the machinery. It asks what an execution context actually is—so that "running a program" has a precise meaning in terms of kernel state—and then what concrete work the kernel must perform to construct one from a file.

Keeping these two questions separate matters because they answer different things. The first is about identity and continuity: when a process execs a new program, what carries over and what is thrown away? A running process does not vanish and reappear; it persists as the same task, yet the program it runs is completely replaced. Understanding exactly which parts survive that replacement is what makes the mechanism comprehensible. The second question is about construction: given an open file, what must the kernel build before the first instruction of the new program can run? The answer is a short list of jobs that the rest of the chapter is organized around, and seeing that list up front turns the detailed sections that follow into a coherent whole rather than a sequence of unrelated subsystems.

The Execution Context

Before looking at what changes across an exec, it helps to fix what a running program consists of in the first place. A process is not just its code; it is a large bundle of kernel state, and running a program means having the kernel build and maintain that bundle on the program's behalf. Naming the pieces makes the rest of the section concrete.

Chapter 1 described a process as an execution context—the whole collection of state a computation needs: the pages it has mapped, the files it has open, the contents of the hardware registers, its credentials, and more. An executable file is, in this light, a recipe for initializing a fresh execution context. It does not contain a process; it contains enough information for the kernel to build one. When a process calls exec, it does not create a new process—the calling process survives, keeping its process id, its open files (except those marked close-on-exec), and its relationships—but its entire user-space context is discarded and rebuilt from the new file. The old address space is torn down, a new one is constructed, and execution restarts at the new program's entry point. This is the sharp line between fork, which duplicates a process, and exec, which replaces the program a process is running; the familiar fork-then-exec idiom of the shell uses both in sequence.

What survives an exec and what is replaced is worth stating precisely, because it defines the mechanism. The task_struct—the process itself— persists, so the pid, parent, controlling terminal, and open file table carry over. Everything that describes the program is replaced: the memory descriptor (mm_struct) and every memory region in it, the signal dispositions (reset, with one important exception the next paragraphs take up), the alternate signal stack, and much of the thread state. If the caller was multithreaded, all the other threads are destroyed—after exec the process is single-threaded again, running the new program. Credentials may change at this boundary, and the process's saved state is reset so that no secret of the old program leaks into the new one. Table 20-1 summarizes the division.

That exception is worth stating carefully, because it is the single most commonly misremembered fact about exec. The kernel calls flush_signal_handlers(me, 0) (kernel/signal.c), and the zero is the whole story: the loop sets every disposition to SIG_DFL unless it is currently SIG_IGN, in which case it is left alone. A signal the old program chose to ignore stays ignored in the new one. This is required behaviour rather than an oversight—it is what lets a shell run a background job with SIGINT and SIGQUIT ignored, knowing the setting survives into the command it execs—but it regularly surprises programmers who assume a fresh program starts with a clean slate, and it is a real source of bugs in daemons that forget to restore SIGPIPE before exec'ing a child. Three related pieces of state are handled differently again: the sa_flags, sa_mask, and sa_restorer of every entry are cleared unconditionally; the alternate signal stack is zeroed outright (sas_ss_sp and sas_ss_size both become zero), because it pointed into an address space that no longer exists; and the blocked signal mask and the set of already-pending signals are not touched at all, so a signal blocked before the exec arrives at the new program still blocked, and one delivered but not yet handled is still waiting.

The claim that the process survives is also true in a slightly stranger way than it first appears. If a non-leader thread calls exec, de_thread (fs/exec.c) does not merely kill the others: it makes the surviving thread become the old group leader. exchange_tids swaps the two thread ids, and the thread-group, process-group, and session pids are transferred across with transfer_pid, so that after the exec the pid the rest of the system knows is still the original one even though the task now answering to it is a different task_struct than the one that had it a moment earlier. The kernel goes so far as to copy the old leader's start_time onto the survivor, on the reasoning that the process's true age is the age of the thread group, not of whichever thread happened to call exec; the source comment makes the argument explicitly. The displaced leader is left as an EXIT_DEAD placeholder and reaped. One side effect is easy to miss: the surviving thread's exit_signal is set to SIGCHLD, so a task created by clone with some other termination signal reverts to the ordinary one the moment it execs.

The kernel also keeps an explicit record that an exec happened, in a counter called self_exec_id that begin_new_exec increments on the way past the point of no return. Two places consult it, and both are asking the same question: is the program I arranged this with still running? When a child exits, do_notify_parent (kernel/signal.c) compares the parent_exec_id the child recorded at fork against the parent's current self_exec_id, and if they differ it forces the termination signal back to SIGCHLD, on the grounds that the parent has since become a different program and the custom signal it once asked for would now be delivered to code that never requested it. The POSIX message-queue code of Chapter 19 uses the counter the same way: mq_notify records the registering task's self_exec_id and refuses to deliver the notification if it no longer matches. In both cases the pid is stable and therefore useless as an identity check; the exec counter is what distinguishes the process from the program.

Finally, a good deal of what exec severs has no counterpart at all in Linux 2.6.11, because the state did not exist. Reading begin_new_exec straight through turns up, in order: a cancellation of any outstanding io_uring work (io_uring_task_cancel), since submitted requests may reference the address space that is about to vanish; an unshare_files, so that a task which was sharing a descriptor table through CLONE_FILES stops sharing it at the exec boundary; a set_mm_exe_file that repoints /proc/<pid>/exe at the new binary; a commit of any pending time-namespace switch (exec_task_namespaces, which is how a setns into a time namespace takes effect only at the next exec); the destruction of every POSIX and interval timer the process owned (posix_cpu_timers_exit, exit_itimers, flush_itimer_signals); an unshare_sighand; a clearing of syscall user dispatch; and the clearing of PF_NO_SETAFFINITY, which quietly restores the ability to change the task's CPU affinity. When the exec is a privilege-raising one there are two more: pdeath_signal is zeroed so the old parent cannot signal the newly privileged process on its own death, and the stack limit is clamped to _STK_LIM so a hostile caller cannot shape the new program's layout by setting an absurd RLIMIT_STACK first. The task's comm—the sixteen-byte short name ps prints—is reset from the executable's base name at the same time.

The logic behind this split is that exec replaces the program but not the process. Anything that identifies the process to the rest of the system—its pid, its parentage, its process group and session, its controlling terminal—must persist, because other processes hold references to it that an exec should not invalidate; a shell that has forked a child and is waiting on its pid must still find that same child after it execs. Anything that belonged to the old program, by contrast, is meaningless to the new one and is discarded: the old code and data, the old heap and stack, and the old signal handlers (which pointed at functions that no longer exist). Open files sit deliberately in between—they survive by default, which is exactly what makes shell redirection work, since the shell arranges a child's file descriptors and then execs the command expecting them to remain—unless a descriptor is marked close-on-exec, the flag a program sets on handles it does not want leaking into the programs it launches. This survive/replace boundary is not incidental; it is the precise contract that lets fork+exec compose into the Unix model of launching programs.

What exec Must Build

Seen from the kernel side, an exec is an assembly line that takes an open file and produces a ready-to-run user context. Five things must be built or decided along the way, and the rest of this chapter is organized around them:

  • Identify the format of the file and find code that knows how to load it — handled by the binary-format framework (§2).
  • Map the program into a fresh address space: create a new mm_struct, map the file's code and data segments, and set up the heap and stack (§3, §4).
  • Arrange the dynamic linker: if the program is dynamically linked, load the linker so it runs first and pulls in the shared libraries (§2.3, §5).
  • Hand the program its inputs: the command-line arguments, the environment, and an auxiliary vector of kernel-supplied values, all laid out on the new stack (§3.4).
  • Settle the new program's privilege: compute its credentials and capabilities, apply any setuid transition, and let the security frameworks veto or constrain the exec (§6, §7).

Figure 20-1 shows the pipeline these five jobs form, from the execve system call down to the first user-space instruction of the new program. Underlying the whole flow is one hard constraint that shapes the design: at a certain step the kernel tears down the caller's old address space, and past that point of no return the exec can no longer fail cleanly—there is nothing left to return to. Everything that can fail (opening the file, checking permissions, parsing the header, preparing credentials) must therefore happen before that point, and everything after it must succeed or the process is killed. This constraint recurs throughout the chapter.

There is a sixth job that no list of this kind usually names, because it is subtraction rather than construction: everything the old program held has to be let go, and doing that safely is harder than it sounds. Some of it is obvious— the address space, the other threads. Most of it is not. A descriptor marked close-on-exec has to be closed after the credentials are decided but before the process becomes dumpable under a new identity, or a watcher could reach the should-be-closed descriptors of a process in the middle of an exec; the kernel comments on exactly that ordering constraint at the call site. Timers have to be destroyed rather than merely disarmed, because a POSIX timer holds a sigevent that may name a thread that is about to be killed. Asynchronous work already submitted to io_uring has to be waited out, because it may hold references into the address space that is about to be unmapped. None of these are things the new program asked for; they are debts the old one left, and the sixth job is settling them.

One more structural fact is easiest to state here, before the detail arrives. The irreversible phase is not one function but three, called by the loader in sequence: begin_new_exec, setup_new_exec, and finalize_exec, all in fs/exec.c. The split is not arbitrary. begin_new_exec does the tearing down and the committing, and along the way calls flush_thread, which on some architectures is the first moment the kernel knows whether the new program is 32- or 64-bit—so setup_new_exec has to run afterwards to pick the memory-mapping layout and set mm->task_size, both of which depend on that answer. finalize_exec then runs last, immediately before the loader hands control to user space, and does almost nothing except store the stack resource limit, because a privilege-raising exec may have clamped it partway through and the value that matters is the final one. Reading the ELF loader with these three landmarks in mind (§3.3) turns a long function into four short phases.

The five constructive jobs also explain why the chapter is ordered as it is. Formats come first (§2) because the kernel cannot do anything with a file until it knows how to read it. The exec pipeline (§3) then drives a file of a known format through loading, which naturally produces the memory layout (§4) and depends on the libraries and dynamic linker (§5) that fill it in. Privilege and security (§6, §7) come last not because they happen last—several of their checks run early, before the point of no return—but because they cut across the whole pipeline: every stage can be observed or vetoed by the credential rules and the security frameworks. Read in this order, the sections trace a single file's journey into a running, constrained process.

Executable Formats

The first thing exec must decide about a file is what kind of file it is—because "run this" means something different for a compiled ELF binary, a shell script, and a Java class file. Rather than build that knowledge into the exec path, Linux treats the question as an extensibility problem: it defines a uniform interface for "a thing that knows how to run some kind of file," and lets an open-ended set of format handlers plug in behind it. This section describes that framework and the handlers built on it. It begins with the plug-in interface and the dispatcher that chooses among handlers, then covers the two handlers that redirect to an interpreter rather than loading code directly—scripts and the user-configurable binfmt_misc—and finally the ELF format itself, which is what nearly every native Linux program actually is.

The pattern is worth noticing because it recurs throughout the kernel: define a small table of function pointers, let implementations register themselves, and dispatch through the table. The virtual filesystem does it for filesystem types, the block layer for I/O schedulers, the network stack for protocols. Applied to execution, it means the core exec code never needs to know how ELF or scripts work—it only knows how to ask each registered handler "can you run this?" and use the first one that says yes. That indirection is what lets Linux support foreign binaries, interpreted languages, and emulated architectures through the same execve a native program uses.

The Binary-Format Framework

Linux does not hard-code knowledge of any one executable layout. Instead it defines a small plug-in interface, struct linux_binfmt (include/linux/binfmts.h), and lets each supported format register a handler. The structure has shrunk to almost nothing: a list hook, a module reference, load_binary to load an executable, and—only when CONFIG_COREDUMP is enabled—core_dump to write a core file and a minimum dump size. The load_shlib pointer of Linux 2.6, which backed the ancient uselib system call for loading a.out shared libraries, has been removed along with the rest of that machinery; a modern shared library is mapped by the dynamic linker with mmap and the kernel has no library-loading entry point at all. Formats add themselves to a global formats list with register_binfmt (fs/exec.c), and the built-in ones register at boot: binfmt_elf, binfmt_script, binfmt_misc, and on some configurations binfmt_elf_fdpic and binfmt_flat (the two no-MMU loaders). This is the same extensibility pattern the filesystem and device layers use, applied to the question "how do I run this file."

Registration takes a side, and the side is load-bearing. The real entry point is __register_binfmt(fmt, insert): with insert zero it appends the format to the tail of the list, with insert nonzero it puts the format at the head. The wrappers register_binfmt and insert_binfmt (include/linux/binfmts.h) are the two halves of that choice, and in the whole tree exactly one format asks to go first: binfmt_misc. That is deliberate. Everything else appends in link order — binfmt_script, then binfmt_elf, then the no-MMU loaders — so the list a running kernel walks is administrator rules first, shebangs second, ELF third. Putting the user-configurable format ahead of the native one is what makes binfmt_misc able to override a format the kernel already understands: a rule can claim ELF files whose machine type is foreign and route them to an emulator, which would be impossible if binfmt_elf saw them first.

The dispatcher is search_binary_handler() (fs/exec.c). It walks the formats list and offers the file to each handler's load_binary in turn. A handler inspects the first bytes of the file—the kernel has already read the first BINPRM_BUF_SIZE (256) bytes into bprm->buf—and either recognizes the format and loads it, or returns -ENOEXEC to mean "not mine, try the next." The first handler that succeeds wins; if the list is exhausted the exec fails with ENOEXEC. This chain is also what makes indirect execution work: a script handler does not run the file directly but rewrites the request to run its interpreter, and the dispatch runs again on that interpreter—so ./script ultimately loads /bin/bash through binfmt_elf.

One long-standing piece of that walk is gone, and its absence is worth stating because the old behavior is still widely described. The 2.6.11 dispatcher, on failing to find an owner, called request_module("binfmt-%04x", ...) with two bytes lifted out of the file's own header and then retried the whole list, hoping user space would supply a module that recognized the magic. In 7.0.12 request_module does not appear in fs/exec.c at all. A format must be built in or already loaded before it can claim anything; demand-loading a loader on the strength of bytes taken from the file being executed is no longer something the kernel will do. The walk is now a single pass and nothing more.

The pass itself is short enough to describe exactly. prepare_binprm and security_bprm_check run once, before the loop, not per handler — the LSM sees the file the caller named, not each candidate format's opinion of it. Then, under the binfmt_lock read lock, each entry is pinned with try_module_get, the lock is dropped across the load_binary call, and the result decides whether to continue. The continue condition is the interesting part: the walk stops not only when a handler succeeds, but whenever bprm->point_of_no_return is set, even on failure. Once a loader has called begin_new_exec and dismantled the old address space there is no old program left to fall back to, so a later error must be reported as a fatal one rather than as "not mine, try the next." That single flag is what keeps a half-completed load from being silently handed to another format.

Two practical details make the framework robust. The first handler to accept a file wins, and the tests are cheap — the script handler's two-byte #! comparison and ELF's four-byte magic are fast rejections for files that are not theirs. The BINPRM_BUF_SIZE buffer the kernel pre-reads is deliberately small (256 bytes) but large enough to hold any format's identifying header and a full shebang line, so a handler can almost always decide from bprm->buf alone without additional reads. And because a handler that rewrites the request (a script or a binfmt_misc rule) sends the dispatcher around again, the framework guards against loops—an interpreter that is itself a script pointing back at the original would otherwise go around forever—by bounding how many times the interpreter can be re-resolved. The result is a small, self-contained mechanism that turns "run this file" into "find the handler that owns it," with the loader details entirely on the handler side. Figure 20-2 traces the dispatch.

It is worth being precise about how that re-resolution actually happens, because the mechanism is flatter than the word "recursion" suggests and flatter than it once was. A redirecting handler does not call back into the dispatcher. It opens its interpreter, stores the resulting file in bprm->interpreter, and returns success. The loop lives one level up, in exec_binprm (fs/exec.c): after each call to search_binary_handler it checks whether an interpreter was left behind, and if so promotes it — bprm->file = bprm->interpreter — and goes around again with the same bprm. The bound is a plain loop counter: the loop refuses to make a seventh pass and fails the exec with ELOOP, which allows five interpreter rewrites before the kernel gives up. So the stack depth of an exec is constant no matter how many layers of script and binfmt_misc rules a file hides behind; only a counter grows. The displaced file is not simply dropped, either. If the format asked for the binary to be passed as an open descriptor, the original bprm->file is moved to bprm->executable and survives to be installed as a file descriptor in the new program; otherwise it is closed on the spot. Asking for that twice is an error — only one executable can be carried through — and the kernel returns ENOEXEC.

Scripts and Miscellaneous Formats

Two of the registered formats do not load machine code at all; they redirect to an interpreter. binfmt_script (fs/binfmt_script.c) implements the familiar shebang: if a file begins with the two bytes #!, load_script reads the rest of that first line as an interpreter path plus an optional single argument, and rewrites the exec so that the interpreter runs with the script's pathname appended to its arguments. After the rewrite the dispatcher runs again and loads the interpreter (usually itself an ELF binary), which then opens and reads the script as ordinary data.

Only the first BINPRM_BUF_SIZE bytes of the file are available to load_script, and what it does when the shebang line runs past them is a detail worth getting right, because the obvious answer is wrong. It does not truncate the interpreter path. Running a prefix of a pathname is a security hazard — /usr/local/bin/python3 cut short could name some other, more permissive binary — so the handler refuses unless it can prove the path is complete. It looks for a newline within the buffer; failing that, it looks for a space, tab, or NUL after the path, either of which proves the path ended before the buffer did. If it finds neither, it returns -ENOEXEC and the exec fails rather than launching something the author did not write. The argument after the path is treated differently and may be truncated without complaint, on the reasoning that the interpreter can always reopen the script and parse its own first line. A file consisting entirely of #! followed by whitespace is rejected for the same reason.

A subtle but important point is what the interpreter actually receives. After the rewrite, the interpreter is exec'd with an argument list that begins with the interpreter path, then the optional shebang argument, then the original pathname of the script—so bash is handed the script's name and opens it itself. This is why a script is not required to be readable as an executable in the way a binary is; the kernel never runs its contents, it only hands the name to the interpreter. It also has a security consequence the kernel is careful about: if the script was reached through a path the caller could not otherwise open (for example an execveat on an O_PATH descriptor), the handler refuses, because otherwise a script could be used to bypass access controls on its own file. The flag carrying that condition is BINPRM_FLAGS_PATH_INACCESSIBLE, set in fs/exec.c when the exec was reached by a descriptor rather than a resolvable name, and it is honored by both redirecting formats: binfmt_misc checks it too, and returns ENOENT rather than hand an interpreter a path it could not open. Only a single argument is allowed on the shebang line, and it is passed as one word—splitting on spaces is a shell behavior, not a kernel one, which is a common source of confusion.

binfmt_misc (fs/binfmt_misc.c) generalizes this to arbitrary formats, configured from user space through /proc/sys/fs/binfmt_misc. An administrator registers a rule that matches a file either by a magic byte sequence at some offset (with a mask) or by filename extension, and names an interpreter to run. This is how a Linux system transparently runs Java .class files through a JVM, Windows .exe files through Wine, or foreign-architecture binaries through an emulator such as QEMU—typing the filename just works because binfmt_misc recognizes it and invokes the right interpreter.

Four flags on a rule tune the behavior, and each corresponds to a specific problem emulation runs into. By default load_misc_binary calls remove_arg_zero and rebuilds the argument list as the interpreter followed by the path of the matched file, which means the program sees an argv[0] the kernel chose; P preserves the caller's original argv[0] instead, so a program that inspects its own invocation name — the busybox idiom, or a shell deciding whether it is a login shell — still behaves correctly under emulation. O hands the matched file to the interpreter as an already-open file descriptor rather than as a path, which is what lets an emulator run a binary the rule can see but the interpreter's own view of the filesystem cannot reach. F goes further and opens the interpreter at registration time, cloning that open file for every later exec, so the emulator remains reachable even inside a container whose root does not contain it — this is the flag that makes multi-architecture container images work without installing QEMU into each one.

The fourth flag, C, is the one most often misdescribed, because it implies O and so looks like a variant of it. It is not about file descriptors; it is about credentials. Normally the setuid and setgid bits that matter are those of the file the kernel will actually load, which after the rewrite is the interpreter — so a setuid foreign binary run through an emulator would silently lose its privileges, because the emulator itself is not setuid. Setting C sets bprm->execfd_creds, and bprm_creds_from_file then computes the new credentials from bprm->executable, the original matched binary, instead of from bprm->file. The effect is that a setuid emulated binary behaves like a setuid native one. That is a deliberate and sharp-edged decision: it makes the emulator a privilege boundary, and a rule carrying C is trusting the interpreter with whatever the matched files can escalate to.

The registration format is a colon-delimited line written to a control file: a name, whether to match by magic or extension, the offset, the magic bytes, a mask, the interpreter, and the flags. Each rule appears as a file under /proc/sys/fs/binfmt_misc that can be examined or disabled, so an administrator can see and manage exactly which foreign formats the system will run. Despite the path, this is not sysctl territory: binfmt_misc is a filesystem type of its own, registered alongside the format handler and conventionally mounted at that location. Because it is declared with FS_USERNS_MOUNT and the rule set hangs off a binfmt_misc pointer in struct user_namespace (include/linux/user_namespace.h), the rules are per-user-namespace: a container can mount its own instance and register its own emulators without affecting the host, and an unprivileged user namespace can do so without any privilege on the host at all. The most consequential use is transparent cross-architecture execution: with QEMU user-mode registered through binfmt_misc, an ARM64 binary runs on an x86-64 host as if native—the kernel recognizes its ELF magic and machine type, hands it to the emulator, and the user never invokes QEMU explicitly. This is the mechanism behind multi-architecture container builds and foreign-binary testing, and it is the modern realization of the "run binaries from other systems" flexibility that Linux 2.6 provided through execution domains and personalities.

The ELF Format

The format that matters most is ELF—the Executable and Linkable Format—which is now the native format for essentially every Linux binary, shared library, and core dump. (The old a.out format, still supported in Linux 2.6, has been removed from the mainline kernel.) An ELF file begins with an ELF header (struct elfhdr) whose first four bytes are the magic 0x7F E L F, followed by fields giving the class (32- or 64-bit), the target architecture, the file type, and the entry point—the virtual address of the first instruction. The kernel validates the magic and calls elf_check_arch to confirm the binary is built for this machine before going further.

The full entry test in load_elf_binary (fs/binfmt_elf.c) is five questions, all answered from the 256 bytes already in bprm->buf and all answered with -ENOEXEC on failure, and the last two are more recent than the others. The magic must match ELFMAG. The file type must be ET_EXEC or ET_DYN and nothing else — a relocatable object or a core dump is rejected here, which is why an unlinked .o file is not executable no matter what its permission bits say. elf_check_arch must accept the machine type. elf_check_fdpic must reject it, because FDPIC binaries belong to binfmt_elf_fdpic and this is how the two ELF loaders divide a shared magic number between them. And can_mmap_file must be true: a file on a filesystem that cannot support private file-backed mappings cannot be executed at all, because every PT_LOAD segment is an mmap and there is no fallback that reads the program into anonymous memory.

The name Executable and Linkable Format hints at ELF's dual nature, and the distinction clarifies what the kernel does and does not care about. An ELF file carries two parallel views of its contents. The section view—a table of many fine-grained sections (.text, .data, .symtab, relocation tables, debug info)—is what the linker uses when combining object files, and what a debugger reads. The segment view—the program header table—is what the loader uses at run time, grouping those sections into a handful of coarse segments that get mapped into memory. At execution time the kernel ignores the section view entirely: it reads only the ELF header and the program headers. This is why a binary can be stripped of its symbol and debug sections and still run perfectly, and why the loader is so simple compared to the linker—it has only a few segments to map, not hundreds of sections to resolve.

Two ELF header type values matter for execution. ET_EXEC is a classic position-dependent executable, linked to load at fixed virtual addresses. ET_DYN is a position-independent executable (PIE) or a shared library, which can be loaded at any base address—the property that lets the kernel randomize where it lands. Modern distributions compile executables as PIE by default precisely so that address-space randomization (§4.3) applies to the main program, not just its libraries, which is a significant change from the 2.6-era world of fixed ET_EXEC binaries.

The information the loader actually needs lives in the program header table: an array of struct elf_phdr entries, each describing a segment—a contiguous piece of the file to be mapped or otherwise handled at run time. Each program header gives a type, the file offset, the virtual address, the size in the file and in memory (which differ for the BSS), and the permission flags (read, write, execute). Table 20-2 lists the program-header types that govern how a program is laid out, and Figure 20-3 shows how the pieces of an ELF file map into a running process.

The third column of Table 20-2 draws a line that is easy to lose. Only four of these types are ever examined by kernel code, and a grep for PT_ in fs/binfmt_elf.c finds exactly that set plus PT_NOTE, which the loader uses only when it is writing a core dump. PT_GNU_RELRO and PT_DYNAMIC never reach the kernel at all; they are instructions to the dynamic linker, carried in the same table because that is where the loader of last resort can find them. The architecture-private range is the exception that proves the rule: the kernel does not interpret those headers either, it simply hands each one to arch_elf_pt_proc, once for the executable and again for its interpreter, and then gives the architecture a final arch_check_elf once every header has been seen — a two-phase hook that exists because some decisions (MIPS floating-point ABI selection is the classic case) cannot be made until both files have been inspected.

Several program-header types carry modern hardening information the loader acts on. PT_GNU_STACK records whether the program needs an executable stack—almost never, so the kernel normally maps the stack non-executable, a basic defense against injected shellcode. PT_GNU_RELRO marks a region (typically the relocated global offset table) that the dynamic linker should make read-only after relocation, closing a class of GOT-overwrite attacks. One last asymmetry closes the section. binfmt_elf is the only format in the tree that is a full participant in both directions of struct linux_binfmt: it supplies load_binary to read ELF files and, under CONFIG_COREDUMP, elf_core_dump to write one, with min_coredump set to ELF_EXEC_PAGESIZE so that a dump smaller than a page is not worth producing. A core file is an ELF file of type ET_CORE — the one type the loader refuses to execute — whose PT_LOAD segments are the dying process's mappings and whose PT_NOTE segment carries the register sets, the signal that killed it, and the auxiliary vector the program was started with. The format the kernel reads at the beginning of a process's life is the same one it writes at the end, which is why a debugger can open an executable and its core dump with a single piece of parsing code.

The exec System Calls

The previous sections established the pieces exec works with—the format framework that recognizes a file and the ELF layout it loads. This section follows the machinery that ties them together: the actual system calls a program invokes to replace itself, and the kernel pipeline they set in motion. It is the heart of the chapter, because it is where the abstract "turn a file into a process" becomes a concrete sequence of steps with a precise structure.

That structure is dominated by one idea introduced in §1: the point of no return. An exec cannot be a simple "do the work and report success or failure," because partway through it destroys the very context that a failure would return to. The kernel therefore splits the work into a long reversible phase—where anything that can go wrong is checked while the caller's program is still intact—and a short irreversible phase that must not fail. Almost everything interesting about the pipeline follows from this split, and the subsections trace it in order: first the system-call entry points that start an exec, then the pipeline and its point of no return, then the ELF loader that runs inside it, and finally the stack the loader hands to the new program. Together they answer, step by step, what happens between calling execve and the first instruction of the new program.

execve, execveat, and fexecve

User space starts an exec through a small family of system calls. The classic one is execve(pathname, argv, envp): run the program at pathname, passing the argument vector argv and environment envp. The libc execl, execlp, execvp, and friends are all thin wrappers that marshal their arguments and ultimately call execve. Modern Linux adds execveat(dirfd, pathname, argv, envp, flags) (fs/exec.c), which resolves pathname relative to an open directory descriptor dirfd and accepts flags such as AT_EMPTY_PATH (execute the file dirfd itself refers to) and AT_SYMLINK_NOFOLLOW. A third flag, AT_EXECVE_CHECK, is newer and inverts the call's purpose: it asks the kernel to run every check an exec of this file would run—permission, security module, the whole verdict—and then return instead of executing anything, setting bprm->is_check so the pipeline stops short. It exists for interpreters. A shell or a script engine about to run a file as code has no way to ask the system's execution policy whether that file is trusted, because it never calls execve on it at all; AT_EXECVE_CHECK gives it exactly that question to ask, so that a policy which forbids executing a downloaded file can also forbid sourcing it. It is worth being precise about how far such a call gets, because the answer bounds what it can tell you. bprm_execve runs the unsafe-state analysis, the scheduler hook, and security_bprm_creds_for_exec, and then, seeing is_check, jumps straight to the exit — it never reaches exec_binprm, so no format handler ever looks at the file. The question answered is "would this system's policy let me run this," not "is this a runnable binary." A shell asking about a shell script gets a verdict, which is exactly the point. With AT_EMPTY_PATH, execveat gives the POSIX fexecve its natural implementation—executing a program by an already-open file descriptor rather than by name. This matters for security: a program that has verified a file descriptor can execute exactly that file, closing the time-of-check-to-time-of-use gap where a path could be swapped between the check and the exec.

All of these converge on one internal routine, do_execveat_common, which counts the arguments, builds the kernel's working state, and drives the pipeline. The three visible entry points differ only in how they name the file—by path, by directory-relative path, or by descriptor—but share the entire loading machinery below. The descriptor case leaves a visible trace: when there is no pathname to report, the kernel synthesizes one of the form /dev/fd/n into bprm->fdpath, and that synthetic name is what later appears as the program's name and travels to user space in AT_EXECFN.

The first thing do_execveat_common does has nothing to do with loading a program, and the reason is a small monument to defensive kernel design. If the calling task carries PF_NPROC_EXCEEDED, the kernel rechecks RLIMIT_NPROC and, if it is still exceeded, fails the exec with EAGAIN. The flag was set earlier, by a set*uid() call that should have failed because the target user already had too many processes. The comment in the source says why it did not: too many programs ignore the return value of setuid(), and a program that believes it dropped privilege when it did not is far more dangerous than one that cannot start a child. So the kernel lets the set*uid() succeed, remembers the debt on the task, and collects it at the next execve — the point where a careless program is about to hand control to something else and where a refusal is impossible to ignore.

A second piece of hardening sits at the other end of the same function and did not exist in Linux 2.6.11. Nothing prevents a caller from passing an empty argv, and for decades the kernel obliged, starting the program with argc of zero. That is legal and almost never expected: a great deal of code reads argv[0] as the program name and begins option parsing at argv[1], so with an empty vector it walks off the end of argv and straight into the environment, where an attacker controls every string. That is precisely the shape of the 2021 pkexec vulnerability. In 7.0.12 the kernel refuses to hand out the ambiguity: if bprm->argc is zero after the strings are copied, it appends an empty string, sets argc to one, and emits a one-time warning naming both the launching and the launched program. The program still sees an odd argv[0], but it sees a valid array.

One property of these calls surprises programmers meeting them for the first time: on success, execve does not return. There is no code after a successful execve to run, because the program that called it no longer exists—its instructions have been replaced. Control resumes instead at the new program's entry point. A return from execve therefore always signals failure, with errno explaining why (the file was not found, was not executable, had an unrecognized format, and so on). This one-way behavior is the user-space face of the point-of-no-return design: the kernel guarantees that if it is going to fail, it fails before replacing the caller, so a returning execve is always safe to handle. It is also why the shell's child, after fork, calls execve and then—only if it returns—prints an error and exits: reaching the line after execve means the command could not be run.

The Exec Pipeline and the Point of No Return

The kernel carries the state of an in-progress exec in a binary parameter structure, struct linux_binprm (include/linux/binfmts.h). It holds the open file, the new memory descriptor mm and the current stack pointer p within the temporary stack, the argument and environment counts, the first BINPRM_BUF_SIZE bytes of the file (buf), the credentials being prepared for the new program (cred), and a set of flags including secureexec and point_of_no_return. This one structure threads through every stage, accumulating the decisions that will define the new process.

A few of its other fields repay a closer look, because each records a decision made in one stage and consumed in another. There are three names, not one: filename is the name the process will appear under, interp is the name of the binary actually executed (they differ once a script or a binfmt_misc rule has redirected the exec), and fdpath is the synthetic /dev/fd/n manufactured for an execveat by descriptor. Two file pointers accompany them, interpreter for the file the next dispatch pass should load and executable for the original binary held back to be passed as a descriptor. unsafe accumulates a mask of LSM_UNSAFE_ bits for the security modules to consult, per_clear records which personality bits the format wants dropped, argmin is the watermark copy_strings checks the argument block against, and rlim_stack is a saved copy of RLIMIT_STACK so that a change made during the exec cannot move the target underneath the code that is laying out the stack. The six single-bit flags are all of the form "a decision taken early that something later must honor," and the structure is annotated __randomize_layout so its field order is not a stable target. Its lifetime is managed by a scope-based cleanup class, so the dozen early returns scattered through the pipeline free it automatically rather than each having to remember.

The open that starts everything is already a policy checkpoint. do_open_execat opens the file read-only but with __FMODE_EXEC set and an access mode of MAY_EXEC, so permission checking asks the execute question rather than the read question — which is why a file can be executable without being readable. It accepts exactly three AT_ flags and rejects anything else with EINVAL, and AT_SYMLINK_NOFOLLOW works by clearing LOOKUP_FOLLOW from the lookup. Two checks then run on the opened file. path_noexec() rejects it with EACCES if the mount carries noexec — note that this is a property of the mount, not the file, so the same inode reached through a different mount may well be executable. Finally exe_file_deny_write_access() takes the write-deny reference on the inode, and this is the origin of an error every developer has seen: ETXTBSY, "text file busy," returned to whoever tries to write the binary while an exec of it is in flight or a process is running it. The reference is released again on failure, and on success when the file is displaced by an interpreter or when the process finally exits.

The pipeline (fs/exec.c) runs in a deliberate order so that everything fallible happens first. alloc_bprm opens the file (do_open_execat) and, through bprm_mm_init, creates a brand-new mm_struct with a single-page temporary stack at the top of the address space—note that the caller's address space is untouched at this point. do_execveat_common then copies the strings onto that temporary stack from the top down (copy_strings), one page at a time, faulting each page of the new stack in as it goes. The order is worth noting because it fixes the layout the program will eventually see: the filename goes first and its address is saved in bprm->exec (this later becomes AT_EXECFN), then the environment, then the arguments — so on a stack that grows downward the argument strings end up below the environment strings, which is the arrangement every C runtime assumes. This is where the familiar E2BIG comes from: a single string may not exceed MAX_ARG_STRLEN (32 pages), and bprm_stack_limits caps the argument and environment block as a whole at a quarter of the stack rlimit or three quarters of _STK_LIM, whichever is smaller, with a floor of the historical ARG_MAX so that a small stack limit cannot make ordinary command lines fail. The pointer arrays are counted against that budget too, because they will occupy the same stack later, at a point where the failure could no longer be reported. Next, bprm_execve prepares the new credentials (prepare_bprm_creds) and invokes the security framework's bprm_creds_for_exec hook, then calls search_binary_handler to choose and run a format's load_binary. Everything to here is reversible: if any step fails, the new mm is discarded and the caller returns from execve with an error, still running its original program.

Between preparing the credentials and consulting the security framework, bprm_execve runs check_unsafe_exec, whose job is to decide whether this is a safe moment to gain privilege. It sets LSM_UNSAFE_PTRACE if the task is being traced and LSM_UNSAFE_NO_NEW_PRIVS if the no-new-privileges bit is set, and then counts how many tasks share the caller's fs_struct. If anyone outside the thread group does, it sets LSM_UNSAFE_SHARE: a differently privileged task that can change the current directory out from under a setuid exec is an obvious hazard, and the security modules are told so rather than left to notice. If nobody does, the kernel takes the opposite action and sets fs->in_exec, which makes a concurrent clone(CLONE_FS) fail until de_thread has finished. That flag is the other half of a handshake met in §1: the current->fs->in_exec = 0 early in begin_new_exec is not an initialization, it is the release of a lock taken here, several stages earlier and in a different function.

One more call in this window is easy to miss and worth understanding, because it is the scheduler taking advantage of exec rather than the other way around. Immediately before the load, bprm_execve calls sched_exec(), which asks the load balancer whether this task should move to a different CPU. Exec is the single cheapest instant in a task's life to migrate it: the old address space is about to be discarded and the new one has not been populated, so there is no resident working set, no warm cache, and nothing to drag across. A migration that would be expensive at any other moment costs almost nothing here, so the balancer is given one free chance to correct a bad placement.

The turning point is begin_new_exec(), which the chosen loader calls once it has decided it can run the file. This function performs the irreversible work: it computes the final credentials from the file (bprm_creds_from_file), kills every other thread of the process (de_thread), installs the new address space in place of the old one (exec_mmap, which drops the caller's mm), resets signal handlers, clears the affected personality bits, closes close-on-exec descriptors, and finally commits the new credentials (commit_creds). The moment it sets bprm->point_of_no_return and tears down the old mm, there is no program to return to. From here a failure cannot be reported. bprm_execve's error path checks point_of_no_return and, if a fatal signal is not already pending, calls force_fatal_sig(SIGSEGV) — the process is killed rather than told. A fatal signal that is already pending is used as-is, so a process killed while its exec was in flight reports the real cause rather than a manufactured segmentation fault. This is why the design so carefully front-loads all validation: the kernel confirms the file is runnable, the permissions pass, and the credentials and security hooks approve before it destroys the caller. Figure 20-4 traces the flow.

The design's key trick is building the new address space alongside the old one rather than modifying it in place. Throughout the reversible phase the kernel accumulates its work—the new mm, the temporary stack, the copied arguments, the prepared credentials—in the linux_binprm and a fresh, detached mm_struct, never touching what the caller is currently running on. This is what makes clean failure possible: to abort, the kernel simply frees the half-built new context and the caller continues, none the wiser. Only exec_mmap, deep inside begin_new_exec, swaps the new mm in for the old and releases the old one. The cost is transient—two address spaces exist for a moment—but the payoff is that the expensive and fallible construction is fully undoable until the single, atomic switch. It is the same prepare-then-commit discipline the credential model (§6) and the journaling filesystems (Chapter 18) use, applied to an entire address space.

Loading an ELF Binary

When the file is an ELF binary, the loader is load_elf_binary() (fs/binfmt_elf.c), the most important load_binary in the kernel. Before the point of no return it re-validates the header and architecture, reads the full program header table, and—if a PT_INTERP entry is present—reads the dynamic linker's pathname and opens that interpreter file too, validating it as a second ELF. It also parses PT_GNU_PROPERTY for the architecture security features. Only then does it call begin_new_exec, crossing into the irreversible phase.

After that, it maps the program. It iterates the program headers and, for each PT_LOAD segment, calls elf_map to mmap the corresponding file region at its virtual address with the segment's permissions—the text segment read-execute, the data segment read-write. Where a segment's memory size exceeds its file size (the BSS), the loader zero-fills the remainder with padzero and extends the mapping with vm_brk_flags. For a position-independent executable it chooses a load bias—a base address to add to every segment's address—by a rule that turns on whether the program has an interpreter, taken up below. If there is an interpreter, the loader maps it too (load_elf_interp) at an mmap'd base and sets the program's entry point to the interpreter's entry rather than the executable's, so the dynamic linker runs first. With everything mapped, create_elf_tables builds the initial stack contents (next subsection) and start_thread sets the user registers—stack pointer and entry address—and returns into user space at the new program's first instruction.

The load bias deserves the detail, because the common summary — "a PIE is placed at ELF_ET_DYN_BASE plus a random offset" — is true of only one of the two cases, and the kernel is explicit about why. That path applies when the executable has a PT_INTERP: load_bias starts at ELF_ET_DYN_BASE, gains arch_mmap_rnd() if PF_RANDOMIZE is set, is rounded down to any alignment the program headers demand, and the mapping is made with MAP_FIXED_NOREPLACE. A static PIE — an ET_DYN object with no interpreter, which includes the dynamic linker itself when it is invoked directly — takes the other branch and gets a load_bias of zero, meaning the kernel names no address at all and lets mmap place the image at the architecture's own (already randomized) mmap base. The reason is the case of running ./ld.so someprog to test a new loader: the loader and the program it goes on to load must not compete for the same range, so programs are placed at ELF_ET_DYN_BASE and loaders are placed in the mmap region. Both are randomized; they are randomized independently, which is the property that matters.

Two mechanisms keep that placement honest. Before mapping the first segment the loader computes total_mapping_size, the span from the start of the first PT_LOAD to the end of the last, and makes the first mmap that large, unmapping the tail immediately afterward. Reserving the whole span up front is what prevents randomization from dropping a later segment on top of something already placed, and the unmap is what allows ELF images with holes between their segments. And the mapping flag is MAP_FIXED_NOREPLACE rather than the older MAP_FIXED: where MAP_FIXED would silently replace whatever already occupied the address, MAP_FIXED_NOREPLACE fails with EEXIST, and the loader logs the collision and aborts the exec. A malformed or hostile ELF with overlapping PT_LOAD segments therefore fails to run instead of quietly clobbering part of its own image. The loader also honors an unusually large p_align through maximum_alignment, which is how binaries built for huge-page-backed text get the alignment they need.

The interpreter handoff is worth dwelling on, because it explains a fact that puzzles newcomers: for a dynamically linked program, the address in ELF header → e_entry is not where the CPU first lands. When a PT_INTERP is present, the kernel loads two ELF objects—the executable and the dynamic linker—and sets the process entry point to the linker's entry, passing the executable's real entry down in the auxiliary vector as AT_ENTRY. So the first user instruction of a dynamic program belongs to ld-linux, which resolves libraries and only then jumps to the program's main path (§5). A statically linked program has no PT_INTERP, so its own e_entry is used directly. There is also a bootstrapping subtlety: the dynamic linker is itself an ELF shared object, but it is written to be self-relocating, because nothing else is loaded yet to relocate it—it must fix up its own references using only the information the kernel left on the stack and in the auxiliary vector. This is why the kernel's job ends at "map both objects and jump to the linker"; everything else the running program needs, the linker assembles itself.

Building the Stack: argv, envp, and the Auxiliary Vector

Before the program runs, the kernel must place its inputs where the C runtime expects them: at the very top of the new stack. This layout is built by create_elf_tables (fs/binfmt_elf.c), working downward from the top of the stack. It writes the argument count argc, then the array of argv pointers terminated by a null, then the array of envp pointers terminated by a null, and finally the auxiliary vector—a set of key/value pairs the kernel uses to hand the program (and especially its dynamic linker) values it could not otherwise know. The strings those pointers reference sit just above, copied there earlier from the caller. When the program starts, its stack pointer points at argc, and the C startup code walks up from there to find everything. Figure 20-5 shows the layout and Table 20-3 lists the key auxiliary-vector entries.

The auxiliary vector is the kernel's private channel to the new program, and several of its entries did not exist in Linux 2.6.11. It tells the dynamic linker where the program's own headers are (AT_PHDR, AT_PHNUM) and where the linker itself was loaded (AT_BASE) so it can relocate; it passes the page size, the hardware capability bitmaps (AT_HWCAP/AT_HWCAP2, which tell libc which CPU features are available), and the entry point (AT_ENTRY). Three entries are security-relevant. AT_RANDOM points at 16 fresh random bytes the kernel places on the stack, from which the C runtime seeds its stack canary and other protections. AT_SECURE carries the secure-exec flag, and when set the dynamic linker ignores dangerous environment variables such as LD_PRELOAD—the mechanism that stops an attacker from injecting a library into a setuid program. AT_SYSINFO_EHDR points at the vDSO, a small shared library the kernel maps into every process (§4.2). Table 20-3 collects the important entries.

The vector is assembled by a chain of NEW_AUX_ENT macros, and the first of them is not in generic code at all: ARCH_DLINFO, an architecture-supplied block that must come first because some architectures align the vector around it. That block is where AT_SYSINFO_EHDR comes from on x86-64 and ARM64, and where they both add AT_MINSIGSTKSZ, the size a signal frame actually needs on this particular CPU. That entry exists because the old compile-time MINSIGSTKSZ constant stopped being true once processors began growing register state — AVX-512 on x86, scalable vectors on ARM64 — so a program that sizes an alternate signal stack from the header constant can be badly wrong, and only the kernel knows the right answer at run time.

Several entries are not information the program lacks but information it should not have to go looking for. AT_UID, AT_EUID, AT_GID, and AT_EGID carry the credentials the exec just committed, mapped through the credential's user namespace so they read as the numbers that namespace uses; the C runtime compares the real and effective pairs as a second opinion alongside AT_SECURE. AT_FLAGS exists mainly to carry AT_FLAGS_PRESERVE_ARGV0, which tells a program launched through a binfmt_misc rule with the P flag that the argv[0] it can see is the caller's original, not one the kernel substituted; AT_EXECFD carries the descriptor of the original binary for the matching O rule (§2.2). And the newest pair, AT_RSEQ_FEATURE_SIZE and AT_RSEQ_ALIGN, tell libc how large and how aligned a struct rseq the running kernel expects, so that restartable sequences can be registered without probing a growing structure by trial and error. The widening of AT_HWCAP to a third and fourth word is the same kind of pressure showing up in a different place.

One detail makes all of this inspectable after the fact. As it builds the vector, create_elf_tables writes it into mm->saved_auxv as well as onto the stack, and that saved copy is what /proc/<pid>/auxv hands back. The stack copy belongs to the program and may be overwritten the moment it starts running; the mm copy persists for the life of the address space, so the auxiliary vector a process was started with can be read from outside it at any time — a genuinely useful debugging handle, and the reason tools can report which vDSO or which load base a running process received.

Because all of this—the strings, the pointer arrays, and the auxiliary vector—lives on the initial stack, its total size is bounded. The kernel caps the combined argument and environment size (historically ARG_MAX, now derived from a fraction of the stack resource limit), which is why a shell expanding a glob to enormously many filenames can fail with "argument list too long": the assembled argv would overflow what exec will place on the stack. The layout also anchors two runtime features. The pointer that ends up in the stack register lets the C startup code (_start) locate argc and walk up to hand main its argc/argv/envp; and the AT_RANDOM bytes are consumed immediately to initialize the stack canary, the guard value the compiler places in each stack frame to detect overflows before they can hijack a return address. In other words, by the time the program's own code runs, the stack the kernel built has already been turned into both its argument area and the seed of its first line of defense.

Program Segments and Memory Layout

Everything the previous sections built—the mapped ELF segments, the freshly grown stack, the interpreter, the auxiliary vector—has to land somewhere in the new process's linear address space, and where it lands is neither arbitrary nor, on a modern kernel, fixed. This section steps back from the mechanics of loading and looks at the finished product: the arrangement of regions a process sees the instant its first instruction runs. That arrangement is the contract between three parties. The compiler and linker decide which bytes are code, which are initialized data, and which are merely reserved space; the kernel decides the base addresses at which those pieces are placed and the boundaries it will enforce; and the C runtime and dynamic linker fill in the rest at run time. Getting the vocabulary and the geography right here is what makes /proc/pid/maps readable, what makes a core dump interpretable, and what makes the security properties of the layout—the subject of the third subsection—make sense.

We proceed from the static to the dynamic. First we name the classic segments a program is built from and the memory-descriptor fields that record their boundaries. Then we assemble those segments, the heap, and the memory-mapping region into the standard process address-space layout and explain why the pieces sit where they do. Finally we account for the single largest change to that layout since Linux 2.6.11—address-space layout randomization, which perturbs almost every base address on every exec and is on by default on every running Linux system today.

Text, Data, BSS, and Stack

Before we can talk about where the pieces of a program sit, we need names for the pieces themselves. The terminology predates Linux by decades and comes from the way a linker classifies the bytes of a program by how they must be initialized and protected: code that never changes, data that starts from a stored value, data that starts from nothing but zero, and the runtime scratch space of the call stack. Linux inherits these four names and their meanings even though, as the next paragraphs note, it implements them with paging rather than the hardware segments the word once implied.

The address space exec builds is traditionally described in terms of segments—logical intervals of the linear address space, a term with historical roots that Linux keeps even though it does not use hardware segmentation to implement them. A program has four classic segments. The text segment holds the executable code, mapped read-execute and shared between processes running the same program. The initialized data segment holds global and static variables with explicit initial values, mapped read-write from the file. The BSS—uninitialized data—holds globals that start at zero; the file stores only its size, and the kernel backs it with fresh zero-filled pages rather than file contents. The stack segment holds the call frames, arguments, and local variables, growing downward from near the top of the user address space.

The kernel records the boundaries of these regions in the memory descriptor, struct mm_struct (include/linux/mm_types.h), so it can answer questions about the process's layout and so tools such as /proc/pid/maps can report it. Table 20-4 lists the fields, which the ELF loader fills in as it maps each segment. Beyond the four segments the descriptor also tracks the heap—the region between start_brk and brk that malloc grows with the brk and mmap system calls—and the argument and environment string ranges, which is how /proc/pid/cmdline and /proc/pid/environ work. Those last two pairs are not quite read-only kernel bookkeeping: a sufficiently privileged process can move them with prctl(PR_SET_MM, ...), which is the sanctioned way to implement the setproctitle trick of rewriting one's own visible command line. The table also lists task_size, which records each process's own ceiling on user addresses rather than deferring to a global constant — a 32-bit program running on a 64-bit kernel has a different one, and setup_new_exec must set it late in the exec because it depends on a thread flag that flush_thread updates.

Two of these regions deserve a closer look because they behave unlike ordinary file-backed mappings. The BSS is the classic example of the kernel storing less than the program needs: a large zero-initialized array costs nothing in the executable file—only a size is recorded in the ELF program header—yet occupies real memory once the process touches it. The loader satisfies this by mapping the file-backed portion of the data segment and then, through padzero (fs/binfmt_elf.c), zero-filling the remainder of the last partial page and extending the mapping with anonymous, demand-zero pages for the rest. Nothing is read from disk; the pages materialize as zeros the first time they are accessed. The heap is the mirror image at run time: it begins empty at start_brk, and malloc grows it upward by moving brk or, for large requests, by carving anonymous regions out of the mmap area instead.

The stack is special in a different way. Unlike the other segments, its final size is not known when exec runs, so the kernel maps only a small initial region and lets it grow on demand: a fault just below the current bottom of the stack, in a VMA marked VM_GROWSDOWN, is treated not as a segmentation fault but as a request to extend the stack downward. To keep a runaway stack from silently colliding with the mmap region beneath it, the kernel refuses to let the two meet: it reserves a stack guard gap (stack_guard_gap, 256 pages by default) that neither the growing stack nor a new mapping may occupy, so an overflow faults cleanly rather than corrupting a neighbouring library. It is worth being clear about how new this is, because the gap is often described as an enlargement of an older defense. The 2.6.11 kernel had no stack guard of any kind: the word "guard" does not appear anywhere in its stack-growth code, and a descending stack could grow until it ran into whatever happened to be below it. A single guard page arrived in 2010, and the 256-page gap replaced it in 2017 after the "Stack Clash" class of attacks demonstrated that one page was trivially jumped over by a large stack frame. So the progression is none, then one, then two hundred and fifty-six — and the size is a kernel command-line parameter, stack_guard_gap=, rather than a sysctl, because it has to be fixed before the first process is built.

Two details of how the gap is enforced are easy to get wrong. It is checked from both sides: expand_downwards refuses to grow the stack to within stack_guard_gap of the preceding mapping, and the brk path performs the mirror-image check when growing the heap upward, looking forward by the same distance before it commits. And it is enforced only against a neighbour that is both accessible and not itself a growable stack — a PROT_NONE mapping is already a barrier and needs no gap, and two stack VMAs adjoining each other are not the hazard the gap exists to prevent. The same start-gap treatment is extended to shadow-stack mappings, which the kernel groups with VM_GROWSDOWN for exactly this purpose: an x86 CET shadow stack (§2.3) is as much a target for a clash as the ordinary one.

The mechanics of the growth itself changed substantially after Linux 2.6.11, and the change is about locking rather than layout. Growing a VMA modifies the address space, but the page-fault handler reaches this point holding only the mmap read lock, which it took on the assumption that a fault is a lookup. Older kernels expanded the stack under that read lock with a finer-grained lock standing in for the missing exclusion, an arrangement that was subtly racy for years. In 7.0.12 the fault path calls lock_mm_and_find_vma (mm/mmap_lock.c), which looks the address up, notices it falls below a VM_GROWSDOWN region, and then upgrades to the write lock — atomically if it can, otherwise dropping the lock, retaking it for writing, and repeating the lookup from scratch because anything could have changed in between. Only then does it call expand_stack_locked, and it downgrades back to a read lock before returning the VMA to the fault handler. expand_downwards additionally refuses any address below mmap_min_addr, so a stack can never grow down into the page at zero.

The Process Address-Space Layout

With the individual regions named, we can assemble them into the whole. The layout is not just a list of regions but an ordering chosen to satisfy competing goals: give the heap and the stack room to grow toward each other without meeting, pack shared libraries densely so many processes can share them, keep the kernel's own mappings out of user reach, and—in modern kernels—scatter everything enough that an attacker cannot predict it. The result is the familiar picture the rest of this subsection walks through, from the low addresses where the executable lives up to the top of the user range just below the kernel.

These pieces are arranged into a standard layout that has evolved since Linux 2.6.11. At the low end sit the program's text and data, loaded from the executable. Above them the heap grows upward from start_brk. Near the top of the user-accessible range sits the stack, growing downward. Between the heap and the stack lies the large memory-mapping region, anchored at mmap_base, where shared libraries, the dynamic linker, and anonymous mmap allocations are placed. Modern kernels use a top-down mmap layout by default: allocations start just below the stack and grow toward lower addresses, which uses the vast 64-bit space more flexibly than the old fixed bottom-up region. The exact extent of the user space is architecture-specific—roughly 128 TiB on x86-64 (47-bit user addresses) and 256 TiB on ARM64 (48-bit), with both architectures able to go wider—but the relative arrangement is the same. Figure 20-6 shows it.

That "able to go wider" conceals a design both reference architectures arrived at independently and implement the same way, and it is worth spelling out because it is invisible unless you go looking. Each defines two ceilings. TASK_SIZE is what the hardware and the page-table configuration allow: 57-bit addresses on x86-64 with five-level paging, and whatever vabits_actual reports on ARM64, up to 52. But DEFAULT_MAP_WINDOW is smaller and fixed — 47 bits on x86-64, the compile-time minimum on ARM64 — and it is DEFAULT_MAP_WINDOW, not TASK_SIZE, that bounds where the kernel places anything on its own initiative. The stack top, the mmap base, and a PIE's load address all live inside the narrower window. A process reaches the wider one only by passing mmap a hint address above the boundary, at which point arch_get_mmap_end raises the ceiling for that request alone. The reason is compatibility with software that stores its own data in the unused high bits of pointers: such programs would break the instant the kernel began handing out addresses that used those bits, so the extra space is opt-in and stays unused unless asked for. A related floor exists at the bottom: mmap_min_addr forbids mapping the lowest addresses at all, so that a null-pointer dereference in the kernel cannot be turned into a jump to attacker-controlled user memory.

The top-down arrangement is worth dwelling on because it is one of the quieter changes since Linux 2.6. On 32-bit systems, address space was scarce, and the legacy layout grew the mmap region upward from a fixed low base just above the heap—an arrangement that could wedge a program between a heap that wanted to grow up and libraries that had nowhere to go. The 64-bit port, with its practically unlimited address space, flips this: arch_pick_mmap_layout places mmap_base high, just below the randomized stack, and grows new mappings downward toward the heap. The two dynamic regions now expand away from a common frontier with terabytes of unused space between them, so they realistically never collide.

"Just below the stack" hides the most practically useful fact in this subsection, which is exactly how far below. The base is computed as the top of the stack region minus a gap minus a random offset, and the gap starts out as the current RLIMIT_STACK, padded by the guard gap and by the range over which the stack top itself will be randomized, then clamped to at least 128 MiB and at most five sixths of the address space. The stack's resource limit is therefore not merely a bound on how far the stack may grow; it is the distance the kernel reserves for that growth, and so it directly determines where every shared library in the process is mapped. Raising ulimit -s moves the entire memory-mapping region downward, which is a genuinely surprising coupling the first time it is observed, and it explains why two shells with different stack limits show visibly different library addresses for the same program. The 128 MiB floor keeps a tiny limit from pushing libraries up against the stack; the five-sixths ceiling keeps a very large one from squeezing the mapping region out of existence.

An unlimited stack cannot be handled by any clamp, and there the kernel changes strategy rather than numbers: mmap_is_legacy returns true and the process gets the old bottom-up layout, with the base set to TASK_UNMAPPED_BASE — a quarter of the way up the address window — plus a random offset, and new mappings growing upward from there. Two other things select the same layout: the ADDR_COMPAT_LAYOUT personality flag, which a program can set for itself, and the vm.legacy_va_layout sysctl, which an administrator can set for everyone. Top-down remains the default the figure shows, but all three escapes are live in 7.0.12, and a surprising amount of software still takes the first one by running under ulimit -s unlimited.

One consequence of this layout is worth making explicit for anyone reading /proc/pid/maps: the addresses are not portable facts about the program but per-run accidents of placement. The same binary, run twice, will show its stack, its libraries, its heap, and—if it is a position-independent executable—its own code at different addresses each time. That unpredictability is not incidental; it is the security feature the final subsection describes, and it is the reason a hard-coded pointer captured from one run is worthless in the next.

Address-Space Layout Randomization

The single largest security change to program execution since Linux 2.6.11 is that the layout just described is randomized on every exec. Address-space layout randomization (ASLR) defeats a whole class of exploits that depend on knowing where code and data live: if the stack, the heap, the libraries, and the executable itself land at unpredictable addresses each run, an attacker cannot reliably hardcode the address of a function to jump to or a buffer to corrupt. ASLR is controlled by the kernel.randomize_va_space sysctl (mm/memory.c), which defaults to 2—the strongest setting, randomizing the stack, the mmap region, the vDSO, and the heap—on any ordinary configuration. The one exception is worth knowing because it surprises people who read the source: if the kernel is built with CONFIG_COMPAT_BRK, the initial value is 1 instead, which leaves the heap where the executable's data ends. The in-tree comment explains why, and it is pure archaeology: ancient libc5-based binaries segfault when the heap does not immediately follow the data segment. No distribution has enabled that option in many years, but the default is conditional rather than absolute. A process opts out only through the ADDR_NO_RANDOMIZE personality flag (used by debuggers for reproducible runs), which clears the PF_RANDOMIZE task flag the loader otherwise sets.

The ELF loader reads the sysctl exactly once per exec, into a local it then uses for every decision that depends on it — both the test that sets PF_RANDOMIZE and, much later, the test for whether the heap should be randomized too. The reason is a small but real correctness concern: an administrator writing to kernel.randomize_va_space while an exec is in progress could otherwise produce a process whose stack and libraries were randomized but whose heap was not, or the reverse. Sampling the value once guarantees that every process is built to a single consistent policy, whichever policy was in force when it started.

The randomization is applied in several places during exec, each drawing fresh entropy. The stack top is perturbed by randomize_stack_top, which masks a fresh random value with STACK_RND_MASK and subtracts that many pages from the page-aligned top, and then further by arch_align_stack, which on x86 shaves off up to another 8 KiB before rounding down to a 16-byte boundary. The two work at different granularities on purpose: the first moves the stack by whole pages so that page-granular guesses fail, and the second moves it within a page so that an attacker who has somehow learned the page still does not know the offset. The ABI alignment is applied last, because the stack pointer handed to main must satisfy it regardless of what either randomizer chose. The mmap base is chosen by arch_pick_mmap_layout using arch_mmap_rnd, whose entropy is tunable through the mmap_rnd_bits sysctl. A dynamically linked position-independent executable's load bias is randomized off ELF_ET_DYN_BASE, and a static one is simply placed by the randomized mmap base (§3.3), so either way the main program's own code moves each run—the change that PIE binaries made possible and that ordinary ET_EXEC binaries cannot benefit from. Finally, when randomize_va_space is 2, arch_randomize_brk offsets the heap start as well, by up to 1 GiB for a 64-bit process and 32 MiB for a 32-bit one. The 16 random bytes delivered through AT_RANDOM complement all this at the language-runtime level, seeding the stack-smashing canary. Taken together, these turn a once-deterministic layout into one an attacker must guess, and they are on by default on every modern Linux system.

It helps to know the three settings of the sysctl and what each buys. A value of 0 disables randomization entirely, reproducing the deterministic Linux 2.6.11 behaviour; it exists mainly for debugging and for the rare workload that mmaps at fixed addresses. A value of 1 randomizes the stack, the mmap region (and thus every shared library and the vDSO), and the load base of PIE executables, but leaves the heap adjacent to the executable's data—the compromise older distributions shipped. The default 2 adds the brk-based heap to the set, so no writable region keeps a predictable relationship to any other. Independently, the amount of entropy—how many bits of address each region is shifted by—is capped by mmap_rnd_bits and its compat sibling, which the administrator can raise toward the architecture's maximum to make guessing exponentially harder at a small cost in address-space fragmentation.

The actual numbers differ enough between the book's two reference architectures to be worth stating, because they are the clearest illustration that "ASLR is enabled" is not a single quantity. For the stack, x86-64 uses an 11-bit page mask, giving about 8 MiB of jitter, while ARM64 uses an 18-bit one, giving about 1 GiB at 4 KiB pages — roughly seven extra bits of entropy for the same defence on the same kernel. For the mmap region the ordering is similar: mmap_rnd_bits is constrained to 28 through 32 on 64-bit x86, whereas ARM64 permits up to 33 with 48- or 52-bit addresses and 4 KiB pages, falling to 31 and 29 as the page size grows to 16 KiB and 64 KiB, since larger pages leave fewer bits below the page boundary to randomize with. The architecture, the page size, and the configured address width therefore all feed into how much an attacker actually has to guess, and a claim about ASLR strength that does not name all three is not saying much.

ASLR is a probabilistic defence, not an absolute one, and it is worth being honest about its limits. Its strength is the number of random bits an attacker must guess; on 32-bit systems that number was small enough to brute-force, which is part of why the 64-bit address space matters so much. A single leaked pointer—from an uninitialized read, a format-string bug, or a side channel—can reveal a region's base and collapse the entropy for everything placed relative to it, which is why ASLR is deployed alongside, not instead of, defences such as non-executable data pages, stack canaries, and the control-flow-integrity features (PT_GNU_PROPERTY, x86 CET, ARM64 BTI) the loader also honours. Randomizing the layout does not fix a memory-safety bug; it raises the cost of turning one into a reliable exploit, and for that it has become non-negotiable baseline hardening.

Everything in this subsection randomizes the user address space, and it is worth closing by noting that the kernel applies the same reasoning to itself, on two separate axes that are easy to confuse with the above. Kernel address-space layout randomization relocates the kernel image at boot, which is a once-per-boot decision and nothing to do with exec. Separately, randomize_kstack_offset perturbs the kernel stack pointer by a small random amount on every system call, so that a bug allowing a kernel stack overwrite cannot rely on a fixed offset between the attacker's data and whatever it is trying to reach. The per-syscall frequency is what distinguishes it: the layouts described earlier are fixed for the lifetime of a process, and an attacker who leaks one pointer keeps the advantage, whereas the kernel stack offset is redrawn thousands of times a second and a leak is stale almost immediately.

Libraries and Dynamic Linking

The exec pipeline of the previous sections stops at a curious place. For the overwhelming majority of programs it does not, in fact, finish loading the program at all: it maps the executable, notices it names an interpreter, maps that, and hands control to it—leaving a second, entirely user-space loading phase to assemble the rest of the process. That second phase is dynamic linking, and it is where most of the code a real program runs actually arrives. Understanding it is what closes the gap between "the kernel jumped to an entry point" and "main runs with a working printf." The kernel's role, as we will see, is deliberately minimal—it maps a couple of files, adds the vDSO, and sets a register—while the interesting work of finding libraries, loading them, and wiring up the calls between them is done by an ordinary (if unusually privileged-looking) program running in the new address space.

It is worth saying that this minimalism is the result of deletion rather than original design, because Linux 2.6 did more. That kernel had a load_shlib method in every binary-format handler and a uselib system call to invoke it (§2.1): loading a shared library was a kernel operation with its own entry point, inherited from a.out. All of it is gone. The method is no longer a field in struct linux_binfmt, and uselib survives only as a stub in kernel/sys_ni.c that returns ENOSYS — the number is still allocated, but nothing implements it. What replaced a dedicated kernel mechanism was not a better kernel mechanism; it was the realization that mmap was already sufficient, and that a user-space program could do the rest.

We approach the subject in two steps. First we contrast the two ways library code can reach a process—copied in at build time as a static library, or loaded at run time as a shared library—and weigh the trade-offs that made shared linking the default. Then we follow the dynamic linker itself through the work it does before the program's first instruction: how the kernel selects and maps it, how it finds and loads the shared objects a program depends on, how it patches the thousands of cross-references between them through the GOT and PLT, and how modern hardening (lazy versus full RELRO, the secure-execution rules for setuid programs) shapes that process.

Static versus Shared Libraries

Before tracing the linker, it is worth being precise about what a "library" even is at the file level, because the word covers two quite different artifacts that enter the program at two different times. One is resolved and gone before the program ever ships; the other is a distinct file that must still be present, and found, every time the program runs. The distinction governs the size of the binary, its portability, its memory footprint across a running system, and how security fixes reach it—so it is the natural starting point.

Most of the code a program runs is not its own—it comes from libraries of shared routines. There are two ways that code reaches the process. With a static library, the needed routines are copied into the executable at link time, so the file is self-contained: exec maps it and the program is ready to run, with no external dependencies. With a shared library, the executable contains only references to the library, and the actual code is loaded at run time from a separate .so file that many processes map simultaneously. The trade-offs are the classic ones. Static linking gives a larger but dependency-free binary that always runs the exact code it was built with. Shared linking gives smaller binaries and—because a single copy of libc's pages is shared read-only across every process using it—dramatically less memory and disk use system-wide, plus the ability to fix a bug in one library without relinking every program. Shared linking is the overwhelming default, which is why almost every ELF executable carries a PT_INTERP naming a dynamic linker. Static linking has not vanished, but it has narrowed: a statically linked glibc program cannot use the name service switch or dlopen, both of which need to load a shared object at run time, so the practical static cases today are self-contained tools, early-boot and rescue binaries, and languages such as Go that supply their own runtime and avoid libc entirely.

The word "shared" deserves to be taken literally, because the sharing is physical rather than a figure of speech. The dynamic linker maps a library with an ordinary MAP_PRIVATE file mapping, and the pages that mapping resolves to are page-cache pages belonging to the file's inode. Two hundred processes mapping libc.so.6 are pointing two hundred sets of page tables at one set of physical pages; the copy-on-write that MAP_PRIVATE implies only ever fires for the writable data pages, never for the text. That is the whole economic argument for shared libraries, and it is also why the position-independence discussed next is not merely a convenience. If the text had to be patched with absolute addresses at load time, every process would dirty its own copy and the sharing would evaporate.

Sharing library code across processes only works if that code makes no assumption about the address it will be loaded at, since each process may map it somewhere different. This is why shared objects are compiled as position-independent code (PIC): they reference their own data and functions relative to the program counter or through indirect tables rather than through absolute addresses, so a single read-only copy of the text pages can be mapped—and physically shared—by every process regardless of where each one places it. The indirection has a measurable cost — an extra load on every cross-object call, and a register reserved to find the tables — which is precisely the price paid to keep the text pages identical and shareable. The same property is what lets the main executable be built as a position-independent executable (PIE) and thus participate in ASLR, as §4.3 described. A shared object also carries a soname (for example libc.so.6) that encodes its binary-compatibility version, so that many minor releases can satisfy the same dependency while an incompatible major bump forces a new soname; symbol versioning refines this further, letting a single library file export several versions of the same function so old binaries keep their old behaviour. At run time the linker does not search the filesystem for these files from scratch—that would be far too slow—but consults a cache built by ldconfig (/etc/ld.so.cache) that maps each soname to a concrete path.

One asymmetry between the executable and its libraries is worth knowing, because it contradicts a reasonable assumption. The kernel refuses writes to a running program's file, returning ETXTBSY (§3.2), and it is natural to expect the same protection for a mapped library. It does not exist. The deny-write is taken by do_open_execat on files the kernel itself opens for execution, which means the main executable, held for the process's lifetime through mm->exe_file, and the PT_INTERP interpreter, whose deny-write load_elf_binary releases the moment it has finished mapping it. A shared object that the dynamic linker maps later is opened with an ordinary open and mapped with an ordinary mmap, and nothing protects it at all. Linux 2.6 did better here: its ELF loader passed MAP_DENYWRITE on the mappings it made, and uselib called deny_write_access. Both flags still exist in the headers, but a comment in include/linux/mman.h records the outcome bluntly — they are "completely ignored throughout the kernel." The protection was removed because it was a denial-of-service tool in the other direction: anyone who could map a file could make it unwritable to its owner.

The Dynamic Linker

When an executable is dynamically linked, the kernel does not resolve its library references itself. As §3.3 described, it sees the PT_INTERP program header, maps the named dynamic linker (/lib64/ld-linux-x86-64.so.2 on x86-64, the analogous ld-linux-aarch64.so.1 on ARM64), and sets the process entry point to the linker's entry, not the program's. So the first user code that runs in a dynamically linked process is the linker. It reads the executable's dynamic section to find which shared objects are needed, maps each one (recursively handling their dependencies), and then performs relocations: it patches the program's and libraries' reference tables so that each call to an external function lands at the address where that function was actually loaded. Only when this is done does it jump to the executable's real entry point, delivered to it in the auxiliary vector as AT_ENTRY.

Being the first user code to run puts the linker in an awkward position that repays a moment's thought, because it has to relocate itself before it can do anything else. It is an ET_DYN object loaded at an address the kernel chose, it has no interpreter of its own — nothing would load one — and so until its own relocations are applied it cannot call a function through the usual tables or read a global through the usual indirection. Its entry code is therefore written to use nothing but program-counter-relative addressing, just far enough to find its own dynamic section and process its own relocations, after which it becomes an ordinary program. What it cannot work out for itself the kernel hands it in the auxiliary vector: AT_BASE is the address the interpreter was loaded at, and AT_PHDR, AT_PHENT and AT_PHNUM locate the executable's program headers, from which the linker finds the program's PT_DYNAMIC and thus its list of dependencies. Those entries exist precisely because the process that would normally discover this information — reading and parsing the ELF file — has already been done once by the kernel, and repeating it would be wasteful.

Two mechanisms make this efficient and safe. Calls to shared-library functions go indirectly through a per-process global offset table (GOT) and procedure linkage table (PLT): the compiler emits a call to a PLT stub, which reads the function's real address from the GOT. By default the linker fills GOT entries lazily—resolving each function's address the first time it is actually called rather than all of them up front—so a program that uses only a few of a library's functions pays only for those. The cost of this indirection is that a writable GOT is a tempting target for attackers, which is where PT_GNU_RELRO (§2.3) comes in: with "full RELRO" the linker resolves everything at startup and then asks the kernel to make the GOT read-only, trading a little startup time for a hardened process. This interplay—the kernel mapping the linker and the segments, the linker resolving symbols through the GOT/PLT, and the two cooperating on RELRO—is how a modern program assembles itself from dozens of shared objects before main ever runs. It is worth being exact about how little the kernel contributes: it never parses PT_GNU_RELRO at all, which appears in the tree only as a constant in the UAPI headers and in a loader unit test. The segment is entirely a message from the link editor to the dynamic linker, and the kernel's whole participation is honouring the mprotect that results.

Memory sealing (mseal, mm/mseal.c) marks a range of VMAs so that their metadata can no longer be changed: after sealing, the range cannot be unmapped, moved, shrunk, expanded into, overwritten by a MAP_FIXED mapping, or reprotected with mprotect. The seal is permanent for the life of the mapping; there is no unseal. Its relevance here is that it closes a real gap in the RELRO story just described. Making the GOT read-only with mprotect stops an accidental write, but an attacker who already has the ability to call mprotect can simply make it writable again, so full RELRO by itself raises the bar rather than setting it. Sealing the same range makes the read-only status irrevocable, and a modern dynamic linker seals its RELRO region for exactly this reason. The kernel applies the same reasoning to the mappings it makes on the process's behalf: the vDSO, its data page, and on ARM64 the 32-bit vector and signal pages are all sealed under CONFIG_MSEAL_SYSTEM_MAPPINGS, so no amount of later confusion in user space can unmap or rewrite the code the kernel put there.

The mprotect the linker depends on can itself be taken away, and the mechanism is worth knowing because it breaks programs that assume otherwise. prctl(PR_SET_MDWE, PR_MDWE_REFUSE_EXEC_GAIN) turns on memory-deny-write-execute for a process: from then on map_deny_write_exec (include/linux/mman.h) refuses any mapping that would be writable and executable at once, and — the stronger half of the rule — refuses to make an existing non-executable mapping executable. The second clause is what closes the loophole, because write-then-mprotect is how the first clause would otherwise be sidestepped, and it is also why just-in-time compilers cannot run under MDWE without being rewritten to use two mappings of the same memory. Like no_new_privs (§7.2) it is a latch with no way back, and it is recorded in the memory descriptor's flags rather than the credentials, which means it survives both fork and exec — unless the process also set PR_MDWE_NO_INHERIT, in which case the bit is cleared for children and the restriction applies only to the process that asked for it.

There is one shared object the linker never has to find, and it is the only one the kernel supplies. The vDSO (§3.4) is a complete ELF shared library built into the kernel image and mapped into every address space, linked with the soname linux-vdso.so.1 on both x86-64 and ARM64. It has a soname, a dynamic symbol table and version definitions like any other library, which is why ldd lists it; it simply has no path, because there is no file. The linker recognizes it by its base address in AT_SYSINFO_EHDR and links against it in place. It is also, as the previous paragraphs described, sealed: the vDSO and its companion data page are mapped with VM_SEALED_SYSMAP, so the one library a process did not choose is also the one it cannot get rid of.

Where the linker looks for those shared objects is a small policy of its own, and one with security consequences. The order is not the obvious one, and getting it right matters because the ordering is the design. The linker searches the deprecated DT_RPATH first, but only if the object has no DT_RUNPATH; then LD_LIBRARY_PATH; then the RUNPATH taken from DT_RUNPATH; then the system directories recorded in the ldconfig cache; and finally the built-in defaults. The two dynamic-section entries therefore sit on opposite sides of the environment variable, and that is the whole point of the newer one. DT_RPATH was baked in at build time and could not be overridden, which made testing a patched library against an installed program impossible; DT_RUNPATH was placed below LD_LIBRARY_PATH so that it can be. They differ in reach as well: DT_RPATH applied to every object in the dependency tree beneath it, while DT_RUNPATH applies only to that one object's direct DT_NEEDED entries, so a library wanting a private search path must carry its own. The environment-variable step is exactly why exec tracks whether the new program is running with elevated privilege. Recall from §3.3 that the kernel sets bprm->secureexec and delivers it to user space as the AT_SECURE auxiliary-vector entry (fs/binfmt_elf.c). When AT_SECURE is set—because the program is setuid, setgid, or gained file capabilities—the dynamic linker ignores LD_LIBRARY_PATH, LD_PRELOAD from untrusted locations, and the other LD_* hooks, so an unprivileged caller cannot trick a privileged program into loading an attacker's library. The list of what gets dropped is longer than LD_PRELOAD alone — LD_LIBRARY_PATH, LD_AUDIT, and the whole family of debugging and tuning variables go with it — and the system-wide /etc/ld.so.preload file remains honoured because it is writable only by root. This is the user-space half of the same secure-execution contract the kernel enforces on credentials; the kernel supplies the one-bit verdict, and the linker acts on it.

Search paths are not quite literal strings, either. The linker expands three tokens inside DT_RPATH and DT_RUNPATH entries: $ORIGIN, the directory holding the object being loaded, which is what lets a relocatable application ship its own libraries alongside itself; $LIB, which becomes lib or lib64 according to the architecture; and $PLATFORM, which comes straight from the AT_PLATFORM auxiliary-vector entry the kernel filled in from its ELF_PLATFORM definition — the string x86_64 or aarch64 — with a companion AT_BASE_PLATFORM naming the real microarchitecture where the two differ. This is a small but genuine kernel-to-linker channel: an architecture can steer library selection through a value only the kernel knows. $ORIGIN is the one with security consequences, and it is refused in secure-execution mode for most uses, since an attacker who controls where a setuid binary appears to live would otherwise control where it looks for libraries.

The kernel's few checks on the interpreter are worth listing, because they are the entirety of its opinion about dynamic linking. The PT_INTERP string must be at least two bytes, no longer than PATH_MAX, and NUL-terminated within the segment; any of those fails the exec with ENOEXEC before the file is even opened. It is then opened through open_exec, so it is subject to the same noexec-mount and execute-permission policy as the program itself. It must carry ELF magic and match the architecture, and here a failure reports ELIBBAD rather than ENOEXEC, which is how a bad interpreter is distinguished from a bad program. It must further be ET_EXEC or ET_DYN and live on a filesystem that supports mmap at all, which can_mmap_file checks explicitly. One check is less obvious: load_elf_binary calls would_dump on the interpreter, so that if the linker is not readable by the invoking user the process is marked non-dumpable. A core dump would otherwise contain the interpreter's mapped text, which is a roundabout way of reading a file you were not allowed to read. Notably absent from the list is any recursion: an interpreter naming an interpreter of its own is simply ignored, because the kernel never looks.

Not all dynamic linking happens at startup. A program can also load a shared object on demand at run time by calling dlopen, which asks the already-resident dynamic linker to map a new .so, run its relocations, and make its symbols available through dlsym—the mechanism behind plugin architectures and lazily loaded optional features. This is the same loader machinery as startup linking, simply invoked later and explicitly rather than implicitly from PT_INTERP. It is worth remembering that from the kernel's point of view none of this—startup linking, lazy PLT resolution, or dlopen—is special: each shared object is just another file mapped with mmap into the memory-mapping region of §4, and each relocation is just a write to a page the process already owns. The elaborate edifice of dynamic linking is built entirely on the handful of primitives the earlier sections established.

Process Credentials and Capabilities

So far this chapter has treated exec as a question of what code runs and where it lands in memory. This section turns to a question that is just as much a part of loading a program: with what authority it runs. Exec is the one moment in a process's life when its identity and privileges can legitimately change—the shell you launch inherits your identity, but passwd becomes root, and a sandboxed helper may come out with less power than it went in. All of that is decided by the credential machinery that runs inside the same bprm_execve pipeline we have already followed, at the same point of no return where the address space is replaced. Because a mistake here is a privilege-escalation bug rather than a crash, the kernel's handling of credentials on exec is among the most carefully guarded code in the system, and it looks very different from the handful of inline uid fields of Linux 2.6.

We build the picture in four layers. First the credential model: the immutable, reference-counted struct cred that replaced those inline fields and the copy-then-commit discipline that keeps it safe. Then the privilege transitions exec itself performs—how setuid bits and file capabilities raise privilege, how secureexec and no_new_privs constrain it. Finally capabilities, the fine-grained decomposition of root's authority into some forty independent powers, and the five sets and file attributes that govern how those powers flow across an exec. Last, the credential system calls—setresuid, setfsuid, capset and their relatives—through which a running process changes its identity without an exec. Together they are the foundation the sandboxing frameworks of §7 build upon.

The Credential Model

Everything in this section rests on one data structure, so we start there. The question it answers is deceptively simple—"who is this process, and what may it do?"—but the way Linux now represents that answer, as a shareable immutable object rather than a few mutable fields, is what makes the rest of the section's guarantees possible. The design is worth understanding before the transitions, because the rules exec follows are direct consequences of how a cred is built and installed.

Every access-control decision the kernel makes—may this process open that file, signal that process, bind that port—rests on the process's credentials: its user and group identities and its capabilities. In Linux 2.6.11 these were a handful of uid and gid fields sitting directly in the task_struct. Linux has since replaced that with a dedicated, reference-counted, RCU-protected struct cred (include/linux/cred.h), and the change is foundational to how exec handles privilege. A cred gathers all the identity in one immutable object: the real, effective, saved, and filesystem user and group ids (uid/euid/suid/fsuid and the group equivalents), the five capability sets, the securebits, the keyrings, the owning user namespace, and the LSM security blob. Because it is reference-counted and copy-on-write, unrelated tasks that share an identity can share one cred object, and because it is immutable once committed, any reader can examine credentials under RCU without locking.

A task actually holds two credential pointers, real_cred and cred (include/linux/sched.h), the objective identity it has and the subjective identity it is acting with. The case where they diverge is worth naming, because it is not exotic: a kernel service that must act as a user does so by calling override_creds, which swaps current->cred and leaves real_cred untouched, and undoes it with revert_creds. The NFS server handling a request, an overlay filesystem touching the lower layer, and io_uring running work on a submitter's behalf all do exactly this. The split means an observer asking "who is this task?" gets a stable answer: __task_cred reads real_cred, so an overridden subjective identity never changes who the task is for the purpose of signalling or ptrace. In 7.0.12 the pattern has a scope-guard form, scoped_with_creds(), so the revert cannot be forgotten on an error path. The rule that makes the model safe is that a committed cred is never modified in place. To change identity, code prepares a new credential (prepare_creds), mutates the copy, and atomically installs it with commit_creds—which is exactly the sequence exec follows. abort_creds discards the copy if the change is abandoned, which is why a failed exec leaves no trace on the caller's identity. Identities are stored as kuid_t/kgid_t values that are meaningful relative to a user namespace, so the same on-disk uid can map to different kernel identities in different containers—another capability absent from Linux 2.6.11. Two fields the summary above skips are worth noting because they carry accounting rather than identity: group_info, the supplementary group list, and ucounts, the per-user-namespace counters that enforce RLIMIT_NPROC and friends per namespace rather than per machine. There is also an invariant the code checks rather than assumes, expressed as cap_ambient_invariant_ok: the ambient set must always be a subset of permitted intersected with inheritable. The capability arithmetic below WARN_ONs it twice, once on entry and once on exit, which is a fair signal of how easy that arithmetic is to get wrong.

commit_creds is worth reading rather than summarizing, because installing the pointer is the least of what it does. It begins with BUG_ON(task->cred != old), refusing to run at all while a subjective override is in force. If any identity or capability actually changed, it calls set_dumpable(task->mm, suid_dumpable) — this is where the fs.suid_dumpable sysctl takes effect, and it is what makes a newly privileged process uncoredumpable, its /proc files root-owned, and its memory unreadable by the user who started it. In the same block it clears pdeath_signal, so an unprivileged parent cannot keep a signal hook into a child that has just gained privilege. Between the two there is an smp_wmb carrying an unusually explicit comment: the dumpability change must become visible before the credential change, because a __ptrace_may_access racing with this code would otherwise see a task that had already dropped privileges but not yet become non-dumpable, and attach to it. The barrier is paired with a read barrier in the ptrace path. Only after all of that does commit_creds publish the new pointer into both real_cred and cred, adjust the keyrings if the filesystem ids moved, move the RLIMIT_NPROC charge between user namespaces, and emit proc_id_connector notifications for anything watching identity changes.

One implementation detail explains a field that otherwise looks odd. Because credentials are read under RCU, freeing one has to wait for a grace period — except that the overwhelmingly common case is a credential that was never published to any RCU reader, such as one built and discarded during a failed exec. The structure therefore ends in a union of an rcu_head and an int non_rcu flag, set optimistically and cleared by get_cred the moment anyone takes a reference. A credential nobody ever referenced is freed immediately; one that might have been observed goes through call_rcu. It is a small optimization, but it sits on the hottest path in the kernel's permission machinery.

Privilege Transitions on exec

With the credential object understood, we can watch it change. An ordinary exec preserves identity—your shell's children are still you—but two mechanisms can raise privilege at this boundary, and a growing set of rules exist to make sure that only happens when it is safe. The tension this subsection resolves is that raising privilege is both essential (a handful of programs genuinely must run as root) and dangerous (every such program is an attack surface), so the kernel surrounds the raise with checks: it recomputes the identity into a staged copy, refuses to honour it if the caller has forsworn new privileges, and flags the whole exec as security-sensitive for user space.

Exec is the moment a process's privilege can change, and the credential pipeline inside bprm_execve is built to compute the new identity carefully. prepare_bprm_creds starts by copying the caller's credentials into bprm->cred. Then, if the executable file carries the set-user-ID mode bit, bprm_fill_uid (fs/exec.c) raises the effective user id to the file's owner—this is the classic setuid mechanism by which, for example, passwd runs as root to edit the shadow file. The set-group-ID case has a condition that is easy to state wrongly: the bit alone is not enough, and the code requires S_ISGID and S_IXGRP together, because S_ISGID on a file with no group-execute bit has historically meant mandatory locking rather than a privilege transition. Note also what bprm_fill_uid does not do: it sets only euid and egid. The saved and filesystem ids are assigned later, in cap_bprm_creds_from_file, which finishes the job with suid = fsuid = euid once it has decided whether the raise survives at all. All of it is committed only inside begin_new_exec, at the point of no return, by commit_creds.

Three guards surround that raise, and each corresponds to a way the mechanism has been abused. The first is the mount: mnt_may_suid refuses the whole thing on a filesystem mounted nosuid, which is why a setuid binary on a USB stick or in a container image mounted that way is simply an ordinary program. The second is a time-of-check defense. Having decided the file looks interesting, the code takes the inode lock, re-reads the mode and the owning ids, and re-runs inode_permission for MAY_EXEC — the comment reads "Did the exec bit vanish out from under us? Give up." An attacker who can flip the mode between the first look and the credential computation gains nothing. The third is the user namespace: the file's owner and group must have mappings in the namespace the new credentials belong to, so a setuid-root binary inside a user namespace that does not map uid 0 raises nothing at all. This is what makes it safe to let an unprivileged user own the contents of a container filesystem.

A raise that survives all of that still drags one more consequence with it. bprm_fill_uid sets bprm->per_clear |= PER_CLEAR_ON_SETID, and the same flag is set when file capabilities grant anything new, which causes the dangerous personality bits to be stripped from the new process. The most consequential of them is ADDR_NO_RANDOMIZE: a process cannot turn off address-space randomization (§4.3) and then exec a setuid program into the predictable layout it just arranged. The same clearing removes the READ_IMPLIES_EXEC personality, so an old-ABI process cannot hand a privileged program an address space in which every readable page is also executable, along with ADDR_COMPAT_LAYOUT, which would otherwise let the caller force the legacy bottom-up mmap layout of §4.2 on a program it does not control, and MMAP_PAGE_ZERO, which would map the null page and turn a null-pointer bug in a privileged program into executable code. The pattern in all four is the same: anything an ordinary process may ask for about its own address space becomes a weapon once it can be imposed on a more privileged successor.

Because a privilege change is dangerous, the kernel marks such an exec as a secure exec (bprm->secureexec, set by cap_bprm_creds_from_file in security/commoncap.c) whenever the credentials actually change—through setuid, set-group-ID, or file capabilities. The test is slightly broader than "something changed," and the extra clause is easy to miss: an exec is also secure if the incoming effective id differs from the caller's real id, so a program that was already running with a raised identity marks its children's execs as secure even when this particular exec raises nothing. The secure-exec flag flows to user space as AT_SECURE in the auxiliary vector, and it makes the dynamic linker ignore attacker-controllable environment variables like LD_PRELOAD and LD_LIBRARY_PATH, so a setuid program cannot be tricked into loading a malicious library. A crucial safety valve is no_new_privs (set with prctl(PR_SET_NO_NEW_PRIVS)): once a task sets it, no subsequent exec may ever grant it more privilege—setuid bits and file capabilities are silently ignored (bprm_fill_uid and cap_bprm_creds_from_file honor it). This one-way latch is what lets an unprivileged process safely execute untrusted programs, and it is the prerequisite for the sandboxing frameworks of §7.

There is a quieter downgrade path that catches people out, and it is the credential half of the unsafe-execution states of §3.2. If the exec is flagged unsafe — the process shares its filesystem information or signal handlers with another thread, or is being traced by a tracer that does not itself hold CAP_SYS_PTRACE over the new credentials — then cap_bprm_creds_from_file does not fail the exec. It quietly reduces it: unless the caller holds CAP_SETUID, the effective ids are put back to the real ones, and the new permitted set is intersected with the old one, so the program comes out with no more than it went in with and possibly less. This is why running a setuid binary under a debugger appears to work but produces an unprivileged process, and why the behaviour is not an error message. The same function also clears SECURE_KEEP_CAPS unconditionally on every exec, since that bit is a statement about a setuid call and has no meaning across a program boundary.

Capabilities

The credential model and the transition rules above still speak largely in terms of user ids, and for privileged programs the user id that matters is zero—root. But "run as root" is a wildly over-broad grant, and the last piece of the credential story is the mechanism that lets the kernel hand out slivers of root's authority instead of the whole thing. Capabilities are what make the principle of least privilege expressible on Linux: rather than asking whether a process is root, most modern permission checks ask whether it holds the specific capability the operation requires. This subsection introduces the capability bits, the five sets that a process carries them in, and the rules that decide which of them survive an exec.

Traditional Unix has a single all-powerful user, root (uid 0), who bypasses every permission check. That is a blunt instrument: a program that needs only to bind a low-numbered port should not need the power to also rewrite the kernel or read every file. Capabilities (include/uapi/linux/capability.h) split root's authority into around forty independent privileges, each a distinct CAP_* bit that can be granted or dropped on its own. Table 20-5 lists representative ones. A network daemon can hold CAP_NET_BIND_SERVICE and nothing else; a backup program CAP_DAC_READ_SEARCH to read any file without the power to change it. Newer kernels have continued to subdivide the most sweeping capability, CAP_SYS_ADMIN, carving out CAP_BPF, CAP_PERFMON, and CAP_CHECKPOINT_RESTORE so that those subsystems can be delegated without handing over near-total control.

The single most important thing to understand about a capability in a modern kernel is that holding one is not a global statement. Every check names a user namespace, and the effective set in a credential is only meaningful relative to the namespace that credential belongs to. capable(cap) is nothing but ns_capable(&init_user_ns, cap) — a question about the host — while ns_capable(ns, cap) asks about a particular namespace, and the answer is computed by walking from the target namespace toward the root. Three rules fall out of that walk. If the credential belongs to the namespace being asked about, the effective bit decides. If the credential belongs to an ancestor, the answer is yes, because a capability held in a parent applies throughout every namespace below it. And if the credential's effective user id is the owner of the namespace being asked about — the identity that created it — the answer is yes for every capability, unconditionally.

That third rule is the one that makes unprivileged containers possible, and it is also the one most often misread. A user who creates a user namespace holds the full capability set inside it without having held anything outside it, which is why an ordinary account can build a container with its own mounts and network stack. The capabilities are real, but they are real only against objects that belong to that namespace; the walk terminates at the namespace boundary, so CAP_SYS_ADMIN obtained this way grants nothing over the host. Two helper forms guard the seams. capable_wrt_inode_uidgid requires both the capability and that the inode's owner and group have mappings in the caller's namespace, which stops a namespace-root from editing files whose ownership it cannot even express. file_ns_capable asks whether the process that opened a file held a capability at the time, which is how a descriptor can carry an authority that outlives the privilege that obtained it; it deliberately does not set PF_SUPERPRIV, the flag every ordinary successful capability check raises for accounting, because the caller may not be privileged at all.

A process holds capabilities in five sets, and understanding them explains how privilege flows across exec. The permitted set is the capabilities the process may use; the effective set is those currently active for permission checks; the inheritable set is those that can pass through an exec to a cooperating program; the bounding set is a ceiling that permitted can never exceed; and the ambient set—a newer addition—lets capabilities survive an exec of an ordinary (non-file-capability) program, which inheritable alone could not do. An executable file can carry file capabilities in a security.capability extended attribute (in its modern namespaced revision-3 form), which grant specific capabilities to any process that execs it—a far safer alternative to making the file setuid-root, because it grants only the listed powers rather than all of them. The revision-3 format exists because of the namespace problem: the attribute carries a rootid field naming the identity that counts as root for it, so a file capability written inside a user namespace is honoured only where that identity maps to zero, and an unprivileged user cannot create a file that becomes privileged the moment it is read from outside the container. Writing the attribute at all requires CAP_SETFCAP over both the caller's namespace and the inode's ownership.

The ambient set repays a second look, because it exists to solve a problem the other four created. Inheritable capabilities were designed to pass through an exec, but they take effect only if the executed file also lists them in its own inheritable set — and almost no file does. The practical consequence was that a process holding capabilities could not run /bin/sh and keep them, which made capability-based privilege useless for anything assembled out of ordinary programs. Ambient capabilities survive an exec of a file with no capability attribute at all, which is what a service manager needs. The safeguards are that a capability can be raised into the ambient set only if it is already in both permitted and inheritable, that dropping it from either drops it from ambient too, that no_new_privs or the absence of CAP_SETPCAP blocks the raise, and that any exec which is already privileged — a file with capabilities, or a setuid transition — clears the ambient set outright, so the two mechanisms never compound.

On exec, cap_bprm_creds_from_file (security/commoncap.c) computes the new capability sets from the file's capabilities, the process's inheritable and bounding sets, and its ambient set, following the rule that the new permitted set is (inheritable & file-inheritable) | (file-permitted & bounding) | ambient, and the new effective set is the full permitted set if the file's effective bit is on, or just the ambient set otherwise — which amounts to the same thing, since a file carrying an effective bit is privileged and has therefore already had its ambient set cleared. The inheritable and bounding sets pass through unchanged; they are the only two that do. All of it is visible at run time in /proc/<pid>/status, whose CapInh, CapPrm, CapEff, CapBnd and CapAmb lines are the five sets in hexadecimal and the fastest way to check what the arithmetic actually produced.

Root remains special, but not in the way it is usually described, and the details are in handle_privileged_root. The grant is not "the full capability set": the new permitted set becomes the caller's bounding set combined with its inheritable set, so a launcher that has already trimmed the bounding set constrains every root program it starts, which is precisely what makes the bounding set useful. The effective bit follows the effective uid alone — a process whose real uid is zero but whose effective uid is not comes out holding the capabilities in permitted without them being active, and must raise them deliberately. And the two privilege mechanisms are not allowed to mix: a setuid-root file that also carries a capability attribute gets no root grant at all when an ordinary user runs it, and the kernel logs warn_setuid_and_fcaps_mixed, on the reasoning that a file whose author went to the trouble of listing capabilities almost certainly did not also mean to hand over everything. All of this can be constrained further through the securebits. The net effect is a system where a service can run with precisely the handful of privileges it needs and no more, which is the foundation the sandboxing frameworks build on next.

Three refinements round out the picture. The securebits flags let a process opt out of the special treatment of root altogether: with SECBIT_NOROOT set, executing a program no longer grants uid 0 the full capability set automatically, so even a root-owned process must obtain its powers explicitly through file or ambient capabilities—and a locked companion bit makes the choice irreversible for the process and its descendants. Together with no_new_privs and the bounding set, securebits let an administrator construct a subtree of the process tree in which root is no longer magic. Two newer securebits extend the idea from privilege to execution policy itself: SECBIT_EXEC_RESTRICT_FILE and SECBIT_EXEC_DENY_INTERACTIVE are the enforcement half of the AT_EXECVE_CHECK flag of §3.1, letting an administrator declare that files a policy would refuse to execute may not be interpreted as scripts either, with locked companions for both. They are also the first securebits an unprivileged process may set on itself, which is why they appear in SECURE_ALL_UNPRIVILEGED rather than only in the privileged mask. The second refinement is simply that the capability list is not frozen: each kernel release may add bits as new privileged operations are carved out of older catch-alls. The third is that exec is not the only moment capabilities are recomputed: cap_task_fix_setuid adjusts them when a process changes identity at run time through the system calls of §6.4, dropping the effective set when a root process moves away from uid 0 and restoring it when it moves back, so that the traditional "temporarily drop privilege and pick it up again" idiom keeps working in a capability world. A process can switch that emulation off with the SECURE_NO_SETUID_FIXUP securebit and manage its own sets explicitly, which is what a program designed around capabilities rather than around uid 0 should do. The current ceiling is recorded as CAP_LAST_CAP (CAP_CHECKPOINT_RESTORE, value 40, in the 7.0 series). Code that enumerates or clears the bounding set must consult CAP_LAST_CAP rather than assuming a fixed count, precisely because the set keeps growing.

Changing Identity at Run Time: the Credential System Calls

Exec is the moment identity usually changes, but not the only one. A login daemon authenticates a user and then becomes that user; a setuid program drops root as soon as it has opened what it needed; a web server binds port 443 and then sheds every capability but the one it still uses. Each of these is a running process rewriting its own credentials through a small family of system calls, and every one of them is a thin wrapper around the discipline of §6.1: prepare_creds a copy, check the caller's right to make the change, mutate the copy, let the security modules adjust it, and commit_creds—or abort_creds if any step refuses. The uid and gid calls live in kernel/sys.c and kernel/groups.c, the capability calls in kernel/capability.c and the prctl branch of security/commoncap.c. All of them sit inside CONFIG_MULTIUSER; a kernel built without it (an EXPERT option for tiny systems) runs everything as uid 0 with every capability and compiles the calls out. __sys_setresuid is the cleanest of the uid calls and the model for the rest. It first translates each argument through the caller's user namespace with make_kuid, failing with EINVAL if a value has no mapping, and returns early if nothing would change. It then asks, for each requested value, whether it is new—equal to none of the current real, effective and saved uids. Shuffling among the ids the process already holds needs no privilege; introducing any new one requires CAP_SETUID, tested with ns_capable_setid so that the check is relative to the credential's own user namespace. Only then does it prepare the new cred, store the values, set fsuid to follow the new euid, and run the security_task_fix_setuid hook before committing. The older calls are the same machine with historical rules. setuid follows POSIX: a caller with CAP_SETUID sets real, effective and saved uid together, which is the one-way door a login program walks through, while an unprivileged caller may only move its effective uid to its real or saved uid. setreuid follows BSD, and its quirky saved-uid rule exists so that a program using only setreuid can still drop privilege permanently. The saved uid is what makes the reversible idiom possible at all: a setuid program sets its effective uid to its real uid while it works on the user's behalf, and the saved uid remembers the privileged identity it may return to. That is exactly the transition cap_task_fix_setuid of §6.3 tracks, clearing the effective capability set on the way out of uid 0 and restoring it from permitted on the way back.

Three details in the uid path are easy to miss. When the real uid changes, set_user attaches the per-user user_struct for the new identity and set_cred_ucounts points the credential at that user's per-namespace counters, against which commit_creds moves the process's RLIMIT_NPROC charge—but a setuid that pushes the new user over the limit does not fail. flag_nproc_exceeded merely sets PF_NPROC_EXCEEDED, and the next execve fails with EAGAIN instead (fs/exec.c), because, as the comment says, too many programs never check whether a call made as root succeeded. Second, ns_capable_setid passes CAP_OPT_INSETID to the LSM capable hook, which is what lets the SafeSetID module (5.1) grant a service CAP_SETUID yet confine it, through the task_fix_setuid, task_fix_setgid and task_fix_setgroups hooks, to an administrator's list of permitted transitions. Third, credentials belong to a thread, not a process: the raw system call changes only the calling thread. POSIX requires the change to be process-wide, so the C library broadcasts it, interrupting every other thread with an internal signal and having each repeat the call; a program that issues the raw system call directly from one thread gets per-thread identities.

The filesystem uid is Linux's own addition and has an odd interface to match. Every other uid call sets fsuid to the new effective uid, so it is normally invisible; setfsuid exists for a file server that must open files with a client's permissions without also becoming that client for signals and ptrace. It returns the previous value rather than a status and fails silently, so callers use setfsuid(-1), which can never succeed, to read the current value back and check. Supplementary groups are replaced wholesale by setgroups, which requires CAP_SETGID through may_setgroups; that function also consults the per-namespace /proc/<pid>/setgroups switch of Chapter 25, Section UID/GID Mapping, the gate that stops an unprivileged user namespace from dropping a group to escape a negative ACL. The 16-bit-id variants of these calls in kernel/uid16.c serve only 32-bit compat processes on x86_64 and arm64, both of which select HAVE_UID16 solely through their 32-bit compat options.

The capability calls exchange two user structures defined in include/uapi/linux/capability.h: a header __user_cap_header_struct holding a version and a pid, and an array of __user_cap_data_struct, each holding 32-bit effective, permitted and inheritable words. Version 1 (0x19980330) carried a single word per set; since capabilities passed 32 the current version 3 (0x20080522) uses an array of two, and version 2 is accepted with a deprecation warning. cap_validate_magic doubles as the negotiation protocol: given an unknown version, the kernel writes its preferred one back into the header and fails with EINVAL, which is how libcap discovers what to send. capget may read any task named by pid, but capset accepts only zero or the caller's own pid. In Linux 2.6.11 a process holding CAP_SETPCAP could rewrite another process's sets; that power was removed in 2.6.29 (David Howells's "CRED: Neuter sys_capset()") as part of the same rework that made struct cred immutable, because a credential only its owner may replace needs no lock to read. cap_capset then enforces the rules in Table 20-6. Permitted can only shrink and effective must stay within it. Inheritable may gain only capabilities the caller already holds in permitted, unless the caller has CAP_SETPCAP, which lets it add any capability still in the bounding set. The ambient set is quietly masked down to stay inside permitted ∩ inheritable, preserving the invariant of §6.1.

The bounding and ambient sets are not part of the capget/capset ABI at all; they and the securebits are reached through prctl, whose capability options cap_task_prctl handles. That function is also the home of PR_SET_KEEPCAPS, the piece that makes the classic daemon start-up work. Left alone, a root process that calls setresuid to an ordinary uid loses its permitted and effective capabilities (and its ambient set, whatever else is configured), because the setuid fixup assumes that leaving uid 0 means leaving privilege. With prctl(PR_SET_KEEPCAPS, 1) first, permitted survives the switch (effective is still cleared), and the process can capset exactly the capabilities it means to keep back into effective, then PR_CAP_AMBIENT_RAISE any that helper programs it executes should inherit. The flag is cleared on every exec, so it cannot leak into a program that did not ask for it. Each step in that sequence is a separate commit_creds, atomic on its own; the sequence as a whole is not, so code doing this must check every return value rather than assume a later step found the state an earlier one left. Every current set can be read without any of these calls from the CapInh, CapPrm, CapEff, CapBnd and CapAmb lines of /proc/<pid>/status.

Security Frameworks and Sandboxing

The credentials of §6 answer the question "who is this process and what is it allowed to do" in the classic Unix vocabulary of users and capabilities. But that vocabulary, however refined, is discretionary: it is ultimately about identity, and a sufficiently privileged identity can do almost anything. Modern systems demand more—policies that constrain even root, sandboxes a program imposes on itself, and the ability to fence off untrusted code so that compromising it yields little. This section surveys the frameworks Linux layers on top of the credential model to meet those demands. None of them is part of the classic exec path itself; all of them hook into it, and together they are the reason a browser tab, a systemd service, or a container can run hostile-by-assumption code on a shared kernel with confidence.

The four mechanisms form a rough progression from system-wide to self-imposed to observational. Linux Security Modules provide the mandatory-access-control plumbing an administrator configures once for the whole system. Seccomp lets a program voluntarily shrink the set of system calls it may make. Landlock lets an unprivileged program confine its own access to files and network ports. And ptrace stands slightly apart—a tool for observing and controlling execution rather than restricting it—but it is governed by the same credential and LSM rules, and it is where the chapter's threads about privilege and tracing meet. We take them in that order.

The Linux Security Modules Framework

We begin with the most general mechanism, the one the others are partly built on. The Linux Security Modules framework is not itself a security policy; it is the kernel-wide scaffolding that lets a policy exist—a systematic set of interception points threaded through every security-relevant operation, together with the rules for who may answer them. Understanding it first matters because seccomp, Landlock, and Yama are all, at bottom, LSMs, and because the exec-time hooks it defines are where several of this chapter's earlier threads—credential commit, secure-exec, domain transition—are actually enforced.

Standard Unix permissions and capabilities implement discretionary access control—the owner of a resource decides who may use it. Many systems need mandatory access control (MAC) as well: a system-wide policy that constrains even root and that users cannot override. The Linux Security Modules (LSM) framework (security/security.c) provides the plumbing for this. Throughout the kernel, at every security-relevant operation, sit hooks—security_bprm_check during exec, security_file_open when opening a file, security_socket_connect when connecting a socket, and hundreds more. A security module registers implementations for the hooks it cares about, and its checks run in addition to the ordinary DAC checks, able only to further restrict, never to grant. The bundled modules include SELinux (label- and type-enforcement based), AppArmor (path- and profile-based), Smack, TOMOYO, and the smaller Yama (which restricts ptrace); the always-on capability logic is itself structured as an LSM. There are now about two hundred and seventy-five hooks, declared in one place in include/linux/lsm_hook_defs.h, and the list of modules has grown well past the comprehensive-policy engines the name first suggested. Several of the newest are single-purpose and a few dozen lines long: LoadPin insists every kernel module and firmware image come from the same filesystem the first one did, SafeSetID constrains which user ids a process may transition to without CAP_SETUID, Lockdown closes the paths by which uid 0 could otherwise write to kernel memory on a Secure Boot system, IPE enforces an administrator-written policy about which binaries may execute at all, and the BPF LSM (Chapter 23) lets a policy be loaded as a verified program rather than compiled in. IMA and EVM, which measure and attest file contents, sit at the end of the order by construction; Chapter 27 describes them, together with SELinux, AppArmor, and the rest of the kernel's security infrastructure.

Two things about the modern framework differ sharply from the single-module design of Linux 2.6.11. First, LSM hooks are now dispatched through efficient per-hook lists (built on static calls), so the overhead of an inactive hook is negligible. Second, and more visibly, Linux now supports LSM stacking: several modules can be active at once, each keeping its own state in a shared per-object security blob embedded in the credential, inode, file, and task structures (their sizes negotiated at boot via lsm_blob_sizes). This is what lets a system run, say, the capability module, Yama, AppArmor, and Landlock simultaneously. The framework no longer enforces the old rule that only one comprehensive module could be active; ordering is what matters instead, and it is fixed at only two points (LSM_ORDER_FIRST for capabilities, LSM_ORDER_LAST for the integrity modules), with everything between taken from CONFIG_LSM or the lsm= boot parameter. A running kernel reports the resulting list in /sys/kernel/security/lsm, and since Linux 6.8 three system calls make it queryable without parsing that file: lsm_list_modules returns the active module ids, lsm_get_self_attr and lsm_set_self_attr read and write the calling process's own security attributes through a common struct lsm_ctx. That last pair matters because the historical interface was a set of per-module files under /proc/<pid>/attr, which had no way to say which module an answer came from once more than one was active. During exec the framework calls a defined sequence of hooks, and the order is not the order they are declared in: bprm_creds_for_exec runs first, from bprm_execve while everything is still reversible, then bprm_check_security once inside search_binary_handler, then bprm_creds_from_file when a loader has committed to the file, and finally bprm_committing_creds and bprm_committed_creds around the installation itself — which is where, for instance, SELinux performs a domain transition, switching the process to a new security context appropriate to the program it is becoming. Seccomp

LSMs express a policy an administrator writes; the next mechanism inverts that, letting a program impose a policy on itself. Seccomp starts from a sobering assumption—that the program may be compromised—and asks how to limit the blast radius when it is. Its answer is to narrow the kernel's attack surface as seen from one process: a task voluntarily surrenders the right to make system calls it does not need, so that code an attacker later injects finds most of the kernel's interface simply unavailable. Because the restriction is self-imposed and irrevocable, it composes cleanly with the credential rules of §6, as we will see.

Where LSMs enforce a policy an administrator configures, seccomp (secure computing, kernel/seccomp.c) lets a program restrict itself, shrinking the set of system calls it is allowed to make. The idea is defense in depth: even if an attacker takes control of a process, a tight seccomp policy limits the damage, because syscalls outside the allowed set are blocked by the kernel. There are two modes. SECCOMP_MODE_STRICT permits only read, write, exit, and sigreturn—enough for a pure computation on already-open descriptors and nothing else. The powerful mode is SECCOMP_MODE_FILTER, where the program installs a BPF program that the kernel runs on every system call, inspecting a struct seccomp_data (the syscall number, the architecture, and the six arguments) and returning an action.

The filter's return value selects from a range of actions, listed in Table 20-7, from silently allowing the call to killing the process outright. Every filter in the stack runs on every call, and the results are combined by taking the lowest value — which is why the constants are numbered the way they are. Read as signed 32-bit quantities they run from SECCOMP_RET_KILL_PROCESS (0x80000000, negative) up to SECCOMP_RET_ALLOW (0x7fff0000), so a plain minimum over the return values always selects the least permissive answer any filter gave. A later filter can therefore tighten an earlier one but can never relax it, and no bookkeeping is required to make that true. Because running every filter on every call would be costly in the common case, an architecture that defines SECCOMP_ARCH_NATIVE lets the kernel precompute a bitmap of the syscall numbers that all installed filters allow unconditionally, whatever the arguments; a hit in that bitmap skips the BPF programs entirely, and /proc/<pid>/seccomp_cache lists which numbers qualified. Filters are inherited across fork and exec and are strictly additive—a process can stack more filters but never remove one, so a sandbox cannot be loosened once entered. Installing a filter requires either CAP_SYS_ADMIN or, more usefully, the no_new_privs latch from §6.2, which guarantees the filter cannot be escaped by exec'ing a setuid program. A newer action, SECCOMP_RET_USER_NOTIF, hands a blocked syscall to a supervising process through a descriptor, letting a monitor emulate or vet syscalls on the sandboxed program's behalf—the mechanism behind modern container runtimes' syscall interception. Seccomp is the backbone of sandboxing in browsers, systemd services, and container engines.

The notification mechanism deserves a closer look, because it is the one action that does not simply decide. Installing a filter with SECCOMP_FILTER_FLAG_NEW_LISTENER returns a descriptor instead of zero, and the supervisor drives it with a small set of ioctls: it reads a pending request with SECCOMP_IOCTL_NOTIF_RECV, answers with SECCOMP_IOCTL_NOTIF_SEND, and can install a file descriptor directly into the stopped process with SECCOMP_IOCTL_NOTIF_ADDFD — which is how a container runtime services a mount or an open the sandbox is not allowed to perform itself, doing the work with its own privilege and handing back the result. Two details keep this honest. Because the sandboxed thread can be killed while a request is outstanding, SECCOMP_IOCTL_NOTIF_ID_VALID lets the supervisor confirm that the cookie it is holding still refers to a live request before it acts on it. And SECCOMP_USER_NOTIF_FLAG_CONTINUE, which tells the kernel to let the original call proceed after all, carries a warning in the UAPI header: the supervisor has already inspected the arguments, the syscall has not yet read them, and nothing prevents another thread from rewriting them in between. It is safe for deciding whether a call is ever allowed, not for deciding whether these particular arguments are.

The remaining flags to seccomp(SECCOMP_SET_MODE_FILTER, ...) handle problems the basic model creates. A filter is a property of a thread, not a process, so a multithreaded program that sandboxes itself one thread at a time leaves a window in which some threads are confined and others are not; SECCOMP_FILTER_FLAG_TSYNC applies the filter to every thread in the group atomically, failing if any sibling has a filter that is not an ancestor of the new one, and SECCOMP_FILTER_FLAG_TSYNC_ESRCH makes that failure distinguishable from an ordinary error. SECCOMP_FILTER_FLAG_LOG records every denial rather than only those the filter explicitly asks to log, which is how a policy is developed in the first place — run the program, collect the denials, and tighten from there. And SECCOMP_FILTER_FLAG_SPEC_ALLOW is an opt-out: by default, installing a filter also enables the speculative-store-bypass mitigation for the task, on the reasoning that a process which has just declared itself untrusted should not be left exposed to Spectre-class attacks, and a program that knows better can decline to pay for it. Finally, a program can ask ahead of time whether the kernel it is running on understands an action at all, with SECCOMP_GET_ACTION_AVAIL, rather than discovering it through a filter that silently behaves differently than intended.

Landlock

Seccomp is powerful but blunt: it reasons about which system call is made, not about what that call touches. The final sandboxing mechanism fills exactly that gap, and it does so with a property none of the others share—it needs no privilege at all. Where mandatory access control historically required an administrator and a system-wide policy, Landlock lets any ordinary program draw a fence around its own object access, which is a genuine shift in who can sandbox what. It is the piece that makes least privilege something an application author can adopt unilaterally rather than something an operator must configure.

Seccomp filters syscalls but cannot easily express "this process may read /etc but write only /tmp," because that is about which objects a syscall touches, not which syscall it is. Landlock (security/landlock/), merged in Linux 5.13, fills that gap. It is an unprivileged sandboxing LSM: any process, with no special privilege, can restrict its own—and its children's—access to the filesystem and, more recently, to network ports. A program builds a ruleset with landlock_create_ruleset, declaring which access rights it wants to govern (the LANDLOCK_ACCESS_FS_* bits: execute, read a file, write a file, read a directory, remove, make a node, and so on); adds rules granting specific accesses beneath specific directories with landlock_add_rule; and then locks the restriction onto itself with landlock_restrict_self. From that point every filesystem access the process makes is checked against the ruleset by Landlock's LSM hooks, and anything not explicitly allowed is denied.

Landlock rulesets are inherited across fork and exec and stack in layers—each new restriction narrows what the process can do, never widens it, and a program launched under a Landlock sandbox cannot escape it by exec'ing something else. Like seccomp, it requires no_new_privs, ensuring the sandbox cannot be circumvented through a privilege-gaining exec. The significance of Landlock is that it puts real, composable sandboxing in the hands of ordinary applications: a document viewer or a build tool can voluntarily confine itself to just the directories it needs, without root, a container, or a system-wide policy—a capability Linux 2.6 had no equivalent of. Recent kernels have extended the same model beyond the filesystem to TCP networking, adding LANDLOCK_ACCESS_NET_BIND_TCP and LANDLOCK_ACCESS_NET_CONNECT_TCP rights so a process can also restrict which ports it may bind or connect to, all through the same create-ruleset / add-rule / restrict-self sequence.

Landlock has kept growing, and the shape of that growth is instructive: each addition closes a hole through which a sandboxed process could still reach outside its fence. LANDLOCK_ACCESS_FS_REFER governs moving a file between directories, an operation that touches two places at once and so could not be expressed by the original rights; LANDLOCK_ACCESS_FS_TRUNCATE closes the gap that a file opened for truncation is not a file opened for writing; and LANDLOCK_ACCESS_FS_IOCTL_DEV covers device ioctls, which are effectively an open-ended second system-call interface hiding behind an already-open descriptor. Beyond the filesystem and TCP rights there are now scopes—LANDLOCK_SCOPE_ABSTRACT_UNIX_SOCKET and LANDLOCK_SCOPE_SIGNAL—which fence off the two channels of Chapter 19 that have no pathname to attach a rule to: a sandboxed process can be stopped from connecting to an abstract socket, or from signalling a process, outside its own domain. Because user space must discover which of these a running kernel supports, landlock_create_ruleset called with LANDLOCK_CREATE_RULESET_VERSION returns an ABI version number rather than a descriptor, and a companion LANDLOCK_CREATE_RULESET_ERRATA query reports fixes within a version; Linux 7.0.12 reports ABI version 8. A library therefore negotiates downward, asking for the rights it wants and falling back to a weaker sandbox on an older kernel instead of failing outright.

Two of the most recent additions are not new rights at all, and both answer complaints from people trying to deploy Landlock rather than design it. The first is audit. A sandbox that silently denies an access is very hard to debug, because the program merely sees EACCES from somewhere and has no way to learn which layer of which domain refused it; Landlock now logs denials through the audit subsystem, tagging each with the identity of the domain that caused it, and gives landlock_restrict_self three flags to control the volume — LANDLOCK_RESTRICT_SELF_LOG_SAME_EXEC_OFF for interpreters that run untrusted code without ever calling execve, LANDLOCK_RESTRICT_SELF_LOG_NEW_EXEC_ON to keep logging across an exec when every program in the domain is expected to comply, and LANDLOCK_RESTRICT_SELF_LOG_SUBDOMAINS_OFF for a container runtime that launches programs which sandbox themselves in turn. The second is the same multithreading problem seccomp solved with TSYNC, and it is solved the same way: a Landlock domain is a property of a thread, so LANDLOCK_RESTRICT_SELF_TSYNC applies the new domain and its logging configuration to every thread in the process at once, enabling no_new_privs on the siblings if the caller has it. Without that flag a threaded program had no race-free way to confine itself, which in practice meant sandboxing had to happen before the first thread was created.

One limit is worth stating plainly because it has no equivalent in seccomp: a process may stack at most sixteen Landlock layers (LANDLOCK_MAX_NUM_LAYERS). The bound exists because every access check must consult every layer, so the cost of a check is linear in the depth of nesting, and sixteen is judged deep enough for a container inside a service inside a session while keeping the check cheap. Exceeding it is a hard E2BIG, not a silent flattening, which is the right failure for a security mechanism but does mean deeply nested sandboxing has a ceiling that a deployment can actually hit.

Execution Tracing with ptrace

The three mechanisms so far all restrict what a process may do. The last one in the chapter does the opposite—it lets one process reach into another and observe or control it completely—yet it belongs here for two reasons. It is the tool through which we watch a program execute (every debugger and syscall tracer is built on it, and it fires an event precisely at exec), and, because it confers total control, it is fenced in by the very credential and LSM rules the rest of this section established. Seeing how tracing is permitted, and how it deliberately loses its power against a privilege-raising exec, ties the chapter's themes of loading, privilege, and observation together.

The last mechanism observes execution rather than restricting it. ptrace (kernel/ptrace.c) is the system call behind debuggers (gdb), tracers (strace), and many sandboxes. A tracer attaches to a tracee—either the tracee volunteers with PTRACE_TRACEME (as a child does after fork, before exec) or the tracer seizes an existing process with PTRACE_ATTACH or the newer PTRACE_SEIZE. Once attached, the tracer can stop the tracee, read and write its memory and registers (PTRACE_PEEKTEXT, PTRACE_GETREGSET), single-step it, intercept its system calls (PTRACE_SYSCALL), and be notified of events. Exec is one such event: with PTRACE_O_TRACEEXEC the tracer receives a PTRACE_EVENT_EXEC stop when the tracee successfully execs a new program, which is how a debugger regains control of a freshly loaded binary. Table 20-8 groups the principal ptrace requests by what they accomplish.

The interface has accumulated two conveniences worth knowing about, both aimed at the same weakness: a tracer stopped inside a tracee used to have to reconstruct from architecture-specific register conventions what it was looking at. PTRACE_GET_SYSCALL_INFO now reports directly whether a stop is a syscall entry, a syscall exit, or a seccomp event, along with the call number, the arguments, and the return value, in a form that is the same on every architecture. PTRACE_GETREGSET and PTRACE_SETREGSET do the corresponding job for register state, naming a set by an ELF note type rather than assuming a fixed layout — which is what lets one debugger handle the base registers, the floating-point state, the vector registers, and ARM64's pointer-authentication keys through a single call.

Where ptrace and seccomp meet, the rules are deliberately asymmetric. SECCOMP_RET_TRACE lets a filter defer a decision to a tracer, which receives a PTRACE_EVENT_SECCOMP stop and may change the syscall number, rewrite the arguments, or suppress the call — but if no tracer is attached the call simply fails with ENOSYS rather than being allowed, so a filter written this way fails closed. Going the other way, a tracer cannot switch a tracee's seccomp filter off: PTRACE_O_SUSPEND_SECCOMP exists only for checkpoint and restore, requires CAP_SYS_ADMIN, and is refused outright if the tracer itself is running under seccomp — which closes the obvious route by which a sandboxed process would escape its own sandbox by tracing a child.

Because ptrace grants total control over another process, who may trace whom is tightly governed. The core check is ptrace_may_access, which compares credentials and consults the LSM ptrace_access_check hook. Note that the mode the caller passes is not a single value: every site must choose between PTRACE_MODE_FSCREDS and PTRACE_MODE_REALCREDS, because a process that has temporarily dropped privilege should be judged on the identity it is acting under, while a check made on behalf of a file operation should be judged on the filesystem identity. Getting that choice wrong has been a real source of bugs, which is why the header refuses to define a bare PTRACE_MODE_ATTACH without one of the two attached.

On top of that core check the Yama module adds a system-wide kernel.yama.ptrace_scope sysctl with four escalating levels. Level 0 is the classic behavior, in which any process may trace another it could signal. Level 1 — the kernel's own default when Yama is built in, and the setting most distributions ship — allows attaching only to a descendant, which stops one compromised process from reading a sibling's memory for keys and session tokens. Level 2 requires CAP_SYS_PTRACE, and level 3 disables attaching altogether and cannot be undone without a reboot; indeed the sysctl handler refuses to lower the value once it has been raised to the maximum, so hardening here is a one-way door.

Level 1 is worth reading carefully, because it is usually described more narrowly than it is. The relationship it requires is descendant, not child: task_is_descendant walks the whole chain of real_parent links, normalizing to thread-group leaders as it goes, so a debugger can attach to a grandchild it launched through a shell. And the rule has a deliberate escape hatch. A process that expects to be traced by something outside its own subtree — a crash reporter, a system-wide debug server — declares the exception itself with prctl(PR_SET_PTRACER, pid), naming the process it is willing to be traced by, or PR_SET_PTRACER_ANY to drop the restriction entirely. Yama records the declaration against the task, checks it in ptracer_exception_found, and honours it only for the declaring process, so the permission is granted by the would-be tracee rather than taken by the tracer. Failing all of that, holding CAP_SYS_PTRACE in the target's user namespace still works, which is what keeps a container manager able to debug what it started.

Tracing also interacts with the privilege rules of this chapter, and the interaction runs in the direction one would hope: a setuid program executed under a tracer normally does not gain its elevated privileges. The exec is flagged LSM_UNSAFE_PTRACE, and cap_bprm_creds_from_file responds by dropping the new effective ids back to the real ones, so a debugger cannot single-step a setuid binary into handing over root. The rule is not absolute, though, and the exception is the sensible one: if the tracer already holds CAP_SYS_PTRACE over the target — the condition ptracer_capable tests — the downgrade is skipped, because such a tracer could simply write to the process's memory afterward and has gained nothing. The privilege is withheld from tracers who would be escalating, not from those who already could. ptrace thus closes the chapter where it fits: a powerful window into a running program, fenced in by the same credential and LSM machinery that governs execution itself.

Summary

This chapter followed a program from an inert file on disk to a running, constrained process, tracing the path of the exec system call. An executable is a recipe for an execution context, and running it means replacing the calling process's entire user-space state while the process itself—its pid, its open files, its place in the process tree—survives. The kernel identifies the file's format through the pluggable binary-format framework, where ELF now reigns and scripts and binfmt_misc redirect to interpreters. It drives the file through the execve/execveat pipeline, building a fresh address space and stack alongside the caller's and doing all fallible work—opening, validating, preparing credentials, consulting the security framework—before the irreversible begin_new_exec tears down the old program and commits the new one at the point of no return. What it builds on the other side is only half the story: for a dynamically linked program the kernel maps two ELF objects and jumps to the second one, leaving the dynamic linker to assemble the rest of the process in user space out of the same mmap every other program uses.

Several threads in the chapter turn out to be the same thread. The point-of-no-return split, the prepare-then-commit discipline of struct cred, and the reserve-then-unmap trick the ELF loader uses to place a PIE are all the same answer to the same problem: build the new thing beside the old one, and switch only when nothing can still fail. The one-way latch appears just as often — no_new_privs, a seccomp filter, a Landlock layer, mseal, MDWE, a locked securebit, and Yama's ptrace_scope can each be tightened but never loosened, which is what lets an untrusted program be handed authority it cannot give back to itself. And the recurring reason a mechanism is shaped the way it is turns out, over and over, to be a namespace: capabilities are checked relative to one, binfmt_misc rules live in one, file capabilities carry a rootid so they mean something only inside one, and identities are kuid_t values that have no meaning outside one.

The larger theme is how much of modern execution is about defense. In Linux 2.6.11, exec loaded a fixed-address binary with a handful of uid fields for security. Today's exec lays a position-independent executable and its libraries at randomized addresses, maps a non-executable stack and a read-only GOT, plants a random seed for the stack canary, and hands the dynamic linker a secure-exec flag that neutralizes environment-based attacks on privileged programs. Privilege itself is now a reference-counted credential object carrying five capability sets rather than raw root, computed carefully across each exec, checked relative to a user namespace rather than globally, and latched by no_new_privs. And a layered stack of frameworks—a stack of LSMs rather than a single module, seccomp filtering system calls, Landlock fencing off files, network ports, abstract sockets and signals without any privilege at all, and Yama restricting who may trace whom—decides what the new program may do. With that, the book's tour of the classic kernel is complete. It began with the raw materials—memory addressing, processes, and interrupts—and built upward through synchronization, the memory-management subsystem, the virtual filesystem and the page cache, the block and filesystem layers, and the ways processes communicate. It ends here, where all of those subsystems converge: turning a file into a process draws on the memory manager to build the address space, the VFS to open the file, the scheduler to run it, the signal and credential machinery to govern it, and the security frameworks to fence it in. The kernel that does all this has grown enormously since Linux 2.6.11, yet it has done so by extending the same small set of ideas this book has traced throughout—objects reached through uniform interfaces, mechanisms separated from policy, work deferred until it is truly needed, and generic infrastructure reused everywhere. Those ideas, more than any particular data structure, are what it means to understand the Linux kernel. The chapters that follow put that claim to the test, first on power management and networking, and then on subsystems that did not exist, or barely existed, in Linux 2.6.11—eBPF, io_uring, namespaces and cgroups, Rust, the security frameworks, KVM, and the kernel's tracing and diagnostic tools—and it will be worth watching how much of each turns out to be the same ideas again, in new clothes.
