Every I/O interface in this book so far has, at bottom, made the same bargain: a process asks the kernel to do one thing—read this, write that—by making a system call, and waits, or arranges to be told later, that the one thing is done. That model has served Unix for fifty years, but on modern hardware it has become the bottleneck. A single NVMe drive can service millions of operations per second and a fast network card can deliver millions of packets, and at those rates the cost of the system call itself—crossing into the kernel, and crossing back, once per operation—comes to dominate the cost of the I/O. io_uring, introduced in Linux 5.1, is the kernel's answer. It replaces the per-operation system call with a pair of shared-memory ring buffers: user space writes I/O requests into one ring and reads results from another, and the kernel reads and writes the same rings from its side, so that many operations can be submitted and completed with few system calls—or, in its most aggressive mode, with none at all.

The result is not merely a faster read; it is a different shape for the whole relationship between an application and the kernel's I/O machinery. io_uring is genuinely asynchronous, so a program can have thousands of operations in flight at once; it is general, covering not just file reads and writes but networking, timeouts, filesystem operations, and even arbitrary device commands through one uniform interface; and it is extensible, with new operation types and completion modes added in nearly every kernel release. This chapter builds it up from the rings outward: the shared queues and the data structures that flow through them, the life of a single request from submission to completion, the range of operations and the ways they are ordered, chained and cancelled, the two mechanisms—submission-queue polling and an async worker pool—that let it run without blocking the submitter, the registered and provided resources that shave the last overheads away, the advanced completion modes that power high-performance networking, and finally the security machinery that so powerful an interface requires—including the restrictions and filters with which a program can confine a ring to the few operations it actually needs.

What io_uring Is

Before the rings themselves comes the problem io_uring solves, stated precisely, because its design is a direct response to the shortcomings of everything that came before it. io_uring is among the newest subsystems this book describes—only sched_ext, from Chapter 7, is younger—and it is easily the fastest-growing. It was merged in Linux 5.1 in early 2019, more than a decade after Linux 2.6.11, and it has been extended in almost every release since, which is why a chapter on it is as much a snapshot of work in progress as a description of a finished design. The pace shows in the shape of the source tree. io_uring began as a single file, fs/io_uring.c, and outgrew it so thoroughly that in Linux 6.0 it was promoted to a top-level directory of its own; in 7.0.12 that directory holds some forty C files and around twenty-six thousand lines, with roughly one file per family of operations. It was created by Jens Axboe, the maintainer of the block layer, together with Christoph Hellwig (see the copyright header of io_uring/io_uring.c), originally to give the storage stack an asynchronous interface that actually worked, and it has since grown to cover networking, timers, and much else. Today it underlies the I/O paths of high-performance databases, network proxies, and storage engines, and it is increasingly the interface a program reaches for when the standard system calls cannot keep a fast device or network link busy. This section looks first at why both synchronous system calls and Linux's earlier asynchronous-I/O interface fall short on modern hardware, and then at the shared-ring idea that answers them.

The rest of the chapter works down this stack: the two subsections below first motivate the design, and the sections that follow detail the rings and everything built on them.

The Cost of Synchronous and Legacy Asynchronous I/O

The traditional I/O calls—read, write, and their relatives from Chapter 16—are synchronous: the calling thread issues one, and the kernel does not return until the operation is done (or, for a non-blocking descriptor, until it determines the operation would block). Each call is a full user-to-kernel round trip, and each moves the data for exactly one operation. When a program must perform many small I/Os, the round trips dominate: the CPU spends more time entering and leaving the kernel than doing useful work, and modern mitigations for CPU speculation vulnerabilities have only made each crossing more expensive. Worse, true overlap is hard to achieve—to keep many operations in flight a program must resort to many threads, each blocked in its own synchronous call, paying the cost of all those threads.

Linux did have an asynchronous interface before io_uring—the kernel's native AIO, implemented in fs/aio.c, set up with io_setup and driven by io_submit, and normally reached through the libaio wrapper library—but it was widely regarded as a disappointment. (It should not be confused with POSIX AIO, the aio_read and aio_write family, which glibc emulates entirely in user space with a pool of threads and which the kernel knows nothing about.) It worked well only for direct I/O that bypassed the page cache; for ordinary buffered file I/O it silently fell back to blocking, defeating its purpose. It still required a system call per submission and per completion reaping. And it covered only a narrow slice of operations—reads and writes, but not the open, accept, recv, and dozens of other operations a real application interleaves with them. The lesson the kernel developers drew, and built io_uring around, was that a general asynchronous interface must be truly async for all I/O, must cover the full range of operations, and must not require a system call for every request. Meeting all three at once is what the shared rings make possible.

The first of those requirements is the subtle one, because the rings do not supply it. Shared memory removes system calls; it does nothing to stop a read from sleeping once the kernel has picked it up, and a thread asleep on the page cache is exactly what the older interface was faulted for. The answer lies elsewhere in the design, in a division of labour that §3.1 sets out in full: io_uring never asks whether an operation will block, it attempts the operation in a mode that forbids blocking and treats the refusal as information. A cached read succeeds outright; one that must wait for the disk is rejected with -EAGAIN before any sleeping happens, leaving the request to be parked on a poll wait or moved to a thread that is allowed to sleep. The consequence matters more than the mechanism, and it is the one thing native AIO could never manage: buffered file I/O becomes genuinely asynchronous to the application without anyone having to pretend that reading from a disk is a non-blocking operation.

io_uring is easily confused with the readiness model that programs have long used to juggle many connections. The select, poll, and epoll family of Chapter 16 tells an application when a descriptor is ready—when a socket has data to read or space to write—but it does not do the I/O; the application must still issue a read or write system call afterward, and each of those is a separate kernel crossing. Readiness notification also does not extend cleanly to storage, where a regular file is essentially always “ready” yet a read may still block while the disk is consulted. io_uring instead follows a completion model: the application asks for the operation itself to be performed and is told when it has finished, with the result in hand, so there is no second syscall and no distinction between the socket and the disk. In effect io_uring folds the “wait until ready” and “now do it” steps that epoll keeps separate into a single asynchronous request, which is why it can express not just reads and writes but a whole graph of interdependent operations, as later sections show.

The Shared-Ring Idea

The central idea of io_uring is to move the submission and reaping of I/O out of system calls and into memory that user space and the kernel share. When an application sets up an io_uring instance, the kernel allocates two circular buffers—a submission queue (SQ) and a completion queue (CQ)—and maps them into the application's address space, so that both sides can read and write them directly without a system call in between. To submit work, the application writes a submission queue entry (SQE) describing an operation into the SQ and advances the queue's tail; to collect results, it reads completion queue entries (CQEs) from the CQ. The kernel does the mirror image: it consumes SQEs from the SQ and produces CQEs into the CQ. Figure 24-2 shows the arrangement.

Two properties of this arrangement give io_uring its power. First, because the rings are shared, a single system call can submit a whole batch of queued SQEs and reap a whole batch of CQEs, amortizing the cost of the kernel crossing over many operations instead of paying it per operation. Second, because submission is decoupled from completion, the interface is inherently asynchronous: the application deposits a request and moves on, and the corresponding completion may appear in the CQ much later, identified by a user_data value the application chose when it submitted. From these two properties everything else in the chapter follows—the polling modes that remove even the batching system call, the linked operations that express dependencies, and the registered resources that strip away the remaining per-operation setup.

Three system calls set this machinery in motion, and they are the only ones io_uring adds. io_uring_setup creates an instance and returns a file descriptor; the application then maps the ring memory through that descriptor. io_uring_enter is the workhorse that submits queued SQEs and waits for completions—and the call that the polling modes of §5 can eliminate. And io_uring_register pins the long-lived resources of §6. Because the queues live in memory that both sides mutate concurrently, every access to a shared field is made with READ_ONCE and WRITE_ONCE and paired acquire/release barriers, as the long comment at the head of io_uring/io_uring.c spells out; getting this coordination exactly right is delicate, which is why almost no program drives the rings by hand. Instead most use liburing, the companion user-space library maintained alongside the kernel by the same authors, which wraps the raw ring memory and the three system calls in a small, correct API. This chapter describes the kernel interface that liburing sits on top of; a real application usually sees io_uring through that library.

That the count has stayed at three is itself a design decision. On x86-64 the calls occupy system call numbers 425, 426, and 427, and no fourth has been added in the seven years since—over a period in which the capability of the interface has grown several times over. io_uring expands by extending tables rather than by adding entry points: the opcode field of a submission queue entry selects from the operation table of §4.1, and the first argument of io_uring_register selects from a separate table of registration commands that now runs to nearly forty, the newest of which appears in §8.2. A new operation therefore costs a table row rather than a fresh system call and a fresh ABI commitment, which is how the subsystem absorbed networking, timers, futexes, and command passthrough without disturbing its three doors. The price is paid on the other side: a program cannot assume the kernel it happens to be running on understands the operations it was compiled against, which is why the interface also has to be able to describe itself, as §4.1 shows.

The Submission and Completion Rings

With the idea in hand, we can look at how the rings are actually built and used: how an application creates an io_uring instance and maps its rings into memory, what the entries that flow through them contain, and the careful protocol of indices and memory barriers by which two concurrent parties—an application and the kernel—share a queue without locks. This section covers those three concerns in turn.

One thing should be said at the outset: the rings, the entry structures, and the offsets that locate them are io_uring's application binary interface: they are defined in include/uapi/linux/io_uring.h, the kernel's public UAPI header, and are guaranteed stable across kernel versions so that a program compiled today keeps working on the kernels of years hence. Everything in this section is therefore not an implementation detail but a contract. The sizes are always powers of two so that the head and tail can be wrapped with a single mask rather than a division, and the shared structures are laid out with cache-line alignment in mind, because the application and the kernel touch them from different CPUs and false sharing between the two would cost exactly the overhead the design exists to avoid.

Setting Up and Mapping the Rings

An application creates an io_uring instance with the first of the interface's three system calls, io_uring_setup (io_uring/io_uring.c). It passes the number of submission entries it wants and a struct io_uring_params (include/uapi/linux/io_uring.h) carrying setup flags and receiving, in return, the exact sizes the kernel chose and—crucially—a set of offsets. The call returns a file descriptor representing the instance, unless the application asked with IORING_SETUP_REGISTERED_FD_ONLY for an index into the ring's own registered-descriptor table instead, which keeps the instance out of the file descriptor table altogether. The application then calls mmap on the ring memory through that descriptor and uses the returned struct io_sqring_offsets and struct io_cqring_offsets to locate, within the mapped region, each field it needs: the head and tail indices, the ring mask and entry count, and the arrays of entries themselves. After this one setup call and a couple of memory mappings, the application holds direct pointers into the shared rings and needs no further system call merely to reach them.

The struct io_uring_params passed to the call repays unpacking, because it is both an input and an output. On input the application fills in the flags that select the instance's mode—the polling and low-latency setup flags of the later sections—and, for a polling instance, the sq_thread_cpu and sq_thread_idle fields that place and tune the poll thread. On return the kernel fills in sq_entries and cq_entries with the sizes it actually chose (both rounded up to a power of two, with the completion ring defaulting to twice the submission ring so that completions rarely have nowhere to go), the two offset structures, and a features bitmask reporting which optional behaviors this kernel supports. That last field is how a program negotiates with the running kernel: before relying on a capability it checks the corresponding IORING_FEAT_ bit—IORING_FEAT_NODROP for guaranteed completion delivery, IORING_FEAT_SINGLE_MMAP for the combined mapping described next, IORING_FEAT_SUBMIT_STABLE for the promise that SQE data may be reused as soon as submission returns, and fifteen others, eighteen bits in all as of 7.0.12—so that one binary can adapt to the feature set of whatever kernel it finds itself on. The list only ever grows, and each bit marks a point at which the interface acquired a guarantee it had not previously made. The full structure is shown below, and Table 24-1 describes each field and the direction in which it is passed.

The mapping itself reflects the ring layout, which is really three regions, each selected on the instance's file descriptor by a fixed magic offset:

  • The submission ring (IORING_OFF_SQ_RING) — the SQ header (head, tail, mask, flags) together with the array of u32 indices, but not the entries themselves.
  • The SQE array (IORING_OFF_SQES) — a flat, contiguous array of the actual struct io_uring_sqe entries the indices point into.
  • The completion ring (IORING_OFF_CQ_RING) — the CQ header together with the array of struct io_uring_cqe entries, held directly.

A fourth magic offset, IORING_OFF_PBUF_RING, maps the provided-buffer rings of §6.2, with the buffer group encoded above IORING_OFF_PBUF_SHIFT so that one offset space serves any number of groups. The three regions above are the ones every instance has; the buffer rings are mapped only by applications that use them.

Historically an application performed two or three mmap calls to map these regions. On modern kernels the submission and completion rings occupy one contiguous region—the kernel signals this by setting IORING_FEAT_SINGLE_MMAP—so a program maps the rings with a single call and the SQE array with a second. The direction of the mapping can even be reversed. With IORING_SETUP_NO_MMAP the application allocates the ring memory itself and passes its address to io_uring_setup, which pins those pages rather than providing its own; a program that wants its rings backed by huge pages, or placed on a particular NUMA node, can arrange it that way and simply hand the result to the kernel. Nor are the sizes settled forever: an instance using the deferred completion mode of §7.2 can grow or shrink both rings at runtime with the IORING_REGISTER_RESIZE_RINGS operation, which takes a fresh struct io_uring_params and migrates any entries still outstanding. The kernel side of what these calls expose is one allocation described by struct io_rings (include/linux/io_uring_types.h), which holds both rings' heads and tails, the constant ring masks and entry counts, the dropped- and overflow-event counters of §2.3, and the completion-entry array itself. Finally, because the instance is represented by an ordinary file descriptor backed by an anonymous inode, it is a first-class kernel object: it can be passed to epoll or poll to wait for completions in a classic event loop, inherited across fork, and torn down simply by closing it, which releases the rings and cancels any operations still in flight. An io_uring instance is thus both an exotic shared-memory construct and an ordinary file—which is why the whole of §8.1 can be framed around who is allowed to open one.

One indirection on the submission side is easy to stumble over, and it is the reason the SQ ring is not simply a queue of entries. The submission ring does not contain SQEs directly; it contains an array of u32 indices into the separate SQE array. This turns the SQE array into an application-managed memory pool: a program can prepare several SQEs concurrently and out of order, hold each one next to its own per-request bookkeeping in whatever data structure suits it, and then—only when an entry is ready—push that entry's integer index onto the submission ring. It can even point two ring slots at the same SQE to submit it twice. In practice many applications forgo the flexibility and fill the SQE array and the index array in lockstep, which makes the indirection pure overhead; for them a ring created with IORING_SETUP_NO_SQARRAY omits the index array entirely, and the kernel reads the SQE at the head position directly. The indirection remains the default, and remains available to those who want it. The completion ring, by contrast, needs no such flexibility and holds CQEs directly, because the kernel is the sole producer and simply appends each result to the next slot. Two setup flags can widen the entries: IORING_SETUP_SQE128 doubles the SQE to 128 bytes for operations that need more parameters (such as the command passthrough of §7.3), and IORING_SETUP_CQE32 doubles the CQE for operations that return extra data.

Those two flags size an entire ring, which is a blunt instrument: an application that needs a 128-byte SQE for one operation in a thousand pays double the submission memory and double the write traffic for all of them. Recent kernels therefore let the two sizes coexist. With IORING_SETUP_SQE_MIXED a ring accepts both 64- and 128-byte submissions, the wide ones identified by the opcode itself, so a program can spend the extra cache line only where an operation genuinely needs it; with IORING_SETUP_CQE_MIXED the completion ring likewise carries both 16- and 32-byte entries, each wide one marking itself with IORING_CQE_F_32 in its flags so the application knows how far to advance. Both arrived during the 7.0 development cycle and are the newest additions to the layout described here—a reminder that even the parts of io_uring presented as fixed ABI are still gaining room to move.

The SQE and CQE

The two entry types are the vocabulary of the interface. A submission queue entry, struct io_uring_sqe (include/uapi/linux/io_uring.h), describes one operation. Its layout is a fixed frame with large unions, because a single structure must serve every operation type: the same fields mean different things for a read than for a socket accept. The opening fields are common—an opcode selecting the operation, per-request flags, an I/O priority, and the file descriptor fd to act on—followed by unions holding an offset, an address (of a buffer or an array of buffers), a length, and an operation-specific flags word. Two fields are the application's own: the 64-bit user_data, copied verbatim into the matching CQE so the application can identify which request completed, and a buffer index or group used by the registered- and provided-buffer machinery of §6. 

/* include/uapi/linux/io_uring.h (abridged) */
struct io_uring_sqe {
	__u8	opcode;		/* type of operation (IORING_OP_*) */
	__u8	flags;		/* IOSQE_* per-request flags */
	__u16	ioprio;		/* I/O priority */
	__s32	fd;		/* file descriptor to operate on */
	union { __u64 off; __u64 addr2; /* ... */ };   /* offset / 2nd address */
	union { __u64 addr; __u64 splice_off_in; /* ... */ }; /* buffer / iovecs */
	__u32	len;		/* buffer size or iovec count */
	union { __u32 rw_flags; __u32 msg_flags; __u32 timeout_flags; /* ... */ };
	__u64	user_data;	/* copied back into the CQE */
	union { __u16 buf_index; __u16 buf_group; /* ... */ };
	/* ... personality, splice_fd_in, further op-specific fields ... */
};

The union-heavy shape is deliberate, and its reasons explain a good deal of how the interface behaves. An SQE is a fixed 64-byte frame—one cache line, a size the kernel asserts at build time with a BUILD_BUG_ON—so that producing one is a single aligned write and the kernel can fetch it in one memory access; the 128-byte IORING_SETUP_SQE128 variant of §2.1 simply spans two lines for the few operations that need more room. Within that frame the unions let the same bytes carry a file offset for a read, a second address for a vectored operation, or a command word for passthrough, and let one flags slot mean rw_flags for I/O, msg_flags for a socket send, or timeout_flags for a timer, so that a single structure covers the whole opcode table of §4 without growing. Two of the tail fields deserve names: the personality field selects a registered set of credentials under which the operation should run—so that a privileged server can perform an operation with the identity of a less-privileged client, subject to the LSM check of §8.1—and splice_fd_in supplies the second descriptor for the splice and tee operations. The flags byte carries the per-request IOSQE_ modifiers—fixed-file, drain, and the link bits—covered with chaining in §4.2. A completion queue entry, struct io_uring_cqe, is far simpler. It carries back the user_data the application supplied, a result res—which holds exactly what the equivalent synchronous system call would have returned, a non-negative value on success or a negative error code on failure—and a flags field conveying out-of-band information such as which provided buffer was used (IORING_CQE_F_BUFFER) or whether more completions for this request are still coming (IORING_CQE_F_MORE, the multi-shot flag of §7.1). Because the result mirrors the synchronous return value, porting code to io_uring is largely a matter of moving the same arguments into an SQE and reading the same result out of a CQE. 

/* include/uapi/linux/io_uring.h */
struct io_uring_cqe {
	__u64	user_data;	/* the sqe->user_data value passed back */
	__s32	res;		/* result: like a system-call return value */
	__u32	flags;		/* IORING_CQE_F_* */
	__u64	big_cqe[];	/* extra 16 bytes when SETUP_CQE32 */
};

The flags field, small as it is, is what lets a single completion carry more than a return value. Beyond the buffer identifier and the multi-shot IORING_CQE_F_MORE bit already mentioned, it can report that a socket still has data waiting (IORING_CQE_F_SOCK_NONEMPTY, a hint that a follow-up receive will succeed immediately), that this CQE is the zero-copy send notification rather than the send result (IORING_CQE_F_NOTIF, §7.3), or that more data will follow for a buffer-ring completion (IORING_CQE_F_BUF_MORE). When a provided buffer is used, the buffer's identifier is packed into the high bits of the same field, above IORING_CQE_BUFFER_SHIFT. This is why a completion is worth more than the equivalent synchronous return: it can convey, in one word alongside the result, the out-of-band information that the older interfaces could only obtain through additional calls. Figure 24-3 draws the two entry types in their rings and highlights the asymmetry between them. On the submission side the ring does not hold SQEs at all: it holds an array of indices into a separate SQE array—one level of indirection, so that the order in which entries are submitted is independent of where they sit in the array (an index the kernel reads with io_get_sqe, bumping sq_dropped if it is out of range, unless the ring opts out of the indirection with IORING_SETUP_NO_SQARRAY). The completion side has no such indirection: the completion ring stores CQEs directly, because the kernel, being the producer, simply writes each result into the next slot.

Heads, Tails, and Memory Ordering

Each ring is a classic circular buffer addressed by two monotonically increasing indices, a head and a tail, masked by the ring size to wrap around. The essential discipline is that for each ring one party owns the tail and the other owns the head, so that the queue is a single-producer, single-consumer channel that needs no lock. For the submission queue the application is the producer: it writes new SQEs and advances the tail, while the kernel advances the head as it consumes them. For the completion queue the roles reverse: the kernel produces, advancing the tail, and the application consumes, advancing the head. Each side can tell whether the queue is empty or full simply by comparing the head and tail it can see. Because the entry count is always a power of two, mapping one of these ever-growing indices to an actual slot is a single bitwise AND with the ring mask (entries - 1)—the slot is index & mask—rather than a modulo.

What makes this safe without locks is memory ordering. When the application publishes a new SQE it must ensure the kernel cannot observe the advanced tail before the SQE's contents are visible, and symmetrically the kernel must ensure a CQE's contents are visible before it advances the tail the application reads. Both sides achieve this with acquire/release barriers—the producer uses a release store to publish the new tail after writing the entry, and the consumer uses an acquire load to read the tail before reading the entry—so that seeing the updated index guarantees seeing the data it refers to. This is the same store-release/load-acquire pattern Chapter 5 described for lockless communication, applied across the user/kernel boundary, and it is documented in detail at the top of io_uring/io_uring.c. Getting this protocol right is the whole reason the shared rings can be used concurrently by two parties at full speed with no system call to serialize them.

Put concretely, each side runs a fixed produce/consume cycle, and the two rings are mirror images. To submit, the application fills an SQE in the array, writes that entry's index into the submission ring at sq_tail & mask, and advances sq_tail with a release store (smp_store_release); the kernel reads sq_tail with a matching acquire load (smp_load_acquire), consumes indices beginning at sq_head & mask, and advances sq_head to free those slots. To complete, the kernel writes the CQE into the completion ring at cq_tail & mask and advances cq_tail with a release store; the application reads cq_tail with an acquire load, consumes CQEs beginning at cq_head & mask, and advances cq_head to tell the kernel those slots may be reused. In each direction the producer's release store of the tail pairs with the consumer's acquire load of it, which—with the READ_ONCE and WRITE_ONCE that guard every shared access—are the exact primitives the header comment in io_uring/io_uring.c prescribes. Figure 24-4 draws one such ring, with its head and tail dividing the circular buffer into occupied and free slots.

A handful of other shared fields round out the protocol, all of them written by one side and only read by the other. Two are error counters. sq_dropped counts submission entries the kernel had to discard because the application wrote an out-of-range index into the submission array—a programming error the application can detect by watching the counter rise. cq_overflow counts completions that could not be posted because the completion ring was full; a modern kernel does not drop these but holds them on an internal list until space frees up, the no-drop behavior detailed in §3.2, so the counter merely records that the application let the ring back up. The rings also carry two runtime flag words in shared memory. The kernel writes sq_flags to raise IORING_SQ_NEED_WAKEUP when a sleeping poll thread must be woken (§5.1), IORING_SQ_TASKRUN when deferred completion work is waiting, and IORING_SQ_CQ_OVERFLOW when completions are being held back on the overflow list—so an application can learn of the backlog by reading a word of memory rather than by watching the counter climb. In the other direction the application writes cq_flags, whose single defined bit, IORING_CQ_EVENTFD_DISABLED, suppresses the eventfd notification while it is reaping completions it already knows about. Because the poll-thread wakeup decision turns on the application updating the submission tail and then reading these flags, that particular check needs a full memory barrier between the two, a subtlety the header comment in io_uring/io_uring.c calls out explicitly. These counters and flags are the small amount of shared state, beyond the entries themselves, that keeps the two sides in agreement about the health and mode of the rings.

One recent option abandons the circular discipline on the submission side altogether. A ring created with IORING_SETUP_SQ_REWIND—a non-circular submission queue, added during the 7.0 cycle and requiring IORING_SETUP_NO_SQARRAY—has the kernel ignore the submission head and tail entirely and take entries from index zero on every submission. The application places the batch it wants at the start of the SQE memory, calls into the kernel, and never touches the indices at all, which suits a program that assembles a complete batch each time round its loop and has no use for a queue that persists between iterations. It cannot be combined with the poll thread of §5.1, which by its nature needs a standing queue to watch.

The Life of a Request

Having seen the rings and the entries, we can follow a single request through the kernel: from the moment the application publishes an SQE, through the kernel's consumption and issuing of the operation, to the posting of a CQE the application eventually reaps. Understanding this path—especially where it runs synchronously and where the kernel must defer work—explains both io_uring's speed and the mechanisms of the later sections. This section traces the submission side, the completion side, and the io_uring_enter system call that drives both.

The theme to watch for is that io_uring runs at two speeds. Whenever it can, the kernel carries a request all the way to completion inline, in the submitting thread, touching no other context—this is the fast path that makes io_uring cheap. Only when an operation would block does it fall back to one of the deferral mechanisms, and even then it never blocks the submitter. The unit that flows along both paths is a single kernel object, the request (struct io_kiocb), created when an SQE is consumed and destroyed when its CQE has been posted; following that object from birth to death is the clearest way to understand the subsystem. Submission and Issue

When the kernel is told there are new SQEs to process—because the application called io_uring_enter, or because the polling thread of §5.1 noticed the tail advance—it runs io_submit_sqes (io_uring/io_uring.c), which consumes the queued entries one by one. For each, it allocates and initializes an internal request object, struct io_kiocb (include/linux/io_uring_types.h)—the kernel's representation of an in-flight operation, belonging to the instance's struct io_ring_ctx—and dispatches it to the handler for its opcode. The dispatch goes through a per-operation table, io_issue_defs (io_uring/opdef.c), which gives each opcode a prep function that validates and unpacks the SQE and an issue function that performs the operation. This table is the seam along which io_uring's many operation types are organized: adding an operation means adding an entry to it. There are in fact two tables, and the reason for the split is itself instructive. Everything the hot path touches lives in io_issue_defs; everything it does not—the opcode's name for /proc output, and the cleanup and fail callbacks invoked only when a request is torn down or rejected —lives in a parallel io_cold_defs array indexed by the same opcode. A single combined structure would work, but it would push the frequently read fields further apart in memory, and the subsystem is built on the principle that the common path should touch as few cache lines as possible.

The struct io_kiocb that flows through this machinery is a compact, reused object rather than a fresh allocation per operation. It carries a back pointer to its struct io_ring_ctx, the resolved file it acts on, the owning task, a reference count, per-request REQ_F_ state flags, a link pointer for chained requests (§4.2), an optional async_data block for operations that must save state when they are punted, and—tellingly—an embedded struct io_uring_cqe, so the result is built up inside the request and later copied into the ring. To keep the hot path off the memory allocator, requests are drawn from a per-context cache: the core refills it in bulk with kmem_cache_alloc_bulk and hands out objects from a free list on the submit state (io_alloc_req over ctx->submit_state), returning each request to the same list when it completes. The submission loop also brackets the batch it is issuing in a block-layer plug (blk_start_plug_nr_ios, the mechanism of Chapter 14, told in advance how many operations to expect), so that a run of queued storage reads and writes is handed to the device together rather than one at a time—another way batching at the ring level turns into batching all the way down.

Each entry in that table is more than a pair of function pointers; it also carries a set of one-bit properties (struct io_issue_def, io_uring/opdef.h) that tell the core how to treat the opcode without knowing anything specific about it. Fourteen such bits are defined. needs_file says the operation acts on a file descriptor, so the core should resolve and pin it first; buffer_select that it may draw a provided buffer (§6.2); iopoll that it can be completed by busy-polling (§7.2); pollin and pollout which readiness condition to wait on; unbound_nonreg_file that a blocking instance should be treated as an unbounded worker, and hash_reg_file that writes to the same regular file should be serialized rather than run concurrently (both §5.2). Others serve narrower purposes: plug marks the storage operations that should join the block-layer plug described above, audit_skip exempts high-frequency operations from audit logging, and is_128 identifies the opcodes that use a 128-byte SQE on the mixed-size rings of §2.1. Two non-bit members complete the picture: async_size gives the amount of state the operation must save if it is punted, and filter_pdu_size, with its companion filter_populate callback, tells the BPF filter machinery of §8.2 how much per-opcode context to present to a filter program. Together these let generic code make the right scheduling, resource, and security decisions for every opcode without knowing what any of them does. The two-phase split matters too: prep runs first and does all validation and unpacking of the SQE up front, so that once a request is accepted its issue handler can run without re-touching user memory, which both simplifies the fast path and closes a class of time-of-check/time-of-use bugs.

The pivotal question for each request is whether it can complete without blocking. The core resolves it concretely: it calls the opcode's issue handler with a non-blocking flag (IO_URING_F_NONBLOCK) set, asking it to do the work only if it can do so without sleeping. Many operations can: a read whose data is already in the page cache, a send into a socket with room in its buffer, a non-blocking poll—these complete immediately, inline, in the submitting context, which is io_uring's fast path and the reason it can be so much faster than a thread-per-request design. When the operation would block, its handler returns -EAGAIN instead of sleeping, and the core takes over: it first tries to arm a poll (io_arm_poll_handler), so that the request waits, without a thread, until the file signals readiness and is then re-issued; and only if the file cannot be polled does it hand the request to the worker pool of §5.2 to run in a context where blocking is allowed. State flags on the request (the REQ_F_ bits, such as REQ_F_FORCE_ASYNC to skip the inline attempt and REQ_F_POLLED to mark a poll-armed request) record which path it took. Either way the submission call returns promptly, and the completion is delivered later.

Completion and Task Work

However a request finishes, its result reaches the application the same way: the kernel posts a CQE. Internally this means filling a completion entry with the request's user_data, result, and flags and advancing the completion ring's tail (io_fill_cqe_req and relatives, io_uring/io_uring.c). A subtlety arises when a completion becomes ready in a context where it cannot be finalized directly—for instance in interrupt context, or on a different CPU than the one that owns the ring. io_uring handles this with task work (io_uring/tw.c): the completion is queued to run in the context of the task that owns the io_uring instance, and is finalized the next time that task runs kernel code, typically when it next calls io_uring_enter. Running completions in the owner's task context keeps the completion path cheap and cache-friendly, and it is the mechanism the low-overhead completion modes of §7.2 tune.

Two refinements of this mechanism matter here, because the setup flags of §7.2 select between them. In the default scheme the kernel queues the completion with the generic task-work facility of Chapter 4 (io_req_task_work_add raising a TWA_SIGNAL notification), which interrupts the owner task promptly to run it. When a ring is created with IORING_SETUP_DEFER_TASKRUN, io_uring instead keeps a private, lock-light list of pending completion work and runs it only when the application asks for completions, avoiding the signal and running the work in bigger batches—a large saving for a single-threaded server, at the cost of promising that only one task will wait on the ring. Either way, when several requests have finished, their CQEs are posted together: __io_submit_flush_completions (io_uring/io_uring.c) fills a run of completion entries and advances the tail once under a single lock acquisition, so that the per-completion cost falls as the batch grows. Batched, task-context completion is as central to io_uring's efficiency as batched submission.

Posting a completion is also where a request's life usually ends. Because the CQE is embedded in the io_kiocb, finalizing a request is a matter of copying that entry into the next ring slot and then dropping the request's last reference; rather than freeing it to the allocator, the core returns it to the per-context cache of §3.1 for the next operation to reuse. The reference count matters because a request is not always owned by one path alone—a poll waiter, a timeout linked to it, and the issuing context may all hold references—and the request is finalized only when the last is dropped. One important case defies the usual one-CQE-then-freed rule: a multi-shot request (§7.1) posts its CQE with the IORING_CQE_F_MORE flag set and is not freed; it stays armed and will post again on the next event, so a single accept or receive request can yield a stream of completions before it is finally torn down.

One more case must be handled: the completion queue can fill up if the application submits faster than it reaps. When there is no room for a new CQE, the kernel does not drop the completion—doing so would lose an I/O result—but records it on an internal overflow list and flushes it into the ring once space appears. This no-drop guarantee (advertised to applications as the IORING_FEAT_NODROP feature) means an application can, if it chooses, size its completion ring smaller than the number of requests it keeps in flight and rely on the kernel to hold the surplus, at some cost in efficiency when overflow occurs.

The enter System Call

The engine that drives submission and completion in the default mode is the second of the three system calls, io_uring_enter (io_uring/io_uring.c). Its cleverness is that one call does both jobs at once: the application tells it how many newly queued SQEs to submit and how many completions to wait for, and the kernel submits the batch, then—if asked—blocks until the requested number of CQEs is available before returning. A common high-throughput loop is therefore a single io_uring_enter per iteration that submits everything queued since the last call and waits for a batch of results, so that even in the syscall-using mode the ratio of operations to system calls can be very high. Eight flags select its behavior. IORING_ENTER_GETEVENTS asks it to wait for completions; IORING_ENTER_SQ_WAKEUP nudges a sleeping poll thread and IORING_ENTER_SQ_WAIT waits for room in a full submission queue (both §5.1); IORING_ENTER_REGISTERED_RING names the ring by a registered index rather than a file descriptor, shaving the descriptor lookup off even this call; and IORING_ENTER_NO_IOWAIT asks that the sleep not be accounted as iowait, which otherwise inflates the idle statistics of a machine whose threads are merely waiting on a ring. The remaining three concern the extended argument described below. It is the one system call an ordinary io_uring workload makes on its hot path—and the polling modes of §5 remove even that.

The call's full signature shows how it fuses the two roles: io_uring_enter(fd, to_submit, min_complete, flags, arg, argsz). The to_submit count says how many newly queued SQEs to consume, and the call returns the number it actually submitted; min_complete, together with IORING_ENTER_GETEVENTS, says how many completions to wait for before returning. Passing to_submit of zero with a non-zero min_complete turns the call into a pure wait, and the reverse into a pure submit, so the one entry point serves a submit-only producer, a wait-only consumer, or the combined loop equally. The final two arguments carry a signal mask to atomically install for the duration of the wait—closing the classic select/pselect race—and, when IORING_ENTER_EXT_ARG is set, point instead to a struct io_uring_getevents_arg (include/uapi/linux/io_uring.h) that bundles the signal mask together with a wait timeout, so an application can block for completions but no longer than a bounded time without a separate timer operation. IORING_ENTER_ABS_TIMER makes that timeout an absolute deadline rather than a relative interval, so that a loop which waits repeatedly does not drift. These options make a single io_uring_enter expressive enough to be the whole of a server's interaction with the kernel on the hot path.

That structure carries one more field, min_wait_usec, which turns the wait into a two-stage affair and is the kernel's answer to a tension this chapter has so far left implicit. Waiting for a single completion gives the lowest latency for that one operation but the worst throughput, since the application is woken for every result; waiting for a large batch reverses the trade, and risks waiting a long time if the batch never fills. A non-zero min_wait_usec asks the kernel to sleep for that window even if enough completions are already available, letting a batch accumulate, and only then to reconsider. When the window expires the waiter is released if anything arrived during it; otherwise it falls back to the ordinary timeout, but now waking on the very next completion rather than on a full batch (io_uring/wait.c). The effect is to spend a bounded, explicitly chosen amount of latency—tens of microseconds, typically—to buy a larger batch, while guaranteeing that a quiet ring still returns promptly. The capability is advertised as IORING_FEAT_MIN_TIMEOUT.

A last refinement removes the copying that all of this implies. Every io_uring_enter that passes an extended argument must copy that structure in from user space, which is a small cost but one paid on a path whose entire purpose is to be cheap. With IORING_ENTER_EXT_ARG_REG the application instead registers a region of wait arguments with the kernel once, as an array of struct io_uring_reg_wait, and thereafter passes only an index into it; the kernel reads the timeout, the signal mask, and the minimum wait from memory it already has mapped. It is the same move as the registered files and buffers of §6 and the registered ring descriptor above, applied to the last remaining per-call copy, and it is characteristic of how the interface has evolved: once the system calls themselves were amortized away, what remained to optimize was everything they still had to touch.

One consequence of this fused design deserves emphasis, because it differs from an ordinary system call: the return value of io_uring_enter reports only how the submission went—the number of SQEs accepted, or an error if the call itself could not proceed—and not whether the operations succeeded. Each operation's own success or failure comes back later in its CQE's res field. A single malformed or failing SQE therefore does not abort the batch or fail the system call: the kernel marks that request failed and posts a completion carrying the negative error code for it (if it was the head of a link, the rest of the chain is cancelled, §4.2), while the other submitted requests proceed normally. An application must accordingly check two things—that io_uring_enter submitted what it expected, and then each CQE's res—rather than treating a successful call as a successful operation.

Operations and Chaining

So far a request has been an abstract “operation.” This section makes it concrete: the breadth of operation types io_uring supports, which is what lets an application drive nearly all of its I/O through the single interface, and the mechanisms for expressing ordering among operations—linking one request to depend on another, draining the queue as a barrier, and attaching timeouts. These two themes are complementary: the wide opcode set means almost anything a program does can become an SQE, and the ordering flags mean those SQEs can encode not just a bag of independent operations but a small program of dependent ones, submitted and run without the application mediating each step. A third subsection then collects the operations that act on neither a file nor a socket—passing a message to another ring, waiting on a futex, reaping a child process, and cancelling a request already in flight.

The Range of Operations

The opcode in each SQE selects from a large and growing set of operations—sixty-five in this kernel, enumerated by enum io_uring_op (include/uapi/linux/io_uring.h) and implemented through the io_issue_defs table. Their range is what distinguishes io_uring from its narrow predecessor: it is not a file-I/O interface with a few extras but a general asynchronous-operation interface. Two things about the current list are more revealing than its length. The first is how far it has drifted from file descriptors. IORING_OP_WAITID reaps a child process and the futex operations wait on a word of user memory, both covered in §4.3; IORING_OP_SOCKET, BIND, and LISTEN mean a server can now build a listening socket, accept on it, read, write, and close without a single system call other than io_uring_enter; and IORING_OP_EPOLL_WAIT lets a program wait on an epoll set from inside the ring, folding the interface of Chapter 19 into the one that was meant to replace it. Several of these have no fd in any meaningful sense, which is why the needs_file bit of §3.1 exists rather than the core simply assuming a descriptor. The second is the pair IORING_OP_NOP128 and IORING_OP_URING_CMD128: these are duplicate opcodes whose only distinction is that they occupy a 128-byte SQE, and they exist so that the mixed-size rings of §2.1 can tell a wide entry from a narrow one by opcode alone. They are the concrete users of the is_128 property bit.

Linking, Draining, and Timeouts

Independent operations are the common case, but applications often need one operation to follow another—write a buffer, then fsync it; connect a socket, then send on it. io_uring expresses such dependencies with the per-SQE flags introduced in §2.2. Setting IOSQE_IO_LINK on an SQE links it to the next: the linked chain executes in order, each request starting only when its predecessor completes successfully, and a failure breaks the chain so the dependents are cancelled rather than run on bad state. This lets a multi-step sequence be submitted as one batch yet execute in the right order, without the application waiting for each step in turn.

Several refinements tune this behavior. IOSQE_IO_HARDLINK is a stronger link that holds the chain together even when a request fails, so the successor runs regardless of its predecessor's result—useful when the steps are ordered but not conditional. The protection covers failures at execution; it does not extend to a request the kernel rejects before running it at all. If prep refuses an SQE—a malformed argument, an unsupported flag—the core downgrades the hard link to an ordinary one and fails the whole chain, on the reasoning that a sequence built on an entry the kernel could not even parse is not a sequence the kernel will try to salvage. Two other per-SQE flags often accompany links. IOSQE_CQE_SKIP_SUCCESS suppresses the completion for a request that succeeds, so a long chain need not flood the completion queue with intermediate results the application does not care about—only the final step, or a failing one, posts a CQE. IOSQE_ASYNC forces a request onto the asynchronous worker path from the start, skipping the inline non-blocking attempt of §3.1, which is occasionally worthwhile for an operation known to block. Internally a chain is recorded by REQ_F_LINK (and REQ_F_HARDLINK) state flags on the head request, which the submission code assembles as it walks the linked SQEs.

Two related mechanisms round this out. IOSQE_IO_DRAIN marks an SQE as a barrier: it will not start until all previously submitted operations have completed, and later operations wait for it, which lets an application insert a synchronization point into the stream. And a special operation, IORING_OP_LINK_TIMEOUT, attaches a timeout to the request it is linked to, cancelling that request if it does not complete in time—the idiomatic way to bound the duration of an otherwise open-ended operation such as a socket receive. The standalone IORING_OP_TIMEOUT is more flexible still: its timeout_flags choose between a relative and an absolute deadline (IORING_TIMEOUT_ABS), select the clock to measure against (IORING_TIMEOUT_BOOTTIME or IORING_TIMEOUT_REALTIME), and can even re-arm repeatedly (IORING_TIMEOUT_MULTISHOT) to fire at an interval. Two further flags matter to a program that must adjust a deadline it has already set: IORING_TIMEOUT_UPDATE, and IORING_LINK_TIMEOUT_UPDATE for the linked variety, turn the operation into a request to modify an armed timeout in place rather than to arm a new one, so a server can extend or shorten a pending deadline without the cancel-and-resubmit race that would otherwise be needed. A third, IORING_TIMEOUT_ETIME_SUCCESS, reports an expiry as a success rather than as -ETIME, which spares an application from treating its own intended timeout as an error. Together, linking, draining, and timeouts let an application express ordering, synchronization, and deadlines entirely within the submission queue, keeping even complex I/O sequences off the system-call path. Ring Messaging, Futexes, and Cancellation

A few further operations show how far the ring model has been stretched. IORING_OP_MSG_RING (io_uring/msg_ring.c) lets one io_uring instance post a completion directly into another's completion queue, giving threads a fast, kernel-mediated way to pass messages or hand off work between their rings without a separate IPC mechanism. It has two modes: posting a data word as a CQE into the target ring, and transferring a registered file descriptor from one ring's table to another's, which lets an acceptor thread hand connections to worker threads entirely through io_uring. Two flags tune the handoff: IORING_MSG_RING_CQE_SKIP suppresses the completion in the target ring, which is what a sender uses when the file descriptor itself is the whole message and a notification would only add work, and IORING_MSG_RING_FLAGS_PASS lets the sender choose the CQE flags the target sees, so a protocol can be carried in the flag bits rather than in a second message.

Futex operations (io_uring/futex.c) let a request wait on a futex (Chapter 19) asynchronously—IORING_OP_FUTEX_WAIT and FUTEX_WAKE, and the vectored FUTEX_WAITV that waits on several at once—so that waiting for a lock can be folded into the same completion loop as I/O rather than blocking a thread. IORING_OP_WAITID does the same for process reaping: the classic waitid blocks a thread until a child changes state, and a server that supervises child processes has traditionally had to dedicate a thread or a signal handler to the job. As a ring operation it becomes one more completion among the rest.

IORING_OP_ASYNC_CANCEL (io_uring/cancel.c) lets an application cancel a previously submitted request by its user_data—essential for a server that must abandon operations when a connection closes or a deadline passes. Its flags widen the match beyond a single key: IORING_ASYNC_CANCEL_ALL cancels every request that matches rather than the first, IORING_ASYNC_CANCEL_FD matches by file descriptor (so closing a connection can cancel all of its outstanding operations at once), IORING_ASYNC_CANCEL_OP matches by opcode, and IORING_ASYNC_CANCEL_ANY matches everything and is for that reason rejected in combination with the descriptor or opcode criteria, since a match that already ignores every key cannot also be narrowed by one. IORING_ASYNC_CANCEL_FD_FIXED is the registered-descriptor form of the file-descriptor match, needed because a direct descriptor (§6.1) is an index into the ring's own table rather than a number the task's descriptor table would recognize, and IORING_ASYNC_CANCEL_USERDATA restores the key match that the others displace: matching on user_data is the default, but naming a descriptor or an opcode silently turns it off, so an application that wants both criteria applied has to ask for the first one back. Cancellation is also available outside the ring: IORING_REGISTER_SYNC_CANCEL performs the same matching synchronously through io_uring_register, waiting for the outcome rather than reporting it as a completion, which suits teardown paths that must know the request is gone before they release the memory it referenced. These operations, none of them classic “I/O,” illustrate the trajectory of the whole subsystem: the shared ring began as a way to submit disk reads and has become a general mechanism for asking the kernel to do work asynchronously, of almost any kind.

Submitting Without System Calls

Batching already reduces io_uring to roughly one system call per group of operations, but the interface can go further and eliminate the submission system call entirely, and it must also cope with operations that genuinely have to block. Two complementary mechanisms address these: a dedicated thread that polls the submission queue so the application never calls into the kernel to submit, and a pool of worker threads that carry out operations that cannot complete inline. Figure 24-7 shows how both fit into the submission path. This section describes both.

The two mechanisms sit on different axes and are independent of each other. SQPOLL attacks the submission cost, removing the system call that hands queued SQEs to the kernel; io-wq attacks the blocking problem, giving the kernel somewhere to run operations that cannot finish inline. A ring may use either, both, or neither: a latency-sensitive server might enable SQPOLL and rarely touch io-wq, while a program doing large buffered reads might lean on io-wq without ever polling. Understanding them together completes the picture of how a request reaches the kernel and how it runs once there.

Submission-Queue Polling

In its most aggressive mode, io_uring removes the submission system call altogether. When an instance is created with the IORING_SETUP_SQPOLL flag, the kernel spawns a dedicated thread, io_sq_thread (io_uring/sqpoll.c), that polls the submission queue's tail and picks up new SQEs as the application writes them—so the application submits work merely by writing an SQE and advancing the tail in shared memory, with no io_uring_enter call at all. On a busy ring this drives the per-operation system-call cost to zero, the ultimate expression of the shared-ring idea. The obvious risk—a thread spinning forever—is managed by an idle timeout: after sq_thread_idle milliseconds without new work—one second if the application asks for zero—the poll thread sleeps, and it sets the IORING_SQ_NEED_WAKEUP flag in the shared ring to tell the application it has done so. The application checks that flag and, only when it is set, makes one io_uring_enter call with IORING_ENTER_SQ_WAKEUP to wake the thread—so the syscall reappears only when the ring has gone idle, never on the hot path. The thread can be pinned to a chosen CPU, and several rings can share one poll thread with IORING_SETUP_ATTACH_WQ, naming an existing ring through the wq_fd field, to avoid dedicating a core to each; a shared thread takes the largest idle timeout of the rings it serves, so the most patient ring sets the sleep threshold for all of them. The flag's name is a historical artifact: it once attached the worker pool of §5.2 as well, but because that pool is now per-task and therefore shared among a task's rings automatically, the flag governs only the poll thread. Passing it without IORING_SETUP_SQPOLL does nothing but validate the descriptor, a check retained so that old programs still receive the errors they expect.

A few details fill in how the thread is managed, and the first corrects a natural assumption: it is not a kernel thread in the usual sense. It is created by create_io_thread (kernel/fork.c), which clones the calling task with CLONE_VM, CLONE_FS, CLONE_FILES, CLONE_SIGHAND, and CLONE_THREAD and marks the result PF_IO_WORKER. The poll thread is therefore a thread of the submitting process—sharing its address space, its file table, and its credentials—that simply never returns to user mode. That is not a detail of bookkeeping: it is the whole reason such a thread can issue a request on the application's behalf and have the result be identical to one the application issued itself, a property §5.2 relies on again for the worker pool. It appears in the thread list as iou-sqp-<pid> and loops polling one or more rings, calling cond_resched so it does not monopolize its CPU and honoring signals so it can be stopped. The shared state for a poll thread is a struct io_sq_data (io_uring/sqpoll.h): it holds a reference count, the list of rings the thread serves, the thread pointer, and the target CPU, so that IORING_SETUP_ATTACH_WQ is implemented simply by having a second ring join an existing io_sq_data rather than create its own thread. Operations that must reconfigure or tear down the ring “park” the poll thread first (io_sq_thread_park/io_sq_thread_unpark), stopping it at a safe point so the ring is not being polled while it changes. Pinning the thread to a CPU (sq_thread_cpu, valid only with IORING_SETUP_SQ_AFF) keeps it off the application's own cores; without that flag sq_thread_cpu is -1 and the thread is left free to run on any online CPU, migrating like any other thread rather than favoring one core by default. Because a poll thread is a standing thread that can busy-wait, creating an SQPOLL ring is gated by the security_uring_sqpoll LSM hook of §8.1, and the mode is best reserved for workloads busy enough to justify a core spinning on their behalf—on a lightly loaded ring the thread mostly sleeps and the polling buys nothing.

One poll thread can serve several rings at once, and the loop that drives it (io_sq_thread) is written to keep any one of them from starving the rest. Each pass walks every ring the thread serves and, whenever more than one ring is attached, caps the number of SQEs it will pull from a single ring's queue in that pass to eight (IORING_SQPOLL_CAP_ENTRIES_VALUE)—a ring that has queued a thousand operations is drained eight at a time, interleaved with its neighbors, rather than monopolizing the thread until it is empty. The same pass also runs the thread's own pending task work, again capped, this time at thirty-two entries per iteration, and, for a ring configured with the busy-poll receive path of §7.3, calls io_napi_sqpoll_busy_poll to poll its registered NAPI IDs for incoming network completions—so the one thread that polls the submission queue also ends up polling the receive side for any ring that asked for it, rather than leaving that to a second mechanism. Requests are issued under the credentials captured when the ring was created (ctx->sq_creds), overridden for the duration of each pass if they differ from the poll thread's own, so a ring's operations run with the identity of whoever set it up even if the descriptor is later handed to another process.

The Async Worker Pool

Polling removes the submission syscall, but some operations still cannot complete without blocking, and something must run them without stalling the submitter. That something is io-wq (io_uring/io-wq.c), io_uring's own pool of worker threads. When the kernel determines a request must block and cannot be handled by a readiness poll, it hands the request to io-wq, whose workers execute it—blocking as needed in their own context—and post its completion when it finishes. The pool creates workers on demand and retires them when idle, so a program that never blocks spawns none. It separates workers into two accounts, bounded and unbounded (IO_WQ_ACCT_BOUND and IO_WQ_ACCT_UNBOUND): bounded work is I/O that will finish in a predictable time, such as a disk read, and its worker count is capped to prevent a flood of slow disk operations from spawning unlimited threads; unbounded work is open-ended, such as waiting on a network receive, and is allowed more workers. The choice between them is not a guess but a property of the request, decided in io_prep_async_work: a request on a regular file is bounded, and a request on anything else is marked unbounded when its entry in the operation table of §3.1 sets unbound_nonreg_file—the bit exists precisely so that a read from a socket and a read from a file, which share an opcode, can land in different accounts. The pool belongs not to a process but to a single task—a struct io_uring_task hangs off task_struct->io_uring, one per thread that has ever used io_uring, and a request's tctx field is set to current->io_uring at the moment it is prepared for submission. That distinction matters on an SQPOLL ring: submission there happens inside the poll thread, not the application thread, so a request punted to io-wq from an SQPOLL ring runs through the poll thread's own worker pool, entirely separate from any pool the application's thread would use if it also issued io_uring calls directly. IORING_REGISTER_IOWQ_AFF and IORING_REGISTER_IOWQ_MAX_WORKERS account for this transparently: on an SQPOLL ring both operations park the poll thread first, look up its task, and apply the change to its pool instead of the calling process's—so an application configuring an SQPOLL ring's worker limits is, without needing to know it, reaching into a different thread's task context to do so. Between SQPOLL removing the submission syscall and io-wq absorbing the operations that must block, io_uring can keep a program's own threads entirely free of I/O waits.

The pool's size and placement are tunable, because unbounded worker growth would itself be a problem. Each account has a max_workers cap that bounds how many workers it will create (nr_workers tracked against it in io_uring/io-wq.c). The two defaults are chosen on different principles. The bounded cap is the smaller of the ring's queue depth and four times the number of online CPUs, on the reasoning that a ring can never have more work outstanding than it has submission slots, and that beyond a few workers per CPU more threads only add contention. The unbounded cap is the calling task's RLIMIT_NPROC, which is to say the pool declines to invent a new limit and reuses the one the administrator already set on the process. An application can raise or lower both with the IORING_REGISTER_IOWQ_MAX_WORKERS operation of io_uring_register, passing a two-element array whose entries are clamped to RLIMIT_NPROC and which is rewritten with the previous values, so that passing zeroes queries the current caps without changing them. IORING_REGISTER_IOWQ_AFF restricts which CPUs the workers may run on. A worker (shown as iou-wrk-<pid>) is created on demand by create_io_worker when work arrives and no idle worker is free, and reclaimed after it sits idle. It is built by the same create_io_thread that produces the poll thread of §5.1, and so is likewise a thread of the submitting process rather than a kernel thread. That is what allows a worker to run the operation in the submitting task's context—its memory map, its credentials, its file table—so that a blocking read or an openat punted to io-wq resolves relative paths, checks permissions, and consumes resource limits exactly as it would have had the owning task made the call itself. Requests reach the pool through io_wq_enqueue, either because the core could not poll the file for readiness or because the application set IOSQE_ASYNC (§4.2) to force the async path from the outset.

One more behavior of the pool matters for correctness rather than performance. Workers run independently, so nothing would otherwise stop two buffered writes to the same file from executing at once and interleaving—an outcome the write path of Chapter 12 does not permit when the calls are made directly. io-wq solves this by hashing: a request whose operation-table entry sets hash_reg_file is stamped with a hash of its target inode, and the pool guarantees that only one item of a given hash runs at a time, queueing the rest behind it while unhashed work continues to run freely. The serialization is skipped where the filesystem does not need it—a direct-I/O write to a file whose operations advertise FOP_DIO_PARALLEL_WRITE is left unhashed and may proceed in parallel—and it is applied unconditionally on an IORING_SETUP_IOPOLL ring. This is the missing half of the hash_reg_file property bit: the table marks the operation, and io-wq enforces what the mark means.

Registered Resources

Even with batching and polling, each operation still carries small per-call overheads: looking up a file descriptor, pinning a user buffer's pages so the kernel can do I/O into it, choosing where a received packet should land. For applications that reuse the same files and buffers across millions of operations, io_uring lets these costs be paid once, in advance, through the third system call, io_uring_register. This section covers the two forms: resources the application pre-registers, and buffers it provides for the kernel to choose among.

io_uring_register(fd, opcode, arg, nr_args) is a multiplexed call: its opcode selects among a long menu of registration operations—for files, buffers, the ring descriptor, an eventfd, worker limits, buffer rings, and more—each acting on the instance named by fd. What the registrations have in common is that they move a recurring per-operation cost to a one-time setup cost, trading a little rigidity (the resources must be declared and are pinned in advance) for a large per-I/O saving. The internal bookkeeping is shared: registered resources are held as reference-counted resource nodes (struct io_rsrc_node, io_uring/rsrc.c) so that an in-flight operation keeps the file or buffer it uses alive even if the table is updated underneath it.

Registered Files and Buffers

The io_uring_register call (io_uring/register.c, rsrc.c) lets an application hand the kernel a set of resources to hold ready. Registered files (IORING_REGISTER_FILES) install a fixed table of file descriptors in the instance; an SQE then refers to a file by its index in that table, with the IOSQE_FIXED_FILE flag set, and the kernel skips the descriptor lookup and reference counting it would otherwise do on every operation. Registered buffers (IORING_REGISTER_BUFFERS) pin a set of user memory buffers once, so that the fixed-variant operations READ_FIXED and WRITE_FIXED can do I/O directly into them without the kernel pinning and unpinning pages (the pin_user_pages() work of Chapter 9, Section 11) on each call, up to 16,384 buffers and 1 GiB apiece in this kernel (IORING_MAX_REG_BUFFERS, io_validate_user_buf_range); a fixed-file table holds up to 1,048,576 entries (IORING_MAX_FIXED_FILES). Because pinning locks memory, the total is charged against RLIMIT_MEMLOCK—but against the calling user, not the process: __io_account_mem tracks pinned pages in user->locked_vm, keyed by the real UID the ring was created under, so two processes running as the same user draw on one shared budget rather than each getting the limit to themselves, and nothing here checks CAP_IPC_LOCK to waive it. A second counter, mm_account->pinned_vm on the creating process's own mm_struct, is updated alongside purely so the pinning shows up in that process's /proc/pid/status the same way an ordinary mlock would, even though the enforced limit lives with the user. The internal bookkeeping is a set of resource nodes and mapped-buffer descriptors (struct io_rsrc_node, struct io_mapped_ubuf, io_uring/rsrc.c). The interface also allows the ring descriptor itself to be registered (IORING_REGISTER_RING_FDS), removing the descriptor lookup from io_uring_enter, and an eventfd to be registered (IORING_REGISTER_EVENTFD) so a classic poll loop can be notified when completions arrive. Registration turns the recurring per-operation setup into a one-time cost, which for a busy server is a substantial saving.

The fixed-file table is more than a lookup cache; it enables direct descriptors, file references that live only inside io_uring and never occupy a slot in the process's ordinary descriptor table. An openat or accept submitted with a file_index installs its result straight into a fixed-table slot instead of returning a number, and passing the sentinel IORING_FILE_INDEX_ALLOC asks the kernel to choose a free slot and report it—so a server can accept a connection and use it in later operations without ever holding a normal file descriptor for it, sidestepping the per-process descriptor limit and the cost of installing into the fd table. Automatic allocation can be confined to part of the table with IORING_REGISTER_FILE_ALLOC_RANGE, which takes a struct io_uring_file_index_range and restricts the kernel's choice to a half-open span of slots, letting an application reserve the rest for indices it assigns itself. When a direct descriptor must eventually become an ordinary one— to hand to a library that knows nothing of io_uring—IORING_OP_FIXED_FD_INSTALL (§4.1) installs it into the descriptor table on demand. Registered tables are also dynamic: an application need not re-register the whole set to change it. The update operations (IORING_REGISTER_FILES_UPDATE, and the versioned _FILES2/_BUFFERS2 and their updates) replace individual slots in place, a table may be created sparse with IORING_RSRC_REGISTER_SPARSE and filled in later, and each entry can carry a tag whose completion notifies the application when an updated resource is finally free to reuse. This lets a long-running server rotate files and buffers through a fixed table without tearing it down. A related operation avoids duplicated work between rings: IORING_REGISTER_CLONE_BUFFERS copies a range of registered buffers from another ring, named by src_fd in a struct io_uring_clone_buffers, into this one's table, so a process that runs a ring per thread pins the underlying pages once rather than once per ring—the pages are not pinned a second time, only the resource nodes are duplicated and the existing ones' reference counts rise. Two flags refine the copy: IORING_REGISTER_SRC_REGISTERED says src_fd is itself a registered ring descriptor rather than an ordinary one, letting the source be named the same way this section's own IORING_REGISTER_RING_FDS names this ring; IORING_REGISTER_DST_REPLACE permits the destination table to already hold entries, which without the flag is an error, so that cloning into a table only ever populates empty slots unless the caller explicitly asks to overwrite them.

Provided Buffers and Buffer Selection

Registered buffers solve the pinning cost but not a subtler problem specific to receiving data: when a server posts many concurrent receives, it does not know which will complete first, so committing a distinct buffer to each ties up memory in proportion to the number of outstanding receives. io_uring's answer is provided buffers. The application hands the kernel a pool of buffers—through the IORING_OP_PROVIDE_BUFFERS operation, or, more efficiently, a ring-mapped buffer pool registered with IORING_REGISTER_PBUF_RING—and submits its receives with the IOSQE_BUFFER_SELECT flag but no assigned buffer. The kernel then picks a buffer from the pool at completion time, only when data has actually arrived (io_buffer_select, io_uring/kbuf.c), and reports which buffer it used in the CQE's flags via IORING_CQE_F_BUFFER. A server can thus keep thousands of receives outstanding backed by a modest shared pool, because a buffer is consumed only by a receive that actually completes. This is a decisive optimization for high-connection-count network servers, and it is the kind of refinement—matching the interface to the real access pattern—that distinguishes io_uring's networking support from a mechanical port of the socket calls.

The ring-mapped form is how modern code uses this feature, and its protocol is the one already familiar from the submission queue. IORING_REGISTER_PBUF_RING sets up, per buffer group, a buffer ring—a small shared ring of struct io_uring_buf descriptors (a buffer group's ring is itself mapped by mmap, at an offset derived from IORING_OFF_PBUF_RING and the group id, when the application asks the kernel to allocate it with IOU_PBUF_RING_MMAP; otherwise the application supplies the memory, just as IORING_SETUP_NO_MMAP lets it supply the main rings in §2.1). The application fills this ring with addresses and lengths of buffers it owns and advances the ring's tail; the kernel consumes an entry when it needs a landing buffer for a completing receive, exactly as in the SQ/CQ protocol of §2.3, so replenishing buffers no longer costs a system call or an SQE. When the operation completes, the CQE's flags carry IORING_CQE_F_BUFFER and the chosen buffer's id in the high bits above IORING_CQE_BUFFER_SHIFT; the application reads the data from that buffer and, when done, returns it to the ring for reuse. A buffer group registered with IOU_PBUF_RING_INC is consumed incrementally, which inverts the usual relationship between buffers and completions: rather than each completion claiming a whole buffer, successive completions fill one buffer from where the last left off, and the kernel sets IORING_CQE_F_BUF_MORE to say that the buffer named in this CQE is only partly used and will appear again. The application does not need to be told separately how much of the buffer is left: io_kbuf_commit advances the buffer-ring entry's addr and shrinks its len in place after every completion, so the same entry the application already has mapped simply describes a smaller remaining span each time it is consulted, until it is exhausted and the ring moves on to the next buffer. A registration can also set a floor, min_left, below which the kernel retires a buffer early rather than trying to land one more small completion in an impractically small remainder—a buffer with a hundred bytes free and a min_left of a hundred is abandoned for the next one instead of being offered for a read that would almost certainly need splitting again. A server reading a stream therefore stops wasting the tail of a large buffer on a small arrival. An application can also ask where the kernel has reached in a group with IORING_REGISTER_PBUF_STATUS, which returns that ring's head; since the application owns the tail, the difference tells it how many buffers are still unconsumed, which is what a replenishment loop needs and cannot otherwise discover. Because a multi-shot receive (§7.1) draws from the group for each arriving message, buffer rings and multi-shot together let a server absorb bursty input with almost no per-message bookkeeping. It is the clearest example in the chapter of io_uring co-designing the data path and the control path for one workload.

Advanced Completion and Networking

The features so far make io_uring fast; the ones in this section make it fast for the hardest workloads—accepting thousands of connections, polling many sockets, sending data without copying it, and driving devices directly. They fall into three groups: completion modes that let one submission yield many completions, modes that minimize completion overhead for latency-critical work, and the networking and passthrough operations that exploit them. This section surveys each. Where the earlier sections made the common path cheap, these features target the extremes—the highest connection counts, the lowest storage latencies, and the largest transfers—so not every application needs them, but the ones that live at those extremes need them badly.

Multi-Shot Operations

Ordinarily one SQE yields one CQE: the request completes and is done. For operations an application repeats in a tight loop—accepting connection after connection, or waiting for a socket to become readable again and again—resubmitting an SQE per occurrence is wasteful. Multi-shot operations remove that waste: a single SQE stays armed and produces a stream of CQEs, one per occurrence, until it is cancelled or errors. A multi-shot POLL_ADD reports every readiness transition—or every readiness state, if the application sets IORING_POLL_ADD_LEVEL to ask for level-triggered rather than the default edge-triggered semantics, the same distinction epoll draws—a multi-shot ACCEPT (IORING_ACCEPT_MULTISHOT) posts a CQE for every incoming connection, and a multi-shot RECV delivers each arriving message—each from one submission. The kernel signals that a multi-shot request remains armed by setting IORING_CQE_F_MORE in each CQE's flags; when that flag is finally clear, the request is finished. The same flag, and the same re-arming logic, also drive READ_MULTISHOT (§4.1), the recurring timeout of §4.2, a multi-shot IORING_OP_URING_CMD (§7.3), and the zero-copy receive path (§7.3)—accept, poll, and recv are only the operations an application is most likely to reach for first. A multi-shot receive is not optional about provided buffers: preparing one without IOSQE_BUFFER_SELECT is rejected outright, since the kernel has nowhere to land a message it cannot predict the size or timing of. Multi-shot pairs naturally with the provided buffers of §6.2—a multi-shot receive draws a fresh buffer from the pool for each message—and together they let a server run its entire accept and receive loop with almost no resubmission at all. A plain multi-shot RECV (not RECVMSG) can additionally be given a total byte budget in the SQE's optlen field: each completion counts against it, and once the running total is exhausted the stream ends on its own, which is a way to bound how much a single armed receive is allowed to deliver without the application having to watch the count itself.

Multi-shot is enabled per operation by a flag in the SQE's operation-specific word: IORING_POLL_ADD_MULTI for poll, IORING_RECV_MULTISHOT for receive, IORING_ACCEPT_MULTISHOT for accept. Underneath, its efficiency rests on io_uring's fast-poll machinery (advertised as IORING_FEAT_FAST_POLL): rather than occupying a worker thread while waiting, an armed request registers interest in the file's readiness and is re-issued cheaply each time the file becomes ready, so a thousand idle multi-shot receives cost a thousand poll registrations, not a thousand threads. The trade-off is that a multi-shot stream is not unconditional. It ends—clearing IORING_CQE_F_MORE—not only on error but also when it cannot proceed, most commonly when a multi-shot receive's provided-buffer pool runs dry; the application must then replenish buffers and re-arm the request. A second, less obvious limit protects the rest of the ring: the completion-ring slot a multi-shot request writes into for each occurrence is filled through a helper (io_req_post_cqe) that, unlike an ordinary completion, does not fall back to the overflow list of §2.3 when the ring is full. If posting fails, the stream does not lose that occurrence's result—it is instead delivered as the final, ordinary completion, which does get the overflow protection, and the multi-shot flag is simply left clear. So a fast producer racing ahead of a slow reaper does not corrupt or drop data, but it does convert a long-running stream back into a single completion the application must notice and explicitly re-arm; multi-shot trades resubmission cost for a duty to keep reaping. A receive that keeps finding more data ready on every retry is also capped against monopolizing one task-work pass: after thirty-two consecutive retries without yielding, the kernel forces the request to requeue rather than loop indefinitely, so one saturated socket cannot starve the rest of the ring's completions. Used with the buffer-pool and reaping limits in mind, multi-shot is the single most effective tool for a high-connection server.

Polled and Deferred Completion

For the lowest-latency workloads, io_uring offers completion modes that trade generality for speed, chosen by setup flags. IORING_SETUP_IOPOLL turns off interrupt-driven completion for direct block I/O and instead has the kernel busy-poll the device for completions; on a fast NVMe drive this removes interrupt latency and overhead entirely, at the cost of a CPU spinning, and is how io_uring reaches the highest storage IOPS the hardware can sustain. That cost is the flag's whole drawback, and IORING_SETUP_HYBRID_IOPOLL exists to soften it: instead of spinning from the moment the request is issued, the kernel first sleeps for an estimate of how long the device will take and only then begins to poll. The estimate is learned rather than configured—io_uring_hybrid_poll (io_uring/rw.c) measures how long each polled request actually ran and keeps the smallest figure it has seen, so a ring spanning devices of different speeds settles on the fastest one's latency and does not oversleep the others. The result recovers most of polling's latency benefit while returning the CPU to other work for the bulk of each request. A second group tunes the task-work completion path of §3.2. IORING_SETUP_COOP_TASKRUN and IORING_SETUP_DEFER_TASKRUN control when and how deferred completions are run, batching them and running them only when the application asks for completions rather than interrupting it, which cuts the per-completion overhead for a single-threaded server. That last mode pairs with IORING_SETUP_SINGLE_ISSUER, a promise that only one task will submit to the ring, which lets the kernel drop synchronization it would otherwise need. These flags do not change what io_uring does, only how cheaply it delivers completions—but for a program bound by completion overhead, that is the whole game.

A few operational details make these modes usable. IORING_SETUP_IOPOLL applies only to direct (O_DIRECT) block I/O on devices that support polled completion, and the restriction is enforced at submission time, not just in how completions are reaped: an opcode whose operation-table entry does not advertise polled completion is rejected outright on such a ring, so an IOPOLL instance cannot fall back to running an unsupported operation the ordinary, interrupt-driven way—it is a ring for polled I/O specifically, not a general-purpose ring with polling as an option. For operations it does accept, it changes how completions are reaped: instead of waiting for an interrupt, io_uring_enter with a min_complete actively polls the device, so the same call that would block for events instead spins until they arrive. The task-work flags form a spectrum of increasing commitment. IORING_SETUP_COOP_TASKRUN runs deferred completion work at the next natural kernel transition instead of forcing it with an inter-processor interrupt, cutting the disturbance to the running task. IORING_SETUP_DEFER_TASKRUN goes further, holding completions until the application explicitly asks for them (and thus requires IORING_SETUP_SINGLE_ISSUER, since only the one waiting task may run that work). To keep the application from missing deferred completions, IORING_SETUP_TASKRUN_FLAG makes the kernel raise IORING_SQ_TASKRUN in the shared flags (§2.3) whenever such work is pending, so a program can cheaply check whether it must enter the kernel to reap. Together these let a carefully written single-threaded server pay almost nothing per completion beyond copying the CQE.

Networking, Zero-Copy, and Command Passthrough

Networking is where io_uring's advanced features come together (io_uring/net.c). Beyond ordinary send/recv and sendmsg/recvmsg, it offers zero-copy send (IORING_OP_SEND_ZC, SENDMSG_ZC): the kernel transmits directly from the application's buffer without copying it into a socket buffer first, a large saving for bulk transfers. Because the buffer must stay untouched until the network card has actually sent it, a zero-copy send produces a second, notification completion—flagged IORING_CQE_F_NOTIF (io_uring/notif.c)—that tells the application when the buffer is free to reuse. A matching zero-copy receive path (io_uring/zcrx.c) and NAPI busy-poll integration (io_uring/napi.c) push networking performance further still.

Zero-copy send needs care over its two-completion protocol, because it is easy to misuse. The first CQE for a SEND_ZC reports the send's result as usual, but the application must not reuse or free the buffer yet: the kernel has only handed the pages to the network stack, which may still be transmitting from them. Only the second, IORING_CQE_F_NOTIF completion signals that the last reference to the buffer has been dropped and it is safe to touch again. This makes zero-copy send a win for large, long-lived buffers where the saved copy outweighs the extra completion, and a loss for small sends where it does not—so it is opt-in per operation. There is a further subtlety the name hides: asking for a zero-copy send does not guarantee one. The network stack may decide it must copy after all, and it does so silently, leaving the application paying for the two-completion protocol without receiving anything in return. Setting IORING_SEND_ZC_REPORT_USAGE makes the kernel report the outcome in the notification CQE's res field, where IORING_NOTIF_USAGE_ZC_COPIED means the data was copied at least in part—the only way to discover that an optimization is not being applied. A send that does not name a registered buffer still has to keep its pages resident until the notification fires, so the kernel pins them for the duration and charges them against the same per-user RLIMIT_MEMLOCK budget as the registered buffers of §6.1 (io_notif_account_mem); naming a registered buffer with IORING_RECVSEND_FIXED_BUF skips this, since those pages are already pinned and accounted. A program that fires off many large zero-copy sends without registering its buffers can therefore hit the same limit a heavy user of registered buffers would, for a reason that has nothing to do with registration.

Several more flags in the operation-specific word tune the rest of the network path. IORING_RECVSEND_POLL_FIRST tells the kernel to wait for readiness before even attempting the operation, avoiding a speculative copy; IORING_RECVSEND_FIXED_BUF directs the transfer at a registered buffer from §6.1, naming it by index in buf_index; and IORING_SEND_VECTORIZED lets a send take a vector of segments rather than one flat range. The most interesting is IORING_RECVSEND_BUNDLE, which works with IOSQE_BUFFER_SELECT to let one operation claim several contiguous buffers from a group at once rather than one: the completion reports how many buffers were used and the id of the first, so a single send can drain a queue of small messages, or a single receive can absorb a burst, without one SQE and one CQE per buffer. Alongside these, the zero-copy receive path binds a registered interface queue so incoming packets land directly in application memory, and NAPI busy-polling lets a latency-sensitive receiver poll the NIC instead of waiting for its interrupt.

The most open-ended operation is command passthrough, IORING_OP_URING_CMD (io_uring/uring_cmd.c). Rather than a fixed operation, it carries a device-specific command to a file's own uring_cmd handler, letting a subsystem expose arbitrary asynchronous operations through io_uring's rings. Its headline use is NVMe passthrough, which sends raw NVMe commands to a drive—and the userspace-block-driver framework ublk, which implements block devices in user space—both riding io_uring's asynchronous, batched, low-overhead transport instead of inventing their own. Because the command can be large, this is the main user of the 128-byte SQE of §2.1, and it composes with the rest of the interface: IORING_URING_CMD_FIXED lets a passthrough command target a registered buffer (§6.1), and a multi-shot variant (IORING_URING_CMD_MULTISHOT) lets one command post repeated completions. Command passthrough turns io_uring from an I/O interface into a general asynchronous request transport, which is much of why it keeps absorbing new roles in the kernel.

Security and Containment

An interface this powerful—shared kernel memory, pools of worker threads, passthrough to devices—is also a large attack surface, and io_uring's history has made its security machinery a first-class concern. This closing section covers it at two scales. The first is the administrator's: the sysctl and the LSM hooks that decide who may create a ring at all, and which of its riskier capabilities they may use. The second is the application's, and it answers a question the rest of the chapter has been quietly accumulating. Every section so far has widened what a single ring can be asked to do; a program that needs only a fraction of that breadth has had no way to say so, and inherits the whole attack surface regardless. The mechanisms of §8.2 let it hand the breadth back, which is the only form of containment that scales with an interface still growing this fast.

Attack Surface and Controls

io_uring's breadth and its asynchronous worker threads have made it the source of a notable run of kernel vulnerabilities, and some large operators have chosen to disable it outright on systems that do not need it. The kernel provides graduated controls for exactly this. The kernel.io_uring_disabled sysctl (sysctl_io_uring_disabled, io_uring/io_uring.c) can disable io_uring entirely, or permit it only to processes in a designated group (sysctl_io_uring_group), so an administrator can deny the interface to untrusted workloads. Creation of a ring is gated by an LSM hook, security_uring_allowed, and further hooks mediate its more sensitive capabilities—security_uring_sqpoll for creating a polling thread, security_uring_cmd for command passthrough, and security_uring_override_creds for the personality mechanism by which a request can run under different credentials—so a security module such as SELinux can permit io_uring while restricting its riskier features. A ring can also be created disabled with IORING_SETUP_R_DISABLED and enabled only after its resources are registered, narrowing the window in which a partially configured ring is usable. Together these let io_uring's performance be adopted without forcing its full attack surface on systems that cannot accept it.

Stated precisely, the controls are the knobs an administrator actually turns. The io_uring_disabled sysctl takes three values: 0 allows io_uring for everyone, 2 refuses every io_uring_setup with -EPERM, and 1 is the middle ground—only processes with CAP_SYS_ADMIN or membership in the io_uring_group gid may create a ring. Whichever value is set, a successful check still falls through to the security_uring_allowed LSM hook, so a policy module has the final say. The R_DISABLED lifecycle completes the picture: a ring created disabled rejects all submission until the application calls io_uring_register with IORING_REGISTER_ENABLE_RINGS (io_register_enable_rings, io_uring/register.c), the idiom being to create the ring, register its files and buffers and drop privileges, and only then enable submission—so an attacker who seizes the process later cannot register new resources. And because an instance is an ordinary file descriptor, the usual containment applies for free: it is confined by the process's namespaces and credentials, its pinned memory is charged to RLIMIT_MEMLOCK, and its worker threads run with the owner's credentials, not elevated ones.

Restricting an Instance

The controls of the previous subsection are an administrator's: they decide whether a process may use io_uring at all. A second set belongs to the application, and exists so that a program can confine itself. A server that will only ever read files and send on sockets still gets a ring that accepts every one of the sixty-five opcodes of §4.1, including command passthrough to devices; if the process is later compromised, the attacker inherits all of it. Restrictions let the program close that gap while it is still trustworthy. Registering IORING_REGISTER_RESTRICTIONS (io_register_restrictions, io_uring/register.c) installs allow-lists of three kinds: which registration operations may be performed, which SQE opcodes may be submitted, and which SQE flags are permitted or required. The call is accepted only on a ring created with IORING_SETUP_R_DISABLED, and only once, which forces the sequence described above into its safe order: create the ring disabled, register the files and buffers the program will need, narrow the ring to the operations it will actually use, then enable submission. After that the restrictions cannot be widened, because there is no interface to widen them.

Allow-listing opcodes is a blunt instrument, though: it can say that a program may call IORING_OP_OPENAT but not which files it may open, or that it may create sockets but not of which family. The newest of io_uring's controls answers exactly that, and does so by borrowing a mechanism from a neighbouring chapter. IORING_REGISTER_BPF_FILTER (io_uring/bpf_filter.c) attaches a BPF filter to an individual opcode. Before the request is issued, the filter runs on a small context (struct io_uring_bpf_ctx) holding the opcode, the SQE flags, the user_data, and—for the operations that define one—a few operation-specific fields: the family, type and protocol for a socket creation, the flags, mode and resolve settings for an open. A filter returns one to allow the request and zero to deny it, in which case the request fails with -EACCES; where several filters are attached to an opcode, every one of them must allow the request—a new registration is chained ahead of whatever is already there, but the check is a logical and across the whole chain, so a second filter can only narrow what an opcode permits, never restore permission an earlier one withheld. A registration flag, IO_URING_BPF_FILTER_DENY_REST, attaches a deny filter to every opcode left unmentioned, turning the whole arrangement from a deny-list into an allow-list in one step. Because each opcode's context struct grows over kernel versions as more operations gain filterable fields, a filter written against an older kernel may see a smaller pdu_size than the running kernel provides; by default the registration simply reports the kernel's actual size back to userspace and lets the filter run against its own, older layout, but a second flag, IO_URING_BPF_FILTER_SZ_STRICT, turns that mismatch into an outright -EMSGSIZE for a filter that would rather fail loudly than run against fields it was not written to expect. The mechanism is also not guaranteed to exist at all: it lives behind CONFIG_IO_URING_BPF, which depends on CONFIG_BPF and CONFIG_NET, so a minimal kernel built without networking or the BPF subsystem falls back to the coarser controls of §8.1 and the opcode allow-list above.

The resemblance to seccomp is not accidental, and it goes deeper than the idea. These filters are written in classic BPF and reach the kernel through bpf_prog_create_from_user, the same entry point kernel/seccomp.c uses (Chapter 10), so the old two-register instruction set has acquired a third user-space entry point decades after eBPF displaced it—for the same reason seccomp still uses it, namely that a filter small enough to audit by eye is what a security check wants. The seccomp parallel extends to who may install one: like a seccomp filter, an io_uring filter may be set only by a process that has set no_new_privs or holds CAP_SYS_ADMIN, so an unprivileged program cannot use a filter to manipulate the behaviour of something it later executes.

The validator passed to bpf_prog_create_from_user is io_uring's own, io_uring_check_cbpf_filter(), and it is the mirror image of seccomp's. Every BPF_LD | BPF_W | BPF_ABS load is rewritten into BPF_LDX | BPF_W | BPF_ABS after a check that its offset is four-byte aligned and lies inside struct io_uring_bpf_ctx, so the program can read nothing but the context and the run-time interpreter never needs a bounds check; a BPF_LEN load is folded into an immediate holding the size of that structure. Everything else must appear on an explicit list of returns, ALU operations, scratch-memory accesses and forward jumps, which leaves no packet access and no way to reach memory the context does not contain, and a program is limited to BPF_MAXINSNS instructions. As with seccomp, there is no operation to remove a filter once it is installed.

Both mechanisms have a second, wider scope that is easy to overlook and is what makes them a real sandbox rather than a per-ring convenience. Registering either one with no ring at all—passing a file descriptor of -1, which io_uring/register.c calls a blind registration— attaches it to the task instead (io_register_restrictions_task, io_register_bpf_filter_task), where it is held at current->io_uring_restrict. A task-scoped restriction applies to every ring the task creates afterwards, because io_uring_setup clones it into each new instance as the instance is built, so a program that has confined itself cannot escape by creating a fresh ring. It also survives the operations that start new programs: kernel/fork.c's copy_process calls io_uring_fork, which duplicates a private copy of the restriction set (__io_uring_fork, io_uring/tctx.c) into every child, and nothing clears them on execve—so a launcher can confine a program before handing control to it whether or not that program knows io_uring exists. The gate is seccomp's rather than the ring's: the caller must have no_new_privs set or hold CAP_SYS_ADMIN, and a task that already carries restrictions may not replace them. Between the two scopes, io_uring has acquired something the rest of the chapter gave no reason to expect: a way to use the fastest I/O interface in the kernel while accepting only a chosen sliver of its surface.

Summary

This chapter described io_uring, the high-performance asynchronous I/O interface Linux added in 5.1 and has extended in nearly every release since. Its foundation is a pair of shared-memory ring buffers—a submission queue the application fills with entries describing operations, and a completion queue the kernel fills with their results—coordinated by head and tail indices and acquire/release memory barriers rather than by locks or, on the hot path, by system calls. An application submits work by writing a struct io_uring_sqe and reaps results by reading a struct io_uring_cqe whose res mirrors the equivalent synchronous return value, all keyed by a user_data value the application controls. A single io_uring_enter can submit and reap a whole batch; submission-queue polling can eliminate even that call; and an internal worker pool absorbs the operations that must block, so a program's own threads need never wait for I/O. A theme recurs wherever the chapter looked closely at who actually owns a piece of this machinery: not the process the intuitive unit would suggest, but something narrower or wider depending on the mechanism—the async worker pool and a task's security restrictions belong to the individual thread that created them, while pinned memory is charged against the real user id and so is shared by every process running as that user. Getting this scope wrong is an easy mistake for a reader to make and, as the chapter's own history of imprecise language on the point shows, an easy one to write down as well.

Around this core io_uring layers the machinery that makes it the fastest I/O path the kernel offers: linked chains that order dependent operations within a single submission, registered files and buffers that pay per-operation setup once, provided buffers the kernel assigns only to receives that complete, multi-shot operations that answer many events from one submission, polled and deferred completion modes for the lowest latency, zero-copy networking, and command passthrough that carries arbitrary device operations over the same rings—balanced by controls and LSM hooks for an interface whose power is also a risk, and by restrictions and BPF filters with which a program can narrow a ring—or every ring it will ever create—to the operations it means to use, before it is in a position to be exploited. The larger significance is that io_uring changes the fundamental unit of interaction with the kernel from the individual, synchronous system call to a stream of asynchronous requests flowing through shared memory—a change as much in kind as in speed, and one still reshaping how high-performance Linux software is written. It is also the clearest illustration of a pattern the last chapters keep returning to: the kernel's newest interfaces are not settled designs but ones still visibly in motion, gaining capabilities faster than the conventions for containing them—which is why io_uring spent its first years adding operations and its later ones learning how to give them back.
