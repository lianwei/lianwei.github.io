Linux 2.6.11 knew a process as a single kind of thing: an entity with a unique process ID, a view of one filesystem, one network stack, and one set of users, competing for the machine's CPU and memory with every other process on equal terms. That model is still the foundation, but modern Linux has learned to partition it. A single kernel can now present many processes each with the convincing illusion of having the machine to itself—its own process IDs starting at 1, its own root filesystem, its own network interfaces, its own notion of who is root—while an administrator caps exactly how much CPU, memory, and I/O each partition may consume. This is the kernel foundation of containers: the technology behind Docker, Podman, and Kubernetes, and the way most server software is deployed today.

There is a striking fact to keep in mind throughout this chapter: the Linux kernel has no container object. Nowhere in the source is there a struct container. What the kernel provides instead are two independent sets of primitives—namespaces, which control what a process can see, and control groups (cgroups), which control what a process can use—plus supporting mechanisms such as capabilities and seccomp. A “container” is what you get when a user-space runtime composes these primitives in a particular way. This chapter builds the picture from those primitives up: the eight namespace types and how a task reaches them, the user namespace that underlies unprivileged containers, the cgroup v2 hierarchy and its resource controllers, the Pressure Stall Information that reports contention, and finally how a container runtime assembles the whole into the thing we run.

What Isolation Means in Linux

Before the mechanisms, it is worth being clear about the goal and why Linux pursues it the way it does. This section explains the problem—running many mutually distrustful workloads on one kernel—and the two orthogonal answers the kernel gives, which the rest of the chapter then develops. The ideas are older than the word “container”: Unix has offered partial isolation since chroot confined a process's view of the filesystem in the 1979 Version 7, and FreeBSD jails and Solaris zones built fuller isolation in the following decades. Linux assembled its own answer incrementally, and on two separate tracks that only later converged. The namespace track began with the mount namespace in 2002, was not complete for unprivileged use until the user namespace landed in 2013, and gained its most recent member, the time namespace, only in 2020. The cgroup track started independently, merged in 2008 as “process containers,” and was substantial enough a design that it needed a rewrite: the multiple, per-controller hierarchies of the original design were replaced by the single unified hierarchy this chapter describes, which left experimental status in 2016. Two decades of incremental, not-always-coordinated work is why the subject feels less like one designed feature than like a toolbox of primitives accumulated piece by piece—and exactly why the kernel has no single “container” abstraction to point to.

Multitenancy Without Virtual Machines

The classic way to run several untrusting workloads on one physical machine is virtualization: give each workload its own virtual machine with its own kernel, and let a hypervisor divide the hardware. That works, but it is expensive—each virtual machine carries a full operating system, boots slowly, and reserves memory whether it uses it or not. For the common case where every workload wants to run on the same Linux kernel anyway, running dozens of copies of that kernel is a great deal of waste.

Containers take the opposite approach: one shared kernel, many isolated userspaces. Because there is only one kernel, a container starts as fast as a process (it is a process, or a small tree of them), adds no per-container kernel memory, and shares the host's page cache and scheduler. The cost of that efficiency is that isolation is now the kernel's responsibility rather than a hardware boundary: the single kernel must convincingly present each workload with its own private view of the system and enforce its resource limits, and any flaw in that enforcement is a flaw in the isolation. Much of this chapter is about how the kernel earns that trust—and §8.2 returns to where the trust has limits.

It helps to see isolation as a spectrum rather than a binary. At one extreme, ordinary processes share everything and are separated only by file permissions; at the other, separate physical machines share nothing. Virtual machines sit near the strong-isolation end, paying a full kernel per tenant for a hardware-enforced boundary; containers sit in the middle, sharing one kernel for near-native density; and hybrid designs such as lightweight virtual machines and user-space kernels deliberately trade some of the container's efficiency back for a stronger boundary. There is no universally right point on this spectrum—only a trade of density and speed against isolation strength. Containers won the common case because most workloads are not mutually hostile and do want the same kernel, so paying for a second kernel per workload buys isolation they do not need. The rest of this chapter is, in effect, the story of how much isolation the shared-kernel point on that spectrum can be made to provide.

Namespaces and Cgroups: Two Orthogonal Mechanisms

Isolation in Linux is built from two mechanisms that answer two different questions, and keeping them distinct is the key to understanding the whole subject. Namespaces answer “what can this process see?”—which process IDs, which mounts, which network interfaces, which users exist as far as this process is concerned. Control groups answer “how much can this process use?”—how much CPU time, how much memory, how much I/O bandwidth. The two are entirely independent: a process can be in a private set of namespaces without any resource limit, or be capped by a cgroup while sharing the host's namespaces, or—as in a real container—both at once. Figure 25-1 draws the two axes.

This orthogonality is not an accident but a deliberate design that keeps each mechanism simple and composable. Namespaces virtualize identifiers and tables—a PID, a mount tree, a network device list—so that the same kernel data structures can hold several disjoint populations at once. Cgroups account and throttle—counting pages charged, CPU cycles consumed, I/O issued—and enforce ceilings on those counts. A container runtime reaches for both because a useful container needs both a private view and a bounded appetite, but the kernel never fuses them, and this chapter treats them in turn: namespaces in §2 through §4, cgroups in §5 through §7, and their composition into a container in §8.

A concrete example makes the split vivid. Suppose two web servers share a host. Put each in its own network and PID namespace, and both can bind port 80 and both can run a process they call PID 1, each oblivious to the other—that is namespaces at work, and it involves no limits at all. Now give each a cgroup capping it at two CPUs and four gigabytes, and neither can starve the other however busy it gets—that is cgroups at work, and it involves no private view at all. Each mechanism is useful without the other, and a real container simply applies both.

One caveat frames the whole chapter: neither namespaces nor cgroups is, by itself, a complete security mechanism. Namespaces limit what names a process can resolve and cgroups limit what resources it can consume, but a process still calls into the one shared kernel through the full system-call interface, and a bug reached through that interface can defeat either. Real containers therefore add a third leg that this chapter touches only in passing but that does the security heavy lifting: capabilities to shed privileges (§3.2), seccomp filters to forbid unneeded system calls (Chapter 20), and Linux Security Modules such as SELinux or AppArmor to constrain what remains. The LSM framework itself has grown two newer, lighter-weight members that fit the same slot: CONFIG_BPF_LSM lets an eBPF program attach directly to security hooks (Chapter 23), and CONFIG_SECURITY_LANDLOCK lets an unprivileged process narrow its own filesystem and network access without any administrator-installed policy at all. Namespaces and cgroups build the container; capabilities, seccomp, and LSMs are what make it a boundary worth trusting.

Namespaces

A namespace virtualizes one class of global kernel resource so that the processes inside the namespace see their own private instance of it, isolated from processes outside. Linux 7.0 has eight namespace types, each covering a different resource. This section introduces all eight and the nsproxy that binds them to a task, then the three system calls that create and join namespaces, and finally the filesystem through which namespaces are named and manipulated as first-class objects. Chapter 3 met the same structures from the process side, as part of a task's identity; here they are the raw material of containers, and the emphasis is on what each type isolates and how a runtime combines them.

The unifying idea is worth stating plainly: in almost every case a namespace is a thin wrapper around a table or index the kernel already maintained. The kernel always had a hostname; the UTS namespace just lets there be several. It always had a mount tree, a set of network interfaces, an IPC object table, a PID allocator; each namespace type lets the kernel keep several disjoint copies and hand each process one. Every task belongs to exactly one namespace of each of the eight types—there is no “no namespace,” only the initial namespaces that the first process starts in and that most processes never leave. Two of the types, user and PID, nest (a new one has a parent and remembers it), which is what lets isolation compound; the other six are flat replacements. Keeping that picture—private copies of familiar tables, one per process, initial ones by default—makes the eight types far less to memorize than they first appear.

The nsproxy and the Eight Namespace Types

Most of a task's namespaces are reached through a single shared structure, struct nsproxy (include/linux/nsproxy.h), pointed to by task_struct->nsproxy. Because the nsproxy is reference-counted and shared, all the threads of a process—and a freshly forked child that changed no namespaces—point at the same one, so entering a namespace is usually a matter of swapping a pointer rather than copying anything. The proxy holds pointers to the mount, UTS, IPC, network, time, and cgroup namespaces, plus a pid_ns_for_children field discussed in §4.1. Two of the eight namespaces are deliberately not in the proxy: a task's active PID namespace is derived from its struct pid rather than stored here, and its user namespace is reached through its credentials (cred->user_ns), because the user namespace governs the very permission checks that guard the others. The structure is small—little more than a reference count and a pointer per namespace, as the definition below and Table 25-1 show—which is exactly why sharing it is cheap.

Each namespace structure begins with a common core—a struct ns_common (include/linux/ns/ns_common_types.h) that carries a reference count, the namespace ns_type, an inode number (inum), a stable 64-bit identifier, and the operations used by the nsfs filesystem of §2.3—and then holds whatever state that resource needs: struct net is large, with its own loopback device, routing, netfilter, and per-protocol state, while struct uts_namespace holds little more than a new_utsname. This shared header is what lets generic code treat any namespace uniformly; the to_ns_common accessor extracts it from any of the eight concrete types, and it is why every namespace can be named by an inode and compared for identity regardless of which resource it virtualizes. The init_nsproxy (kernel/nsproxy.c) is the proxy every task starts from, pointing at the initial instance of each namespace (init_uts_ns, init_net, init_pid_ns, and so on), which carry well-known low inode numbers; the whole namespaced world grows by branching off these initial instances. The shared header is shown below, and Table 25-3 describes its fields. Figure 25-2 shows a task reaching its namespaces.

The single reference count of earlier kernels has split into two. __ns_ref still governs memory lifetime—when it hits zero the namespace is unlinked from the namespace trees and freed after an RCU grace period—but a namespace can be alive and yet inactive well before that: __ns_ref_active counts live users (a task with the namespace in its nsproxy or cred, an open nsfs file descriptor, a bind mount of a /proc/<pid>/ns link), and it is what actually gates whether the namespace can still be opened, listed, or reentered. A namespace whose last active user goes away becomes inactive—no longer discoverable—while remaining allocated for as long as something still pins it by __ns_ref, such as a file whose f_cred still points at a user namespace nobody is running in anymore; the socket-passed-between-processes case in kernel/nscommon.c is exactly this. Dropping the last active reference on a non-user namespace also drops one active reference on the user namespace that owns it, cascading up the ownership chain—so a user namespace stays listable for exactly as long as any namespace it owns still is.

The ops field deserves a closer look, because it is what makes the whole scheme polymorphic. So the ops pointer is the seam along which one body of namespace-generic code serves all eight types: nsfs opens and closes links through get and put, setns enters a namespace through install, and the NS_GET_* ioctls of §2.3 walk ownership and nesting through owner and get_parent—each dispatched to the correct implementation without a single type-specific branch.

Switching a task's namespaces is careful pointer work rather than deep copying. Because a single nsproxy is shared by every thread of a process, the kernel never edits one in place; instead create_new_namespaces (kernel/nsproxy.c) allocates a fresh proxy that reuses the unchanged namespace pointers and installs new ones only for the types being replaced, and switch_task_namespaces then swaps the task's pointer to it under the task lock. The old proxy is reference-counted and freed when its last user drops it (free_nsproxy). On the fork path, copy_namespaces short-circuits entirely when no CLONE_NEW* flag is set—the overwhelmingly common case—so an ordinary fork simply shares the parent's proxy and costs a single reference increment. This is why namespaces impose essentially no overhead on processes that do not use them, and only modest cost on those that do.

Creating and Joining: clone, unshare, setns

Three system calls create and enter namespaces, and they cover three different moments. clone and its successor clone3 (kernel/fork.c) create a new process already placed in new namespaces: for each CLONE_NEW* flag passed, the child gets a fresh namespace of that type instead of sharing the parent's, wired up by copy_namespaces during the fork. unshare (kernel/nsproxy.c) moves the calling process into new namespaces without forking, replacing its nsproxy with one that holds fresh namespaces for the requested types—the mechanism behind the unshare(1) command. And setns (kernel/nsproxy.c) joins an existing namespace named by a file descriptor, which is how a tool enters the namespaces of an already-running container. Table 25-5 summarizes the three.

The setns path repays a closer look because joining several namespaces at once must be all-or-nothing. The kernel first builds a candidate namespace set and validates it (prepare_nsset and validate_nsset, kernel/nsproxy.c)—checking, among other things, that the caller has the required capability in the target user namespace—and only if every requested namespace is permitted does it apply them together in commit_nsset, which installs the new user credentials, mount root, and so on and then swaps the task's nsproxy via switch_task_namespaces. A pidfd can name a target process whose whole namespace set is to be joined at once. Ordering matters here: the user namespace must be entered before the others, because it is what authorizes them—a subtlety that the two-phase prepare/commit split exists to get right.

Two constraints on these calls trip up newcomers and are worth spelling out. First, privilege: creating a namespace of any type requires CAP_SYS_ADMIN in the user namespace that will own it, with one pivotal exception—creating a user namespace requires no privilege at all, which is the whole basis of unprivileged containers (§3). The standard recipe is therefore to unshare a new user namespace first, gaining a full capability set inside it, and then create the other namespaces under that new authority. setns likewise demands CAP_SYS_ADMIN in the target namespace's owning user namespace, so a process cannot enter a namespace it has no authority over. Second, the PID-namespace quirk: unsharing or setting a PID namespace does not move the calling process into it, because a live process cannot change its own PID. Instead the new namespace is recorded in pid_ns_for_children (§4.1) and takes effect for the caller's next child, which becomes PID 1 of the new namespace. This is why unshare --pid must be followed by a fork before anything actually runs inside the new PID namespace—a detail that surprises nearly everyone the first time.

The nsfs Filesystem and /proc/pid/ns

Namespaces are not merely transient kernel state; they are nameable objects with a lifetime, exposed through a small pseudo-filesystem called nsfs (fs/nsfs.c). Every namespace a process belongs to appears as a magic symbolic link under /proc/<pid>/ns/—.../ns/net, .../ns/pid, .../ns/user, and so on. These links have two important properties. Their target text encodes the namespace type and its unique inode number, so two processes are in the same namespace exactly when their links point to the same inode—the standard way to test namespace membership. And opening one yields a file descriptor that keeps the namespace alive even if every process in it exits, which is how a container manager can hold a namespace open to re-enter later, and the fd that setns consumes.

The nsfs file descriptors also answer queries through ioctl. A caller can walk the namespace hierarchy and read its attributes: NS_GET_USERNS returns the user namespace that owns a given namespace, NS_GET_PARENT returns the parent of a nested user or PID namespace, NS_GET_NSTYPE reports which of the eight types it is, and NS_GET_OWNER_UID returns the owning UID of a user namespace (include/uapi/linux/nsfs.h). Further ioctls (NS_GET_ID for the stable 64-bit identifier, and the NS_GET_PID_IN_PIDNS family) translate identifiers between namespaces, so a manager can ask “what number does this process have inside that PID namespace?” without entering it. Through nsfs, then, namespaces become inspectable, referenceable kernel objects rather than hidden per-task state—exactly what a container runtime needs to manage them.

Two practical details make nsfs more than a curiosity. The magic-link target has a readable form—net:[4026531840], the type name followed by the namespace's inode number in brackets—so even a shell script can compare two processes' namespaces by reading and matching these strings, and tools like lsns traditionally enumerate the system's namespaces by walking /proc this way. More importantly, the “keeps the namespace alive” property enables persistent namespaces with no member process at all: a bind mount of a /proc/<pid>/ns/ link onto an ordinary file pins the namespace for as long as the mount exists. This is exactly how ip netns add creates a named network namespace—it bind-mounts the link under /var/run/netns/—so an administrator can configure a network namespace, let the creating process exit, and have later processes enter it by name. A namespace, in other words, can outlive every process that ever lived in it, held open by nothing but a file descriptor or a bind mount.

Walking /proc to enumerate namespaces has always had an obvious flaw: it only finds namespaces that some visible process is currently in, and a persistent, bind-mounted namespace with no member process is invisible to it. Recent kernels close that gap directly with the listns system call (kernel/nstree.c), which walks a dedicated set of red-black trees—one per namespace type, plus a global one—that every namespace registers itself in at creation (ns_tree_add) and leaves at destruction (ns_tree_remove), independent of whether any process currently has it open. A caller passes a struct ns_id_req naming a namespace type to filter on and, optionally, an owning user namespace—LISTNS_CURRENT_USER asks for exactly the namespaces owned by the caller's own user namespace—and gets back an array of stable ns_id values it can resolve further with the ioctls above. Seeing every namespace on the host this way—regardless of which user namespace owns it—requires CAP_SYS_ADMIN in the initial user namespace and residence in the initial PID namespace (may_see_all_namespaces): real host-level administration, not merely privilege inside a container's own user namespace. Short of that, each candidate namespace is only reported back if it happens to be one of the caller's own current namespaces (is_current_namespace)—so an unprivileged or contained caller can use listns to resolve the stable ns_id of the namespaces it already belongs to, but not to discover namespaces it does not. Full, container-wide enumeration by ns_id—the kind a host-level monitoring agent, lsns, or an orchestrator with real root wants—remains the province of a genuine system administrator.

User Namespaces and Capabilities

Of the eight namespaces, the user namespace is the keystone, because it is what lets an unprivileged user create the others safely. It virtualizes the UID and GID number spaces and the capability model, so that a process can be fully privileged inside its namespace while remaining unprivileged on the host. This section covers the UID/GID mapping that makes “fake root” possible and the per-namespace capability rules that bound what that root can actually do.

Two structural facts frame everything that follows. First, user namespaces nest into a tree: each records its parent, its level (the initial namespace is level 0), and its owner—the host UID that created it—and nesting is capped at 32 levels deep (kernel/user_namespace.c) so the tree cannot grow without bound. Second, the user namespace is the root of authority for all the others: because every other namespace records which user namespace owns it, and every privileged operation is checked against that owner, the user namespace is where the question “is this process allowed to do this?” is ultimately answered. That is why it was the last namespace to be completed—arriving only in 2013, more than a decade after the mount namespace—and why it remains the most scrutinized: getting its permission model wrong would compromise every isolation guarantee built on top of it.

UID/GID Mapping and Fake Root

A user namespace (struct user_namespace, include/linux/user_namespace.h) carries a mapping between the UIDs and GIDs seen inside it and those of its parent. The mapping is written once, after creation, through /proc/<pid>/uid_map and gid_map (proc_uid_map_write, kernel/user_namespace.c): each line maps a range of inside IDs to a range of parent IDs. The classic unprivileged-container mapping makes inside UID 0 correspond to the user's own unprivileged host UID, so a process that is root inside the container is really running as that ordinary user on the host. This is the celebrated fake root: full administrative identity within the namespace, no added privilege outside it. The kernel keeps these two worlds straight with two distinct types. A kuid_t (include/linux/uidgid.h) is a kernel-internal UID, unique across the whole system; the ordinary uid_t a process sees is namespace-relative. Every credential check translates: make_kuid(ns, uid) converts a namespace-relative UID down to a system-wide kuid_t through the namespace's map, and from_kuid(ns, kuid) converts back up for display. Because file ownership and permission checks operate on kuid_t values, a file owned by host UID 1000 is correctly seen as owned by root inside a namespace that maps inside-0 to host-1000, and access to a file the host user cannot reach is denied no matter what the inside UID claims. The mapping, in other words, is not a bypass of permission checks but a relabeling that those checks see through. Figure 25-3 illustrates the translation.

Who may write which mapping is itself a carefully guarded question, because the map is the namespace's grant of identity. The rules (new_idmap_permitted, kernel/user_namespace.c) draw a sharp line. An unprivileged process may write only the trivial single-line self-map that maps one inside ID to its own effective UID on the host—enough to become root inside its own namespace but nothing more. Mapping a range of IDs (so a container can have many users) requires CAP_SETUID or CAP_SETGID over the parent namespace, which an ordinary user does not have. This is why containers rely on the small setuid helpers newuidmap and newgidmap: an administrator pre-assigns each user a block of subordinate IDs in /etc/subuid and /etc/subgid, and the helpers—trusted to honor those files—write the wider map on the user's behalf. The map is also write-once: once set it is immutable for the life of the namespace, and any ID with no mapping resolves to the overflow ID (overflowuid, normally 65534, the conventional nobody, and tunable through /proc/sys/kernel/overflowuid), so an unmapped file simply appears owned by nobody rather than leaking a real identity.

One mapping rule exists purely to close a security hole and is worth calling out. Before a process may write gid_map, it must first disable the setgroups system call for the namespace by writing deny to /proc/<pid>/setgroups. The reason is subtle: some files grant access by excluding a group (mode bits that deny a group permissions the world has), and if a process could enter a user namespace, drop a group it was in via setgroups, and then map GIDs freely, it could shed a group specifically to gain access it was meant to be denied. Requiring setgroups to be turned off before an unprivileged gid_map is written removes that avenue. It is a small illustration of the general theme that the user namespace's power makes even its bookkeeping security-sensitive.

A second, less well-known guard protects the same mapping from a subtler abuse: a namespace whose uid_map assigns inside UID 0 must trace back to a creator who could be trusted with file capabilities. When a write to uid_map maps ID 0 (verify_root_map, kernel/user_namespace.c), the kernel checks a flag—parent_could_setfcap—recorded on the namespace at creation time from whether the creating credentials held CAP_SETFCAP. Without that check, an unprivileged process could unshare a user namespace, map its own UID to inside-root, and then use file capabilities (Chapter 20) inside the namespace to grant itself abilities its creator was never trusted with in the parent namespace. Tying the root mapping to the creator's own CAP_SETFCAP closes that path without restricting the ordinary, non-file-capability uses of fake root.

UID/GID mapping as described so far is a property of a whole user namespace, applied uniformly to every process and file the namespace can see. Since Linux 5.12, the same translation can instead be attached to a single mount, independent of any process's user namespace: mount_setattr with the MOUNT_ATTR_IDMAP flag (fs/namespace.c) takes a user-namespace file descriptor and installs an idmapped mount—a struct mnt_idmap (include/linux/mnt_idmapping.h) carried on the mount itself that reinterprets the UIDs and GIDs stored on disk through that mapping for every access through that mount, regardless of which namespace the accessing process is in. This is the mechanism behind letting a container engine bind-mount a single shared host directory into containers running under different, non-overlapping UID/GID ranges and have each container see sensible ownership, without physically chown-ing the underlying files or juggling per-container copies; it is also how systemd-homed makes a home directory portable across machines whose local UID assignment for the same user may differ. The two mechanisms compose cleanly: a process's kuid_t is still translated by its own user namespace's uid_map, and the VFS additionally translates through the mount's mnt_idmap (via vfsuid_t/vfsgid_t, the mount-relative analog of kuid_t) when the access crosses that mount—so idmapped mounts extend the same relabeling idea from “per namespace” to “per mount,” without touching /proc/<pid>/uid_map at all.

Capabilities Per Namespace

Fake root is convincing because Linux long ago split the monolithic power of root into roughly forty capabilities—CAP_NET_ADMIN to configure networking, CAP_SYS_ADMIN for a grab-bag of administrative operations, CAP_BPF to load BPF programs (Chapter 23), and so on—and the user namespace makes each capability relative to a namespace. When a process creates a new user namespace, the kernel grants it a full capability set within that namespace (set_cred_user_ns sets cap_effective, cap_permitted, and the bounding set to CAP_FULL_SET, kernel/user_namespace.c), so it can mount filesystems, configure the container's network, and create further nested namespaces—all the operations that make a container. But those capabilities hold only over resources owned by that user namespace or its descendants. The same function clears cap_inheritable and cap_ambient to empty, which matters the moment the process execs: the new full capability set governs what the process can do directly, but a subsequently executed program only inherits capabilities through the ordinary file capability and set-user-ID-root rules of Chapter 20—an unprivileged program run inside the namespace does not automatically pick up the creator's full set just because the namespace itself is fully privileged.

This scoping is exactly what makes unprivileged containers safe. A process with CAP_SYS_ADMIN inside its user namespace can mount a filesystem in its own mount namespace, but the same capability grants nothing over the host's mounts, because those are owned by the initial user namespace where the process has no privilege at all. Each namespace records the user namespace that owns it, and every privileged operation checks the capability against that owning namespace—ns_capable(owning_user_ns, CAP_...)—not against the caller's own namespace. Creating a user namespace is itself the one privileged-seeming operation any unprivileged process may perform (subject to the per-user limit described below and the administrator controls of §8.2), and everything else follows from the mappings and the owning-namespace capability checks. The user namespace is thus both the enabler of unprivileged containers and, as §8.2 notes, historically their largest source of kernel security bugs.

The mechanism behind “relative to a namespace” is a single distinction in the kernel's permission checks. The old capable(CAP_...) asks whether a task holds a capability in the initial user namespace—true system-wide privilege. The newer ns_capable(ns, CAP_...) asks whether it holds the capability in a specific user namespace. Kernel code that acts on a namespaced resource was converted to call ns_capable against the user namespace that owns the resource, so a process with full capabilities in its own user namespace passes checks on resources it owns and fails checks on the host's. Each task's capabilities still live in its credentials as the familiar sets of Chapter 20—effective, permitted, inheritable, bounding, and ambient—but those sets are now interpreted relative to the task's user namespace. Creating a new user namespace resets them to full within the new namespace; crucially, it does not raise the task's privilege in any ancestor, so the new power is real but strictly local.

Two guardrails keep this from being abused as a denial-of-service or escalation vector. The number of user namespaces a user may create is bounded by a per-user count (the ucounts mechanism and the user.max_user_namespaces limit), so a process cannot exhaust kernel memory by creating namespaces without end, and the 32-level nesting cap of the section intro bounds depth. Those guardrails address resource exhaustion; the subtler danger—that granting an unprivileged user a full capability set inside a namespace exposes kernel code paths never written for hostile unprivileged callers—is the security theme that §8.2 takes up.

PID and the Other Namespaces

The user namespace is the most security-critical, but the PID namespace is the most conceptually distinctive, because it makes a single process have several identities at once. This section examines PID namespaces and the struct pid that implements them, then surveys the remaining namespaces—network, mount, IPC, UTS, and time—more briefly, since each virtualizes its resource on the same pattern. A useful way to read the section is by contrast: the PID namespace shows the hardest case of the “private copy of a global table” idea, where one object must carry several identities simultaneously, while the others show progressively simpler instances of the same idea—from the network namespace, which duplicates almost the entire network stack, down to the UTS namespace, which duplicates a single string.

PID Namespaces and struct pid

A PID namespace (struct pid_namespace, include/linux/pid_namespace.h) gives its processes their own PID number space, starting again at 1. PID namespaces nest: a namespace has a parent and a level, and a process visible in a child namespace is also visible in every ancestor, under a different number in each. The kernel represents this with a level of indirection that is the key to the whole design. The internal handle for a process is a struct pid (include/linux/pid.h), and it does not hold a single number; it holds an array, numbers[], of struct upid entries—one per level, each pairing a number with the namespace it belongs to. 

/* include/linux/pid.h (abridged) */
struct upid {
	int nr;			/* the PID number at this level */
	struct pid_namespace *ns;
};

struct pid {
	refcount_t count;
	unsigned int level;	/* how many namespaces deep */
	/* ... */
	struct upid numbers[];	/* one entry per level, [0] = init ns */
};

So the process a container calls PID 1 might be PID 4217 in the host's initial namespace and PID 88 in an intermediate one: one struct pid, three upid entries. Translating between a task and a namespace-relative number walks this array—pid_nr_ns finds the nr whose ns matches, returning 0 if the process is not visible in that namespace at all, which is how isolation is enforced (a container simply cannot name a process outside it). The process that is number 1 in a namespace is its init: it becomes the child_reaper that inherits orphaned descendants, and if it dies the whole namespace is torn down and its remaining processes killed, as described below. Figure 25-4 shows the nesting.

The init of a PID namespace carries special responsibilities that mirror the host's init exactly. Signals from an ancestor namespace are filtered—the namespace's PID 1 does not receive signals for which it has no handler, so it cannot be killed by accident from outside—and when it does exit, the kernel does not reparent its orphans upward but runs zap_pid_ns_processes (kernel/pid_namespace.c), which disables further PID allocation and sends SIGKILL to every remaining process in the namespace. A container therefore cannot outlive its init: kill PID 1 and the whole namespace is emptied, just as killing the host's init would end the system. The reboot system call is similarly virtualized—when a namespace's init calls it, the kernel records the requested action in pid_ns->reboot and terminates the namespace with a corresponding exit code rather than rebooting the host, so a container manager can watch its container's init exit and see that the workload asked to restart or power off.

Two further details round out the picture. The nesting depth is capped at MAX_PID_NS_LEVEL, which is 32 (include/linux/pid_namespace.h)—a hard limit precisely because struct pid's numbers[] array grows by one entry per level, so unbounded nesting would mean unbounded allocations. And, as §2.2 noted, entering a PID namespace does not renumber the entering process itself; only its children are born into the new namespace. This is why a container's /proc, which reports PIDs relative to the reader's PID namespace, must be a fresh proc mount made after the fork into the new namespace: mounted from inside, it shows only the namespace's own processes, numbered from 1, completing the illusion that the container is a machine unto itself.

One more field of struct pid_namespace is worth calling out because it is directly settable and often surprises people: pid_max. Just as the host has a global /proc/sys/kernel/pid_max ceiling on how large a PID number may grow, each PID namespace carries its own pid_max, exposed as the same /proc/sys/kernel/pid_max path but scoped to that namespace's own sysctl table (register_pidns_sysctls, kernel/pid.c). Because a process's identity at each level is allocated independently—alloc_pid walks the ancestor chain and allocates a number from each level's own idr against that level's own pid_max—lowering a container's pid_max shrinks only the numbers visible inside it without touching the host's allocator, and a container cannot use a generously raised inside value to escape whatever cap an ancestor namespace enforces on its own layer of the process's numbers[] array.

Network, Mount, and the Rest

The remaining namespaces virtualize their resources on the same principle—give each namespace a private instance of some global table—but differ in how much state that involves. The network namespace (struct net, include/net/net_namespace.h) is the heaviest: a new network namespace begins with nothing but a loopback device and gets its own network interfaces, routing tables, netfilter and connection-tracking state, socket ports, and per-protocol configuration, so two containers can both bind port 80 without conflict. Interfaces are moved between namespaces one at a time, and the usual way to connect a container to the host is a veth pair—a virtual Ethernet cable with one end in each namespace.

The mount namespace (struct mnt_namespace, fs/mount.h)—the very first namespace Linux gained, hence the generic flag name CLONE_NEWNS—gives each namespace its own tree of mounts, so a container can have an entirely different root filesystem while mount propagation settings control which mount events cross the boundary. The IPC namespace isolates System V semaphores, message queues, and shared memory along with POSIX message queues, so two containers cannot see or collide over each other's IPC objects. The UTS namespace is the simplest, isolating just the hostname and domain name that uname reports—which is why each container can have its own hostname. Finally the time namespace is the newest, virtualizing not the wall clock but offsets for the monotonic and boot-time clocks, applied cheaply in the vDSO (Chapter 10; Chapter 6 describes the mechanism in full) so that a checkpointed and restored container can preserve the illusion of continuous uptime; the offsets themselves are readable and, before any process has entered the namespace, writable through /proc/<pid>/timens_offsets (fs/proc/base.c), which is exactly the hook a checkpoint/restore tool uses to reinstall a container's saved clock skew before its processes resume running. Together with the PID, user, and cgroup namespaces, these give a container a complete private view of the system on every axis that matters.

Two of these repay a little more detail because containers lean on them heavily. The network namespace is not just isolated but starts almost empty: a fresh one has only a loopback interface, and even that comes up administratively down, so a runtime must move or create interfaces and configure addressing before the container has any connectivity. The standard bridge to the host is the veth pair mentioned above—two linked virtual interfaces, one left in the host namespace and attached to a bridge, the other moved into the container—so the container's traffic reaches the host stack over what looks to each side like an ordinary cable. The mount namespace, for its part, carries a propagation setting on every mount that decides whether mount and unmount events cross the namespace boundary: a shared mount propagates events to its peers, a private mount keeps them to itself, a slave mount receives events from its master but sends none back, and an unbindable mount cannot be bind-mounted at all. A container runtime typically makes the container's root a slave of the host's mounts, so that new host mounts (a plugged-in disk, say) can be made to appear inside the container while the container's own mounts stay invisible to the host—the fine control that makes a shared-kernel filesystem view both flexible and contained.

A mount namespace is not the only way to build a private mount tree, and modern container runtimes increasingly avoid creating one at all. open_tree with the OPEN_TREE_CLONE flag (fs/namespace.c) clones a subtree of mounts into a free-floating, unattached copy referenced only by a file descriptor—a detached mount tree that exists outside every mount namespace until something attaches it. That file descriptor can be reshaped in place—mount_setattr applies read-only or the MOUNT_ATTR_IDMAP idmapping of §3.1 to it before it is ever visible to any process—and then move_mount grafts the finished tree onto a path in a target mount namespace, or the newer combined open_tree_attr system call does the clone-and-configure step in one call. This lets a runtime assemble a container's entire root filesystem—bind mounts, an idmapped overlay, read-only layers—as an isolated construction project, fully configured and validated, and publish it into the container's mount namespace with a single atomic graft, rather than building it up mount-by-mount inside a namespace the container's processes can already see.

Control Groups

Namespaces control what a process sees; control groups—cgroups—control what it can use. A cgroup is a group of processes to which resource limits and accounting are applied collectively, arranged in a hierarchy so that limits nest. Modern Linux uses cgroup v2, a redesign that replaced the tangled multiple hierarchies of the original with a single unified one. This section covers the unified hierarchy and its interface, then the kernel data structures—css, css_set, and the task's link to them—that implement it.

A word of history clarifies why there are two versions. The original cgroups (retroactively “v1”) arrived in 2008 and let each controller have its own hierarchy, so a process could be in one place for the memory controller and another for CPU. That flexibility sounded useful but proved a decade-long mistake: controllers could not cooperate (the memory and I/O controllers could not agree on which cgroup owned a writeback, for instance), and userspace could not reason about a process's resources without consulting every hierarchy at once. Cgroup v2, developed to fix this and declared stable in 2016, imposes one hierarchy for all controllers—less flexible, but coherent. Both are backed by kernfs, the same in-kernel pseudo-filesystem library that backs sysfs, so a cgroup is quite literally a directory whose files are the control interface. This chapter describes v2, which is what containers use; v1 persists only for backward compatibility.

The Unified Hierarchy

In cgroup v1, every resource controller had its own separate hierarchy, and a process could sit at different places in each—a flexibility that proved unmanageable. Cgroup v2 (mounted as the cgroup2 filesystem, normally at /sys/fs/cgroup) imposes a single unified hierarchy: one tree of cgroup directories, and a process belongs to exactly one cgroup in it, with all controllers acting at that one location. Figure 25-5 contrasts this single tree with v1's tangle of separate per-controller hierarchies. The tree is a real directory tree in a kernfs-backed filesystem, so a cgroup is created with mkdir and a process is moved into it by writing its PID to the cgroup's cgroup.procs file. Each cgroup exposes a set of interface files; Table 25-7 lists the core ones, which exist in every cgroup independent of any controller.

Two rules give the hierarchy its shape. First, controllers are enabled top-down: a cgroup's cgroup.subtree_control can enable only controllers that its own cgroup.controllers lists (which its parent in turn enabled for it), so a resource is distributed down the tree, never conjured at a leaf. Second, the no-internal-process constraint holds that, except at the root, a cgroup may not simultaneously contain processes and enable controllers for children—processes live only at the leaves. This forces a clean picture in which interior cgroups partition resources among their children and the actual work runs in the leaves, which is what makes hierarchical resource distribution well defined. Together these rules turn the directory tree into a predictable resource-division scheme rather than an arbitrary graph.

The no-internal-process rule has one deliberate exception, the threaded cgroup, which exists because some resources are naturally per-thread. A cgroup's cgroup.type is normally domain, meaning it holds whole processes; writing threaded makes it the root of a threaded subtree in which the individual threads of one process may be split across child cgroups. Thread-granular controllers such as cpu then act per-thread within the subtree, while process-wide controllers such as memory still act only at the subtree's domain root—because it makes no sense to charge one thread's memory separately from its siblings that share an address space. The kernel tracks this with a dom_cgrp back-pointer (a cgroup is threaded when its dom_cgrp differs from itself, kernel/cgroup/cgroup.c), so the two kinds of controller can coexist in one tree.

The cgroup is also the unit of two whole-group process-lifecycle operations, and both matter to anything that manages containers. Writing 1 to cgroup.freeze (cgroup_freeze, kernel/cgroup/freezer.c) stops every process in the cgroup and its descendants in place without killing or losing any of them—the cgroup-native replacement for signaling each process individually with SIGSTOP, and the mechanism behind a container runtime's “pause” operation, since it freezes the whole tree atomically rather than racing against processes that fork while being stopped one at a time. The freeze is cooperative rather than forcible: each task is flagged with JOBCTL_TRAP_FREEZE and parks itself in do_freezer_trap (kernel/signal.c) on its next trip through the signal-delivery path back to user space. There it sleeps interruptibly, so a frozen task can still be killed with SIGKILL, and the frozen field of cgroup.events becomes 1 only once every task has actually parked—the event a runtime polls to know the pause is complete. Writing 1 to cgroup.kill is the symmetric whole-group teardown: it sends SIGKILL to every process in the cgroup and its descendants at once, which is both faster and more reliable than a caller walking cgroup.procs and signaling each PID by hand. Each kill also bumps a per-cgroup kill_seq counter that cgroup_post_fork rechecks, so a child forked while the kill was in progress is killed as it is born instead of escaping.

A final piece of machinery makes the statistics files affordable at scale. A busy server may read cpu.stat or memory.stat for thousands of cgroups, and maintaining those totals as shared atomic counters updated on every page fault or scheduler tick would be a bottleneck. Cgroup v2 instead uses rstat (kernel/cgroup/rstat.c), which accumulates statistics per CPU without shared writes and folds them up the hierarchy lazily—only when something reads a stat file—so accounting stays cheap on the hot path and the cost of aggregation is paid only by the (rare) reader. It is the same “keep the fast path lock-free, defer the expensive combine” pattern that recurs throughout the kernel.

css, css_set, and Task Membership

Underneath the filesystem, three data structures connect a task to its resource limits. A struct cgroup represents a node in the tree. For each controller active on a cgroup there is a cgroup subsystem state, struct cgroup_subsys_state (universally abbreviated css, include/linux/cgroup-defs.h), which is that controller's per-cgroup state—the memory controller's css, for instance, is embedded in the struct mem_cgroup that holds the group's memory counters. A task does not point at its cgroup directly; it points at a css_set (struct css_set), which is a cached bundle of “the css for every controller, for this task's cgroup.”

The indirection through css_set exists for efficiency. Every task in the same cgroup has identical controller memberships, so they can all share one css_set: the kernel deduplicates them, keeping a hash of existing sets and pointing each task at the matching one (task->cgroups, include/linux/sched.h). On a machine with thousands of tasks in a handful of cgroups there are only a handful of shared css_set objects, so fork and exit—which just take or drop a reference on the shared set—stay cheap, and the mapping from set to cgroups is kept by cgrp_cset_link records. Figure 25-6 shows the chain from tasks through a shared css_set to the per-controller css objects of their cgroup. Moving a process to another cgroup, by writing its PID to cgroup.procs, runs cgroup_attach_task (kernel/cgroup/cgroup.c), which migrates the task to the css_set matching its new position—creating that set if no other task already needed it.

Each css has a lifecycle of its own, managed so that runtime code can reach it locklessly. A controller's per-cgroup state is created by the controller's css_alloc and css_online callbacks when the controller is enabled on a cgroup, and it is reference-counted with a percpu_ref (include/linux/cgroup-defs.h)—a counter split across CPUs so that taking a short-lived reference on the hot path (a page being charged to a memory cgroup, say) needs no shared write. A css is marked CSS_ONLINE between its online and offline callbacks; when a cgroup is removed the reference is “killed,” and once the last outstanding reference drops the state is freed after an RCU grace period, so a task that is mid-operation on a css never has it vanish underneath it. Every cgroup also owns a special self css that carries the base per-cgroup statistics through rstat even when no controller is enabled.

Migration—moving a task from one cgroup to another—is careful precisely because it must not fail halfway. When a PID is written to cgroup.procs, cgroup_attach_task does not simply repoint the task; it runs a two-phase migration (kernel/cgroup/cgroup.c). A prepare phase first ensures the destination css_set exists—allocating it, and any it depends on, up front—so that every allocation that could fail happens before anything changes. Only then does a commit phase move the task (and, for a whole process, all its threads) to the new set atomically. This mirrors the prepare/commit discipline seen elsewhere in this book and guarantees that a migration either fully succeeds or leaves the task exactly where it was, never in a torn state between two cgroups.

The Controllers

The hierarchy is only scaffolding; the actual limiting and accounting is done by controllers (also called subsystems), each governing one resource and contributing its own interface files to every cgroup where it is enabled. This section walks through the three most important—cpu, memory, and io—then the pids and cpuset controllers and the delegation model that lets an unprivileged user manage a subtree, and finally the rdma, misc, and dmem controllers that ration resources owned by device drivers. Across all of them, cgroup v2 offers the same three kinds of control, and recognizing which a given file provides makes the dozens of interface files far easier to hold in mind. A weight (such as cpu.weight or io.weight) divides a resource proportionally among siblings only when they compete, leaving it uncapped when idle. A limit (such as cpu.max, memory.max, or io.max) is a hard ceiling enforced even when the resource is free. And a protection (such as memory.min and memory.low) reserves a floor a cgroup keeps even when the rest of the system is starved. cpu, memory, and io

The cpu controller limits processor time, and it offers two complementary knobs. cpu.weight sets a proportional share—a cgroup with twice the weight of its sibling gets twice the CPU when the two compete, but neither is capped when the machine is idle—by feeding into the fair scheduling class of Chapter 7, whose EEVDF scheduler weighs the group as a single entity among its siblings. cpu.max sets a hard bandwidth ceiling as a quota and period (“this much CPU time per that much wall-clock time”), throttling the cgroup once it exhausts its quota in a period even if CPUs are idle. cpu.stat reports usage and how often the group was throttled. The pair covers the two things an operator wants: fair sharing under contention, and firm caps for billing or predictability. Two refinements tune the edges: cpu.max.burst lets a cgroup that has under-used its quota bank a little slack and briefly exceed it, smoothing bursty workloads, and cpu.uclamp.min/cpu.uclamp.max clamp the utilization the scheduler perceives for the group—raising it to keep a latency-sensitive workload on fast CPU-frequency states, or lowering it to let a background one run cool. A third refinement is qualitative rather than quantitative: writing cpu.idle marks the whole cgroup as a background, best-effort consumer—effectively giving it SCHED_IDLE at the group level (Chapter 7)—so it runs only when nothing else wants the CPU at all, which is a cleaner way to express “never get in the way” than trying to pick a weight low enough to approximate it.

The memory controller is the most elaborate, because memory cannot simply be throttled—once granted it must be reclaimed or the workload killed. Its accounting lives in struct mem_cgroup (mm/memcontrol.c), and every charge to a page or slab object is billed to the mem_cgroup of the allocating task as the allocation happens. Four thresholds shape its behavior: memory.max is a hard limit that triggers reclaim and, if that fails, the cgroup OOM killer; memory.high is a soft limit that throttles the workload by forcing it into reclaim as it approaches, without killing; and memory.min and memory.low are protections that shield a cgroup's memory from reclaim when the system is under pressure elsewhere. memory.current reports usage and memory.events counts significant events such as hitting the limit or an OOM kill—the signals an orchestrator watches to size a workload. Its accounting reaches beyond user pages: kernel memory charged on a cgroup's behalf—slab objects, socket buffers, page tables—is billed too, so a workload cannot escape its limit by pushing allocation into the kernel. Swap is bounded separately by memory.swap.max, so a container cannot quietly convert memory pressure into swap thrashing, and memory.reclaim lets an operator ask the kernel to proactively reclaim from a cgroup—shrinking an idle workload's footprint before its neighbors need the memory. Two further files round out the picture. memory.peak records the cgroup's historical high-water mark of usage—useful for right-sizing a memory.max after the fact, since memory.current alone cannot say how close a workload ever came to its limit—and, like memory.swap.max's sibling memory.swap.peak, can be reset by writing to it. And memory.oom.group, if set, changes what happens when the cgroup OOM killer fires: instead of picking a single victim task within the cgroup, it kills every process in the cgroup together, which is what a container runtime wants for a workload that is only meaningful as a whole—killing half of a database cluster's threads and leaving the rest to run in an inconsistent state is rarely better than killing all of it. Where memory itself is compressed rather than paged out, memory.zswap.max bounds how much of a cgroup's swapped-out memory zswap (Chapter 8) may hold in its compressed pool, keeping one cgroup's compression activity from starving its neighbors' pool space.

The io controller limits block-device I/O, integrating with the multiqueue block layer of Chapter 14. io.max caps bandwidth and IOPS per device (as bytes-per-second and operations-per-second limits keyed by device number), while io.weight gives proportional sharing of a device's throughput under contention, and io.stat reports per-device bytes and operations. Because a single logical request can generate I/O long after the process that issued it has moved on—writeback of dirty pages is the classic case—the io and memory controllers cooperate to attribute such deferred I/O back to the responsible cgroup, so that a container cannot escape its I/O limit simply by dirtying pages and letting the kernel flush them later. Behind the two files sit different mechanisms: io.max is enforced by a simple throttle (block/blk-throttle.c), while io.weight's proportional sharing is driven by a cost model (block/blk-iocost.c) that estimates each device's capacity so shares are meaningful across very different disks. A third, latency-oriented controller, io.latency (block/blk-iolatency.c), protects a cgroup's I/O latency target by throttling competing cgroups when it is missed—useful when the goal is not a bandwidth cap but a responsiveness guarantee.

pids, cpuset, and Delegation

Two smaller controllers round out the common set. The pids controller (kernel/cgroup/pids.c) caps the number of processes a cgroup may contain through pids.max, with pids.current reporting the count and pids.peak its historical high—a simple but essential defense against fork bombs, since a runaway process that cannot fork past its limit cannot exhaust the host's PID space. The cpuset controller (kernel/cgroup/cpuset.c) instead pins a cgroup to particular CPUs and memory nodes through cpuset.cpus and cpuset.mems, which matters on large NUMA machines where confining a workload to CPUs near its memory avoids cross-node penalties. It can go further and turn a cgroup into a partition root by writing cpuset.cpus.partition, which comes in two strengths: writing root gives the cgroup exclusive use of the CPUs named in cpuset.cpus.exclusive while those CPUs still take part in the kernel's normal load-balancing machinery, while writing isolated removes them from load balancing entirely, so a latency-critical or real-time workload owns them outright with no interference even from the scheduler's own housekeeping. Beyond these, the kernel provides the hugetlb controller, whose per-size limits Chapter 8, Section 4.4 describes, and the three device-resource controllers of §6.3, each following the same pattern of interface files.

Finally, delegation is what lets an unprivileged user—or an unprivileged container—safely manage its own subtree of the hierarchy. An administrator delegates a cgroup by granting the user write access to its directory and to a specific few of its files: cgroup.procs, cgroup.threads, and cgroup.subtree_control. The delegatee can then create sub-cgroups, move its own processes among them, and enable controllers for them, but cannot affect anything above its delegated root, because it lacks write access there. The containment is enforced by the migration rule itself: moving a process requires write access to the destination cgroup.procs and to the cgroup.procs of the common ancestor of the source and destination, so a delegatee can shuffle tasks freely within its subtree but cannot pull a process in from outside it or push one out. The nsdelegate mount option ties this to cgroup namespaces (§2.1), so that a container's cgroup namespace root becomes a natural delegation boundary it cannot escape. Delegation is what makes cgroup v2 usable inside unprivileged containers: a container can run its own systemd, managing a private cgroup subtree, without any power over the host's.

rdma, misc, and dmem: Controllers for Device Resources

The controllers so far govern resources that the core kernel allocates itself: CPU time, pages, block I/O, and tasks. Three smaller controllers govern resources that belong to device drivers, and they share one design. The controller only counts. The driver that hands out the resource calls a try-charge function before allocating and an uncharge function after freeing, and the charge fails if it would take this cgroup or any ancestor past its limit. The cgroup charged is the one the calling task belongs to at that moment, and the charge stays with that cgroup until the resource is freed. Table 25-8 lists the files each controller adds. What separates the three is what each can do when a limit is hit.

The rdma controller (kernel/cgroup/rdma.c, Linux 4.11) limits the objects user space creates on an RDMA adapter through the verbs interface. It counts two resources per device. hca_handle is the number of open device contexts, charged by ib_rdmacg_try_charge() when user space allocates a ucontext. hca_object is the number of verbs objects of every kind (queue pairs, completion queues, memory regions, protection domains), charged when each user object is created (drivers/infiniband/core/rdma_core.c). An adapter joins the controller through rdmacg_register_device(), and the limits are written per device, as in mlx5_0 hca_handle=2 hca_object=2000. A charge that would exceed rdma.max fails with -EAGAIN, which the verbs call returns to user space. There are no weights or protections, because the kernel cannot take a queue pair back from the process that owns it.

The misc controller (kernel/cgroup/misc.c, 5.13) is for scalar resources with a host-wide capacity that would not justify a controller of their own. The resource types are a compile-time list, enum misc_res_type in include/linux/misc_cgroup.h. In 7.0 it holds the AMD SEV and SEV-ES address-space IDs and, since 6.16, the Intel TDX host key IDs: hardware slots that each confidential virtual machine consumes and that the processor provides only in limited number. The owner declares the total with misc_cg_set_capacity(), which appears in the root's misc.capacity. KVM charges one slot with misc_cg_try_charge() when it creates an SEV or TDX guest. A charge that would exceed the capacity or any ancestor's misc.max fails with -EBUSY and is counted in misc.events. Version 6.11 added misc.events.local for events in the cgroup itself and misc.peak for its high-water mark.

The dmem controller (kernel/cgroup/dmem.c, 6.14, CONFIG_CGROUP_DMEM) is the newest, and it addresses a long-standing gap: memory on a device, above all the video memory (VRAM) of a discrete GPU. The memory controller counts only system RAM, so before 6.14 a container could fill a GPU's memory and push every other tenant's buffers out to system memory without any cgroup noticing. A driver now describes each pool of device memory as a region by calling dmem_cgroup_register_region() with its size and a name. DRM drivers do this through drmm_cgroup_register_region(), which names the region drm/<device>/<region>, for example drm/0000:03:00.0/vram0. In 7.0.12 the Intel xe driver registers each VRAM region (6.14) and amdgpu registers its vram (6.15). The interface files are keyed by region name, one line per region. The root's dmem.capacity lists every region and its size, and dmem.current reports usage. dmem.max, dmem.min, and dmem.low set a limit and two protections with the same meaning as their memory-controller namesakes. All values are in bytes, because a device's allocation granularity need not match the CPU's page size.

Each pairing of a cgroup and a region has a struct dmem_cgroup_pool_state. It is created on the first charge or limit write, and it wraps the same page_counter the memory controller uses, here counting bytes instead of pages. Each pool's counter is chained to the pool for the same region in the parent cgroup, so one page_counter_try_charge() enforces every ancestor's dmem.max. dmem_cgroup_try_charge() charges the current task's cgroup and, on success, returns the pool. The driver stores the pool with the allocation (TTM keeps it in ttm_resource->css) so that dmem_cgroup_uncharge() credits the right cgroup however much later the buffer is freed. On failure the function returns -EAGAIN and, if asked, the limit pool: the pool, possibly an ancestor's, whose limit was hit.

The limit pool exists because device memory, unlike a queue pair or an ASID, can be taken back. A GPU buffer can be evicted to system memory and brought back when it is next needed, so a charge that fails should first evict, the way an allocation that crosses memory.max reclaims before it gives up. The TTM memory manager shared by most discrete-GPU drivers, whose wound/wait locking Chapter 5, Section 5.15 describes, does exactly that. ttm_resource_alloc() turns -EAGAIN into -ENOSPC, the same error a full VRAM produces, so the allocation falls into TTM's normal eviction walk with the limit pool passed along. For each candidate buffer, ttm_bo_evict_cb() first asks dmem_cgroup_state_evict_valuable(), which answers with three rules:

  • A buffer may be evicted only if it is charged to the limit pool or to one of its descendants. A cgroup that is over its own limit therefore evicts its own buffers, or those of its children, and never those of a neighbor that is within its share.
  • A buffer whose pool is at or below its effective dmem.min is never evicted. The effective values come from page_counter_calculate_protection(), the same function that distributes memory.min and memory.low down the hierarchy.
  • A buffer whose pool is at or below its effective dmem.low is skipped on the first pass. If that pass evicts nothing and some buffer was skipped for this reason, TTM walks again with ignore_low set.

When the device itself is full and no cgroup limit was hit, there is no limit pool. The function then uses the root as the limit, so the protections still decide which tenants' buffers move first. The result is the memory controller's model, limits that trigger reclaim and protections that shield a working set, applied to memory the CPU's page allocator never sees.

Pressure Stall Information

Limiting resources raises a question: how does an operator know when a workload is starved—waiting on CPU, memory, or I/O it cannot get? Classic metrics like load average and free memory answer this poorly. Linux's answer is Pressure Stall Information (PSI, kernel/sched/psi.c), which measures directly how much time work is lost to resource contention. This section covers what PSI measures and the trigger mechanism that lets software react to pressure the moment it appears.

PSI exists because the old indicators mislead. Load average counts runnable tasks but cannot tell a busy-and-healthy system from an overloaded one, and free-memory counts say nothing about a machine that has just enough memory to avoid the OOM killer yet spends its time thrashing pages in and out. PSI, merged in Linux 4.20 from work at Meta to pack data-center machines closer to their limits, answers the question the operator actually has—“how much useful work is my hardware losing to contention right now?”—by timing stalls directly. Because that timing adds a small per-task cost, PSI is a build option (CONFIG_PSI) and can be turned off at boot (psi=0) on systems that do not need it; the static key psi_disabled makes the accounting free when it is off. A kernel can also be built with CONFIG_PSI_DEFAULT_DISABLED, shipping PSI compiled in but dormant until psi=1 is passed on the command line, which lets a distribution offer it without imposing its cost on every machine.

Measuring Contention

PSI tracks, for each of three resources—CPU, memory, and I/O—the fraction of time that tasks are stalled waiting for it, and reports two levels of severity. The some metric is the fraction of time at least one task is stalled on the resource (work is delayed); the full metric is the fraction of time every runnable task is stalled on it (no work is progressing at all, a sign of severe contention). Each is reported as a percentage averaged over 10-second, 60-second, and 300-second windows, plus a running total in microseconds. The distinction is what makes PSI actionable: a little “some” memory pressure is normal, but rising “full” memory pressure means the machine is thrashing and a workload should be shed. Figure 25-7 contrasts the two.

What counts as a stall is chosen carefully, which is why PSI sees problems the old metrics miss. A task is counted as memory-stalled while it waits in reclaim or for a page that was evicted to be read back—that is, while it is thrashing—so memory pressure rises exactly when a workload is technically within its limit yet getting no work done, the case free-memory counts cannot detect. Likewise a task is I/O-stalled while blocked waiting for a device, and CPU-stalled while runnable but not scheduled. The some/full distinction has a subtlety worth noting for CPU: at the whole-system level a runnable task essentially always gets a CPU eventually, so system-wide CPU full is not meaningful; it becomes meaningful only within a cgroup, where every one of a group's tasks can be runnable yet none scheduled because another cgroup is holding the processors—precisely the throttling a cpu.max or a low cpu.weight produces. The system-wide /proc/pressure/cpu file nevertheless prints a full line, always zero, so that every pressure file has the same two-line format and one parser handles them all.

Memory stalls in particular are not inferred from task state alone; they are declared by the code that causes them. Every path where a task is held up for want of memory brackets the wait with psi_memstall_enter() and psi_memstall_leave() (kernel/sched/psi.c), which set and clear the task's TSK_MEMSTALL flag: direct reclaim and compaction in the page allocator (mm/page_alloc.c, mm/vmscan.c, Chapter 17), waiting for a page to be read back in mm/filemap.c and mm/page_io.c—but only when the page is marked as recently part of the working set, so ordinary first-time reads do not count while genuine refaults do—and the throttling a cgroup suffers above its memory.high in mm/memcontrol.c. Because direct reclaim keeps the stalled task on the CPU, PSI tracks such tasks under a separate count, NR_MEMSTALL_RUNNING (include/linux/psi_types.h): a task busily scanning LRU lists looks productive to the scheduler, but PSI correctly counts it as stalled, so memory full can be reported even while every CPU is busy—busy doing nothing but reclaim.

The accounting itself is cheap by design. Each CPU keeps its own running stall totals (a per-CPU psi_group_cpu), updated without shared locks as tasks change state, and the kernel folds them together only when someone reads a pressure file—the same defer-the-combine pattern as cgroup rstat (§5.1). The three percentages an average file shows are resampled on a slow two-second cadence, while the underlying microsecond total accumulates continuously, so the averages are a smoothed view and the total is the exact figure a careful monitor integrates itself. When the per-CPU figures are combined, each CPU's stall time is weighted by how long that CPU was non-idle, so an idle CPU does not dilute pressure on a busy one and a machine with one thrashing core out of sixty-four still reports meaningful contention.

The per-CPU updates happen on every relevant scheduler event—enqueue, dequeue, context switch, entry to and exit from a memory stall—through psi_task_change(), which publishes the change under a per-CPU sequence counter and then walks the task's cgroup and every one of its ancestors, updating each level's struct psi_group in turn. A stall is therefore charged to the whole chain at once: a parent cgroup's pressure reflects all of its descendants, and the root group is the system-wide figure behind /proc/pressure. The price is that the cost of each update grows with nesting depth, which is why an administrator can switch PSI off for an individual cgroup by writing 0 to its cgroup.pressure file (Linux 6.1): its pressure files disappear and the kernel stops accumulating stall time for that level, while accounting continues for its ancestors. Booting with cgroup_disable=pressure does the same for every cgroup at once, keeping only the system-wide files.

PSI is exposed both system-wide and per cgroup. The files /proc/pressure/cpu, /proc/pressure/memory, and /proc/pressure/io give whole-system pressure, while each cgroup carries cpu.pressure, memory.pressure, and io.pressure files reporting the same metrics for just that cgroup's tasks—so an orchestrator can attribute contention to the exact workload causing it. A fourth resource, IRQ pressure (Linux 6.1), appears as /proc/pressure/irq and a per-cgroup irq.pressure on kernels built with CONFIG_IRQ_TIME_ACCOUNTING. It charges a cgroup for the time its running task lost to hard- and soft-interrupt processing (Chapter 4) on that CPU (psi_account_irqtime()), and it reports only a full line: while an interrupt handler runs, the interrupted task makes no progress at all, so there is no “some” case to distinguish. It is the metric that exposes a workload slowed not by its own demands but by a network card or storage device flooding its CPU with interrupts. Table 25-9 lists the metrics and where they appear.

Triggers and Notifications

Polling a pressure file periodically would miss brief spikes and waste CPU, so PSI adds a trigger mechanism for event-driven reaction. A program writes a threshold to a pressure file—“tell me when stall time exceeds X microseconds within a Y-microsecond window”—which creates a struct psi_trigger (kernel/sched/psi.c), and then blocks in poll (or epoll) on the file descriptor. The kernel, which is already accumulating stall times, wakes the waiter the moment the threshold is crossed, so the program reacts to pressure in milliseconds rather than at the next poll interval. This is the foundation of userspace out-of-memory managers such as oomd and systemd-oomd: rather than waiting for the kernel OOM killer to fire when memory is already exhausted, they watch memory.pressure triggers and shed load before the machine thrashes, choosing which workload to stop by policy instead of leaving it to the kernel's heuristics. PSI thus closes the loop that the controllers open: cgroups impose the limits, and PSI reports, precisely and promptly, when those limits are starting to hurt.

The trigger's two numbers—a threshold and a window—give it its precision. The window may be up to ten seconds, the threshold must be positive and no larger than the window, and the meaning is “wake me if stall time reaches the threshold within any window of that length.” Crucially, triggers are not evaluated on the slow two-second cadence of the average files; the kernel monitors armed triggers on a faster internal poll timer whose period is one-tenth of the smallest window in use (kernel/sched/psi.c), so a program watching a half-second window learns of a spike within a fraction of a second. That fast path is driven by a per-group kernel thread, psimon, running at a low SCHED_FIFO real-time priority (Chapter 7) so that it can sample stall times even when the machine is under exactly the pressure it is meant to report. Because a trigger can be created on a cgroup's own memory.pressure just as easily as on the system-wide file, a supervisor can arm a different threshold for each workload—tight for a latency-critical service, loose for a batch job—and be notified about exactly the one that is suffering. It is this combination of per-workload scope and sub-second latency that lets modern userspace act on contention as a first-class signal rather than a statistic read after the fact.

A real-time thread is not something an arbitrary user should be able to spawn, so since Linux 6.5 PSI distinguishes privileged from unprivileged trigger writers. The /proc/pressure files are world-writable, and psi_trigger_create() checks CAP_SYS_RESOURCE in the credentials of whoever opened the file—so a privileged supervisor can open it and hand the descriptor to a less-privileged helper. A privileged trigger joins the psimon-driven fast path. An unprivileged one is accepted only if its window is a whole multiple of two seconds, and it is then evaluated by the ordinary two-second averaging work instead, so ordinary users get pressure notifications without being able to create real-time load. Either way the contract with userspace is the same and deliberately narrow. Each open file descriptor holds at most one trigger (a second write fails with EBUSY); closing the descriptor destroys it. A crossed threshold is reported as EPOLLPRI, and events are rate-limited to at most one per window: a stall that keeps growing does not produce a storm of wakeups, but one that crosses the threshold again during the quiet period is remembered and delivered once the window has elapsed, so no breach is silently lost. If the cgroup is removed while a program is polling its pressure file, the poll returns EPOLLERR, telling a supervisor to stop watching a workload that no longer exists.

The Anatomy of a Container

With namespaces and cgroups in hand, we can finally answer what a container is. It is not a kernel object but a recipe: a particular combination of the primitives this chapter has described, assembled by a user-space runtime. This closing section walks through what that runtime actually does to start a container, and then looks honestly at where the isolation's limits—and its risks— lie.

Because the recipe lives in user space, it has been standardized there rather than in the kernel. The Open Container Initiative (OCI) specifications define an image format—a stack of filesystem layers plus a JSON configuration listing the namespaces, cgroup limits, capabilities, and seccomp profile to apply—so that any compliant runtime can run any compliant image. This is why the same image runs under Docker, Podman, and Kubernetes: those tools differ in how they build and orchestrate containers, but underneath they drive a small low-level runtime (most commonly runc) that turns the OCI configuration into exactly the kernel calls of this chapter. The kernel, true to form, knows nothing of any of this; it sees only a process that unshared some namespaces, joined a cgroup, and dropped some privileges.

What a Container Runtime Does

When a runtime such as runc (the low-level engine under Docker and Kubernetes) starts a container, it performs, in essence, a carefully ordered sequence of the operations from this chapter. It creates a new user namespace and writes its UID/GID maps, so the rest of the setup can proceed unprivileged (§3). It creates fresh mount, PID, network, IPC, UTS, and often cgroup and time namespaces (§2), giving the container its private view. Inside the mount namespace it assembles the container's root filesystem and calls pivot_root into it, so the container sees only its own files. It creates a cgroup for the container and writes the configured memory.max, cpu.max, pids.max, and the rest (§5–§6), then moves the container's first process into it. It drops capabilities to the minimal set the workload needs (§3.2) and installs a seccomp filter (Chapter 20) restricting which system calls the container may make. Only then does it exec the container's actual program as PID 1 of its new PID namespace. Figure 25-8 shows the layers that result.

The order of those steps is not arbitrary; each depends on the last. The user namespace comes first because it is what grants the capabilities the remaining setup needs. The other namespaces come next, and only inside the new mount namespace can the runtime safely assemble the root filesystem—typically an overlay mount (Chapter 12) stacking the image's read-only layers under a writable one—and pivot_root into it. pivot_root itself imposes two preconditions that shape the runtime's first mount operations. The new root must be a mount point, so the runtime bind-mounts the root filesystem onto itself. And the call fails with EINVAL if the mounts involved have shared propagation (path_pivot_root() in fs/namespace.c), so the runtime first remounts the whole inherited tree recursively private or slave (§4.2). That also guarantees that nothing it mounts inside the container leaks back into the host's mount table. It then mounts a fresh /proc (which, as §4.1 explained, must be created after the fork into the new PID namespace to show only the container's processes), a restricted /dev, and /sys, and masks a handful of dangerous paths such as /proc/sysrq-trigger so the container cannot reach them. The masks are ordinary bind mounts: an empty file or /dev/null mounted over each sensitive file, and read-only bind mounts over trees such as /proc/sys.

The kernel adds its own rules about what a container may mount. A proc or sysfs instance could reveal far more than the runtime intended, so when the caller's mount namespace is owned by a non-initial user namespace, mount_too_revealing() (fs/namespace.c) allows a new instance only if one is already fully visible in that namespace. That means no locked mount covers anything but an empty directory, and the new mount is no less restrictive than the existing one in its locked read-only and access-time settings. The rule explains a common surprise. Once a runtime has masked paths in a container's /proc, a rootless container engine running inside it, which creates its own user namespace, cannot mount a fresh /proc for a nested PID namespace, because every /proc it can see has files covered. Nested container setups therefore often run with an unmasked /proc. The covering mounts count as locked because whenever a mount namespace is copied into a less-privileged user namespace, the kernel marks the inherited mounts MNT_LOCKED and locks their read-only, nosuid, nodev, and noexec flags (lock_mnt_tree()). A process that is “root” only inside its user namespace cannot unmount or loosen a mount it inherited from a more privileged namespace to uncover what lies beneath.

Networking is wired up—often by a separate plugin, the CNI plugins of Kubernetes being the common case—by moving one end of a veth pair into the new network namespace. Since Linux 6.7, performance-sensitive deployments can use netkit devices (drivers/net/netkit.c) instead: a paired virtual device like veth, but its transmit routine runs a BPF program attached through the multi-program BPF framework. That program can redirect a packet leaving the container straight to the physical device (NETKIT_REDIRECT), skipping the per-CPU backlog re-queue that a packet crossing a veth pair normally takes. A rootless container, which cannot attach anything to the host's own network namespace, usually gets connectivity from a user-space network stack such as slirp4netns or pasta, which carries the container's traffic over ordinary host sockets. Dropping capabilities and installing the seccomp filter come last, just before exec, so that all the privileged setup happens while the runtime still holds privilege and the container's own code begins life already confined. A no_new_privs bit is set along the way so that no later exec of a setuid binary can regain what was dropped. The bit is also a kernel requirement: seccomp refuses to install a filter with EACCES unless the caller either has no_new_privs set or holds CAP_SYS_ADMIN in its user namespace (kernel/seccomp.c). Otherwise a filter could make a setuid program misbehave by failing chosen system calls under it.

Two additions to clone3() (§2.2) let a runtime close races that older runtimes had to tolerate. With CLONE_INTO_CGROUP (Linux 5.7), the runtime passes a file descriptor for the container's cgroup directory and the child is created already inside it. cgroup_css_set_fork() (kernel/cgroup/cgroup.c) checks the same write permissions a cgroup.procs migration would and chooses the child's css_set before the task becomes visible, so there is no window in which the child runs, allocates memory, or forks while still charged to the runtime's cgroup. With CLONE_PIDFD the runtime receives a pidfd for the container's PID 1 at the moment of creation. It can then wait on, signal, and later setns() into the container through a handle that cannot be redirected to an unrelated process if the PID number is reused.

Security and the Attack Surface

Because a container shares the host kernel, its isolation is only as strong as that kernel's enforcement—and this is the fundamental difference from a virtual machine. A VM escape must defeat the hardware virtualization boundary; a container escape need only find one kernel bug reachable from inside the container. The attack surface is the entire system-call interface, which is why the seccomp filter of Chapter 20 matters so much in practice: by forbidding the system calls a workload does not need, it removes large swaths of kernel code from the container's reach, shrinking the surface where a bug could be exploited. Dropping unnecessary capabilities does the same for privileged operations. A flat deny-list is sometimes too blunt, because some workloads legitimately need an operation a container must not perform directly, such as creating a device node or mounting a particular filesystem. For these, a filter can return SECCOMP_RET_USER_NOTIF (Linux 5.0, Chapter 20). The system call is suspended and handed to a supervisor process over a notification file descriptor. The supervisor examines the arguments, performs a safe, vetted version of the operation on the container's behalf, and can even install a file descriptor into the container (SECCOMP_IOCTL_NOTIF_ADDFD) before supplying the result. Container managers such as LXD use this to emulate selected privileged calls without granting the privilege itself.

In practice, then, real containers are hardened in depth: namespaces and cgroups are only the first two of several layers. A Linux Security Module—SELinux or AppArmor—confines what files and operations the container's processes may touch even within their namespaces, a read-only root filesystem keeps a compromised process from modifying its own image, and no_new_privs blocks privilege regain. Because the kernel stacks LSMs, these major policies can be combined with Landlock (Chapter 20). Landlock is an unprivileged LSM that lets a process, or the runtime acting for it, restrict its own filesystem and network access further, with a ruleset that only ever narrows and is inherited across fork and exec. The most security-conscious deployments go further and run rootless: the entire container, runtime included, runs as an unprivileged user via a user namespace, so even a total escape yields only that unprivileged user's authority on the host. Several kernel changes made this practical. Overlayfs has been mountable inside a user namespace since Linux 5.11 (FS_USERNS_MOUNT in fs/overlayfs/super.c), so rootless engines no longer need the slower FUSE-based fuse-overlayfs. Idmapped mounts (§3.1) let a rootless container share a host volume with file ownership translated correctly instead of chown-ing it. And cgroup delegation (§6.2) lets the unprivileged user manage the container's resource limits. Each layer is independently imperfect, but an attacker must defeat all of them at once, which is what makes the composition defensible even though no single primitive is a hard boundary.

Where that is not enough, the industry reaches back up the isolation spectrum of §1.1. Sandboxes such as gVisor interpose a user-space kernel that services the container's system calls itself, so the container almost never touches the host kernel directly; lightweight virtual machines such as Kata Containers and Firecracker wrap each container in a fast-booting VM, buying a hardware-enforced boundary at a fraction of a traditional VM's cost. Both trade some of the container's density and speed for isolation nearer a virtual machine's—a reminder that “container” names a point on a continuum, not a fixed guarantee. The far end of that continuum is the confidential container. A lightweight VM of the Kata kind runs under AMD SEV-SNP or Intel TDX, so its memory is encrypted even against the host kernel. That is where the misc controller's limits on SEV ASIDs and TDX HKIDs (§6.3) come in: they ration the scarce hardware slots such guests consume.

The user namespace deserves a final, honest word. It is what makes unprivileged containers possible, and it is also, historically, one of the larger sources of Linux privilege-escalation bugs—because it lets an unprivileged user reach code paths (in filesystems, networking, and elsewhere) that once assumed their caller was already privileged. That tension is real: the same feature that lets an ordinary user safely run a container also exposes kernel code that was never written with hostile unprivileged callers in mind. The mainline kernel gives administrators two levers. The user.max_user_namespaces limit (§3.2) can be lowered, or set to zero to forbid new user namespaces entirely. And since Linux 6.1, create_user_ns() calls the userns_create LSM hook (security_create_user_ns()), so SELinux (through the user_namespace { create } permission), AppArmor profiles, or a BPF LSM program can decide per process who may create one. Distributions layer their own policy on top. Debian's long-standing kernel.unprivileged_userns_clone sysctl, for example, is a distribution patch, not a mainline interface, and the kernel continues to harden the code paths themselves. The larger point closes the chapter: Linux's containers are not a security boundary of the same kind as a virtual machine, but a set of composable isolation primitives whose strength is exactly the strength of the one kernel beneath them—which is why the subsystems of this entire book, and their correctness, are ultimately what a container's isolation rests on.

Summary

This chapter described how Linux 7.0 isolates and limits processes to build containers, and stressed the fact that the kernel has no container object at all. Isolation rests on two orthogonal mechanisms. Namespaces control what a process can see. Linux has eight types: mount, UTS, IPC, PID, network, user, cgroup, and time. Six of them are reached through the shared, reference-counted struct nsproxy, while the user namespace hangs off the task's credentials and the active PID namespace off its struct pid. Namespaces are created and joined with clone, unshare, and setns, the last committing a whole set all-or-nothing. Each one embeds a struct ns_common whose proc_ns_operations let one body of generic code serve all eight types, and whose split memory and active reference counts decide how long it lives and whether it can still be found. Through nsfs every namespace is a first-class object: a link under /proc/<pid>/ns, an fd that pins it, a bind mount that keeps it alive with no member process, and a stable 64-bit ID that the NS_GET_* ioctls and the listns system call report.

The user namespace is the keystone. By mapping UIDs and GIDs through a write-once uid_map and gid_map, it lets an unprivileged user become root inside a container (“fake root”) without gaining any privilege on the host. The map-writing rules, the setgroups guard, and the CAP_SETFCAP check on a root mapping keep that grant from leaking, and idmapped mounts apply the same translation to a single mount. Its capabilities are full but relative: ns_capable checks them against the user namespace that owns the resource, so they never reach an ancestor. The PID namespace gives each container its own numbering, its own pid_max, and an init whose death empties the namespace, all implemented by a struct pid that carries one number per nesting level. The network, mount, IPC, UTS, and time namespaces each virtualize their own table, from a whole network stack down to a pair of clock offsets, and the new mount API lets a runtime build a detached mount tree and graft it into place in one step.

Control groups control what a process can use. Cgroup v2 arranges all processes in a single unified hierarchy of kernfs directories, links each task through a shared, deduplicated css_set to the per-controller state of its cgroup, migrates tasks with the same prepare-then-commit discipline, and distributes resources top-down under the no-internal-process rule. It also makes the cgroup the unit of whole-group lifecycle operations, cgroup.freeze and cgroup.kill. Its controllers (cpu, memory, io, pids, cpuset, rdma, misc, dmem, and more) share, cap, or protect each resource through weights, limits, and protections such as cpu.weight, memory.max, and memory.low. Cpuset partitions hand CPUs to a workload outright, and delegation lets an unprivileged container manage its own subtree safely. Resources that drivers own are charged by the driver itself. RDMA objects and confidential-VM key slots can only be refused, but GPU memory under the dmem controller can be reclaimed: a charge over dmem.max makes TTM evict buffers from the over-limit subtree, sparing those protected by dmem.min and dmem.low. Pressure Stall Information completes the picture. It reports how much time work is lost to CPU, memory, I/O, and interrupt contention, charges each stall to every ancestor cgroup, and wakes userspace managers such as systemd-oomd as soon as a trigger's threshold is crossed.

A container, finally, is the composition of all these: namespaces, a cgroup, dropped capabilities, no_new_privs, and a seccomp filter, described by the OCI specifications and applied by a user-space runtime in a deliberate order. The kernel enforces its own rules on that composition. pivot_root refuses shared propagation, inherited mounts are locked, a fresh proc may be mounted only where one is already fully visible, and clone3 can place a child directly into its cgroup. Because a container shares the host kernel, it is hardened in depth with security modules, Landlock, seccomp user notification, read-only images, and rootless operation. Administrators can limit or police user-namespace creation itself, and where even that is too weak a boundary, user-space kernels and lightweight or confidential virtual machines sit further up the isolation spectrum. But a container's isolation is ultimately only as strong as the single kernel beneath it, which is why everything else in this book, and its correctness, underlies the container abstraction that so much of modern computing now runs on.
