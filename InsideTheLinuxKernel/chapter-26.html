For its entire history the Linux kernel has been written in C, with assembly for the few places C cannot reach. C gave the kernel direct control over memory and hardware and a simple, predictable mapping to machine code, and those virtues are why it endures. But they come with a standing liability: C does nothing to stop a program from reading past the end of an array, using memory after it has been freed, or dereferencing a dangling pointer, and in a codebase of tens of millions of lines maintained by thousands of people, those mistakes are made constantly. Study after study of serious kernel vulnerabilities finds that around two-thirds of them are memory-safety bugs—exactly the class of error the language cannot catch.

Linux 7.0 can be built with a second language that was designed to catch them. Rust is a systems language with performance and low-level control comparable to C, but with a compiler that proves, before the code runs, that safe code cannot cause a memory-safety or data-race bug. Bringing such a language into the most safety-critical C program in the world is a large undertaking, and it is deliberately incremental: Rust in Linux is for new code—drivers and modules—not a rewrite of the core, and it interoperates with the existing C through a carefully designed boundary. This chapter explains how that works: why Rust was added and on what terms, how Rust source is built and linked into a C kernel, the safe/unsafe boundary and the kernel crate that spans it, the error-handling and allocation models that differ sharply from ordinary Rust, the ownership and locking abstractions that make kernel objects safe to share, the macros that declare a module, three of the kernel's sample drivers read closely, and finally the real Rust drivers already merged. Rust arrived in Linux 6.1 as an explicitly labeled experiment; during the 7.0 development cycle the kernel's maintainers declared that experiment concluded, so this final chapter describes not a trial but a permanent, if still young, part of how the kernel is built.

Why Rust in the Kernel

Adding a second language to a project as large and conservative as the kernel is not done lightly, and understanding the decision is the best way into the subject. This section makes the case that motivated it—the persistent cost of memory-safety bugs—and then draws the careful boundaries the kernel community placed around Rust so that adopting it would not destabilize the C kernel it joins.

It helps to appreciate how unusual this step is. For more than three decades the kernel was written in exactly one language—C, with small pockets of architecture-specific assembly—and that uniformity is itself a feature: one language means one mental model, one set of idioms, one toolchain, and a contributor base that can read and modify any part of the tree. Introducing a second general-purpose language dilutes that uniformity and imposes real costs: a heavier build dependency, a new class of reviewer expertise, and the friction of two communities with different habits maintaining one code base. The kernel community adopted Rust not because these costs are small but because the problem Rust solves is large enough to justify them. The rest of this section explains that problem and the guardrails that make the trade-off worthwhile.

The Case for a Second Language

The argument for Rust rests on a single, well-measured fact: most severe kernel security bugs are memory-safety bugs. Use-after-free, buffer overflow, and data-race defects—not logic errors—dominate the serious CVEs, and they persist decade after decade despite better tooling, more review, and static analyzers, because C offers the programmer no help in avoiding them. A pointer in C carries no information about whether it is still valid, who owns the memory it points to, or whether another thread is touching it at the same moment; keeping all of that correct is left entirely to human discipline, and at kernel scale human discipline statistically fails.

Rust attacks this at the language level. Its ownership system tracks, at compile time, exactly one owner for every value and a set of rules about borrowing references to it: you may have many shared read-only references or one exclusive mutable reference, never both at once, and no reference may outlive the value it points to. The compiler's borrow checker enforces these rules and rejects code that violates them, which means an entire catalogue of bugs—use-after-free, double-free, data races on shared memory, iterator invalidation—becomes a compile error rather than a runtime crash or an exploit. Crucially, this checking costs nothing at run time: the same machine code a careful C programmer would write is produced, but with a proof attached that the dangerous mistakes were not made. For a kernel, whose bugs are security vulnerabilities in the most privileged code on the machine, moving that class of error from runtime to compile time is a decisive advantage. It is worth being precise about why this class of bug has proven so stubborn in C. The problem is not that kernel developers are careless; it is that C's type system simply does not encode the information needed to catch these mistakes. Consider a freed object: after kfree(p), the pointer p is still a perfectly valid-looking value, and nothing in the language stops a second kfree(p) (a double-free) or a later p->field access (a use-after-free). Whether either is a bug depends on program-wide reasoning about every path that might reach that line—reasoning that no compiler performs and that grows exponentially harder as call graphs deepen and concurrency is added. Locking is the same story: the rule “hold this spinlock before touching that field” lives only in comments and reviewers' memories, never in the types, so the compiler cannot notice when a new code path forgets it. Decades of sanitizers, fuzzers, and static analyzers have chipped away at the symptoms, but they are all after-the-fact detectors that find bugs already written; none of them change the underlying fact that the language permits the mistake in the first place.

Rust's contribution is to make the compiler a before-the-fact enforcer. The ownership rules described above are not a lint that can be ignored or a runtime check that can be disabled—they are part of what it means for a program to type-check, so a use-after-free or a data race in safe Rust is as impossible to compile as a type mismatch is in C. Two properties make this practical for a kernel. First, the checks are zero-cost: ownership and borrowing are erased after compilation, leaving machine code with no garbage collector, no reference-count churn, and no runtime that a C caller would have to accommodate—the reason Rust can sit in the same address space and the same call chains as C without penalty. This is precisely what rules out the obvious alternatives: a garbage-collected language cannot run in interrupt context or hold raw locks, and C++ offers richer abstractions but none of Rust's compile-time aliasing guarantees. Second, Rust provides a controlled escape hatch—the unsafe keyword—for the small fraction of operations the compiler cannot prove sound, such as dereferencing a raw pointer handed over from C. Far from weakening the model, unsafe is what makes it usable in a kernel: it concentrates the dangerous operations into small, clearly marked, individually audited regions, so that the safe majority of the code carries the compiler's full guarantee and reviewers can focus their scrutiny where it is actually needed. The whole architecture of Figure 26-1 is built to keep that unsafe surface as small and as reviewed as possible.

“Zero-cost” needs one qualification, because not every guarantee can be settled at compile time. Ownership and borrowing are checked entirely by the compiler, but whether an array index is in range, or whether an addition overflows, usually depends on run-time values. For these Rust inserts cheap run-time checks: indexing a slice is bounds-checked, and integer arithmetic is overflow-checked when CONFIG_RUST_OVERFLOW_CHECKS is set, which it is by default. A failed check is a Rust panic, and the kernel defines what that means. Rust is compiled with -Cpanic=abort, so there is no unwinding, and the crate's panic handler (rust/kernel/lib.rs) prints the message with pr_emerg! and calls BUG(). An out-of-bounds write that in C would silently corrupt a neighboring object becomes an immediate, attributable oops at the faulting line, which is far easier to diagnose and much harder to exploit. A panic is still a crash, though, and the kernel crate steers driver code away from it: it prefers APIs that return Option or Result (checked indexing with get, checked arithmetic, fallible allocation) so a bad value becomes an error the caller handles (§4). Where a condition can be proven at compile time instead, build_assert! makes a violation a build failure.

The data-race guarantee also has a kernel-specific meaning. Ordinary Rust defines atomics with the C++ memory model, but kernel Rust shares memory with C code that follows the Linux Kernel Memory Model (LKMM, specified in tools/memory-model/). Mixing two memory models on the same variables would be unsound, so the crate's atomics (rust/kernel/sync/atomic.rs) follow LKMM semantics and document LKMM as the only memory model for Rust in the kernel, telling code to avoid Rust's own atomics. A Rust driver and the C subsystem beneath it therefore agree on what every barrier and ordered access means, and the compile-time ban on unsynchronized sharing sits on top of the same concurrency rules Chapter 5 describes for C.

What Rust for Linux Is and Is Not

The effort that brought Rust into the kernel, called Rust for Linux, was merged in Linux 6.1 at the end of 2022, and its scope was deliberately modest. Rust in the kernel is not a rewrite: the tens of millions of lines of C are not going anywhere, and no core subsystem—the scheduler, the memory manager, the VFS—has been reimplemented. What Rust is for is new leaf code, principally device drivers and self-contained modules, where the memory-safety benefit is highest and the blast radius of adopting a new language is smallest. A driver is a natural unit to write in a new language: it has a well-defined interface to the rest of the kernel, it is the kind of code most often written by less-specialized developers, and drivers are, historically, where a large share of kernel bugs live.

How modestly it began, and how far it has come, shows that scope in practice. The project grew out of tree from 2020, and what Linux 6.1 merged was infrastructure only. The kernel crate was six files (allocator, errors, printing, strings, the prelude, and the crate root), there was a single rust_minimal sample, and drivers/ held no Rust at all. Real users followed one release at a time:

  • 6.8: the first Rust driver, the AX88796B network PHY driver.
  • 6.11: the rnull null block driver.
  • 6.12: the DRM panic QR-code encoder and the QT2025 network PHY driver.
  • 6.15: the Nova GPU core driver.
  • 6.16: a Rust cpufreq-dt driver and the Nova DRM driver.
  • 6.18: the Rust Binder driver and the Tyr GPU driver.
  • 6.19: the T-Head TH1520 PWM driver.

By 7.0.12 the crate under rust/kernel/ has grown to about 150 files and nearly 48,000 lines. The growth has followed the leaf-first plan: each abstraction arrived to serve a driver that needed it, and no core subsystem was rewritten along the way (§8 surveys the result).

The choice of drivers as the entry point is strategic as well as technical. A driver sits at the edge of the kernel, talking to hardware on one side and a stable subsystem interface on the other, so a Rust driver can be added, built, and loaded without any C code needing to change and without the rest of the kernel needing to understand Rust at all—the object files link together and the module loads like any other. This means the two languages genuinely coexist: a running kernel can contain a Rust driver calling a C subsystem which in turn calls a C driver, all in one address space, with the Rust portions carrying the compiler's safety guarantee and the C portions unchanged. Rust for Linux was not conceived as a beachhead for replacing C but as a way to write the next driver, and then the one after that, in a safer language while the existing kernel keeps working exactly as before.

Several deliberate constraints keep the effort contained. Rust support is optional, gated behind a Kconfig option (§2.1), so a kernel can be built with no Rust at all; a distribution adopts it only when it chooses to. Rust code is meant to reach C only through the kernel crate's reviewed abstractions, not by calling C ad hoc. The safe/unsafe boundary of Figure 26-1 is enforced by a written rule, by code review, and in part by the compiler. The written rule is in Documentation/rust/general-information.rst: leaf modules such as drivers should not use the C bindings directly. It is a policy rather than a technical barrier, because the raw bindings remain reachable as kernel::bindings. The compiler supplies the rest: all kernel Rust is built with -Dunsafe_op_in_unsafe_fn, so even inside an unsafe function each unsafe operation needs its own explicit block, and a make CLIPPY=1 build flags any unsafe block that lacks a // SAFETY: justification (§3.1). And for its first years the whole facility was officially an experiment, a label retired only in the 7.0 development cycle; even now some combinations (mixed GCC-and-LLVM builds, for one) remain young, and the crate keeps evolving release to release as more of the kernel's C APIs gain safe Rust wrappers. The right way to read this chapter, then, is as a description of a young but real capability: not the future of the whole kernel, but a genuine, shipping way to write parts of it in a language that makes an entire category of its worst bugs impossible.

It is equally important to be clear about what Rust for Linux is not trying to be, because the non-goals shape the design as much as the goals. It is not an attempt to make the whole kernel memory-safe: the C core remains, with all its existing behavior and all its existing bugs, and a Rust driver that calls into a buggy C subsystem inherits that subsystem's flaws just as a C driver would—Rust's guarantee covers the Rust code, not the C it calls. It is not a promise that Rust code cannot crash: safe Rust rules out memory-safety bugs and data races, but logic errors, deadlocks, and deliberate unsafe mistakes are all still possible, so Rust raises the floor rather than removing the need for care. And it is not a performance play; the goal is to match C, not beat it, and any Rust abstraction that imposed runtime overhead a C kernel programmer would not accept would be rejected on exactly those grounds. Understanding these limits is what keeps expectations honest: Rust removes one large, well-defined class of the kernel's most dangerous bugs from the new code that opts into it, and it is precisely because that claim is narrow that it can be kept.

Building Rust Code

Before any Rust can run in the kernel, the build system has to turn .rs source into object files that link alongside the C, and it has to teach Rust about the thousands of C types and functions it must call. This section covers the toolchain and configuration that gate Rust support, and then the pipeline—rustc, bindgen, and the linker—that produces a mixed C-and-Rust kernel.

Two facts shape everything that follows. First, Rust is not part of the kernel's traditional toolchain: where a C build needs only a C compiler and binutils, a Rust build additionally needs a Rust compiler and a binding generator, so the build system must detect them, check their versions, and refuse to proceed if they are missing or wrong. Second, Rust does not natively understand the kernel's C interfaces, so something must translate the C headers into a form Rust can call—and, going the other way, present the Rust code to the C linker as though it were just more object files. The build machinery in rust/ exists to solve exactly these two problems, and the two subsections below take them in turn.

A third requirement is less obvious and comes from mixing two compilers in one image. Wherever the kernel depends on how code is generated, rustc must produce exactly what the C compiler does. That covers keeping floating-point and SIMD registers out of kernel code, the retpoline and return-thunk mitigations, the type hashes that control-flow integrity checks on indirect calls, and the special tables that static keys and WARN rely on. Much of the machinery below, from the per-architecture target description to the list of options RUST refuses to coexist with, exists to keep the two compilers in agreement.

The Toolchain and Kconfig

Rust support is off unless the machine building the kernel has the right tools, and the build checks for them explicitly. The check is driven by a script, scripts/rust_is_available.sh, invoked by the make rustavailable target; it verifies that a Rust compiler (rustc), the binding generator (bindgen), and a compatible libclang are present and meet minimum versions. Only if they do does the Kconfig symbol RUST_IS_AVAILABLE (init/Kconfig) become true, which in turn is what allows the main RUST option to be enabled. A further gate is per-architecture: an architecture advertises Rust support by selecting HAVE_RUST (arch/Kconfig), and in Linux 7.0 that set is x86-64, little-endian arm64, little-endian ARMv7, 64-bit RISC-V (only when the C side is also built with Clang), LoongArch, and the user-mode-Linux port. The RUST option also carries its own list of incompatibilities in init/Kconfig: it cannot be combined with structure-layout randomization (RANDSTRUCT), since Rust code built against bindgen's view of a structure could disagree with the shuffled layout the C compiler actually emits, and it permits MODVERSIONS only when symbol CRCs are computed from debug information (GENDWARFKSYMS), because the older tool that computes them by parsing C source cannot read Rust. The availability check does more than compare version numbers. scripts/rust_is_available.sh first confirms that the RUSTC, BINDGEN, and CC variables name programs that exist, then compares the rustc and bindgen versions against the minimums in scripts/min-tool-version.sh. It next asks bindgen which libclang it loaded and checks that version as well, since bindgen parses C through libclang. It warns about bindgen releases with known bugs (0.66.0 and 0.66.1, and anything before 0.69.5 paired with libclang 19.1 or later), and, when the C compiler is itself Clang, about a mismatch between that compiler's version and the libclang version. Last, it checks that the Rust toolchain ships the source of the core library, because the kernel compiles core itself (§2.2) rather than linking a prebuilt copy. Kconfig computes RUST_IS_AVAILABLE by running the script during configuration, which is why a silently missing RUST option is best diagnosed with make rustavailable: the script then prints the reason it rejected the toolchain.

Beyond RANDSTRUCT and MODVERSIONS, the RUST entry in 7.0.12 lists conflicts that all come from code generation the two compilers must agree on. Type-based control-flow integrity (CFI) is allowed only if rustc can normalize integer types the way Clang does when it hashes a function's signature, and enabling both selects CFI_ICALL_NORMALIZE_INTEGERS, so an indirect call from C into Rust, or back, checks against the same hash. The padding some x86 mitigations place before every function (CALL_PADDING) needs rustc 1.81, and return thunks (MITIGATION_RETHUNK) combined with KASAN need rustc 1.83. Software tag-based KASAN (KASAN_SW_TAGS) is excluded outright, and BTF debug information (DEBUG_INFO_BTF) is allowed only with a pahole that can skip Rust compilation units, and only without LTO. Finally, when MODVERSIONS is on, RUST selects EXTENDED_MODVERSIONS: the classic version table stores each symbol name in a fixed 56-byte field, and Rust's mangled names (§2.2) routinely exceed it.

The per-architecture gate deserves a closer look, because it reflects how much of Rust support is architecture-specific even though the language is not. Selecting HAVE_RUST is a promise that several pieces are in place for that architecture: the target the Rust compiler is asked to build for (its calling convention, pointer width, and ABI must match what the C kernel expects), any architecture-specific flags Rust code must be compiled with, and confirmation that the resulting objects link correctly into that architecture's kernel image. The architectures arrived one at a time. In 6.1 x86-64 was the only one; user-mode Linux followed in 6.3, LoongArch in 6.8, arm64 in 6.9, RISC-V in 6.10, and 32-bit ARMv7 in 6.15. Both architectures this book follows, x86-64 and arm64, are now fully maintained, but a given driver builds only on the architectures whose Rust support—and whose safe abstractions—cover what it needs. Documentation/rust/arch-support.rst records each architecture's support level and constraints. Most of the constraints exist because rustc generates code through LLVM: it can target only what LLVM supports, and bindgen depends on libclang. For the same reason the documentation recommends building the whole kernel with make LLVM=1. Pairing Rust with a GCC-built C kernel works for some configurations but is described as very experimental, and RISC-V does not offer it at all.

The target is the most concrete part of that promise. Most architectures name one of rustc's built-in bare-metal targets in their Makefile: aarch64-unknown-none-softfloat on arm64 (with rustc older than 1.85, aarch64-unknown-none with NEON disabled), riscv64imac-unknown-none-elf, loongarch64-unknown-none-softfloat, and arm-unknown-linux-gnueabi. Each keeps floating-point and SIMD registers out of generated code, as the kernel requires. x86-64 has no suitable built-in target, so the build creates one. A host program, scripts/generate_rust_target.rs, reads the kernel configuration and writes scripts/target.json, which selects soft-float and disables MMX, and adds the retpoline and straight-line-speculation hardening features when MITIGATION_RETPOLINE or MITIGATION_SLS is set. arch/x86/Makefile then adds the remaining rules: SSE and AVX disabled, no red zone, IBT branch protection, and return thunks. The result is Rust code that obeys the same code-generation rules as the C compiled beside it.

One requirement surprises newcomers who know ordinary Rust: the kernel crate uses language and library features that are not yet stable, so not every compiler, used in the ordinary way, can build it. The tree therefore sets a minimum—in Linux 7.0, rustc 1.78.0 and bindgen 0.65.1, recorded in scripts/min-tool-version.sh—and the top-level Makefile exports RUSTC_BOOTSTRAP=1, which lets a stable release compiler accept those unstable features. Releases before 6.11 pinned a single exact compiler version; since 6.11 the kernel takes the minimum and any newer stable release, and the rustavailable check fails only when a tool is missing or too old. The RUSTC_HAS_* flags in Table 26-1 are how the tree copes with that span without forking: rather than demanding one exact version, the build probes what the installed compiler can do and enables the corresponding code paths, so the kernel supports a range of toolchains while still using newer features where available. RUSTC_HAS_COERCE_POINTEE, for example, is true from rustc 1.84 and lets the kernel's smart pointers use the language's own coercion support in place of two older unstable features.

RUSTC_BOOTSTRAP=1 on its own would let any crate enable any unstable feature, so the build fences it. The crates in rust/ may use what they need, but every other Rust object—each driver, sample, and out-of-tree module—is compiled with -Zallow-features set to the rust_allowed_features list in scripts/Makefile.build. In 7.0.12 the list holds nine features, among them asm_goto, arbitrary_self_types, and used_with_arg, and a driver that asks for anything else fails to compile. The comment above the list records that seven of the nine have since become stable in newer compilers; they remain on the list only because the 1.78 minimum predates them. The list is meant to shrink to nothing as the minimum rises.

A few behaviors are configurable. The “Rust hacking” menu in lib/Kconfig.debug offers RUST_DEBUG_ASSERTIONS, which compiles in rustc's debug assertions for all Rust code including core, and RUST_OVERFLOW_CHECKS, on by default, which makes integer overflow panic (§1.1). RUST_BUILD_ASSERT_ALLOW is an escape hatch that turns an unprovable build_assert! from a link failure into a runtime check (§2.2 shows the mechanism), and RUST_KERNEL_DOCTESTS builds the examples in the kernel crate's documentation as KUnit tests, so the documented examples are run as tests. Everything else is fixed in KBUILD_RUSTFLAGS in the top-level Makefile: panics abort, there are no unwind tables, each crate is a single codegen unit, the relocation model is static, symbols use Rust's v0 mangling, and the optimization level follows the C side's choice between CC_OPTIMIZE_FOR_PERFORMANCE (-Copt-level=2) and CC_OPTIMIZE_FOR_SIZE (-Copt-level=s).

The final entry in Table 26-1, make rust-analyzer, addresses a practical concern rather than the build itself: because kernel Rust is no_std, built against generated bindings, and compiled with an unusual set of flags, an ordinary IDE cannot make sense of it out of the box. The target emits a rust-project.json describing every crate, its dependencies, and its build flags, which lets a language server give accurate completion and error-checking for in-tree Rust—an ergonomic detail, but an important one for making the code approachable to the driver authors it is meant for. The other developer targets in the table serve the same audience. make rustfmt and make rustfmtcheck format Rust code, or check its formatting, against the tree's .rustfmt.toml. make rustdoc generates HTML documentation for the kernel crate and its dependencies. make rusttest runs host-side unit tests, which in 7.0.12 cover only the procedural macros; anything that needs a running kernel is tested through KUnit instead.

From .rs to .o: rustc, bindgen, and Linking

The heart of the build is bridging two languages. C code the Rust must call—every function, struct, and constant in the headers it touches—is translated into Rust declarations automatically by bindgen, which reads a single umbrella header (rust/bindings/bindings_helper.h) and emits a Rust module of extern "C" declarations (rust/bindings/). Because bindgen works from preprocessed C, it cannot see functions that are static inline in headers or generated by macros; for those the kernel provides small C helpers (rust/helpers/) that call the inline function under an ordinary exported name bindgen can bind to. UAPI headers get the same treatment through a separate rust/uapi/ crate. The result is that Rust sees the whole C API it needs, expressed as raw unsafe declarations.

Several details keep the bindings faithful to the kernel being built. bindgen is given the same C flags the kernel's own compilation uses (when the kernel is built with GCC, minus the GCC-only options libclang would reject), so structure layouts, configuration-dependent fields, and type sizes match what the C compiler sees for this configuration and architecture. The file rust/bindgen_parameters lists the exceptions. Some types are blocklisted, such as the __kernel_size_t family, which the bindings crate maps to Rust's native usize and isize instead; others, such as spinlock and several x86 register-state structures, are declared opaque, so Rust sees a blob of the right size and alignment rather than fields it might be tempted to touch. The helpers go through bindgen too. rust/helpers/helpers.c includes 56 small files in 7.0.12, one per subsystem from atomic.c to xarray.c, each defining functions named rust_helper_*. bindgen turns them into bindings_helpers_generated.rs, and a sed pass in rust/Makefile renames each declaration to the plain C name, with a #[link_name] attribute pointing at the helper. Rust code therefore calls bindings::foo in the same way whether foo is a real C function or a helper wrapping a static inline.

The reason this generation must be automatic rather than hand-written is scale and drift. The kernel exposes tens of thousands of functions, structs, and constants, and they change every release; maintaining a parallel set of Rust declarations by hand would be both enormous and perpetually out of date. By running bindgen as part of the build, the Rust side always sees the current C API of the exact tree being compiled—if a C struct gains a field or a function changes signature, the regenerated binding reflects it, and Rust code that used it incorrectly fails to compile rather than silently mismatching the C layout. This is also why the bindings are regenerated per build rather than checked in: they are a mechanical projection of the C headers, valid only for the configuration and architecture they were produced from.

On top of those raw bindings sits the layered crate structure that rust/Makefile builds in a fixed order: core (Rust's own standard-library core, which the kernel compiles from the Rust toolchain's bundled source rather than using a prebuilt copy, because the kernel is no_std and must build core with the same kernel-appropriate flags as everything else), then compiler_builtins (the kernel's own minimal stand-in for the compiler-rt support routines Rust normally links, mostly stubs that panic, because the kernel should never need them), then the small ffi, build_error, and pin-init crates, then the generated bindings and uapi crates, and finally the kernel crate itself. The procedural macros of §6, together with pin-init's own internal macro crate, are a separate, host-side build: they run inside the compiler rather than in the kernel, so rust/Makefile compiles them as host libraries, against vendored copies of the proc-macro2, quote, and syn crates that ship in the tree itself. The order is a dependency order: each crate can only be built once the crates it imports exist, and the kernel crate sits at the top because it depends on all of them. Note what is absent—Rust's std library, which assumes an operating system underneath it (files, threads, a heap that aborts on failure) and therefore cannot exist inside the kernel; kernel Rust builds only on core, the freestanding subset, and supplies its own replacements (fallible allocation, kernel locks, and the rest of the kernel crate) for the facilities std would otherwise provide.

One of those small crates shows how the build turns an unproven assumption into a build failure. rust/build_error.rs defines a single function that panics and is exported under the symbol name rust_build_error. The build_assert! macro (§1.1) calls it only on the path where the asserted condition is false. When the optimizer proves the condition true, it deletes that path and the call with it; when it cannot, the call survives into the object file. The crate is compiled so that other crates can refer to it, but its object is linked into vmlinux only when RUST_BUILD_ASSERT_ALLOW is set. Otherwise any surviving call is an undefined symbol, and the link of vmlinux, or modpost's check of a module, fails.

Drivers and samples are compiled by a different rule, the %.o: %.rs pattern in scripts/Makefile.build, and its unit is a crate, not a file. A Kbuild line such as obj-$(CONFIG_NOVA_CORE) += nova_core.o names the crate root, nova_core.rs. That file declares its submodules with mod, and rustc follows those declarations and compiles the whole tree—36 source files under drivers/gpu/nova-core/—into one object, where a C driver's Makefile would list every object separately. The rule also fixes the environment every driver sees. -Zcrate-attr=no_std makes the crate no_std without the author writing it. --extern kernel and --extern pin_init make those crates available, and rustc resolves them through the metadata files (libkernel.rmeta and its siblings) that rust/Makefile wrote beside each core object. --sysroot=/dev/null ensures nothing from the installed Rust toolchain is picked up by accident. And the same rule runs objtool, so Rust objects are checked as C objects are.

Each Rust crate is compiled by rustc into an ordinary .o object—the same kind of object the C compiler produces—so from the linker's point of view Rust and C objects are indistinguishable and link together into vmlinux or a .ko module exactly as Chapter 1's build system (and Appendix B's module machinery) already describe. The glue that makes this seamless is small but essential: rust/exports.c runs Rust symbols through the kernel's ordinary EXPORT_SYMBOL_GPL machinery so that a Rust function can be called from C (and tracked by modpost) just like any other kernel symbol, and rust/ffi.rs pins down the exact meaning of C's integer and pointer types on the Rust side so the two languages agree on how arguments are laid out. Figure 26-2 traces the pipeline.

The export step is mechanical. Once core.o, helpers.o, bindings.o, and kernel.o are built, rust/Makefile runs nm over each and writes one EXPORT_SYMBOL_RUST_GPL line per defined function or data symbol into a generated header; exports.c defines that macro as EXPORT_SYMBOL_GPL and includes all four headers. Every such symbol is exported, including those of the bindings and helpers that drivers are not supposed to call. The comment in the Makefile explains why: Rust generics and inline functions are compiled in the crate that uses them, so a safe kernel-crate wrapper inlined into a module can leave that module calling a binding or helper directly. The names involved can be long, because the v0 mangling scheme encodes the crate, the module path, and any generic arguments into each symbol. That is why KSYM_NAME_LEN was raised to 512 bytes in 6.1, so kallsyms can hold them, and why RUST selects EXTENDED_MODVERSIONS (§2.1). These core crates are always built into vmlinux, since RUST is a boolean option rather than a tristate. A loadable Rust module contains only its own crate and reaches everything else through these exports, which is why the option's help text says it is needed even to load an external module written in Rust.

A last group of generated files keeps Rust consistent with C where the kernel patches or annotates its own code. Static keys and WARN work by emitting entries into special sections (__jump_table, __bug_table) from inline assembly, built from architecture-specific macros in C headers. Rather than reimplement those macros, the build runs .rs.S templates in rust/kernel/ through the C preprocessor with the architecture's headers, producing Rust source that contains the same assembly text. A Rust static_branch_unlikely! or warn_on! therefore emits exactly the entries its C counterpart does, and the existing code-patching and reporting machinery handles both without knowing which language produced them.

The Safe/Unsafe Boundary

Everything distinctive about Rust in the kernel follows from one idea: a line drawn through the code separating operations the compiler has verified from operations it has been told to trust. This section explains what lies on each side of that line—the raw unsafe bindings and the C helpers below it, the safe kernel crate above it—and how the crate's job is to make the line as easy for driver authors to stay above as possible.

It is worth naming why this boundary is the organizing idea of the whole chapter, and not merely a coding convention. In C there is no such line at all: every operation is equally unchecked, so the reasoning that keeps a pointer valid or a lock held is spread uniformly across millions of lines, and a reviewer auditing for memory-safety bugs has, in principle, the entire kernel to examine. Rust's boundary changes the economics of that audit. Above the line, the compiler has already proven the absence of an entire class of bugs, so a reviewer can trust that code the way they trust that a well-typed C program will not add an integer to a struct. Below the line sits a small, explicitly marked body of unsafe code that concentrates all the operations the compiler could not verify. Safety review, which in C must be everywhere, becomes in Rust a matter of auditing that concentrated core—and everything this section describes is machinery for making that core as small, as visible, and as reviewed as it can be.

The concentration can be measured. In 7.0.12, rust/kernel/ holds about 1,500 unsafe blocks, while the 71 Rust files under drivers/ hold about 170 between them, so roughly nine in ten sit inside the crate. Even the driver figure is lopsided. Binder accounts for 139, because it is a port of a large existing C driver and still shares a few data structures with C. nova-core has 22, the DRM panic QR encoder 3 (it is entered from C with raw buffers), and the cpufreq-dt driver 3. The PHY drivers, the null block driver, Tyr, and the rest contain none. Binder is also the only driver that imports kernel::bindings at all; nova-core's bindings module is its own description of the GPU firmware interface, not the kernel's C API.

Bindings, Helpers, and unsafe

Rust divides all code into two kinds. Ordinary safe Rust is fully checked by the compiler: within it, the ownership and borrowing rules guarantee memory safety, and there is simply no way to write a use-after-free. Certain operations, though—dereferencing a raw pointer, calling a foreign C function, accessing a union—cannot be verified by the compiler, and Rust requires them to be wrapped in an unsafe block. An unsafe block does not disable checking of the surrounding code; it is a narrowly scoped promise from the programmer that this operation upholds the invariants the compiler cannot see, and by convention every one is accompanied by a // SAFETY: comment justifying the promise. The point is not to avoid unsafe but to confine it: to keep the unverified operations few, small, and reviewed, so that the vast majority of code remains provably safe.

Two common misunderstandings are worth dispelling, because they determine how the boundary is actually maintained. The first is that unsafe “turns off the compiler”—it does not. Inside an unsafe block the borrow checker and type checker remain fully active; unsafe unlocks exactly five extra abilities (dereferencing a raw pointer, calling an unsafe function, accessing a mutable static, implementing an unsafe trait, and reading a union field) and nothing else. It is a narrow grant of specific capabilities, not a suspension of the rules. The second is that unsafe marks code that is wrong; in truth it marks code whose correctness the compiler cannot check and the programmer therefore guarantees. That guarantee is a genuine proof obligation: the author of an unsafe block is asserting that the block upholds every invariant the surrounding safe code relies on, and the // SAFETY: comment is where that assertion is written down and made reviewable. The kernel's Rust coding guidelines (Documentation/rust/coding-guidelines.rst) require every unsafe block to carry one. They pair it with the /// # Safety section in the documentation of every unsafe function, which states the preconditions its callers must meet (or, for an unsafe trait, what implementors must guarantee). The boundary is therefore patrolled not by the compiler alone but by a discipline of written, checkable safety arguments. Clippy checks the discipline in both directions: undocumented_unsafe_blocks flags an unsafe block with no // SAFETY: comment, while unnecessary_safety_comment and unnecessary_safety_doc flag a safety comment or # Safety section attached to code that is not unsafe, so that the markers keep their meaning.

The obligations come in more forms than unsafe blocks. An unsafe fn passes the proof to its callers, and because the kernel compiles with -Dunsafe_op_in_unsafe_fn (§1.2), even the body of an unsafe fn must put each unsafe operation in its own commented block. An unsafe trait passes the proof to whoever implements it. Implementing AlwaysRefCounted (§5.1) promises that its methods really increment and decrement the C object's reference count; implementing FromBytes promises that any bit pattern is a valid value of the type; and the workqueue, hrtimer, list, allocator, and lock-backend traits each encode a layout or lifetime contract the compiler cannot check. The crate declares about thirty such traits in 7.0.12.

Thread safety is the most pervasive case. Rust tracks it with two marker traits: Send, meaning a value may be moved to another thread, and Sync, meaning it may be shared between threads by reference. The compiler derives both automatically for ordinary Rust types, but not for a type that holds a raw pointer to a C object, because it cannot know whether the C side tolerates concurrent access. Each such wrapper therefore states its thread safety explicitly with unsafe impl Send or unsafe impl Sync, with a // SAFETY: comment pointing at the C object's own locking or reference counting; the crate contains about 160 of these. A wrong one would let safe driver code race on a C object, so these few lines get some of the closest review in the crate.

A third kind of written argument records type invariants. A wrapper's documentation can carry a /// # Invariants section, for example stating that its pointer is valid and that it holds a reference on the C object for as long as the wrapper lives. Each place that constructs or modifies the value then carries an // INVARIANT: comment showing the invariant is established, and // SAFETY: comments elsewhere can cite the invariant instead of re-proving it. The 7.0.12 crate has about 120 # Invariants sections and 170 // INVARIANT: comments. Also new in 7.0 is the safety module's unsafe_precondition_assert!, with which an unsafe fn can check its own # Safety precondition at run time when RUST_DEBUG_ASSERTIONS is enabled; otherwise it compiles to nothing.

This structure is exactly why the generated bindings are the way they are. Every function bindgen produces is declared unsafe, because calling into C can do anything—C has none of Rust's guarantees—so from Rust's side the entire kernel C API is a wall of unsafe operations. The helpers in rust/helpers/ are equally unsafe to call; they exist only so that inline and macro C functions are reachable at all. If drivers called these bindings directly, every driver would be riddled with unsafe and the safety benefit would evaporate. The design rules that out by policy (§1.2): driver code is expected never to touch bindings directly, but only the safe kernel crate, which is the one place allowed to hold the unsafe calls—each wrapped, justified, and reviewed once on behalf of everyone. The boundary of Figure 26-1 is therefore a real engineering discipline: unsafe is permitted, but only inside the crate, and a driver that needs a C API not yet wrapped is expected to add the safe wrapper to the crate rather than reach past it.

The helpers also cost something at run time. A helper is compiled C, so a Rust call through one is a real cross-language function call, even when the C function it wraps is a one-line static inline that C callers get inlined for free. For most operations the cost is negligible, but some helpers sit on hot paths. The Rust atomics, for example, are implemented through rust/helpers/atomic.c, which scripts/atomic/gen-rust-atomic-helpers.sh generates from the same description as the C atomics, so that the two languages share one implementation of the kernel memory model. In 7.0.12 the helpers in all but three of the helper files are marked __rust_helper, which helpers.c defines as empty. The marker is groundwork: it identifies the functions a future build could inline directly into their Rust callers, so that calling a C static inline from Rust would cost no more than calling it from C.

This is not merely folklore; it is written into the crate itself. The kernel crate's own documentation states the rule plainly—if you need a kernel C API that is not yet wrapped, add the wrapper here first instead of bypassing the crate—so that the safe surface grows deliberately and every path from Rust into C passes through code that has been reviewed for soundness. The payoff of this discipline compounds over time: each wrapper written once and audited once turns an unsafe C entry point into a safe building block that any number of drivers can use without ever writing unsafe themselves, which is why the set of things a Rust driver can do safely grows with every release even though the underlying C API is unchanged.

The kernel Crate and the Prelude

The kernel crate (rust/kernel/lib.rs) is where the kernel's C world is re-expressed as safe Rust, and it is large and growing: it wraps allocation, synchronization, device and driver models, the miscdevice and platform interfaces, workqueues, timers, the DMA and I/O layers, filesystems, network PHYs, and much more, each as a module under rust/kernel/. Being no_std (§2.2), the crate cannot draw on Rust's normal standard library and instead supplies its own kernel-appropriate replacements—fallible allocation, kernel locks, and the rest—for the facilities a hosted program would take from std. It is worth seeing the recurring shape these abstractions take, because once recognized it appears everywhere in the crate. A typical wrapper is a Rust type that owns a C object—holding its pointer or embedding its storage—and exposes only methods that are sound to call, translating each into the underlying unsafe C call internally with a justifying // SAFETY: comment. Rust's ownership model then supplies two guarantees for free. Construction is the only way to obtain the wrapper, so an object cannot be used before it is properly initialized; and Rust's deterministic destruction—the Drop trait, which runs automatically when a value goes out of scope—lets the wrapper release the C resource (free the memory, unlock the lock, drop the reference count) at exactly the right moment, without the caller having to remember. This is the same resource-acquisition-is-initialization idea C++ programmers know, but enforced by the compiler and combined with the borrow checker, so that the wrapper cannot be misused even in the presence of early returns, error paths, or the ? operator of §4.1. The ForeignOwnable trait (rust/kernel/types.rs) handles this. into_foreign turns an owning pointer such as a KBox or Arc into a raw void * for C to store, and the unsafe borrow and from_foreign recover a temporary reference, or the ownership itself, when C hands the pointer back. Error Handling and Allocation

Two things ordinary Rust takes for granted are false in a kernel: that a program may unwind and abort when something goes wrong, and that allocating memory always succeeds. Kernel code can do neither. A Rust panic in the kernel is a BUG() (§1.1), not a way out of a failed system call, and an allocation can genuinely fail under memory pressure. The kernel crate therefore reshapes Rust's error and allocation models to suit, and this section covers both, since together they account for much of what makes kernel Rust look different from the Rust taught in tutorials.

The two are treated together because in the kernel they are inseparable. The most common reason a kernel operation fails is precisely that an allocation did not succeed, so the error model and the allocation model meet at every turn: allocation returns an error, and error propagation carries that failure outward. Ordinary Rust keeps them apart—allocation is infallible and simply aborts, while errors are a separate Result mechanism—but kernel Rust folds allocation failure into the same Result plumbing as every other error, so that running out of memory is handled by exactly the same ?-propagation a driver already uses for a bad argument or a busy device. Understanding this unification is the key to reading the code in this section.

Result, Error, and the ? Operator

Kernel Rust reports failure the way idiomatic Rust does everywhere: through return values, not exceptions. A fallible operation returns a Result<T>—the crate's alias for core::result::Result with the kernel's own Error type (rust/kernel/error.rs)—which is either Ok(value) on success or Err(e) on failure. That Error is a thin wrapper over a familiar C errno: the crate exposes the usual codes as constants under code, so code::EINVAL, code::ENOMEM, and the rest are ordinary values a function can return (the prelude imports them, so a driver simply writes EINVAL), and an Error converts cleanly back to the negative-errno integer the C kernel expects at the boundary. What makes this pleasant rather than tedious is the ? operator: appended to a fallible call, it returns early with the error if there is one and otherwise unwraps the success value, so a sequence of operations that each might fail reads as a straight line, with the error paths handled implicitly and correctly. Result is also marked #[must_use]: the compiler warns when one is dropped unexamined, and a kernel built with CONFIG_WERROR turns that warning into a build failure, so a kernel Rust author cannot silently forget to check a return value the way a C author can drop an error code.

The code module does not mirror every errno. In 7.0.12 it declares 55 codes: the classic POSIX ones from EPERM to ERANGE, plus EOVERFLOW, ETIMEDOUT, and the kernel-internal codes that never reach user space unchanged, such as ERESTARTSYS (Chapter 11), EPROBE_DEFER (Chapter 13), ENOTSUPP, and EIOCBQUEUED. A code is added when an abstraction or driver first needs it; for any other value, Error::from_errno builds the error from its integer.

The Error type is deliberately thin because its whole job is to move cleanly across the C boundary in both directions. When Rust calls a C function that returns a negative errno, the crate's helpers turn that integer into a Result—to_result maps a non-negative return to Ok and a negative one to the corresponding Err, and from_err_ptr does the same for the C convention of encoding an error in a returned pointer—so C-style status codes become idiomatic Rust results the moment they enter Rust. Going the other way, when a Rust function implements a C operation, its Error is converted back with to_errno into the negative integer the C caller expects. The upshot is that Result and the C errno convention are two views of the same information, and the crate translates automatically at each crossing; a driver author writes only in terms of Result and never handles a raw errno. A common convenience is Result with no success value—written Result and meaning Result<()>—for the many operations that either succeed or fail without producing anything, which is exactly the shape of most of the C ops methods a driver implements (§6.2). 

fn setup(n: usize) -> Result<KVec<u32>> {
    if n == 0 {
        return Err(code::EINVAL);   // reject bad input with -EINVAL
    }
    let mut v = KVec::new();
    for i in 0..n {
        v.push(i as u32, GFP_KERNEL)?;  // ? propagates -ENOMEM on failure
    }
    Ok(v)                            // success carries the built vector
}

The example also shows what ? replaces in C. If the fifth push fails, ? returns at once, and on the way out Rust drops every local already constructed, so the partly filled vector is freed without a line of cleanup code. A C function that has acquired several resources unwinds them by hand, jumping to a ladder of goto labels that release them in reverse order (or, since 6.5, through the __free() and guard() attributes of include/linux/cleanup.h). In Rust the unwinding is simply the destructors of whatever is in scope (§5).

? also converts as it returns. It passes the error through Rust's From trait, so it can be applied to any call whose error type converts into Error, and error.rs supplies those conversions. AllocError, the error of every allocating call, becomes ENOMEM, and so does LayoutError, raised when an array size computation overflows. TryFromIntError (a narrowing integer conversion that does not fit), Utf8Error, and a formatting error become EINVAL. That is why the example's push, whose own error type is AllocError, can be followed by ? in a function that returns Result<KVec<u32>>. Collection errors that are not about memory map to EINVAL instead: KVec's PushError, returned when a vector is full and was not allowed to grow, deliberately does not become ENOMEM, because nothing ran out. Where a different code is wanted, map_err substitutes it, as in .map_err(|_| EBUSY)?.

The representation is chosen so that none of this costs anything. An Error is a single NonZeroI32 holding the negative errno, with the type invariant that it lies between -MAX_ERRNO (−4095) and −1. Because zero can never be an Error, the compiler uses zero to encode Ok(()), so a Result<()> occupies the same four bytes as the C int it replaces and comes back in the same register. The invariant is checked where errors enter Rust. Error::from_errno, which to_result uses, treats zero or an out-of-range value as a bug: it logs a warning and substitutes EINVAL rather than build an invalid Error. For C interfaces that return pointers, to_ptr encodes an Error as an ERR_PTR. For diagnostics, Error's debug format asks the C errname() for the symbolic name, so a failure printed with {:?} reads EINVAL rather than −22 when CONFIG_SYMBOLIC_ERRNAME is enabled.

The reverse conversion, for C calling Rust, lives in the crate as well. from_result runs a closure returning Result<T> and yields either the success value or the error's negative errno as the C integer. The extern "C" trampolines the crate installs in C operation tables (§6.2) wrap each call to a driver's Rust method in it, so a driver never writes return -EFOO. The one thing a Rust error is not is a panic. Calling unwrap() or expect() on a Result or Option asserts that failure cannot happen, and if the assertion is wrong the result is a BUG(). The kernel's convention is to propagate with ? instead and let the caller see an errno. Only about 27 such calls appear in the 7.0.12 drivers, nearly all in Binder and nova-core where the surrounding code has just established the value is present.

Fallible Allocation

The deeper departure is allocation. In ordinary Rust, Box::new and Vec::push allocate and, if the system is out of memory, simply abort the program—acceptable for an application, unthinkable for the kernel, which must handle allocation failure gracefully rather than crash. Kernel Rust therefore has no implicit, infallible allocation at all. Its heap types—KBox for a single boxed value, KVec for a growable vector, and vmalloc-backed variants—take the allocation as an explicit, fallible operation: every call that might allocate is passed a GFP flag (the same GFP_KERNEL, GFP_ATOMIC, and so on from Chapter 8) and returns a Result, so out-of-memory is an Err the caller must handle, never a silent abort. In the example above, v.push(i, GFP_KERNEL)? says “grow the vector, sleeping for memory if needed, and propagate -ENOMEM if even that fails.”

This makes the GFP context—may this allocation sleep? is it running in interrupt context?—a visible, mandatory argument of every allocation, rather than an unwritten rule a C programmer must remember. The type system guarantees that a flag is given, not that it is the right one: GFP_KERNEL passed while a spinlock is held still compiles, and is caught as it is in C, at run time by the might-sleep checks of CONFIG_DEBUG_ATOMIC_SLEEP (Chapter 5). Because the standard library's allocating types assume the infallible model, the kernel cannot use them and instead maintains its own allocation layer (rust/kernel/alloc/) providing these fallible types over the kernel's real allocators—kmalloc, vmalloc, and their kin. The effect is that a whole category of C kernel bug—an unchecked allocation that returns NULL and is then dereferenced—is structurally impossible: there is no unchecked allocation to forget, because the type system will not let the result be used without first confronting the failure case.

That layer took its present form in 6.13. Until then the kernel built the standard alloc crate with its infallible paths compiled out (no_global_oom_handling) and bolted fallible methods onto its Box and Vec through extension traits. 6.13 replaced this with the kernel's own Allocator trait and its own generic Box and Vec, and removed both the alloc crate and the GlobalAlloc hook from the build. Kernel Rust therefore has no global heap at all; every allocation names its allocator, either explicitly or through the type it creates.

Which allocator backs a value is part of its type, not a call-site decision, and the crate provides a family of types for the kernel's different allocators. For a single boxed value there is KBox over kmalloc, VBox over vmalloc, and KVBox over the kvmalloc strategy that tries a physically contiguous kmalloc first and falls back to a virtually contiguous vmalloc; the growable vectors KVec, VVec, and KVVec mirror the same three choices. This maps directly onto the allocator distinctions of Chapter 8: kmalloc memory is physically contiguous and suits small or DMA-facing buffers, while vmalloc memory is only virtually contiguous but can satisfy large requests, and encoding the choice in the type means an object carries its allocation strategy with it and is freed through the matching path automatically when it is dropped. Because these types mirror the standard Box and Vec interfaces and dereference to the boxed value or to a slice, code that uses them reads like ordinary Rust—indexing, iteration, push—with the single, deliberate difference that every operation which might allocate takes a GFP flag and returns a Result, keeping the kernel's allocation discipline visible in the source rather than hidden in a library.

Under the types sits one trait, Allocator (rust/kernel/alloc.rs), an unsafe trait in the sense of §3.1 with essentially one operation: realloc(ptr, layout, old_layout, flags, nid). A fresh allocation is a realloc from nothing, freeing is a realloc to size zero, and growing a vector is a realloc to the larger layout. The three backends in rust/kernel/alloc/allocator.rs, Kmalloc, Vmalloc, and KVmalloc, map it onto the C krealloc_node_align, vrealloc_node_align, and kvrealloc_node_align. Two properties of the C allocators show through. Each backend declares the minimum alignment it always provides (ARCH_KMALLOC_MINALIGN for kmalloc, a page for vmalloc). And because kmalloc guarantees natural alignment only for power-of-two sizes, Kmalloc pads every request to a multiple of its alignment before calling C, so a Rust type declared with a large alignment still gets correctly aligned memory. The nid argument, added in 6.18, places memory on a particular NUMA node (Chapter 8); NumaNode::NO_NODE leaves the choice to the allocator. Since Box<T, A> and Vec<T, A> are generic over the allocator A, the destructor calls A::free, which is how a KBox is kfreed and a VVec vfreed without the program ever naming the free function.

The Flags type exposes the GFP flags Rust code needs so far: GFP_KERNEL, GFP_KERNEL_ACCOUNT (which charges the memory to the caller's memory cgroup, Chapter 25), GFP_ATOMIC, and GFP_NOWAIT, combined with | with the modifiers __GFP_ZERO, __GFP_HIGHMEM, and __GFP_NOWARN. The same flags reach every other allocating interface in the crate, not only the box and vector types: Arc::new(value, flags), Page::alloc_page(flags), DMA-coherent buffers, and the pinned initializers KBox::pin_init and Arc::pin_init (§5.2). They also support a familiar kernel idiom, allocating before taking a spinlock so that nothing allocates while it is held. A KVec is grown with reserve(n, GFP_KERNEL) outside the lock, and inside it elements are added with push_within_capacity, which never allocates and returns PushError if the space has run out. Binder's freeze notification code does exactly this. When the reserved space proves too small, it drops its spinlock, reserves more with GFP_KERNEL, and takes the lock again. Ownership, Pinning, and Synchronization

The hardest part of writing safe wrappers for a C kernel is that C kernel objects are shared, self-referential, and refcounted in ways Rust's ownership model does not directly express. Bridging that gap is the real work of the kernel crate, and it rests on three ideas: reference-counting types for shared ownership, pinning for objects that must not move, and lock types that make shared mutable state safe. This section takes them in turn.

What unites the three is that each reconciles a specific mismatch between Rust's ownership model and how the C kernel actually manages objects. Rust's default assumptions—a value has one owner, lives on the stack or moves freely when passed around, and is mutated by only one holder at a time—are exactly the assumptions kernel objects violate: they are shared through refcounts, wired into lists by their address, and mutated concurrently under locks. Rather than abandon Rust's guarantees to accommodate this, the crate builds types that re-express the kernel's patterns inside the ownership model, so that shared, pinned, concurrently mutated objects still get compile-time safety. The three subsections are three instances of that same move.

The code is in two places. rust/kernel/sync/ holds Arc and ARef, the lock types, and the other synchronization primitives collected in Table 26-6. rust/pin-init/ holds the in-place initialization library that pinning depends on. Both build on Opaque, the wrapper for a C object whose contents Rust must not interpret, which §5.1 introduces.

Refcounting: Arc, ARef, and Opaque

Rust's basic rule—one owner, or many readers xor one writer—is too strict for a kernel full of objects shared among threads and lists. The crate's answer for Rust-created objects is Arc (rust/kernel/sync/arc.rs), an atomically reference-counted pointer: cloning an Arc bumps a refcount and hands out another shared owner, and the object is freed when the last Arc is dropped. It resembles the standard library's Arc but is a separate implementation, with differences described below. For objects that live on the C side and carry their own refcount—a struct device, a task_struct, an mm_struct—the crate provides ARef<T> (rust/kernel/sync/aref.rs), an owned reference that increments the C object's refcount when taken and decrements it when dropped, for any type that implements AlwaysRefCounted. Both types turn the kernel's manual get/put refcount discipline—a classic source of leaks and use-after-free—into something the compiler manages automatically through ownership.

Arc comes with two companions that handle the awkward moments its shared model creates. A shared Arc gives out only read access—many owners cannot all be allowed to mutate—yet an object usually needs to be filled in before it is shared. UniqueArc covers that gap: it is an allocation that is provably the only reference to its object, so it permits full mutation, and once initialization is complete it converts into an ordinary shareable Arc. This gives the natural build-it-then-publish lifecycle—allocate, populate freely, then hand out shared references—without ever allowing mutation through an alias. In the other direction, ArcBorrow lets code hold a temporary borrow of an Arc's contents without bumping the refcount, for paths that need access but not ownership. All of these deref transparently to the underlying object, so through an Arc the wrapped value is used exactly as if it were held directly, and the reference counting stays invisible until the last owner drops.

The differences from the standard Arc follow from the kernel's rules. The count is a Refcount, a wrapper for the C refcount_t of Chapter 5, so an overflow saturates with a warning instead of wrapping to zero and freeing a live object. Creating an Arc allocates, so Arc::new takes GFP flags and returns a Result (§4.2). There are no weak references: the standard Weak type needs a second count, and kernel code has not needed one. An Arc is also pinned by construction. It never gives out a mutable reference to its contents, so the contents never move, and an Arc can hold a mutex or another self-referential C object directly (§5.2). Arc implements ForeignOwnable (§3.2), so C can hold one as a raw pointer and lend it back as an ArcBorrow; workqueue items and hrtimer callbacks carry their Rust data this way. Finally, an Arc can point at a trait object (Arc<dyn Trait>), so a driver can keep objects of different types behind one interface.

ARef is the C-side counterpart, and its trait is small. AlwaysRefCounted has two methods: inc_ref, which takes another reference, and the unsafe dec_ref, which releases one. Each wrapper maps them onto its C pair: for Task they call get_task_struct and put_task_struct, and for Device, get_device and put_device. In 7.0.12 the crate implements AlwaysRefCounted for 22 C types. They include the driver-model devices of the PCI, platform, auxiliary, USB, and I2C buses, DRM devices and GEM objects, Task, Credential, File, Mm, PidNamespace, block-layer requests, and firmware nodes. (Both types moved from kernel::types to kernel::sync::aref in 6.17, and the old path still re-exports them.) The distinction between a plain reference and an ARef carries over from C. A callback that receives &Device borrows the device only for the duration of the call, just as C code may use a struct device pointer it was handed without taking a reference. Code that must keep the device longer converts the reference with ARef::from(&dev), which calls inc_ref, and the matching put happens when the ARef is dropped. The misc-device sample (samples/rust/rust_misc_device.rs) does this in its open method, keeping the device so that later reads and writes can log through it.

A subtler tool is Opaque<T> (rust/kernel/types.rs). Many C structs must be wrapped without Rust ever assuming their exact layout or that their fields can be freely read and written—a struct mutex or a struct work_struct has internal invariants and may be modified by C behind Rust's back. Opaque wraps such a struct so that Rust holds it, passes its address to C, and never treats it as an ordinary movable, inspectable Rust value. It is the crate's standard device for saying “this is a C object; store it, give C a pointer to it, but do not presume to understand its insides,” and it appears throughout the wrappers as the foundation on which the safe abstractions are built.

Opaque<T> is defined as an UnsafeCell<MaybeUninit<T>> together with a PhantomPinned marker, and each part removes one assumption Rust would otherwise make. UnsafeCell tells the compiler that the contents can change even through a shared reference, which is true whenever C modifies the struct. MaybeUninit means the contents need not be a valid T, so a struct that C has not initialized yet can be stored. PhantomPinned makes the type immovable once pinned (§5.2). Opaque::ffi_init returns an initializer that hands a raw pointer to the uninitialized struct to a C init function, such as __mutex_init or init_waitqueue_head. get returns a raw pointer for passing to other C functions, and reading the contents requires unsafe. The typical wrapper is a #[repr(transparent)] struct around one Opaque field. Device, for example, wraps a single Opaque<bindings::device> (plus a zero-sized marker), so it has exactly the layout of a C struct device, and Device::from_raw can turn a struct device * received from C into a &Device without copying anything.

Pinned Initialization

Opaque raises a problem that is central to kernel Rust. Many C objects contain pointers to themselves or are entered into lists that record their address—a struct mutex registers itself with lockdep, a work item links into a queue by address. Such an object must never be moved in memory after it is set up, because moving it would leave those recorded addresses dangling. But ordinary Rust values are freely movable: passing one to a function or returning it can copy it to a new address. Reconciling this is what pinning does. A pinned value is one the type system guarantees will never move again, expressed through Pin and the crate's PinInit machinery, and it is the precondition for safely holding any self-referential C object.

The difficulty is that such an object cannot be built the ordinary Rust way—construct it as a value and then move it into place—because the very act of moving it into place would relocate it after its self-pointers were set. The pin-init library (rust/pin-init/, surfaced as rust/kernel/init.rs) solves this with in-place initialization: a struct is annotated #[pin_data], and the pin_init! macro produces an initializer that constructs the object directly at its final address, so it is correct from birth and never moved. A driver rarely manipulates this machinery by hand; it appears as a required pattern when embedding a lock or other pinned primitive in a struct, and understanding that pinning is why those patterns exist is enough to use them. Figure 26-3 contrasts the ordinary construct-then-move path with pinned in-place initialization.

The pattern has a few parts. Inside the struct, #[pin] marks the fields that are structurally pinned, which must stay at their address; the other fields are ordinary values. In the initializer, a pinned field is written field <- initializer rather than field: value. The arrow means “run this initializer on the field's final location” instead of “move this value in.” An initializer is itself a value, of type impl PinInit<T, E>, which is what new_mutex!, Opaque::ffi_init, and CondVar::new return: something that can only be run in place. If one field's initializer fails, the generated code drops the fields already initialized, in reverse order, before returning the error, the same cleanup that ? gives ordinary code (§4.1). A pinned type cannot implement the ordinary Drop, whose &mut self would allow the value to be moved, so it implements PinnedDrop instead, which receives Pin<&mut Self>, and the struct is declared #[pin_data(PinnedDrop)]. The initializer only describes the construction; the memory comes from whoever runs it. KBox::pin_init(init, flags) and Arc::pin_init(init, flags) allocate and then initialize in place, and stack_pin_init! does the same on the stack.

In-place initialization helps unpinned values too. A large structure built as an ordinary value is first assembled on the stack and then copied to the heap, and kernel stacks are small (normally 16 KiB on x86-64 and arm64, Chapter 3). The unpinned form, an Init initializer run by KBox::init, builds such a structure directly in its heap allocation. The library predates most of the crate: it was merged in 6.4, moved to rust/pin-init/ in 6.15 as a standalone crate that is also published for user-space Rust, and in 7.0 its macros were rewritten as procedural macros on top of syn (§2.2). rust/kernel/init.rs adapts it to the kernel, adding the GFP-aware InPlaceInit methods and the try_ macros that default to the kernel's Error.

It is worth being clear about what Pin actually is, because it is the most unfamiliar concept in kernel Rust. Pin is not a runtime container that locks memory down; it is a compile-time promise, encoded in the type, that the value it wraps will never be moved again for the rest of its life. Once a value is pinned, safe Rust offers no way to move it, so any code holding a raw pointer into it—C code that recorded the object's address—can rely on that pointer staying valid. Two details make the pattern practical. First, initialization can fail in the same way allocation can. pin_init! builds an initializer that cannot fail, and try_pin_init! one whose error type is the kernel's Error, so constructing a pinned object that might fail (because it allocates, or because a C setup call can return an error) folds into the same ? propagation as everything else in §4. Second, pinning composes with refcounting: the common way to hold a pinned kernel object is an Arc whose contents are pin-initialized, giving an object that is at once shared, refcounted, and guaranteed not to move—precisely the combination a lock-bearing kernel structure needs.

Locks: Mutex, SpinLock, and lockdep

Rust's borrow checker prevents data races within a single thread's view of memory, but sharing mutable data across threads needs a lock, and here the kernel crate does something C cannot: it makes the lock and the data it protects a single, inseparable object. A kernel Mutex<T> or SpinLock<T> (rust/kernel/sync/lock/) contains the data of type T, and the only way to reach that data is to lock: calling lock() returns a guard through which the data can be read and written, and when the guard goes out of scope the lock is released automatically. Because the data is unreachable without holding the lock, and the lock is always released when the guard is dropped, two whole classes of C locking bug—accessing shared data without the lock, and forgetting to unlock on some error path—cannot be written. These types wrap the same C struct mutex and spinlock_t this book has described, so they interoperate with C locking and participate in lockdep (Chapter 5) through a lock-class key, giving Rust locks the same deadlock-detection the C kernel enjoys. Because a lock embeds itself in lockdep by address, it is one of the pinned objects of §5.2, which is why a struct holding a Mutex uses the #[pin_data] pattern. Alongside the locks the crate wraps the other synchronization primitives of Chapter 5, listed in Table 26-6.

Both lock types are one generic type. Lock<T, B> (rust/kernel/sync/lock.rs) holds the C lock state in an Opaque, the data in an UnsafeCell, and a PhantomPinned marker, and the unsafe Backend trait (§3.1) supplies init, lock, unlock, and try_lock for one C primitive. Mutex<T> is Lock<T, MutexBackend>, over struct mutex, and SpinLock<T> is Lock<T, SpinLockBackend>, over spinlock_t. The lockdep class comes from the constructor macros. new_mutex!(value) and new_spinlock!(value) pass a name (by default the source file and line) and a static lock_class_key that static_lock_class! creates at that call site. Each place in the source that creates locks therefore gets its own lockdep class, as in C, where mutex_init also declares a static key at its call site. Thread safety follows from the type. A Lock is Sync whenever its data is Send, because the lock serializes all access, so a Mutex<T> can be shared between threads even when T alone could not be. The guard is the opposite: it is not Send, so it cannot be moved to another thread, because a C mutex must be released by the task that acquired it.

The example below puts §5.1 to §5.3 together: a structure with an embedded mutex, initialized in place inside a new Arc. 

use kernel::sync::{new_mutex, Arc, Mutex};

#[pin_data]
struct Counter {
    #[pin]
    hits: Mutex<u64>,          // embeds a C struct mutex: must not move
    log: KVec<u8>,            // ordinary field, freely movable
}

fn new_counter() -> Result<Arc<Counter>> {
    Arc::pin_init(
        pin_init!(Counter {
            hits <- new_mutex!(0u64), // initialized at its final address
            log: KVec::new(),
        }),
        GFP_KERNEL,                 // allocation can fail: Err(ENOMEM)
    )
}

fn bump(c: &Counter) -> u64 {
    let mut hits = c.hits.lock();   // mutex_lock(); may sleep
    *hits += 1;
    *hits                           // guard dropped here: mutex_unlock()
}

The guard deserves a second look, because it is what makes the “lock contains the data” design feel natural rather than restrictive. The guard returned by lock() behaves like a transparent handle to the protected value: it derefs to T, so code reads and writes the data through the guard exactly as if it held the value directly, and the only visible difference from unlocked access is that the guard had to be obtained first. The scope of the lock is therefore the lexical scope of the guard, made explicit in the code and enforced by the compiler—no separate unlock call to match, and no possibility of an early return or a ? slipping past one, because the guard's destructor runs on every exit path. For the case where data is protected by a lock stored elsewhere—common in the kernel, where one lock guards fields spread across several structures—the crate provides LockedBy, which ties a piece of data to a particular lock so that the data can only be accessed on proof that that lock is held. The proof is a reference to the lock's own protected data, which only a guard can provide: access takes a shared reference and access_mut a mutable one. Because types cannot tell one instance of a lock from another, access also compares the address passed in with the lock recorded when the LockedBy was created, and panics on a mismatch. Between the two, the crate can express both the “lock wraps its data” case and the kernel's looser “this lock protects those fields” convention, with the access rule checked at compile time where the types can express it and at run time where they cannot. In 7.0.12 Binder is its only in-tree user: each Binder node keeps part of its state under the lock of the process that owns it.

The lock types remove the two most common locking bugs, but not every one. Deadlock is still possible. Two code paths can take the same two locks in opposite orders, and nothing in the type system notices; lockdep catches it at run time, exactly as for C, which is why every Rust lock is registered with a class. Sleeping in atomic context is not checked at compile time either. A driver holding a SpinLock guard can call Mutex::lock or allocate with GFP_KERNEL. The code compiles, and CONFIG_DEBUG_ATOMIC_SLEEP reports it at run time (§4.2). Finally, unlike the standard library's mutex, the kernel's has no poisoning, the mechanism by which a lock records that its holder panicked. A Rust panic in the kernel is a BUG() (§1.1), not an unwinding that other threads could recover from, so lock() returns the guard directly rather than a Result.

Modules and Vtables

Two procedural macros do the structural work that lets a Rust file be a kernel module and plug into the kernel's C interfaces. This section covers the module! macro that declares a module and the #[vtable] macro that lets Rust safely implement the C operation tables the kernel calls back through. Table 26-7 lists these and the other procedural macros kernel Rust code uses.

Both are procedural macros—Rust code that runs at compile time and generates more Rust code—which is the mechanism the crate uses whenever a uniform but tedious body of boilerplate must be produced from a compact declaration. That is exactly the shape of the two problems this section addresses. A kernel module needs a fixed set of C-visible entry points and metadata; an operations table needs a C struct of function pointers wired to the right callbacks. Writing either by hand would mean repetitive, error-prone glue in every module and driver, so the macros generate it instead, letting the author write only the parts that differ—the module's metadata and the driver's actual logic—while the mechanical scaffolding is emitted for them.

The macros live in their own crate, rust/macros/: nine files and about 1,750 lines in 7.0.12, with one entry point per macro in lib.rs. Like the pin-init macro crate (rust/pin-init/internal/), it is a host-side proc-macro library that rustc loads while it compiles kernel code (§2.2), so none of it ends up in the kernel image. What reaches the image is the code the macros generate, which the compiler type-checks like any hand-written Rust; a macro saves typing but adds no guarantee of its own. The crate was rewritten for 7.0. Until then most of its macros parsed their input by walking the raw token stream by hand. 6.19 vendored the syn, quote, and proc-macro2 crates into rust/, and in 7.0 module!, #[vtable], #[export], concat_idents!, and #[kunit_tests] were converted to parse with syn and to build their output with quote! (for module!, commit c578ad703ae9), the same change 7.0 made to the pin-init macros (§5.2). The visible result is better diagnostics: a mistake in a module! block is now reported as a compiler error that points at the offending key, where the old parser often stopped with a panic inside the macro.

The module! Macro

A C kernel module supplies module_init and module_exit functions and a block of MODULE_* metadata macros (Appendix B). The Rust equivalent is the single module! macro (rust/macros/module.rs), which takes the module's metadata as named fields—the Rust type that implements the module, its name, authors, description, license, and any module params—and generates all the C-visible glue: the metadata the modinfo tooling reads, and the init and exit entry points the kernel calls. The named type must implement the crate's Module trait (rust/kernel/lib.rs), whose init method is the module's constructor: it runs when the module loads, returns Result<Self>, and on success yields the module object that lives for the module's lifetime. Cleanup needs no explicit exit function—when the module is unloaded the object is dropped, and Rust's ordinary Drop runs whatever teardown the type defines, so resources are released automatically. The order comes from the struct: Rust first runs the type's own drop method, if it has one, and then drops the fields in the order they are declared. A module that registers a device and then allocates a buffer the device uses should therefore declare the registration field first, so the device is unregistered before the buffer is freed.

This is a small but telling improvement over the C pattern. In C, forgetting to undo something in the exit function—leaving a registration in place, failing to free a buffer—is an easy and common mistake; in Rust, teardown is the compiler-generated consequence of the object being dropped, so it cannot be forgotten, and it is automatically correct even when initialization failed partway through: on that path the values init has already created are still local variables, which Rust drops in the reverse order of their creation, the order a C error ladder unwinds by hand. The module! block and the Module trait together turn “a loadable module” into an ordinary Rust object with a constructor and a destructor.

The metadata the macro accepts mirrors the C MODULE_* family closely. Beyond the type, name, authors, description, and license, it takes optional alias, firmware, and imports_ns lists and a params block for module parameters, and it emits them as the same modinfo entries the C tooling and modprobe already read—so a Rust module is indistinguishable from a C one to the module utilities. The license field is not decorative: as with C modules, it feeds the kernel's tainting logic, and a module declared with a non-GPL license is denied the GPL-only symbols, so the same licensing boundary this book has described applies unchanged to Rust. For Rust the boundary is harder still to avoid: every symbol the core and kernel crates define is exported to modules with EXPORT_SYMBOL_GPL, through the lists rust/Makefile generates for rust/exports.c, so a Rust module under a non-GPL-compatible license could not resolve even the crate it is built on. The init method receives a ThisModule handle—the Rust equivalent of C's THIS_MODULE—identifying the running module for the APIs that need it. For modules whose top-level state must itself be pinned, the crate offers a second trait, InPlaceModule, whose init returns a pinned initializer (impl PinInit<Self, Error>) rather than a plain value, so even the module object can embed a lock, a device registration, or another pinned primitive from §5.2. Every ordinary Module is automatically an InPlaceModule through a blanket implementation, and that pinned form is the one the generated init code calls.

What the macro generates (rust/macros/module.rs) is close to what the C macros expand into. For a loadable module it defines the two functions the module loader looks up by name, init_module and cleanup_module, unmangled and placed in .init.text and .exit.text; C's module_init and module_exit produce the same two symbols as aliases of the functions they name. For a built-in module it defines __<name>_init and puts a pointer to it in the .initcall6.init section, the device_initcall level that module_init also uses for built-in code. On architectures with HAVE_ARCH_PREL32_RELOCATIONS, x86_64 and arm64 among them, that entry is a 32-bit offset emitted with global_asm!, as in C. Both paths call one private __init function, hidden inside two nested modules so that nothing else in the crate can call it. __init does not build the module object on the stack. It calls InPlaceModule::init, runs the returned initializer directly into a static MaybeUninit slot, and turns an Err into a negative errno with to_errno(), which the loader passes back as the result of the finit_module system call (Appendix B). The exit function drops the object in that slot in place. The macro also defines THIS_MODULE, a null pointer when the module is built in, as in C; the __LOG_PREFIX that pr_info! and its relatives print before each message, the job C does with pr_fmt and KBUILD_MODNAME; and the modinfo strings, each a NUL-terminated key=value array in the .modinfo section, prefixed by <name>. when the module is built in, exactly as C's __MODULE_INFO does.

The macro is strict about its input. The keys must appear in a fixed order (type, name, authors, description, license, alias, firmware, imports_ns, params), only type, name, and license are required, and every string except the description must be ASCII. A key that is out of order, repeated, or unknown is a compile error that lists the expected order. Since 7.0, type may be any Rust type rather than a bare identifier. imports_ns (since 6.19) emits import_ns entries, the Rust form of MODULE_IMPORT_NS(), which a module needs before the loader lets it use symbols exported with EXPORT_SYMBOL_NS_GPL; in 7.0.12 the PWM abstraction is its only user, importing the PWM namespace for every Rust PWM driver.

Module parameters arrived in 6.19 (rust/kernel/module_param.rs). Each entry in params names an integer type (i8 through u64, isize, or usize), a default, and a description. The macro emits the parmtype and parm strings that modinfo shows, and a struct kernel_param in the __param section, so the value can be given at load time (insmod rust_minimal.ko test_parameter=5) or, for a built-in module, on the kernel command line as rust_minimal.test_parameter=5. The C set callback parses the string into a SetOnce cell (Table 26-6), and the module reads the value with module_parameters::test_parameter.value(), which returns the default if nothing was set. Compared with C's module_param() this is a first step. Only integers are supported, and the permission is fixed at 0, so the parameter has no file under /sys/module/<name>/parameters/ and cannot be changed after the module is loaded.

Most drivers never write module! themselves. In 7.0.12 only ten files call it directly: Binder, the rnull block driver, the find_bit benchmark in lib/, and seven samples. The other fifteen Rust modules in drivers/ and samples/ are bus drivers, and they use one of the module_*_driver! macros: module_platform_driver! (six modules), module_pci_driver! (three), module_phy_driver! (two), and the auxiliary, I2C, USB, and PWM variants (one each). Apart from the PHY macro, which registers an array of PHY drivers itself, these expand to the generic module_driver! in rust/kernel/driver.rs. It defines a module type holding a single pinned driver::Registration, implements InPlaceModule for it with try_pin_init!, and passes it to module!. Loading the module registers the driver with its bus; unloading drops the registration, which unregisters it. This is the C module_driver() macro of include/linux/device/driver.h, which module_pci_driver() and module_platform_driver() expand to, with its paired register and unregister calls replaced by a value and its Drop. Chapter 13 describes the driver model these registrations plug into.

vtable and Implementing C Ops

The kernel is built on operation tables: a driver registers a struct of function pointers—file_operations, net_device_ops, and the like—and the kernel calls back through them (the polymorphism this book has relied on since the VFS of Chapter 12). Rust expresses the same idea with a trait, and the #[vtable] macro (rust/macros/vtable.rs) bridges the two. A trait marked #[vtable] corresponds to one of these C ops structs; a driver implements the trait with impl, providing Rust methods for the operations it supports, and the crate's abstraction builds the C function-pointer table from that impl, inserting safe Rust-to-C shims that translate arguments, convert errors, and uphold the invariants the C side assumes. Because some ops are optional, the macro generates a set of HAS_* constants recording which methods the impl actually provided, so the abstraction can populate the C table with a real pointer or a null as appropriate. The upshot is that implementing a kernel interface in Rust is writing a normal trait impl of safe methods, while the unsafe business of matching C's calling convention and nullable function pointers is handled once, inside the crate.

A crucial property of this arrangement is that it changes nothing on the C side. The generated ops table is a perfectly ordinary C struct of function pointers, so the C subsystem that invokes it—the VFS, the network stack, the driver core—calls a Rust-backed operation exactly as it calls a C one, with no awareness that the implementation is in Rust. The shim the abstraction places between the C entry point and the Rust method is where the two worlds are reconciled: it presents the raw C arguments to the Rust method as safe types, and it converts the method's Result back into the negative-errno integer the C caller expects (§4.1), so a Rust error returned deep in a driver surfaces to C as an ordinary error code. This is why the HAS_* constants matter beyond mere optimization: leaving a nullable function pointer null when the trait did not implement that operation is part of the C contract for many ops structs—the kernel checks for null before calling—so faithfully reproducing which callbacks are present is what lets a partial Rust implementation slot into a C interface without surprising the caller. The result is genuine interoperability: Rust implementing an interface C defined, callable from C, with the language boundary invisible to both sides.

The macro itself does less than this description suggests; it never sees the C struct. Applied to a trait, it adds a bool constant HAS_<METHOD>, defaulting to false, for every method, and an associated constant USE_VTABLE_ATTR with no default. Applied to an impl of the trait, it sets HAS_<METHOD> to true for every method the impl defines (an impl may also set one explicitly) and supplies USE_VTABLE_ATTR, so an impl that forgets the attribute fails to compile instead of silently reporting every method as absent. Since 7.0 a #[cfg] on a method is copied onto its constant, so a method compiled out by the configuration is reported as absent too. Optional methods still need a body in the trait, but it is never meant to run, because the C side will see a null pointer instead. By convention that body calls build_error!(VTABLE_DEFAULT_ERROR), so a Rust caller that reaches it leaves a call to rust_build_error in the object file and the build fails (§2.2).

The rest of the work is done by the abstraction for each interface. For misc devices, rust/kernel/miscdevice.rs defines a generic MiscdeviceVTable<T> with one unsafe extern "C" shim per operation, and builds the file_operations table as an associated constant, abridged here: 

impl<T: MiscDevice> MiscdeviceVTable<T> {
    const VTABLE: bindings::file_operations = bindings::file_operations {
        open: Some(Self::open),
        release: Some(Self::release),
        mmap: if T::HAS_MMAP { Some(Self::mmap) } else { None },
        unlocked_ioctl: if T::HAS_IOCTL { Some(Self::ioctl) } else { None },
        #[cfg(CONFIG_COMPAT)]
        compat_ioctl: if T::HAS_COMPAT_IOCTL {
            Some(Self::compat_ioctl)
        } else if T::HAS_IOCTL {
            bindings::compat_ptr_ioctl
        } else {
            None
        },
        // read_iter, write_iter, and show_fdinfo follow the same pattern.
        ..pin_init::zeroed()
    };
}

Because VTABLE is a constant, the compiler evaluates the if expressions at build time and emits one finished table per driver type into read-only data, the equivalent of the static const struct file_operations a C driver declares; ..pin_init::zeroed() sets every field the abstraction does not handle to null. open and release are always installed: open is a required method, and the default release just drops the per-file object. The compat_ioctl entry follows a C convention too. A driver with only an ioctl method gets compat_ptr_ioctl, the helper C drivers use when their ioctl arguments are pointers to structures with the same layout for 32-bit and 64-bit processes. Registration then stores the table's address in the fops field of the struct miscdevice it embeds.

The shims are where the safety argument is made. The ioctl shim, for example, reads file->private_data, which the open shim set to the object T::open returned (converted with ForeignOwnable::into_foreign, §5.1). It borrows that object back with ForeignOwnable::borrow, wraps the raw struct file pointer as a &File, calls T::ioctl, and turns an Err into a negative errno with to_errno(). Each step that relies on C keeping its promises (that private_data holds what open stored, that the file stays valid during the call) is an unsafe block with a SAFETY comment, and that code exists once per interface, in the abstraction, rather than once per driver. What the shims do not do is catch panics. Kernel Rust is compiled with -Cpanic=abort, and the kernel's panic handler (rust/kernel/lib.rs) prints the message and calls BUG(), so nothing ever unwinds into C. A Rust driver that panics in a callback behaves like a C driver that hits BUG().

Eight traits carry #[vtable] in 7.0.12: MiscDevice, the block layer's mq::Operations (used by rnull, Chapter 14), net::phy::Driver, cpufreq::Driver, drm::Driver, opp::ConfigOps, and the configfs GroupOperations and AttributeOperations. What they have in common is that the C side gives a null pointer a meaning. The VFS answers an ioctl on a file without unlocked_ioctl with -ENOTTY (vfs_ioctl() in fs/ioctl.c), and phylib's phy_read_status() falls back to genphy_read_status() when a PHY driver leaves read_status unset. The bus driver traits (pci::Driver, platform::Driver, usb::Driver, i2c::Driver, and auxiliary::Driver) do not use the attribute. Their adapters always install the C probe and remove callbacks, and the optional unbind method has an empty default that is safe to call, so a plain trait with default methods is enough. #[vtable] is needed only where whether a pointer is present is itself part of the interface.

Writing a Driver

The abstractions of the previous sections come together in actual driver code, and seeing them in a working module is the clearest way to understand how they fit. This section walks through three of the kernel's own samples: a minimal module that shows the skeleton every Rust module shares, a misc character device that puts locking, fallible allocation, user-space I/O, and a C operation table to work, and a PCI driver that binds to a device through the driver model and maps its registers.

All three are real files that ship in the tree under samples/rust/, so they compile and load on any kernel configured with Rust support and serve as the reference the documentation points newcomers to. The directory is gated by SAMPLES_RUST, a boolean menu that depends on RUST and sits inside the general SAMPLES menu; it builds nothing by itself. Each sample has its own tristate option beneath it—SAMPLE_RUST_MINIMAL, SAMPLE_RUST_MISC_DEVICE, SAMPLE_RUST_DRIVER_PCI, and so on—so each can be built in or as a module independently. In 7.0 the directory holds fifteen sample modules. Besides the three read here there are drivers for the platform, USB, I2C, auxiliary, and faux buses, an I2C client, DMA-coherent allocation, SoC device registration, configfs, two debugfs variants, and a printing sample that exercises every log level and fires a tracepoint defined in a companion C file (rust_print_events.c), along with a separate option, SAMPLE_RUST_HOSTPROGS, for Rust programs that run on the build host. Read in order, the three samples here form a progression. The first establishes the fixed skeleton that every Rust module—however large—begins from. The second keeps that skeleton but fills it with the locking, allocation, user-space I/O, and operation-table machinery a character driver needs. The third replaces the module-wide object with a per-device one that the bus creates and destroys as hardware comes and goes. The steps run from “a module that loads” to “a driver that does something” to “a driver the device model manages.”

A Minimal Module

The smallest Rust module (samples/rust/rust_minimal.rs) is worth reading line by line, because everything larger is an elaboration of it. It opens with use kernel::prelude::*; to bring in the common vocabulary, then a module! block declaring the metadata and naming the type that implements the module. That type is an ordinary struct—here holding a KVec of numbers—and it implements kernel::Module: its init allocates and fills the vector (each fallible push propagating -ENOMEM with ?), logs through pr_info!, and returns the constructed object. A Drop impl logs on the way out. There is no exit function and no manual cleanup: unloading the module drops the struct, which first runs the body of Drop::drop—while the vector is still intact, which is why it can print it—and then drops the fields, freeing the vector. 

use kernel::prelude::*;

module! {
    type: RustMinimal,
    name: "rust_minimal",
    authors: ["Rust for Linux Contributors"],
    description: "Rust minimal sample",
    license: "GPL",
}

struct RustMinimal {
    numbers: KVec<i32>,
}

impl kernel::Module for RustMinimal {
    fn init(_module: &'static ThisModule) -> Result<Self> {
        pr_info!("Rust minimal sample (init)\n");
        let mut numbers = KVec::new();
        numbers.push(72, GFP_KERNEL)?;
        numbers.push(108, GFP_KERNEL)?;
        numbers.push(200, GFP_KERNEL)?;
        Ok(RustMinimal { numbers })
    }
}

impl Drop for RustMinimal {
    fn drop(&mut self) {
        pr_info!("My numbers are {:?}\n", self.numbers);
        pr_info!("Rust minimal sample (exit)\n");
    }
}

Compact as it is, this skeleton already demonstrates the chapter's themes: safe code throughout (no unsafe anywhere), fallible allocation carrying its GFP context and error, logging through the printk-backed macros, and lifecycle managed by construction and Drop rather than paired init/exit functions. The listing is lightly abridged: the file in the tree also declares a params block with one i64 parameter, test_parameter (default 1), which init reads through the macro-generated module_parameters::test_parameter.value(), and it reports whether it was built in or loaded by printing !cfg!(MODULE).

A few details reward a closer look. The struct holds a KVec<i32> purely to have some owned, heap-allocated state to manage; it plays no functional role beyond showing that whatever a module allocates in init is freed for it when the module unloads, with no free call to write. The three push calls each take GFP_KERNEL and end in ?, so the module's construction can genuinely fail and report -ENOMEM—and because init returns Result<Self>, a failure there means the module simply does not load, with nothing partially initialized to unwind. The Drop impl prints the vector with the {:?} debug formatter, the same mechanism ordinary Rust uses, here backed by the kernel's logging. None of this is special-purpose sample code; it is exactly the shape a real module's skeleton takes, which is why every driver later in the chapter can be read as this pattern with more inside it. Figure 26-4 shows that lifecycle.

Building and loading the sample takes nothing beyond configuration. With CONFIG_RUST=y, which needs a toolchain that passes make rustavailable (§2.1), enabling SAMPLES, SAMPLES_RUST, and SAMPLE_RUST_MINIMAL=m produces samples/rust/rust_minimal.ko. That file is an ordinary ELF module that modinfo, insmod, and rmmod handle like any other; nothing in the module loader knows it was written in Rust. Loading it with a parameter and then unloading it produces the log below. Every line carries the module name, because the pr_*! macros print through a "%s: %pA" format whose first argument is the __LOG_PREFIX that module! defines (§6.1). The %pA specifier is a Rust-only printk extension that renders a Rust formatting object, so all the formatting is done by Rust's core::fmt inside the call to _printk. 

# insmod samples/rust/rust_minimal.ko test_parameter=5
# rmmod rust_minimal
# dmesg --notime | tail -5
rust_minimal: Rust minimal sample (init)
rust_minimal: Am I built-in? false
rust_minimal: test_parameter: 5
rust_minimal: My numbers are [72, 108, 200]
rust_minimal: Rust minimal sample (exit)

A Misc Character Device

A more realistic sample (samples/rust/rust_misc_device.rs) registers a misc character device—a /dev node userspace can open and drive with read, write, and ioctl—and in doing so exercises most of the chapter. The module registers a MiscDevice whose open, read_iter, write_iter, and ioctl operations are provided by implementing the crate's misc-device trait, an instance of the #[vtable] pattern of §6.2: Rust methods stand in for the C file_operations, and the crate builds the C table and shims. Per-open state—an integer the ioctls get and set, plus a KVVec byte buffer that reads and writes on the same open file share—is kept behind a Mutex, so the data is reachable only while the lock is held, and the lock-holding struct uses the #[pin_data] pinning of §5.2. Values are moved between the driver and userspace with the crate's checked user-pointer accessors rather than raw copy_to_user, and the ioctl handler returns a Result, so an unsupported command or a bad address becomes a clean Err that the crate converts to the negative errno the C caller expects. The registration options name the node with a C-string literal, c"rust-misc-device", and the abstraction always asks for a dynamic minor, so the device appears as /dev/rust-misc-device under the misc major, 10 (Chapter 13).

The sample repays study because each piece of the machinery has a visible job. Opening the device allocates a fresh per-open object and hands it back as a Pin<KBox<Self>>—fallible allocation (§4.2) and pinning (§5.2) meeting in one line—so every open gets its own pinned, heap-allocated state and the kernel ties that object's lifetime to the open file. The trait's associated type, type Ptr = Pin<KBox<Self>>, tells the abstraction how that object is kept in the file's private_data; the later callbacks get it back as a borrow, which read_iter and write_iter fetch through kiocb.file() and ioctl receives directly as a Pin<&Self>. The device registration is itself an owned value, MiscDeviceRegistration, embedded as a pinned field of the module struct—which is why this sample implements InPlaceModule (§6.1) and constructs itself with try_pin_init! rather than returning a plain value: creating it registers the device with the kernel and dropping it deregisters, so the /dev node appears when the module loads and vanishes when it unloads without an explicit unregister call. open is handed that registration and takes a counted reference to the struct device the misc core created for the node, ARef::from(misc.device()) (§5.1); stored in the per-open object as dev: ARef<Device>, it lets every later dev_info! and dev_err! name the device it logs about. When the last reference to the open file goes away, the abstraction's default release converts private_data back into the Pin<KBox<Self>> and drops it. The sample's PinnedDrop impl only logs a farewell; the mutex, the buffer, and the device reference are released by the ordinary field drops that follow.

The data path uses the VFS's iterator-based entry points rather than plain read and write, so the C read(2) and write(2) paths reach it through the same read_iter and write_iter hooks that vectored and asynchronous I/O use (Chapter 16). read_iter receives a Kiocb, the Rust view of struct kiocb that carries the file and the current position, and an IovIterDest wrapping the destination iov_iter. It locks the state and calls iov.simple_read_from_buffer(kiocb.ki_pos_mut(), &inner.buffer), the counterpart of C's simple_read_from_buffer(), which copies from the current position and advances it. write_iter receives an IovIterSource; it locks the state, clears the buffer, and appends the whole incoming iterator with copy_from_iter_vec(&mut inner.buffer, GFP_KERNEL), which grows the KVVec as needed (from kmalloc, or vmalloc for a large write). It then resets the position to zero so the next read starts at the beginning. The two copies run with the mutex held, which is correct here: a Mutex may be held across a page fault, and the buffer being filled or drained is exactly the shared state the lock protects.

The ioctl path shows the user-pointer accessors at work. The three command numbers are compile-time constants built by the const fns _IO, _IOR::<i32>, and _IOW::<i32> from kernel::ioctl, which reproduce the C encoding of include/uapi/asm-generic/ioctl.h (direction, argument size, the type character '|', and numbers 0x80–0x82), so a C program built against the same macros produces identical numbers. The handler turns the raw argument into a UserPtr with UserPtr::from_addr(arg), takes the size encoded in the command with _IOC_SIZE(cmd), and wraps both in a UserSlice. Then, according to direction, it calls .reader() or .writer() to get a UserSliceReader to pull an incoming value in or a UserSliceWriter to push a result back out. Each transfer is checked against the length of that region, and one that does not fit fails with EFAULT instead of reading too much or writing past the buffer. The ordering is deliberate. set_value reads the new value from userspace before taking the lock. get_value copies the value out under the lock, drops the guard explicitly, and only then writes it to userspace. Either way the user access, which can fault and sleep, stays outside the critical section. An unrecognized command is logged with dev_err! and answered with ENOTTY, the conventional “inappropriate ioctl” reply. The file's documentation comment even carries a complete user-space C test program that opens /dev/rust-misc-device, issues the three ioctls, and checks that the value round-trips.

What is notable is how much correctness the code gets for free. The lock cannot be bypassed, because the state is inside it; the user copy cannot overflow, because the accessor checks every length; the ioctl cannot leak on an error path, because there are no manual cleanup paths to leak on; and no allocation can be used unchecked. The same device in C is entirely writable correctly, but nothing in C prevents the mistakes. In the Rust version the compiler rejects an unlocked access, a missed cleanup, or an unchecked allocation outright. An out-of-range user copy is not a compile error, because its length is known only at run time, but the accessor turns it into an ordinary EFAULT rather than memory corruption. That is the whole argument of the chapter reduced to a single small driver: identical behavior, identical performance, but a compiler-checked guarantee that the memory-safety bugs were not made.

A PCI Driver

The misc device's object lives exactly as long as its module. A driver for real hardware is different: its object lives as long as its binding to one device, and the bus, not the module, decides when that begins and ends. The PCI sample (samples/rust/rust_driver_pci.rs) shows the shape every Rust bus driver shares. It drives QEMU's pci-testdev, a virtual test device with vendor ID 0x1b36 (Red Hat) and device ID 0x0005, so it probes in any QEMU guest started with -device pci-testdev. The module boilerplate collapses into one module_pci_driver! invocation, which expands through module_driver! (§6.1) into a module whose only job is to register the driver with the PCI core on load and unregister it on unload. The match table comes from pci_device_table!. It pairs each pci::DeviceId with an IdInfo value of the driver's choosing, which probe receives for the entry that matched. It also emits the MODULE_DEVICE_TABLE alias data, so udev can load the module automatically when a matching device appears. The core of the file, lightly abridged, follows. 

type Bar0 = pci::Bar<{ Regs::END }>;

#[pin_data(PinnedDrop)]
struct SampleDriver {
    pdev: ARef<pci::Device>,
    #[pin]
    bar: Devres<Bar0>,
    index: TestIndex,
}

kernel::pci_device_table!(
    PCI_TABLE,
    MODULE_PCI_TABLE,
    <SampleDriver as pci::Driver>::IdInfo,
    [(pci::DeviceId::from_id(pci::Vendor::REDHAT, 0x5), TestIndex::NO_EVENTFD)]
);

impl pci::Driver for SampleDriver {
    type IdInfo = TestIndex;
    const ID_TABLE: pci::IdTable<Self::IdInfo> = &PCI_TABLE;

    fn probe(pdev: &pci::Device<Core>, info: &Self::IdInfo) -> impl PinInit<Self, Error> {
        pin_init::pin_init_scope(move || {
            pdev.enable_device_mem()?;
            pdev.set_master();

            Ok(try_pin_init!(Self {
                bar <- pdev.iomap_region_sized::<{ Regs::END }>(0, c"rust_driver_pci"),
                index: *info,
                _: {
                    let bar = bar.access(pdev.as_ref())?;
                    dev_info!(pdev, "pci-testdev data-match count: {}\n",
                              Self::testdev(info, bar)?);
                    Self::config_space(pdev);
                },
                pdev: pdev.into(),
            }))
        })
    }

    fn unbind(pdev: &pci::Device<Core>, this: Pin<&Self>) {
        if let Ok(bar) = this.bar.access(pdev.as_ref()) {
            bar.write8(this.index.0, Regs::TEST);   // reset pci-testdev
        }
    }
}

kernel::module_pci_driver! {
    type: SampleDriver,
    name: "rust_driver_pci",
    authors: ["Danilo Krummrich"],
    description: "Rust PCI driver",
    license: "GPL v2",
}

The pci::Driver trait inverts the usual C allocation pattern. A C probe() allocates its private structure, often with devm_kzalloc(), and stores it with pci_set_drvdata(). The Rust probe instead returns an initializer, impl PinInit<Self, Error>, and the adapter's C-callable probe_callback runs it into a pinned KBox and stores the result as the device's driver data. pin_init_scope lets probe run fallible setup with ? before handing the initializer back: here enable_device_mem() and set_master(). Inside try_pin_init!, bar <- runs another initializer: iomap_region_sized::<{ Regs::END }>(0, c"rust_driver_pci") reserves BAR 0, maps it, and yields a Devres<Bar0>. The _: { ... } entry is a block that runs once the fields above it are initialized, so it can already use bar to exercise the device. Finally pdev.into() turns the borrowed device into a counted ARef<pci::Device> the driver keeps. Any ? that fails unwinds only the fields already built, and the PCI core sees the error as a failed probe.

The parameter types carry a second idea, the device context. A Device<Ctx> is the same C struct device viewed through a zero-sized type-state parameter that records what the holder may assume. Normal promises nothing. Bound guarantees that the device is bound to a driver for as long as the reference lives. Core marks a reference valid only inside a bus callback such as probe or unbind, during which the driver core holds the device lock. (CoreInternal is a variant kept private to bus abstractions.) Methods are implemented only for the context that makes them safe: enable_device_mem and set_master exist only on pci::Device<Core>, while iomap_region_sized and config_space need only Device<Bound>. Each context dereferences to the weaker one below it (Core to Bound to Normal), so a stronger reference works wherever a weaker one is asked for, never the reverse. Only the Normal form can be reference-counted, so a reference stored past the callback, like the sample's ARef<pci::Device>, keeps the device alive but drops every guarantee. The rules C states in comments, such as “call this only from probe” or “only while bound,” thus become type errors.

Devres<T> solves the matching lifetime problem for resources. C's devm_* helpers release a resource when the driver unbinds (Chapter 13), but nothing stops other code from keeping the pointer, a classic use-after-unbind bug. A Rust Devres keeps its value inside a Revocable and registers a devres action on the device. During unbind the driver core runs devres_release_all(); the action revokes the value, waiting with synchronize_rcu() for any reader still inside a try_access() section, and only then unmaps the BAR and releases the region. A worker or timer that still holds the Devres afterward gets None from try_access(), not a stale mapping. Code that holds a &Device<Bound> calls access(dev) instead. That returns the plain &Bar0 with no RCU section at all, because a bound reference to the same device proves revocation cannot yet have happened. The check is merely that dev is the device the resource belongs to, failing with EINVAL otherwise.

The mapping itself is typed by its size. Bar0 is pci::Bar<{ Regs::END }>, a BAR known to be at least 16 bytes long (the mapping fails at probe time with EINVAL if the hardware's BAR is smaller), so the accessors read8, read32, and write8 at constant offsets such as Regs::OFFSET are checked with build_assert!. An offset beyond the size or a misaligned one fails the build rather than the machine. When an offset is known only at run time, as in the sample's testdev, which writes to an offset it has just read from the device, the try_ variants (try_write8 and friends) check it at run time and return EINVAL. config_space() gives the same kind of typed accessor for PCI configuration space, which the sample uses to print the revision, vendor ID, and BAR 0 address. Teardown mirrors probe. unbind receives &pci::Device<Core> and a pinned reference to the driver object while the device is still bound, so it can still access the BAR to reset the test device. The driver core then releases the devres resources. After that, a Rust-only post_unbind_rust hook in struct device_driver, called from device_unbind_cleanup(), takes the driver data back and drops it, running the sample's PinnedDrop. The platform, USB, I2C, and auxiliary samples follow the same pattern with their own bus types. So do production drivers such as Nova and Tyr (§8.1).

Rust in the Tree Today

The samples show what the interfaces look like; the real measure of Rust in the kernel is the production code that now uses them. This closing section surveys the Rust drivers and subsystems actually merged in Linux 7.0, and then takes an honest look at where the effort stands and where it is going. The inventory is easy to take, because Rust files are easy to find. Outside rust/, samples/, and the build scripts, 7.0.12 holds 73 .rs files: 71 under drivers/, about 23,000 lines between them, plus one KASAN test and one benchmark. The distribution is very uneven. Two drivers, Binder and nova-core, account for nearly nine lines in ten, and most of the rest are drivers of a few hundred lines each.

The merged code matters because it answers, with evidence rather than argument, the question that hangs over any new language in an old code base: does it actually work at scale? Three different kinds of answer appear in the tree, and they are worth distinguishing. There are reimplementations of existing C drivers—Binder, the null block driver, the ASIX PHY driver, and cpufreq-dt—kept in the tree alongside the originals they duplicate. They prove the language can take over code the kernel already depends on, and they give each new subsystem abstraction a known-good C driver to be checked against. There is greenfield code written in Rust from the first line—Nova, Tyr, the QT2025 PHY, and the TH1520 PWM driver—which has no C counterpart and shows Rust becoming a default choice for new work in some areas. And there are Rust components inside C subsystems, such as the DRM panic screen's QR-code encoder, which C calls through an exported function and which shows the two languages mixed at a finer grain than a whole driver. The size of a driver says little about its category: the reimplementations range from Binder's nine thousand lines to the ASIX PHY's hundred-odd, and the greenfield drivers from nova-core's ten thousand to the PWM driver's four hundred. Together they show Rust moving from proof-of-concept to production across quite different parts of the kernel.

Real Drivers: Binder, Nova, PHY

Rust is past the toy stage: the tree carries 71 real .rs driver files, several of them substantial. The most prominent is a from-scratch Rust rewrite of Binder (drivers/android/binder/), the Android IPC driver that is one of the most security-sensitive and heavily-fuzzed pieces of the kernel—precisely the kind of complex, attack-exposed code whose memory-safety bugs Rust is meant to prevent. Graphics is another frontier: Nova (drivers/gpu/drm/nova/ and the drivers/gpu/nova-core/ support driver), a new driver for modern NVIDIA GPUs, is being written in Rust from the start, as is Tyr (drivers/gpu/drm/tyr/), a DRM driver for Arm Mali GPUs built on the CSF firmware interface; even the DRM core carries Rust, in the encoder that draws the panic message as a QR code from inside the panic handler (drivers/gpu/drm/drm_panic_qr.rs). Networking has merged Rust PHY drivers (drivers/net/phy/), and there are Rust drivers for null block devices, cpufreq, and PWM, plus the growing set of bus and subsystem samples. Table 26-8 lists them all.

The three drivers in this section's title mark the range. Binder is the strongest evidence, because it is not a leaf driver but a whole complex subsystem: process and thread state, transactions, nodes, a memory-range allocator, and statistics, mirroring the structure of the C driver it can replace, and carrying the Android IPC that every app on a device depends on. That a body of code this large and this security-critical can be written mostly in safe Rust, with its unsafe gathered where it still meets C, is the clearest evidence that the language scales to real subsystems. Nova is the greenfield case: rather than extend the aging nouveau driver, it is a fresh driver for modern NVIDIA GPUs, split into a DRM front end and a lower layer for the firmware and hardware details—an architecture chosen freely because the code was new. The PHY drivers are the everyday case: small, self-contained network-transceiver drivers of the sort the kernel has thousands of in C, now written in Rust with no drama, which is exactly the unremarkable adoption the whole effort was meant to enable. The paragraphs below take the large drivers first and then the small ones.

A closer look at Binder shows what porting a large C driver involves. The Rust driver is 18 files and about 9,300 lines, built as a single object, rust_binder, and only built in: ANDROID_BINDER_IPC_RUST is a bool, like its C counterpart. User space sees no difference. Both drivers implement the same include/uapi/linux/android/binder.h interface, and the ANDROID_BINDER_DEVICES list of device nodes applies to either. Three small C files remain in the directory, and they show where the boundary still falls. The first, rust_binderfs.c, is the driver's own copy of binderfs, the per-IPC-namespace pseudo-filesystem that creates the binder device nodes; it calls into Rust through a handful of #[no_mangle] functions such as rust_binder_new_context. Because the device nodes are created by this C filesystem rather than by the misc-device abstraction of §7.2, the Rust side builds its file_operations, rust_binder_fops, directly from the raw bindings, which is much of the reason Binder holds most of the drivers' unsafe blocks (§3). The second, rust_binder_events.c, defines the tracepoints. Its probes read fields of Rust objects through a table of field offsets, RUST_BINDER_LAYOUT, that the Rust code exports, so the C side never needs to know the Rust layout. The third, page_range_helper.c, is a small helper for the page-range code. Not everything was a straight translation. The buffer allocator, for instance, starts as a small sorted KVec of ranges and switches to a pair of RBTrees, one for allocated and one for free ranges, once a process holds more than eight buffers. The unused pages of a process's buffer area are given back under memory pressure by a shrinker in page_range.rs. The port also shows how the kernel crate grows. A comment in deferred_close.rs records that its logic for closing files from a task-work callback was proposed for kernel::fs and rejected there for being too Binder-specific, so it stays in the driver.

Nova shows a different shape. nova-core (36 files, about 10,500 lines) is a PCI driver for NVIDIA GPUs from Turing onward; its chipset table covers the Turing, Ampere, and Ada families. Modern NVIDIA GPUs are driven through the GPU System Processor (GSP), a RISC-V core that runs NVIDIA's own firmware, so most of nova-core is a boot loader for that firmware. Probe waits for the GPU's boot ROM (GFW) to finish, parses the video BIOS, and runs its FWSEC firmware to carve out a protected memory region. It then loads the Booter firmware on the SEC2 microcontroller, which places the GSP firmware in that region, waits for the GSP's RISC-V core to come up, and runs the command sequence the firmware requests. Finally it talks to the running GSP over a shared-memory command queue, the first exchange being a query for the GPU's name. The firmware files, version 570.144, are loaded from nvidia/<chip>/gsp/, and the firmware abstraction emits the matching MODULE_FIRMWARE entries at compile time. nova-core then creates an auxiliary-bus device, nova-drm, to which the separate nova DRM driver (4 files, about 200 lines) binds. That driver so far offers three ioctls: a parameter query and GEM buffer creation and lookup. Register definitions are generated by a register! macro local to the driver, which gives each register a typed accessor with named bitfields; it is the macro the PCI sample's comment hopes to see move into the shared crate (§7.3). Both Kconfig entries still warn that the driver “is work in progress and may not be functional”: in 7.0 Nova brings the GPU up but does not yet render or compute.

Tyr (6 files, about 600 lines) is Nova's counterpart for Arm GPUs, a platform driver for Mali GPUs with the Command Stream Frontend (CSF). It matches the rockchip,rk3588-mali and arm,mali-valhall-csf device-tree compatibles. Its probe enables the clocks and the mali and sram regulators through the clk and regulator abstractions, soft-resets the GPU, powers up the L2 cache, reads the GPU's identification registers, and registers a DRM device. Tyr does not define a new interface to user space. It implements the uAPI of panthor, the C driver for the same hardware, and in 7.0 offers its first ioctl, DEV_QUERY, through which user space written for panthor can identify the GPU. Like Nova it is marked work in progress.

The smaller drivers fill in the rest. The two PHY drivers show both sides of the port-versus-new split within one subsystem. ax88796b_rust.rs, the first Rust driver merged (6.8), covers the same three ASIX PHYs as the C ax88796b.c. Kconfig calls it a “reference driver” with equivalent features and offers it as a bool choice within the C driver's option. qt2025.rs (6.12) is new: it drives the AMCC QT2025 10-gigabit SFP+ PHY used on Tehuti TN40xx network cards, and it was the first Rust driver to load firmware, writing qt2025-2.0.3.3.fw into the PHY's built-in 8051 microcontroller over Clause 45 MDIO. rnull (6.11) reimplements the C null_blk test device on the block::mq abstractions, and since 6.18 it is configured like null_blk, through configfs: each directory created under /sys/kernel/config/rnull/ is a device whose blocksize, size, rotational, and irqmode attributes are set before writing power. rcpufreq_dt.rs (6.16) is a Rust version of the generic cpufreq-dt driver, built on the cpufreq, opp, and clk abstractions, and pwm_th1520.rs (6.19) drives the PWM controller of the T-Head TH1520 RISC-V SoC through the PWM subsystem's waveform interface.

Finally, Rust reaches into C subsystems at a finer grain than a driver. The DRM panic QR encoder (6.12) is not a driver at all but a component of the C panic code. When DRM_PANIC_SCREEN_QR_CODE is set, drm_panic.c compresses the tail of the kernel log with zlib and calls the Rust functions drm_panic_qr_generate and drm_panic_qr_max_data_size, both marked #[export] (§6) so that their signatures are checked against the C header. The encoder has to work inside the panic handler, with no allocation, in buffers the C side preallocated. Two non-driver files test Rust against existing C infrastructure. mm/kasan/kasan_test_rust.rs commits a deliberate use-after-free that the C KASAN KUnit suite expects to catch, proving that Rust code is instrumented by the sanitizer like C, and lib/find_bit_benchmark_rust.rs times the Rust bitmap API against the C find_*_bit() benchmark it mirrors.

The Road Ahead

For all this progress, Rust in the kernel remains young, and its central limitation is simple: a Rust driver can only be as complete as the safe abstractions available to it, and much of the kernel's vast C API is not yet wrapped. Writing a driver for a subsystem whose Rust bindings are thin still means extending the kernel crate first—a significant effort that must be reviewed by both the subsystem's C maintainers and the Rust maintainers. So the frontier advances abstraction by abstraction, each new wrapper opening a subsystem to Rust, and the work is as much social as technical: two communities, with different tools and instincts, learning to maintain one kernel together. There have been genuine tensions over that collaboration, and they are part of the honest picture.

The rules and the record of that collaboration are both in the tree. The rule is the one §1.2 quoted from Documentation/rust/general-information.rst: drivers do not call the C bindings directly, and subsystems provide the abstractions they need instead. That is why nearly every driver above arrived together with, or just after, the abstractions it needed—the PHY library for the ASIX driver, firmware loading for QT2025, the block multiqueue layer for rnull, and the PCI, DMA, firmware, and auxiliary-bus abstractions for Nova. The record is in MAINTAINERS. In 7.0.12 more than fifty of its entries cover Rust files. About half are entries added for Rust, usually marked [RUST], such as PCI SUBSYSTEM [RUST] or DRM DRIVERS AND COMMON INFRASTRUCTURE [RUST], and they normally list the C subsystem's own maintainers or reviewers next to the Rust developers. The rest are the existing C entries themselves—the VFS, RCU, locking, the driver core, KUnit, the clock and regulator frameworks, and others—which now list the Rust abstraction files alongside their C sources. A subsystem's maintainers decide whether and how Rust enters it, and once it has, they are responsible for both languages.

The status of the effort changed during the 7.0 cycle. At the 2025 Maintainers Summit the experiment that began in 6.1 was declared concluded, and commit 9fa7153c31a3 (“rust: conclude the Rust experiment”), merged for 7.0, removed the section of Documentation/rust/index.rst that had described Rust support as experimental. The commit message notes that the label had already ceased to be fully accurate: Rust was in production use, some well-known distributions enabled it, and it was in millions of devices via Android. It is equally careful about what the decision does not mean. Not every kernel configuration, architecture, and toolchain works, and some combinations, mixed GCC and LLVM builds and the coming GCC-based Rust support among them, remain “quite experimental.” The list of open work follows from earlier sections. The kernel still depends on unstable compiler features that must be stabilized upstream before it can build with an ordinary stable Rust (§2.1). The toolchain story still assumes LLVM. And each subsystem that wants Rust drivers must first acquire and maintain its abstractions.

It is worth being equally candid about the limits, because overselling Rust would misrepresent where things stand. Rust is not being used to rewrite the kernel's core: the scheduler, the memory manager, the VFS, and the other subsystems this book has described are C and will remain C, both because rewriting working, exhaustively tested code carries risk with little reward and because those subsystems are exactly the deeply interconnected core that the leaf-first strategy deliberately avoids. The tree bears this out: kernel/, fs/, net/, block/, ipc/, and arch/ contain no Rust at all, and mm/ and lib/ one test file each. Nor does Rust make a driver automatically correct—its guarantee is the absence of memory-safety bugs and data races in safe code, not the absence of logic errors, deadlocks, or mistakes in the unsafe blocks and C code it builds on. And the coexistence is not a transitional phase on the way to a Rust kernel; it is the intended end state. A running kernel that mixes C and Rust, with each language used where it fits, is what the effort is building toward, not a milestone to be passed through. Holding these limits in view is what keeps the case for Rust credible rather than hype.

Yet the trajectory is clear. Each release wraps more of the kernel and merges more Rust drivers, and with the experiment concluded the language has moved from trial to expectation. The argument underneath it does not weaken: the kernel's worst bugs are memory-safety bugs, and here is a language that makes them compile errors, at no runtime cost, for the new code most likely to contain them. Rust will not replace the C kernel this book describes—the two will coexist for a very long time—but it has become a permanent second tool in the kernel's workshop, and the parts of Linux written in it will only grow. That makes this a fitting place to end the book: not at a finished kernel, but at a kernel still acquiring new ways to be built, in the most literal sense, more safely.

Summary

This chapter described Rust in the Linux kernel, the ability—added in Linux 6.1 as an experiment and, since the 7.0 cycle, a permanent part of the kernel—to write kernel code in a language whose compiler proves, before the code runs, that safe code cannot cause the memory-safety and data-race bugs behind most severe kernel vulnerabilities. Ownership and borrow checking turn use-after-free, double-free, and data races into compile errors at no run-time cost. The few checks that must wait for run time, such as slice bounds and integer overflow, end in a panic that the kernel turns into BUG(), and the crate's atomics follow the Linux Kernel Memory Model, so Rust and C agree on every barrier. The effort is deliberately scoped. Rust is for new leaf code, chiefly drivers, not a rewrite of the C core, and it is optional: the RUST option appears only when make rustavailable finds at least rustc 1.78 and bindgen 0.65.1, and only on architectures that select HAVE_RUST, x86-64 and arm64 among them.

The build makes the two languages link as one. bindgen projects the C headers into an all-unsafe bindings crate on every build, and small C helpers expose the static inline functions and macros it cannot see. rust/Makefile compiles core, the support crates, the bindings, and the kernel crate, in dependency order, into ordinary objects in vmlinux, and exports their symbols with EXPORT_SYMBOL_GPL so that modules can link against them. Each driver is one crate compiled into one object, limited to a fenced list of unstable features, and rustc is configured per architecture to generate code by the C compiler's rules: no floating-point registers, the same speculation mitigations and CFI hashes, and the same static-key and WARN tables.

The heart of the design is the safe/unsafe boundary. The kernel crate wraps the bindings in safe abstractions, each unsafe block justified by a // SAFETY: comment and reviewed once on behalf of every user, so that drivers need little or no unsafe of their own; about nine in ten of the tree's unsafe blocks sit inside the crate, and its 77 public modules double as a map of what can be written in Rust today. Above the boundary the crate reshapes Rust for the kernel: Result and ? over the familiar errnos, with an Error no larger than the C int it replaces; fallible allocation through KBox, KVec, and their vmalloc and kvmalloc variants, which take explicit GFP flags and leave no global heap; Arc for Rust-owned and ARef for C-refcounted objects, with Opaque for C structures Rust must not interpret; pinned in-place initialization through pin_init! for objects that must never move; and Mutex and SpinLock types that contain the data they guard and register with lockdep, so shared state cannot be touched unlocked while lock-ordering mistakes are still caught at run time.

The module! macro turns a type implementing Module into a loadable module, generating the same init and exit symbols, initcall entry, and .modinfo strings as the C macros, with teardown left to Drop; most drivers reach it through a module_*_driver! macro. #[vtable] lets a trait implementation fill a C operations table, recording which optional methods exist so that C sees a null pointer where it expects one. The kernel's samples put these together: a minimal module with no unsafe and no exit function, a misc device whose state is reachable only under its lock and whose user copies are length-checked, and a PCI driver whose device contexts make “only in probe” and “only while bound” into type errors and whose Devres mappings are revoked when the device unbinds.

In 7.0.12 that machinery carries real code: 71 driver files, led by a Rust reimplementation of Binder and the new Nova and Tyr GPU drivers, together with PHY, block, cpufreq, and PWM drivers and a QR-code encoder inside the C panic path. The core subsystems remain C, and Rust is meant to coexist with them rather than replace them. What changed in 7.0 is the label. With the experiment declared concluded, the remaining work—unstable compiler features, the dependence on LLVM, and abstractions built subsystem by subsystem—is the ordinary business of a permanent second language, one that makes an entire class of the kernel's worst failures impossible in the new code written in it.
