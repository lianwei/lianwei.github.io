Security in the kernel is not one subsystem but a stack of them. A process carries an identity and a set of privileges; mandatory access control modules decide, at hundreds of hook points, whether that identity may do what it asks; integrity machinery establishes whether the code and data involved are the ones somebody intended; cryptography and key management keep secrets secret and make signatures checkable; audit writes down what happened; and a final layer of lockdown and compiler hardening protects the kernel against the possibility that every one of the layers above has been bypassed by a memory-corruption bug.

Earlier chapters have already described several of these pieces where they naturally belong. Chapter 20 covers credentials, capabilities, the credential system calls, and — in §7.1 of that chapter — the Linux Security Modules framework itself, its hook lists, stacking, and the lsm_* system calls, together with seccomp, Landlock, and Yama. Chapter 25 explains how capabilities are scoped by user namespaces; Chapter 10 explains how audit hooks the system-call path; Chapter 18 introduces fscrypt and fs-verity from the filesystem's side; and Appendix B follows a module signature from the build to load_module(). This chapter supplies what those sections assume: the modules that answer the hooks (§2), the crypto API they all call and the random number generator beside it (§3), the keyrings that anchor every signature check (§4), the integrity subsystems (§5 and §6), the audit pipeline (§7), lockdown (§8), and the hardening options that turn the kernel's own memory into a harder target (§9).

The Security Architecture in Layers

Each piece of security infrastructure answers one question about an operation: who is asking, whether policy allows it, whether the code and data involved are genuine, how secrets and signatures are handled, what is recorded, and whether the kernel itself can still be trusted to enforce the answers. The pieces form layers because the higher ones call the lower ones — an LSM hook may consult IMA, IMA calls the crypto API and the keyrings, and all of them rely on lockdown and hardening to keep their own code and data intact — and because the hardware beneath them, from CPU crypto instructions to the TPM, differs between x86_64 and ARM64 while the software interfaces do not.

Security Since Linux 2.6

Security in Linux 2.6.11 went beyond process credentials, the capability bits, and the Linux Security Modules hooks. The kernel's first git commit (2.6.12-rc2, imported in April 2005) already contains security/selinux/avc.c, security/keys/ with request_key.c and user_defined.c, kernel/audit.c and kernel/auditsc.c, and crypto/api.c. They were small: crypto/api.c was 233 lines and kernel/audit.c 839.

Everything else in this chapter arrived later, and most of it arrived for one of two reasons. The first was a change in the threat model. Once firmware could verify the bootloader, and the bootloader the kernel (UEFI Secure Boot), the root user stopped being the top of the trust hierarchy: a kernel booted under Secure Boot must not let uid 0 load unsigned code, and that requirement produced module signing, the system keyrings, kexec_file_load() signature checks, and the lockdown LSM (5.4). The second was the attack data. After years of kernel exploits built from the same handful of primitives — stack overflows, use-after-free on slab objects, overwritten function pointers, leaked kernel addresses — the kernel grew a matching set of defences: hardened usercopy (4.8), FORTIFY_SOURCE (4.13), slab freelist hardening (4.14), heap initialization on allocation (5.3), control-flow integrity in the compiler (5.13, redesigned as kCFI in 6.1), and hardware branch-target and pointer-authentication checks on both architectures.

The modules themselves multiplied too. Smack arrived in 2.6.25, IMA and TOMOYO in 2.6.30, AppArmor in 2.6.36, EVM in 3.2, Yama and dm-verity in 3.4, LoadPin in 4.7, SafeSetID in 5.1, fs-verity and lockdown in 5.4, the BPF LSM in 5.7, Landlock in 5.13, and the Integrity Policy Enforcement LSM in 6.12. The framework that hosts them changed shape underneath. In 2.6.11 it was a single struct security_operations table filled in by one primary module, which had to forward calls to a secondary module by hand. 4.2 replaced the table with per-hook lists (security_hook_heads); 5.1 put the per-object security blobs under the framework's control and added the lsm= ordering; 6.8 gave every module a numeric ID and the lsm_* system calls; 6.9 turned IMA and EVM from hard-wired calls into ordinary LSMs; and 6.12 replaced the list walks with static calls. Linux 7.0.12 defines 276 hooks in include/linux/lsm_hook_defs.h and fourteen modules under security/, and since 6.19 the boot-time ordering and blob sizing live in their own file, security/lsm_init.c. The kernel crypto API, once a handful of software ciphers, now registers several hundred algorithm implementations, with separate code paths for the AES instructions of both architectures and a parallel library interface in lib/crypto/ for callers that need one fixed algorithm and no indirection.

A third pressure is more recent: the kernel can no longer assume that the hardware and the platform around it are honest either. A TPM on a motherboard bus can be sniffed or impersonated by an interposer, so since 6.10 the kernel can wrap its TPM traffic in HMAC and encrypted sessions (§4.4). A confidential virtual machine on AMD SEV-SNP, Intel TDX or Arm CCA does not trust its host at all (Chapter 28); its kernel obtains a signed attestation report through the configfs TSM_REPORTS interface (6.7) in drivers/virt/coco/, and on SEV-SNP it can use a virtual TPM run by the guest's own Secure VM Service Module instead of one supplied by the host (drivers/char/tpm/tpm_svsm.c, 6.16). Since 6.19 the same distrust reaches PCIe devices: with CONFIG_PCI_TSM, writing the name of a platform security manager such as tsm0 (from /sys/class/tsm) to a device's tsm/connect attribute makes drivers/pci/tsm.c authenticate the device over an SPDM session and turn on PCIe IDE link encryption, following the TDISP protocol; AMD SEV-TIO (drivers/crypto/ccp/sev-dev-tsm.c) is the first back end, and pci_tsm_bind(), which will assign a device interface to a confidential VM, has no in-tree caller yet in 7.0. And the expected arrival of quantum computers that break RSA and ECDSA has started to show up in the signature code: 7.0 adds the post-quantum ML-DSA scheme of NIST FIPS 204 to the crypto API and the X.509 and PKCS#7 parsers, allows module signing with ML-DSA keys, and drops SHA-1 as a module-signing digest.

Six Layers and a Hardware Floor

Figure 27-1 arranges the infrastructure into six layers. The order is deliberate: each layer assumes the ones below it. A MAC decision means nothing if the subject's credentials can be forged; an integrity measurement means nothing if the hash function can be swapped out; an audit trail means nothing if the kernel that writes it can be patched by a root process at run time. Lockdown and hardening sit on top because they are the layers that keep the kernel's own code and data trustworthy, and every other layer is code and data in that kernel.

Read from the bottom up, the layers answer six different questions. Who is asking? is answered by struct cred: user and group ids, capability sets, the keyrings a task can search, and a pointer to every security module's private view of the task. May this subject do this to that object? is answered first by discretionary checks and capabilities and then by the LSM hooks, which can only refuse. Is this the code or data somebody vouched for? is the integrity layer's question; IMA, EVM, fs-verity, dm-verity, and module signatures each answer it for a different kind of object, and IPE turns their answers into policy. Can anyone else read or change it? is the job of the crypto API and the key retention service. What happened? is answered by audit. And can the kernel still be trusted to answer the other five? is the concern of lockdown, which removes the interfaces through which a privileged process could rewrite the kernel, and of the hardening options, which make it harder for a bug to do the same thing.

The layers also share plumbing, and that is one reason to study them together. The integrity modules call the crypto API to hash files and verify signatures; the crypto API's asymmetric algorithms are reached through the asymmetric key type; the system keyrings decide which signatures count; IMA records its verdicts through audit; IMA, EVM, and IPE are themselves LSMs and therefore live in the same hook lists as SELinux; and the lockdown level is itself an LSM hook, security_locked_down(), that dozens of drivers consult. Underneath all of them sits the random number generator of §3.5, from which keys, nonces, salts and stack canaries are drawn.

Each layer also has its own user-space surface, and knowing which file or system call belongs to which layer is much of what an administrator needs. Credentials appear in /proc/pid/status and change through the set*id() and capset() calls. LSM state is read and written through /proc/pid/attr/ and, since 6.8, the lsm_get_self_attr(), lsm_set_self_attr() and lsm_list_modules() system calls. SELinux keeps its policy interface in its own selinuxfs; AppArmor, TOMOYO, LoadPin, SafeSetID and IPE use directories in securityfs, mounted at /sys/kernel/security, whose lsm file lists the active modules in order. Integrity is visible there too: ima/ascii_runtime_measurements and ima/policy, the evm switch, and the firmware event log in tpm0/binary_bios_measurements. Keys are managed with add_key(), request_key() and keyctl() and listed in /proc/keys; the crypto API shows its registry in /proc/crypto and accepts work through AF_ALG sockets; the RNG answers getrandom(); audit talks to auditd over NETLINK_AUDIT; and the lockdown level is the single file /sys/kernel/security/lockdown. Hardening has almost no run-time interface: it is chosen when the kernel is built and on its command line, with a few sysctls such as kernel.kptr_restrict, kernel.dmesg_restrict and kernel.unprivileged_bpf_disabled (§9.3).

Loading a kernel module shows the layers working on one request, because it passes through all of them in turn. finit_module() first calls may_init_module(), which demands CAP_SYS_MODULE in the initial user namespace and refuses everything once kernel.modules_disabled is set; that is the identity layer. kernel_read_file() then reads the image and calls security_kernel_read_file() and security_kernel_post_read_file() with READING_MODULE, and in that one hook list access control and integrity meet. SELinux checks the system:module_load permission against the file's label; LoadPin insists that every module come from the filesystem the first one came from; IPE evaluates its op=KERNEL_MODULE rules; and IMA, if its policy has a MODULE_CHECK rule, hashes the image through the crypto API, extends a TPM PCR, and appraises the hash against a signature in security.ima or the module's own appended signature, checked against the .ima keyring.

load_module() next calls module_sig_check(). A module that ends in the ~Module signature appended~ marker goes to verify_pkcs7_signature() with the secondary keyring, where the crypto API's sig transforms check an RSA, ECDSA or ML-DSA signature; a signature that is present but wrong is always fatal. An unsigned module is refused if module.sig_enforce is set and otherwise loads only if security_locked_down(LOCKDOWN_MODULE_SIGNATURE) allows it, which is the lockdown layer's say. audit_log_kern_module() attaches the module's name to the system call's audit record. Finally, after relocation, module_enable_rodata_ro(), module_enable_data_nx() and module_enable_text_rox() give the module the same W^X layout as the core kernel, and on x86_64 module_finalize() seals its unused ENDBR instructions and rewrites its kCFI call sites for FineIBT just as boot did for vmlinux. Each step belongs to a different layer, and the module runs only if every one of them agrees.

Two Architectures, One Model

Almost all of this infrastructure is architecture-independent C, but it leans on hardware in six places, and x86_64 and ARM64 provide that hardware differently. Table 27-8 in §9.2 lists the features side by side.

The first is cryptographic and random-number instructions. x86_64 has AES-NI, PCLMULQDQ for GHASH, the SHA extensions, and the wider VAES and VPCLMULQDQ forms for AVX2 and AVX-512; ARM64 has the ARMv8 Cryptography Extensions (AESE, AESMC, PMULL, and the SHA-1/SHA-2/SHA-3 instructions) used through kernel-mode NEON. The crypto API hides the difference behind algorithm priorities, and the lib/crypto functions behind per-architecture back ends (§3.4). Both architectures also have random-number instructions — RDRAND and RDSEED on x86_64, RNDR and RNDRRS (ARMv8.5) on ARM64 — that seed the kernel's random number generator but are never trusted as its only source (§3.5).

The second is a hardware root of trust. PCs usually carry a discrete or firmware TPM on the LPC, SPI, or I2C bus, reached through the TIS or CRB interfaces. Many ARM64 systems instead implement the TPM as a trusted application in TrustZone (the firmware TPM driver drivers/char/tpm/tpm_ftpm_tee.c), reach a TPM in the secure world through the CRB interface carried over Arm's Firmware Framework (tpm_crb_ffa.c, 6.15), or seal keys directly with a TEE or a SoC key block, which is why trusted keys have several back ends (§4.4). A confidential guest on SEV-SNP can use a virtual TPM provided by its own Secure VM Service Module (tpm_svsm.c, 6.16).

The third is boot verification. UEFI Secure Boot is available on both architectures, and the kernel's EFI stub, its platform keyring and its lockdown code treat them the same way (§8.2). What differs is the firmware below UEFI: on ARM64 the earlier boot stages run in Trusted Firmware-A and the secure world, and the chain of trust usually starts in the SoC's boot ROM rather than in a PC firmware image.

The fourth is separating the kernel from user memory. x86_64 has SMEP and SMAP (3.7), which fault if the kernel executes or touches a user page outside stac()/clac() brackets, and since 6.19 Linear Address Space Separation (LASS, Chapter 2) also blocks kernel-mode accesses to the user half of the address space by address alone; ARM64 has the PXN page-table bit, Privileged Access Never (PAN, 4.3) and Enhanced PAN, which play the same roles, and since 7.0 PAN support is always built. ARM64 adds memory tagging (MTE), which CONFIG_KASAN_HW_TAGS uses to catch use-after-free and out-of-bounds accesses in production kernels at low cost; x86_64 has no equivalent.

The fifth is control-flow protection. x86_64 has Indirect Branch Tracking and user-space shadow stacks (CET); ARM64 has Branch Target Identification, Pointer Authentication, and the Guarded Control Stack. The kernel uses only a subset for itself: IBT, or FineIBT combined with kCFI, on x86_64, and BTI, PAC and the software shadow call stack on ARM64. Shadow stacks and the Guarded Control Stack (6.6 and 6.13) protect user processes only (§9.2).

The sixth is confidential computing, where the hardware protects a guest from the hypervisor. AMD SEV-SNP and Intel TDX encrypt and integrity-protect guest memory on x86_64; Arm's Confidential Compute Architecture does the same with Realms on ARM64. The guest-side drivers in drivers/virt/coco/ (sev-guest, tdx-guest, arm-cca-guest) all export their attestation reports through the same configfs TSM_REPORTS interface, so user space asks for evidence the same way on both architectures (Chapter 28).

The Major Security Modules

Chapter 20, §7.1 describes the LSM framework: the hook definitions in include/linux/lsm_hook_defs.h, dispatch through static calls, stacking, the fixed first and last positions, and the lsm_* system calls. A hook is only half of a security module, though. The other half is per-object state: a label on every inode, task, socket and IPC object, kept in blobs whose sizes the framework adds up at boot so that several modules can share one allocation. The three modules that implement complete mandatory-access-control policies use that state very differently — SELinux attaches type-enforcement labels and caches decisions in its access vector cache, AppArmor attaches profiles that match pathnames against compiled DFAs, and Smack compares short text labels against a rule list. Because their labels would conflict, only one of them can be active at a time, but each stacks with the minor modules, the BPF LSM, and the integrity modules. The minor modules are the other half of the picture: TOMOYO, Yama, LoadPin and SafeSetID each enforce one kind of restriction in a few hundred lines, and the BPF LSM registers a stub on every hook so that a policy can be loaded as a program.

Blobs, Order, and Exclusivity

In Linux 2.6 an LSM owned the security pointer in each kernel object outright, which is one reason only one module could be active. Stacking required turning that pointer into a shared allocation. Each module now describes how much space it needs in a struct lsm_blob_sizes, with one field per object type — lbs_cred, lbs_file, lbs_inode, lbs_task, lbs_sock, lbs_superblock, lbs_ipc, lbs_msg_msg, lbs_key, lbs_perf_event, lbs_tun_dev, lbs_ib for InfiniBand, lbs_bdev for block devices, lbs_bpf_map, lbs_bpf_prog and lbs_bpf_token for BPF objects, and, new in the 7.0.y stable series, lbs_backing_file — and during boot the framework converts each request into an offset within one combined blob per object: 

/* security/lsm_init.c */
static void __init lsm_blob_size_update(unsigned int *sz_req,
					unsigned int *sz_cur)
{
	unsigned int offset;

	if (*sz_req == 0)
		return;

	offset = ALIGN(*sz_cur, sizeof(void *));
	*sz_cur = offset + *sz_req;
	*sz_req = offset;
}

The trick is in the last line: the module's own lsm_blob_sizes structure is rewritten in place, so that after initialization the field that held a size holds the module's offset. Every module's accessor then becomes a single addition. SELinux, for example, finds its credential state with selinux_cred(), which returns cred->security + selinux_blob_sizes.lbs_cred, and its inode state with selinux_inode(), which does the same with inode->i_security and lbs_inode. Figure 27-2 shows the resulting layout for a typical stack. The inode blob is special in one respect: it is freed through RCU, so lsm_prepare() reserves a struct rcu_head at offset zero before the first module's area, and the blob comes from a dedicated slab cache, lsm_inode_cache.

Two of the fields are not object blobs in the usual sense. lbs_xattr_count (6.6) is the number of extended attributes a module may want to write when a new inode is created. security_inode_init_security() allocates one array with a slot for every module's attributes, lets each module's inode_init_security hook fill its slots — SELinux writes security.selinux, Smack up to two SMACK64 attributes — and, because EVM is ordered last, reaches EVM's hook only after the others, so that EVM can compute security.evm over the attributes they have just produced, before the filesystem writes them all with the new inode. lbs_backing_file gives modules state on the hidden backing file that overlayfs and FUSE passthrough open on the lower filesystem. Before it existed, an mmap() or mprotect() of an overlayfs file was checked only against the upper file the user opened, never against the lower file whose pages were actually mapped. The fix added the backing_file_alloc, backing_file_free and mmap_backing_file hooks in 7.1 and was backported to 7.0.4, together with an SELinux change that uses them.

The framework's own initialization code moved in 6.19 from security/security.c into a new file, security/lsm_init.c, in a series that also gave struct lsm_info a set of initcall slots. A module is declared with DEFINE_LSM() (or DEFINE_EARLY_LSM() for the few that must run before the memory allocators are fully up), which places a struct lsm_info in the .lsm_info.init section. The structure names the module through its struct lsm_id, gives its order and flags, points at its blob sizes, and supplies an init function plus optional initcall_pure, initcall_early, initcall_core, initcall_subsys, initcall_fs, initcall_device, and initcall_late callbacks. Before 6.19 each module registered its securityfs files and late setup with ordinary initcalls of its own; now the framework runs them in module order, which lets it skip modules that were configured but not enabled.

The order itself is computed by lsm_order_parse(). It appends every LSM_ORDER_FIRST module (only capability), then the names in the lsm= boot parameter or, without it, in CONFIG_LSM, then every LSM_ORDER_LAST module (IMA and EVM). Names of modules that were not built are ignored, and a module missing from the list is disabled — so a kernel booted with lsm=selinux runs without Yama or Landlock. A module can also be switched off by its own parameter, such as selinux=0 or apparmor=0. The legacy security= parameter still works, but only when lsm= is absent; it disables every other LSM_FLAG_LEGACY_MAJOR module and appends the chosen one. Booting with lsm.debug logs each decision, and the result is the ordered list in /sys/kernel/security/lsm. The default CONFIG_LSM in 7.0.12 is landlock,lockdown,yama,loadpin,safesetid,selinux,smack,tomoyo,apparmor,ipe,bpf; distributions trim it to the modules they use.

Two flags in lsm_info preserve history. LSM_FLAG_LEGACY_MAJOR marks the modules that the old security= boot parameter could select — SELinux, AppArmor, Smack, and TOMOYO — and LSM_FLAG_EXCLUSIVE marks the modules that still cannot share the kernel with each other. SELinux, Smack, and AppArmor carry both flags, so in 7.0.12 only one of the three can be active, however the lsm= list is written: the first exclusive module in the list is selected, and any later one is skipped. The constraint is no longer about blob space — the blobs above would accommodate all three — but about the interfaces that assume a single answer: the /proc/pid/attr files, the secmark and NetLabel packet-labeling machinery, and the "security context" strings that audit, D-Bus, and the network stack carry around. TOMOYO, Landlock, Yama, LoadPin, SafeSetID, IPE, the BPF LSM, and the integrity modules are not exclusive and can be stacked with any of the three.

Those interfaces are being rewritten one at a time so that the flag can eventually go. For twenty years a "secid", one u32, was how audit rules, IPC, NetLabel and the network stack carried a security label without knowing which module produced it. 6.13 replaced it in the internal interfaces with struct lsm_prop, which has one member for each module that has such an identifier — selinux, smack, apparmor and bpf — so that hooks such as security_current_getlsmprop_subj() can return all of them at once. 6.14 did the same for context strings: struct lsm_context carries the text, its length, and the ID of the module that produced it; security_release_secctx() offers the structure to every module, and only the one whose ID matches frees it. In 6.18 audit learned to log more than one subject context. Each module that supplies one registers with audit_cfg_lsm(); if more than one does, the record carries subj=? and a separate AUDIT_MAC_TASK_CONTEXTS record lists every module's context. Only the three exclusive modules register, so a 7.0.12 kernel still writes a single subj= field, but nothing in the audit format now assumes there is only one.

SELinux: Labels, Policy, and the AVC

SELinux attaches a security context — a string such as system_u:system_r:sshd_t:s0, made of user, role, type, and MLS level fields — to every subject and object, and decides each access by looking up the pair of types in a compiled policy. The kernel never handles the strings on its fast paths. security_context_to_sid() maps each distinct context to a 32-bit security identifier (SID) in the SID table (security/selinux/ss/sidtab.c), and the per-object blobs hold only SIDs: the task's credential blob, struct cred_security_struct, has sid, osid, and the exec_sid, create_sid, keycreate_sid, and sockcreate_sid overrides that /proc/self/attr writes set; an inode's struct inode_security_struct has a sid, an object sclass, and an initialized state. Until 6.18 the credential structure was still called task_security_struct, a name left over from before credentials were split from tasks; 6.18 renamed it and introduced a genuinely per-task struct task_security_struct, in the lbs_task blob, to hold the small decision cache described below. Files, sockets, superblocks, IPC objects, keys, BPF objects and perf events each have a structure of their own in the corresponding blob.

Inode labels come from the filesystem. When an inode is first instantiated, inode_doinit_with_dentry() reads the security.selinux extended attribute (XATTR_NAME_SELINUX) and converts it to a SID; for filesystems without xattr support the policy supplies a label per filesystem type or per path prefix (genfscon rules). New files are labeled at creation by selinux_inode_init_security(), which computes the type from the creating process, the parent directory, and the policy's type-transition rules, and asks the filesystem to write the xattr atomically with the inode. Processes change domain on exec, in the bprm_creds_for_exec hook, as Chapter 20 describes.

The policy itself is a binary blob written by user space to /sys/fs/selinux/load (sel_write_load() → security_load_policy()). The security server in security/selinux/ss/ parses it into a policydb — the type-enforcement rules in an access-vector table (avtab.c), conditional rules switched by booleans (conditional.c), and MLS constraints (mls.c) — and security_compute_av() answers the one question the rest of SELinux asks: for a source SID, a target SID, and an object class, which permissions are allowed, which should be audited on grant, and which on denial. The answer is a struct av_decision with fields allowed, auditallow, auditdeny, seqno, and flags.

Two mechanisms let the policy grow without changing that interface. A policy capability is a flag in the policy that switches on a newer kernel behavior, so that an old policy keeps its old meaning on a new kernel; 7.0.12 knows fifteen of them, listed under /sys/fs/selinux/policy_capabilities/, and recent additions include netlink_xperm (6.13), netif_wildcard (6.15), genfs_seclabel_wildcard (6.16), functionfs_seclabel (6.18), memfd_class (6.19) and bpf_token_perms (7.0). Extended permissions refine a single permission by an argument: allowxperm rules for ioctl (4.3) name the individual ioctl command numbers a domain may use on a file class, and since 6.13 nlmsg rules do the same for netlink message types. Decisions that involve them are computed by security_compute_xperms_decision() and cached alongside the ordinary vector.

The rest of selinuxfs is the user-space side of the same server. /sys/fs/selinux/enforce switches between enforcing and permissive mode; booleans/ flips conditional rules; policy reads back the loaded policy; and status is a page that user-space object managers such as D-Bus and systemd map read-only to learn about mode changes and policy reloads without a system call, because they keep AVCs of their own for objects the kernel never sees. Some files remain only as stubs. disable lost its function when run-time disabling was removed in 6.4, and so did checkreqprot, the switch that let policy check the protection an application asked for in mmap() rather than the one the kernel applied. The user file, deprecated in 6.13, was reduced to a stub in the 7.0.y stable series, so that writes to all three are accepted and ignored instead of filling the log.

Computing that answer means walking policy tables, so SELinux caches it in the access vector cache (AVC, security/selinux/avc.c): an RCU-protected hash table of struct avc_entry records keyed by (ssid, tsid, tclass), with AVC_CACHE_SLOTS buckets (1 << CONFIG_SECURITY_SELINUX_AVC_HASH_BITS, 512 by default) and a reclaim threshold tunable through /sys/fs/selinux/avc/cache_threshold; since 6.19 the number of buckets can be raised to 16,384 at build time. A policy reload bumps a sequence number and flushes the cache. Since 6.16 there is also a small per-task cache in front of the AVC for the hottest hook of all, the inode permission check made on every component of every path walk. It holds four recent decisions for directories, tagged with the task's SID and the policy sequence number, so it is discarded when either changes: 

/* security/selinux/hooks.c (abridged) */
static int selinux_inode_permission(struct inode *inode, int requested)
{
	u32 sid = current_sid();
	...
	mask = requested & (MAY_READ|MAY_WRITE|MAY_EXEC|MAY_APPEND);
	if (!mask)
		return 0;

	tsec = selinux_task(current);
	if (task_avdcache_permnoaudit(tsec, sid))
		return 0;

	isec = inode_security_rcu(inode, requested & MAY_NOT_BLOCK);
	if (IS_ERR(isec))
		return PTR_ERR(isec);
	perms = file_mask_to_av(inode->i_mode, mask);

	rc = task_avdcache_search(tsec, isec, &avdc);
	if (likely(!rc)) {
		/* Cache hit. */
		avdp = &avdc->avd;
		denied = perms & ~avdp->allowed;
		if (unlikely(denied) && enforcing_enabled() &&
			!(avdp->flags & AVD_FLAGS_PERMISSIVE))
			rc = -EACCES;
	} else {
		/* Cache miss. */
		rc = avc_has_perm_noaudit(sid, isec->sid, isec->sclass,
					  perms, 0, avdp);
		task_avdcache_update(tsec, isec, avdp);
	}

	audited = avc_audit_required(perms, avdp, rc, ...);
	if (likely(!audited))
		return rc;
	...
}

The structure of this function is the structure of SELinux enforcement generally. The hook converts the VFS request (MAY_READ and friends) into the object class's permission bits with file_mask_to_av(); it finds the subject SID in the credential blob and the object SID in the inode blob; it obtains an av_decision from a cache, falling back to avc_has_perm_noaudit(), which looks up the global AVC under rcu_read_lock() and on a miss calls security_compute_av() and inserts the result; and it decides separately whether the access must be audited, so that the common case — allowed and not audited — returns without touching the audit code at all. Note also enforcing_enabled() and AVD_FLAGS_PERMISSIVE: in permissive mode, globally or for a single domain, a denial is computed and logged but not enforced, which is how policies are developed. The very first test, task_avdcache_permnoaudit(), handles the extreme case: since 6.17 a policy can declare a domain both permissive and neveraudit — a domain the policy deliberately leaves unrestricted and silent — and for a task in such a domain the hook returns before it even looks at the inode.

The same model extends to the network, where the objects are packets and peers rather than files. With secmark, an nftables or iptables rule stamps a packet with a SID (skb->secmark), and selinux_socket_sock_rcv_skb() checks that the receiving socket's domain may receive packets of that type. Peer labeling carries the sender's label itself: NetLabel puts it in CIPSO or CALIPSO IP options (security/selinux/netlabel.c), and labeled IPsec binds it to the security association (xfrm.c). The Netfilter hooks selinux_ip_forward() and selinux_ip_postroute() apply the checks to forwarded and outgoing traffic, and the small caches in netif.c, netnode.c and netport.c map interfaces, addresses and ports to SIDs.

AppArmor and Smack

AppArmor takes the opposite approach to naming objects. Instead of labels stored on the files, it confines a program with a profile of rules written against pathnames — /etc/ssl/** r, or /var/log/nginx/*.log w, — attached to a task's credential as an aa_label. A profile can be in enforce, complain (log but allow), kill, unconfined, or user mode (APPARMOR_ENFORCE, APPARMOR_COMPLAIN, APPARMOR_KILL, APPARMOR_UNCONFINED, APPARMOR_USER). A label is not always a single profile: struct aa_label ends in a vector of profiles, so a task can be confined by several at once — written A//&B — and an access must be allowed by every one. That is how a container gets its own policy namespace (struct aa_ns, named :ns: in a label) with profiles its administrator loads, while the host's profile for the container still applies on top. Labels are interned in a red-black tree so that equal vectors share one object, and a label refers to its profiles through an aa_proxy, so that replacing a profile redirects every task that uses it without visiting the tasks. The text policy never enters the kernel: the apparmor_parser tool compiles every profile's path rules into a deterministic finite automaton and loads the binary result through /sys/kernel/security/apparmor/.load and .replace. Each profile's struct aa_ruleset carries a file policy database whose struct aa_dfa holds the compressed transition tables — YYTD_ID_DEF, BASE, NXT, CHK, an equivalence-class table EC that folds the input alphabet, and ACCEPT tables that map final states to permission sets.

At file_open, apparmor_file_open() takes the task's label and calls aa_path_perm(), which reconstructs the file's path (relative to the task's namespace root) and feeds it through the DFA in aa_str_perms(). The match itself is a tight loop over the string: 

/* security/apparmor/match.c (abridged) */

Matching costs time proportional to the path length and nothing in the number of rules, because all of a profile's globs have been merged into one automaton ahead of time; the final state indexes the permission table. The price of path naming is that the same inode can have several names (hard links, bind mounts, different mount namespaces) and a name can be changed by a rename between the check and the use. AppArmor answers the first concern by mediating on the name used at access time — which is the name an administrator writes rules about — and the second by mediating rename and link as operations in their own right. For operations where a path makes no sense AppArmor has rule classes of its own (AA_CLASS_* in security/apparmor/include/apparmor.h): capabilities, resource limits, network families and socket types, signals, ptrace, mount and pivot_root, and, in more recent kernels, the creation of user namespaces and the use of io_uring's credential override and SQPOLL thread (both 6.7) and fine-grained mediation of Unix-domain sockets by address and peer label (6.17). Rules for D-Bus and X11 are compiled into the same profiles but enforced in user space: the D-Bus daemon asks the kernel for a decision by writing the query to /sys/kernel/security/apparmor/.access, so one policy covers both sides.

Smack, the Simplified Mandatory Access Control Kernel, keeps SELinux's idea of labels in extended attributes (security.SMACK64 for the object, security.SMACK64EXEC for the label a program runs with) but replaces the policy language with a flat list of subject object access triples, loaded through /sys/fs/smackfs/load2 or, for a process restricting itself, load-self2. A handful of labels have fixed meanings, and smk_access() evaluates them before it consults the rule list: 

/* security/smack/smack_access.c (abridged) */

The hard-coded labels are single characters: _ (floor), ^ (hat), * (star), @ (web) and ?, which marks an object whose label could not be determined. Access modes in a rule are letters from rwxatlb: read, write, execute, append, transmute, lock, and "bringup", a development aid that grants the access but logs it. Two more attributes control labeling. A directory marked SMACK64TRANSMUTE passes its own label, rather than the creator's, to new files when the creator has the t access to it, which lets several labeled programs share a spool directory. SMACK64MMAP on a library names a label, and a process may map the library only if that label has at least the access the process itself has, so that code meant for less privileged programs cannot be loaded into a more privileged one. Smack also labels network traffic, which is where much of its code lives: SMACK64IPIN and SMACK64IPOUT set a socket's labels, outgoing IPv4 packets carry the label in a CIPSO option through NetLabel, the netlabel and ipv6host smackfs files give fixed labels to unlabeled hosts, and the receiver checks the packet's label against its socket's. A process that holds CAP_MAC_ADMIN can be further restricted by onlycap, which limits privilege to the listed labels, and relabel-self lists the labels an unprivileged process may switch to.

The design is aimed at embedded systems and appliances — its documentation names Tizen as a user — where the set of labels is small and a policy an engineer can read in one sitting is worth more than SELinux's expressiveness.

TOMOYO and the Single-Purpose Modules

TOMOYO (2.6.30) is the fourth of the legacy major modules and the only one not marked exclusive. It names objects by path, as AppArmor does, but it names subjects by history: a TOMOYO domain is the chain of programs that led to a process, such as <kernel> /sbin/init /usr/sbin/sshd /bin/bash, and tomoyo_find_next_domain() extends the chain on every execve(). The same shell is therefore a different subject when sshd starts it than when a web server does. Each domain is assigned a profile that puts each category of check in one of four modes — disabled, learning, permissive or enforcing. In learning mode every access a domain makes becomes an allow rule, up to max_learning_entry (2,048 by default), so an administrator can run a system through its normal workload and then switch it to enforcing mode with the policy it generated. The policy lives in /sys/kernel/security/tomoyo/ (domain_policy, exception_policy, profile, manager); it is loaded by /sbin/tomoyo-init, which the kernel runs just before /sbin/init; and the query file lets a supervising program approve or reject a denied access interactively. TOMOYO's per-task state is a struct tomoyo_task in the lbs_task blob.

The rest are small modules that each close one gap. Yama (3.4) restricts ptrace(), because a process that can attach to another process running as the same user can read its memory, including its keys and passwords. Its single setting, /proc/sys/kernel/yama/ptrace_scope, has four values. 0 is classic Unix behavior. 1, the module's default, is relational: a process may attach only to its own descendants, or to a process that named it with prctl(PR_SET_PTRACER), which is how a crash handler or debugger launched by a program gets through. 2 requires CAP_SYS_PTRACE, and 3 forbids attaching altogether. Once 3 is written it cannot be lowered until reboot, because the sysctl handler raises its own minimum when the maximum is reached. Yama needs just four hooks: ptrace_access_check, ptrace_traceme, task_prctl and task_free.

LoadPin (4.7) ensures that everything the kernel reads as code or policy comes from one trusted filesystem. Its kernel_read_file hook remembers the superblock of the first file read — a module, firmware image, kexec kernel or IMA policy — and, when loadpin.enforce is set, rejects any later file from a different filesystem. In enforcing mode its kernel_load_data hook also rejects loads that come from a memory buffer with no file behind them, such as init_module() and kexec_load(). loadpin.exclude= (5.3) exempts chosen file types, and since 6.0 a file on a dm-verity device is also accepted if the device's root digest appears in a list user space writes to /sys/kernel/security/loadpin/dm-verity. The kernel.loadpin.enforce sysctl can be changed only if the pinned filesystem is writable; on the read-only, verified root of a Chrome OS device, the system it was written for, enforcement cannot be switched off at run time.

SafeSetID (5.1) lets a system service hold CAP_SETUID or CAP_SETGID without making it equivalent to root. An administrator writes parent:child pairs to safesetid/uid_allowlist_policy (and, since 5.10, gid_allowlist_policy); the task_fix_setuid, task_fix_setgid and task_fix_setgroups hooks then reject any transition not on the list for a UID that has a policy. Its capable hook closes the side door: such a UID is refused CAP_SETUID for anything other than a set*id() call, such as writing a user namespace's UID map.

The BPF LSM (5.7) is a module with no policy of its own. Its whole registration, security/bpf/hooks.c, is 39 lines: it expands lsm_hook_defs.h once more to install a stub, bpf_lsm_hook(), that returns the hook's default value for every hook. A BPF_PROG_TYPE_LSM program attaches to one of those stubs through a BPF trampoline, either globally (BPF_LSM_MAC) or for the tasks of one cgroup (BPF_LSM_CGROUP, 6.0), and its return value becomes the module's answer. Its only blob is on inodes, where it anchors inode-local storage maps; kfuncs let a program read extended attributes (6.8) and, since 6.15, set and remove attributes in the security.bpf. namespace, so a BPF policy can keep labels on files just as SELinux does. The module is active only if bpf appears in the lsm= list, and its programs can be signed (§4.3). systemd uses it to enforce RestrictFileSystems=, and security monitoring tools attach to it for visibility as much as for enforcement; Chapter 23 describes how the verifier keeps such programs within the hooks' return-value rules. The remaining stackable modules have fuller treatments elsewhere: Landlock in Chapter 20, IPE in §6.3, and lockdown in §8.1.

Coexistence is mechanical once the blobs are shared. A hook such as security_file_open(), called from do_dentry_open() in fs/open.c, is a one-line call_int_hook(file_open, file); that macro walks the static-call slots for the hook in LSM order and stops at the first module that returns something other than the hook's default, which is zero for every access check. Not every hook is a veto. 54 of the 276 hooks return void and are called through call_void_hook(), which runs every module: allocation, free, and notification hooks such as inode_free_security or bprm_committed_creds, where each module must update its own state. A second group has a non-zero default, usually -EOPNOTSUPP, meaning "not mine": inode_getsecurity, getselfattr, secid_to_secctx and similar hooks are asked of each module in turn until the one that owns the attribute or the label answers, which is how getxattr("security.selinux") reaches SELinux and security.SMACK64 reaches Smack through the same call. A few hooks combine answers in their own way. security_vm_enough_memory_mm() grants the overcommit reserve for privileged tasks only if every module agrees the caller counts as privileged, and the lsm_* system calls collect one struct lsm_ctx from each module that has the attribute rather than stopping at the first.

Some subsystems make their own decision first and ask the LSMs afterwards; others ask the LSMs about something that is not an access check at all. The integrity modules tell IPE what they have verified through two "set integrity" hooks, security_bdev_setintegrity() and security_inode_setintegrity() (§6.3); the lockdown LSM answers the locked_down hook (§8.1); and the key subsystem calls security_key_permission() after its own permission bits (§4.1).

The Kernel Crypto API

Almost every subsystem in the rest of this chapter computes a hash, checks a signature, or encrypts something: IMA hashes files, dm-verity hashes blocks, the key subsystem verifies X.509 certificates, encrypted keys wrap their payloads with AES-CBC, and outside the security code dm-crypt, fscrypt, IPsec, kTLS, WireGuard and zswap's compressors all need the same primitives. The kernel crypto API in crypto/ is the shared answer. It is a registry of named algorithm implementations, a lookup engine that picks the best implementation for a name and can build compound algorithms from templates on demand, and a request model that lets the same caller code drive a CPU instruction set extension or a DMA engine on a PCIe card. In Linux 2.6.11 the API was a few hundred lines of crypto/api.c with a synchronous cipher and digest interface; the asynchronous request model, templates, self-tests and the type system described here all arrived later in the 2.6 series and have been refined ever since.

In 7.0 the kernel's cryptography comes in two tiers, and the line between them has moved several times in recent releases. The API in crypto/ exists for callers that learn the algorithm only at run time — a dm-crypt table line such as aes-xts-plain64, an IMA policy rule's hash, an fscrypt encryption mode, an IPsec SA negotiated by an IKE daemon — and for anything that may be offloaded to an engine, completed asynchronously, or assembled from templates. The library interface in lib/crypto/ is a set of ordinary C functions for callers that know the algorithm when they are compiled: no allocation, no name lookup, no indirect calls. WireGuard (5.6) was written against the library from its first day, and other code keeps moving across — TCP-MD5 signatures, for example, dropped crypto_ahash for the MD5 library in 6.19 — while the API's own entries for the common hashes and ciphers have become wrappers around the library code.

Algorithms, Transforms, and Types

Two objects carry the whole design. An algorithm, struct crypto_alg, describes one implementation: its generic name, its unique driver name, a priority, sizes, flags that include its type, and the module that provides it. Implementations never fill in a bare crypto_alg; they embed one as the base of a type-specific structure such as struct shash_alg or struct skcipher_alg, which adds the type's operations. A transform, struct crypto_tfm, is an instantiated handle on an algorithm — one per key, typically — with a per-implementation context area (expanded key schedule, hardware session) allocated behind it:

The rest of cra_flags describes how an implementation behaves, and callers filter on it (§3.2). CRYPTO_ALG_ASYNC marks an implementation that may return before the work is done; CRYPTO_ALG_NEED_FALLBACK one that allocates a second, software transform for inputs its hardware cannot handle; CRYPTO_ALG_KERN_DRIVER_ONLY one whose keys live in a hardware engine; and CRYPTO_ALG_INTERNAL a building block, such as a SIMD inner cipher, that only other implementations may use. CRYPTO_ALG_ALLOCATES_MEMORY warns that a request may call kmalloc(); dm-crypt and dm-integrity, which run on the memory-reclaim path, put it in the mask to exclude such implementations. CRYPTO_ALG_FIPS_INTERNAL (5.18) marks an algorithm that may be used in FIPS mode only inside an approved construction — plain dh is reachable only as part of ffdhe2048(dh) and its siblings — and CRYPTO_ALG_REQ_VIRT (6.16) one that accepts virtual addresses as well as scatterlists (§3.3). On the transform side, crt_flags holds CRYPTO_TFM_NEED_KEY, set at allocation for keyed algorithms and cleared by a successful setkey, so that a forgotten key produces -ENOKEY instead of encryption under zeros (algorithms flagged CRYPTO_ALG_OPTIONAL_KEY are exempt), and request flags such as CRYPTO_TFM_REQ_FORBID_WEAK_KEYS, which makes DES reject its known weak keys and makes xts reject keys whose two halves are equal, as it always does in FIPS mode.

The split between algorithm and transform is also a split between immutable and per-key state. The key, once expanded by setkey, lives in the transform's context, so one transform can serve any number of concurrent requests under the same key — dm-crypt keeps one per device, fscrypt one per file key — while each request carries its own IV and data. Allocation goes through crypto_alloc_tfm_node(), which looks the name up, takes a reference on the algorithm and on its module (so a module cannot be unloaded while a transform uses it), allocates the context from the type's ctxsize, and runs the type's init_tfm and the implementation's cra_init; crypto_free_*() reverses all of it. Allocation may sleep and may load modules, so callers do it at setup time. For code that needs a private copy of a keyed hash in atomic context, crypto_clone_ahash() (6.4) duplicates an existing transform without a lookup: TCP-AO's tcp_sigpool_start() clones its pool's transform under rcu_read_lock_bh() with GFP_ATOMIC for every segment it signs.

Names, Priorities, Templates, and Larvals

Every algorithm has two names. cra_name is the generic name of the mathematics — "cbc(aes)" — and many implementations share it; cra_driver_name names one implementation — "cbc-aes-aesni", "cbc-aes-ce" — and must be unique. A caller nearly always asks for the generic name and lets cra_priority decide. All registered algorithms live on one list, crypto_alg_list, under the reader-writer semaphore crypto_alg_sem, and the core lookup is a linear scan that accepts an exact driver-name match immediately and otherwise keeps the highest-priority algorithm whose generic name matches: 

/* crypto/api.c */
static struct crypto_alg *__crypto_alg_lookup(const char *name, u32 type,
					      u32 mask)
	__must_hold_shared(&crypto_alg_sem)
{
	struct crypto_alg *q, *alg = NULL;
	int best = -2;

	list_for_each_entry(q, &crypto_alg_list, cra_list) {
		int exact, fuzzy;

		if (crypto_is_moribund(q))
			continue;

		if ((q->cra_flags ^ type) & mask)
			continue;

		exact = !strcmp(q->cra_driver_name, name);
		fuzzy = !strcmp(q->cra_name, name);
		if (!exact && !(fuzzy && q->cra_priority > best))
			continue;

		if (unlikely(!crypto_mod_get(q)))
			continue;

		best = q->cra_priority;
		if (alg)
			crypto_mod_put(alg);
		alg = q;

		if (exact)
			break;
	}

	return alg;
}

The type/mask pair is the API's filter language: a bit set in mask means "the algorithm's flag must equal the bit in type". Passing type = 0, mask = CRYPTO_ALG_ASYNC, for example, demands an implementation that completes synchronously. The wrapper crypto_alg_lookup() adds one more filter: it first searches with CRYPTO_ALG_TESTED required, so an implementation that has not passed its self-test (§3.4) is invisible; if only an untested, non-larval match exists, the lookup fails with -ELIBBAD.

A template, struct crypto_template, is a constructor for compound algorithms. Its create method parses the parameters inside the parentheses, looks up the inner algorithms as spawns, and registers a new struct crypto_instance whose cra_name is the full compound name. hmac, cbc, ctr, xts, gcm, authenc, essiv, pkcs1 and many more are templates, which is why any hash can be wrapped in HMAC and any block cipher run in any mode without anyone writing the combination by hand. A dedicated implementation of a common combination simply registers under the same cra_name with a higher priority: both gcm(aes) on x86_64 ("generic-gcm-vaes-avx512", priority 800) and hmac(sha256) ("hmac-sha256-lib", priority 300) are registered directly, and the template version is never built unless someone asks for it by driver name.

What happens when the name is not registered yet? The answer is the larval, a placeholder struct crypto_larval (an embedded crypto_alg flagged CRYPTO_ALG_LARVAL, an adult pointer and a completion) that is put on the list under the requested name so that concurrent requests for the same name wait for one construction instead of racing to build several:

Module autoloading uses the alias namespace crypto-: every implementation module declares MODULE_ALIAS_CRYPTO("sha256") and friends, which expands to crypto-sha256 aliases, so request_module() can only load crypto modules and an unprivileged AF_ALG bind() cannot be used to load arbitrary modules. If no module supplies the name, the larval goes to the crypto manager in crypto/algboss.c through a blocking notifier chain (loading the cryptomgr module first if nobody answered). cryptomgr_notify() parses the outermost template name and starts a cryptomgr_probe kernel thread that calls crypto_lookup_template() (itself autoloading crypto-authenc and the like) and then the template's create method. Figure 27-3 follows a request for authenc(hmac(sha256),cbc(aes)), the AEAD that IPsec uses for CBC-mode ESP with HMAC authentication, through that machinery.

Registration runs the other half. crypto_register_alg() (for a driver's own algorithms) and crypto_register_instance() (for a template's) validate the descriptor, add it to crypto_alg_list, and create a test larval carrying the new algorithm as its adult. cryptomgr_schedule_test() runs alg_test() in a cryptomgr_test thread, and crypto_alg_tested() then sets CRYPTO_ALG_TESTED on the algorithm, lets it displace lower-priority implementations of the same name (crypto_alg_finish_registration() tears down template instances built on the old one), and completes everyone waiting on the test larval. When a module carrying a better implementation loads later — aesni_intel, say — existing transforms keep the implementation they were created with; new allocations pick the new one.

Several details refine this picture. crypto_alg_mod_lookup() adds CRYPTO_ALG_INTERNAL to the mask unless the caller mentions it in type or mask, so internal building blocks are invisible to ordinary users; /proc/crypto lists them with internal : yes. In FIPS mode a test that rejects an algorithm marks it CRYPTO_ALG_FIPS_INTERNAL instead of failing the registration, and crypto_alg_lookup() then refuses it to anyone who did not ask for that flag. Built-in algorithms register long before the test machinery can run, so since 5.16 their test larvals are only queued: the late initcall crypto_algapi_init() calls crypto_start_tests(), which launches every pending test, each in its own cryptomgr_test kthread, and a lookup that arrives earlier starts its own larval's test from crypto_larval_wait(). With CONFIG_CRYPTO_SELFTESTS off no test larval is created and algorithms are marked tested at once. Unregistration runs in reverse: crypto_unregister_alg() calls crypto_remove_alg(), which sets CRYPTO_ALG_DEAD, takes the algorithm off the list, and walks cra_users with crypto_remove_spawns() to tear down every template instance built on it; lookups skip dead or dying algorithms, and the core warns if anyone still holds a reference and the algorithm has no cra_destroy. Drivers for hot-unpluggable hardware set CRYPTO_ALG_DUP_FIRST (6.16) so that the core registers a kmemdup() copy of the descriptor whose lifetime it controls.

Everything else — ahash, skcipher, aead, akcipher, kpp, acomp — uses the request model. The caller allocates a request (aead_request_alloc(), or SYNC_SKCIPHER_REQUEST_ON_STACK() for small synchronous skciphers), points it at source and destination scatterlists, sets a completion callback, and submits. Scatterlists are the currency because the data being encrypted is usually in page cache pages, bios or socket buffers that are neither contiguous nor necessarily mapped; a hardware engine wants DMA addresses, and a CPU implementation walks the list with skcipher_walk_virt() and skcipher_walk_done(), mapping a chunk at a time. The submission returns 0 when the operation finished synchronously, -EINPROGRESS when it was queued and the callback will run later (possibly in softirq context), or -EBUSY when the request was put on a backlog because the caller set CRYPTO_TFM_REQ_MAY_BACKLOG. /* include/linux/crypto.h */
static inline int crypto_wait_req(int err, struct crypto_wait *wait)
{
	switch (err) {
	case -EINPROGRESS:
	case -EBUSY:
		wait_for_completion(&wait->completion);
		reinit_completion(&wait->completion);
		err = wait->err;
		break;
	}

	return err;
}

The generic callback crypto_req_done() ignores the -EINPROGRESS notification that a backlogged request has started and completes the crypto_wait on the final status. Callers that can pipeline — dm-crypt, IPsec — instead pass their own callback and keep many requests in flight. Hardware drivers in drivers/crypto/ (Intel QAT, AMD CCP, NXP CAAM, Arm CryptoCell, HiSilicon, virtio-crypto and many SoC engines) register algorithms flagged CRYPTO_ALG_ASYNC, usually with priorities above the CPU implementations, and many of them queue requests through the generic crypto_engine (crypto/crypto_engine.c, crypto_transfer_skcipher_request_to_engine() and its siblings), which feeds a kthread worker one request at a time. Note the mask in the DCP example: type = 0, mask = CRYPTO_ALG_ASYNC asks for a synchronous implementation, and the wait idiom is there only because the API does not promise it.

The hash interfaces were reworked in 6.15 and 6.16 to take work away from callers and drivers. ahash_request_set_virt() (6.15) lets a caller pass a virtual address instead of building a scatterlist. Since 6.16 the API itself buffers partial blocks for both shash and ahash, so implementations see only whole blocks, and every implementation exports its state in one standard layout — the hash state, the partial block and a length byte (HASH_STATE_AND_BLOCK()), with HASH_MAX_STATESIZE sized for the worst case, sha3-224. That common format is what lets the core switch implementations in mid-hash: an asynchronous driver that cannot handle virtual addresses gets a synchronous fallback transform in the fb field of its crypto_tfm, and ahash_do_req_chain() exports the state, finishes the request on the fallback and imports the result back. HASH_REQUEST_ON_STACK() (6.16) gives synchronous callers an on-stack ahash request; used against an asynchronous transform it returns -EAGAIN rather than letting a completion write to a dead stack frame. In the same release hmac gained an ahash form, shash calls from hard-IRQ context were forbidden, and the request chaining added in 6.15 was taken out again.

Compression follows the same request model. zswap keeps an acomp transform, request and buffer per CPU for each pool, submits each page with crypto_wait_req(), and so works unchanged with a software lz4 or zstd and with Intel's IAA accelerator, whose driver registers deflate-iaa. Since 6.15 acomp requests also accept virtual addresses and folios, and the per-CPU scratch streams that synchronous scomp algorithms need moved into the acomp core; UBIFS, EROFS, IPComp and the hibernation image writer in kernel/power/swap.c are other users. Not all bulk encryption goes through the API at all: with inline encryption the storage controller encrypts data on its way to the medium, and fscrypt hands it a key through blk-crypto instead of a transform (Chapter 14). Only the blk-crypto fallback, for devices without the hardware, allocates crypto_sync_skcipher transforms for the supported modes — AES-256-XTS, AES-128-CBC-ESSIV, Adiantum and SM4-XTS. Hardware-wrapped keys (BLK_CRYPTO_KEY_TYPE_HW_WRAPPED, 6.15) go further and never expose the raw key to the kernel.

Self-Tests, Architecture Code, and the Library Interface

crypto/testmgr.c holds an alg_test_descs[] table with one struct alg_test_desc per algorithm name: the test routine, the known-answer vectors from crypto/testmgr.h, a generic_driver used as a reference, and fips_allowed. With CONFIG_CRYPTO_SELFTESTS (6.16; earlier kernels had the inverted CONFIG_CRYPTO_MANAGER_DISABLE_TESTS) every registration runs the vectors before the algorithm becomes visible; with CONFIG_CRYPTO_SELFTESTS_FULL the tests also compare each optimized implementation against the generic one on random inputs, which is how bugs in hand-written assembly are caught. Booting with fips=1 (when CONFIG_CRYPTO_FIPS is set) changes the rules: algorithms not marked fips_allowed are rejected, and a self-test failure is fatal — alg_test() calls panic("alg: self-tests for %s (%s) failed in fips mode!"), since a FIPS-validated module must not run with a broken primitive. /proc/crypto shows the outcome for every registered implementation:

Speed measurements are the job of a separate module, tcrypt, whose option was renamed CONFIG_CRYPTO_BENCHMARK in 6.16, and the per-algorithm usage counters of CONFIG_CRYPTO_STATS were removed in 6.10. FIPS mode is visible to user space as /proc/sys/crypto/fips_enabled, with fips_name and fips_version beside it. The library interface has its own checks: when fips_enabled is set, the SHA-1, SHA-2, SHA-3 and ML-DSA library code runs a power-on known-answer test at boot and panics on failure ("sha256: FIPS self-test failed"), and since 6.17 lib/crypto/tests/ holds KUnit suites for the library functions.

Architecture-specific implementations are where most of the speed comes from, and the two architectures this book follows get it from different instruction-set extensions. x86_64 has AES-NI (one round per instruction), its vector forms VAES on AVX2 and AVX-512, PCLMULQDQ for GHASH and POLYVAL, and the SHA extensions; ARMv8 has the optional Cryptography Extensions (AESE/AESD/AESMC, PMULL, SHA1/SHA256 and, in ARMv8.2, SHA512, SHA3 and SM3/SM4) alongside plain NEON. Both share one constraint: kernel code may not touch vector registers without saving the user state, so every implementation brackets its work with kernel_fpu_begin()/kernel_fpu_end() on x86 (after checking irq_fpu_usable()) or scoped_ksimd() on arm64 (6.19, after checking may_use_simd()), and falls back to scalar code when it cannot. On x86 that check used to fail often enough to shape the API: until 6.16 the AES skciphers were registered as internal __-prefixed algorithms and wrapped by the SIMD helper in crypto/simd.c, which handed requests to the cryptd thread whenever the FPU was unusable, making them asynchronous. Once 6.15 made kernel-mode FPU use reliable in softirq context — fpregs_lock() now disables bottom halves, and irq_fpu_usable() consults a per-CPU kernel_fpu_allowed flag — 6.16 removed the wrappers, which is why cbc-aes-aesni above reports async : no. The crypto API's sha256, hmac(sha256) and chacha20 entries are now thin wrappers around these library functions (hence the driver names ending in -lib), and 7.0 extended the pattern to AES: the AES-NI and ARMv8 CE single-block code moved under lib/crypto/, and the generic aes cipher became aes-lib. fs-verity switched from crypto_shash to the SHA-2 library in 6.17 and since 6.18 also uses sha256_finup_2x(), which hashes two blocks interleaved to keep the SHA-NI or CE pipeline full (§6.1). The library has grown quickly. Besides the long-standing ChaCha20, Poly1305, the ChaCha20-Poly1305 AEAD, Curve25519, BLAKE2s, AES, AES-GCM, AES-CFB, DES, SM3 and ARC4, it gained SHA-384/512 and a single SHA-256 module in 6.17, MD5 in 6.18, SHA-3, BLAKE2b and POLYVAL in 6.19, and in 7.0 the NH hash used by Adiantum and the ML-DSA verifier, while arm64's AES code moved under it as well. Its users are a cross-section of the kernel: WireGuard, TCP-MD5, MPTCP, SCTP authentication, IPv6 segment routing's HMAC, the SMB client and server, Ceph's messenger, fscrypt file names, fs-verity, AppArmor policy hashes, encrypted and trusted keys, BPF program tags, the RNG of §3.5, kexec_file_load(), and the x86 kexec purgatory, which checks the loaded image's SHA-256 digest before jumping to it, with no crypto API underneath.

User space reaches the API through AF_ALG sockets (crypto/af_alg.c, 2.6.38). A program creates a socket, bind()s it with a struct sockaddr_alg whose salg_type is "hash", "skcipher", "aead" or "rng" and whose salg_name is any API name, sets the key with setsockopt(ALG_SET_KEY), and accept()s an operation socket to which it writes plaintext and from which it reads the result; splice() lets data move from a file or pipe without a copy. The four socket types are separate modules (algif_hash, algif_skcipher, algif_aead and algif_rng), and since 6.2 ALG_SET_KEY_BY_KEY_SERIAL lets a program name a key in its keyring — of type user, logon, encrypted or trusted (§4) — instead of passing key bytes through its own memory. It exists mainly to reach hardware engines and to let tools like cryptsetup use exactly the kernel's implementation; for ordinary software cryptography a user-space library is faster. The separate NETLINK_CRYPTO interface (crypto/crypto_user.c, CONFIG_CRYPTO_USER) lets an administrator list algorithms and adjust priorities.

The Kernel Random Number Generator

Key generation, nonces, stack canaries, the slab freelist secret, TCP initial sequence numbers and every getrandom() call need unpredictable bytes, and none of them get those bytes from the crypto API. The kernel's RNG lives in drivers/char/random.c, not in crypto/, and the CRYPTO_ALG_TYPE_RNG algorithms of Table 27-2 are consumers of it rather than the other way round: stdrng (the SP800-90A DRBG in crypto/drbg.c) seeds itself from get_random_bytes() plus jitterentropy_rng for FIPS deployments. The Linux 2.6.11 driver kept a 4,096-bit input pool mixed with a twisted LFSR, separate blocking and non-blocking output pools extracted with SHA-1, and an entropy estimate that /dev/random drained on every read. The design in 7.0 is the result of a rewrite between 5.4 and 5.18, mostly by Jason A. Donenfeld, and has two halves.

The input pool is a single BLAKE2s hash state (5.17 replaced SHA-1). mix_pool_bytes() feeds data into it; credit_init_bits() counts how much of that data is believed to be entropy, and the count matters only during boot: at 128 bits (POOL_EARLY_BITS) crng_init moves from CRNG_EMPTY to CRNG_EARLY, and at 256 bits (POOL_READY_BITS) to CRNG_READY, which prints crng init done, flips the crng_is_ready static key, and stops crediting altogether. Sources arrive through a small set of entry points. add_interrupt_randomness(), called from the generic IRQ code on every interrupt, folds the cycle counter, the interrupted instruction pointer and the IRQ number into a per-CPU fast_pool with a SipHash-style permutation, and after 1,024 interrupts or one second pushes it into the input pool from a timer. add_input_randomness() and add_disk_randomness() mix event timings; add_device_randomness() mixes MAC addresses, DMI strings and similar data that differ between machines but are not credited as entropy; add_hwgenerator_randomness() takes output from the drivers/char/hw_random/ framework, whose hwrng_fillfn() kernel thread (hwrng) reads TPM, virtio-rng or SoC TRNG devices and credits each block according to the driver's quality — entropy bits per 1,024 bits of output — while /dev/hwrng and the sysfs files rng_available and rng_current expose the device directly; add_bootloader_randomness() takes the seed passed in the x86 SETUP_RNG_SEED setup_data, the device tree's /chosen/rng-seed or the EFI LINUX_EFI_RANDOM_SEED table; and add_vmfork_randomness() (5.18), driven by the VM Generation ID device in drivers/virt/vmgenid.c, forces an immediate reseed when a virtual machine has been cloned from a snapshot (the device is found through ACPI, or since 6.10 through the device tree). If nothing else supplies entropy, wait_for_random_bytes() calls try_to_generate_entropy() (5.4), which credits the jitter of a timer bouncing between CPUs against the cycle counter.

The CPU itself is a source on both architectures. random_init_early() runs before interrupts are enabled and fills a BLAKE2s block from arch_get_random_seed_longs(), falling back to arch_get_random_longs(). On x86_64 these are RDSEED and RDRAND (arch/x86/include/asm/archrandom.h); x86_init_rdrand() disables both if eight samples fail or barely change, and the AMD setup code clears RDSEED on Zen 5 parts without fixed microcode and on the Cyan Skillfish APU. A confidential-computing guest cannot trust the timing sources at all, because the host sees and can steer its interrupts, so since 6.9 cc_random_init() in arch/x86/coco/core.c mixes 32 bytes of RDRAND output into the pool whenever guest memory encryption is active and panics with "RDRAND is defective." if the instruction returns nothing. On ARM64 the seed call prefers the firmware's SMCCC TRNG service, then the ARMv8.5 RNDRRS register, and arch_get_random_longs() reads RNDR. With random.trust_cpu=on (the default) the CPU's bits are credited and the RNG can be ready before the first interrupt; random.trust_bootloader (5.18) does the same for the bootloader seed. Every later extraction also mixes fresh RDSEED or RNDRRS output into extract_entropy(), which is an HKDF-like expansion of the pool's BLAKE2s digest.

The output half is a ChaCha20 generator with fast key erasure (5.18). crng_reseed() extracts 32 bytes from the input pool into base_crng.key and bumps base_crng.generation; it is self-rescheduling delayed work that runs every uptime/2 seconds during early boot and every 60 seconds after that, plus on resume from suspend or hibernation and on VM fork. Each CPU keeps its own key in struct crng crngs. A caller of get_random_bytes() or get_random_u32() ends in crng_make_state(): 

/* drivers/char/random.c (abridged) */
static void crng_fast_key_erasure(u8 key[CHACHA_KEY_SIZE],
				  struct chacha_state *chacha_state,
				  u8 *random_data, size_t random_data_len)
{
	u8 first_block[CHACHA_BLOCK_SIZE];

	memcpy(random_data, first_block + CHACHA_KEY_SIZE, random_data_len);
	memzero_explicit(first_block, sizeof(first_block));
}

Every request first overwrites the per-CPU key with the first half of a fresh ChaCha block, so a later memory disclosure cannot reconstruct earlier output; the caller then runs the returned ChaCha state for as many blocks as it needs and wipes it. A generation mismatch tells the CPU that base_crng has been reseeded and that it must derive a new key from it. Small values come from per-CPU batches: get_random_u8() through get_random_u64() refill a buffer of ChaCha output only when it is used up or the generation changes, and get_random_u32_below() uses Lemire's multiply-and-reject method to avoid modulo bias. The same generation counter is published in vdso_k_rng_data so that the vDSO getrandom() of 6.11 (Chapter 10) can tell user space when its own ChaCha state must be refreshed.

User space sees one generator behind three doors. getrandom(2) (3.17) blocks only until crng_init reaches CRNG_READY, returns -EAGAIN instead with GRND_NONBLOCK, and with GRND_INSECURE (5.6) never blocks. Since 5.6 /dev/random behaves like getrandom() with no flags, and GRND_RANDOM no longer selects a separate pool; /dev/urandom behaves like GRND_INSECURE and logs a rate-limited warning when read before the RNG is ready. Writes to either device mix data into the pool without credit; the RNDADDENTROPY ioctl credits it and needs CAP_SYS_ADMIN, as does RNDRESEEDCRNG, which forces a reseed (and fails with -ENODATA before the RNG is ready); RNDZAPENTCNT and RNDCLEARPOOL survive only as no-ops. /proc/sys/kernel/random/entropy_avail now reports 256 once the RNG is ready, and writes to urandom_min_reseed_secs are accepted but ignored. In-kernel code that must not run before the RNG is ready calls wait_for_random_bytes(), checks rng_is_initialized(), or registers a callback with execute_with_initialized_rng().

Keys and Keyrings

The crypto API computes; it does not remember. Secrets that must outlive a single operation — a Kerberos ticket for an NFS mount, the master key of an encrypted filesystem, a certificate that vouches for kernel modules, a disk key sealed to the TPM — need a place to live that has an owner, a lifetime, access control, and a way to be found by name. That place is the key retention service in security/keys/. The 2.6.11 kernel already contained it. Twenty years on it carries three quite different loads: per-user and per-session secrets that user space hands to kernel clients (network filesystems, fscrypt, dm-crypt), the system keyrings that anchor every signature check the kernel makes, and hardware-bound keys that never exist in the clear outside a TPM or trusted execution environment.

struct key and Key Types

A struct key (include/linux/key.h) is a reference-counted object identified by a 32-bit serial number, unique system-wide and kept in a red-black tree, with a type, a description string used as its name, an owner, a permissions mask, an optional expiry time, a state (uninstantiated, positive, or negative with an error code) and a payload whose meaning belongs entirely to the type:

The last union shows that a keyring is just a key whose payload is an associative array (lib/assoc_array.c) of links to other keys, indexed by type, domain tag and description. The array is a radix tree of 16-way nodes keyed on a hash of the index key, so a keyring holding thousands of keys is still searched in a few node hops, and readers walk it under RCU without taking the keyring's semaphore. Keyrings can link to keyrings, so the structure is a graph, and searching it is how keys are found: keyring_search_rcu() descends into nested keyrings with an explicit stack that stops at KEYRING_SEARCH_MAX_DEPTH (six levels), and key_link() refuses a link that would create a cycle. The restrict_link pointer lets a keyring vet every key linked into it, which is how the system keyrings of §4.3 enforce "only keys signed by a trusted key may be added".

A struct key_type supplies the behavior: preparse and instantiate to parse and attach a payload, update, revoke, destroy, describe for /proc/keys, an optional read that returns the payload to user space, match_preparse for custom lookup, and, for asymmetric keys, asym_query, asym_eds_op and asym_verify_signature. Less visible hooks round it out: vet_description rejects malformed names before anything is allocated (the logon type uses it to demand a prefix:), free_preparse and match_free release what the parse steps built, lookup_restriction parses the restriction strings of §4.3, def_datalen pre-charges the quota, and a request_key actor replaces the /sbin/request-key upcall of §4.2 — in 7.0.12 only the NFS idmapper's nfs_idmap_legacy_upcall provides one. Two type flags change behavior wholesale: KEY_TYPE_NET_DOMAIN (5.3) makes every key of the type carry its network namespace as the domain tag, so dns_resolver, rxrpc and NVMe psk keys looked up in one container are invisible to another, and KEY_TYPE_INSTANT_REAP (6.7) lets the garbage collector free expired keys of the type at once instead of after the grace period described below, which DNS results need because they expire by the thousand. Permissions are a 32-bit mask of four 8-bit groups — possessor, user, group, other — each holding VIEW, READ, WRITE, SEARCH, LINK and SETATTR bits. The unusual one is the possessor class. A process possesses a key if it can reach it by searching its own thread, process and session keyrings (the search marks the reference with a "possessed" bit), and possessor bits are added to whichever of the user, group or other groups applies. The design lets a key be usable by any process in a login session that holds it while staying invisible to other processes of the same user. key_task_permission() implements the rule and then defers to the LSMs: 

/* security/keys/permission.c (abridged) */
	key = key_ref_to_ptr(key_ref);

	/* use the second 8-bits of permissions for keys the caller owns */
	if (uid_eq(key->uid, cred->fsuid)) {
		kperm = key->perm >> 16;
		goto use_these_perms;
	}
	...
	/* otherwise use the least-significant 8-bits */
	kperm = key->perm;

	/* use the top 8-bits of permissions for keys the caller possesses
	 * - possessor permissions are additive with other permissions
	 */

		kperm |= key->perm >> 24;

		return -EACCES;

	/* let LSM be the final arbiter */

SELinux and Smack label keys through the key_alloc hook and decide in key_permission, which is how an Android or Fedora policy can confine which domains read which keys. Every key is charged to its owner's struct key_user quota — 200 keys and 20,000 bytes by default, a million keys and 25,000,000 bytes for root — adjustable through /proc/sys/kernel/keys/maxkeys, maxbytes, root_maxkeys and root_maxbytes; keys created by kernel services with KEY_ALLOC_NOT_IN_QUOTA are not charged. Keys that are revoked, expire, or lose their last reference are not freed synchronously: the garbage collector in security/keys/gc.c, a work item driven by key_gc_timer, unlinks dead keys from every keyring and destroys them, waiting key_gc_delay (five minutes, /proc/sys/kernel/keys/gc_delay) after expiry so that users get -EKEYEXPIRED rather than -ENOKEY for a while.

The flags word records where a key is in that life cycle and what may be done to it. KEY_FLAG_REVOKED is set by KEYCTL_REVOKE: the key stays visible but every use fails with -EKEYREVOKED until the grace period ends. KEY_FLAG_INVALIDATED, set by KEYCTL_INVALIDATE (3.5), is harsher — the key vanishes from searches immediately and the collector is kicked at once — and is how CIFS discards a Kerberos SPNEGO key as soon as session setup has consumed it. KEY_FLAG_KEEP makes a key impossible to unlink or revoke; .blacklist entries are created with it so that a revocation, once loaded, cannot be withdrawn. KEY_FLAG_BUILTIN marks keys compiled into the kernel, and KEY_FLAG_ROOT_CAN_CLEAR and KEY_FLAG_ROOT_CAN_INVAL let root flush the private caches of kernel services (the DNS resolver, CIFS and NFS idmapper keyrings) without owning them.

The Key Syscalls and the request-key Upcall

User space manages keys with three system calls in security/keys/keyctl.c. add_key(type, description, payload, plen, keyring) creates a key (or updates one with the same type and description) and links it into a keyring. request_key(type, description, callout_info, dest_keyring) searches the caller's keyrings and, if callout_info is given, asks user space to construct the key on a miss. Everything else is multiplexed through keyctl(operation, ...), whose 33 operations run from KEYCTL_GET_KEYRING_ID (0) through KEYCTL_DESCRIBE, KEYCTL_READ, KEYCTL_LINK, KEYCTL_SEARCH, KEYCTL_SETPERM, KEYCTL_SET_TIMEOUT, KEYCTL_INSTANTIATE and KEYCTL_NEGATE, the public-key operations KEYCTL_PKEY_QUERY through KEYCTL_PKEY_VERIFY, KEYCTL_DH_COMPUTE and KEYCTL_RESTRICT_KEYRING, to KEYCTL_WATCH_KEY (32), which delivers change notifications through a watch queue. Special negative IDs name the caller's keyrings without knowing their serials: KEY_SPEC_THREAD_KEYRING (−1), KEY_SPEC_PROCESS_KEYRING (−2), KEY_SPEC_SESSION_KEYRING (−3), KEY_SPEC_USER_KEYRING (−4) and KEY_SPEC_USER_SESSION_KEYRING (−5). The keyctl utility from keyutils wraps them all:

Each line of /proc/keys gives the serial in hex, seven state flags (Instantiated, Revoked, Dead, in Quota, Under construction, Negative, invalidated), the usage count, the expiry ("perm" for none), the permission mask, owner, group, type, and the type's describe output. The user key got the default mask add_key() computes, 0x3f010000: every permission for possessors and VIEW for the owning user, so the owner's other sessions can see the key exists but cannot read it.

The later keyctl operations follow what the users of the service needed. KEYCTL_GET_PERSISTENT (3.13, CONFIG_PERSISTENT_KEYRINGS) returns a per-user _persistent.uid keyring that belongs to no session and is discarded after three days of disuse (/proc/sys/kernel/keys/persistent_keyring_expiry), so that Kerberos KEYRING: credential caches outlive a login for cron jobs and daemons. KEYCTL_MOVE (5.3) relinks a key from one keyring to another atomically, refusing to displace an existing key if KEYCTL_MOVE_EXCL is given. KEYCTL_CAPABILITIES (5.3) fills a byte array with KEYCTL_CAPS0_* and KEYCTL_CAPS1_* bits — persistent keyrings, Diffie-Hellman, public-key operations, big_key, KEYCTL_MOVE, per-namespace keyring names, key tags, notifications — so keyutils can ask instead of probing. KEYCTL_WATCH_KEY (5.8, CONFIG_KEY_NOTIFICATIONS) attaches a watch to a key or keyring, and NOTIFY_KEY_INSTANTIATED, _UPDATED, _LINKED, _UNLINKED, _CLEARED, _REVOKED, _INVALIDATED and _SETATTR records arrive in a pipe opened with pipe2(O_NOTIFICATION_PIPE), the general watch queue of kernel/watch_queue.c; a desktop agent can thus learn that a Kerberos ticket was replaced without polling /proc/keys. Three more special IDs complete the set: KEY_SPEC_GROUP_KEYRING (−6) is reserved and returns -EINVAL, while KEY_SPEC_REQKEY_AUTH_KEY (−7) and KEY_SPEC_REQUESTOR_KEYRING (−8) name the authorization key and the requester's destination keyring inside a request-key helper.

The keyring hierarchy is anchored in struct cred (described in Chapter 20): thread_keyring, process_keyring (shared by all threads, kept in the thread group's credentials), session_keyring (inherited across fork() and execve(), typically created at login by pam_keyinit), and request_key_auth. Per-user keyrings named _uid.N and _uid_ses.N are found through a register keyring in each user namespace, so containers in separate user namespaces (Chapter 25) get separate user keyrings. search_cred_keyrings_rcu() searches the thread, process and session keyrings in that order, falling back to the user-session keyring if there is no session keyring. /* security/keys/request_key.c */
struct key *request_key_tag(struct key_type *type,
			    const char *description,
			    struct key_tag *domain_tag,

		callout_len = strlen(callout_info);

				   callout_info, callout_len,
				   NULL, NULL, KEY_ALLOC_IN_QUOTA);

		if (ret < 0) {

The user-space program (keyutils' request-key) consults /etc/request-key.conf to pick a handler — a Kerberos helper for cifs.spnego, the DNS resolver for dns_resolver, the NFS idmapper for id_resolver — which calls KEYCTL_ASSUME_AUTHORITY to act on the requester's behalf and then KEYCTL_INSTANTIATE with the payload, or KEYCTL_NEGATE/KEYCTL_REJECT with a timeout. A negative key is real: it sits in the keyring with an error code so that repeated requests for a name that cannot be resolved fail fast instead of forking a helper each time. A kernel built with CONFIG_STATIC_USERMODEHELPER routes this and every other usermode-helper call through one fixed binary, a hardening option that §9.3 returns to.

Kernel services usually keep their upcall results out of the caller's keyrings. The DNS resolver's init code builds a credential set with prepare_kernel_cred(), allocates a root-owned .dns_resolver keyring, installs it as that set's thread_keyring with jit_keyring set to KEY_REQKEY_DEFL_THREAD_KEYRING, and runs every dns_query() under those credentials (scoped_with_creds()), so results land in one shared cache instead of in whichever user's session happened to trigger an NFS or CIFS mount. User space chooses the same default destination with KEYCTL_SET_REQKEY_KEYRING and the KEY_REQKEY_DEFL_* constants. Linux 5.3 adapted lookups to containers and to path walk: types flagged KEY_TYPE_NET_DOMAIN are matched against the caller's network namespace tag, and request_key_rcu() searches without sleeping and never upcalls, so AFS can check access during RCU path walk (afs_request_key_rcu()). The same release added CONFIG_KEYS_REQUEST_CACHE, a one-entry cache in task_struct->cached_requested_key that keeps the key returned by the last successful request_key() until the task returns to user space or exits; a network filesystem that requests the same key for every component of one open() path then pays for the keyring search once.

The .ima and .evm keyrings use restrict_link_by_digsig_builtin() (or the _and_secondary variant) since 6.6, which also demands that the certificate carry the digitalSignature key usage and not be a CA, so a CA key cannot be repurposed to sign files directly. MOK keys reach .machine only when shim exports the MokListTrustedRT variable (set by mokutil --trust-mok); otherwise, and for any key the machine keyring's restriction rejects, they fall back to .platform. CONFIG_INTEGRITY_CA_MACHINE_KEYRING (6.4) applies restrict_link_by_ca() so only CA certificates enter .machine, and CONFIG_INTEGRITY_CA_MACHINE_KEYRING_MAX further excludes CAs that also have digitalSignature set. User space can put the same kind of fence around its own keyrings with KEYCTL_RESTRICT_KEYRING (4.12); for asymmetric keys the restriction string is builtin_trusted, builtin_and_secondary_trusted or key_or_keyring:serial (with :chain to also accept keys vouched for by the keyring itself), and once set a restriction can never be removed.

Revocation runs through the same machinery. Entries of .blacklist are keys of type blacklist whose description is the data — tbs: followed by the SHA-256 of a certificate's to-be-signed part, or bin: followed by the hash of a binary — created with KEY_ALLOC_SET_KEEP so they can never be removed. x509_get_sig_params() checks every parsed certificate with is_hash_blacklisted() and marks a hit, so the certificate can be neither added as a key nor used in a PKCS#7 chain; IMA appraisal calls is_binary_blacklisted() on file digests; and CONFIG_SYSTEM_REVOCATION_LIST adds whole certificates whose keys are rejected by is_key_on_revocation_list(), the call visible in the code above. Signatures are also checked for purpose: the enum key_being_used_for argument — module, firmware, kexec PE image, key, unspecified or BPF — makes pkcs7_verify() demand plain pkcs7-data without authenticated attributes for modules (7.0's CONFIG_PKCS7_WAIVE_AUTHATTRS_REJECTION_FOR_MLDSA relaxes this for ML-DSA signatures, because released OpenSSL versions cannot omit the attributes), authenticated attributes for firmware, and Authenticode for kexec images, so a signature made for one purpose cannot be replayed for another. Keys inside the keyrings are named by identifiers derived from the certificate: keyctl search %:.builtin_trusted_keys asymmetric id:hex matches the tail of a subject key identifier or issuer-plus-serial, ex: demands an exact match, and dn: matches the subject name.

BPF programs gained the same kind of check in 6.18. BPF_PROG_LOAD now accepts a signature, its size, and a keyring_id in union bpf_attr; when a signature is present, bpf_prog_verify_signature() in kernel/bpf/syscall.c resolves the keyring — a system keyring if system_keyring_id_check() accepts the ID, otherwise a key the caller can search for — and passes the instruction array and the signature to bpf_verify_pkcs7_signature(), which ends in the same verify_pkcs7_signature() path. A failure aborts the load before the verifier runs. The signature covers a small loader program; the loader checks the hashes of the maps it is given, so a signed loader extends trust to the real program, and an LSM can require signed loads through the bpf_prog_load hook. The opposite direction, a BPF program checking a signature, has existed since 6.1: the kfuncs bpf_lookup_user_key(), bpf_lookup_system_key(), bpf_key_put() and bpf_verify_pkcs7_signature() in kernel/bpf/helpers.c let a BPF LSM program verify, for example, an fs-verity digest or a signed configuration blob against a keyring before allowing an operation.

Trusted Keys, Encrypted Keys, and the TPM

A user key's payload sits in kernel memory and in whatever file user space loaded it from. Trusted keys (2.6.38) close that gap: the kernel asks a hardware root of trust to generate a random key and seal it, and user space only ever sees the sealed blob, which it can store on disk and hand back on the next boot for the hardware to unseal. With a TPM, sealing can bind the key to PCR values (§5.1), so the blob unseals only if the machine booted the expected software. The back end is chosen at boot with trusted.source= from trusted_key_sources[] in security/keys/trusted-keys/trusted_core.c, and the seal and unseal operations are static calls: 

/* security/keys/trusted-keys/trusted_core.c */

The sources mirror the hardware landscape of the two architectures. On x86_64 servers and PCs the TPM is a discrete chip on LPC or SPI, or firmware TPM in the platform's management engine, and tpm is the natural choice. ARM64 systems often have no discrete TPM; there the tee source (5.13) asks a trusted application in OP-TEE or another TrustZone OS to seal with a hardware-unique key, and NXP i.MX and Layerscape SoCs can use their CAAM (caam, 5.19) or, on older i.MX parts, the DCP engine (dcp, 6.10, sealing with its unique or one-time-programmable key). A firmware TPM implemented as a TrustZone application is also common on ARM64, driven by drivers/char/tpm/tpm_ftpm_tee.c (5.4) or, on Arm FF-A systems, by the CRB-over-FF-A transport tpm_crb_ffa.c (6.15). pkwm, new in 7.0, uses IBM PowerVM's key-wrapping module. The random key material comes from the source's own generator unless trusted.rng=kernel (5.19) selects get_random_bytes_wait() instead, for platforms whose hardware RNG is not trusted.

User space drives trusted and encrypted keys through command strings in the add_key() payload rather than through raw key bytes: 

$ keyctl add trusted kmk "new 32 keyhandle=0x81000001" @u
440502848
$ keyctl pipe 440502848 > kmk.blob          # sealed blob, safe to store
$ keyctl add encrypted evm "new trusted:kmk 32" @u
159771175
$ keyctl pipe 159771175 > evm.blob
# next boot:
$ keyctl add trusted kmk "load $(cat kmk.blob)" @u
$ keyctl add encrypted evm "load $(cat evm.blob)" @u

new asks the source to generate and seal a key of 32 to 128 bytes; load hands back a blob for unsealing; update reseals an existing key, allowed only if it was created migratable. TPM options travel in the same string: keyhandle= names the parent storage key (mandatory for TPM 2.0 unless the blob carries it), blobauth= sets an authorization value, and hash=, policydigest= and policyhandle= bind a TPM 2.0 key to a policy, typically a PCR policy that user space computed; migratable= decides whether the key may be resealed later, and pcrinfo= and pcrlock= are TPM 1.2 holdovers. Since 5.13, TPM 2.0 blobs use the ASN.1 TPMKey format of trusted-keys/tpm2key.asn1, shared with the OpenSSL TPM 2.0 engines, so the parent handle travels with the blob. Unsealing happens inside the hardware each boot; only the source that sealed a blob can open it, so a stolen disk image carries nothing usable.

Encrypted keys (security/keys/encrypted-keys/) are the software companion: a random key generated by the kernel and stored on disk encrypted (AES-CBC, with an HMAC-SHA256 over the blob) under a master key named trusted:name or user:name. Many encrypted keys can share one trusted master key, so a single TPM-sealed secret can protect the EVM HMAC key (§5.3), eCryptfs keys (format ecryptfs) and NVDIMM security keys (format enc32), and dm-crypt accepts encrypted keys as :encrypted: volume keys. The data key is protected by AES-CBC under a key derived from the master key with SHA-256, and the blob carries an HMAC-SHA256 so that tampering is detected before the key is used. Like trusted keys, they are never exported in the clear: keyctl read returns the encrypted form. Normally the kernel generates the data key itself; CONFIG_USER_DECRYPTED_DATA (5.18) lets new accept caller-supplied plaintext instead, for migrating an existing key under a new master key, at the cost of that key having once been in user space.

The TPM driver itself lives in drivers/char/tpm/. tpm-chip.c registers /dev/tpmN and the resource-managed /dev/tpmrmN (4.12), whose tpm2-space.c swaps TPM 2.0 object and session contexts in and out so that several users can share a TPM with very few slots; tpm1-cmd.c and tpm2-cmd.c build commands for the two protocol generations; and transport drivers cover TIS over LPC/SPI/I²C (tpm_tis*.c), the Command Response Buffer interface used by firmware TPMs (tpm_crb.c), the TEE firmware TPM, the SVSM vTPM inside AMD SEV-SNP guests (tpm_svsm.c, 6.16) and a software proxy for containers (tpm_vtpm_proxy.c). In-kernel users go through a small API — tpm_default_chip(), tpm_pcr_extend(), tpm_pcr_read(), tpm_get_random() — and since 6.10 CONFIG_TCG_TPM2_HMAC can protect that traffic with HMAC and encrypted TPM 2.0 sessions (tpm2-sessions.c), because an attacker with a logic analyzer on the SPI bus could otherwise read unsealed keys or forge PCR extends. The sessions cost a salted key exchange per command, so 6.12 added the tpm.disable_pcr_integrity parameter to skip them for the frequent PCR extends that IMA issues, and 6.18 turned the option off by default. The firmware's own measurements of the boot process are exported as /sys/kernel/security/tpm0/binary_bios_measurements, the event log that the next section continues.

Integrity Measurement: IMA and EVM

Secure Boot and module signatures stop at the kernel. Once user space runs, the files that get executed, mapped and read are whatever happens to be on disk. The Integrity Measurement Architecture (IMA, merged in 2.6.30) carries the chain past that point. It can measure a file (hash it, log the hash, and extend a TPM PCR so the log cannot be rewritten), it can appraise a file (compare the hash or a signature with a reference stored in the security.ima extended attribute and refuse access on a mismatch), and it can audit a file (emit the hash as an audit record). The Extended Verification Module (EVM, 3.2) protects the reference values themselves: it keeps an HMAC or signature over a file's security xattrs and metadata, so an offline attacker cannot simply rewrite security.ima to match a modified binary. Both live in security/integrity/, and since 6.9 both are ordinary LSMs named ima and evm that register hooks like any other module (they used to be called from fixed points in the VFS). Their per-inode state lives in the LSM blob, and since 6.19 their initialization also runs from the LSM framework's ordered init calls rather than from separate initcalls of their own.

Measuring Files into the TPM

IMA's main entry points are LSM hooks: bprm_check_security for execve(); bprm_creds_from_file for CREDS_CHECK rules, which match on the credentials the new program will run with (moved there in 6.19, when set-user-ID credentials came to be computed only in that hook); bprm_creds_for_exec for execveat() with AT_EXECVE_CHECK (6.14), which lets a script interpreter ask whether a script may run and so have it measured and appraised like a binary; mmap_file and file_mprotect for executable mappings; kernel_post_read_file and kernel_post_load_data (with their pre-read counterparts) for modules, firmware, kexec images, policies and certificates, where IMA hashes the buffer the kernel has already read, so the content checked is exactly the content used; key_post_create_or_update for keys added to a watched keyring (5.6); and file_post_open for ordinary opens. The last one runs at the end of do_open() in fs/namei.c, after vfs_open() has succeeded, so IMA sees a fully opened file it can read: 

/* security/integrity/ima/ima_main.c */
static int ima_file_check(struct file *file, int mask)
{
	struct lsm_prop prop;

	security_current_getlsmprop_subj(&prop);
	return process_measurement(file, current_cred(), &prop, NULL, 0,
				   mask & (MAY_READ | MAY_WRITE | MAY_EXEC |
					   MAY_APPEND), FILE_CHECK, 0, false);
}

Every hook funnels into process_measurement(), which takes the hook identity and works through the stages shown in Figure 27-5. The hook identities are the func= values of the policy: FILE_CHECK, BPRM_CHECK, CREDS_CHECK, MMAP_CHECK, MMAP_CHECK_REQPROT (6.3, which judges the protection the application asked for rather than the one the kernel applied, a difference only when READ_IMPLIES_EXEC adds PROT_EXEC), MODULE_CHECK, FIRMWARE_CHECK, KEXEC_KERNEL_CHECK, KEXEC_INITRAMFS_CHECK, POLICY_CHECK and POST_SETATTR. Three more, KEXEC_CMDLINE (5.3), KEY_CHECK (5.6) and CRITICAL_DATA (5.12), measure a buffer rather than a file and go through the smaller process_buffer_measurement(), and SETXATTR_CHECK (5.15) only limits which hash algorithms may be written into security.ima:

  1. ima_get_action() walks the policy rules and returns a bitmask of IMA_MEASURE, IMA_APPRAISE, IMA_AUDIT and IMA_HASH, together with the PCR and template to use. A rule can match on the hook, the access mask, the file owner or group and the caller's IDs (each with =, < or >), the filesystem magic, name, FUSE subtype (fs_subtype=, 6.19) or UUID, and the subject or object LSM label, which is why the hook passes the caller's lsm_prop.
  2. Per-inode state lives in a struct ima_iint_cache in the inode's LSM blob. Its flags record what has already been done (IMA_MEASURED, IMA_APPRAISED, …), so a file is hashed once and then served from cache until something invalidates it. When the last writer closes the file, ima_check_last_writer() compares the inode's change cookie (STATX_CHANGE_COOKIE, i.e. i_version) with the value recorded at measurement time and clears the flags if they differ; a change to security.ima or to the protected metadata does the same. On a stacked filesystem such as overlayfs the cache also tracks the underlying real inode (6.7) and its metadata inode (6.10), because a copy-up changes the data without touching the overlay inode. On a filesystem that cannot report changes at all, such as FUSE (SB_I_IMA_UNVERIFIABLE_SIGNATURE), the file is re-evaluated on every access.
  3. ima_collect_measurement() hashes the file contents through the crypto API (§3) with the algorithm from the xattr or the ima_hash= default. The Kconfig default is still SHA-1, and SHA-256 is the usual choice.
  4. ima_store_measurement() builds a template entry and calls ima_add_template_entry(). Appraisal and auditing follow.

A second group of hooks does bookkeeping rather than measuring. file_release runs the last-writer check above. path_post_mknod and inode_post_create_tmpfile mark a newly created file so that it can be written before it has a security.ima value. inode_post_setattr clears the appraisal state when the owner or mode changes, because a policy rule may match on those. The inode_setxattr, inode_removexattr, inode_set_acl and inode_remove_acl hooks guard security.ima itself: writing it needs CAP_SYS_ADMIN and a hash algorithm permitted by any SETXATTR_CHECK rule, and changing it or an EVM-protected attribute forces the next access to appraise again (since 6.18, writing an unrelated xattr no longer clears the record that the file is signed). kernel_module_request refuses requests for crypto-pkcs1(rsa,…) templates, because loading the RSA module would itself need an appraisal that needs RSA.

The measurement list is append-only and every append is anchored in hardware:

A PCR cannot be written, only extended: the TPM replaces its value with H(old || new). After boot the PCR therefore summarizes the whole sequence of measurements, and a remote verifier that receives the list together with a TPM quote (a PCR value signed by a key that never leaves the TPM) can replay the list and check that it matches. tpm_pcr_extend() requires one digest per allocated PCR bank (SHA-1, SHA-256, …), so each template entry carries a digest for every bank. The PCR is 10 by default (CONFIG_IMA_MEASURE_PCR_IDX, range 8–14). The duplicate check means a file whose content has not changed is logged once even if many paths open it. When IMA detects a violation — a file opened for write while it is being measured, or measured while a writer holds it open — it records an entry whose PCR digests are all 0xff bytes. The PCR then no longer matches any clean replay, and the verifier knows the measurement is untrustworthy. Since 6.15 an open_writers violation is recorded once per write-open file and a ToMToU (time-of-measure, time-of-use) violation once per read-open, instead of on every open, which kept busy files from flooding the list; the violations file counts them. Since 6.14 IMA also stops extending the PCR and appending to the list once the reboot notifier has run, so measurements taken while the system is shutting down cannot leave the TPM and the log out of step. Without a TPM, IMA still keeps the list, but nothing anchors it.

The first entry is the boot_aggregate, a hash over PCRs 0–7 (and 8–9 for non-SHA-1 banks) that ties the file measurements to the firmware and boot-loader measurements of §4.4. The list is exported through securityfs:

Each line gives the PCR, the template hash (the value that was extended), the template name, and the template fields — for ima-ng an algorithm-prefixed file digest and the path name (the hashes above are shortened). The per-bank file names were added in 6.10; the old names are symbolic links to the SHA-1 variants. A bank whose algorithm the crypto API does not provide is named by its TPM algorithm number instead (…_tpm_alg_id, a fix in 7.0.10). Other templates add fields: ima-sig appends the file signature; ima-ngv2 and ima-sigv2 (5.19) prefix the digest with its type, ima: for a plain file hash or verity: for an fs-verity digest, so the two can never be confused; ima-modsig (5.4) records an appended module signature; evm-sig (5.14) adds the EVM signature and the metadata it covers; and ima-buf logs a buffer instead of a file. ima_template= selects a template at boot and ima_template_fmt= builds a custom one from field names such as d-ng|n-ng|sig. Buffers logged with ima-buf include the kexec command line, keys added to watched keyrings and critical data: the running kernel's version string, SELinux's state and a hash of its loaded policy, device-mapper table changes (dm-ima, 5.15), and the kexec_load and kexec_execute records described next.

Across a kexec_file_load() reboot the list is carried into the new kernel by ima_add_kexec_buffer() and restored by ima_load_kexec_buffer(), because the TPM PCRs are not reset by a kexec and the new kernel's list must still replay to them (Appendix A). Since 6.16 the list is copied when the kexec is executed rather than when the image is loaded, so measurements taken in between are not lost. The segment reserved at load time has CONFIG_IMA_KEXEC_EXTRA_MEMORY_KB of headroom; if the list has outgrown it, as much as fits is copied, and the kexec_load and kexec_execute critical-data records, which carry the segment size, the list size and the entry count at each point, let a verifier see whether entries were dropped. A crash (kdump) kernel does not receive the list, and since 6.17 it honors ima=off so that it need not measure at all. In 7.0 the new kernel also checks that the buffer handed over lies in addressable RAM before reading it.

Appraisal, Policy, and Secure Boot

Measurement only reports; appraisal enforces. When a rule says appraise, ima_appraise_measurement() reads security.ima and compares it with the freshly computed digest. The first byte of the xattr is a type from enum evm_ima_xattr_type: IMA_XATTR_DIGEST_NG (a bare hash with an algorithm byte, protected only by EVM; the older IMA_XATTR_DIGEST implied SHA-1), EVM_IMA_XATTR_DIGSIG (a signature verified against the .ima keyring), or IMA_VERITY_DIGSIG (5.19, a version-3 signature over an fs-verity file digest, §6.1, accepted only by a rule with appraise_type=sigv3). A rule with appraise_type=imasig rejects a bare hash with the cause IMA-signature-required, and appraise_type=modsig (5.4) also accepts a signature appended to a module or kernel image. The .ima keyring (with the default CONFIG_INTEGRITY_TRUSTED_KEYRING) only accepts keys signed by a built-in trusted key, or also by a secondary one if CONFIG_IMA_KEYRINGS_PERMIT_SIGNED_BY_BUILTIN_OR_SECONDARY is set (§4.3), so the root of appraisal trust is the same as for modules. If the comparison fails and the ima_appraise= mode is enforce (the default), the access gets -EACCES; fix rewrites the xattr instead (for labeling a filesystem once), and log only records the failure. Choosing a mode needs CONFIG_IMA_APPRAISE_BOOTPARAM, and the parameter is ignored when the machine booted with Secure Boot on.

A hash in security.ima is maintained by the kernel. A newly created file passes appraisal while it is still empty (the IMA_NEW_FILE flag), and when the last writer of an appraised file closes it, ima_update_xattr() rehashes the file and rewrites security.ima, which EVM then covers with a fresh HMAC. A signature cannot be maintained that way: a signed file that is modified simply fails its next appraisal, which is the point. Every failure goes to the audit log with AUDIT_INTEGRITY_DATA and a cause such as missing-hash, invalid-hash, invalid-signature or one of EVM's missing-HMAC and invalid-HMAC.

The policy is a list of rules, built into the kernel through ima_policy= (tcb, appraise_tcb, secure_boot, critical_data, fail_securely), then replaced at run time by writing rules to /sys/kernel/security/ima/policy. Each rule is an action (measure, appraise, audit or hash, each with a dont_ form; dont_audit came in 6.19) followed by the conditions listed above and by options: appraise_type=, appraise_flag=check_blacklist (reject a hash on the .blacklist keyring, §4.3), appraise_algos= (5.15, the hash algorithms a signature may use), digest_type=verity (5.19), pcr=, template=, keyrings= and label= for buffer measurements, and permit_directio. tcb measures every executable, every mapping with PROT_EXEC, every module, firmware file and IMA policy, and every file root opens for reading; since 6.14 it skips tmpfs only for FILE_CHECK, so programs run from tmpfs are measured too. With CONFIG_IMA_APPRAISE_BUILD_POLICY, appraisal rules chosen at build time are enforced without a command-line option and survive a custom policy: 

# Do not bother with pseudo-filesystems.
dont_measure fsmagic=0x9fa0
dont_appraise fsmagic=0x62656572
# Measure everything executed, and every file root opens for reading.
measure func=BPRM_CHECK mask=MAY_EXEC
measure func=FILE_CHECK mask=MAY_READ uid=0
# Executables and libraries must carry a valid signature.
appraise func=BPRM_CHECK appraise_type=imasig
appraise func=MMAP_CHECK mask=MAY_EXEC appraise_type=imasig

(The two magic numbers are PROC_SUPER_MAGIC and SYSFS_MAGIC.) The policy file can be written once unless CONFIG_IMA_WRITE_POLICY is set, and with CONFIG_IMA_APPRAISE_REQUIRE_POLICY_SIGS the new policy must itself be a signed file loaded by path, so the policy becomes another appraised object.

The firmware's Secure Boot state also feeds into the policy. Both x86_64 (with EFI) and ARM64 imply CONFIG_IMA_SECURE_AND_OR_TRUSTED_BOOT, which builds ima_efi.c; it supplies architecture rules when the machine booted with Secure Boot enabled:

	"appraise func=KEXEC_KERNEL_CHECK appraise_type=imasig",

	"measure func=KEXEC_KERNEL_CHECK",

This is the mainline mechanism by which Secure Boot reaches into the running kernel. With CONFIG_IMA_ARCH_POLICY, booting under Secure Boot makes module and kexec signatures mandatory, using either the native signature checks of Appendix B or IMA signatures. Kexec appraisal also accepts keys from the .platform keyring, the UEFI db keys, because the kernel being loaded was signed for the firmware and not for the running kernel. The command-line secure_boot policy is the same idea without the firmware check: it requires signatures for modules, firmware, kexec kernels and the IMA policy, accepting an appended signature for modules and checking module hashes against the blacklist. Since 6.19 IMA can also appraise modules that the kernel decompresses itself: it hashes the compressed file as read and defers the decision until the module's buffer is available, so the secure_boot rule accepts imasig|modsig there as well. §8.2 places this in the full chain.

EVM: Protecting the Security Attributes

IMA appraisal and the MAC modules of §2 both trust xattrs: SELinux trusts security.selinux, Smack and AppArmor their own labels, the capability code security.capability, and IMA security.ima. Anyone who can mount the disk elsewhere can rewrite those values. EVM closes the gap by storing security.evm, which covers the configured security xattrs (SELinux, Smack's label plus three more with CONFIG_EVM_EXTRA_SMACK_XATTRS, AppArmor, IMA and file capabilities, plus any added through /sys/kernel/security/integrity/evm/evm_xattrs with CONFIG_EVM_ADD_XATTRS; POSIX ACLs are covered indirectly, through the mode bits they change) together with the inode number, generation, owner, group and mode, and optionally the filesystem UUID:

  • HMAC mode: evm_calc_hmac() computes an hmac(sha1) (the name is fixed in evm_crypto.c) with crypto_alloc_shash(), keyed by the encrypted key named evm-key. That key is normally sealed by a trusted key (§4.4), so the HMAC can only be recomputed on the machine whose TPM unseals it. Every legitimate change to a protected xattr or attribute goes through EVM's inode_post_setxattr or inode_post_setattr hook, which updates the HMAC.
  • Signature mode: security.evm holds a signature verified against the .evm keyring. Portable signatures (EVM_XATTR_PORTABLE_DIGSIG) leave out the inode number and generation, so a distribution can sign files at build time and ship them in a package. Files with portable signatures are immutable as far as EVM is concerned.

evm_verifyxattr() is the check IMA calls before it trusts security.ima (Figure 27-5). EVM's own inode_setxattr hook refuses a change to a protected xattr whose current HMAC does not verify. EVM stays inactive until user space loads its key and writes the initialization flags (EVM_INIT_HMAC = 1, EVM_INIT_X509 = 2) to /sys/kernel/security/evm, typically from the initramfs before the root filesystem is mounted.

Two more flags (4.16) govern what happens next. EVM_SETUP_COMPLETE forbids further writes to the file, and loading the HMAC key sets it automatically. EVM_ALLOW_METADATA_WRITES = 4 is for systems that use only portable signatures: while no HMAC key is loaded it lets protected xattrs and metadata be changed without EVM's checks (a signed file then simply fails its next verification), and it is refused or cleared once an HMAC key is present. With an HMAC key loaded, the inode_init_security hook computes security.evm for each new file from the xattrs the LSMs are about to attach (7.0 sorts them into the configured order first, because Smack's attributes had begun to arrive in a different order than evmctl and the verification path used). X.509 certificates can be loaded into the .evm and .ima keyrings by the kernel itself from /etc/keys/x509_evm.der and /etc/keys/x509_ima.der (CONFIG_EVM_LOAD_X509, CONFIG_IMA_LOAD_X509). evm=fix on the command line lets the kernel rewrite invalid HMACs, as ima_appraise=fix does for hashes. Overlayfs marks its superblock SB_I_EVM_HMAC_UNSUPPORTED (6.10), because the overlay inode's number and the lower files' xattrs do not form a stable HMAC input, and its inode_copy_up_xattr hook lets only a portable signature be copied to the upper layer; an HMAC or a non-portable signature is discarded.

Verified Content: fs-verity, dm-verity, and IPE

IMA hashes a whole file before access and caches the verdict. That is expensive for large files, and it says nothing about blocks that are paged out and later read back from a disk that someone has tampered with. The verity mechanisms take the other approach: they hash the data lazily, one block at a time, at the moment it is read from storage, against a Merkle tree whose root is the only value that must be trusted. fs-verity (5.4) does this per file; dm-verity (3.4) does it for a whole read-only block device. The Integrity Policy Enforcement LSM (IPE, 6.12) then turns "this content was verified against a signed root" into an access-control property: execute only code that came from a verified source. The cost therefore moves from open time to read time, and blocks that are never read are never hashed.

Merkle Trees and fs-verity

Figure 27-6 shows the tree both mechanisms build. The content is split into blocks (usually 4 KiB). Each data block is hashed, the hashes are packed into hash blocks of the same size, those blocks are hashed in turn, and so on until a single block remains; its hash is the root hash. With SHA-256 and 4 KiB blocks each hash block holds 128 digests, so a 1 GiB file needs a three-level tree of about 8 MiB. To verify a block the kernel hashes it, compares the result with the digest in its level-0 hash block, verifies that hash block against level 1, and continues until it reaches a hash block that has already been verified. Only the first read of each hash block costs a walk to the root.

The parameters are chosen when the tree is built. fs-verity offers SHA-256 and SHA-512 and an optional salt that is hashed in front of every block. Its tree block size can be anything from 1 KiB up to the page size or the filesystem block size, whichever is smaller. Before 6.3 the tree block had to equal the page size, which meant a file sealed on a 4 KiB-page x86_64 machine could not be verified on an ARM64 kernel with 16 KiB or 64 KiB pages. Now that the two sizes may differ, the record of which hash blocks are verified has two forms. When a tree block fills a page, the page's PG_checked flag records it, and the flag disappears with the page if the page is reclaimed. When the blocks are smaller, a per-file bitmap records them. Since 7.0-rc3 fs-verity cannot be enabled at all on kernels with pages larger than 64 KiB (some PowerPC and Hexagon configurations), because all three filesystems cache the tree at a 64 KiB-aligned offset in the page cache.

fs-verity is a library in fs/verity/ that ext4, f2fs and btrfs call through struct fsverity_operations; ext4's use of it, including where the tree is stored, is described in Chapter 18. A process enables it with FS_IOC_ENABLE_VERITY, passing the hash algorithm, block size, an optional salt and an optional signature. The file must be open read-only, and no writer may have it open. The kernel reads the whole file, builds the tree, and writes it through the filesystem's write_merkle_tree_block operation. It then stores a struct fsverity_descriptor and marks the inode (S_VERITY, shown as FS_VERITY_FL and STATX_ATTR_VERITY). After that the file can never be opened for writing again. Since 7.0 setattr_prepare() also refuses to change its size for every filesystem; btrfs had lacked that check. The file digest returned by FS_IOC_MEASURE_VERITY is the hash of that descriptor, so it binds the root hash and the file size: a tiny value that identifies gigabytes of content and costs nothing to recompute at open time. The FS_IOC_READ_VERITY_METADATA ioctl (5.12) returns the tree, the descriptor or the signature, so a file can be backed up or copied together with its tree, and the BPF kfunc bpf_get_fsverity_digest() (6.8) gives BPF LSM programs the same digest.

Reads verify as they complete. Filesystems call fsverity_verify_bio() or fsverity_verify_blocks() from their read-completion paths (deferred to a workqueue, since hashing can sleep), and both end in verify_data_block() in fs/verity/verify.c. Since 7.0 the read_folio and readahead paths start readahead of the needed hash pages, through fsverity_readahead(), when they submit the data I/O. The hashes are then usually in memory by the time the data arrives, instead of being read only after it completes; the author measured 64 KiB sequential reads rising from about 2.5 to 3.7 GB/s:

A failure gives the reader -EIO; there is no way to read a corrupted block of a verity file. Since 6.17 the hashing goes through the SHA-2 library of §3.4 instead of a crypto_shash, and since 6.18, when two data blocks are pending, the code uses sha256_finup_2x() to hash them interleaved, which roughly doubles throughput on CPUs with SHA-NI or the ARMv8 SHA-2 instructions. The per-file struct fsverity_info (tree parameters, root hash, file digest, and the bitmap of verified hash blocks) moved in two steps. In 6.18 the generic inode::i_verity_info pointer gave way to a field in the filesystem-specific inode. In 7.0 that field went too, and the info now lives in an rhashtable keyed by inode, so filesystems no longer pay a pointer in every inode for a feature few files use. The info is inserted before S_VERITY is set, so the flag check is enough to know it exists. 7.0 also added tracepoints (fsverity_enable, fsverity_verify_data_block, fsverity_merkle_hit and others) that show which reads were served by already-verified hash blocks.

fs-verity proves that the content matches a digest. Deciding whether that digest is acceptable is left to policy. Three options exist: the legacy built-in signature (CONFIG_FS_VERITY_BUILTIN_SIGNATURES, checked against the .fs-verity keyring, optionally made mandatory by /proc/sys/fs/verity/require_signatures); an IMA IMA_VERITY_DIGSIG signature in security.ima, selected by an appraise rule with digest_type=verity; or an IPE rule (§6.3). The built-in signature is checked each time the file's verity info is set up, that is, on the first open after the inode was loaded. The .fs-verity keyring is writable by root until user space restricts it. The fs-verity documentation and a comment in fs/verity/signature.c both discourage the built-in signature in favor of the other two options or of user-space checks. Overlayfs (6.6) is a fourth consumer. With verity=on or verity=require, a metacopy file in the upper layer records the fs-verity digest of the lower data file it redirects to, and overlayfs checks the lower file against that digest when it is opened. composefs is built on this: it mounts a signed or measured image of metadata over a shared store of verity-sealed content files.

dm-verity: A Verified Block Device

dm-verity is a device-mapper target (drivers/md/dm-verity-target.c) that applies the same tree to a whole read-only device, typically the root filesystem image of Android, ChromeOS, or an immutable server OS. The tree lives on a separate hash device or in a reserved area of the same device, and the table line supplies everything else: 

# dmsetup create vroot --readonly --table \
  "0 2097152 verity 1 /dev/sda2 /dev/sda3 4096 4096 262144 1 sha256 \
   <root-hash-hex> <salt-hex> \
   2 root_hash_sig_key_desc vroot.sig"

The fields are the version, data and hash devices, the two block sizes, the number of data blocks, the hash start block, the algorithm, the root hash, the salt, and optional arguments. Here the optional argument names a user-type key, found with request_key() in the caller's keyrings, that holds a PKCS#7 signature over the root hash. dm-verity-verify-sig.c checks it with verify_pkcs7_signature() against the built-in keyring, or against the secondary or .platform keyrings when CONFIG_DM_VERITY_VERIFY_ROOTHASH_SIG_SECONDARY_KEYRING or ..._PLATFORM_KEYRING is set (§4.3). Since 7.0 a third source is the .dm-verity keyring. Booting with dm_verity.keyring_unsealed=1 leaves it open, so the boot process can add keys meant only for verity images (systemd's discoverable disk images) and then restrict it. The keyring is consulted only when it holds keys and has a restriction set, so by default nothing changes. A missing signature is accepted unless the dm_verity.require_signatures=1 module parameter is set. That parameter is the switch that makes the check mandatory. On every read the target walks the tree: 

/* drivers/md/dm-verity-target.c */
int verity_hash_for_block(struct dm_verity *v, struct dm_verity_io *io,
			  sector_t block, u8 *digest, bool *is_zero)
{
	int r = 0, i;

	if (likely(v->levels)) {
		/*
		 * First, we try to get the requested hash for
		 * the current block. If the hash block itself is
		 * verified, zero is returned. If it isn't, this
		 * function returns 1 and we fall back to whole
		 * chain verification.
		 */
		r = verity_verify_level(v, io, block, 0, true, digest);
		if (likely(r <= 0))
			goto out;
	}

	memcpy(digest, v->root_digest, v->digest_size);

	for (i = v->levels - 1; i >= 0; i--) {
		r = verity_verify_level(v, io, block, i, false, digest);
		if (unlikely(r))
			goto out;
	}
	...
}

verity_verify_level() reads hash blocks through dm-bufio and marks each one hash_verified once it matches, which is the dm-verity form of the cache in Figure 27-6. Since 6.19, version-1 SHA-256 tables hash with the SHA-256 library directly (use_sha256_lib) and, like fs-verity, hash two blocks interleaved when the CPU benefits. Other algorithms still use a crypto_shash; support for asynchronous hash drivers was dropped in 6.17. Before a mismatch is reported, verity_recheck() (6.8) reads the block again into a kernel buffer and hashes it there. Without that step, a process doing O_DIRECT reads of several blocks into one buffer could change the data between the read and the hash and cause a false failure. ignore_zero_blocks returns zeros, without checking the data, for blocks whose expected hash is that of an all-zero block, as in a sparse image. check_at_most_once verifies each data block only on its first read, which saves CPU time on slow devices at the cost of not detecting later changes.

On a mismatch the target first tries forward error correction if CONFIG_DM_VERITY_FEC data is configured (use_fec_from_device, fec_roots, fec_blocks, fec_start). Since 6.15 FEC also repairs hash blocks whose read failed, and since 6.19 the status line reports how many blocks it corrected. If correction fails, the target acts according to its mode: fail the I/O (the default), log only (ignore_corruption), or reboot or panic (restart_on_corruption, panic_on_corruption). restart_on_error and panic_on_error (6.12) do the same for plain I/O errors. The reboot and panic modes suit systems that would rather reboot into a fallback image than run on corrupted data. Every mismatch sets the corruption flag shown as C in dmsetup status and generates a uevent carrying DM_VERITY_ERR_BLOCK_NR. The first 100 mismatches are also logged, and with CONFIG_DM_AUDIT they are reported through the audit subsystem of §7. With try_verify_in_tasklet, reads whose hash blocks are already cached are verified in the bottom-half workqueue rather than a kworker, which cuts read latency. Since 6.15 the size limit for that fast path is set per I/O priority class (the use_bh_bytes module parameter), and since 6.16 it is skipped when the CPU needs to reschedule. A root device can be set up without an initramfs with dm-mod.create= (5.1), and LoadPin can trust files from verity devices whose root hashes it was given (§2.4).

IPE: Policy over Provenance

fs-verity and dm-verity make content tamper-evident, and dm-verity can check a signature, but neither decides what may run. IPE (security/ipe/, 6.12) is a minor LSM that does exactly that and nothing else. It has no labels and no notion of users. Its rules match an operation (op=EXECUTE, FIRMWARE, KMODULE, KEXEC_IMAGE, KEXEC_INITRAMFS, POLICY, X509_CERT) against properties of the file's origin. The properties are boot_verified, dmverity_roothash=, dmverity_signature, fsverity_digest= and fsverity_signature, each compiled in only if the matching CONFIG_IPE_PROP_* option and the verity feature behind it are enabled. A rule matches when all its properties do. The first matching rule for the operation decides; otherwise a DEFAULT for the operation applies, and failing that the global DEFAULT: 

policy_name=Locked_Appliance policy_version=1.0.0
DEFAULT action=DENY

op=EXECUTE boot_verified=TRUE action=ALLOW
op=EXECUTE dmverity_signature=TRUE action=ALLOW
op=EXECUTE fsverity_signature=TRUE action=ALLOW
op=KMODULE dmverity_roothash=sha256:a3f1...9c action=ALLOW

The properties come from hooks the verity code calls. When a dm-verity device is resumed, security_bdev_setintegrity() passes the root hash (LSM_INT_DMVERITY_ROOTHASH) and the result of the signature check (LSM_INT_DMVERITY_SIG_VALID), and IPE stores them in its block-device blob. fs-verity reports a verified built-in signature through security_inode_setintegrity() (LSM_INT_FSVERITY_BUILTINSIG_VALID). boot_verified is true for files on the root superblock that the initramfs_populated hook marked after the initramfs was unpacked, which lets the boot policy trust a signed initramfs before any verity device exists. At access time IPE's bprm_check_security, mmap_file, file_mprotect, kernel_read_file and kernel_load_data hooks build an evaluation context and call ipe_evaluate_event(). For a file on overlayfs the context uses the real inode underneath. Since 6.19 bprm_creds_for_exec also evaluates op=EXECUTE for execveat(…, AT_EXECVE_CHECK), so a script interpreter that asks can be held to the same policy as a binary. Three consequences follow from evaluating the source rather than the file. First, an executable mapping with no file behind it (JIT code) and a module loaded from a buffer with init_module() have no properties, so DEFAULT op=EXECUTE action=DENY forbids anonymous executable memory unless a rule allows it. Second, mprotect() is checked only when it adds execute permission to a region that lacked it. Third, until a policy is activated IPE allows everything.

Policies are text with an attached PKCS#7 signature. They are written to /sys/kernel/security/ipe/new_policy, verified against the built-in keyring (or the secondary and platform keyrings, with CONFIG_IPE_POLICY_SIG_SECONDARY_KEYRING and CONFIG_IPE_POLICY_SIG_PLATFORM_KEYRING), and activated through policies/<name>/active; a version number prevents rollback to an older signed policy. A boot policy can be compiled in with CONFIG_IPE_BOOT_POLICY. Each policy gets a directory holding its pkcs7, policy, name and version files plus write-only update and delete files. An update must keep the policy name and raise the version, or it fails with -ESTALE. Activating a policy older than the active one is refused, and the active policy cannot be deleted. enforce switches between enforcing and permissive mode, and ipe.enforce=0 and ipe.success_audit=1 set the initial state from the command line. Policy loads and mode changes produce AUDIT_IPE_POLICY_LOAD (with an errno field since 6.16) and AUDIT_IPE_CONFIG_CHANGE records. Every denial produces an AUDIT_IPE_ACCESS record, and successes do too if success_audit is enabled: 

type=1420 audit(1653364370.067:61): ipe_op=EXECUTE ipe_hook=MMAP enforcing=1
  pid=2241 comm="ld-linux.so" path="/deny/lib/libc.so.6" dev="sda2"
  ino=14549020 rule="DEFAULT action=DENY"

(This sample is from the kernel's IPE documentation, wrapped here.) IPE and IMA appraisal overlap in purpose but differ in style. IMA attaches a signature to each file and checks it when the file is opened; IPE trusts whole verified volumes, or verity-sealed files, and costs almost nothing at open time because the hashing is done lazily by the verity layer. The two can be stacked.

The Audit Subsystem

Access control decides; audit remembers. The audit subsystem (kernel/audit.c, kernel/auditsc.c, kernel/auditfilter.c) produces structured records of security-relevant events — system calls that match administrator rules, LSM denials, integrity failures, policy loads, logins reported by user space — and delivers them to a single privileged daemon, auditd, over a netlink socket, without letting a slow consumer lose events silently. How syscall auditing hooks the entry and exit path, and why rules are evaluated only at exit, is covered in Chapter 10. Behind that hook every record follows the same path whatever produced it: it is formatted into a struct audit_buffer, queued as a netlink message on a backlog with an administrator-set limit, and sent by the kauditd kernel thread, which holds or retries messages while no daemon is listening. Administrator rules decide which system calls, files and directory trees generate records; the LSMs and IMA use the same channel for their denials and measurements. The pipeline itself is CONFIG_AUDIT; system-call auditing, file watches and directory trees are CONFIG_AUDITSYSCALL, which needs architecture support and is turned on automatically on both x86_64 and ARM64.

Building a Record

Every audit record, whoever produces it, is built with the same three calls: audit_log_start() allocates a struct audit_buffer for a message type, audit_log_format() (and helpers such as audit_log_untrustedstring() and audit_log_d_path(), which escape or hex-encode values a user could have chosen) appends text, and audit_log_end() queues the result. The start function is where most of the policy lives: 

/* kernel/audit.c (abridged) */
struct audit_buffer *audit_log_start(struct audit_context *ctx, gfp_t gfp_mask,
				     int type)
{
	struct audit_buffer *ab;

	if (audit_initialized != AUDIT_INITIALIZED)
		return NULL;

	if (unlikely(!audit_filter(type, AUDIT_FILTER_EXCLUDE)))
		return NULL;
	...
	if (!(auditd_test_task(current) || audit_ctl_owner_current())) {
		long stime = audit_backlog_wait_time;

		while (audit_backlog_limit &&
		       (skb_queue_len(&audit_queue) > audit_backlog_limit)) {
			/* wake kauditd to try and flush the queue */
			wake_up_interruptible(&kauditd_wait);

			/* sleep if we are allowed and we haven't exhausted our
			 * backlog wait limit */
			if (gfpflags_allow_blocking(gfp_mask) && (stime > 0)) {
				...
				stime = schedule_timeout(rtime);
				...
			} else {
				...
				audit_log_lost("backlog limit exceeded");
				return NULL;
			}
		}
	}

	ab = audit_buffer_alloc(ctx, gfp_mask, type);
	...
	audit_get_stamp(ab->ctx, &ab->stamp);
	...
	audit_log_format(ab, "audit(%llu.%03lu:%u): ",
			 (unsigned long long)ab->stamp.ctime.tv_sec,
			 ab->stamp.ctime.tv_nsec/1000000,
			 ab->stamp.serial);

	return ab;
}

Three details matter. First, the AUDIT_FILTER_EXCLUDE list lets the administrator drop whole record types before any work is done. Second, the backlog check is the subsystem's flow control. When more than audit_backlog_limit records (64 by default, settable with audit_backlog_limit= or by auditd) are waiting, a producer that may sleep blocks for up to audit_backlog_wait_time (60 seconds) for kauditd to drain the queue. This deliberately slows the system down rather than losing events. A producer in atomic context — LSMs call with GFP_ATOMIC — cannot wait, so the record is lost. The daemon itself, and the task holding the audit control mutex, are exempt, or the system could deadlock. The second exemption only postpones the wait: once audit_receive() has dropped the mutex, it puts that sender (auditctl, say) to sleep for up to audit_backlog_wait_time if the queue is still too long. The total time producers have spent waiting accumulates in backlog_wait_time_actual (5.9), which auditctl -s reports next to the current backlog length. Third, the audit(seconds.millis:serial) stamp is taken from the task's audit context when there is one, so every record produced during one system call carries the same serial number and user space can stitch the SYSCALL, PATH, CWD, PROCTITLE and any AVC records into one event, ended by an EOE record.

A lost record goes to audit_log_lost(), which counts it and applies the failure mode set by auditctl -f: AUDIT_FAIL_SILENT (0), AUDIT_FAIL_PRINTK (1, the default), or AUDIT_FAIL_PANIC (2). The last is for sites where an unaudited action is worse than a crash. When a rate limit is set, the warning and the failure action come at most once a second, except in panic mode, where every loss counts. The running total appears as lost in auditctl -s; since 4.11 an AUDIT_SET whose mask is only AUDIT_STATUS_LOST returns and resets it, and the reset is logged. The end of a record is short: 

/* kernel/audit.c */
static void __audit_log_end(struct sk_buff *skb)
{
	struct nlmsghdr *nlh;

	if (audit_rate_check()) {
		/* setup the netlink header, see the comments in
		 * kauditd_send_multicast_skb() for length quirks */
		nlh = nlmsg_hdr(skb);
		nlh->nlmsg_len = skb->len - NLMSG_HDRLEN;

		/* queue the netlink packet */
		skb_queue_tail(&audit_queue, skb);
	} else {
		audit_log_lost("rate limit exceeded");
		kfree_skb(skb);
	}
}

void audit_log_end(struct audit_buffer *ab)
{
	struct sk_buff *skb;

	if (!ab)
		return;

	while ((skb = skb_dequeue(&ab->skb_list)))
		__audit_log_end(skb);

	/* poke the kauditd thread */
	wake_up_interruptible(&kauditd_wait);

	audit_buffer_free(ab);
}

The record is already a netlink message: audit_log_format() writes directly into an sk_buff, so delivery is a queue operation and audit_log_end() can be called in any context, including interrupts. The optional rate limit (audit_rate_limit, messages per second, 0 = unlimited) drops records rather than waiting. The skb_list exists since 6.18 so that one buffer can carry auxiliary records. When more than one LSM supplies security contexts, audit_log_subj_ctx() writes subj=? in the main record and adds an AUDIT_MAC_TASK_CONTEXTS (1425) record listing subj_selinux=…, subj_apparmor=… and so on. This is the audit side of the LSM stacking work described in Chapter 20.

Two global settings decide whether records are made at all. The audit= boot parameter sets audit_default. With audit=0 the subsystem is never initialized, so audit_log_start() returns NULL for every caller until the next boot. With no parameter, audit starts disabled and auditd enables it later, but audit_alloc() gives a new task an audit context only once auditing has been enabled at least once (audit_ever_enabled). Every process started before auditd, including the early services of the boot, runs without a context and produces no system-call records for its whole life; audit=1 closes that gap. At run time audit_enabled is 0 (off: no system-call records, and most kernel producers test it before logging, though LSM denials are still produced and delivered), 1 (on), or 2, AUDIT_LOCKED, set by auditctl -e 2. In the locked state audit_do_config_change() refuses every change to the settings, AUDIT_ADD_RULE and AUDIT_DEL_RULE are refused, and only a reboot unlocks the configuration; since 7.0.10 the tree commands AUDIT_TRIM and AUDIT_MAKE_EQUIV (§7.3) are refused too. Each change, allowed or refused, is itself recorded as an AUDIT_CONFIG_CHANGE (1305) record.

Each record also says who is responsible. Besides its credentials, every task carries a login UID (loginuid, printed as auid=) and a session ID (sessionid, printed as ses=). They live in struct task_struct, not in the cred, so neither changes when the task runs a set-user-ID program or switches users through su or sudo, and both are inherited at fork. A login service sets them by writing the user's UID to /proc/self/loginuid, as pam_loginuid does. Only the task itself may write the file. audit_set_loginuid() takes the next value of a global counter as the new session ID and emits an AUDIT_LOGIN (1006) record with the old and new values and the result. The first write needs no privilege, because the value starts unset (4294967295, which ausearch shows as unset). Changing a set value requires CAP_AUDIT_CONTROL, and two audit features (3.13), set with AUDIT_SET_FEATURE and lockable until reboot, narrow even that: loginuid_immutable forbids any change, and only_unset_loginuid allows only a reset to unset. This is how a record of root deleting a file still names the administrator who logged in, and why rules commonly carry -F auid>=1000 -F auid!=unset to select actions taken by people rather than by daemons that systemd started with an unset login UID.

kauditd and the Netlink Channel

User space talks to audit through a NETLINK_AUDIT socket. auditd sends AUDIT_SET with its port ID to register as the audit daemon (it needs CAP_AUDIT_CONTROL), and auditctl sends AUDIT_ADD_RULE, AUDIT_GET and friends. Every message is refused unless the sender is in the initial user namespace, and the control commands also require the initial PID namespace. A sender in another user namespace gets -ECONNREFUSED, as if the kernel had no audit support. PAM stacks commonly refuse a login when they cannot write an audit record but let it proceed when audit is absent, so -EPERM would lock users out of every container. User-space records, the AUDIT_USER_* ranges 1100–1199 and 2100–2999 sent by login programs, sudo, systemd and SELinux's user-space object managers, need CAP_AUDIT_WRITE rather than CAP_AUDIT_CONTROL. They pass through the USER filter list, and the kernel prefixes the sender's pid, uid, auid, ses and subj fields, so a process cannot claim to be someone else. The kernel thread kauditd_thread() drains the queues (Figure 27-7). Each record on the main audit_queue is first multicast to the AUDIT_NLGRP_READLOG group, which any process with CAP_AUDIT_READ can join (systemd-journald can be configured to), and then unicast to auditd. A send that fails with -EAGAIN moves the record to the retry queue. If no daemon is registered, or it has died, the record is printed to the kernel log (as audit: type=1400 …, rate-limited) and kept on the hold queue, so that a restarted auditd receives what it missed — provided auditing was enabled at boot with audit=1. Both side queues are bounded by the backlog limit, and the hold and retry queues are flushed (with up to five unicast attempts per record) before the main queue on each pass.

The registration itself is an RCU-protected struct auditd_connection holding the daemon's PID, netlink port ID and network namespace. auditd must be in the initial PID namespace but may run in another network namespace; the multicast group exists only in the initial one. An AUDIT_SET must name the sender's own PID. Before accepting it, audit_replace() (4.6) unicasts an AUDIT_REPLACE probe to the registered daemon, and if that daemon is still alive the newcomer is refused with -EEXIST. Only the registered daemon may unregister, by sending PID 0. A send that returns -ECONNREFUSED means the daemon's socket is gone, and auditd_reset() drops the registration and moves the retry queue onto the hold queue. Joining AUDIT_NLGRP_READLOG (3.16) is itself logged, as an AUDIT_EVENT_LISTENER record (5.8), so an administrator can see which programs read the stream. When auditd is sent SIGTERM, SIGHUP, SIGUSR1 or SIGUSR2, audit_signal_info() saves the sender's PID, login UID and LSM label, and auditd fetches them with AUDIT_SIGNAL_INFO to log who stopped or reconfigured it.

The same channel controls TTY auditing (drivers/tty/tty_audit.c), which records what an administrator types. pam_tty_audit sends AUDIT_TTY_SET to turn it on for the login process; the flag is kept in signal_struct and inherited by every process of the session. The N_TTY line discipline passes the input each process reads to tty_audit_add_data(), which collects it in a 4 KiB per-process buffer. The buffer is emitted as a hex-encoded AUDIT_TTY (1319) record when it fills, when the process switches terminals or between canonical and raw mode, when it exits, and before a shell sends its own AUDIT_USER_TTY record. Input typed in canonical mode with echo off, such as a password, is skipped unless the log_passwd option is set, and the master side of a pseudo-terminal is never recorded.

Rules, Filter Lists, Watches, and Trees

Rules are kept in audit_filter_list[], one RCU-protected list per filter point, and each rule is a conjunction of field comparisons (uid, auid, arch, syscall, a0–a3, success, exit, LSM labels, path, directory, executable, key) with an action of always or never. Table 27-6 lists where each list is consulted. audit_filter() in kernel/auditfilter.c handles the lists that need no task context (USER, EXCLUDE); the syscall lists are evaluated in kernel/auditsc.c.

A rule carries at most 64 fields (AUDIT_MAX_FIELDS) and an optional key of up to 256 bytes, set with -k. When the rule matches, the key is copied into the audit context and printed as key= in the SYSCALL record, so searches can select events by purpose. Besides comparing a field with a constant, a rule can compare two attributes of the task or object (AUDIT_FIELD_COMPARE, 3.3, as in -C auid!=uid), or match the executable (exe=, 4.3), the session ID (4.10), the filesystem type (4.15), or the socket address family (saddr_fam, 5.3). On the exit lists the first matching rule decides, so never rules for noisy cases go first, and auditctl -A (AUDIT_FILTER_PREPEND) inserts a rule at the head instead of the tail. Each exit rule also gets a priority from its insertion position. Once a rule has matched during a system call, a candidate from another list can override it only if it has a higher priority, which gives the same result as one ordered list.

File rules are where audit meets the VFS. A rule such as auditctl -w /etc/shadow -p wa -k shadow becomes an exit-list rule with a watch and a permission mask. The mask names system-call classes, not operations. audit_match_perm() asks audit_classify_syscall() which class the current call belongs to. It checks the access mode in the flags of open, openat and openat2, treats execve as x, and looks other calls up in the read, write and attribute-change tables built from include/asm-generic/audit_*.h. A -F dir= rule watches a whole subtree; kernel/audit_tree.c (2.6.24) tags every inode in the tree with marks grouped into struct audit_chunks and follows mounts and moves. An -F exe= rule uses the path marks of kernel/audit_fsnotify.c to identify an executable even if it is replaced. All three are fsnotify groups, the same backend as inotify and fanotify. At syscall exit the inodes recorded in the audit_context are compared against the rules (audit_filter_inodes()), so a watched file generates a full SYSCALL+PATH event no matter which syscall touched it. Rules tied to an inode are not on the exit list at all. They live in audit_inode_hash[], 32 buckets keyed by inode number, and audit_filter_inodes() examines only the buckets of the inodes the call recorded, so a large number of watches costs little on calls that touch none of them. For tree rules, AUDIT_TRIM drops the marks on mounts that are no longer under a tree's path, and AUDIT_MAKE_EQUIV extends every tree that covers one path to the mounts under another, which is needed after a bind mount.

Records from Security Modules

Most security modules report denials through one helper in security/lsm_audit.c (2.6.31): 

/* security/lsm_audit.c */
void common_lsm_audit(struct common_audit_data *a,
	void (*pre_audit)(struct audit_buffer *, void *),
	void (*post_audit)(struct audit_buffer *, void *))
{
	struct audit_buffer *ab;

	if (a == NULL)
		return;
	/* we use GFP_ATOMIC so we won't sleep */
	ab = audit_log_start(audit_context(), GFP_ATOMIC | __GFP_NOWARN,
			     AUDIT_AVC);

	if (ab == NULL)
		return;

	if (pre_audit)
		pre_audit(ab, a);

	dump_common_audit_data(ab, a);

	if (post_audit)
		post_audit(ab, a);

	audit_log_end(ab);
}

The caller fills a struct common_audit_data naming the object (a path, dentry, inode, socket, capability, …), and dump_common_audit_data() prints pid=, comm= and the object description, which audit_log_lsm_data() (split out in 6.15) formats from one of 18 LSM_AUDIT_DATA_* kinds, from paths and sockets to keys, lockdown reasons (unused since SELinux dropped its lockdown check in 5.16, §8.1) and, since 6.14, netlink message types. The callbacks add module-specific text. SELinux's pre-callback writes avc: denied { read } and its post-callback the scontext=, tcontext=, tclass= and permissive= fields. AppArmor and Smack use the same helper and the same AUDIT_AVC type with their own fields (apparmor="DENIED" operation=… profile=…). Because the helper allocates atomically, these records are the first to go when the backlog is full. SELinux controls the volume through policy, not a rate limit. The auditdeny and auditallow bits that come back with each access decision, and are cached with it in the AVC (§2.2), decide what is logged: dontaudit rules silence expected denials, auditallow rules record selected grants, and every other denial produces a record each time it happens. SELinux also writes records outside this helper: AUDIT_MAC_POLICY_LOAD (1403) when a policy is loaded, AUDIT_MAC_STATUS (1404) when enforcing mode changes, AUDIT_MAC_CONFIG_CHANGE (1405) when a boolean changes, and AUDIT_SELINUX_ERR (1401) for invalid contexts and transitions.

The newer modules call audit_log_start() directly with their own types. IMA and EVM use integrity_audit_msg() with AUDIT_INTEGRITY_DATA (1800) for failures and AUDIT_INTEGRITY_RULE (1805) for audit policy rules. IPE uses AUDIT_IPE_ACCESS (1420) and AUDIT_IPE_POLICY_LOAD (1422). Landlock (security/landlock/audit.c, 6.15) emits AUDIT_LANDLOCK_ACCESS (1423) for each denial, naming the sandbox domain and the "blockers" (the access rights that were missing) and describing the object with the same audit_log_lsm_data(), and AUDIT_LANDLOCK_DOMAIN (1424) records when a domain is first involved in a denial and when it is freed. The design problem Landlock solved is that its policies are written by unprivileged applications, so the sandboxed program controls whether its denials are logged through landlock_restrict_self() flags: LANDLOCK_RESTRICT_SELF_LOG_SAME_EXEC_OFF for interpreters that run untrusted code without an execve(), LANDLOCK_RESTRICT_SELF_LOG_NEW_EXEC_ON to log denials by the programs it launches too (off by default), and LANDLOCK_RESTRICT_SELF_LOG_SUBDOMAINS_OFF for container runtimes whose payloads create their own domains (Chapter 20 describes the sandbox itself). The lockdown LSM, by contrast, reports its denials only to the kernel log (§8.1).

Not every security record comes from an LSM. The core kernel reports anomalies: AUDIT_ANOM_ABEND (1701) when a process dumps core, AUDIT_ANOM_PROMISCUOUS (1700) when a network device enters promiscuous mode, and AUDIT_ANOM_LINK and AUDIT_ANOM_CREAT (5.5) when the protected_symlinks, protected_hardlinks, protected_fifos or protected_regular sysctls block an access. Other subsystems add their own types. AUDIT_KERN_MODULE (4.11) names each module loaded, and since 4.12 each module removed; failed loads, dropped by a 6.4 reorganization of the loader, are logged again since 6.17. AUDIT_BPF (5.6) records program loads and unloads. AUDIT_NETFILTER_CFG records table changes, and AUDIT_NETFILTER_PKT records packets matched by the iptables AUDIT target or an nftables log level audit statement, with source and destination ports since 7.0. AUDIT_TIME_ADJNTPVAL and AUDIT_TIME_INJOFFSET (5.2) record clock adjustments. AUDIT_DM_CTRL and AUDIT_DM_EVENT (5.16) report device-mapper table changes and integrity failures in dm-crypt, dm-integrity and dm-verity. AUDIT_FANOTIFY (4.15) records the decision of a fanotify permission listener such as fapolicyd, with the rule number and trust values since 6.3. Many of these are auxiliary records attached to the current system call, and are produced only when the task's audit context is not a dummy, that is, when at least one system-call rule is loaded. A security violation should be logged even without rules, so 6.16 made the ANOM_LINK and ANOM_CREAT records, and 6.18 the fanotify records, depend only on audit_enabled.

Kernel Lockdown and the Chain of Trust

Every mechanism so far assumes the kernel itself is intact. Traditionally, though, root could change the running kernel at will: load an unsigned module, write /dev/mem, poke MSRs or I/O ports, kexec into an arbitrary image, or attach a kprobe that reads any variable. On a machine whose boot was verified by Secure Boot that is a hole: a root compromise turns into a persistent kernel compromise, and the boot-time signatures become pointless. The lockdown LSM (5.4, after years out of tree as a set of distribution patches) closes the interfaces through which user space, even with every capability, can modify or read the running kernel.

The Lockdown LSM

Lockdown is a single hook, security_locked_down(reason), placed at every sensitive interface, and a single global level. The reasons form one ordered enumeration in include/linux/security.h, split into two groups by the markers LOCKDOWN_INTEGRITY_MAX and LOCKDOWN_CONFIDENTIALITY_MAX. Integrity reasons protect the kernel from modification; confidentiality reasons also protect kernel memory from being read, since it can hold keys and other secrets. Linux 7.0.12 defines 28 reasons, 20 for integrity and 8 for confidentiality, checked at about 75 call sites in drivers, file systems, tracing, BPF and architecture code. The module itself is small: 

/* security/lockdown/lockdown.c (abridged) */
static enum lockdown_reason kernel_locked_down;

static int lock_kernel_down(const char *where, enum lockdown_reason level)
{
	if (kernel_locked_down >= level)
		return -EPERM;

	kernel_locked_down = level;
	pr_notice("Kernel is locked down from %s; see man kernel_lockdown.7\n",
		  where);
	return 0;
}

static int lockdown_is_locked_down(enum lockdown_reason what)
{
	if (WARN(what >= LOCKDOWN_CONFIDENTIALITY_MAX,
		 "Invalid lockdown reason"))
		return -EPERM;

	if (kernel_locked_down >= what) {
		if (lockdown_reasons[what])
			pr_notice_ratelimited("Lockdown: %s: %s is restricted; see man kernel_lockdown.7\n",
				  current->comm, lockdown_reasons[what]);
		return -EPERM;
	}

	return 0;
}

static struct security_hook_list lockdown_hooks[] __ro_after_init = {
	LSM_HOOK_INIT(locked_down, lockdown_is_locked_down),
};

Because the reasons are ordered, a request is denied whenever its reason is at or below the current level. Setting the level to LOCKDOWN_INTEGRITY_MAX denies every integrity reason, and LOCKDOWN_CONFIDENTIALITY_MAX denies all of them. The level can only rise: lock_kernel_down() refuses to lower it. It is set by the lockdown=integrity or lockdown=confidentiality boot parameter, by CONFIG_LOCK_DOWN_KERNEL_FORCE_INTEGRITY or ..._FORCE_CONFIDENTIALITY, or at run time by writing the level name to /sys/kernel/security/lockdown, which shows the current level in brackets (none [integrity] confidentiality). CONFIG_SECURITY_LOCKDOWN_LSM_EARLY registers the module as an early LSM so that a level from the command line applies before most of the kernel has initialized. An early LSM is also always initialized, first and regardless of the lsm= list. Without the option, lockdown is enforced only if lockdown appears in lsm= or CONFIG_LSM (every default list includes it). Otherwise lockdown= still records a level, but no hook enforces it. The securityfs file checks nothing beyond its 0644 mode, since the only change a write can make is to raise the level. Building the module selects CONFIG_MODULE_SIG, for the reason given below. Other LSMs may implement the same hook: the decision is the usual LSM conjunction (Chapter 20), and the reason strings in lockdown_reasons[] (security/security.c) are shared so every module reports a denial the same way. Even before lockdown, CONFIG_STRICT_DEVMEM and CONFIG_IO_STRICT_DEVMEM limited /dev/mem to non-RAM regions not claimed by a driver. Lockdown removes the device for everyone. Several reasons are not on/off switches but select the safe variant of an operation. LOCKDOWN_MODULE_SIGNATURE is checked only after a module's signature has failed to verify, so signed modules still load, and LOCKDOWN_KEXEC blocks the old kexec_load() system call, which takes raw segments, while kexec_file_load() is still allowed with a verifiable image, or with an unsigned one that IMA's policy is certain to appraise (ima_appraise_signature()). Both depend on the signature code being built. Selecting CONFIG_MODULE_SIG covers modules, but a kernel without CONFIG_KEXEC_SIG never reaches the kexec check in kexec_file_load(), and only IMA stands between the image and the next kernel. Hibernation is refused because the resume image would be an unsigned copy of kernel memory read back from disk.

The other partial reasons follow the same idea. Under LOCKDOWN_DEBUGFS, a debugfs file that is only world-readable and has no ioctl or mmap stays usable; opening anything else for writing, or changing a file's mode or owner, is refused. LOCKDOWN_MODULE_PARAMETERS refuses only hardware parameters (I/O ports, IRQs and memory addresses declared with module_param_hw). LOCKDOWN_PERF refuses only sampling of interrupted register state (PERF_SAMPLE_REGS_INTR), which can expose kernel registers. LOCKDOWN_ACPI_TABLES ignores table overrides from the initrd, the acpi_rsdp= and efivar_ssdt= parameters and the configfs table loader. LOCKDOWN_PCI_ACCESS covers configuration-space writes and BAR mappings through sysfs and /proc/bus/pci, the pciconfig_write() system call and, since 5.16, raw CXL mailbox commands. The two debugger reasons refuse the gdb remote stub, falling back to kdb if it is built, and strip kdb of the commands that read or write memory, instead of disabling the debugger. At the confidentiality level, LOCKDOWN_TRACEFS makes tracefs refuse to create its files, so the tracing interface is simply absent. The newest reason, LOCKDOWN_XEN_USER_ACTIONS (7.0, part of the fix for Xen advisory XSA-482), keeps the privcmd driver in an unprivileged Xen guest limited to hypercalls for the domain it serves as a device model, even if its unrestricted parameter is set, so that a guest booted with Secure Boot cannot use hypercalls against itself. The reasons tagged XMON, RTAS and DEVICE_TREE belong to powerpc; the x86-only ones (IOPORT, MSR, mmiotrace) have no ARM64 counterpart because ARM64 has no I/O port space and exposes no raw system-register device.

Mainline has only two implementations of the hook: the lockdown module and the BPF LSM, whose programs may attach to locked_down like any other hook. SELinux had a third from 5.6 to 5.15, with a lockdown class that let policy allow chosen domains through, but 5.16 removed it. The hook has no credential argument and is often called where current has nothing to do with the request. The clearest case was BPF. bpf_probe_read_kernel() checked lockdown every time it ran, so a tracing program attached to sched_switch was judged by the label of whichever task it interrupted, and the denial record it produced tried to wake kauditd with the runqueue lock held, which could deadlock. Since 5.13 the BPF checks run when the verifier resolves the helper, so the decision is made once, for the task loading the program. The enumeration's own comment also warns that the operations behind a reason may change between releases. Both points argue for using the hook only to express the global level.

From Secure Boot to Runtime Policy

Lockdown is the runtime end of a chain of trust whose firmware and boot-loader parts are described in Appendix A. Figure 27-8 collects the pieces. UEFI firmware verifies the shim against its db database and refuses anything matching dbx; shim verifies the boot loader and kernel with the distribution's certificate or the owner's Machine Owner Keys; and the kernel, once running, imports those same databases into the keyrings of §4.3. load_uefi_certs() in security/integrity/platform_certs/load_uefi.c reads db into .platform (unless shim's MokIgnoreDB variable says the owner has chosen not to trust it) and dbx into .blacklist. Only when Secure Boot is on, since otherwise the variables are unprotected, does it read MokListXRT into .blacklist and MokListRT into .machine (or into .platform when CONFIG_INTEGRITY_MACHINE_KEYRING is off). The Secure Boot test is IMA's arch_ima_get_secureboot(), which is built only with CONFIG_IMA_ARCH_POLICY, so a kernel without that option loads no MOK keys at all. The built-in keys compiled into the kernel image anchor .builtin_trusted_keys, and .secondary_trusted_keys accepts additions signed by those and has .machine linked into it, so owner-enrolled keys are trusted wherever the secondary keyring is. Each verifier then picks the keyrings it trusts: module signatures use the built-in and secondary keyrings (Appendix B); kexec_file_load() also accepts .platform, because the next kernel was signed for the firmware (Appendix A); IMA appraisal uses .ima; dm-verity and IPE use their configured keyrings.

What ties Secure Boot to the runtime checks? In mainline the link is explicit and opt-in. With CONFIG_IMA_ARCH_POLICY, booting with Secure Boot on makes module and kexec signatures mandatory (§5.2), but it does not raise the lockdown level: the lockdown level comes only from the command line, Kconfig, or securityfs. Many distributions carry a patch that locks the kernel down to integrity level whenever Secure Boot is detected, so on those systems lockdown appears to follow Secure Boot automatically. Without lockdown, Secure Boot protects the boot but not the running kernel from root. Lockdown without signature enforcement is weaker still, because the boot itself could have been replaced.

The two architectures share this design but reach it differently. On x86_64 the EFI stub records the Secure Boot state in boot_params.secure_boot, which setup_arch() reports as Secure boot enabled and IMA reads. ARM64 servers and laptops with UEFI follow the same chain, but nothing is passed from the stub: arch_ima_get_secureboot(), built for ARM64 since 5.11, reads the SecureBoot and SetupMode variables through the runtime services and logs ima: secureboot mode enabled. The ARM64 EFI stub also ignores a dtb= option unless Secure Boot is known to be off, because a device tree loaded from disk is unauthenticated input that describes the hardware the kernel trusts. Together with Kernel is locked down from ..., these log lines show how a running system's chain was set up. Many embedded ARM64 systems boot without UEFI, verifying the kernel in their own firmware (for example U-Boot FIT image signatures); their .platform keyring is then empty and the chain of trust is anchored in .builtin_trusted_keys and in dm-verity root hashes passed on the kernel command line or in a signed boot image. Measured boot works the same way on both: firmware measurements live in PCRs 0–7, the boot loader extends PCRs 8–9, the EFI stub measures the initrd (5.17) and the command line (6.1) into PCR 9, or into the matching register of a confidential-computing guest (6.9), and IMA's boot_aggregate (§5.1) binds the runtime log to all of them. Finally, lockdown protects the kernel only through its interfaces. A kernel bug that lets an attacker write kernel memory directly bypasses it, which is why the last layer of the stack — making such bugs harder to exploit — matters.

Hardening the Kernel Itself

The layers so far decide who may do what. The last layer assumes the kernel has bugs: an out-of-bounds write, a use-after-free, a missing length check. Kernel self-protection does not fix those bugs. It makes them harder to turn into exploits, by removing the predictable structure an attacker needs: writable function pointers, known addresses, uninitialized memory, and indirect branches that can go anywhere. Most of these defenses are Kconfig options, compiler features, or CPU features, and they are scattered across the tree. They fall into three groups by the step of an exploit they block: memory-safety checks stop a bad length or pointer from reaching memory it should not, control-flow integrity limits where a corrupted indirect call or return can land, and read-only mappings, randomization and initialization hide addresses and leave less stale data to leak.

Memory-Safety Hardening

The copy routines that cross the user/kernel boundary are the most common place for an overflow to leak or corrupt memory, so every copy_to_user() and copy_from_user() is checked in two steps (Chapter 10). The first, check_copy_size() in include/linux/ucopysize.h, is always built. It asks the compiler for the size of the kernel-side object with __builtin_object_size(). If the length is a compile-time constant larger than the object, the build fails. If a length computed at run time is larger, the kernel warns through copy_overflow() and refuses the copy. It also refuses any length above INT_MAX, which is usually a negative error value that was converted to an unsigned size. The second step is hardened usercopy (CONFIG_HARDENED_USERCOPY, 4.8). For lengths not known at compile time, check_object_size() calls __check_object_size() in mm/usercopy.c, which finds out what the pointer points into and checks that the whole range stays inside it. A range that wraps around the address space or starts at NULL is rejected. On the current task's stack the range must stay within the stack, and on x86 with frame pointers within one stack frame. In a kmap() page or a vmalloc area it must stay within that mapping. In a slab object it must stay within the cache's whitelist region, and in a multi-page allocation within the compound page. It must never overlap kernel text. A failure calls usercopy_abort(), which logs Kernel memory exposure attempt detected (or overwrite attempt) with the object involved and then calls BUG(). That kills the calling task with an oops. The whole system goes down only if panic_on_oops is set. A slab cache opts in to user copies by declaring the whitelist with kmem_cache_create_usercopy() (4.16), so a copy that touches any other part of an object fails even if it stays within the object (Chapter 8). The kmalloc() caches whitelist their whole objects. The run-time check sits behind a static key and can be switched off with hardened_usercopy=off (4.19), and CONFIG_HARDENED_USERCOPY_DEFAULT_ON (6.15) sets its default.

CONFIG_FORTIFY_SOURCE (4.13) applies the same idea to the string and memory functions. include/linux/fortify-string.h wraps memcpy(), memset(), strcpy(), strscpy() and their relatives in inline versions that compare the length with the sizes of the destination and the source. Since 6.3 they use __builtin_dynamic_object_size(), which also knows the size of an object whose size is computed at run time, such as a buffer allocated with a variable length. An overflow the compiler can prove is a build error. One found at run time calls __fortify_panic(), which reports the function and the two sizes through __fortify_report() and then calls BUG(). memcpy() has a softer third case (6.1). A copy that stays inside the enclosing structure but runs past the end of the field named as the destination prints detected field-spanning write and proceeds, because many older callers copy several adjacent fields at once on purpose. Those callers are being converted to group the fields with struct_group(), or to call unsafe_memcpy(), whose extra argument records why the span is intended.

These checks are only as good as the compiler's knowledge of object sizes, and arrays at the end of structures used to defeat it. Since 6.5 the kernel is built with -fstrict-flex-arrays=3, so only a true flexible array member ([]) is treated as having unknown size, while an old-style trailing [0] or [1] array is bounded like any other array. A flexible array can then be annotated with __counted_by() (6.5), whose argument names the field that holds the element count. With GCC 15.1 or Clang 20.1 and later (CONFIG_CC_HAS_COUNTED_BY), both __builtin_dynamic_object_size() and the bounds sanitizer use that field as the array's real length. Linux 7.0 adds __counted_by_ptr() for pointer members, which needs GCC 16 or Clang 22. The sanitizer is CONFIG_UBSAN_BOUNDS (5.7), which checks every array index whose bound is known. With CONFIG_UBSAN_TRAP (5.7) a bad index executes a trap instruction instead of printing a report, which keeps the added code small enough for production kernels (Chapter 29).

Linux 7.0 also changes how most allocations are written. The new kmalloc_obj(), kmalloc_objs() and kmalloc_flex() macros in include/linux/slab.h, with kzalloc_, kvmalloc_ and kvzalloc_ variants, take a variable or a type instead of a byte count, return a pointer of the right type, and make the GFP argument optional, defaulting to GFP_KERNEL. They compute sizes with the saturating size_mul() and struct_size_t(), so a count that overflows yields SIZE_MAX and the allocation fails instead of returning a short buffer. A tree-wide conversion in 7.0 rewrote more than 8,000 files to use them. kmalloc_flex() also stores the count in the __counted_by() field when the compiler provides __builtin_counted_by_ref() (treated as unavailable for Clang older than 22.1), so the bound is valid before the array is first used. The caller below still assigns the count itself, which is required with compilers that lack the builtin: 

/* include/linux/watch_queue.h */
struct watch_filter {
	...
	u32			nr_filters;	/* Number of filters */
	struct watch_type_filter filters[] __counted_by(nr_filters);
};

/* kernel/watch_queue.c, watch_queue_set_filter() */
	wfilter = kzalloc_flex(*wfilter, filters, nr_filter);
	if (!wfilter)
		goto err_filter;
	wfilter->nr_filters = nr_filter;

Uninitialized memory is the second class. A structure copied to user space with a padding hole, or a stack variable read before it is written, leaks whatever the previous user of that memory left behind, which is often a kernel pointer that defeats KASLR. Three options close this hole at different levels. CONFIG_INIT_STACK_ALL_ZERO (5.9) makes the compiler zero every automatic variable, and since 5.16 it is the default whenever the compiler supports it. init_on_alloc=1 and init_on_free=1 (5.3; defaults from CONFIG_INIT_ON_ALLOC_DEFAULT_ON and CONFIG_INIT_ON_FREE_DEFAULT_ON) zero page and slab memory when it is allocated or freed. The Kconfig help estimates the cost of init_on_alloc at under 1% for most workloads and of init_on_free at 3–5%, and if CONFIG_PAGE_POISONING is active, poisoning takes precedence over both. CONFIG_KSTACK_ERASE wipes the used part of the kernel stack on return to user space, so the next system call cannot read what the previous one left there. This option began as the GCC_PLUGIN_STACKLEAK plugin in 4.20 and was renamed in 6.17 when Clang gained support through its stack-depth instrumentation. CONFIG_KSTACK_ERASE_RUNTIME_DISABLE adds the kernel.stack_erasing sysctl to turn it off. The kernel reports the resulting policy in one boot message, such as mem auto-init: stack:all(zero), heap alloc:on, heap free:off. The allocation-time check is a static key, so the disabled case costs one patched-out branch: 

/* include/linux/mm.h */
static inline bool want_init_on_alloc(gfp_t flags)
{
	if (static_branch_maybe(CONFIG_INIT_ON_ALLOC_DEFAULT_ON,
				&init_on_alloc))
		return true;
	return flags & __GFP_ZERO;
}

Heap exploitation is the third class: an attacker who can overflow or reuse one object wants a useful victim object placed next to it. SLUB's defenses are covered with the allocator in Chapter 8. CONFIG_SLAB_FREELIST_HARDENED (4.14) stores each free-list pointer XORed with a random per-cache value and with the byte-swapped address where it is stored, so an attacker who overwrites it cannot aim it at a chosen address without knowing the secret. It also catches the simplest double free, freeing the object that is already at the head of the free list. CONFIG_SLAB_FREELIST_RANDOM (4.7) randomizes the order of free objects in a new slab. CONFIG_RANDOM_KMALLOC_CACHES (6.6) spreads kmalloc() callers across 16 copies of each size class (the normal cache plus 15), chosen by hashing the call site with a random seed picked at boot, so an attacker cannot easily arrange for a victim object to share a cache with the one they control. CONFIG_SLAB_BUCKETS (6.11) gives allocations whose size user space controls, namely System V messages (msg_msg) and memdup_user() copies, their own set of caches. CONFIG_LIST_HARDENED (6.6) adds cheap consistency checks to list manipulation, and CONFIG_BUG_ON_DATA_CORRUPTION turns detected corruption into a BUG() instead of a warning. Finally, randstruct (CONFIG_RANDSTRUCT_FULL or CONFIG_RANDSTRUCT_PERFORMANCE, a GCC plugin since 4.13 and also supported by Clang 16 and later since 5.19) shuffles the field order of structures marked __randomize_layout, and of structures containing only function pointers, using a seed generated at build time. The performance variant, available only with the GCC plugin, shuffles within cache-line-sized groups of fields to keep hot fields together. The seed is kept in scripts/basic/randomize.seed until make mrproper, because external modules must be built with the same layout, and it must not be published. struct task_struct and struct file are among those marked. This defense helps only when the attacker cannot get the exact build, so distribution kernels, whose layouts are public, gain little from it.

Stack overflows are the oldest class. CONFIG_STACKPROTECTOR_STRONG places a canary between local arrays and the saved return address and checks it before returning. The two architectures keep the canary in different places. Since 6.15, x86_64 reads a per-CPU __stack_chk_guard that is switched with each task. Before that the compiler required the canary at the fixed offset %gs:40, which constrained the per-CPU area layout. ARM64 uses a per-task canary (CONFIG_STACKPROTECTOR_PER_TASK, 5.0): the compiler loads it from current->stack_canary through the sp_el0 register that already points at the current task. CONFIG_VMAP_STACK places kernel stacks in vmalloc space with guard pages, so overflowing a stack faults instead of overwriting a neighbor, and CONFIG_RANDOMIZE_KSTACK_OFFSET (5.13) shifts the stack pointer by a random amount on each system call entry, so stack addresses cannot be predicted from one call to the next. The shift is up to 1008 bytes in 16-byte steps. The next offset is chosen on the way out of each system call, from the time-stamp counter on x86_64 and from get_random_u16() on ARM64, to give user space as little control over its timing as possible. The offset used to be kept per CPU. Since 7.0.4 it lives in current->kstack_offset, because an attacker who migrated a task during a system call could keep the original CPU's offset from being updated.

Some defenses aim at finding memory bugs in production rather than blocking them. KFENCE (CONFIG_KFENCE, 5.12) is a sampling detector cheap enough to leave on. Every 100 ms by default (kfence.sample_interval) it diverts one slab allocation to a pool of 255 objects, each on its own page between guard pages, and reports any out-of-bounds or use-after-free access to them. Hardware tag-based KASAN on ARM64 MTE (§1.3) checks every slab allocation instead of a sample. refcount_t (Chapter 5) saturates instead of wrapping on overflow, unconditionally since 5.5, which turns a reference-count overflow into a memory leak instead of a use-after-free. CONFIG_PAGE_TABLE_CHECK (5.17) checks each change to a user page table and catches an anonymous page mapped writable twice, or a page shared wrongly between anonymous and file mappings. Finally, because exploits often trigger the same bug many times, kernel.oops_limit (default 10000) and kernel.warn_limit (6.2, off by default) panic the system once that many oopses or warnings have occurred, instead of letting an attacker retry indefinitely (Chapter 3).

Control-Flow Integrity on x86_64 and ARM64

An attacker who can overwrite memory usually aims to redirect execution, either by corrupting a function pointer (forward edge) or a saved return address (backward edge). The kernel defends both edges with a mix of compiler and hardware features, and this is where the two architectures differ most.

For forward edges, kCFI (Clang -fsanitize=kcfi, 6.1; the option was CONFIG_CFI_CLANG until it was renamed CONFIG_CFI in 6.18, in preparation for GCC support) stores a hash of each function's type in front of it and checks at every indirect call that the target has the hash the call site expects. A corrupted pointer can therefore reach only functions with an identical prototype (Chapter 1). A mismatch is a fatal trap unless CONFIG_CFI_PERMISSIVE makes it a warning. BPF programs compiled by the JIT carry a kCFI hash as well (6.8), so the kernel can call them through checked indirect calls. The hardware complements are coarser. Intel's Indirect Branch Tracking (CONFIG_X86_KERNEL_IBT, 5.18) faults if an indirect branch lands anywhere other than an ENDBR64 instruction (Chapter 2), and objtool lists the ENDBR64 instructions of functions whose address is never taken, and apply_seal_endbr() overwrites them at boot. ARM64's Branch Target Identification (CONFIG_ARM64_BTI_KERNEL, 5.8) does the same with BTI landing pads on pages marked guarded. On x86_64 the two combine into FineIBT. When the CPU has IBT, boot-time patching rewrites the kCFI checks so that the hash is compared at the target, behind the ENDBR64, which is cheaper than checking at the call site.

The cfi= boot parameter selects the scheme. kcfi and fineibt force one or the other, off disables both, and auto, the default with CONFIG_CFI_AUTO_DEFAULT (6.11), chooses FineIBT whenever the CPU has IBT. Further options adjust the result. norand keeps the compiler's hashes instead of rehashing them at boot with a random seed (6.2), so that an attacker cannot precompute them from the image. warn (6.15) reports violations without stopping, and debug (6.18) logs the patching steps. paranoid (6.15) adds a hash check at the call site too. FineIBT normally checks only at the target, so an indirect call could still land on an ENDBR64 with no check behind it, such as an exception entry point. In auto mode this option is enabled unless the CPU has FRED, whose exception entry gives an attacker less to work with. bhi (6.15) needs CONFIG_FINEIBT_BHI, which depends on the compiler recording each function's argument count. It poisons the argument registers when the hash check fails, so that a speculatively executed call past the mismatch cannot use attacker-chosen values, which defends against Branch History Injection. The boot log reports the outcome, for example Using paranoid FineIBT+BHI CFI.

For backward edges ARM64 has two mechanisms. Pointer authentication (CONFIG_ARM64_PTR_AUTH, 5.0 for user space; CONFIG_ARM64_PTR_AUTH_KERNEL, 5.7 as part of the former option and separated in 5.14) signs the return address with PACIASP on function entry and checks it with AUTIASP before returning. The signature lives in the unused upper bits of the pointer and uses a key the kernel keeps in thread_struct.keys_kernel (struct ptrauth_keys_kernel) and installs on every entry from user space and every context switch. Each task gets its own random key when it is created, in copy_thread(), so a signed pointer leaked from one task cannot be reused in another. A forged return address then fails authentication and faults. Shadow call stacks (CONFIG_SHADOW_CALL_STACK, 5.8, Clang) keep a second copy of return addresses in a separate stack reached through register x18. With CONFIG_UNWIND_PATCH_PAC_INTO_SCS (6.2) a single kernel image patches its PAC instructions into shadow-stack pushes and pops at boot if the CPU lacks PAC. On x86_64 the kernel itself has no backward-edge hardware protection in 7.0.12: CET shadow stacks (CONFIG_X86_USER_SHADOW_STACK, 6.6) and ARM64's Guarded Control Stack (CONFIG_ARM64_GCS, 6.13) are offered to user processes only (Chapter 2). Both architectures can also shrink the set of usable return-oriented gadgets with CONFIG_ZERO_CALL_USED_REGS (5.15), which makes the compiler clear the registers a function used before it returns. The Kconfig help estimates that this removes about 20% of ROP gadgets for under 1% run-time cost, and that it grows the image by under 1% on x86_64 and about 5% on ARM64. Read-Only Data, Randomization, Mitigations, and a Checklist

A function pointer that cannot be written cannot be hijacked. CONFIG_STRICT_KERNEL_RWX and CONFIG_STRICT_MODULE_RWX map kernel and module text read-only and executable, and data non-executable. Neither option can be deselected on x86_64 or ARM64. Only rodata=off on the command line turns the protection off, and the kernel then logs Kernel memory protection disabled. On ARM64 the default rodata=on also removes the writable aliases that the linear map would otherwise give to kernel text and read-only data, which can force the linear map to be built from smaller pages, and rodata=noalias (6.18) keeps the aliases for speed. On x86_64 module text comes from a cache of read-only executable large pages kept by the execmem allocator (enabled in 6.15). The module loader gets the pages writable only while it fills them, and execmem_restore_rox() makes them read-only and executable again before the module runs. CONFIG_DEBUG_WX scans the page tables at boot for any mapping that is both writable and executable. Data that is written only during initialization is tagged __ro_after_init, which places it in .data..ro_after_init (include/linux/cache.h). The LSM hook lists, the lockdown hook table in §8.1, and many operation tables carry this tag. mark_readonly() write-protects that section once init is about to run: 

/* init/main.c (abridged) */
static void mark_readonly(void)
{
	if (IS_ENABLED(CONFIG_STRICT_KERNEL_RWX) && rodata_enabled) {
		...
		flush_module_init_free_work();
		jump_label_init_ro();
		mark_rodata_ro();
		debug_checkwx();
		rodata_test();
	} else if (IS_ENABLED(CONFIG_STRICT_KERNEL_RWX)) {
		pr_info("Kernel memory protection disabled.\n");
	}
	...
}

Static keys, which the hardening options above use for their run-time switches, need special care, because switching a key writes both the patched code and the key's own counter. A key that should never change after boot is declared with DEFINE_STATIC_KEY_TRUE_RO() or DEFINE_STATIC_KEY_FALSE_RO(), which puts it in .data..ro_after_init, and jump_label_init_ro() seals every such key just before the section is write-protected, so that the jump-label code never tries to update it afterwards. x86_64 uses such a key to pin security bits in its control registers (5.3). Once cr_pinning is enabled during boot, native_write_cr4() puts back SMEP, SMAP, UMIP, FSGSBASE and CET if a write tries to clear them, and native_write_cr0() does the same for the write-protect bit, then both warn. A return-oriented chain that reaches a mov to %cr4 therefore cannot switch off SMEP or SMAP, and it cannot clear the key either, because the key itself is read-only. The same reasoning motivates CONFIG_STATIC_USERMODEHELPER, promised in §4.2. call_usermodehelper_setup() replaces the path of every helper, including request_key's /sbin/request-key, a piped core-dump handler and the module loader's modprobe_path, with the one fixed binary named by CONFIG_STATIC_USERMODEHELPER_PATH (default /sbin/usermode-helper), which receives the original arguments and decides what to run. An empty path disables usermode helpers altogether. An attacker who overwrites a path string in kernel memory, and modprobe_path has long been a favorite target, therefore cannot make the kernel execute an arbitrary program as root.

Randomization makes the addresses an attacker needs unknown. KASLR (CONFIG_RANDOMIZE_BASE) chooses a random physical and virtual base for the kernel image at boot. On x86_64 the virtual base moves in 2 MiB steps within the 1 GiB kernel-image region, which leaves fewer than 512 possible positions, about 9 bits of entropy, so a single leaked text address reveals the whole layout. On x86_64, CONFIG_RANDOMIZE_MEMORY also randomizes the bases of the direct map, vmalloc and vmemmap regions. ARM64 gets its seed from EFI or the device tree's /chosen/kaslr-seed (Appendix A, Chapter 2; user-space ASLR is in Chapter 20). Randomization is only as good as the secrecy of kernel pointers. kptr_restrict and CONFIG_SECURITY_DMESG_RESTRICT hide addresses in /proc files and the kernel log, %p prints hashed values, and the confidentiality lockdown level closes /proc/kcore.

Speculative-execution attacks such as Spectre, Meltdown and their successors are not memory-safety bugs at all. They let an attacker infer data through cache side effects of instructions the CPU executed speculatively and then discarded. The kernel's response is a set of per-vulnerability mitigations (KPTI, retpolines, IBRS, buffer clearing, branch-history barriers on x86; branch predictor invalidation and the BHB loops in arch/arm64/kernel/proton-pack.c on ARM64), selected at boot and reported in /sys/devices/system/cpu/vulnerabilities/, one file per issue. Linux 7.0.12 has 19 such files, from meltdown to recent additions such as indirect_target_selection (6.15), tsa and old_microcode (6.16), and vmscape (6.17):

The mitigations= parameter controls them as a group: off, auto, or auto,nosmt. Since 6.17 it also accepts attack-vector controls such as no_user_kernel, no_user_user, no_guest_host, no_guest_guest and no_cross_thread, so a system that runs no untrusted guests can skip the mitigations that only guard guest/host boundaries.

The last group of settings removes features that attackers rely on but most systems never use. make hardening.config (6.7) merges the fragment kernel/configs/hardening.config, plus an architecture fragment such as arch/x86/configs/hardening.config or arch/arm64/configs/hardening.config, into the current configuration and turns on most options of this section in one step. Several interfaces have been restricted because exploits used them as tools rather than as targets. CONFIG_BPF_UNPRIV_DEFAULT_OFF (5.13, default y) sets kernel.unprivileged_bpf_disabled, so that only privileged users can load BPF programs (Chapter 23). vm.unprivileged_userfaultfd (5.2, default 0) prevents users without CAP_SYS_PTRACE from handling page faults raised by kernel code through userfaultfd, which exploits used to pause the kernel in the middle of a copy from user space and widen a race window. Since 5.11 any process may still open a userfaultfd with UFFD_USER_MODE_ONLY, which handles only faults from user-mode code. Turning off CONFIG_LEGACY_TIOCSTI (6.2) or setting dev.tty.legacy_tiocsti=0 removes the ability to push characters into a terminal's input queue, and turning off CONFIG_LDISC_AUTOLOAD (5.1) stops unprivileged users from loading a rarely used line-discipline module just by selecting it. kernel.io_uring_disabled (6.6) restricts or removes io_uring (Chapter 10), and kernel.dmesg_restrict and kernel.perf_event_paranoid limit what the kernel log and performance counters reveal (Chapter 29). Summary

The kernel's security infrastructure is a set of layers that each answer one question. Credentials and capabilities say who is asking. LSMs decide whether a labeled subject may touch a labeled object. The crypto API and the key service supply confidentiality and the means to verify signatures. IMA, EVM, fs-verity, dm-verity and IPE establish whether code and data are what they claim to be. Audit records what happened, and lockdown and self-protection keep the kernel that enforces all of this intact.

Access control is one framework with many modules. Each LSM declares in lsm_blob_sizes how much private state it needs on credentials, inodes, files, sockets and the other kernel objects, and the framework allocates one shared blob and hands every module its own offset. Capabilities always come first and IMA and EVM always last; between them the boot-time lsm= list orders Landlock, the minor modules, one exclusive major module (SELinux, AppArmor or Smack) and the BPF LSM. The 276 hooks are dispatched through static calls, and an access check stops at the first module that refuses. SELinux answers most questions from its access vector cache before consulting the policy server; AppArmor matches path names against compiled profiles; Smack compares short labels; and the small modules such as Yama, LoadPin and SafeSetID each close one specific gap. Audit records the outcome. A denial is formatted by common_lsm_audit(), a system call by the syscall-exit code, and both go through audit_log_start() into a queue that the kauditd thread drains to the registered auditd over NETLINK_AUDIT. When a record must be dropped because the queue is over its backlog limit, the audit_failure setting decides whether the loss is silent, reported with printk(), or a panic.

The key service and the integrity layers build on that framework. Keys live in keyrings attached to threads, processes, sessions and users; a missing key can be fetched through the request_key() upcall to /sbin/request-key, and trusted keys are generated and sealed by a TPM, a TEE, an SoC key unit (CAAM, DCP) or, since 7.0, the PowerVM key wrapping module (PKWM), so that the kernel never stores them in clear. IMA measures files into a log extended into PCR 10 and appraises them against signatures or hashes in security.ima, while EVM protects those security attributes with an HMAC or signature in security.evm. fs-verity and dm-verity check files and block devices block by block against a Merkle tree whose root can be signed, and IPE turns those properties into a policy over what may execute. Lockdown caps what even root may do: its 28 reasons, split into integrity and confidentiality levels, close the interfaces through which root could modify the running kernel or read its secrets.

Several themes cross the layers. The first is the hook: almost every mechanism in this chapter is reached through a security_*() call placed in the core kernel, whether the module behind it is SELinux, IMA (an LSM since 6.9), lockdown, or IPE. The second is the keyring as trust anchor. Module signatures, kexec images, IMA appraisal, dm-verity root hashes, IPE policies and, since 6.18, BPF programs all reduce to "is this signed by a key on that keyring?", and §8.2 showed how those keyrings are themselves populated from a firmware-verified boot, with link restrictions and the blacklist deciding which keys may join them. The third is measurement versus enforcement: IMA measurement and TPM PCRs record what happened so that a remote party can judge it (the list is even carried across kexec, because the PCRs are not reset), while appraisal, verity and IPE refuse what fails a check locally. A deployment usually wants both. The fourth is that self-protection now lives largely in the compiler. Fortified string functions, __counted_by() bounds, kCFI, zeroed stack variables and, in 7.0, typed allocation macros that turn an overflowing size into a failed allocation all depend on information only the compiler has.

The crypto API is the shared engine underneath. Transforms are looked up by name, assembled from templates, and resolved to the highest-priority driver, whether that is generic C, AES-NI and VAES on x86_64, the ARMv8 Crypto Extensions on ARM64, or an offload engine. With CONFIG_CRYPTO_SELFTESTS (6.16), every implementation passes its known-answer self-test before it becomes visible, and in FIPS mode a failure halts the kernel. Kernel code that needs a single fixed algorithm increasingly calls the lib/crypto library functions directly, and the API's own SHA-2, ChaCha20, AES and ML-DSA entries now wrap that library. Random numbers come from beside the API rather than through it: drivers/char/random.c hashes interrupt timings, device data, bootloader seeds and RDSEED or RNDRRS output into a BLAKE2s pool and serves every caller, from getrandom() to stack canaries, from per-CPU ChaCha20 keys that erase themselves as they are used.

Underneath every layer the kernel defends itself. It runs W^X with randomized placement, keeps critical data read-only after boot, checks copies to and from user space against the bounds of the kernel object, can verify the type of every indirect call, and pins the control-register bits an attacker would need to clear. A growing share of the trust decisions now extends beyond the CPU, to TPM sessions protected against bus interposers, to confidential-guest attestation reports, and since 6.19 to PCIe devices authenticated through the PCI TSM. The architectural differences between x86_64 and ARM64 are real but narrow. They lie in the acceleration instructions, in how control flow is protected (IBT and FineIBT versus BTI, pointer authentication and shadow call stacks), and in where trusted keys are sealed (TPM versus a TEE or SoC key unit). Above that level the two architectures run the same code. Table 27-10 sets these changes against the security model of Linux 2.6.11.
