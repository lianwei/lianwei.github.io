Linux 2.6.11 was a kernel that owned the machine outright. It could run as a guest—Xen's paravirtualized Linux was maintained out of tree—but the kernel itself had no notion of hosting another operating system. That changed quickly. The Kernel-based Virtual Machine, written by Avi Kivity at Qumranet, was merged into Linux 2.6.20 in early 2007 as drivers/kvm/kvm_main.c, moved to virt/kvm/ in 2.6.25, and has since grown into one of the kernel's largest subsystems: about 11,000 lines of architecture-independent code in virt/kvm, about 100,000 in arch/x86/kvm, and almost 60,000 in arch/arm64/kvm. It is the hypervisor underneath most of the public cloud, of Android's virtualization framework, and of the Linux development environment on ChromeOS. KVM also runs on s390, PowerPC, RISC-V, LoongArch, and MIPS, each with its own directory under arch/; like the rest of this book, the chapter follows x86_64 and ARM64. The subsystem is still moving quickly: Intel TDX host support arrived in 6.16, ARM64 nested virtualization became usable in the same release, and 7.0 adds a mediated x86 PMU that hands the hardware performance counters to a guest while it runs.

Chapter 25 described the other way Linux isolates workloads: a container shares the host kernel and is fenced off by namespaces and cgroups, so its boundary is the system-call interface and every kernel bug reachable from it (Chapter 25, §8.2). A virtual machine draws the line lower. Its guest runs its own kernel on virtual hardware; the boundary is the instruction set and a small number of device interfaces, enforced by the processor's virtualization extensions. KVM's defining design choice is where it puts the hypervisor that enforces that boundary: not in a separate microkernel beneath Linux, but in Linux, so that a virtual CPU is a thread the ordinary scheduler runs, and guest memory is ordinary process memory the ordinary memory manager pages. This chapter follows that design from the /dev/kvm interface down through the run loops on both architectures, including the nested case in which a guest is itself a hypervisor; the two-level translation that virtualizes memory; the newer machinery for guests that do not trust the host at all; the interrupt, timer, and performance-counter virtualization that gives a guest its per-CPU hardware; the device paths that make a guest useful, ending with what Linux does when it is the guest; and virtio, the device framework that guest drivers and host device implementations are both written against. Chapter 2, §12 already explains the address-translation hardware (EPT, NPT, and ARM64 stage-2) in depth; here that hardware is seen from the hypervisor's side, and Chapter 27, §1.1 covers the attestation and device-trust interfaces that a confidential guest uses to prove what it is running.

Virtualization in the Kernel

A hypervisor must make a guest operating system believe it controls a real machine while keeping the actual machine for itself. Hardware virtualization extensions make that possible: the guest runs natively until it touches something the hypervisor has reserved, and the processor then forces an exit. Two questions remain, where the hypervisor itself lives and who models the machine's devices, and KVM answers both the same way. The privileged half lives inside Linux, and everything that does not need privilege is left to a user-space program, the virtual machine monitor. Figure 28-1 (§1.3) draws the resulting division of labor.

Trap-and-Emulate and Hardware Assistance

The classical recipe for virtualization, formalized by Popek and Goldberg in 1974, is trap-and-emulate: run the guest kernel deprivileged, so that every sensitive instruction—one that reads or changes machine state the hypervisor must control, such as loading a page-table base or masking interrupts—traps to the hypervisor, which emulates its effect on a virtual copy of that state and resumes the guest. The recipe works only if every sensitive instruction is also privileged, so that it traps when run outside the most privileged mode. The original x86 failed that test. Instructions such as POPF silently ignored the interrupt flag in user mode rather than trapping, and SGDT revealed the host's descriptor table. Early x86 hypervisors therefore resorted to dynamic binary translation (VMware) or to paravirtualization, in which the guest kernel is modified to call the hypervisor instead of executing the problematic instructions (Xen).

Intel VT-x and AMD-V, introduced in the mid-2000s, removed the problem by adding a new dimension of privilege rather than repairing the old one. The CPU gains a guest mode—VMX non-root operation on Intel, guest mode under VMRUN on AMD—in which all four rings exist as usual, so the guest kernel really runs at ring 0, but a hypervisor-defined set of events causes a VM exit back to the host. A per-vCPU control structure in memory (the VMCS on Intel, the VMCB on AMD) holds both the guest's register state and the hypervisor's choice of which events exit. Before any of this can be used, each CPU must be switched into the hypervisor's own mode: VMXON enters VMX root operation on Intel, and setting EFER.SVME enables SVM on AMD. Since 6.12 KVM does this on every online CPU when the module loads (kvm_enable_virtualization() in virt/kvm/kvm_main.c) rather than when the first VM is created; the kvm.enable_virt_at_load parameter can restore the old behaviour, but TDX refuses to initialize without it. Because a CPU left in VMX operation blocks INIT, the reboot and crash-kexec paths call cpu_emergency_disable_virtualization() to leave it again. ARM took the same path in a form that fits its exception-level model: the ARMv7 virtualization extensions and ARMv8 provide an exception level, EL2 (Hyp mode in ARMv7 terms), above the kernel's EL1, and the hypervisor at EL2 configures, through HCR_EL2 and related registers, which guest operations trap to it. In ARMv8.0 the host kernel still runs at EL1 and needs a separate piece of code at EL2. ARMv8.1 added the Virtualization Host Extensions (VHE), which redirect EL1 register accesses to their EL2 counterparts so that a kernel written for EL1 can run at EL2 with few changes. Linux has used them since 4.6, making the host kernel the EL2 hypervisor in the same sense that it is the VMX-root hypervisor on x86 (§4.1). On both architectures the second ingredient arrived shortly afterwards: hardware two-dimensional paging—Intel EPT, AMD NPT, and ARM stage-2 translation—so that the guest can own its page tables without the hypervisor shadowing every update (Chapter 2, §12.5).

Two-dimensional paging was the first of many additions whose purpose is to make exits rarer. A round trip through the hypervisor costs on the order of a thousand cycles even when the handler does almost nothing, so each processor generation moved another frequent event into hardware. APICv and posted interrupts on Intel, AVIC on AMD, and the GICv3 and GICv4 virtual CPU interfaces on ARM deliver interrupts to a running guest without an exit (§7.2). The guest reads time directly: on x86 the TSC with a hardware-applied offset (and, on newer CPUs, scaling), and on ARM64 the virtual counter with the CNTVOFF_EL2 offset (§7.4). Intel's page-modification log records dirtied pages for migration (§5.4). VMCS shadowing and ARM's FEAT_NV2 remove most of the exits that a nested hypervisor would otherwise take (§4.4). The newest generation changes the trust model rather than the cost. AMD SEV-SNP, Intel TDX, and Arm CCA let a guest keep its memory and registers hidden from the hypervisor that runs it (§6.3).

With hardware assistance, the hypervisor's main loop is short to state: load guest state, enter guest mode, wait for an exit, decide what the exit means, and either handle it and re-enter or hand it to someone else. Everything else in this chapter is about making the exits rare, the handling fast, and the state correct.

The Kernel as Hypervisor

Hypervisors are traditionally sorted into two types. A type 1 or bare-metal hypervisor such as Xen or VMware ESXi runs directly on the hardware and schedules guests itself; a type 2 or hosted hypervisor such as VirtualBox runs as an application on a conventional operating system. KVM does not fit either box cleanly, and the reason is the key to its design. KVM is a set of modules (kvm.ko plus kvm-intel.ko or kvm-amd.ko on x86; built into the kernel on ARM64) that turn Linux itself into the bare-metal hypervisor. The hardware's most privileged mode belongs to Linux. On ARM64 that is literally true only with VHE; without it, Linux installs and controls a small hypervisor object at EL2 and itself runs at EL1 (§4.1). The hypervisor-specific code is small because almost every other service a hypervisor needs is already in the kernel:

  • Scheduling. Each virtual CPU is a thread of the virtual-machine monitor process, and it executes guest code inside an ioctl() call. When the scheduler preempts that thread, the vCPU stops; CFS/EEVDF fairness, cgroup CPU limits, CPU affinity, and real-time priorities apply to vCPUs with no extra code (Chapter 7). KVM needs only two hooks. A preempt notifier unloads a vCPU's hardware state when its thread is switched out and reloads it on whichever CPU the thread runs next (§2.2). The PF_VCPU flag charges ticks taken in guest mode to the guest column of /proc/stat rather than to system time (§3.1).
  • Memory management. Guest RAM is an ordinary anonymous or file-backed mapping in the monitor's address space. It can be swapped, migrated between NUMA nodes, merged by KSM (Chapter 8, §4.8), backed by transparent or hugetlbfs huge pages, and charged to a memory cgroup—all by the same code that manages any process's memory. The kernel memory KVM allocates for the VM (struct kvm, each struct kvm_vcpu, the second-stage page tables) uses GFP_KERNEL_ACCOUNT and is charged to the same cgroup. The exception is the private memory of a confidential guest, which since 6.8 lives in a guest_memfd file that the VMM does not map, so the host cannot read it through the VMM's address space (§6.1).
  • Devices and drivers. The host's network stack, block layer, and device drivers serve the guest's I/O, either through a user-space emulator or through in-kernel accelerators.
  • Security and accounting. A VM is a process: it has credentials, can be confined by an LSM and seccomp, appears in ps and top, and is killed with a signal. The right to create VMs is the right to open /dev/kvm, a misc device (minor 232) whose permissions distributions usually grant to a kvm group. The scarce hardware keys of confidential guests (SEV ASIDs and TDX HKIDs) are limited by the misc cgroup controller (Chapter 25, §6.3). Per-VM and per-vCPU counters are exported through statistics file descriptors (§2.1).

The price of this reuse is that the hypervisor's trusted computing base is the whole Linux kernel. A type 1 design with a small hypervisor can in principle be smaller and easier to verify; the protected-KVM work described in §6.4 is ARM64's answer to that criticism, moving a small trusted core back below Linux without giving up the hosted programming model. The two models are often combined. Kata Containers and Firecracker-based runtimes start each container, or each serverless function, inside its own lightweight VM. The workload keeps the container interface, while the isolation boundary moves down to KVM. KVM is also not the only hypervisor interface in Linux 7.0. When Linux runs as Xen's privileged domain 0, the hypervisor is Xen, and Linux's role is to manage guests through /dev/xen/privcmd. The Microsoft Hyper-V root partition driver (drivers/hv/mshv_root_main.c, 6.15) exposes /dev/mshv, a KVM-like file-descriptor API through which a VMM such as Cloud Hypervisor runs guests on the Microsoft hypervisor. It reuses KVM's generic code for pending work before guest entry (VIRT_XFER_TO_GUEST_WORK, kernel/entry/virt.c). The ACRN service module (/dev/acrn_hsm, 5.12) and the Nitro Enclaves driver (/dev/nitro_enclaves, 5.10) let a Linux guest ask the hypervisor below it to create VMs or enclaves. All of these delegate the privileged work to a separate hypervisor; only KVM makes Linux the hypervisor itself.

The User-Space VMM Split

KVM virtualizes a CPU and its memory; it does not, by itself, implement a computer. Firmware, a PCI bus, disks, network cards, serial ports, and the policy of how much memory and how many vCPUs a guest gets all live in a user-space virtual machine monitor (VMM). QEMU is the oldest and most complete, emulating dozens of machine types and hundreds of devices. The newer VMMs are deliberately small and written in Rust: crosvm (from ChromeOS, also the basis of Android's virtualization framework), Firecracker (AWS's microVM monitor behind Lambda and Fargate), and Cloud Hypervisor. They share crates through the rust-vmm project and emulate only a handful of virtio devices, which shrinks the attack surface that a guest can reach. Two smaller VMMs are useful for reading. kvmtool (lkvm) is a minimal C monitor that boots a Linux guest with virtio devices. The KVM selftests in tools/testing/selftests/kvm carry their own VMM library (lib/kvm_util.c) that builds VMs, memslots, and vCPUs for hundreds of focused tests, so the kernel tree contains a working VMM.

The split gives each side what it is good at. The kernel keeps the code that must be fast or privileged: entering and leaving guest mode, maintaining the second-stage page tables, delivering virtual interrupts, and emulating the few devices—interrupt controllers and timers—that are touched on nearly every exit. The VMM keeps everything that is large, policy-laden, or rarely exercised. When the guest touches something only the VMM understands, the vCPU's ioctl(KVM_RUN) returns to user space with a description of the access; the VMM emulates it and calls KVM_RUN again. In-kernel accelerators (vhost, §8.2) and direct device assignment (VFIO, §8.3) exist to take the hottest of those paths away from the VMM again. Figure 28-1 shows the resulting architecture.

The dividing line is not fixed, and each VM can move it. KVM_CAP_SPLIT_IRQCHIP (4.4) keeps only the local APICs in the kernel and leaves the I/O APIC and PIC to the VMM (§7.1). MSR filters (5.10) send chosen MSR accesses out as KVM_EXIT_X86_RDMSR or KVM_EXIT_X86_WRMSR (§3.4). KVM_CAP_EXIT_HYPERCALL on x86 and the ARM64 SMCCC filter (6.4) forward selected hypercalls (§4.3), and KVM_EXIT_MEMORY_FAULT (6.8) hands private/shared conversions to the VMM (§6.2). In the other direction, KVM_CAP_X86_DISABLE_EXITS lets a guest with dedicated CPUs execute HLT, MWAIT, or PAUSE without exiting at all (§2.3). Linux 7.0 adds two exit reasons, bringing the total in include/uapi/linux/kvm.h to 44. KVM_EXIT_SNP_REQ_CERTS lets the VMM supply the certificate chain when an SEV-SNP guest asks the firmware for an attestation report. KVM_EXIT_ARM_LDST64B passes the ARM64 64-byte single-copy-atomic instructions (LD64B, ST64B, and variants) that target an address outside any memslot to the VMM, which must emulate them in full. In each case KVM keeps the mechanism, and the decision moves to whichever side has the information to make it.

Two consequences of the figure recur throughout the chapter. First, because guest code runs inside a system call made by a vCPU thread, everything that can interrupt a system call—signals, preemption, a pending reschedule—must be able to interrupt guest execution, and KVM's run loop is built around checking for exactly those conditions before each entry. Second, because guest memory is host user memory, anything the host memory manager does to those pages must be reflected in the second-stage page tables, which is the job of the MMU notifiers in §5.3.

The /dev/kvm Object Model

KVM has no system calls of its own. Its entire user-space interface is a character device, /dev/kvm, and a family of anonymous-inode files reached from it, each answering a different set of ioctl() commands defined in include/uapi/linux/kvm.h. Ordinary file semantics do the bookkeeping. A descriptor's lifetime is its object's lifetime, so a VM disappears when the last descriptor that refers to it is closed. The interface grows by new ioctls and capabilities rather than new system calls, so one VMM binary can probe and run on many kernel versions.

Three Kinds of File Descriptor

The interface is a hierarchy of three file types, shown in Figure 28-2. At the top is the system file descriptor, obtained by opening /dev/kvm, a misc device (kvm_dev, minor KVM_MINOR) registered by kvm_init() in virt/kvm/kvm_main.c. Its ioctl handler, kvm_dev_ioctl(), answers questions about the host—the API version (KVM_GET_API_VERSION has returned 12 since 2.6.22), the supported extensions, the size of the per-vCPU shared area—and creates virtual machines. KVM_CREATE_VM calls kvm_create_vm(), which allocates the architecture's struct kvm, takes a reference on the caller's mm_struct, initializes the SRCU domains and interrupt routing, runs kvm_arch_init_vm() with the requested VM type, makes sure every CPU has virtualization enabled (VMXON or EFER.SVME on x86, EL2 initialization on ARM64), registers an MMU notifier on the caller's address space, and adds the VM to the global vm_list. The result is returned as a VM file descriptor, an anonymous inode named kvm-vm.

kvm_dev_ioctl_create_vm() orders these steps so that user space never sees a half-built VM. It reserves a descriptor number with get_unused_fd_flags(O_CLOEXEC) first, so that running out of descriptors fails before anything is allocated; then it builds the VM, wraps it in a file with anon_inode_getfile(), and announces it with a KVM_EVENT_CREATE_VM uevent on the /dev/kvm device. Only then does it call fd_install(), the point after which another thread could use or close the descriptor. Along the way kvm_create_vm() sets max_vcpus to the architecture's KVM_MAX_VCPUS and creates a debugfs directory, /sys/kernel/debug/kvm/pid-fd, which gains a vcpuN subdirectory for each vCPU and holds the text statistics that older tools such as kvm_stat read.

The VM file descriptor configures the machine as a whole: its memory map, its in-kernel interrupt controller, interrupt routing, eventfd bindings, and dirty-page logging. KVM_CREATE_VCPU on it, handled by kvm_vm_ioctl_create_vcpu(), allocates a struct kvm_vcpu and a zeroed page for its struct kvm_run, lets the architecture build its part with kvm_arch_vcpu_create() (on x86 this allocates the VMCS or VMCB), inserts the vCPU into the VM's vcpu_array xarray, and returns a vCPU file descriptor named kvm-vcpu:N. The ID must be below KVM_MAX_VCPU_IDS, and creation fails with -EINVAL once the VM holds max_vcpus vCPUs. On x86 that limit is CONFIG_KVM_MAX_NR_VCPUS (6.7), 1024 by default and 4096 with MAXSMP; on ARM64 it is 512, the most a GICv3 can address, or fewer if the VM's vGIC is smaller. The vCPU descriptor carries the operations that belong to one processor: get and set registers, and above all KVM_RUN. Three more kinds of file hang off the VM descriptor: device file descriptors from KVM_CREATE_DEVICE, which configure in-kernel devices such as the ARM64 vGIC and the KVM–VFIO bridge through KVM_SET_DEVICE_ATTR; statistics file descriptors from KVM_GET_STATS_FD (5.14), which expose binary counters (exits, halt-poll successes, page-table pages) without debugfs and which the vCPU descriptor also offers for per-vCPU counters; and guest_memfd files from KVM_CREATE_GUEST_MEMFD, which §6.1 describes.

One rule binds the hierarchy to its creator. kvm_vm_ioctl(), kvm_vcpu_ioctl(), and kvm_device_ioctl() all begin with if (kvm->mm != current->mm || kvm->vm_dead) return -EIO;. A VM's memory map is expressed in host virtual addresses of the process that created it, so the descriptors are useless in any other address space even if passed over a Unix socket or inherited across fork(). The second half of the test, vm_dead, is KVM's fail-stop mechanism. When KVM finds its own state for a VM inconsistent, a condition that elsewhere in the kernel might justify BUG_ON(), it uses KVM_BUG_ON(cond, kvm) from include/linux/kvm_host.h. That prints a one-time warning and calls kvm_vm_bugged(), which sets vm_bugged and vm_dead and sends every vCPU KVM_REQ_VM_DEAD to force it out of guest mode. From then on every VM, vCPU, and device ioctl returns -EIO. The host keeps running and only that guest is lost; the VMM can still close the descriptors to free it.

Descriptor lifetimes are tied together by a reference count, users_count in struct kvm, which starts at 1 for the VM descriptor. Every vCPU, device, and statistics descriptor takes a further reference with kvm_get_kvm() and drops it in its release method, and a struct kvm_run mapping keeps its vCPU file open. Closing the VM descriptor runs kvm_vm_release(), which detaches the irqfds and calls kvm_put_kvm(); the VM itself lives on until the last reference goes. The final kvm_put_kvm() calls kvm_destroy_vm(), which reverses creation. It sends a KVM_EVENT_DESTROY_VM uevent, removes the debugfs directory and the vm_list entry, frees the I/O buses, unregisters the MMU notifier, lets kvm_arch_destroy_vm() free the architecture state and the vCPUs, destroys in-kernel devices, frees the memslots, drops its reference on hardware virtualization, and finally releases the mm_struct with mmdrop(). There is no ioctl to destroy a single vCPU. A vCPU lives as long as its VM, so a VMM that unplugs a virtual CPU parks the thread and reuses the same descriptor if the CPU is plugged back in.

A statistics descriptor is read-only and self-describing, and it is the one descriptor without the mm check, so a VMM can hand it to a separate monitoring process. Reading it with pread(), served by kvm_stats_read() in virt/kvm/binary_stats.c, returns a struct kvm_stats_header that gives the offsets of an identifier string, of an array of struct kvm_stats_desc, and of the data. Each descriptor names one counter and encodes its type (cumulative, instantaneous, peak, linear or logarithmic histogram), its unit, and a decimal or binary exponent. The descriptors never change for the life of the file, so a monitor parses them once and afterwards rereads only the data block.

Three synchronization choices in this structure shape all of KVM. The memory map (memslots) and the I/O bus tables (buses) are read on almost every exit and changed rarely, so they are published with RCU under the VM's own SRCU domain, kvm->srcu; a vCPU holds an SRCU read lock for most of its time in the kernel, and an update swaps in a new copy and waits with synchronize_srcu(). Sleepable RCU is required because the readers sleep—faulting in a guest page may wait for disk I/O. The memslots are kept in two complete sets per address space so that an update can edit the inactive set and swap it in atomically. The second-stage page tables are protected by mmu_lock, which is an rwlock_t on x86, ARM64, and s390 so that faults on different pages can be handled in parallel under the read lock while zapping and splitting take it for writing. And the mmu_invalidate_* fields implement the sequence-count protocol with which page faults detect a concurrent MMU-notifier invalidation (§5.3).

Each vCPU is a struct kvm_vcpu, again with an embedded struct kvm_vcpu_arch that dominates its size on x86 (register cache, LAPIC pointer, MMU contexts, the pending-event queue) and ARM64 (the saved EL1 system registers in ctxt, the vGIC CPU interface, timers, the trap configuration).

The preempt_notifier deserves a word. Guest state is expensive to load (a VMCS must be made current with VMPTRLD; ARM64 must write dozens of EL1 system registers), so KVM keeps it loaded on the physical CPU for as long as the vCPU thread stays there, not just for the duration of one guest entry. vcpu_load() records the vCPU in the per-CPU kvm_running_vcpu, registers the notifier, and calls kvm_arch_vcpu_load(); if the scheduler then switches away, kvm_sched_out() calls kvm_arch_vcpu_put() to unload it and kvm_sched_in() reloads it—on whatever CPU the thread lands on—when the thread runs again. This is the hook by which an ordinary scheduler, unaware of virtualization, can migrate a vCPU safely (Chapter 3 introduces preempt notifiers). kvm_sched_out() also marks the vCPU preempted if it was runnable, information that directed yield (§3.2) and the guest-visible steal-time "preempted" flag (§7.4) both use.

The third structure, struct kvm_run, is not kernel-private at all. kvm_vm_ioctl_create_vcpu() allocates a page for it, and kvm_vcpu_fault() serves that page at offset 0 of the vCPU file, so the VMM maps it with mmap() and reads the outcome of every KVM_RUN without another system call. The mapping size returned by KVM_GET_VCPU_MMAP_SIZE also covers, on x86, a second page holding the data of string port I/O, and a page for the coalesced-MMIO ring; the vCPU's dirty ring (§5.4) is mapped at a further offset.

The protocol is simple: exit_reason names which member of the union is valid. For an MMIO read, the VMM fills in mmio.data and calls KVM_RUN again; KVM notices that it was waiting for the data, completes the guest's load instruction, and continues. Two input fields deal with races between the VMM and the vCPU thread. immediate_exit makes the next KVM_RUN return -EINTR at once, without entering the guest; a VMM that wants to stop a vCPU sets it and then sends the vCPU thread a signal, so that whether the signal arrives just before or during KVM_RUN, the thread comes back. The HINT_UNSAFE_IN_KVM() wrapper renames the field inside the kernel to immediate_exit__unsafe so that the one place allowed to read it, the KVM_RUN case of kvm_vcpu_ioctl(), is easy to audit; the field lives in user-writable memory and may change at any moment. The trailing s.regs area lets x86 and s390 VMMs synchronize registers through the shared page (KVM_CAP_SYNC_REGS) instead of issuing KVM_GET_REGS after every exit.

The vCPU mutex is held for the whole of KVM_RUN, which can last seconds, so other vCPU ioctls issued from a different thread simply wait; the few that need other locking—interrupt injection on s390, RISC-V, and other architectures, the TDX KVM_TDX_INIT_VCPU and KVM_TDX_INIT_MEM_REGION commands on x86—are offered first to kvm_arch_vcpu_unlocked_ioctl(), which on ARM64 handles nothing. A vCPU's descriptor is installed before KVM_CREATE_VCPU has finished publishing the vCPU, so a thread that guesses the descriptor number early waits on the vCPU mutex until creation is complete. The pid check exists because KVM uses vcpu->pid to find the task to boost when another vCPU yields to this one. Capabilities and VM Types

KVM's API has only ever had version 12, yet it has gained hundreds of features. They are negotiated with capabilities: integer constants KVM_CAP_*, which include/uapi/linux/kvm.h numbers up to 247 in 7.0. KVM_CHECK_EXTENSION returns 0 for an unsupported capability and a positive value—often a limit, such as the maximum number of vCPUs for KVM_CAP_MAX_VCPUS—for a supported one. Issued on the system descriptor it describes what the host can do; issued on a VM descriptor (KVM_CAP_CHECK_EXTENSION_VM) it describes what this VM can do, which differs when the VM type restricts features. Behaviour that changes the ABI is not switched on by merely existing: the VMM must opt in with KVM_ENABLE_CAP on the VM or vCPU. Examples are the dirty ring (KVM_CAP_DIRTY_LOG_RING), forwarding of hypercalls to user space (KVM_CAP_EXIT_HYPERCALL), per-VM halt-poll limits (KVM_CAP_HALT_POLL), letting the guest execute HLT, MWAIT, or PAUSE without exiting (KVM_CAP_X86_DISABLE_EXITS), and nested EL2 on ARM64 (KVM_CAP_ARM_EL2, which is a vCPU feature selected at KVM_ARM_VCPU_INIT time once the capability is reported). A capability can also stop being architecture-specific: in 7.0 MMU notifiers are always built, so common code now reports KVM_CAP_SYNC_MMU on every architecture.

x86 also has the reverse of a capability. A quirk is a historical behaviour that KVM keeps by default so that old VMMs and guests do not break, even though it differs from real hardware. A VMM that wants the architectural behaviour turns quirks off with KVM_CAP_DISABLE_QUIRKS2, which also reports which quirks the host knows about. 7.0 defines eleven KVM_X86_QUIRK_* bits. For example, by default KVM rewrites a guest's VMCALL into VMMCALL on AMD hosts, and the reverse on Intel (KVM_X86_QUIRK_FIX_HYPERCALL_INSN), and on Intel it ignores the guest's PAT and forces write-back memory in EPT (KVM_X86_QUIRK_IGNORE_GUEST_PAT). The newest, KVM_X86_QUIRK_VMCS12_ALLOW_FREEZE_IN_SMM, arrived in 7.0.

Capabilities say what KVM can do; the guest's CPU model says what the guest will be told. On x86 the VMM asks the system descriptor for KVM_GET_SUPPORTED_CPUID, the CPUID leaves that both the hardware and KVM support on this host, and for KVM_GET_EMULATED_CPUID, features such as MOVBE and RDPID that KVM can emulate even when the processor lacks them. The KVM_X86_XCOMP_GUEST_SUPP attribute, read with KVM_GET_DEVICE_ATTR on the same descriptor, lists the XSAVE state components a guest may enable. From these the VMM builds the guest's CPUID table, usually the subset common to every host the VM may migrate to, and installs it with KVM_SET_CPUID2 on each vCPU. KVM treats that table as authoritative: kvm_vcpu_after_set_cpuid() recomputes which features the guest may use. After the first KVM_RUN, KVM_SET_CPUID2 succeeds only if the new table is identical to the old one (5.17). That exception exists because QEMU reuses vCPU descriptors for CPU hot-unplug and hot-plug.

ARM64 has no CPUID instruction; a guest discovers features by reading ID registers such as ID_AA64ISAR0_EL1, which KVM traps and emulates. Since 6.7 a VMM can lower selected fields with KVM_SET_ONE_REG, and the VM-level KVM_ARM_GET_REG_WRITABLE_MASKS reports which fields of which registers can be changed. Once any vCPU of the VM has run, the ID registers are frozen, and a write of a different value fails with -EBUSY. The vCPU features requested at KVM_ARM_VCPU_INIT are frozen in the same spirit: since 6.5 every vCPU of a VM must ask for the same set, and an initialization that asks for a different set fails with -EINVAL.

The argument of KVM_CREATE_VM is a machine type whose meaning is architecture-specific. On x86 it selects the kind of guest: KVM_X86_DEFAULT_VM (0), KVM_X86_SW_PROTECTED_VM (1, a test type that exercises private memory without hardware encryption), KVM_X86_SEV_VM, KVM_X86_SEV_ES_VM, KVM_X86_SNP_VM, and KVM_X86_TDX_VM (2–5); the bitmask returned for KVM_CAP_VM_TYPES (6.8) says which the host supports. On ARM64 the low byte is instead the guest's intermediate-physical-address size, KVM_VM_TYPE_ARM_IPA_SIZE(bits), bounded by KVM_CAP_ARM_VM_IPA_SIZE; it fixes how many levels the stage-2 page tables need. The machine type is the first of several places where the two architectures expose the same abstraction with different vocabulary.

A Minimal VMM

Everything above fits into a program of about sixty lines. The x86 version below creates a VM with one page of RAM at guest physical address 0x1000, loads a few bytes of 16-bit real-mode code that writes a character to I/O port 0x3f8 (the first serial port) and halts, and services the resulting exits. Error handling is omitted. 

/* minimal-vmm.c: a user-space program, x86_64 host */
#include <fcntl.h>
#include <linux/kvm.h>
#include <stdio.h>
#include <string.h>
#include <sys/ioctl.h>
#include <sys/mman.h>

static const unsigned char code[] = {
	0xba, 0xf8, 0x03,       /* mov  $0x3f8, %dx */
	0xb0, 'K',              /* mov  $'K', %al   */
	0xee,                   /* out  %al, (%dx)  */
	0xf4,                   /* hlt              */
};

int main(void)
{
	int kvm = open("/dev/kvm", O_RDWR | O_CLOEXEC);
	if (ioctl(kvm, KVM_GET_API_VERSION, 0) != KVM_API_VERSION)
		return 1;
	int vm = ioctl(kvm, KVM_CREATE_VM, 0);          /* KVM_X86_DEFAULT_VM */

	void *mem = mmap(NULL, 0x1000, PROT_READ | PROT_WRITE,
			 MAP_SHARED | MAP_ANONYMOUS, -1, 0);
	memcpy(mem, code, sizeof(code));
	struct kvm_userspace_memory_region region = {
		.slot = 0, .guest_phys_addr = 0x1000,
		.memory_size = 0x1000, .userspace_addr = (unsigned long)mem,
	};
	ioctl(vm, KVM_SET_USER_MEMORY_REGION, &region);

	int vcpu = ioctl(vm, KVM_CREATE_VCPU, 0);
	int size = ioctl(kvm, KVM_GET_VCPU_MMAP_SIZE, 0);
	struct kvm_run *run = mmap(NULL, size, PROT_READ | PROT_WRITE,
				   MAP_SHARED, vcpu, 0);

	struct kvm_sregs sregs;
	ioctl(vcpu, KVM_GET_SREGS, &sregs);
	sregs.cs.base = 0;                              /* flat real mode */
	sregs.cs.selector = 0;
	ioctl(vcpu, KVM_SET_SREGS, &sregs);
	struct kvm_regs regs = { .rip = 0x1000, .rflags = 0x2 };
	ioctl(vcpu, KVM_SET_REGS, &regs);

	for (;;) {
		ioctl(vcpu, KVM_RUN, 0);
		switch (run->exit_reason) {
		case KVM_EXIT_IO:
			if (run->io.direction == KVM_EXIT_IO_OUT &&
			    run->io.port == 0x3f8)
				putchar(*((char *)run + run->io.data_offset));
			break;
		case KVM_EXIT_HLT:
			return 0;
		default:        /* KVM_EXIT_FAIL_ENTRY, KVM_EXIT_INTERNAL_ERROR, ... */
			fprintf(stderr, "exit_reason %u\n", run->exit_reason);
			return 1;
		}
	}
}

A real VMM differs in scale rather than kind: it maps gigabytes instead of a page, usually with several memory slots around the PCI hole; it loads firmware rather than raw code; it creates an in-kernel interrupt controller with KVM_CREATE_IRQCHIP (after which HLT no longer exits to user space, because KVM can itself wake the vCPU when an interrupt arrives); it sets the guest's CPUID with KVM_SET_CPUID2; and it runs each vCPU in its own thread.

A real VMM also has to respect an order of operations that the example avoids. On x86, KVM_CREATE_IRQCHIP fails with -EINVAL once any vCPU exists, and CPUID must be set before the first KVM_RUN. On ARM64 the vGIC may be created after the vCPUs but not once any of them has run, and its resources are mapped only on the first KVM_RUN. The example uses the original KVM_SET_USER_MEMORY_REGION; its 6.8 successor, KVM_SET_USER_MEMORY_REGION2, takes a larger structure with guest_memfd and guest_memfd_offset fields and is required for private memory (§6.1). Complete, compilable examples of each step live in the KVM selftests (§1.3), whose tools/testing/selftests/kvm/lib/kvm_util.c wraps every ioctl used here.

The ARM64 version differs in exactly the places the architectures differ. ARM64 has no port I/O and no HLT exit: devices are MMIO, so the loop handles KVM_EXIT_MMIO, and the guest stops by calling the PSCI SYSTEM_OFF firmware function, which KVM reports as KVM_EXIT_SYSTEM_EVENT with type KVM_SYSTEM_EVENT_SHUTDOWN. There is no KVM_SET_REGS; every register is addressed through KVM_SET_ONE_REG with a 64-bit ID that encodes architecture, size, and register. And a vCPU must be initialized before it runs: 

/* ARM64 replacement for the register setup above */
	struct kvm_vcpu_init init;
	ioctl(vm, KVM_ARM_PREFERRED_TARGET, &init);     /* host's CPU type */
	init.features[0] |= 1 << KVM_ARM_VCPU_PSCI_0_2;
	ioctl(vcpu, KVM_ARM_VCPU_INIT, &init);

	__u64 pc = 0x1000;
	struct kvm_one_reg reg = {
		.id   = KVM_REG_ARM64 | KVM_REG_SIZE_U64 | KVM_REG_ARM_CORE |
			KVM_REG_ARM_CORE_REG(regs.pc),
		.addr = (unsigned long)&pc,
	};
	ioctl(vcpu, KVM_SET_ONE_REG, &reg);

KVM_ARM_VCPU_INIT resets the vCPU to the architectural reset state for the requested feature set—PSCI version, PMU, SVE, pointer authentication, nested EL2—and the feature set cannot change afterwards, which is how ARM64 KVM keeps the guest's view of the CPU consistent across migration.

The Run Loop on x86

On x86 a single KVM_RUN call may enter and leave the guest thousands of times before it returns to user space. Most of those exits, such as a write to the TSC-deadline MSR, a second-stage fault on memory the host already has, or an interrupt window opening, are finished in the kernel. Some are handled on a fastpath that re-enters the guest without enabling host interrupts. Only exits that need a device model or a policy decision reach the VMM. The work is split across three layers: generic code in virt/kvm/kvm_main.c, the x86 run loop in arch/x86/kvm/x86.c, and the vendor modules kvm-intel and kvm-amd, which plug into it through one table of function pointers.

From KVM_RUN to vcpu_enter_guest()

Figure 28-3 traces the call. kvm_vcpu_ioctl() hands KVM_RUN to kvm_arch_vcpu_ioctl_run() in arch/x86/kvm/x86.c, which does the once-per-call work: vcpu_load() to make the vCPU's VMCS or VMCB current on this CPU, kvm_sigset_activate() to install the signal mask the VMM set with KVM_SET_SIGNAL_MASK, kvm_load_guest_fpu() to swap the host's FPU and vector state for the guest's, and kvm_vcpu_srcu_read_lock() to enter the VM's SRCU read side. It then copies in any registers the VMM dirtied in kvm_run->s.regs and finishes whatever exit it last reported: if the previous return was an IN instruction or an MMIO read, the callback stored in vcpu->arch.complete_userspace_io copies the VMM's answer into the guest's registers and advances the instruction pointer. Only then does it call vcpu_run().

The function also screens out the cases in which there is nothing to run. An application processor that has not yet received INIT and SIPI (KVM_MP_STATE_UNINITIALIZED) never enters the guest: it sleeps in kvm_vcpu_block() and returns -EAGAIN when woken, or -EINTR with KVM_EXIT_INTR if a signal woke it, and the VMM simply calls KVM_RUN again. Register sets named in kvm_valid_regs or kvm_dirty_regs that this VM cannot synchronize fail with -EINVAL. The complete_userspace_io callback runs before the immediate_exit test, not after it, and the ordering is deliberate: a VMM about to save a vCPU for live migration sets immediate_exit and calls KVM_RUN once, so that a half-finished IN or MMIO read is folded into the guest's registers without the guest executing another instruction. kvm_x86_vcpu_pre_run() then gives the vendor a veto: VMX ends the run with an emulation-failure exit if the guest state is one that hardware cannot run and KVM cannot emulate, and SVM refuses with -EINVAL an SEV VM whose encryption state has not been initialized. On the way out the sequence unwinds in reverse order. If the VMM asked for registers in kvm_valid_regs and the guest's state is not protected, store_regs() copies them into kvm_run->s.regs, which saves the VMM a KVM_GET_REGS call.

vcpu_run() is the outer loop. Each iteration either enters the guest or, if the vCPU is halted (its mp_state is not runnable), blocks in vcpu_block() until an interrupt or event makes it runnable. Between iterations it injects expired timer interrupts and checks whether the thread has work pending that only a return toward user space can perform: 

/* arch/x86/kvm/x86.c (abridged) */
static int vcpu_run(struct kvm_vcpu *vcpu)
{
	int r;

	vcpu->run->exit_reason = KVM_EXIT_UNKNOWN;

	for (;;) {
		if (kvm_vcpu_running(vcpu)) {
			r = vcpu_enter_guest(vcpu);
		} else {
			r = vcpu_block(vcpu);
		}

		if (r <= 0)
			break;

		kvm_clear_request(KVM_REQ_UNBLOCK, vcpu);
		if (kvm_cpu_has_pending_timer(vcpu))
			kvm_inject_pending_timer_irqs(vcpu);
		...
		if (__xfer_to_guest_mode_work_pending()) {
			kvm_vcpu_srcu_read_unlock(vcpu);
			r = kvm_xfer_to_guest_mode_handle_work(vcpu);
			kvm_vcpu_srcu_read_lock(vcpu);
			if (r)
				return r;
		}
	}

	return r;
}

The last block is where KVM meets the generic entry code of Chapter 10. Guest mode is, for the host, a long excursion inside a system call, so the work that the kernel normally performs on the way back to user mode—rescheduling when TIF_NEED_RESCHED or the lazy-preemption flag TIF_NEED_RESCHED_LAZY (6.13) is set, running task work, delivering signals—must be performed before each guest entry instead. xfer_to_guest_mode_handle_work() in kernel/entry/virt.c (introduced for 5.9 as kernel/entry/kvm.c and renamed in 6.18, when its Kconfig symbol became VIRT_XFER_TO_GUEST_WORK) calls schedule() and resume_user_mode_work() as needed and returns -EINTR when a signal is pending, in which case kvm_handle_signal_exit() sets KVM_EXIT_INTR and KVM_RUN returns so that the VMM's signal handler can run. This is the mechanism the VMM uses to regain control of a vCPU thread at any time.

The other branch of the loop handles a vCPU that is not runnable. vcpu_block() sends a guest that executed HLT (KVM_MP_STATE_HALTED) to kvm_vcpu_halt(), which may poll for a wake-up event before sleeping (halt polling, §7.4), and a vCPU in any other waiting state, such as an AP waiting for SIPI, straight to kvm_vcpu_block(). Before either, it moves the guest's LAPIC timer from the VMX preemption timer to a host hrtimer, because the preemption timer counts only in guest mode and the timer's expiry may be exactly the event that should wake the vCPU; it moves it back after waking. A wake-up that leaves the vCPU still not runnable, such as a host signal, returns 1 so that the loop can service the host work without changing the guest's activity state. Otherwise kvm_apic_accept_events() processes any pending INIT or SIPI and a halted vCPU becomes KVM_MP_STATE_RUNNABLE again. The lines the listing omits inject pending Xen event-channel upcalls and, for a VMM that emulates the interrupt controller itself, end the run with KVM_EXIT_IRQ_WINDOW_OPEN when the VMM has set request_interrupt_window and the guest can now accept an interrupt.

vcpu_enter_guest() is the inner function, about 450 lines long. Its sequence is:

  1. If any request bit is set, service it: flush the TLB, reload the MMU root, update kvm-clock, deliver an NMI or SMI, process a pending APICv state change, and the rest of x86's 34 architecture-specific requests (§3.2). Some requests end the run with an exit to user space, such as KVM_REQ_TRIPLE_FAULT becoming KVM_EXIT_SHUTDOWN, and KVM_REQ_VM_DEAD fails it with -EIO.
  2. If an interrupt or exception is pending (KVM_REQ_EVENT), call kvm_check_and_inject_events() to choose the highest-priority event and program it into the VMCS or VMCB for injection at entry, or request an interrupt-window exit if the guest cannot take it yet.
  3. Make sure the MMU root is valid with kvm_mmu_reload().
  4. Disable preemption, call the vendor's prepare_switch_to_guest hook (which saves host segment and MSR state that VM exit will not restore), disable interrupts, and publish IN_GUEST_MODE with smp_store_release(&vcpu->mode, IN_GUEST_MODE); drop the SRCU read lock, because the vCPU may stay in the guest indefinitely and must not hold up memslot updates.
  5. If APICv or AVIC is active, call the vendor's sync_pir_to_irr hook to move posted interrupts that arrived while the vCPU was outside guest mode, whose notification IPI therefore found no guest to deliver to, into the virtual APIC's IRR (§7.2). Then re-check, now with interrupts off, that no request, kick, or entry work has arrived (kvm_vcpu_exit_request()); if one has, undo and loop. Because mode was published first, anyone who sets a request after this point will see IN_GUEST_MODE and send an IPI, so no request can be lost.
  6. Switch the state that neither the hardware nor prepare_switch_to_guest switches: reload the FPU registers if they were evicted (switch_fpu_return() when TIF_NEED_FPU_LOAD is set), load the guest's XCR0 and XSS (kvm_load_xfeatures()), its debug registers if it is using them, the counters of the mediated vPMU (kvm_mediated_pmu_load(), 7.0, §7.5), and its PKRU. Collect run_flags for the vendor hook: KVM_RUN_FORCE_IMMEDIATE_EXIT when step 2 left an event that KVM must re-examine as soon as the guest is entered, KVM_RUN_LOAD_GUEST_DR6, and KVM_RUN_LOAD_DEBUGCTL (6.17) when the host's DEBUGCTL MSR has changed since the last entry.
  7. Call guest_timing_enter_irqoff(), which sets PF_VCPU on the task so that ticks arriving while it is in the guest are charged to guest time (the guest column of /proc/stat), and enter the guest with kvm_x86_call(vcpu_run)(vcpu, run_flags). The call sits in a small inner loop: when the vendor's fastpath returns EXIT_FASTPATH_REENTER_GUEST, KVM syncs posted interrupts again, re-checks for requests and kicks, counts the exit, and re-enters without leaving the interrupts-off region.
  8. After the exit, restore the host's PKRU, performance counters (kvm_mediated_pmu_put()), and debug registers, set OUTSIDE_GUEST_MODE, restore the host's XCR0, and call the vendor's handle_exit_irqoff hook. On CPUs affected by VMSCAPE, set the per-CPU flag x86_ibpb_exit_to_user (6.17) so that an indirect branch predictor barrier is issued before this CPU next returns to user space, where the VMM could otherwise be steered by branch predictions the guest trained. Then briefly enable interrupts so that any host interrupt that caused the exit is serviced, call guest_timing_exit_irqoff(), re-enable preemption, re-take the SRCU lock, and finally dispatch the exit through kvm_x86_call(handle_exit), unless the fastpath already chose to return to user space (EXIT_FASTPATH_EXIT_USERSPACE), in which case vcpu_enter_guest() returns 0 at once.

Two refinements keep the common exits cheap. First, a fastpath (5.6): the vendor vcpu_run hook returns a fastpath_t after looking at the exit reason while interrupts are still disabled. vmx_exit_handlers_fastpath() handles WRMSR (and, since 6.18, the immediate form of WRMSRNS), the preemption-timer exit, which is the only fastpath exit allowed while a nested guest runs, HLT (6.12), and INVD (6.18). svm_exit_handlers_fastpath() handles the same instructions when the CPU reports the next instruction pointer, since decoding the instruction from guest memory might sleep, and never for a nested guest. Only two MSR writes qualify: the x2APIC interrupt-command register, so that a guest IPI is sent without leaving the interrupts-off region, and the TSC-deadline timer. The return value tells the inner loop of step 7 what to do. EXIT_FASTPATH_REENTER_GUEST sends it straight back into the guest without the preemption and interrupt dance of step 8. EXIT_FASTPATH_EXIT_HANDLED means the exit is complete but the outer loop must run, for example to block a vCPU whose HLT found no pending interrupt. EXIT_FASTPATH_EXIT_USERSPACE (6.12) means that skipping the instruction produced an exit to user space, such as a single-step debug exit, and EXIT_FASTPATH_NONE leaves everything to handle_exit. In 7.0 a vCPU with the mediated vPMU loses the fastpath while any enabled guest counter counts retired instructions (kvm_pmu_is_fastpath_emulation_allowed()), because an emulated instruction must also be counted, and only the full path does that. Second, guest state that the hardware does not switch is switched lazily: host MSRs that only matter in user mode are restored by a user-return notifier on the way out to user space, not on every exit.

Requests and Kicks

Much of what happens to a vCPU is decided by somebody else: another vCPU sends it an IPI, the MMU-notifier code needs its TLB flushed, a timer expires, a device signals an interrupt, the VMM changes an APIC setting. KVM funnels all of this through one mechanism. A request is a bit in vcpu->requests; kvm_make_request() sets it with set_bit() after an smp_wmb() that publishes any data the request refers to, and kvm_check_request() in the target's run loop tests and clears it. Bits 0–7 are generic (KVM_REQ_TLB_FLUSH, KVM_REQ_VM_DEAD, KVM_REQ_UNBLOCK, KVM_REQ_DIRTY_RING_SOFT_FULL); architectures define more from KVM_REQUEST_ARCH_BASE with KVM_ARCH_REQ(). Flags in the upper bits of the request number say how urgent it is: KVM_REQUEST_WAIT makes the sender wait until the target has left guest mode, and KVM_REQUEST_NO_WAKEUP says that a halted vCPU need not be woken.

The flags occupy bits 8–10, above the 8-bit request index selected by KVM_REQUEST_MASK. The third flag, KVM_REQUEST_NO_ACTION, marks a request that carries no work at all. KVM_REQ_OUTSIDE_GUEST_MODE (5.18) combines it with KVM_REQUEST_WAIT and KVM_REQUEST_NO_WAKEUP, so that kvm_make_all_cpus_request() with it never sets a bit; it only forces every running vCPU out of guest mode and waits until each has left. The x86 MMU uses it after a vCPU maps host MMIO into the guest, so that every vCPU's next entry re-evaluates whether it must clear CPU buffers, and TDX uses it to keep vCPUs from contending with a SEAMCALL that the TDX module reported busy. kvm_make_request() rejects such a request at build time. x86 defines 34 architecture requests; ARM64 defines 12.

Setting a bit is not enough if the target is running guest code, since it checks its requests only between entries. kvm_vcpu_kick() closes the gap. It first tries kvm_vcpu_wake_up() in case the target is blocked. If the target is the vCPU that the calling thread itself is running, the kick only writes EXITING_GUEST_MODE, which the step 5 re-check will see; no IPI and no atomic operation are needed, because only a vCPU's own thread ever moves it into guest mode. Otherwise, kvm_arch_vcpu_should_kick() atomically changes the target's mode from IN_GUEST_MODE to EXITING_GUEST_MODE with cmpxchg(); only the caller that wins that transition sends an IPI (smp_send_reschedule(), or a synchronous smp_call_function_single() for KVM_REQUEST_WAIT). The reschedule IPI is preferred when the sender need not wait because KVM allows kicks with interrupts disabled, where the function-call IPI machinery could deadlock on cross-CPU locks. The IPI itself does nothing but cause a VM exit, after which the vCPU sees the request before it can re-enter, thanks to the ordering in steps 4 and 5 above. VM-wide operations use kvm_make_all_cpus_request(), which collects the physical CPUs of the vCPUs that need an IPI in a per-CPU cpumask and kicks them all at once with kvm_kick_many_cpus(); for example, kvm_flush_remote_tlbs(), called whenever second-stage mappings are removed, makes KVM_REQ_TLB_FLUSH on every vCPU unless the architecture can flush all of them directly (ARM64 broadcasts a TLBI by VMID instead; x86 can use a Hyper-V enlightenment when running nested).

The reverse problem—a vCPU waiting on another vCPU—arises with spinlocks. If the lock holder's vCPU thread is preempted on the host, the waiter spins on a lock that cannot be released. Intel's pause-loop exiting and AMD's pause filter cause a PAUSE_INSTRUCTION or PAUSE exit when the guest executes PAUSE many times within a short window. The handlers (handle_pause(), pause_interception()) widen that window for the vCPU (grow_ple_window()), so that a guest that spins for good reason exits less often, and call kvm_vcpu_on_spin(). It needs at least two vCPUs and walks them round-robin, starting after the one it last boosted (kvm->last_boosted_vcpu). It skips a vCPU whose thread is not ready (the flag is set when a runnable vCPU thread is preempted), one that is blocked with nothing to wake it, and, when the spinner was in guest kernel mode, a preempted vCPU that was in guest user mode with no interrupt pending, since a lock that the guest kernel waits for is almost always held in the kernel. A candidate that is itself in a pause loop is chosen only every other time. The first suitable vCPU receives the physical CPU through kvm_vcpu_yield_to(), a wrapper around the scheduler's yield_to(); after three failed attempts the spinner gives up and re-enters the guest. VMX always passes "spinner in kernel mode", because pause-loop exiting operates only at CPL 0; SVM passes the guest's actual CPL. ARM64 uses the same function for trapped WFE instructions. A paravirtual guest can be more direct: the KVM_HC_SCHED_YIELD hypercall (5.3) names the vCPU it is waiting for, typically the target of an IPI, and the PV spinlock hypercall KVM_HC_KICK_CPU wakes a halted waiter (§8.4).

VMX and SVM Behind kvm_x86_ops

x86 KVM is one generic module, kvm.ko, and two vendor modules. kvm-intel.ko drives VMX (and, for Intel TDX, the TDX module); kvm-amd.ko drives SVM and SEV. The vendor module fills in a struct kvm_x86_ops—vt_x86_ops in arch/x86/kvm/vmx/main.c or svm_x86_ops in arch/x86/kvm/svm/svm.c—with about 130 hooks, listed once in arch/x86/include/asm/kvm-x86-ops.h. Because these hooks sit on the hottest path in the hypervisor, they are not called through the structure: since 5.12 each is a static call, and kvm_x86_vendor_init() patches every call site to the vendor function when the vendor module loads. Only one vendor module can be loaded at a time; the second fails with -EEXIST. Hooks declared KVM_X86_OP_OPTIONAL may be left NULL, and the _RET0 variant defaults to a stub that returns 0. Since 6.18, kvm.ko exports its internal functions with EXPORT_SYMBOL_FOR_KVM_INTERNAL(), which makes them visible only to the vendor modules rather than to every module.

The two vendors' entry paths are structurally identical. On Intel, vmx_vcpu_run() writes any dirty guest state to the VMCS, then calls the noinstr function vmx_vcpu_enter_exit(), which applies speculative-execution mitigations (L1D flush, buffer clearing), restores the guest's CR2, and calls the assembly routine __vmx_vcpu_run in arch/x86/kvm/vmx/vmenter.S. That routine loads the guest's general-purpose registers—the VMCS does not hold them—and executes VMLAUNCH for the first entry on a VMCS or VMRESUME thereafter. When the guest exits, the CPU loads the host state recorded in the VMCS, which resumes execution at the instruction after VMRESUME; the routine saves the guest registers and returns. vmx_vcpu_enter_exit() then reads VM_EXIT_REASON from the VMCS. On AMD, svm_vcpu_run() and svm_vcpu_enter_exit() call __svm_vcpu_run in arch/x86/kvm/svm/vmenter.S, which executes VMRUN with the physical address of the VMCB in RAX; the exit code is read from vmcb->control.exit_code. For SEV-ES and SNP guests, whose registers live in the encrypted save area, the separate __svm_sev_es_vcpu_run saves host state and leaves the guest registers to the hardware.

The assembly is also where the speculative-execution defenses that must sit next to the world switch live. __vmx_vcpu_run takes flags that select VMRESUME over VMLAUNCH, ask it to save the guest's SPEC_CTRL MSR, and request a VERW buffer clear when the vCPU can reach host MMIO (VMX_RUN_CLEAR_CPU_BUFFERS_FOR_MMIO). Immediately after the exit, before the first unbalanced RET, both vendors refill the return stack buffer (FILL_RETURN_BUFFER) so that the host cannot return through predictions the guest left behind, and VMX restores the host's SPEC_CTRL. Still inside the noinstr region, vmx_handle_nmi() runs the host's NMI handler if the exit was caused by an NMI, before any instrumented code can run.

The differences are in the details. The VMCS is an opaque structure accessed only with the VMREAD and VMWRITE instructions and made current per CPU with VMPTRLD—which is why vCPU migration between physical CPUs requires VMCLEAR and reload in vmx_vcpu_load(). The VMCB is ordinary memory with a documented layout, and KVM reads and writes its fields directly, marking changed areas in a clean-bits field so the CPU can skip reloading them. Intel's "acknowledge interrupt on exit" means that an external interrupt that causes an exit has already been taken from the APIC, so vmx_handle_exit_irqoff() invokes the host's handler for that vector directly. KVM refuses to load on a CPU without this exit control. Since 6.9, a kernel built with CONFIG_X86_FRED dispatches the vector through fred_entry_from_kvm(), even on hardware without FRED, which avoids the indirect call through the IDT gate. On AMD the interrupt is simply still pending and is delivered when vcpu_enter_guest() enables interrupts. Intel provides a VMX preemption timer that counts down in guest mode and forces an exit, which KVM uses to emulate the guest's TSC-deadline timer without a host hrtimer; AMD has no equivalent.

TDX adds a third backend inside kvm-intel.ko. For a TD (trust domain) vCPU, the vt_* wrappers in arch/x86/kvm/vmx/main.c route each hook to arch/x86/kvm/vmx/tdx.c instead of vmx.c: vt_vcpu_run() calls tdx_vcpu_run() when is_td_vcpu(vcpu), which enters the guest not with VMRESUME but by asking the TDX module, through a SEAMCALL, to do so (tdh_vp_enter()). §6.3 returns to TDX.

Port I/O shows the general shape of an exit that may leave the kernel. handle_io() decodes the port, size, and direction from the exit qualification and calls kvm_fast_pio(). The I/O is first offered to in-kernel devices registered on the VM's KVM_PIO_BUS—the emulated PIT and PIC, and any ioeventfd (§7.3). If none claims the port, emulator_pio_in_out() fills in kvm_run->io, copies the data into the second page of the vCPU mapping (hence io.data_offset = KVM_PIO_PAGE_OFFSET * PAGE_SIZE), sets exit_reason = KVM_EXIT_IO, and returns 0. For an IN it also arms complete_userspace_io, so that the next KVM_RUN writes the VMM's data into RAX before re-entering. MMIO follows the same pattern through the instruction emulator in arch/x86/kvm/emulate.c, which must decode the faulting instruction to learn the access size and register; that decoding is a large part of why x86 MMIO exits are expensive, and why paravirtual devices prefer port I/O or a hypercall for their doorbells.

Exits that the hardware does not have to take are a tuning knob. The VMCS and VMCB contain bitmaps of intercepted MSRs, I/O ports, exceptions, and instructions; KVM intercepts as little as correctness allows. Accesses to MSRs that are pure guest state (FS_BASE, SYSENTER_*, and so on) pass through. With KVM_CAP_X86_DISABLE_EXITS a VMM that pins one vCPU per dedicated physical CPU can even let the guest execute HLT, MWAIT, and PAUSE natively, enter deep C-states, and, since 6.17, read the APERF and MPERF frequency counters directly, trading host CPU time for latency. The capability must be enabled before any vCPU is created, and on CPUs affected by Cross-Thread Return Address Predictions KVM warns that it should be used only with SMT disabled or with trusted guests.

Two other capabilities add exits that protect the host. A guest that issues atomic operations on data split across cache lines locks the memory bus for every core; with KVM_CAP_X86_BUS_LOCK_EXIT (5.12) KVM reports each such bus lock as KVM_EXIT_X86_BUS_LOCK so that the VMM can throttle the guest (AMD gained the exit in 6.16). A guest can also hold a CPU in microcode indefinitely, for instance in an endless chain of event deliveries that never reaches an instruction boundary, where no ordinary exit can occur. Intel's notify VM exit, enabled with KVM_CAP_X86_NOTIFY_VMEXIT (6.0), forces an exit after a configurable window; KVM resumes the guest, or returns KVM_EXIT_NOTIFY if the VMM asked for it or the VM context was corrupted.

Every exit can be observed. The kvm_entry and kvm_exit tracepoints in arch/x86/kvm/trace.h record each entry and each exit reason with its qualification, kvm_fast_mmio and kvm_userspace_exit mark the cheapest and most expensive outcomes, and the per-vCPU statistics of §2.1 count exits by kind (exits, io_exits, mmio_exits, halt_exits, irq_exits, and others). perf kvm stat live turns the tracepoints into per-reason counts and latencies, and it is usually the first tool to use when a guest runs slowly.

The Run Loop on ARM64

ARM64 has no VMX-style instruction that loads a guest in one step. It has an exception level, EL2, whose system registers control a second stage of translation and decide which guest operations trap. Everything KVM does on ARM64 depends on which kernel code runs at EL2. That code can be the whole host kernel (VHE), a small hypervisor object linked into the kernel image (nVHE), or the same object hardened so that it no longer trusts the host (protected KVM). In every configuration, entering a guest is a sequence of system-register writes ending in ERET, and every exit arrives as an exception whose syndrome register says why. The same trap-and-merge approach supports nested virtualization on both architectures: KVM emulates the VMX or SVM instructions, or the EL2 registers, that a guest hypervisor uses, and merges what it asks for with what the host requires (§4.4).

EL2 and the Three Ways to Use It

An ARMv8 CPU boots the kernel at EL2 when firmware allows it. The early assembly described in Appendix A, §5.2 decides what to do with that level, and the decision fixes how KVM works for the life of the system. The kvm-arm.mode= boot parameter, parsed by early_kvm_mode_cfg() in arch/arm64/kvm/arm.c and recorded in enum kvm_mode since 5.11, selects among the configurations shown in Figure 28-4. ARM64 KVM cannot be built as a module: CONFIG_KVM is a bool, because the EL2 code has to be installed while the kernel still owns EL2 during boot.

  • VHE (Virtualization Host Extensions, ARMv8.1, used by KVM since 4.6). With HCR_EL2.E2H set, EL2 can run an ordinary OS kernel: accesses to EL1 register names are redirected to their EL2 counterparts, and EL2 gets a two-range address space like EL1's. The whole host kernel, KVM included, simply stays at EL2. has_vhe() is true, a hypervisor call is a direct function call, and the guest's EL1 state and stage-2 tables are loaded once at vcpu_load() time by kvm_vcpu_load_vhe() rather than on every entry. This is the default on any CPU that implements VHE.
  • nVHE (kvm-arm.mode=nvhe, or any CPU without VHE). The kernel drops to EL1 at boot and leaves a small, separately linked hypervisor at EL2. That object is built from arch/arm64/kvm/hyp/nvhe/ with every symbol renamed by objcopy --prefix-symbols=__kvm_nvhe_, so the EL2 code cannot accidentally call into the EL1 kernel. The kernel reaches it with HVC: kvm_call_hyp_nvhe() issues an SMCCC call whose function number is KVM_HOST_SMCCC_FUNC(fn), and handle_host_hcall() in hyp/nvhe/hyp-main.c dispatches through the host_hcall[] table. The host is fully trusted. EL2 just switches state on its behalf.
  • Protected KVM (kvm-arm.mode=protected, pKVM). The layout is the same as nVHE. When initialisation finishes, however, finalize_pkvm() issues __pkvm_prot_finalize on every CPU, and from that point the host kernel runs under a stage-2 translation that the EL2 code owns. Even a kernel exploit can no longer touch the hypervisor's memory, including the pages the host has donated to it. On a CPU that implements VHE, the EL2 code runs in hVHE mode (6.5; has_hvhe(), ARM64_KVM_HVHE). The early ID-register override code treats kvm-arm.mode=protected as an alias for arm64_sw.hvhe=1. The kernel still drops to EL1, but the small hypervisor sets HCR_EL2.E2H for itself and uses the VHE register layout. §6.4 returns to pKVM.

A fourth value, kvm-arm.mode=nested (KVM_MODE_NV), is VHE plus permission to expose a virtual EL2 to guests (§4.4). kvm-arm.mode=none disables KVM.

Part of the choice is made before early_kvm_mode_cfg() runs. The ID-register override code in arch/arm64/kernel/pi/idreg-override.c treats kvm-arm.mode=nvhe as an alias for id_aa64mmfr1.vh=0. Hiding VHE that way makes the kernel drop to EL1 before start_kernel(). When the parameter itself is parsed, early_kvm_mode_cfg() only checks that the result is consistent. nested requires a kernel still running at EL2, and protected is ignored with a warning if the kernel ended up at EL2 anyway. If firmware entered the kernel at EL1, no hypervisor can be installed, and every value except none is ignored. The boot log names the outcome in one line, such as kvm [1]: VHE mode initialized successfully. The other modes print Hyp nVHE, Protected nVHE, or Protected hVHE instead, and +NV2 follows VHE when nested virtualization is available.

The configurations differ in cost and in trust. VHE avoids an extra exception-level transition on every exit, and leaves most guest system registers in place across exits that the kernel handles itself. nVHE pays for a full save and restore of the EL1 context on each entry, because host and guest share EL1. pKVM pays that cost and also maintains stage-2 tables for the host, but it is the only configuration in which the host kernel is not trusted with guest memory. Android's virtualization framework ships it for that reason. In every mode the host-facing side of KVM is the same code in arch/arm64/kvm/. Only what happens behind kvm_call_hyp_ret() changes.

The World Switch

kvm_arch_vcpu_ioctl_run() in arch/arm64/kvm/arm.c has the same shape as the x86 loop in §3.1, written in one function instead of three. If the previous exit was KVM_EXIT_MMIO, it first calls kvm_handle_mmio_return() to put the VMM's read data into the target register. It then loads the vCPU, returns -EINTR at once if wants_to_run is false because user space set immediate_exit (§3.1), installs the signal mask, and iterates while ret > 0:

  1. kvm_xfer_to_guest_mode_handle_work() deals with signals and rescheduling. check_vcpu_requests() then services the KVM_REQ_* bits. A dead VM ends the run with -EIO. A powered-off or paused vCPU sleeps in kvm_vcpu_sleep() (KVM_REQ_SLEEP), a PSCI CPU_SUSPEND waits in kvm_vcpu_suspend() (KVM_REQ_SUSPEND, 5.19), and KVM_REQ_VCPU_RESET applies a pending PSCI CPU_ON. The other requests refresh state: a steal-time record, GICv4 and PMU reloads, interrupts that the guest deactivated through a trapped register (KVM_REQ_VGIC_PROCESS_UPDATE, 6.19), a full dirty ring, and finally the nested-virtualization requests (§4.4). There is no TLB-flush request on ARM64. kvm_arch_flush_remote_tlbs() issues a broadcast TLBI by VMID from EL2, so no vCPU has to be kicked (§3.2).
  2. With preemption disabled, kvm_nested_flush_hwstate() (6.17) re-arms an SError that is pending for a nested guest, and kvm_pmu_flush_hwstate() updates the level of the vPMU overflow interrupt. With interrupts disabled, kvm_vgic_flush_hwstate() writes pending virtual interrupts into the GIC list registers (§7.1). On an nVHE host, kvm_pmu_update_vcpu_events() then copies perf's per-CPU list of host-only and guest-only counters into the vCPU, where the EL2 code finds it (§7.5).
  3. smp_store_mb(vcpu->mode, IN_GUEST_MODE) publishes the mode. Then kvm_vcpu_exit_request() rechecks for requests and pending work that raced in. It also stops the entry in two ARM64-specific cases. With a user-space irqchip, a change in the timer or PMU interrupt line that the VMM has not yet seen ends the run with KVM_EXIT_INTR. A vCPU thread that has moved to a CPU outside the VM's supported_cpus mask gets KVM_EXIT_FAIL_ENTRY with KVM_EXIT_FAIL_ENTRY_CPU_UNSUPPORTED (5.18, §7.5). In every case the work of step 2 is undone, and the loop either starts again or ends.
  4. kvm_arch_vcpu_ctxflush_fp() (5.17) marks the FP registers as owned by nobody if the current task's FP state is no longer loaded, so that EL2 does not save a stale host copy when the guest first touches them. After trace_kvm_entry, kvm_arm_vcpu_enter_exit(), a noinstr function, brackets kvm_call_hyp_ret(__kvm_vcpu_run, vcpu) with guest_state_enter_irqoff() and guest_state_exit_irqoff().
  5. Back in the host, the mode returns to OUTSIDE_GUEST_MODE and the exit is counted. State is then synchronized in a fixed order. kvm_pmu_sync_hwstate() runs first, so that the vGIC samples the current level of the PMU interrupt line. kvm_vgic_sync_hwstate() reads the list registers back, which tells the timer code whether its interrupts are still active. Then come kvm_timer_sync_user() for a user-space irqchip and kvm_timer_sync_nested() for a vCPU in virtual EL2. Finally, kvm_arch_vcpu_ctxsync_fp() binds the guest's FP and SVE registers to this CPU if the guest used them, so that the host saves them lazily.
  6. If the exit was ARM_EXCEPTION_IRQ, interrupts are briefly enabled around an ISB, because the architecture takes a pending interrupt only after a context-synchronization event. The host IRQ that caused the exit is handled there, while guest time is still being accounted. guest_timing_exit_irqoff() then closes the accounting window, interrupts are enabled, and trace_kvm_exit records the exit code, exception class, and guest PC.
  7. handle_exit_early() deals with SError, and kvm_nested_sync_hwstate() (6.17) retries delivery of an SError meant for a nested guest. Preemption is then re-enabled.
  8. vcpu_mode_is_bad_32bit() (5.14) catches a guest that has dropped into AArch32 although the host cannot support it there: on a system where only some CPUs implement 32-bit EL0, or in any vCPU with nested virtualization. The architecture gives the hypervisor no way to prevent the switch. The vCPU loses its VCPU_INITIALIZED flag, the exit becomes ARM_EXCEPTION_IL, and the VMM must issue KVM_ARM_VCPU_INIT again. Otherwise handle_exit() decides what the exit means (§4.3).

When the loop ends, a VM with a user-space irqchip receives the final timer and PMU line levels in kvm_run (kvm_timer_update_run(), kvm_pmu_update_run()), and the signal mask is restored. If an exception injection or a PC increment is still pending, kvm_call_hyp(__kvm_adjust_pc) commits it before vcpu_put(), so that the registers user space reads match the state in which the guest will resume. The per-CPU setup lives in kvm_arch_vcpu_load(), which runs at vcpu_load() and again whenever the thread is scheduled back in. Besides the VMID work described below, it loads the timer before the vGIC so that physical interrupt deactivation for nested timers is set up correctly. It also loads the debug registers, the fine-grained trap configuration (kvm_vcpu_load_fgt(), 6.18), the VHE register state, FP ownership, and the guest's PMU event exclusions. It requests a steal-time update when PV time is enabled, decides whether WFI and WFE trap (§4.3), and sets the pointer-authentication traps. In pKVM mode it calls __pkvm_vcpu_load (6.14), which makes the hypervisor's private copy of the vCPU current on that CPU. Finally it flags the vCPU if the CPU is outside supported_cpus, which step 3 then reports.

The work behind __kvm_vcpu_run is the world switch. In nVHE and pKVM it starts with an HVC from EL1. The EL2 host vector saves the host's general registers. handle_trap() sees ESR_ELx_EC_HVC64, and handle___kvm_vcpu_run() calls the EL2 copy of __kvm_vcpu_run(). In pKVM mode, that handler does not trust the host's struct kvm_vcpu. pkvm_get_loaded_hyp_vcpu() fetches the hypervisor's private copy, and flush_hyp_vcpu() copies in only the fields the host may change. The guest runs on the copy, and sync_hyp_vcpu() copies back only what the host needs to see. The nVHE switch itself is compact: 

/* arch/arm64/kvm/hyp/nvhe/switch.c (abridged) */
int __kvm_vcpu_run(struct kvm_vcpu *vcpu)
{
	host_ctxt = host_data_ptr(host_ctxt);
	host_ctxt->__hyp_running_vcpu = vcpu;
	guest_ctxt = &vcpu->arch.ctxt;

	pmu_switch_needed = __pmu_switch_to_guest(vcpu);
	__sysreg_save_state_nvhe(host_ctxt);	/* host EL1 registers */
	__debug_save_host_buffers_nvhe(vcpu);	/* SPE, TRBE, BRBE off */
	dsb(nsh);
	__kvm_adjust_pc(vcpu);			/* pending PC change or exception */
	__sysreg32_restore_state(vcpu);
	__sysreg_restore_state_nvhe(guest_ctxt);	/* guest EL1 registers */

	mmu = kern_hyp_va(vcpu->arch.hw_mmu);
	__load_stage2(mmu, kern_hyp_va(mmu->arch));	/* VTTBR_EL2, VTCR_EL2 */
	__activate_traps(vcpu);				/* HCR_EL2, CPTR_EL2 */
	__hyp_vgic_restore_state(vcpu);
	__timer_enable_traps(vcpu);
	__debug_switch_to_guest(vcpu);

	do {
		/* Jump in the fire! */
		exit_code = __guest_enter(vcpu);
		/* And we're baaack! */
	} while (fixup_guest_exit(vcpu, &exit_code));

	__sysreg_save_state_nvhe(guest_ctxt);
	__sysreg32_save_state(vcpu);
	__timer_disable_traps(vcpu);
	__hyp_vgic_save_state(vcpu);
	dsb(nsh);
	__deactivate_traps(vcpu);
	__load_host_stage2();			/* pKVM: host stage-2; else off */
	__sysreg_restore_state_nvhe(host_ctxt);
	...					/* FPEXC32 if guest owns FP */
	__debug_switch_to_host(vcpu);
	__debug_restore_host_buffers_nvhe(vcpu);
	if (pmu_switch_needed)
		__pmu_switch_to_host(vcpu);
	host_ctxt->__hyp_running_vcpu = NULL;
	return exit_code;
}

Most of that ordering comes from hardware rules. The SPE and TRBE trace buffers and the BRBE branch-record buffer must be flushed and disabled before the host's EL1 translation regime is replaced (__debug_save_host_buffers_nvhe()), and each dsb(nsh) waits for page-table walks that started before the switch. The 32-bit registers are restored before the EL1 system registers because of Cortex-A57 and Cortex-A72 errata, and every VM register must be in place before __load_stage2() enables stage-2 translation. __pmu_switch_to_guest() uses the counter list that step 2 copied in. If the host masks interrupts through the GIC priority mask (pseudo-NMI), the function first unmasks them in ICC_PMR_EL1, because a guest entered with low-priority interrupts masked could leave only through its own traps. The caller adds work of its own. The non-protected path of handle___kvm_vcpu_run() brackets the call with fpsimd_lazy_switch_to_guest() and fpsimd_lazy_switch_to_host() (6.14), which program the guest's SVE vector length when it already owns the FP registers. The protected path refuses to run the guest, with -EINVAL, if the host left SME streaming mode enabled.

__guest_enter, in arch/arm64/kvm/hyp/entry.S, saves the host's callee-saved registers, loads the guest's x0–x30 from vcpu->arch.ctxt, and executes ERET into guest EL1. When the guest traps, the EL2 vector __kvm_hyp_vector (hyp/hyp-entry.S) branches to el1_sync. Three SMCCC calls, the Spectre workarounds ARM_SMCCC_ARCH_WORKAROUND_1 (Spectre-v2), _2 (Spectre-v4), and _3 (Spectre-BHB), are answered right there in assembly with a result of 0 and without saving any state, because the exception entry into EL2 has already done what they ask for. Every other trap continues to __guest_exit, which stores the guest registers and returns an ARM_EXCEPTION_* code (IRQ, EL1_SERROR, TRAP, IL) to the C caller.

fixup_guest_exit() plays the part of x86's fastpath. It first copies SPSR_EL2 into the vCPU's PSTATE (synchronize_vcpu_pstate(), which also works around Cortex-A510 erratum 2077057) and records ESR_EL2. A trap that arrives together with a pending SError goes straight back to the host, which injects the SError and lets the guest replay the instruction. Otherwise the function indexes a table of EL2 handlers by exception class: hyp_exit_handlers[], or pvm_exit_handlers[] for a protected guest. If a handler returns true, the loop re-enters the guest without ever leaving EL2. These handlers do the lazy FP/SVE switch (kvm_hyp_handle_fpsimd()). kvm_hyp_handle_sysreg() emulates GICv3 CPU-interface registers and the counter registers (kvm_handle_cntxct(), 6.14), and applies workarounds for Cavium ThunderX2 and Ampere errata. kvm_hyp_handle_mops() (6.7) resets the registers of a MOPS memory-copy instruction that was interrupted and resumed on a different kind of CPU, so that it restarts from its prologue. For instruction, data, and watchpoint aborts, kvm_hyp_handle_memory_fault() captures FAR_EL2 and HPFAR_EL2 into vcpu->arch.fault (__populate_fault_info()) before the host sees the exit, and kvm_hyp_handle_dabt_low() can also emulate a GICv2 CPU-interface access in place. The protected table is stricter. It has no CP15 entry, sends SYS64 to kvm_handle_pvm_sys64(), which answers ID-register reads from the hypervisor's own view of the VM and injects UNDEF for restricted registers, and turns every SVE trap into UNDEF. In nVHE mode, EL2 also checks for itself that a protected guest has not dropped into AArch32. It does not trust the host to make the check of step 8, so it clears VCPU_INITIALIZED and returns ARM_EXCEPTION_IL.

The VHE variant in hyp/vhe/switch.c is shorter. __kvm_vcpu_run() masks all of DAIF, issues pmr_sync() so that the interrupt controller sees the new priority mask, and calls __kvm_vcpu_run_vhe(). That function saves and restores only the registers that the host kernel uses at EL2 and the guest uses at EL1 (sysreg_save_host_state_vhe(), sysreg_restore_guest_state_vhe()). It sets the trap configuration, which on CPUs with Cortex-A76 erratum 1165522 must come after the guest's stage-1 and stage-2 setup, and runs the same __guest_enter loop. On the way out, an ISB makes the restored host registers take effect before fpsimd_lazy_switch_to_host() touches FP state, because in VHE mode the FP traps in CPTR_EL2 also apply to EL2 itself. The VHE handler table adds ERET (kvm_hyp_handle_eret(), 6.10), which lets a guest hypervisor return to its nested guest without a full exit. It also adds class 0x3F, an implementation-defined trap that Apple CPUs raise for PMU registers, which kvm_hyp_handle_impdef() (6.15) rewrites as an ordinary SYS64 trap for the host. Its SYS64 handler, kvm_hyp_handle_sysreg_vhe(), first tries the nested-virtualization helpers for EL2 TLBI instructions, the guest hypervisor's timer registers (6.14), CPACR_EL1, and ZCR_EL2 (6.11). The VHE fixup_guest_exit() also rewrites the saved PSTATE so that a guest hypervisor, which really runs at EL1, sees itself at EL2. The EL1 registers, the VMID, and VTTBR_EL2 were already loaded by kvm_arch_vcpu_load(). That function also allocates the VMID through kvm_arm_vmid_update(), and invalidates TLB and I-cache contexts with __kvm_flush_cpu_context when another vCPU of the same VM last ran on this CPU. VMIDs are the ARM64 counterpart of VPIDs, as Chapter 2, §12.4 explains. Because the host and the guest kernel use different exception levels, a VHE host can keep the guest's EL1 context loaded while it handles an exit, and swap it out only on vcpu_put(). That is the main reason VHE exits are cheaper.

Exception Classes and Exit Handling

x86 tells KVM why the guest stopped with a VMX exit reason or an SVM exit code. ARM64 uses the same mechanism as any other exception taken to a higher level: the exception class field of ESR_EL2, plus an instruction-specific syndrome. handle_exit() in arch/arm64/kvm/handle_exit.c first switches on the ARM_EXCEPTION_* code. An exit that came back with an SError pending simply resumes, because handle_exit_early() has already dealt with the SError. With the RAS extension, it reads the deferred syndrome from DISR_EL1 and classifies it in kvm_handle_guest_serror(). Without RAS, it injects a virtual SError into the guest. IRQ and EL1_SERROR also just resume. HYP_GONE, which means that kvm_reboot() has already reset EL2 to the hyp stub, becomes KVM_EXIT_FAIL_ENTRY with a return value of 0. An illegal exception return, including the 32-bit case of §4.2, becomes KVM_EXIT_FAIL_ENTRY with -EINVAL. Anything unexpected becomes KVM_EXIT_INTERNAL_ERROR. For TRAP, handle_trap_exceptions() first checks whether the trapped instruction was an AArch32 conditional instruction whose condition failed, which the architecture allows a CPU to trap anyway. Such an instruction is just skipped. Otherwise kvm_get_exit_handler() indexes arm_exit_handlers[] with ESR_ELx_EC(esr). Two exits deserve a closer look. A guest that executes WFI has nothing to do. If a guest hypervisor asked to trap its own guest's waits, kvm_handle_wfx() forwards the exit to it. Otherwise kvm_vcpu_wfi() drops the vGIC state with kvm_vgic_put(), calls the generic kvm_vcpu_halt() (which may poll before it sleeps, §7.4), and reloads with kvm_vgic_load(). This mirrors x86's HLT. WFE, which spin-lock loops use, calls kvm_vcpu_on_spin() instead, to yield to a preempted lock holder (§3.2). The ARMv8.7 variants WFIT and WFET (FEAT_WFxT, supported since 5.19) carry a deadline in a register. If the deadline has already passed on the guest's virtual counter, the instruction just completes. Otherwise WFIT sets the IN_WFIT flag, so that the timer code also wakes the vCPU at the deadline. Whether WFI and WFE trap at all is decided at vcpu_load() time. When the vCPU thread is the only task on its CPU, kvm_vcpu_should_clear_twe() lets the guest execute WFE natively. kvm_vcpu_should_clear_twi() does the same for WFI only when the guest's interrupts arrive through GICv4 direct injection (§7.2), because only then can the hardware wake a guest that waits natively. The kvm-arm.wfi_trap_policy= and kvm-arm.wfe_trap_policy= boot parameters (6.11) override these defaults with trap or notrap.

A data abort on an address outside every memslot is MMIO. io_mem_abort() in arch/arm64/kvm/mmio.c needs the syndrome's ISV bit, which says that the hardware has decoded the access size, the target register, and the direction. With that, it tries kvm_io_bus_write() or kvm_io_bus_read() on KVM_MMIO_BUS, so that in-kernel devices such as the vGIC distributor and ioeventfds (§7.3) can claim the access. When an in-kernel device accepts it, the result is written back at once by kvm_handle_mmio_return(), and the guest resumes without leaving the kernel (counted in mmio_exit_kernel). Otherwise it fills run->mmio and returns KVM_EXIT_MMIO (mmio_exit_user). Unlike x86, there is no instruction emulator. If the guest used an instruction the syndrome cannot describe, such as a load-pair or a write-back addressing mode, KVM returns KVM_EXIT_ARM_NISV when the VMM enabled KVM_CAP_ARM_NISV_TO_USER (5.5), and otherwise fails the run with -ENOSYS. A protected guest receives a synchronous external abort instead, because its VMM is not trusted to emulate the access. Guest kernels therefore access MMIO with simple LDR/STR instructions. Since 7.0, the 64-byte single-copy-atomic LD64B/ST64B family, which the syndrome marks with a load/store type, leaves as KVM_EXIT_ARM_LDST64B for a VMM that exposed FEAT_LS64 and must emulate the instruction in full (§1.3). Hardware memory errors can be handed over the same way. Since 6.19, a VMM that enables KVM_CAP_ARM_SEA_TO_USER receives KVM_EXIT_ARM_SEA, with the syndrome, the faulting virtual address, and the guest physical address when it is known, for a synchronous external abort that the host's firmware-first (APEI) error handling has not claimed. The VMM can then decide how to report the error to the guest. Without the capability, and for aborts on KVM's own stage-2 tables, KVM injects an SError itself. Hypercalls follow a similar split. Since 6.4 the VMM can install an SMCCC filter with the KVM_ARM_VM_SMCCC_FILTER attribute. A range marked KVM_SMCCC_FILTER_FWD_TO_USER leaves the kernel as KVM_EXIT_HYPERCALL. Unfiltered calls are answered in kvm_smccc_call_handler(): PSCI, TRNG, the PV-time and PTP services, and the standard feature queries.

Nested Virtualization

A guest that wants to run its own hypervisor needs the virtualization hardware, but it must not get the real thing. Both architectures solve this by trapping and emulating the guest hypervisor (L1). KVM (L0) then builds the hardware state for the nested guest (L2) by merging what L1 asked for with what L0 requires. Chapter 2, §12.9 covers the address translation side. The run-loop side looks like this.

On Intel, nested VMX dates from 3.1 and lives in arch/x86/kvm/vmx/nested.c; the module parameter kvm_intel.nested has been on by default since 4.20. L1's VMLAUNCH or VMRESUME exits to L0, where nested_vmx_run() checks L1's VMCS, cached as struct vmcs12, and nested_vmx_enter_non_root_mode() calls prepare_vmcs02() to build the VMCS that the hardware actually runs. VMREAD and VMWRITE would trap on every access, so KVM uses hardware VMCS shadowing (enable_shadow_vmcs) to let L1 touch most fields without an exit. When L2 exits, nested_vmx_reflect_vmexit() decides whether L1 asked to intercept that event. If so, __nested_vmx_vmexit() writes the exit into vmcs12 and resumes L1. If not, L0 handles the exit itself. AMD's version, from 2.6.30, mirrors this in arch/x86/kvm/svm/nested.c: nested_svm_vmrun() reads L1's VMCB, enter_svm_guest_mode() merges it into vmcb02 through nested_vmcb02_prepare_control(), and nested_svm_exit_handled() and nested_svm_vmexit() reflect exits. Both sides shadow L1's EPT or NPT tables with the shadow-paging code (nested_ept_init_mmu_context(), nested_svm_init_mmu_context(), and the PTTYPE_EPT instantiation of mmu/paging_tmpl.h), because hardware walks only one level of second-stage tables. Live migration of a VM whose L2 is running is supported by KVM_GET_NESTED_STATE and KVM_SET_NESTED_STATE (KVM_CAP_NESTED_STATE, 4.19), which serialize vmcs12 or vmcb12 with a KVM_STATE_NESTED_FORMAT_VMX or _SVM tag.

ARM64 nested support is newer and depends on hardware help. With FEAT_NV, the guest hypervisor runs at EL1 with HCR_EL2.NV set, so its EL2 register accesses and its ERET trap to the real EL2. FEAT_NV2 goes further: most of those accesses become loads and stores to a memory page at the address in VNCR_EL2, so they no longer cause exits. KVM's code arrived in pieces from 6.3 onward and is spread over arch/arm64/kvm/nested.c and emulate-nested.c. Guest exceptions that L1 would see are injected with kvm_inject_nested_sync(). Returns from virtual EL2 go through kvm_emulate_nested_eret(). triage_sysreg_trap() decides whether a trapped register access belongs to L1 or to L0. For each stage-2 context that L1 builds, a shadow struct kvm_s2_mmu is maintained, found by lookup_s2_mmu() and switched in by kvm_vcpu_load_hw_mmu(). Since 6.16, kvm_handle_vncr_abort() resolves faults on the VNCR page. The feature is visible only when the host boots with kvm-arm.mode=nested, the CPU has FEAT_NV2 (ARM64_HAS_NESTED_VIRT), and the interrupt controller is a GICv3, or a GICv5 with GICv3 compatibility. Without such a GIC, KVM refuses to initialize. The VMM checks KVM_CAP_ARM_EL2 (6.16) and sets the KVM_ARM_VCPU_HAS_EL2 feature bit in KVM_ARM_VCPU_INIT. KVM_ARM_VCPU_HAS_EL2_E2H0 additionally asks for a guest EL2 without VHE, for guest hypervisors that need one. KVM_CAP_ARM_EL2_E2H0 (6.16) reports that option only on CPUs that implement HCR_EL2.NV1, which some NV2-capable designs leave out.

The nested machinery also shows up in the run loop of §4.2. At the end of check_vcpu_requests(), check_nested_vcpu_requests() handles three requests. KVM_REQ_NESTED_S2_UNMAP (6.12) empties a shadow stage-2 that has been recycled for a new L1 context. KVM_REQ_MAP_L1_VNCR_EL2 (6.16) re-creates the EL2 mapping of the page that L1's VNCR_EL2 names. KVM_REQ_GUEST_HYP_IRQ_PENDING (6.15) delivers an IRQ exception to L1 when the vGIC finds an interrupt for the guest hypervisor while L2 runs. It is handled last, because it may switch the vCPU from L2 to L1 context. SErrors aimed at L2 are carried across entries by kvm_nested_flush_hwstate() and kvm_nested_sync_hwstate(), and kvm_timer_sync_nested() keeps the guest hypervisor's timers in step after each exit from virtual EL2.

Memory Virtualization

Chapter 2, §12 explains how the hardware composes a guest's page tables with a second set of tables that translate guest-physical addresses to host-physical ones. KVM owns that second set. It builds it lazily, one fault at a time, from a table of memory slots that maps guest-physical ranges onto the VMM's virtual addresses. Because those addresses are ordinary anonymous or file-backed memory, the host kernel stays free to reclaim, migrate, compact, and swap the pages behind them. Most of the remaining work is keeping the second-stage tables consistent with those host decisions, and recording which pages a guest has written so that live migration can copy them. The four subsections follow that order: how memslots map guest frames to host pages (§5.1), how a second-stage fault is resolved on x86 and ARM64 (§5.2), how MMU notifiers keep the tables coherent with the host mm (§5.3), and how written pages are tracked (§5.4). Private memory bound through guest_memfd skips the VMM's address space altogether; §6 covers that path.

Memslots: From Guest Frame to Host Page

KVM has no memory of its own to give a guest. The VMM allocates ordinary user memory, usually an anonymous or memfd mapping, possibly backed by hugetlbfs or transparent huge pages. It then describes each piece to KVM with KVM_SET_USER_MEMORY_REGION2: 

/* include/uapi/linux/kvm.h */
struct kvm_userspace_memory_region2 {
	__u32 slot;		/* (address space << 16) | slot id */
	__u32 flags;		/* KVM_MEM_LOG_DIRTY_PAGES, _READONLY, _GUEST_MEMFD */
	__u64 guest_phys_addr;
	__u64 memory_size;	/* 0 deletes the slot */
	__u64 userspace_addr;	/* start of the VMM's mapping */
	__u64 guest_memfd_offset;
	__u32 guest_memfd;	/* fd from KVM_CREATE_GUEST_MEMFD (§6.1) */
	__u32 pad1;
	__u64 pad2[14];
};

The older KVM_SET_USER_MEMORY_REGION takes the same structure without the guest_memfd fields and accepts only the first two flags. The 2 variant and KVM_CAP_USER_MEMORY2 arrived in 6.8 together with guest_memfd. KVM_MEM_LOG_DIRTY_PAGES turns on dirty tracking (§5.4). KVM_MEM_READONLY makes guest writes exit to user space as MMIO, which is how a VMM emulates flash or ROM; it is refused for x86 VMs whose state is protected from the host. KVM_MEM_GUEST_MEMFD binds the slot to a guest_memfd file (§6.1) and excludes both other flags. kvm_set_memory_region() checks that the size, guest-physical address, and user address are page-aligned and that the user range passes access_ok(). A slot holds at most KVM_MEM_MAX_NR_PAGES ((1UL << 31) - 1) pages, and a slot that overlaps another one in the same address space fails with -EEXIST. An existing slot can be moved to a new guest-physical base or have its flags changed, but it cannot be resized or pointed at different user memory. A guest_memfd slot cannot be changed at all, only deleted.

Each region becomes a memslot, a struct kvm_memory_slot holding base_gfn, npages, userspace_addr, the flags, an optional dirty bitmap, the bound guest_memfd file, and an arch part. The x86 arch part holds reverse maps and per-level huge-page tracking. A guest-physical frame number (gfn) is translated by finding its slot and adding an offset. That is all __gfn_to_hva_memslot() does: slot->userspace_addr + (gfn - slot->base_gfn) * PAGE_SIZE. Gaps between slots have no backing memory. A guest access there becomes MMIO, which is how the VMM's emulated devices get their exits. Figure 28-5 shows the two lookups and the shortcut that the hardware tables provide.

The slots of one address space form a struct kvm_memslots. It is indexed three ways: an interval tree by host address (hva_tree), used when the host mm invalidates a range; an rbtree by gfn (gfn_tree); and a hash by slot id. A VM-wide last_used_slot hint, plus a per-vCPU copy in vcpu->last_used_slot that is discarded whenever the generation changes, makes repeated lookups cheap. With CONFIG_KVM_SMM, x86 has two address spaces, the second for System Management Mode, which a vCPU uses while it is in SMM. KVM_MAX_NR_ADDRESS_SPACES is then 2, but a VM with private memory gets only one, because SMM is not supported for such guests. Every other architecture has one. Up to KVM_USER_MEM_SLOTS slots are available to user space, as reported by KVM_CAP_NR_MEMSLOTS. That is SHRT_MAX (32767) on most architectures. x86 subtracts three internal slots, for the VMX TSS, the APIC access page, and the identity-mapped page table that real-mode guests need on CPUs without unrestricted guest support.

Memslots are read on every fault and every guest-memory access the kernel makes on the guest's behalf, but change rarely. KVM therefore keeps two copies of each kvm_memslots (kvm->__memslots[as][2]) and updates them in read-copy-update style. kvm_set_memslot() runs under kvm->slots_lock and classifies the change as KVM_MR_CREATE, KVM_MR_DELETE, KVM_MR_MOVE, or KVM_MR_FLAGS_ONLY. A deletion or move first installs an invalid copy of the old slot, so that no vCPU can create new mappings through it, and zaps its second-stage entries. Then kvm_prepare_memory_region() allocates or reuses the dirty bitmap (setting every bit when KVM_DIRTY_LOG_INITIALLY_SET is in force) and calls kvm_arch_prepare_memory_region(). The inactive copy is edited, and kvm_swap_active_memslots() publishes it with rcu_assign_pointer() and waits in synchronize_srcu_expedited(&kvm->srcu). This is why every vCPU holds the SRCU read lock while it runs (§2.2). The swap also waits until no MMU notifier invalidation is running (mn_active_invalidate_count is zero), so that an invalidation never sees one set of slots at its start and another at its end. Finally kvm_arch_commit_memory_region() applies architecture-side effects, such as starting or stopping dirty logging (§5.4). How a deleted slot's entries are zapped depends on the architecture. x86 normally zaps only that slot with kvm_mmu_zap_memslot(), but VMs of the default type keep the historical behavior of discarding every entry (kvm_mmu_zap_all_fast()) unless the VMM disables KVM_X86_QUIRK_SLOT_ZAP_ALL (6.12).

A generation number in kvm_memslots lets caches derived from memslots notice that they are stale. Bit 63 (KVM_MEMSLOT_GEN_UPDATE_IN_PROGRESS) is set while an update is in flight, so no cache can record a value from the middle of an update. After the swap the number advances by the number of address spaces, so address space 0 uses even generations, address space 1 odd ones, and the two never share a value. One example of such a cache is x86's MMIO SPTEs, which encode part of the generation so that a later EPT_MISCONFIG can tell whether a cached "this is MMIO" decision still holds. When the bits stored in the SPTE wrap around, kvm_mmu_invalidate_mmio_sptes() zaps everything to rule out a false match.

The second half of the path, from host virtual address to page frame, is ordinary memory management. __kvm_faultin_pfn() fills a struct kvm_follow_pfn and calls hva_to_pfn(). That function tries the lockless get_user_page_fast_only(), but only when a writable mapping is wanted. A read-only lookup through that path could race with a copy-on-write break and leave KVM pointing at the old page. Otherwise, or if the fast path fails, it calls get_user_pages_unlocked(), which can fault the page in, swapping or allocating as needed. VM_IO and VM_PFNMAP mappings of device memory have no struct page to take a reference on, so hva_to_pfn_remapped() reads the pfn straight from the host page table with follow_pfnmap_start(), calling fixup_user_fault() first if the entry is not yet present. Failures come back as special pfn values: KVM_PFN_ERR_SIGPENDING when a signal interrupted the wait, KVM_PFN_ERR_HWPOISON for a page with an uncorrectable memory error, and KVM_PFN_ERR_NEEDS_IO when a FOLL_NOWAIT lookup would have to wait for I/O.

The reference taken by GUP is dropped as soon as the second-stage entry is installed. If the mapping is writable, kvm_release_faultin_page() first marks the page dirty while mmu_lock is still held. KVM does not pin guest RAM. It relies on MMU notifiers (§5.3) to learn when the page goes away. The kernel's own accesses to guest memory, such as kvm_read_guest() and kvm_write_guest(), also go through the host virtual address, as ordinary user copies. Only kvm_vcpu_map(), used for pages such as a nested guest's virtual-APIC page or VMCB, holds a page outside notifier protection. It refuses VM_PFNMAP memory unless the kvm.allow_unsafe_mappings parameter (6.13) is set, because nothing would stop that memory from being unmapped underneath it. VFIO is different again: devices that DMA into guest memory need it pinned, which is the long-term pinning case described in Chapter 9.

Second-Stage Faults: TDP MMU and Stage-2

A guest's first access to a frame finds no second-stage entry. Intel reports an EPT violation (handle_ept_violation() in vmx/vmx.c), AMD an NPF exit (npf_interception() in svm/svm.c), and both call kvm_mmu_page_fault() with the faulting guest-physical address and an error code built from the exit qualification. The page-fault hook of the vCPU's MMU context is kvm_tdp_page_fault(), and on 64-bit hosts with the default kvm.tdp_mmu=1 that leads to the TDP MMU. The TDP MMU was introduced in 5.10 and has been the default since 5.15. Its entry point is short: 

/* arch/x86/kvm/mmu/mmu.c */
static int kvm_tdp_mmu_page_fault(struct kvm_vcpu *vcpu,
				  struct kvm_page_fault *fault)
{
	int r;

	if (page_fault_handle_page_track(vcpu, fault))
		return RET_PF_WRITE_PROTECTED;

	r = fast_page_fault(vcpu, fault);	/* lockless permission fixups */
	if (r != RET_PF_INVALID)
		return r;

	r = mmu_topup_memory_caches(vcpu, false);
	if (r)
		return r;

	r = kvm_mmu_faultin_pfn(vcpu, fault, ACC_ALL);	/* gfn -> pfn */
	if (r != RET_PF_CONTINUE)
		return r;

	r = RET_PF_RETRY;
	read_lock(&vcpu->kvm->mmu_lock);

	if (is_page_fault_stale(vcpu, fault))	/* raced with an invalidation? */
		goto out_unlock;

	r = kvm_tdp_mmu_map(vcpu, fault);

out_unlock:
	kvm_mmu_finish_page_fault(vcpu, fault, r);
	read_unlock(&vcpu->kvm->mmu_lock);
	return r;
}

Three details explain the design. First, the pfn is looked up before mmu_lock is taken, because GUP may sleep. kvm_mmu_faultin_pfn() records kvm->mmu_invalidate_seq first, and is_page_fault_stale() rechecks it under the lock (§5.3). Second, the lock is taken for read. kvm_tdp_mmu_map() (arch/x86/kvm/mmu/tdp_mmu.c) walks the paging-structure hierarchy with a tdp_iter under rcu_read_lock(), allocates missing levels, and installs entries with cmpxchg (tdp_mmu_set_spte_atomic()). That way vCPUs faulting in parallel do not serialize, and a lost race simply returns RET_PF_RETRY so that the guest re-executes the access. Third, kvm_mmu_hugepage_adjust() asks host_pfn_mapping_level() how the VMM's page is mapped in the host page tables. When the host uses a 2 MiB or 1 GiB mapping and the memslot is suitably aligned, the second-stage entry can be equally large. Before any of this, fast_page_fault() resolves write-protection and access-tracking faults on an existing entry with a single atomic update and no lock at all.

kvm_mmu_faultin_pfn() does more than translate. If the fault's private or shared state disagrees with the gfn's memory attributes (§6.2), it prepares a KVM_EXIT_MEMORY_FAULT exit (6.8) and returns -EFAULT, so that the VMM can convert the page and let the guest retry. A gfn with no memslot becomes an MMIO fault. A slot that is being deleted or moved (KVM_MEMSLOT_INVALID) makes the fault return RET_PF_RETRY, so the vCPU keeps re-entering the guest until the update ends. If an invalidation covering the gfn is already in progress, the fault backs off before calling GUP at all. Private faults then take the pfn from guest_memfd. Everything else goes through hva_to_pfn(), first with FOLL_NOWAIT. If that lookup would need I/O, KVM tries to start an async page fault (§5.3), and if it cannot, repeats the lookup allowing it to sleep but to be interrupted by a signal. kvm_handle_error_pfn() maps the error pfns onto outcomes: a pending signal exits to user space with KVM_EXIT_INTR, a write to a read-only slot is emulated (and so becomes an MMIO exit), a poisoned page raises SIGBUS in the VMM, and anything else returns -EFAULT. The RET_PF_* results feed the per-vCPU statistics pf_taken, pf_fixed, pf_emulate, and pf_spurious.

The mapping level is bounded from several directions. kvm_mmu_hugepage_adjust() gives up at once for a slot with dirty logging. Otherwise kvm_mmu_max_mapping_level() consults the slot's per-level lpage_info, which forbids a huge page that would cross the slot's edge, whose guest and host addresses are aligned differently, that mixes private and shared attributes, or that covers a gfn write-tracked by the shadow MMU. It then takes the host's mapping size from host_pfn_mapping_level(), or for guest_memfd asks the vendor's gmem_max_mapping_level hook, which on SEV-SNP and TDX respects the granularity of the RMP or Secure EPT. A further limit comes from the iTLB multihit erratum of many Intel CPUs, where changing the size of a page that has executable iTLB entries can cause a machine check. With the kvm.nx_huge_pages mitigation on (the default auto enables it only on affected CPUs with mitigations enabled), huge second-stage pages are mapped non-executable. An instruction fetch that hits one gets 4 KiB pages instead. A recovery worker, a vhost_task since 6.14 that is tuned by nx_huge_pages_recovery_ratio and nx_huge_pages_recovery_period_ms, periodically zaps some of those split pages so that they can become huge again if the guest stops executing from them. TDP MMU roots are shared: kvm_tdp_mmu_alloc_root() reuses an existing root whose page role matches, so all vCPUs in the same mode walk one tree, and roots live until a memslot update or VM teardown invalidates them. Finally, KVM_PRE_FAULT_MEMORY (6.11, x86 only) runs this fault path from user space for a range of guest-physical addresses, so that a VMM can populate memory before the guest touches it.

The older shadow MMU (mmu.c and the paging_tmpl.h template) is still built and still needed. It serves CPUs or configurations without EPT/NPT (kvm_intel.ept=0, kvm_amd.npt=0), where KVM must shadow the guest's own page tables and write-protect them to notice changes. It also shadows L1's EPT or NPT tables for a nested guest (§4.4). The private memory of TDX guests is handled by a further variant: mirror roots in the TDP MMU, whose changes are forwarded to the TDX module through the external_spt hooks instead of being written directly (§6.3). MMIO is tracked by deliberately misconfigured entries. An access to an address with no slot installs an MMIO SPTE, so the next access causes EPT_MISCONFIG. AMD has no such exit, so its MMIO SPTEs set reserved bits instead and come back as an NPF with the reserved-bit error code. Both routes reach handle_mmio_page_fault() through kvm_mmu_page_fault(), which checks the cached generation (§5.1). handle_ept_misconfig() first offers it to KVM_FAST_MMIO_BUS, where an ioeventfd (§7.3) can claim a doorbell write without decoding the instruction at all.

On ARM64 the guest abort goes to kvm_handle_guest_abort() in arch/arm64/kvm/mmu.c. Synchronous external aborts are handed to kvm_handle_guest_sea() first. The IPA comes from HPFAR_EL2. A translation fault beyond the largest IPA the hardware supports injects an address-size fault into the guest, and one between that limit and the IPA size chosen for the VM (KVM_VM_TYPE_ARM_IPA_SIZE) injects an external abort. An unexpected fault status code returns -EFAULT to the VMM. For a nested guest, kvm_walk_nested_s2() first translates the address through L1's stage-2 tables. If L1's tables do not map it or do not allow the access, the fault is injected into L1 as its own stage-2 abort (§4.4). KVM then looks up the memslot. No slot, or a write to a read-only slot, normally means MMIO and io_mem_abort() (§4.3). The exceptions are an instruction fetch and an access made by the guest's own stage-1 table walk, which both get an external abort, and a cache maintenance instruction, which is simply skipped. An access-flag fault is fixed in place by handle_access_fault(). Everything else goes to gmem_abort() (6.18) for a guest_memfd slot or to user_mem_abort() otherwise.

user_mem_abort() follows the same protocol as x86. It looks at the VMA to choose a mapping size: PUD_SIZE or PMD_SIZE for a hugetlbfs VMA when the slot's guest and host addresses are aligned alike, the next size down for the contiguous-hint hugetlb sizes, and PAGE_SIZE otherwise or when dirty logging sets force_pte. For a nested guest the size is also clamped to L1's own stage-2 mapping. It samples mmu_invalidate_seq, calls __kvm_faultin_pfn(), takes the lock with kvm_fault_lock() (mmu_lock for read, or for write under pKVM), backs out if mmu_invalidate_retry() fires, and may upgrade a 4 KiB mapping to a block with transparent_hugepage_adjust() when the host backs it with a THP. The memory type comes from the VMA. Ordinary RAM is mapped Normal cacheable. A VM_PFNMAP mapping of device memory gets Device-nGnRE, or Normal non-cacheable if the driver set VM_ALLOW_ANY_UNCACHED (6.9), as vfio-pci does for device BARs. A cacheable VM_PFNMAP mapping is accepted only on a CPU with FEAT_S2FWB and coherent instruction caches, which user space can test with KVM_CAP_ARM_CACHEABLE_PFNMAP_SUPPORTED (6.17); otherwise the fault fails with -EFAULT. During dirty logging a read fault maps the page read-only, so the first write still faults. A page is made executable only when the fault is an instruction fetch, unless the CPU's instruction cache needs no maintenance (ARM64_HAS_CACHE_DIC), and an MTE-enabled guest gets cleared tags on pages it has not seen before. Finally the function calls kvm_pgtable_stage2_map(), or kvm_pgtable_stage2_relax_perms() for a permission fault on an existing entry of the same size, and marks the page dirty if it was mapped writable. gmem_abort() is a reduced version that always maps single pages, takes the pfn from kvm_gmem_get_pfn(), and turns a failure into a KVM_EXIT_MEMORY_FAULT exit.

The stage-2 tables are built by the generic walker in arch/arm64/kvm/hyp/pgtable.c, the same code that builds the nVHE hypervisor's own stage-1 tables. When it installs a cacheable mapping on a CPU without FEAT_S2FWB, it cleans the page to the point of coherency first, because the guest may run with its caches off. When it makes a page executable, it invalidates the instruction cache. With CONFIG_ARM64_HW_AFDBM, KVM sets VTCR_EL2.HA, so the hardware sets the stage-2 access flag itself and access-flag faults become rare. Under pKVM, the host cannot write stage-2 tables, so the KVM_PGT_FN() macro (6.14) redirects each call to a pkvm_ variant. That variant records the mapping in an interval tree and asks EL2 to install it with the __pkvm_host_share_guest hypercall, after EL2 checks that the host really owns the page. Unmapping, permission changes, write-protection, and aging have matching hypercalls: __pkvm_host_unshare_guest, __pkvm_host_relax_perms_guest, __pkvm_host_wrprotect_guest, __pkvm_host_test_clear_young_guest, and __pkvm_host_mkyoung_guest.

Keeping Second-Stage Tables Coherent

Because KVM does not pin guest memory, the host can reclaim, swap, migrate, compact, or deduplicate (KSM) a page that a guest has mapped. Before it does so, the core mm calls the mmu_notifier chain of the owning mm_struct, and KVM registers one per VM (kvm_mmu_notifier_ops in virt/kvm/kvm_main.c). Chapter 2, §12.7 introduces the idea. The callbacks are:

  • invalidate_range_start and invalidate_range_end. The first raises mn_active_invalidate_count, which holds off memslot swaps (§5.1), and invalidates any gfn_to_pfn_cache covering the range. It then searches each address space's hva_tree. Only if some memslot overlaps does it take mmu_lock for write and call kvm_mmu_invalidate_begin() (which increments mmu_invalidate_in_progress), widening the recorded gfn range to include the overlap so that concurrent invalidations merge into one range. It calls kvm_unmap_gfn_range() on every overlapping memslot through kvm_handle_hva_range(), and flushes remote TLBs if anything was zapped. On ARM64 that also unmaps the range from every nested guest's shadow stage-2 (6.11). On AMD SEV, but not SEV-SNP, kvm_arch_guest_memory_reclaimed() then writes back caches, because the hardware does not keep a page's encrypted cache lines coherent for its next owner. The second callback calls kvm_mmu_invalidate_end(), which increments mmu_invalidate_seq and then decrements the in-progress count.
  • clear_flush_young, clear_young, and test_young. These let page reclaim's referenced-bit scans see guest accesses. They call kvm_age_gfn() and kvm_test_age_gfn(), which read and clear the accessed bits in second-stage entries. Only clear_flush_young may flush TLBs afterwards, and x86 skips even that (CONFIG_KVM_ELIDE_TLB_FLUSH_IF_YOUNG, 6.13), as its own ptep_clear_flush_young() does for host page tables, because a stale TLB entry only makes a page look older than it is. Since 6.15, x86 and s390 age entries without taking mmu_lock (CONFIG_KVM_MMU_LOCKLESS_AGING). On ARM64 the hardware usually maintains the stage-2 access flag (§5.2).
  • release, called when the VMM's mm is torn down. It zaps everything with kvm_flush_shadow_all().

The fault paths close the race with a sequence-count check. They read mmu_invalidate_seq before the unlocked pfn lookup. Under mmu_lock they call mmu_invalidate_retry_gfn(), which reports a retry if an invalidation covering this gfn is in progress or if the sequence count has moved. A pfn that might have been freed in between is thus never installed. The invalidation is synchronous on the host's side: the mm does not free the page until the notifier returns, and the notifier returns only after the entries are gone and the TLBs are flushed. The same callbacks serve mprotect(), NUMA balancing, and THP collapse, so a guest always sees memory with the host's current permissions.

Two related features ride on these mechanisms. Async page faults (x86 and s390, CONFIG_KVM_ASYNC_PF) handle the case where the pfn lookup would block on I/O. Instead of stalling the vCPU, kvm_arch_setup_async_pf() queues async_pf_execute() on a workqueue to fault the page in. On x86 a guest that enabled the feature with MSR_KVM_ASYNC_PF_EN then receives a "page not present" #PF whose address is a token, so that it can schedule another task. By default this is done only while the guest runs in user mode, because a fault taken in the guest kernel may come from a context that cannot sleep. For a nested guest, L1 must also have asked for the event as a #PF VM exit. When the event cannot be delivered, or the vCPU faults again on a gfn that is still being fetched, KVM parks the vCPU in an artificial halt (KVM_REQ_APF_HALT), during which it can still take interrupts. Since 5.8 the "page ready" notification arrives as an ordinary interrupt on the vector programmed into MSR_KVM_ASYNC_PF_INT. A Linux guest booted with no-kvmapf does not use the feature. The gfn_to_pfn_cache (kvm_gpc_activate()) lets the kernel keep a long-lived mapping of a guest page and have it invalidated by the same notifier machinery. Its users are the kvm-clock area (vcpu->arch.pv_time) and the Xen emulation's shared-info, vcpu_info, vcpu_time_info, and runstate pages. A user checks the cache with kvm_gpc_check() and remaps it with kvm_gpc_refresh() before each access.

Dirty Logging for Live Migration

Live migration copies guest memory while the guest runs, then recopies whatever the guest wrote meanwhile, until the remaining set is small enough to send during a short pause. KVM's part is to report which pages were written. Chapter 2, §12.8 describes the hardware support. The VMM enables tracking on a memslot by setting KVM_MEM_LOG_DIRTY_PAGES with a KVM_MR_FLAGS_ONLY update. guest_memfd slots cannot be tracked. The architecture's commit hook then prepares the slot. On x86, kvm_mmu_slot_apply_flags() splits huge mappings to 4 KiB when kvm.eager_page_split is set (the default), so that a write dirties 4 KiB rather than 2 MiB. It then write-protects the slot's second-stage entries, or clears their dirty bits when PML is in use. Each later write to a protected page takes a cheap fault that calls mark_page_dirty_in_slot() and restores write access. On Intel hardware with Page-Modification Logging (the kvm_intel.pml parameter, on by default), the CPU instead appends written gfns to a 512-entry buffer. KVM drains it into the dirty log with vmx_flush_pml_buffer() on every VM exit, and the CPU forces a PML_FULL exit when the buffer runs out. PML is not used while an L2 guest runs, and AMD has no equivalent in 7.0, so write-protection does the job there. When logging is switched off, kvm_mmu_recover_huge_pages() (6.13) collapses the split mappings back into huge pages in place instead of zapping them. ARM64 write-protects the slot with kvm_mmu_wp_memory_region(), but splits block mappings eagerly only if the VMM sets KVM_CAP_ARM_EAGER_SPLIT_CHUNK_SIZE (6.5). The default chunk size is 0, and blocks are then split lazily as each write fault maps a single page (force_pte). The VMM collects the result in one of the two ways that Table 28-5 compares.

Pre-copy, the scheme described so far, fails to converge when the guest dirties memory faster than the network can carry it. The alternative is post-copy: the VMM moves the vCPU and device state after one pass over memory, or none, resumes the guest on the destination at once, and fetches each remaining page the first time the guest touches it while the source streams the rest in the background. KVM needs no interface of its own for this, because it reaches guest RAM through the VMM's page tables. The destination VMM registers guest memory with userfaultfd in missing mode (Chapter 9, §7). When a vCPU faults on a page that has not arrived, KVM's hva_to_pfn() lands in handle_userfault(). On x86 the first attempt uses FOLL_NOWAIT and returns at once, which lets a guest that enabled async page faults (§5.3) run another task while the async worker waits for the page. Otherwise the vCPU thread itself sleeps until the VMM's fault thread reads the event and installs the page with UFFDIO_COPY. On x86 that wait is interruptible (6.2): a signal ends it with KVM_PFN_ERR_SIGPENDING, and KVM_RUN returns -EINTR with KVM_EXIT_INTR, so the VMM can still stop a vCPU that is waiting on the network. ARM64 waits killably. Post-copy works only for guest RAM in anonymous, shmem, or hugetlbfs mappings, because a guest_memfd file cannot be registered with userfaultfd in 7.0.

guest_memfd and Confidential Computing

Everything so far assumes that the host may read and write guest memory, and in a classic VM it may. A confidential VM removes that assumption. The CPU, its firmware, or a small trusted hypervisor ensures that the host kernel and the VMM cannot read or modify the guest's private memory and register state, even with full control of the machine. Such a guest cannot be built on memory that the VMM maps into its own address space, so KVM gained a new kind of memory, guest_memfd, whose private pages the host can allocate and account but never map. Whether a guest page is private or shared becomes a per-page attribute that the fault path consults. The protection itself comes from hardware, in AMD SEV-SNP, Intel TDX, and Arm CCA, or, on ARM64 hosts without CCA, from protected KVM's EL2 hypervisor. §6.1 describes guest_memfd itself, §6.2 the per-page private/shared attribute and how a guest converts memory between the two states, §6.3 the three hardware schemes and the KVM code that drives each of them, and §6.4 the pKVM hypervisor and how much of its protected-guest support is upstream in 7.0.12.

guest_memfd: Memory Without a User Mapping

A memslot backed only by userspace_addr cannot hold private memory. The VMM's mapping is the very access path that private memory has to close. Mapping it and promising not to touch it is not enough: an errant write through that mapping, or a kernel copy_from_user() on it, would at best read ciphertext and at worst corrupt the guest. Under SEV-SNP and TDX the hardware's integrity tracking makes such an access fault or poison the page. Since 6.8, KVM's answer has been guest_memfd. The VMM issues KVM_CREATE_GUEST_MEMFD on the VM fd with a size and flags. kvm_gmem_create() in virt/kvm/guest_memfd.c accepts only a non-zero, page-aligned size and the flags that kvm_gmem_get_supported_flags() allows for this VM, and __kvm_gmem_create() returns a file descriptor whose pages belong to it:

Since 6.19 the object comes in two halves. The inode, embedded in a struct gmem_inode, stands for the physical storage and holds the creation flags and a NUMA shared_policy. The file, whose private_data is a struct gmem_file, is one VM's view of that storage: the VM pointer and the memslot bindings. Files hang off the mapping's i_private_list, and kvm_gmem_for_each_file() walks them whenever a range must be invalidated. __kvm_gmem_create() always makes one of each, but the comment above the two structures already describes one guest_memfd shared by several VMs, each with its own view.

The file lives on a private pseudo-filesystem and its page cache holds the guest's folios. The AS_INACCESSIBLE flag on the mapping, described with the other address_space flags in Chapter 15, tells reclaim, compaction, and migration to leave those folios alone, and kvm_gmem_migrate_folio() refuses any migration that still reaches it. The VMM then registers a slot with KVM_MEM_GUEST_MEMFD, passing the fd and an offset. kvm_gmem_bind() checks that the fd is a guest_memfd of the same VM, that the offset is page-aligned and the range lies inside the file, and that no other slot is bound to any part of it, then records the slot in the file's bindings xarray. A slot of this kind still carries userspace_addr for whatever part of the range the guest shares with the host, unless the file was created with GUEST_MEMFD_FLAG_MMAP. Such a slot is marked KVM_MEMSLOT_GMEM_ONLY, and the x86 fault path then takes shared pages from guest_memfd as well.

Pages are allocated on first fault by kvm_gmem_get_pfn(), which zeroes a new folio before marking it up to date so that no stale host data reaches the guest, or in advance with fallocate(). The size is fixed at creation: kvm_gmem_setattr() refuses to truncate the file, and kvm_gmem_fallocate() requires FALLOC_FL_KEEP_SIZE, a page-aligned range inside the file, and no other mode bit except FALLOC_FL_PUNCH_HOLE, which gives pages back. Folios are order-0 in 7.0.12 (huge pages are a TODO in the source), so every second-stage mapping of guest_memfd memory is 4 KiB. A punch runs under the mapping's invalidate lock. kvm_gmem_invalidate_begin() walks each file's bindings, starts an MMU invalidation, and zaps the range's second-stage mappings (only the private ones, unless the file was created shared) before truncate_inode_pages_range() frees the folios. This is the counterpart of the MMU-notifier path in §5.3, needed because no host mm maps these pages.

Two other paths complete the picture. A hardware memory error in a guest_memfd folio reaches kvm_gmem_error_folio(), which zaps the guest's mappings but leaves the page in the file and returns MF_DELAYED. The next kvm_gmem_get_pfn() on that page fails with -EHWPOISON, which on x86 makes KVM_RUN fail with a memory-fault exit filled in, so the VMM decides what to do. Closing the file runs kvm_gmem_release(), which takes slots_lock, clears the file pointer in every bound memslot, zaps everything the file mapped, and drops its VM reference; the folios themselves live as long as the inode. Because the file pins the VM and not the other way round, kvm_gmem_bind() drops its file reference even on success, and kvm_gmem_get_file() uses get_file_active() so that a memslot never revives a file that is being released.

Two arch hooks let confidential-computing code run at allocation and free time. kvm_arch_gmem_prepare() is called when a folio is first handed to the guest. On SEV-SNP that is sev_gmem_prepare(), which looks the page up in the hardware's Reverse Map Table and, unless it is already assigned, assigns it to the guest with rmp_make_private(). kvm_arch_gmem_invalidate() (sev_gmem_invalidate()), called from the mapping's free_folio operation, returns the page to the host with rmp_make_shared(), first splitting a 2 MB RMP entry with PSMASH if needed, and flushes the page's cache lines before the folio is freed. Initial guest images are loaded through kvm_gmem_populate(). It runs under slots_lock and, for each page, requires the gfn to be private already (§6.2), pins the VMM's source page, and calls a vendor callback with the source page and the destination pfn. SNP's sev_gmem_post_populate() copies the data, makes the page private in the RMP, and has the Secure Processor encrypt and measure it in place with SNP_LAUNCH_UPDATE. TDX's tdx_gmem_post_populate() maps the page through the mirror EPT, which ends in TDH.MEM.PAGE.ADD (§6.3). snp_launch_update() and tdx_vcpu_init_mem_region() are the two callers.

guest_memfd is not only for confidential guests. Since 6.18 the GUEST_MEMFD_FLAG_MMAP flag lets the VMM mmap() the fd, and GUEST_MEMFD_FLAG_INIT_SHARED makes its contents shared from the start. Only VM types without private memory accept the second flag. kvm_gmem_mmap() requires GUEST_MEMFD_FLAG_MMAP and a MAP_SHARED mapping, and kvm_gmem_fault_user_mapping() raises SIGBUS rather than map a page of a file that was not created shared. ARM64 selects KVM_GUEST_MEMFD on these terms, with a stage-2 fault path of its own (gmem_abort(), §5.2). This gives a VMM guest memory that the rest of the host never maps by accident, with a NUMA policy that mbind() on the mapping stores in the file (kvm_gmem_set_policy()). Discovery goes through KVM_CAP_GUEST_MEMFD and KVM_CAP_GUEST_MEMFD_FLAGS.

Private and Shared: Memory Attributes and Conversion

A confidential guest still needs shared memory for its virtio rings, its bounce buffers, and the hypervisor-communication pages. It decides at run time which guest-physical pages are which. KVM records the decision per gfn in kvm->mem_attr_array, an xarray set by KVM_SET_MEMORY_ATTRIBUTES (KVM_CAP_MEMORY_ATTRIBUTES, 6.8). The only attribute so far is KVM_MEMORY_ATTRIBUTE_PRIVATE, and kvm_supported_mem_attributes() offers it only on VM types with private memory. In 7.0.12 those are the x86 SEV-SNP, TDX, and software-protected types; ARM64 has none. The ioctl takes a page-aligned, non-empty range and a flags field that must be zero. The handler, kvm_vm_set_mem_attributes(), returns at once if the range already has the requested attributes. Otherwise it first reserves an xarray entry for every gfn, so that the update cannot fail half-way for lack of memory, and then follows the invalidation protocol of §5.3. kvm_pre_set_memory_attributes() bumps the invalidation sequence and zaps existing second-stage mappings for the range, the new values are stored, and kvm_arch_post_set_memory_attributes() runs as the invalidation ends. On x86 the two arch hooks also keep, for each huge-page size, a record of which large frames now mix private and shared pages, so that the fault path never installs a 2 MB or 1 GB mapping that straddles the two states. Each fault then has two independent opinions about whether a gfn is private, and Figure 28-6 shows how they are reconciled.

  • The access itself. On SEV-SNP, the NPF error code carries PFERR_GUEST_ENC_MASK when the guest's own page tables mark the access encrypted (the C-bit). On TDX, a gfn is shared if the GPA's shared bit is set, as tested by vt_is_tdx_private_gpa(). Either way the exit handler turns the answer into the synthetic PFERR_PRIVATE_ACCESS bit and fault->is_private.
  • The VMM's record, read with kvm_mem_is_private().

The check sits in kvm_mmu_faultin_pfn(). It reads the invalidation sequence first, so that a conversion racing with the fault is caught as a stale fault. On a mismatch, kvm_mmu_prepare_memory_fault_exit() fills run->memory_fault with the gpa, the size, and KVM_MEMORY_EXIT_FLAG_PRIVATE if the access was private, and KVM_RUN returns -EFAULT with exit_reason == KVM_EXIT_MEMORY_FAULT. This is an implicit conversion: the guest touched memory in the other state. Explicit conversions arrive first as hypercalls. An SNP guest's Page State Change request (snp_begin_psc()) and a TDX guest's TDG.VP.VMCALL<MapGPA> (tdx_map_gpa()) are both turned into KVM_EXIT_HYPERCALL with nr == KVM_HC_MAP_GPA_RANGE, provided the VMM opted in through KVM_CAP_EXIT_HYPERCALL. In both cases policy stays in user space: the VMM updates the attributes, may discard the old copy (punching a hole in the guest_memfd or madvise()-ing the shared range), and re-enters the guest. The VM type KVM_X86_SW_PROTECTED_VM exercises this machinery without any hardware protection, for development and testing; it is built only with CONFIG_KVM_SW_PROTECTED_VM, which depends on EXPERT. With no hardware signal for the first opinion, kvm_mmu_page_fault() derives PFERR_PRIVATE_ACCESS for such a VM from the attributes themselves, so the two opinions agree by construction. KVM_PRE_FAULT_MEMORY (§5.2) does the same on every VM type with private memory.

SEV-SNP, TDX, and Arm CCA

The three hardware architectures share a goal and differ in where the trusted code sits. Table 28-6 compares them with pKVM, the software scheme described in §6.4. All three hardware schemes put each confidential VM in its own memory encryption key domain, prevent the host from reading or replaying the guest's register state, and provide attestation, a signed report that the guest can present to a remote party to prove what was loaded. Inside the guest, the sev-guest, tdx-guest, and arm-cca-guest drivers all deliver that report through the configfs TSM_REPORTS interface (Chapter 27, §1.1). KVM's job is to drive the launch protocol, map pages in the right state, and run the guest through whatever entry instruction the scheme requires.

On AMD, plain SEV encrypts memory with a key selected by the guest's ASID. SEV-ES (Encrypted State) also encrypts the register save area (VMSA). The hypervisor can no longer read guest registers on an exit, so the guest's #VC handler copies exactly the registers an exit needs into a shared GHCB page and executes VMGEXIT. KVM handles that in sev_handle_vmgexit(). SEV-SNP (Secure Nested Paging) adds the Reverse Map Table. It is a per-host-page record of the owner and guest address, maintained by the host with rmp_make_private() and rmp_make_shared() (arch/x86/virt/svm/sev.c) and checked by hardware on every access. The RMP stops the host from remapping or replaying guest pages. The launch commands, from snp_launch_start() to snp_launch_finish(), go through sev_mem_enc_ioctl() to the Secure Processor driver. SEV ASIDs are a scarce resource, charged to the misc cgroup controller as described in Chapter 25, §6.3.

An SNP launch has three steps. KVM_SEV_SNP_LAUNCH_START (snp_launch_start()) creates the guest context in the firmware with the guest policy; the policy bits the firmware supports can be read from /dev/kvm as the KVM_X86_SNP_POLICY_BITS attribute (6.19). KVM_SEV_SNP_LAUNCH_UPDATE feeds pages through kvm_gmem_populate() as §6.1 described, each with a type: normal, zero, unmeasured, secrets, or CPUID. If the firmware rejects a CPUID page, it writes the values it would accept into the page, and sev_gmem_post_populate() copies them back to the VMM's buffer so that the VMM can see which leaves failed. KVM_SEV_SNP_LAUNCH_FINISH (snp_launch_finish()) encrypts and measures every vCPU's VMSA with snp_launch_update_vmsa(), then passes the optional identity block and 32 bytes of VMM-chosen host data to the firmware, which completes the launch measurement.

At run time the guest talks to KVM through the GHCB protocol, and sev_handle_vmgexit() dispatches on the exit code. Besides MMIO and the Page State Change requests of §6.2 (snp_begin_psc()), it handles AP creation (sev_snp_ap_creation()), with which the guest supplies or withdraws the VMSA that a vCPU runs from, the AP halt loop, termination requests, and guest requests. A guest request is a message encrypted between the guest and the Secure Processor, usually asking for an attestation report. snp_handle_guest_req() forwards it with SEV_CMD_SNP_GUEST_REQUEST without being able to read it. The extended form also asks for the certificate chain that verifies the report's signature. Since 7.0, a VMM that enabled KVM_SEV_SNP_ENABLE_REQ_CERTS gets a KVM_EXIT_SNP_REQ_CERTS exit with the gpa and size of the guest's buffer and writes the certificates itself. Otherwise snp_handle_ext_guest_req() returns an empty table.

Two 6.18 additions narrow what the host can learn. With ciphertext hiding (the ciphertext_hiding_asids module parameter), the firmware stops the host from reading even the ciphertext of SNP guest memory, which closes a side channel. The price is that the ASIDs given to SNP are taken out of the range that SEV-ES guests can use. With Secure TSC, the guest's TSC frequency is fixed at SNP_LAUNCH_START, and KVM marks the guest TSC protected (guest_tsc_protected), so it no longer changes the offset or frequency the guest sees. Separately, KVM_CAP_VM_MOVE_ENC_CONTEXT_FROM (5.16) moves the encryption context of a running SEV guest to a new VM on the same host, which lets a VMM be upgraded without restarting the guest.

Intel TDX goes further. The guest, a trust domain, is not run by KVM directly but by the TDX module, Intel-signed software that executes in the CPU's SEAM mode. KVM asks it to act through SEAMCALL wrappers in arch/x86/virt/vmx/tdx/tdx.c: tdh_mng_create() to create a TD with a private host key ID (HKID), tdh_mem_page_add() during launch, tdh_mem_page_aug() to add a private page at run time, and tdh_vp_enter() to run a vCPU. The last is what tdx_vcpu_run() calls in place of VMRESUME. Because only the module may write the secure EPT, KVM's TDP MMU keeps a mirror of it (§5.2) and forwards each change through the set_external_spte and link_external_spt hooks to tdx_sept_set_private_spte() and tdx_sept_link_private_spt().

A TD's launch has the same shape as an SNP launch. KVM_TDX_CAPABILITIES reports which attributes and CPUID bits the module lets the VMM configure. KVM_TDX_INIT_VM allocates a key ID, charges it to the misc cgroup (MISC_CG_RES_TDX), creates the TD with tdh_mng_create(), and programs the key into every package's memory controller with tdh_mng_key_config(). KVM_TDX_INIT_VCPU creates each vCPU, and KVM_TDX_GET_CPUID (6.16) reads back the CPUID values the module will actually present. KVM_TDX_INIT_MEM_REGION loads the initial image. tdx_vcpu_init_mem_region() calls kvm_gmem_populate() one page at a time, and the callback maps each page through the mirror with kvm_tdp_mmu_map_private_pfn() (6.19). Because the TD is not yet runnable, the set_external_spte hook turns that into TDH.MEM.PAGE.ADD, which copies the source page into the encrypted destination. With the KVM_TDX_MEASURE_MEMORY_REGION flag, TDH.MR.EXTEND also adds the page to the TD's build measurement. KVM_TDX_FINALIZE_VM (tdh_mr_finalize()) seals the measurement, and only then may vCPUs run or KVM_PRE_FAULT_MEMORY be used. From then on a private fault becomes TDH.MEM.PAGE.AUG, which adds a page that the guest must accept with TDG.MEM.PAGE.ACCEPT before using it.

Taking a private page away is harder, because the module must be sure that no vCPU still caches a translation for it. tdx_sept_remove_private_spte() blocks the range (TDH.MEM.RANGE.BLOCK), advances the TD's TLB epoch (TDH.MEM.TRACK) and kicks every vCPU out of the guest so that each one flushes on re-entry, removes the page (TDH.MEM.PAGE.REMOVE), and writes back and invalidates its cache lines under the TD's key with TDH.PHYMEM.PAGE.WBINVD before clearing it for reuse by the host. A SEAMCALL in this sequence can fail as busy if a vCPU holds the same lock inside the module, so KVM wraps it in tdh_do_no_vcpus(), which retries once with every vCPU held outside the guest. All of this works on 4 KiB pages; huge private pages are still a TODO in tdx.c.

The guest talks to the host with TDG.VP.VMCALL. A call whose leaf number is a VMX exit reason (CPUID, HLT, port I/O, MSR access, or an EPT violation, which stands for MMIO) is recast as that exit by tdcall_to_vmx_exit_reason() and handled by the ordinary code. handle_tdvmcall() takes the TDX-specific leaves. MapGPA is the conversion request of §6.2, and ReportFatalError becomes a KVM_EXIT_SYSTEM_EVENT of type KVM_SYSTEM_EVENT_TDX_FATAL. Three reach the VMM as KVM_EXIT_TDX: GetQuote, which asks the VMM to turn a TD report in a shared buffer into a signed attestation quote, SetupEventNotifyInterrupt (6.16), and the user-space part of GetTdVmCallInfo. Every other leaf is refused with SUBFUNC_UNSUPPORTED.

Arm's Confidential Compute Architecture defines a fourth security state, the Realm world. Guests there are managed by a Realm Management Monitor that the normal-world hypervisor drives through the Realm Management Interface. In 7.0.12 only the guest half is upstream: a Linux kernel running as a realm detects it in arch/arm64/kernel/rsi.c (since 6.13) and uses the Realm Services Interface to share and unshare its memory. arm64_rsi_init() reads the realm configuration and sets prot_ns_shared to the top IPA bit, which then marks every shared mapping. set_memory_decrypted() asks the RMM to set the range's RIPAS to EMPTY (rsi_set_memory_range_shared()), and the arm-cca-guest driver collects attestation tokens with the RSI attestation calls. KVM cannot yet create realms. On ARM64 hosts today the nearest substitute is pKVM, which upstream protects the hypervisor from the host but not yet the guests (§6.4).

None of the three yet lets a confidential guest give a physical device direct access to its private memory. §8.3 describes how far the PCI TSM core (6.19) has come toward that, and why a device assigned with VFIO still reaches a confidential guest's data only through shared bounce buffers.

Protected KVM: Deprivileging the Host

pKVM takes the nVHE layout of §4.1 and turns it around. Instead of trusting the host and serving it, the EL2 code distrusts it. At boot, with kvm-arm.mode=protected, the host carves out memory for the hypervisor and calls __pkvm_init. EL2 then builds its own stage-1 tables and a stage-2 table for the host (kvm_host_prepare_stage2()), and finalize_pkvm() issues __pkvm_prot_finalize on every CPU to switch that stage-2 on. From then on, every host access goes through a translation that only EL2 can change. A host fault on memory not yet mapped reaches handle_host_mem_abort() at EL2, which maps it on demand (host_stage2_idmap()) as long as the host still owns the page.

Ownership is tracked per page in a small state machine in arch/arm64/kvm/hyp/nvhe/mem_protect.c. The host can share a page with the hypervisor (__pkvm_host_share_hyp()), donate pages to it (__pkvm_host_donate_hyp(), used for the hypervisor's copies of VM and vCPU state created by __pkvm_init_vm() and __pkvm_init_vcpu()), or share a page with a guest (__pkvm_host_share_guest(), reached from KVM_PGT_FN() in §5.2). EL2 also intercepts the host's SMCs. kvm_host_psci_handler() relays PSCI power calls so that a CPU coming online re-enters through the hypervisor, and kvm_host_ffa_handler() mediates FF-A memory sharing with the secure world, so the host cannot hand protected memory to TrustZone. All guest entries go through the copy-in, copy-out flush_hyp_vcpu() and sync_hyp_vcpu() pair described in §4.2.

EL2 keeps its own table of VMs. Since 6.18, pkvm_init_host_vm() reserves a handle in it with __pkvm_reserve_vm as soon as the VM is created. The hypervisor's copy of the VM and of each vCPU is built later, on the first KVM_RUN, once the VM's features can no longer change: pkvm_create_hyp_vm() donates memory and calls __pkvm_init_vm, which copies the features the host enabled into EL2's structure, and __pkvm_init_vcpu does the same for each vCPU. __pkvm_vcpu_load and __pkvm_vcpu_put attach the hypervisor's vCPU to a physical CPU when the host loads the vCPU there and detach it when the host puts it, and __pkvm_teardown_vm hands the donated pages back to the host when the VM is destroyed.

A guest that is itself confidential needs more: its memory must be donated rather than shared, so that the host's stage-2 no longer maps it. Part of that support is upstream. EL2 has a separate handler table, pvm_exit_handlers[], that restricts the system registers and features a protected guest may see, and the hypervisor's VM structure copies an is_protected flag from the host's (hyp/nvhe/pkvm.c). In 7.0.12, however, nothing on the host sets that flag, and there is no hypercall to donate a page to a guest. The guest half of the protocol is already upstream: drivers/virt/coco/pkvm-guest/arm-pkvm-guest.c (6.12) issues MEM_SHARE and MEM_UNSHARE hypercalls from set_memory_decrypted() and set_memory_encrypted() and registers MMIO regions with MMIO_GUARD, but the mainline EL2 code implements none of those calls. Mainline pKVM therefore protects the hypervisor, and through it the stage-2 tables of every guest, against a compromised host kernel. Guests whose memory the host cannot read are the remaining step.

Interrupts, Timers, and Performance Counters

A guest spends much of its life waiting for interrupts and taking them, so their cost shapes how a VM performs more than almost anything else. A virtual interrupt has three costs: the exit that the guest's access to its interrupt controller would cause, the hop through the VMM when a device backend wants to raise one, and the wake-up of a vCPU thread that is asleep in HLT or WFI. KVM attacks all three. It emulates the interrupt controller in the kernel and lets hardware virtualize most of it. It routes interrupts from eventfds without involving user space. And it keeps timers and idle vCPUs cheap. The performance-monitoring unit raises the same questions on a smaller scale. A guest that profiles itself needs counters and an overflow interrupt, and KVM either emulates them on top of host perf events or hands the hardware to the guest while it runs. The section follows that order. §7.1 describes the in-kernel interrupt controllers, the APIC family on x86 and the GIC on ARM64, and the hardware that virtualizes the part the guest touches most. §7.2 follows an interrupt that reaches a running guest without an exit, through posted interrupts and GICv4, and §7.3 the eventfd shortcuts that take the VMM off the interrupt and notification paths. §7.4 covers the guest's timers and clock, steal time, and halt polling, and §7.5 the two designs of a virtual PMU.

Virtual Interrupt Controllers

On x86 the guest expects a local APIC per CPU, an I/O APIC, and, for legacy software, a pair of 8259A PICs (Chapter 4, §2.2). All three exist in the kernel: arch/x86/kvm/lapic.c, ioapic.c, and i8259.c. KVM_CREATE_IRQCHIP instantiates the full set. A VMM that enables KVM_CAP_SPLIT_IRQCHIP (4.4) gets only the local APICs in the kernel and emulates the I/O APIC and PIC itself. The local APIC is the one that matters for speed, because the guest touches it on every interrupt and every IPI. Interrupt sources are named by GSI. A routing table installed with KVM_SET_GSI_ROUTING maps each GSI to an irqchip pin or to an MSI address and data pair. KVM_IRQ_LINE asserts a pin, and KVM_SIGNAL_MSI (3.5) injects a message directly. Through the I/O APIC or an MSI route, both reach kvm_irq_delivery_to_apic(), which finds the destination vCPUs and calls __apic_accept_irq().

How much of this lives in the kernel is decided when KVM is built and when the VM is created. CONFIG_KVM_IOAPIC (6.17, default y) builds the I/O APIC, PIC, and PIT models. Without it, KVM_CREATE_IRQCHIP and KVM_CREATE_PIT2 do not exist, and the split mode is the only one left. A VMM enables split mode before it creates any vCPU, and the capability's argument reserves GSI routes for the pins of its user-space I/O APIC. KVM must still know which guest vectors come from level-triggered pins, because their EOIs have to reach the device model so that it can lower or re-raise the line. kvm_scan_ioapic_routes() collects those vectors from the reserved routes, and the guest's EOI for one of them ends KVM_RUN with KVM_EXIT_IOAPIC_EOI. x2APIC behaviour is negotiated with KVM_CAP_X2APIC_API (4.8). KVM_X2APIC_API_USE_32BIT_IDS lets routes and MSIs name APIC IDs above 255, and KVM_X2APIC_API_DISABLE_BROADCAST_QUIRK stops KVM from treating destination 0xff as a broadcast, which logical mode and VMs with more than 255 vCPUs need. Linux 7.0 adds two flags for the guest-visible Suppress EOI Broadcast feature. KVM_X2APIC_ENABLE_SUPPRESS_EOI_BROADCAST, allowed only with a split irqchip, makes KVM advertise the feature and honour it, and KVM_X2APIC_DISABLE_SUPPRESS_EOI_BROADCAST hides it. A VMM that sets neither keeps the old quirk, under which a split irqchip advertises the feature but suppresses nothing.

Without hardware help, accepting an interrupt sets a bit in the software IRR (Interrupt Request Register) of the virtual APIC, kicks the vCPU (§3.2), and lets vcpu_enter_guest() inject the highest-priority vector through the VM-entry interruption-information field. Every guest access to the APIC page, every EOI, and every IPI then costs an exit. APICv (Intel, enable_apicv, 3.9) removes most of these. The CPU reads and writes a virtual-APIC page directly, evaluates and delivers pending vectors itself, and completes EOIs without exiting. AMD's equivalent, AVIC (arch/x86/kvm/svm/avic.c, 4.7), uses a backing page per vCPU and a table of physical APIC IDs. Since 6.18 its avic parameter defaults to "auto", which turns AVIC on for Zen 4 and later CPUs that have x2AVIC. Intel's IPI virtualization (enable_ipiv, 6.0) goes further: a guest's ICR write sends a posted IPI to the target vCPU with no exit at all. AVIC does the same for running targets, and since 6.18 kvm_amd has an enable_ipiv parameter too, forced off on Zen 1 and Zen 2 because of an erratum that loses wake-ups. Some configurations defeat this hardware. Both APICv and AVIC give way when they are disabled or the VM has no in-kernel local APIC yet, when a debugger blocks the vCPU's interrupts (KVM_GUESTDBG_BLOCKIRQ), when a Hyper-V guest uses AutoEOI, and once the guest changes an APIC ID or the APIC base or two vCPUs share an ID. AVIC, which virtualizes less, has more reasons: a vCPU that runs a nested guest or waits for an interrupt window, an in-kernel PIT in reinject mode (which must see every EOI), an SEV guest, aliased logical IDs, and APIC IDs beyond its table. KVM records each such reason with kvm_set_apicv_inhibit() (APICV_INHIBIT_REASON_*). When the set of reasons changes, it raises KVM_REQ_APICV_UPDATE on every vCPU, so that the next entry switches between the hardware path and full emulation.

On ARM64 the guest expects a GICv3 (Chapter 4, §2.3): a distributor for shared interrupts (SPIs), one redistributor per CPU for private interrupts (SGIs and PPIs) and LPIs, and an optional ITS that translates MSIs into LPIs. The memory-mapped parts are emulated in arch/arm64/kvm/vgic/ (vgic-mmio-v3.c, vgic-its.c) as devices on KVM_MMIO_BUS. The VMM creates them with KVM_CREATE_DEVICE and the types KVM_DEV_TYPE_ARM_VGIC_V3 and KVM_DEV_TYPE_ARM_VGIC_ITS (4.8). KVM_CREATE_IRQCHIP survives only to create a GICv2. The CPU interface, the part the guest uses to acknowledge and complete interrupts, is virtualized by the GIC hardware itself. A hypervisor loads up to 16 list registers (ICH_LR<n>_EL2; the count comes from ICH_VTR_EL2), each describing one virtual interrupt and its state. The guest's system-register accesses to its CPU interface are then served from those registers without trapping.

Each interrupt is a struct vgic_irq. Raising one with kvm_vgic_inject_irq() puts it on the target vCPU's ap_list of active-or-pending interrupts (vgic_queue_irq_unlock()), makes KVM_REQ_IRQ_PENDING, and kicks the vCPU. On the way into the guest, kvm_vgic_flush_hwstate() calls vgic_flush_lr_state(), which first summarizes the list (summarize_ap_list()). Only if some entries will not fit does it sort them, pending before active and then by priority. It writes the first nr_lr into the LRs. On the way out, kvm_vgic_sync_hwstate() reads the LRs back and drops interrupts the guest has completed (§4.2).

Overflow is the hard case, because the guest must still be able to complete interrupts that sit in no LR, and Linux 6.19 rewrote this logic. vgic_v3_configure_hcr() arms maintenance interrupts that force an exit when the picture changes. NPIE fires once no pending interrupt is left in the LRs, so that KVM can load the next batch. LRENPIE reports the deactivation of an active interrupt that has no LR, and UIE fires when the LRs are nearly empty. With the combined EOI mode the hardware's count of such deactivations (EOIcount) tells KVM how far down the list to retire interrupts. When the guest splits priority drop from deactivation (EOImode=1), deactivations can come in any order, and an SPI can even be deactivated from another CPU, so KVM traps ICV_DIR_EL1 while that could matter. The rest of the vGIC's life is driven by the VMM. It places the distributor and redistributors through device attributes and finishes with KVM_DEV_ARM_VGIC_CTRL_INIT. The first KVM_RUN then maps the resources (kvm_vgic_map_resources()). LPIs are looked up in a per-VM xarray (lpi_xa, 6.9), and each ITS caches MSI translations in an xarray of its own (translation_cache, 6.10). For migration, KVM_DEV_ARM_ITS_SAVE_TABLES and KVM_DEV_ARM_VGIC_SAVE_PENDING_TABLES write the ITS tables and the LPI pending bits into guest memory, where they travel with the guest's RAM, and KVM_DEV_ARM_ITS_RESTORE_TABLES reads them back. A guest hypervisor under nested virtualization programs list registers of its own. KVM folds them into the real ones through a per-CPU shadow interface (vgic-v3-nested.c, 6.15) and raises the guest hypervisor's maintenance interrupt on the PPI the VMM chose with KVM_DEV_ARM_VGIC_GRP_MAINT_IRQ. A host on a GICv5 can also run GICv3 guests through vgic-v5.c (6.17). In 7.0.12 that compatibility mode is all it offers: there are no native GICv5 guests and no GICv4 direct injection on such a host.

Posted Interrupts and GICv4

An interrupt for a running vCPU still needs a way to reach the guest without an exit. On Intel this is the posted interrupt (3.10). Each vCPU has a struct pi_desc: a 256-bit Posted-Interrupt Request bitmap (PIR), an "outstanding notification" bit (ON), and the notification vector and destination. The sender sets the vector's PIR bit and ON, then sends the physical CPU an ordinary IPI on POSTED_INTR_VECTOR. A CPU in guest mode recognizes that vector, merges the PIR into the virtual IRR, and delivers the interrupt to the guest, all without leaving the guest: 

/* arch/x86/kvm/vmx/common.h (comments abridged) */
static inline void __vmx_deliver_posted_interrupt(struct kvm_vcpu *vcpu,
						  struct pi_desc *pi_desc, int vector)
{
	if (pi_test_and_set_pir(vector, pi_desc))
		return;

	/* If a previous notification has sent the IPI, nothing to do.  */
	if (pi_test_and_set_on(pi_desc))
		return;

	/* pairs with the barrier after setting vcpu->mode in vcpu_enter_guest() */
	kvm_vcpu_trigger_posted_interrupt(vcpu, POSTED_INTR_VECTOR);
}

kvm_vcpu_trigger_posted_interrupt() sends the IPI only if the target is IN_GUEST_MODE. Otherwise it calls kvm_vcpu_wake_up(), and the next entry copies the PIR into the IRR (vmx_sync_pir_to_irr()). The memory barrier in pi_test_and_set_on() pairs with the one after vcpu_enter_guest() sets the mode, which is the same race-free protocol that requests use. A TDX guest has no other path: tdx_deliver_interrupt() calls the same function, because the TDX module allows no APIC emulation by the host.

The IOMMU can post interrupts too. With VT-d posted-interrupt support, the interrupt remapping entry of an assigned device's MSI is rewritten to point at the vCPU's pi_desc (vmx_pi_update_irte()). The device's interrupt then sets the PIR bit and sends the notification itself, and no host interrupt handler runs. The device and the vCPU can each be anywhere. When the vCPU is scheduled onto another CPU, vmx_vcpu_pi_load() updates the destination. When it blocks, pi_enable_wakeup_handler() switches the notification vector to POSTED_INTR_WAKEUP_VECTOR and queues the vCPU on that CPU's wakeup_vcpus_on_cpu list, so that pi_wakeup_handler() can wake the thread that should handle the interrupt. AMD's AVIC does the same with a doorbell MSR write (avic_ring_doorbell()) for running vCPUs and an IOMMU "GA log" entry (avic_ga_log_notifier()) for vCPUs that are not running.

Not every device interrupt can be posted. kvm_pi_update_irte() posts only fixed and lowest-priority interrupts (kvm_irq_is_postable()) whose destination resolves to exactly one vCPU (kvm_intr_is_single_vcpu()), because neither vendor's IOMMU can post a multicast. Anything else stays in remapped mode: the interrupt reaches the host, and KVM synthesizes the guest's interrupt through the irqfd. The guest can retarget its MSIs at any time, so every routing change on an irqfd with a producer calls kvm_arch_update_irqfd_routing() to rewrite the IRTE. Blocking must also cope with a device that arrives late. Since 6.17, when the first bypass IRQ is attached to a VM, vmx_pi_start_bypass() kicks every vCPU with KVM_REQ_UNBLOCK, so that a vCPU that blocked earlier without the wakeup vector arms it. A vCPU that is preempted rather than blocked needs no wake-up, because its thread is still runnable. For it vmx_vcpu_pi_put() sets the descriptor's Suppress Notification bit (SN) instead, and posted interrupts collect in the PIR until the vCPU is loaded again.

The pairing between a VFIO device's interrupt and a VM's irqfd (§7.3) is set up by the small irqbypass manager (virt/lib/irqbypass.c, 4.4). VFIO registers each MSI vector as a producer keyed by its eventfd, and KVM registers each irqfd as a consumer keyed the same way. When the two match, kvm_arch_irq_bypass_add_producer() runs. On x86 it reprograms the IOMMU through the pi_update_irte hook (vmx_pi_update_irte() or avic_pi_update_irte()). Both reach the IOMMU driver through irq_set_vcpu_affinity() on the host IRQ, passing a vendor structure that names the target: the pi_desc and vector for VT-d, the vCPU's backing page for AMD. Since 6.17 the manager keeps producers and consumers in two global xarrays indexed by the eventfd_ctx pointer, so each eventfd pairs at most one producer with one consumer. Around each connection and disconnection it calls the stop and start hooks of both sides.

On ARM64, the same hook calls kvm_vgic_v4_set_forwarding(), which uses GICv4 to map the device's LPI to a virtual LPI (its_map_vlpi()). With GICv4 (vgic-v4.c, 4.15), each vCPU is a vPE with a virtual LPI pending table in memory. When the vCPU is loaded, vgic_v4_load() makes its vPE resident on the local redistributor (its_make_vpe_resident()), and the GIC delivers vLPIs straight to the guest. A vLPI for a vPE that is not resident sets the bit in its pending table and fires a per-vCPU doorbell interrupt instead, whose handler (vgic_v4_doorbell_handler()) wakes the vCPU. GICv4.1 also lets the guest's SGIs (its IPIs) take the direct path (vgic_v4_configure_vsgis()). Unlike APICv, GICv4 is off by default and needs kvm-arm.vgic_v4_enable=1. Only MSI routes can be forwarded. ARM64 uses the consumer's stop and start hooks to halt every vCPU of the VM while a vLPI is mapped or unmapped (kvm_arm_halt_guest()). A routing change cannot remap the vLPI, because resolving the new translation needs the ITS mutex and the update runs under a spinlock. kvm_arch_update_irqfd_routing() therefore unmaps it, and the interrupt falls back to software injection through the ITS.

irqfd and ioeventfd

The remaining cost is the round trip through the VMM. A device model that signals "buffer used" by calling KVM_IRQ_LINE needs a system call per interrupt, and a guest notification that becomes KVM_EXIT_MMIO costs a return to user space, a wake-up of the device thread, and a fresh KVM_RUN. KVM replaces both paths with eventfds (Chapter 19, §6.1), in virt/kvm/eventfd.c (2.6.32). Figure 28-7 shows both directions.

KVM_IRQFD binds an eventfd to a GSI. KVM hooks a wait-queue entry into the eventfd whose callback, irqfd_wakeup(), runs inside eventfd_signal(), in the context of whatever signalled it: a vhost worker, a VFIO interrupt handler, or a VMM thread's write(). The callback reads the current routing entry under a seqcount (routing can change at any time with KVM_SET_GSI_ROUTING) and tries kvm_arch_set_irq_inatomic(). On x86 that handles MSI routes through kvm_irq_delivery_to_apic_fast(), which ends in a posted interrupt or an IRR update and kick. On ARM64 it handles MSIs whose translation is already in the ITS cache (vgic_its_inject_cached_translation()), as well as SPIs. Anything that might sleep, such as an ITS table walk in guest memory or a level-triggered I/O APIC pin, returns -EWOULDBLOCK and is deferred to irqfd_inject() on a workqueue.

Since 6.17 kvm_irqfd_register() adds the entry with add_wait_queue_priority_exclusive(). A priority entry goes at the head of the eventfd's wait queue, and an exclusive one ends the wake-up there, so KVM, and only KVM, is woken when the eventfd is signalled. The call fails with -EBUSY if the queue already has a priority waiter, so an eventfd can back at most one irqfd, in any VM. irqfd_wakeup() consumes the eventfd's count itself (eventfd_ctx_do_read()), so the counter never builds up. If the eventfd is already signalled when the irqfd is assigned, the interrupt is injected at once. When the eventfd is closed, EPOLLHUP detaches the irqfd and queues its shutdown on irqfd_cleanup_wq. On x86 the atomic path covers more than MSIs: kvm_arch_set_irq_inatomic() also delivers Hyper-V SynIC routes (KVM_IRQ_ROUTING_HV_SINT) and Xen event channels (KVM_IRQ_ROUTING_XEN_EVTCHN), so the paravirtual interrupts of Hyper-V and Xen guests take the same shortcut.

Level-triggered interrupts need an extra step, because the line must be lowered when the guest acknowledges it. With KVM_IRQFD_FLAG_RESAMPLE (3.7) the VMM passes a second eventfd. When the guest EOIs the interrupt, an ack notifier (irqfd_resampler_ack()) lowers the line and signals that eventfd, so the device model can check whether to raise it again. All the irqfds that resample one GSI share a resampler, with one ack notifier and one IRQ source ID: an EOI lowers the line once and then signals every resample eventfd on the list (irqfd_resampler_notify()). Interrupts thus never pass through the VMM, and with irqbypass and posted interrupts or GICv4 they need not pass through the host's interrupt handlers either.

KVM_IOEVENTFD works in the other direction. It registers a struct _ioeventfd device on KVM_MMIO_BUS, or on KVM_PIO_BUS with KVM_IOEVENTFD_FLAG_PIO, for an address, a length and, optionally, a value (KVM_IOEVENTFD_FLAG_DATAMATCH). When an exit handler offers a guest write to kvm_io_bus_write(), ioeventfd_write() checks the range and value, calls eventfd_signal(), and the vCPU re-enters the guest without the VMM ever seeing the access. A zero-length ioeventfd matches any write to the address and is also placed on KVM_FAST_MMIO_BUS. On x86 it can then be completed from the EPT-misconfiguration exit without decoding the instruction (§5.2). This is the mechanism behind every virtio queue notification under KVM (§8.2).

Timers, Steal Time, and Halt Polling

A guest's timer is one more interrupt source, and an important one. On x86 the local APIC timer is emulated in lapic.c. In the basic scheme a host hrtimer (apic_timer_fn()) fires at the guest's deadline and injects the timer vector. When VMX offers a preemption timer (parameter preemption_timer), KVM instead programs the deadline into the VMCS (start_hv_timer() → vmx_set_hv_timer()). Expiry is then a PREEMPTION_TIMER exit handled on the fastpath (handle_fastpath_preemption_timer()), with no host interrupt at all. That timer counts only while the CPU is in guest mode, so vcpu_block() switches back to the hrtimer (kvm_lapic_switch_to_sw_timer()) before a halted vCPU sleeps. lapic_timer_advance (a boolean parameter since 6.10, on by default) fires the timer slightly early to hide the entry latency, and adjust_lapic_timer_advance() tunes each vCPU's lead from how early or late its expiries actually land. Time itself comes from kvm-clock (Chapter 6, §2.7). On KVM_REQ_CLOCK_UPDATE, kvm_guest_time_update() writes a pvclock_vcpu_time_info record that lets the guest convert its TSC to nanoseconds. When the host TSC is stable, the "master clock" (use_master_clock) gives every vCPU the same reference point, so the guest's clock stays monotonic across vCPUs.

When the guest owns its physical CPU, for example when HLT and MWAIT no longer exit (§3.4), a different scheme pays off. With pi_inject_timer, which defaults to on when the host isolates CPUs from timer housekeeping (nohz_full), KVM keeps the LAPIC timer in an hrtimer that is not pinned to the vCPU's CPU, so it fires on a housekeeping CPU, and delivers the expiry as a posted interrupt (kvm_can_post_timer_interrupt(), which also requires APICv). The isolated CPU then takes no timer exit at all. The clock the guest reads is its TSC, which KVM shapes with an offset and, where the hardware can scale it, a ratio. KVM_SET_TSC_KHZ sets a vCPU's frequency, or, on the VM file descriptor (KVM_CAP_VM_TSC_CONTROL, 5.19), the default for new vCPUs. Writes to the guest's TSC pass through kvm_synchronize_tsc(), which treats a value written within a second of the previous vCPU's as meant to match it and gives both the same offset. Only when every vCPU is matched, and the host itself uses the TSC as its clocksource, does pvclock_update_vm_gtod_copy() turn on the master clock. Migration avoids the heuristic. The VMM saves and restores each vCPU's offset with the KVM_VCPU_TSC_OFFSET attribute (5.16), and KVM_GET_CLOCK returns kvm-clock together with the host's real time and TSC (KVM_CLOCK_REALTIME, KVM_CLOCK_HOST_TSC), from which the destination computes how much time passed in flight. TDX guests, and SEV-SNP guests with Secure TSC, keep the TSC out of the host's hands: guest_tsc_protected makes KVM refuse to change it.

On ARM64 the generic timer is part of the CPU architecture, and that makes the guest's timer partly hardware. The guest reads the counter directly, offset by CNTVOFF_EL2, and programs its virtual timer registers without trapping. get_timer_map() in arch/arm64/kvm/arch_timer.c decides which of the guest's timers are backed directly by hardware and which are emulated with an hrtimer. Under VHE both the virtual and the physical EL1 timers are direct, because the host uses the EL2 timers. Under nVHE the physical timer is emulated. A guest hypervisor under NV has four timers: in its own virtual EL2 context its EL2 timers run on the hardware and its EL1 timers are emulated, and while its guest runs the mapping flips. A direct physical timer also needs the guest's physical counter offset to be zero, or FEAT_ECV's CNTPOFF_EL2 to apply it. Otherwise KVM traps the guest's physical timer and counter accesses and corrects for the offset itself. When a direct timer fires while the guest runs, the host still takes the physical interrupt (kvm_arch_timer_handler()) and injects the virtual PPI. Because that PPI is mapped to the physical one (kvm_vgic_map_phys_irq()), the guest's deactivation also deactivates the physical interrupt. When the vCPU blocks, kvm_timer_vcpu_put() calls kvm_timer_blocking(), which arms a background hrtimer (kvm_bg_timer_expire()) for the earliest guest deadline so that the timer can wake the vCPU. For migration, KVM_ARM_SET_COUNTER_OFFSET (6.4) sets one VM-wide offset that applies to both the virtual and the physical counter of every vCPU, existing or future. It fails with -EBUSY if a vCPU ioctl runs at the same time and is refused for protected VMs. Once it is used, KVM silently ignores writes of CNTVCT_EL0 and CNTPCT_EL0 through KVM_SET_ONE_REG, the older way to restore a counter. The VMM also chooses each timer's PPI, with the KVM_ARM_VCPU_TIMER_CTRL attributes KVM_ARM_VCPU_TIMER_IRQ_VTIMER and _PTIMER and, for NV, _HVTIMER and _HPTIMER.

A vCPU is a thread, so it can be preempted on the host, and the guest's scheduler should know when that happens. Both architectures export steal time: a per-vCPU record in guest memory that KVM updates each time the vCPU thread is loaded onto a CPU. It adds the time the thread spent runnable but not running, which is exactly the host scheduler's sched_info.run_delay (Chapter 6, §10.2). On x86 the guest enables it with MSR_KVM_STEAL_TIME and KVM fills struct kvm_steal_time in record_steal_time(). The same record carries a preempted flag that guest spinlocks (vcpu_is_preempted()) and the paravirtual TLB flush (§8.4) consult. On ARM64 the guest discovers the record with the SMCCC call ARM_SMCCC_HV_PV_TIME_ST, the VMM places it with KVM_ARM_VCPU_PVTIME_CTRL (5.5), and kvm_update_stolen_time() fills it on KVM_REQ_RECORD_STEAL. That record holds only the stolen time. It has no preempted flag, so an ARM64 guest's vcpu_is_preempted() always returns false.

When a guest goes idle, its vCPU executes HLT or WFI, and both end in kvm_vcpu_halt(). Sleeping and waking a thread costs several microseconds, and an idle guest is often woken again almost at once by an I/O completion, so halt polling (4.0) first spins for a while: 

/* virt/kvm/kvm_main.c, kvm_vcpu_halt() (abridged) */
	do_halt_poll = halt_poll_allowed && vcpu->halt_poll_ns;

	start = cur = poll_end = ktime_get();
	if (do_halt_poll) {
		ktime_t stop = ktime_add_ns(start, vcpu->halt_poll_ns);

		do {
			if (kvm_vcpu_check_block(vcpu) < 0)
				goto out;	/* interrupt or request arrived */
			cpu_relax();
			poll_end = cur = ktime_get();
		} while (kvm_vcpu_can_poll(cur, stop));
	}

	waited = kvm_vcpu_block(vcpu);	/* really sleep */
	...
	/* then grow or shrink vcpu->halt_poll_ns based on halt_ns */

kvm_vcpu_can_poll() stops early if another task wants the CPU (single_task_running(), need_resched()), so polling only burns cycles that nobody else wanted. The per-vCPU window adapts. It starts at halt_poll_ns_grow_start (10 µs). It doubles (halt_poll_ns_grow) after a halt that outlasted the window but not the cap, halves (halt_poll_ns_shrink) after one that outlasted the cap. A window that shrinks below the start value drops to zero, so a vCPU whose halts are all long stops polling until a short halt grows the window again. It is capped by the halt_poll_ns parameter: 200 µs on x86 and 500 µs on ARM64 (KVM_HALT_POLL_NS_DEFAULT). The VMM can override the cap per VM with KVM_CAP_HALT_POLL. A guest can also turn polling off for itself through MSR_KVM_POLL_CONTROL, which kvm_arch_no_poll() reads, when it polls in its own idle driver (drivers/cpuidle/cpuidle-haltpoll.c). Whether polling pays shows in the per-vCPU statistics read through KVM_GET_STATS_FD: halt_successful_poll against halt_attempted_poll, the time in halt_poll_success_ns, halt_poll_fail_ns, and halt_wait_ns, and histograms of all three. Virtual Performance Counters

A guest that runs perf expects a performance-monitoring unit of its own: counters it programs through MSRs on x86, or through PMEVTYPER<n>_EL0 and PMEVCNTR<n>_EL0 on ARM64, and an interrupt when one overflows. The host's perf subsystem (Chapter 29, §9) already owns those counters, so the original design on both architectures is an emulated vPMU built on top of perf. A guest write to an event selector traps, and KVM turns it into a pinned kernel counter. pmc_reprogram_counter() in arch/x86/kvm/pmu.c (3.3) and kvm_pmu_create_perf_event() in arch/arm64/kvm/pmu-emul.c (PMUv3 emulation since 4.6) both call perf_event_create_kernel_counter() for the vCPU thread with exclude_host set, so the counter runs only while that thread is in guest mode. The sample period is chosen so that the perf event overflows exactly where the guest's counter would wrap. The overflow callback, kvm_perf_overflow() or kvm_pmu_perf_overflow(), records the overflow in the guest's status register and raises a request. The vCPU then injects the guest's interrupt, through the LAPIC's LVTPC entry on x86 (kvm_pmu_deliver_pmi()) or, on ARM64, through the vGIC as the per-CPU interrupt the VMM chose with KVM_ARM_VCPU_PMU_V3_IRQ.

What the emulated vPMU offers is conservative. On x86, KVM_GET_SUPPORTED_CPUID reports at most architectural PMU version 2 in leaf 0xA (kvm_init_pmu_capability()) and caps the number of general-purpose and fixed counters. Instructions that KVM emulates still count: kvm_pmu_instruction_retired() and kvm_pmu_branch_retired() advance the matching guest counters. Two Intel features exist only in this design. PEBS needs hardware whose PEBS can write through EPT (vmx_pebs_supported()), and legacy LBRs are lent to the guest through a host perf call-stack event (intel_pmu_create_guest_lbr_event()). Neither is offered with the mediated vPMU, and hosts with Arch LBR get no guest LBRs at all. A VMM that wants no vPMU for a VM sets KVM_PMU_CAP_DISABLE through KVM_CAP_PMU_CAPABILITY (5.18) before it creates vCPUs. Event filters installed with KVM_SET_PMU_EVENT_FILTER can list exact events or, with KVM_PMU_EVENT_FLAG_MASKED_EVENTS (6.3), masked patterns that match whole families of unit-mask values. On ARM64 the emulated PMU advertises at most PMUv3p5 (kvm_arm_pmu_get_pmuver_limit()). A guest hypervisor under NV partitions the counters with MDCR_EL2.HPMN as on real hardware: counters below HPMN belong to its guest, and the rest count only in its own virtual EL2 (kvm_pmu_hyp_counter_mask(), 6.13).

The emulated design is accurate enough for profiling, but it is costly. Every reprogramming is an exit plus a perf operation, guest RDPMC instructions and counter-MSR accesses exit too, and the guest's events compete with host events for the same hardware, so the perf scheduler may multiplex them. Hybrid x86 CPUs, whose core types have different PMUs, get no vPMU at all (kvm_init_pmu_capability()). Linux 7.0 adds a second x86 design, the mediated vPMU, which gives the guest the hardware counters outright while it runs. It is off by default and is enabled with the enable_mediated_pmu parameter of kvm_intel or kvm_amd. It needs an in-kernel LAPIC and recent PMU hardware: on Intel, architectural PMU version 4 with full-width counter writes and VMCS loading of PERF_GLOBAL_CTRL; on AMD, PerfMonV2. Each pass through vcpu_enter_guest() brackets the guest with a PMU context switch, done with interrupts disabled: 

/* arch/x86/kvm/pmu.c, kvm_mediated_pmu_load() (abridged) */
	perf_load_guest_context();	/* schedule out host exclude_guest events */
	wrmsrq(kvm_pmu_ops.PERF_GLOBAL_CTRL, 0);
	perf_load_guest_lvtpc(kvm_lapic_get_reg(vcpu->arch.apic, APIC_LVTPC));
	kvm_pmu_load_guest_pmcs(vcpu);	/* guest counters and event selectors */
	kvm_pmu_call(mediated_load)(vcpu);

	/* ... guest runs; VMX loads PERF_GLOBAL_CTRL at entry and exit ... */

/* kvm_mediated_pmu_put(): save the guest counters, zero the hardware,
 * then perf_put_guest_lvtpc() and perf_put_guest_context() */

While guest counters are loaded, the LVTPC points at a dedicated vector, PERF_GUEST_MEDIATED_PMI_VECTOR (Chapter 4), so an overflow reaches kvm_handle_guest_mediated_pmi(), which only raises KVM_REQ_PMI, instead of the host's NMI handler. Counter MSRs and RDPMC no longer exit, provided the VM exposes as many counters, of the same width, as the hardware has (kvm_need_rdpmc_intercept()). Event-selector writes still trap, so the VMM's event filter still applies: KVM writes the hardware selector itself and clears its enable bit for a forbidden event (kvm_mediated_pmu_refresh_event_filter()). The price is exclusivity, and perf enforces it. When the first vCPU of a mediated-PMU VM is created, kvm_arch_vcpu_precreate() calls perf_create_mediated_pmu(). That call fails with -EBUSY if the host has any event that also counts in guest mode, the NMI watchdog's cycle counter being the usual one. While such VMs exist, perf refuses new events of that kind with -EOPNOTSUPP.

ARM64 has no mediated mode in 7.0. Its vPMU is always emulated, and the work goes into choosing and fencing the hardware behind it. On a heterogeneous system the VMM picks one host PMU with KVM_ARM_VCPU_PMU_V3_SET_PMU (5.18). A vCPU that then runs on a CPU of another type gets KVM_EXIT_FAIL_ENTRY with reason KVM_EXIT_FAIL_ENTRY_CPU_UNSUPPORTED. KVM_ARM_VCPU_PMU_V3_SET_NR_COUNTERS (6.16) limits the counters the guest sees, and KVM_ARM_VCPU_PMU_V3_FILTER (5.10) restricts its events; it is the counterpart of x86's KVM_SET_PMU_EVENT_FILTER (5.3). Host events need fencing too. The PMUv3 driver tells KVM which counters exclude the guest or the host (kvm_set_pmu_events(), called from drivers/perf/arm_pmuv3.c). Under nVHE those counters are switched at every guest entry and exit. Under VHE, host and guest kernels already run at different exception levels, so only EL0 counting has to change, and kvm_vcpu_pmu_restore_guest() flips it at vcpu_load().

Devices

A guest needs disks, network interfaces, and consoles, and KVM supplies none of them. Devices are where the split between kernel and VMM matters most, and where a deployment chooses between generality and speed. There are three models. A device can be emulated by the VMM, one exit per register access. It can be a paravirtual virtio device, whose backend may move into the host kernel as vhost. Or it can be a real device assigned to the guest through VFIO and the IOMMU. The guest kernel cooperates with its own paravirtual drivers and hooks. The sections follow that order. §8.1 covers emulation, both in the VMM and in the handful of devices that KVM models itself. §8.2 follows a virtio request from the guest's kick to a vhost worker in the host kernel. §8.3 assigns a PCI function through VFIO and iommufd and traces what becomes of its memory, registers, interrupts, and migration state. §8.4 turns to the guest, and to what Linux changes when it finds itself running on KVM.

Emulated Devices

An emulated device copies a real one register for register, so that an unmodified guest driver works. The VMM claims a range of guest-physical or port addresses by leaving it out of every memslot. Each guest access then becomes KVM_EXIT_MMIO or KVM_EXIT_IO (§3.4, §4.3), and the VMM's model of the device decides what the access means. This is how QEMU provides the i440FX and Q35 chipsets, an e1000 NIC, an AHCI disk controller, a PL011 UART for ARM64 guests, and hundreds more. It is complete, but it is slow. A legacy NIC driver may touch half a dozen registers per packet, and each access is a full trip from guest to KVM to VMM and back. On x86, an MMIO access also needs the instruction emulator to decode it.

The few devices that are both simple and hot are emulated in the kernel instead. Each VM has a small array of I/O buses, kvm->buses[], indexed by enum kvm_bus: KVM_MMIO_BUS, KVM_PIO_BUS, KVM_FAST_MMIO_BUS, and one each for s390 and LoongArch. A bus is an array of address ranges sorted by address, each pointing at a struct kvm_io_device with read and write methods, and kvm_io_bus_get_first_dev() finds the target with a binary search. Registration never edits a bus in place. kvm_io_bus_register_dev() builds a copy with the new range inserted, publishes it with rcu_assign_pointer(), and frees the old array after an SRCU grace period, so the exit path looks devices up without taking a lock. A bus holds at most NR_IOBUS_DEVS (1000) ranges, which also caps the number of ioeventfds (§7.3) a VM can register. Every MMIO or PIO exit is offered to these buses before it can leave KVM. On x86, vcpu_mmio_write() tries the vCPU's own local APIC first and then kvm_io_bus_write(), and only an access that no in-kernel device claims becomes KVM_EXIT_MMIO.

On x86 the in-kernel devices are the local APIC, the I/O APIC, the PIC, and the 8254 PIT (arch/x86/kvm/i8254.c), plus the PMU and the Hyper-V and Xen hypercall interfaces. Which of the interrupt controllers a VM gets depends on the irqchip mode chosen in §7.1, and the PIT is created separately with KVM_CREATE_PIT2. The PIT shows how much work even a simple device can be. Channel 0 is an hrtimer whose callback, pit_timer_fn(), queues pit_do_work() on a per-VM kthread worker (kvm-pit/ followed by the VMM's PID), which raises IRQ 0 through the in-kernel PIC and I/O APIC. Old guests keep time by counting ticks, so by default the PIT runs in reinject mode. A tick that expires while the previous one is still unacknowledged is counted rather than dropped, and kvm_pit_ack_irq() releases the next one when the guest's EOI arrives. APICv and AVIC complete EOIs without an exit, so reinject mode inhibits them (APICV_INHIBIT_REASON_PIT_REINJ), and a VMM that gives its guest a better clock turns reinjection off with KVM_REINJECT_CONTROL. With KVM_PIT_SPEAKER_DUMMY the PIT also answers port 0x61, where channel 2's gate and output appear and which calibration loops poll. On ARM64 the in-kernel devices are the vGIC with its ITS, the architected timers, and the PMU (arch/arm64/kvm/pmu-emul.c).

Two larger emulations serve guests written for other hypervisors. CONFIG_KVM_HYPERV (a separate option since 6.8, default y) implements, in arch/x86/kvm/hyperv.c, the parts of Microsoft's Hyper-V interface that Windows needs in order to run well. These include the synthetic interrupt controller (SynIC, 4.5) with its synthetic timers, the reference TSC page, paravirtual TLB-flush and IPI hypercalls, and the enlightened VMCS for nested Hyper-V. The VMBus control path stays in the VMM. HVCALL_POST_MESSAGE exits with KVM_EXIT_HYPERV, while HVCALL_SIGNAL_EVENT completes in the kernel once the VMM has bound the connection ID to an eventfd with KVM_HYPERV_EVENTFD (4.17). CONFIG_KVM_XEN (default n) does the same for Xen HVM guests in arch/x86/kvm/xen.c. KVM maintains the shared-info page and each vCPU's info and runstate areas (5.12). It delivers event channels as an interrupt routing type (KVM_IRQ_ROUTING_XEN_EVTCHN, 5.17), and it completes the hot hypercalls itself: EVTCHNOP_send, SCHEDOP_poll, and the single-shot timer. Every other Xen hypercall exits with KVM_EXIT_XEN, so a VMM can run unmodified Xen guests with no Xen hypervisor present.

For device registers whose writes need no immediate answer, such as a frame buffer or a doorbell that the VMM can process late, KVM_REGISTER_COALESCED_MMIO offers a middle path. coalesced_mmio_write() appends the write to a ring and resumes the guest at once. There is one ring per VM, in a page that the VMM maps at KVM_COALESCED_MMIO_PAGE_OFFSET of a vCPU's mmap. Each 24-byte entry holds the address, the length, and up to eight bytes of data, so a 4 KiB page has 170 slots. One slot is always left empty, and a write that finds the ring full simply takes the normal exit. Since 4.20 (KVM_CAP_COALESCED_PIO), a zone with its pio flag set does the same for port writes. Only writes are buffered, and the guest assumes they reach the device in order, so the VMM must drain the ring every time it gets control, before it handles the exit that brought it there. These are optimizations at the edges. To make I/O fast, the device has to be designed for virtualization.

virtio and vhost

virtio is that design. A virtio device exposes one or more virtqueues in guest memory. Each has a descriptor table, an "available" ring in which the driver posts buffers, and a "used" ring in which the device returns them. The guest driver (Chapter 14, §9.2 walks through virtio-blk) posts a batch of buffers and then notifies the device with a single register write (virtqueue_kick()). The device consumes the batch, fills the used ring, and raises one interrupt (vring_interrupt() on the guest side). With VIRTIO_RING_F_EVENT_IDX, each side also tells the other when it next needs a notification, so a busy queue runs for long stretches with no kicks or interrupts at all. Section 9 describes the virtio framework itself, including how to add a new device on either side.

When the virtio backend lives in the VMM, the kick is an ioeventfd and the interrupt is an irqfd (§7.3). The VMM's I/O thread sleeps on the kick eventfd, processes the queue with ordinary system calls, and signals the call eventfd. KVM_RUN never returns for I/O. The remaining costs are the wake-up of a user-space thread and the copies between guest buffers and host sockets or files. vhost (drivers/vhost/) removes those costs by moving the data path of the backend into the host kernel. vhost-net (2.6.34) connects a virtqueue pair to a tap device, vhost-scsi serves storage, and vhost-vsock (4.8) carries host-guest sockets. vhost-vdpa (5.7) hands the rings to hardware that implements virtio natively, and VDUSE (5.15, drivers/vdpa/vdpa_user/) lets a user-space process implement a vDPA device that can then serve a VM through vhost-vdpa or the host itself through virtio-vdpa. The VMM keeps the control plane. It opens /dev/vhost-net, describes guest memory, and wires each queue to the same eventfds it gives KVM: 

/* VMM: hand a virtio-net queue pair to vhost-net (error handling omitted) */
int vh = open("/dev/vhost-net", O_RDWR);
ioctl(vh, VHOST_SET_OWNER, NULL);           /* bind to this process; start worker */
ioctl(vh, VHOST_SET_FEATURES, &features);   /* negotiated virtio feature bits */
ioctl(vh, VHOST_SET_MEM_TABLE, mem);        /* guest_phys_addr -> userspace_addr */

for (unsigned int q = 0; q < 2; q++) {      /* 0 = RX, 1 = TX */
	struct vhost_vring_state num  = { .index = q, .num = 256 };
	struct vhost_vring_addr  addr = { .index = q,
		.desc_user_addr = hva(desc[q]), .avail_user_addr = hva(avail[q]),
		.used_user_addr = hva(used[q]) };
	struct vhost_vring_file  kick = { .index = q, .fd = kick_fd[q] };
	struct vhost_vring_file  call = { .index = q, .fd = call_fd[q] };
	struct vhost_vring_file  tap  = { .index = q, .fd = tap_fd };

	ioctl(vh, VHOST_SET_VRING_NUM,  &num);
	ioctl(vh, VHOST_SET_VRING_ADDR, &addr);
	ioctl(vh, VHOST_SET_VRING_KICK, &kick);   /* guest -> vhost */
	ioctl(vh, VHOST_SET_VRING_CALL, &call);   /* vhost -> guest */
	ioctl(vh, VHOST_NET_SET_BACKEND, &tap);

	/* the same eventfds, registered with KVM */
	struct kvm_ioeventfd io = { .addr = notify_gpa(q), .len = 2, .fd = kick_fd[q],
				    .datamatch = q,
				    .flags = KVM_IOEVENTFD_FLAG_DATAMATCH };
	struct kvm_irqfd irq = { .fd = call_fd[q], .gsi = gsi_of(q) };

	ioctl(vm_fd, KVM_IOEVENTFD, &io);
	ioctl(vm_fd, KVM_IRQFD, &irq);
}

From then on the VMM is out of the data path, as Figure 28-8 shows. A guest kick runs ioeventfd_write() in the vCPU thread. The eventfd_signal() there reaches vhost_poll_wakeup(), a wait-queue callback that vhost installed on the kick eventfd, and that queues the queue's work item with vhost_worker_queue() and wakes the worker. The worker runs handle_tx_kick(), and handle_tx() walks the available ring and passes each buffer to the tap socket's sendmsg(), with optional zero copy (experimental_zcopytx). Receive is symmetric. vhost also polls the tap socket, and when packets arrive, handle_rx() copies them into guest buffers. vhost_signal() then signals the call eventfd, which is an irqfd, so the guest is interrupted without any user-space thread waking up. For guests that keep a queue busy, VHOST_SET_VRING_BUSYLOOP_TIMEOUT lets the worker poll the ring briefly before it sleeps, which is the vhost counterpart of halt polling.

A worker serves every queue attached to it, so each handler limits itself. handle_tx() stops after VHOST_NET_WEIGHT bytes (512 KiB) or VHOST_NET_PKT_WEIGHT (256) packets and requeues its work item, so a busy TX queue cannot starve RX. Without zero copy, TX also batches. When the tap socket's send buffer is unlimited, as it is by default, vhost_net_build_xdp() prepares up to VHOST_NET_BATCH (64) packets as XDP buffers, and vhost_tx_batch() hands them to tun in a single sendmsg() (TUN_MSG_PTR). Zero copy is still off by default (experimental_zcopytx=0). Feature negotiation has also outgrown its 64-bit ioctl. The UDP-tunnel GSO offloads that vhost-net gained in 6.17 are virtio-net feature bits 65 and 67, so that release added VHOST_GET_FEATURES_ARRAY and VHOST_SET_FEATURES_ARRAY, and vhost-net learned VIRTIO_F_IN_ORDER at the same time.

The worker is a thread of the VMM. Since 6.4 it is a vhost_task (vhost_task_create() in kernel/vhost_task.c), created with CLONE_VM | CLONE_THREAD inside the process that called VHOST_SET_OWNER. It shares that process's address space, so it can reach guest memory through the same host-virtual addresses that VHOST_SET_MEM_TABLE recorded, using vhost_copy_from_user() and its relatives. Its CPU time, cgroup limits, and resource limits are those of the VMM. Before 6.4 the worker was a kernel thread that borrowed the VMM's mm and had to be attached to its cgroups explicitly. VHOST_SET_FORK_FROM_OWNER (6.17) lets a VMM choose that older kthread mode again, and the fork_from_owner_default module parameter sets the default for every device. VHOST_SET_OWNER creates one worker per device. VHOST_NEW_WORKER (6.5) creates more, and VHOST_ATTACH_VRING_WORKER binds a queue to one of them, so a multiqueue device can spread its queues across CPUs instead of serializing them on a single thread. This design gives vhost-net roughly the cost model of an in-kernel network stack serving a local socket. The same eventfd plumbing also works across process boundaries. vhost-user, a protocol spoken over a UNIX socket, lets a separate process such as a DPDK switch or virtiofsd own the queues. KVM cannot tell the difference, because it sees only eventfds.

Two more parts of the vhost interface matter to a VMM. The first is a device IOTLB. When the guest has a virtual IOMMU and negotiates VIRTIO_F_ACCESS_PLATFORM, ring and buffer addresses are I/O virtual addresses rather than guest-physical ones, and the memory table no longer applies. vhost then translates through a cache of IOVA-to-HVA mappings. On a miss, vhost_iotlb_miss() queues a VHOST_IOTLB_MISS message that the VMM reads from the vhost fd, and the VMM answers by writing a VHOST_IOTLB_UPDATE back (in the VHOST_IOTLB_MSG_V2 format since 4.19). The second is dirty logging for live migration. KVM's dirty log (§5.4) records only what is written through KVM: the guest's own stores, through second-stage mappings, and KVM's own accesses to guest memory. vhost writes guest memory through the VMM's mapping instead, which KVM never sees. With VHOST_F_LOG_ALL negotiated and a bitmap installed by VHOST_SET_LOG_BASE, vhost_log_write() sets a bit for every page the worker writes, and the VMM merges that bitmap with KVM's before each copy pass.

VFIO Device Assignment

The fastest device is a real one that the guest drives itself, typically an SR-IOV virtual function of a NIC or an NVMe controller, or a whole GPU. Giving a guest a physical device raises two problems. The device must not be able to DMA outside the guest's memory, and its registers and interrupts must reach the guest without passing through the host. VFIO (drivers/vfio/, 3.6) solves both by exposing a device to user space as a file descriptor, protected by the IOMMU (Chapter 13, §7.3). The modern interface combines a per-device character device, /dev/vfio/devices/vfioN (6.6), with iommufd (/dev/iommu, drivers/iommu/iommufd/, 6.2), which manages the I/O address spaces. The older group and container ioctls (VFIO_GROUP_SET_CONTAINER, VFIO_SET_IOMMU, VFIO_IOMMU_MAP_DMA) remain for compatibility. iommufd can also provide them itself (CONFIG_IOMMUFD_VFIO_CONTAINER), so that an older VMM runs unchanged on the new core. CONFIG_VFIO_NOIOMMU gives user-space drivers access to a device with no IOMMU behind it. That mode taints the kernel and cannot be used for a guest, because nothing translates or confines the device's DMA. 

/* VMM: assign a PCI function through VFIO cdev + iommufd (abridged) */
int iommufd = open("/dev/iommu", O_RDWR);
int dev     = open("/dev/vfio/devices/vfio0", O_RDWR);

struct vfio_device_bind_iommufd bind = { .argsz = sizeof(bind), .iommufd = iommufd };
ioctl(dev, VFIO_DEVICE_BIND_IOMMUFD, &bind);

struct iommu_ioas_alloc ioas = { .size = sizeof(ioas) };
ioctl(iommufd, IOMMU_IOAS_ALLOC, &ioas);

/* map all guest RAM so that device IOVA == guest physical address */
struct iommu_ioas_map map = { .size = sizeof(map), .ioas_id = ioas.out_ioas_id,
	.flags = IOMMU_IOAS_MAP_FIXED_IOVA | IOMMU_IOAS_MAP_READABLE |
		 IOMMU_IOAS_MAP_WRITEABLE,
	.user_va = (__u64)guest_ram, .length = ram_size, .iova = 0 };
ioctl(iommufd, IOMMU_IOAS_MAP, &map);          /* pins the pages */

struct vfio_device_attach_iommufd_pt at = { .argsz = sizeof(at),
					    .pt_id = ioas.out_ioas_id };
ioctl(dev, VFIO_DEVICE_ATTACH_IOMMUFD_PT, &at);

/* BARs: mmap the region, then expose it to the guest as a memslot */
ioctl(dev, VFIO_DEVICE_GET_REGION_INFO, &bar0);  /* .index = VFIO_PCI_BAR0_REGION_INDEX */
void *bar = mmap(NULL, bar0.size, PROT_READ | PROT_WRITE, MAP_SHARED, dev, bar0.offset);

/* MSI-X vector 0 -> eventfd, which is also a KVM irqfd */
ioctl(dev, VFIO_DEVICE_SET_IRQS, irq_set);   /* VFIO_IRQ_SET_DATA_EVENTFD |
						VFIO_IRQ_SET_ACTION_TRIGGER */

Each piece of the device then follows its own path. The guest's memory reaches the device through the IOMMU. IOMMU_IOAS_MAP pins the guest's pages with FOLL_LONGTERM (Chapter 9, §11), because a device cannot take a page fault. This is the one place in KVM's world where guest memory cannot be swapped, migrated, or deduplicated. The device's registers reach the guest through memslots. The BAR mapping that vfio_pci_core_mmap() creates is a VM_PFNMAP region filled in by vfio_pci_mmap_huge_fault(). Once the VMM registers it as a memslot, KVM's hva_to_pfn_remapped() (§5.1) installs second-stage entries that point at the device's MMIO, and guest register accesses proceed with no exit. Only PCI configuration space and the MSI-X table stay under the VMM's control, accessed through reads and writes on the device fd, so that the host keeps control of interrupt routing.

The BAR mapping must also be able to disappear on demand. If the guest clears the memory-enable bit in the device's command register, or the VMM resets the device, a later access to a BAR could hang or corrupt the bus. Before either happens, vfio_pci_zap_and_down_write_memory_lock() calls unmap_mapping_range() on the BAR part of the device file. That fires the MMU notifiers, so KVM drops its second-stage entries as well (§5.3), and a fault on the BAR returns VM_FAULT_SIGBUS until memory decoding is turned back on. Guest RAM can also be mapped without going through the VMM's page tables. IOMMU_IOAS_MAP_FILE (6.13) maps a range of a memfd by file offset, so the mapping belongs to the file rather than to one process's address space, and IOMMU_IOAS_CHANGE_PROCESS (6.13) can then move its pinned-page accounting to a new VMM process during a live update. Since 6.19 the same call accepts a dma-buf, and vfio-pci can export a BAR as one (VFIO_DEVICE_FEATURE_DMA_BUF). One assigned device can then DMA straight into another's BAR, peer to peer, through the mappings in the guest's IOAS.

Interrupts take the eventfd path. The host's handler, vfio_msihandler(), does nothing but call eventfd_signal(), and that eventfd is a KVM irqfd. When irqbypass pairs the two (§7.2), the IOMMU posts the interrupt into the vCPU (VT-d or AMD IOMMU) or the GIC delivers it as a vLPI (GICv4), and the host handler does not run at all. Legacy INTx, which is level-triggered and may be shared, cannot take that path. vfio_intx_handler() masks the line before it signals the eventfd, and the line stays masked until the guest has serviced the device. A VMM wires this up with two eventfds. The trigger is a KVM irqfd with KVM_IRQFD_FLAG_RESAMPLE (§7.3), and its resample eventfd is handed back to VFIO as the unmask eventfd (VFIO_IRQ_SET_ACTION_UNMASK), so the guest's EOI unmasks the physical line without a trip through user space. A small KVM device, KVM_DEV_TYPE_VFIO (virt/kvm/vfio.c), connects the two subsystems. KVM_DEV_VFIO_FILE_ADD gives the VFIO file the struct kvm pointer (vfio_file_set_kvm()). It also tells KVM whether the device's DMA might bypass CPU cache coherency (kvm_arch_register_noncoherent_dma()), in which case x86 KVM must honor the guest's memory types. For guests that want a virtual IOMMU of their own, iommufd builds nested translation. A parent page table allocated with IOMMU_HWPT_ALLOC_NEST_PARENT (6.7) holds the GPA mapping, and IOMMU_VIOMMU_ALLOC (6.13) represents the guest-visible IOMMU instance, mirroring two-stage CPU translation. Around it, IOMMU_VDEVICE_ALLOC (6.13) gives each assigned device its guest-visible ID, IOMMU_HWPT_INVALIDATE (6.8) passes the guest's IOTLB invalidations to the hardware, and IOMMU_VEVENTQ_ALLOC (6.15) carries faults and events back to the guest's IOMMU driver. IOMMU_HW_QUEUE_ALLOC (6.17) goes further on hardware that virtualizes its command queue, such as the SMMUv3 CMDQV on NVIDIA Grace (drivers/iommu/arm/arm-smmu-v3/tegra241-cmdqv.c), by letting the hardware consume the guest's invalidation queue directly.

Assignment has costs: pinned memory cannot be overcommitted, and live migration needs device cooperation. Vendor variant drivers in drivers/vfio/pci/ supply what the generic driver cannot. Six of them implement migration: mlx5 and hisilicon (5.18), pds (6.6), qat (6.10), virtio (6.13, for virtio-net functions), and xe (6.19, for Intel Xe SR-IOV functions). nvgrace-gpu (6.9) does something else: it exposes the cache-coherent memory of a Grace Hopper GPU to the guest as a BAR. Migration is a state machine driven through VFIO_DEVICE_FEATURE. VFIO_DEVICE_FEATURE_MIGRATION reports the states a device supports, and VFIO_DEVICE_FEATURE_MIG_DEVICE_STATE (5.18) moves it among RUNNING, STOP, STOP_COPY, and RESUMING. Entering a saving or resuming state returns a data fd, from which the source VMM reads the device's state and to which the destination VMM writes it. vfio_mig_get_next_state() breaks any requested change into these arcs. Optional states refine the protocol. PRE_COPY (6.2) streams most of the state while the device still runs, as RAM is copied while the guest runs. RUNNING_P2P stops the device from starting new peer-to-peer DMA, so that a VM with several assigned devices can stop them one by one without one writing into another that has already stopped. Pages that a device writes by DMA must also be reported dirty, and KVM never sees those writes. Either the device tracks them itself (VFIO_DEVICE_FEATURE_DMA_LOGGING_START and VFIO_DEVICE_FEATURE_DMA_LOGGING_REPORT, 6.1, implemented by mlx5 and pds), or the IOMMU does, with dirty bits in its own page tables. A page table allocated with IOMMU_HWPT_ALLOC_DIRTY_TRACKING on VT-d, AMD-Vi, or SMMUv3 is read back with IOMMU_HWPT_GET_DIRTY_BITMAP (6.7).

Assigning a device to a confidential VM is harder still, because the guest must be able to trust a device that the host could have tampered with. PCI TSM (6.19, drivers/pci/tsm.c) begins that work on the host side. Through the platform's security manager it authenticates a device and turns on PCIe IDE link encryption (Chapter 27, §1.1), and it exports pci_tsm_bind(), which binds a device function to a struct kvm as a TDISP trusted device interface. In 7.0 nothing in KVM or VFIO calls it yet. A confidential guest therefore still reaches assigned devices through shared memory, with its DMA bounced through unencrypted swiotlb buffers.

The Guest Side

Linux running as a KVM guest detects its host and adapts. On x86, x86_hyper_kvm in arch/x86/kernel/kvm.c recognizes the "KVMKVMKVM" signature at CPUID leaf 0x40000000, and kvm_guest_init() installs paravirtual operations for each KVM_FEATURE_* bit the host advertises. They include the kvm-clock clocksource, the steal-time clock (static_call_update(pv_steal_clock, kvm_steal_clock)), a paravirtual EOI that avoids an exit (MSR_KVM_PV_EOI_EN), asynchronous page faults (KVM_FEATURE_ASYNC_PF_INT, §5.3), and multicast IPIs in a single hypercall (KVM_HC_SEND_IPI). Paravirtual spinlocks (pv_ops_lock.wait = kvm_wait, pv_ops_lock.kick = kvm_kick_cpu, KVM_HC_KICK_CPU) let a waiter halt instead of spinning on a lock whose holder has been preempted. KVM_FEATURE_PV_SCHED_YIELD (5.3) applies the same idea to function-call IPIs. kvm_smp_send_call_func_ipi() sends the IPI and, if a target vCPU is preempted, gives the sender's time slice to it with KVM_HC_SCHED_YIELD. KVM_FEATURE_MSI_EXT_DEST_ID (5.10) lets MSIs address more than 255 vCPUs without an emulated interrupt-remapping unit, by borrowing reserved bits of the MSI address. A host that gives every vCPU a dedicated physical CPU sets KVM_HINTS_REALTIME. The guest then keeps native spinlocks and skips the PV TLB flush and PV sched-yield, which help only when vCPUs can be preempted. The remote TLB flush shows how the pieces combine: 

/* arch/x86/kernel/kvm.c (comments abridged) */
static void kvm_flush_tlb_multi(const struct cpumask *cpumask,
			const struct flush_tlb_info *info)
{
	u8 state;
	int cpu;
	struct kvm_steal_time *src;
	struct cpumask *flushmask = this_cpu_cpumask_var_ptr(__pv_cpu_mask);

	cpumask_copy(flushmask, cpumask);
	/* flush only running vCPUs; queue a flush-on-entry for preempted ones */
	for_each_cpu(cpu, flushmask) {
		src = &per_cpu(steal_time, cpu);
		state = READ_ONCE(src->preempted);
		if ((state & KVM_VCPU_PREEMPTED)) {
			if (try_cmpxchg(&src->preempted, &state,
					state | KVM_VCPU_FLUSH_TLB))
				__cpumask_clear_cpu(cpu, flushmask);
		}
	}

	native_flush_tlb_multi(flushmask, info);
}

A native TLB shootdown sends an IPI to every target CPU and waits. In a guest, a target vCPU may be preempted on the host, and the sender would wait for a whole host scheduling period. The steal-time record (§7.4) already tells the guest which vCPUs are preempted. The guest marks each of those with KVM_VCPU_FLUSH_TLB and skips it, and KVM's record_steal_time() flushes that vCPU's TLB before it next enters the guest. Confidential guests add one more hook. When the host advertises KVM_FEATURE_MIGRATION_CONTROL (5.14), an SEV guest installs pv_ops.mmu.notify_page_enc_status_changed, which reports each private-to-shared conversion with KVM_HC_MAP_GPA_RANGE. That becomes the user-space exit described in §6.2, and it tells the VMM which pages it can migrate in the clear. Once the guest's list is complete, it writes KVM_MIGRATION_READY to MSR_KVM_MIGRATION_CONTROL, and only then may the VMM migrate it.

An ARM64 guest needs far less of this, because the architecture provides in hardware what x86 guests get from paravirtualization. TLB invalidations are broadcast by TLBI ... IS instructions without IPIs, so no preempted-vCPU problem arises. The GIC's virtual CPU interface makes EOI cheap, and the architected counter needs no paravirtual clock. What remains is discovered through SMCCC. The guest asks for the KVM vendor-hypervisor UID (kvm_init_hyp_services() in drivers/firmware/smccc/kvm_guest.c) and the services behind it. It uses pv_time_init() in arch/arm64/kernel/paravirt.c to install para_steal_clock, and drivers/ptp/ptp_kvm_arm.c to read the host's clock precisely (x86 uses KVM_HC_CLOCK_PAIRING for the same purpose). Since 6.15 the vendor services also answer a question that migration between different hosts raises: on which CPU implementations might this VM run? If the guest finds ARM_SMCCC_KVM_FUNC_DISCOVER_IMPL_VER and ARM_SMCCC_KVM_FUNC_DISCOVER_IMPL_CPUS, kvm_arm_target_impl_cpu_init() reads a list of MIDR, REVIDR, and AIDR values and passes it to cpu_errata_set_target_impl(). Errata workarounds are then enabled for every listed implementation, not only for the CPU the guest booted on. KVM does not answer these calls itself. The VMM enables them in the KVM_REG_ARM_VENDOR_HYP_BMAP_2 firmware pseudo-register and handles them through the SMCCC filter (§4.3). As §7.4 noted, ARM64's vcpu_is_preempted() simply returns false. The guest side of pKVM protected VMs is already in drivers/virt/coco/pkvm-guest/arm-pkvm-guest.c, which implements set_memory_decrypted() as a MEM_SHARE hypercall and guards MMIO regions through an ioremap hook. The host side of those calls, as §6.4 noted, is not in 7.0.12.

Finally, both architectures run the same virtio drivers (§9). On x86 these usually sit on virtio-pci, where vp_notify() writes the queue index to the notification address that the VMM registered as an ioeventfd. ARM64 guests use virtio-pci or the simpler virtio-mmio transport described by the device tree. A confidential guest cannot let a device read its private memory, so it insists on VIRTIO_F_ACCESS_PLATFORM. On x86, arch/x86/mm/mem_encrypt.c installs virtio_require_restricted_mem_acc() as the virtio memory-access check, and the virtio core refuses any device that does not offer the feature (§9.2). With the feature negotiated, vring_use_map_api() (vring_use_dma_api() before 6.18) is true, so every buffer goes through the DMA API and therefore through swiotlb bounce buffers in shared memory, as it does for an assigned device (§8.3).

Two paravirtual devices let the host take memory back from a guest. virtio-balloon inflates by allocating guest pages and reporting their frame numbers, so that the host can discard them. Its free page reporting (5.7, VIRTIO_BALLOON_F_REPORTING) goes further. mm/page_reporting.c hands large free blocks of the buddy allocator to the device in the background, pageblock-sized by default, so the host can reclaim memory the guest is not using while the guest keeps it. virtio-mem (5.8, drivers/virtio/virtio_mem.c) resizes the guest instead, plugging and unplugging memory blocks through memory hotplug. It onlines added memory as ZONE_MOVABLE where it can, so that the memory can be unplugged again later (Chapter 17, §9.5). Table 28-8 summarizes the guest-side features of the two architectures.

virtio: The Paravirtual Device Framework

Section 8.2 used virtio as the reason vhost is fast, and §8.4 listed it among the things a guest runs. It deserves a section of its own, because it is the device interface that both halves of a virtualized system are written against. When Rusty Russell merged it into 2.6.24 in October 2007, each hypervisor carried its own paravirtual drivers: Xen had netfront and blkfront, lguest had its own, and KVM was about to grow a third set. virtio replaced them with one set of guest drivers written against an abstract device, plus a small transport layer per hypervisor. The interface has been an OASIS standard since version 1.0 (2016), which fixed the little-endian "modern" layout. Version 1.1 (2019) added the packed virtqueue, 1.2 (2022) added most of the newer device types (file system, sound, memory, I2C, GPIO, SCMI), 1.3 (2023) added the administration virtqueue, and the 1.4 committee specification (April 2026) defines 23 device types.

The same driver now runs under QEMU and KVM, crosvm, Firecracker, and Cloud Hypervisor, under Xen through grant-table DMA operations (drivers/xen/grant-dma-ops.c), on s390 channel I/O, on a remote processor that shares memory with the application CPU, and on SmartNICs and DPUs that implement virtio queues in silicon. Linux implements both sides of the interface. The driver side is the core in drivers/virtio/ and about thirty device drivers that live in their own subsystems, such as drivers/net/virtio_net.c and drivers/block/virtio_blk.c. The device side is vhost, vringh, vDPA, and VDUSE, all in the host kernel. Figure 28-9 shows the layers. A new device type touches every one of them: a specification, a driver against the core, and at least one device implementation for the driver to talk to.

The virtio Device Model

Every virtio device, whatever its transport, has four parts. A device status field records how far the driver has got in bringing the device up. Feature bits are offered by the device and accepted, as a subset, by the driver. A device configuration space holds device-specific parameters, such as a disk's capacity or a NIC's MAC address. One or more virtqueues in memory shared between driver and device carry the actual requests. There are three kinds of notification: the driver tells the device that it has made buffers available (a "kick"), the device tells the driver that it has used buffers (normally an interrupt), and the device tells the driver that its configuration space has changed. The transport decides how each part is reached. It might be PCI capabilities and MSI-X vectors, MMIO registers and one interrupt line, or s390 channel commands. Nothing above the transport needs to know which.

The status field is a byte of flags that the driver sets in order: ACKNOWLEDGE (1) once the driver has noticed the device, DRIVER (2) once it knows how to drive it, FEATURES_OK (8) after feature negotiation, and DRIVER_OK (4) when the device is live. The device can set DEVICE_NEEDS_RESET (64) when it has hit an error it cannot recover from, and the driver sets FAILED (128) when it gives up. The initialization sequence in §3.1 of the specification is the protocol that both sides must follow. The driver resets the device by writing 0, sets ACKNOWLEDGE and DRIVER, reads the offered features, writes back the subset it understands, and sets FEATURES_OK. It must then read the status back, because a device that cannot work with that subset refuses it by leaving FEATURES_OK clear. Only then does the driver read configuration space, set up its virtqueues, and set DRIVER_OK. Reset is the only way back. Features cannot be renegotiated without a full reset, and a driver must not post buffers or kick before DRIVER_OK. Version 1.4 adds a SUSPEND status bit (16) with VIRTIO_F_SUSPEND (bit 43) for pausing a device during migration. Linux 7.0.12 implements neither.

Feature bits are virtio's versioning mechanism. A device never changes its behavior because the specification changed. It offers a new bit, and the behavior applies only if the driver accepts it, so a 2008 driver and a 2026 device still work together. The modern interface allows 128 feature bits, although Linux could test only the low 64 until 6.17 (§9.2). The first users of the upper half are virtio-net's UDP-tunnel segmentation-offload bits, 65 to 68, which is why vhost gained its feature-array ioctls in the same release (§8.2). Bits 0 to 23 and most bits above 49 belong to the device type, so VIRTIO_NET_F_MAC (5) and VIRTIO_BLK_F_RO (5) can share a number. The range from 24 to 43 is reserved for features of the ring and the transport, which every device type shares, although virtio-net has also been given bits 41 and 42. Table 28-9 lists the shared bits that Linux knows about. VIRTIO_F_VERSION_1 separates the modern interface from the legacy one, which predates the standard: a legacy device uses the guest's native byte order and a fixed queue layout. The kernel's types record which side of that line a value is on. __virtio16, __virtio32, and __virtio64 in include/uapi/linux/virtio_types.h are converted by virtio16_to_cpu() and its relatives, which check virtio_is_little_endian(), while fields that exist only in the modern interface are plain __le16 and __le32. Version 1.1 added an optional fifth part, shared memory regions. A region is a range of memory that the device owns and the driver maps directly, identified by an 8-bit ID whose meaning depends on the device type. A virtqueue buffer is guest memory that the driver lends to the device; a region is the reverse, usually host memory that the VMM maps into the guest-physical address space. virtio-pci describes each region with a SHARED_MEMORY_CFG capability in the 64-bit struct virtio_pci_cap64 form, because regions can be gigabytes long. virtio-mmio selects one with SHMSel (0x0ac) and reads its length and base from 0x0b0 to 0x0bc, where a length of all ones means the region does not exist. A driver calls virtio_get_shm_region(), which goes to the transport's get_shm_region. Three drivers use one. virtio-fs maps its DAX cache (region 0), so that file pages are shared with the host page cache instead of copied through the queue. virtio-gpu maps host-visible memory (region 1) for blob resources that the host's GPU driver allocated. virtio-pmem (6.8) can take its persistent-memory range from region 0 instead of configuration space, and its validate() clears VIRTIO_PMEM_F_SHMEM_REGION when the transport cannot provide the region.

The Linux virtio Core

drivers/virtio/virtio.c turns that protocol into a Linux bus. virtio_bus is a bus_type named "virtio" (the driver model of Chapter 13, §4.2), and every device on it is a struct virtio_device declared in include/linux/virtio.h. The device carries its struct virtio_device_id (device type and vendor), a pointer to the transport's virtio_config_ops, the negotiated features as a 128-bit array (two u64s since 6.17, so bits above 63 are reachable), the list of its virtqueues, and, since 6.18, an optional virtio_map_ops table that replaces the DMA API for transports whose "DMA device" is not a real struct device. A transport discovers a device, fills in id and config, and calls register_virtio_device(). That allocates an index from an IDA, names the device virtio%u, resets it, sets ACKNOWLEDGE, and adds it to the bus. Matching is by device ID, with VIRTIO_DEV_ANY_ID as a wildcard, and the uevent carries MODALIAS=virtio:d%08Xv%08X, so udev loads the right module. In sysfs, /sys/bus/virtio/devices/virtio0/ shows device, vendor, status, and features, the last as a string of 0 and 1 characters, one per bit. The bus also implements irq_get_affinity() (6.14), which returns the CPU mask of a queue's interrupt through the transport's get_vq_affinity, so that blk_mq_map_hw_queues() can map virtio-blk's and virtio-scsi's hardware queues to the CPUs that their interrupts are spread over.

The transport contract is struct virtio_config_ops in include/linux/virtio_config.h. get, set, and generation access configuration space; get_status, set_status, and reset drive the status byte; get_features (with get_extended_features for bits above 63) and finalize_features negotiate; find_vqs and del_vqs create and destroy virtqueues and their interrupts. synchronize_cbs waits for running callbacks, set_vq_affinity spreads queue interrupts, get_shm_region exposes shared-memory windows such as virtio-fs's DAX cache, and disable_vq_and_reset and enable_vq_after_reset reset one queue at a time. Adding a transport means implementing this table and calling register_virtio_device(); every driver then works on it unchanged.

Probing is where the core runs the initialization sequence on the driver's behalf. virtio_dev_probe(), abridged: 

static int virtio_dev_probe(struct device *_d)
{
	struct virtio_device *dev = dev_to_virtio(_d);
	struct virtio_driver *drv = drv_to_virtio(dev->dev.driver);
	u64 device_features[VIRTIO_FEATURES_U64S];
	u64 driver_features[VIRTIO_FEATURES_U64S];

	virtio_add_status(dev, VIRTIO_CONFIG_S_DRIVER);
	virtio_get_features(dev, device_features);

	/* driver_features = bits listed in drv->feature_table[] */
	...
	/* accept the intersection (the legacy table if !VERSION_1) */
	for (i = 0; i < VIRTIO_FEATURES_U64S; ++i)
		dev->features_array[i] = driver_features[i] & device_features[i];

	virtio_debug_device_filter_features(dev);     /* debugfs overrides */

	/* ring and transport bits (28 to 41) are kept for the transport */
	for (i = VIRTIO_TRANSPORT_F_START; i < VIRTIO_TRANSPORT_F_END; i++)
		if (virtio_features_test_bit(device_features, i))
			__virtio_set_bit(dev, i);

	err = dev->config->finalize_features(dev);    /* the transport may clear bits */
	if (drv->validate)
		err = drv->validate(dev);             /* re-finalized if it changed bits */

	err = virtio_features_ok(dev);       /* set FEATURES_OK, read it back */
	err = drv->probe(dev);
	if (!(dev->config->get_status(dev) & VIRTIO_CONFIG_S_DRIVER_OK))
		virtio_device_ready(dev);             /* sets DRIVER_OK */
	if (drv->scan)
		drv->scan(dev);
	virtio_config_core_enable(dev);      /* deliver config interrupts */
	return 0;
err:
	virtio_add_status(dev, VIRTIO_CONFIG_S_FAILED);
	return err;
}

Several rules follow from that order. The core grants ring and transport features without the driver asking, and vring_transport_features() in virtio_ring.c then clears whichever of them the ring code does not implement; the PCI transport keeps SR-IOV, queue reset, and the admin queue on top. validate() runs after negotiation but before FEATURES_OK, so it is the place to drop a feature the device offered but cannot honor; virtnet_validate() clears VIRTIO_NET_F_MTU when the advertised MTU is below 68. virtio_features_ok() also applies a platform policy. The memory-access callback that a confidential guest installs (virtio_require_restricted_mem_acc(), §8.4) makes it fail any device that did not negotiate both VERSION_1 and ACCESS_PLATFORM, and a device that clears FEATURES_OK produces "device refuses features". A driver whose probe() must post buffers before it returns, as virtio-net does to fill its receive queues, calls virtio_device_ready() itself first. The scan() hook runs after DRIVER_OK, so it is the place for work that already needs live queues, such as registering virtio-rng's hwrng, which immediately reads from the device.

Configuration space has its own rules. virtio_cread() and virtio_cwrite() take the configuration structure type and member name and apply the right endianness conversion. virtio_cread_feature() reads a field only if its feature bit was negotiated and returns -ENOENT otherwise. Wide or multi-field reads go through __virtio_cread_many(), which retries until the transport's generation counter is unchanged, because the device may update the space between two 32-bit accesses. A configuration-change interrupt reaches virtio_config_changed(), which calls the driver's config_changed() under a spinlock with interrupts disabled. Drivers therefore schedule work from it, as virtio-net does for link state and virtio-blk does for capacity changes. Until probe completes, and again whenever a driver calls virtio_config_driver_disable(), the core only records that a change is pending and delivers it later.

Teardown mirrors probe. virtio_dev_remove() disables configuration callbacks and calls the driver's remove(), which must reset the device with virtio_reset_device() before freeing its queues, so the device stops touching their memory. The core warns if the status byte is not zero afterward, and then sets ACKNOWLEDGE again so that another driver can bind to the device. Suspend and resume use freeze() and restore(), and since 6.14 reset_prepare() and reset_done() handle a PCIe function-level reset. In both cases the core repeats the reset and feature negotiation itself and calls the driver to rebuild its queues. On shutdown the core breaks every queue with virtio_break_device() and resets the device, so that it stops DMA before the IOMMU is torn down; a driver can supply shutdown() (6.15) instead, as virtio-gpu does. A broken queue is the general response to a device that misbehaves. Its operations fail, and virtqueue_is_broken() lets a driver stop waiting for it. For testing, CONFIG_VIRTIO_DEBUG (6.10) creates /sys/kernel/debug/virtio/<device>/, which shows the offered device_features and lets a developer mask individual bits through filter_feature_add before rebinding the driver, a quick way to exercise fallback paths without changing the device.

Two small modules sit beside the core. drivers/virtio/virtio_anchor.c (6.0) is always built in (CONFIG_VIRTIO_ANCHOR) even when virtio itself is a module, because it holds virtio_check_mem_acc_cb, the policy hook that architecture code sets early in boot with virtio_set_mem_acc_cb(). x86 memory encryption and s390 protected virtualization install virtio_require_restricted_mem_acc(), the policy that virtio_features_ok() enforces above, and Xen installs xen_virtio_restricted_mem_acc() (§9.4). drivers/virtio/virtio_dma_buf.c (5.10) lets one virtio device share a buffer with another. An exporter wraps dma_buf_export() with virtio_dma_buf_export() and supplies a get_uuid() operation, and an importer that finds is_virtio_dma_buf() true calls virtio_dma_buf_get_uuid() to name the same host-side object in its own requests instead of copying the data. virtio-gpu exports its buffer objects this way when the device offers VIRTIO_GPU_F_RESOURCE_UUID, asking the host for the UUID with a RESOURCE_ASSIGN_UUID command.

Virtqueues and the Ring Implementation

A virtqueue is a queue of buffers. The driver adds a buffer as a chain of descriptors, each giving an address and length, with the device-readable parts first and the device-writable parts after them. The device returns the chain's head with the number of bytes it wrote. The specification defines two memory layouts for this, declared for Linux in include/uapi/linux/virtio_ring.h. The split layout has three areas. The descriptor table is an array of 16-byte struct vring_desc (addr, len, flags, next), with VRING_DESC_F_NEXT to chain and VRING_DESC_F_WRITE to mark a buffer the device writes. The available ring (struct vring_avail) is written only by the driver: an array of chain heads and a free-running idx. The used ring (struct vring_used) is written only by the device: {id, len} pairs and its own idx. Each area has a single writer, which suits a device that is software reading memory through caches. The queue size is a power of two up to 32,768.

The packed layout (virtio 1.1, Linux 5.0) folds all three into one ring of 16-byte struct vring_packed_desc (addr, len, id, flags). The driver writes descriptors into the ring in order and marks them available with the AVAIL (bit 7) and USED (bit 15) flags set relative to a wrap counter that flips each time the ring wraps. The device writes used descriptors back into the same slots, returning the buffer id. Driver and device then touch fewer cache lines per buffer, and a hardware device can fetch descriptors with one sequential DMA read, which is why virtio hardware favors the packed layout. Indirect descriptors (VIRTIO_RING_F_INDIRECT_DESC) work with both layouts: one ring slot points to a separately allocated table holding the whole chain, so a request with many scatter-gather elements uses one slot.

Notifications are expensive for a virtual device, because a kick is a VM exit and an interrupt is an injection, so both sides suppress them. Without EVENT_IDX, each side sets a flag that asks the other not to notify (VRING_AVAIL_F_NO_INTERRUPT and VRING_USED_F_NO_NOTIFY). With it, each side publishes an index instead: the driver writes used_event at the end of the available ring, the device writes avail_event at the end of the used ring, and the other side notifies only when its own index moves past that value. The test, shared by both sides through include/uapi/linux/virtio_ring.h, is vring_need_event(): (u16)(new_idx - event_idx - 1) < (u16)(new_idx - old), true when the event index falls in the batch just published, with wraparound handled by 16-bit arithmetic. The packed layout has an equivalent pair of event-suppression structures with enable, disable, and descriptor-specific modes.

drivers/virtio/virtio_ring.c (about 3,900 lines) implements both layouts behind struct vring_virtqueue, which embeds the public struct virtqueue and records the layout as one of four values: split, packed, and since 7.0 an in-order variant of each, used when VIRTIO_F_IN_ORDER is negotiated and the device promises to return buffers in the order it received them, so the driver can reclaim descriptors without walking chains. Each layout has a struct virtqueue_ops table, but the public functions dispatch through VIRTQUEUE_CALL(), a switch on the layout that calls the right function directly, because an indirect call per buffer would cost a retpoline. The transport creates queues with vring_create_virtqueue(), passing its notify function and the driver's callback. For the split layout the ring memory is one physically contiguous allocation, and if it cannot be found the size is halved until it fits when the transport allows it (may_reduce_num). Barriers come from weak_barriers. A device emulated by software on another CPU needs only the SMP barriers virt_mb() and virt_wmb(), but a real device needs mb() and dma_wmb(), so negotiating VIRTIO_F_ORDER_PLATFORM clears weak_barriers. Buffers are DMA mapped when vring_use_map_api() says so, which is when ACCESS_PLATFORM was negotiated or the guest is a Xen domain. A legacy device without that feature is assumed to see guest-physical addresses directly.

The driver's bookkeeping never relies on the shared ring. Free descriptors are chained through a private struct vring_desc_extra array, which also keeps each descriptor's DMA address, length, and flags, so unmapping a completed buffer does not read back descriptors that the device could have rewritten. Per-head state holds the caller's token and any indirect table. vq.num_free counts free slots, and an add that needs more returns -ENOSPC. A chain uses an indirect table when the device supports one, the chain has more than one element, and a slot is free. The table is allocated with the caller's GFP flags, minus __GFP_HIGHMEM, and if that allocation fails the chain falls back to direct descriptors. Inside the split ring's single allocation, whose size vring_size() computes, legacy PCI requires the used ring to start on a 4,096-byte boundary (VIRTIO_PCI_VRING_ALIGN), while modern devices need only SMP_CACHE_BYTES. Under IN_ORDER a device may write a single used element for a whole batch, and the driver then returns each earlier buffer with the full device-writable length it posted (total_in_len) and the last with the length the device reported. A used element whose ID is out of range or not an outstanding head goes to BAD_RING(), which logs the error and breaks the queue. Defining DEBUG at the top of virtio_ring.c turns that into BUG(), makes START_USE() panic when two contexts use one queue at once, which quickly finds a missing lock, and warns when more than 100 ms pass between adding a buffer and kicking.

The driver-facing API is small. virtqueue_add_sgs() posts a chain from arrays of scatterlists, the first out_sgs device-readable and the next in_sgs device-writable, with an opaque token returned on completion; virtqueue_add_outbuf() and virtqueue_add_inbuf() are the one-direction forms. virtqueue_kick() notifies if suppression allows it. It is virtqueue_kick_prepare(), which takes the barrier and makes the suppression decision, followed by virtqueue_notify(), which calls the transport, and drivers that hold a lock while adding buffers call the two separately so the expensive notification happens after the lock is dropped. virtqueue_get_buf() returns the next completed token and the byte count the device reports. The queue does no locking of its own: the caller must serialize every operation on one virtqueue, usually with a per-queue spinlock. The callback passed to find_vqs runs from vring_interrupt() in hard-interrupt context, so the usual completion handler disables callbacks, drains the queue, and re-enables them, looping if virtqueue_enable_cb() reports that more buffers arrived in the window: 

static void my_done(struct virtqueue *vq)          /* hard-IRQ context */
{
	struct my_dev *md = vq->vdev->priv;
	struct my_req *req;
	unsigned int len;
	unsigned long flags;

	spin_lock_irqsave(&md->lock, flags);
	do {
		virtqueue_disable_cb(vq);
		while ((req = virtqueue_get_buf(vq, &len)) != NULL) {
			req->len = min(len, req->buf_len);   /* never trust len */
			complete(&req->done);
		}
	} while (!virtqueue_enable_cb(vq));          /* raced with the device */
	spin_unlock_irqrestore(&md->lock, flags);
}

The length is a value written by the device, and so is everything else it writes. A driver must bound it before use, for the reasons §9.5 gives. virtqueue_enable_cb_delayed() asks for the interrupt only after about three-quarters of the outstanding buffers complete, which suits transmit queues, and virtqueue_poll() lets a NAPI handler check for work without enabling interrupts. Newer interfaces serve high-performance drivers. virtqueue_resize() (6.0) and virtqueue_reset() (6.6) rebuild one queue while the others keep running, which is what ethtool -G on virtio-net uses. The _premapped add functions (6.13) take buffers the driver has already mapped, which AF_XDP zero copy needs. Such drivers map buffers with virtqueue_map_single_attrs() and its relatives, which were added in 6.6 as virtqueue_dma_*() and renamed in 6.18 when virtio_map_ops arrived, so that the mapping goes through the transport's map operations when it has them. And virtqueue_add_inbuf_cache_clean() (7.0) marks a device-writable buffer that shares a cache line with CPU-written data as safe for the DMA debugging code, for structures laid out with __dma_from_device_group_begin().

Transports

virtio-pci is the transport on x86 and the most common one on ARM64 servers. Its devices use vendor ID 0x1af4, which Qumranet donated before Red Hat bought it. Device IDs 0x1000 to 0x103f are transitional devices that speak both interfaces, with the virtio type in the PCI subsystem device ID, and 0x1040 plus the virtio type is a modern-only device, such as 0x1041 for a NIC. virtio_pci_probe() in drivers/virtio/virtio_pci_common.c tries the modern interface first and falls back to the legacy one (CONFIG_VIRTIO_PCI_LEGACY), whose registers sit in I/O port BAR 0 in guest byte order. A modern device describes its registers with vendor-specific PCI capabilities, each a struct virtio_pci_cap naming a BAR, an offset, and a length: COMMON_CFG (1) for features, status, and queue setup; NOTIFY_CFG (2) for the kick addresses; ISR_CFG (3) for the interrupt status byte used without MSI-X; DEVICE_CFG (4) for configuration space; PCI_CFG (5), a window through configuration space for firmware that cannot map BARs; and SHARED_MEMORY_CFG (8) for regions such as the virtio-fs DAX window. The parsing code is a library, virtio_pci_modern_dev.c (5.12), that vp_vdpa reuses to drive a virtio-pci device as a vDPA device.

struct virtio_pci_common_cfg is a window, not a list. The driver writes device_feature_select to choose which 32 bits of features device_feature shows, and writes queue_select to choose which queue's queue_size, queue_msix_vector, the queue_desc, queue_avail, and queue_used address pairs, and queue_enable it is looking at. Each queue's kick address is the notify capability's base plus its queue_notify_off times notify_off_multiplier, and vp_notify() writes the queue index there with one 16-bit store, the store a VMM catches with an ioeventfd (§7.3). With VIRTIO_F_NOTIFICATION_DATA, vp_notify_with_data() writes the queue's next available position as well, so hardware need not read the ring to learn how far to fetch. Interrupts use MSI-X when available. Without it, vp_find_vqs() falls back to shared INTx with the ISR byte, which reports bit 0 for a queue event and bit 1 for a configuration change.

Fields added after virtio 1.0 sit in struct virtio_pci_modern_common_cfg, which extends the common structure with queue_notify_data, queue_reset, admin_queue_index, and admin_queue_num. An older device's capability is shorter, so vp_modern_probe() records the length it mapped, and vp_finalize_features() refuses NOTIF_CONFIG_DATA, RING_RESET, or ADMIN_VQ if the field that the feature needs lies beyond it. MSI-X allocation has three steps, the second added in 6.11: one vector per queue plus one for configuration changes and one for the admin queue; then the same with the admin queue, a slow path, sharing the configuration vector; and then one vector for configuration changes and one shared by all queues. The vectors appear in /proc/interrupts under the device's name: virtio0-config, virtio0-input.0 for a per-queue vector, named after the queue, or virtio0-virtqueues when the queues share one. That is the first thing to check when a guest's interrupts look wrong. When the driver passes an affinity descriptor, the vectors are managed interrupts that the IRQ core spreads across CPUs. Otherwise vp_set_vq_affinity() sets an affinity hint, as virtio-net does for its queue pairs. The force_legacy module parameter makes a transitional device use its legacy interface, which is how a device's legacy path is tested.

The administration virtqueue (virtio 1.3, Linux 6.8) lets a PCI physical function manage its SR-IOV virtual functions. vp_modern_admin_cmd_exec() sends commands that query and select the supported command set, read and write a member's legacy registers, and, since 6.13, create device-state objects, read and write device parts, and stop or freeze a member for migration. drivers/vfio/pci/virtio/ builds on it. It binds to a virtio-net VF and offers it to a VM through VFIO (§8.3), translating accesses to an emulated legacy I/O BAR into admin commands on the PF, so a guest with only a legacy driver can use a hardware VF, and implements VFIO live migration by moving the VF's device state through the PF.

virtio-mmio (drivers/virtio/virtio_mmio.c) is a block of 32-bit registers for platforms without PCI, used by many ARM64 VMMs, Firecracker, and most embedded hypervisors. The block begins with the magic value 0x74726976 ("virt" in little-endian ASCII) and a version: 1 is legacy and 2 is modern, which requires VERSION_1. DeviceID at 0x008 gives the device type, and 0 means "no device here", so a VMM can reserve slots that the driver skips with -ENODEV. The rest follows the same window pattern as PCI: QueueSel at 0x030, the queue size, ring addresses, and QueueReady registers, QueueNotify at 0x050 for kicks, InterruptStatus and InterruptACK at 0x060 and 0x064, Status at 0x070, ConfigGeneration at 0x0fc, and configuration space from 0x100. A version 1 device has no separate ring addresses. The driver writes the page size to GuestPageSize (0x028) once and, for each queue, the alignment to QueueAlign (0x03c) and the page frame number of the whole contiguous split ring to the 32-bit QueuePFN (0x040), so vm_setup_vq() refuses a ring placed above what 32 bits of page frame number can reach. Version 2 replaces these with a 64-bit address for each area (0x080 to 0x0a4) and QueueReady (0x044). One interrupt line serves the whole device, and vm_interrupt() reads the status register to tell a queue event from a configuration change. Discovery is by device tree ("virtio,mmio"), ACPI (LNRO0005), or, with CONFIG_VIRTIO_MMIO_CMDLINE_DEVICES, the kernel command line, as in virtio_mmio.device=4K@0xa000000:48, which is how Firecracker describes devices without firmware tables. A child node with compatible = "virtio,device22" (the type in hexadecimal) becomes the virtio device's of_node, so a virtio-i2c or virtio-gpio controller can have child devices described in the device tree (Chapter 13, §5.2).

The other transports follow the same pattern. drivers/s390/virtio/virtio_ccw.c uses channel command words, such as CCW_CMD_READ_FEAT and CCW_CMD_SET_VQ, and kicks with a hypercall. drivers/virtio/virtio_vdpa.c presents any vDPA device to the host kernel as a virtio device, so the host can use a SmartNIC's virtio queues, or a VDUSE device, with the ordinary virtio-net or virtio-blk driver. drivers/remoteproc/remoteproc_virtio.c creates virtio devices from a remote processor's firmware resource table, the basis of rpmsg. User-mode Linux's arch/um/drivers/virtio_uml.c speaks vhost-user over a UNIX socket, so UML can use device back ends written for QEMU, and drivers/platform/mellanox/mlxbf-tmfifo.c carries console and network virtqueues over a hardware FIFO between a BlueField DPU and its host. Xen guests use the PCI and MMIO transports, but with grant-table DMA operations (drivers/xen/grant-dma-ops.c, 5.19). When a device's device-tree node names a "xen,grant-dma" node as its IOMMU, or in a PV guest, or with CONFIG_XEN_VIRTIO_FORCE_GRANT, xen_virtio_restricted_mem_acc() installs these operations on the device's parent and makes the device negotiate ACCESS_PLATFORM. Every address the driver puts in a ring is then a grant reference with bit 63 set rather than a guest frame, so the backend domain can map only the pages it was granted. Writing a virtio Driver

A virtio driver has two halves: the virtio half, which is nearly the same for every device, and the subsystem half, which registers a network device, a block device, a hwrng, or a sound card. The smallest complete example in the tree is virtio-rng (drivers/char/hw_random/virtio-rng.c, about 260 lines), and Documentation/driver-api/virtio/writing_virtio_drivers.rst gives a dummy skeleton. The virtio half of a driver for a hypothetical device with a request queue, an event queue, and one optional configuration field looks like this: 

#include <linux/module.h>
#include <linux/virtio.h>
#include <linux/virtio_config.h>
#include <uapi/linux/virtio_foo.h>        /* config struct, VIRTIO_FOO_F_* */

struct foo_dev {
	struct virtio_device *vdev;
	struct virtqueue *req_vq, *evt_vq;
	spinlock_t lock;                  /* serializes req_vq */
	struct work_struct config_work;
	u32 max_len;
};

static int foo_init_vqs(struct foo_dev *fd)
{
	struct virtqueue_info vqs_info[] = {
		{ "requests", foo_req_done },     /* completion loop shown earlier */
		{ "events",   foo_evt_done },
	};
	struct virtqueue *vqs[2];
	int err;

	err = virtio_find_vqs(fd->vdev, 2, vqs, vqs_info, NULL);
	if (err)
		return err;
	fd->req_vq = vqs[0];
	fd->evt_vq = vqs[1];
	return 0;
}

static void foo_del_vqs(struct foo_dev *fd)
{
	struct virtio_device *vdev = fd->vdev;
	void *buf;

	virtio_reset_device(vdev);        /* the device stops using the rings */
	while ((buf = virtqueue_detach_unused_buf(fd->evt_vq)))
		kfree(buf);
	vdev->config->del_vqs(vdev);
}

static int foo_probe(struct virtio_device *vdev)
{
	struct foo_dev *fd;
	int err;

	fd = kzalloc(sizeof(*fd), GFP_KERNEL);
	if (!fd)
		return -ENOMEM;
	fd->vdev = vdev;
	vdev->priv = fd;
	spin_lock_init(&fd->lock);
	INIT_WORK(&fd->config_work, foo_config_work);

	if (virtio_cread_feature(vdev, VIRTIO_FOO_F_MAX_LEN,
				 struct virtio_foo_config, max_len, &fd->max_len))
		fd->max_len = PAGE_SIZE;  /* feature not negotiated */

	err = foo_init_vqs(fd);
	if (err)
		goto out_free;

	virtio_device_ready(vdev);        /* DRIVER_OK before the first kick */
	err = foo_fill_evt_vq(fd);        /* virtqueue_add_inbuf(), virtqueue_kick() */
	if (err)
		goto out_del;
	return 0;                         /* subsystem registration, omitted */

out_del:
	foo_del_vqs(fd);
out_free:
	kfree(fd);
	return err;
}

static void foo_remove(struct virtio_device *vdev)
{
	struct foo_dev *fd = vdev->priv;

	cancel_work_sync(&fd->config_work); /* the core disabled config_changed */
	foo_del_vqs(fd);
	kfree(fd);
}

static void foo_config_changed(struct virtio_device *vdev)
{
	struct foo_dev *fd = vdev->priv;

	schedule_work(&fd->config_work);  /* called under a spinlock */
}

static int foo_freeze(struct virtio_device *vdev)
{
	foo_del_vqs(vdev->priv);
	return 0;
}

static int foo_restore(struct virtio_device *vdev)
{
	struct foo_dev *fd = vdev->priv;
	int err = foo_init_vqs(fd);       /* the core has renegotiated features */

	if (err)
		return err;
	virtio_device_ready(vdev);
	return foo_fill_evt_vq(fd);
}

static const struct virtio_device_id id_table[] = {
	{ VIRTIO_ID_FOO, VIRTIO_DEV_ANY_ID },
	{ 0 },
};

static const unsigned int features[] = {
	VIRTIO_FOO_F_MAX_LEN,
};

static struct virtio_driver foo_driver = {
	.driver.name        = KBUILD_MODNAME,
	.id_table           = id_table,
	.feature_table      = features,
	.feature_table_size = ARRAY_SIZE(features),
	.probe              = foo_probe,
	.remove             = foo_remove,
	.config_changed     = foo_config_changed,
	.freeze             = pm_sleep_ptr(foo_freeze),
	.restore            = pm_sleep_ptr(foo_restore),
};
module_virtio_driver(foo_driver);
MODULE_DEVICE_TABLE(virtio, id_table);
MODULE_DESCRIPTION("virtio foo driver");
MODULE_LICENSE("GPL");

The feature table lists only device-specific bits; the core supplies the ring and transport bits. Only listed bits can be negotiated, so a driver never sees behavior it did not ask for. A driver that needs different bits from a legacy device supplies feature_table_legacy as well, as virtio-blk and virtio-net do. The virtqueue_info array (6.11) pairs each queue's name with its callback; a NULL name skips a queue the driver does not use, and setting ctx gives a queue a per-buffer context pointer, which virtio-net uses for mergeable receive buffers. A driver with one queue per CPU passes an irq_affinity descriptor so that the transport spreads the MSI-X vectors, and the bus's irq_get_affinity() (§9.2) then lets the block layer match its queues to them. remove() resets the device before it frees anything, and a device that holds buffers the driver posted returns none of them after the reset, so virtqueue_detach_unused_buf() reclaims them. freeze() and restore() are the same teardown and setup. The device is reset across suspend, so the driver repeats everything except allocating its own state.

The skeleton leaves out the request path, which is where most driver bugs are. A request that sends a header and some data and receives a status byte is posted as one chain of three scatterlist entries, two device-readable and one device-writable: 

struct foo_req {
	struct completion done;           /* written by the CPU */
	__dma_from_device_group_begin();
	struct virtio_foo_req_hdr hdr;    /* device-readable */
	u8 status;                        /* device-writable */
	__dma_from_device_group_end();
};

static int foo_submit(struct foo_dev *fd, struct foo_req *req,
		      void *data, unsigned int data_len)
{
	struct scatterlist hdr_sg, data_sg, status_sg;
	struct scatterlist *sgs[] = { &hdr_sg, &data_sg, &status_sg };
	unsigned long flags;
	bool notify;
	int err;

	sg_init_one(&hdr_sg, &req->hdr, sizeof(req->hdr));
	sg_init_one(&data_sg, data, data_len);    /* kmalloc()ed, never the stack */
	sg_init_one(&status_sg, &req->status, sizeof(req->status));
	init_completion(&req->done);

	spin_lock_irqsave(&fd->lock, flags);
	err = virtqueue_add_sgs(fd->req_vq, sgs, 2, 1, req, GFP_ATOMIC);
	notify = !err && virtqueue_kick_prepare(fd->req_vq);
	spin_unlock_irqrestore(&fd->lock, flags);
	if (err)
		return err;                       /* -ENOSPC: ring full, retry later */
	if (notify)
		virtqueue_notify(fd->req_vq);     /* the VM exit, outside the lock */
	return 0;
}

Every buffer in a chain must be memory that the DMA API can map: memory from kmalloc() or the page allocator, never the stack (which is in vmalloc space with CONFIG_VMAP_STACK) and never a vmalloc() buffer passed to sg_init_one(), which assumes a linear-map address. The device-writable part must not share a cache line with fields the CPU writes while the request is in flight, because on a platform without coherent DMA the CPU's write-back can overwrite what the device wrote. The __dma_from_device_group_begin() markers align the DMA fields to ARCH_DMA_MINALIGN, as virtio-gpio, virtio-input, virtio-scsi, and vsock do. The GFP flags passed to the add function are used for an indirect table (§9.3), so they must match the context: GFP_ATOMIC under a spinlock. A full ring is normal, not an error. virtio-blk stops the blk-mq hardware queue on -ENOSPC and restarts it from its completion handler, but it does not stop the queue on -ENOMEM, since no completion is guaranteed to arrive to restart it. Batching kicks matters as much as anything else for performance. virtio-blk kicks only for the last request of a blk-mq batch, and virtio-net only when the stack has no more packets queued (netdev_xmit_more()). In Kconfig, a driver depends on VIRTIO, a symbol with no prompt that each transport selects, so the driver can be built only when some transport is.

A driver must also decide how far to trust its device. When virtio began, the device was the hypervisor, which could read all of guest memory anyway, so drivers believed what it wrote. In a confidential guest (§8.4) the host is outside the trust boundary, and every value the device writes is untrusted input: used lengths, IDs, configuration fields, and the contents of replies. The core does little of this checking for the driver. Validating used lengths in the ring code was merged for 5.16 and reverted before the release, because several devices, legacy ones in particular, report wrong lengths that their drivers had learned to ignore. CONFIG_VIRTIO_HARDEN_NOTIFICATION (5.19) keeps every queue broken until DRIVER_OK and breaks the queues again in virtio_reset_device(), so that a callback cannot run against a half-initialized or half-torn-down driver, but too many drivers did not cope with it, and it has depended on BROKEN since 6.0. A new driver should therefore check every device-written length and index before using it, prefer fixed-size replies, treat a malformed reply as an I/O error, and use virtio_break_device() when the device is clearly misbehaving instead of crashing the guest.

Adding a new device type, rather than a driver for an existing one, starts with the specification. Appendix B of virtio 1.4, "Creating New Device Types", sets out the rules. Device IDs are assigned by the OASIS virtio technical committee, requested on the virtio-comment@lists.linux.dev list, and an experimental device uses an ID counting down from 65535 until one is assigned. Configuration space is for initialization-time parameters. Anything that changes at run time, or could grow large, belongs in a virtqueue, as virtio-net's control queue carries its receive filters, and no writable field that triggers an action should be wider than 32 bits, because a driver may not be able to write it atomically. Every later change to the device, such as a new configuration field, a new queue, or new behavior, needs a new feature bit. PCI devices should also budget their MSI-X vectors, since a system may have as few as 256 in total. The kernel side then follows writing_virtio_drivers.rst, which says that an ID must be at least reserved in the specification before it is added to include/uapi/linux/virtio_ids.h. The device's configuration structure and request formats go in a new include/uapi/linux/virtio_foo.h, because VMMs and device implementations include them too. Fields use __le16, __le32, and __le64 for a modern-only device, and the __virtio types only if a legacy device exists. The patches go to the virtualization list and the virtio maintainers, Michael S. Tsirkin and Jason Wang, whose VIRTIO CORE entry in MAINTAINERS covers the core, the uapi headers, vDPA, and tools/virtio/. Driver files themselves go to the subsystem the device belongs to, so virtio-snd is reviewed by the ALSA maintainers and virtio-i2c by the I2C maintainers. Implementing the Device Side

A virtio device implementation has the same duties wherever it runs. It presents the transport: PCI configuration space and capabilities, or an MMIO register block. It keeps the status byte, the offered and accepted features, and configuration space. It translates the addresses the driver writes into memory it can reach. It walks the available ring, performs each request, writes the used ring, and notifies. Linux offers several places to put that logic, and a new device type usually passes through more than one of them, starting with the simplest.

The simplest is a device model in the VMM, which is how QEMU, crosvm, Firecracker, and Cloud Hypervisor implement most devices; the Rust VMMs share the virtio-queue crate from the rust-vmm project. The VMM handles the transport registers in its MMIO exit path (§8.1) and records the ring addresses when the driver enables a queue. Those are guest-physical addresses, so it translates them through the same table of memory regions it gave KVM with KVM_SET_USER_MEMORY_REGION2. For the data path it registers an ioeventfd on each queue's notify address, with a datamatch on the queue index for PCI, and an irqfd for each interrupt vector (§7.3), so that an I/O thread processes the queue without returning from KVM_RUN. The processing is a loop. Read the available index with acquire ordering, follow each chain, do the work, write the used element, publish the used index with release ordering, and signal the irqfd only if vring_need_event() against used_event says the driver wants it. Every value in the ring comes from the guest and must be checked: each address and length against guest memory, the chain length against the queue size so that a descriptor loop cannot hang the device, and indirect tables for nesting. A write of 0 to the status byte must stop all processing and forget the rings. Most security bugs in virtio device models have been in exactly these checks.

When the data path must be in the host kernel, the device becomes a vhost backend. The VMM still owns the control plane and hands the rings over with the ioctls of §8.2. The kernel side is a character device that calls vhost_dev_init() with its virtqueues and the weights that bound one pass of the worker, passes the generic ioctls to vhost_dev_ioctl() and vhost_vring_ioctl(), and adds one of its own to attach a backend with vhost_vq_set_backend(). The handler for a queue then uses the vhost ring API. drivers/vhost/test.c, the backend for the ring tests, is the smallest example: 

static void handle_vq(struct vhost_test *n)      /* runs in the vhost worker */
{
	struct vhost_virtqueue *vq = &n->vqs[VHOST_TEST_VQ];
	unsigned int out, in;
	size_t len, total_len = 0;
	int head;

	mutex_lock(&vq->mutex);
	if (!vhost_vq_get_backend(vq))
		goto out;
	vhost_disable_notify(&n->dev, vq);           /* no kicks while we poll */
	for (;;) {
		head = vhost_get_vq_desc(vq, vq->iov, ARRAY_SIZE(vq->iov),
					 &out, &in, NULL, NULL);
		if (unlikely(head < 0))
			break;                       /* malformed chain: stop */
		if (head == vq->num) {               /* ring empty */
			if (unlikely(vhost_enable_notify(&n->dev, vq))) {
				vhost_disable_notify(&n->dev, vq);
				continue;            /* raced with the guest */
			}
			break;
		}
		len = iov_length(vq->iov, out);      /* out iovecs: guest data */
		vhost_add_used_and_signal(&n->dev, vq, head, 0);
		total_len += len;
		if (unlikely(vhost_exceeds_weight(vq, 0, total_len)))
			break;                       /* requeue; let others run */
	}
out:
	mutex_unlock(&vq->mutex);
}

vhost_get_vq_desc() does the validation that a VMM device model must do by hand. It translates every descriptor into user-space iovecs through the memory table or the device IOTLB, rejects loops and out-of-range addresses, and splits the chain into out device-readable and in device-writable entries. The backend then moves data with ordinary copy_from_iter() and copy_to_iter() or hands the iovecs to a socket or file. vhost_add_used_and_signal() writes the used element and signals the call eventfd only if event suppression allows it. vhost implements only the split layout: VHOST_FEATURES offers indirect descriptors, event index, VERSION_1, and dirty logging, but not RING_PACKED. In-tree backends are net, scsi, vsock, and test, and a new one is a large commitment, because it puts a guest-facing parser into the host kernel.

vhost-user moves the same protocol out of the kernel. The VMM sends the memory table, as file descriptors of the shared guest memory, and the kick and call eventfds over a UNIX socket to a separate process, which maps guest memory and runs the ring loop itself. DPDK's virtio-net switch, virtiofsd, and many storage targets work this way, and the rust-vmm vhost-user-backend crate is a common starting point. The kernel's only part is KVM's eventfds, and that is what makes vhost-user attractive for a new device type. A crash stays in one process, the process can be sandboxed, and the device can be developed with ordinary user-space tools.

vDPA (virtio data path acceleration, drivers/vdpa/, 5.7) is for hardware whose queues are virtio rings but whose control path is vendor-specific. A vDPA driver registers a struct vdpa_device whose struct vdpa_config_ops in include/linux/vdpa.h mirrors the virtio interface: device operations (get_device_features(), set_driver_features(), get_status(), set_status(), reset(), get_config(), set_config()), per-queue operations (set_vq_address(), set_vq_num(), set_vq_ready(), set_vq_cb(), kick_vq(), get_vq_state(), and set_vq_state()), and DMA operations for devices with their own translation (set_map(), dma_map(), dma_unmap()). A vDPA device is then bound to one of two bus drivers. vhost_vdpa exposes it to a VMM as /dev/vhost-vdpa-N, and the hardware reads guest memory directly through the IOMMU. Through get_vq_notification() it can even map the device's doorbell page into the guest, so a kick reaches hardware without a VM exit. virtio_vdpa gives it to the host kernel's own virtio drivers instead. In-tree drivers cover NVIDIA (mlx5), Intel (ifcvf), AMD Pensando (pds), Marvell (octeon_ep), Alibaba, and SolidRun hardware, plus drivers/vdpa/virtio_pci/, which drives a virtio-pci device as a vDPA device, and drivers/vdpa/vdpa_sim/, software net and block devices for testing.

Around the data path, vDPA has a management interface and the hooks that live migration needs. The vdpa generic-netlink family in drivers/vdpa/vdpa.c lists the management devices that parent drivers register with vdpa_mgmtdev_register(), and routes iproute2's vdpa dev add, vdpa dev del, and vdpa dev set to their dev_add(), dev_del(), and dev_set_attr(). A virtio-net device takes attributes such as its MAC address, MTU, and maximum number of queue pairs. vdpa dev config show reads the configuration space back. vhost-vdpa's own ioctls (VHOST_VDPA_GET_DEVICE_ID, VHOST_VDPA_SET_STATUS, VHOST_VDPA_GET_CONFIG, VHOST_VDPA_SET_VRING_ENABLE, and others) give the VMM the rest of the virtio control path, and the VHOST_BACKEND_F_* bits negotiate the optional parts. A queue's interrupt can skip the VMM. When the parent implements get_vq_irq(), vhost-vdpa registers the interrupt as an irqbypass producer, so with posted interrupts (§7.2) the device interrupts the vCPU directly. For migration, suspend() and resume() (6.0, reached through VHOST_VDPA_SUSPEND and VHOST_VDPA_RESUME) stop and restart processing. get_vq_state() returns where each queue stopped: the available index for a split ring, or the available and used indices and their wrap counters for a packed one. The destination restores them with set_vq_state(). Virtqueue groups and address-space IDs (5.19, set_group_asid()) let a device translate some queues through a separate IOMMU address space. QEMU uses this to shadow the virtio-net control queue, so that it sees the guest's MAC and filter changes and can replay them on the destination while the data queues keep running on guest memory. get_vq_desc_group() (6.7) separates descriptor tables from buffers in the same way, and bind_mm() (6.4) lets a device that works on process virtual addresses, such as vdpa_sim with use_va, use the VMM's address space directly.

VDUSE (vDPA device in user space, drivers/vdpa/vdpa_user/, 5.15) lets a process implement a vDPA device. It writes a struct vduse_dev_config (name, device type, features, number of queues, and the initial configuration space) to VDUSE_CREATE_DEV on /dev/vduse/control, sets up each queue with VDUSE_VQ_SETUP, and then serves /dev/vduse/<name>. read() returns requests such as VDUSE_SET_STATUS and VDUSE_UPDATE_IOTLB, answered with write(). VDUSE_IOTLB_GET_FD returns a file to mmap() the memory the driver uses, which is a bounce buffer when the driver is the host kernel's, so the process never sees arbitrary kernel memory. VDUSE_VQ_GET_INFO returns the ring addresses, VDUSE_VQ_SETUP_KICKFD attaches an eventfd for kicks, and VDUSE_VQ_INJECT_IRQ signals completion. Because a host-kernel driver then depends on a user-space process, VDUSE accepts only block, net (6.10, with CAP_NET_ADMIN), and file-system (6.15) devices. API version 1 (7.0) adds queue groups and address spaces, so that a control queue can be translated separately from the data queues.

vringh (drivers/vhost/vringh.c, 3.10) is the device-side ring library for code that is neither vhost nor a VMM. It walks a split ring held in user memory, kernel memory, or behind a vDPA IOTLB (vringh_init_user(), vringh_init_kern(), vringh_init_iotlb(), with matching getdesc, complete, and need_notify functions). vdpa_sim uses it to emulate devices, mlx5 uses it for the control queue that its hardware does not implement, and CAIF uses it to serve a modem's rings.

Linux also provides the tools to test a device implementation. tools/virtio/virtio_test.c builds the guest's virtio_ring.c as a user-space program and runs it against the vhost_test module, so one process exercises both sides of the ring. vringh_test does the same for vringh, and tools/virtio/ringtest/ benchmarks alternative ring layouts. vdpa_sim gives virtio_vdpa and vhost_vdpa a device to talk to without hardware, and the virtio debugfs feature filter (§9.2) makes it easy to check a device against a driver that accepts fewer features. tools/virtio/vhost_net_test.c (6.9) runs the guest ring code against vhost-net and a tap device. The selftests in tools/testing/selftests/drivers/net/virtio_net/ (6.10) run in a guest with two virtio-net interfaces whose host tap devices are wired back to back with a tc mirred redirect, and check the device features end to end. tools/virtio/virtio-trace/ is a guest agent that splices ftrace ring-buffer pages to the host over virtio-serial ports, which is useful for tracing a guest driver and the host device together. A typical path for a new device type is to reserve an ID and write the specification text, add the uapi header and the Linux driver, prototype the device in a VMM or as a vhost-user back end, and only move the data path into vhost or hardware through vDPA when measurements call for it. The driver does not change at any step, which is the point of the framework.

Summary

KVM turns Linux into a hypervisor without writing a second operating system. A virtual machine is a process, each vCPU is a thread that spends most of its life inside KVM_RUN, and guest RAM is ordinary anonymous or file-backed memory in that process. The scheduler, the page allocator, cgroups, and the rest of the kernel work on virtual machines exactly as they work on any other workload. What KVM adds is the narrow layer that hardware virtualization needs: entering and leaving guest mode, second-stage page tables, and virtual interrupt controllers and timers.

The user-space interface is a set of file descriptors. /dev/kvm creates VMs, a VM fd owns memslots and devices, and a vCPU fd runs one virtual processor and shares struct kvm_run with the VMM. Capabilities and VM types tell the VMM what the host can do. Every exit KVM cannot finish in the kernel becomes a KVM_EXIT_* code in that page, and the VMM—QEMU, crosvm, Firecracker, or cloud-hypervisor—handles it and calls KVM_RUN again. Other threads reach a vCPU through requests, KVM_REQ_* bits that it checks before every entry, and a kick, an IPI that forces it out of guest mode to see them. On x86, vcpu_enter_guest() drains pending requests, calls the vendor's vcpu_run hook through kvm_x86_ops static calls, and dispatches the exit through kvm_vmx_exit_handlers[] or svm_exit_handlers[]. On ARM64, kvm_arch_vcpu_ioctl_run() enters __kvm_vcpu_run() directly under VHE or through a hypercall to the EL2 object under nVHE and pKVM, and dispatches by the ESR exception class through arm_exit_handlers[]. Both architectures can also host a hypervisor inside a guest: KVM emulates VMX, SVM, or EL2 for it and merges its controls with the host's, on ARM64 with FEAT_NV2 since 6.16.

Memory virtualization rests on memslots, which map guest frame numbers to host virtual addresses, and on a second-stage table built lazily on faults: the TDP MMU for EPT and NPT, and kvm_pgtable for ARM64 stage 2. KVM does not pin guest RAM. MMU notifiers keep the second-stage tables coherent with the host's page tables, so guest memory can be swapped, migrated, compacted, and merged by KSM like any other, and an async page fault lets an x86 guest run another task while the host fetches a page. Live migration builds on the same machinery. Dirty logging reports written pages through a per-slot bitmap or per-vCPU rings, fed by write protection or Intel's PML, and post-copy migration fetches pages on demand through userfaultfd, with no KVM interface of its own.

Confidential computing breaks that model on purpose. guest_memfd provides memory that the VMM never maps, per-page memory attributes record which gfns are private, and a guest that converts a page between private and shared exits to the VMM with KVM_EXIT_MEMORY_FAULT or a hypercall exit. SEV-SNP and TDX enforce the separation in hardware. KVM drives the AMD Secure Processor's launch commands, or calls the TDX module through SEAMCALLs and keeps a mirror of the secure EPT that only the module may write. Arm CCA realms are supported only on the guest side, and pKVM at EL2 so far shields the hypervisor and every guest's stage-2 tables from the host, though not yet guest memory.

Interrupts and timers move into the kernel and then into hardware. The in-kernel LAPIC and vGIC emulate the controllers. APICv, AVIC, and the GIC virtual CPU interface let the guest acknowledge and complete interrupts without exits, and posted interrupts and GICv4 deliver them to a running vCPU directly, even from an assigned device. irqfd and ioeventfd take the VMM off the interrupt and notification paths. Guest timers run on the VMX preemption timer, an hrtimer, or the architected timer itself, steal time tells the guest how long its vCPUs waited for a host CPU, and halt polling spends a little CPU time for faster wake-ups. Performance counters are emulated on host perf events or, on x86 since 7.0, handed to the guest whole by the mediated vPMU.

Devices span the same range. The VMM emulates most of them, and KVM keeps in the kernel only the models whose exits would cost too much: the interrupt controllers and timers, and on x86 the PIT and the Hyper-V and Xen interfaces. Coalesced MMIO lets the VMM batch writes that need no immediate answer. vhost moves a virtio backend into a host kernel worker, and VFIO hands a whole PCI function to the guest behind the IOMMU, which iommufd programs and which can also track the device's dirty pages for migration. Linux as a guest cooperates through paravirtual clocks, steal time, spinlocks, TLB flushes, and memory-return drivers on x86, and through a handful of SMCCC services on ARM64, whose hardware needs far less help.

virtio is the device interface both sides share. A device is a status byte, a set of feature bits that the driver accepts a subset of, a configuration space, and virtqueues in shared memory, in the split layout or the packed one. The core in drivers/virtio/virtio.c runs the reset, feature negotiation, and DRIVER_OK sequence for every driver, and virtio_ring.c implements both ring layouts with event suppression, so a driver supplies a feature table, its queues, and its subsystem code. Transports adapt the core to PCI, MMIO, s390 channel I/O, vDPA, and remote processors. The same device can be implemented by a VMM, by vhost in the host kernel, by a vhost-user process, by vDPA hardware, which adds suspend, queue-state, and address-space hooks so that hardware queues can migrate with the VM, or by a VDUSE process, and a new device type starts with an ID and a feature-bit design in the specification. Because the device may be hostile in a confidential guest, a driver must bound every value the device writes; the core checks only the ring's own IDs.
