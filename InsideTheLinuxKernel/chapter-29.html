Every other chapter of this book describes what the kernel does. This one describes how the kernel tells you what it did, and how you ask it questions while it is running. In Linux 2.6.11, those were nearly the same thing: the kernel had printk(), the oops and panic(), the magic SysRq key, and a kprobes interface that only a kernel module could use. A Linux 7.0.12 kernel has a layered toolkit that you can use on a production machine without rebuilding or rebooting it. A lockless log buffer can take messages from NMI context. Watchdogs notice a CPU that has stopped scheduling. The compiler leaves a patchable call site at the start of almost every function, and the function tracer turns those sites on and off by rewriting kernel text while the system runs. Thousands of static tracepoints cost one no-op instruction when they are disabled. A breakpoint can be planted on almost any kernel or user instruction, and a hardware-counter subsystem can sample every CPU thousands of times a second. Every report the kernel prints can carry a stack trace with symbol names, produced by an unwinder that has to work even in NMI context. x86-64 and ARM64 share almost all of this code. They differ where it touches the hardware: how kernel text is patched, how the stack is unwound, and how a stuck CPU is interrupted. x86-64 has a true NMI, while ARM64 Linux has none and relies on an optional GICv3 pseudo-NMI instead.

This chapter works through that toolkit from the bottom up. It starts with the kernel log and its consoles (§2) and with the code that runs when something goes wrong: BUG(), WARN(), the oops, panic(), the stack unwinders and symbol tables that every report depends on, and the mechanisms that keep the evidence (§3). A full memory image taken by kdump is the subject of Appendix A. The chapter then covers the detectors that watch for stuck CPUs and tasks, and summarizes the sanitizers covered elsewhere in the book (§4). The middle of the chapter is the tracing infrastructure in kernel/trace/: ftrace's live patching of function entries (§5), the per-CPU ring buffer and the tracefs control files (§6), tracepoints and trace events (§7), and the dynamic kprobes, fprobes and uprobes (§8). After that come perf_events in kernel/events/ (§9), and finally the latency tracers, the runtime verification monitors, and the kernel debuggers built on top of all of these (§10). The eBPF programs that make most of these hooks programmable are the subject of Chapter 23. This chapter describes the hooks those programs attach to.

How the Kernel Reports on Itself

The diagnostic code in the kernel is spread across many directories, but it answers a small number of questions. Each question has its own family of mechanisms, with its own buffer and its own user-space interface, and most of those families did not exist in Linux 2.6.11.

1.1 Five Questions, Five Families of Mechanism

The first question is what did the kernel say? Subsystems and drivers write human-readable messages with printk() and its wrappers. The messages go into a single global log, which consoles copy to a serial port or the screen and which user space reads through /dev/kmsg. The second question is what went wrong? Assertions (BUG(), WARN()), exceptions the kernel cannot handle (the oops), and the final panic() all write their reports through printk(). They can also hand the log to persistent storage or to a crash kernel. The third question is is anything stuck, or about to break? Detectors answer it. The soft- and hard-lockup watchdogs notice a CPU that has stopped scheduling or stopped taking interrupts. The hung-task detector notices a task that has slept uninterruptibly for too long, and RCU stall warnings notice a grace period that cannot end. The workqueue watchdog (CONFIG_WQ_WATCHDOG, 4.5) notices a worker pool that has made no progress for workqueue.watchdog_thresh seconds (30 by default) and prints BUG: workqueue lockup. A second group of debug options finds bugs before they hang anything. Lockdep reports a lock-order inversion the first time it sees one, long before the deadlock it could cause. The compiler-instrumented sanitizers (KASAN, KCSAN, UBSAN) catch memory and concurrency errors at the access that commits them. Almost every report from the second and third families carries a stack trace, so the unwinders and symbol tables of §3.5 serve all of them.

The fourth question is what is the kernel doing right now, and in what order? That is the job of the tracing infrastructure. There are static tracepoints, which developers compiled in at interesting places. There is the function tracer (ftrace), which can hook the entry and exit of nearly every kernel function. And there are dynamic probes (kprobes, uprobes, and the fprobes built on the function tracer), which can be placed at run time on almost any kernel instruction, on any user-space instruction, or on a function's entry and exit. All three write binary records into a per-CPU ring buffer that is read through tracefs. The fifth question is where does the time go? perf_events answers it. It counts hardware events such as cycles, instructions and cache misses, and it samples the instruction pointer and call stack when a counter overflows. It also treats tracepoints, kprobes and timers as events, so one interface can count or sample any of them.

Two kinds of question get less space here. The first is what exactly was the state of the kernel when it stopped? kgdb and kdb (§10.4) halt a live kernel in place. A kdump vmcore (Appendix A) preserves the memory of one that crashed, for the crash utility to read. And /proc/kcore presents the memory of the running kernel as an ELF core file that gdb or drgn can open. The second is the steady stream of counters: /proc/meminfo, /proc/vmstat, the per-device statistics in sysfs, and the pressure-stall figures in /proc/pressure/. Those numbers belong to the subsystems that keep them and are described with those subsystems. Chapter 12 covers the pseudo filesystems that export them, and Chapter 25 covers PSI.

Figure 29-1 places these families side by side. The columns are not sealed off from one another. An oops is printed through printk. On x86-64, and on ARM64 kernels that use pseudo-NMI, the hard-lockup detector is a perf_events client that counts CPU cycles; other ARM64 kernels use the buddy detector, in which each CPU watches a neighbor's timer interrupts instead (§4.1). On x86-64 a kprobe on a function's first instruction reuses the ftrace call site there instead of planting a breakpoint; ARM64 lacks that optimization. And the trace events of the fourth column are also perf events and eBPF attach points. Seen from user space, though, there are four separate paths in: /dev/kmsg and the consoles, persistent storage read on the next boot, the tracefs filesystem at /sys/kernel/tracing, and the perf_event_open() system call. The bpf() system call is a fifth path. It loads programs onto the same hooks and hands their results back through BPF maps (Chapter 23).

Who may ask is restricted as well, because diagnostic output reveals kernel addresses and other users' data. Reading the kernel log needs CAP_SYSLOG when kernel.dmesg_restrict is set, and its default comes from CONFIG_SECURITY_DMESG_RESTRICT (§2.3). /proc/kallsyms by default shows zeros instead of addresses to readers without CAP_SYSLOG, and to everyone when kernel.kptr_restrict is 2 (§3.5). tracefs is created with mode 0700, so only root can use it unless it is mounted with uid=, gid= or mode= options. perf_event_open() is governed by kernel.perf_event_paranoid. At its default of 2, an unprivileged user can profile only their own processes, and only in user mode. CAP_PERFMON (5.8) grants full perf access without the rest of root (§9.1). Kernel lockdown (Chapter 27) sits above all of these. Even integrity mode closes debugfs and mmiotrace, stops kgdb from writing kernel memory, and disables bpf_probe_write_user(). Confidentiality mode also refuses /proc/kcore, kprobe events created through tracefs or perf_event_open(), the BPF helpers that read kernel memory, kdb memory reads, and perf samples of kernel registers. tracefs then creates no files at all.

1.2 From printk Alone to an Observability Stack

Linux 2.6.11 had printk() writing into a fixed character array, log_buf, guarded by a spinlock. It had panic() and the oops, the magic SysRq key, and kernel/kprobes.c. kprobes is older than the kernel's git history, which starts at 2.6.12, but it had no tracefs front end: using a kprobe meant writing a kernel module. Almost all of the rest of this chapter was added later. Most of it arrived between 2.6.26 and 2.6.36 and grew out of the real-time and tracing work of that period.

Two later waves followed. Between 4.0 and 5.8 the emphasis moved to finding bugs and to programmability. KASAN (4.0) and KCSAN (5.8) brought compiler instrumentation into the kernel. tracefs was split out of debugfs (4.1). eBPF programs could attach to kprobes (4.1) and tracepoints (4.7), and hist triggers (4.7) let trace events aggregate data in the kernel instead of streaming every record to user space. After 5.10 the most visible work was the rewrite of printk: the lockless ring buffer (5.10), nbcon consoles (6.7) and printer kthreads (6.12). It removed the last obstacle to PREEMPT_RT, which became selectable on x86-64 and ARM64 in 6.12. Table 29-1 lists the main milestones. Each version in the table was checked against the git history of the file or symbol that introduced the mechanism.

These mechanisms share a design rule. Instrumentation that is turned off must cost almost nothing, because it has to stay compiled into production kernels to be useful. When the instrumentation is turned on, it must be safe to run from any context, including NMI handlers and the scheduler, and the scheduler is one of the things it is used to observe. Both requirements come up again and again in this chapter. They explain the NOPs patched into function entries and the static keys behind every tracepoint. They also explain why the printk and trace buffers are lockless and why console printing was moved into dedicated threads. A third rule follows from the second: instrumentation must not instrument itself, and it must stay out of code that runs before the kernel can tolerate it. Functions marked notrace get no ftrace call site. Code marked noinstr (5.8) goes into the .noinstr.text section, where the compiler adds no tracing, sanitizer or coverage hooks, objtool warns about any call that leaves the section, and kprobes refuse to probe. The entry code uses it for the instructions that run before RCU and context tracking know that the CPU has entered the kernel (Chapter 4). Where recursion cannot be ruled out by construction, it is caught at run time. The function tracer (ftrace_test_recursion_trylock()), the trace ring buffer (trace_recursive_lock()) and perf's software events (perf_swevent_get_recursion_context()) each keep one recursion guard per context (task, softirq, hardirq and NMI), and they drop a nested event instead of recursing.

printk and the Kernel Log

printk() is the oldest diagnostic in the kernel. For most of its life it was also one of the most dangerous: a call from the wrong context could deadlock or stall the machine. In Linux 7.0 it is two separate mechanisms. One stores a record in a lockless ring buffer, which is fast and safe in any context, including NMI. The other prints stored records to the consoles, either immediately or later from a dedicated thread. Printing is the slow half, and it is the half the kernel may postpone. There is one log for the whole machine: every CPU, driver and container writes to the same buffer, and each record carries a sequence number, a timestamp, a level and the identity of its caller.

2.1 Log Levels, Rate Limits, and Dynamic Debug

Each message begins with a level prefix. KERN_EMERG through KERN_DEBUG are the two-character strings "\0010" to "\0017": the start-of-header byte KERN_SOH followed by a digit. KERN_CONT ("\001c") marks a continuation of the previous line. The pr_emerg() … pr_debug() macros add the prefix and the file's pr_fmt(). dev_err() and its relatives also attach the device's identity as structured dev_info (subsystem and device name). vprintk_store() strips the prefix and stores the level in the record. Four numbers in /proc/sys/kernel/printk, the console_printk[] array, decide what reaches the consoles. They are the console log level (default CONFIG_CONSOLE_LOGLEVEL_DEFAULT, 7), the default level for messages that do not give one, the minimum console level, and the boot-time default. A message is printed on a console only if its level is numerically lower than the console log level. Every message is stored, whatever its level. The default message level is 4 (KERN_WARNING, from CONFIG_MESSAGE_LOGLEVEL_DEFAULT). It applies to a printk() with no prefix, or with KERN_DEFAULT, which is the empty string. The minimum console level is 1, so even dmesg -n 1 cannot silence KERN_EMERG. Boot parameters set the console level before any user space runs. loglevel=n sets it directly, quiet sets it to CONFIG_CONSOLE_LOGLEVEL_QUIET (4), and debug sets it to 10, so every level reaches the console. ignore_loglevel, which can also be changed at run time as the printk.ignore_loglevel module parameter, prints every message whatever the setting.

Two additions serve the people who read these messages rather than the people who write them. A driver's probe routine should report failure with dev_err_probe(dev, err, fmt, …) (5.9, drivers/base/core.c), which returns err so it can end a return statement. For -EPROBE_DEFER, which only means that a supplier is not ready yet, it logs at debug level and records the text as the device's deferral reason, listed in the debugfs file devices_deferred. It prints nothing for -ENOMEM, which has already been reported, and an error such as "error -ENODEV: …" (through %pe) for anything else, so a deferred probe no longer fills the log with false errors (Chapter 13, §3.3). The second addition is the printk index (CONFIG_PRINTK_INDEX, 5.15, kernel/printk/index.c). Every printk(), pr_*() and dev_*() call site with a constant format also emits an entry into a .printk_index section, at no run-time cost. Debugfs lists the entries per module under printk/index/module (vmlinux for the core kernel), one line per site in the form <4> mm/oom_kill.c:line function "format", with ,c after the level for a continuation. Tools that watch /dev/kmsg for particular messages can compare the index of a new kernel against their patterns and find messages that were reworded or removed before the change goes unnoticed in production.

Because a message storm can itself take a machine down, the API has rate-limited and one-shot forms. printk_ratelimited() and pr_warn_ratelimited() keep a static struct ratelimit_state per call site. By default it allows a burst of 10 messages every 5 seconds (DEFAULT_RATELIMIT_BURST and DEFAULT_RATELIMIT_INTERVAL). When a new interval begins, ___ratelimit() in lib/ratelimit.c reports how many messages were dropped with a "callbacks suppressed" line. The older printk_ratelimit() shares one state across the whole kernel, tuned by the kernel.printk_ratelimit and kernel.printk_ratelimit_burst sysctls. Its header comment asks new code not to use it, because one noisy caller then silences everyone else. pr_warn_once() and printk_once() keep a static flag. One variant exists because of context: printk_deferred() is for code holding scheduler locks. It stores the record but never wakes or calls a console from that context. Internally it passes the pseudo-level LOGLEVEL_SCHED, and vprintk_emit() turns that into an offloaded flush, as shown below. Code that cannot convert every call inside a region brackets the region with printk_deferred_enter() and printk_deferred_exit() instead. The page allocator, the workqueue code, the stack depot and kmemleak do this around paths that may print while they hold their own locks, because a console driver could call back into them. NMI context and the printk CPU-sync section (§2.4) are deferred in the same way automatically. Finally, printk() guards against recursion. A per-CPU counter, with a separate one for NMI context, allows three nested calls, for example a console driver that warns while it prints. A deeper call is dropped.

The format string is expanded by vsnprintf() in lib/vsprintf.c, which adds kernel-specific %p extensions. A letter after %p selects a printer. %pS prints a code address as a symbol and offset (§3.5). %pe (5.5) prints an error pointer as the name of its errno, such as -ENOMEM. %pI4 and %pM print IPv4 and MAC addresses, %pR a struct resource, %pOF a device-tree node, %pt a date and time, and %pg a block device. %pV expands a nested format and its arguments, which is how dev_err() builds its prefix, and %pA calls back into Rust's formatting for the Rust pr_*! macros. A plain %p does not print the address at all. Since 4.15 it prints a SipHash of the pointer, keyed with random bytes, so that log messages no longer reveal where the kernel and its objects live (Appendix A). Until the random-number generator is ready it prints (____ptrval____). %px prints the raw value and needs a reason in code review, and %pK obeys kernel.kptr_restrict. For debugging, the no_hash_pointers boot parameter (5.12), spelled hash_pointers=never since 6.17, turns hashing off and prints a large warning banner. The default, hash_pointers=auto, also turns it off when slab debugging is enabled.

pr_debug() works differently. With CONFIG_DYNAMIC_DEBUG, each call site expands into a struct _ddebug record (include/linux/dynamic_debug.h) in a dedicated ELF section. The record holds the module, function, file, line and format string, a flags byte (_DPRINTK_FLAGS_PRINT and the _DPRINTK_FLAGS_INCL_* decorations), and a static key that guards the actual call. A disabled pr_debug() is therefore a single no-op instruction that the jump-label code can patch into a jump (the mechanism is described with tracepoints in §7.1). Writing a query to /proc/dynamic_debug/control enables a set of call sites at run time. The same file also appears as dynamic_debug/control under debugfs. For example, echo 'file drivers/usb/core/hub.c +p' > /proc/dynamic_debug/control sets the print flag (p) on every pr_debug() in that file. Other flags decorate each line: m adds the module name, f the function, s the source file name (6.6), l the line number and t the thread ID. d (6.19) adds a stack dump after the message, and _ stands for no flags. A query selects sites by func, file, module, format, line or class. Classes (6.1) are named categories that a driver declares with DECLARE_DYNDBG_CLASSMAP. They were written for DRM's drm.debug categories, but in 7.0 DRM's use of them still depends on CONFIG_BROKEN. The same queries can be given at boot with dyndbg="query", or for one module with module.dyndbg=. modprobe accepts dyndbg= as a module option too, so a module's messages can be enabled from its first line. With only CONFIG_DYNAMIC_DEBUG_CORE, a module opts in by defining DYNAMIC_DEBUG_MODULE. Reading the control file lists every call site in the running kernel. The parser and the site table are in lib/dynamic_debug.c.

2.2 The Lockless printk Ring Buffer

Until 5.10, printk() copied text into log_buf under logbuf_lock, a raw spinlock. In normal use that worked. In an NMI, or on a CPU that oopsed while it held the lock, it deadlocked. A series of per-CPU "printk-safe" buffers and NMI buffers was added to work around the problem. 5.10 replaced the design with the printk ring buffer in kernel/printk/printk_ringbuffer.c. It has no lock. Writers on any CPU, in any context, reserve space with atomic compare-and-exchange operations, and readers detect and skip records that were overwritten while they read them.

The structure is two rings that work together, shown in Figure 29-2. The descriptor ring (struct prb_desc_ring) is an array of 2count_bits descriptors, with a parallel array of struct printk_info metadata. The text data ring (struct prb_data_ring) is a byte array of 2size_bits bytes. It holds variable-length data blocks, and each block begins with the ID of the descriptor that owns it. Each descriptor packs its ID and a two-bit state into one word, state_var, so a single cmpxchg can change both. Each descriptor also records the logical positions (text_blk_lpos) of its data block. 

/* kernel/printk/printk_ringbuffer.h (abridged) */
struct printk_info {
	u64	seq;		/* sequence number */
	u64	ts_nsec;	/* timestamp in nanoseconds */
	u16	text_len;	/* length of text message */
	u8	facility;	/* syslog facility */
	u8	flags:5;	/* internal record flags */
	u8	level:3;	/* syslog level */
	u32	caller_id;	/* thread id or processor id */
	...
	struct dev_printk_info	dev_info;
};

struct prb_desc_ring {
	unsigned int		count_bits;
	struct prb_desc		*descs;
	struct printk_info	*infos;
	atomic_long_t		head_id;
	atomic_long_t		tail_id;
	atomic_long_t		last_finalized_seq;
};

struct printk_ringbuffer {
	struct prb_desc_ring	desc_ring;
	struct prb_data_ring	text_data_ring;
	atomic_long_t		fail;
};

A descriptor goes through four states (enum desc_state). It is desc_reserved while a writer owns it and desc_committed once the data is consistent. A committed record can still be reopened, which is how a KERN_CONT continuation is appended with prb_reserve_in_last(). It becomes desc_finalized when it can no longer change, which happens when the writer calls prb_final_commit() or a newer record is reserved. Finally it becomes desc_reusable when the tail moves past it. Readers see only finalized records. A reader that looks up a descriptor and finds an unexpected ID gets the pseudo-state desc_miss and knows the slot has been recycled.

The writer's path is prb_reserve(), then copy the text, then prb_commit() or prb_final_commit(). prb_reserve() calls desc_reserve(), which advances head_id with a cmpxchg loop. If the ring is full it first pushes tail_id forward, marking the oldest descriptor reusable. It then calls data_alloc(), which does the same with head_lpos and tail_lpos on the data ring. That call can in turn invalidate old descriptors whose blocks are being overwritten. A writer that is interrupted between these steps, perhaps by an NMI that also calls printk(), is safe because every step is a single atomic transition that the next writer can see and work around. Readers call prb_read_valid() with the sequence number they want next. They copy the text out and then re-check the descriptor state. If the record was recycled during the copy, the reader drops it and reports the gap as lost records. The original comment block in printk_ringbuffer.c gives the memory-barrier argument in detail. A KUnit test, printk_ringbuffer_kunit_test.c, stress-tests that argument with concurrent writers and readers.

The buffer size is set at build time by CONFIG_LOG_BUF_SHIFT (default 17, so 128 KiB of text, in a range of 4 KiB to 32 MiB) and at boot by log_buf_len=. The descriptor count is derived from the text size by assuming an average record of 32 bytes (PRB_AVGBITS 5). Large machines get more space automatically. CONFIG_LOG_CPU_MAX_BUF_SHIFT (default 12) allows 4 KiB for each possible CPU after the first, and if no log_buf_len= was given, log_buf_add_cpu() enlarges the buffer when that allowance exceeds half of it. With the defaults this happens above 17 possible CPUs. Sizes are rounded up to a power of two. The first messages cannot wait for an allocator, so they go into a static array, __log_buf, managed by a static ring buffer, printk_rb_static. If a larger size was requested, setup_log_buf(), called early in start_kernel() before the page allocator is set up, allocates bigger arrays from memblock, copies every record written so far into the new ring buffer, and switches the global prb pointer to it. It logs how many messages were dropped if the copy fell short. Otherwise the static buffer serves for the life of the system. log_buf_vmcoreinfo_setup() exports the address of prb and the offsets of its fields in the kdump VMCOREINFO note (Appendix A), so that crash and makedumpfile can extract the log from the memory image of a kernel that died before it wrote anything to disk.

Each record has a fixed shape. vprintk_store() formats the text into a block of at most 1024 bytes (PRINTKRB_RECORD_MAX), so a longer message is truncated. The reopening of a record for a KERN_CONT fragment, described above, happens only if the previous record came from the same caller and is not yet finalized. Otherwise the fragment becomes a new record flagged LOG_CONT. Fragments from two CPUs therefore no longer merge into one line, but a fragment that arrives late is printed on a line of its own. The timestamp, ts_nsec, is taken with local_clock() when vprintk_store() starts. It counts nanoseconds since boot and appears as [seconds.microseconds] when CONFIG_PRINTK_TIME or printk.time=1 is set. It is not wall-clock time, so dmesg -T, which converts it by adding it to the boot time, can be wrong after a suspend. caller_id identifies the writer: a thread ID in task context, or otherwise the CPU number with the top bit set. CONFIG_PRINTK_CALLER (5.1) prints it on every line as [T123] or [C3], which untangles messages from different CPUs. Since 7.0, CONFIG_PRINTK_EXECUTION_CTX stores the CPU and task name of the caller as well (caller_id2 and comm), so that a console can report them even when it prints the record later from another context. It is selected only by netconsole's dynamic configuration, whose sysdata feature appends both to each packet.

2.3 Reading the Log: /dev/kmsg and syslog(2)

User space reads the log through three interfaces. The oldest is the syslog() system call, SYSCALL_DEFINE3(syslog, …). It is a thin wrapper around do_syslog(type, buf, len, SYSLOG_FROM_READER), which dispatches on the action codes in include/linux/syslog.h listed in Table 29-2. /proc/kmsg is the same function called with SYSLOG_FROM_PROC. A read from it consumes records, so only one reader (historically klogd) can use it sensibly.

The modern interface is /dev/kmsg (kmsg_fops in kernel/printk/printk.c, 3.5). Each open file has its own sequence-number cursor, starting at the oldest record, so any number of readers can follow the log independently. Each read() returns exactly one record as a line of the form prio,seq,usec,flag;text. prio is the syslog priority, facility × 8 + level, so a kernel KERN_ERR message reads 3 and a message written by user space reads 8 or more. seq is the record's sequence number and usec its timestamp in microseconds. flag is c for a continuation fragment and - otherwise, and with CONFIG_PRINTK_CALLER a caller= field follows it. Non-printable bytes and backslashes in the text are escaped as \xNN, so every record is one line, followed by indented SUBSYSTEM=/DEVICE= lines from dev_info. A read blocks until a record arrives unless the file is non-blocking, and poll() works, which is how journald and dmesg -w follow the log. If records were overwritten since the last read, the read fails with EPIPE and moves the cursor to the oldest surviving record, so the reader knows it lost data and can carry on. lseek() moves the cursor: SEEK_SET to the oldest record, SEEK_END past the newest, and SEEK_DATA to the first record after the last SYSLOG_ACTION_CLEAR, which lets dmesg keep its old semantics. Writing to /dev/kmsg injects a record, which is how systemd logs early-boot messages into the kernel log. A <N> prefix sets the priority. Without one the record gets the default message level, and the facility is always forced to be non-zero (LOG_USER by default), so injected messages can be told apart from the kernel's own. A single write is limited to 1024 bytes. The printk.devkmsg= boot parameter, also the kernel.printk_devkmsg sysctl, selects on, off or ratelimit, the default. ratelimit allows each open file 10 writes every 5 seconds and silently drops the rest. off makes every open of /dev/kmsg fail with EPERM, for readers as well as writers.

Access is controlled by syslog_action_restricted() and the dmesg_restrict sysctl (2.6.37), which defaults to CONFIG_SECURITY_DMESG_RESTRICT. If the restriction is off, READ_ALL and SIZE_BUFFER are open to everyone. If it is on, or for any other action, the caller needs CAP_SYSLOG. The LSM hook security_syslog() is checked in both cases. For the two files the capability check is made only when they are opened. A readable open of /dev/kmsg is checked as READ_ALL, and a write-only open needs no permission. /proc/kmsg is checked at open() too, so a daemon can open it and then drop its privileges. There is no log namespace: a container sees the host's log, and the same sysctl governs it. The restriction matters because kernel messages can leak pointers and other layout information. It belongs to the kernel's broader hardening against information leaks, which Chapter 27 discusses.

2.4 Consoles: console_lock and nbcon

Storing a record is the cheap half of printk(). The other half is printing it, and a serial console at 115200 baud prints roughly 11 characters per millisecond. A console is a struct console in include/linux/console.h. It has a name, a set of CON_* flags, and its own seq recording how far it has printed. Until recently it had a single write() callback. All such legacy consoles are serialized by the global console_lock, a semaphore. Whoever holds it prints every pending record to every console in console_flush_all(), called from console_unlock(). A printk() that finds the lock free therefore does all the console work in its own context. That could be an interrupt handler or a task holding a hot spinlock, and the delay is unbounded. Since 4.16 the job can at least be passed on. A printk() that finds another CPU printing spins briefly in console_trylock_spinning(), the printing CPU hands it the lock after the current record, and the newcomer continues. The work is then spread over the callers instead of falling on one unlucky one, but it is still not bounded. On PREEMPT_RT, where no code path may introduce unbounded latency, this was the last obstacle to merging the real-time patches. It is the main reason the console layer was redesigned.

Consoles are chosen on the command line. Each console=nameindex,options parameter, for example console=ttyS0,115200, adds an entry to a table of up to eight preferred consoles, and the last one given also becomes /dev/console, the terminal that init uses for its standard input and output. Firmware can add an entry as well: on ARM64 the device-tree stdout-path or the ACPI SPCR table names the serial port. register_console() matches each driver against the table, links the console into console_list, and decides where it starts printing. A console with CON_PRINTBUFFER starts at the oldest record, so messages from before it existed still appear on it. Others start at the next new record. A boot console (CON_BOOT, created by earlycon= or earlyprintk=) prints from very early in boot with a minimal driver that needs no probing. When a real console that will become /dev/console registers, the boot consoles are unregistered and the real console skips the replay, so nothing is printed twice. The keep_bootcon parameter keeps them, which helps when the real driver hangs, and printk_late_init() removes any boot console whose code lives in init memory that is about to be freed. Since 6.2 the list is changed under console_list_lock and walked under SRCU (console_srcu), so printk() can walk it without taking console_lock. /proc/consoles lists the registered consoles and their flags. console_lock still serializes the legacy consoles, and it is also the lock that the virtual-terminal and fbcon code take to serialize screen updates, which is one reason it is hard to remove.

The redesign is the nbcon (non-blocking console) infrastructure in kernel/printk/nbcon.c. The basic infrastructure arrived in 6.7, and atomic flushing, emergency sections and printer threads in 6.12. A console that sets CON_NBCON has two callbacks instead of one. write_thread() is called from a dedicated kernel thread, named pr/nameindex (for example pr/ttyAMA0), which runs at nice −20 and may sleep and take the driver's normal locks (through device_lock()). write_atomic() can run in any context, including NMI and panic. Instead of a global lock, each nbcon console has an atomic ownership word: 

/* include/linux/console.h (abridged) */
struct nbcon_state {
	union {
		unsigned int	atom;
		struct {
			unsigned int prio		:  2;
			unsigned int req_prio		:  2;

	};
};

enum nbcon_prio {
	NBCON_PRIO_NONE = 0,
	NBCON_PRIO_NORMAL,
	NBCON_PRIO_EMERGENCY,

	NBCON_PRIO_MAX,

A context acquires a console with nbcon_context_try_acquire() at one of these priorities. A higher-priority context can ask the owner to hand the console over (req_prio), and the owner checks for such requests between records. The driver marks the stretches where the hardware state is inconsistent, such as the middle of reprogramming a UART FIFO, with nbcon_enter_unsafe() and nbcon_exit_unsafe(), and a takeover waits until those stretches are over. Serial drivers get this marking almost for free. Since 6.12, uart_port_lock() also acquires the port's nbcon console at normal priority and marks it unsafe (nbcon_device_try_acquire()), so ordinary tty output and console output never drive the UART at the same time. nbcon_device_release() then prints any records that queued up in the meantime if no printer thread will. Only during a panic, and only as a last resort, does nbcon_atomic_flush_unsafe() take a console even in an unsafe section. A driver whose write_atomic() is not safe in every context can set CON_NBCON_ATOMIC_UNSAFE (6.19), and its write_atomic() is then used only in that final flush. The code that prints an oops (oops_enter()), a WARN() (__warn()), a lockdep report or an RCU stall warning enters an emergency section (nbcon_cpu_emergency_enter()). Its messages are then printed atomically and immediately, not handed to the thread, so the report reaches the console even if the machine then dies.

vprintk_emit() decides how to flush, as Figure 29-3 shows. It stores the record with vprintk_store(). Then printk_get_console_flush_type() fills in a struct console_flush_type with four flags, based on the current priority and on which kinds of console are registered. At normal priority, if the printer kthreads are running, nbcon consoles are flushed by waking them (nbcon_kthreads_wake()). In emergency or panic context, or before the threads exist, they are flushed atomically in the caller (nbcon_atomic_flush_pending()). Legacy consoles are flushed directly with console_trylock_spinning() and console_unlock(), unless the caller is in NMI context, inside the printk CPU-sync section, or on PREEMPT_RT. In those cases the flush is deferred to an irq_work, or on PREEMPT_RT to a pr/legacy thread. The CPU-sync section is a reentrant spinning lock, taken with printk_cpu_sync_get_irqsave() (5.14, under its current name since 5.19). dump_stack(), the NMI backtrace code and the lockup detectors hold it so that a multi-line report from one CPU is not interleaved with another's, and a CPU holding it must not wait for console_lock. During a panic nothing is offloaded. The panic CPU prints to nbcon consoles atomically, and if any exist it leaves the legacy consoles alone until the other CPUs have been stopped (printk_legacy_allow_panic_sync()), because until then another CPU might hold a legacy driver's lock. A console that fell behind far enough to lose records prints a line such as ** 12 printk messages dropped ** in their place.

The conversion of drivers is still under way. In 7.0 the nbcon drivers include the ARM PL011 UART (drivers/tty/serial/amba-pl011.c, 6.15), which is common on ARM64 servers and virtual machines, several other SoC UARTs (i.MX in 6.13, NVIDIA Tegra UTC in 6.15, SiFive in 6.16), the DRM log client (drivers/gpu/drm/clients/drm_log.c, 6.14), and netconsole (7.0). The 8250/16550 driver that most x86 machines use for their serial console was converted early in 2025, but the conversion was reverted. In 7.0.12 that driver is still a legacy console, so on a typical x86 server the serial console still goes through console_lock. Boot consoles (CON_BOOT, set up with earlycon= before the real driver probes) are also legacy, and while one is registered, printk_get_console_flush_type() does not use the nbcon paths at all. netconsole sends each record as a UDP packet, and it is often the only practical console on a headless machine. A network driver cannot safely transmit from every context, so netconsole sets CON_NBCON_ATOMIC_UNSAFE. Its printer thread does the normal work, and its write_atomic() runs only in the last flush of a panic.

When Things Go Wrong: BUG, Oops, and Panic

The kernel has no supervisor to report its own failures to, so it has to report them itself, in a state where it cannot trust much of its own code. The path runs from an assertion or a bad memory access to an oops, a taint mark, and possibly a panic(). Each report must carry a stack trace with symbol names, produced without taking locks or allocating memory. The evidence must then get off a dying machine before it reboots: to a crash kernel, to persistent storage, or to an operator at the console.

3.1 BUG() and WARN(): Trapping Instructions and the Bug Table

BUG_ON(cond) asserts that a condition cannot happen and that the kernel cannot continue if it does. WARN_ON(cond) asserts that the condition should not happen but that the kernel can carry on.

The two are not equally welcome in new code. Documentation/process/deprecated.rst lists BUG() and BUG_ON() as deprecated, and scripts/checkpatch.pl warns about every new one: "Do not crash the kernel unless it is absolutely unavoidable--use WARN_ON_ONCE() plus recovery code (if feasible) instead of BUG() or variants". A BUG_ON() in a driver turns a recoverable inconsistency into a dead machine, often while the task holds locks that then hang the other CPUs too. The 7.0 tree still contains about 14,500 BUG_ON() calls, against about 23,600 calls to WARN_ON() and WARN_ON_ONCE(). The WARN macros return the value of their condition, so the check and the recovery fit in one statement, as in if (WARN_ON_ONCE(!ops)) return -EINVAL;. WARN(cond, fmt, ...) adds a message. WARN_ONCE() and WARN_ON_ONCE() report only the first time a call site fires, which keeps a warning in a hot path from flooding the log. WARN_TAINT() lets the caller choose the taint flag instead of TAINT_WARN. CONFIG_BUG, which can be turned off only under CONFIG_EXPERT, removes the reports. BUG() then still traps on x86 and ARM64, but with no bug-table entry, and WARN_ON() only evaluates its condition.

Both kinds of assertion are hot-path macros, sprinkled through tens of thousands of call sites. They must not cost a function call, a branch to a large out-of-line block, or a string reference in the instruction stream. Both architectures compile them to a single trapping instruction. The rest of the information is placed in a separate table, the __bug_table section, which holds one struct bug_entry per call site: 

/* include/asm-generic/bug.h (abridged) */
/* BUG_REL(type, name) is "signed int name##_disp", a PC-relative
 * offset, on x86 and ARM64 (GENERIC_BUG_RELATIVE_POINTERS) */
struct bug_entry {

#endif

};

/* arch/x86/include/asm/bug.h (abridged) */
#define _BUG_FLAGS(cond_str, ins, flags, extra)			\

#define BUG()							\

On x86 the trapping instruction is UD2, the architecturally defined invalid opcode. It raises #UD, and exc_invalid_op() in arch/x86/kernel/traps.c calls handle_bug() before it does any of the normal exception-entry work. That way a WARN() inside the entry code cannot recurse. handle_bug() decodes the instruction at regs->ip and switches on its type. A plain UD2 goes to report_bug(). Since 6.19, a WARN() with printf arguments on x86-64 compiles to a call through the WARN_trap static call to __WARN_trap, which executes a UD1 whose operand points at the bug entry. That type goes to report_bug_entry(), and the arguments are recovered from the saved registers instead of being formatted at the call site. Other UD1/UDB encodings carry Clang's UBSAN trap reports and CFI failures. If the report says "warning", handle_bug() advances regs->ip past the trapping instruction and returns. The instruction behaved, in effect, as a call to a reporting function. A BUG() falls through to the ordinary invalid-opcode path and dies with "invalid opcode".

On ARM64 the instruction is BRK #0x800 (BUG_BRK_IMM). BRK carries a 16-bit immediate, and the kernel uses that immediate to multiplex all of its software breakpoints. Since 6.17, the EL1 BRK handler call_el1_break_hook() in arch/arm64/kernel/debug-monitors.c dispatches on the immediate with a fixed series of tests. Before that, handlers registered themselves on a list. The same function routes kprobes, kretprobes, KGDB, KASAN software tags, UBSAN traps and CFI failures, so we will meet it again in §8: 

/* arch/arm64/kernel/debug-monitors.c (abridged) */

{

bug_brk_handler() calls report_bug(regs->pc, regs). For a warning it steps the PC over the BRK. For a bug it calls die("Oops - BUG", regs, esr). The common code, __report_bug() in lib/bug.c, is shared by both architectures. It looks up the trapping address in the bug table (find_bug(), which also searches the tables of loaded modules) and implements WARN_ONCE by setting BUGFLAG_DONE in the entry. It prints the "------------[ cut here ]------------" line, and then either calls __warn() or prints "kernel BUG at file:line!". __warn() prints a "WARNING: …" line, the list of loaded modules, the registers and a backtrace. It calls check_panic_on_warn(), which panics if panic_on_warn is set, and sets TAINT_WARN. Figure 29-4 shows how these paths fit together.

A warning's report has a fixed shape. Since 6.19 its first line is WARNING: file:line at func+0x1c/0x80, CPU#3: comm/pid, which puts the source location, the function, the CPU and the task in one line that can be searched for. Without CONFIG_DEBUG_BUGVERBOSE the file and line are missing. With CONFIG_DEBUG_BUGVERBOSE_DETAILED (6.19), the text of the condition, such as [!ops], is stored as the entry's format string and printed after the cut here line, at a cost of about 100 KB. Then come the message of a WARN(), the "Modules linked in:" list from print_modules(), the registers or a backtrace, and the end-of-trace marker. CONFIG_MODULE_UNLOAD_TAINT_TRACKING (5.19) adds the tainting modules that have already been unloaded to that list. Last, an error_report_end tracepoint (5.17 for warnings) lets test harnesses catch every warning without parsing the log. A WARN_ONCE() remembers in its bug entry that it has fired. Writing to /sys/kernel/debug/clear_warn_once (4.15) clears every BUGFLAG_DONE, and the .data..once section used by printk_once(), so the warnings can fire again on a test system. Three sysctls decide how far a warning may go. kernel.panic_on_warn, tested by check_panic_on_warn(), turns every warning into a panic. syzkaller and many test fleets run with it, because a warning otherwise scrolls by unnoticed. kernel.warn_limit (6.2) panics once the number of warnings since boot, shown in /sys/kernel/warn_count, reaches the limit. It is 0, which means off, by default. kernel.traceoff_on_warning stops the trace ring buffer at the first warning, so the events that led up to it are not overwritten (§6).

3.2 The Oops and the Taint Mask

An oops is the kernel's report of an exception it cannot handle in kernel mode: a BUG(), a NULL or wild pointer dereference, a general protection fault, an ARM64 synchronous external abort, and so on. On x86, die() in arch/x86/kernel/dumpstack.c is three steps. oops_begin() takes die_lock, a raw spinlock the owning CPU may take again, so a fault inside the oops path does not deadlock. It then calls the generic oops_enter(). __die() prints the header line ("Oops: str: err [#n] SMP PTI", listing the configuration features in effect), the registers and the stack trace, and it calls notify_die(DIE_OOPS) for debuggers. oops_end() hands control to a crash kernel if one is loaded and kexec_should_crash() agrees. Otherwise it adds TAINT_DIE, calls oops_exit(), and either panics or kills the task with rewind_stack_and_make_dead(). ARM64's die() in arch/arm64/kernel/traps.c follows the same steps in one function, and its header line reads "Internal error: str: …". The generic halves do the diagnostics plumbing. oops_enter() enters an nbcon emergency section (§2.4), stops tracing so the ring buffer keeps the events that led up to the oops, and turns off lock debugging. If kernel.oops_all_cpu_backtrace (5.8) is set, it also backtraces every other CPU. oops_exit() prints "---[ end trace 0000000000000000 ]---" (the random oops ID was dropped in 5.17, so the number is always zero), leaves the emergency section, and calls kmsg_dump(KMSG_DUMP_OOPS).

An oops has a regular layout, and reading one is a skill in its own right. A fault-specific preamble comes first. For a bad kernel access on x86 the page-fault handler prints "BUG: kernel NULL pointer dereference, address: 0000000000000008" if the address is in the first page, and "BUG: unable to handle page fault for address:" otherwise. Two #PF: lines then decode the error code, for example "supervisor read access in kernel mode" and "not-present page", and a walk of the page tables for that address follows. A general protection fault reports "general protection fault, probably for non-canonical address 0x…". x86-64 does not report the address of a #GP, so the kernel decodes the faulting instruction to guess it. ARM64 prints "Unable to handle kernel paging request at virtual address …" (or NULL pointer dereference, write to read-only memory, and so on), then "Mem abort info:" and "Data abort info:" blocks that decode the ESR, and a page-table walk headed "pgtable: 4k pages, 48-bit VAs". Next come the header line with its oops count, and the identity line from dump_stack_print_info(): "CPU: 3 UID: 0 PID: 1234 Comm: modprobe Tainted: G W 7.0.12 #1 PREEMPT(voluntary)". Since 6.11 a second line spells out the taint letters, and "Hardware name:" follows, from DMI or the device tree. The registers name the faulting instruction (RIP: 0010:func+0x1c/0x80 on x86, pc : func+0x1c/0x80 on ARM64). A "Code:" line shows the instruction bytes around the fault, with the faulting byte in angle brackets on x86, and scripts/decodecode disassembles it. The "Call Trace:" comes last (§3.5). The first oops may have scrolled off a VGA console by the time the machine stops, so x86's oops_end() saves the registers of the first oops and prints them again as an "executive summary" at the very end.

oops_end() then chooses between a panic and killing the task. An oops in interrupt context has no task to kill, so it panics with "Fatal exception in interrupt". With panic_on_oops set, by sysctl or by the oops=panic boot option, it panics with "Fatal exception". Otherwise rewind_stack_and_make_dead() abandons the possibly corrupted kernel stack and calls make_task_dead() (5.17), which replaced the plain do_exit() on this path. It panics if the dying task is the idle task, and do_exit() later panics with "Attempted to kill init!" if it is init. It notes a task that oopsed with interrupts disabled or a raised preempt count, and repairs both so the exit can proceed. A task that oopses again while it is already exiting is parked for good, with "Fixing recursive fault but reboot is needed!". make_task_dead() also counts oopses. An oops leaks every reference the task held at the time, and an attacker who can trigger the same oops repeatedly can overflow a reference count that is not a refcount_t, turning a harmless-looking crash into a use-after-free. kernel.oops_limit (6.2, default 10,000) therefore panics with "Oopsed too often" once the count, visible in /sys/kernel/oops_count, reaches the limit.

Killing the task and carrying on is a deliberate choice. Often the oops happened in a system call on behalf of one process, and the rest of the system is healthy enough to save the log. But the kernel may now hold a lock that will never be released, or a half-updated data structure. Every later bug report from this boot is therefore suspect, and the kernel records that in the taint mask. add_taint() sets a bit in tainted_mask. print_tainted() renders the mask as a string of letters, and that string appears in every subsequent oops and warning header (Tainted: G D W). /proc/sys/kernel/tainted exposes the raw bits. Taint is sticky: a write to that file by CAP_SYS_ADMIN can only add bits, and nothing short of a reboot clears them. Each module's own contribution appears in /sys/module/name/taint, and tools/debugging/kernel-chktaint decodes a mask into sentences. The second argument of add_taint() records whether lockdep can still be trusted: a warning leaves it running, but an oops (TAINT_DIE) turns it off. panic_on_taint=mask (5.8) turns chosen taints into a panic, and its nousertaint option refuses writes to /proc/sys/kernel/tainted that would set those bits, so user space cannot trigger the panic. 3.3 panic()

panic() is the end of the line: the kernel has decided it cannot continue at all. The function, vpanic() in kernel/panic.c, is a careful sequence of steps. Each step aims to get one more piece of evidence out, or to reach one more recovery mechanism, before something in the dying kernel stops it: 

/* kernel/panic.c (abridged) */
void vpanic(const char *fmt, va_list args)
{
	...
	local_irq_disable();
	preempt_disable_notrace();
	...
	if (panic_try_start()) {
		/* go ahead */
	} else if (panic_on_other_cpu())
		panic_smp_self_stop();		/* someone else is panicking */

	console_verbose();
	bust_spinlocks(1);
	len = vscnprintf(buf, sizeof(buf), fmt, args);
	pr_emerg("Kernel panic - not syncing: %s\n", buf);
	...					/* dump_stack() unless an oops did */

	kgdb_panic(buf);			/* enter the debugger, if any */

	if (!_crash_kexec_post_notifiers)
		__crash_kexec(NULL);		/* kdump: does not return */

	panic_other_cpus_shutdown(_crash_kexec_post_notifiers);
	printk_legacy_allow_panic_sync();
	atomic_notifier_call_chain(&panic_notifier_list, 0, buf);
	sys_info(panic_print);
	kmsg_dump_desc(KMSG_DUMP_PANIC, buf);	/* pstore and friends */

	if (_crash_kexec_post_notifiers)
		__crash_kexec(NULL);

	console_flush_on_panic(CONSOLE_FLUSH_PENDING);
	...
	if (panic_timeout != 0)
		emergency_restart();	/* reboot unless panic_timeout is 0 */
	pr_emerg("---[ end Kernel panic - not syncing: %s ]---\n", buf);
	...				/* nbcon_atomic_flush_unsafe(), spin forever */
}

Several details explain the shape of this function. Only one CPU may run it: panic_try_start() claims panic_cpu with an atomic compare-and-exchange, and every other CPU that calls panic() parks itself. From that moment, vprintk_emit() silently drops messages from other CPUs (§2.4), so a storm of secondary failures cannot bury the original report. A new 7.0 option, panic_force_cpu=, can first redirect the panic to a chosen CPU, for platforms whose crash kernel must start there. Code in NMI context, such as the hard-lockup detector (§4.1) or x86's handler for unknown NMIs, calls nmi_panic() instead. It returns if this CPU is already panicking. If another CPU is panicking, it loops in nmi_panic_self_stop(), which on x86 also saves the CPU's registers if a crash dump is being prepared.

The panicking CPU then makes sure that its report is complete and can be seen. console_verbose() raises the console log level to 15 (CONSOLE_LOGLEVEL_MOTORMOUTH), so nothing is filtered. bust_spinlocks(1) increments oops_in_progress, which tells console drivers such as the 8250 UART to try their port lock rather than spin on it, since a stopped CPU may hold it. The stack is dumped unless an oops has just printed it, and only with CONFIG_DEBUG_BUGVERBOSE. Before the final flush, console_unblank() wakes a blanked screen, and debug_locks_off() silences lockdep, whose reports would only be noise from here on. What else goes into the log is chosen by the panic_sys_info= boot parameter or the kernel.panic_sys_info sysctl (6.17). Both take a comma-separated list: tasks, mem, timers, locks, ftrace, all_bt (an NMI backtrace of every CPU, taken before they are stopped) and blocked_tasks. The same lib/sys_info.c helper serves the hung-task and lockup detectors (§4). panic_console_replay (6.17) prints the whole log on the consoles again at the end. Together they replace the numeric bitmask panic_print, which still works but has been deprecated since 6.18.

The crash kernel gets control early by default, before the panic notifiers and before kmsg_dump(). Those steps run arbitrary driver code in a broken kernel, and any of them might hang. The crash kernel is a second kernel loaded in advance with kexec_load() or kexec_file_load(). __crash_kexec() jumps into it, and the new kernel captures the old one's memory as /proc/vmcore. The loading, the reserved memory region and the jump are described in Appendix A. The crash_kexec_post_notifiers boot parameter reverses the order for platforms that must run notifiers, or save to pstore, before the jump. panic_other_cpus_shutdown() stops the other CPUs with smp_send_stop(), or with crash_smp_send_stop() when the crash kernel is to run after the notifiers, so they cannot keep changing memory while it is being dumped. Both architectures first send an ordinary IPI (REBOOT_VECTOR on x86, IPI_CPU_STOP on ARM64) and wait up to a second, so CPUs can leave their critical sections. CPUs that are still running then get an NMI on x86, or IPI_CPU_STOP_NMI on ARM64. That IPI is a real pseudo-NMI only when GICv3 priority masking is enabled. Without it, ARM64 can only print "SMP: failed to stop secondary CPUs".

The panic notifier chain is the hook for code that has one last thing to say. It is an atomic notifier, so the callbacks run with interrupts off, and the other CPUs have usually stopped already. pvpanic (drivers/misc/pvpanic/) registers at the highest priority. It writes PVPANIC_PANICKED, or PVPANIC_CRASH_LOADED when a crash kernel will run, to a virtual device, so that QEMU or a cloud host learns that the guest has died and can restart it or capture its memory. Hyper-V guests report the panic to the host through synthetic crash registers, and pass the tail of the log through a kmsg dumper. The host wants that report even when kdump is configured, so drivers/hv/hv_common.c sets crash_kexec_post_notifiers. AMD SEV-SNP hosts and powerpc firmware-assisted dump set it too. The IPMI driver records the panic in the baseboard management controller's event log (ipmi_msghandler.panic_op=). The panic LED trigger lights an LED. KFENCE checks the canaries of all its objects one last time, and the hung-task detector stops checking, so it cannot report the stopped tasks as hung. ftrace dumps its ring buffer to the console when ftrace_dump_on_oops is set (§6). On both x86 and ARM64 a notifier prints "Kernel Offset: 0x… from 0x…". That is the KASLR displacement, which is needed to map the addresses in the report back to System.map or a vmlinux (Appendix A).

Finally, the boot parameter or sysctl panic= (panic_timeout, default CONFIG_PANIC_TIMEOUT, usually 0) decides what happens next. A positive value prints "Rebooting in n seconds.." and waits, calling the panic_blink hook to flash the keyboard LEDs on x86 machines with an i8042 controller. A negative value reboots at once, and zero prints the end-of-panic line and spins forever. After that line, suppress_printk keeps later messages from scrolling it off the screen. The reboot is an emergency_restart(), not an orderly shutdown, and reboot=panic_warm (or panic_cold and so on) gives it a different reboot mode from an ordinary reboot. Machines in data centers usually set a timeout so they come back on their own. panic_on_oops, panic_on_warn, softlockup_panic, hardlockup_panic, hung_task_panic and panic_on_rcu_stall, and on x86 panic_on_unrecovered_nmi and panic_on_io_nmi, turn the corresponding reports into panics. The counting limits warn_limit and oops_limit (§3.1, §3.2) are a softer form of the same policy. They are how a fleet operator says "a kernel in this state is not worth keeping alive; take a crash dump and reboot".

3.4 Leaving Evidence: kmsg_dump, pstore, and SysRq

If no crash kernel is configured, the panic log exists only in RAM and on whatever console was attached. kmsg_dump is the hook that copies the tail of the log to somewhere that survives a reboot. A struct kmsg_dumper registered with kmsg_dump_register() has a dump() callback and a max_reason. kmsg_dump_desc() calls each dumper whose max_reason is at least the current reason: KMSG_DUMP_PANIC, KMSG_DUMP_OOPS, KMSG_DUMP_EMERG (emergency restart) or KMSG_DUMP_SHUTDOWN. The callback pulls lines out of the printk ring buffer with kmsg_dump_get_line() or kmsg_dump_get_buffer(). It runs in panic context, so it must not sleep, allocate memory or take locks that might be held. Each dumper reads through its own struct kmsg_dump_iter (5.13), a private cursor into the lockless ring buffer (§2.2), so several dumpers can walk the log independently. Since 6.12 the callback receives a struct kmsg_dump_detail that carries the reason and the panic message as well. The dumpers are kept on an RCU list, so walking it takes no lock. A dumper that leaves max_reason at KMSG_DUMP_UNDEF gets only oopses and panics, unless the printk.always_kmsg_dump parameter is set. KMSG_DUMP_EMERG comes from emergency_restart(), and KMSG_DUMP_SHUTDOWN from an ordinary reboot, halt or power-off and from kexec.

The main dumper is pstore (persistent storage, fs/pstore/). It is a small framework with backends on one side and a filesystem on the other. A backend registers a struct pstore_info with pstore_register(), giving read/write/erase callbacks and a flags mask of the record types it accepts. The types are PSTORE_FLAGS_DMESG for kmsg dumps, CONSOLE for a running copy of the console, FTRACE for function-trace records, and PMSG for user-space messages written to /dev/pmsg0. On the next boot the framework reads every record back and presents it as a file under /sys/fs/pstore, for example dmesg-ramoops-0 or dmesg-efi_pstore-id, where systemd-pstore collects it. There are three main backends. ramoops (fs/pstore/ram.c) uses a region of RAM that the firmware does not clear on a warm reset. That region comes from module parameters (mem_address, mem_size, record_size, console_size, ftrace_size, pmsg_size), from a "ramoops" device-tree node (the usual choice on ARM64 boards), or, since 6.11, from a named reserve_mem= region via mem_name. efi-pstore (drivers/firmware/efi/efi-pstore.c) writes records into UEFI variables and is the usual choice on x86 and ARM64 servers. fs/pstore/blk.c writes to a block device partition reserved for the purpose.

Several details make pstore usable in a dying kernel. Only one backend can be registered at a time. A second pstore_register() fails with "backend '…' already loaded", and the pstore.backend= parameter chooses which one wins. The dmesg front end copies up to pstore.kmsg_bytes of the log (default 10,240 bytes), newest first, in chunks of the backend's record size. Each chunk starts with a header such as Panic#2 Part1, and the parts of one dump share the number, so they can be put back together. The records are compressed with zlib deflate, the only algorithm left since 6.6, unless pstore.compress=none. In a panic, an emergency restart or an NMI, the CPU that holds the backend's buf_lock may already have been stopped. pstore therefore only tries the lock in those cases, and skips the dump if it is busy rather than deadlock. ramoops adds a max_reason parameter, which replaced dump_oops, optional Reed-Solomon ECC over each zone (ecc=), and mem_type, which chooses a write-combined, uncached or cached mapping. fs/pstore/zone.c is the common layer for backends on raw storage, and drivers/mtd/mtdpstore.c uses it to put pstore on an MTD flash partition. Some kmsg dumpers bypass pstore. mtdoops writes to flash directly, the Hyper-V dumper hands the log to the host, and drm_panic (6.10) draws the panic on the screen through the display's scanout buffer. It shows a short message (user), the tail of the log (kmsg) or a QR code that encodes it (qr_code, whose encoder is written in Rust; see Chapter 26), as chosen by drm.panic_screen=.

The magic SysRq key goes the other way: it lets a human ask a wedged machine for a report. A SysRq request comes from the keyboard (Alt+SysRq+key), a serial BREAK followed by the key, or a write to /proc/sysrq-trigger. The keyboard path runs from the input layer's interrupt handling, so it works when user space is dead and as long as interrupts are still being serviced. __handle_sysrq() in drivers/tty/sysrq.c looks the key up in sysrq_key_table[], checks its enable_mask against the /proc/sys/kernel/sysrq bitmask (default CONFIG_MAGIC_SYSRQ_DEFAULT_ENABLE), and calls the handler of the struct sysrq_key_op. Writes to /proc/sysrq-trigger bypass the mask, since that file can only be written by root. Subsystems add their own keys with register_sysrq_key(). kgdb adds g, for example. 3.5 Stack Traces: Unwinders and Symbols

Nearly every report in this chapter ends with a stack trace: the oops and WARN() (§3.1, §3.2), panic(), the lockup and hung-task detectors (§4), the SysRq l, t and w keys, the stacktrace trigger (§7.3) and perf callchains (§9.4). Producing one takes two separate pieces of machinery. An unwinder walks the stack and finds the chain of return addresses, and kallsyms turns each address into a function name and an offset. Both have to work in the worst conditions the kernel knows: in NMI context, with arbitrary locks held, and on a stack that may itself be corrupted. Neither may take a lock, allocate memory or fault.

On x86-64 the unwinder is chosen at build time under "Choose kernel unwinder" in arch/x86/Kconfig.debug. Since 4.15 the default has been the ORC unwinder (UNWINDER_ORC, added in 4.14; the name stands for "Oops Rewind Capability"). ORC is a simplified form of the DWARF call-frame information that user-space debuggers use. At build time objtool, run with --orc, follows every code path in every object file and records, for each range of instructions, a six-byte struct orc_entry from arch/x86/include/asm/orc_types.h. The entry says which register the caller's stack pointer is computed from and at what offset (sp_reg, sp_offset), where the caller's frame pointer was saved (bp_reg, bp_offset), and what kind of frame this is. ORC_TYPE_CALL is an ordinary call, with the return address just below the caller's stack pointer. ORC_TYPE_REGS marks a full struct pt_regs pushed on entry from an interrupt or exception, and ORC_TYPE_REGS_PARTIAL only the hardware's IRET frame. ORC_TYPE_END_OF_STACK and ORC_TYPE_UNDEFINED stop the walk. The entries live in two parallel sections, .orc_unwind_ip and .orc_unwind. scripts/sorttable sorts the vmlinux tables at build time, and a module's tables are sorted when it is loaded. orc_find() narrows the search with the orc_lookup[] index, which has one slot per 256-byte block of kernel text, and finishes with a binary search. unwind_next_frame() in arch/x86/kernel/unwind_orc.c then applies the entry to step to the caller. Because the tables, not the code, describe the frames, the compiler need not maintain a frame pointer, and %rbp becomes an ordinary register again. The Kconfig help puts the gain at 5–10% over frame pointers, at a cost of about 2–4 MB of tables. The alternatives are UNWINDER_FRAME_POINTER, which follows the %rbp chain, and UNWINDER_GUESS (EXPERT only), which treats every kernel text address on the stack as a return address.

Printing the trace is a separate step. __show_trace_log_lvl() in arch/x86/kernel/dumpstack.c prints Call Trace: and walks every stack the CPU may have been using, following the link from each one to the stack it interrupted: the exception stacks (NMI, #DB, #DF, #MC, and #VC in SEV guests), the IRQ stack, the entry trampoline stack and the task stack. Each stack's lines are bracketed by markers such as <IRQ> and </IRQ>, or <TASK> and </TASK>. The function does not print only the frames the unwinder found. It scans every word of each stack and prints every value that is a kernel text address. A value in the slot where the unwinder expected the next return address is printed plain; any other is printed with a ? prefix. Those question-marked lines are usually stale return addresses left over from earlier calls, but when a corrupted stack has confused the unwinder they are often the only clue to where the code came from. Where the function-graph tracer (§5.4) has replaced a return address with return_to_handler, ftrace_graph_ret_addr() recovers the original, and a struct pt_regs found at an interrupt or exception boundary is printed in full.

ARM64 always builds with frame pointers (FRAME_POINTER is selected unconditionally), and its unwinder in arch/arm64/kernel/stacktrace.c follows the AAPCS64 frame records. Each non-leaf function stores the pair x29, x30 (the caller's frame pointer and the link register) on its stack and points x29 at it. kunwind_stack_walk() checks that each record is 8-byte aligned and lies on a stack it knows about: the task stack, the per-CPU IRQ and overflow stacks, the SDEI stacks, or the EFI runtime-services stack. It strips any pointer-authentication code from each return address with ptrauth_strip_kernel_insn_pac(). Since 6.13 the exception entry code also leaves a struct frame_record_meta in each pt_regs, recognized by a frame record whose two words are zero. Its type FRAME_META_TYPE_PT_REGS tells the unwinder to step across an exception boundary using the saved PC, and FRAME_META_TYPE_FINAL marks the end of the task's stack. dump_backtrace() prints Call trace: and one line per frame, annotated with where the address came from: (P) for the PC in saved registers, (T) for a blocked task's saved PC, (C) for the caller of the dumping code, (U) when unknown, and F or K when the address was recovered from the function-graph tracer or from a kretprobe.

Code that needs a trace as data rather than as text uses the generic API in kernel/stacktrace.c: stack_trace_save() for the current task, stack_trace_save_tsk() for a sleeping task, stack_trace_save_regs() from a saved register set, and stack_trace_save_user() for the user-space part. Each fills an array of return addresses through the architecture's arch_stack_walk(). /proc/pid/stack is a thin wrapper around stack_trace_save_tsk() that shows up to 64 frames and is readable only with CAP_SYS_ADMIN. Live patching (Appendix B) needs a stronger guarantee: stack_trace_save_tsk_reliable() returns an error rather than a trace whenever the unwinder cannot be sure it found every frame, for example at an interrupt boundary or at an address with no unwind data. The livepatch transition calls it on every task to check that none is running a function being replaced. An architecture opts in with HAVE_RELIABLE_STACKTRACE. x86-64 has it whenever ORC or objtool stack validation is enabled, and ARM64 gained it in 6.17, together with HAVE_LIVEPATCH.

Turning an address into a name such as vfs_write+0x1a3/0x3c0 is the job of kallsyms (kernel/kallsyms.c). A kernel built with CONFIG_KALLSYMS carries its own symbol table, generated by scripts/kallsyms.c from the linker's symbol list, the same list that becomes System.map. Adding the table moves the code it describes, so scripts/link-vmlinux.sh links the kernel two or three times until the addresses stop changing. The table is built to be small and to be read without locks or allocation. Addresses are 32-bit relative offsets in kallsyms_offsets[], sorted by address. Names in kallsyms_names[] are compressed against a table of 256 tokens (kallsyms_token_table[]), each standing for a common substring, and kallsyms_markers[] records where every 256th name starts so a lookup need not decompress from the beginning. get_symbol_pos() does a binary search on the addresses and takes the next higher address as the end of the symbol, which gives both the offset and the size printed after the slash. Since 6.2 a second array, kallsyms_seqs_of_names[], keeps the symbols in name order, so kallsyms_lookup_name() is a binary search as well. An address outside vmlinux is tried in turn against loaded modules (module_address_lookup()), BPF JIT images and ftrace trampolines. Only text symbols are included unless CONFIG_KALLSYMS_ALL is set. User space sees the table as /proc/kallsyms, with the addresses shown as zero unless kptr_restrict and CAP_SYSLOG allow them.

Most code reaches kallsyms through the pointer extensions of printk() in lib/vsprintf.c. %pS prints function+0xoff/0xsize, followed by [module] for an address in a module. %pB is the variant for return addresses in backtraces. It looks up the address minus one, so that a call that is the last instruction of a function, as happens before a call to a noreturn function, is attributed to the caller rather than to whatever function follows it in memory. A trailing b, as in the %pBb and %pSb used by the dumpers of both architectures, adds the module's build ID when CONFIG_STACKTRACE_BUILD_ID (5.14) is set, so a report can be matched with the exact debug-info files. Offline, two scripts finish the job. scripts/faddr2line turns function+offset into a source file and line using the debug info in vmlinux or a module, and scripts/decode_stacktrace.sh runs over a whole pasted oops, adding a file and line to every frame.

Many detectors have to keep a stack trace rather than print it. KASAN records where every object was allocated and freed, kmemleak where each unreferenced block came from, page_owner who allocated each page, and the SLUB debugger who last allocated and freed each object. Storing a full array per object would cost more memory than the objects, and most of the traces are identical. The stack depot (lib/stackdepot.c, 4.6) removes the duplicates. stack_depot_save_flags() hashes the array of return addresses, looks it up in a hash table, and stores it only if it is new, in pools of four pages. It returns a 32-bit depot_stack_handle_t, which is all the caller keeps. stack_depot_fetch() and stack_depot_print() turn the handle back into a trace. Until 6.8 stored traces were never freed. A caller that passes STACK_DEPOT_FLAG_GET now takes a reference, which stack_depot_put() drops, so traces that are no longer needed can be evicted.

Detectors: Watchdogs and Debug Options

Many serious kernel bugs never trap. A CPU spins with interrupts disabled, a task waits forever for a mutex nobody will release, or a write lands one byte past a buffer. The kernel catches these with detectors: periodic checks that a CPU or task is still making progress, and compile-time instrumentation that checks memory and lock usage as the code runs. The progress checks (the soft- and hard-lockup watchdogs, the workqueue watchdog and the hung-task detector) cost little and are enabled in most production kernels. They only print a report by default; a fleet that would rather reboot and keep a crash dump sets kernel.softlockup_panic, kernel.hardlockup_panic, kernel.hung_task_panic or workqueue.panic_on_stall. Most compile-time instrumentation costs too much CPU time or memory for production, so it belongs in debug and test builds such as those run by syzbot and KernelCI.

4.1 The Soft- and Hard-Lockup Detectors

A soft lockup is a CPU that has run kernel code for a long time without scheduling. Interrupts still arrive, but no other task gets the CPU. A hard lockup is a CPU that has stopped taking interrupts at all. Both are detected in kernel/watchdog.c with one threshold, watchdog_thresh (default 10 seconds, /proc/sys/kernel/watchdog_thresh), and one per-CPU high-resolution timer. The timer fires every sample_period, which is the soft-lockup threshold of 2 × watchdog_thresh divided by NUM_SAMPLE_PERIODS (5), so 4 seconds by default. Its handler, watchdog_timer_fn(), does three things, shown in the top half of Figure 29-5: 

/* kernel/watchdog.c (abridged) */
static enum hrtimer_restart watchdog_timer_fn(struct hrtimer *hrtimer)
{
	...
	watchdog_hardlockup_kick();	/* hrtimer_interrupts++ (proof of IRQs) */

	/* kick the softlockup detector */
	if (completion_done(this_cpu_ptr(&softlockup_completion))) {
		reinit_completion(this_cpu_ptr(&softlockup_completion));
		stop_one_cpu_nowait(smp_processor_id(),
				softlockup_fn, NULL,
				this_cpu_ptr(&softlockup_stop_work));
	}

	hrtimer_forward_now(hrtimer, ns_to_ktime(sample_period));
	...
	/* Check for a softlockup. */
	touch_ts = __this_cpu_read(watchdog_touch_ts);
	duration = is_softlockup(touch_ts, period_ts, now);
	if (unlikely(duration)) {
		...
		pr_emerg("BUG: soft lockup - CPU#%d stuck for %us! [%s:%d]\n", ...);
		...
		add_taint(TAINT_SOFTLOCKUP, LOCKDEP_STILL_OK);
		...
		thresh_count = duration / get_softlockup_thresh();
		if (softlockup_panic && thresh_count >= softlockup_panic)
			panic("softlockup: hung tasks");
	}
	return HRTIMER_RESTART;
}

The soft-lockup proof works through the CPU stopper. softlockup_fn() runs on the per-CPU stopper thread, the highest-priority task on the CPU, and it updates watchdog_touch_ts. If that timestamp is more than 2 × watchdog_thresh seconds old when the timer next looks, the scheduler has not been able to run even the highest-priority task for that long. The usual cause is a loop with preemption disabled, or a non-preemptible kernel spinning without cond_resched(). Code that is known to run for a long time legitimately calls touch_softlockup_watchdog(). Since 7.0, softlockup_panic is a count, not a boolean: the kernel panics only once a single lockup has lasted that many thresholds. On 6.10 and later kernels, CONFIG_SOFTLOCKUP_DETECTOR_INTR_STORM also samples per-CPU interrupt counts. It can then report that a soft lockup was caused by an interrupt storm, not by a task.

Several details keep the check honest. The timestamps come from get_timestamp(), which is running_clock() shifted right by 30 bits, roughly seconds. Each timer run first calls kvm_check_and_clear_guest_paused(). If the host stopped this virtual machine, the guest's clock jumped while nothing ran, and the function touches the watchdog so that the jump is not mistaken for a lockup. A touch does not record a new time. touch_softlockup_watchdog() stores the marker SOFTLOCKUP_DELAY_REPORT in watchdog_report_ts, and the next timer run simply starts a new measurement period. A report also starts a new period (update_report_ts()), so a CPU that stays stuck is reported again every 2 × watchdog_thresh seconds, each time with a larger "stuck for" figure. The report is printed under printk_cpu_sync_get_irqsave(), so lines from several CPUs do not interleave. After the "BUG: soft lockup" line, the interrupt-storm option prints the CPU's system, softirq, hardirq and idle percentages for each of the last five sample periods. If the newest sample showed more than 50% hardirq time, the kernel also took a snapshot of the interrupt counts one sample period into the lockup, and it now prints the five interrupts that fired most often since then. The module list follows, then the last places interrupts were enabled and disabled (print_irqtrace_events()), then the registers and stack of the interrupted code. Last, the kernel sets TAINT_SOFTLOCKUP (L). One consumer acts before any report: at three quarters of the threshold, scx_softlockup() (6.13) tells sched_ext to eject a loaded BPF scheduler, because a misbehaving one can live-lock the machine into soft lockups. scx_hardlockup() (6.19) does the same when a hard lockup is detected, and the report is then skipped.

A hard lockup cannot be detected from the hrtimer, because the hrtimer is an interrupt and a hard-locked CPU does not take interrupts. The check must come from something that still runs: either a non-maskable interrupt on the same CPU, or another CPU. Both designs exist. Each one compares the CPU's hrtimer_interrupts count with the value it saw last time (is_hardlockup()) and reports "Watchdog detected hard LOCKUP on cpu n" if the count has not moved. The check increments hardlockup_count, and it reports a CPU only once until that CPU recovers. If the stuck CPU is the one running the check (the NMI case), the report shows the registers of the code the NMI interrupted. If a neighbor detected it (the buddy case), the neighbor asks the stuck CPU for its backtrace with trigger_single_cpu_backtrace(). With hardlockup_panic set, the report ends in nmi_panic(regs, "Hard LOCKUP"), the NMI-safe entry to panic() described in §3.3. How the check is delivered is where the two architectures in this book differ most.

  • The perf hard-lockup detector (kernel/watchdog_perf.c, CONFIG_HARDLOCKUP_DETECTOR_PERF) creates one pinned PERF_COUNT_HW_CPU_CYCLES event per CPU (§9). Its sample period is chosen by hw_nmi_get_sample_period() so that the counter overflows about once every watchdog_thresh seconds. Each overflow runs watchdog_overflow_callback(), and from there watchdog_hardlockup_check(). On x86 the PMU overflow interrupt is delivered as an NMI, so this works however long interrupts have been disabled. There, hw_nmi_get_sample_period() is just cpu_khz × 1000 × watchdog_thresh. A CPU running above its nominal frequency in turbo mode overflows sooner than that. So x86-64 selects CONFIG_HARDLOCKUP_CHECK_TIMESTAMP, and the NMI handler ignores an overflow that arrives less than 4/5 of the threshold after the previous one. The detector holds one hardware counter on every CPU for as long as it runs, and the boot log says so ("NMI watchdog: Enabled. Permanently consumes one hw-PMU counter."). nmi_watchdog=0 or the kernel.nmi_watchdog sysctl gives the counters back to perf users. Since 6.10, nmi_watchdog=rNNN counts a raw PMU event instead of cycles, for example Intel's rarely used ref-cycles event (r300), and the kernel falls back to cycles if the raw event does not work.
  • ARM64 has no architectural NMI. Its PMU interrupt can behave like one only with pseudo-NMI: CONFIG_ARM64_PSEUDO_NMI, enabled at boot with irqchip.gicv3_pseudo_nmi=1. In that mode the kernel no longer masks interrupts by setting PSTATE.I. It lowers the GICv3 priority mask instead, so a higher-priority interrupt still gets through while "interrupts are disabled" (Chapter 4 describes the mechanism). arch/arm64/kernel/watchdog_hld.c makes the perf detector available only if arm_pmu_irq_is_nmi() confirms that the PMU driver could request_nmi() its interrupt. It derives the period from the CPU's maximum cpufreq frequency, or 5 GHz if that is unknown. Which detector a kernel has is decided by Kconfig, not at boot. Building with CONFIG_ARM64_PSEUDO_NMI makes the perf detector available (HAVE_PERF_EVENTS_NMI), so Kconfig picks it over the buddy detector unless CONFIG_HARDLOCKUP_DETECTOR_PREFER_BUDDY is set. Booted without irqchip.gicv3_pseudo_nmi=1, such a kernel logs "NMI not fully supported" and "Hard watchdog permanently disabled" and has no hard-lockup detector at all. The probe also has to wait: the arm_pmuv3 driver registers after the watchdog starts, so it calls lockup_detector_retry_init() to repeat the probe once the PMU exists.
  • The buddy detector (kernel/watchdog_buddy.c, CONFIG_HARDLOCKUP_DETECTOR_BUDDY, 6.5) needs no NMI and no PMU. On every third hrtimer tick, each CPU checks the hrtimer_interrupts count of the next online CPU (watchdog_next_cpu()). Three sample periods are 12 seconds by default, 20% more than watchdog_thresh. A hard-locked CPU is then reported by its neighbor. The neighbor cannot read the stuck CPU's registers. It can only ask that CPU for a backtrace, which works only if NMI backtraces are available. When a CPU comes online or goes offline, the neighbor relationships shift, so watchdog_hardlockup_enable() and watchdog_hardlockup_disable() first touch the next CPU's watchdog to avoid a false report. The buddy detector costs no hardware counter. It is the practical choice on ARM64 systems without pseudo-NMI, and on virtual machines without a virtual PMU.

Both detectors are controlled from the kernel command line and from /proc/sys/kernel. nowatchdog turns both off, nosoftlockup only the soft-lockup check and nmi_watchdog=0 only the hard-lockup check. The sysctls watchdog, soft_watchdog and nmi_watchdog do the same at run time. watchdog_cpumask (4.2) limits the detectors to a set of CPUs. It starts as the housekeeping CPUs, so nohz_full CPUs, which are meant to run one task without interruption, are left out by default, and the boot log says "Disabling watchdog on nohz_full cores by default". softlockup_panic and hardlockup_panic, with build-time defaults from CONFIG_BOOTPARAM_SOFTLOCKUP_PANIC and CONFIG_BOOTPARAM_HARDLOCKUP_PANIC, turn a report into a panic. softlockup_all_cpu_backtrace (3.16) and hardlockup_all_cpu_backtrace (4.4) add an NMI backtrace of every other CPU. That is often the only way to see which CPU holds the lock a stuck CPU is spinning on. Since 6.19, softlockup_sys_info and hardlockup_sys_info accept the same list of extra dumps as panic_sys_info in §3.3, and all_bt in that list implies the all-CPU backtrace. Since 6.16, /sys/kernel/softlockup_count and /sys/kernel/hardlockup_count count reports since boot, so monitoring can notice a lockup that did not panic the machine. KVM and Hyper-V guests on x86 call hardlockup_detector_disable() at boot, because a vCPU that an overcommitted host does not schedule looks exactly like a hard-locked CPU.

The hrtimer side of this mechanism (high-resolution timers and how they are programmed) is covered in Chapter 6. The one call the rest of the kernel needs is touch_nmi_watchdog(). It is used in code that legitimately keeps a CPU busy with interrupts off for a long time, such as the reboot delay loop in panic(). RCU has its own, independent detector. An RCU CPU stall warning is printed when a grace period has waited too long (21 seconds by default) for a CPU to pass through a quiescent state. That usually means the CPU is looping with preemption or interrupts disabled, so it often appears before or alongside a soft-lockup report. The bookkeeping RCU does on each scheduler tick, which also drives stall detection, is described in Chapter 6.

The workqueue watchdog mentioned in §1 applies the same idea to the worker pools of Chapter 4. wq_watchdog_timer_fn() in kernel/workqueue.c is an ordinary timer that runs every workqueue.watchdog_thresh seconds (30 by default; 0 turns it off). For each pool with pending work it takes the later of two times: the pool's last_progress_ts, which advances when work arrives at an idle pool or a worker starts processing, and the last time the watchdog was touched. touch_softlockup_watchdog() touches this watchdog too, through wq_watchdog_touch(). If that time is older than the threshold, the timer prints "BUG: workqueue lockup - pool cpus=… stuck for ns!" for each stuck pool and dumps the state of every workqueue with show_all_workqueues(), the same dump SysRq-t ends with. For a stuck per-CPU pool it also prints the stacks of the pool's busy workers. The usual culprit is a work item that runs for a long time without sleeping, which stops the concurrency-managed pool from starting the next one. workqueue.panic_on_stall (6.12) panics after that many stalls, and workqueue.panic_on_stall_time (7.0) panics once a single stall has lasted that many seconds. Like the soft-lockup check, the timer calls kvm_check_and_clear_guest_paused() so that a paused virtual machine does not look stuck.

4.2 The Hung-Task Detector

A task can also get stuck while every CPU is healthy, for example by sleeping in TASK_UNINTERRUPTIBLE on a lock or I/O completion that never comes. The hung-task detector in kernel/hung_task.c is a kernel thread, khungtaskd. It wakes every hung_task_timeout_secs (default CONFIG_DEFAULT_HUNG_TASK_TIMEOUT, 120 seconds), or more often if hung_task_check_interval_secs (4.19) is set lower, and walks every thread in check_hung_uninterruptible_tasks(). It does not record when a task went to sleep. It looks at the task's context-switch counters instead. task_is_hung() skips any task that is not in TASK_UNINTERRUPTIBLE, or that is also TASK_WAKEKILL, TASK_NOLOAD or TASK_FROZEN. For the rest it compares nvcsw + nivcsw with the last_switch_count saved on the previous scan. If the count changed, it saves the new count and the current jiffies in last_switch_time. A task whose switch count has not changed for a full timeout, while it is in a plain uninterruptible sleep, is reported with "INFO: task comm:pid blocked for more than n seconds." and its stack. The design deliberately skips TASK_KILLABLE and TASK_IDLE sleepers. A killable sleep can be ended by the user, and an idle kernel thread is supposed to sleep forever.

The report is meant for a log that may be read much later. After the "blocked for more than" line come the taint flags and the kernel release, the line "Blocked by coredump." (6.14) if the task is waiting for its own process's core dump to finish, the hint "echo 0 > /proc/sys/kernel/hung_task_timeout_secs" disables this message., and the task's stack from sched_show_task(). Only hung_task_warnings reports (10 by default, -1 for no limit) are printed per boot. After the last one the kernel says "Future hung task reports are suppressed, see sysctl kernel.hung_task_warnings". Every detection is still counted in hung_task_detect_count (6.13, in /proc/sys/kernel) and still fires the sched_process_hang tracepoint. When a scan reported hung tasks, it then prints every lock held in the system (with lockdep) and, if hung_task_all_cpu_backtrace (5.8) is set, a backtrace of every CPU. hung_task_sys_info (6.19) adds any of the panic_sys_info dumps of §3.3. hung_task_panic was a boolean until 6.19. It is now a count: the kernel panics with "hung_task: blocked tasks" once a single scan finds that many hung tasks, so a value above 1 rides out an isolated stall but still reboots a machine where a lock pile-up has stuck many tasks at once. A few more details keep the scan cheap and quiet. hung_task_check_count caps how many threads one scan visits. The walk drops the RCU read lock every tenth of a second so that it does not hold up a grace period. khungtaskd pauses across suspend and hibernation, and it stops reporting once the kernel has oopsed or panicked.

The stack of a hung task shows where it is waiting, but not who it is waiting for. Recent kernels add that with blocker tracking (CONFIG_DETECT_HUNG_TASK_BLOCKER). Before a task sleeps on a mutex (since 6.15), a semaphore (6.16) or an rw-semaphore (6.17), it records the lock and its type in task_struct->blocker. When the task is reported, debug_show_blocker() finds the lock's owner, or for a semaphore its last holder, and prints that task's stack as well ("INFO: task A:1 is blocked on a mutex likely owned by task B:2."). For an rw-semaphore the message also says whether each task is a reader or a writer. One report then shows both ends of the deadlock. Lockdep, described below, catches the same class of bug before it happens. The hung-task detector catches it in production, where lockdep is not enabled.

UBSAN (lib/ubsan.c, 4.5) uses the compiler's undefined-behavior instrumentation. Every checked operation gets a test and a call to a __ubsan_handle_*() function that prints a report. The checks are chosen one by one in lib/Kconfig.ubsan. Array bounds (CONFIG_UBSAN_BOUNDS), invalid bool loads (CONFIG_UBSAN_BOOL) and invalid enum loads (CONFIG_UBSAN_ENUM) are on by default. Shift overflow (CONFIG_UBSAN_SHIFT), integer division by zero (CONFIG_UBSAN_DIV_ZERO) and reaching __builtin_unreachable() (CONFIG_UBSAN_UNREACHABLE) must be selected. Misalignment (CONFIG_UBSAN_ALIGNMENT) defaults to on only on architectures without efficient unaligned access. Integer overflow and truncation (CONFIG_UBSAN_INTEGER_WRAP, 6.15) is still marked BROKEN while the kernel is annotated for it. A report opens with the cut here line and "UBSAN: array-index-out-of-bounds in file:line:column", gives the offending values, and ends with a stack dump and ---[ end trace ]---. It is a warning, so panic_on_warn makes it fatal (6.2), and a KUnit test running at the time is marked as failed. With CONFIG_UBSAN_TRAP the call is replaced by a trap instruction, which keeps the code about 5% smaller, small enough for production. The trap is a UD1 on x86 and a BRK with immediate 0x5500 plus the check type on ARM64, decoded by the same handlers shown in §3.1. Instead of the full report, the kernel names the check ("UBSAN: array index out of bounds") and oopses. On ARM64 with KVM in nVHE or protected mode, CONFIG_UBSAN_KVM_EL2 (6.16) instruments the EL2 hypervisor code as well, where any violation panics the host. The array-bounds check has become important as the kernel annotates flexible arrays with __counted_by. It is one of the hardening features Chapter 27 discusses.

kmemleak (mm/kmemleak.c, 2.6.31) records every slab, vmalloc and per-CPU allocation, and the memblock allocations made during boot. Its kmemleak kernel thread periodically does what a tracing garbage collector does: it scans the data sections, the stacks and every recorded object for values that look like pointers to recorded objects. The scan is conservative. Any word that happens to hold an object's address keeps that object alive, so kmemleak can miss a leak but rarely invents one. Two rules cut false reports further. An object must be at least 5 seconds old, and an unreferenced object whose contents changed since the previous scan (kmemleak keeps a CRC32 checksum of each object) counts as referenced for one more round, since something is evidently still writing to it. With CONFIG_DEBUG_KMEMLEAK_AUTO_SCAN the first scan runs 60 seconds after boot and then every 10 minutes. Each leak is reported once, in /sys/kernel/debug/kmemleak, as an "unreferenced object 0x… (size n):" entry. The entry shows the allocating task and the time, a hex dump of the object's first bytes, a "backtrace (crc …):" line and the allocation stack. The log gets one line, "kmemleak: n new suspected memory leaks". Writing to the same file controls kmemleak. scan forces a scan, scan=secs changes the period, clear forgets the leaks reported so far, dump=addr prints what is known about one object, and off disables kmemleak for good. kmemleak=off on the command line disables it at boot, and kmemleak=on enables it in a kernel built with CONFIG_DEBUG_KMEMLEAK_DEFAULT_OFF. Code that keeps its only reference somewhere kmemleak does not scan annotates the object with kmemleak_not_leak(), kmemleak_ignore() or kmemleak_no_scan().

Debug objects (lib/debugobjects.c, 2.6.26) track the life cycle of objects such as timers, hrtimers, work items, RCU heads and per-CPU counters. Each type supplies a struct debug_obj_descr, and its code calls debug_object_init(), debug_object_activate(), debug_object_deactivate(), debug_object_destroy() and debug_object_free() at the matching points. For a timer these are timer_setup(), add_timer(), expiry or deletion, and so on. The tracker keeps a struct debug_obj for each live object in a hash of 16,384 buckets keyed by address, with one of the states initialized, inactive, active or destroyed. A transition that does not fit, such as activating an object that is already active or freeing one that is still active, is reported with a WARN: "ODEBUG: free active (active state 0) object: … object type: timer_list hint: fn". The hint comes from the descriptor's debug_hint() callback. It names the timer or work function, which usually identifies the owner faster than the address does. The descriptor's fixup callbacks then try to repair the damage so the system keeps running. timer_fixup_free(), for example, stops the timer with timer_delete_sync() before its memory is reused. With CONFIG_DEBUG_OBJECTS_FREE, the slab, page and vmalloc free paths also call debug_check_no_obj_freed(). It catches a kfree() of memory that still contains an active object even when the owner never called debug_object_free(). Only the first five reports are printed. The warnings count in /sys/kernel/debug/debug_objects/stats keeps going. The debug_objects and no_debug_objects boot parameters override CONFIG_DEBUG_OBJECTS_ENABLE_DEFAULT.

The fault-injection framework (lib/fault-inject.c, 2.6.20) gives each failure point a struct fault_attr and a should_fail() test. Instances such as failslab, fail_page_alloc, fail_make_request, fail_io_timeout, fail_futex, fail_usercopy (5.10) and fail_skb_realloc (6.13) appear in debugfs with the same controls. probability is a percentage, interval fails only every nth eligible call, times limits the total number of failures (-1 for no limit), and space lets that many bytes of requests succeed first. task-filter restricts failures to tasks that have written 1 to /proc/pid/make-it-fail. With CONFIG_FAULT_INJECTION_STACKTRACE_FILTER, require-start, require-end, reject-start and reject-end restrict them to callers whose stack passes through a given address range. The same settings can be given at boot, as in failslab=interval,probability,space,times. For a deterministic test, a task writes n to /proc/self/fail-nth (4.13), and the nth fault-injection point it reaches fails whatever the probabilities say. A fuzzer such as syzkaller uses this to fail each allocation in a system call in turn. fail_function (4.16) extends the idea to any function marked with ALLOW_ERROR_INJECTION(). Writing a function name to /sys/kernel/debug/fail_function/inject installs a kprobe that skips the function and returns the chosen retval. Together they let a test force exactly the allocation failure that a real system would see once a year.

CONFIG_DEBUG_VM is the memory manager's assertion switch. It turns VM_BUG_ON() and VM_WARN_ON() into real BUG_ON() and WARN_ON() checks. Without it they compile to BUILD_BUG_ON_INVALID(), which only checks that the expression is valid C and generates no code. The variants VM_BUG_ON_PAGE(), VM_BUG_ON_FOLIO(), VM_BUG_ON_VMA() and VM_BUG_ON_MM(), and their VM_WARN_ON_ONCE_*() counterparts, first dump the page, folio, VMA or mm_struct involved (for a page through dump_page()), which is how most page-state bugs are diagnosed. The checks are cheap compared with the sanitizers, so they belong in every test kernel.

ftrace: Function Tracing by Live Patching

ftrace can call a tracing function at the entry of almost any of the kernel's tens of thousands of functions. It does this without recompiling the kernel and, while tracing is off, at a cost of one NOP per function. The idea is to make the compiler leave a small placeholder at the start of every function, record where the placeholders are, and rewrite them in the running kernel's text when a tracer asks. The same machinery supports the function tracer, the function-graph tracer, kprobes on function entry, fprobes, BPF trampolines and live patching. All of it is built when CONFIG_FUNCTION_TRACER is set, and the patching needs CONFIG_DYNAMIC_FTRACE, which is on by default with it. Without dynamic ftrace, every function really calls the tracer stub on every entry.

5.1 Call Sites: -pg, -mfentry, and Patchable Function Entries

The placeholder comes from compiler options that were originally meant for profilers. GCC's -pg inserts a call to mcount into every function, after the prologue. The first ftrace, merged in 2.6.27 (kernel/trace/ftrace.c), used it. Calling mcount after the prologue meant the tracer could not see the arguments in their original registers. x86-64 therefore moved to -mfentry in 3.7, which emits a call __fentry__ as the very first instruction, before the stack frame is built. At that point the arguments and the return address are exactly where the caller put them. ARM64 started with -pg and _mcount in 3.16. Since 5.5 it uses a more general compiler feature, -fpatchable-function-entry=N,M. The compiler emits N NOPs, M of them before the function's entry symbol, and records each site's address in a section. There is nothing to call at all until ftrace writes an instruction.

The build has to collect the call sites into a table, and kernel/trace/Kconfig chooses among three ways of doing it. The preferred one is the compiler itself. With FTRACE_MCOUNT_USE_CC, which is selected whenever the compiler accepts -mrecord-mcount (GCC does), the compiler writes the address of each call __fentry__ into a __mcount_loc section. If it cannot, x86-64 falls back to objtool (FTRACE_MCOUNT_USE_OBJTOOL, 5.12). objtool walks every object file, records each call, and with HAVE_OBJTOOL_NOP_MCOUNT also overwrites it with a 5-byte NOP. Architectures with neither fall back to the original scripts/recordmcount. On ARM64 the compiler writes the table into __patchable_function_entries as part of -fpatchable-function-entry. The linker script places either section between __start_mcount_loc and __stop_mcount_loc. Since 5.17 on x86-64 and 6.15 on ARM64, scripts/sorttable sorts it at build time (BUILDTIME_MCOUNT_SORT), so boot does not have to. ftrace_init() runs early in start_kernel(), after the memory allocators are up and before the scheduler is initialized. It passes the range to ftrace_process_locs(), which allocates one struct dyn_ftrace per site in page-sized groups and logs ftrace: allocating N entries in M pages. Each record holds the call-site address ip, a flags word, and an architecture part. The low bits of flags count how many tracers want this function, and the high bits record whether the site is enabled, needs full registers, or calls a dedicated trampoline. Modules go through the same path when they load, and their table is sorted then.

Whether the kernel boots with CALLs or NOPs at those sites depends on the toolchain. x86 does not ask GCC for -mnop-mcount, so a GCC-built x86-64 vmlinux has a real call __fentry__ at the top of every traceable function, and __fentry__ itself is a bare RET (arch/x86/kernel/ftrace_64.S). Until ftrace_init() runs, every function call pays for that extra call. Then ftrace_update_code() converts each site with ftrace_nop_initialize(). On x86 that is ftrace_make_nop(), which first checks that the site really holds the expected CALL. At this point only the boot CPU runs and interrupts are disabled, so x86 writes with text_poke_early() instead of the INT3 protocol of §5.2. A module's sites are converted the same way before any of its code can run. When objtool has already written the NOPs (CC_USING_NOP_MCOUNT), ftrace_need_init_nop() is false and the step is skipped. On ARM64 the entry already holds NOPs, and the step is ftrace_init_nop(), which writes the MOV X9, X30 described below and points the ops literal at ftrace_nop_ops. The boot log then shows ftrace: allocated M pages with G groups.

Figure 29-6 shows the two architectures' call sites in their two states. On x86-64 the site is one 5-byte instruction after the optional ENDBR64 that indirect-branch tracking requires. It is either a 5-byte NOP or a CALL rel32. ARM64 instructions are 4 bytes and a BL clobbers the link register, so one instruction is not enough. With DYNAMIC_FTRACE_WITH_ARGS (6.2) the compiler leaves two NOPs at the entry. At boot ftrace_init_nop() turns the first into MOV X9, X30, which saves the caller's return address. The second is the one that is later turned into BL ftrace_caller. With DYNAMIC_FTRACE_WITH_CALL_OPS (6.3), the compiler also leaves two NOPs before the function, 8-byte aligned. ftrace uses them as a 64-bit literal that holds a pointer to the struct ftrace_ops this function should call. With BTI enabled, a BTI C landing pad precedes the entry NOPs. A BL reaches only ±128 MB, so a module far from the core kernel calls through a PLT entry. CALL_OPS has two preconditions in arch/arm64/Kconfig. It cannot be combined with kernel CFI (CFI), which stores a type hash just before each function where the literal would go. With GCC it also needs -falign-functions, which GCC ignores at -Os, so CC_OPTIMIZE_FOR_SIZE rules it out. The ARM64 Makefile then passes -fpatchable-function-entry=4,2 instead of -fpatchable-function-entry=2. Without CALL_OPS every enabled site calls the shared ftrace_caller, which takes the ops from the global function_trace_op or walks the list. The MOV X9, X30 costs almost nothing while tracing is off, because under the AAPCS64 calling convention X9 is a scratch register that holds nothing live at function entry.

Not every recorded address is usable. When a __weak function is overridden, its code may be left in the image without a symbol, or dropped, but its __mcount_loc entry survives. The address then resolves to whatever symbol precedes it, at a large offset. Since 6.15, scripts/sorttable zeroes every entry that does not fall inside a function in the symbol table, and ftrace_process_locs() skips zeroed entries. As a second line of defense on x86, test_for_valid_rec() checks that each address lies no further than FTRACE_MCOUNT_MAX_OFFSET (the size of ENDBR64) from the start of a symbol. A record that fails is marked FTRACE_FL_DISABLED, can never be enabled, and is listed as __ftrace_invalid_address___offset in available_filter_functions.

The opposite problem is code that must never get a call site. notrace (include/linux/compiler_types.h) expands to __attribute__((__no_instrument_function__)) on x86, or to __attribute__((patchable_function_entry(0, 0))) where the call sites are patchable entries, as on ARM64. Whole files opt out by removing $(CC_FLAGS_FTRACE) from their compiler flags in the Makefile. The tracing code in kernel/trace/ itself is built that way, along with code that runs before ftrace can cope, such as early boot and decompression code. FUNCTION_SELF_TRACING (6.19) turns tracing back on for a few of the tracing files, for debugging the tracing infrastructure.

5.2 Rewriting Kernel Text Safely

Changing an instruction in code that other CPUs may be executing at that moment is the hard part. The architectures again take different approaches, because their rules for cross-modifying code differ. On x86 a 5-byte instruction can cross a cache line, and another CPU may fetch half of the old instruction and half of the new. The kernel therefore uses the INT3 protocol of smp_text_poke_batch_add() and smp_text_poke_batch_finish() (arch/x86/kernel/alternative.c; the names date from 6.16). The protocol has three steps, with an IPI to synchronize all CPUs after each. First it writes a one-byte INT3 over the first byte of every site. Then it writes the last four bytes. Finally it replaces the INT3 with the new first byte. A CPU that hits the INT3 in the meantime traps into smp_text_poke_int3_handler(), which emulates the new instruction, so every CPU sees either the whole old instruction or the whole new one. ftrace queues sites in batches of up to 256 (TEXT_POKE_ARRAY_MAX, one page of 16-byte entries). A full batch, or a site that is not in ascending address order, is flushed with its three synchronizing IPIs before the next one is started. ftrace first checks that every site holds the bytes it expects, so a corrupted site stops the operation with a ftrace_bug() report before anything is written: 

/* arch/x86/kernel/ftrace.c (abridged) */
void ftrace_replace_code(int enable)
{
	...
	for_ftrace_rec_iter(iter) {		/* pass 1: verify */
		rec = ftrace_rec_iter_record(iter);
		switch (ftrace_test_record(rec, enable)) {
		case FTRACE_UPDATE_IGNORE:
		default:
			continue;
		case FTRACE_UPDATE_MAKE_CALL:
			old = ftrace_nop_replace();
			break;
		case FTRACE_UPDATE_MODIFY_CALL:
		case FTRACE_UPDATE_MAKE_NOP:
			old = ftrace_call_replace(rec->ip, ftrace_get_addr_curr(rec));
			break;
		}
		ret = ftrace_verify_code(rec->ip, old);
		if (ret) {
			...
			ftrace_bug(ret, rec);
			return;
		}
	}

	for_ftrace_rec_iter(iter) {		/* pass 2: queue the new bytes */
		...
		smp_text_poke_batch_add((void *)rec->ip, new, MCOUNT_INSN_SIZE, NULL);
		ftrace_update_record(rec, enable);
	}
	smp_text_poke_batch_finish();		/* INT3, tail, head, sync */
}

A failed check prints a report headed ------------[ ftrace bug ]------------. For a mismatch it says ftrace failed to modify and the symbol, and dumps the actual: and expected: bytes. It then names the operation that was attempted, such as Setting ftrace call site to NOP or Initializing ftrace call sites, and prints the record's flags, reference count and trampolines. A fault on reading or writing the site is reported as ftrace faulted on modifying or ftrace faulted on writing. A warning follows, and with it ftrace_kill(), which disables ftrace for good: it sets ftrace_disabled, stops calling any tracer, and also disarms the kprobes that use ftrace. The header of the trace file then reads # WARNING: FUNCTION TRACING IS CORRUPTED. The cause is usually something else that wrote the text, such as another patching mechanism or a stray write.

ARM64 is simpler, because every instruction is a naturally aligned 4-byte word. The architecture allows a concurrent writer to replace a NOP with a B/BL (and back) without stopping other CPUs, as long as the instruction cache is invalidated afterward. ftrace_modify_code() calls aarch64_insn_patch_text_nosync() for each site. The ops literal is written with aarch64_insn_write_literal_u64(), and an aligned 64-bit store is single-copy atomic. The generic code calls arch_ftrace_update_code(), which by default runs the whole update under stop_machine(). x86 overrides it to patch directly, since the INT3 protocol needs no stop. ARM64 also patches without stopping the machine, and passes FTRACE_MAY_SLEEP so a long update can reschedule. The order of the two writes keeps every CPU consistent. ftrace_make_call() first stores the ops pointer in the literal and then turns the NOP into BL. ftrace_make_nop() does the reverse: it points the literal at ftrace_nop_ops, whose callback does nothing, and then restores the NOP. A CPU that runs the site in between finds either no call or a valid ops. When a module site is out of BL range, the branch goes to the module's ftrace PLT, and a module without one fails with ftrace: no module PLT for function.

Both architectures write through a temporary writable alias of the text page, because kernel text is mapped read-only (text_poke() on x86, the FIX_TEXT_POKE0 fixmap on ARM64). On x86 ftrace holds text_mutex while it patches, which serializes it against module loading and other text changes. ARM64 serializes the individual writes with a raw spinlock, patch_lock. The same patching primitives serve jump labels (§7.1), static calls, kprobes (§8.1) and, on x86, the boot-time alternatives.

Rewriting the sites is one step of ftrace_modify_all_code() (kernel/trace/ftrace.c), which orders the steps so that no CPU can call a callback for a function it does not want. When the set of tracers changes, it first points the shared ftrace_call slot in ftrace_caller at ftrace_ops_list_func(), which checks every ops' filter. It then rewrites the sites. Only after that does it publish the new function_trace_op, send an IPI so that every CPU sees it, and switch the slot to the final function, which may skip the checks when a single ops is left. Turning the function-graph tracer's return hook on or off comes last. Since 6.19, x86-64 can also patch a site to a JMP instead of a CALL (DYNAMIC_FTRACE_WITH_JMP). BPF trampolines use it for fexit and fmod_ret programs, which call the traced function themselves. Entered by a jump, the trampoline returns straight to the traced function's caller, which keeps the CPU's return-address predictor balanced.

5.3 struct ftrace_ops: Who Gets Called

A user of ftrace describes itself with a struct ftrace_ops (include/linux/ftrace.h). It gives a callback, a set of functions to attach to (a filter hash and a "notrace" hash; an empty filter means every function), and flags that say what the callback needs: 

/* include/linux/ftrace.h (abridged) */
typedef void (*ftrace_func_t)(unsigned long ip, unsigned long parent_ip,
			      struct ftrace_ops *op, struct ftrace_regs *fregs);

struct ftrace_ops {
	ftrace_func_t			func;
	struct ftrace_ops __rcu		*next;
	unsigned long			flags;	/* FTRACE_OPS_FL_* */
	void				*private;
	...
#ifdef CONFIG_DYNAMIC_FTRACE
	struct ftrace_ops_hash		local_hash;
	struct ftrace_ops_hash		*func_hash;	/* filter + notrace */
	...
	unsigned long			trampoline;	/* x86: per-ops trampoline */
	unsigned long			trampoline_size;
	...
#ifdef CONFIG_DYNAMIC_FTRACE_WITH_DIRECT_CALLS
	unsigned long			direct_call;	/* e.g. a BPF trampoline */
#endif
#endif
};

register_ftrace_function() adds the ops to the global ftrace_ops_list, recomputes the per-record reference counts, and runs ftrace_replace_code() on every record whose state changed. What each enabled site calls depends on how many ops want it. If exactly one ops traces a function, the site can call that ops directly. On x86 that means an ops-specific trampoline, a copy of ftrace_caller made by create_trampoline() with the ops pointer and callback built in. On ARM64 it means writing the ops pointer into the function's literal. If several ops want the same function, the site goes through ftrace_ops_list_func(), which walks the list and tests each ops' hash. On ARM64 the literal then points to ftrace_list_ops. Tracers do not pay for each other when their filters do not overlap.

The flags carry the contract. FTRACE_OPS_FL_SAVE_REGS asks for a complete pt_regs. Of this book's two architectures only x86 provides it, through ftrace_regs_caller. The normal ftrace_regs holds only the argument registers, stack pointer, frame pointer and return address. That is what DYNAMIC_FTRACE_WITH_ARGS guarantees, and it is all ARM64 offers. FTRACE_OPS_FL_IPMODIFY says the callback may change the instruction pointer, so the traced function resumes somewhere else. At most one IPMODIFY ops may own a function. FTRACE_OPS_FL_RECURSION asks ftrace to protect the callback against recursion (the meaning was inverted in 5.11, when protection became opt-in). With it, or with FTRACE_OPS_FL_RCU, the site calls ftrace_ops_assist_func(), which takes a recursion bit around the callback and, for FL_RCU, skips the callback where RCU is not watching. Without it, the callback must guard itself with ftrace_test_recursion_trylock(), as the function tracer and klp_ftrace_handler() do. The bits live in the task's current->trace_recursion, one per context (normal, softirq, irq, NMI), plus one "transition" bit that tolerates a single nested hit while preempt_count is being updated on interrupt entry. A function that recurses anyway is dropped silently; CONFIG_FTRACE_RECORD_RECURSION lists such functions in recursed_functions. FTRACE_OPS_FL_PERMANENT marks an ops that must never be bypassed: while one is registered, writing 0 to the kernel.ftrace_enabled sysctl fails with -EBUSY. Other flags mark an ops that follows set_ftrace_pid (FL_PID), one that is dynamically allocated (FL_DYNAMIC, set by the core for any ops outside the kernel's static data), and the direct-call and graph users described next.

Two users shape these flags. Live patching (kernel/livepatch/patch.c) registers an ops with FTRACE_OPS_FL_DYNAMIC | FTRACE_OPS_FL_IPMODIFY | FTRACE_OPS_FL_PERMANENT on each patched function. It adds FTRACE_OPS_FL_SAVE_REGS only on architectures without DYNAMIC_FTRACE_WITH_ARGS (since 5.11), so neither x86-64 nor ARM64 pays for a full pt_regs. Its handler, klp_ftrace_handler(), calls ftrace_regs_set_instruction_pointer() to redirect execution into the new version of the function. The consistency model that decides when each task may switch to the new code is described in Appendix B. Direct calls (register_ftrace_direct(), 5.5) let an ops name a single target address, direct_call, that the site calls instead of the generic caller. They exist for BPF trampolines, which implement fentry, fexit and fmod_ret programs (Chapter 23). The BPF trampoline saves and restores what it needs itself, so a traced function costs about a direct call. Since 6.4 the API takes the ops itself, register_ftrace_direct(ops, addr), with the functions chosen by the ops' filter, and ARM64 supports direct calls when CALL_OPS is available. When the site is also wanted by other ops, it calls the generic caller instead, which runs the other callbacks and then arch_ftrace_set_direct_caller(). On x86 that stores the target in the saved orig_ax slot, and ftrace_regs_caller returns into the trampoline rather than to the function. ARM64 reaches a target beyond BL range the same way, through ftrace_caller, which reads direct_call from the ops. A BPF trampoline that modifies the instruction pointer and a live patch on the same function would break the "one IPMODIFY owner" rule, so since 6.0 the two negotiate through the ops' ops_func callback (FTRACE_OPS_CMD_ENABLE_SHARE_IPMODIFY_SELF), and the BPF trampoline then calls the patched function. In 7.0 x86-64 selects HAVE_SINGLE_FTRACE_DIRECT_OPS: all BPF trampolines share one ftrace_ops, and attaching or detaching a trampoline updates its hash with update_ftrace_direct_add(), update_ftrace_direct_del() or update_ftrace_direct_mod() instead of registering a new ops. ARM64 still uses one ops per trampoline.

Removing an ops is harder than adding one, because a CPU may be inside the callback, or inside the trampoline that calls it, when the site is turned back into a NOP. Callbacks run with preemption disabled, so for a statically allocated ops waiting for every CPU to schedule would be enough. A dynamically allocated ops (FTRACE_OPS_FL_DYNAMIC) and its x86 trampoline are freed, so ftrace_shutdown() does more. It calls synchronize_rcu_tasks_rude(), which forces every CPU through a schedule, because the callback may run where ordinary RCU is not watching. It then calls synchronize_rcu_tasks(), which waits until every task that might have been preempted on the trampoline has voluntarily scheduled or returned to user space. Only then is the trampoline freed. These RCU flavors are described in Chapter 5.

The state of every site can be read back from tracefs. enabled_functions lists each function that at least one ops is attached to, with the reference count and flag letters: R (full registers), I (IPMODIFY), D (direct), O (called through a CALL_OPS literal) and M (once modified by an IPMODIFY or direct ops). After the flags come the trampoline or ops the site calls and, for a direct call, direct--> and the target, shown as direct(jmp)--> when the site jumps. touched_functions (6.4) lists every function that has ever had a callback attached since boot, so grep ' M ' touched_functions shows which functions a live patch or BPF program has ever redirected, which is useful when a crash dump shows unexpected code. available_filter_functions lists every site that can be traced, and available_filter_functions_addrs (6.5) adds each site's address.

The tracers built directly on ftrace_ops are small. The function tracer records one event per call; its options add a stack trace to each event (func_stack_trace), merge consecutive calls to the same function (func-no-repeats, 5.13), or record the arguments (func-args, 6.15). The stack tracer (CONFIG_STACK_TRACER) checks the stack depth at every traced function and keeps the deepest stack seen in stack_trace and stack_max_size. It is turned on with the kernel.stack_tracer_enabled sysctl or the stacktrace boot parameter, and stack_trace_filter limits where it checks. The function profiler (CONFIG_FUNCTION_PROFILER) counts calls and time per function without the ring buffer, and is read from trace_stat/functionN after writing 1 to function_profile_enabled. For problems early in boot, the filters can be set on the command line before any user space exists: ftrace=function, ftrace_filter=, ftrace_notrace=, ftrace_graph_filter= and ftrace_graph_max_depth=. Boot-time tracing (CONFIG_BOOTTIME_TRACING, 5.6) accepts a complete tracing setup, including instances and events, from bootconfig.

5.4 The Function-Graph Tracer and Return Hooking

A callback at function entry cannot see the function return. To trace returns, fgraph (kernel/trace/fgraph.c) uses a trick from debuggers: on entry it replaces the function's return address with the address of return_to_handler, and it saves the real one on a per-task shadow stack. When the traced function returns, it "returns" into return_to_handler (assembly, one per architecture). That routine calls ftrace_return_to_handler(), which pops the shadow stack, runs the return callbacks, and jumps to the real return address. Where the return address lives is architecture specific, and the entry hooks in each ftrace.c show the difference: 

/* arch/x86/kernel/ftrace.c (abridged) */
void ftrace_graph_func(unsigned long ip, unsigned long parent_ip,
		       struct ftrace_ops *op, struct ftrace_regs *fregs)
{
	struct pt_regs *regs = &arch_ftrace_regs(fregs)->regs;
	unsigned long *stack = (unsigned long *)kernel_stack_pointer(regs);
	unsigned long return_hooker = (unsigned long)&return_to_handler;
	unsigned long *parent = (unsigned long *)stack;	/* on the stack */
	...
	if (!function_graph_enter_regs(*parent, ip, 0, parent, fregs))
		*parent = return_hooker;
}

/* arch/arm64/kernel/ftrace.c (abridged) */
void ftrace_graph_func(unsigned long ip, unsigned long parent_ip,
		       struct ftrace_ops *op, struct ftrace_regs *fregs)
{
	unsigned long return_hooker = (unsigned long)&return_to_handler;
	unsigned long frame_pointer = arch_ftrace_regs(fregs)->fp;
	unsigned long *parent = &arch_ftrace_regs(fregs)->lr;	/* saved X9 */
	unsigned long old;
	...
	old = *parent;
	if (!function_graph_enter_regs(old, ip, frame_pointer,
				       (void *)frame_pointer, fregs)) {
		*parent = return_hooker;
	}
}

On x86 the return address is on the stack at the moment of the CALL __fentry__. On ARM64 it is in the link register, which the call site copied to X9 and ftrace_caller saved in ftrace_regs. When ftrace_caller restores the "link register", it restores the hooked value. With pointer authentication, the function signs its return address with PACIASP only after the patched entry instructions, so the hook replaces a value that is not yet signed. That is why ARM64 needs patchable function entries for ftrace to work with pointer authentication.

Up to 6.10, fgraph supported a single user. Since 6.11 up to 16 struct fgraph_ops (each with an entryfunc and a retfunc, registered with register_ftrace_graph()) can be active at once. That is how the function-graph tracer and fprobes (§8.2), and through fprobes the BPF kprobe_multi programs, share the mechanism. Each fgraph_ops embeds an ftrace_ops with its own filter, and all of them are attached as sub-ops of one manager ops, whose filter is the union of theirs. On entry, function_graph_enter_regs() pushes a frame holding the real return address, the function, and (on ARM64) the frame pointer, then calls the entryfunc of each user whose filter matches. A user that returns zero does not want the return. If none wants it, the frame is popped again and the return address is left alone, so a filtered-out function costs no return hook. Otherwise a word after the frame records a 16-bit bitmap of the users to call on return, and the type and size of the frame. An entry callback can also reserve up to 256 bytes on the shadow stack with fgraph_reserve_data(), and the return callback gets it back with fgraph_retrieve_data(). The function-graph tracer keeps each call's start time there. When only one user is registered, a static call and a static key (fgraph_do_direct) call it directly instead of looping over the array.

The shadow stack is a 4 KB array per task (SHADOW_STACK_SIZE), allocated from the fgraph_stack slab cache for every existing task when the first user registers, and for each new task at fork while any is registered. When a deep call chain fills it, the function is simply not hooked and the task's trace_overrun counter is incremented; the funcgraph-overrun option prints the count. On return, ftrace_return_to_handler() pops the frame, checks it, and runs the return callbacks with the return value, which it reads from the saved registers with ftrace_regs_get_return_value() (6.14). On ARM64 the check compares the saved frame pointer with the current one (HAVE_FUNCTION_GRAPH_FP_TEST). A mismatch means the shadow stack no longer matches the real one; fgraph then stops, warns with Bad frame pointer: expected X, received Y, and "returns" into panic() rather than to a wrong address. Stack unwinders meet the hooked addresses too, and use ftrace_graph_ret_addr() to translate each return_to_handler back to the real caller (§3.5).

The function_graph tracer is the best-known user. It records an entry event and a return event for every traced function and prints them as C-like nested blocks, with the duration of each call: 

# cd /sys/kernel/tracing
# echo vfs_read > set_graph_function
# echo function_graph > current_tracer
# cat trace
 2)               |  vfs_read() {
 2)               |    rw_verify_area() {
 2)   0.271 us    |      security_file_permission();
 2)   0.802 us    |    }
 2)               |    seq_read() {
 ...
 2) + 14.237 us   |  }

The character before a duration flags a slow call: + for more than 10 µs, ! for more than 100 µs, # for more than 1 ms, * for more than 10 ms, @ for more than 100 ms and $ for more than 1 s. The funcgraph-retval option (6.5) adds each function's return value, which is often the quickest way to find which function in a deep call chain turned a success into -EINVAL. A value that looks like an error code is printed in decimal, other values in hex, and funcgraph-retval-hex prints them all in hex. The value is simply the return register, so for a void function it is meaningless, and on ARM64 a narrow return type may carry garbage in the upper bits. funcgraph-args (6.15) adds the arguments, decoded through BTF, and funcgraph-retaddr (6.13) adds the caller's address. max_graph_depth limits how deep the tracer follows calls, set_graph_notrace prunes the subtrees below the listed functions, and funcgraph-proc, funcgraph-abstime and funcgraph-tail change the layout. Writing a number of microseconds to tracing_thresh makes the tracer record only calls that took longer, as single return lines, which turns it into a cheap latency filter.

The Trace Ring Buffer and tracefs

Every ftrace tracer, every trace event and every dynamic probe writes into the same data structure, the trace ring buffer. It is a different structure from the printk ring buffer (§2.2), built for a different load: millions of small binary records per second, written from any context, including NMIs, and read by one consumer per CPU. Users never touch it directly. They control it, and every tracer that writes into it, through a few dozen files in tracefs, and they can create further independent copies of the whole arrangement as instances.

6.1 A Per-CPU, Lockless Ring of Pages

kernel/trace/ring_buffer.c (2.6.28, lockless since 2.6.32) implements a struct trace_buffer that contains one struct ring_buffer_per_cpu for each CPU. Each per-CPU buffer is a circular, doubly linked list of struct buffer_page "sub-buffers". By default these are single pages, but since 6.8 buffer_subbuf_size_kb can make them larger, so bigger events fit. Each sub-buffer's data page starts with a buffer_data_page header that holds a full timestamp and a commit count of the bytes written, followed by the events. An event has a 4-byte header, type_len:5 and time_delta:27, followed by array[]. The 27-bit field holds the nanoseconds since the previous event, enough for gaps of about 134 ms. A type_len of 1 to 28 is the payload length in 4-byte words, so a data event of up to 112 bytes needs no other length field. A value of 0 means the length is stored in array[0], which larger events use. The top three values mark metadata rather than data: RINGBUF_TYPE_PADDING (29) fills the unused end of a sub-buffer or marks a discarded event, TIME_EXTEND (30) carries a 59-bit delta split between time_delta and array[0] when the gap is too long, and TIME_STAMP (31) carries an absolute time. It is written only by a buffer in absolute-timestamp mode. The histogram triggers of §7.3 used that mode until 5.13; nothing in the 7.0 tree turns it on, so timestamp_mode normally shows [delta] absolute, with the active mode in brackets. Figure 29-7 shows one per-CPU buffer.

The design rests on one rule: a per-CPU buffer is written only by its own CPU. A writer therefore never competes with another CPU, only with interrupts and NMIs that arrive on the same CPU while it is writing. Those nest strictly: an interrupting writer always finishes before the interrupted one resumes. Space is reserved with a single local_add_return() on the tail page's write field. A local_t operation is atomic against interrupts on the same CPU but needs no bus lock. An interrupt that reserves space between the read and the add simply gets the next slot. The reservation also has to compute a timestamp delta, and an interrupt can change the "previous event" under it. That makes the timestamp code the subtle part: 

/* kernel/trace/ring_buffer.c (abridged) */
static struct ring_buffer_event *
__rb_reserve_next(struct ring_buffer_per_cpu *cpu_buffer,
		  struct rb_event_info *info)
{
	...
	tail_page = info->tail_page = READ_ONCE(cpu_buffer->tail_page);
 /*A*/	w = local_read(&tail_page->write) & RB_WRITE_MASK;
	barrier();
	rb_time_read(&cpu_buffer->before_stamp, &info->before);
	rb_time_read(&cpu_buffer->write_stamp, &info->after);
	barrier();
	info->ts = rb_time_stamp(cpu_buffer->buffer);
	...
 /*B*/	rb_time_set(&cpu_buffer->before_stamp, info->ts);
 /*C*/	write = local_add_return(info->length, &tail_page->write);
	write &= RB_WRITE_MASK;
	tail = write - info->length;

	/* See if we shot pass the end of this buffer page */
	if (unlikely(write > cpu_buffer->buffer->subbuf_size))
		return rb_move_tail(cpu_buffer, tail, info);

	if (likely(tail == w)) {
		/* Nothing interrupted us between A and C */
 /*D*/		rb_time_set(&cpu_buffer->write_stamp, info->ts);
		...
	} else {
		/* SLOW PATH - Interrupted between A and C */
		...
	}
	...
}

Each writer increments committing before it reserves and decrements it after it commits. Only the outermost writer, the one that brings the count back to zero, moves commit_page and the page's commit field up to the write position. A reader therefore never sees an event that an interrupted writer has reserved but not yet filled in. When the tail page is full, rb_move_tail() pads its end and advances tail_page. If the next page is the head page, which holds the oldest unread data, the buffer is full. In the default overwrite mode the writer uses cmpxchg on the RB_PAGE_HEAD flag bit, stored in the low bits of the previous page's next pointer, to push the head forward, and counts the lost events in overrun. With the overwrite option off, new events are dropped instead.

Reading is done one page at a time. A reader takes the per-CPU reader_lock (readers are rare, so a lock is fine on that side) and calls rb_get_reader_page(). That splices its empty private reader_page into the ring in place of the head page and takes the head page out, using the same flag-bit cmpxchg so a writer racing to overwrite the head is detected. The page is now out of the ring, and the reader can consume it, copy it to user space with splice() through per_cpu/cpuN/trace_pipe_raw, or (since 6.10) let user space mmap() it directly with ring_buffer_map(). Tools such as trace-cmd read the binary pages this way and parse the events on another machine.

The layout of a mapping is defined in include/uapi/linux/trace_mmap.h. The first page is a struct trace_buffer_meta that reports the sub-buffer size and count, the ID of the sub-buffer currently owned by the reader and how far it has been read, and the entries, overrun and lost-event counts. The sub-buffers follow. User space consumes the reader sub-buffer in place and then issues the TRACE_MMAP_IOCTL_GET_READER ioctl, which swaps the next one in, so events reach the tool without any copy. A mapped buffer cannot also be swapped with a snapshot buffer (§6.3): while it is mapped, writes to snapshot and snapshot triggers fail with -EBUSY. Persistent buffers placed at a raw physical address cannot be mapped at all.

Writers can run in NMI context, so they cannot call wake_up() themselves. rb_wakeups() queues an irq_work instead, and the blocked reader in ring_buffer_wait() is woken from that safe context. For per-CPU readers such as trace_pipe_raw, the buffer_percent file (5.0) sets how full the buffer must be before the wakeup is sent. The default is 50. A value of 0 wakes the reader on the first event, and 100 waits until the buffer is full. A higher value means fewer wakeups and larger splice() transfers for tools like trace-cmd, at the risk of overwriting data if the reader falls behind. A reader of all CPUs, such as trace_pipe, is woken as soon as any data arrives.

An interrupting writer is expected; a recursive one is not. If a tracepoint fires inside code that the ring buffer itself calls, the inner write would corrupt the reservation that is still in progress. trace_recursive_lock() keeps a current_context bitmask in the per-CPU buffer, with one bit each for normal, softirq, hardirq and NMI context. A second reservation in a context whose bit is already set is refused. An extra transition bit covers the few instructions after an interrupt arrives and before preempt_count records it. With CONFIG_FTRACE_RECORD_RECURSION the refused caller is listed in recursed_functions. Code that must write a second event from inside a reservation, as synthetic events do, brackets it with ring_buffer_nest_start() and ring_buffer_nest_end(), which move the bit window up to a fresh set of context bits.

The buffer is sized per CPU. The default, TRACE_BUF_SIZE_DEFAULT, is 1,441,792 bytes (1408 KB) per CPU, and trace_buf_size= on the command line changes it. So that machines which never trace do not pay for the memory, tracer_alloc_buffers() creates the global buffer at its minimum size during boot. tracing_update_buffers() expands it to the full size the first time a tracer is selected or an event is enabled, or at boot if the kernel contains a trace_printk(). Until then, buffer_size_kb reads as a small value followed by "(expanded: 1408)". The per-CPU buffers are not freed when a CPU goes offline, so a trace taken before a hot-unplug can still be read.

Every loss is counted per CPU, and per_cpu/cpuN/stats prints the counters. entries is the number of unread events in the buffer. overrun counts events overwritten in overwrite mode, and dropped events counts events refused with overwrite off. commit overrun counts events lost because nested writers, typically an interrupt storm, wrapped all the way around to the page that an interrupted writer was still committing. A nonzero value there means the buffer is too small for the interrupt load. The file also shows bytes of unread data, the timestamps of the oldest event and of now, and read events. When a reader finds that pages were overwritten since its last read, trace and trace_pipe print CPU:N [LOST M EVENTS] at the gap, so a hole in a trace is always marked.

A typical session combines several of these files. Writing :mod:ext4 to set_ftrace_filter selects every function in ext4.ko, appending ext4_evict_inode:stacktrace adds a stack trace whenever that one function is hit, and echo function > current_tracer starts the tracer. Writing nop to current_tracer patches every site back to a NOP. The trace file begins with a header that explains its columns: 

# cat trace
# tracer: function
#
# entries-in-buffer/entries-written: 212/212   #P:8
#
#                                _-----=> irqs-off/BH-disabled
#                               / _----=> need-resched
#                              | / _---=> hardirq/softirq
#                              || / _--=> preempt-depth
#                              ||| / _-=> migrate-disable
#                              |||| /     delay
#           TASK-PID     CPU#  |||||  TIMESTAMP  FUNCTION
#              | |         |   |||||     |         |
              rm-4182    [003] .....  5123.441279: ext4_evict_inode <-evict

The first header line gives the events still in the buffer, the events written since the last reset (the difference was overwritten) and the number of online CPUs. Each record then shows the command and PID, the CPU, five flag characters and the timestamp in seconds. The flags come from the header that every event carries (§7.1) and are decoded by trace_print_lat_fmt(). The first is d when interrupts were off, b when bottom halves were disabled, and D for both. The second shows pending reschedule requests: N when both TIF_NEED_RESCHED and the folded PREEMPT_NEED_RESCHED bit are set, n or p when only one is, and L, l, b or B for combinations that include the lazy request of PREEMPT_LAZY. The third is h in a hardirq, s in a softirq, H in a hardirq that interrupted a softirq, and z or Z in an NMI. The last two are the preempt-disable depth and the migrate-disable depth, in hexadecimal. The tracer subtracts its own preemption disable, so ..... means the code ran preemptible in task context. The flags show, for example, that a function ran in softirq context with preemption disabled, without any extra instrumentation. Command names are not stored in the events. They come from saved_cmdlines, which the sched_switch probe fills, and a PID that has been evicted from it prints as <...>. Writing a larger number to saved_cmdlines_size fixes that for long traces with many short-lived tasks.

The timestamps come from the clock selected in trace_clock. The default, local, is sched_clock() on the current CPU. It is the cheapest, but it is not synchronized across CPUs, so two events on different CPUs that happen close together can appear in the wrong order. If sched_clock() is marked unstable, the kernel switches the default to global at late init and logs "Unstable clock detected", unless trace_clock= was given. global keeps a shared last value so time never goes backwards across CPUs, at the cost of a shared cache line. counter is an atomic counter rather than a time, and gives a strict global order. uptime counts ticks. perf is local_clock(), the clock that perf events use, so traces from both tools can be merged. mono, mono_raw, boot and tai are the NMI-safe fast accessors of the timekeeping core. They match the corresponding clock_gettime() clocks, so records written to trace_marker can be lined up with an application's own log. x86-tsc is the raw TSC. Clocks that do not count nanoseconds (counter, uptime, x86-tsc) are printed as raw values.

A line written to set_ftrace_filter can also attach a command to a function, in the form function:command[:count]. traceon and traceoff switch the buffer, snapshot takes a snapshot (§6.3), enable_event and disable_event switch a trace event (:system:event), dump prints the whole buffer to the console, cpudump prints only the current CPU's, and stacktrace records a stack. The count limits how many times the command fires, and the same line with a leading ! removes it. traceoff is the standard way to freeze a trace at the moment of a bug: with the error path as the trigger function, the events that led to the error stay in the buffer instead of being overwritten.

All of this can also be set on the kernel command line, which matters when the problem happens before user space starts. ftrace= selects a tracer, and ftrace_filter=, ftrace_notrace= and ftrace_graph_filter= set its filters. trace_event= enables events, trace_trigger= (6.2) attaches triggers to them, and trace_options=, trace_clock= and trace_buf_size= set the rest. alloc_snapshot allocates the snapshot buffer at boot. tp_printk also copies every enabled trace event into the kernel log. That helps when the machine dies before the trace can be read, but it can flood a serial console, and tp_printk_stop_on_boot turns it off once boot completes. To keep the boot-time trace from being overwritten, traceoff_after_boot (6.15) stops tracing once the late initcalls have run. ftrace_boot_snapshot (5.18) instead takes a snapshot just before init memory is freed and leaves the live buffer running. alloc_snapshot=name and ftrace_boot_snapshot=name apply the same to a boot instance (§6.3). The same settings, including per-instance ones, can be given as a structured tree through bootconfig, which kernel/trace/trace_boot.c applies.

Developers often add records of their own with trace_printk() (include/linux/trace_printk.h), a printk() look-alike that writes into the trace ring buffer instead of the kernel log. It is cheap enough for the scheduler or an interrupt handler, because with a constant format string it does no formatting at all. The macro places a pointer to the format in a special section and calls __trace_bprintk(), which stores only that pointer and the binary arguments. The text is produced when the buffer is read, and the printk_formats file maps format addresses back to strings for tools that read raw buffers. A call with no arguments becomes the cheaper trace_puts(). trace_printk() is meant only for debugging. If the kernel or a loaded module contains a call to it, trace_printk_init_buffers() allocates extra per-CPU buffers and prints a large NOTICE banner warning that "this is a DEBUG kernel and it is unsafe for production use". Since 6.12 the trace_printk_dest option chooses which instance (§6.3) receives the output. User space has a counterpart in the trace_marker file, through which an application can write its own marks into the same timeline as the kernel's events. Many applications hard-code the top-level path. Since 6.16 an instance that sets the copy_trace_marker option also receives every write to the top-level trace_marker, and the top level can clear the option to keep those writes out of its own buffer.

6.3 Instances, Snapshots, and Persistent Buffers

The top-level directory is the global tracing instance. mkdir instances/name creates another one, with its own ring buffer, its own enabled events and its own tracing_on. Since 3.15 an instance can also run its own function tracer with its own filters, because each instance gets a separate struct ftrace_ops. An instance has every file that depends on a buffer, such as events/, trace_options, trace_clock, buffer_size_kb, tracing_cpumask, snapshot and set_ftrace_filter. Files that describe the kernel as a whole exist only at the top level: available_filter_functions, saved_cmdlines, printk_formats, and the dynamic-event files kprobe_events, uprobe_events and dynamic_events. A probe defined there appears in every instance's events/ directory and can be enabled in any of them. Instances let several tools trace at the same time without disturbing each other. rmdir fails with -EBUSY while an instance's files are open or a kernel user holds a reference.

Kernel code can create or look up an instance with trace_array_get_by_name(name, systems). The systems argument (6.8) limits which event subsystems get directories in it, and NULL means all of them. The caller enables events in the instance with trace_array_set_clr_event(), writes free-form records with trace_array_printk() after calling trace_array_init_printk(), and drops its reference with trace_array_put(). The qla2xxx SCSI driver creates a qla2xxx instance this way and enables its own qla events there, so its debug records stay out of the global buffer. samples/ftrace/sample-trace-array.c shows the whole pattern.

Instances can also be created on the command line, before any user space exists. trace_instance=foo,sched:*,irq:* creates foo during boot and enables the listed events in it. Flags appended to the name with ^ change how it starts: ^traceoff creates it with tracing off, and ^traceprintk sends trace_printk() output to it. An @ suffix places the instance in a persistent region, as described below.

A snapshot is a second ring buffer of the same size, allocated the first time it is needed. Writing 1 to snapshot, or firing a snapshot trigger (§7.3), swaps the two buffers in constant time. The old contents are then frozen for reading through snapshot while tracing continues into the fresh buffer. Writing 0 frees the spare buffer, and any other number clears it without a swap. The per-CPU per_cpu/cpuN/snapshot files swap a single CPU, which needs CONFIG_RING_BUFFER_ALLOW_SWAP. In-kernel code calls tracing_snapshot() to take one at a chosen point, and tracing_snapshot_cond_enable() registers a callback that decides on each attempt whether the swap should happen, which the histogram snapshot() action uses. The latency tracers (§10.1) use the same swap to keep the trace of the worst case seen so far, so the snapshot file returns -EBUSY while one of them is the current tracer.

The last evidence-saving use connects tracing back to §3.4. Since 6.12 an instance can live in memory that survives a warm reboot: reserve_mem=12M:4096:trace trace_instance=boot_map@trace places the boot_map instance in a region set aside by reserve_mem, using ring_buffer_alloc_range(). An address and size (@start:size) can name the region directly instead, where the firmware or memmap= keeps it out of normal use. At boot, rb_cpu_meta_valid() checks the meta data that the previous kernel left in the region and, if it is consistent, keeps the old pages as readable data. The new kernel records where its own text and modules were loaded, and when it prints the old records, trace_adjust_address() applies the difference, so function addresses resolve to the right symbols despite KASLR. Kernel text has been handled since 6.12 and module text since 6.15. last_boot_info shows the old addresses for tools that parse the raw pages. Because the previous kernel's format strings are not valid in the new one, trace_printk() into a persistent instance always records the formatted text rather than the binary form.

The old data stays until the instance is used again: selecting a tracer, enabling an event or emptying it by reading clears it, and from then on the instance records the current boot for the next one to read. Since 6.19 trace_instance=backup=boot_map copies the old contents into an ordinary backup instance at boot, so boot_map can start recording again from the command line while the previous boot's trace is kept for reading, and rmdir instances/backup frees the copy afterwards.

This is the trace counterpart of ramoops: the last few seconds of events before a hang, recovered on the next boot. When the machine is still alive enough to print, ftrace_dump() does the same job directly. It is called by SysRq-z and, when ftrace_dump_on_oops is set, from a die notifier and a panic notifier, and it writes the buffer to the console. A large buffer over a slow serial line can take minutes, so ftrace_dump_on_oops=orig_cpu (or =2) dumps only the CPU that oopsed. Since 6.9 instance names can be listed too: ftrace_dump_on_oops,foo,bar=orig_cpu dumps the global buffer, all of foo, and the oopsing CPU's part of bar.

Tracepoints and Trace Events

ftrace can hook the entry of almost any function, but it cannot tell you what the function was doing. It only sees the arguments as raw registers. A tracepoint is the opposite: a hook a maintainer placed by hand at a meaningful point, such as a context switch, a block request completion or a page fault, with typed arguments chosen for that point. A 7.0 tree defines about 1,700 trace events in the 174 headers under include/trace/events/, and nearly 3,000 more in headers kept next to the drivers, filesystems and networking code that use them. The mechanism has two layers. The tracepoint itself, from include/linux/tracepoint.h and kernel/tracepoint.c (2.6.28), is just a patchable call site with a list of probe functions. The trace event layer, from include/trace/ and kernel/trace/trace_events.c (2.6.30), adds a probe that records a fixed binary layout into the ring buffer of §6, plus a self-describing format, filters and triggers. Perf (§9) and BPF (Chapter 23) attach to the same tracepoints with their own probes.

7.1 A Tracepoint Is a Static Key and a Static Call

A tracepoint has to be nearly free when nobody is listening, because some sit in the scheduler and the page-fault path and run millions of times a second. The declaration macro achieves this with two kinds of code patching. The core of it is __DECLARE_TRACE(): 

/* include/linux/tracepoint.h (abridged) */
#define __DECLARE_TRACE(name, proto, args, cond, data_proto)			\
	__DECLARE_TRACE_COMMON(name, PARAMS(proto), PARAMS(args), PARAMS(data_proto)) \
	static inline void __do_trace_##name(proto)			\
	{								\
		TRACEPOINT_CHECK(name)					\
		if (cond) {						\
			guard(srcu_fast_notrace)(&tracepoint_srcu);	\
			__DO_TRACE_CALL(name, TP_ARGS(args));		\
		}							\
	}								\
	static inline void trace_##name(proto)				\
	{								\
		if (static_branch_unlikely(&__tracepoint_##name.key))	\
			__do_trace_##name(args);			\
		if (IS_ENABLED(CONFIG_LOCKDEP) && (cond)) {		\
			WARN_ONCE(!rcu_is_watching(),			\
				  "RCU not watching for tracepoint");	\
		}							\
	}

The call site trace_sched_switch(...) therefore expands inline to a static_branch_unlikely() test on the key member of struct tracepoint. That is a static key, also called a jump label. The compiler emits a NOP at the test, records the site in the __jump_table section, and moves the body out of line. When the first probe registers, static_key_enable() rewrites every recorded NOP into a jump to the body. The two architectures patch differently, with the same primitives that ftrace uses (§5.2):

  • On x86-64, arch/x86/kernel/jump_label.c switches between a 2-byte or 5-byte NOP and a JMP of the same size. It uses smp_text_poke_single() for a single site, or smp_text_poke_batch_add() and smp_text_poke_batch_finish() to batch many sites into one round of INT3-based patching.
  • On ARM64, arch/arm64/kernel/jump_label.c writes a NOP or a B with aarch64_insn_patch_text_nosync(). Every instruction is 4 bytes, so there is no size choice. arch_jump_label_transform_apply() then issues one synchronization for the whole batch.

Once the branch is taken, __DO_TRACE_CALL() must call each registered probe. The probes live in funcs, an RCU-protected array of struct tracepoint_func. With one probe, an indirect call through the array would cost a retpoline on affected x86 CPUs. So, where the architecture has HAVE_STATIC_CALL, the macro calls static_call(tp_func_##name) instead. When exactly one probe is registered, the static call points straight at it. With more than one, it points at the generated __traceiter_##name(), which loops over the array. Again the architectures differ:

  • x86-64 has HAVE_STATIC_CALL and, with objtool, HAVE_STATIC_CALL_INLINE. objtool records every static-call site, and the kernel patches the CALL instruction at the site itself, so the tracepoint ends up as a direct call to the probe.
  • ARM64 has no inline static calls. Since 7.0 it selects HAVE_STATIC_CALL, but only when kernel CFI is enabled. That variant uses an out-of-line trampoline that loads its target from a literal into X16 and branches to it. It exists because kCFI would otherwise reject the indirect call to __static_call_nop() or __static_call_return0(). Without CFI, ARM64 tracepoints always call __traceiter_##name().

Changing the number of probes is the delicate part, because the target of the static call and the data pointer it passes are read separately: with one probe, __DO_TRACE_CALL() loads funcs[0].data and then calls whatever the static call points at. tracepoint_add_func() and tracepoint_remove_func() in kernel/tracepoint.c therefore classify the array as holding 0, 1, 2 or more probes and order their updates for each transition. Going from 0 to 1, the static call is aimed at the probe before funcs is published and the static key enabled. Going from 1 to 2, it is switched to __traceiter_##name() before the two-entry array is published, because the iterator copes with either array. The dangerous sequences are 1→0→1 and N→…→2→1, after which a CPU still holding the old data could call the new probe with it. So the first step records an SRCU grace-period cookie with start_poll_synchronize_srcu(), and before the last step retargets the static call, tp_rcu_cond_sync() waits for that grace period unless it has already elapsed. Probes run in priority order: register_trace_prio_##name() inserts a probe ahead of the first one with a lower priority, and the default is TRACEPOINT_DEFAULT_PRIO, 10. Unregistration never fails for lack of memory. If the smaller array cannot be allocated, func_remove() overwrites the departing entry in place with the empty tp_stub_func().

The probe call runs under guard(srcu_fast_notrace). tracepoint_probe_unregister() builds a new funcs array, publishes it, and frees the old one with call_srcu() on tracepoint_srcu, so no CPU can still be walking it. Until 7.0 the guard simply disabled preemption. The change to SRCU-fast readers lets probes such as BPF programs run preemptibly, which real-time users had asked for. A second variant, __DECLARE_TRACE_SYSCALL(), was added in 6.13 for the system-call tracepoints. It uses guard(rcu_tasks_trace), and its old arrays are freed with call_rcu_tasks_trace(). It also calls might_fault(), so its probes may fault in user memory. That is what lets a sleepable BPF program read a system call's string arguments.

__DECLARE_TRACE_COMMON() also generates the registration API: register_trace_##name(probe, data), its _prio variant, unregister_trace_##name(), and trace_##name##_enabled() for call sites that must do work just to compute the arguments. A tracepoint with no trace event attached is declared with plain DECLARE_TRACE(). Since 6.16 those get a _tp suffix, as in pelt_cfs_tp, to mark them as bare hooks with no tracefs file. The scheduler's PELT and sched_overutilized_tp hooks exist only for modules and BPF tp_btf programs.

Three variants put more logic behind the static branch. TRACE_EVENT_CONDITION() supplies the cond argument of __DECLARE_TRACE(), so a test that would otherwise be an if around every call runs only while the tracepoint is enabled; btrfs, f2fs and DAMON use it. TRACE_EVENT_FN() attaches regfunc and unregfunc callbacks, kept in struct tracepoint_ext, which tracepoint_add_func() calls before the first probe is added and tracepoint_remove_func() after the last one is removed. The sys_enter and sys_exit tracepoints use them: syscall_regfunc() sets SYSCALL_WORK_SYSCALL_TRACEPOINT on every thread, so the system-call entry and exit code takes its slow path only while someone is listening. Finally, a widely included header that cannot pull in a trace-event header uses DECLARE_TRACEPOINT() and tracepoint_enabled() from include/linux/tracepoint-defs.h, which test the same static key, and calls an out-of-line function that fires the event. include/linux/page_ref.h does this for the page_ref_* events.

Modules can define tracepoints and attach to them. The module loader finds a module's tracepoints through its __tracepoints_ptrs section, and tracepoint_module_coming() announces them to anyone registered with register_tracepoint_module_notifier(). A module carrying any taint other than out-of-tree, staging, unsigned, test or livepatch, typically one force-loaded past a version mismatch, is skipped, and trace_module_add_events() logs "module has bad taint, not creating trace events". For a module to attach a probe to a core tracepoint, the core must say EXPORT_TRACEPOINT_SYMBOL_GPL(name), which exports the struct tracepoint, the iterator and the static-call key. The module must then call tracepoint_synchronize_unregister() after its last unregistration and before its code can be freed. It waits for both an SRCU and an RCU Tasks Trace grace period, which covers both kinds of tracepoint. Every tracepoint also has __probestub_##name(), an empty function with the probe's prototype. The t: tracepoint probes of §8.4 register it as the probe and put an fprobe on it. Since 6.13 Rust code can fire tracepoints too. A C file that defines CREATE_RUST_TRACE_POINTS emits an exported rust_do_trace_##name(), and Rust's declare_trace! macro tests the static key inline before calling it. The Rust Binder driver uses this.

A tracepoint costs memory whether or not any code fires it: the struct tracepoint, the iterator and stub, and for a trace event the generated probes and metadata, up to about 5 KB in all. 6.19 added a build-time check for dead ones. TRACEPOINT_CHECK(), placed inside the static inline __do_trace_##name() and in the export macros, emits the name into a __tracepoint_check section. Because the function is inline, the string exists only in objects that actually call trace_##name(). Building with make UT=1 runs scripts/tracepoint-update on vmlinux.o and on each module, and it prints warning: tracepoint 'x' is unused for every defined name with no matching entry. The final link discards the section.

7.2 TRACE_EVENT and the Multiple-Include Trick

A trace event is declared once, in a header, with TRACE_EVENT(). Here is the event recorded on every successful execve(): 

/* include/trace/events/sched.h */
TRACE_EVENT(sched_process_exec,

	TP_PROTO(struct task_struct *p, pid_t old_pid,
		 struct linux_binprm *bprm),

	TP_ARGS(p, old_pid, bprm),

	TP_STRUCT__entry(
		__string(	filename,	bprm->filename	)
		__field(	pid_t,		pid		)
		__field(	pid_t,		old_pid		)
	),

	TP_fast_assign(
		__assign_str(filename);
		__entry->pid		= p->pid;
		__entry->old_pid	= old_pid;
	),

	TP_printk("filename=%s pid=%d old_pid=%d", __get_str(filename),
		  __entry->pid, __entry->old_pid)
);

fs/exec.c fires it with trace_sched_process_exec(current, old_pid, bprm). The single declaration carries five pieces of information. TP_PROTO and TP_ARGS give the C prototype. TP_STRUCT__entry gives the record layout, where __string() declares a variable-length field stored after the fixed part. TP_fast_assign fills the record, and TP_printk formats it for the trace file.

Every file that includes <trace/events/sched.h> sees only the tracepoint declaration, because in normal use TRACE_EVENT() reduces to DECLARE_TRACE_EVENT(). Exactly one C file in each subsystem, kernel/sched/core.c for the scheduler, defines CREATE_TRACE_POINTS before the include. Then the #include <trace/define_trace.h> at the bottom of the header becomes active. It defines the struct tracepoint objects and then includes include/trace/trace_events.h. That file includes the event header again and again, with the TRACE_HEADER_MULTI_READ guard lifted. Before each pass it redefines the macros, using one of the files in include/trace/stages/, so each pass extracts a different artifact from the same text:

  1. stage1_struct_define.h emits struct trace_event_raw_sched_process_exec: a struct trace_entry header, the fields, and a flexible __data[] array for strings.
  2. stage2_data_offsets.h emits a struct holding the offset and length of each dynamic field.
  3. stage3_trace_output.h emits the output function that runs TP_printk.
  4. stage4_event_fields.h emits the field descriptions behind the format file and the filter parser.
  5. stage5_get_offsets.h emits the function that measures the dynamic fields for a given set of arguments.
  6. stage6_event_callback.h emits the probe trace_event_raw_event_sched_process_exec(). It disables preemption, returns early if the event is soft-disabled, reserves sizeof(*entry) + __data_size bytes with trace_event_buffer_reserve(), runs TP_fast_assign, and commits with trace_event_buffer_commit().
  7. stage7_class_define.h emits struct trace_event_class and struct trace_event_call, and places a pointer to the latter in the _ftrace_events section.

include/trace/perf.h and include/trace/bpf_probe.h then include the header once more, to emit perf_trace_##call() and __bpf_trace_##call(). One macro invocation thus yields the tracepoint, the record type, three probes for three consumers, and the metadata. Writers of events never see any of this.

The probe, the output function and the field tables are generated per event class, not per event. TRACE_EVENT() is shorthand for a DECLARE_EVENT_CLASS() plus one DEFINE_EVENT() of the same name. When several events share a prototype, layout and output, one class and several DEFINE_EVENT()s reuse trace_event_raw_event_class() and the rest, so each extra event costs only its struct tracepoint, its trace_event_call and the iterator. DEFINE_EVENT_PRINT() keeps a class but overrides its TP_printk. In include/trace/events/, 310 classes carry about 700 such events, beside about 1,000 stand-alone TRACE_EVENT() declarations. samples/trace_events/trace-events-sample.h is the maintained, commented reference for all of these macros.

Fields come from a small vocabulary. __field() and __field_struct() hold a scalar or a structure, and __array() a fixed-size array. Variable-size data goes after the fixed part through __dynamic_array() and its specializations __string(), __string_len(), __vstring() for a format and va_list, __bitmask() and __cpumask(). Each has an accessor, such as __get_str() or __get_cpumask(), for TP_fast_assign and TP_printk. The __rel_ variants (5.17) record an offset from the field itself rather than from the start of the record; they mirror the __rel_loc fields that user_events may declare. Since 6.10 __assign_str() takes only the field name, because __string() already recorded the source expression. For output, __print_symbolic() and __print_flags() turn numbers into names, and __print_array() and __print_hex() dump arrays and bytes.

TP_printk runs when the buffer is read, possibly long after the event, so it may format only data inside the record. When an event is registered, trace_event_raw_init() calls test_event_printk() (5.13), which parses the print format. Each %p extension that dereferences its argument, such as %pI4, %pU or %pd, must be handed the address of something in the record, or the kernel warns "event name has unsafe dereference of argument N". A plain %s on a pointer field cannot be judged at boot, so since 6.13 that field is marked for checking, and when the event is printed ignore_event() accepts the pointer only if it points into the record, into kernel read-only data or at a registered tracepoint string. Otherwise the output shows EVENT name: HAS UNSAFE POINTER FIELD 'field' instead of following the pointer. The fix is always to copy the string with __string().

User-space parsers read the print format as text, so an enum constant in it, such as a name inside __print_symbolic(), would mean nothing to them. TRACE_DEFINE_ENUM(x) and TRACE_DEFINE_SIZEOF(x) place a struct trace_eval_map in the _ftrace_eval_map section, and at boot or module load trace_event_update_all() rewrites each such name in the event formats into its number. About 40 headers under include/trace/events/ rely on it, among them the scheduler's and the GFP flag tables in mmflags.h.

At boot, and when a module loads, trace_events.c walks _ftrace_events and creates events/system/event/ for each trace_event_call. Since 6.6 these directories are provided by eventfs, which creates the dentries only when someone looks them up, saving many megabytes on machines with thousands of events. Each tracing instance gets a struct trace_event_file per event, and that pointer is the data argument the probe receives. Enabling an event means calling trace_event_reg(), which runs tracepoint_probe_register(call->tp, call->class->probe, file). Each instance registers its own probe instance, so each instance can enable the event separately. The format file publishes the layout, which is how perf, trace-cmd and libtraceevent parse binary records without kernel headers: 

# cat /sys/kernel/tracing/events/sched/sched_process_exec/format
name: sched_process_exec
ID: 312
format:
	field:unsigned short common_type;	offset:0;	size:2;	signed:0;
	field:unsigned char common_flags;	offset:2;	size:1;	signed:0;
	field:unsigned char common_preempt_count;	offset:3;	size:1;	signed:0;
	field:int common_pid;	offset:4;	size:4;	signed:1;

	field:__data_loc char[] filename;	offset:8;	size:4;	signed:0;
	field:pid_t pid;	offset:12;	size:4;	signed:1;
	field:pid_t old_pid;	offset:16;	size:4;	signed:1;

print fmt: "filename=%s pid=%d old_pid=%d", __get_str(filename), REC->pid, REC->old_pid

The four common_ fields are struct trace_entry, shared by every event. The ID differs from kernel to kernel. A __data_loc field is a 32-bit word whose low 16 bits hold the offset of the data from the start of the record and whose high 16 bits hold its length.

Events are enabled per instance in several ways. Writing 1 to an event's enable file, or to the enable file of its system directory or of events/, switches one event or a whole group. set_event takes system:event names with globs, and a leading ! disables. Since 6.14 a :mod:module suffix is remembered when the module is not loaded yet, and its events are enabled when it loads. The trace_event= boot parameter takes the same syntax. It is applied twice, once in event_trace_enable() at early init and again from an early_initcall, because the system-call events must set their per-task flag on PID 1, which does not exist the first time. Reading enable gives 0 or 1, with a * appended while a trigger holds the event in soft mode. set_event_pid (4.4) and set_event_notrace_pid (5.7) restrict recording to, or away from, a set of PIDs. The test is cheap because a probe on sched_switch stores the verdict for the incoming task in a per-CPU ignore_pid flag, which trace_event_buffer_reserve() reads. With the event-fork option, children of listed tasks are added as they are created.

The per-call events under events/syscalls/, such as sys_enter_openat, are not written with TRACE_EVENT(). With CONFIG_FTRACE_SYSCALLS, each SYSCALL_DEFINEn() also emits a struct syscall_metadata holding the argument types and names, and kernel/trace/trace_syscalls.c builds a trace_event_call from it at boot. Their probes hang on the two raw tracepoints sys_enter and sys_exit and look up the event file by system-call number. Since 6.19 the enter events of about 65 calls that take a user pointer, openat, execve and write among them, also copy the string or buffer it points to into an extra field named __arg_val, up to syscall_user_buf_size bytes (§6.2). The copy may fault, which is why these two tracepoints are the faultable kind declared through __DECLARE_TRACE_SYSCALL().

7.3 Filters, Triggers, Histograms, and Synthetic Events

Each event directory has a filter file. Writing a C-like expression over the fields, such as prev_state & 2 && prev_pid != 0, makes kernel/trace/trace_events_filter.c compile it into a small program of predicates. Numeric fields take ==, !=, <, <=, >, >= and &; string fields take ==, != and ~, a glob match. Predicates combine with &&, ||, ! and parentheses. Besides the event's own fields, a filter can test common_cpu (also spelled CPU) and COMM. A few suffixes widen the language: .function (6.3) compares a code address with a function's whole range, as in call_site.function == security_prepare_creds; .ustring (5.17) reads a user-space string; and a cpumask field, or a scalar field holding a CPU number, can be tested against CPUS{17-42} (6.6) with &, == or !=. A filter file in a system directory applies the expression to every event in the system that has the named fields. A rejected expression leaves an error message, with a caret under the offending token, in the filter file and in error_log. In 7.0 the show_event_filters and show_event_triggers files list every event that has a filter or trigger set, so they no longer need to be found by walking the tree.

Reserving the record in the ring buffer and discarding it on rejection would be slow, because a discard needs several atomic operations to undo the reservation. Since 4.7, when an event has a filter or is soft-disabled, trace_event_buffer_lock_reserve() builds the record instead in a per-CPU page, trace_buffered_event. The filter runs on that copy, and only if it passes does __buffer_unlock_commit() copy it into the ring buffer with ring_buffer_write(). An event that interrupts another one on the same CPU, or that is larger than the page, falls back to reserving in the ring buffer and discarding there. A hist trigger that uses common_timestamp reads the timestamp the ring buffer stores with each event, which the scratch copy lacks, so it turns the scratch page off for its instance through tracing_set_filter_buffering(). Either way, filtering is cheap but not free, because the probe has already run and filled in the fields.

The trigger file (kernel/trace/trace_events_trigger.c) attaches actions that run when the event fires, each with an optional filter. The commands are traceon and traceoff, snapshot (§6.3), stacktrace, enable_event and disable_event, enable_hist and disable_hist, and hist. An event can be soft-disabled: registered, so the tracepoint is live, but not recording. enable_event flips that state on another event, which allows "trace the block layer only after this function returns an error" without any code.

A trigger is written as command[:count] [if filter], and the same string with a leading ! removes it. For example, stacktrace:5 if bytes_req >= 65536 on kmem:kmalloc records the call stack of the first five large allocations. Where the trigger runs depends on whether it has a filter. A trigger without one runs from trace_trigger_soft_disabled() before the probe builds the record, so it works even on a soft-disabled event. A trigger with a filter needs the field values, so it is marked TRIGGER_COND and runs at commit from __event_trigger_test_discard(), after the filter. enable_event names its target as system:event, and its count, like the others, limits how many times it fires.

The hist trigger (4.7, kernel/trace/trace_events_hist.c) aggregates in the kernel instead of recording. It keeps a lock-free hash map, built on kernel/trace/tracing_map.c, keyed by one or more fields, with sums as values. Reading the event's hist file prints the table. hist:keys=call_site.sym:vals=bytes_req:sort=bytes_req.descending on kmem:kmalloc, for example, totals allocations by caller with no user-space post-processing.

Keys and values take modifiers. On a key, .sym and .sym-offset print an address as a symbol, .execname prints a PID's command, .syscall a system-call name and .hex the value in hexadecimal. .log2 and .buckets=N (5.15) group values into power-of-two or fixed-width bins. On a value, .percent and .graph (6.2) print each entry's share as a percentage or a bar, and nohitcount (6.2) drops the default hitcount column. common_stacktrace (named stacktrace before 6.4) keys a histogram by kernel call stack, and common_cpu and, since 6.16, common_comm are also available as keys. The map has 2048 entries by default. size= rounds up to a power of two between 128 and 131072, and the output ends with totals for hits, entries and drops, the last counting events that found the map full. A name= lets several events share one map, and :pause, :cont and :clear control an existing histogram. With CONFIG_HIST_TRIGGERS_DEBUG, a hist_debug file (5.8) shows how each field and variable was resolved.

Hist triggers can also save per-key variables and correlate two events. A synthetic event (4.17, in kernel/trace/trace_events_synth.c since 5.8) is an event with no tracepoint, defined from user space and fired by a hist action. The classic use measures wakeup latency from two scheduler events: 

# cd /sys/kernel/tracing
# echo 'wakeup_lat pid_t pid; u64 lat' >> synthetic_events
# echo 'hist:keys=pid:ts0=common_timestamp.usecs' \
      >> events/sched/sched_waking/trigger
# echo 'hist:keys=next_pid:lat=common_timestamp.usecs-$ts0:onmatch(sched.sched_waking).wakeup_lat(next_pid,$lat)' \
      >> events/sched/sched_switch/trigger
# echo 'hist:keys=lat:sort=lat' >> events/synthetic/wakeup_lat/trigger
# cat events/synthetic/wakeup_lat/hist

The first trigger saves a timestamp in variable ts0, keyed by the woken PID. When that PID is switched in, the second trigger computes the difference. Its onmatch() action fires wakeup_lat, and the third trigger turns the synthetic event into a latency histogram. Other actions are onmax() and onchange(), which can save() fields or take a snapshot(). With them, "capture the trace of the worst wakeup" needs no new kernel code.

Synthetic events can also be created through dynamic_events with an s: prefix, and since 6.3 a field can be an unsigned long[] that carries a stack trace saved with common_stacktrace, which reports where a task blocked when it is finally woken. Kernel code can define and fire them too, through synth_event_create() and synth_event_trace(), exported since 5.6.

Three later additions build new events on old ones. An eprobe (5.15, kernel/trace/trace_eprobe.c) is a dynamic event attached to an existing event. It can dereference a pointer field, as in e:openat raw_syscalls.sys_enter nr=$id filename=+8($args):ustring, which on x86-64 reads the second system-call argument as a user string, or it can keep only some fields. TRACE_CUSTOM_EVENT() (5.18, include/trace/trace_custom_events.h) does the same at compile time. A module declares a new record layout and print format for the tracepoint of an existing event, and the result appears under events/custom/. The sample in samples/trace_events/trace_custom_sched.c finds its tracepoints with for_each_kernel_tracepoint() and binds them with trace_custom_event_event_update().

user_events (kernel/trace/trace_events_user.c) let a process define events of its own. The code was merged in 5.18 but marked BROKEN before that release, and became usable in 6.4 after its ABI was reworked. A process opens user_events_data and issues the DIAG_IOCSREG ioctl with the event's description, the address of a word in its own memory and a bit number. The kernel sets that bit while anyone has the event enabled and clears it when they stop, so the process tests the bit before doing any work. The ioctl returns a write index, and the process emits a record by calling write() with the index followed by the payload. USER_EVENT_REG_PERSIST (6.7, requires CAP_PERFMON) keeps an event after its last user closes it, until DIAG_IOCSDEL. USER_EVENT_REG_MULTI_FORMAT (6.9) lets a program change an event's format without colliding with the old one: each name and format pair gets its own event, named name.id in the user_events_multi system. These events land in the same buffers as kernel events and are timestamped by the same clock.

7.4 Are Tracepoints an ABI?

Once events were published with formats, tools began to depend on them, and the kernel faced a question it has never answered formally. Is sched_switch's field list a user-space ABI? One episode shaped the working answer. In 2.6.39, removing the Big Kernel Lock's lock_depth counter from the common event header shifted every field by four bytes. PowerTOP 1.9x, which had hard-coded the offsets, broke badly. Linus applied a partial revert that left four bytes of padding in every event. The padding was removed only in 3.9, after PowerTOP 2 had switched to reading the format file the way perf and trace-cmd do. The rule that emerged is that the kernel tries not to break widely used events, and tools are expected to parse format and tolerate added, moved or removed fields. The bare _tp tracepoints of §7.1 sidestep the question by having no format at all, and that is one reason maintainers create them.

BPF made the question sharper, because tp_btf and fentry programs see raw kernel types through BTF and can break on any structure change. The kernel's position is that such programs use CO-RE relocations and take the risk themselves. In practice, tracepoints are the most stable instrumentation the kernel offers, followed by function entry (§5), with arbitrary instruction offsets (§8) the least stable.

Dynamic Probes

Tracepoints exist only where someone put them, and ftrace sees only function entries and returns. To look at an arbitrary instruction, at a function's return value without the graph tracer, or at a user-space program, the kernel plants breakpoints at run time. Four related facilities do this: kprobes for any kernel instruction, kretprobes and the ftrace-based fprobes for function entry and exit, and uprobes for user-space instructions. All of them can be driven from tracefs as dynamic events, as well as from perf and from BPF.

8.1 kprobes: A Breakpoint on Any Instruction

A kprobe is described by struct kprobe in include/linux/kprobes.h: 

/* include/linux/kprobes.h (abridged) */
struct kprobe {
	struct hlist_node hlist;            /* in the kprobe_table hash */
	struct list_head list;              /* probes sharing this address */
	unsigned long nmissed;              /* hits skipped by recursion */
	kprobe_opcode_t *addr;              /* where the breakpoint sits */
	const char *symbol_name;            /* or symbol + offset */
	unsigned int offset;
	kprobe_pre_handler_t pre_handler;   /* before the instruction */
	kprobe_post_handler_t post_handler; /* after it */
	kprobe_opcode_t opcode;             /* the original instruction */
	struct arch_specific_insn ainsn;    /* copied or simulated insn */
	u32 flags;
};

register_kprobe() in kernel/kprobes.c resolves symbol_name plus offset through kallsyms, or takes addr as given, and passes the result to check_kprobe_address_safe(). Only core-kernel or module text is accepted. The function refuses the vsyscall gate area; anything marked NOKPROBE_SYMBOL(), placed in .kprobes.text or, on x86, in the entry text, which covers the breakpoint and exception paths themselves (the list is in /sys/kernel/debug/kprobes/blacklist); jump-label and static-call sites, which other code rewrites at run time; BUG() and WARN() sites found by find_bug(); and the __cfi_ and __pfx_ preamble symbols that kCFI and function padding place in front of functions. A module's .init.text is refused with -ENOENT once its initialization has finished, and a probed module is pinned with try_module_get() while its text is being patched. On x86, can_probe() decodes forward from the start of the function to make sure the address is on an instruction boundary. With IBT, arch_adjust_kprobe_addr() moves a probe at sym+0 past the 4-byte ENDBR64, because an indirect call that lands on an INT3 instead of ENDBR64 raises a control-protection fault.

If the address is an ftrace call site (§5.1), check_ftrace_location() decides. With KPROBES_ON_FTRACE, which x86-64 selects, the probe is marked KPROBE_FLAG_FTRACE and implemented as an ftrace_ops whose callback, kprobe_ftrace_handler(), calls the handlers, so no breakpoint is needed. The callback takes ftrace's recursion lock and sets the saved IP to the probe address plus one, which is what an INT3 would have left. It then calls the post-handler as if a 5-byte NOP had been stepped. A pre-handler that returns nonzero has changed the IP itself, and the callback then leaves it alone. Without KPROBES_ON_FTRACE the probe is refused with -EINVAL, because ftrace owns the call site. On ARM64 the patched call site is the BL at func+4, so a probe there fails, while func+0, which ftrace turns into MOV X9, LR, takes an ordinary BRK. Every other address goes through arch_prepare_kprobe(), which saves and analyses the original instruction, and arch_arm_kprobe(), which replaces it with a breakpoint. Figure 29-8 follows a probe hit on each architecture.

On x86-64, the breakpoint is the one-byte INT3, written with text_poke() followed by smp_text_poke_sync_each_cpu(). The trap enters exc_int3(), which calls kprobe_int3_handler(): 

/* arch/x86/kernel/kprobes/core.c (abridged) */
int kprobe_int3_handler(struct pt_regs *regs)
{
	...
	addr = (kprobe_opcode_t *)(regs->ip - sizeof(kprobe_opcode_t));
	kcb = get_kprobe_ctlblk();
	p = get_kprobe(addr);

	if (p) {
		if (kprobe_running()) {
			if (reenter_kprobe(p, regs, kcb))
				return 1;
		} else {
			set_current_kprobe(p, regs, kcb);
			kcb->kprobe_status = KPROBE_HIT_ACTIVE;
			if (!p->pre_handler || !p->pre_handler(p, regs))
				setup_singlestep(p, regs, kcb, 0);
			else
				reset_current_kprobe();
			return 1;
		}
	} else if (kprobe_is_ss(kcb)) {
		...     /* second INT3, after the copied instruction */
		resume_singlestep(p, regs, kcb);
		kprobe_post_process(p, regs, kcb);
		return 1;
	}
	return 0;
}

After the pre-handler, the displaced instruction must still execute. arch_prepare_kprobe() has already decoded it with the x86 instruction decoder, and prepare_emulation() assigns an emulate_op to instructions whose only effects are on the instruction pointer, the stack or the interrupt flag. These are cli, sti, pushf and popf, which must be emulated because stepping them would change the interrupt state of the trap handler; ret and lret; near call, jmp, jcc, loop and jcxz; and indirect call and jmp through a register or memory operand. They are executed on the saved registers, and the trap returns straight to the new IP. Far calls and jumps, INT3 itself and IRET cannot be probed at all. Anything else is copied into an executable slot from the kprobe instruction cache, and the trap returns into the copy. Since 5.13 the copy is followed by a second INT3. Before that, the hardware trap flag was used to single-step it. When the second trap arrives, the handler recognizes it by its address, corrects any RIP-relative effects, runs the post-handler, and resumes after the original instruction. On non-preemptible kernels, a probe without a post-handler on a "boostable" instruction gets a JMP back instead of the second INT3, which saves one trap.

x86 also has optimized kprobes (arch/x86/kernel/kprobes/opt.c). If the instructions covered by a 5-byte JMP rel32 are safe to move, with no jump into the middle of them and no indirect jump in the function, the probe is first armed with INT3. can_optimize() decodes the whole function to check this. It also gives up in the entry text, when fewer than five bytes remain before the end of the function, and when any instruction in the function has an exception-table entry, because the fixup code may jump back into the function. A background optimizer then waits OPTIMIZE_DELAY jiffies and calls synchronize_rcu_tasks(), so that no task can be preempted inside the region. Finally it replaces the INT3 with a jump to a detour buffer. The buffer saves registers, calls the handlers, executes the displaced instructions and jumps back. The probe then costs about as much as an ftrace callback. A probe with a post-handler is never optimized, since there is no single step after which to call it. The sysctl debug.kprobes-optimization turns optimization off.

ARM64 has a fixed instruction width, so the breakpoint is a 4-byte BRK. Its 16-bit immediate selects the user: kprobes use BRK #0x004, uprobes #0x005, the kprobe step #0x006 and kretprobes #0x007, all defined in arch/arm64/include/asm/brk-imm.h. arch_arm_kprobe() writes it with aarch64_insn_patch_text(), which uses stop_machine(). The trap is routed through el1_brk64() and call_el1_break_hook() (§3.1) to kprobe_brk_handler(). Instructions that depend on the PC, such as branches, ADR, ADRP and literal loads, cannot run from another address. They are simulated by the functions in arch/arm64/kernel/probes/simulate-insn.c, as are NOPs, which need no slot at all. arm_kprobe_decode_insn() rejects instructions that cannot run anywhere but in place: MSR writes, MRS reads other than DAIF, exception-generating instructions, ERET, hints not known to be safe to step, exclusive loads and stores, the MOPS memory-copy sequences, and any address between an LDXR and its STXR, because a breakpoint there would clear the exclusive monitor on every attempt and the loop would never complete. Everything else runs from an execute-out-of-line slot followed by BRK #0x006. That design arrived in 5.10, replacing hardware single-step. kprobes had become usable from early_initcall, before the hardware debug state is initialized, and hardware stepping is unreliable at that point. ARM64 has neither optimized kprobes nor KPROBES_ON_FTRACE, so a probe on a function's first instruction is always a BRK. For function entry on ARM64, fprobes (§8.2) are the cheaper choice.

Probe handlers may not sleep. Breakpoint-based probes run them in the trap handler with interrupts disabled; ftrace-based and optimized probes run them from a callback with preemption disabled, but not necessarily with interrupts off. If a handler hits another kprobe, reenter_kprobe() steps over the second one and counts it in nmissed, rather than recursing. Several probes on one address share a single breakpoint through an aggregate probe. The list member chains them.

Kernel modules use the API directly: register_kprobe(), or register_kprobes() for an array; disable_kprobe() and enable_kprobe(), which disarm and rearm a probe without unregistering it; and unregister_kprobe(), which waits for an RCU grace period so that no handler is still running when it returns. samples/kprobes/ has working examples. Registered probes live in kprobe_table, a 64-bucket hash keyed by address, and the subsystem is ready from early_initcall() time. When a module is unloaded, or when its .init.text is freed, kprobes_module_callback() marks the probes in that text KPROBE_FLAG_GONE; they stay registered but are never armed again. /sys/kernel/debug/kprobes/list prints one line per probe: address, type (k or r), sym+offset, module, and flags such as [GONE], [DISABLED], [OPTIMIZED] and [FTRACE]. Writing 0 to /sys/kernel/debug/kprobes/enabled disarms every probe at once.

8.2 Return Probes: kretprobes, rethook, and fprobes

A struct kretprobe contains a kprobe on the function's entry. Its pre-handler saves the real return address and replaces it with the address of a trampoline. When the function returns into the trampoline, the return handler runs and control goes back to the saved address. This is the same return-address substitution that function_graph performs (§5.4). The saved addresses must be kept per task, because the function may be running in many tasks at once:

  • On x86-64, kretprobes are built on rethook (5.18, kernel/trace/rethook.c), selected through HAVE_RETHOOK and KRETPROBE_ON_RETHOOK. arch_rethook_prepare() records the return address and stack frame in a struct rethook_node, pushes it on current->rethooks, and overwrites the return slot on the stack with arch_rethook_trampoline.
  • ARM64 does not select HAVE_RETHOOK. It uses the older kretprobe code, which keeps instances on current->kretprobe_instances, and replaces the link register with __kretprobe_trampoline. That trampoline is a single BRK #0x007, so the return costs another exception. kretprobe_brk_handler() sets the PC to the address that kretprobe_trampoline_handler() returns.

struct kretprobe adds the return handler, an optional entry_handler, a data_size of private storage per instance (at most KRETPROBE_MAX_DATA_SIZE, 4 KB) through which the entry handler can pass values to the return handler, and maxactive, the number of calls that can be in flight at once. If the entry_handler returns nonzero, that call's return is not hooked. Instances come from a lockless objpool (6.7) preallocated at registration, either directly or through rethook_alloc(). A maxactive of zero defaults to max(10, 2 × num_possible_cpus()). When the pool runs dry, for example because many tasks are asleep inside the probed function, a return is missed and counted in nmissed. register_kretprobe() also insists that the address is a function entry, according to kprobe_on_func_entry(), and x86 refuses __switch_to() through kretprobe_blacklist, because that function returns into a different task.

An fprobe (kernel/trace/fprobe.c, 5.18) gives the same entry and exit callbacks without any breakpoint, because it hooks the ftrace call site at function entry. Its interface is struct fprobe, holding an entry_handler, an exit_handler and an entry_data_size of up to 15 words for passing data from entry to exit. As with kretprobes, an entry handler that returns nonzero suppresses the exit handler for that call, and the call is not counted as missed. An fprobe is registered with register_fprobe() using a filter glob and an optional exclusion glob, or with register_fprobe_ips() or register_fprobe_syms() using an address or symbol list. unregister_fprobe() waits for an RCU grace period, and unregister_fprobe_async() leaves that to the caller. A module notifier, fprobe_module_callback(), drops the addresses of a module that is being unloaded. One fprobe can attach to thousands of functions at once. This is what BPF's kprobe_multi link uses (kernel/trace/bpf_trace.c), and why bpftrace can attach to vfs_* in a second. The kprobe session programs added in 6.10 attach one BPF program to both ends of a call through the same mechanism, and the program's return value at entry is exactly this skip decision.

fprobes were originally built on ftrace plus rethook. In 6.14 they were rebuilt on the function-graph infrastructure, which gave them fgraph's per-task shadow stack (§5.4) for return addresses and the reserved per-call storage for entry data. This requires HAVE_FUNCTION_GRAPH_FREGS, HAVE_FTRACE_GRAPH_FUNC and DYNAMIC_FTRACE_WITH_ARGS, which both x86-64 and ARM64 select. As a result, return probing on ARM64 no longer needs an exception, and there is no instance pool to size: a call is counted in nmissed only when the task's shadow stack has no room for the entry data. All fprobes share one fgraph_ops, and an rhltable called fprobe_ip_table maps a function address to the fprobes attached to it. Since 6.19, fprobes with only an entry handler use a plain ftrace_ops instead, which avoids fgraph's return hook entirely. The handlers receive struct ftrace_regs, not a full pt_regs. That is why fprobe events can read arguments and the return value, but not every register.

8.3 uprobes

A uprobe (3.5, kernel/events/uprobes.c) is a breakpoint in user-space code. It is identified not by a virtual address but by an (inode, offset) pair. That way, one registration covers every process that maps the file, including processes that have not started yet. uprobe_register(inode, offset, ref_ctr_offset, uc) attaches a struct uprobe_consumer and, since 6.12, returns the struct uprobe * itself. Removal is split in two: uprobe_unregister_nosync() detaches a consumer, and uprobe_unregister_sync() waits until no handler can still be running, so a tool that removes thousands of probes waits only once. The consumer's handler runs at the probe and its optional ret_handler at the function's return. Since 6.13 both receive a __u64 *data cookie, through which a consumer that has both handlers can pass a value from entry to return. The filter callback decides per mm_struct whether the breakpoint is wanted in that process at all. A handler that returns UPROBE_HANDLER_REMOVE asks for the breakpoint to be taken out of the current process, which happens only if every consumer asks and the filters agree. UPROBE_HANDLER_IGNORE (6.13) only skips the ret_handler for this call.

Registration walks the file's address-space reverse map and calls install_breakpoint() in every VMA that maps the offset. The uprobe_mmap() hook in mmap() does the same for later mappings, and a forked child inherits the patched pages with the rest of its address space. Only private, file-backed, executable mappings qualify: valid_vma() rejects shared and hugetlb mappings and, at registration, writable ones. The write goes through uprobe_write_opcode(), rewritten in 6.16. It calls get_user_pages_remote() with FOLL_FORCE | FOLL_WRITE | FOLL_SPLIT_PMD, which breaks copy-on-write and splits a huge-page mapping, so the breakpoint lands in a private anonymous copy of the page for that one process. __uprobe_write() then clears the PTE, writes the instruction into that copy in place and maps it again. The page cache, and every process not being traced, keep the original code. On removal the original bytes are written back. If the anonymous page is then identical to the page-cache page and nobody else holds it, its PTE is zapped, so the process maps the shared page again on its next fault, and collapse_pte_mapped_thp() may rebuild a huge mapping. UPROBE_SWBP_INSN is 0xcc (INT3) on x86 and BRK #0x005 on ARM64. The optional ref_ctr_offset supports USDT probes that come with a semaphore. In the same write path, the kernel increments a counter in the process's data while the probe is active, so the application can skip the work of preparing arguments when nobody is listening.

When a task hits the breakpoint, the trap handler only sets TIF_UPROBE. The work is done by uprobe_notify_resume() on the way back to user space, in process context with interrupts enabled. handle_swbp() runs under rcu_read_lock_trace(), which allows the handlers to sleep; that is what lets sleepable BPF programs attach to uprobes. It first tries find_active_uprobe_speculative(), which looks the address up in the uprobe tree under the uprobes_seqcount sequence counter and validates the VMA with mmap_lock_speculate_try_begin(), without taking mmap_lock. Only if that fails does it fall back to a locked lookup. If no uprobe is found but the instruction really is a breakpoint, the task gets SIGTRAP, as it would without uprobes. Otherwise handler_chain() runs every consumer's handler. If a handler moved the instruction pointer, the displaced instruction is skipped. If the architecture can emulate it, arch_uprobe_skip_sstep() does so. Otherwise pre_ssout() executes it out of line, in a slot of the per-process [uprobes] page, the XOL area, which is mapped on first use. On x86, NOPs, branches (branch_setup_xol_ops()) and push (push_setup_xol_ops()) are emulated. Other instructions are copied into a 128-byte slot, with RIP-relative operands rewritten, and stepped with the hardware trap flag, X86_EFLAGS_TF. On ARM64, NOPs and PC-relative instructions are simulated, and the rest are stepped with user_enable_single_step().

For return probes, arch_uretprobe_hijack_return_addr() swaps the return address, on the stack on x86 or in the link register on ARM64, for a trampoline in the XOL page. On ARM64 with the Guarded Control Stack enabled, the copy on the shadow stack is rewritten too, and the probe is abandoned if the two disagree. Return instances are kept per task, at most MAX_URETPROBE_DEPTH (64) deep; beyond that, a return is not hooked and a rate-limited message is printed. Instances made stale by longjmp() are dropped when the stack pointer shows that their frames are gone. uprobe_handle_trampoline() runs the ret_handlers and restores the original return address.

Each hit costs at least one trap, and usually two. That is significant for heavily used probes such as USDT probes in language runtimes, and x86-64 has recently added two system calls that avoid traps:

  • uretprobe (6.11, syscall 335) makes the return trampoline execute syscall instead of int3.
  • uprobe (6.18, syscall 336) applies to probes placed on a 5-byte NOP in a 64-bit process that does not cross a page boundary. The first hit still traps, and arch_uprobe_optimize() then rewrites the NOP into a CALL to a [uprobes-trampoline] page, which enters the kernel through the system call. That page must lie within reach of a 32-bit displacement, so get_uprobe_trampoline() reuses or maps one near the probe. Unregistering puts the NOP back.

Both system calls check that they were invoked from the kernel's own trampoline and fail with SIGILL otherwise. When a consumer has changed the stack pointer, or when the task uses a shadow stack, sys_uretprobe returns through the slow IRET path rather than the trampoline. Compat tasks keep the breakpoint. ARM64 has neither system call, and its uprobes always use BRK.

The register syntax is architecture-specific. That is the most visible reason to prefer BTF names, which work the same on both architectures. Here is the same probe written three ways: 

# cd /sys/kernel/tracing
# echo 'p:getname getname_flags path=+0(%di):ustring flags=%si' >> kprobe_events
# echo 'p:getname_a64 getname_flags path=+0(%x0):ustring flags=%x1' >> kprobe_events
# echo 'f:getname_btf getname_flags filename:ustring flags' >> dynamic_events
# echo 'f:getname_ret getname_flags%return name=$retval->name:string' >> dynamic_events
# echo 1 > events/fprobes/enable
# cat trace_pipe

All four probe getname_flags(), which copies a user-supplied path into a struct filename. The first line works only on x86-64, where the first two arguments arrive in %di and %si. The second is its ARM64 equivalent, using %x0 and %x1. The :ustring type reads the string from user memory. The third and fourth lines work on both architectures, because they name the arguments and the returned structure's field, and BTF supplies the locations and types. Argument names and $argN resolved through BTF arrived for fprobe and kprobe events in 6.5, together with trace_fprobe itself. With BTF, $arg* expands to all of a function's arguments, -> and . follow members to any depth, and $retval takes its type from the prototype and is rejected for a void function. Since 6.9, $argN can also be used in a return probe; the value is saved at entry and recorded together with the return value. The same definitions are what perf probe writes after it has translated source lines and variable names into offsets and locations using DWARF. A uprobe event names a file and an offset, as in r:bash/readline /bin/bash:OFFSET line=+0($retval):string, which records each line that bash's readline() returns. Tools such as bpftrace and perf usually create probes through perf_event_open() instead, with PERF_TYPE_TRACEPOINT or the dynamic kprobe and uprobe PMUs (§9.1). Those probes are local to the file descriptor and do not appear in the tracefs lists.

A t: event attaches to an existing tracepoint, including the bare _tp tracepoints that have no trace event of their own (§7.1). With BTF, its arguments are the tracepoint's prototype arguments, as in t sched_switch preempt prev_pid=prev->pid next_pid=next->pid. Since 6.17, several tracepoint probes can share one tracepoint, and both tracepoint-probe and fprobe events install their hook only while enabled, so a defined but disabled event costs nothing. kprobe_profile and uprobe_profile list each event's hit count and, for kprobes, its miss count. Kprobe events can also be created and enabled from the kernel command line with kprobe_event=, using semicolons between definitions and commas instead of spaces, which makes it possible to trace boot before user space exists. Under confidentiality lockdown, kprobe and fprobe events cannot be created at all (LOCKDOWN_KPROBES), and tracefs itself is closed (LOCKDOWN_TRACEFS).

perf_events

ftrace and the trace events answer "what happened, in what order". The perf_events subsystem answers "how often, and where". It counts hardware events such as cycles, instructions and cache misses, plus software events such as page faults and context switches, and it samples the CPU state every N events. It began in 2.6.31 as kernel/perf_counter.c, was renamed kernel/perf_event.c in 2.6.32 once it covered more than hardware counters, became kernel/events/core.c in 3.0, and has grown into a general event framework. Tracepoints, kprobes, uprobes and hardware breakpoints can all be perf events, and every sampling profiler on Linux, from perf record to continuous-profiling agents, sits on top of it.

9.1 perf_event_open() and struct perf_event_attr

There is one system call, perf_event_open(attr, pid, cpu, group_fd, flags), which returns a file descriptor for one event. pid and cpu choose the scope. A pid of 0 means the caller and a positive value another task. With cpu -1 the event follows that task to any CPU, and with a CPU number it counts only while the task runs there. A pid of -1 with a CPU number counts every task on that CPU, and -1 for both is rejected. The flags are PERF_FLAG_FD_CLOEXEC, PERF_FLAG_FD_NO_GROUP, PERF_FLAG_FD_OUTPUT and PERF_FLAG_PID_CGROUP. The last turns pid into a file descriptor for a cgroup directory, so a per-CPU event counts only while tasks of that cgroup run there. Everything else is in struct perf_event_attr:

The size field makes the structure extensible. A caller built against older headers passes a smaller size, and the kernel zero-fills the fields it did not supply. A size of 0 is read as PERF_ATTR_SIZE_VER0, the original 64 bytes. A caller built against newer headers may pass a larger size only if every byte the kernel does not know is zero. Otherwise perf_copy_attr() writes the kernel's own size back into attr.size and fails with -E2BIG, which lets a tool probe for features. The structure has grown to PERF_ATTR_SIZE_VER9, 144 bytes, the last step adding config4 in 6.19. config1 to config4 extend config for PMUs whose event encoding needs more than 64 bits. How a PMU splits them into fields is published in its format/ directory in sysfs.

The fixed type values are PERF_TYPE_HARDWARE (0) for generic events such as PERF_COUNT_HW_CPU_CYCLES, which each PMU driver maps to its own encoding, PERF_TYPE_SOFTWARE (1), PERF_TYPE_TRACEPOINT (2) with the event ID from tracefs in config, PERF_TYPE_HW_CACHE (3), PERF_TYPE_RAW (4) for a model-specific encoding, and PERF_TYPE_BREAKPOINT (5) for hardware watchpoints, which use the x86 debug registers or the ARM64 watchpoint registers. Every other PMU, from an uncore memory controller to the kprobe and uprobe PMUs of §8.4, registers dynamically. Its type number and the format of its config bits appear under /sys/bus/event_source/devices/pmu/. On a system with more than one core PMU, such as a hybrid Intel part or a big.LITTLE ARM64 system, a generic hardware or cache event must also say which core type it is for. Since 5.13, bits 63:32 of config (PERF_PMU_TYPE_SHIFT) may carry the dynamic type of the PMU, which must then have set PERF_PMU_CAP_EXTENDED_HW_TYPE. With those bits zero, the event goes to the PMU registered as PERF_TYPE_RAW, or to whichever PMU accepts it first (§9.2).

An event either counts or samples. A counting event is read with read(). read_format selects what comes back: the count, the time_enabled and time_running totals, a unique ID, the number of lost samples (PERF_FORMAT_LOST, 6.0) and, with PERF_FORMAT_GROUP, the values of every member of a group in one call. A sampling event has a sample_period, or a sample_freq that the kernel converts to a period and keeps adjusting. A frequency above kernel.perf_event_max_sample_rate is refused with -EINVAL. On every overflow it writes a record whose content is selected by the sample_type bits. Events can be grouped by passing a leader's file descriptor as group_fd. A group is scheduled onto the PMU as a unit, so ratios such as instructions per cycle are measured over exactly the same intervals. Only the leader may be pinned or exclusive.

An event's file descriptor is controlled with ioctl(). PERF_EVENT_IOC_ENABLE, DISABLE and RESET act on the whole group with PERF_IOC_FLAG_GROUP. REFRESH enables an event for a given number of overflows and disables it after the last one. PERIOD changes the sample period. SET_OUTPUT redirects records to another event's buffer, and PAUSE_OUTPUT stops writing to it. SET_FILTER installs a tracepoint filter or an address filter, and SET_BPF and QUERY_BPF attach and list BPF programs. ID returns the event's ID, and MODIFY_ATTRIBUTES (4.17) changes a hardware breakpoint in place. Several attribute bits control an event across fork() and exec(). inherit copies the event into every child created after it was opened, and inherit_thread limits that to threads. enable_on_exec keeps the event off until the next exec(), so perf stat command measures the command and not the tool's own setup. remove_on_exec (5.13) drops the event at exec(), and sigtrap (5.13) sends a synchronous SIGTRAP to the task that caused an overflow, with sig_data in si_perf_data. A program can use this to set watchpoints on its own memory.

Access is controlled by kernel.perf_event_paranoid, which defaults to 2. CAP_PERFMON (5.8) bypasses it. At level 2, a user without the capability must set exclude_kernel, and may not sample physical addresses or kernel-mode branches (perf_allow_kernel()). Level 1 allows kernel profiling. Level 0 also allows CPU-wide events (perf_allow_cpu()). Level -1 also allows raw tracepoint data, PERF_SAMPLE_RAW on most tracepoint events (perf_allow_tracepoint()), and lifts the locked-memory limit of §9.3. No level grants access to another user's task. An event on a task must pass perf_check_permission(): either CAP_PERFMON, or ptrace_may_access() in PTRACE_MODE_READ_REALCREDS mode. A sigtrap event sends signals, so it also needs CAP_KILL or ptrace attach rights. Every open also passes through the security_perf_event_open() LSM hook. Kernel lockdown refuses sample_regs_intr, which would expose register contents captured in the kernel.

event_init() validates attr and claims the event, or returns -ENOENT so the core can try the next PMU. add() and del() put the event on a hardware counter and take it off. The core calls them when the owning task is switched in and out (__perf_event_task_sched_in() and __perf_event_task_sched_out()), and when it rotates events. start() and stop() run and pause a counter that is already placed. The flags qualify each call. add() with PERF_EF_START also starts the counter, stop() with PERF_EF_UPDATE folds the hardware count into event->count, and start() with PERF_EF_RELOAD reprograms the remaining period. The transaction methods let the core add a whole group and ask once, in commit_txn(), whether it fits. If it does not, the group is left off as a unit. event_idx() tells user space which hardware counter to read directly. setup_aux() supports PMUs that stream large amounts of data into a separate AUX buffer, such as Intel PT and ARM SPE.

perf_init_event() finds the PMU for a new event. An inherited child event tries its parent's PMU first. Otherwise the core looks the type up in pmu_idr, with hardware and cache events mapped to PERF_TYPE_RAW or to the extended type of §9.1. If no PMU owns the number, as with the ARM64 core PMUs, which take dynamic types, the core walks the pmus list and offers the event to each event_init() until one returns something other than -ENOENT. A PMU may also rewrite attr.type and return -ENOENT to forward the event. Since 6.5 the software PMU does this for cpu-clock and task-clock, which have their own cpu_clock and task_clock PMUs. perf_try_init_event() then applies the generic checks that the capabilities word selects. A PMU with PERF_PMU_CAP_NO_EXCLUDE cannot filter by privilege level, so it rejects the exclude_* bits. One without PERF_PMU_CAP_EXTENDED_REGS rejects requests for extended registers, and one with PERF_PMU_CAP_NO_INTERRUPT cannot sample at all. An uncore PMU sets scope (6.12), such as PERF_PMU_SCOPE_DIE or PERF_PMU_SCOPE_PKG. The core then places each event on one online CPU of that domain, publishes the cpumask attribute in sysfs, and migrates the events when that CPU goes offline, work that each uncore driver used to do itself.

Events live in contexts. Each CPU has a perf_cpu_context, and since the 6.2 rework each task has a single perf_event_ctxp pointer in task_struct, replacing one pointer per context type. Inside a context, every PMU that has events there gets a perf_event_pmu_context. It holds that PMU's pinned_active and flexible_active lists, so the core can schedule one PMU without walking the others. A PMU's task_ctx_nr says what it can do. perf_hw_context marks a CPU PMU, and perf_sw_context marks the software, tracepoint, kprobe, uprobe and breakpoint PMUs. perf_invalid_context marks an uncore PMU, which cannot count per task or per cgroup at all. All hardware members of a group must use one PMU. Software events may join a hardware group because they never fail to schedule, and adding a hardware event to a pure software group moves the group to the hardware PMU. An event's state is ACTIVE while it is on the PMU and INACTIVE while it is waiting to be placed. OFF means it is disabled, ERROR that a pinned group could not be placed, and EXIT that its task has exited. REVOKED (6.16) lets perf_pmu_unregister() remove a PMU, for example when its module is unloaded, while file descriptors for its events are still open.

The two architectures fill this in very differently. On x86, arch/x86/events/core.c defines a single static struct pmu pmu with the x86_pmu_* methods and delegates model detail to a struct x86_pmu description filled by intel_pmu_init() or the AMD equivalent. Each Intel counter accepts only some events, so x86_schedule_events() solves a small assignment problem over the event constraints. On ARM64, drivers/perf/arm_pmu.c provides the armpmu_* methods and armpmu_register(), while drivers/perf/arm_pmuv3.c (moved from arch/arm64/kernel/ in 6.4) supplies the architected PMUv3 operations, such as armv8pmu_get_event_idx() and armv8pmu_handle_irq(). Because the PMU is architected, one driver covers every Armv8 and Armv9 core, and heterogeneous systems register one PMU per core type. Hybrid Intel parts do the same on x86, registering cpu_core, cpu_atom and, where present, cpu_lowpower with the shared x86_pmu_* methods. CGROUP_SWITCHES (5.13) counts only switches between tasks in different cgroups. dummy counts nothing and exists to carry side-band records, and bpf-output receives the data of bpf_perf_event_output(). cpu-clock and task-clock are sampled from an hrtimer, perf_swevent_hrtimer(). That timer is also the fallback profiler on machines, typically virtual machines, whose PMU is not exposed. Hardware breakpoints are a PMU of the same kind (kernel/events/hw_breakpoint.c, PERF_TYPE_BREAKPOINT). Their slots are the four x86 debug address registers, or the up to 16 breakpoint and 16 watchpoint registers that an ARM64 core reports. The core counts slots per CPU and per task, so an event that would not fit is refused with -ENOSPC when it is created rather than failing to schedule.

7.0 adds one more claimant to the core PMU: the mediated vPMU of KVM (Chapter 28, §7.5). The Intel and AMD core PMUs set PERF_PMU_CAP_MEDIATED_VPMU, which lets KVM hand the hardware counters to a guest. When KVM creates a VM with a mediated PMU, it calls perf_create_mediated_pmu(). That fails with -EBUSY if any host event on such a PMU counts guest mode, that is, any event without exclude_guest. While such VMs exist, opening an event of that kind fails with -EOPNOTSUPP. When KVM loads the guest's PMU state, perf_load_guest_context() schedules the host's exclude_guest events off the PMU, and perf_put_guest_context() puts them back. Host profiling therefore continues in host mode, and the guest owns the counters while it runs.

9.3 Sampling, the mmap Ring Buffer, and Multiplexing

A sampling event is programmed to overflow after sample_period events, and the overflow interrupt does the work. Figure 29-9 follows one sample from the counter to user space.

On x86-64, the counter is loaded with minus the period, and the local APIC's LVTPC entry is programmed with APIC_DM_NMI, so the overflow arrives as an NMI. perf_event_nmi_handler(), registered with register_nmi_handler(NMI_LOCAL, ..., "PMI"), calls the model's handler, such as intel_pmu_handle_irq(). Because it is an NMI, the sample can land inside code that runs with interrupts disabled, and that is essential for profiling the kernel. On ARM64, the PMU raises a per-CPU interrupt. armpmu_request_irq() first tries request_nmi(), or request_percpu_nmi() for a per-CPU PPI. Either succeeds only with GICv3 pseudo-NMI enabled. Otherwise it falls back to an ordinary IRQ, and the profile of IRQ-disabled regions collapses onto the instruction that re-enables interrupts. The pseudo-NMI mechanism is the same one the hard-lockup detector needs (§4.1).

__perf_event_overflow() first accounts the interrupt (__perf_event_account_interrupt()). Each event may take max_samples_per_tick samples per tick on a CPU, derived from kernel.perf_event_max_sample_rate (100000 per second by default), so that a short period cannot livelock the CPU. An event that exceeds it is throttled. Its counter is stopped and a PERF_RECORD_THROTTLE record is written. On the next tick, perf_adjust_freq_unthr_context() restarts it and writes PERF_RECORD_UNTHROTTLE. Since 6.16 the whole group is throttled and restarted together, so the members of a group stay comparable. For a frequency event, the period is recomputed from the time since the previous overflow (perf_adjust_period()), and the tick refines it again from the count. The function then pauses or resumes an AUX event if aux_pause or aux_resume is set. It runs any attached BPF_PROG_TYPE_PERF_EVENT program, and a return of 0 drops the sample. It counts down the overflow limit set by PERF_EVENT_IOC_REFRESH, queues a task_work for sigtrap events, and calls event->overflow_handler. That is normally perf_event_output_forward(), or perf_event_output_backward() for write_backward events. perf_prepare_sample() gathers the fields that sample_type requests. It walks the kernel stack with the architecture's unwinder and, if allowed, the user stack (§9.4).

A second limit bounds the time spent in the handler. perf_sample_event_took() keeps a running average of how long each sample takes. When the average exceeds the share of CPU time allowed by kernel.perf_cpu_time_max_percent (25 by default), it lowers perf_event_max_sample_rate and logs perf: interrupt took too long (X > Y), lowering kernel.perf_event_max_sample_rate to Z. The message is common on virtual machines, where PMU accesses trap to the hypervisor. Setting the percentage to 0 or 100 disables the adjustment, which the kernel warns "can hang your system", and leaves only the per-tick limit.

The output goes to a ring buffer that user space maps with mmap() on the event's file descriptor (kernel/events/ring_buffer.c, split out in 3.1). The first page is a struct perf_event_mmap_page, which holds data_head, data_tail and the fields that let user space read a counter directly (index, offset, cap_user_rdpmc, pmc_width) and convert TSC values to perf time. A power-of-two number of data pages follows. The kernel is the only writer, and __perf_output_begin() reserves space with a local_t compare-and-exchange on data_head. The reader publishes how far it has read in data_tail, and the kernel never overwrites unread data in that mode. If the buffer is full, it counts the loss and later emits a PERF_RECORD_LOST record. Waking the reader from NMI context is not safe, so perf_output_wakeup() queues the pending_irq irq_work instead. Besides samples, the buffer carries side-band records such as MMAP2, COMM, FORK, KSYMBOL and TEXT_POKE, which perf report needs to turn addresses into symbols. On x86-64, TEXT_POKE records the code patching of §5.2, §7.1 and §8.1, so that a tool decoding an instruction trace sees the code as it was. 7.0 defines 22 record types, the last being PERF_RECORD_CALLCHAIN_DEFERRED (§9.4).

Several attributes shape the buffer. The kernel wakes the reader every wakeup_events samples or, with the watermark bit, every wakeup_watermark bytes. By default the watermark is half the buffer. A mapping made without PROT_WRITE cannot move data_tail, so the kernel overwrites the oldest data instead of dropping new records. With write_backward, which writes records from the end of the buffer towards the start, this gives a flight-recorder buffer. A tool stops it with PERF_EVENT_IOC_PAUSE_OUTPUT and reads the newest records first, starting at data_head. PERF_EVENT_IOC_SET_OUTPUT sends an event's records to another event's buffer, which is how perf record shares one buffer per CPU among all its events. AUX data from Intel PT, ARM SPE or CoreSight goes to a second mapping at the file offset given in aux_offset, with its own aux_head and aux_tail. PERF_RECORD_AUX records in the main buffer describe each chunk. Mapped pages are charged as locked memory. Each user may lock kernel.perf_event_mlock_kb per online CPU (516 KB, 512 KB plus one page, by default), and anything beyond that counts against the process's RLIMIT_MEMLOCK. CAP_IPC_LOCK or a paranoid level of -1 lifts the limit.

Hardware has few counters, and users often ask for more events than fit. Each context keeps pinned_groups and flexible_groups in red-black trees, sorted by CPU, PMU, cgroup and insertion order, so scheduling visits only the groups that can run on this CPU and PMU. Pinned groups are scheduled first. A pinned group that cannot be placed goes into the ERROR state. Its read() then returns 0, end of file, and poll() reports POLLERR until it is enabled again. Flexible groups are then added in order until one does not fit, and that sets rotate_necessary and starts the per-PMU hrtimer perf_mux_hrtimer_handler(). Every perf_event_mux_interval_ms, one tick (1000 / HZ ms) by default and adjustable per PMU in sysfs, it calls perf_rotate_context(). That function takes the flexible groups off, moves the first active flexible group of the task and CPU contexts to the back of its tree, and schedules them in again. Each event's time_enabled and time_running record how long it wanted the PMU and how long it had it. Tools scale counts by the ratio of the two and print the percentage alongside. Pinned groups are never rotated, so a measurement that must not be scaled should be pinned.

9.4 Callchains and Deferred User-Space Unwinding

A sample with PERF_SAMPLE_CALLCHAIN needs a stack trace taken in interrupt or NMI context. The kernel part is easy, because the kernel's own unwinder, ORC on x86-64 and frame records on ARM64, works anywhere. The user part is hard. The only unwinder that is safe in NMI context follows frame pointers, because it cannot fault in pages or parse DWARF tables. Many distribution binaries are built without frame pointers, so perf record --call-graph dwarf instead copies a chunk of the user stack (sample_stack_user) into every sample and unwinds it later in user space, at great cost in buffer bandwidth.

On x86-64, perf_callchain_user() follows the rbp chain with page faults disabled, and handles 32-bit tasks separately. When a uprobe hits a function entry, it also reads the return address from the stack, because the new function has not set up its frame yet. On ARM64, it calls arch_stack_walk_user() (6.10), which follows AArch64 frame records or AArch32 compat frames. Neither architecture unwinds a guest's stack from the host. A user callchain is also never taken from a task other than the one running. Chain length is bounded by kernel.perf_event_max_stack (127 frames by default) and kernel.perf_event_max_contexts_per_stack (8), which limits the PERF_CONTEXT_* markers that separate the kernel and user parts. An event can lower its own limit with sample_max_stack.

6.17 added a generic facility for doing the user unwind later, in kernel/unwind/deferred.c. A tracer calls unwind_deferred_init() once, and unwind_deferred_request() from the interrupt. That queues a task_work on the current task and returns a cookie that identifies the request. When the task is about to return to user space, it is in a context that may fault, and the task_work runs unwind_user_faultable() once. It hands the same trace to every tracer that asked during that kernel entry. 6.19 wired perf to it. With attr.defer_callchain set, the sample's callchain holds the kernel frames followed by a PERF_CONTEXT_USER_DEFERRED marker and the cookie. A later PERF_RECORD_CALLCHAIN_DEFERRED record carries the user frames, and the tool stitches the two together. The benefit is largest for long system calls that take many samples in the kernel: the user stack is walked once instead of once per sample.

In 7.0 the user-space unwinder still follows frame pointers. HAVE_UNWIND_USER_FP is selected by x86-64 only, so on ARM64 deferred callchains are not yet available. SFrame, a compact unwind format that would make frame pointers unnecessary, is not supported in 7.0. Perf is the only user of the facility in this release. Deferral applies only to samples taken in the current task, and if the request cannot be queued, for example because the task is exiting, the sample falls back to an immediate user unwind.

Perf is also one of BPF's main attach mechanisms. A BPF program can be attached to a perf event with PERF_EVENT_IOC_SET_BPF or through a BPF link, and it then runs on every overflow or tracepoint hit. It can read the sample, filter it, or aggregate stacks in a map instead of streaming them. That is how most continuous profilers work, as Chapter 23 describes.

Latency Analysis, Runtime Verification, and Debuggers

The last group of tools is built from the pieces above. The latency tracers combine tracepoints with ftrace snapshots to capture the worst case automatically. RTLA packages them for real-time tuning. Runtime verification turns tracepoints into a live check of a formal model. Finally, kgdb and kdb stop the whole kernel for interactive inspection, which is the oldest debugging method of all.

10.1 The Latency Tracers: irqsoff to timerlat

The latency tracers measure the interval between two kernel events and keep the worst case. They are ftrace tracers, selected through current_tracer, and they hook the kernel at a few fixed points. Since 4.19, kernel/trace/trace_preemptirq.c is the one place where changes of the interrupt flag and the preempt count are reported. trace_hardirqs_off() and trace_hardirqs_on(), called by local_irq_disable(), local_irq_enable() and the entry code when CONFIG_TRACE_IRQFLAGS is set, inform lockdep, call the irqsoff tracer through tracer_hardirqs_off() and tracer_hardirqs_on(), and fire the irq_disable and irq_enable tracepoints. A per-CPU flag, tracing_irq_cpu, drops the redundant calls made while interrupts are already off. trace_preempt_off() and trace_preempt_on() do the same for preemption. preempt_count_add() calls them only when the count first leaves zero and preempt_count_sub() only when it returns to zero, so nested sections add nothing. They fire the preempt_disable and preempt_enable tracepoints (CONFIG_TRACE_PREEMPT_TOGGLE), which the RV monitors of §10.3 also consume. IRQSOFF_TRACER selects TRACE_IRQFLAGS and PREEMPT_TRACER requires a preemptible kernel. Both add a call to every outermost interrupt or preemption toggle, which is why they belong in debug kernels.

  • irqsoff, preemptoff and preemptirqsoff (2.6.27, kernel/trace/trace_irqsoff.c) time the sections run with interrupts off, with preemption off, or with either. start_critical_timing() stamps the outermost disable on the current CPU. At the matching enable, check_critical_timing() computes the length and asks report_latency() whether to keep it. With tracing_thresh at zero, only a new maximum above tracing_max_latency is kept, and update_max_tr_single() swaps the CPU's live buffer into the snapshot buffer (§6.3), so the snapshot always holds the worst section seen so far. With tracing_thresh set, every section at least that long is recorded, which gives a list of offenders instead of a single winner. While active, the tracer forces the overwrite, latency-format and pause-on-trace options, so that a second latency cannot corrupt the copy. With the function-trace option (on by default), the snapshot contains every function called in the section. With display-graph, it holds a function-graph trace, which only the top-level instance supports. Only one of the three tracers can run at a time.
  • wakeup, wakeup_rt and wakeup_dl (kernel/trace/trace_sched_wakeup.c) measure scheduling latency: the time from waking a task to that task running. Probes on sched_wakeup, sched_wakeup_new, sched_switch and sched_migrate_task follow one task at a time. A wakeup is ignored unless the woken task has a higher priority than both the task already being followed and the waker, so the measurement is always of the most urgent task that had to wait. The interval ends at the sched_switch that puts the task on a CPU, and goes through the same report_latency() and snapshot logic. wakeup (2.6.27) considers every task, wakeup_rt (2.6.30) only real-time and deadline tasks, and wakeup_dl (3.14) only deadline tasks. Once a deadline task is being followed, no other wakeup displaces it.
  • hwlat (4.9, kernel/trace/trace_hwlat.c) looks for latency the kernel did not cause. Its kthread spins with interrupts disabled for width out of every window (by default, 0.5 s of each second), reading the clock in pairs. The gap within a pair is the inner latency and the gap between iterations is the outer one. A sample whose gap exceeds tracing_thresh (10 µs if unset) is recorded. NMIs that land in a sample are counted and timed (nmi-count and nmi-total in the output), so they are not mistaken for anything else. What remains comes from below the kernel: a System Management Interrupt, firmware, or a hypervisor taking the CPU away. The control files live in hwlat_detector/. Its mode file selects round-robin, the default, in which a single hwlatd thread moves to the next CPU of tracing_cpumask after each window. The alternatives are per-cpu (5.14), with one hwlatd/N thread per CPU, and none.

For all of these tracers, reading trace shows the snapshot, not the live buffer. A typical session is short: 

# cd /sys/kernel/tracing
# echo 0 > tracing_max_latency
# echo preemptirqsoff > current_tracer
# sleep 60; cat tracing_max_latency     # worst section, in µs
# cat trace                             # function trace of that section

5.14 added two tracers in kernel/trace/trace_osnoise.c that measure what a real-time application actually experiences, rather than one kernel path. osnoise runs a per-CPU kthread, osnoise_main(), which spends runtime_us of every period_us (both one second by default) in run_osnoise(). That function reads the time in a tight loop, and any gap longer than tracing_thresh (1 µs if unset) counts as noise. The tracer's own tracepoints, nmi_noise, irq_noise, softirq_noise and thread_noise, attribute each gap to the interrupt or thread that caused it, with the noise of nested interrupts subtracted. A gap that none of them explains is counted as hardware noise. Each period ends with one line in the trace. It gives the runtime, the total noise, the percentage of the CPU left to the workload, the largest single noise, and the number of hardware, NMI, IRQ, softirq and thread interferences.

timerlat arms a periodic hrtimer on each CPU, every timerlat_period_us (1000 µs by default). timerlat_irq() records how late the timer interrupt ran, as an irq sample. It then wakes a thread, timerlat_main(), which records how late it ran, as a thread sample. The two numbers separate interrupt latency from scheduling latency. If print_stack holds a value in µs, the timer interrupt saves a stack trace, and timerlat prints it when the thread latency exceeds that value. The saved stack often identifies the code that kept the thread from running. Since 6.5, a user-space thread can play the measured thread. With the OSNOISE_WORKLOAD option off, a thread pinned to CPU N opens osnoise/per_cpu/cpuN/timerlat_fd. Only one opener per CPU is allowed, and an unpinned opener gets -EPERM. The thread then calls read() in a loop. Each read() returns when the next timer fires, after recording the thread sample. The next read() records a third sample, user-ret: the time from the timer's expiry until the thread came back into the kernel, which includes the return to user space and the work done in between.

Both tracers are configured in the osnoise/ directory of tracefs. Its files are cpus, period_us, runtime_us, timerlat_period_us, print_stack, stop_tracing_us and stop_tracing_total_us. The last two stop tracing as soon as a single noise or IRQ latency, or a total noise or thread latency, exceeds their value, which freezes the trace around the event. The options file (6.2) holds flags. OSNOISE_WORKLOAD, on by default, dispatches the kernel workload threads. PANIC_ON_STOP turns a stop into a panic, so that kdump can capture the state. OSNOISE_PREEMPT_DISABLE and OSNOISE_IRQ_DISABLE run the osnoise loop with preemption or interrupts disabled, so that thread noise, or all noise except NMIs and the hardware, drops out of the measurement. DEFAULTS restores the defaults. Since 5.16 the tracers can run in several trace instances at once. Since 6.15, each sample is also a tracepoint, osnoise:osnoise_sample and osnoise:timerlat_sample, so triggers, histograms and BPF programs can consume the samples without parsing the trace.

10.2 RTLA

The osnoise and timerlat files are a mechanism, not a tool. RTLA, the Real-Time Linux Analysis tool in tools/tracing/rtla/ (5.17), wraps them in three commands, rtla osnoise, rtla timerlat and rtla hwnoise (6.3). The first two each have a top and a hist mode. RTLA creates its own trace instance, configures the tracer, and prints per-CPU summaries or latency histograms. hwnoise is osnoise run with OSNOISE_IRQ_DISABLE, so it reports only the noise that interrupts cannot explain: NMIs and the hardware itself. Unlike hwlat, it measures every selected CPU at once.

For timerlat, the choice of measured thread matters. Since 6.5, RTLA can run it in user space (-u, timerlat_u.c), one thread per CPU reading timerlat_fd. Since 6.10 this is the default whenever timerlat_fd exists, and -k falls back to the kernel threads. -U (6.9) enables the tracer for the user's own application, which opens and reads timerlat_fd itself, so the latency of the real workload is measured. -P sets the measuring threads' scheduling policy, including SCHED_DEADLINE. -C (6.5) places them in a cgroup. --dma-latency holds /dev/cpu_dma_latency open, and --deepest-idle-state (6.13) limits the idle states of the measured CPUs. Together, these two options decide deliberately whether idle-exit latency is part of the result.

RTLA's most useful feature is the stop condition. With rtla timerlat top -a 50, tracing stops the moment a latency exceeds 50 µs. -i and -T set separate IRQ and thread thresholds, and -s sets print_stack. RTLA then runs its auto-analysis (timerlat_aa.c, 6.3) over the trace and prints a breakdown: how long the IRQ was delayed, which interrupts and softirqs ran, which thread blocked the timerlat thread, and for how long. A latency spike becomes a short explanation. --dump-tasks adds the task that was running on every CPU, and -t saves the stopped trace to a file. --aa-only (6.4) keeps only the analysis and skips the per-sample output, while --no-aa turns the analysis off to save CPU.

Since 6.15, rtla timerlat collects its samples with a BPF program (timerlat.bpf.c) attached to the osnoise:timerlat_sample tracepoint. The program builds the histogram and the summary in BPF maps inside the kernel, so samples no longer pass through the trace buffer to user space. RTLA falls back to the tracefs path when BPF or the tracepoint is missing, or when RTLA_NO_BPF=1 is set. Since 6.17, --on-threshold and --on-end (actions.c) attach actions to the stop condition and to the end of the run. trace saves the trace, signal sends a signal to a process, and shell runs a command. continue resumes measuring instead of stopping, so one run can collect several spikes. 7.0 adds --bpf-action, which tail-calls a user-supplied BPF program from the collector when the threshold is crossed. That lets analysis run in the kernel at the moment of the spike. 

# rtla timerlat top -c 2-3 -a 50 --dump-tasks
# rtla timerlat hist -c 2-3 -d 1h -T 100 \
      --on-threshold shell,command="cat /proc/interrupts" --on-threshold continue
# rtla hwnoise -c 2-3 -d 10m

10.3 Runtime Verification

Tracing records what happened, but a person must still decide whether it was wrong. Runtime verification (kernel/trace/rv/, 6.0) makes that decision automatically. A monitor is a formal model of correct behaviour, written as a deterministic automaton or, since 6.17, as a linear temporal logic formula. It is compiled into C and fed with tracepoint events. Any event the model does not allow in its current state is a violation. The wip monitor ("wakeup in preemptive") is the textbook example. It models a per-CPU property: a task may be woken only while preemption is disabled. tools/verification/rvgen (called dot2k before 6.17) generates its tables from a Graphviz description, tools/verification/models/wip.dot: 

/* kernel/trace/rv/monitors/wip/wip.h (abridged) */
static const struct automaton_wip automaton_wip = {
	.state_names = {
		"preemptive",
		"non_preemptive",
	},
	.event_names = {
		"preempt_disable",
		"preempt_enable",
		"sched_waking",
	},
	.function = {
		{ non_preemptive_wip,      INVALID_STATE,      INVALID_STATE },
		{      INVALID_STATE,     preemptive_wip, non_preemptive_wip },
	},
	.initial_state = preemptive_wip,
	.final_states = { 1, 0 },
};

/* kernel/trace/rv/monitors/wip/wip.c (abridged) */
#define RV_MON_TYPE RV_MON_PER_CPU
#include "wip.h"
#include <rv/da_monitor.h>

static void handle_sched_waking(void *data, struct task_struct *task)
{
	da_handle_event(sched_waking_wip);
}
...
	rv_attach_trace_probe("wip", sched_waking, handle_sched_waking);

The handlers are tracepoint probes, attached with rv_attach_trace_probe(). da_handle_event(), generated by include/rv/da_monitor.h for the monitor type chosen with RV_MON_TYPE (global, per-CPU or per-task), looks up the next state in the function table and installs it with try_cmpxchg(). If another event raced in, it retries, up to MAX_DA_RETRY_RACING_EVENTS (3) times, and then resets the monitor with a warning. A monitor ignores events until it knows the system is in the initial state. The event that guarantees this, here preempt_enable, goes through da_handle_start_event(), which starts the monitor instead of checking the event. Every valid transition emits the event_wip trace event. If the next state is INVALID_STATE, the monitor calls rv_react() and emits error_wip. A sched_waking in the preemptive state therefore reports a bug at the moment it happens, with the stack of the offending path available. Per-task monitors keep their state in task_struct, in an array of CONFIG_RV_PER_TASK_MONITORS slots (2 by default, at most 8). Enabling more per-task monitors than there are slots fails with -EBUSY. In 7.0, da_monitor.h was reworked to use fewer macros, which affects only monitor authors.

A monitor is a struct rv_monitor, registered with rv_register_monitor(), whose second argument names a parent. Since 6.15, parents are containers that group many small specifications, each simple enough to check by inspection. Linux 7.0 ships these monitors:

  • wip (per-CPU) and wwnr ("wakeup while not running", per-task), both 6.0, are the original examples.
  • The sched container (6.15) holds scheduler properties: sco (scheduling context operations), snroc (a task sets itself non-runnable only in its own context), scpd (schedule() is called with preemption disabled), snep (schedule() does not enable preemption), sts (schedule() implies a task switch), nrp (need-resched leads to preemption), sssw (setting a sleeping state is followed by a sleep or a wakeup) and opid (wakeup and need-resched happen with preemption and interrupts disabled). sco and snroc came in 6.15 and the rest in 6.17.
  • The rtapp container (6.17) holds two per-task LTL monitors for real-time applications, pagefault and sleep.

An LTL monitor (include/rv/ltl_monitor.h) states a property over time. tools/verification/models/rtapp/pagefault.ltl is a single line, RULE = always (RT imply not PAGEFAULT). rvgen turns the formula into a Büchi automaton and then into C. The hand-written part of the monitor sets the atomic propositions from tracepoints with ltl_atom_update(), and every update re-validates the automaton. The sleep rule is richer. A real-time task may sleep only for an RT-friendly reason, such as a futex wait or an absolute clock_nanosleep() on CLOCK_MONOTONIC or CLOCK_TAI. It must then be woken by a task of equal or higher priority, a hard interrupt or an NMI. Blocking on an rt_mutex or a PI futex, and RCU and migration threads, are allowed explicitly.

Monitors are controlled through rv/ in tracefs: available_monitors, enabled_monitors (write a name to enable a monitor, or a name prefixed with ! to disable it; nested monitors appear as sched:sco), monitoring_on, available_reactors and reacting_on. Each monitor also has a directory under rv/monitors/, nested inside its container's directory, with enable, desc and reactors files. The reactors are nop (the default), printk and panic. The printk reactor uses vprintk_deferred() because it may run inside the scheduler, and panic stops the machine for a crash dump. Since 6.19, reactors receive a va_list, and rv_react() runs them under a lockdep map that declares a wait-free context, so a reactor that takes a sleeping lock is reported. The rv tool in tools/verification/rv/ (6.2) wraps the interface: rv list shows the monitors, and rv mon wip -r printk -t enables one with a reactor and prints its events. The cost is one table lookup per event. That makes it practical to check scheduler and real-time properties continuously in a test fleet, not just when a bug is suspected.

10.4 kgdb and kdb

Sometimes the only way to understand a state is to stop the kernel and look at it. kgdb (2.6.26, moved to kernel/debug/ in 2.6.35) is an in-kernel GDB stub. An exception or breakpoint enters kgdb_handle_exception(), and kgdb_cpu_enter() makes the CPU that wins dbg_master_lock the master. The master brings the other CPUs to a halt with kgdb_roundup_cpus(). Each of them enters kgdb_cpu_enter() through kgdb_nmicallback() as a slave and spins on dbg_slave_lock with interrupts disabled until the master releases it. The generic roundup uses an asynchronous IPI. Architectures that can do better override it, and nokgdbroundup disables it. The master then speaks the GDB remote protocol (kernel/debug/gdbstub.c) over a polled I/O driver registered with kgdb_register_io_module(). When the debugger resumes the kernel, every CPU leaving the debugger calls dbg_touch_watchdogs(), which resets the soft-lockup watchdog (§4.1), the clocksource watchdog and the RCU stall timer, so the time spent stopped is not reported as a hang.

The usual I/O driver is drivers/tty/serial/kgdboc.c, which shares a serial console and is selected with kgdboc=ttyS0,115200. With kgdboc=kms,kbd, kdb uses kernel mode setting to show itself on the graphics console and reads the keyboard. kgdboc_earlycon (5.8) uses a boot console before the tty layer exists, and there are also USB debug-port drivers. kgdbwait makes the kernel wait for the debugger early in boot. SysRq-g (§3.4) breaks in at any time, and kgdb_breakpoint() breaks in from code. kgdbcon copies printk output to GDB, and drivers/misc/kgdbts.c is a self-test, run with kgdbts=V1. kdb (kernel/debug/kdb/, merged in 2.6.35) is a built-in command shell on the same stub, for use without a second machine. md and mm display and modify memory, and rd and rm do the same for registers. bt, btp, bta and btc print backtraces of the current task, a given PID, all tasks, or every CPU. ps, dmesg, lsmod and per_cpu inspect the system state, and bp and ss set breakpoints and single-step. ftdump (kernel/trace/trace_kdb.c) dumps the ftrace ring buffer, and kgdb switches the same session over to the GDB protocol.

Much kernel debugging with GDB does not use kgdb at all. The gdbstub of QEMU, or a JTAG probe, stops the virtual or physical CPUs from outside. That needs no kernel support and works even when the kernel is wedged. CONFIG_GDB_SCRIPTS (scripts/gdb/, 4.0) adds Python helpers that GDB loads with vmlinux, and they work over kgdb too. lx-symbols loads module symbols and sets a breakpoint to reload them whenever a module is loaded. lx-dmesg walks the printk ring buffer of §2.2. lx-ps, lx-lsmod, lx-mounts, lx-slabinfo, lx-interruptlist and lx-timerlist recreate familiar views, and convenience functions such as $lx_current() and $lx_per_cpu() can be used inside GDB expressions. The kernel documentation recommends booting with nokaslr, so that symbol addresses match vmlinux.

The architecture-specific parts are small but telling. x86 rounds up the other CPUs by sending an NMI with apic_send_IPI_allbutself(NMI_VECTOR), so even a CPU spinning with interrupts disabled stops. ARM64 sends the IPI_KGDB_ROUNDUP IPI, which can reach such a CPU only when it is delivered as a pseudo-NMI, the recurring ARM64 theme of this chapter. Breakpoints are INT3 on x86, and on ARM64 they are BRK with the immediates KGDB_DYN_DBG_BRK_IMM (0x400) and KGDB_COMPILED_DBG_BRK_IMM (0x401), dispatched by the same BRK handler in arch/arm64/kernel/debug-monitors.c as the kprobe immediates. Under kernel lockdown, kgdb and kdb refuse to read or write kernel memory (LOCKDOWN_DBG_READ_KERNEL and LOCKDOWN_DBG_WRITE_KERNEL), because a debugger is by definition a way around every other protection.

Summary

The kernel's diagnostic facilities form layers. Each new mechanism reuses the ones below it: the same static keys, live text patching and ring buffers serve dynamic debug, ftrace, tracepoints, probes and perf, and one interface such as tracefs or perf_event_open() reaches several mechanisms at once.

At the bottom are the ways the kernel reports on itself without being asked. Messages enter through printk() with a level prefix, rate limiting or dynamic debug, whose disabled pr_debug() sites cost one patched no-op. The printk ring buffer (5.10) is lockless, so any context, including NMIs and a panicking CPU, can append to it, and /dev/kmsg gives each reader its own position. nbcon consoles (6.7) print from their own kthreads (6.12) in normal operation and take over atomically in an emergency, which removed the last obstacle to PREEMPT_RT in mainline. BUG and WARN are trapping instructions found through the bug table. An oops kills the current task and sets a taint bit, and panic() stops the other CPUs, writes the log through kmsg dumpers to pstore, or hands over to a kdump kernel. panic_on_warn, warn_limit and oops_limit decide how far up that ladder an error climbs, and panic_sys_info chooses what is dumped on the way. Every report carries a stack trace from the ORC unwinder on x86-64 or the frame-record unwinder on ARM64, named through the compressed kallsyms table.

Detectors find the failures that produce no error at all. The soft-lockup detector uses a per-CPU hrtimer that checks whether the CPU stopper thread, the highest-priority task on the CPU, has run recently. The hard-lockup detector needs a non-maskable source: a perf cycle counter overflowing into a true NMI on x86-64, a pseudo-NMI on ARM64 when the GIC priority mask is in use, and otherwise the buddy detector, in which each CPU watches a neighbor's timer interrupts. The hung-task detector, the workqueue watchdog and RCU stall warnings watch tasks, work items and grace periods. The sanitizers (KASAN, KFENCE, KCSAN, UBSAN, kmemleak) and lockdep instrument the code itself to catch memory corruption, races and lock-order errors before they become crashes.

Above that is instrumentation that costs nothing until it is switched on. Compiler-generated __fentry__ or patchable-entry sites become live calls when ftrace patches them, using smp_text_poke_*() with its INT3 protocol on x86-64 and aarch64_insn_patch_text*() on ARM64. Every user, from the function tracer to livepatch and BPF trampolines, is a struct ftrace_ops or a direct call. The function-graph tracer hooks returns through a per-task shadow stack that fprobes have shared since 6.14. A tracepoint is a static key around a static call, and the TRACE_EVENT() macro expands one description into the record layout, the format file and the output code. kprobes plant breakpoints, or reuse an ftrace site, at almost any kernel instruction, and uprobes do the same on an (inode, offset) pair in user code. Dynamic events turn both into trace events from a command string, with arguments typed through BTF. What the hooks produce lands in a per-CPU lockless ring of pages that readers consume through tracefs, splice() or, since 6.10, mmap(). Instances, snapshots and persistent buffers in reserved memory (6.12) keep separate or surviving copies, and filters, hist triggers and synthetic events reduce the data inside the kernel.

perf_events adds hardware counters behind one system call. A struct perf_event_attr selects a PMU, which may be one of several on a hybrid x86 or big.LITTLE ARM64 system, and an event that counts or samples. Overflow interrupts are true NMIs on x86-64 and pseudo-NMIs, when enabled, on ARM64. Samples go to a per-event mmap ring buffer, and the core multiplexes event groups when there are more events than counters. In 7.0 KVM's mediated vPMU (Chapter 28, §7.5) can claim the core PMU for a guest. User callchains can be unwound later, in task context, by the deferred unwinding facility (6.17, used by perf since 6.19), which in 7.0 works only with frame pointers on x86-64.

The analysis layer sits on top. The irqsoff, preemptoff and wakeup tracers record the worst latency seen, hwlat measures time stolen by firmware, and osnoise and timerlat measure noise and timer-wakeup latency on isolated CPUs, including from a user-space thread through timerlat_fd. RTLA wraps them in a command-line tool that collects with BPF since 6.15 and can run actions on a threshold since 6.17. Runtime verification checks the kernel against deterministic automata or LTL formulas, such as the scheduler and rtapp monitors, and a reactor can warn or panic on a violation. kgdb and kdb stop the whole machine for interactive inspection, helped by the GDB scripts in scripts/gdb. Access to all of this is policy: dmesg_restrict, kptr_restrict and pointer hashing, perf_event_paranoid and CAP_PERFMON, and kernel lockdown, while noinstr keeps the hooks themselves out of code that must not be traced.
