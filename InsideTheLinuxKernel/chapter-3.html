A process is the kernel's unit of living work. Every running program, every daemon, every container workload, and every kernel helper thread exists because the kernel allocated a process descriptor, assigned it an identity, gave it an address space, and placed it on a run queue. The fundamentals — fork, exec, exit, wait — have not changed since the earliest Unix systems. But the data structures, the creation paths, the identity model, and the context-switch machinery have evolved enormously between Linux 2.6.11 and Linux 7.0.12. This chapter traces that evolution.

Process management in Linux 2.6.11 was shaped by uniprocessor and small-SMP i386 systems. Almost every process-management structure of that kernel has since changed. task_struct has roughly tripled, from about 120 members in 2.6 to some 350 in a fully configured 7.0 kernel. The old do_fork() entry point has given way to kernel_clone() and the extensible clone3() system call. PIDs, once allocated from a pidmap bitmap and found through four hash tables, are now reference-counted struct pid objects allocated from a per-namespace IDR, and a process can be held through a file descriptor (a pidfd). The kernel stack is vmalloc'd with guard pages, thread_info lives inside task_struct rather than at the bottom of the stack, and current comes from a per-CPU variable on x86_64 and from the SP_EL0 register on ARM64 instead of from the old stack-masking trick. The context switch must also carry FSGSBASE, PKRU, and the much larger FPU/SIMD state, and cooperate with the PCID/ASID machinery behind KPTI.

The chapter first defines what a process is and how Linux builds threads from the same object, then dissects the descriptor: task_struct, its state bitmask, its identifiers (PIDs, struct pid, PID namespaces, pidfds), and where the descriptor and its kernel stack live in memory. Three sections on organization follow: the list_head toolkit from which every kernel list is built; the other generic structures used throughout the kernel (red-black trees, the IDR and IDA allocators, kref, lock-free lists, ring buffers, hash tables, and notifier chains); and the structures that apply them to processes — the process list, the run queues, the family tree, wait queues, and resource limits. The rest of the chapter follows a process through its life: the context switch on x86_64 and ARM64, creation through clone3() and copy_process(), the kernel threads the system runs on its own behalf, the namespaces that give each process its view of the system, and finally exit, reaping, and pidfd notification. Scheduling policy — the decision of which process to run — is deferred to Chapter 7; namespaces and cgroups as container building blocks are treated in full in Chapter 25.

Processes, Lightweight Processes, and Threads

A process is an instance of a program in execution: the collection of kernel data structures that fully describes how far a program has progressed. From the kernel's point of view, a process is an entity to which system resources — CPU time, memory, open files, credentials, namespaces — are allocated.

The three terms in this section's title name the same underlying object viewed at different levels. A process is the user-space abstraction — a program with its own address space and resources. A thread is the POSIX abstraction — a flow of execution within a process, sharing that process's memory and file descriptors. A lightweight process (LWP) is the kernel's implementation of a thread: a schedulable task_struct that happens to share resources with others. Linux does not distinguish these internally — every flow of execution, whether a single-threaded program, one thread of a multithreaded program, or a kernel worker, is one task_struct on one run queue. The differences are entirely a matter of which resources are shared, decided by the flags passed to clone().

The Linux Threading Model

Unix traditionally offered only fork() and exec(). Multithreading was bolted on later, and different systems chose different implementation strategies. Linux chose a distinctive one: a thread is just a process that shares resources with other processes.

This is called a 1:1 threading model: each user-space thread maps to exactly one kernel-schedulable entity. It contrasts with the M:N models some other systems used, where many user threads are multiplexed onto fewer kernel threads by a user-space scheduler. The 1:1 choice keeps the kernel simple (the scheduler already knows how to schedule tasks; threads need no new machinery) and gives every thread true parallelism and independent blocking, at the cost of a task_struct per thread. The older LinuxThreads library approximated this before the kernel had proper thread-group support; NPTL (glibc 2.3.2+) is the modern implementation, relying on kernel features like thread groups, CLONE_SETTLS for per-thread TLS, and futexes for fast user-space synchronization.

The mechanism is clone(). When a thread library (NPTL, the Native POSIX Thread Library, since glibc 2.3.2) creates a new thread, it calls clone() with flags requesting that the new lightweight process share the parent's:

  • address space (CLONE_VM)
  • file descriptor table (CLONE_FILES)
  • filesystem context (CLONE_FS)
  • signal handlers (CLONE_SIGHAND)
  • signal delivery (CLONE_THREAD)

The result is a new task_struct — a full process descriptor with its own PID, kernel stack, and scheduling state — that happens to share most resources with its siblings. The kernel does not have a separate "thread" data structure. Every schedulable entity is a task_struct.

These flags are not independent — the kernel enforces a sharing hierarchy in copy_process() (kernel/fork.c). A thread group must share signal handling, and shared signal handling in turn requires a shared address space:

/* kernel/fork.c — copy_process() */
/* Thread groups must share signals as well... */
if ((clone_flags & CLONE_THREAD) && !(clone_flags & CLONE_SIGHAND))
    return ERR_PTR(-EINVAL);
/* Shared signal handlers imply shared VM... */
if ((clone_flags & CLONE_SIGHAND) && !(clone_flags & CLONE_VM))
    return ERR_PTR(-EINVAL);

So CLONE_THREAD ⇒ CLONE_SIGHAND ⇒ CLONE_VM. This is why a POSIX thread necessarily shares the address space: the threading model is a single point on a continuum of resource sharing, and the kernel forbids the incoherent combinations. A plain fork() sits at one end (share nothing, copy-on-write the address space); vfork() shares the VM but suspends the parent; a full pthread sits at the other end (share everything relevant). All three are clone() with different flag sets.

Thread Groups

POSIX requires that all threads of a multithreaded application share a single PID (as seen by getpid()), receive signals as a group, and exit together on _exit(). Linux implements this through thread groups.

When a process calls clone() with CLONE_THREAD, the new task joins the caller's thread group:

  • Its tgid (thread group ID) is set to the leader's pid.
  • getpid() returns tgid, not pid, so all threads report the same PID.
  • gettid() returns the per-thread pid.
  • Signals sent to the thread group (e.g., kill(pid, sig)) are delivered to the group as a whole, with the leader's signal_struct serving as the shared mailbox.
  • exit_group() terminates all threads in the group.
/* include/linux/sched.h:1059-1060 */
pid_t    pid;      /* Per-thread, unique system-wide */
pid_t    tgid;     /* Thread group ID = leader's pid */

Each task also carries a group_leader pointer (include/linux/sched.h) to the first task in its thread group — the one whose pid equals the shared tgid. The helper thread_group_leader(p) simply tests whether the task is that leader; in the kernel it is implemented as p->exit_signal >= 0, because only a group leader has a real exit signal to deliver to its parent (non-leader threads use -1). The leader is special in a few ways: it is the task that remains as a zombie holding the group's exit status until reaped, and its signal_struct is the shared per-group state that getpid(), group signal delivery, and resource accounting all key off.

It helps to distinguish the two shared signal structures a thread group owns. sighand_struct (shared via CLONE_SIGHAND) holds the dispositions — the table of handlers, so that changing a handler with sigaction() affects every thread. signal_struct (shared via CLONE_THREAD) is the wider per-thread-group state: the shared pending-signal queue, the group's resource limits (rlimits), the group exit code, session and process-group PIDs, and aggregated CPU-time accounting. A signal directed at the process (e.g. kill(tgid, ...)) lands on signal_struct's shared queue and may be handled by any thread that has it unblocked; a signal directed at a specific thread (tgkill()) targets that task's private queue.

Group termination ties these together. When any thread calls exit_group() — which is what the C library's exit() and a return from main() invoke — the kernel sets SIGNAL_GROUP_EXIT in the shared signal_struct and calls zap_other_threads() to deliver a fatal signal to every other thread, so the whole process comes down together. A lone exit() system call (rare from C programs) terminates only the calling thread. Thread joining uses a lightweight kernel mechanism rather than signals: NPTL passes each thread's TID address via CLONE_CHILD_CLEARTID, and when the thread exits the kernel writes 0 to that address and issues a FUTEX_WAKE — which is exactly how pthread_join() learns the thread is gone.

In Linux 2.6, NPTL had already replaced the older LinuxThreads library. In 7.0.12 the model is unchanged, but the PID infrastructure underneath has been completely rewritten (see "The struct pid Abstraction" and "PID Namespaces" in "Identifying a Process" below).

Process Descriptor

To manage a process, the kernel keeps all of its state in a process descriptor: struct task_struct, defined in include/linux/sched.h. In Linux 2.6.11 this structure was already the largest in the kernel. In 7.0.12 it has grown to approximately 350 fields and bitfields, reflecting two decades of new subsystems, security features, and scheduling classes.

Overview of task_struct

/* include/linux/sched.h:820 */

    struct fs_struct        *fs;

    /* Namespaces */

    /* Signals */
    struct signal_struct    *signal;
    struct sighand_struct __rcu *sighand;

    struct seccomp          seccomp;

    /* ... approximately 300 more fields ... */

Figure 3-1 shows task_struct in its role as the hub of a process: a small number of pointers reach out to reference-counted satellite structures, and the CLONE flags passed at creation time decide which of them are shared with siblings rather than copied.

The randomized_struct_fields_start / _end markers enable the randstruct GCC plugin to randomize the layout of fields between those markers at compile time, making it harder for exploits to predict field offsets. This is a security feature absent in 2.6.

The few fields above the randomization boundary are deliberate. thread_info must be the very first member (when CONFIG_THREAD_INFO_IN_TASK is set) because low-level assembly and current_thread_info() assume it sits at offset 0; and __state/saved_state are kept at fixed offsets because they are touched on the scheduler's hottest paths. The kernel's own comment is explicit: "only scheduling-critical items should be added above here." Everything else is fair game for randomization, so the same source builds two kernels with different field offsets — an exploit compiled against one cannot assume the layout of another.

The "approximately 350 fields" figure describes a typical distribution kernel; the real number is highly configuration-dependent. The task_struct definition is guarded by roughly 80 #ifdef blocks, so entire clusters of fields appear or vanish with options like CONFIG_SCHED_CORE, CONFIG_RT_MUTEXES, CONFIG_BLK_CGROUP, CONFIG_NUMA_BALANCING, and the various sanitizers. A stripped-down embedded build has a much smaller descriptor than a server kernel with every subsystem enabled — one reason the structure is never accessed by hard-coded offsets but always through named fields and helper accessors.

One frequently-read field that spans several of these groups is flags — a bitmask of PF_* per-task flags that record durable properties of the task rather than transient scheduler state. Kernel code tests them constantly on hot paths. Representative flags include PF_KTHREAD (the task is a kernel thread with no user address space), PF_EXITING (the task has entered do_exit() and must not acquire new resources), PF_WQ_WORKER and PF_IO_WORKER (workqueue / io_uring worker threads, which the scheduler treats specially so a sleeping worker can spawn a replacement), PF_MEMALLOC (the task is reclaiming memory, so nested allocations must not recurse into reclaim), PF_KSWAPD, and PF_NO_SETAFFINITY (user space may not change the task's CPU affinity). Because these are plain bit tests on a field the scheduler already has in cache, they are far cheaper than following a pointer into a subsystem structure.

What's New in task_struct Since 2.6

Several entire subsystems have added fields to task_struct:

sched_ext (CONFIG_SCHED_CLASS_EXT): the BPF-extensible scheduler class. A struct sched_ext_entity scx field allows BPF programs to make per-task scheduling decisions at runtime.

io_uring (CONFIG_IO_URING): the high-performance async I/O subsystem adds struct io_uring_task *io_uring for per-task submission and completion state.

seccomp and syscall_user_dispatch: seccomp filtering (BPF-based syscall sandboxing) and syscall user dispatch (for WINE/emulation) each get their own fields.

Namespace pointers (nsproxy): while namespaces existed in embryonic form in 2.6, the modern struct nsproxy holds pointers to seven of the eight namespace types (UTS, IPC, mount, PID for children, network, time, and cgroup); the eighth, the user namespace, is reached through the task's credentials (cred->user_ns). "Namespaces and Container Identity" later in this chapter covers them in detail.

RCU fields: preemptible RCU, tasks-RCU, and tasks-trace-RCU each add per-task tracking fields for safe read-side critical sections.

PSI (Pressure Stall Information): psi_flags tracks whether the task is stalled on CPU, memory, or I/O, feeding the pressure stall monitors used by Android's LMKD and systemd-oomd.

Restartable sequences (rseq): a struct rseq_data rseq field registers a user-space per-CPU critical-section region. rseq lets user code run fast per-CPU operations (counters, allocator free-lists) without atomics; if the task is preempted or migrated mid-sequence, the kernel aborts the sequence so user space can retry. The scheduler notifies this subsystem on every context switch (see the rseq/mm_cid hooks in Context Switching below).

KASAN/KCSAN/UBSAN: sanitizer support adds per-task tracking for memory-safety and concurrency checks during development.

Core scheduling (CONFIG_SCHED_CORE): fields such as core_cookie and core_node support coordinated task selection across SMT (hyperthread) siblings. Tasks tagged with the same cookie via prctl(PR_SCHED_CORE) are allowed to run simultaneously on sibling threads of a physical core; mismatched tasks force the sibling idle instead. This is a mitigation against cross-hyperthread side-channel leaks (L1TF, MDS) that lets trusted workloads keep SMT enabled.

Futex robust and PI lists (robust_list, pi_state_list): pointers that let the kernel clean up after a thread that dies while holding a lock. Robust futexes let the kernel mark a userspace lock as owner-dead so another thread can recover, and priority-inheritance futexes track PI state so a low-priority lock holder can be boosted — both essential for robust and real-time userspace synchronization.

Core States

The original states remain:

  • TASK_RUNNING (0): the process is either executing on a CPU or ready to be scheduled. Unlike many textbooks, Linux uses a single state for both "running" and "ready."
  • TASK_INTERRUPTIBLE (1): the process is sleeping and will wake on the awaited event or on a signal.
  • TASK_UNINTERRUPTIBLE (2): the process is sleeping and will wake only on the awaited event. Signals are deferred until the task wakes. Used for short, critical I/O waits where interruption would corrupt state.

States Added Since 2.6

TASK_KILLABLE (TASK_WAKEKILL | TASK_UNINTERRUPTIBLE): a compromise introduced in 2.6.25. The task sleeps like UNINTERRUPTIBLE but will wake for fatal signals (SIGKILL). This prevents unkillable processes stuck in NFS or FUSE waits while still protecting against ordinary signal interruption.

TASK_IDLE (TASK_UNINTERRUPTIBLE | TASK_NOLOAD): used by idle kernel threads. Like UNINTERRUPTIBLE but does not contribute to the system load average. Without this, the kworker threads that sleep in UNINTERRUPTIBLE state would inflate the load average misleadingly.

TASK_PARKED: a kthread has been parked via kthread_park() and will not be scheduled until kthread_unpark() is called. Used for CPU hotplug: per-CPU kthreads are parked when a CPU goes offline.

TASK_NEW: a freshly created task that has not yet been made runnable. This transient state prevents the scheduler from picking up a half-initialized process.

TASK_FROZEN: the task has been frozen for system suspend or hibernation, or by the cgroup v1 freezer. The freezer moves the task's current sleep state into saved_state and sets __state to TASK_FROZEN; on thaw the saved state is restored, so the task is not scheduled again until both thaw and its original wakeup have happened.

TASK_WAKING: the task is being woken up and is in transit between sleep and the run queue. This transient state prevents races in the wakeup path on SMP systems.

TASK_RTLOCK_WAIT: used by PREEMPT_RT for tasks blocked on an RT mutex that has been converted from a regular spinlock.

TASK_FREEZABLE: not a state on its own but a modifier flag OR'd into a normal sleep state (TASK_INTERRUPTIBLE/TASK_UNINTERRUPTIBLE) to mark that sleep as a safe point at which the task may be frozen. When the freezer runs, a task sleeping as TASK_FREEZABLE is moved directly to TASK_FROZEN — its real state saved in saved_state and restored on thaw — instead of being woken. Introduced in Linux 6.1, it replaced the older, error-prone pattern of sprinkling explicit freezable_schedule() / try_to_freeze() calls through sleeping code paths. (A lockdep-checked variant, TASK_FREEZABLE_UNSAFE, exists for the rare case of freezing with locks held.)

State Transitions

A process spends its lifetime cycling through a small number of states. Understanding the transitions — and which kernel functions trigger them — is essential for reading scheduler and wait-queue code. Figure 3-2 summarizes the major transitions.

TASK_NEW → TASK_RUNNING

When copy_process() creates a new task_struct, the task starts in TASK_NEW. This transient state exists to prevent the scheduler from picking up a half-initialized process. Once initialization is complete, kernel_clone() calls wake_up_new_task(), which sets the state to TASK_RUNNING and places the task on its CPU's run queue. From this point on, the scheduler may select it for execution at any time.

TASK_RUNNING → Sleep States

A running task voluntarily goes to sleep by setting its state to one of the sleep states and calling schedule():

/* Typical sleep pattern */
set_current_state(TASK_INTERRUPTIBLE);  /* or UNINTERRUPTIBLE, KILLABLE */
if (!condition)
    schedule();   /* yields the CPU — task is dequeued from the run queue */
__set_current_state(TASK_RUNNING);      /* after wakeup */

The choice of sleep state determines what can wake the task:

Sleep StateWakes on eventWakes on signalWakes on fatal signalAffects load avg

TASK_IDLE is TASK_UNINTERRUPTIBLE | TASK_NOLOAD. The TASK_NOLOAD flag tells the load-average calculation to ignore this task. Without it, idle kworker threads sleeping in TASK_UNINTERRUPTIBLE would inflate the load average, making it useless as a system health metric.

Sleep → TASK_WAKING → TASK_RUNNING

When the awaited event occurs, the wakeup path calls try_to_wake_up() in kernel/sched/core.c. This function:

  1. Sets the task's state to TASK_WAKING — a transient state that serializes the wakeup on SMP systems. Without it, two CPUs attempting to wake the same task simultaneously could corrupt the run-queue state.
  2. Selects a target CPU for the task (possibly migrating it).
  3. Enqueues the task on the target CPU's run queue.
  4. Sets the state to TASK_RUNNING.

The TASK_WAKING state is invisible to userspace and lasts only microseconds, but it is critical for correctness on multiprocessor systems.

TASK_RUNNING → TASK_STOPPED / TASK_TRACED

A running or sleeping task can be stopped by:

  • Job control signals: SIGSTOP, SIGTSTP, SIGTTIN, SIGTTOU set the state to TASK_STOPPED. The task remains stopped until it receives SIGCONT.
  • ptrace: when a debugger is tracing a task, the task enters TASK_TRACED at various trace points (system call entry/exit, signal delivery, etc.). The debugger must explicitly resume it with ptrace(PTRACE_CONT, ...) or similar.

In Linux 7.0.12, TASK_STOPPED and TASK_TRACED are implemented as composite states:

#define TASK_STOPPED    (TASK_WAKEKILL | __TASK_STOPPED)
#define TASK_TRACED     __TASK_TRACED

The TASK_WAKEKILL component in TASK_STOPPED means a stopped task can be woken by SIGKILL — you can always kill a stopped process. The kernel also tracks stopped/traced status via the jobctl field rather than relying solely on __state:

#define task_is_traced(task)   ((READ_ONCE(task->jobctl) & JOBCTL_TRACED) != 0)
#define task_is_stopped(task)  ((READ_ONCE(task->jobctl) & JOBCTL_STOPPED) != 0)

This dual tracking (state bits + jobctl flags) avoids races in the signal and ptrace paths.

TASK_RUNNING → EXIT_ZOMBIE → EXIT_DEAD

When a task calls do_exit():

  1. The exit_state is set to EXIT_ZOMBIE. The task_struct and struct pid are retained so the parent can retrieve exit status.
  2. do_notify_parent() sends SIGCHLD to the parent.
  3. The task calls schedule() one final time — it will never be selected again.
  4. When the parent calls wait(), release_task() sets exit_state to EXIT_DEAD and frees the descriptor.

If the parent has set SA_NOCLDWAIT or ignores SIGCHLD, the kernel can skip the zombie state entirely — exit_notify() sets exit_state to EXIT_DEAD and calls release_task() itself (see "When No Zombie Is Created" in "Destroying Processes").

Special States: TASK_PARKED and TASK_FROZEN

TASK_PARKED: per-CPU kthreads are parked via kthread_park() when their CPU is taken offline during CPU hotplug. A parked thread sits in TASK_PARKED and is invisible to the scheduler until kthread_unpark() is called when the CPU comes back online. This is cleaner than destroying and recreating kthreads on every hotplug cycle.

TASK_FROZEN: the cgroup freezer (or system suspend) sets a task to TASK_FROZEN. The task remains in whatever state it was in but the scheduler will not select it. Thawing restores the original state. This is used by container managers to freeze an entire cgroup subtree, by system suspend/hibernate to freeze all userspace tasks, and by checkpoint/restore (CRIU) to freeze tasks before snapshotting their state. Chapter 21, §3.3 describes the suspend freezer.

Setting State Safely

The kernel uses set_current_state() and __set_current_state() to update the state field:

/* include/linux/sched.h:240-269 */
#define __set_current_state(state_value)                  \
    do {                                                  \
        debug_normal_state_change((state_value));         \
        trace_set_current_state(state_value);             \
        WRITE_ONCE(current->__state, (state_value));      \
    } while (0)

#define set_current_state(state_value)                    \
    do {                                                  \
        debug_normal_state_change((state_value));         \
        trace_set_current_state(state_value);             \
        smp_store_mb(current->__state, (state_value));    \
    } while (0)

#define set_special_state(state_value)                    \
    do {                                                  \
        unsigned long flags; /* may shadow */             \
                                                          \
        raw_spin_lock_irqsave(&current->pi_lock, flags);  \
        debug_special_state_change((state_value));        \
        trace_set_current_state(state_value);             \
        WRITE_ONCE(current->__state, (state_value));      \
        raw_spin_unlock_irqrestore(&current->pi_lock, flags); \
    } while (0)

set_current_state() includes a full memory barrier (smp_store_mb) to ensure that any prior memory accesses (e.g., checking a condition variable) are visible before the state change. This is critical for the classic sleep/wakeup pattern to avoid missed wakeups. The __set_current_state() variant omits the barrier and is used when the caller knows ordering is already guaranteed (e.g., when setting TASK_RUNNING after wakeup).

There is a third variant. set_special_state() is for the handful of states where the blocking task cannot use the ordinary condition-based wait loop — TASK_STOPPED, TASK_TRACED, and TASK_DEAD. In those cases a wakeup may already be in flight, and its TASK_RUNNING store would race with (and silently undo) the state change. Taking current->pi_lock around the write serializes against try_to_wake_up(), which holds the same lock. All three variants also emit a trace_set_current_state() tracepoint, which did not exist in 2.6.

In Linux 2.6 these were simpler macros. The modern versions add debug instrumentation and use WRITE_ONCE to prevent compiler tearing.

Identifying a Process

The kernel needs to name processes — to itself and to user space. It must answer questions like "which task is PID 4217?", "which threads belong to this process?", and "is this the same process I saw a moment ago, or has the number been recycled?" The answers rest on a small set of numeric identifiers (pid and tgid), a reference-counted struct pid object that decouples identity from the (much larger) task descriptor, an IDR-based lookup path that is namespace-aware, and file-descriptor handles (pidfds) that make process references race-free. This section builds that picture from the numbers up, contrasting the modern design with the four-hash-table scheme of Linux 2.6.

PIDs and TGIDs

Every task_struct has two numeric identifiers:

  • pid: a unique per-task identifier, allocated from a system-wide number space (or from a PID namespace). Every thread has a distinct pid.
  • tgid: the thread group ID. For the thread group leader, tgid == pid. For other threads in the group, tgid equals the leader's pid.

The getpid() system call returns tgid, not pid, so all threads in a process report the same PID to userspace. The gettid() system call returns the true per-thread pid.

The maximum PID value defaults to PID_MAX_DEFAULT (32,768) but can be set up to 4,194,304 on 64-bit systems via /proc/sys/kernel/pid_max.

PID numbers are handed out cyclically rather than always picking the lowest free value. alloc_pid() (kernel/pid.c) uses idr_alloc_cyclic(), which continues upward from the last-allocated number and only wraps back around after reaching pid_max. Two consequences matter in practice:

  • Recycling is delayed. A just-freed PID is not immediately reissued, which makes the classic "wrong process" race (acting on a PID after the original owner exited and the number was reused) far less likely — although only pidfds (below) close the race entirely.
  • Low PIDs are reserved after the first wrap. Once the allocator cursor passes RESERVED_PIDS (300), wrapping restarts from 300 rather than 1, keeping the small, well-known PIDs of long-lived system daemons stable. PID 1 in particular is only ever the namespace's init.

Since Linux 6.7 the limit is a per-namespace field (pid_namespace.pid_max), so a container can cap its own PID space independently of the host.

The struct pid Abstraction

In Linux 2.6, PID-to-task lookup used a flat bitmap (pidmap_array) for allocation and four separate hash tables (pid_hash[PIDTYPE_PID], pid_hash[PIDTYPE_TGID], etc.) for lookup. This worked but was not namespace-aware.

Linux 7.0.12 uses a fundamentally different design centered on struct pid:

/* include/linux/pid.h:53-75 */
struct upid {
    int nr;                        /* PID number in this namespace */
    struct pid_namespace *ns;      /* The namespace */
};

struct pid {
    refcount_t count;
    unsigned int level;            /* Deepest namespace level */
    spinlock_t lock;
    struct {
        u64 ino;                   /* Inode number for pidfs */
        struct rhash_head pidfs_hash;
        struct dentry *stashed;    /* Cached pidfs dentry */
        struct pidfs_attr *attr;
    };
    struct hlist_head tasks[PIDTYPE_MAX];  /* Tasks using this PID */
    struct hlist_head inodes;
    wait_queue_head_t wait_pidfd;          /* pidfd poll notifications */
    struct rcu_head rcu;
    struct upid numbers[];                 /* Flexible array: one per ns level */
};

Key differences from 2.6:

  1. Namespace awareness: the numbers[] flexible array stores one struct upid per namespace level. A process visible in nested namespaces has multiple numeric IDs — one per level.
  2. Reference counting: struct pid is reference-counted independently of task_struct. Code can hold a reference to a PID without pinning the (much larger) task descriptor in memory.
  3. pidfd support: the wait_pidfd wait queue and pidfs fields enable file-descriptor-based process handles. A pidfd is a stable, race-free handle to a process that doesn't suffer from PID recycling problems.
  4. IDR-based allocation: the old pidmap_array bitmap is gone. PID allocation uses the kernel's IDR (ID Radix tree) allocator within each pid_namespace, providing faster allocation and better scalability.

The independent reference count is what makes the whole design robust. A struct pid lives as long as anything holds a reference — a task using it, an open pidfd, a /proc inode, or a poller waiting on wait_pidfd — not merely as long as the task is alive. When the last reference drops, free_pid() does not free the structure immediately; it hands it to RCU via call_rcu(&pid->rcu, delayed_put_pid). This lets lookups run locklessly under rcu_read_lock(): a reader that races with an exiting task either sees a valid struct pid or a NULL tasks[] slot, never freed memory.

PID Lookup: From Number to Task

In several circumstances, the kernel must derive a process descriptor pointer from a PID number. This occurs, for instance, when servicing the kill() system call: when process P1 wishes to send a signal to P2, it invokes kill() with P2's PID as a parameter. The kernel must find P2's task_struct to deliver the signal.

The Old Approach (Linux 2.6): Four Hash Tables

In Linux 2.6, scanning the process list sequentially and checking the pid field of each process descriptor was feasible but rather inefficient — an O(n) operation. To speed up the search, four hash tables were introduced. Why multiple hash tables? Because a process descriptor includes fields that represent different types of PID, and each type requires its own hash table:

Table 3-3. The four hash tables and corresponding fields in the process descriptor (Linux 2.6)

Hash table typeField nameDescription
PIDTYPE_PIDpidPID of the process
PIDTYPE_TGIDtgidPID of the thread group leader
PIDTYPE_PGIDpgrpPID of the process group leader
PIDTYPE_SIDsessionPID of the session leader

The four hash tables were dynamically allocated during kernel initialization, and their addresses were stored in the pid_hash array. The size of each table depended on the amount of available RAM; for example, on a system with 512 MB of RAM, each hash table was stored in four page frames and contained 2,048 entries.

The Hash Function

A PID was transformed into a table index using the pid_hashfn macro:

/* Linux 2.6 */
#define pid_hashfn(x) hash_long((unsigned long) x, pidhash_shift)

The pidhash_shift variable stored the length in bits of a table index (e.g., 11 for a 2,048-entry table). The hash_long() function on a 32-bit architecture was essentially:

unsigned long hash_long(unsigned long val, unsigned int bits)
{
    unsigned long hash = val * 0x9e370001UL;
    return hash >> (32 - bits);
}

This is Knuth's multiplicative hashing: the PID is multiplied by a large constant, the multiplication overflows the 32-bit register, and the high-order bits of the result are used as the hash index. The constant 0x9e370001 (2,654,404,609) is a prime approximately equal to 2³² × (√5 − 1)/2 — the golden ratio scaled to 32 bits. Knuth showed that this choice of constant produces particularly well-distributed hash values, minimizing collisions. With pidhash_shift = 11, the function yields values from 0 to 2,047.

Collision Handling and Per-PID Lists

As any basic data structures course explains, a hash function does not guarantee a one-to-one correspondence between PIDs and table indexes. Two different PIDs that hash to the same index are said to collide. Linux used chaining to handle collisions: each table entry was the head of a doubly linked list (hlist) of colliding process descriptors. Chaining was preferable to a flat table because at any given moment the number of processes is usually far below the maximum PID value (32,768) — most entries in a flat table would be wasted.

The data structures were more sophisticated than a simple hash chain, because the kernel also needed to quickly find all processes belonging to a given thread group, process group, or session. For example, looking up a thread group number in the TGID hash table returns only the group leader's descriptor. To find the other threads, the kernel maintained a per-PID list for each PID number.

Each task_struct embedded four pid structures (one per PID type) with these fields:

Table 3-4. The fields of the pid structure (Linux 2.6)

TypeNameDescription
intnrThe PID number
struct hlist_nodepid_chainLinks to the next and previous elements in the hash collision chain
struct list_headpid_listHead of (or link in) the per-PID list of processes sharing this number

So there were two kinds of linked lists at play:

  1. Hash chain (pid_chain): linked all process descriptors whose PID numbers hashed to the same table slot — these are different PIDs that happen to collide.
  2. Per-PID list (pid_list): linked all process descriptors that share the same PID number for a given type — for example, all threads in a thread group sharing the same TGID.

The Modern Approach (Linux 7.0.12): IDR + struct pid

Linux 7.0.12 replaces the four hash tables with a two-step lookup using the IDR (ID Radix tree) allocator. Figure 3-4 illustrates the complete lookup path and how multiple tasks can share a single struct pid through the tasks[] hlist arrays.

Step 1: Number → struct pid — find_pid_ns() looks up a PID number in a namespace's IDR:

/* kernel/pid.c:361 */
struct pid *find_pid_ns(int nr, struct pid_namespace *ns)
{
    return idr_find(&ns->idr, nr);
}

/* Convenience: look up in the current namespace */
struct pid *find_vpid(int nr)
{
    return find_pid_ns(nr, task_active_pid_ns(current));
}

The IDR is a thin layer over the XArray, a radix tree with 64 slots per node, so a lookup by PID number takes only a few pointer hops and there are no hash collision chains to walk. Section 7.2 describes the allocator and the order in which alloc_pid() uses it.

Step 2: struct pid → task_struct — pid_task() follows the tasks[] hlist:

/* kernel/pid.c:457 */
struct task_struct *pid_task(struct pid *pid, enum pid_type type)
{
    struct task_struct *result = NULL;
    if (pid) {
        struct hlist_node *first;
        first = rcu_dereference_check(
            hlist_first_rcu(&pid->tasks[type]),
            lockdep_tasklist_lock_is_held());
        if (first)
            result = hlist_entry(first, struct task_struct,
                                 pid_links[(type)]);
    }
    return result;
}

The pid->tasks[type] array is an array of hlist_head — one per PID type. Each hlist_head points to a chain of task_struct nodes linked via task->pid_links[type]. For PIDTYPE_PID, there is always at most one task. For PIDTYPE_PGID, all tasks in a process group are chained together.

PID Namespaces

PID namespaces are a cornerstone of Linux containers. Each namespace has its own PID number space starting from 1, its own init process (child_reaper), and its own /proc mount.

Each namespace is a struct pid_namespace (include/linux/pid_namespace.h, shown in full in "PID Namespace Details" later in this chapter). Its key members are an idr that allocates the namespace's PID numbers (replacing the 2.6 pidmap), the child_reaper that acts as its init, its nesting level, and a parent pointer.

A process in a nested PID namespace has a struct pid with level set to the depth and a numbers[] entry for each ancestor namespace. The pid_vnr() function returns the PID number as seen in the caller's namespace, while pid_nr() returns the global (init namespace) number.

In practice, most kernel code does not start from a struct pid at all — it holds a task_struct and wants a number. The task_pid_nr() family (include/linux/pid.h) provides those accessors, all built on __task_pid_nr_ns(task, type, ns):

/* include/linux/pid.h — task → number accessors */
task_pid_nr(tsk)        /* global (init-ns) per-thread PID */
task_pid_vnr(tsk)       /* per-thread PID in the current namespace */
task_tgid_nr(tsk)       /* global TGID — this is what getpid() reports */
task_tgid_vnr(tsk)      /* TGID in the current namespace */
task_pgrp_vnr(tsk)      /* process-group ID in the current namespace */
task_session_vnr(tsk)   /* session ID in the current namespace */
/* ...and _ns variants that take an explicit struct pid_namespace * */

The distinction mirrors pid_nr() vs pid_vnr(): the plain _nr forms return the number in the initial namespace (a stable, global identifier used for logging and internal bookkeeping), while the _vnr ("virtual") forms return the number as the task's own namespace sees it (what a container's getpid() returns). A tidy example is is_global_init(), which is simply task_tgid_nr(tsk) == 1.

Two behaviors of PID namespaces surprise newcomers. First, creating one is deferred to the next child: clone(CLONE_NEWPID) or unshare(CLONE_NEWPID) does not move the caller into the new namespace — it sets the caller's nsproxy->pid_ns_for_children, and only tasks fork()ed afterward become members (with the first such child becoming PID 1). This is because a running task's PID cannot change underneath it. Second, PID namespaces are strictly hierarchical and one-way visible: a task is visible (with a different number) in its own namespace and every ancestor, but is completely invisible in sibling or descendant namespaces — which is exactly why a container cannot signal a process on the host.

The namespace's init (child_reaper) is load-bearing: when it dies, every remaining task in the namespace is killed, tearing down the whole container — the counterpart of the global init, whose death panics the kernel. "PID Namespace Details" in "Namespaces and Container Identity" covers the nesting limit, the per-namespace pid_max, and the zap_pid_ns_processes() teardown.

pidfds: File Descriptors for Processes

Traditional Unix process management suffers from PID recycling races: between the time you learn a process's PID and the time you send it a signal or wait for it, the original process may have exited and the PID may have been reused for an unrelated process.

Linux solves this with pidfds — file descriptors that reference a struct pid:

/* Created via: */
int pidfd = pidfd_open(pid, 0);       /* From an existing PID */
/* Or at clone time: */
clone3(&args);  /* with CLONE_PIDFD → returns pidfd in args.pidfd */

A pidfd:

  • Holds a reference to struct pid, preventing confusion from PID reuse.
  • Supports poll() — you can wait for a process to exit without busy-polling.
  • Can be passed to pidfd_send_signal() for race-free signal delivery.
  • Can be passed to pidfd_getfd() to duplicate a file descriptor from another process (with appropriate privileges).
  • Lives on the pidfs filesystem (mounted internally), giving each pidfd a stable inode number.

This is one of the most significant process-management improvements since Linux 2.6.

Process Descriptor Handling

Kernel Stack and thread_info

In Linux 2.6, the kernel packed thread_info at the bottom of the kernel stack. The current macro worked by masking the stack pointer to find thread_info, then following its task pointer to task_struct. This was fast but fragile — any stack overflow would corrupt thread_info and crash the system.

Linux 7.0.12 has reorganized this:

CONFIG_THREAD_INFO_IN_TASK (enabled on both x86_64 and ARM64): thread_info is embedded as the first field of task_struct itself, not placed on the stack:

/* include/linux/sched.h:820-827 */
struct task_struct {
#ifdef CONFIG_THREAD_INFO_IN_TASK
    struct thread_info  thread_info;  /* Must be first */
#endif
    /* ... */
};

This means current_thread_info() is simply a cast of the current pointer:

/* include/linux/thread_info.h */
#define current_thread_info() ((struct thread_info *)current)

VMAP_STACK (CONFIG_VMAP_STACK): on x86_64, kernel stacks are allocated with vmalloc() instead of the buddy allocator. This provides:

  1. Guard pages: unmapped pages surround each stack, so an overflow triggers an immediate page fault instead of silently corrupting adjacent memory.
  2. No physical contiguity requirement: vmalloc'd stacks don't need physically contiguous pages, reducing allocation failures under memory pressure.
/* arch/x86/include/asm/page_64_types.h */
#ifdef CONFIG_KASAN
#define THREAD_SIZE_ORDER   (2 + KASAN_STACK_ORDER)  /* 4 pages + KASAN */
#else
#define THREAD_SIZE_ORDER   2                         /* 4 pages = 16 KB */
#endif
#define THREAD_SIZE  (PAGE_SIZE << THREAD_SIZE_ORDER)

On ARM64, THREAD_SIZE is similarly 16 KB (or larger with KASAN). VMAP stacks are also supported.

The kernel stack is not only where kernel functions push their locals — its very top holds the struct pt_regs. When a task enters the kernel via a syscall, interrupt, or exception, the CPU's entry code saves the interrupted register state (user or kernel) into a pt_regs frame at the top of that task's kernel stack. The task_pt_regs(task) macro computes this address (task_stack_page(task) + THREAD_SIZE - padding, minus one pt_regs), and it is how ptrace, core-dump code, and syscall-argument access reach a task's saved registers. Because each task has its own stack, each has its own private pt_regs — nested interrupts push additional frames further down the same stack.

The current Macro

The current macro is the most frequently used accessor in the kernel. Its implementation is architecture-specific:

x86_64: current reads from a per-CPU variable:

/* arch/x86/include/asm/current.h:15-28 */
DECLARE_PER_CPU_CACHE_HOT(struct task_struct *, current_task);

static __always_inline struct task_struct *get_current(void)
{
    if (IS_ENABLED(CONFIG_USE_X86_SEG_SUPPORT))
        return this_cpu_read_const(const_current_task);
    return this_cpu_read_stable(current_task);
}
#define current get_current()

The GS segment register points to the per-CPU area, so current compiles to a single mov instruction reading from %gs:offset. The cache_hot annotation ensures the per-CPU variable is placed in a cache-hot region. The const variant allows the compiler to CSE (Common Subexpression Elimination) multiple reads of current within a function.

ARM64: current reads from the SP_EL0 system register:

/* arch/arm64/include/asm/current.h:15-24 */
static __always_inline struct task_struct *get_current(void)
{
    unsigned long sp_el0;
    asm ("mrs %0, sp_el0" : "=r" (sp_el0));
    return (struct task_struct *)sp_el0;
}
#define current get_current()

When the kernel runs at EL1, the SP_EL0 register is free (it normally holds the user-mode stack pointer, which isn't needed in kernel mode). ARM64 Linux repurposes it to hold the task_struct pointer, updated on every context switch. This is a single-instruction read with no memory access.

Comparison with Linux 2.6: the old approach masked %esp to find thread_info at the bottom of the stack, then dereferenced thread_info->task. This required the stack to be naturally aligned (2^13 for 8 KB stacks) and made VMAP stacks impossible. The modern approach is faster, more robust, and decouples current from the stack layout.

Process Descriptor Allocation

Process creation requires allocating several distinct memory objects. The kernel uses dedicated slab caches for the most critical structures to minimize allocation overhead and fragmentation.

Slab Caches for Process Structures

The dup_task_struct() Function

When copy_process() creates a new task, the first step is dup_task_struct(), which allocates and initializes the raw descriptor:

/* kernel/fork.c:910 — simplified */
static struct task_struct *dup_task_struct(struct task_struct *orig, int node)
{
    struct task_struct *tsk;

    /* 1. Allocate task_struct from slab cache */
    tsk = alloc_task_struct_node(node);

    /* 2. Copy parent's task_struct (arch hook may adjust) */
    arch_dup_task_struct(tsk, orig);

    /* 3. Allocate kernel stack (vmalloc or page allocator) */
    alloc_thread_stack_node(tsk, node);

    /* 4. Initialize stack reference count */
    refcount_set(&tsk->stack_refcount, 1);
    account_kernel_stack(tsk, 1);

    /* 5. Allocate shadow call stack (ARM64 SCS) */
    scs_prepare(tsk, node);

    /* 6. Set up thread_info, stack canary, clear stale flags */
    setup_thread_stack(tsk, orig);
    set_task_stack_end_magic(tsk);       /* STACK_END_MAGIC sentinel */
    tsk->stack_canary = get_random_canary();  /* -fstack-protector */

    /* 7. Initialize reference counts */
    refcount_set(&tsk->rcu_users, 2);   /* user-visible + scheduler */
    refcount_set(&tsk->usage, 1);       /* rcu_users reference */

    return tsk;
}

The steps deserve closer attention:

  • arch_dup_task_struct() performs a structure copy with architecture-specific adjustments. On x86_64 this is essentially *tsk = *orig followed by FPU state initialization. The copy gives the child an identical starting state to the parent.
  • set_task_stack_end_magic() writes the sentinel STACK_END_MAGIC (0x57AC6E9D) at the lowest address of the kernel stack. If the stack overflows, this word is corrupted, and the kernel can detect it. With VMAP_STACK and guard pages this is a secondary defense, but on non-VMAP configurations it is the primary overflow detector.
  • stack_canary is a random value placed on the stack by GCC's -fstack-protector feature. It is checked before function return to detect stack buffer overflows. Each task gets its own random canary, preventing an attacker who leaks one task's canary from exploiting another.
  • Shadow Call Stack (scs_prepare()): on ARM64, the Shadow Call Stack is a separate, hidden stack that stores only return addresses. A function's return address is pushed onto the SCS at entry and popped at return. Even if the main stack is corrupted by a buffer overflow, the return address on the SCS remains intact. Each task gets its own SCS, allocated here.

Kernel Stack Allocation (VMAP_STACK)

The kernel stack allocation strategy depends on the configuration:

With VMAP_STACK (default on x86_64 and ARM64):

/* kernel/fork.c:331 — alloc_thread_stack_node() with VMAP_STACK */
static int alloc_thread_stack_node(struct task_struct *tsk, int node)
{
    /* Try the per-CPU cache first (2 stacks cached per CPU) */
    vm_area = alloc_thread_stack_node_from_cache(tsk, node);
    if (vm_area) {
        kasan_unpoison_range(vm_area->addr, THREAD_SIZE);
        memset(stack, 0, THREAD_SIZE);
        tsk->stack_vm_area = vm_area;
        tsk->stack = stack;
        return 0;
    }

    /* Cache miss: vmalloc a new stack */
    stack = __vmalloc_node(THREAD_SIZE, THREAD_ALIGN,
                           GFP_VMAP_STACK, node, ...);
    /* ... */
}

Key points:

  • Per-CPU caching: NR_CACHED_STACKS (2) stacks are cached per CPU to avoid repeated vmalloc/vfree overhead. Since vmalloc() is relatively slow and vfree() triggers TLB flushes, caching makes fork-heavy workloads significantly faster.
  • Guard pages: vmalloc'd stacks are naturally surrounded by unmapped guard pages (the vmalloc area has guard holes between allocations). A stack overflow triggers an immediate page fault rather than silently corrupting adjacent memory.
  • Stack zeroing: cached stacks are memset to zero to prevent information leaks between processes.

Without VMAP_STACK (some embedded configurations):

/* kernel/fork.c:407 */
static int alloc_thread_stack_node(struct task_struct *tsk, int node)
{
    struct page *page = alloc_pages_node(node, GFP_KERNEL, THREAD_SIZE_ORDER);
    tsk->stack = page ? page_address(page) : NULL;
    /* No guard pages, no caching */
}

This is the legacy path — simple and fast, but without overflow protection.

Freeing: The Two-Phase Lifecycle

A process descriptor is not freed atomically. Instead, the stack and the task_struct have separate lifetimes:

  1. Stack release (put_task_stack() → release_task_stack() → free_thread_stack()): the stack can be freed once the task is in TASK_DEAD state and no one holds a stack reference. With VMAP_STACK, the freed stack is returned to the per-CPU cache if there is room, otherwise it is vfree()d.
  2. task_struct release (free_task() → free_task_struct()): the task_struct is freed back to the slab cache. This also calls arch_release_task_struct(), bpf_task_storage_free(), and free_kthread_struct() for kernel threads.
/* kernel/fork.c:530 */
void free_task(struct task_struct *tsk)
{
    scs_release(tsk);                     /* Free shadow call stack */
    release_task_stack(tsk);              /* Free kernel stack */
    arch_release_task_struct(tsk);
    if (tsk->flags & PF_KTHREAD)
        free_kthread_struct(tsk);
    bpf_task_storage_free(tsk);
    free_task_struct(tsk);                /* Return to slab cache */
}

The reference counting (tsk->usage, tsk->rcu_users, tsk->stack_refcount) ensures that neither the stack nor the descriptor is freed while any code path still references them — essential in an SMP kernel where multiple CPUs may be examining a dying task's state.

The final descriptor free is additionally deferred through RCU. Many lookups — find_task_by_vpid(), /proc walkers, the scheduler's remote-task inspection — dereference a task_struct under nothing but rcu_read_lock(). So when rcu_users reaches zero, put_task_struct_rcu_user() does not free the descriptor immediately; it schedules __put_task_struct() via call_rcu() (the __put_task_struct_rcu_cb callback), so the memory is only returned to the slab cache after a grace period, once every in-flight RCU reader has finished. This is the same lockless-lookup discipline that protects struct pid: a reader racing with an exiting task always sees valid memory, never a freed descriptor.

Doubly Linked Lists

Before examining how the kernel tracks processes, it is worth understanding the fundamental data structure that underpins nearly every list in the kernel: the list_head doubly linked list.

The list_head Data Structure

Rather than embedding next/prev pointers directly into each data structure (as older operating systems did), Linux defines a single, generic list node type:

/* include/linux/types.h:204 */
struct list_head {
    struct list_head *next, *prev;
};

This tiny structure is then embedded inside whatever data structure needs to participate in a list. The key insight is that the next and prev pointers point to other list_head fields, not to the containing structures. To recover a pointer to the containing structure from a list_head pointer, the kernel uses the container_of macro (discussed below).

This design means that a single set of list manipulation functions works for every list in the kernel — process lists, wait queues, timer lists, inode lists, and hundreds more — without requiring type-specific code for each one.

Figure 3-6 illustrates the arrangement. Part (a) shows a circular doubly linked list of three elements: each large box is a containing structure (a task_struct, say) and the small shaded box inside it is the embedded list_head. The next and prev pointers connect the list_head fields to one another — not to the containing structures. Part (b) shows an empty list, where the sentinel head points back at itself.

Creating and Initializing Lists

A new list is created with the LIST_HEAD macro, which declares and initializes a sentinel node. The sentinel's next and prev both point to itself, representing an empty circular list:

/* include/linux/list.h:33 */
#define LIST_HEAD(name) \
    struct list_head name = { &(name), &(name) }

For dynamic initialization (e.g., in a structure allocated at runtime), use INIT_LIST_HEAD():

static inline void INIT_LIST_HEAD(struct list_head *list)
{
    WRITE_ONCE(list->next, list);
    WRITE_ONCE(list->prev, list);
}

The WRITE_ONCE() ensures the compiler does not split or reorder the stores — important on SMP systems where another CPU might be reading the list concurrently.

The container_of Macro

The list_entry macro is defined as:

#define list_entry(ptr, type, member) \
    container_of(ptr, type, member)

And container_of itself performs pointer arithmetic to recover the enclosing structure:

/* include/linux/container_of.h:19 */
#define container_of(ptr, type, member) ({                \
    const typeof(((type *)0)->member) *__mptr = (ptr);    \
    (type *)((char *)__mptr - offsetof(type, member)); })

Given a pointer to a list_head named tasks inside a task_struct, list_entry subtracts the offset of tasks within task_struct to recover the address of the task_struct itself. This is how the kernel navigates from a generic list node back to the specific structure that contains it — a zero-cost abstraction at runtime (it compiles to a single pointer subtraction).

Hash Lists (hlist)

For hash tables where the list head must be as small as possible (one pointer instead of two), Linux provides the hlist family:

/* include/linux/types.h:208 */
struct hlist_head {
    struct hlist_node *first;
};

struct hlist_node {
    struct hlist_node *next, **pprev;
};

An hlist is not circular: the pprev pointer in each node points to the next field of the previous node (or to the first field of the hlist_head), rather than to the previous node itself. This asymmetry makes hlist_head only one pointer wide (8 bytes on 64-bit), halving the memory cost of hash table buckets compared to list_head. The PID hash table, dentry cache, and inode hash all use hlist.

The API mirrors the list_head API: hlist_add_head(), hlist_del(), hlist_empty(), hlist_entry(), hlist_for_each_entry(), and so on.

RCU-Protected Lists

Many of the lists in this chapter — the PID hash chains (pid->tasks[]), the thread group list, the global task list — are read far more often than they are modified, and readers must not be forced to take a lock on every traversal. For these, the kernel provides RCU-aware variants of the list API in include/linux/rculist.h. They have the same shape as the ordinary functions but add the memory-ordering guarantees that make lockless reading safe:

/* Writers (still hold the update-side lock, e.g. tasklist_lock): */
list_add_rcu(new, head);         hlist_add_head_rcu(n, h);
list_del_rcu(entry);             hlist_del_rcu(n);

/* Readers (only rcu_read_lock(), no update-side lock): */
rcu_read_lock();
list_for_each_entry_rcu(pos, head, member) { ... }
hlist_for_each_entry_rcu(pos, head, member) { ... }
rcu_read_unlock();

The write-side helpers publish a new node with an rcu_assign_pointer() store, which carries a release barrier: a concurrent reader that observes the new next pointer is guaranteed to also see the node's fully-initialized contents. On the delete side, list_del_rcu() deliberately leaves the removed node's next pointer intact (it only poisons pprev), so a reader that is currently standing on that node can still follow it forward to the rest of the list; the node itself must not be freed until a grace period has elapsed (synchronize_rcu() or call_rcu()). The reader-side iterators wrap each pointer fetch in rcu_dereference(), which enforces the dependent-load ordering the scheme relies on.

This is exactly the machinery behind the lockless lookups described earlier: pid_task() walks pid->tasks[type] with hlist_first_rcu()/rcu_dereference() under rcu_read_lock(), and because both struct pid and task_struct are freed only after an RCU grace period, a reader can never dereference a stale node.

List Hardening (New in 7.0.12)

Modern kernels include CONFIG_LIST_HARDENED, which adds runtime integrity checks to list operations:

/* include/linux/list.h — with CONFIG_LIST_HARDENED */
static __always_inline bool __list_add_valid(struct list_head *new,
                                              struct list_head *prev,
                                              struct list_head *next)
{
    /* Verify prev->next == next and next->prev == prev */
    /* On failure: WARN, report corruption, return false */
}

When a list_add() or list_del() detects that the list's internal pointers are inconsistent (e.g., prev->next != next), it reports a kernel warning and refuses the operation. This catches list corruption bugs — often caused by use-after-free or data races — before they turn into silent memory corruption. Additionally, list_del() poisons the removed node's pointers with LIST_POISON1 (0x100) and LIST_POISON2 (0x122), so any subsequent dereference of the removed node triggers a fault.

Those poison constants are not raw low addresses. Each is offset by POISON_POINTER_DELTA (from CONFIG_ILLEGAL_POINTER_VALUE), which on 64-bit architectures relocates them into a non-canonical, guaranteed-unmapped region (for example 0xdead000000000000 + 0x100). Without the delta, 0x100 and 0x122 would sit in the low page that some configurations can map; with it, dereferencing a poisoned pointer reliably faults instead of silently reading valid memory. The same delta protects other poison values across the kernel (page mapping, timers, etc.).

Comparison with Linux 2.6

The list_head design has been remarkably stable across kernel versions. The core structure and API (list_add, list_del, list_entry, list_for_each_entry) are identical to Linux 2.6. The main additions in 7.0.12 are:

  • CONFIG_LIST_HARDENED: runtime corruption detection (2.6 had CONFIG_DEBUG_LIST but it was slower and less targeted)
  • list_first_entry(), list_last_entry(), list_first_entry_or_null(): convenience macros not present in 2.6
  • list_entry_is_head(): cleaner loop termination check, replacing raw pointer comparison
  • list_for_each_entry_safe(): existed in 2.6 but is now more widely used and audited
  • WRITE_ONCE/READ_ONCE in list operations: explicit compiler barrier annotations for lockless list traversals

Beyond Lists: Core Kernel Data Structures

The list_head is the kernel's most common container, but not its only one. A handful of other generic structures recur throughout this book, in the scheduler, the PID allocator, the driver model, interrupt handling, and nearly every subsystem that must tell another about an event, so it pays to meet them once, together, before they appear in context. Each is defined in a header under include/linux/ with a small implementation in lib/ or kernel/, and most follow the design rule of list_head: the node is embedded in the caller's object, and container_of recovers the object from it. This section covers red-black trees, the IDR and IDA integer allocators, kref, lock-free llist lists, the kfifo ring buffer, fixed-size hash tables, and notifier chains, and ends with a guide to which structure fits which job (Table 3-7). Two larger structures have their own homes: the XArray in Chapter 15, Section 4 and the maple tree in Chapter 9, Section 3.2.

Red-Black Trees

When objects must be kept sorted by a key, and found, inserted, and removed in logarithmic time, the kernel uses a red-black tree (include/linux/rbtree.h, lib/rbtree.c). The node is three words, and a tree that also tracks its smallest element adds one more pointer to the root:

/* include/linux/rbtree_types.h:5 */
struct rb_node {
    unsigned long  __rb_parent_color;   /* parent pointer | color in bit 0 */
    struct rb_node *rb_right;
    struct rb_node *rb_left;
} __attribute__((aligned(sizeof(long))));

struct rb_root {
    struct rb_node *rb_node;
};

/* include/linux/rbtree_types.h:26 */
struct rb_root_cached {
    struct rb_root rb_root;
    struct rb_node *rb_leftmost;        /* smallest node, found in O(1) */
};

Because nodes are word-aligned, the low bits of a node's address are always zero, so the tree stores each node's color in bit 0 of its parent pointer and rb_parent() masks the low two bits off. The red-black rules (a red node never has a red child, and every path from a node down to a leaf passes the same number of black nodes) keep the longest path at most twice the shortest, so a tree of n nodes is never deeper than about 2 log2(n + 1).

The library deliberately does not know how to compare keys. The caller walks down from the root comparing its own key at each step, links the new node into the empty slot it reaches with rb_link_node(), and then calls rb_insert_color(), which only recolors and rotates to restore the rules. rb_erase() removes a node and rebalances. Keeping the comparison in the caller lets the compiler inline it instead of calling a function pointer at every level. Since Linux 5.12 the header also provides helpers that write the descent loop for the caller. They take a comparison function, but because the helpers are __always_inline the comparison is still inlined:

/* include/linux/rbtree.h:223 */
static __always_inline void
rb_add(struct rb_node *node, struct rb_root *tree,
       bool (*less)(struct rb_node *, const struct rb_node *))
{
    struct rb_node **link = &tree->rb_node;
    struct rb_node *parent = NULL;

    while (*link) {
        parent = *link;
        if (less(node, parent))
            link = &parent->rb_left;
        else
            link = &parent->rb_right;
    }

    rb_link_node(node, parent, link);
    rb_insert_color(node, tree);
}

rb_find() and rb_find_add() are the matching lookup and lookup-or-insert, and rb_entry() is container_of under another name. Ordered traversal uses rb_first(), rb_next(), and rb_prev(). The tree has no lock of its own; the caller serializes writers, usually with a spinlock. Two variants appear throughout this book. A rb_root_cached (4.14) remembers the leftmost node, so the smallest element costs O(1), and rb_add_cached() and rb_erase_cached() keep the cache current. An augmented tree (include/linux/rbtree_augmented.h) stores in each node a value computed from its whole subtree, together with callbacks, generated by RB_DECLARE_CALLBACKS(), that the rebalancing code calls after every rotation to keep the value correct. The fair scheduler's run queue uses both: it is a cached tree of sched_entity nodes ordered by virtual deadline and augmented with the minimum vruntime of each subtree, so that the EEVDF pick can skip subtrees that hold no eligible task (Section 8.2 and Chapter 7, Section 3.3). Interval trees (include/linux/interval_tree_generic.h), which reverse mapping uses to find every VMA that maps a given file page (Chapter 17, Section 3.3), are augmented red-black trees whose extra value is the largest end address in each subtree. The high-resolution timer queues, epoll's set of watched files, and the deadline I/O scheduler's sort lists are red-black trees as well.

Integer ID Allocation: IDR and IDA

Many kernel objects are named to user space by a small integer: PIDs, System V IPC identifiers, POSIX timer IDs, the inode numbers of /proc entries. Two allocators hand these out (include/linux/idr.h, lib/idr.c). The IDR maps each allocated ID to a pointer. The IDA only records which IDs are in use. Both are front ends to the XArray, the radix tree that also indexes the page cache (Chapter 15, Section 4). The IDR was rebuilt on the radix tree in Linux 4.11, and the radix tree itself became the XArray in 4.20, so radix_tree_root is now a #define for xarray:

/* include/linux/idr.h:20 */
struct idr {
    struct radix_tree_root  idr_rt;     /* an XArray */
    unsigned int            idr_base;   /* lowest ID handed out */
    unsigned int            idr_next;   /* where idr_alloc_cyclic() resumes */
};

/* include/linux/idr.h:263 */
struct ida {
    struct xarray xa;
};

idr_alloc(idr, ptr, start, end, gfp) finds the lowest free ID in the range [start, end), stores ptr there, and returns the ID. idr_alloc_cyclic() instead resumes the search just past the last ID it handed out and wraps at the end, which is why PIDs climb steadily instead of reusing a number the moment it is freed. Each tree node carries an IDR_FREE mark when some slot beneath it is free, so allocation descends straight to a free slot without scanning. idr_find() is a tree walk that is safe under rcu_read_lock() alone, idr_replace() changes the pointer stored for an existing ID, and idr_remove() frees the ID. Allocation may need memory for new tree nodes, so a caller that must hold a spinlock brackets the critical section with idr_preload(GFP_KERNEL), which fills a per-CPU reserve of nodes while sleeping is still allowed, and idr_preload_end(). The PID allocator uses all of these. alloc_pid() (kernel/pid.c) preloads, takes pidmap_lock, and calls idr_alloc_cyclic() with a NULL pointer in each namespace from the task's own up to the root, which reserves the numbers without publishing anything. Only when every level has a number, and the namespace is confirmed to still accept new processes, does idr_replace() install the struct pid, so a concurrent find_pid_ns() (Section 4.4) finds either nothing or a complete object.

The IDA is the right choice when only uniqueness matters. Each XArray entry covers 1,024 IDs with a 128-byte bitmap, and while only a few low IDs in such a range are in use, the bits are stored directly in the entry as a value and no bitmap is allocated. ida_alloc(), ida_alloc_range(), and ida_free() take the XArray's own lock, so callers need no locking of their own. Workqueue worker IDs, platform device IDs, mount peer-group IDs, and the inode numbers of dynamically created /proc entries all come from IDAs. For new code, Documentation/core-api/idr.rst marks the IDR interface as deprecated in favor of calling the XArray directly with xa_alloc(), but the IDR remains in wide use, including for PIDs and IPC identifiers.

Reference Counting with kref

An object reachable from several places must not be freed while any of them still holds a pointer to it. The usual answer is a reference count, and the generic form is struct kref (include/linux/kref.h):

/* include/linux/kref.h:19 */
struct kref {
    refcount_t refcount;
};

/* include/linux/kref.h:62 */
static inline int kref_put(struct kref *kref, void (*release)(struct kref *kref))
{
    if (refcount_dec_and_test(&kref->refcount)) {
        release(kref);
        return 1;
    }
    return 0;
}

kref_init() sets the count to 1 for the creator, kref_get() adds a reference, and kref_put() drops one and, when it drops the last, calls release. The release function receives the kref, not the object, so it recovers the object with container_of before freeing it. Since Linux 4.11 the counter is a refcount_t rather than a bare atomic_t, so it saturates instead of wrapping and warns on an increment from zero. A whole class of use-after-free bugs becomes a leak and a warning (Chapter 5, Section 5.5). The kernel's documentation (Documentation/core-api/kref.rst) gives three rules. Take a reference with kref_get() before handing a pointer to another thread. Call kref_put() when done with it. And to obtain a reference without already holding one, as when looking an object up in a shared table, the lookup must be serialized against the final kref_put(). Two helpers implement that third rule. If the table is protected by a lock, kref_put_mutex() and kref_put_lock() take the lock only when the count is about to reach zero, so the release function can remove the object from the table before anyone else can find it. If lookups are lockless under RCU, kref_get_unless_zero() refuses to revive an object whose count has already reached zero. The driver model's struct kobject embeds a kref, and that is how every device, driver, and sysfs directory is reference-counted (Chapter 13, Section 3.1).

Lock-Free Lists: llist

Some lists must accept entries from contexts where a lock is impossible or too costly: an interrupt handler queuing deferred work, one CPU handing a request to another, or code that runs in NMI context. For these the kernel has llist (include/linux/llist.h, Linux 3.1), a singly linked, NULL-terminated list whose head is one pointer and whose operations are single atomic instructions:

/* include/linux/llist.h:56 */
struct llist_head {
    struct llist_node *first;
};

struct llist_node {
    struct llist_node *next;
};

/* include/linux/llist.h:234 */
static inline bool llist_add_batch(struct llist_node *new_first,
                                   struct llist_node *new_last,
                                   struct llist_head *head)
{
    struct llist_node *first = READ_ONCE(head->first);

    do {
        new_last->next = first;
    } while (!try_cmpxchg(&head->first, &first, new_first));

    return !first;      /* true if the list was empty */
}

llist_add() pushes one node with this compare-and-exchange loop, and any number of producers may push at once. Consumers normally take the whole list in one step with llist_del_all(), a single xchg() that replaces the head with NULL and returns the detached chain. Because pushes go on the front, the chain comes back newest first. A consumer that needs arrival order calls llist_reverse_order() before walking it with llist_for_each_entry_safe(). Removing a single node with llist_del_first() is safe only with one consumer. If two consumers ran it at once, one could succeed with its compare-and-exchange against a head that the other had removed and pushed back in the meantime, the classic ABA problem.

The return value of llist_add() is what makes the structure useful. It is true only when the list was empty, so exactly one producer learns that it must wake the consumer, and every later producer simply adds and returns until the consumer drains the list. This is how the cross-CPU function-call queue batches many requests behind one IPI (Chapter 4, Section 3.7). irq_work, the deferred frees of vfree() called from interrupt context, and the page allocator's trylock_free_pages list (Chapter 8) work the same way. The header warns that on architectures whose compare-and-exchange is not NMI-safe the list cannot be used from an NMI handler, so code that does so must depend on CONFIG_ARCH_HAVE_NMI_SAFE_CMPXCHG.

Ring Buffers: kfifo

A producer that generates bytes or records, and a consumer that drains them at its own pace, need a bounded queue between them. kfifo (include/linux/kfifo.h, lib/kfifo.c) is the kernel's ring buffer, and its core is five fields:

/* include/linux/kfifo.h:49 */
struct __kfifo {
    unsigned int    in;      /* elements ever written */
    unsigned int    out;     /* elements ever read */
    unsigned int    mask;    /* size - 1; size is a power of two */
    unsigned int    esize;   /* element size in bytes */
    void            *data;
};

The two indices are never reduced modulo the buffer size. They count up forever and simply wrap around at 232. The number of stored elements is in - out in unsigned arithmetic, and the slot an index refers to is index & mask. That is why the size must be a power of two: kfifo_alloc() rounds a requested size up to one, and kfifo_init(), which wraps a buffer the caller supplies, rounds down. Full and empty are told apart without giving up a slot, because in - out is the full size in one case and zero in the other. A write copies the data into the buffer (in two pieces if it wraps past the end), issues smp_wmb(), and only then advances in. A read copies data out before it advances out. As a result, one producer and one consumer can share a kfifo with no lock at all. With several producers only the producers need to serialize among themselves, and likewise for several consumers. kfifo_in_spinlocked() and kfifo_out_spinlocked() take a caller-supplied lock for that case.

The API is a set of type-generic macros. DECLARE_KFIFO(name, type, size) embeds a fifo together with a fixed array of type, DECLARE_KFIFO_PTR() declares one whose buffer is allocated later, kfifo_put() and kfifo_get() move single elements, and kfifo_in() and kfifo_out() move arrays. kfifo_to_user() and kfifo_from_user() copy directly between the ring and a user buffer, which suits the read() and write() methods of a character driver. Record fifos (STRUCT_KFIFO_REC_1 and STRUCT_KFIFO_REC_2) prefix each variable-length record with a one- or two-byte length. The serial core's transmit buffer is a kfifo (Chapter 13, Section 9.6), as are the event queues of many USB, input, and IIO drivers. Through Linux 2.6.32 the fifo was allocated separately and carried a pointer to its own spinlock. Since 2.6.33 it is embedded in its owner, and locking, when needed, is the caller's choice.

Fixed-Size Hash Tables

Section 6.5 showed that an hlist_head is one pointer wide so that an array of them makes a compact hash table. Since Linux 3.7, include/linux/hashtable.h packages that pattern so that each user does not reinvent it:

/* include/linux/hashtable.h */
#define DEFINE_HASHTABLE(name, bits)                                    \
    struct hlist_head name[1 << (bits)] =                               \
            { [0 ... ((1 << (bits)) - 1)] = HLIST_HEAD_INIT }

#define hash_min(val, bits)                                             \
    (sizeof(val) <= 4 ? hash_32(val, bits) : hash_long(val, bits))

#define hash_add(hashtable, node, key)                                  \
    hlist_add_head(node, &hashtable[hash_min(key, HASH_BITS(hashtable))])

#define hash_for_each_possible(name, obj, member, key)                  \
    hlist_for_each_entry(obj, &name[hash_min(key, HASH_BITS(name))], member)

The table is a plain array of 2bits buckets whose size is fixed when it is declared. DEFINE_HASHTABLE() defines and initializes a static table, and DECLARE_HASHTABLE() embeds one in a structure, to be set up with hash_init(). The key must be an integer. hash_min() picks the 32- or 64-bit multiplicative hash from include/linux/hash.h, which multiplies by a constant derived from the golden ratio (0x61C88647 for 32 bits) and keeps the top bits bits of the product. A key built from a string or a structure must first be reduced to an integer by the caller. hash_for_each_possible() visits every object in the key's bucket, not only the matching ones, so the loop body must compare the full key itself. The table has no lock: the caller supplies one, or uses the _rcu variants (hash_add_rcu(), hash_for_each_possible_rcu()) for lockless readers, exactly as with the RCU list functions of Section 6.6. The cgroup core's css_set_table is one, used to find an existing css_set that a task can share instead of allocating a new one (Chapter 25, Section 5.2). The workqueue code keeps its unbound worker pools in another, keyed by a hash of their attributes. When the number of entries cannot be bounded in advance, a fixed table degrades into long chains. The resizable, RCU-safe rhashtable (lib/rhashtable.c) grows and shrinks in the background instead, and System V IPC uses one to map keys to objects (Chapter 19, Section 3.1).

Notifier Chains

Many events in one subsystem concern code elsewhere that the first subsystem should not need to know about: a network interface going down, the system about to reboot or panic, a module being loaded, a CPU changing frequency. A notifier chain (include/linux/notifier.h, kernel/notifier.c) is a publish-subscribe list for such events. A subscriber registers a struct notifier_block, and the publisher calls every registered block in priority order, passing an event code and a pointer to event data:

/* include/linux/notifier.h:54 */
struct notifier_block {
    notifier_fn_t notifier_call;   /* int (*)(struct notifier_block *,
                                              unsigned long, void *) */
    struct notifier_block __rcu *next;
    int priority;                  /* higher runs earlier */
};

/* include/linux/notifier.h:185 */
#define NOTIFY_DONE         0x0000      /* Don't care */
#define NOTIFY_OK           0x0001      /* Suits me */
#define NOTIFY_STOP_MASK    0x8000      /* Don't call further */
#define NOTIFY_BAD          (NOTIFY_STOP_MASK|0x0002)
#define NOTIFY_STOP         (NOTIFY_OK|NOTIFY_STOP_MASK)

Registration inserts the block in descending priority order, and notifier_call_chain() walks the list, calling each block until one returns a value with NOTIFY_STOP_MASK set. A subscriber can therefore veto an event by returning NOTIFY_BAD, and notifier_from_errno() and notifier_to_errno() carry an error code through the return value. The walk function takes no lock itself. The four kinds of chain differ in how they protect the walk against concurrent registration, and therefore in the context in which the callbacks run:

  • Atomic (ATOMIC_NOTIFIER_HEAD). The walk runs under rcu_read_lock(), registration takes a spinlock, and unregistration waits for an RCU grace period. The chain may be called from interrupt or other atomic context, and its callbacks must not sleep. panic_notifier_list is atomic, as is die_chain, which notify_die() calls on a kernel-mode trap (Chapter 4, Section 6.9).
  • Blocking (BLOCKING_NOTIFIER_HEAD). The walk holds a read-write semaphore for reading, so callbacks run in process context and may sleep. reboot_notifier_list is blocking, as is module_notify_list, which announces module state changes (Appendix B, Section 4.2).
  • Raw (RAW_NOTIFIER_HEAD). There is no protection at all, and the caller provides its own. The network-device chain netdev_chain is raw and is only registered on and called under the RTNL lock.
  • SRCU (SRCU_NOTIFIER_HEAD, 2.6.19). The walk is an SRCU read-side section, so callbacks may sleep, and readers pay almost nothing. Unregistration takes a mutex and waits for an SRCU grace period. This suits chains that are called often but rarely change, such as cpufreq_transition_notifier_list.

The four kinds date from Linux 2.6.17 (SRCU from 2.6.19). Before that, every chain shared one global read-write lock for registration and the walk took no lock at all, so nothing told a subscriber what context its callback would run in. Notifier chains remain convenient but opaque. The publisher cannot see who is listening, the order depends on priorities chosen independently by each subscriber, and when a callback vetoes partway through, the subscribers already called must be unwound by hand. Where the order of callbacks matters, the kernel has moved away from them. CPU hotplug used notifier chains until Linux 4.10 removed the last of the old registration functions in favor of the hotplug state machine, in which each subsystem registers a numbered startup and teardown step with cpuhp_setup_state() and the core runs the steps in a fixed order, and in reverse when a CPU goes down.

The Process List and Organizational Structures

Allocating a descriptor for each process is only half the job; the kernel must also be able to find processes quickly, and along several different axes at once. It needs to walk every task in the system (for /proc, accounting, or the OOM killer), pick the best runnable task on a CPU (scheduling), navigate the parent/child tree (wait(), reparenting, signals), and put a task to sleep on a specific event and wake it later. No single data structure serves all of these, so a task_struct is threaded through many of them simultaneously — the global process list, per-CPU run queues, the parent/child/sibling tree, thread-group and PID lists, and per-event wait queues. This section walks through those organizational structures, the global tasklist_lock that guards the process tree, and the per-process resource limits that bound what each task may consume.

The Process List

The first example of a doubly linked list in the kernel is the process list, which links together all existing process descriptors. Each task_struct includes a tasks field of type list_head:

/* include/linux/sched.h:954 */
struct list_head tasks;

The prev and next fields of this list_head point to the tasks field of the previous and next task_struct in the list, respectively. The head of the process list is the init_task descriptor — the process descriptor of process 0 (the swapper or idle task). The tasks.prev field of init_task points to the tasks field of the most recently inserted process.

The SET_LINKS and REMOVE_LINKS macros from Linux 2.6 no longer exist. Instead, the kernel uses list_add_tail() to insert a new process into the list during copy_process(), and list_del_rcu() to remove it during release_task():

/* kernel/fork.c — in copy_process() */
list_add_tail_rcu(&p->tasks, &init_task.tasks);

/* kernel/exit.c — in release_task() → __exit_signal() */
list_del_rcu(&tsk->tasks);

The _rcu variants are used because the process list can be traversed under RCU protection without holding tasklist_lock, allowing lockless readers (e.g., /proc filesystem scanning).

tasklist_lock deserves an introduction, since it recurs throughout this chapter. It is a single global reader-writer spinlock (kernel/fork.c: __cacheline_aligned DEFINE_RWLOCK(tasklist_lock)) that protects the process tree and its associated lists — the tasks list, the children/sibling links, the parent/real_parent pointers, thread-group membership, and the ptraced lists. The rules are:

  • Writers (copy_process() adding a task, release_task() removing one, reparent paths, ptrace attach/detach) take write_lock_irq(&tasklist_lock), giving them exclusive access to mutate the tree.
  • Readers that need a stable snapshot of the tree (signal delivery to a group, wait() scanning children, many /proc paths) take read_lock(&tasklist_lock); many readers may proceed in parallel.
  • RCU readers can often skip the lock entirely — because insertion and removal use the _rcu list primitives and the descriptors are freed only after a grace period, a walk under rcu_read_lock() sees a consistent list without blocking writers at all.

Being one global lock, tasklist_lock is deliberately taken for short, well-defined critical sections; the shift of hot read paths (like /proc enumeration) to RCU is what keeps it from becoming a scalability bottleneck on large systems.

Iterating over the Process List

The for_each_process() macro scans the entire process list:

/* include/linux/sched/signal.h:639 */
#define for_each_process(p) \
    for (p = &init_task ; (p = next_task(p)) != &init_task ; )

The macro starts at init_task and follows the tasks.next pointers until it wraps back to init_task. At each iteration, p points to the currently scanned process descriptor. The next_task() helper is simply list_entry(p->tasks.next, struct task_struct, tasks).

To iterate over all threads in all processes, use the nested for_each_process_thread():

/* include/linux/sched/signal.h:662 */
#define for_each_process_thread(p, t) \
    for_each_process(p) for_each_thread(p, t)

This is a double loop: the outer loop iterates over process group leaders via the tasks list, and the inner for_each_thread() iterates over the thread group's thread_head list (using thread_node in each task_struct). Note that because this is a double loop, a break statement only exits the inner loop — a common pitfall.

These iteration macros are used in /proc filesystem implementations, the OOM killer, signal delivery to process groups, and debugging tools. They require either the tasklist_lock (read side) or RCU read-side protection for safe traversal.

The Lists of TASK_RUNNING Processes

When looking for a new process to run on a CPU, the kernel considers only the runnable processes — those in the TASK_RUNNING state. How these processes are organized has changed dramatically between Linux 2.6 and 7.0.12.

The Linux 2.6 Approach: The O(1) Scheduler

Earlier Linux versions put all runnable processes in a single list called the runqueue. Because it was too costly to maintain this list in priority order, the scheduler had to scan the entire list to find the best runnable process — an O(n) operation.

Linux 2.6 solved this by splitting the runqueue into 140 per-priority linked lists, one for each priority level (0–139). Each task_struct included a run_list field of type list_head that linked it into the list for its priority level. A prio_array_t data structure held all 140 lists plus a bitmap:

Table 3-8. The fields of the prio_array_t data structure (Linux 2.6)

unsigned long [5]bitmapPriority bitmap: bit k is set iff priority list k is non-empty
struct list_head [140]queueThe 140 heads of the per-priority lists

Inserting a process was O(1):

/* Linux 2.6 enqueue_task — equivalent */
list_add_tail(&p->run_list, &array->queue[p->prio]);
__set_bit(p->prio, array->bitmap);
array->nr_active++;
p->array = array;

Finding the highest-priority runnable process was also O(1): the scheduler called sched_find_first_bit() on the bitmap to find the highest-priority non-empty list, then picked the first entry. On multiprocessor systems, each CPU had its own runqueue (its own set of 140 lists), avoiding lock contention.

Linux 7.0.12: Per-CPU Run Queues and Scheduler Classes

The modern kernel has replaced the monolithic runqueue with a layered design. Each CPU has a per-CPU run queue (struct rq, defined in kernel/sched/sched.h), which contains sub-runqueues for each scheduling class:

CFS/EEVDF: The Red-Black Tree

The CFS (Completely Fair Scheduler) sub-runqueue, enhanced with the EEVDF (Earliest Eligible Virtual Deadline First) algorithm, organizes runnable tasks in a red-black tree (struct rb_root_cached) keyed by virtual deadline:

    unsigned int            nr_queued;     /* Number of queued entities */

    struct sched_entity     *curr;         /* Currently running entity */
    /* ... */
};

Each sched_entity contains an rb_node for insertion into the tree, plus scheduling state:

/* include/linux/sched.h:575 — struct sched_entity (key fields) */

    struct load_weight  load;          /* Task weight (derived from nice) */
    struct rb_node      run_node;      /* RB-tree node */
    u64                 deadline;      /* Virtual deadline */
    u64                 vruntime;      /* Virtual runtime consumed */
    s64                 vlag;          /* Virtual lag (fairness tracking) */
    u64                 slice;         /* Time slice for this entity */
    unsigned char       on_rq;         /* Currently on the runqueue? */
    /* ... */
};

Enqueuing a task inserts its sched_entity into the red-black tree:

/* kernel/sched/fair.c:914 */
static void __enqueue_entity(struct cfs_rq *cfs_rq, struct sched_entity *se)
{
    sum_w_vruntime_add(cfs_rq, se);
    se->min_vruntime = se->vruntime;
    se->min_slice = se->slice;
    rb_add_augmented_cached(&se->run_node, &cfs_rq->tasks_timeline,
                            __entity_less, &min_vruntime_cb);
}

The tree is ordered by virtual deadline (__entity_less() compares deadline), and each node is augmented with the smallest vruntime in its subtree (min_vruntime). EEVDF may only pick an eligible entity — one that has not received more than its fair share — so pick_eevdf() first tries the cached leftmost node, which wins in O(1) if it is eligible; otherwise it descends the tree, using the augmented min_vruntime values to skip subtrees with no eligible entity, and finds the eligible entity with the earliest deadline in O(log n). Insertion and removal are O(log n) as well — slower than the 2.6 O(1) scheduler's list operations, but EEVDF provides much better fairness and latency guarantees.

Real-Time: The Priority Array

The RT sub-runqueue retains a design similar to 2.6's prio_array_t, but with 100 priority levels (0–99) instead of 140:

/* kernel/sched/sched.h:311 */
struct rt_prio_array {
    DECLARE_BITMAP(bitmap, MAX_RT_PRIO+1);  /* 100 priorities + delimiter */
    struct list_head queue[MAX_RT_PRIO];     /* Per-priority linked lists */
};

struct rt_rq {
    struct rt_prio_array active;
    unsigned int         rt_nr_running;
    /* ... */
};

For RT tasks, finding the highest-priority runnable task is still O(1): scan the bitmap for the first set bit, then take the head of that priority's list. SCHED_FIFO tasks run until they voluntarily yield or are preempted by a higher-priority task; SCHED_RR tasks rotate within their priority level after their time slice expires.

Deadline: Another Red-Black Tree

The deadline sub-runqueue also uses a red-black tree, but keyed by absolute deadline rather than virtual deadline:

/* kernel/sched/sched.h:866 */
struct dl_rq {
    struct rb_root_cached root;             /* RB-tree ordered by deadline */
    unsigned int          dl_nr_running;
    /* ... */
};

SCHED_DEADLINE tasks specify a runtime budget, period, and deadline. The kernel uses Earliest Deadline First (EDF) scheduling with CBS (Constant Bandwidth Server) admission control to guarantee that deadline tasks receive their bandwidth without starving other tasks.

The Parent/Child Hierarchy

Processes 0 and 1 are created by the kernel during boot. Process 0 (the swapper or idle task) is the ancestor of all kernel threads. Process 1 (init, typically systemd on modern systems) is the ancestor of all user-space processes.

When a process creates children with fork() or clone(), each child's real_parent and parent are set to the creating process. The child is added to the parent's children list via list_add_tail(&child->sibling, &parent->children). The result is a process tree — visible via pstree(1) — rooted at init.

Consider a scenario where process P0 successively creates P1, P2, and P3, and P3 in turn creates P4:

                P0
              / | \
            P1  P2  P3
                     |
                    P4
  • P0's children list contains P1, P2, and P3 (linked through their sibling fields, in creation order).
  • P3's children list contains P4.
  • P1, P2, P3 are siblings: P1's sibling.next points to P2's sibling, and P2's sibling.next points to P3's sibling.
  • P4's real_parent and parent both point to P3.

The Distinction Between real_parent and parent

For most processes, real_parent == parent. They diverge only when ptrace is involved:

  1. A debugger calls ptrace(PTRACE_ATTACH, pid) (or PTRACE_SEIZE) to attach to a target process P.
  2. The kernel sets P->parent to the debugger's task_struct, so the debugger receives SIGCHLD and can wait() on P.
  3. P->real_parent remains unchanged — it still points to P's biological parent.
  4. P is added to the debugger's ptraced list via P->ptrace_entry.
  5. When the debugger detaches (or exits), P->parent is restored to P->real_parent.

This two-pointer design ensures that the biological parent can always reclaim the child after the debugger is done.

The tree must also survive the death of an interior node. When a process exits while it still has children, those children are reparented: in Linux 2.6 always to init, in 7.0.12 to another live thread of the dying process, else to the nearest ancestor that has declared itself a child subreaper with prctl(PR_SET_CHILD_SUBREAPER, 1) (as service managers such as systemd do), else to the init of the child's PID namespace. "Reparenting: What Happens When a Parent Dies" in "Destroying Processes" walks through find_new_reaper() step by step.

How Processes Are Organized

The state of a process (Table 3-1 in "Process State") determines how the kernel keeps track of it. Processes fall into three categories:

  • Run queues — Processes in TASK_RUNNING state are grouped in per-CPU run queues. Each scheduler class (CFS/EEVDF, RT, Deadline, etc.) maintains its own sub-queue within the per-CPU struct rq. The transitional states TASK_WAKING and TASK_NEW are also associated with the run queue infrastructure — TASK_WAKING means the process is being migrated to a run queue by try_to_wake_up(), and TASK_NEW means it was just created by copy_process() and has not yet been enqueued for the first time. See "The Lists of TASK_RUNNING Processes" above for the full scheduler class hierarchy.
  • Wait queues — Processes in TASK_INTERRUPTIBLE, TASK_UNINTERRUPTIBLE, or one of the compound sleeping states (TASK_KILLABLE, TASK_IDLE, TASK_FREEZABLE combinations) are subdivided into many classes, each corresponding to a specific event. The process state alone does not provide enough information to retrieve them quickly, so they are placed on wait queues associated with the event they are waiting for. The TASK_RTLOCK_WAIT state is similar but uses a specialized RT-mutex wait mechanism rather than a general wait queue. TASK_FROZEN processes are managed by the freezer subsystem during suspend/hibernate.
  • No specific list — Processes in TASK_STOPPED, TASK_TRACED, EXIT_ZOMBIE, EXIT_DEAD, TASK_DEAD, or TASK_PARKED state are not linked in dedicated lists. There is no need to group them: stopped and traced processes are accessed via PID or via the children/ptraced lists of a particular parent; zombie and dead processes are found through the parent's children list when the parent calls wait(); and parked kthreads are managed individually by kthread_park()/kthread_unpark().

Wait Queues

Wait queues have several uses in the kernel, particularly for interrupt handling, process synchronization, and timing. A process must often wait for some event to occur — a disk operation to complete, a system resource to be released, or a fixed interval of time to elapse. Wait queues implement conditional waits on events: a process wishing to wait for a specific event places itself in the proper wait queue and relinquishes the CPU. When the event occurs, the kernel wakes up the processes in the corresponding wait queue.

Wait queues are implemented as doubly linked lists whose elements include pointers to process descriptors. Each wait queue is identified by a wait queue head:

/* include/linux/wait.h:35 */
struct wait_queue_head {
    spinlock_t      lock;
    struct list_head head;
};
typedef struct wait_queue_head wait_queue_head_t;

Because wait queues are modified by interrupt handlers as well as by major kernel functions, the doubly linked list must be protected from concurrent accesses. Synchronization is achieved by the lock spinlock in the wait queue head. The head field is the head of the list of waiting processes.

Elements of a wait queue list are of type wait_queue_entry:

/* include/linux/wait.h:28 */
struct wait_queue_entry {
    unsigned int        flags;
    void                *private;       /* Usually points to task_struct */
    wait_queue_func_t   func;           /* Wake-up function */
    struct list_head    entry;          /* Links into wait_queue_head.head */
};

Each element represents a sleeping process. The private field stores the process descriptor pointer (in Linux 2.6 this field was called task and was explicitly typed as struct task_struct *; in 7.0.12 it is a void * for flexibility). The func field stores the address of the wake-up function to call when the event occurs.

Exclusive and Non-Exclusive Processes

It is not always convenient to wake up all sleeping processes in a wait queue. For instance, if two or more processes are waiting for exclusive access to a resource, it makes sense to wake up just one process. This process takes the resource, while the others continue to sleep. (Waking all of them would cause a problem known as the thundering herd: multiple processes wake up only to race for a resource that can be accessed by one of them, with all but one having to go back to sleep.)

Thus, there are two kinds of sleeping processes:

  • Exclusive processes (denoted by WQ_FLAG_EXCLUSIVE in the flags field) are selectively woken up by the kernel — typically only one at a time.
  • Non-exclusive processes (no WQ_FLAG_EXCLUSIVE flag) are always woken up when the event occurs.

The flags available in Linux 7.0.12 are:

/* include/linux/wait.h:19 */
#define WQ_FLAG_EXCLUSIVE  0x01   /* Wake only one exclusive waiter */
#define WQ_FLAG_WOKEN      0x02   /* Was woken up */
#define WQ_FLAG_CUSTOM     0x04   /* Custom wake function, skip bookkeeping */
#define WQ_FLAG_DONE       0x08   /* Callback ran and finished */
#define WQ_FLAG_PRIORITY   0x10   /* Insert at head of queue (high priority) */

The WQ_FLAG_PRIORITY flag is new in modern kernels — it allows a waiter to be inserted at the front of the queue, ahead of other non-exclusive waiters. This is used by the kernel's priority-aware subsystems.

Non-exclusive processes are always placed at the beginning of the wait queue list, while exclusive processes are placed at the end. When the kernel wakes up the queue, it walks the list from head to tail, waking all non-exclusive processes first, then waking one (or more) exclusive processes. This ordering guarantees that non-exclusive waiters always get woken.

Putting a Process to Sleep

The old way (Linux 2.6): sleep_on() — deprecated and removed. In 2.6, the sleep_on() function put the current process to sleep:

/* Linux 2.6 — sleep_on() (simplified) */
void sleep_on(wait_queue_head_t *wq)
{
    wait_queue_t wait;
    init_waitqueue_entry(&wait, current);
    current->state = TASK_UNINTERRUPTIBLE;
    add_wait_queue(wq, &wait);
    schedule();
    remove_wait_queue(wq, &wait);
}

This was a well-known source of race conditions: between setting the state and calling schedule(), the event could occur and the wake-up could be lost. The sleep_on() family has been removed entirely from Linux 7.0.12.

The prepare/finish pattern: A safer approach (introduced in 2.6, still used in 7.0.12) separates preparation from sleeping:

DEFINE_WAIT(wait);
prepare_to_wait_exclusive(&wq, &wait, TASK_INTERRUPTIBLE);
if (!condition)
    schedule();
finish_wait(&wq, &wait);

prepare_to_wait() sets the process state and inserts the entry into the wait queue atomically (under the wait queue lock). finish_wait() sets the state back to TASK_RUNNING and removes the entry from the queue. The DEFINE_WAIT macro initializes the entry with autoremove_wake_function(), which automatically removes the entry from the queue when woken — an important safeguard.

The modern way: wait_event*() macros. The recommended API in Linux 7.0.12 wraps the entire sleep loop into a single macro:

/* include/linux/wait.h — ___wait_event() core (simplified) */

({                                                                     \

The wake_up macro is essentially:

void wake_up(wait_queue_head_t *q)
{
    struct wait_queue_entry *curr;
    list_for_each_entry(curr, &q->head, entry) {
        if (curr->func(curr, TASK_NORMAL, 0, NULL)
            && (curr->flags & WQ_FLAG_EXCLUSIVE))
            break;
    }
}

The loop walks the wait queue list from head to tail. For each entry, it calls the wake-up function (func). If the function returns 1 (process was actually woken) and the entry is exclusive, the loop breaks. Because non-exclusive processes are always at the beginning and exclusive processes at the end, this ensures that all non-exclusive processes are woken, followed by at most one exclusive process.

Process Resource Limits

Each process has an associated set of resource limits, which specify the amount of system resources it can use. These limits keep a user from overwhelming the system (its CPU, disk space, and so on).

The resource limits for the current process are stored in current->signal->rlim[] — that is, in a field of the process's signal descriptor (see Chapter 11). The field is an array of elements of type struct rlimit, one for each resource limit:

/* include/uapi/linux/resource.h */
struct rlimit {
    unsigned long rlim_cur;
    unsigned long rlim_max;
};

The rlim_cur field is the current (soft) resource limit for the resource. For example, current->signal->rlim[RLIMIT_CPU].rlim_cur represents the current limit on the CPU time of the running process.

The rlim_max field is the maximum (hard) allowed value for the resource limit. By using the getrlimit() and setrlimit() system calls, a user can always increase the rlim_cur limit of some resource up to rlim_max. However, only the superuser (or, more precisely, a process that has the CAP_SYS_RESOURCE capability) can increase the rlim_max field or set the rlim_cur field to a value greater than the corresponding rlim_max field.

Most resource limits contain the value RLIM_INFINITY (0xffffffffffffffff on 64-bit systems), which means that no user limit is imposed on the corresponding resource (of course, real limits exist due to kernel design restrictions, available RAM, available space on disk, etc.). However, the system administrator may choose to impose stronger limits on some resources. Whenever a user logs into the system, the kernel creates a process owned by the superuser, which can invoke setrlimit() to decrease the rlim_max and rlim_cur fields for a resource. The same process later executes a login shell and becomes owned by the user. Each new process created by the user inherits the content of the rlim array from its parent, and therefore the user cannot override the limits enforced by the administrator.

Changes Since Linux 2.6

Three resource limits are new compared to the 2.6 kernel:

  • RLIMIT_NICE (13): Controls the minimum nice value (highest priority) a non-privileged process can set. The actual nice limit is computed as 20 - rlim_cur. For example, a value of 1 means the process can set nice to 19 (lowest priority); a value of 40 means it can set nice to -20 (highest priority).
  • RLIMIT_RTPRIO (14): Controls the maximum real-time priority an unprivileged process can request via sched_setscheduler() or sched_setattr(). A value of 0 means the process cannot use RT scheduling policies.
  • RLIMIT_RTTIME (15): Sets a CPU time budget (in microseconds) for RT-scheduled processes. If a process running under SCHED_FIFO or SCHED_RR consumes more than this amount without voluntarily relinquishing the CPU, the kernel sends SIGXCPU at the soft limit and SIGKILL at the hard limit. This is a safety net against RT tasks that enter infinite loops.

The prlimit() System Call

Linux 2.6 provided only getrlimit() and setrlimit(), which operate on the calling process's own limits. Linux 7.0.12 adds the prlimit64() system call (available since 2.6.36), which can get and set resource limits of any process identified by PID:

/* kernel/sys.c */
SYSCALL_DEFINE4(prlimit64, pid_t, pid, unsigned int, resource,
                const struct rlimit64 __user *, new_rlim,
                struct rlimit64 __user *, old_rlim)

The caller must have CAP_SYS_RESOURCE capability to raise hard limits on another process. The kernel also performs a Spectre-safe array bounds check on the resource index using array_index_nospec() — a hardening measure not present in 2.6.

Limits are inherited across fork() and preserved across exec(). They apply per process (per thread group, since rlim lives in signal_struct) for most limits, but four are checked against a per-user total: RLIMIT_NPROC, RLIMIT_SIGPENDING, RLIMIT_MSGQUEUE, and RLIMIT_MEMLOCK (for memory locked through shmctl(SHM_LOCK) and SHM_HUGETLB/hugetlbfs, via user_shm_lock(); ordinary mlock() is still counted per process). In 2.6 these totals lived in the global struct user_struct; since 5.14 they are kept in struct ucounts (UCOUNT_RLIMIT_*), which counts per user per user namespace and charges every ancestor namespace too, so the same UID inside two containers no longer shares one counter (see "ucounts: Preventing Namespace Exhaustion" in "Namespaces and Container Identity").

Process Switch

A process switch (context switch) is the act of suspending the currently running process on a CPU and resuming a different one. It is one of the most performance-critical operations in the kernel. Linux 7.0.12 performs context switches through context_switch() in kernel/sched/core.c, which orchestrates:

  1. Memory-management context switch (switch_mm())
  2. Register context switch (switch_to())

Hardware Context

While each process can have its own address space, all processes have to share the CPU registers. So before resuming the execution of a process, the kernel must ensure that each such register is loaded with the value it had when the process was suspended.

The set of data that must be loaded into the registers before the process resumes its execution on the CPU is called the hardware context. The hardware context is a subset of the process execution context, which includes all information needed for the process execution. In Linux, a part of the hardware context of a process is stored in the process descriptor, while the remaining part is saved on the Kernel Mode stack.

In the description that follows, we assume the prev local variable refers to the process descriptor of the process being switched out and next refers to the one being switched in to replace it. We can thus define a process switch as the activity consisting of saving the hardware context of prev and replacing it with the hardware context of next. Because process switches occur quite often, it is important to minimize the time spent in saving and loading hardware contexts.

Process switching occurs only in Kernel Mode. The contents of all registers used by a process in User Mode have already been saved on the Kernel Mode stack before performing process switching (see Chapter 4). This includes the User Mode stack pointer.

Historical: Hardware Context Switching (i386)

Old versions of Linux (before 2.6) took advantage of the hardware support offered by the x86 architecture and performed a process switch through a far jmp instruction to the selector of the Task State Segment Descriptor of the next process. While executing this instruction, the CPU performs a hardware context switch by automatically saving the old hardware context and loading a new one. Linux 2.6 moved to software context switching for the following reasons:

  • Step-by-step switching performed through a sequence of mov instructions allows better control over the validity of the data being loaded. In particular, it is possible to check the values of the segmentation registers, which might have been forged by a malicious user. This type of checking is not possible when using a single far jmp instruction.
  • The amount of time required by the old approach and the new approach is about the same. However, it is not possible to optimize a hardware context switch, while there is room for improving the current software switching code.

Linux 7.0.12 continues to use software context switching on all architectures.

Task State Segment (x86_64)

Although Linux doesn't use the TSS for hardware context switches, it is still forced to set up a TSS for each CPU in the system. This is done for two reasons:

  1. Kernel stack pointer on privilege change: When an x86_64 CPU switches from User Mode to Kernel Mode (via a system call or interrupt), it fetches the Kernel Mode stack pointer (RSP0) from the TSS. The hardware reads tss.sp0 automatically — the kernel must keep this updated on every context switch.
  2. I/O Permission Bitmap: When a User Mode process attempts to access an I/O port by means of an in or out instruction, the CPU checks the I/O Permission Bitmap stored in the TSS to verify whether the process is allowed to access the port. If the IOPL field in RFLAGS does not grant access, the CPU falls back to checking the bitmap.

In Linux 7.0.12, the TSS is defined as a per-CPU structure:

/* arch/x86/include/asm/processor.h */
struct tss_struct {
    struct x86_hw_tss   x86_tss;       /* Fixed hardware portion */
    struct x86_io_bitmap io_bitmap;    /* I/O permission bitmap */
} __aligned(PAGE_SIZE);

DECLARE_PER_CPU_PAGE_ALIGNED(struct tss_struct, cpu_tss_rw);

struct x86_hw_tss {
    u32   reserved1;
    u64   sp0;              /* Kernel stack pointer for ring 0 */
    u64   sp1;
    u64   sp2;              /* Reused by entry_SYSCALL_64 as scratch */
    u64   reserved2;
    u64   ist[7];           /* Interrupt Stack Table (7 dedicated stacks) */
    u32   reserved3;
    u32   reserved4;
    u16   reserved5;
    u16   io_bitmap_base;   /* Offset to I/O permission bitmap */
} __attribute__((packed));

Unlike the original Intel design where each process had its own TSS, Linux uses one TSS per CPU. At each process switch, the kernel updates the sp0 field of the TSS so that the CPU can correctly switch to the new process's kernel stack on the next entry to kernel mode. The IST (Interrupt Stack Table) entries provide dedicated stacks for critical interrupts (NMI, double fault, machine check, etc.) — these are not changed during normal context switches.

The io_bitmap_base field points to the I/O permission bitmap within the TSS. Linux 7.0.12 optimizes this with a "lazy" approach: the bitmap is only loaded into the TSS when a process that uses I/O permissions is scheduled in. For processes that do not use I/O ports, io_bitmap_base is set to a value beyond the TSS limit, causing any in/out instruction to immediately raise a #GP (General Protection) exception.

On ARM64, there is no TSS equivalent. The kernel stack pointer is stored in SP_EL1, and privilege transitions are handled by the exception vector mechanism rather than segment-based lookups.

The thread Field

At every process switch, the hardware context of the process being replaced must be saved somewhere. It cannot be saved on the TSS, as in the original Intel design, because Linux uses a single TSS for each processor, not one for every process. Instead, each process descriptor includes a field called thread of type struct thread_struct, in which the kernel saves the hardware context whenever the process is being switched out.

On x86_64 (arch/x86/include/asm/processor.h):

Note that general-purpose registers (rax, rbx, rcx, etc.) are not stored in thread_struct — they are saved on the Kernel Mode stack by the scheduler entry code and exception handlers. The thread_struct stores only those registers that need special handling during context switches: stack pointer, segment bases, debug registers, and extended state.

The floating-point, SSE, AVX, AVX-512, and AMX states are stored in a separate struct fpu that is placed immediately after the task_struct in memory. This state is managed by the XSAVE/XRSTOR instruction family. Saving is eager — switch_fpu() saves the outgoing task's registers on every switch away from a user task — but restoring is deferred: the incoming task is marked TIF_NEED_FPU_LOAD and its registers are reloaded only on the way back to user mode, so a kernel thread or a task that switches out again before returning to user space never pays for an XRSTOR (see "Saving and Restoring FPU/SIMD State" below).

Performing the Process Switch

A process switch may occur at just one well-defined point: the schedule() function, which is discussed at length in Chapter 7. Here, we are only concerned with how the kernel performs a process switch.

Essentially, every process switch consists of two steps:

  1. Switching the address space: Loading the new process's Page Global Directory (PGD) into the hardware page table register (CR3 on x86_64, TTBR0_EL1 on ARM64). This is described in Chapter 9.
  2. Switching the hardware context: Saving the current CPU registers and kernel stack pointer for prev, and restoring those of next. This is the heart of the context switch.

We assume that prev points to the descriptor of the process being replaced, and next to the descriptor of the process being activated. Both are local variables of the schedule() function.

The switch_to Macro and the "Three-Process" Problem

The register context switch is performed by the switch_to macro. It has three parameters — prev, next, and last — and the third requires careful explanation.

In any process switch, three processes are involved, not just two. Consider this scenario:

  1. The kernel switches off process A to activate process B. In schedule(), prev = A and next = B. As soon as switch_to deactivates A, the execution flow of A freezes.
  2. Much later, the kernel wants to reactivate A. At that point, some other process C is running. The kernel executes switch_to with prev = C and next = A.
  3. When A resumes, it finds its old kernel stack exactly as it left it — with the local variables prev = A and next = B. But the scheduler needs to know which process was just replaced (C, not A), so it can complete C's bookkeeping (e.g., free C's task_struct if C was exiting).

The last output parameter solves this: the macro arranges for A's prev variable to be overwritten with C's descriptor after A resumes. In the current implementation, switch_to(prev, next, prev) writes the return value into prev, so after A wakes up, prev points to C. This value is then passed to finish_task_switch(prev).

On x86_64, the macro is a thin wrapper:

/* arch/x86/include/asm/switch_to.h:49 */
#define switch_to(prev, next, last)                          \
do {                                                         \
    ((last) = __switch_to_asm((prev), (next)));              \
} while (0)

The return value of __switch_to_asm() (carried in %rax) is the descriptor of the process that was just replaced — this becomes last.

The __switch_to_asm() Function (x86_64)

__switch_to_asm() is the assembly core of the context switch, defined in arch/x86/entry/entry_64.S. It performs three critical operations: saving the old stack, switching to the new stack, and jumping to the C function that handles everything else.

SYM_FUNC_START(__switch_to_asm)
    /* 1. Save callee-saved registers on prev's kernel stack. */
    pushq   %rbp
    pushq   %rbx
    pushq   %r12
    pushq   %r13
    pushq   %r14
    pushq   %r15

    /* 2. Switch stacks.
     *    %rdi = prev task_struct, %rsi = next task_struct. */
    movq    %rsp, TASK_threadsp(%rdi)    /* prev->thread.sp = rsp */
    movq    TASK_threadsp(%rsi), %rsp    /* rsp = next->thread.sp */

    /* 3. Update the stack canary (CONFIG_STACKPROTECTOR). */
    movq    TASK_stack_canary(%rsi), %rbx
    movq    %rbx, PER_CPU_VAR(__stack_chk_guard)

    /* 4. Fill the RSB to mitigate Spectre v2. */
    FILL_RETURN_BUFFER %r12, RSB_CLEAR_LOOPS, X86_FEATURE_RSB_CTXSW

    /* 5. Restore callee-saved registers from next's kernel stack. */
    popq    %r15
    popq    %r14
    popq    %r13
    popq    %r12
    popq    %rbx
    popq    %rbp

    /* 6. Jump (not call) to __switch_to() — the return address
     *    is already on next's stack from a previous switch. */
    jmp     __switch_to
SYM_FUNC_END(__switch_to_asm)

The stack switch is the single most important instruction in the entire process switch — it happens at step 2. After movq TASK_threadsp(%rsi), %rsp, the kernel is executing on next's kernel stack. Everything that follows (the pop instructions, the jmp) operates on next's stack, restoring the state that was pushed there when next was previously switched out.

The pushed registers form a struct inactive_task_frame on the stack:

struct inactive_task_frame {
    unsigned long r15, r14, r13, r12;
    unsigned long bx;
    unsigned long bp;
    unsigned long ret_addr;   /* Return address from the previous switch_to call */
};

Step 4 (RSB filling) is a Spectre v2 mitigation not present in Linux 2.6. When switching from a shallower to a deeper call stack, the CPU's Return Stack Buffer may contain stale entries from user space. Overwriting it with safe kernel return addresses prevents speculative execution of attacker-controlled targets.

Step 6 uses jmp instead of call because the return address is already on the stack — it's the ret_addr field of inactive_task_frame, placed there during next's previous switch. When __switch_to() executes ret, it returns directly to the context_switch() caller.

ARM64 is simpler than x86_64 because there are no segment registers, no TSS, and no I/O permission bitmaps. The stp/ldp (store pair / load pair) instructions efficiently save and restore two 64-bit registers at a time.

switch_mm: Memory Context Switch

x86_64: switch_mm() loads the new process's PGD into CR3. With PCID (Process Context ID) support, the kernel tags each address space with a 12-bit PCID to avoid flushing the entire TLB on every switch — only entries for the new PCID need validation. With KPTI (Kernel Page Table Isolation) enabled, each mm has two PGDs — one for kernel mode and one for user mode — and CR3 is loaded with the appropriate one.

ARM64: switch_mm() writes the new process's PGD to TTBR0_EL1 (the user-space translation table base register). ASID (Address Space ID) tagging serves the same role as PCID on x86 — each mm is assigned a unique ASID, and the TLB can hold entries from multiple address spaces simultaneously. TTBR1_EL1 (kernel mappings) is never changed, as it is shared across all processes.

Saving and Restoring FPU/SIMD State

FPU and SIMD state is the largest portion of the hardware context — up to 8 KB with AVX-512, or even larger with Intel AMX (tiles). Its handling has changed significantly since Linux 2.6:

x86_64: Modern kernels use eager FPU save/restore. The XSAVE/XRSTOR instruction family saves and restores all extended register state (FPU, SSE, AVX, AVX-512, AMX) in a single operation. The state is stored in a struct fpu allocated immediately after the task_struct. In Linux 2.6, FPU state was saved lazily: the kernel set the TS flag in CR0 so that the first floating-point instruction after a context switch triggered a #NM (Device Not Available) exception. The exception handler would then save the previous process's FPU state and restore the current one. This optimization avoided saving/restoring FPU state for processes that didn't use floating point, but it added complexity and was incompatible with certain security mitigations. Modern kernels save a user task's FPU state at every switch away from it, via switch_fpu() in step 1 of __switch_to() (arch/x86/include/asm/fpu/sched.h); kernel threads are skipped, and so is a task whose registers were already saved (TIF_NEED_FPU_LOAD set). The restore half is deferred: arch_exit_to_user_mode_prepare() calls switch_fpu_return() only when the task actually heads back to user space, and skips the XRSTOR entirely if the task returns on the same CPU and still owns the registers.

ARM64: the scheme is the same — eager save, deferred restore. fpsimd_thread_switch(), step 1 of __switch_to(), saves the outgoing task's FPSIMD (and SVE/SME) state if it is live in the registers, then sets TIF_FOREIGN_FPSTATE on the incoming task unless the registers on this CPU already hold its state; fpsimd_restore_current_state() reloads them on the way back to user mode. SVE state can be very large (up to 256 bytes per Z register × 32 registers = 8 KB at the maximum vector length, plus predicate registers), so SVE is enabled per task on demand: a task starts without TIF_SVE, its first SVE instruction traps, and only from then on is the full SVE state saved and restored; the kernel may drop it back to plain FPSIMD at a later system call.

Finishing the Switch: prepare_task_switch() and finish_task_switch()

The register swap performed by switch_to() is bracketed by two bookkeeping functions that run in different process contexts — and understanding that asymmetry is the key to the whole switch. prepare_task_switch() runs while prev is still current; finish_task_switch() runs after next has resumed, so it executes on next's kernel stack even though its argument describes the task that was just displaced.

prepare_task_switch() (called at the very top of context_switch(), while still on prev's stack) arms everything the incoming task will need and snapshots the outgoing one:

  • kmap_local_sched_out() — tears down any temporary per-task kernel mappings (they will be re-established on the other side).
  • perf_event_task_sched_out() — stops the outgoing task's performance counters and, for hardware PMUs, saves their contents.
  • rseq_preempt() and sched_info_switch() — flag the restartable-sequence abort and record scheduling statistics.
  • prepare_task(next) — sets next->on_cpu = 1 so that a wakeup on another CPU spins in smp_cond_load_acquire() until the switch completes, preventing a task from running on two CPUs at once.
  • prepare_lock_switch() — hands the runqueue lock's ownership annotation across the switch (see below).

finish_task_switch(prev) is where the loose ends are tied up. Recall from the "three-process" discussion that its prev argument is really last — the descriptor of the process that was actually replaced (process C in the earlier example), recovered from the return value of switch_to(). Creating Processes

Unix operating systems rely heavily on process creation to satisfy user requests. For example, the shell creates a new process whenever the user enters a command. Traditional Unix systems treat all processes the same way: resources owned by the parent process are duplicated in the child process. This approach makes process creation very slow and inefficient, because it requires copying the entire address space of the parent process. The child process rarely needs to read or modify all the resources inherited from the parent; in many cases, it issues an immediate execve() and wipes out the address space that was so carefully copied.

Modern Linux kernels solve this problem with three mechanisms:

  • Copy-on-Write (COW): Both parent and child share the same physical pages with read-only permissions. When either tries to write, the kernel copies only that page. This is fully explained in Chapter 9.
  • Lightweight processes: Both parent and child can share per-process kernel data structures such as page tables, the open file table, and the signal dispositions — controlled by CLONE flags.
  • vfork(): Creates a process that shares the parent’s memory address space. The parent’s execution is blocked until the child exits or executes a new program.

clone3(): The Extensible Interface

The clone3() system call (added in Linux 5.3) takes a versioned struct clone_args from user space, providing an extensible interface that avoids the register-packing limitations of the original clone():

    __aligned_u64 parent_tid;   /* Parent TID pointer */

    __aligned_u64 stack_size;   /* Stack size */

Key advantages of clone3() over clone():

  1. Separate pidfd field: In legacy clone(), CLONE_PIDFD reuses the parent_tid pointer, making it mutually exclusive with CLONE_PARENT_SETTID. clone3() has a dedicated pidfd field.
  2. set_tid array: Specify exact PIDs for the child in each nested PID namespace level. Critical for checkpoint/restore (CRIU).
  3. cgroup field: With CLONE_INTO_CGROUP, the child is placed directly into the specified cgroup at creation time.
  4. CLONE_NEWTIME: Creates a new time namespace, allowing the child to see different values for CLOCK_MONOTONIC and CLOCK_BOOTTIME.
  5. Versioning via size: The kernel checks the size of the user-provided structure, allowing future extensions without breaking backward compatibility.

The kernel_clone() Function

The kernel_clone() function (formerly do_fork() in Linux 2.6, renamed in 5.10) handles all clone(), fork(), and vfork() system calls. All parameters are packed into a single struct kernel_clone_args. Here are its most significant steps:

  1. Validate CLONE_PIDFD: If both CLONE_PIDFD and CLONE_PARENT_SETTID are set and point to the same location, return -EINVAL.
  2. Determine ptrace event: Unless CLONE_UNTRACED is set, determine whether to report PTRACE_EVENT_VFORK, PTRACE_EVENT_CLONE, or PTRACE_EVENT_FORK to the tracer.
  3. Call copy_process(): The workhorse that creates the new task_struct and sets up all kernel data structures.
  4. Record the sched_process_fork tracepoint: Must happen before waking the child.
  5. Get the child’s PID: Call get_task_pid() / pid_vnr() to obtain the PID visible in the caller’s namespace.
  6. Write parent_tid: If CLONE_PARENT_SETTID is set, write the child’s PID to the parent’s user-mode variable.
  7. Set up vfork completion: If CLONE_VFORK is set, initialize a completion structure.
  8. Wake up the child: Call wake_up_new_task(p) to set TASK_RUNNING, select a CPU, and enqueue on the run queue.
  9. Notify the tracer: If the parent is being traced, call ptrace_event_pid().
  10. Wait for vfork: If CLONE_VFORK, block the parent until the child releases its address space.
  11. Return the child’s PID.
/* kernel/fork.c:2612 — simplified */
pid_t kernel_clone(struct kernel_clone_args *args)
{
    u64 clone_flags = args->flags;
    struct completion vfork;
    struct task_struct *p;
    struct pid *pid;
    int trace = 0;
    pid_t nr;

    /* Step 1: validate CLONE_PIDFD */
    if ((clone_flags & CLONE_PIDFD) &&
        (clone_flags & CLONE_PARENT_SETTID) &&
        (args->pidfd == args->parent_tid))
        return -EINVAL;

    /* Step 2: determine ptrace event */
    if (!(clone_flags & CLONE_UNTRACED)) {
        if (clone_flags & CLONE_VFORK)
            trace = PTRACE_EVENT_VFORK;
        else if (args->exit_signal != SIGCHLD)
            trace = PTRACE_EVENT_CLONE;
        else
            trace = PTRACE_EVENT_FORK;
        if (likely(!ptrace_event_enabled(current, trace)))
            trace = 0;
    }

    /* Step 3: create the child */
    p = copy_process(NULL, trace, NUMA_NO_NODE, args);
    if (IS_ERR(p))
        return PTR_ERR(p);

    /* Steps 5-6: get PID, write parent_tid */
    pid = get_task_pid(p, PIDTYPE_PID);
    nr = pid_vnr(pid);
    if (clone_flags & CLONE_PARENT_SETTID)
        put_user(nr, args->parent_tid);

    /* Step 7: set up vfork completion */
    if (clone_flags & CLONE_VFORK) {
        p->vfork_done = &vfork;
        init_completion(&vfork);
        get_task_struct(p);
    }

    /* Step 8: wake the child */
    wake_up_new_task(p);

    /* Step 10: wait for vfork completion */
    if (clone_flags & CLONE_VFORK)
        if (!wait_for_vfork_done(p, &vfork))
            ptrace_event_pid(PTRACE_EVENT_VFORK_DONE, pid);

    put_pid(pid);
    return nr;
}

The wake_up_new_task() Function

After copy_process() returns, the child is in the TASK_NEW state (invisible to the scheduler). wake_up_new_task() in kernel/sched/core.c makes it runnable:

  1. Sets the child’s state to TASK_RUNNING.
  2. Calls select_task_rq() to pick the best CPU for the child.
  3. Enqueues the child on the chosen CPU’s run queue via activate_task().
  4. Calls wakeup_preempt() to check if the child should preempt the current task on that CPU.

In Linux 2.6, wake_up_new_task() tried to force the child to run before the parent if they were on the same CPU and did not share page tables. The idea was that if the child immediately calls exec(), running it first avoids unnecessary COW page faults. Modern kernels leave this decision to the scheduler’s load balancing heuristics.

  1. Allocates a new task_struct from the slab cache (NUMA-aware).
  2. Calls arch_dup_task_struct() to copy the parent’s task_struct (including FPU state on x86).
  3. Allocates a kernel stack. With CONFIG_VMAP_STACK (default on x86_64), this is a virtually-mapped stack with guard pages for overflow detection.

  5. Calls setup_thread_stack() to initialize the thread_info.
  6. Sets the stack canary to a new random value.

  • Checks whether the number of processes owned by the user exceeds RLIMIT_NPROC. If so, returns -EAGAIN (unless the process has CAP_SYS_RESOURCE).
  • Checks that nr_threads does not exceed max_threads (tunable via /proc/sys/kernel/threads-max).
  • Clears PF_SUPERPRIV and sets PF_FORKNOEXEC.
  • Initializes scheduler statistics, timers, and bookkeeping fields to zero.

Calls copy_creds() to duplicate the parent’s credential structure (struct cred). LSM hooks via security_task_alloc() perform additional access control checks.

The key insight is the struct fork_frame, which overlays the inactive_task_frame (callee-saved registers) and pt_regs (full register set) at the top of the kernel stack. Under the tasklist_lock, the function establishes the child’s position in the process hierarchy:

  • If CLONE_PARENT or CLONE_THREAD is set, the child’s real_parent is set to the grandparent (the caller’s parent), making the child a sibling.
  • Otherwise, real_parent is set to current (normal parent-child relationship).
  • If CLONE_THREAD: the child’s exit_signal is set to -1 (only the last thread sends a signal). The child is added to the thread group.

After releasing tasklist_lock: install the pidfd, call sched_post_fork(), cgroup_post_fork(), and emit the task_newtask trace event.

Error Handling: The bad_fork Unwinding Ladder

copy_process() acquires roughly a dozen resources in sequence — credentials, the fd table, the fs context, signal handlers, the memory descriptor, namespaces, the I/O context, a PID, a pidfd, and more. If any step fails, everything acquired before it must be released in reverse order. Rather than nest a dozen levels of if, the kernel uses the classic C goto ladder: each allocation is paired with a bad_fork_cleanup_* label, and a failure jumps to the label matching the last successful step.

This pattern — unchanged in spirit since Linux 2.6 — is the reason copy_process() can be read top-to-bottom as “acquire, acquire, acquire” and bottom-to-top as “release, release, release.”

The vfork() Handshake

vfork() is the one creation path where the parent must block until the child is done with the shared address space. Recall that vfork() passes CLONE_VM | CLONE_VFORK: parent and child share the very same mm_struct, so the child runs on the parent’s memory. Letting both run concurrently would corrupt the parent’s stack, so the kernel serializes them with a completion:

  1. In kernel_clone(), when CLONE_VFORK is set, the parent points p->vfork_done at an on-stack struct completion and takes an extra reference on the child.
  2. After wake_up_new_task(), the parent calls wait_for_vfork_done(), which sleeps in TASK_KILLABLE on that completion.
  3. The child runs until it either calls execve() (which installs a brand-new mm) or exits. Both paths funnel through mm_release(), which detects the non-NULL vfork_done and calls complete_vfork_done() to wake the parent.

Only then does the parent return from vfork(). This is why the child of a vfork() must not return from the calling function or modify any variable other than the pid_t return of vfork() — until it calls execve() or _exit(), it is literally running on the parent’s stack. The same mm_release() path also handles CLONE_CHILD_CLEARTID: it clears the child’s TID word and issues a FUTEX_WAKE, which is the mechanism pthread_join() relies on to detect thread termination.

Copy-on-Write (COW)

When fork() is called without CLONE_VM, the child gets a logical copy of the parent’s address space via dup_mm() → dup_mmap(). Rather than physically duplicating every page, the kernel performs the following:

  1. dup_mm() allocates a new mm_struct, copies the parent’s fields, and calls mm_init() to initialize the new memory descriptor.
  2. dup_mmap() clones the parent’s virtual-memory map. Modern kernels store VMAs in a maple tree (mm->mm_mt) rather than the red-black tree plus vm_next/vm_prev linked list used through Linux 5.x (the list was removed in 6.1). dup_mmap() first calls __mt_dup() to build an identical maple tree in one efficient pass, then iterates the parent’s VMAs with for_each_vma(). For each one it takes a per-VMA write lock (vma_start_write()), skips VM_DONTCOPY regions, gives VM_WIPEONFORK regions a clean slate, duplicates the descriptor with vm_area_dup(), links the child into the parent’s anon-VMA chain via anon_vma_fork(), and finally calls copy_page_range(). It is copy_page_range() that walks the page tables and, for every present writable page, write-protects the PTE in both the parent and the child and bumps the page’s reference count.
  3. When either process later writes to a shared page, a page fault occurs. The fault handler detects the COW condition, allocates a new page frame, copies the contents, and restores write permission for the faulting process.

Because both address spaces are locked and modified together, dup_mmap() runs under mmap_write_lock on the old mm and a nested write lock on the new one. If duplication fails partway through (typically -ENOMEM), the partially built child tree is torn down and the fork is aborted — the parent’s mappings are never disturbed.

This mechanism makes fork() extremely efficient:

  • A fork() followed by exec() (the common case) may never copy a single data page.
  • Even without exec(), only pages that are actually modified get duplicated.
  • The cost of fork() is proportional to the number of page table entries, not the number of physical pages.

The implementation is fully described in the section “Copy On Write” in Chapter 9.

Kernel Threads

Traditional Unix systems delegate some critical tasks to intermittently running processes, including flushing disk caches, swapping out unused pages, servicing network connections, and so on. Because some of these system processes run only in Kernel Mode, modern operating systems delegate their functions to kernel threads, which are not encumbered with the unnecessary User Mode context.

Kernel threads differ from regular processes in the following ways:

  • Kernel threads run only in Kernel Mode, while regular processes run alternatively in Kernel Mode and in User Mode.
  • Because kernel threads run only in Kernel Mode, they use only kernel-space addresses. Regular processes use the full virtual address space.
  • Kernel threads have no user-mode address space: their mm field is NULL. They borrow the previous process’s active_mm for kernel page table access — the lazy TLB mode described in the “Performing the Process Switch” section.
  • Kernel threads are effectively immune to signals. Because they never return to user mode, they never run the signal-delivery path, so a SIGKILL aimed at a kthread is simply ignored. A kernel thread is shut down cooperatively instead, via kthread_stop() (described below). This is why you cannot kill -9 a [kworker] or [kswapd0] entry in ps.
  • They are marked by the PF_KTHREAD flag in task_struct.flags, which the kernel tests in dozens of places to skip user-space-only work (signal delivery, address-space teardown, ptrace, OOM scoring).

Linux 7.0.12 also has a second, newer class of task that looks like a kernel thread but is not one: the user worker, flagged PF_USER_WORKER. These are created with user_mode_thread() and are used by io_uring (PF_IO_WORKER) and vhost. Unlike a true kthread they are cloned from a user-space thread and keep that thread’s credentials, cgroup, and address space, so they can perform I/O on the submitting task’s behalf. The helper task_can_run_userspace() distinguishes the two families:

/* include/linux/sched.h:1830 */
    return task->mm && !(task->flags & (PF_KTHREAD | PF_USER_WORKER));

    movq    %rax, %rdi      /* prev (for schedule_tail) */
    movq    %rsp, %rsi      /* regs */

The Canonical Kernel Thread Loop

Because signals cannot be used to terminate a kthread, shutdown is cooperative. Almost every kernel thread is therefore written as a loop that sleeps for work and polls kthread_should_stop():

static int my_kthread_fn(void *data)
{
    while (!kthread_should_stop()) {
        set_current_state(TASK_INTERRUPTIBLE);
        if (no_work_pending())
            schedule();                 /* Sleep until woken */
        __set_current_state(TASK_RUNNING);

        do_the_work(data);
    }
    return 0;   /* Becomes kthread->result */
}

The set_current_state() before the emptiness test is the standard sleep/wake race avoidance idiom described in “How Processes Are Organized”: the state must be set before re-checking the condition, or a wakeup arriving in between would be lost.

Stopping a Kernel Thread

kthread_stop() is the counterpart of kthread_run(). It is a synchronous call — it does not return until the thread has actually exited:

/* kernel/kthread.c */
int kthread_stop(struct task_struct *k)
{
    struct kthread *kthread;
    int ret;

    get_task_struct(k);                             /* Pin the descriptor */
    kthread = to_kthread(k);
    set_bit(KTHREAD_SHOULD_STOP, &kthread->flags);  /* Raise the flag */
    kthread_unpark(k);                              /* Un-park if parked */
    set_tsk_thread_flag(k, TIF_NOTIFY_SIGNAL);      /* Break out of sleeps */
    wake_up_process(k);                             /* Wake it up */
    wait_for_completion(&kthread->exited);          /* Block until it dies */
    ret = kthread->result;                          /* Collect its return value */
    put_task_struct(k);
    return ret;
}

Two details deserve attention. First, set_tsk_thread_flag(k, TIF_NOTIFY_SIGNAL) is how the kernel nudges a thread that is blocked in an interruptible sleep without sending a real signal — helpers such as wait_event_interruptible() and schedule_timeout_interruptible() check signal_pending(), which also returns true for TIF_NOTIFY_SIGNAL. Second, the caller blocks on the exited completion, which the kthread layer signals from the exit path; this guarantees the thread is fully gone before kthread_stop() returns, so the caller can safely free any data the thread was using.

A kernel thread that never calls kthread_should_stop() and never sleeps interruptibly will hang kthread_stop() forever. This is why the polling loop above is a strict convention rather than a style preference.

Parking: Suspending a Per-CPU Thread

Many kernel threads are per-CPU (ksoftirqd/N, migration/N, kworker/N:M). When a CPU is taken offline, destroying and later recreating its threads would be wasteful and racy, so the kthread layer instead parks them:

  • kthread_park(k) sets KTHREAD_SHOULD_PARK, wakes the thread, and waits on the parked completion.
  • The thread notices via kthread_should_park() and calls kthread_parkme(), which marks itself parked and sleeps in TASK_PARKED.
  • kthread_unpark(k) clears the bit, restores the CPU affinity, and wakes the thread so it resumes its loop.

The TASK_PARKED state (see Table 3-1) exists specifically for this purpose: a parked thread is neither runnable nor blocked on a resource, and the scheduler will not migrate it to another CPU. This mechanism did not exist in Linux 2.6, where CPU hotplug had to tear down and recreate per-CPU threads.

Borrowing a User Address Space

A kernel thread has mm == NULL, so it cannot dereference a user-space pointer — there is no user page table loaded. Some kernel threads nevertheless need to read or write another process’s memory: vhost worker threads copying virtio buffers, io_uring workers completing an asynchronous read, or the AIO subsystem. For these cases the kthread layer offers a temporary address-space borrow:

/* kernel/kthread.c:1615 — simplified */
void kthread_use_mm(struct mm_struct *mm)
{
    struct task_struct *tsk = current;

    WARN_ON_ONCE(!(tsk->flags & PF_KTHREAD));
    WARN_ON_ONCE(tsk->mm);              /* Must not already have one */

    mmgrab(mm);
    task_lock(tsk);
    local_irq_disable();
    active_mm     = tsk->active_mm;
    tsk->active_mm = mm;
    tsk->mm        = mm;                /* Now current->mm is valid */
    membarrier_update_current_mm(mm);
    switch_mm_irqs_off(active_mm, mm, tsk);   /* Load the page tables */
    local_irq_enable();
    task_unlock(tsk);
    mmdrop_lazy_tlb(active_mm);         /* Release the borrowed lazy mm */
}

Between kthread_use_mm() and the matching kthread_unuse_mm(), the kernel thread has a real user address space: copy_from_user() and copy_to_user() work normally, and the thread appears to the memory-management code like a user task. kthread_unuse_mm() reverses the operation, restoring mm = NULL and returning the thread to lazy-TLB mode.

These functions were named use_mm()/unuse_mm() in Linux 2.6 and earlier; they were renamed and hardened in 5.8 to make the PF_KTHREAD-only contract explicit. Note that mmgrab() (not mmget()) is used: the kthread takes a reference on the descriptor, not on the address space itself, so a concurrent exit_mm() can still tear down the mappings.

Process 0 (swapper / idle)

The ancestor of all processes, called process 0, the idle process, or, for historical reasons, the swapper process, is a kernel thread created from scratch during the initialization phase of Linux. This ancestor process uses statically allocated data structures:

  • A process descriptor stored in init_task, initialized by the INIT_TASK macro.
  • A kernel stack stored in init_stack (the init_thread_union).
  • Statically initialized tables: init_mm, init_fs, init_files, init_signals, init_sighand.
  • The master kernel Page Global Directory in swapper_pg_dir.
/* init/init_task.c */
struct task_struct init_task = {
    .thread_info = INIT_THREAD_INFO(init_task),
    .__state     = 0,
    .stack       = init_stack,
    .usage       = REFCOUNT_INIT(2),
    .flags       = PF_KTHREAD,
    .prio        = MAX_PRIO - 20,
    .comm        = INIT_TASK_COMM,
    .mm          = NULL,
    .active_mm   = &init_mm,
    /* ... */
};

The start_kernel() function initializes all kernel data structures, enables interrupts, and creates two child processes:

  1. Process 1 (init): Created via user_mode_thread(kernel_init, ...). This kernel thread executes kernel_init(), which completes initialization, then calls kernel_execve() to load /sbin/init (or systemd), transforming itself into the first user-mode process.
  2. Process 2 (kthreadd): Created via kernel_thread(kthreadd, ...). This becomes the parent of all other kernel threads.

After creating these two, process 0 calls cpu_startup_entry(CPUHP_ONLINE), which enters the idle loop — essentially an infinite loop calling do_idle() that executes architecture-specific halt instructions (HLT on x86_64, WFI/WFE on ARM64) with interrupts enabled. Process 0 is selected by the scheduler only when there are no other tasks in the TASK_RUNNING state.

In multiprocessor systems, there is a process 0 for each CPU. The boot CPU (CPU 0) runs the original init_task. Each additional CPU gets its own idle thread created by fork_idle() during CPU hotplug bring-up, with a PID of 0.

Process 1 (init)

The kernel thread created by process 0 executes the kernel_init() function, which completes kernel initialization (loading modules, setting up consoles, mounting the root filesystem). Then it calls kernel_execve() to load /sbin/init (or whatever was specified on the kernel command line via init=). As a result, the init kernel thread becomes a regular user-mode process with its own address space.

Process 1 is special in several ways:

  • It is the fallback parent for orphaned processes. When a parent exits before its children, those children are reparented to the nearest child_subreaper ancestor, or to init if no subreaper exists.
  • It must call wait() on its children to reap zombies. If init fails to do this, zombie processes accumulate.
  • If init exits, the kernel panics — it is the only process whose death is considered fatal.
  • In PID namespaces, each namespace has its own “init” process (the child_reaper). This per-namespace init has the same special properties.
  • Init receives signals differently: signals for which init has not installed a handler are silently dropped (the SIGNAL_UNKILLABLE flag).

Namespaces and Container Identity

Linux namespaces provide process-level isolation for system resources. Each namespace type gives a process its own virtualized view of a global resource, so that changes made inside one namespace are invisible to processes in other namespaces. Namespaces are the foundation of Linux containers (Docker, LXC, Kubernetes pods).

In Linux 2.6.11, exactly one namespace type existed: the mount namespace (CLONE_NEWNS, added in 2.4.19). Everything else arrived later — UTS and IPC in 2.6.19, PID in 2.6.24, network in 2.6.29, user in 3.8, cgroup in 4.6, and time in 5.6. By Linux 7.0.12 there are eight namespace types, and the entire infrastructure has been generalized into a common framework.

This section treats namespaces as part of a process’s identity: the nsproxy a task carries, the generic ns_common object every namespace embeds, and the system calls that create and enter them. Chapter 25 returns to namespaces as the raw material of containers, side by side with cgroups, and Chapter 6 follows the time namespace’s clock offsets into the timekeeping code and the vDSO.

The nsproxy Structure

Each process holds a pointer to a shared nsproxy structure that groups all of its namespace references:

/* include/linux/nsproxy.h:32-42 */
struct nsproxy {
    refcount_t count;
    struct uts_namespace   *uts_ns;
    struct ipc_namespace   *ipc_ns;
    struct mnt_namespace   *mnt_ns;
    struct pid_namespace   *pid_ns_for_children;
    struct net             *net_ns;
    struct time_namespace  *time_ns;
    struct time_namespace  *time_ns_for_children;
    struct cgroup_namespace *cgroup_ns;
};

Note that nsproxy does not contain the PID namespace of the current process — only pid_ns_for_children. The process’s own PID namespace is accessed via task_active_pid_ns(tsk). Similarly, the user namespace is stored in the process’s credentials (struct cred), because it governs capability checks.

The Generic Namespace Object: struct ns_common

The eight namespace types have almost nothing in common at the level of what they isolate — a mount table and a hostname string are unrelated things. But they need identical plumbing: a reference count, a way to be represented as a file in /proc, a type tag, and a set of operations for setns(). Linux factors all of this into a single embedded structure, struct ns_common, which every namespace type includes as a member named ns:

/* include/linux/ns/ns_common_types.h */
struct ns_common {
    struct {
        refcount_t __ns_ref;   /* Memory lifetime (do not use directly) */
    } ____cacheline_aligned_in_smp;
    u32                            ns_type;   /* CLONE_NEWNET, CLONE_NEWPID, ... */
    struct dentry                  *stashed;  /* Cached nsfs dentry for /proc/<pid>/ns/* */
    const struct proc_ns_operations *ops;     /* get/put/install/owner callbacks */
    unsigned int                   inum;      /* Inode number seen by userspace */
    union {
        struct ns_tree;                       /* ns_id + active refcount + tree nodes */
        struct rcu_head ns_rcu;
    };
};

Because ns_common is embedded rather than pointed to, converting between a concrete namespace and the generic object is a compile-time operation in both directions: container_of() going one way (wrapped in helpers such as to_pid_ns(), to_time_ns()), and a C11 _Generic selection going the other:

#define to_ns_common(__ns)                                    \
    _Generic((__ns),                                          \
        struct pid_namespace *:  &(__ns)->ns,                 \
        struct user_namespace *: &(__ns)->ns,                 \
        struct net *:            &(__ns)->ns,                 \
        /* ... one line per namespace type ... */)

This is a notable modernization: in Linux 2.6 each namespace type rolled its own atomic_t count and its own teardown path. Today a single set of macros — ns_ref_get(), ns_ref_put(), ns_common_init(), ns_common_free() — works uniformly across all eight types, and each type only supplies a free callback for the parts that are genuinely its own.

Two-Tier Reference Counting

Linux 7.0.12 splits namespace lifetime into two independent counts, a design that did not exist in earlier kernels:

CounterTypeGovernsIncremented by
__ns_refrefcount_tMemory lifetime. When it reaches zero the namespace is removed from the namespace trees and freed after an RCU grace period.Any internal pointer, including a file->f_cred that outlives the creating task.
__ns_ref_activeatomic_tUserspace visibility. When it reaches zero the namespace can no longer be opened via /proc/<pid>/ns/, resolved from a file handle, or discovered via listns().Any live task using it (through nsproxy or cred), any open namespace file descriptor, any bind mount of one.

A namespace therefore passes through three states:

  • Active (__ns_ref_active > 0) — in use and visible to userspace.
  • Inactive (__ns_ref_active == 0, __ns_ref > 0) — every task has exited and every fd is closed, but some internal reference (typically a struct file’s cached credentials, possibly passed to another process over a UNIX socket) still pins the memory. The namespace is alive but invisible. It can even be resurrected back to active, for example by the SIOCGSKNS ioctl on a socket, which hands back the network namespace the socket belongs to.
  • Destroyed (__ns_ref == 0) — unlinked from the trees and freed.

The initial namespaces (init_pid_ns, init_net, init_user_ns, and so on) are special-cased: is_ns_init_id() short-circuits every get and put, so their counts remain pinned at 1 forever and the hot paths avoid an atomic operation entirely.

Three Ways to Create and Enter Namespaces

1. clone() / clone3() — create a new process in new namespaces at fork time. Inside the kernel, copy_namespaces() checks whether any CLONE_NEW* flags are set. If none, the child increments the parent’s nsproxy refcount. If any are set, create_new_namespaces() allocates a new nsproxy with fresh namespace structures.

2. unshare() — create new namespaces for the current process without forking. ksys_unshare() in kernel/fork.c:3123 builds a new nsproxy and installs it via switch_task_namespaces(). This is used by container runtimes to set up isolation before exec-ing the container’s init process.

3. setns() — enter an existing namespace. Each namespace is represented as a file under /proc/<pid>/ns/. The setns() syscall (kernel/nsproxy.c:563) opens this file, extracts the struct ns_common, and installs it into the caller’s nsproxy. Since Linux 5.3, setns() can also accept a pidfd, allowing the caller to enter all namespaces of a target process at once.

Inside copy_namespaces()

The fork path is optimized for the overwhelmingly common case in which the child shares every namespace with its parent:

/* kernel/nsproxy.c — copy_namespaces(), condensed */
if (likely(!(flags & (CLONE_NEWNS | CLONE_NEWUTS | CLONE_NEWIPC |
                      CLONE_NEWPID | CLONE_NEWNET |
                      CLONE_NEWCGROUP | CLONE_NEWTIME)))) {
        if ((flags & CLONE_VM) ||
            likely(old_ns->time_ns_for_children == old_ns->time_ns)) {
                get_nsproxy(old_ns);      /* Just bump the shared refcount */
                return 0;
        }
} else if (!ns_capable(user_ns, CAP_SYS_ADMIN))
        return -EPERM;

if ((flags & (CLONE_NEWIPC | CLONE_SYSVSEM)) ==
                (CLONE_NEWIPC | CLONE_SYSVSEM))
        return -EINVAL;

Three things are worth extracting from this fragment:

  • The nsproxy is copy-on-write at the granularity of the whole set. Requesting even one new namespace forces allocation of an entirely fresh nsproxy; the seven unchanged pointers are simply copied and their individual refcounts bumped. This is why the comment in nsproxy.h notes that a namespace’s own count is “the number of nsproxies pointing to it, not the number of tasks.”
  • The permission check is ns_capable(user_ns, CAP_SYS_ADMIN), not capable(). The capability is evaluated relative to the caller’s user namespace — the mechanism that makes unprivileged containers possible (see “User Namespace and Capabilities” below).
  • CLONE_NEWIPC and CLONE_SYSVSEM are mutually exclusive. CLONE_SYSVSEM asks to share the parent’s System V semaphore undo list, but after switching to a new IPC namespace those semaphore arrays are unreachable, so the combination is rejected outright rather than silently producing a dangling undo list.

When new namespaces are requested, create_new_namespaces() calls each subsystem’s copy_* helper in a fixed order — mount, UTS, IPC, PID, cgroup, net, time — each of which either returns the old namespace with a bumped refcount (if its flag is absent) or allocates a new one. Failures unwind through a goto ladder (out_time, out_net, out_cgroup, …) that releases exactly the namespaces acquired so far, in the same style as the bad_fork ladder in copy_process().

Note the asymmetry in the last two fields: create_new_namespaces() installs the new time namespace into time_ns_for_children but copies the old time_ns into time_ns. A task that calls unshare(CLONE_NEWTIME) does not itself move into the new time namespace — only its children do. This is the same rule as pid_ns_for_children, and for the same reason: changing a running task’s clock offsets or PID out from under it would break every timestamp and PID it has already observed.

Namespace File Descriptors and the nsfs ioctls

Every entry in /proc/<pid>/ns/ is a symlink into nsfs, a tiny internal filesystem whose sole purpose is to give namespaces an inode identity. Holding such a file descriptor open keeps the namespace alive even after every task in it has exited — the trick container runtimes use to keep an empty network namespace around. Because two processes are in the same namespace exactly when the symlinks resolve to the same inode, stat’ing them is the standard userspace comparison:

Namespace Identity: IDs, Trees, and listns()

Historically there was no way to enumerate the namespaces on a system. Tools such as lsns(8) had to scan every entry in /proc, stat every link under each ns/ directory, and deduplicate the resulting inode numbers — an approach that is racy, slow on large systems, and structurally unable to see a namespace that has no running task in it. Linux 7.0.12 fixes this with two additions.

First, every namespace receives a 64-bit monotonically increasing ID (ns_id) in addition to its recyclable inode number. IDs are never reused, so an ID is a stable handle for the lifetime of the system. The initial namespaces get fixed low IDs:

/* include/uapi/linux/nsfs.h */
enum init_ns_id {
    IPC_NS_INIT_ID    = 1ULL,
    UTS_NS_INIT_ID    = 2ULL,
    USER_NS_INIT_ID   = 3ULL,
    PID_NS_INIT_ID    = 4ULL,
    CGROUP_NS_INIT_ID = 5ULL,
    TIME_NS_INIT_ID   = 6ULL,
    NET_NS_INIT_ID    = 7ULL,
    MNT_NS_INIT_ID    = 8ULL,
};

Second, namespaces are now linked into namespace trees. Each ns_common carries a struct ns_tree holding three tree nodes, so a single namespace simultaneously belongs to three orderings:

  • the unified tree of every namespace on the system;
  • the per-type tree (all network namespaces, all PID namespaces, …);
  • the owner tree of the user namespace that owns it — and, if the namespace is itself a user namespace, it also carries the root of the tree of namespaces it owns.

Each tree is maintained as a red-black tree and a list kept in the same sorted order, giving O(log n) lookup by ID together with cheap sequential iteration:

/* include/linux/ns/nstree_types.h */
struct ns_tree_root {
    struct rb_root   ns_rb;          /* O(log n) lookup by ns_id */
    struct list_head ns_list_head;   /* Same order, cheap iteration */
};

struct ns_tree {
    u64                 ns_id;
    atomic_t            __ns_ref_active;
    struct ns_tree_node ns_unified_node;  /* Global tree */
    struct ns_tree_node ns_tree_node;     /* Per-type tree */
    struct ns_tree_node ns_owner_node;    /* Owning user ns's tree */
    struct ns_tree_root ns_owner_root;    /* Namespaces this one owns */
};

On top of this sits the new listns() system call (number 470 on both x86-64 and ARM64):

/* kernel/nstree.c:763 */
SYSCALL_DEFINE4(listns, const struct ns_id_req __user *, req,
                u64 __user *, ns_ids, size_t, nr_ns_ids, unsigned int, flags);

struct ns_id_req {
    __u32 size;
    __u32 spare;
    __u64 ns_id;         /* Resume cookie: last ID returned, or 0 to start */
    struct {
        __u32 ns_type;   /* Filter: CLONE_NEWNET, ..., or 0 for all types */

The call fills ns_ids with up to nr_ns_ids namespace IDs and is resumable: passing the last ID received back in req->ns_id continues the walk, so a caller can page through a system with millions of namespaces without holding any lock across calls. Setting user_ns_id restricts the walk to the owner tree of one user namespace, which is how an unprivileged container manager enumerates exactly the namespaces it created. An ID obtained this way can then be turned back into an open file descriptor with open_by_handle_at() using a struct nsfs_file_handle, closing the loop without going through /proc at all.

PID Namespace Details

PID namespaces have the most complex semantics of the eight, because unlike a hostname or a mount table, a PID is not merely a value a process reads — it is an identity that other processes use to refer to it, and that identity must remain consistent from every vantage point simultaneously.

/* include/linux/pid_namespace.h */
struct pid_namespace {
    struct idr              idr;            /* PID allocator for this namespace */
    struct rcu_head         rcu;
    unsigned int            pid_allocated;  /* In-use count + PIDNS_ADDING bit */
    struct task_struct      *child_reaper;  /* This namespace's "init" (PID 1) */
    struct kmem_cache       *pid_cachep;    /* Sized for this nesting level */
    unsigned int            level;          /* 0 = initial namespace */
    int                     pid_max;        /* Per-namespace PID ceiling */
    struct pid_namespace    *parent;
    struct user_namespace   *user_ns;       /* Owning user namespace */
    struct ucounts          *ucounts;
    int                     reboot;         /* Exit code if the ns "rebooted" */
    struct ns_common        ns;
    struct work_struct      work;
};
  • Hierarchical PID translation: A process has a distinct PID in every namespace level from its own up to the root. Recall from “Identifying a Process” that struct pid ends with a variable-length numbers[] array holding one struct upid per level; pid_nr_ns(pid, ns) simply indexes that array. A process in a namespace at level 3 therefore has four valid PIDs at once, and each is the only PID visible from its respective level.
  • Nesting is bounded: MAX_PID_NS_LEVEL is 32. The limit exists specifically to bound the size of struct pid, whose allocation is sized by level, which is why each namespace carries its own pid_cachep slab cache.
  • Per-namespace pid_max: In Linux 2.6 — and indeed until quite recently — pid_max was a single global sysctl. It is now a field of pid_namespace, so a container can be given a much smaller PID ceiling than the host as a lightweight defence against fork bombs.
  • Per-namespace init: The first process in a PID namespace becomes its child_reaper — PID 1 within that namespace. It inherits the two special properties of the global init described later in “Destroying Processes”: orphans in the namespace are reparented to it, and signals with default actions are not delivered to it, so a container’s init cannot be accidentally killed by a stray SIGTERM from inside the container.
/* kernel/pid.c:533 */
pid_t pid_nr_ns(struct pid *pid, struct pid_namespace *ns)
{
    struct upid *upid;
    pid_t nr = 0;
    if (pid && ns->level <= pid->level) {
        upid = &pid->numbers[ns->level];
        if (upid->ns == ns)
            nr = upid->nr;
    }
    return nr;
}

The guard ns->level <= pid->level encodes the fundamental visibility rule of PID namespaces: a process is visible from its own namespace and every ancestor, but never from a descendant or a sibling namespace. Asking for the PID of a process that lives in a deeper or unrelated namespace returns 0, which callers treat as “does not exist.”

Tearing Down a PID Namespace

When a namespace’s init dies, the entire namespace must die with it — otherwise its remaining processes would be orphans with no reaper. zap_pid_ns_processes() performs this shutdown:

  1. disable_pid_allocation() clears the PIDNS_ADDING bit in pid_allocated, so no further process can be created in the namespace even if an existing one is mid-fork().
  2. SIGCHLD is set to SIG_IGN in the dying init, which makes every terminating child autoreap instead of becoming a zombie waiting to be collected. This is what makes the shutdown fast.
  3. The namespace’s idr is walked from index 2 upward (skipping init itself) and SIGKILL is sent to every task found.
  4. The dying init then waits until pid_allocated drops to the expected residual count, guaranteeing that the namespace is fully drained before it finishes exiting.

Walking the namespace’s own idr rather than the global task list is a deliberate scalability choice: the cost is proportional to the number of processes in the container, not to the number of processes on the host.

Recall from “PID Namespaces” in “Identifying a Process” that CLONE_NEWPID takes effect only for the caller’s children, because a running task’s PID cannot change underneath it; that is why nsproxy stores pid_ns_for_children rather than a PID namespace pointer, and why unshare(CLONE_NEWPID) must be followed by a fork() before the new numbering takes effect. The clone3() interface adds a related capability: the set_tid array (bounded by MAX_PID_NS_LEVEL) lets a privileged caller request specific PIDs at each level, which is how checkpoint/restore tools such as CRIU recreate a container with its original PIDs intact.

User Namespace and Capabilities

The user namespace is the keystone of unprivileged containers, and the only namespace whose contents live in struct cred rather than in nsproxy — because it governs capability checks, which are a property of credentials:

/* include/linux/user_namespace.h */
struct user_namespace {
    struct uid_gid_map     uid_map;
    struct uid_gid_map     gid_map;
    struct uid_gid_map     projid_map;
    struct user_namespace  *parent;
    int                    level;
    kuid_t                 owner;   /* Creator's UID, in the parent namespace */
    kgid_t                 group;
    struct ns_common       ns;
    unsigned long          flags;
    bool                   parent_could_setfcap;
    struct ucounts         *ucounts;
    long ucount_max[UCOUNT_COUNTS];          /* Per-namespace resource ceilings */
    long rlimit_max[UCOUNT_RLIMIT_COUNTS];
};
  • UID/GID mapping: Each user namespace has uid_map, gid_map, and projid_map, written once via /proc/<pid>/uid_map and friends. A map is a list of {first, lower_first, count} extents: “count IDs starting at first inside this namespace correspond to count IDs starting at lower_first in the parent.” The kernel translates in both directions via make_kuid() (outside → inside) and from_kuid() (inside → outside), and stores every UID internally as an opaque kuid_t so that a raw integer can never be compared across namespace boundaries by accident.
  • Map layout is size-optimized: struct uid_gid_map is a union sized to exactly one 64-byte cache line. Up to UID_GID_MAP_MAX_BASE_EXTENTS (5) extents are stored inline and searched linearly; beyond that the union switches to a pair of pointers to sorted forward and reverse arrays searched by binary search, up to UID_GID_MAP_MAX_EXTENTS (340).
  • Full capabilities inside: Creating a new user namespace grants a full capability set inside it, even to an unprivileged user. Those capabilities are real, but they only authorize operations on objects owned by that namespace.
  • Gating other namespaces: Most CLONE_NEW* flags require CAP_SYS_ADMIN — but the check is ns_capable(user_ns, CAP_SYS_ADMIN), evaluated in the caller’s user namespace. An unprivileged user therefore first creates a user namespace (which needs no privilege), and can then create all other namespace types within it. This single design decision is what made rootless containers possible.
  • Nesting is bounded: create_user_ns() refuses to create a child if parent_ns->level > 32. Without this, a user could nest namespaces indefinitely and force unbounded recursion in the capability and ID-translation walks.

ucounts: Preventing Namespace Exhaustion

Once any user can create namespaces, namespace creation itself becomes a denial-of-service vector. Linux answers this with the ucounts mechanism: per-user, per-namespace counters with per-namespace ceilings. The UCOUNT_COUNTS enumeration includes one entry for each namespace type — UCOUNT_USER_NAMESPACES, UCOUNT_PID_NAMESPACES, UCOUNT_NET_NAMESPACES, and so on — plus counters for other user-triggerable kernel objects such as inotify instances and fanotify marks. The limits are exposed as /proc/sys/user/max_*_namespaces.

The counters are hierarchical: creating a namespace charges the creating user in every ancestor user namespace up to the root, so a user cannot escape a limit imposed by the host administrator merely by nesting deeper. Since Linux 5.14 the same infrastructure also backs several rlimits (RLIMIT_NPROC, RLIMIT_MSGQUEUE, RLIMIT_SIGPENDING, RLIMIT_MEMLOCK), which is why struct ucounts carries a second rlimit[] array. None of this existed in Linux 2.6, where a single global struct user_struct tracked per-user process counts.

The Time Namespace

The time namespace, added in Linux 5.6, is the newest of the eight and the most narrowly scoped. It exists almost entirely to make checkpoint/restore work: when CRIU restores a container on a different machine hours later, the restored processes must not observe CLOCK_MONOTONIC jumping backward, since the POSIX contract says that clock never decreases.

/* include/linux/time_namespace.h */
struct timens_offsets {
    struct timespec64 monotonic;
    struct timespec64 boottime;
};

struct time_namespace {
    struct user_namespace *user_ns;
    struct ucounts        *ucounts;
    struct ns_common      ns;
    struct timens_offsets offsets;
    struct page           *vvar_page;      /* Per-namespace vDSO data page */
    bool                  frozen_offsets;  /* Set once a task has joined */
};

Three properties make it unusual:

  • It virtualizes offsets, not clocks. Only CLOCK_MONOTONIC and CLOCK_BOOTTIME are affected, and only by the addition of a fixed offset. CLOCK_REALTIME is deliberately not namespaced: wall-clock time is expected to be globally consistent, and virtualizing it would break TLS certificate validation, file timestamps, and distributed protocols.
  • Offsets freeze on first use. The frozen_offsets flag makes /proc/<pid>/timens_offsets writable only until a task actually joins the namespace. Allowing a live adjustment would let CLOCK_MONOTONIC move backward for a running process — exactly the guarantee the namespace exists to preserve.
  • It reaches into the vDSO. Because clock_gettime() normally never enters the kernel at all, per-namespace offsets must be visible to the userspace vDSO code. Each time namespace therefore owns a vvar_page holding its own copy of the timekeeping data; vdso_join_timens() remaps the task’s vDSO variable page to point at it. The time namespace is thus the only namespace whose implementation extends into userspace-executed code, and the reason find_timens_vvar_page() is consulted on every fault of the vDSO VMA.

Like the PID namespace, the time namespace uses the “for children” pattern: unshare(CLONE_NEWTIME) sets time_ns_for_children, and only descendants observe the new offsets.

Destroying Processes

Most processes “die” in the sense that they terminate the execution of the code they were supposed to run. When this occurs, the kernel must be notified so that it can release the resources owned by the process: memory, open files, semaphores, and any other kernel objects we encounter in this book.

The usual way for a process to terminate is to invoke the exit() library function, which releases resources allocated by the C library, executes each function registered with atexit(), and ends up invoking a system call that evicts the process from the system. Alternatively, the kernel may force a whole thread group to die when a process receives an unhandled signal or an unrecoverable CPU exception occurs.

Process Termination

In Linux 7.0.12 there are two system calls that terminate a user-mode application:

  • exit_group(): Terminates a full thread group (whole multithreaded application). Implemented by do_group_exit(). This is what the exit() C library function invokes.
  • _exit(): Terminates a single thread. Implemented by do_exit(). This is what pthread_exit() invokes.

The do_group_exit() Function

do_group_exit() (kernel/exit.c:1094) kills all threads in the thread group of current:

  1. Checks if SIGNAL_GROUP_EXIT is already set (another thread started the exit). If so, uses the existing group_exit_code.
  2. Otherwise, acquires sighand->siglock, sets SIGNAL_GROUP_EXIT, stores the termination code, and calls zap_other_threads(current) to send SIGKILL to every other thread.
  3. Calls do_exit(exit_code) for the current thread. This function never returns.

Note that do_group_exit() does not wait for the other threads to actually die. It marks them and returns to kill itself; each sibling notices the pending SIGKILL on its next return from kernel mode and runs its own do_exit(). Group exit is therefore inherently concurrent, which is exactly why the coordination described next is needed.

Coordinating With a Coredump: synchronize_group_exit()

A thread group that is dying because of a fatal signal may simultaneously be dumping core, and a coredump must observe a consistent, frozen snapshot of the address space. If exiting threads were allowed to run exit_mm() while the dumper was walking their memory, the dump would be garbage. synchronize_group_exit() is the barrier that prevents this:

/* kernel/exit.c:868 */
static void synchronize_group_exit(struct task_struct *tsk, long code)
{
    ...
    spin_lock_irq(&sighand->siglock);
    signal->quick_threads--;
    if ((signal->quick_threads == 0) &&
        !(signal->flags & SIGNAL_GROUP_EXIT)) {
            signal->flags           = SIGNAL_GROUP_EXIT;
            signal->group_exit_code = code;
            signal->group_stop_count = 0;
    }
    tsk->flags |= PF_POSTCOREDUMP;      /* Must be set under siglock */
    core_state = signal->core_state;
    spin_unlock_irq(&sighand->siglock);

    if (unlikely(core_state))
            coredump_task_exit(tsk, core_state);   /* Block until dump done */
}

The quick_threads counter is a second, cheaper thread count maintained alongside signal->live. When it reaches zero the kernel knows the last thread has entered do_exit() and can promote a plain _exit() into a group exit without a separate scan. The PF_POSTCOREDUMP flag must be set while holding siglock because the thread that induces the dump counts, under the same lock, exactly those threads that do not yet have the flag — the two operations race otherwise. If a dump is in flight, coredump_task_exit() parks the thread until the dumper is finished with its memory.

Releasing the Address Space: exit_mm()

exit_mm() (kernel/exit.c:550) is the step that turns a user process into something structurally indistinguishable from a kernel thread — a task with mm == NULL running on borrowed page tables:

/* kernel/exit.c:550 — condensed */
static void exit_mm(void)
{
    struct mm_struct *mm = current->mm;

    exit_mm_release(current, mm);      /* Futex cleanup + vfork completion */
    if (!mm)
            return;                    /* Kernel thread: nothing to do */

    mmap_read_lock(mm);
    mmgrab_lazy_tlb(mm);               /* Keep the mm alive as a lazy-TLB mm */
    BUG_ON(mm != current->active_mm);

    task_lock(current);
    smp_mb__after_spinlock();          /* Ordering for membarrier() */
    local_irq_disable();
    current->user_dumpable = (get_dumpable(mm) == SUID_DUMP_USER);
    current->mm = NULL;                /* No user address space from here on */
    membarrier_update_current_mm(NULL);
    enter_lazy_tlb(mm, current);       /* Keep using its page tables for now */
    local_irq_enable();
    task_unlock(current);
    mmap_read_unlock(mm);

    mm_update_next_owner(mm);
    mmput(mm);                         /* Drop the real reference */
    if (test_thread_flag(TIF_MEMDIE))
            exit_oom_victim();
}

Several subtleties are worth drawing out:

  • The task does not stop using the page tables. Setting current->mm = NULL only says “I have no user address space”; active_mm still points at the old mm, and mmgrab_lazy_tlb() takes the corresponding lazy reference. This is the same lazy-TLB state a kernel thread lives in, described in “Performing the Process Switch”. The final mmdrop_lazy_tlb_sched() happens in finish_task_switch() once some other task has taken over the CPU — the kernel cannot free the page tables it is currently executing on.
  • mmput() versus mmdrop(). mmput() drops mm_users. If that reaches zero the mappings are torn down immediately (exit_mmap() unmaps every VMA and frees the page tables), but the mm_struct itself survives while mm_count is non-zero — which it is, thanks to the lazy-TLB grab three lines earlier.
  • exit_mm_release() is where vfork() ends. It calls complete_vfork_done(), releasing a parent that has been blocked in wait_for_vfork_done() since the child was created (see “The vfork() Handshake”). It also runs futex_exit_release(), walking the robust futex list so that any futex the dying thread holds is marked FUTEX_OWNER_DIED rather than deadlocking every waiter.
  • mm_update_next_owner() hands off mm->owner to a surviving thread or child, so that memory-cgroup accounting continues to have a valid task to charge.
  • user_dumpable is latched before mm is dropped, because wait() and the pidfd machinery may need to know whether the exiting task was dumpable long after its mm_struct is gone.

Dying From a Kernel Oops: make_task_dead()

do_exit() assumes a cooperative, orderly death. A task that dies because of a kernel oops — a NULL dereference in a driver, a failed BUG_ON() — arrives from an arbitrary context that may have interrupts disabled, a non-zero preempt count, or spinlocks held. make_task_dead() is the hardened entry point that repairs enough state to make do_exit() survivable:

  • It panics outright if the fault happened in interrupt context (“Aiee, killing interrupt handler!”) or in the idle task (“Attempted to kill the idle task!”) — neither has anywhere to return to.
  • It re-enables interrupts and resets the preempt count if the oops left them wrong, printing a note naming the offending task.
  • It enforces kernel.oops_limit. This is a genuine security control rather than a robustness one: every oops that occurs while a reference is held leaks that reference, and an attacker who can trigger a harmless-looking oops repeatedly can wrap a non-refcount_t counter and turn an unexploitable bug into an exploitable one. Once the counter passes the limit the kernel panics deliberately.
  • If the task is already PF_EXITING — a recursive fault inside the exit path itself — there is no safe way to continue. The kernel prints “Fixing recursive fault but reboot is needed!”, forces futex_exit_recursive(), marks the task EXIT_DEAD, and jumps straight to do_task_dead(), skipping all remaining cleanup. The task is abandoned and its resources leak, on the theory that a leak is better than a crash.

The exit_notify() Function

exit_notify() (kernel/exit.c:737) handles what happens to the dying process’s children and how the parent is informed:

  1. Reparent children: Calls forget_original_parent(), which finds a new parent for all children.
  2. Handle orphaned process groups: If last thread, send SIGHUP + SIGCONT to any orphaned process group.
  3. Set EXIT_ZOMBIE.
  4. Decide notification:
    • If traced: do_notify_parent() sends signal to tracer.
    • If thread group leader and group empty: do_notify_parent() sends exit_signal (usually SIGCHLD) to parent.
    • If untraced sub-thread: autoreap immediately; do_notify_pidfd() wakes pidfd pollers.
  5. Autoreap if appropriate: Change exit_state to EXIT_DEAD and call release_task() immediately — no zombie created.

When No Zombie Is Created

The last step deserves elaboration, because a surprising number of terminating processes never become zombies at all. do_notify_parent() returns a boolean autoreap, and the decision is made there:

/* kernel/signal.c — do_notify_parent(), condensed */
if (!tsk->ptrace && sig == SIGCHLD &&
    (psig->action[SIGCHLD-1].sa.sa_handler == SIG_IGN ||
     (psig->action[SIGCHLD-1].sa.sa_flags & SA_NOCLDWAIT))) {
        autoreap = true;
        if (psig->action[SIGCHLD-1].sa.sa_handler == SIG_IGN)
                sig = 0;             /* Don't even send the signal */
}
if (valid_signal(sig) && sig)
        __send_signal_locked(sig, &info, tsk->parent, PIDTYPE_TGID, false);
__wake_up_parent(tsk, tsk->parent);

This implements a specific POSIX.1 rule: if the parent has explicitly set SIGCHLD to SIG_IGN, or has passed SA_NOCLDWAIT to sigaction(), it is declaring that it will never call wait(). The kernel takes it at its word and reaps the child itself. Note the asymmetry the comment in the source calls out: with SA_NOCLDWAIT the kernel still delivers SIGCHLD (POSIX leaves this implementation-defined); with SIG_IGN it suppresses the signal entirely. A daemon that wants fire-and-forget children without accumulating zombies uses one of these two mechanisms; this is precisely why signal(SIGCHLD, SIG_IGN) is a zombie-avoidance idiom rather than merely a way to silence a notification.

__wake_up_parent() is called in both branches, even when no signal is sent, because a parent blocked in wait4() whose last child just self-reaped must be woken so it can return -ECHILD instead of sleeping forever.

Threads autoreap for a different reason. An ordinary sub-thread that is not the group leader and is not traced has no one to notify — wait() operates on thread groups, not individual threads — so exit_notify() reaps it on the spot. Only the group leader lingers as a zombie, and only until the whole group is gone.

Zombie State

A zombie is a terminated process whose exit status has not yet been collected by its parent via wait(). The zombie retains its task_struct and struct pid so the parent can retrieve the exit code, resource usage statistics, and the PID. A zombie consumes very little memory, but large numbers indicate a parent that is not reaping its children.

The reason a zombie must hold onto its struct pid is subtler than the memory cost suggests: as long as the entry exists, that PID number cannot be recycled. If the kernel freed it immediately, a parent that had recorded the child’s PID could later signal or wait() for a completely unrelated new process that happened to be assigned the same number. The zombie is, in effect, a reservation on the identity — which is also why pidfd (which pins the struct pid directly) makes the whole class of PID-reuse race disappear.

Two special cases are worth noting. Threads that are not group leaders never enter EXIT_ZOMBIE at all; they autoreap as described above. And a group leader whose sub-threads are still running sits in EXIT_ZOMBIE without being reapable — wait() will not return it until thread_group_empty() is true, which is why the last thread to leave calls release_task() on the leader on its way out.

Reparenting: What Happens When a Parent Dies

The forget_original_parent() function (kernel/exit.c:698) reparents children in three stages, implemented by find_new_reaper() (kernel/exit.c:636):

  1. Try another thread in the same thread group: find_alive_thread() scans for a thread that is not PF_EXITING. A multithreaded program losing one thread should not have its children fostered out of the process.
  2. Try a child subreaper: Walk up the real_parent chain looking for an ancestor with is_child_subreaper set (via prctl(PR_SET_CHILD_SUBREAPER, 1)). Added in Linux 3.4 for process supervisors like systemd, which want to inherit the orphans of the services they manage rather than losing them to PID 1.
  3. Fall back to namespace init: The child_reaper of the PID namespace — the namespace’s init process.

The subreaper walk is guarded in a way that repays a second look:

/* kernel/exit.c:636 — find_new_reaper(), condensed */
if (father->signal->has_child_subreaper) {
        unsigned int ns_level = task_pid(father)->level;

        for (reaper = father->real_parent;
             task_pid(reaper)->level == ns_level;     /* Stay in this pidns */
             reaper = reaper->real_parent) {
                if (reaper == &init_task)
                        break;
                if (!reaper->signal->is_child_subreaper)
                        continue;
                thread = find_alive_thread(reaper);
                if (thread)
                        return thread;
        }
}
return child_reaper;

Two flags are involved, not one. is_child_subreaper marks a process that has volunteered; has_child_subreaper is inherited by every descendant and acts as a cheap “there is a subreaper somewhere above me” hint, so the common case skips the walk entirely. The loop terminates on task_pid(reaper)->level == ns_level rather than by comparing namespaces directly — the source comment explains why a namespace comparison would be wrong: an exiting parent could have been injected into the namespace by setns() followed by fork(), so the reaper chain can cross a namespace boundary that a naive check would not catch. A container’s orphans must never escape to a reaper on the host.

After finding the new parent, all children are reparented by updating real_parent and parent pointers. If any child has pdeath_signal set (via prctl(PR_SET_PDEATHSIG)), it receives that signal now. reparent_leader() additionally forces p->exit_signal = SIGCHLD on every reparented child — as the source comment puts it, “We don’t want people slaying init.” Without this, a child created with an exotic exit_signal (clone() permits any signal) could deliver that signal to the reaper when it died, letting an unprivileged process fire arbitrary signals at PID 1.

There is one further case, handled by find_child_reaper(): the dying process is the namespace’s child_reaper. If another live thread in its group exists, that thread is promoted to be the namespace’s init. If not, the namespace has lost its init, and the kernel calls zap_pid_ns_processes() to tear the entire PID namespace down — the shutdown sequence described in “Tearing Down a PID Namespace”. This is the kernel-side mechanism behind the familiar container behaviour that killing PID 1 kills the container.

The Final Free: do_task_dead() and finish_task_switch()

There is a bootstrapping problem hidden at the end of process destruction. The very last thing a dying task must do is free its own task_struct and kernel stack — but it is executing on that stack, using that descriptor as current. It cannot free them itself. Linux resolves this by deferring the final release to whichever task runs next:

/* kernel/sched/core.c:6901 */
void __noreturn do_task_dead(void)
{
    /* Causes final put_task_struct in finish_task_switch(): */
    set_special_state(TASK_DEAD);

    /* Tell freezer to ignore us: */
    current->flags |= PF_NOFREEZE;

    __schedule(SM_NONE);
    BUG();                      /* We must never be scheduled again */
    for (;;)
            cpu_relax();
}

set_special_state() is used rather than a plain set_current_state() because it takes pi_lock, serializing against a concurrent wakeup that might otherwise flip the task back to TASK_RUNNING between the store and the call to __schedule(). Once TASK_DEAD is set the scheduler will not put the task back on a run queue, so __schedule() is a one-way door. PF_NOFREEZE is set so that a system suspend in progress does not wait for a task that can never respond.

The switch that follows lands in finish_task_switch() — running on the incoming task’s stack, with the dead task now merely a pointer. As described in “Finishing the Switch”, that function checks the saved previous state and, on TASK_DEAD, performs the two releases the dying task could not perform for itself:

  • mmdrop_lazy_tlb_sched() drops the lazy-TLB reference taken by exit_mm(), finally allowing the mm_struct and its page tables to be freed — safe now, because the CPU has switched to a different address space.
  • put_task_struct_rcu_user() drops the last reference. The descriptor and stack are not freed immediately but after an RCU grace period, because lockless readers elsewhere in the kernel (an in-flight find_task_by_vpid(), a /proc walk) may still hold an RCU-protected pointer to it.

So a process’s existence ends in two stages separated by a context switch: release_task() unhooks it from every list and frees everything nameable, and finish_task_switch(), running as some other task on some other stack, finally reclaims the memory the dying task was standing on. In Linux 2.6 this handoff was signalled by a PF_DEAD flag inspected by the scheduler; folding it into the TASK_DEAD state removed a flag and a special case from the switch path.

Inside the Kernel: do_wait()

All four variants funnel into do_wait() after packing their arguments into a single descriptor:

/* kernel/exit.h */
struct wait_opts {
    enum pid_type      wo_type;      /* PIDTYPE_PID, PIDTYPE_PGID, PIDTYPE_MAX */
    int                wo_flags;     /* WNOHANG, WEXITED, WNOWAIT, ... */
    struct pid         *wo_pid;      /* Target, or NULL for "any child" */

    struct waitid_info *wo_info;     /* siginfo output (waitid) */
    int                wo_stat;      /* Encoded status output (wait4) */
    struct rusage      *wo_rusage;

    wait_queue_entry_t child_wait;
    int                notask_error; /* -ECHILD unless some child might match */
};

kernel_waitid_prepare() fills this in and performs the argument validation. Note two rules enforced there: unknown option bits are rejected with -EINVAL, and at least one of WEXITED, WSTOPPED, or WCONTINUED must be present — a waitid() that asks to be told about nothing is an error rather than a silent no-op. (wait4() and waitpid() supply WEXITED implicitly, which is why they have no such requirement.) The P_PIDFD case resolves the descriptor with pidfd_get_pid(), converting it to the same struct pid the other cases use, so everything downstream is identical.

The blocking loop itself is a textbook example of the sleep/wake idiom introduced earlier in this chapter:

/* kernel/exit.c:1712 */
static long do_wait(struct wait_opts *wo)
{
    int retval;

    init_waitqueue_func_entry(&wo->child_wait, child_wait_callback);
    wo->child_wait.private = current;
    add_wait_queue(&current->signal->wait_chldexit, &wo->child_wait);

    do {
            set_current_state(TASK_INTERRUPTIBLE);   /* Before the scan! */
            retval = __do_wait(wo);
            if (retval != -ERESTARTSYS)
                    break;                           /* Found something, or -ECHILD */
            if (signal_pending(current))
                    break;
            schedule();
    } while (1);

    __set_current_state(TASK_RUNNING);
    remove_wait_queue(&current->signal->wait_chldexit, &wo->child_wait);
    return retval;
}

The wait queue lives in signal->wait_chldexit — it is shared by the whole thread group, so any thread can reap a child created by any other. The entry uses a custom wake function, child_wait_callback(), rather than the default: when a child exits it wakes every waiter on the queue, but most of those waiters are waiting for a different child. The callback calls pid_child_should_wake() to filter, so a process with a thousand children does not stampede a thousand threads awake on every exit.

__do_wait() performs the actual scan under tasklist_lock and drives the tri-state notask_error:

  • It starts pessimistic at -ECHILD: “you have no such child.”
  • Any child that could eventually match the criteria — even one that is still running and therefore not reapable now — clears notask_error to 0.
  • If the scan finds a reapable child, its PID is returned immediately.
  • Otherwise, a notask_error of -ECHILD is returned right away, while a cleared one becomes -ERESTARTSYS — the signal to do_wait() that it should sleep and try again. Unless, of course, WNOHANG was specified, in which case 0 is returned without sleeping.

This three-way distinction is what makes wait() return -ECHILD promptly for a process with no children while still blocking correctly for one whose children are merely still alive. The __WNOTHREAD flag short-circuits the outer while_each_thread() loop, restricting the search to the calling thread’s own children instead of the whole group’s.

Encoding the Exit Status

wait_task_zombie() (kernel/exit.c:1175) is what actually harvests a zombie. It first picks the right status value — a thread group that died together reports its shared group_exit_code, while an individual death reports exit_code:

status = (p->signal->flags & SIGNAL_GROUP_EXIT)
       ? p->signal->group_exit_code : p->exit_code;

That single integer packs three separate pieces of information, in a layout inherited unchanged from V7 Unix and still decoded by the <sys/wait.h> macros:

BitsMeaningUserspace macro
0x7f (low 7)Terminating signal number, or 0 for a normal exitWTERMSIG(), WIFSIGNALED()
0x80A core dump was producedWCOREDUMP()
0xff00 (bits 8–15)The value passed to exit(), when the low 7 bits are zeroWEXITSTATUS()

The waitid() path unpacks this into an explicit cause and status pair — CLD_EXITED, CLD_KILLED, or CLD_DUMPED — which is the main reason to prefer it over wait4() in new code: it exposes a full siginfo_t instead of a bit-packed integer, and it is the only variant that can distinguish an exit status of 0 from “killed by signal 0”. This layout is also why exit statuses are effectively limited to 8 bits: exit(256) is reported to the parent as 0.

Two flags modify the harvest. WNOWAIT reads the status but leaves the zombie in place, so it can be collected again later — useful for a supervisor that wants to peek without consuming the notification. Without it, wait_task_zombie() moves the child to EXIT_DEAD (or EXIT_TRACE, if a tracer reparented it and must be told first) using an atomic exchange, which guarantees that among many threads racing to reap the same child, exactly one wins and calls release_task().

pidfd Notification

When a process exits, do_notify_pidfd() wakes any waiters on pid->wait_pidfd. User-space programs can poll()/epoll() on a pidfd to detect process exit — without being the parent and without PID reuse concerns:

/* User-space example */
int pidfd = pidfd_open(target_pid, 0);
struct pollfd pfd = { .fd = pidfd, .events = POLLIN };
poll(&pfd, 1, -1);
/* Process has exited */

Summary

Processes in Linux 7.0.12 are still built on the same fork/exec/exit/wait model that Unix established decades ago, and a 2.6-era programmer would still recognize every one of those system calls. Underneath, almost nothing is the same. The process descriptor has roughly tripled in size and is now split across a dozen reference-counted satellite structures. PIDs have become namespace-aware, reference-counted objects with file-descriptor handles. The kernel stack is decoupled from thread_info and fenced with guard pages. Context switching has grown to cover PCID, KPTI, FSGSBASE, and protection keys. Process creation is extensible through clone3(), and the entire lifecycle — creation, identity, accounting, and teardown — is container-aware through namespaces and cgroups.

The main points to carry forward are:

  • One structure, no threads. task_struct is the universal process descriptor. There is no separate "thread" structure — a thread is simply a task_struct that shares mm, files, fs, and sighand with its siblings via CLONE flags. What userspace calls a process is a thread group, identified by its tgid.
  • State is a bitmask, not an enum. The five classic states and two exit states have grown to seventeen bits plus compound names, including TASK_KILLABLE, TASK_IDLE, TASK_PARKED, TASK_FROZEN, and TASK_RTLOCK_WAIT. set_current_state() carries the memory barrier that makes the sleep/wakeup handshake safe; set_special_state() exists for the transitions that must also be safe against a concurrent waker.
  • struct pid is the real identity. A PID number is now just a key. The reference-counted, namespace-aware struct pid is what the kernel actually holds, which is what makes pidfds — and PID-reuse-free signalling and waiting — possible.
  • Finding current is architectural. It is a per-CPU variable on x86_64 and SP_EL0 on ARM64, not the stack-pointer masking trick of 2.6. Correspondingly, thread_info now lives inside task_struct, and kernel stacks can be vmalloc'd with guard pages so an overflow faults instead of silently corrupting a neighbour.
  • The list primitives are load-bearing. list_head, hlist, and container_of() are the connective tissue of the whole kernel, and the RCU variants are what let readers walk the process list without taking a lock. CONFIG_LIST_HARDENED turns the classic debug-only consistency checks into a production exploit-mitigation.
  • A small toolkit covers most other needs. Red-black trees keep objects sorted (with cached and augmented forms for the scheduler and reverse mapping), the IDR and IDA hand out integer IDs on top of the XArray, kref ties object lifetime to a saturating refcount_t, llist and kfifo pass work between contexts without locks, hashtable.h packages the hlist hash table, and notifier chains of four locking kinds broadcast events to subscribers the publisher does not know.
  • Processes are organized for the question being asked. The all-encompassing init_task list is for iteration; the parent/child and thread-group lists are for topology; the per-CPU runqueues and their six scheduler classes (with EEVDF's deadline-ordered red-black tree for normal tasks) are for dispatch; the wait queues are for blocking; and stopped, traced, zombie, and parked tasks need no list at all. Resource limits (RLIM_NLIMITS = 16) are enforced per thread group through signal->rlim, while the four per-user totals live in namespace-aware ucounts.
  • Switching is a three-layer act. context_switch() handles the address space, switch_to() / __switch_to() handles the architectural registers, and finish_task_switch() does the cleanup that can only safely run once the new task is on the CPU — including releasing the descriptor of a task that just died. PCID/ASID tagging, KPTI PGD swapping, FSGSBASE, PKRU, and the FPU/SIMD save (with its restore deferred to the return to user mode) all live in this path.
  • Creation is one function with many front doors. fork(), vfork(), clone(), and clone3() all converge on kernel_clone() → copy_process(), which replaced 2.6's do_fork(). clone3()'s versioned struct clone_args is the extensible interface that made CLONE_PIDFD, set_tid, and cgroup placement at fork time possible. Copy-on-write means the expensive-looking fork() copies page tables, not pages.
  • Kernel threads are ordinary tasks with no mm. They are marked PF_KTHREAD, are immune to signals they do not explicitly accept, and are managed through a small lifecycle protocol — kthread_should_stop(), kthread_stop(), and park/unpark for per-CPU threads. kthread_use_mm() lets one temporarily borrow a user address space, which is how io_uring and vhost workers touch user memory.
  • Namespaces are now a framework, not eight special cases. Every namespace embeds a struct ns_common with a two-tier refcount that separates memory lifetime from userspace visibility, a stable 64-bit ns_id, and membership in rbtree-indexed namespace trees that the listns() syscall enumerates. PID and time namespaces both use the "for children" deferral pattern; user namespaces are what make unprivileged containers possible.
  • Termination is a long, ordered teardown. do_exit() releases resources in a strict order, exit_notify() reparents orphans — consulting the child_subreaper chain before falling back to the namespace's init — and the task lingers as a zombie only so its parent can read the exit status. release_task() does the final removal, and the very last reference is dropped by the next task to run, in finish_task_switch(). A parent that ignores SIGCHLD gets autoreaping instead of zombies.
  • Waiting is namespace- and pidfd-aware. The whole wait() family funnels into do_wait(), whose child_wait_callback() filters wakeups so a process with many children is not woken for every unrelated exit. waitid(P_PIDFD, …) closes the PID-reuse race that waitpid() can never fully avoid.
