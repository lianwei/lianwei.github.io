You could think of the kernel as a server that answers requests; these requests come either from a process running on a CPU or an external device issuing an interrupt. Parts of the kernel are not run serially, but in an interleaved way — and on multiprocessor systems, truly in parallel. This interleaving gives rise to race conditions, which must be controlled through proper synchronization techniques. Linux 7.0.12 offers a rich hierarchy of locking primitives, from the nearly invisible per-CPU variables and atomic operations to the heavyweight sleeping mutexes and wound/wait deadlock avoidance. This chapter explains when synchronization is needed, which primitives exist, how they work internally, and how to choose the right tool for each situation.

Two definitions underpin everything that follows. A race condition exists when the correctness of a computation depends on the relative timing of two or more concurrent execution paths — that is, when some interleaving of their instructions produces a result that no serial ordering would produce. A critical region is a stretch of code that accesses shared data and must therefore not be interleaved with any other execution path that touches the same data. Synchronization is the discipline of ensuring that every critical region is entered by only as many execution paths as the data can tolerate — usually one writer, sometimes many readers.

The difficulty is that the granularity at which the programmer thinks is not the granularity at which the machine executes. Consider a shared counter incremented from two CPUs. In C it is a single expression, and it is tempting to read it as a single indivisible act:

counter++;              /* looks atomic; is not */

The processor sees three separate operations — load, add, store — and any other CPU may act between them. If both CPUs load the value 5, both compute 6, and both store 6, one increment has silently vanished. No amount of care in the C source prevents this, because the problem is not in the source; it is in the fact that a read-modify-write sequence is not indivisible at the hardware level. The two architectures this book follows solve it differently, and the difference explains a great deal about the primitives in this chapter.

On x86_64 the instruction set offers read-modify-write instructions that can be made atomic with a lock prefix, which is exactly what the kernel emits:

/* arch/x86/include/asm/atomic.h:30 */
static __always_inline void arch_atomic_add(int i, atomic_t *v)
{
        asm_inline volatile(LOCK_PREFIX "addl %1, %0"
                     : "+m" (v->counter)
                     : "ir" (i) : "memory");
}

ARM64 is a load-store architecture and has no such instruction. It instead provides a load-exclusive / store-exclusive pair: ldxr takes a reservation on the address, stxr succeeds only if nothing has touched it since, and the code retries until it does:

// arch/arm64/include/asm/atomic_ll_sc.h -- the LL/SC form
        prfm    pstl1strm, %2
1:      ldxr    %w0, %2
        add     %w0, %w0, %w3
        stxr    %w1, %w0, %2
        cbnz    %w1, 1b          // retry if the reservation was lost

Armv8.1 added the Large System Extensions (LSE), which restore a single-instruction form — stadd for an atomic add. Linux does not choose between them at compile time. arch/arm64/include/asm/lse.h (line 26) wraps both forms in an ALTERNATIVE(llsc, lse, ARM64_HAS_LSE_ATOMICS). The compiled image therefore contains the LL/SC sequence, and the alternatives framework overwrites it in place during boot — in apply_boot_alternatives() and later apply_alternatives_all() (arch/arm64/kernel/alternative.c) — if the CPU reports the ARM64_HAS_LSE_ATOMICS capability. Operations that return a value use a slightly different mechanism, alternative_has_cap_likely(), which resolves to a patched branch rather than a patched instruction, but the effect is the same: one source-level API, two machine encodings, chosen after the kernel has seen the hardware. This is a pattern worth noticing early, because it recurs throughout the chapter: the kernel presents one portable API, and the cost behind it depends on hardware the caller never sees.

How the Kernel Services Requests

To understand concurrency in the kernel, consider it as a waiter servicing two kinds of clients: customers (user-mode processes issuing system calls and exceptions) and bosses (hardware interrupts). The waiter's policy is:

  1. If a boss calls while the waiter is idle, the waiter starts servicing the boss.
  2. If a boss calls while the waiter is servicing a customer, the waiter interrupts the customer and starts servicing the boss.
  3. If a boss calls while the waiter is already servicing another boss, the waiter nests — it pauses the first boss's work and handles the new boss. When the new boss is done, it resumes the previous one.
  4. A boss (interrupt) may set a flag indicating that the current customer should be replaced. After all boss work is done, the waiter may drop the current customer and pick up a new one.

The services performed by the waiter correspond to code executed with the CPU in kernel mode; while the CPU runs user-mode code the waiter is considered idle. Rules 1–3 describe nested kernel control paths (Chapter 4). Rule 4 describes kernel preemption.

In practical terms, kernel code can be interrupted at almost any point by hardware interrupts, and on an SMP system multiple CPUs execute kernel code simultaneously. Any shared data structure can be accessed concurrently, creating race conditions unless the programmer takes explicit precautions.

How a Customer Request Arrives

A customer request is a deliberate transition from user mode to kernel mode, and the instruction that makes it is architecture-specific. The x86 instructions used by Linux 2.6, int $0x80 and sysenter, are no longer the normal path.

On x86_64 a 64-bit process issues the syscall instruction. The CPU loads the entry point from the MSR_LSTAR model-specific register, written at boot in syscall_init() (arch/x86/kernel/cpu/common.c, line 2267), and lands on entry_SYSCALL_64 (arch/x86/entry/entry_64.S, line 87). Vector 0x80 still exists, but only for 32-bit binaries: the IDT entry at IA32_SYSCALL_VECTOR points at asm_int80_emulation or entry_INT80_32 depending on configuration (arch/x86/kernel/idt.c, lines 124–126).

On ARM64 the instruction is svc #0, which raises a synchronous exception from EL0 to EL1. The vector routes to el0t_64_sync_handler(), which decodes the exception class and dispatches to el0_svc() and then do_el0_svc() (arch/arm64/kernel/entry-common.c, lines 737, 718, 724).

What matters here is not the instruction but its consequence: on the far side of it, the CPU is running kernel code on the same task, using that task's kernel stack, with current still pointing at it.

Interrupts are the detail worth being precise about, because the whole chapter depends on it. Both architectures arrive with interrupts masked: x86_64 clears the flags named in MSR_SYSCALL_MASK, including IF (arch/x86/kernel/cpu/common.c, line 2292), and ARM64 enters EL1 with the DAIF bits set. Neither leaves them that way. ARM64 re-enables them explicitly one call before the syscall body:

/* arch/arm64/kernel/entry-common.c:718 */
static void noinstr el0_svc(struct pt_regs *regs)
{
        arm64_enter_from_user_mode(regs);
        cortex_a76_erratum_1463225_svc_handler();
        fpsimd_syscall_enter();
        local_daif_restore(DAIF_PROCCTX);   /* interrupts on from here */
        do_el0_svc(regs);
        arm64_exit_to_user_mode(regs);
        fpsimd_syscall_exit();
}

So the masking lasts only for the few instructions that establish a valid kernel context. By the time any system call implementation runs, the waiter has picked up a customer and a boss may call at any moment. Boss requests, which arrive asynchronously rather than by request, are the subject of Chapter 4, Interrupts and Exceptions.

The Four Execution Contexts

The waiter analogy has two roles, but Linux 7.0.12 distinguishes four execution contexts, and almost every rule in this chapter is stated in terms of them. A given line of kernel code may run in more than one, and what it is allowed to do depends on which one it is in at the time:

  • Task context (also called process context). The kernel is running on behalf of a task, on that task's kernel stack, and current is meaningful. This is the only context that may sleep — that is, the only one in which a mutex may be taken, memory allocated with GFP_KERNEL, or user memory touched. Kernel threads such as the kworker pool and ksoftirqd also run here, which is worth stressing: task context does not imply that any user process is waiting.
  • Softirq context. Deferred work — softirqs, tasklets, and BH workqueues — runs after a hardware interrupt handler returns, or from ksoftirqd when the backlog grows. It may not sleep. It is not associated with the task it happens to interrupt, so current is whatever task was unlucky enough to be running.
  • Hardirq context. An interrupt handler, entered with local interrupts disabled on this CPU (whether the interrupt line is also masked depends on the flow handler — handle_level_irq() masks it, handle_fasteoi_irq() normally does not; see Chapter 4). It may not sleep, and it must be short, because everything else on the CPU is stopped while it runs.
  • NMI context. A non-maskable interrupt, which can arrive even with interrupts disabled — including in the middle of a handler that is holding a lock. NMI code therefore cannot take any lock that non-NMI code might already hold — doing so deadlocks the CPU against itself, and no amount of interrupt disabling prevents it. NMI handlers are restricted to lock-free techniques, per-CPU data, and at most locks taken exclusively from NMI context.

The kernel records which of these it is in inside the preempt_count word described in the next section, and exposes four queries for it:

/* include/linux/preempt.h:118-133 */
/*
 * Macros to retrieve the current execution context:
 *
 * in_nmi()             - We're in NMI context
 * in_hardirq()         - We're in hard IRQ context
 * in_serving_softirq() - We're in softirq context
 * in_task()            - We're in task context
 */
#define in_nmi()                (nmi_count())
#define in_hardirq()            (hardirq_count())
#define in_serving_softirq()    (softirq_count() & SOFTIRQ_OFFSET)
#define in_task()               (!(preempt_count() & \
                                   (NMI_MASK | HARDIRQ_MASK | SOFTIRQ_OFFSET)))

Two older macros, in_softirq() and in_interrupt(), survive but the header now marks them explicitly as deprecated and not to be used in new code. The reason is that they conflate two different questions. in_softirq() tests the whole SOFTIRQ_MASK, which is non-zero both when a softirq is genuinely executing and when some unrelated code has merely called local_bh_disable(); only in_serving_softirq(), which tests the single SOFTIRQ_OFFSET bit, answers the question people usually mean. Code that branches on in_interrupt() to decide whether it may sleep is asking a question with no reliable answer, which is why the modern advice is that a function should know its own context from its caller rather than interrogate the CPU at runtime.

Under CONFIG_PREEMPT_RT the accounting moves: softirq_count() is redefined to read current->softirq_disable_cnt (include/linux/sched.h, line 1266) rather than a field of preempt_count, because on an RT kernel softirqs are serialised per task rather than per CPU. The queries above still work; what they are reading has changed underneath them.

Where the Waiter Analogy Breaks Down

The analogy is worth keeping, because it captures the asymmetry between synchronous and asynchronous work exactly. But it was written for a single-processor kernel, and a reader who leans on it too hard will draw three wrong conclusions.

There is more than one waiter. On SMP there is one waiter per CPU and a single shared set of tables. Every rule in the analogy is about what one waiter does with one request at a time, so the analogy says nothing whatever about the most important race in a modern kernel: two CPUs writing the same structure at the same instant. This is why disabling interrupts — which perfectly solves the boss-interrupts-customer problem — is not a lock, and why almost every primitive in this chapter has both an SMP aspect and a local-interrupt aspect.

Not all work belongs to a boss or a customer. Softirqs and tasklets are work that a boss handed over to be done later; they run in neither role, and they cannot sleep even though no interrupt is in progress. Kernel threads are the opposite case — the waiter tidying the kitchen with nobody at the table. A kworker running a work item, or ksoftirqd draining a softirq backlog, is in full task context and may sleep, yet no user process is waiting on it. Data shared with either of these needs protection that the four rules do not suggest.

Under PREEMPT_RT the bosses become employees. The defining property of a boss is that he cannot be made to wait. Forced threading breaks exactly that: with CONFIG_IRQ_FORCED_THREADING, most interrupt handlers run in scheduled kernel threads, and the timer softirq is drained by a dedicated ktimers/N thread (kernel/softirq.c, lines 1110–1150). A threaded handler is scheduled like anything else, can block on an rt-mutex, and can be preempted by a higher-priority task. Code written on the assumption that an interrupt handler is atomic with respect to everything else on its CPU is simply wrong on an RT kernel, which is why this chapter treats the RT case alongside the stock one rather than as an appendix.

Kernel Preemption

A kernel is preemptive if a process switch can occur while the replaced process is executing kernel code. Linux distinguishes two kinds of process switches:

  • Planned process switch: A kernel path voluntarily calls schedule() — for example, because it must sleep waiting for I/O. This happens in both preemptive and non-preemptive kernels.
  • Forced process switch: An asynchronous event (such as an interrupt awakening a higher-priority task) causes the scheduler to replace the current task involuntarily. This happens only in preemptive kernels.

The main motivation for kernel preemption is to reduce dispatch latency — the delay between a task becoming runnable and actually getting the CPU. Real-time workloads (audio/video pipelines, industrial controllers), interactive desktops, and network-intensive servers all benefit from lower dispatch latency. Without preemption, a high-priority task awakened by an interrupt must wait until the currently-running kernel path either returns to user mode or voluntarily calls schedule() — potentially hundreds of microseconds or even milliseconds later.

It is fair to ask why a chapter on synchronization opens with a scheduling feature. The answer is that kernel preemption is the reason a great deal of the rest of the chapter exists. Before it was introduced, a kernel path on a uniprocessor could assume that nothing else would touch its data unless an interrupt arrived, so disabling interrupts was very nearly a complete defence. Preemption destroyed that assumption: two ordinary tasks can now be inside the same critical region on the same CPU, with no interrupt involved at all. Every primitive in this chapter that is described as “also disabling preemption” — and that is most of them, including the plain spin_lock() — is doing so because of what this section describes.

Two clarifications are worth making at the outset, because both are common misreadings.

The first is that disabling preemption is not a lock. It prevents the scheduler from replacing the current task on this CPU. It does nothing whatever about another CPU running the same code at the same instant, and nothing about an interrupt handler on this CPU. A preempt_disable() region is safe against exactly one of the five sources of concurrency listed earlier in this chapter, and treating it as general mutual exclusion is a classic way to write code that passes every test on a uniprocessor and corrupts data in the field.

The second is that preemption is no longer a single on/off switch. Linux 2.6 had a binary choice, CONFIG_PREEMPT set or not. Linux 7.0.12 offers five models, from PREEMPT_NONE through PREEMPT_RT, and with CONFIG_PREEMPT_DYNAMIC the choice among the first few can be made at boot time rather than at build time — which is why a distribution can now ship one kernel binary for servers, desktops, and low-latency workloads alike. Newest of them is lazy preemption, which reduces the throughput cost of a preemptible kernel by deferring most preemption to the next tick.

The rest of this section works through that machinery from the bottom up. It begins with preempt_count, the single word that records both how deeply preemption is disabled and which execution context the CPU is in, and with the different places the two architectures keep it. It then surveys the five preemption models and the macros that manipulate the counter, before turning to the question of what actually happens at the moment preemption occurs — where the preemption points are, and how the scheduler is entered from them. Two shorter parts cover the mechanisms that are new since Linux 2.6: the TIF_NEED_RESCHED flags and lazy preemption, and the static-call machinery that makes CONFIG_PREEMPT_DYNAMIC possible. The section closes with PREEMPT_RT, which is best understood as the logical end point of the same progression, and with a comparison against Linux 2.6.

The preempt_count Field

Kernel preemption is governed by a single integer called preempt_count. Logically it belongs to the running thread — it says how deeply this execution has disabled preemption — but the two architectures store it in different places, and the difference is visible in the code.

On x86_64 it is not kept with the task at all. It is a per-CPU variable, so that reading it costs one segment-relative load with no dependency on current:

/* arch/x86/include/asm/preempt.h */
DECLARE_PER_CPU_CACHE_HOT(int, __preempt_count);

This raises an obvious question: if the counter lives in a per-CPU variable, what saves and restores it across a context switch? The answer is that nothing does, and nothing needs to. Every context switch happens inside schedule(), with preemption disabled, so preempt_count holds the same known value on the way out as it does on the way in. The scheduler guarantees the invariant, and the switch code is spared the work.

ARM64 takes the other approach and keeps the counter per task, in thread_info, where current_thread_info() finds it:

/* arch/arm64/include/asm/preempt.h:10 */
static inline int preempt_count(void)
{
        return READ_ONCE(current_thread_info()->preempt.count);
}

The counter itself is 32 bits on both architectures and packs the same sub-fields. Where the two differ is the inverted need-resched flag: x86_64 folds it into bit 31 of that same word, while ARM64 places it in a second 32-bit half of a u64, as PREEMPT_NEED_RESCHED = BIT(32), with count and flag declared as a union so that one 64-bit test covers both. The figure and table below show the x86_64 layout; on ARM64, read the need-resched field as a separate word above the one drawn here.

The rule is simple: preemption is permitted only when preempt_count == 0 (more precisely, when the value with the MSB masked off is zero). The field is greater than zero when any of the following conditions holds:

  1. The kernel is executing an interrupt service routine (hardirq count > 0).
  2. Deferrable functions (softirqs/tasklets) are disabled or executing (softirq count > 0).
  3. Kernel preemption has been explicitly disabled via preempt_disable() (preemption depth > 0).

These rules mean the kernel can be preempted only when it is executing an exception handler (in particular a system call), the kernel preemption has not been explicitly disabled, and local interrupts are enabled.

On x86_64, the kernel uses a clever optimization: bit 31 (PREEMPT_NEED_RESCHED) is the inverse of the need-resched condition. This means preempt_enable() can test for "counter is zero AND reschedule is needed" with a single decrement-and-test-for-zero instruction — if the decrement result is exactly 0x00000000 (all counter bits zero AND the resched bit cleared), a call to preempt_schedule() is needed. This eliminates a separate branch to read thread_info.flags, which was the approach used in Linux 2.6.

The counter encoded three sub-fields (preemption depth, softirq count, and hardirq count) but had no NMI tracking and no embedded need-resched bit.

Evolution from Linux 2.6

In Linux 2.6.11, preemption was a simple compile-time binary choice: either CONFIG_PREEMPT=y (preemptive kernel) or not set (non-preemptive). There was no concept of multiple preemption "models":

  • Non-preemptive (CONFIG_PREEMPT not set): The kernel could never be forcibly preempted. Process switches happened only at voluntary schedule() calls or on return to user mode. This was the default for all distributions until the 2.6 series.
  • Preemptive (CONFIG_PREEMPT=y): The kernel could be preempted at any point where preempt_count == 0. This was introduced in Linux 2.5 and was considered a "low-latency desktop" feature.

The PREEMPT_VOLUNTARY option was added shortly after 2.6.11 (in 2.6.13, by Ingo Molnár) as a middle ground — inserting cond_resched() calls at strategic points without enabling full forced preemption. PREEMPT_NONE was simultaneously formalized as the explicit "no preemption" choice (previously it was simply "CONFIG_PREEMPT not set").

PREEMPT_NONE — No Forced Preemption (Server)

This is the traditional Linux preemption model, geared towards maximum throughput. The kernel will never forcibly preempt a task running in kernel mode. A process switch occurs only when:

  • The kernel code path explicitly calls schedule() (e.g., to wait for I/O).
  • The kernel is about to return to user mode and finds TIF_NEED_RESCHED set.

While this provides good throughput, latencies can be unbounded: a CPU-bound system call (e.g., a large copy_to_user() or a long pathname lookup) will delay higher-priority tasks until it completes. Select this for database servers, batch computation nodes, and HPC systems where throughput matters more than response time.

PREEMPT_VOLUNTARY — Voluntary Kernel Preemption (Desktop)

This model inserts explicit preemption check points throughout the kernel via cond_resched() and might_sleep(). These functions check whether TIF_NEED_RESCHED is set and, if so, voluntarily call schedule():

/* kernel/sched/core.c */
int __sched __cond_resched(void)
{
    if (should_resched(0) && !irqs_disabled()) {
        preempt_schedule_common();
        return 1;
    }
#ifndef CONFIG_PREEMPT_RCU
    rcu_all_qs();  /* Report RCU quiescent state */
#endif
    return 0;
}

The might_sleep() macro additionally serves as a debugging aid — when called from atomic context (where sleeping would be a bug), it triggers a warning:

/* include/linux/kernel.h */
# define might_sleep() \
    do { __might_sleep(__FILE__, __LINE__); might_resched(); } while (0)

In this model, might_resched() calls __cond_resched(). The kernel source contains thousands of cond_resched() calls in long-running loops (filesystem traversals, memory reclaim, network packet processing) to bound worst-case latency to a few milliseconds. Select this for general-purpose desktop systems.

PREEMPT — Preemptible Kernel (Low-Latency Desktop)

This model makes all kernel code preemptible except critical sections protected by preempt_disable(), spinlocks, or interrupt handlers. The key difference from PREEMPT_VOLUNTARY: preemption happens automatically at the moment preempt_count drops to zero — there is no need for explicit check points.

When a higher-priority task is awakened (e.g., by an interrupt), the scheduler sets TIF_NEED_RESCHED. At the very next preempt_enable() or spin_unlock(), the counter hits zero, the kernel detects the resched flag, and calls preempt_schedule() immediately. This reduces worst-case latency from milliseconds to hundreds of microseconds.

With CONFIG_PREEMPT, cond_resched() becomes a no-op (it's not needed — preemption happens everywhere anyway). The slight cost is increased context-switch overhead from more frequent switches that disturb CPU caches.

PREEMPT_LAZY — Scheduler-Controlled Preemption

New in Linux 7.0.12, PREEMPT_LAZY is a compromise between full preemption and voluntary preemption. It is fundamentally similar to PREEMPT (full) but less eager to preempt SCHED_NORMAL tasks. The scheduler uses TIF_NEED_RESCHED_LAZY instead of TIF_NEED_RESCHED for non-urgent reschedules. The lazy flag does not trigger immediate preemption at preempt_enable() — instead, preemption is deferred until the next timer tick (typically 1–4ms):

/* kernel/sched/core.c – scheduler_tick() */
if (dynamic_preempt_lazy() && tif_test_bit(TIF_NEED_RESCHED_LAZY))
    resched_curr(rq);  /* promotes lazy → immediate */

This recovers some throughput gains of voluntary preemption while keeping the preemptible kernel infrastructure for real-time tasks (which still get immediate TIF_NEED_RESCHED). On architectures that support it (CONFIG_ARCH_HAS_PREEMPT_LAZY — currently ARM64), this is the default preemption model.

The key benefit: lock holder preemption (where a task holding a spinlock is preempted, forcing other CPUs to spin longer) is reduced, because the tick-based deferral gives lock holders time to release their locks naturally.

PREEMPT_RT — Fully Preemptible Kernel (Real-Time)

PREEMPT_RT transforms the kernel for hard real-time use by making nearly everything preemptible. It requires CONFIG_EXPERT and architecture support. Key changes:

  • spinlock_t becomes a sleeping rt_mutex with priority inheritance
  • rwlock_t becomes a sleeping rwbase_rt lock
  • Interrupt handlers run as SCHED_FIFO kernel threads (threaded IRQs)
  • Only raw_spinlock_t and a few critical paths remain non-preemptible
  • Softirqs execute in dedicated kernel threads, eliminating long softirq processing delays

Under PREEMPT_RT, worst-case latency drops to tens of microseconds on well-tuned systems. The trade-off is lower peak throughput (5–15% typical) due to the overhead of priority inheritance, thread scheduling for interrupts, and reduced batching.

Implementation Details

The preempt_disable() macro is deceptively simple:

/* include/linux/preempt.h */
#define preempt_disable() \
do { \
    preempt_count_inc(); \
    barrier(); \
} while (0)

The barrier() after the increment is critical: it prevents the compiler from reordering instructions across the preemption-disable boundary. Without it, the compiler might move accesses to per-CPU data before the increment, creating a race where the code accesses per-CPU data without preemption protection.

The preempt_enable() macro is more complex and differs depending on whether the kernel is built with CONFIG_PREEMPTION:

/* include/linux/preempt.h — CONFIG_PREEMPTION enabled */
#define preempt_enable() \
do { \
    barrier(); \
    if (unlikely(preempt_count_dec_and_test())) \
        __preempt_schedule(); \
} while (0)

Here barrier() comes before the decrement — this ensures all critical-section memory accesses complete before preemption is re-enabled. The preempt_count_dec_and_test() function is architecture-specific. On x86_64, it uses a single decl instruction with a conditional jump on zero:

/* arch/x86/include/asm/preempt.h */
static __always_inline bool __preempt_count_dec_and_test(void)
{
    return GEN_UNARY_RMWcc("decl", __my_cpu_var(__preempt_count), e,
                           __percpu_arg([var]));
}

The GEN_UNARY_RMWcc macro generates a decl %gs:__preempt_count instruction and sets the condition code e (equal/zero). Because of the inverted PREEMPT_NEED_RESCHED bit in bit 31, the entire word reaching zero means both "preempt_count is zero" AND "reschedule is needed" — a two-condition check in a single instruction.

When CONFIG_PREEMPTION is not set (non-preemptive kernels), preempt_enable() simply decrements the counter without any reschedule check:

/* include/linux/preempt.h — no CONFIG_PREEMPTION */
#define preempt_enable() \
do { \
    barrier(); \
    preempt_count_dec(); \
} while (0)

And when CONFIG_PREEMPT_COUNT is also disabled (for maximum throughput), all these macros become plain barrier() calls — the preemption counter doesn't exist at all, and the compiler barriers are the only remaining effect.

The should_resched() Helper

The should_resched() function tests whether the preempt_count equals a given offset (typically 0), which implicitly checks both that all counters are zero and that PREEMPT_NEED_RESCHED is cleared (meaning a reschedule is pending):

/* arch/x86/include/asm/preempt.h */
static __always_inline bool should_resched(int preempt_offset)
{
    return unlikely(raw_cpu_read_4(__preempt_count) == preempt_offset);
}

This is used by cond_resched() (with offset 0) and by the interrupt return path to decide whether preemption should occur.

Scoped Preemption with guard()

Linux 7.0.12 introduces scoped lock guards (via include/linux/cleanup.h) that use the GCC/Clang __attribute__((cleanup)) to automatically re-enable preemption when a variable goes out of scope:

/* include/linux/preempt.h */
DEFINE_LOCK_GUARD_0(preempt, preempt_disable(), preempt_enable())

Usage in kernel code:

void some_function(void)
{
    guard(preempt);  /* preempt_disable() called here */

    /* ... access per-CPU data safely ... */
    ptr = this_cpu_ptr(&per_cpu_data);
    ptr->counter++;

    /* preempt_enable() called automatically at scope exit */
}

This eliminates the common bug of forgetting to call preempt_enable() on error paths — a class of bug that historically caused hard-to-debug "scheduling while atomic" warnings.

A Typical Usage Pattern

preempt_disable();           /* preempt_count: 0 → 1 */
/* ... critical section: safe from preemption ... */
ptr = this_cpu_ptr(&per_cpu_data);
ptr->counter++;
preempt_enable();            /* preempt_count: 1 → 0, may reschedule */

Calls nest correctly — each preempt_disable() must have a matching preempt_enable():

preempt_disable();           /* count: 0 → 1 */
  preempt_disable();         /* count: 1 → 2 */
  preempt_enable();          /* count: 2 → 1 (no reschedule, count > 0) */
preempt_enable();            /* count: 1 → 0 (may reschedule now) */

The get_cpu() / put_cpu() pair is a common idiom for code that needs both the CPU number and preemption protection:

int cpu = get_cpu();         /* preempt_disable() + smp_processor_id() */
per_cpu(my_data, cpu).x++;
put_cpu();                   /* preempt_enable() */

How Preemption Actually Happens

Preemption can be triggered at three distinct points in kernel execution:

1. Return from preempt_enable() — The most common path. When a kernel code path re-enables preemption and a higher-priority task is waiting:

/* include/linux/preempt.h (simplified) */
#define preempt_enable() \
do { \
    barrier(); \
    if (unlikely(preempt_count_dec_and_test())) \
        __preempt_schedule(); \
} while (0)

The preempt_count_dec_and_test() decrements the counter and returns true if the result is zero (on x86_64, this is a single decl + jz). __preempt_schedule() is the actual call to the scheduler:

/* kernel/sched/core.c */
asmlinkage __visible void __sched notrace preempt_schedule(void)
{
    if (likely(!preemptible()))
        return;
    preempt_schedule_common();
}

static void __sched notrace preempt_schedule_common(void)
{
    do {
        preempt_disable_notrace();
        preempt_latency_start(1);
        __schedule(SM_PREEMPT);
        preempt_latency_stop(1);
        preempt_enable_no_resched_notrace();
    } while (need_resched());
}

The SM_PREEMPT flag tells the scheduler this is an involuntary switch. The loop handles the case where yet another reschedule is requested between __schedule() returning and preemption being re-enabled.

2. Return from interrupt in kernel mode — When an interrupt fires while kernel code is running, the return path calls preempt_schedule_irq():

/* kernel/sched/core.c */
asmlinkage __visible void __sched preempt_schedule_irq(void)
{
    BUG_ON(preempt_count() || !irqs_disabled());

    do {
        preempt_disable();
        local_irq_enable();
        __schedule(SM_PREEMPT);
        local_irq_disable();
        sched_preempt_enable_no_resched();
    } while (need_resched());
}

This function runs with interrupts disabled (just returned from IRQ context). It temporarily re-enables them for the actual scheduling, then loops until no more reschedules are pending.

3. Return from interrupt/exception to user mode — On return to user mode, the kernel always checks TIF_NEED_RESCHED in the thread flags and calls schedule() if set. This happens in all preemption models, even PREEMPT_NONE, because the kernel can always switch tasks at user-mode boundaries.

TIF_NEED_RESCHED and Lazy Preemption

The TIF_NEED_RESCHED flag in the thread's thread_info.flags is set by the scheduler whenever it determines that the current task should be replaced — for example, when try_to_wake_up() awakens a higher-priority task, or when a task exhausts its time quantum.

Linux 7.0.12 introduces lazy preemption via a second flag, TIF_NEED_RESCHED_LAZY. The key insight: immediate preemption provides great latency but hurts throughput because it forces frequent context switches that pollute caches. Lazy preemption sets TIF_NEED_RESCHED_LAZY instead of TIF_NEED_RESCHED for non-urgent reschedules, deferring the actual switch until the next timer tick:

/* kernel/sched/core.c */
static __always_inline int get_lazy_tif_bit(void)
{
    if (dynamic_preempt_lazy())
        return TIF_NEED_RESCHED_LAZY;
    return TIF_NEED_RESCHED;
}

On the timer tick path (scheduler_tick()), the kernel promotes lazy reschedules to immediate ones:

/* kernel/sched/core.c – scheduler_tick() */
if (dynamic_preempt_lazy() && tif_test_bit(TIF_NEED_RESCHED_LAZY))
    resched_curr(rq);   /* sets TIF_NEED_RESCHED, triggering preemption */

This gives PREEMPT_LAZY model a behavior between PREEMPT_NONE and PREEMPT (full): preemption happens, but is deferred by up to one tick (typically 1–4ms). ARM64 has a dedicated TIF_NEED_RESCHED_LAZY bit (bit 2); x86_64 currently falls back to TIF_NEED_RESCHED when lazy preemption is not available at the architecture level.

PREEMPT_RT: The Fully Preemptible Kernel

PREEMPT_RT takes a radically different approach: instead of restricting preemption to moments when preempt_count == 0, it makes nearly all critical sections preemptible by converting spinlock_t from a spinning lock into a sleeping rt_mutex. This means:

  1. Spinlock holders can be preempted — unlike regular spinlocks which disable preemption while held, RT-mutex-based locks allow the holder to sleep or be preempted.
  2. Priority inheritance — if a high-priority task blocks on a lock held by a low-priority task, the low-priority task temporarily inherits the higher priority to prevent unbounded priority inversion.
  3. Interrupt handlers run in threads — hardirqs become SCHED_FIFO kernel threads, making them preemptible and subject to priority scheduling.
  4. Only raw_spinlock_t remains non-preemptible — used for the scheduler itself, the timer system, and a few other critical paths that cannot tolerate sleeping.

Under PREEMPT_RT, the worst-case latency drops from milliseconds to tens of microseconds, making Linux suitable for hard real-time applications.

When Synchronization Is Necessary

Chapter 1 introduced the concept of critical region — a section of code that accesses shared data and must not be executed concurrently by another execution context. A closely related concept is the race condition: it occurs when the outcome of a computation depends on how two or more interleaved kernel control paths are nested. A critical region is the code section that must be executed atomically to prevent race conditions.

Synchronization is required whenever two or more kernel control paths can access the same data structure concurrently and at least one of those accesses is a write. Identifying and protecting critical regions is one of the hardest tasks in kernel development — once a critical region has been identified, it must be suitably protected to ensure that at most one kernel control path is inside that region at any time.

What makes this hard is not writing the lock, it is knowing that a lock is needed at all. A missing lock produces no compiler warning and no immediate symptom. The window in which the race can occur is often a handful of instructions wide, so the buggy code may run correctly billions of times before the interleaving that breaks it finally happens — typically on a customer's larger machine, under a load the developer never reproduced, months after the code was merged. The bug is in the code from the first day; only its manifestation is rare. This asymmetry is why the kernel invests so heavily in the reasoning discipline and the tooling described in this section: the goal is to establish that code is race-free by argument, not by observing that it has not yet crashed.

Two developments since Linux 2.6 have changed how this reasoning is done. First, the kernel now has a written, formal memory model — the Linux-Kernel Memory Model in tools/memory-model/ — so questions about whether a given access pattern is legal have a definitive answer rather than a folk one. Second, the kernel has a runtime data-race detector, KCSAN, so a whole class of missing-synchronization bugs can now be found deliberately instead of waiting for them to surface. This section covers what concurrency the kernel developer must anticipate, what happens when it is not handled, and how to decide what needs protecting.

Race Conditions and Data Races

Modern kernel documentation carefully distinguishes two problems that are easily conflated: race conditions and data races. The distinction matters because they are found by different means and fixed by different tools.

A race condition is a defect in the algorithm: the code's result depends on the order in which concurrent paths interleave. Checking that a file exists and then opening it is a race condition even if every individual memory access is perfectly atomic, because the file can be removed in between. Race conditions are a matter of program logic, and no amount of access marking will fix one — the fix is to hold a lock across the whole operation, or to restructure it so the check and the action are a single atomic step.

A data race is narrower and is defined by the language and memory model rather than by the algorithm. Documentation/dev-tools/kcsan.rst gives the definition precisely: two memory accesses form a data race if they conflict — they touch the same location and at least one is a write — they happen concurrently in different threads, and at least one of them is a plain (unmarked) C access.

The reason the "plain access" clause is there is that a plain access grants the compiler complete freedom. The compiler is entitled to assume that no other thread is touching the variable, so it may fuse two reads into one, split a single store into several narrower ones, spill a value to the variable and reload it, or re-materialize a load it had already performed. Each of these is a legal optimization for single-threaded code, and each can break concurrent code that looked correct in the source. A data race is therefore undefined behavior, not merely a timing hazard: the machine code the compiler emits need not correspond to the program that was written.

The kernel's answer is to mark accesses that are deliberately concurrent, which both constrains the compiler and records the intent for tooling and for the next reader. tools/memory-model/Documentation/access-marking.txt enumerates the options:

Sources of Concurrency

Interleaving of kernel control paths arises from multiple sources. The developer must consider all of them when deciding what protection a data structure needs — it is enough to overlook one to have an unprotected critical region. A useful habit is to walk this list explicitly for each shared structure rather than reasoning only about the case that prompted the code:

  1. SMP parallelism: Multiple CPUs execute kernel code simultaneously. Any globally visible data structure can be accessed in parallel from different CPUs. Even disabling preemption or interrupts on one CPU does not prevent another CPU from accessing the same data — this is the single most common mistake carried over from uniprocessor thinking.
  2. Interrupt vs. process context: A hardware interrupt can arrive at any time while a process-context path is manipulating a data structure. If the interrupt handler also accesses that data, the process-context code is effectively "preempted" mid-operation. Note that in Linux 7.0.12 handlers always run with interrupts disabled — kernel/irq/handle.c issues a WARN_ONCE() and re-disables them if a handler returns with interrupts on — so hardirq handlers do not nest with one another on a CPU, and the hazard is specifically between interrupt and non-interrupt context.
  3. Softirq/tasklet vs. process context: When a hardirq returns, softirqs execute immediately (on the same CPU). If process-context code was manipulating shared data without disabling bottom halves, the softirq can see a half-updated state.
  4. Softirq concurrency on SMP: The same softirq can run simultaneously on different CPUs (unlike tasklets). Softirq handlers that access global data need their own locking.
  5. Kernel preemption: Under every preemption model except PREEMPT_NONE, a process running in kernel mode can be replaced by another process at any preempt_enable() point, and the new process might access the same data structures. Because CONFIG_PREEMPT_DYNAMIC makes the model selectable at boot or at runtime, code cannot assume at compile time that it is running on a non-preemptible kernel.
  6. CPU migration: Preemption also means the task can resume on a different CPU. Any reasoning that depends on staying on one CPU — per-CPU counters and caches above all — is only valid while preemption or migration is disabled. This is why this_cpu_ptr() requires preemption to be off, and why smp_processor_id() warns when it is not.
  7. Workqueue and kthread concurrency: Kernel worker threads (kworker) and dedicated kernel threads can run on any CPU and may share data structures with other kernel paths. Two different work items from the same workqueue can run concurrently on different CPUs unless the queue was created ordered or with a concurrency limit. A single work item is better behaved: Documentation/core-api/workqueue.rst guarantees it will not be re-entered — at most one worker executes it system-wide — provided nobody changes its work function, requeues it to a different workqueue, or reinitialises it.
  8. Exception nesting: Page faults, debug traps, and other exceptions can occur during kernel execution and may access shared data (e.g., the mm_struct).
  9. NMI context: Non-maskable interrupts — perf sampling, the hardlockup watchdog, some machine-check paths — cannot be blocked by any of the mechanisms above. local_irq_disable() does not stop them. An NMI can therefore land in the middle of a critical region that disabled interrupts, which is why NMI-reachable code must not take a lock that ordinary code might already hold, and instead relies on per-CPU data, atomics, and lock-free structures.
  10. PREEMPT_RT: On a real-time kernel several of the guarantees above are deliberately withdrawn. Most device interrupt handlers become threads, spinlock_t becomes a sleeping rt_mutex, and — as Documentation/locking/locktypes.rst warns — softirq context becomes preemptible, so per-CPU data may not assume that being in a bottom half implies exclusion. Code that is correct only because of non-preemptibility is correct only on non-RT kernels.

Sources 1 through 4 already existed in Linux 2.6. Sources 5 through 10 are, to varying degrees, consequences of how the kernel has changed since: preemption became the norm rather than an option, per-CPU data became pervasive, NMI-context code multiplied with perf and the watchdogs, and PREEMPT_RT moved from an out-of-tree patch set to a supported configuration.

The Consequences of Races

The consequences of inadequate synchronization range from silent data corruption to kernel panics, deadlocks, security vulnerabilities, and undefined behavior. They are worth separating, because they differ enormously in how quickly they are noticed:

  • Silent data corruption is the most dangerous outcome, precisely because nothing appears to go wrong. A corrupted counter, a lost list entry, or a torn pointer may sit in memory for hours before anything reads it, at which point the crash occurs in code that is entirely innocent. The reported stack trace points at the victim, not the culprit.
  • Kernel panics at least fail loudly, but a race that corrupts a list pointer typically panics somewhere far removed from the unlocked write that caused it.
  • Deadlock and livelock arise from the attempted fix as often as from the original bug — an added lock taken in the wrong order, or taken in a context that cannot sleep, converts a rare corruption into a reliable hang.
  • Use-after-free is the classic lifetime race: one path frees an object while another is still dereferencing it. This is why reference counting and RCU exist, and both are covered later in this chapter.
  • Security vulnerabilities follow directly from the above. A race in a permission check is a privilege-escalation primitive, and a use-after-free is frequently exploitable rather than merely fatal. Attackers can also do something the ordinary user cannot: run the racing operation in a tight loop on many CPUs to widen a window that occurs naturally once in a billion executions. A race being "almost impossible to hit" is not a security argument.

Identifying Critical Regions

To identify critical regions, the developer must answer three questions for every shared data structure:

  1. Which kernel control paths access it? (interrupts, softirqs, process context, workqueues, NMI)
  2. What operations do they perform? (read-only, read-write, write-only)
  3. On how many CPUs can these paths run simultaneously? (UP vs. SMP)

The answers determine the primitive. The most restrictive context that touches the data sets the floor: if any accessor runs in interrupt context, no accessor may use a sleeping lock, and the interrupt-safe variant of the chosen lock is required in the paths that do not run with interrupts already disabled. If every accessor is in process context and any of them may sleep, a mutex is appropriate. If readers vastly outnumber writers and the structure is reached through a pointer, RCU may remove the reader-side cost entirely.

Two further habits matter as much as the analysis itself. The first is to write the answer down next to the data, not just next to the lock. The kernel convention is a comment on the structure member naming its protecting lock, so that the invariant survives the next person to touch the code:

struct my_device {
    spinlock_t   lock;       /* protects the fields below */
    unsigned int count;      /* @lock */
    struct list_head items;  /* @lock */
    unsigned long stats;     /* atomic, no lock; diagnostics only */
};

The second is to let the machine check the claim. Reasoning about interleavings is exactly the kind of task humans are bad at, and Linux 7.0.12 ships three tools that turn parts of the argument into something testable. lockdep validates lock ordering and context correctness at runtime; its important property is that the two conflicting acquisition orders never have to occur concurrently for it to complain. Each order need only be observed once, at any time, on any CPU — so, as Documentation/locking/lockdep-design.rst puts it, a deadlock that would normally require more than three CPUs and a very unlikely constellation of tasks, interrupt contexts and timings can be detected on a lightly loaded single-CPU system. KCSAN detects data races directly, and the KCSAN assertions ASSERT_EXCLUSIVE_WRITER() and ASSERT_EXCLUSIVE_ACCESS() let a developer state an invariant such as "only the CPU owning this queue ever writes this field" and have it enforced at runtime. All three are covered in detail in the Lock Validation section at the end of this chapter.

An Example: The Buffer Race

Suppose two different kernel control paths need to access the same data structure, which contains a buffer pointer and an integer indicating its length:

struct shared_buf {
    char *data;
    int   len;
};

static struct shared_buf shared;
static DEFINE_SPINLOCK(buf_lock);

The two fields are not independent: len is only meaningful as a description of the buffer that data currently points to. They must therefore be updated as a unit. If one path writes a new pointer to data and then updates len, while another path reads between those two writes, the reader sees the new data pointer paired with the old len. If the new buffer is shorter than the old one, the reader walks off the end of it — a heap overflow produced by code in which every individual statement is correct.

Note that this is a hazard about the invariant relating two fields, not about the width of either access. Both fields are naturally aligned and word-sized, so each individual store is atomic on x86_64 and ARM64; no store tears. Atomicity of the individual accesses is simply not the property that was needed. The fix is to make the pair of updates atomic with respect to readers by placing every statement that touches either field inside one critical region:

spin_lock(&buf_lock);
shared.data = new_data;
shared.len  = new_len;
spin_unlock(&buf_lock);

Readers must take the same lock; a lock held by only one side protects nothing. With the lock held on both sides the accesses are no longer concurrent, so they are no longer data races either, and they are correctly left as plain C accesses — READ_ONCE() and WRITE_ONCE() are neither required nor wanted here.

The choice of primitive depends on which contexts are involved, and this example is deliberately the simple case. If one of the paths is a hardware interrupt handler, plain spin_lock() is not enough on the process-context side: the interrupt can arrive on the same CPU while the lock is held and spin forever waiting for a lock that only the interrupted code can release. That case requires spin_lock_irqsave(). If instead one path is a softirq, spin_lock_bh() is the right variant. Choosing correctly among these is what the rest of this chapter teaches.

When Synchronization Is Not Necessary

Certain design choices and kernel guarantees eliminate race conditions without explicit locking. Exploiting these guarantees produces faster code — no lock acquisition, no cache-line bouncing, no risk of deadlock — but requires the programmer to prove that the conditions hold and will continue to hold as the code evolves.

This is, for that reason, the most dangerous material in the chapter. Every argument in this section is a conditional proof: the data needs no lock because some premise holds. The trouble is that omitting a lock leaves no trace in the source. A lock that is taken is visible; a lock that was reasoned away is invisible, and so is the reasoning. When someone later calls the function from a new context, or the code is compiled with a different preemption model, the premise quietly stops holding and nothing announces the change — the code still compiles, still passes its tests, and is now wrong.

The practical consequence is a rule that costs nothing and prevents a great deal: whenever a lock is omitted deliberately, write down why, next to the data. A one-line comment naming the premise ("only ever touched from the NAPI poll of this queue") turns an invisible assumption into something the next reader can check and the next patch can be tested against. Where the premise can be expressed to the machine — lockdep_assert_held(), ASSERT_EXCLUSIVE_WRITER(), __ro_after_init — that is better still, because then the compiler or the kernel checks it rather than the reader.

There is a second reason for care that did not apply in Linux 2.6. Several of the guarantees listed below are configuration-dependent, and the set of configurations grew substantially since Linux 2.6. Code that is correct on a non-preemptible kernel may race under PREEMPT_RT, where interrupt handlers become threads and softirq context becomes preemptible. Each rule below therefore states not just the guarantee but the conditions under which it actually holds.

Kernel Execution Ordering Guarantees

The following design rules (many discussed in Chapter 4) restrict how kernel control paths can interleave:

  1. The same interrupt cannot be handled twice at once — while a handler for a given IRQ is running, the genirq layer has set IRQD_IRQ_INPROGRESS on that descriptor (kernel/irq/handle.c, handle_irq_event()), and the flow handlers consult it under desc->lock. Note that the mechanism is this per-descriptor state, not masking of the interrupt line: handle_fasteoi_irq(), the common flow handler on modern x86_64 and ARM64 systems, does not mask the line at all except for IRQS_ONESHOT threaded interrupts.
  2. Interrupt handlers do not nest — in Linux 7.0.12 handlers always run with interrupts disabled, so a different IRQ cannot interrupt one that is executing. This is enforced, not merely conventional: kernel/irq/handle.c issues a WARN_ONCE() and re-disables interrupts if a handler returns with them enabled. (This dates from Linux 2.6.35; before it, handlers registered without SA_INTERRUPT, later IRQF_DISABLED, ran with interrupts enabled and nesting was normal.)
  3. Interrupt handlers, softirqs, and tasklets are non-preemptible and non-blocking — they cannot be suspended by a process context path. On PREEMPT_RT this is not true. force_irqthreads() is unconditionally true there (include/linux/interrupt.h), so device handlers run in schedulable threads unless they are marked IRQF_NO_THREAD, and softirq context is preemptible.
  4. A kernel path in interrupt context cannot be interrupted by a deferrable function or a system call — softirqs and tasklets run only after all hardirq handlers complete; process context doesn't resume until bottom halves finish.
  5. Softirqs and tasklets cannot interleave on the same CPU — on a given CPU, softirqs execute sequentially (the __do_softirq() loop runs with preemption disabled). Again, not on PREEMPT_RT, where softirq processing is preemptible; kernel/softirq.c annotates the local_bh lock with the comment "PREEMPT_RT makes BH preemptible."
  6. The same tasklet cannot run simultaneously on multiple CPUs — tasklet_trylock() sets TASKLET_STATE_RUN with test_and_set_bit() and so admits exactly one runner (include/linux/interrupt.h). Softirqs, by contrast, can run on multiple CPUs simultaneously.
  7. The current task's kernel stack is private — local variables, and anything reachable only from them, cannot be seen by another task. This is the one guarantee in the list that no configuration option weakens.

Rule 7 is often over-generalised into "anything reachable through current is safe", which is false. current reaches a great deal of shared state: current->mm is shared by every thread in the process, current->files and current->fs may be shared depending on how the thread was cloned, and current->signal is per thread-group. A second task can also reach the task's own task_struct — that is precisely what /proc readers, ptrace, and the scheduler do. What is private is the kernel stack, not the task structure.

Examples of Simplifications

  • Interrupt handlers and tasklets need not be reentrant — since the same handler never executes concurrently with itself, there is no need for internal locking against self-preemption.
  • A per-CPU counter incremented only from softirq context needs only local_bh_disable() / local_bh_enable() on the writer side on a non-RT kernel, because softirqs on the same CPU cannot interleave. On PREEMPT_RT that reasoning fails, and the modern portable spelling is a local_lock_t, which costs nothing beyond the existing preempt_disable() on non-RT builds and becomes a real per-CPU lock on RT. Local locks are covered later in this chapter.
  • Kernel data initialized before the structure that references it is registered is safely published by the registration itself. When a driver's module_init() function fills in a private structure and only then calls cdev_add(), register_netdev() or similar, the registration function performs the store that makes the object reachable, and provides the ordering; the initialization needs no barrier of its own. Note that the publication point is the registration call, not the end of module_init() — anything registered halfway through initialization is reachable from that moment on, so any field the registered object exposes must already be valid. What the loader itself guarantees is narrower: another module cannot bind to this one's exported symbols until it reaches MODULE_STATE_LIVE, because strong_try_module_get() returns -EBUSY while it is still MODULE_STATE_COMING (kernel/module/main.c).

Module parameters are a common counter-example rather than an example. It is tempting to treat them as write-once at load time, but a parameter declared with a writable permission such as 0644 is exported to /sys/module/<name>/parameters/ and can be changed at any time thereafter. include/linux/moduleparam.h says so directly: if the parameter is writable, accesses may need kernel_param_lock() around them — especially charp parameters, whose old string is kfree()d when the value changes, making a careless reader a use-after-free.

Caution: Correctness That Depends on Configuration

The classic version of this mistake is code that is correct on a uniprocessor but races on SMP. The kernel's locking primitives compile down to almost nothing on CONFIG_SMP=n — spin_lock() reduces to preempt_disable() — so the correct primitive should be used even in code that "will only ever run on UP". The cost is negligible and the alternative is code that silently breaks the day it is built for SMP.

The same trap now has two more modern forms, and they are considerably easier to fall into because the machine on the developer's desk is usually SMP already:

  • Correct only on non-RT. Any argument of the form "this is safe because it runs in softirq context" or "because interrupt handlers cannot sleep" is an assumption about the preemption model, not about the code. PREEMPT_RT is now a supported in-tree configuration on both x86_64 and ARM64, so that assumption is a build-time coin toss rather than a fact.
  • Correct only on x86_64. The x86 TSO memory model forbids most of the reordering that ARM64 permits, so a missing barrier frequently has no observable effect on x86_64 and fails on ARM64. Code developed and tested only on x86 can carry such bugs indefinitely. This is covered in detail under Memory Barriers later in this chapter.

All three share a shape: the code is not wrong here, so nothing reveals that it is wrong elsewhere. This is what the validation tooling is for — lockdep and KCSAN find these on the machine you have, rather than waiting for the configuration that breaks them.

The rest of this chapter describes what to do when synchronization is necessary — how to prevent data corruption using the rich hierarchy of synchronization primitives available in Linux 7.0.12.

Synchronization Primitives

We now examine how kernel control paths can be interleaved while avoiding race conditions among shared data. Linux 7.0.12 provides a rich hierarchy of synchronization techniques — from the nearly invisible per-CPU variables and atomic operations that avoid locking entirely, through busy-wait spinlocks for short critical sections, to heavyweight sleeping mutexes for longer operations that may involve I/O.

The obvious question, faced with a list this long, is why the kernel needs so many. A user-space programmer typically gets one mutex and one condition variable and does everything with them. The answer is that a kernel primitive has to be paid for out of the latency budget of whatever it protects, and those budgets differ by orders of magnitude. A lock guarding a four-instruction update to a list head cannot afford a context switch; a lock held across a disk read cannot afford to spin. A primitive that is correct in both cases would be badly wrong in each. So rather than one general-purpose lock, the kernel offers a spectrum, and the price of that spectrum is that the programmer must choose.

Underneath the variety there are only three strategies, and it is worth naming them before meeting the individual APIs:

  • Do not share. Give each CPU or each task its own copy, so that there is no concurrent access to serialize. Per-CPU variables are the pure form of this.
  • Share, but make the operation indivisible. If the entire update is a single atomic instruction, no other CPU can observe a half-finished state and no lock is needed. Atomic operations, and the lock-free algorithms built from cmpxchg(), work this way.
  • Share, and make the other path wait. This is locking proper, and the interesting question becomes how the loser waits — by spinning, by sleeping, or (in the case of RCU and seqlocks) by not waiting at all on the read side and paying the cost entirely on the write side.

The first two are always preferable when they apply, because they cannot deadlock. Most of this section is nevertheless about the third, because most data does not decompose neatly per-CPU and most updates are larger than one instruction.

The Three Lock Categories

The single most useful piece of orientation in modern Linux locking is a taxonomy that did not exist in Linux 2.6. Documentation/locking/locktypes.rst divides every lock in the kernel into exactly three categories:

  • Sleeping locks — the waiter blocks and the CPU runs something else. mutex, rt_mutex, semaphore, rw_semaphore, ww_mutex, percpu_rw_semaphore. These may be acquired only in process context.
  • CPU local locks — local_lock_t, which serializes access to per-CPU data against other contexts on the same CPU and does nothing at all about other CPUs.
  • Spinning locks — the waiter busy-waits with preemption disabled. raw_spinlock_t and bit spinlocks are always in this category; spinlock_t and rwlock_t are in it only on non-PREEMPT_RT kernels. Bit spinlocks stay put for a mundane reason: a single bit has nowhere to store an RT-mutex, so they cannot be substituted even in principle, and the raw_spinlock_t restrictions apply to them everywhere.

That last clause is the reason the taxonomy matters so much more than it would have in Linux 2.6. On a PREEMPT_RT kernel, spinlock_t and rwlock_t move from the spinning category to the sleeping category — they are reimplemented on top of rt_mutex, so a task that fails to acquire one blocks rather than spins, and preemption is not disabled while the lock is held. Meanwhile local_lock is substituted with a per-CPU spinlock_t, which on such a kernel is itself a sleeping lock. The substitution is done in headers, so the call sites do not change and nothing in the source hints at it.

The practical consequence is worth stating plainly, because it invalidates a habit of thought that mainline Linux 2.6 allowed: "can this call block?" is a question about the kernel configuration, not about the name of the function. spin_lock() cannot block on the kernel on your desk and can block on an RT build of the same source. Only raw_spinlock_t and bit spinlocks are guaranteed to spin everywhere, which is precisely why the low-level code that truly cannot sleep — the scheduler, the timer core, the interrupt entry paths — uses raw_spinlock_t explicitly rather than relying on spinlock_t behaving as it historically did.

Lock Nesting Rules

The three categories are not merely descriptive; they impose an ordering on which locks may be held while acquiring which others. Per locktypes.rst, the basic rules are:

  • Locks within a single category nest arbitrarily, subject to the usual requirement that everyone acquires them in a consistent order.
  • A sleeping lock may not be acquired while holding a CPU-local or spinning lock. This is just the rule that you must not sleep with preemption disabled, restated in terms of lock types.
  • CPU-local and spinning locks may be acquired while holding a sleeping lock.
  • Spinning locks may be acquired while holding anything at all.

Because PREEMPT_RT reclassifies spinlock_t, rwlock_t and local_lock, these rules collapse into a three-level ordering that a lock may only ever be taken downward through:

1. Sleeping locks — mutex, rt_mutex, rw_semaphore, ww_mutex, semaphore, percpu_rw_semaphore
2. spinlock_t, rwlock_t, local_lock
3. raw_spinlock_t and bit spinlocks

In particular, a spinlock_t may not be acquired while holding a raw_spinlock_t. On a non-RT kernel that combination is entirely harmless — spinlock_t is raw_spinlock_t there — which is exactly what makes it a trap: the bug is invisible on the machine it was written on and is a potential sleep-in-atomic on an RT build.

Fortunately this does not have to be caught by review. Lockdep checks the ordering, and it checks it on non-RT kernels too, so an RT violation is discoverable without ever booting an RT kernel. The relevant option is CONFIG_PROVE_RAW_LOCK_NESTING, which depends on CONFIG_PROVE_LOCKING and defaults to y on any architecture that selects ARCH_SUPPORTS_RT — which both x86_64 and ARM64 do. Lock validation is covered in detail later in this chapter.

Choosing Among the Primitives

Within those constraints, the choice of technique depends on several factors:

  • Duration of the critical section — spinning wastes CPU cycles; sleeping incurs context-switch overhead. Short sections (a few instructions) favor spinlocks; longer sections (may allocate memory, do I/O) require sleeping locks.
  • Context of the accessor — interrupt handlers and softirqs cannot sleep, so they must use non-blocking primitives (spinlocks, atomic ops, RCU). Process context can use either.
  • Number and type of accessors — if most accesses are reads, reader/writer locks or RCU can dramatically improve scalability. If there's a single writer and many readers, RCU is often optimal.
  • Scope — some techniques (per-CPU variables, local IRQ disabling) protect against concurrency on a single CPU only. Others (spinlocks, atomic operations) provide system-wide exclusion across all CPUs.
  • Deadlock avoidance — locks must be acquired in a consistent order; some primitives (WW-mutexes) have built-in deadlock avoidance.

The one property that occasionally still justifies a semaphore is that it has no notion of an owner, so up() may be called by a task other than the one that called down(), and even from interrupt context. A mutex deliberately forbids both, which is what allows it to support priority inheritance and to be checked by lockdep. The Big Kernel Lock (BKL, lock_kernel()/unlock_kernel()) was completely removed in Linux 2.6.39.

A reader who wants the decision procedure rather than the mechanisms can skip ahead to "Choosing the Right Synchronization Primitive," which reduces all of this to a flowchart and a table.

Per-CPU Variables

The best synchronization technique is to avoid sharing data in the first place. Every explicit synchronization primitive has a significant performance cost. Per-CPU variables give each processor its own copy of a data structure, eliminating inter-CPU contention entirely.

Basically, a per-CPU variable is an array of data structures, one element per each CPU in the system. A CPU should not access the elements corresponding to other CPUs; on the other hand, it can freely read and modify its own element without fear of race conditions, because it is the only CPU entitled to do so. This also means, however, that per-CPU variables can be used only in particular cases — basically, when it makes sense to logically split the data across the CPUs of the system.

Why Per-CPU Variables Are Fast

Per-CPU variables provide two key performance advantages:

  1. No locking overhead — since each CPU works exclusively on its own copy, no spinlock, atomic operation, or memory barrier is needed for access. The only requirement is disabling preemption to ensure the task stays on the same CPU during the access.
  2. No cache line bouncing — the elements of the per-CPU array are laid out in memory so that each CPU's data falls on a different cache line. Without per-CPU separation, two CPUs incrementing the same counter would trigger constant cache line invalidations (the "ping-pong" effect), which can cost hundreds of cycles per access on modern NUMA systems. With per-CPU variables, each CPU's counter lives in its own cache line, so no inter-CPU cache coherency traffic is generated.

Limitations

While per-CPU variables provide protection against concurrent accesses from several CPUs, they do not protect against:

  • Asynchronous functions on the same CPU — an interrupt handler can preempt process-context code on the same CPU. If both access the same per-CPU variable, additional synchronization (disabling interrupts or using local_lock) is needed.
  • Kernel preemption — if a kernel control path gets the address of its local per-CPU copy and is then preempted and migrated to another CPU, the address still refers to the previous CPU's element. This is why preemption must be disabled during access.

Declaration and Definition

Linux 7.0.12 provides several macros for statically declaring per-CPU variables, each placing the variable in a different ELF section with different alignment and caching properties:

/* include/linux/percpu-defs.h */
DEFINE_PER_CPU(type, name);                    /* regular section */
DEFINE_PER_CPU_SHARED_ALIGNED(type, name);     /* cache-line aligned, shared section */
DEFINE_PER_CPU_READ_MOSTLY(type, name);        /* read-mostly section */
DEFINE_PER_CPU_CACHE_HOT(type, name);          /* hot-path optimization */

DECLARE_PER_CPU(type, name);                   /* extern declaration */

Each per-CPU variable occupies a separate memory region for each possible CPU. The linker places them in special .data..percpu sections, and the boot code replicates them for each possible CPU. The SHARED_ALIGNED variant ensures the variable is padded to a full cache line to prevent false sharing with adjacent variables.

Access Primitives

Per-CPU variables must be accessed with preemption disabled to ensure the code stays on the same CPU throughout the access. Linux 7.0.12 provides two families of access primitives:

The this_cpu_* family — preferred for simple read/modify/write operations. On x86_64, these compile to a single instruction using %gs-segment-relative addressing, with no lock prefix needed:

int val = this_cpu_read(counter);       /* read this CPU's copy */
this_cpu_write(counter, val + 1);       /* write this CPU's copy */
this_cpu_inc(counter);                  /* atomic increment on this CPU */
this_cpu_dec(counter);                  /* atomic decrement on this CPU */
this_cpu_add(counter, delta);           /* atomic add on this CPU */
this_cpu_and(flags, mask);              /* atomic AND on this CPU */
this_cpu_or(flags, bits);               /* atomic OR on this CPU */
this_cpu_xchg(var, new_val);            /* atomic exchange on this CPU */
this_cpu_cmpxchg(var, old, new);        /* atomic compare-and-exchange */

For example, this_cpu_inc(counter) on x86_64 compiles to:

incl %gs:counter    /* single instruction — inherently preemption-safe */

The architecture qualification matters. ARM64 has no instruction that combines per-CPU address relocation with a read-modify-write, so the same macro expands there to preemption protection wrapped around a genuine atomic. The consequences for choosing between this_cpu_* and raw_cpu_* are taken up in Per-CPU Statistics later in this chapter.

The get_cpu_ptr / put_cpu_ptr family — for multi-statement critical sections that need a pointer to the per-CPU data:

/* Explicit preemption control: */
int *p = get_cpu_ptr(&per_cpu_var);     /* disable preemption, get pointer */
*p += 1;
/* ... more operations on *p ... */
put_cpu_ptr(&per_cpu_var);              /* re-enable preemption */

The per_cpu() macro — accesses a specific CPU's copy (not necessarily the local CPU). This is used for aggregation (summing counters across all CPUs):

unsigned long total = 0;
int cpu;
for_each_online_cpu(cpu)
    total += per_cpu(my_counter, cpu);

Dynamic Per-CPU Allocation

When per-CPU data must be allocated at runtime (e.g., for dynamically loaded modules or data structures created on demand), the kernel provides:

The dynamic allocator in Linux 7.0.12 uses a NUMA-aware chunk-based scheme (mm/percpu.c) that keeps each CPU's allocation in memory local to that CPU's NUMA node, minimizing cross-node memory latency. Chapter 8, Section 3.4 describes how it works: chunks, units, the first chunk built at boot, and the balance work that keeps pages ready for atomic callers.

Since Linux 6.5+, the RAII cleanup pattern is also available:

DEFINE_FREE(free_percpu, void __percpu *, free_percpu(_T))

/* Usage with guard: automatically freed when scope exits */
void __percpu *data __free(free_percpu) = alloc_percpu(struct my_data);

Per-CPU Variables and Interrupt Context

A subtle point: this_cpu_inc() is safe against preemption (single instruction) but not against interrupts on the same CPU. If an interrupt handler also calls this_cpu_inc() on the same variable, the process-context this_cpu_inc() and the interrupt-context this_cpu_inc() can interleave. However, since both are single-instruction RMW operations on x86, they are inherently atomic against interrupts (interrupts are only taken between instructions).

For multi-statement critical sections, however, interrupt safety must be handled explicitly:

local_irq_save(flags);              /* or use local_lock_irqsave() */
p = this_cpu_ptr(&my_data);
p->field1++;
p->field2 = compute_something();
local_irq_restore(flags);

Atomic Operations

When a data structure is a simple integer counter or a bit field, atomic operations provide synchronization without locking. They use hardware atomic instructions (e.g., lock prefix on x86, ldxr/stxr or LSE atomics on ARM64) to perform read-modify-write in a single indivisible step.

Atomic operations are the lowest-level synchronization primitive in the kernel. Higher-level constructs — spinlocks, mutexes, reference counters, completion variables — are all ultimately built on top of atomic operations and memory barriers. Using atomics directly is appropriate when:

  • The shared state is a single integer or bit field (not a complex data structure)
  • The operation on the shared state can be expressed as a single atomic step
  • No multi-variable invariant needs to be maintained across the operation

Why Atomics Are Necessary

Consider a simple counter increment on a multiprocessor. In C, counter++ compiles to three separate operations:


1. Load counter from memory into register     (mov counter, %eax)
2. Increment the register                      (inc %eax)
3. Store the register back to memory           (mov %eax, counter)

If two CPUs execute this sequence concurrently, both may load the same value, both increment it, and both store back — losing one increment. Atomic operations solve this by making the read-modify-write appear as one indivisible operation to all CPUs.

Atomic Integer Operations

The kernel provides atomic_t (32-bit) and atomic64_t (64-bit) types:


/* include/linux/types.h */
typedef struct { int counter; } atomic_t;
typedef struct { s64 counter; } atomic64_t;

The struct wrapper is intentional: it prevents direct C arithmetic (counter++) which would not be atomic. All access must go through the atomic_*() API, making non-atomic usage a compile-time error.

Architecture Implementation

The x86_64 implementation (arch/x86/include/asm/atomic.h) uses the LOCK prefix:

    asm_inline volatile(LOCK_PREFIX "addl %1, %0"
                 : "+m" (v->counter)
                 : "ir" (i) : "memory");
}

static __always_inline int arch_atomic_add_return(int i, atomic_t *v)
{
    return i + xadd(&v->counter, i);  /* xadd returns old value */
}

The LOCK prefix on x86_64 does not assert the external bus lock (as it did on ancient 486 systems). Instead, it locks the cache line in the L1 cache of the executing core, which is far more efficient. The "memory" clobber tells the compiler this is a full compiler barrier.

ARM64 provides two mechanisms (atomic_ll_sc.h and atomic_lse.h):


/* LL/SC fallback (all ARMv8) */

/* LSE atomics (ARMv8.1+, CONFIG_ARM64_LSE_ATOMICS) */
    stadd   w3, [x2]           // single instruction atomic add

The refcount_t Type

Linux 7.0.12 introduces refcount_t as a hardened replacement for atomic_t in reference counting:

    kfree(obj);

Memory Barriers

Modern CPUs and compilers reorder memory operations for performance. When correctness depends on ordering — which is almost always the case in synchronization code — explicit barriers are required. Without barriers, even logically correct code can produce wrong results because one CPU may observe another CPU's writes in a different order than they were issued.

Why Reordering Happens

Both the compiler and CPU independently reorder memory operations:

  1. Compiler reordering — The C standard allows the compiler to reorder any memory accesses that do not have data dependencies. For example, the compiler may move a store below an unrelated load to fill a pipeline stall, or eliminate a "redundant" load that it doesn't realize is modified by another CPU.
  2. CPU reordering — Modern out-of-order processors execute instructions in whatever order fills their execution units most efficiently. Store buffers allow writes to be delayed and coalesced. Invalidation queues mean a CPU may not immediately see another CPU's writes.

The Barrier Hierarchy

The kernel organizes barriers from cheapest to most expensive:


/* From cheapest to most expensive: */

barrier();              /* Compiler only — zero CPU cost */
                        /* Prevents compiler from reordering across this point */

smp_wmb();              /* Write ordering only */
                        /* x86: compiler barrier  |  ARM64: dmb ishst */

smp_rmb();              /* Read ordering only */
                        /* x86: compiler barrier  |  ARM64: dmb ishld */

smp_mb();               /* Full read+write ordering */
                        /* x86: lock addl $0,-4(%rsp)  |  ARM64: dmb ish */

mb();                   /* Full barrier including MMIO (device I/O) */
                        /* x86: mfence  |  ARM64: dsb sy */

The rule is simple: use the weakest barrier that satisfies your ordering requirement. Every unnecessary barrier is wasted performance, especially on ARM64 where barriers are expensive (50-100 cycles for dmb ish).

Acquire and Release Semantics

Linux 7.0.12 strongly encourages paired acquire/release semantics over raw barriers. They express the programmer's intent directly and map to hardware instructions on weakly-ordered architectures:


/* Producer: publish data, then signal readiness */
WRITE_ONCE(data->field1, value1);
WRITE_ONCE(data->field2, value2);
smp_store_release(&flag, 1);    /* all writes above visible before flag */
/* ARM64: stlr — single instruction with release semantics */
/* x86:   barrier() + MOV — TSO guarantees store ordering already */

/* Consumer: check flag, then read data */
if (smp_load_acquire(&flag)) {  /* flag read before any reads below */
    /* ARM64: ldar — single instruction with acquire semantics */
    val1 = READ_ONCE(data->field1);  /* guaranteed to see producer's writes */
    val2 = READ_ONCE(data->field2);
}

This pattern is preferable to raw barriers for three reasons:

  1. Self-documenting — the code clearly shows what is being protected and the direction of the ordering constraint
  2. Optimal code generation — on ARM64, ldar/stlr is cheaper than ldr + dmb; on x86, it generates the same code as raw access
  3. Paired validation — tools like KCSAN can verify that acquire/release pairs match up correctly

Barrier Pairing Rules

Barriers must always be used in pairs between communicating CPUs. A single barrier on one CPU without a matching barrier on the reader/writer is meaningless:


/* WRONG: barrier on writer but not reader */
CPU 0:  WRITE_ONCE(a, 1);  smp_wmb();  WRITE_ONCE(b, 1);
CPU 1:  if (READ_ONCE(b))  use(READ_ONCE(a));  /* may see a=0! */

/* CORRECT: paired barriers */
CPU 0:  WRITE_ONCE(a, 1);  smp_wmb();  WRITE_ONCE(b, 1);
CPU 1:  if (READ_ONCE(b)) { smp_rmb();  use(READ_ONCE(a)); }  /* a=1 guaranteed */

The pairing rules are:

  • smp_wmb() on writer pairs with smp_rmb() on reader
  • smp_store_release() on writer pairs with smp_load_acquire() on reader
  • smp_mb() pairs with itself (most expensive, least specific)

READ_ONCE() and WRITE_ONCE()

These macros prevent the compiler from tearing, merging, or inventing accesses:


/* Ensures a single load instruction; prevents repeated reads */
int x = READ_ONCE(shared_var);

/* Ensures a single store instruction; prevents store tearing */
WRITE_ONCE(shared_var, new_val);

Without READ_ONCE(), the compiler may:

  • Split a read into multiple smaller loads (tearing)
  • Reload a value from memory (creating a TOCTOU race)
  • Merge two reads into one (missing an update)
  • Invent a store to a shared variable it uses as a scratch register

Without WRITE_ONCE(), the compiler may:

  • Split a write into multiple stores (tearing)
  • Merge two writes into one (losing an intermediate value another CPU expects to see)
  • Reorder the write across other memory accesses

They are essential in all lockless code and are a 7.0.12-era best practice absent from Linux 2.6, where raw volatile casts were used inconsistently.

Speculative Execution Barriers

Linux 7.0.12 added barriers for CPU speculative execution vulnerabilities (Spectre/Meltdown):


barrier_nospec();       /* Prevent speculative execution past this point */
                        /* x86: lfence  |  ARM64: dsb nsh; isb (or SB instruction) */

array_index_nospec(idx, size);  /* Bounds-clamp index to prevent Spectre v1 */
                                /* Returns 0 if idx >= size, otherwise idx */

These have no equivalent in Linux 2.6 and represent a fundamental shift in how the kernel reasons about correctness — it must now defend against speculative side-channel attacks, not just concurrent execution.

Spinlocks

Spinlocks are the fundamental mutual-exclusion primitive for code that cannot sleep. A spinlock protects a critical region by busy-waiting: if the lock is held, the acquiring CPU spins in a tight loop until it becomes available. They are appropriate for short critical sections (typically a few microseconds or less) where the overhead of sleeping/waking would exceed the wait time.

When to Use Spinlocks

Spinlocks are the right choice when:

  • The critical section is short (a few memory accesses, no I/O waits)
  • The code runs in atomic context (interrupt handlers, softirqs, code with preemption disabled)
  • The lock must be acquirable from interrupt context
  • The protected data is accessed from multiple CPUs concurrently

Spinlocks are the wrong choice when:

  • The critical section may sleep (allocating memory with GFP_KERNEL, calling copy_from_user(), etc.)
  • The hold time may be long or variable — use a mutex instead
  • Only one CPU ever accesses the data — use per-CPU variables or local_lock instead

On x86_64, arch_spinlock_t is a struct qspinlock — a 4-byte atomic value:


/* include/asm-generic/qspinlock_types.h */
typedef struct qspinlock {
    union {
        atomic_t val;

            u8 locked;      /* 1 = locked */

        };
    };
} arch_spinlock_t;

The entire lock fits in a single 32-bit word, which is critical for cache efficiency and allows atomic operations on sub-fields (individual bytes) for fast-path optimization.

From Ticket Locks to Queued Spinlocks

Linux 2.6 used a simple test-and-set (or later, ticket) spinlock. Ticket locks guaranteed FIFO fairness but caused severe cache-line bouncing on large NUMA systems because every spinning CPU repeatedly reads and writes the same cache line.

Linux 7.0.12 uses queued spinlocks (qspinlock), which solve this problem through a three-level design:

  1. Uncontended (fast path): A single atomic_try_cmpxchg_acquire(&lock->val, 0, 1) — if the lock word is zero, set locked=1 and proceed. This is a single instruction on x86 and succeeds in the common case.
  2. One waiter (pending path): The first contender sets the pending byte and spins on the locked byte — optimized for the common 2-CPU contention case.
  3. Multiple waiters (MCS queue): If a third CPU arrives, it enqueues in a per-CPU MCS queue (linked list of local spin nodes). Each waiter spins on its own cache line, avoiding NUMA traffic entirely.

The qspinlock Fast Path

The implementation from include/asm-generic/qspinlock.h:


static __always_inline void queued_spin_lock(struct qspinlock *lock)
{
    int val = 0;

    if (likely(atomic_try_cmpxchg_acquire(&lock->val, &val, _Q_LOCKED_VAL)))
        return;             /* Fast path: lock was free, acquired! */

    queued_spin_lock_slowpath(lock, val);  /* Contention: pending or MCS */
}

static __always_inline void queued_spin_unlock(struct qspinlock *lock)
{
    smp_store_release(&lock->locked, 0);  /* Single byte store with release */
}

The fast path is a single cmpxchg instruction — if the entire 32-bit lock word is zero, atomically set it to 1. The unlock is equally fast: a single byte store with release semantics.

The Slowpath: Pending and MCS

When the fast path fails (from kernel/locking/qspinlock.c):


void queued_spin_lock_slowpath(struct qspinlock *lock, u32 val)
{
    /* Phase 1: If only one other CPU holds it, try the "pending" path */
    if (val == _Q_PENDING_VAL) {
        val = atomic_cond_read_relaxed(&lock->val,
                    (VAL != _Q_PENDING_VAL) || !cnt--);
    }

    if (val & ~_Q_LOCKED_MASK)
        goto queue;         /* Already contended, go straight to MCS */

    /* Set pending bit: (0,0,1) -> (0,1,1) */
    val = queued_fetch_set_pending_acquire(lock);
    if (unlikely(val & ~_Q_LOCKED_MASK))
        goto queue;         /* Race: someone else set pending/tail */

    /* Spin on the locked byte (same cache line, but brief) */
    if (val & _Q_LOCKED_MASK)
        smp_cond_load_acquire(&lock->locked, !VAL);

    /* Got it! Clear pending, set locked: (0,1,0) -> (0,0,1) */
    clear_pending_set_locked(lock);
    return;

queue:
    /* Phase 2: MCS queue — spin on local per-CPU node */
    node = this_cpu_ptr(&qnodes[0].mcs);
    idx = node->count++;
    tail = encode_tail(smp_processor_id(), idx);

    node->locked = 0;
    node->next = NULL;

    /* Publish our node as the new tail */
    old = xchg_tail(lock, tail);

    if (old & _Q_TAIL_MASK) {
        prev = decode_tail(old, qnodes);
        WRITE_ONCE(prev->next, node);
        /* Spin on OUR OWN node->locked (local cache line!) */
        arch_mcs_spin_lock_contended(&node->locked);
    }

    /* We're the head — wait for lock owner to release */
    val = atomic_cond_read_acquire(&lock->val,
                !(VAL & _Q_LOCKED_PENDING_MASK));
    /* Acquire the lock */
    ...
}

When to Use Which Variant

Choosing the correct spin_lock variant depends on who else might access the same data:


/* Only process context accesses the data: */
spin_lock(&lock);           /* preempt_disable() sufficient */

/* IRQ handler also accesses the data: */
spin_lock_irqsave(&lock, flags);  /* Must disable IRQs to prevent deadlock */

/* Softirq also accesses the data: */
spin_lock_bh(&lock);       /* Disable bottom halves */

The rule: if an interrupt handler can acquire the same lock, the process-context code must disable that interrupt level before acquiring. Otherwise, the interrupt fires while the lock is held, tries to acquire it again, and deadlocks forever (single CPU spinning on itself).

How spin_lock() Works Internally

On a non-RT kernel, spin_lock() does:

  1. Call preempt_disable() — prevent preemption while holding the lock.
  2. Call queued_spin_lock(&lock->rlock.raw_lock) — the qspinlock fast path attempts an atomic cmpxchg(val, 0, _Q_LOCKED_VAL). If it succeeds (lock was free), the lock is acquired.
  3. If the fast path fails (contention), enter the slowpath: set pending or join the MCS queue and spin locally.

spin_unlock() does:

  1. Call queued_spin_unlock() — on x86, this is a simple smp_store_release(&lock->locked, 0).
  2. Call preempt_enable() — may trigger a reschedule if TIF_NEED_RESCHED is set.

Paravirtualized Spinlocks

In virtual machines, spinning wastes the host CPU's time slice. Linux 7.0.12 supports PV (paravirtualized) qspinlocks that detect virtualization and halt the vCPU instead of busy-waiting:


/* When running as VM guest: */
if (pv_enabled()) {
    /* Instead of spinning, yield the vCPU to the hypervisor */
    pv_wait_node(node, prev);   /* calls halt/HLT instruction */
}

The lock holder then uses a pv_kick_node() to wake the halted vCPU when releasing. This avoids the "lock holder preemption" problem where a vCPU holding a spinlock is descheduled by the hypervisor, causing all other vCPUs to spin uselessly.

raw_spinlock vs spinlock on PREEMPT_RT

On CONFIG_PREEMPT_RT kernels, spinlock_t is redefined as a sleeping rt_mutex. This means:

  • spin_lock() may sleep (and does priority inheritance).
  • Code that truly cannot sleep (interrupt handlers, scheduler, etc.) must use raw_spinlock_t directly.

/* On PREEMPT_RT:
 * spinlock_t     → sleeping rt_mutex (preemptible, PI)
 * raw_spinlock_t → actual spinning lock (non-preemptible)
 */
raw_spin_lock(&raw_lock);    /* Always spins, never sleeps */
spin_lock(&regular_lock);    /* On RT: may sleep with PI */

Read/Write Spinlocks

Read/write spinlocks allow multiple concurrent readers but exclusive writers. They are appropriate when reads vastly outnumber writes and all accesses are in non-sleeping context. The fundamental insight is that data structures which are read far more often than modified (routing tables, module lists, file system metadata caches) can achieve higher concurrency by allowing multiple CPUs to read simultaneously.

Basic Usage


DEFINE_RWLOCK(my_rwlock);

/* Reader path — multiple CPUs can hold simultaneously */
read_lock(&my_rwlock);
/* ... read data ... */
read_unlock(&my_rwlock);

/* Writer path — exclusive access, blocks all readers and writers */
write_lock(&my_rwlock);
/* ... modify data ... */
write_unlock(&my_rwlock);

The qrwlock Structure

In Linux 7.0.12, arch_rwlock_t is a queued read/write lock (include/asm-generic/qrwlock_types.h):


typedef struct qrwlock {
    union {
        atomic_t cnts;          /* Reader count + writer state */
        struct {
            u8 wlocked;         /* Locked for write? (0xff = locked) */

        };
    };

Implementation Details

The read lock fast path (include/asm-generic/qrwlock.h):


static inline void queued_read_lock(struct qrwlock *lock)
{
    int cnts;
    cnts = atomic_add_return_acquire(_QR_BIAS, &lock->cnts);
    if (likely(!(cnts & _QW_WMASK)))   /* No writer active or waiting? */
        return;                         /* Fast path: acquired! */
    queued_read_lock_slowpath(lock);    /* Writer present: queue up */
}

The write lock fast path:


static inline void queued_write_lock(struct qrwlock *lock)
{
    int cnts = 0;
    if (likely(atomic_try_cmpxchg_acquire(&lock->cnts, &cnts, _QW_LOCKED)))
        return;                         /* Fast path: no readers, acquired! */
    queued_write_lock_slowpath(lock);   /* Readers present: wait */
}

The write slowpath from kernel/locking/qrwlock.c:


void queued_write_lock_slowpath(struct qrwlock *lock)
{
    /* Serialize with other writers via the embedded qspinlock */
    arch_spin_lock(&lock->wait_lock);

    /* Try direct acquire if no readers */
    if (!(cnts = atomic_read(&lock->cnts)) &&
        atomic_try_cmpxchg_acquire(&lock->cnts, &cnts, _QW_LOCKED))
        goto unlock;

    /* Set WAITING flag — new readers will queue instead of entering */
    atomic_or(_QW_WAITING, &lock->cnts);

    /* Wait for all existing readers to drain */
    do {
        cnts = atomic_cond_read_relaxed(&lock->cnts, VAL == _QW_WAITING);
    } while (!atomic_try_cmpxchg_acquire(&lock->cnts, &cnts, _QW_LOCKED));

unlock:
    arch_spin_unlock(&lock->wait_lock);
}

Key design insight: the _QW_WAITING flag tells new readers "a writer is queued — don't enter, wait behind the writer." This solves the classic writer starvation problem where continuous reader arrivals could indefinitely postpone a writer.

Limitations and Modern Alternatives

Read/write spinlocks have largely fallen out of favor in modern kernel code because:

  1. Reader scalability is limited — every read_lock() does an atomic_add on the shared counter, causing cache bouncing among readers. On 64+ core systems this can be as slow as a regular spinlock.
  2. Cannot nest with the same lock — unlike RCU's read-side, a reader cannot recursively take the same rwlock.
  3. On PREEMPT_RT — they become sleeping rwbase_rt locks with potential priority inversion.

Seqlocks

Seqlocks provide an optimistic readers approach: writers always proceed immediately (they never block waiting for readers), and readers optimistically read the data, then check whether a writer intervened during their read. If a writer did intervene, the reader retries. This is the inverse of read/write spinlocks, where writers wait for readers — seqlocks give writers absolute priority.

The concept is elegantly simple: a sequence counter is incremented to an odd value when a writer enters and to the next even value when the writer exits. Readers sample the counter before and after reading; if the counter changed or was odd, they know a write occurred during their read and must retry.

Two Layers: seqcount_t and seqlock_t

Linux 7.0.12 separates seqlocks into two distinct primitives:

  1. seqcount_t — the raw sequence counter. It provides the reader-retry mechanism but does not include any writer serialization. The caller must provide external locking for writers.
  2. seqlock_t — a convenience wrapper that bundles a seqcount_t with a spinlock_t for writer mutual exclusion.

/* include/linux/seqlock_types.h */
typedef struct seqcount {
    unsigned sequence;              /* even = stable, odd = writer active */
#ifdef CONFIG_DEBUG_LOCK_ALLOC
    struct lockdep_map dep_map;
#endif
} seqcount_t;

typedef struct seqlock {
    seqcount_spinlock_t seqcount;   /* sequence counter + lockdep */
    spinlock_t lock;                /* writer mutual exclusion */
} seqlock_t;

How Seqlocks Work


/* Writer — always succeeds immediately */
write_seqlock(&my_seqlock);
/*  1. spin_lock(&my_seqlock.lock)     — serialize writers */
/*  2. sequence++ (now ODD)            — signal "write in progress" */
/*  3. smp_wmb()                       — writes below visible after counter */
/* ... modify data ... */
write_sequnlock(&my_seqlock);
/*  4. smp_wmb()                       — data writes visible before counter */
/*  5. sequence++ (now EVEN)           — signal "write complete" */
/*  6. spin_unlock(&my_seqlock.lock) */

/* Reader — lockless, may retry */
unsigned seq;
do {
    seq = read_seqbegin(&my_seqlock);
    /*  1. wait while sequence is ODD (writer active) */
    /*  2. record the EVEN sequence value */
    /* ... read data ... */
} while (read_seqretry(&my_seqlock, seq));
    /*  3. smp_rmb() */
    /*  4. if sequence != recorded value → data may be inconsistent, retry */

The Implementation

From include/linux/seqlock.h, the reader side:

static inline int do_read_seqcount_retry(const seqcount_t *s, unsigned start)
{
    smp_rmb();              /* ensure all reads complete before check */
    return do___read_seqcount_retry(s, start);  /* sequence != start? */
}

The writer side:


static inline void do_raw_write_seqcount_begin(seqcount_t *s)
{
    kcsan_nestable_atomic_begin();
    s->sequence++;          /* even → odd: "write in progress" */
    smp_wmb();              /* writes after this point are part of update */
}

static inline void do_raw_write_seqcount_end(seqcount_t *s)
{
    smp_wmb();              /* all update writes visible before counter */
    s->sequence++;          /* odd → even: "write complete" */
    kcsan_nestable_atomic_end();
}

The two smp_wmb() barriers are critical:

  • Before writing data: ensures the counter increment (odd) is visible before any data modifications
  • After writing data: ensures all data modifications are visible before the counter increment (even)

Without these barriers, a reader on a weakly-ordered architecture might see the final (even) counter value but still read stale data.

Reader Starvation and Writer Livelock

The seqlock bargain — writers never wait — has a price, and it is paid entirely by readers. It shows up as two failure modes that none of the code above makes visible, and both are absent from a lightly loaded test machine by construction: they need a write rate high enough to interfere with reads.

Reader starvation. A lockless reader makes progress only if it completes an entire pass with no writer intervening. There is no bound on how many times it may fail. Under a sharp spike in write activity — and a spike is exactly what a seqlock invites, since writers are never throttled by readers — a reader can retry for an unbounded time while making no forward progress at all.

The kernel's remedy is to give up on optimism after the first failure. read_seqbegin_or_lock() starts as an ordinary lockless reader, but if that attempt fails, the next iteration promotes itself into a locking reader that acquires the write-side lock and therefore excludes writers for the duration:

int seq = 0;            /* must start even: first pass is lockless */

do {
    read_seqbegin_or_lock(&lock, &seq);
    /* ... read the data ... */
} while (need_seqretry(&lock, seq));
done_seqretry(&lock, seq);

The seq variable is doing double duty here, which is easy to misread. It is both the sampled counter and the mode selector: an even value means “try lockless”, an odd value means “take the lock”. That is why it must be initialised to zero before the loop and why the same variable must be threaded through every iteration. done_seqretry() then releases the lock only if one was actually taken. Because a retry is guaranteed to terminate on the second pass, the loop runs at most twice.

The canonical user is d_walk() in fs/dcache.c, which walks the dentry tree under rename_lock: a rename storm would otherwise starve the walk indefinitely.

Writer livelock. The mirror image, and the more serious of the two. A reader spins while the counter is odd, and the counter is odd for exactly as long as the writer sits between its two increments. If the writer is preempted or interrupted in that window, every reader that arrives spins not for a few instructions but for however long the writer stays descheduled.

Documentation/locking/seqlock.rst puts the consequence bluntly: a reader in that situation “will spin for the entire scheduler tick”, and “if that reader belongs to a real-time scheduling class, it can spin forever and the kernel will livelock.” A sufficiently high-priority reader can prevent the writer it is waiting for from ever being scheduled again.

This is the reason the write side must run with preemption disabled, and it is the real justification for the typed seqcount_LOCKNAME_t variants introduced above. Naming the associated lock lets the seqcount determine whether that lock already disables preemption and add preempt_disable() only when it does not — so the requirement is satisfied automatically rather than by every caller remembering it.

Both hazards point the same way. A seqlock is the right choice when the read side is short, self-contained, and copies out what it needs; it degrades badly the moment the read side becomes long enough to overlap writes routinely.

Read-Copy Update (RCU)

RCU is the kernel's most scalable synchronization mechanism for read-mostly data structures. It achieves wait-free reads with zero overhead — no atomic operations, no memory barriers, no cache-line bouncing on the reader side. The cost is paid entirely by writers, who must defer reclamation of old data until all pre-existing readers have finished.

RCU represents a fundamental paradigm shift from traditional locking: instead of preventing concurrent access, it allows readers to access data structures concurrently with writers, relying on careful memory ordering and deferred destruction to maintain safety.

The RCU Guarantee

RCU provides a single, powerful guarantee:

Any data structure visible to an RCU reader at the start of its read-side critical section remains valid (not freed) for the entire duration of that critical section.

This means:

  • Readers can always follow RCU-protected pointers safely
  • Writers can modify data structures (including removing elements) at any time
  • Old versions of data are only freed after all pre-existing readers finish

What a Reader May and May Not Do

The guarantee above is stated in terms of what RCU promises. The corresponding obligations on the reader are short, but two of them are routinely misremembered.

A reader may not block. Documentation/RCU/whatisRCU.rst states it directly: “It is illegal to block while in an RCU read-side critical section, though kernels built with CONFIG_PREEMPT_RCU can preempt RCU read-side critical sections.” The two halves of that sentence are easy to run together, and they are not the same thing. Being preempted is involuntary and, under preemptible RCU, entirely permitted — the grace period simply has to wait longer. Blocking is voluntary: calling something that sleeps, such as taking a mutex or allocating with GFP_KERNEL. That remains illegal no matter how the kernel is configured, and it is what SRCU exists to permit.

Read-side critical sections happen without being asked for. This is the second surprise, and it follows directly from the flavor consolidation described at the end of this chapter. Because one grace period now covers every reader flavor, anything that makes a CPU non-preemptible is an RCU reader:

“Note that anything that disables bottom halves, preemption, or interrupts also enters an RCU read-side critical section. Acquiring a spinlock also enters an RCU read-side critical section, even for spinlocks that do not disable preemption, as is the case in kernels built with CONFIG_PREEMPT_RT=y. Sleeplocks do not enter RCU read-side critical sections.”

Two practical consequences follow. Code holding a spinlock already has RCU protection and need not add rcu_read_lock() to obtain it — though saying so explicitly still documents the intent and keeps lockdep informed. And more importantly, a long region with preemption disabled extends every concurrent grace period, whether or not its author was thinking about RCU at all.

Finally, RCU is not a substitute for reference counting. It keeps an object alive for the duration of a critical section, not beyond it. A reference that must outlive the section has to be converted into a real one before the section ends — which is the try-get pattern described later in this chapter.

Core Concepts

  1. Read-side critical section: Bracketed by rcu_read_lock() / rcu_read_unlock(). On non-PREEMPT_RCU kernels, these simply disable/enable preemption — literally zero overhead beyond the preemption counter manipulation. On PREEMPT_RCU, they manipulate a per-task nesting counter.
  2. Publish-subscribe: Writers prepare a new version of a data structure, then atomically publish it using rcu_assign_pointer() (which includes a smp_store_release()). Readers use rcu_dereference() to safely follow the pointer (which includes a data-dependency barrier).
  3. Grace period: After publishing new data and removing old data from the data structure, the writer must wait for all pre-existing readers to complete before freeing the old version. synchronize_rcu() blocks until the grace period elapses; call_rcu() registers a callback to be invoked asynchronously after the grace period.
/* Reader — extremely cheap (no atomics, no barriers on most architectures) */
rcu_read_lock();                        /* preempt_disable() or nesting++ */
struct foo *p = rcu_dereference(global_ptr);  /* data-dependency load */
/* use p — guaranteed valid for duration of rcu_read_lock() */
do_something(p->field);
rcu_read_unlock();                      /* preempt_enable() or nesting-- */

/* Writer (update) — pays the synchronization cost */
struct foo *old, *new;
new = kmalloc(sizeof(*new), GFP_KERNEL);
*new = *old;                            /* copy old data */
new->field = new_value;                 /* modify the copy */
old = rcu_dereference_protected(global_ptr, lockdep_is_held(&my_lock));
rcu_assign_pointer(global_ptr, new);    /* publish (smp_store_release) */
synchronize_rcu();                      /* wait for all pre-existing readers */
kfree(old);                             /* safe to free now */

/* Or: non-blocking deferred free */
call_rcu(&old->rcu_head, my_free_callback);  /* free after grace period */

How Grace Periods Work

A grace period is the time it takes for every CPU to pass through a quiescent state — a point where the CPU is known not to be in an RCU read-side critical section. Quiescent states include:

  • Executing in user mode
  • Executing the idle loop
  • Context switch (schedule)
  • CPU going offline

The Tree RCU implementation (kernel/rcu/tree.c) organizes CPUs into a hierarchy of rcu_node structures and uses per-CPU rcu_data structures to track quiescent states efficiently. On a 256-CPU system, instead of checking a single global counter (which would bounce among 256 caches), it uses a tree where each node covers a subset of CPUs — dramatically reducing cache contention.

Polled Grace Periods

The table's updater entries divide into two kinds: synchronize_rcu() blocks until a grace period has elapsed, and call_rcu() hands the work to a callback. Both are awkward for an updater that can neither block nor conveniently be resumed in a callback — a common position for code that is already holding something, or that batches many updates and would rather not allocate an rcu_head for each one.

Polled grace periods, which have no counterpart in 2.6, resolve this by making the grace period something an updater can ask about rather than wait for. The updater takes a snapshot of RCU's internal state and can test it later at a moment of its own choosing:

unsigned long cookie = get_state_synchronize_rcu();

/* ... continue doing useful work; do not block ... */

if (poll_state_synchronize_rcu(cookie)) {
    /* a full grace period has elapsed since the snapshot;
     * anything removed before it is now safe to free  */
}

The cookie is an opaque sequence value, so the test is a comparison rather than a wait. Three related forms complete the interface: start_poll_synchronize_rcu() takes a snapshot and nudges RCU into starting a grace period if none is in progress, which matters when nothing else would; cond_synchronize_rcu() is the obvious combination, blocking only if the grace period has not already passed — its implementation is literally if (!poll_state_synchronize_rcu(oldstate)) synchronize_rcu();; and the _full() variants use a wider struct rcu_gp_oldstate snapshot that is accurate across both normal and expedited grace periods.

The pattern this enables is worth naming, because it is the reason the interface exists: an updater can unlink an object, record a cookie in it, carry on, and reclaim the object much later — by which time the grace period has almost always elapsed for free, with no blocking and no per-object callback.

Implementation: Zero-Cost Readers

On non-PREEMPT_RCU kernels, the reader implementation is astonishingly simple:

/* include/linux/rcupdate.h — non-preemptible RCU */

{
    preempt_disable();      /* One instruction: incl %gs:__preempt_count */
}

static inline void __rcu_read_unlock(void)
{
    preempt_enable();       /* decl %gs:__preempt_count + resched check */
}

/* kernel/rcu/tree_plugin.h — preemptible RCU */

{
    current->rcu_read_lock_nesting++;
    /* No atomic, no barrier — just a local variable increment */
}

#define rcu_dereference(p) \

    smp_store_release(&p, RCU_INITIALIZER(v))

The most common RCU pattern is protecting a linked list:

list_add_rcu(&entry->list, &my_list);  /* immediately visible to new readers */

The key insight: list_del_rcu() unlinks the node but does not corrupt its next pointer. Any reader currently traversing through that node can still follow next to the subsequent element. The node remains valid in memory until the grace period completes.

Local Locks

Local locks are a Linux 7.0.12 addition (not present in 2.6) that provide per-CPU synchronization with lockdep validation. They replace ad-hoc preempt_disable() / local_irq_disable() patterns with named, debuggable locks that have proper lock ordering annotations.

The Problem Local Locks Solve

In Linux 2.6, protecting per-CPU data typically looked like this:

/* Linux 2.6 — ad-hoc per-CPU protection */
preempt_disable();
struct my_data *d = this_cpu_ptr(&my_percpu_data);
d->counter++;
preempt_enable();

/* Or with IRQ protection: */
local_irq_save(flags);
struct my_data *d = this_cpu_ptr(&my_percpu_data);
d->field = new_value;
local_irq_restore(flags);

This pattern has several serious problems:

  1. No lockdep tracking — lock ordering violations are invisible to the lock validator
  2. No annotation — impossible to tell which preempt_disable() protects which data
  3. PREEMPT_RT incompatible — preempt_disable() cannot be converted to a sleeping lock
  4. No lock guard support — cannot use scoped lock guards for automatic unlock

Local locks solve all four problems:

/* Linux 7.0.12 — proper local_lock protection */
#include <linux/local_lock.h>

struct my_cpu_data {
    local_lock_t    lock;       /* protects all fields below */
    unsigned long   counter;
    struct list_head queue;
};

static DEFINE_PER_CPU(struct my_cpu_data, cpu_data) = {
    .lock = INIT_LOCAL_LOCK(cpu_data.lock),
};

/* Usage — clear lockdep annotation, PREEMPT_RT-safe */
local_lock(&cpu_data.lock);
this_cpu_ptr(&cpu_data)->counter++;
local_unlock(&cpu_data.lock);

Implementation Details

On non-RT kernels, a local_lock_t contains only lockdep metadata — no actual lock state:

/* include/linux/local_lock_internal.h — non-PREEMPT_RT */
typedef struct local_lock {
#ifdef CONFIG_DEBUG_LOCK_ALLOC
    struct lockdep_map  dep_map;    /* lockdep tracking */
    struct task_struct  *owner;     /* debug: who holds this */
#endif
} local_lock_t;

/* __local_lock() expands to: */
#define __local_lock(lock)          \
    do {                            \
        preempt_disable();          \
        local_lock_acquire(lock);   /* lockdep annotation only */  \
    } while (0)

On PREEMPT_RT kernels, a local_lock_t is a real spinlock_t (which on RT is a sleeping mutex with priority inheritance):

/* include/linux/local_lock_internal.h — PREEMPT_RT */
typedef spinlock_t local_lock_t;    /* sleeping lock on RT! */

#define __local_lock(__lock)        \
    do {                            \
        migrate_disable();          /* pin to this CPU */    \
        spin_lock((__lock));        /* acquire real lock */  \
    } while (0)

This dual implementation is the key innovation: the same source code compiles to zero-overhead preempt disable on normal kernels, and to a proper sleeping lock on PREEMPT_RT.

What Local Locks Do Not Do

The name invites a misreading that is worth heading off, because the compiler will not catch it. A local_lock_t does not exclude other CPUs. On a non-RT kernel it compiles down to preemption or interrupt disabling, and Documentation/locking/locktypes.rst is blunt about what that buys: “disabling preemption or interrupts are pure CPU local concurrency control mechanisms and not suited for inter-CPU concurrency control.”

So a local lock protects a per-CPU variable against the other things that can run on this CPU — another task after a preemption, a softirq, an interrupt handler — and against nothing else. If CPU 1 needs to reach into CPU 0's copy of the data, as a summing read side or a hot-unplug drain or a per-CPU cache reclaimer does, holding the local lock on CPU 1 excludes nobody. Such code needs a real cross-CPU lock, or it needs to be structured so the remote access is safe by construction: read-only against a value written atomically, or performed with the owning CPU stopped.

This is also why the RT mapping is not simply a debugging nicety. On PREEMPT_RT a local_lock_t becomes a per-CPU spinlock_t, which does not disable preemption — the critical section stays preemptible, and exclusion comes from the lock itself. Code that quietly relied on local_lock() to keep preemption off, rather than to protect the named data, breaks there. The correct fix is to say what was meant: if the requirement is atomicity against interrupts, use the _irqsave variant; if it is that a section must not be preempted, that is a preempt_disable(), and on an RT kernel it deserves justification.

When to Use Local Locks

Use local_lock when:

  • Protecting per-CPU data from preemption (or preemption + IRQs)
  • The code must work correctly on PREEMPT_RT
  • You want lockdep to validate lock ordering

Do not use local_lock when:

  • Data is shared across CPUs → use spinlock, mutex, or RCU
  • You just need a quick preempt_disable() for a single read
  • The critical section already holds a spinlock

Mutexes

Mutexes are the primary sleeping mutual-exclusion primitive in Linux 7.0.12. Introduced by Ingo Molnar in 2006 (Linux 2.6.16) to replace counting semaphores, they provide stricter semantics that enable better debugging, priority inheritance, and performance optimizations impossible with semaphores.

Mutex Rules (Enforced by Design)

  1. Only the owner can unlock — the owner field tracks who holds the lock
  2. Recursive locking is forbidden — immediately detected by debug builds
  3. Cannot be used in interrupt/softirq context — might_sleep() warns
  4. Must not be held when task exits — detected by debug builds
  5. A mutex must be initialized via the API — not via memset or struct copy
  6. Multiple unlocks are not permitted — owner tracking prevents this
  7. Held mutexes must not be reinitialized — re-running mutex_init() on a locked mutex silently discards the owner and the wait list
  8. Memory holding a locked mutex must not be freed — the classic version of this bug is freeing the containing object from inside the critical section, so that mutex_unlock() writes to memory that has been reallocated

The full list is in Documentation/locking/mutex-design.rst, which adds that these semantics “are fully enforced when CONFIG_DEBUG_MUTEXES is enabled”. That qualification matters: on a production build most of these are conventions the code is expected to honour, not invariants the kernel checks. A mutex bug that only reproduces under load is often one of these rules being broken on a rare path, and the first diagnostic step is to rebuild with CONFIG_DEBUG_MUTEXES and lockdep on.

Two of the optimizations that make a mutex faster than a counting semaphore follow directly from the rules: because there is exactly one owner and the owner is recorded, the uncontended path can be a single cmpxchg, and a contending task can ask whether the owner is currently running and spin instead of sleeping if it is.

What does not follow — and is worth being precise about, because the two are easily conflated — is priority inheritance. A plain struct mutex on a non-RT kernel has none; there is no priority-inheritance code in kernel/locking/mutex.c at all. Priority inheritance is the defining feature of rt_mutex, discussed in the next section, and a mutex acquires it only on PREEMPT_RT, where struct mutex is a thin wrapper around rt_mutex_base. On a server kernel, a low-priority task holding a mutex that a high-priority task wants will not be boosted, and the high-priority task waits.

The Three Lock Paths

Path 1 — Fast path (uncontended):

static __always_inline bool __mutex_trylock_fast(struct mutex *lock)
{
    unsigned long curr = (unsigned long)current;
    unsigned long zero = 0UL;

    /* Single atomic cmpxchg: if owner==0, set owner=current */
    if (atomic_long_try_cmpxchg_acquire(&lock->owner, &zero, curr))
        return true;    /* Got the lock in one instruction! */
    return false;
}

On x86_64, this compiles to a single LOCK CMPXCHG instruction. When the lock is uncontended (the common case), this is all that happens.

Path 2 — Optimistic spinning (midpath):

/* kernel/locking/mutex.c — mutex_optimistic_spin() (simplified) */
if (!mutex_can_spin_on_owner(lock))  /* owner not running? don't spin */
    goto fail;

if (!osq_lock(&lock->osq))          /* queue on MCS spinner lock */
    goto fail;

for (;;) {
    owner = __mutex_trylock_or_owner(lock);
    if (!owner)
        break;              /* got the lock! */

    if (!mutex_spin_on_owner(lock, owner))
        goto fail_unlock;   /* owner slept or was preempted */

    cpu_relax();
}
osq_unlock(&lock->osq);
return true;    /* acquired without sleeping! */

Path 3 — Slowpath (sleep): adds task to FIFO wait_list, sets TASK_UNINTERRUPTIBLE, calls schedule(). The handoff mechanism ensures fairness: when the first waiter has been waiting too long, it sets MUTEX_FLAG_HANDOFF, and the unlock path hands the lock directly to it.

RT-Mutexes (Priority-Inheritance Mutexes)

RT-mutexes are sleeping mutual-exclusion locks that implement priority inheritance (PI) — the fundamental mechanism for preventing priority inversion in real-time systems. When a high-priority task blocks on an rt_mutex held by a low-priority task, the holder's effective priority is temporarily boosted to the blocker's priority.

The Priority Inversion Problem

Priority inversion occurs when a high-priority task is effectively blocked by a lower-priority task:

  1. Low-priority task L acquires lock X
  2. High-priority task H arrives and blocks on X
  3. Medium-priority task M preempts L (doesn't need X)
  4. H is now effectively blocked by M — unbounded priority inversion!

With an rt_mutex, when H blocks on the lock, L's priority is boosted to H's level. Now M cannot preempt L, so L finishes quickly and releases the lock to H.

The struct rt_mutex_base

/* include/linux/rtmutex.h */
struct rt_mutex_base {
    raw_spinlock_t      wait_lock;     /* protects waiters tree and owner */
    struct rb_root_cached waiters;     /* RB-tree of waiters, prio-ordered */
    struct task_struct  *owner;        /* owner | RT_MUTEX_HAS_WAITERS */
};

/* kernel/locking/rtmutex_common.h */
struct rt_mutex_waiter {
    struct rt_waiter_node tree;        /* node in lock's waiters tree */
    struct rt_waiter_node pi_tree;     /* node in owner's pi_waiters tree */
    struct task_struct    *task;        /* the waiting task */
    struct rt_mutex_base  *lock;       /* lock being waited on */
    unsigned int          wake_state;
};

struct rt_waiter_node {
    struct rb_node  entry;             /* RB-tree linkage */
    int             prio;              /* task priority */
    u64             deadline;          /* SCHED_DEADLINE: absolute deadline */
};

Key design: RB-tree waiters (not a list) — highest-priority waiter is the leftmost cached node (O(1) access). Each task has a pi_waiters tree of the top-waiter from each rt_mutex it owns — the task's effective priority is the minimum of its own priority and all pi_waiters.

Priority Inheritance Chain Walking

The most complex part of rt_mutex is transitive priority propagation:

/* kernel/locking/rtmutex.c — simplified chain walk */
static int rt_mutex_adjust_prio_chain(struct task_struct *task, ...)
{
again:
    if (++depth > max_lock_depth)  /* default: 1024 */
        return -EDEADLK;

    raw_spin_lock(&task->pi_lock);
    waiter = task->pi_blocked_on;
    if (!waiter) goto out;         /* end of chain */

    /* Requeue waiter with updated priority */
    rt_mutex_dequeue(lock, waiter);
    waiter_update_prio(waiter, task);
    rt_mutex_enqueue(lock, waiter);

    /* Boost/deboost the lock owner */
    owner = rt_mutex_owner(lock);
    rt_mutex_adjust_prio(lock, owner);

    /* Continue walking if owner is also blocked */
    next_lock = task_blocked_on_lock(owner);
    if (next_lock) { task = owner; goto again; }
}

The chain walk is fully preemptible (drops locks between steps), bounded by max_lock_depth, and handles concurrent lock graph changes.

What Priority Inheritance Cannot Fix

Priority inheritance solves inversion caused by lock ownership, and only that. It works by finding the task that holds what the blocked task needs and raising its priority, which presupposes both that such a task exists and that raising its priority will get it scheduled. Neither holds universally.

Documentation/locking/locktypes.rst puts the limit plainly: PI “clearly cannot preempt preemption-disabled or interrupt-disabled regions of code, even on PREEMPT_RT kernels.” If the low-priority holder is inside a preempt_disable() section, or an interrupt handler is running on that CPU, boosting its priority changes nothing — the scheduler is not being consulted. The boosted task will run when the non-preemptible region ends and not before.

This is the real reason PREEMPT_RT does so much conversion work rather than simply making every lock a PI lock. Boosting is only useful in code the scheduler can act on, so RT executes “most such regions of code in preemptible task context, especially interrupt handlers and soft interrupts”. Threaded interrupt handlers and sleeping spinlock_t are not ends in themselves; they exist to shrink the set of regions in which priority inheritance is powerless. What is left — raw_spinlock_t sections, genuine interrupt-disabled code, the scheduler and timer core — is precisely the residual latency of an RT kernel.

Two smaller limits are worth stating alongside it. Inheritance is transitive but not retroactive: it applies while a task is blocked, so a holder that is preempted before anyone blocks on it is not boosted until the first waiter arrives. And PI addresses inversion, not deadlock — an rt_mutex will boost a holder happily while a lock cycle forms around it, which is why rt_mutex carries its own deadlock detection rather than relying on the boost to break the chain.

Proxy Locking: Acquiring on Behalf of Another Task

Every other lock in this chapter is acquired by the task that will use it. The rt_mutex has a second, stranger interface where one task starts an acquisition for someone else, and it exists for one caller: PI futexes.

The problem is FUTEX_CMP_REQUEUE_PI. A userspace condition variable needs to move waiters from the condvar's futex to the associated mutex's futex without waking them, and the mutex's futex has a kernel-side rt_mutex attached to it for priority inheritance. The requeueing task must therefore enqueue a different task as a waiter on that rt_mutex — the classic invariant that the blocking task is current does not hold. The comment at kernel/locking/rtmutex.c flags exactly this: “When invoked from rt_mutex_start_proxy_lock() waiter::task != current !”

The API in kernel/locking/rtmutex_api.c splits an acquisition into its parts, each marked “Special API call for PI-futex support”:

  • rt_mutex_init_proxy_locked() — initialize an rt_mutex already held by a named task, used when the kernel discovers an existing userspace owner.
  • rt_mutex_start_proxy_lock() — enqueue the waiter and run deadlock detection, but do not wait. It returns 1 if the lock was acquired outright, in which case the caller must wake the task it acted for.
  • rt_mutex_wait_proxy_lock() — the wait, performed later by the task itself.
  • rt_mutex_cleanup_proxy_lock() — remove the waiter if the wait was abandoned, on a signal or timeout.

The split is the whole point, and it is also the hazard. The underscore-prefixed __rt_mutex_start_proxy_lock() does not dequeue the waiter on failure, while the plain form does; either way, once a waiter is enqueued the sequence must be finished by a wait or a cleanup, or the rt_mutex is left with a waiter that will never run. Ordinary kernel code should never touch these functions — they are listed here because their existence explains why the rt_mutex internals are structured around a waiter object rather than around current.

Read/Write Semaphores

Read/write semaphores (struct rw_semaphore) are sleeping locks that allow multiple concurrent readers or a single exclusive writer. They are the standard choice when shared data is read frequently but written rarely, and the critical section may sleep.

When to Use rwsem

  • Data protection where reads greatly outnumber writes
  • Critical sections that may sleep (allocate memory, perform I/O)
  • File system inode locking (i_rwsem), memory map locking (mmap_lock)
  • VMA tree protection, address space operations

The struct rw_semaphore

/* include/linux/rwsem.h — non-PREEMPT_RT */
struct rw_semaphore {
    atomic_long_t       count;    /* reader count + writer/flag bits */
    atomic_long_t       owner;    /* owner task + READER_OWNED/NONSPINNABLE */
#ifdef CONFIG_RWSEM_SPIN_ON_OWNER
    struct optimistic_spin_queue osq;  /* MCS queue for spinning writers */
#endif
    raw_spinlock_t      wait_lock;     /* protects wait_list */
    struct list_head    wait_list;      /* blocked waiters (FIFO) */
};

The count field packs everything into a single long: bit 0 = WRITER_LOCKED, bit 1 = FLAG_WAITERS, bit 2 = FLAG_HANDOFF, bit 63 = FLAG_READFAIL, bits 8-62 = reader count (each reader adds RWSEM_READER_BIAS = 256).

Fast Paths

/* kernel/locking/rwsem.c — reader fast path */
static inline bool rwsem_read_trylock(struct rw_semaphore *sem, long *cntp)
{
    /* Atomic add RWSEM_READER_BIAS (256) to count */
    *cntp = atomic_long_add_return_acquire(RWSEM_READER_BIAS, &sem->count);

    if (!(*cntp & RWSEM_READ_FAILED_MASK)) {
        rwsem_set_reader_owned(sem);
        return true;    /* No writer, no waiters → got it! */
    }
    return false;       /* Conflict → undo and slowpath */
}

/* Writer fast path */
static inline bool rwsem_write_trylock(struct rw_semaphore *sem)
{
    long tmp = RWSEM_UNLOCKED_VALUE;    /* 0 */
    /* cmpxchg: if count==0, set count=RWSEM_WRITER_LOCKED */
    if (atomic_long_try_cmpxchg_acquire(&sem->count, &tmp, RWSEM_WRITER_LOCKED)) {
        rwsem_set_owner(sem);
        return true;
    }
    return false;
}

Reader acquisition is a single atomic add. If no conflicting flags are set, the reader has the lock immediately. Multiple readers run concurrently without blocking each other.

Optimistic Spinning and Fairness

Like mutexes, writers use optimistic spinning (OSQ-based) when the current holder is running. The RWSEM_NONSPINNABLE bit indicates spinning won't help (too many readers).

The handoff mechanism prevents starvation: when a writer is on the wait_list, new readers are blocked (they see RWSEM_FLAG_WAITERS). If the first waiter has waited too long, RWSEM_FLAG_HANDOFF ensures direct lock transfer.

Blocking new readers as soon as a writer is queued is what makes the lock fair, and it has a consequence that is easy to overlook: read acquisition is not recursive. A task that already holds the lock for reading and tries to take it for reading again will deadlock if a writer arrived in between — the second acquisition blocks behind the queued writer, and the writer blocks behind the reference the task is still holding. Nothing detects this at the point of use; it needs lockdep, or a writer arriving at the wrong moment.

Ownership is also enforced by default. Documentation/locking/locktypes.rst notes that an rwsem “complies by default with the strict owner semantics” — the task that acquired it is the task that must release it — while adding that “there exist special-purpose interfaces that allow non-owner release for readers” for the few subsystems that genuinely need to hand a read reference to another context.

Fairness Inverts on PREEMPT_RT

The fairness described above is a property of the non-RT implementation. PREEMPT_RT maps rw_semaphore onto a separate rt-mutex-based implementation, and the result is not merely slower — it is asymmetric in a way that has no counterpart on a normal kernel.

Priority inheritance works by having a blocked task donate its priority to the task holding what it needs. That works when there is exactly one holder to donate to, and rwsem readers break the assumption:

  • A preempted low-priority reader keeps its lock, and a blocked writer cannot boost it — a writer “cannot grant its priority to multiple readers”. So a high-priority writer can be starved by a low-priority reader that is not running.
  • A preempted low-priority writer is boosted, because the readers waiting behind it can each donate priority to the single holder. So a writer cannot starve readers.

The practical reading is that on an RT kernel an rwsem read-side critical section should be short and should avoid being preemptible for long, since it is the one direction the priority-inheritance machinery cannot repair.

Downgrade

down_write(&sem);
/* modify data (exclusive) */
downgrade_write(&sem);  /* atomic: writer → reader, no gap */
/* read-only access — other readers can now enter */
up_read(&sem);

WW-Mutexes (Wound/Wait Deadlock Avoidance)

WW-mutexes solve a fundamental problem: how to acquire multiple locks in an unpredictable order without deadlock. Traditional lock ordering rules fail when the set of locks is determined at runtime — common in GPU drivers, filesystem renames, and database-style transactions.

This primitive did not exist in Linux 2.6 — it was introduced in Linux 3.11 (2013) specifically for the DRM/TTM GPU memory management subsystem.

The Problem

Two tasks need to lock two GPU buffer objects discovered in different orders:

Task T1:                    Task T2:
  lock(buf_A)                 lock(buf_B)
  lock(buf_B) ← blocks       lock(buf_A) ← blocks
  DEADLOCK!                   DEADLOCK!

Two Algorithms

Wound/Wait (DEFINE_WW_CLASS): Older transaction wounds newer one (newer gets -EDEADLK and backs off). Newer waits for older. Optimistic: older never backs off.

Wait/Die (DEFINE_WD_CLASS): Older transaction waits. Newer dies immediately with -EDEADLK. Pessimistic: newer always backs off immediately.

Data Structures

/* include/linux/ww_mutex.h */
struct ww_class {
    atomic_long_t stamp;           /* global ticket counter */
    unsigned int is_wait_die;      /* 0=wound/wait, 1=wait/die */
};

struct ww_mutex {
    struct mutex base;             /* inherits all mutex features */
    struct ww_acquire_ctx *ctx;    /* owning transaction (or NULL) */
};

struct ww_acquire_ctx {
    struct task_struct *task;
    unsigned long stamp;           /* ticket (lower = older = higher priority) */
    unsigned int acquired;         /* locks held in this transaction */
    unsigned short wounded;        /* set when wounded by older */
    unsigned short is_wait_die;    /* algorithm choice */
};

Usage Pattern

DEFINE_WW_CLASS(buffer_class);   /* or DEFINE_WD_CLASS() */

struct ww_acquire_ctx ctx;
struct buffer *bufs[2] = { buf_a, buf_b };
struct buffer *slow = NULL;    /* already held by a previous lock_slow() */
struct buffer *contended;
int i, ret;

ww_acquire_init(&ctx, &buffer_class);   /* get ticket stamp — once */

retry:
    for (i = 0; i < 2; i++) {
        if (bufs[i] == slow)
            continue;               /* lock_slow() already acquired it */
        ret = ww_mutex_lock(&bufs[i]->lock, &ctx);
        if (ret == -EDEADLK)
            goto backoff;
    }

    ww_acquire_done(&ctx);          /* optional: acquire phase over */

    /* ... all buffers locked; use the data ... */

    ww_mutex_unlock(&bufs[1]->lock);
    ww_mutex_unlock(&bufs[0]->lock);
    ww_acquire_fini(&ctx);
    return 0;

backoff:
    contended = bufs[i];            /* the one that returned -EDEADLK */

    /* Drop every lock this context holds — those taken on this pass,
     * and the one carried over from the previous lock_slow(). */
    while (i-- > 0)
        if (bufs[i] != slow)
            ww_mutex_unlock(&bufs[i]->lock);
    if (slow)
        ww_mutex_unlock(&slow->lock);

    ww_mutex_lock_slow(&contended->lock, &ctx);   /* blocks; cannot fail */
    slow = contended;               /* skip it on the next pass */
    goto retry;

Three details in that skeleton are easy to get wrong, and each has a distinct failure mode.

The contended lock must be remembered and skipped. ww_mutex_lock_slow() does not merely wait — it acquires. Jumping straight back to retry without recording that fact means locking it a second time within the same context, which returns -EALREADY. The kernel's own example in Documentation/locking/ww-mutex-design.rst carries a res_obj pointer for exactly this and skips it at the top of the loop. That -EALREADY is not purely an error path, incidentally: drivers that build the lock list from userspace input use it deliberately to detect a duplicate handle in an ioctl argument.

Everything must be released before the slow path. Backing off means backing off completely. A context that keeps one lock while blocking in ww_mutex_lock_slow() on another has recreated the hold-and-wait condition the whole mechanism exists to prevent, and the algorithm's progress guarantee no longer applies.

The context is not re-initialized on retry. ww_acquire_init() is called once, outside the loop, and the stamp it assigned persists across every backoff. This is the load-bearing part. Because stamps are handed out in increasing order, a task that has been forced to retry keeps its original, older stamp while newer transactions arrive with larger ones — so each backoff makes it relatively older, and eventually old enough that nothing can force it back off again. Re-initializing inside the retry loop would issue a fresh, younger stamp each time and convert a bounded retry into a livelock.

The key guarantee follows from that ordering: older transactions never back off, so at least one transaction always makes progress and no livelock is possible.

One asymmetry between the two algorithms shows up here. Under Wait/Die the loser learns its fate synchronously — the ww_mutex_lock() call that would have blocked returns -EDEADLK itself. Under Wound/Wait, wounding is lazy: the older task sets wounded = 1 in the victim's context and wakes it, but the victim only acts on it at its next acquisition, where __ww_mutex_check_kill() inspects the flag. A wounded transaction that happens to have taken its last lock already will run to completion without ever backing off. The wound is a request to yield at the next convenient point, not a signal delivered mid-flight — which is precisely why the algorithm is safe to use around long critical sections in a GPU submission path.

Completions

Completions are a lightweight event signaling mechanism: one or more tasks wait for an event that another task (or interrupt handler) signals. They are the correct primitive for "wait until this operation finishes" patterns — replacing the error-prone use of binary semaphores for signaling that was common in Linux 2.6.

Why Not Semaphores for Signaling?

In Linux 2.6, developers often used down()/up() on a binary semaphore to signal completion of an asynchronous operation. This had several problems:

  1. Semantic confusion — semaphores are mutual exclusion primitives, not signaling primitives; using them for signaling obscures intent
  2. No complete_all() — waking all waiters required repeated up() calls with race conditions
  3. Counter overflow — multiple up() calls could accumulate, causing spurious wakeups later
  4. No reinit — couldn't easily reset after complete_all()
  5. Priority inversion — semaphores can cause PI issues when used as event signals; completions don't, because there's no "owner"

Completions solve all these problems with a purpose-built interface.

The struct completion

/* include/linux/completion.h */
struct completion {
    unsigned int done;                /* completion counter */
    struct swait_queue_head wait;     /* simple wait queue (smaller than wait_queue) */
};

The done counter semantics:

  • 0 — not yet complete, waiters will sleep
  • 1..UINT_MAX-1 — completed N times (each wait_for_completion() decrements by 1)
  • UINT_MAX — permanently complete (complete_all() was called; all waiters pass through)

Using swait_queue_head (simple waitqueue) instead of the full wait_queue_head makes completions smaller and usable in all contexts including hard IRQ.

Implementation

/* kernel/sched/completion.c */
void complete(struct completion *x)
{
    unsigned long flags;

    raw_spin_lock_irqsave(&x->wait.lock, flags);
    if (x->done != UINT_MAX)
        x->done++;                    /* increment counter */
    swake_up_locked(&x->wait, 0);    /* wake one waiter */
    raw_spin_unlock_irqrestore(&x->wait.lock, flags);
}

void complete_all(struct completion *x)
{
    raw_spin_lock_irqsave(&x->wait.lock, flags);
    x->done = UINT_MAX;              /* permanently done */
    swake_up_all_locked(&x->wait);   /* wake ALL waiters */
    raw_spin_unlock_irqrestore(&x->wait.lock, flags);
}

/* Waiter (simplified) */
void wait_for_completion(struct completion *x)
{
    raw_spin_lock_irq(&x->wait.lock);
    if (!x->done) {
        DECLARE_SWAITQUEUE(wait);
        do {
            __prepare_to_swait(&x->wait, &wait);
            __set_current_state(TASK_UNINTERRUPTIBLE);
            raw_spin_unlock_irq(&x->wait.lock);
            schedule();                /* sleep */
            raw_spin_lock_irq(&x->wait.lock);
        } while (!x->done);
        __finish_swait(&x->wait, &wait);
    }
    if (x->done != UINT_MAX)
        x->done--;                    /* consume one completion */
    raw_spin_unlock_irq(&x->wait.lock);
}

Key properties:

  • complete() is safe to call from any context (including hard IRQ, NMI)
  • wait_for_completion() may sleep — only callable from process context
  • If complete() is called before wait_for_completion(), the waiter doesn't sleep (counter is already > 0)
  • complete_all() sets done = UINT_MAX, waking all current and future waiters until reinit_completion()

Common Usage Patterns

/* Pattern 1: One-shot "operation done" signal */
DECLARE_COMPLETION_ONSTACK(done);

kthread_run(worker_func, &done, "worker");
/* ... do other work ... */
wait_for_completion(&done);    /* wait for worker to finish */

/* In worker_func: */
complete(&done);               /* signal: I'm done */

/* Pattern 2: Reusable with timeout */
struct completion fw_loaded;
init_completion(&fw_loaded);

request_firmware_nowait(..., firmware_callback, &fw_loaded);
ret = wait_for_completion_timeout(&fw_loaded, 5 * HZ);
if (!ret) {
    /* timeout — firmware didn't load in 5 seconds */
}
reinit_completion(&fw_loaded); /* reset for next use */

/* Pattern 3: complete_all() for module shutdown */
complete_all(&shutdown_done);  /* wake all threads waiting for shutdown */

The Lifetime Trap: Completions on the Stack

Pattern 1 above puts the completion on the stack, which is idiomatic and, as written, correct. It is also one step away from a bug that is very hard to find, and the step is Pattern 2.

A completion is not finished being used when wait_for_completion() returns. The waiter is woken from inside complete(), but complete() still has work to do afterwards — it holds the completion's own lock while it does so. If the waiter returns from its function at that moment, the stack frame holding the completion is gone, and the completer is left writing into whatever now occupies those bytes.

For the plain wait_for_completion() this is handled: the waiter cannot proceed until the completion has been signalled, so the ordering is at least well defined. The danger arrives with every variant that can return without the event having happened:

  • wait_for_completion_timeout() — returns 0 when the time expires
  • wait_for_completion_interruptible() — returns -ERESTARTSYS on a signal
  • wait_for_completion_killable() — returns on a fatal signal

In each case the wait has ended but the other side has not been told to stop. Pattern 2 is precisely this shape: when the five-second timeout expires, firmware_callback has not been cancelled and will still call complete(&fw_loaded) whenever the firmware eventually arrives. If fw_loaded lived on the stack of a function that has since returned, that call corrupts an unrelated frame.

Documentation/scheduler/completion.rst is explicit that the lockdep annotation is not the main reason to use DECLARE_COMPLETION_ONSTACK(): the macro exists “not just to make lockdep happy, but also to make it clear that limited scope had been considered and is intentional.” It adds that the wait “might complete prematurely while the object might still be in use by another thread”, that returning “will deallocate the function stack and cause subtle data corruption”, and — the sentence worth remembering — that “simple testing might not trigger these kinds of races.”

The rule that follows is about ownership rather than about completions. A stack-allocated completion is safe only when the waiting function cannot return until every possible completer has finished with it. As soon as a timeout or a signal can end the wait early, that guarantee is gone, and the completion must either outlive both parties — embedded in a structure whose lifetime is already managed, which is what the documentation recommends — or be protected by something that can definitively cancel the completer before the wait returns.

Disabling Interrupts and Deferrable Functions

Disabling local interrupts or deferrable functions (softirqs, tasklets) is the most primitive synchronization technique in the kernel. It doesn't use locks at all — instead, it prevents certain code paths from running on the local CPU, eliminating concurrency at its source.

This technique is used when:

  • Data is accessed from both process context and interrupt/softirq context on the same CPU
  • The critical section is very short (a few instructions)
  • You need to protect per-CPU data from being corrupted by an interrupt that preempts the current code

Critical limitation: Disabling interrupts/softirqs only protects against concurrency on the local CPU. On SMP systems, another CPU can still access shared data concurrently, so you must combine interrupt disabling with a spinlock (hence spin_lock_irqsave()).

Local Interrupt Disabling

The kernel provides two pairs of macros for disabling/enabling hardware interrupts on the local CPU:

/* Pair 1: Save/restore — PREFERRED (nestable, composable) */
unsigned long flags;
local_irq_save(flags);      /* save current IF state + disable IRQs */
/* ... critical section ... */
local_irq_restore(flags);   /* restore previous IF state (may stay disabled!) */

/* Pair 2: Unconditional — only when you KNOW IRQs are currently enabled */
local_irq_disable();        /* unconditionally disable */
local_irq_enable();         /* unconditionally enable */

Why local_irq_save()/local_irq_restore() is preferred: If a function disables interrupts and then calls another function that also disables interrupts, the inner function must not re-enable interrupts when it returns. local_irq_save()/local_irq_restore() handles this correctly by saving and restoring the previous state rather than assuming it was enabled.

Architecture Implementation

On x86_64, interrupt disabling maps directly to the cli/sti instructions:

/* arch/x86/include/asm/irqflags.h */
static __always_inline void native_irq_disable(void)
{
    asm volatile("cli": : :"memory");   /* Clear Interrupt Flag */
}

static __always_inline void native_irq_enable(void)
{
    asm volatile("sti": : :"memory");   /* Set Interrupt Flag */
}

static __always_inline unsigned long native_local_irq_save(void)
{
    unsigned long flags = native_save_fl();  /* pushfq; read EFLAGS */
    native_irq_disable();                    /* cli */
    return flags;
}

On ARM64, two mechanisms are available:

/* arch/arm64/include/asm/irqflags.h */

/* Method 1: DAIF masking (traditional) — set bits in PSTATE.DAIF */
static __always_inline void __daif_local_irq_disable(void)
{
    barrier();
    asm volatile("msr daifset, #3");   /* mask IRQ + FIQ */
    barrier();
}

/* Method 2: Priority masking (GICv3) — write to ICC_PMR_EL1 */
static __always_inline void __pmr_local_irq_disable(void)
{
    barrier();
    write_sysreg_s(GIC_PRIO_IRQOFF, SYS_ICC_PMR_EL1);
    barrier();
}

/* Runtime selection based on hardware capability */
static inline void arch_local_irq_disable(void)
{
    if (system_uses_irq_prio_masking())
        __pmr_local_irq_disable();      /* pseudo-NMI support */
    else
        __daif_local_irq_disable();     /* traditional */
}

The priority masking method (PMR) is used when the kernel is configured with pseudo-NMI support — it allows certain high-priority interrupts to fire even when "interrupts are disabled," enabling features like perf profiling in critical sections.

/* Protect data accessed from both process context and IRQ handler */

Disabling Softirqs/BH (Bottom Halves)

Softirqs (and tasklets, which run atop softirqs) are deferrable functions — they execute after hardware interrupts return to process context. If your code shares data with a softirq handler, you need to prevent softirqs from preempting you.

local_bh_disable();         /* increment softirq disable count; defer softirqs */
/* ... critical section (softirqs cannot run here) ... */
local_bh_enable();          /* decrement count; if zero, run pending softirqs */
How It Works: The preempt_count Field

The kernel tracks interrupt/softirq/preemption nesting in a single per-task integer called preempt_count:

/* include/linux/preempt.h — bit layout of preempt_count */
/*
 * PREEMPT_MASK:  bits  0-7   (preemption depth, max 256)
 * SOFTIRQ_MASK:  bits  8-15  (softirq disable count, max 256)
 * HARDIRQ_MASK:  bits 16-19  (hardirq nesting depth, max 16)
 * NMI_MASK:      bits 20-23  (NMI nesting depth, max 16)

{

            migrate_disable();     /* non-RT: stay on this CPU */
            rcu_read_lock();       /* satisfy RCU BH requirements */
        }
    }

    /* Increment per-CPU + per-task softirq disable counters */
    this_cpu_add(softirq_ctrl.cnt, cnt);

}

void __local_bh_enable_ip(unsigned long ip, unsigned int cnt)
{
    u32 pending;

    /* Only check for pending softirqs on last enable (outermost) */
    if (current->softirq_disable_cnt != cnt)
        goto out;

    pending = local_softirq_pending();
    if (!pending || !preemptible()) {
        if (!preemptible() && pending)
            wakeup_softirqd();   /* wake ksoftirqd to process later */
        goto out;
    }

    /* Pending softirqs exist and we're preemptible — run them now */
    __do_softirq();

out:
    current->softirq_disable_cnt -= cnt;
    this_cpu_sub(softirq_ctrl.cnt, cnt);
    if (!current->softirq_disable_cnt) {
        rcu_read_unlock();
        migrate_enable();
    }
}

Scope-Based Cleanup: guard() and scoped_guard()

Linux 7.0.12 introduces scope-based resource management (entirely absent in Linux 2.6) via include/linux/cleanup.h. This is the kernel's answer to C++'s RAII: resources are automatically released when the variable goes out of scope, enforced by GCC's __attribute__((cleanup())).

The Problem: Error-Path Resource Leaks

The traditional kernel pattern uses goto chains for error unwinding:

/* Traditional pattern — error-prone */
int old_style(struct device *dev)
{
    struct resource *r;
    int ret;

    mutex_lock(&dev->lock);

    r = alloc_resource();
    if (!r) {
        ret = -ENOMEM;
        goto err_unlock;
    }

    ret = setup_hardware(dev, r);
    if (ret)
        goto err_free;      /* forget this goto = LEAK */

    ret = register_device(dev);
    if (ret)
        goto err_free;      /* add new error path = must audit ALL gotos */

    mutex_unlock(&dev->lock);
    return 0;

err_free:
    free_resource(r);
err_unlock:
    mutex_unlock(&dev->lock);  /* forget this = DEADLOCK */
    return ret;
}

The Solution: Automatic Cleanup

/* Modern pattern — cleanup is automatic */
int modern_style(struct device *dev)
{
    int ret;

    guard(mutex)(&dev->lock);     /* auto-unlock at scope exit */

    struct resource *r __free(kfree) = alloc_resource();
    if (!r)
        return -ENOMEM;           /* lock auto-released, r is NULL so no free */

    ret = setup_hardware(dev, r);
    if (ret)
        return ret;               /* lock auto-released, r auto-freed */

    ret = register_device(dev);
    if (ret)
        return ret;               /* lock auto-released, r auto-freed */

    no_free_ptr(r);               /* SUCCESS: inhibit free */
    return 0;                     /* lock auto-released */
}

No goto, no labels, no possibility of forgetting to unlock. Every return statement automatically triggers cleanup in LIFO order.

ACQUIRE() / ACQUIRE_ERR() — Conditional Locks at Function Scope

scoped_cond_guard() has two limitations that matter in practice: it forces the protected code into a nested block, and the failure action is fixed at the macro call, so it cannot report why the acquisition failed. ACQUIRE() is the newer form that removes both. It declares a named guard instance at ordinary function scope, and ACQUIRE_ERR() then reports the outcome as a plain error code — zero on success, negative otherwise:

DEFINE_GUARD_COND(pci_dev, _try, pci_dev_trylock(_T));
...
ACQUIRE(pci_dev_try, lock)(dev);

rc = ACQUIRE_ERR(pci_dev_try, &lock);
if (rc)
    return rc;      /* not acquired; nothing to release */

/* lock is held, and released when this scope ends */

The conditional variant itself comes from DEFINE_GUARD_COND(), which attaches a try-style acquisition to an existing guard class. ACQUIRE_ERR() is, in the header's own words, “effectively a PTR_ERR() conversion of the guard pointer”: the guard holds either the acquired lock or an error, and the macro turns that into the value the caller returns.

Both conditional forms are current and neither is deprecated. Use scoped_cond_guard() when the failure action is simple and the critical section is naturally a block; use ACQUIRE() when the function needs the lock for the rest of its body, or when the specific error must be propagated to the caller.

LIFO Ordering Rule

/* CORRECT: lock defined before object (lock released AFTER object freed) */
guard(mutex)(&lock);
struct object *obj __free(remove_free) = alloc_add();

/* WRONG: object defined before lock */
struct object *obj __free(remove_free) = NULL;
guard(mutex)(&lock);
obj = alloc_add();
/* BUG: on error return, remove_free(obj) runs AFTER mutex_unlock()!
   but remove_free() requires the lock to be held! */

Best practice: Always define and initialize __free() variables in one statement, and place them after the guard that protects them.

Choosing the Right Synchronization Primitive

The preceding sections described roughly twenty distinct primitives, and a reader arriving at the end of them could be forgiven for wondering how anyone ever picks one. The answer is that the choice is far more constrained than the size of the menu suggests. Most of the constraints are not preferences at all but hard requirements imposed by the surrounding code: if the critical section can block, every spinning lock is off the table; if the caller runs in hardirq context, every sleeping lock is off the table. In practice, two or three questions eliminate all but a handful of candidates, and the remaining choice among those is a performance judgement rather than a correctness one.

That ordering matters, because the two kinds of mistake are not remotely symmetric. Choosing a primitive that is heavier than necessary costs throughput, and it costs it visibly: the contention shows up in perf lock, the cache-line bouncing shows up in profiles, and the fix is a contained, local change. Choosing one that is lighter than necessary costs correctness, and it costs it invisibly. A missing barrier or a lock that does not cover the interrupt path produces a race that may fire once a week on one machine in a fleet, corrupt a structure whose damage is only noticed thousands of instructions later, and resist every attempt at reproduction. The asymmetry argues for a clear bias: establish correctness first with the most obviously sufficient primitive, and optimize only when measurement shows the choice is costing something. A mutex that turns out to be unnecessary is a afternoon's work to remove. A race that shipped is a bug report from a customer.

Five properties of the data and its callers determine the answer:

  1. Context: Can the code sleep? Process context can; hardirq, softirq, NMI, and any region holding a spinning lock or with preemption disabled cannot. This is the first question because it is a hard filter rather than a preference — the answer removes roughly half the menu outright.
  2. What the data is: A single counter, a pointer to a structure, a whole data structure, or a one-shot event? This determines the answer more often than anything else. A counter wants atomic_t; a pointer read by many and replaced by few wants RCU; an event wants a completion. Reaching for a lock before asking this question is how a this_cpu_inc() ends up wrapped in a global mutex.
  3. Access pattern: Read-mostly, write-mostly, or balanced? A 1000:1 read-to-write ratio makes RCU or a seqlock dramatically cheaper than any lock, because both drive the reader's cost toward zero at the expense of the writer. A balanced ratio makes that trade pointless.
  4. Duration: How long does the critical section hold? Spinning is only sensible when the expected wait is shorter than the cost of two context switches — tens of nanoseconds to a few microseconds. Anything that copies a page, waits on hardware, or calls into an allocator that might reclaim belongs under a sleeping lock.
  5. Scope: Per-CPU, per-object, or global? Scope decides contention before any primitive does. A well-chosen per-object lock outperforms the cleverest global one, because the cheapest lock is the one no other CPU ever touches; this is why so much of the kernel's scalability work has been splitting locks rather than speeding them up.

One caveat frames everything below. The tables in this section give uncontended costs, and uncontended cost is the least important number in a real system. A spin_lock() whose cache line is already exclusive to this CPU costs a handful of nanoseconds; the same call on a line currently owned by a CPU in another NUMA node costs hundreds. What determines the performance of a synchronization design is almost never the instruction sequence of the lock — it is how often two CPUs want the same cache line at the same time. Use the numbers to compare primitives, never to predict throughput.

Finally, this section describes how to make the choice deliberately; it does not replace the machinery that checks the choice was right. Lockdep (CONFIG_PROVE_LOCKING) validates lock ordering, context correctness, and IRQ safety at runtime, and it finds classes of error that no amount of design care prevents. The workflow that actually works is to choose deliberately using the criteria here, then run the result under a debug kernel and let the validator disagree.

The Decision Flowchart

The steps below are ordered cheapest-first, and the first step that applies wins. That ordering is deliberate: each step asks whether a weaker mechanism suffices, so working down the list naturally lands on the lightest primitive that is still correct. Working the list in the other direction — starting from "which lock?" — skips the three cases where the right answer is no lock at all, and those three cases cover a surprising fraction of kernel code.

The list is a filter, not a lookup table. Several steps can apply to the same structure, because different fields of one object routinely want different treatment: a device structure might hold a refcount_t for its lifetime, an RCU-protected pointer to its current configuration, and a mutex for its ioctl path, all at once. Ask the questions per field, not per structure.

Step 1: Do you need synchronization at all? If the data is truly private to one thread — an on-stack variable, or a structure not yet published to any other CPU — no synchronization is needed, and adding some obscures that fact from the next reader. If the data is per-CPU and only accessed with preemption disabled, per-CPU variables suffice; on PREEMPT_RT, where preemption is not disabled by the usual means, express that requirement as a local_lock so it survives the RT transformation.

Step 2: Is it a simple counter? Use atomic_t / atomic64_t for increment/decrement/test. Use refcount_t for reference counting, which saturates rather than wrapping and so converts a refcount bug from an exploitable use-after-free into a leak. For a reference count on an RCU-managed object that is contended by many CPUs, use rcuref_t: it replaces atomic_inc_not_zero()'s try_cmpxchg() loop, whose behavior degrades quadratically with the number of concurrent operations, with an unconditional atomic_add_negative_relaxed() fast path.

Step 3: Is it a one-shot event notification? Use completion. The temptation here is to reach for a semaphore initialized to zero, which does work; the completion exists because it makes the intent explicit, is cheaper, and handles the case where the event fires before anyone waits for it.

Step 4: Is the data read-mostly? "Read-mostly" here means a ratio steep enough that making readers free is worth making writers expensive — as a rough guide, tens of reads per write and upward. Below that, the ordinary locks are simpler and no slower.

  • Pointer-based structures: Use RCU (zero-cost readers)
  • Small sequential data: Use seqlock (readers retry on write)
  • Read side must sleep: Use SRCU — the one RCU flavor that permits blocking inside the read-side critical section, at the cost of an explicitly initialized domain and a slower read side. The kernel's own guidance is emphatic that this is a fallback: if you do not need to sleep, plain RCU is almost always faster and easier
  • Readers extremely frequent, writers extremely rare, both can sleep: Use percpu_rw_semaphore, which pushes essentially all cost onto the writer by giving each CPU its own read counter. CPU hotplug and filesystem freezing use it
  • Frequent reads, occasional writes, can sleep: Use rw_semaphore

Step 5: Can the code sleep? If none of the above applies, an ordinary mutually-exclusive lock is the answer, and this last question picks which kind.

  • Cannot sleep: spinlock (+ _irqsave / _bh variants). Use raw_spinlock_t only where the code must spin even on PREEMPT_RT — scheduler and low-level interrupt code — and never merely because the section is short
  • Can sleep: mutex (normal), rt_mutex (needs PI), ww_mutex (multiple locks)

Whichever step the answer comes from, prefer the guard() and scoped_guard() forms described in the previous section over an explicit unlock. They do not change the choice of primitive; they remove the entire category of bugs where an error path forgets to release it.

The last entry deserves particular attention because it inverts an assumption that decades of kernel code have trained. On PREEMPT_RT, spin_lock_irqsave() does not disable interrupts. The RT definition sets flags = 0 and calls plain spin_lock(), which is now a sleeping rt_mutex acquisition; the kernel's own documentation states plainly that the _irq and _irqsave suffixes "do not affect the CPU's interrupt disabled state." Synchronization Scenarios

The previous section chose a primitive from the properties of the data. This section chooses one from the properties of the code that touches it, and it is the more mechanical of the two exercises: once you can name every context that reaches a data structure, the required protection follows almost without judgement. That is why this material is worth treating as a lookup table rather than a discussion. Getting it wrong is the most common cause of kernel deadlocks and data corruption, and — because the failure needs an interrupt to land inside a specific window on a specific CPU — the resulting bug is one of the least reproducible in the kernel.

The question to ask of any shared structure is not "is this concurrent?" but the sharper pair: what else touches this data, and can that thing interrupt me while I hold the lock? Those two halves are genuinely separate problems, and the confusion that makes this topic hard is that a single function call solves both at once.

The first problem is another CPU. A second processor can execute the same critical section at the same time as this one. Nothing about disabling interrupts helps here; the other CPU is not affected by the local CPU's interrupt mask. Only a lock helps — that is what the spin_lock() part of every recommendation below is for.

The second problem is this CPU. A higher-priority context — an interrupt, a softirq — can preempt this code while it holds the lock, and if that context tries to take the same lock it will spin forever waiting for a lock that only it can release by returning. This is a genuine self-deadlock and it needs no second CPU at all; it happens on a uniprocessor. Nothing about holding a lock helps here. Only suppressing the higher-priority context helps — that is what the _irqsave, _irq and _bh suffixes are for.

Every recommendation in this section is therefore a pair: a lock for the other CPUs, and possibly a suffix for this one. Reading the table with that split in mind explains what otherwise looks arbitrary — why the interrupt handler in Scenario 3 uses a bare spin_lock() while the process-context code guarding the same data uses spin_lock_irqsave(). Both need the lock, because both can race with the other CPU. Only one of them can be interrupted by the other, so only one needs a suffix.

That asymmetry is the single rule that generates the whole table. Kernel execution contexts form a strict priority hierarchy, and preemption runs in exactly one direction:

  1. NMI — the non-maskable interrupt, which by definition no software can defer.
  2. Hardirq — an interrupt handler, which preempts softirqs and process context.
  3. Softirq/BH — deferred work, which preempts process context only.
  4. Process context — system calls, kernel threads, workqueues; preempts nothing.

A context must lock out every context above it, and never needs to lock out anything below it. A hardirq handler cannot be interrupted by a softirq, so it never needs _bh; process context can be interrupted by both, so it needs the strongest suffix of whatever touches the data. If you remember only one thing from this section, remember that the direction of the rule is fixed, and that it is the lower-priority side that carries the cost.

Two boundaries on this material are worth stating up front, because both are places where the classical 2.6-era analysis no longer tells the whole story on a 7.0.12 kernel. First, the hierarchy above assumes an interrupt handler actually runs in interrupt context — with threaded interrupts, discussed below, it often does not. Second, the entire table assumes a non-PREEMPT_RT kernel; on RT the suffixes do not do what their names say, and the differences are set out at the end of this section. The kernel's own authoritative version of this table lives in Documentation/kernel-hacking/locking.rst, and it is worth reading alongside this one.

Scenario 1: Data Accessed Only by Process Context

This is the easiest case and by far the most common one, because most kernel data is never touched by an interrupt handler at all. Only the first of the two problems above applies: another CPU can run the same code, but nothing can preempt this code and then demand the same lock. No suffix is required, and that in turn means the critical section is allowed to sleep — which unlocks the whole family of sleeping locks and, with them, the ability to call kmalloc(GFP_KERNEL), copy to and from user space, or take a second mutex inside the section.

Note that "process context" here includes more than system calls. Kernel threads, workqueue items, and the thread half of a threaded interrupt handler are all process context and all follow this rule.

If a data structure is accessed only by process-context code (system call handlers, kernel threads, workqueues):

  • Uniprocessor: Kernel preemption is the only concern. preempt_disable()/preempt_enable() suffices for short sections, or use a mutex if the critical section may sleep.
  • SMP: Use a mutex (if you can sleep) or a spinlock (if you cannot). A mutex is preferred because it allows sleeping and has better contention behavior.
/* Example: process-context-only protection */
static DEFINE_MUTEX(my_mutex);
static struct my_data shared;

/* In system call or kernel thread: */
guard(mutex)(&my_mutex);
shared.field = new_value;      /* safe: no IRQ/softirq access */
/* mutex auto-released at scope exit */

Why not just preempt_disable() on SMP? Because another CPU could be accessing the data simultaneously. Preemption disabling only prevents concurrency on the local CPU.

Scenario 2: Data Accessed Only by Interrupt Handlers

Data touched only from interrupt handlers is unusual but does occur in drivers that keep hardware state entirely inside their ISR. The analysis splits on a question that is easy to miss: whether the data is shared with the same handler running elsewhere, or with a different handler entirely. The two cases have different answers, because a handler cannot preempt itself but can be preempted by another vector.

Single interrupt handler:

  • Uniprocessor: No synchronization needed — the handler can't re-enter on the same CPU.
  • SMP: Use a spinlock — the same handler can run on different CPUs simultaneously.

Multiple different interrupt handlers sharing data:

  • Uniprocessor: Use local_irq_save()/local_irq_restore().
  • SMP: Use spin_lock_irqsave()/spin_lock_irqrestore().

The _irqsave here deserves an explanation, because Golden Rule 3 below says interrupt handlers never need it. The rule holds for the handler's own interrupt, which is masked while it runs. It does not hold for other vectors: whether a handler runs with all interrupts disabled or only its own is, in the kernel's own words, architecture-specific, so two different handlers sharing data must not assume they are mutually excluded. Documentation/kernel-hacking/locking.rst is explicit that this case requires spin_lock_irqsave(). This is the one place where an interrupt handler legitimately carries a suffix.

/* Example: shared data between multiple IRQ handlers */
static DEFINE_SPINLOCK(shared_irq_lock);

irqreturn_t handler_a(int irq, void *dev_id)
{
    unsigned long flags;
    spin_lock_irqsave(&shared_irq_lock, flags);
    /* ... access shared data ... */
    spin_unlock_irqrestore(&shared_irq_lock, flags);
    return IRQ_HANDLED;
}

Scenario 3: Data Accessed by Process Context and Interrupts

This is the most common and important scenario in driver code, and the one the _irqsave suffix exists for. It is also the first case where both halves of the problem are live at once: two CPUs can run the two functions simultaneously, and the interrupt can land on the CPU that already holds the lock. A bare spinlock solves the first and deadlocks on the second.

The rule is asymmetric, and the asymmetry is the whole point: the process-context side pays for the suffix, the interrupt side does not.

  • SMP: Process-context code uses spin_lock_irqsave(). The interrupt handler uses spin_lock() (IRQs already disabled in hardirq context).
/* Example: process context + IRQ handler */
static DEFINE_SPINLOCK(dev_lock);

/* Process context — must disable IRQs */
ssize_t my_write(struct file *f, const char __user *data, ...)
{
    unsigned long flags;
    spin_lock_irqsave(&dev_lock, flags);   /* disable IRQ + lock */
    ring_buffer_write(&buf, data, count);
    spin_unlock_irqrestore(&dev_lock, flags);
    return count;
}

/* Interrupt handler — IRQs already disabled */
irqreturn_t my_irq(int irq, void *dev_id)
{
    spin_lock(&dev_lock);                  /* just lock, no IRQ save needed */
    ring_buffer_read(&buf, hw_register);
    spin_unlock(&dev_lock);
    return IRQ_HANDLED;
}

Why must process context use _irqsave? If process context only uses spin_lock(), and a hardirq fires on the same CPU while the lock is held, the handler will try to acquire the same lock → deadlock.

Scenario 4: Data Accessed by Process Context and Softirqs/Tasklets

Softirqs and tasklets are deferrable functions that execute after hardware interrupts return. They can preempt process context but cannot preempt hardirq handlers. This scenario is Scenario 3 one rung down the hierarchy, and it has the same shape: the lower-priority side suppresses the higher-priority one, the higher-priority side does not reciprocate. Only the suffix changes, from _irqsave to the cheaper _bh.

Tasklets are deprecated. include/linux/interrupt.h in 7.0.12 carries the notice directly above the tasklet declarations: "This API is deprecated. Please consider using threaded IRQs instead." Tasklets remain in the tree and a great deal of existing driver code still uses them, so the locking rules here still matter for reading that code. They are not, however, the right choice for anything new — a threaded interrupt handler is the modern replacement, and as discussed below it runs in process context and changes the locking analysis entirely.

Which lock to use:

  • Process context must use spin_lock_bh() — disables softirq/tasklet execution on the local CPU before acquiring the spinlock, preventing the deadlock where a softirq preempts and tries to acquire the same lock.
  • Softirq/tasklet must use spin_lock() — softirqs already run with BH disabled (a softirq cannot preempt another softirq on the same CPU), so only the spinlock is needed for cross-CPU protection.
  • On uniprocessor: process context needs only local_bh_disable().

Why spin_lock_bh() and not spin_lock_irqsave()? Disabling softirqs is cheaper than disabling all hardware interrupts. Since no hardirq handler accesses this data (by definition of this scenario), we don't need _irqsave.

Why the softirq uses plain spin_lock(): When a softirq runs, BH is already disabled on that CPU. No other softirq can preempt it on the same CPU. The only remaining concurrency is from other CPUs — which the spinlock handles.

/* Example: process context + softirq (networking pattern) */
static DEFINE_SPINLOCK(net_lock);
static struct packet_queue queue;

/* Process context (sending a packet) — MUST disable BH */
void send_packet(struct sk_buff *skb)
{
    spin_lock_bh(&net_lock);           /* disable BH + acquire lock */
    enqueue_packet(&queue, skb);
    spin_unlock_bh(&net_lock);         /* release lock + re-enable BH */
}

/* NET_RX softirq (receiving packets) — BH already disabled */
void net_rx_action(void)
{
    spin_lock(&net_lock);              /* just acquire the spinlock */
    skb = dequeue_packet(&queue);
    spin_unlock(&net_lock);
}

Real-world examples: This pattern is common in the networking stack — socket buffers, routing tables, and connection tracking tables accessed from both system calls and NET_RX/NET_TX softirqs.

Scenario 5: Data Accessed by Interrupts and Softirqs

The hardirq handler has higher priority — softirqs execute only after all pending hardirq handlers complete. This asymmetry determines which lock variant each context needs.

This pairing is the natural shape of a modern device driver: the hardirq handler does the minimum work needed to quiet the device and hand the data off, and a softirq does the expensive processing later with interrupts enabled. That "with interrupts enabled" is exactly what makes the softirq the vulnerable side here. Note that this is the one scenario where the softirq is the lower-priority participant and therefore the one that pays; in Scenario 4 the softirq was the higher-priority side and paid nothing.

Which lock to use:

  • Hardirq handler uses spin_lock() — it's the highest-priority context. A softirq cannot preempt a running hardirq handler, and IRQs are already disabled by hardware. Only the bare spinlock is needed for cross-CPU protection.
  • Softirq must use spin_lock_irq() — softirqs run with interrupts enabled. A hardirq could fire on the same CPU and try to acquire the same lock → deadlock. spin_lock_irq() disables interrupts first.

Why spin_lock_irq() and not spin_lock_irqsave()? In softirq context, interrupts are always enabled when the softirq starts, so we know the state to restore is "enabled." _irq is slightly cheaper than _irqsave (no flags save/restore).

/* Example: IRQ handler + softirq sharing hardware state */
static DEFINE_SPINLOCK(hw_lock);
static struct hw_ring hw_ring;

/* Hardirq handler — highest priority, bare spinlock */
irqreturn_t my_irq(int irq, void *dev_id)
{
    spin_lock(&hw_lock);               /* IRQs off by hw, just need SMP lock */
    hw_ring_push(&hw_ring, read_hw_register());
    raise_softirq_irqoff(MY_SOFTIRQ); /* IRQs already off — skip the save */
    spin_unlock(&hw_lock);
    return IRQ_HANDLED;
}

/* Softirq — must prevent hardirq from preempting */
void my_softirq_action(void)
{
    spin_lock_irq(&hw_lock);           /* disable IRQs + acquire lock */
    while (!hw_ring_empty(&hw_ring)) {
        item = hw_ring_pop(&hw_ring);
        process_item(item);
    }
    spin_unlock_irq(&hw_lock);         /* release lock + re-enable IRQs */
}

Real-world examples: Network device drivers where the hardirq collects received packets and the NAPI softirq processes them. Block device drivers where the hardirq signals I/O completion and a softirq processes completed requests.

Scenario 6: Data Accessed by All Contexts

When process context, hardirq handlers, AND softirqs all access the same data, each context needs the strongest protection its own position in the hierarchy demands. This is not a new rule but the previous three applied at once, and it is worth working through precisely because the answer for each context is unchanged from the scenario that introduced it.

Notice in particular that adding softirq access to a structure already shared with an interrupt handler costs the process-context side nothing. It was already using spin_lock_irqsave(), and disabling hardware interrupts implicitly prevents softirq execution too, since softirqs run on the return path from an interrupt. The suffixes are not independent options but a chain of increasing strength, and _irqsave is the top of it.

Which lock to use:

  • Process context uses spin_lock_irqsave(&lock, flags) — the most protective variant. Saves IRQ state, disables hardware interrupts (implicitly disables softirqs too), and acquires the spinlock. Protects against hardirq, softirq, and other-CPU concurrency simultaneously.
  • Hardirq handler uses spin_lock(&lock) — IRQs are already disabled by hardware when a hardirq runs. Since IRQ disable implies softirq disable, only the bare spinlock is needed for cross-CPU protection.
  • Softirq uses spin_lock_irq(&lock) — the softirq runs with IRQs enabled. A hardirq could fire and try to take the same lock. spin_lock_irq() prevents that deadlock. BH is already off in softirq context.

Why not just use spin_lock_irqsave() everywhere? You could — it's always safe. But it's wasteful in hardirq context (IRQs are already off) and slightly wasteful in softirq context (where we know IRQs are enabled, so _irq suffices without saving flags).

/* All-contexts scenario — e.g., timer/counter accessed from everywhere */
static DEFINE_SPINLOCK(global_lock);
static struct shared_state state;

/* Process context: highest risk — must block everything */
void process_func(void)
{
    unsigned long flags;
    spin_lock_irqsave(&global_lock, flags);  /* disables IRQs (⊃ BH) + lock */
    state.counter++;
    spin_unlock_irqrestore(&global_lock, flags);
}

/* Hardirq handler: IRQs already disabled by hardware */
irqreturn_t irq_handler(int irq, void *data)
{
    spin_lock(&global_lock);                 /* bare spinlock (already safe) */
    state.hw_events++;
    spin_unlock(&global_lock);
    return IRQ_HANDLED;
}

/* Softirq: must prevent hardirq deadlock */
void softirq_handler(void)
{
    spin_lock_irq(&global_lock);             /* disable IRQs + lock */
    state.processed += process_batch(&state);
    spin_unlock_irq(&global_lock);
}

Alternative with guard():

/* Modern style using scope-based cleanup */
void process_func(void)
{
    guard(spinlock_irqsave)(&global_lock);   /* auto-restore at scope exit */
    state.counter++;
}

Real-world examples: Timer interrupt updating jiffies (accessed by process context, timer IRQ, and softirq timers). Certain device drivers with interrupt coalescing where the same ring buffer is touched from all three contexts.

Scenario 7 (New in 7.0.12): Per-CPU Data with PREEMPT_RT

The six scenarios above all answer the question "which lock?". This one answers a different question: what to do when the data needs no lock at all, because each CPU has its own copy, and the only thing that must be prevented is the CPU changing underneath you. Per-CPU data is the cheapest synchronization in the kernel precisely because it removes the cross-CPU half of the problem entirely, leaving only the local half.

On standard kernels, per-CPU data accessed only in process context needs only preempt_disable() to prevent migration. On PREEMPT_RT kernels, preempt_disable() is avoided because it increases worst-case latency.

The tension that local_lock_t resolves is that these two requirements look incompatible. Non-RT wants a non-preemptible section, which costs nothing; RT wants something it can preempt and prioritize, which a non-preemptible section is by definition not. local_lock() is the abstraction that lets one piece of source code express the intent — "this CPU's copy is mine for the duration" — and be compiled into whichever mechanism the kernel configuration actually needs.

Which lock to use:

  • Standard kernel: local_lock() compiles to preempt_disable() + lockdep annotations. Zero cost but gives lockdep lock-ordering validation.
  • PREEMPT_RT kernel: local_lock() becomes a real per-CPU spinlock_t (which itself is an rt_mutex). It's a sleeping lock — other tasks can preempt while waiting.
  • Per-CPU data + IRQ access: Use local_lock_irqsave() (combines per-CPU protection with IRQ disabling).

Why not just preempt_disable() directly?

  1. PREEMPT_RT compatibility: local_lock() gives the RT kernel a proper lock to wait on instead of a non-preemptible section.
  2. Lockdep validation: local_lock() participates in dependency tracking, catching ordering bugs.
  3. Self-documenting: clearly communicates "this protects per-CPU data."
/* Works correctly on both standard and PREEMPT_RT kernels */
static DEFINE_PER_CPU(struct my_data, cpu_data);
static DEFINE_PER_CPU(local_lock_t, cpu_data_lock);

void update_cpu_data(void)
{
    local_lock(&cpu_data_lock);           /* non-RT: preempt_disable() */
                                          /* RT: acquire per-CPU rt_mutex */
    struct my_data *d = this_cpu_ptr(&cpu_data);
    d->counter++;
    local_unlock(&cpu_data_lock);         /* non-RT: preempt_enable() */
                                          /* RT: release rt_mutex */
}

/* Per-CPU data also accessed from IRQ handler: */
void update_from_process(void)
{
    local_lock_irqsave(&cpu_data_lock);   /* non-RT: local_irq_save + lockdep */
    this_cpu_ptr(&cpu_data)->hits++;      /* RT: acquire per-CPU rt_mutex */
    local_unlock_irqrestore(&cpu_data_lock);
}

Real-world examples: The memory management subsystem uses local_lock to protect per-CPU folio batches — mm/swap.c declares both a plain lock and a separate lock_irq in the same structure, a compact illustration of the two variants living side by side. The slab allocator uses one for its per-CPU sheaves (mm/slub.c), and the networking stack embeds local_lock_t in softnet_data (include/linux/netdevice.h).

A narrower variant. 7.0.12 also provides local_lock_nested_bh()/local_unlock_nested_bh() for data that is already known to be accessed only from softirq context. With lockdep enabled these verify that assumption; without it they add no overhead at all, and unlike local_lock() they do not disable preemption. On PREEMPT_RT they become a real lock, which is what allows the underlying local_bh_disable() serialization to be removed. See Documentation/locking/locktypes.rst.

Scenario 8: Data Shared with an NMI Handler

The non-maskable interrupt sits at the top of the hierarchy, and it breaks the rule that generates every other row of this table. Every scenario so far has been solved by a lower-priority context suppressing a higher-priority one. There is no way to suppress an NMI. local_irq_disable() does not stop it — that is what "non-maskable" means — so the standard remedy is simply unavailable.

The consequence is stark: a spinlock shared with an NMI handler is a deadlock waiting to happen. If an NMI arrives on a CPU that already holds the lock and the NMI handler tries to take it, the handler spins forever on a lock that can only be released by the code it interrupted, and no suffix exists that would have prevented the interruption. The deadlock needs no second CPU and cannot be engineered away with a stronger lock.

Code reachable from an NMI therefore does not use locks at all. The available techniques are:

  • Per-CPU data with lock-free access — the NMI touches only its own CPU's copy, and the non-NMI side is written so that any state the NMI can observe is consistent. This is how perf collects samples.
  • Atomic operations and cmpxchg loops, which need no lock to be held across the update.
  • Deferring the work entirely. irq_work exists largely for this: its enqueue path is explicitly documented as NMI-safe (kernel/irq_work.c), so an NMI handler can record the bare minimum and schedule a normal interrupt to do anything that requires locking.

The practical rule for driver authors is that if in_nmi() can be true on a path, every lock on that path is a bug, and the fix is to move the locked work out of NMI context rather than to change the lock.

Threaded Interrupt Handlers Change the Question

Everything above assumes that an interrupt handler runs in interrupt context. On a 7.0.12 kernel that is frequently untrue, and when it is untrue the entire analysis shifts by one rung.

A handler registered with request_threaded_irq() is split in two. The small primary handler still runs in true hardirq context and usually does nothing but acknowledge the device and return IRQ_WAKE_THREAD. The real work runs in a dedicated kernel thread — which is process context. It can sleep, it can take a mutex, and code that shares data only with the threaded half is governed by Scenario 1, not Scenario 3. Pushing work into the thread is often the cleanest way to make a lock problem disappear entirely.

This is not a niche configuration. Booting with threadirqs forces threading for most handlers, and on PREEMPT_RT force_irqthreads() is unconditionally true (include/linux/interrupt.h), so threading is the default rather than the exception.

Forced threading is not universal, though, and the exceptions matter: irq_setup_forced_threading() declines to thread any handler marked IRQF_NO_THREAD, IRQF_PERCPU or IRQF_ONESHOT. Since IRQF_TIMER is defined to include IRQF_NO_THREAD, timer interrupts in particular keep running in real hardirq context even on RT. True interrupt context never disappears completely; it just becomes much rarer than the classical model assumes.

What PREEMPT_RT Does to These Scenarios

The table in this section describes a non-RT kernel. On PREEMPT_RT the same source code remains correct — that is the design goal of the RT locking work — but it is correct for different reasons, and one of those differences is a trap worth stating explicitly.

On PREEMPT_RT, spin_lock_irqsave() does not disable interrupts. spinlock_t becomes an rt_mutex, and include/linux/spinlock_rt.h defines the _irqsave form as setting flags = 0 and calling plain spin_lock(). Documentation/locking/locktypes.rst states it plainly: the _irq and _irqsave suffixes "do not affect the CPU's interrupt disabled state."

This does not break the scenarios above, because their purpose is served another way: interrupt handlers are threaded, so the hardirq that the suffix was defending against no longer runs at the point where it could deadlock. What it does break is code that used spin_lock_irqsave() for a second, undocumented purpose — to obtain an interrupt-free region for its own sake, perhaps to serialize against a hardware register or to guarantee a bounded window. That guarantee silently disappears on RT. Code that genuinely requires interrupts off must say so with local_irq_save(), or use raw_spinlock_t, which remains a true spinning lock on RT.

local_bh_disable() loses more than it appears to. It still keeps a per-CPU counter, so in_softirq() still reports what you expect, but on RT it no longer disables preemption — __local_bh_disable_ip() in kernel/softirq.c calls migrate_disable() instead. The section is therefore preemptible, and a BH-disabled region no longer serializes two tasks against each other on the same CPU.

This is worth stating carefully because a great deal of older code disables bottom halves not to keep softirqs out but to get exclusive use of a per-CPU variable, relying on the fact that the region could not be preempted. That reasoning fails on RT. A per-CPU local_lock can be forced back into the path with CONFIG_PREEMPT_RT_NEEDS_BH_LOCK, but it is not enabled by default and its own help text describes it as something that "should not be needed"; the intended fix is to name the data being protected with local_lock_nested_bh() rather than to restore a per-CPU big kernel lock.

The Golden Rules

  1. If an IRQ handler accesses the data → process context MUST use spin_lock_irqsave()
  2. If a softirq accesses the data → process context MUST use spin_lock_bh() (or _irqsave if IRQ also accesses)
  3. IRQ handlers NEVER need _irqsave — they already run with IRQs disabled
  4. Softirqs NEVER need _bh — they already run with BH disabled
  5. spin_lock_irqsave() is always safe — it covers all cases but may be overkill
  6. Use guard(spinlock_irqsave) for automatic cleanup in new code
  7. Nothing masks an NMI — if in_nmi() can be true on a path, no lock on it is safe
  8. On PREEMPT_RT the suffixes do not disable interrupts — use local_irq_save() or raw_spinlock_t if that is what you actually need

Lock Validation: lockdep

Linux 7.0.12 includes a powerful runtime lock validator called lockdep (CONFIG_PROVE_LOCKING). This is a major improvement over Linux 2.6, where lock ordering bugs could lurk for years before triggering a rare deadlock under specific timing conditions.

Lockdep doesn't detect actual deadlocks — it detects potential deadlocks by proving that the lock ordering observed so far could lead to a deadlock if certain execution paths were combined. A single lockdep warning can prevent thousands of real deadlocks in production.

That distinction is the whole reason the tool works, and it is worth dwelling on before any of the mechanism makes sense. A locking bug is dangerous precisely because it is rare: an AB–BA deadlock needs two threads to reach two specific lines in a specific interleaving, which on a lightly loaded test machine may not happen in a year of running. But each half of that bug — one thread taking A then B, another taking B then A — is perfectly ordinary code that runs constantly. Lockdep watches the halves.

So it never needs the race to occur. It needs each path to execute once, at any time, on any CPU, and it will then report the deadlock those two paths would produce if they ever ran concurrently. A bug that testing might have found once a decade becomes one that a boot-time smoke test finds on the first run. This is why kernel continuous-integration systems run lockdep-enabled builds even though nobody would ship one.

Three design choices make that possible, and the consequences of each recur throughout this section:

  • Lockdep validates classes, not instances. Ten thousand inodes share one i_lock class, so the graph stays small and a rule learned from one inode applies to all of them. The cost is that a legitimate parent→child ordering between two locks of the same class looks like self-deadlock, which is what the _nested() annotations exist to resolve.
  • It reasons over accumulated history, not the current stack. Every edge it has ever observed stays in the graph, so evidence from an early boot path is still available to contradict a driver loaded an hour later.
  • It proves potential, not fact. Lockdep will warn about an ordering your code could never actually execute concurrently. If two paths are mutually exclusive for a reason lockdep cannot see, you must say so with an annotation — silencing lockdep is occasionally correct, ignoring it never is.

Two practical properties surprise nearly everyone the first time.

Lockdep is one-shot. The first report calls debug_locks_off() and prints "turning off the locking correctness validator", after which every remaining lock check in the kernel is dead until reboot. This is deliberate — once an inconsistency is found the graph can no longer be trusted, and a cascade of derived reports would bury the one report that was real — but it has a sharp practical edge: you cannot find the second bug until you have fixed the first, and a clean log following a known splat proves nothing at all.

Lockdep also has no runtime switch. It is a compile-time feature costing roughly 5–30% throughput plus several megabytes of static tables — acceptable in a test kernel, not in a production one. That asymmetry is what makes the rest of this section worth reading: you get one pass, in a debug build, to extract everything the tool can tell you, so it pays to know precisely what it can and cannot see.

What follows is how lockdep represents locks, the bug classes it detects, how to configure and annotate it, and how to read its output — then its relatives: a compiler extension new in this era that catches some of the same mistakes without running the kernel at all, and the runtime sanitizers that find the bugs lockdep is structurally blind to.

How Lockdep Works

Lockdep's machinery reduces to three questions asked on every single lock acquisition, in order. Which class is this? — collapsing millions of lock instances into a few thousand types. What was already held when it was taken? — turning each acquisition into edges in a graph. Does the graph now contain a contradiction? — a cycle, or an IRQ-safety conflict, or a wait-type inversion.

The first question is what makes the other two affordable. Asking them per instance would mean a graph with millions of nodes and a cycle search on every spin_lock(); asking them per class keeps the graph in the low thousands and lets a rule learned once apply forever.

Lock Classes

Lockdep tracks lock classes, not individual instances. A class is determined by the lock's initialization site (source file + line number):

/* Different classes (different initialization sites): */
static DEFINE_SPINLOCK(lock_a);   /* class: "lock_a" at file.c:10 */
static DEFINE_SPINLOCK(lock_b);   /* class: "lock_b" at file.c:11 */

/* Array of locks — all the SAME class (same init site): */
for (i = 0; i < N; i++)
    spin_lock_init(&array[i].lock);   /* all class "array[].lock" at file.c:15 */

Dependency Graph

Every time a lock is acquired while another lock is already held, lockdep adds an edge to a directed dependency graph. After each new edge, lockdep searches for cycles:

/* Lockdep observes these orderings: */
Thread 1: lock(A), lock(B)   → edge: A → B
Thread 2: lock(B), lock(C)   → edge: B → C
Thread 3: lock(C), lock(A)   → edge: C → A  → CYCLE: A→B→C→A → WARNING!

IRQ Safety Validation

Lockdep tracks whether a lock is used in hardirq context, softirq context, or with IRQs enabled/disabled:

Data Structures

Lockdep's internal architecture revolves around three key structures that together track every lock acquisition in the system.

struct lock_class — The Lock Type Identity

Every distinct lock initialization site produces one lock class. The kernel pre-allocates a fixed array of MAX_LOCKDEP_KEYS (8192) class slots. Once allocated, a class is never freed:

/* include/linux/lockdep_types.h */

struct lock_class {
    struct hlist_node       hash_entry;     /* global classhash table linkage */

    /* Dependency graph: bidirectional edges to other classes */
    struct list_head        locks_after;    /* classes acquired AFTER this one */
    struct list_head        locks_before;   /* classes acquired BEFORE this one */

    const char             *name;           /* human-readable: "(&dev->mutex)" */
    unsigned long           key;            /* unique class identifier */

    /* IRQ/softirq usage tracking — one bit per state combination */
    unsigned long           usage_mask;     /* bitmask of all observed states */

    /* Wait type classification for RT-aware validation */
    u8                      wait_type_inner; /* what does HOLDING this imply? */
    u8                      wait_type_outer; /* what context can ACQUIRE this? */

    /* Lock statistics (CONFIG_LOCK_STAT) */
    unsigned long           contention_point[4];  /* where contention happened */
    unsigned long           contending_point[4];  /* who was holding the lock */
};

The usage_mask field is the key to IRQ safety validation. Each bit represents a combination of direction × state × access type:

struct lockdep_map — Embedded in Every Lock

Every spinlock, mutex, rwsem, and rwlock contains a lockdep_map that maps the instance to its class:

struct lockdep_map {
    struct lock_class_key  *key;           /* points to static key at init site */
    struct lock_class      *class_cache[2]; /* cached class (direct + read) */
    const char             *name;          /* for /proc/lockdep output */
    u8                      wait_type_inner;
    u8                      wait_type_outer;
    u8                      lock_type;     /* LD_LOCK_NORMAL or LD_LOCK_PERCPU */
};

/* Macro expansion of DEFINE_SPINLOCK(my_lock): */
static struct lock_class_key __key;      /* unique key for this init site */
spinlock_t my_lock = {
    .dep_map = { .key = &__key, .name = "my_lock" }
};

struct held_lock — Per-Task Lock Stack

Each task maintains a stack of up to MAX_LOCK_DEPTH (48) currently held locks:

/* include/linux/sched.h — inside struct task_struct */
struct held_lock held_locks[MAX_LOCK_DEPTH];  /* 48 slots */
int lockdep_depth;                            /* current stack depth */
u64 curr_chain_key;                           /* running hash of the chain */

struct held_lock {
    u64                     prev_chain_key; /* chain hash BEFORE this acquisition */
    unsigned long           acquire_ip;     /* instruction pointer of lock() call */
    struct lockdep_map     *instance;       /* which lock instance */

    unsigned int            class_idx:13;   /* index into lock_classes[] */
    unsigned int            irq_context:2;  /* 0=normal, 1=softirq, 2=hardirq */
    unsigned int            trylock:1;      /* acquired via trylock (no deadlock) */
    unsigned int            read:2;         /* 0=exclusive, 1=read, 2=recursive */
    unsigned int            check:1;        /* should lockdep validate this? */
    unsigned int            hardirqs_off:1; /* were IRQs disabled at acquisition? */
    unsigned int            sync:1;         /* synchronize_*() pseudo-lock */
    unsigned int            references:11;  /* for pin_lock reference counting */
};

The chain key is a rolling hash of all locks held so far. If a chain was seen before (hash match), lockdep skips the expensive cycle check (fast path). Only new chains trigger BFS validation.

The Global Dependency Graph

The classes and the per-task stack meet in a single system-wide graph. Each class carries two adjacency lists — locks taken after it and locks taken before it — so the cycle search can walk in either direction, which matters because the two halves of an AB–BA report are found by searching forward from one lock and backward from the other:

/* Adjacency list entries for the dependency graph */
struct lock_list {
    struct list_head        entry;     /* linked to class->locks_after or locks_before */
    struct lock_class      *class;    /* the other class in this edge */
    struct lock_trace      *trace;    /* stack trace when edge was added */
    u16                     distance; /* for shortest-path reporting */
};
/* When lock(A) then lock(B) observed:
 *   A->locks_after += {B}    (forward edge)
 *   B->locks_before += {A}   (backward edge)
 * Cycle detection: BFS from B following locks_after — if reaches A, cycle exists */

AB-BA Deadlock Detection

The algorithm works on observed orderings across all CPUs and tasks. The two conflicting orderings don't need to happen simultaneously or on the same CPU:

Time 1 (any CPU):  lock(A) → lock(B)    → record edge: A → B
Time 2 (any CPU):  lock(B) → lock(A)    → about to add edge: B → A
                                         → BFS from A follows A→B... reaches A? NO
                                         → BFS from B? B→A would reach B? YES → CYCLE!

This catches deadlocks from a single execution of each path, without requiring the race to actually occur.

IRQ Safety (Transitive Check)

Lockdep checks transitive IRQ safety through the dependency graph:

If:   A is USED_IN_HARDIRQ  (taken in IRQ handler)
And:  A → B edge exists     (B acquired after A somewhere)
And:  B is ENABLED_HARDIRQ  (B taken with IRQs on somewhere else)
Then: UNSAFE! — IRQ fires while holding B → handler takes A →
      but someone else holds A waiting for B → DEADLOCK

Wrong-Context Detection (Wait Types)

Cycle detection asks whether an ordering is safe. Wait types ask a different question entirely: whether a lock had any business being taken here, regardless of what else was held. Every lock class carries a rating of how long it may make the caller wait, and lockdep enforces that a critical section may only ever nest locks that wait no longer than the one enclosing it. Sleeping inside a spinlock is the famous instance, but the rule generalizes:

/* Wait type hierarchy (include/linux/lockdep_types.h): */
enum lockdep_wait_type {
        LD_WAIT_INV = 0,  /* not checked, catch all */
        LD_WAIT_FREE,     /* wait free: RCU read-side, seqcount readers */
        LD_WAIT_SPIN,     /* spin loops: raw_spinlock_t, arch_spinlock_t */
#ifdef CONFIG_PROVE_RAW_LOCK_NESTING
        LD_WAIT_CONFIG,   /* spinlock_t — preemptible on PREEMPT_RT */
#else
        LD_WAIT_CONFIG = LD_WAIT_SPIN,
#endif
        LD_WAIT_SLEEP,    /* sleeping locks: mutex, rwsem, ww_mutex */
        LD_WAIT_MAX,
};

/* Each class carries TWO ratings (include/linux/lockdep_types.h):
 *   wait_type_outer  "can be taken in this context"
 *   wait_type_inner  "presents this context"
 *
 * Rule enforced by check_wait_context():
 *   next_outer <= min(wait_type_inner of every lock already held)
 *
 * Taking a SLEEP lock while holding a SPIN lock → immediate BUG */

The ordering of that enum is the rule, and the two ratings are what make it work. A lock's outer type says how long acquiring it may block the caller; its inner type says how long anything nested inside it is then permitted to block. Acquiring a lock is legal when its outer type is no greater than the inner type of everything already held. Most locks set only wait_type_inner and check_wait_context() uses it for both, which is why the distinction rarely comes up.

RCU is the instructive exception, because for it the two genuinely differ. rcu_lock_map is declared with wait_type_outer = LD_WAIT_FREE and wait_type_inner = LD_WAIT_CONFIG (kernel/rcu/update.c), and each half buys something:

  • The outer LD_WAIT_FREE says rcu_read_lock() waits for nothing, so it is legal absolutely anywhere — inside a raw_spinlock_t, inside an NMI, inside any context at all. This is the rating's real meaning: not "restrictive" but "imposes no wait on whoever takes it."
  • The inner LD_WAIT_CONFIG says that once inside a read-side critical section you may still take a spinlock_t, but not a mutex or rwsem. Attempting the latter is what lockdep reports — and the choice of LD_WAIT_CONFIG rather than LD_WAIT_SPIN is deliberate, because CONFIG_PREEMPT_RT implies PREEMPT_RCU, making the read-side section itself preemptible.

The conditional in the middle deserves attention, because it means this check is not always compiled in. Without CONFIG_PROVE_RAW_LOCK_NESTING, LD_WAIT_CONFIG is defined to equal LD_WAIT_SPIN; the two ratings become indistinguishable, and taking a spinlock_t inside a raw_spinlock_t passes silently. That is correct for a non-RT kernel, where spinlock_t genuinely does not sleep, and a latent bug on an RT one, where it does. The option is default y if ARCH_SUPPORTS_RT, and both x86-64 and ARM64 select ARCH_SUPPORTS_RT, so on this book's two example architectures the check is on by default. On an architecture without RT support it is off, and RT-specific nesting bugs can accumulate there unnoticed.

Recursive Lock Detection

The simplest deadlock is a lock taken twice by the same task, and it is also the one most often introduced by refactoring — a helper acquires a lock, and someone later calls that helper from a path that already holds it. Because lockdep already maintains a stack of currently held locks per task, this check is nearly free: the class being acquired is compared against the classes already on the stack. That comparison is also why legitimate same-class nesting needs an annotation to distinguish itself:

/* This is a bug — lockdep catches it: */
spin_lock(&inode->i_lock);
spin_lock(&child_inode->i_lock);  /* SAME CLASS! → deadlock warning */

/* Fix: tell lockdep this is a different hierarchy level: */
spin_lock(&inode->i_lock);
spin_lock_nested(&child_inode->i_lock, SINGLE_DEPTH_NESTING);

Using Lockdep

Using lockdep well is mostly two skills: turning it on with the right options, and knowing what to do when it is wrong. The second takes judgement. Because lockdep proves potential rather than fact, it will sometimes report an ordering your code cannot actually execute concurrently — and the reflex to silence that warning is exactly as dangerous as the reflex to ignore it. An annotation is a claim you are making to the validator; if the claim is false you have not suppressed a false positive, you have hidden a real one.

CONFIG_PROVE_LOCKING is the only option most people need, since it selects the rest, but two deserve individual attention. CONFIG_PROVE_RAW_LOCK_NESTING is default y on any architecture selecting ARCH_SUPPORTS_RT — which includes both x86-64 and ARM64 — and switching it off silently removes the spinlock_t-inside-raw_spinlock_t check described above. CONFIG_PROVE_RCU requires no decision at all: it is def_bool PROVE_LOCKING, so enabling lockdep automatically validates every rcu_dereference() against the lock named in its lockdep_is_held() condition. CONFIG_PROVE_RCU_LIST, which extends the same checking to the RCU list helpers, is deliberately not included — it defaults to off because unconverted callers still generate false positives.

Lockdep Annotations

Annotations exist because class-based validation is an approximation, and an approximation is sometimes wrong in the safe direction and sometimes in the unsafe one. Each annotation below corrects a specific approximation error, and each carries a specific risk if misapplied — they are listed roughly in order of decreasing safety, with the last two capable of hiding real bugs outright.

Nested locking (same class, different levels):

/* Tell lockdep this is a legitimate parent→child order: */
spin_lock(&parent_inode->i_lock);       /* class: "i_lock", subclass 0 */
spin_lock_nested(&child_inode->i_lock, SINGLE_DEPTH_NESTING);  /* subclass 1 */
spin_lock_nested(&grandchild->i_lock, 2);                      /* subclass 2 */

Custom lock classes:

static struct lock_class_key my_special_key;
lockdep_set_class(&dev->lock, &my_special_key);  /* override class */

Disabling validation (use sparingly!):

lockdep_set_novalidate_class(&lock);  /* disable ordering checks */
lockdep_set_notrack_class(&lock);     /* disable ALL tracking (nuclear) */

Runtime assertions:

lockdep_assert_held(&rcu_state.barrier_mutex);      /* must be held */
lockdep_assert_held_read(&mm->mmap_lock);           /* at least read-held */
lockdep_assert_held_write(&mm->mmap_lock);          /* exclusively held */
lockdep_assert_not_held(&dev->power.lock);          /* must NOT be held */
might_sleep();                                       /* assert sleepable */
cant_sleep();                                        /* assert non-sleepable */
cant_migrate();                                      /* assert pinned to CPU */

Lock pinning (prevent unexpected release):

struct pin_cookie cookie = lockdep_pin_lock(&rq->__lock);
/* ... code that must NOT release rq->__lock ... */
lockdep_unpin_lock(&rq->__lock, cookie);  /* reports if lock was released */

Locks in Dynamically Allocated Memory

Everything above assumes a lock class is anchored to a static key, which is what DEFINE_SPINLOCK and spin_lock_init() normally arrange. Loadable modules break that assumption in a way worth understanding, because the failure is silent and the symptom appears far from the cause.

A class key living in module text or in a kmalloc'd structure can be freed while lockdep still holds pointers to it. The class survives in the global tables, its name now points at unmapped memory, and the next module load may place a different lock at the same address and inherit the dead class's entire dependency history. Modules that register locks dynamically therefore call:

struct lock_class_key *key = kmalloc(sizeof(*key), GFP_KERNEL);

lockdep_register_key(key);          /* announce the key to lockdep */
lockdep_set_class(&obj->lock, key);

/* ... teardown, before freeing key or the module text holding it ... */
lockdep_unregister_key(key);        /* purge every class using this key */
kfree(key);

lockdep_unregister_key() removes the classes derived from that key together with every graph edge touching them. Omitting it is not a leak so much as a correctness bug: the stale edges remain and can produce a cycle report naming a lock that no longer exists.

When Lockdep Gives Up

Lockdep's tables are statically sized, which is the price of running inside the locking fast path where allocation is impossible. Exhausting one is not a graceful degradation — it prints "BUG: MAX_LOCKDEP_KEYS too low!" (or the corresponding message for entries, chains, or stack traces), calls print_lockdep_off(), and disables validation for the rest of the boot, exactly as a real report would.

This matters because the message looks like a bug in your code and is not; it means the tool ran out of room, and every check after that point silently did nothing. On a kernel with many modules loaded it is easy to hit. Most limits are tunable:

The class limit is the one that cannot be raised, because class_idx in struct held_lock is a MAX_LOCKDEP_KEYS_BITS-wide bitfield. Running out of classes therefore has to be diagnosed rather than configured away. The usual cause is dynamic keys that are registered but never unregistered, as in the previous subsection, so that each module load or object creation consumes slots permanently; a large module count on a distribution kernel can also simply exhaust the table honestly. A class count sitting just under 8192 in /proc/lockdep_stats distinguishes honest exhaustion from a leak.

Because every one of these paths ends in the same self-disable as a genuine report, the first thing to establish in any lockdep investigation is whether the validator was still running when the interesting code executed. Alongside lockdep_stats, lockdep registers /proc/lockdep (every known class and its dependencies) and /proc/lockdep_chains (every observed acquisition chain), plus /proc/lock_stat when CONFIG_LOCK_STAT is set.

Compile-Time Checking: Context Analysis

Every check described so far shares one limitation: the code has to run. Lockdep learns nothing about a path never taken, so a driver's error-handling branch, a rarely reached quirk, or a code path gated on hardware nobody has can hold a locking bug indefinitely without a single splat. Coverage, not cleverness, is lockdep's binding constraint.

Linux 7.0.12 pairs it with a tool that has the opposite trade-off. Context analysis (CONFIG_WARN_CONTEXT_ANALYSIS) is a Clang language extension — the kernel's application of Clang's thread-safety analysis — that checks locking rules at compile time. It examines every branch, including the ones that never execute, and it costs nothing at runtime because there is no runtime component. What it cannot do is follow anything decided dynamically, which is precisely lockdep's strength. The two are complements rather than alternatives.

The model is to name, in the type system, which lock protects which data:

struct my_data {
        spinlock_t lock;
        int counter __guarded_by(&lock);   /* declare the rule */
};

/* The compiler now rejects any access to d->counter that
 * cannot prove d->lock is held. No execution required. */

/* Functions declare their expectations in the same vocabulary: */
void bump(struct my_data *d) __must_hold(&d->lock);
void take(struct my_data *d) __acquires(&d->lock);
void drop(struct my_data *d) __releases(&d->lock);

/* And for reader/writer distinctions: */
int  read_it(struct my_data *d) __must_hold_shared(&d->lock);

Several of those names will look familiar: __must_hold, __acquires and __releases were previously Sparse annotations that documented intent and counted acquisitions without understanding which lock was involved. They now expand to context-analysis attributes, so annotations written years ago for documentation value have quietly become enforced. The supported primitives cover essentially everything in this chapter: raw_spinlock_t, spinlock_t, rwlock_t, mutex, seqlock_t, bit_spinlock, RCU, SRCU, rw_semaphore, local_lock_t and ww_mutex.

The connection to lockdep runs deeper than a shared vocabulary. On a kernel built without lockdep, lockdep_assert_held() does not compile to nothing — it expands to __assume_ctx_lock(), feeding the assertion to the static analyzer instead. The same line of source is a runtime check in a debug build and a compile-time premise in a production one.

Availability. Context analysis requires Clang 22 or later and is opt-in per subsystem, not tree-wide: a Makefile must set CONTEXT_ANALYSIS := y for a directory or CONTEXT_ANALYSIS_file.o := y for one object. Early adopters include kernel/sched, crypto, kernel/kcsan and mm/kfence. Enabling it tree-wide with CONFIG_WARN_CONTEXT_ANALYSIS_ALL is possible and, in the documentation's own words, not recommended — the unannotated majority of the kernel produces too many false positives.

The limitation to keep in mind is that the analysis is syntactic. It does not infer locks acquired or released inside inline functions, and it constrains patterns such as conditional acquisition in one function with a matching conditional release in another — legal C that the analyzer cannot verify, and which must be marked context_unsafe() to opt out locally. That is the mirror image of lockdep's blindness: lockdep sees only what ran, and context analysis sees only what can be proved from the text.

KCSAN: Concurrency Sanitizer

Linux 7.0.12 includes KCSAN (Kernel Concurrency Sanitizer, CONFIG_KCSAN), a dynamic data race detector that complements lockdep:

A data race occurs when two threads access the same memory location concurrently, at least one access is a write, and no synchronization orders the accesses. Data races are undefined behavior in C and can cause silent data corruption.

How KCSAN Works: Watchpoint Sampling

KCSAN uses a watchpoint-based sampling approach:

  1. Instrumentation: The compiler (-fsanitize=thread) inserts a check before every memory access
  2. Watchpoint setup: Periodically, KCSAN sets a watchpoint on the accessed address
  3. Delay: KCSAN delays for a configurable window to allow concurrent accesses to be detected
  4. Detection: If another CPU accesses the same address during the window, a data race is reported
  5. Value check: After the delay, if the value changed without a watchpoint hit, a race of "unknown origin" is reported
/* Simplified KCSAN detection algorithm: */
void __kcsan_check_access(const volatile void *ptr, size_t size, int type) {
    if (likely(should_skip()))      /* sampling: skip most accesses */
        return;

    if (try_consume_watchpoint(ptr, size)) {
        /* Another CPU has a watchpoint here — RACE DETECTED! */
        kcsan_report_known_origin(ptr, size, type, ...);
        return;
    }

    if (set_watchpoint(ptr, size, type)) {
        udelay(is_interrupt() ? kcsan_udelay_interrupt : kcsan_udelay_task);
        if (value_changed(ptr, size))
            kcsan_report_unknown_origin(ptr, size, type, ...);
        remove_watchpoint();
    }
}

KCSAN Annotations

Unlike lockdep, KCSAN reports races that are frequently intentional. The kernel is full of deliberately unsynchronized accesses — statistics counters where an occasional lost update is irrelevant, flags polled in a loop, heuristics whose staleness is harmless. The correct response is not to silence the tool but to mark the access as deliberate, which documents the intent for the next reader and, in the case of data_race(), tells the compiler as much as it tells KCSAN:

Examples of Race Condition Prevention

Everything up to this point has described primitives in isolation: what a spinlock guarantees, what RCU costs, which primitive to reach for. Real kernel code almost never uses one primitive alone. The examples in this section were chosen because each of them combines two or more of the mechanisms already described, and because in every case the combination exists to solve a problem that no single primitive can solve.

Three combinations recur so often that they are worth naming before the examples begin. The first is reference count plus lock: a counter tells you whether an object is still alive, a lock tells you whether its fields are stable, and the interesting code is the handful of instructions where one hands over to the other. The second is RCU plus reference count: RCU keeps a structure allocated for the duration of a lookup, but the moment the lookup finishes the reader needs something that outlives the read-side critical section, so it converts its RCU protection into a reference before letting go. The third is fast path plus slow path: a lockless sequence that usually succeeds, backed by a locked sequence that is always correct, with a carefully constructed test deciding between them.

A second theme runs through the examples: the write side and the read side are optimized for different things, and the asymmetry is deliberate. Timekeeping accepts an expensive, elaborate update path in order to make the read path a handful of loads. Per-CPU statistics make the increment free and the sum expensive. Per-VMA locking makes the page-fault path lock-free at the cost of a slower and more intricate mmap(). When a kernel data structure looks lopsided, the lopsidedness is usually the point.

Each example below gives the 7.0.12 code, but the code is not the lesson. What matters is the reasoning that produced it: which race the author was worried about, why the obvious solution was too slow, and what had to be given up in exchange.

Reference Counters

Reference counting answers a question that locking cannot: not may I touch this object, but does this object still exist. A lock protects a structure's contents; it says nothing about whether the structure is about to be freed out from under you. The two are complementary, and the majority of use-after-free bugs in the kernel come from code that has one and believes it has the other.

The counting rule itself is simple — increment when you take a pointer, decrement when you drop it, free at zero — and almost all of the difficulty lies in two places. The first is arithmetic safety: a counter that wraps turns a leak into an exploitable use-after-free. The second is the acquisition itself, which is a race whenever the pointer was obtained without a lock. Linux has a distinct mechanism for each.

Evolution: atomic_t → refcount_t

Linux 2.6 used raw atomic_t for reference counting, which provided no protection against overflow/underflow bugs. Linux 4.11 introduced refcount_t, a hardened counter that saturates on overflow and warns on underflow:

/* include/linux/refcount.h */
typedef struct refcount_struct {
    atomic_t refs;
} refcount_t;
/* refcount_inc() on zero → WARN (use-after-free attempt)
 * refcount_inc() overflow → saturates at REFCOUNT_SATURATED
 * refcount_dec() below zero → WARN (double-free attempt) */

Real-World: Socket Reference Counting

Sockets are the canonical example because their lifetime is genuinely hard: a socket is reachable from a file descriptor, from one or more hash tables used by incoming packets, and from timers, and these paths run concurrently on different CPUs. The code below is the straightforward half — taking a reference when you already hold one, and dropping the last one.

/* net/core/sock.c — socket initialization */
void sock_init_data(struct socket *sock, struct sock *sk) {
    refcount_set(&sk->sk_refcnt, 1);    /* initial reference */
}

/* include/net/sock.h — acquire/release */
static __always_inline void sock_hold(struct sock *sk) {
    refcount_inc(&sk->sk_refcnt);       /* acquire reference */
}

static inline void sock_put(struct sock *sk) {
    if (refcount_dec_and_test(&sk->sk_refcnt))
        sk_free(sk);                    /* last reference → free */
}

The Try-Get Race: refcount_inc_not_zero()

sock_hold() is written with refcount_inc(), and that is only correct because of an unstated precondition: the caller must already hold a reference. Incrementing a counter you have no claim on is not a reference acquisition, it is a race. Between the moment you load the pointer and the moment you increment, another CPU can drop the last reference and free the object, and your increment lands in freed memory.

This matters precisely where reference counting is most useful — a lookup in a hash table, where you find a pointer you did not previously own. The kernel's answer is an atomic conditional increment that refuses to resurrect a dead object:

/* net/core/sock.c — acquiring a reference found by lookup */
if (refcount_inc_not_zero(&sk->sk_refcnt)) {
    /* reference acquired; the socket cannot be freed while we hold it */
} else {
    /* count was already zero: the socket is being destroyed.
     * Treat the lookup as a miss. */
}

The distinction between the two functions is a reliable readability cue. refcount_inc() in a lookup path is nearly always a bug; refcount_inc_not_zero() where the caller obviously holds a reference is merely redundant. Note that refcount_inc_not_zero() is marked __must_check — ignoring the result compiles to a warning, because ignoring it means proceeding with an object that may already be gone.

The conditional increment does not, by itself, guarantee that the memory it operates on is still there to be read. Something must keep the object allocated for the duration of the attempt, and that something is normally RCU — which is why this pattern appears again, in its complete form, in the RCU examples below.

The Last-Reference Race: refcount_dec_and_lock()

Dropping a reference has a symmetric problem. The usual shape is if this was the last reference, remove the object from the table that publishes it, then free it — and removal requires the table's lock. Writing that as a plain test followed by a lock acquisition opens a window: after you observe zero and before you take the lock, nothing stops another CPU from finding the object in the still-populated table.

The naive fix — take the lock first, then decrement — is correct but pays for the lock on every release, when the overwhelming majority of releases are not the last one. refcount_dec_and_lock() gets both properties:

/* lib/refcount.c */
bool refcount_dec_and_lock(refcount_t *r, spinlock_t *lock)
{
    if (refcount_dec_not_one(r))
        return false;      /* fast path: was > 1, decremented, no lock taken */

    spin_lock(lock);
    if (!refcount_dec_and_test(r)) {
        spin_unlock(lock);
        return false;      /* someone else took a reference meanwhile */
    }
    return true;           /* count is now zero AND lock is held */
}

The fast path uses refcount_dec_not_one(), which decrements only if the value is something other than one, and reports failure without changing anything when it is. So a release from a count of five never touches the lock. Only the potentially-final release takes it, and then re-tests under the lock — because between the two tests another CPU could have performed a successful refcount_inc_not_zero(). On success the function returns with the lock still held, so the caller can unlink and free without reopening the window. The variants refcount_dec_and_mutex_lock() and refcount_dec_and_lock_irqsave() apply the same structure to the other two lock types.

Scaling the Counter Itself: percpu_ref

Everything above assumes the counter is worth a shared cache line. For an object referenced from every CPU in the system — a block device queue, an aio context, a cgroup — it is not. A refcount_t is a single location that every get and put must own exclusively, so the counter becomes the contended resource even when the object it guards is never contended at all.

percpu_ref removes that line from the fast path by splitting the count across CPUs. In its normal mode a get is this_cpu_add() on the local counter and a put is the matching decrement — no atomic read-modify-write on shared memory, no cache-line ping-pong. include/linux/percpu-refcount.h describes the result as “a refcount with similar semantics to atomic_t — atomic_inc(), atomic_dec_and_test() — but percpu.”

The cost is that a distributed counter cannot be tested against zero. Summing the per-CPU values is not atomic, and a sum that reads zero proves nothing, because a CPU already visited may have incremented after it was read. So percpu_ref gives up the one operation that makes reference counting useful, and buys it back with an explicit teardown protocol:

  • The object starts with an initial reference that the owner keeps and that ordinary users never drop.
  • While that reference is held the counter is in per-CPU mode, and percpu_ref_put() does not check for zero — as the header puts it, “it can't, if it was in percpu mode.”
  • Teardown calls percpu_ref_kill(), which collects the per-CPU counters back into a single atomic_long_t, issues the appropriate barriers, and marks the reference as shutting down so that puts begin checking for zero.
  • Only then does the owner drop the initial reference. The release callback fires when the last outstanding user drops theirs.

The ordering is the entire protocol, and reversing it is the characteristic bug: dropping the initial reference before percpu_ref_kill() lets the count fall to zero while puts are still unchecked, so the release callback never runs and the object leaks. percpu_ref_kill() also is the synchronization for two-stage shutdown — it returns true exactly once and false to every later caller, so racing teardown attempts resolve without a separate lock.

Two further properties are easy to assume and wrong. percpu_ref takes rcu_read_lock() internally to keep the per-CPU pointer stable across a mode switch, but it does not imply “RCU grace periods of any kind”; code that publishes the object for lockless lookup must still arrange its own call_rcu() in the free path, as fs/aio.c does for struct kioctx.

The try-get story is correspondingly different. refcount_inc_not_zero() asks whether the count is still non-zero; percpu_ref_tryget_live() cannot, so it asks a different question — whether the reference has been killed. In per-CPU mode it simply performs this_cpu_inc() and returns true, which is sound precisely because the initial reference is still held and the object therefore cannot be dying. Only once percpu_ref_kill() has switched the counter to atomic mode does it fall back to checking the __PERCPU_REF_DEAD bit and then atomic_long_inc_not_zero(). This is why the fast path of a lockless lookup costs a per-CPU increment rather than a shared atomic.

The accompanying caveat is subtle enough to be worth quoting: “Completion of percpu_ref_kill() in itself doesn't guarantee that this function will fail. For such guarantee, percpu_ref_kill_and_confirm() should be used.” The kill is asynchronous, so a caller that must know no further references can be handed out has to wait for the confirm callback rather than for percpu_ref_kill() to return. Callers already inside an RCU read-side critical section can use percpu_ref_tryget_live_rcu() and skip the internal rcu_read_lock().

The progression across this section is one of trading generality for scale. atomic_t counts anything and checks nothing; refcount_t adds saturation and the acquire/release ordering that reference counting actually requires; lockref fuses the count with the lock guarding the object it belongs to; and percpu_ref abandons zero-detection during the object's lifetime in exchange for a fast path that never leaves the local CPU. The right choice is the least specialized one whose fast path is not a bottleneck.

Lockref: Fusing a Lock and a Count

The reference-count patterns above still take a lock on their slow paths, and for most objects that is fine. For one object it was not. The directory entry cache is consulted on every path lookup in the system, and each lookup takes and drops a reference on several dentries. At that frequency the d_lock spinlock became the limiting factor on multi-socket machines — not because it was held for long, but because the cache line holding it bounced between every CPU doing path resolution.

What made this frustrating is that the contending operations were trivial. Incrementing a count does not need mutual exclusion in any deep sense; it needs to be atomic with respect to the lock, so that it cannot happen while a writer is making a structural change. struct lockref obtains exactly that by putting the lock and the count in the same 64-bit word:

/* include/linux/lockref.h */
#define USE_CMPXCHG_LOCKREF \
    (IS_ENABLED(CONFIG_ARCH_USE_CMPXCHG_LOCKREF) && \
     IS_ENABLED(CONFIG_SMP) && SPINLOCK_SIZE <= 4)

struct lockref {
    union {
#if USE_CMPXCHG_LOCKREF
        aligned_u64 lock_count;     /* both fields as one word */
#endif
        struct {
            spinlock_t lock;        /* 4 bytes */
            int count;              /* 4 bytes */
        };
    };
};

Because both fields occupy one word, a single cmpxchg can read the lock state and the count together, modify the count, and store the result — failing if either has changed:

/* lib/lockref.c */
#define CMPXCHG_LOOP(CODE, SUCCESS) do {                                \
    int retry = 100;                                                    \
    struct lockref old;                                                 \
    BUILD_BUG_ON(sizeof(old) != 8);                                     \
    old.lock_count = READ_ONCE(lockref->lock_count);                    \
    while (likely(arch_spin_value_unlocked(old.lock.rlock.raw_lock))) { \
        struct lockref new = old;                                       \
        CODE                                                            \
        if (likely(try_cmpxchg64_relaxed(&lockref->lock_count,          \
                                         &old.lock_count,               \
                                         new.lock_count))) {            \
            SUCCESS;                                                    \
        }                                                               \
        if (!--retry)                                                   \
            break;                                                      \
    }                                                                   \
} while (0)

bool lockref_get_not_zero(struct lockref *lockref)
{
    bool retval = false;

    CMPXCHG_LOOP(
        new.count++;
        if (old.count <= 0)
            return false;
    ,
        return true;
    );

    spin_lock(&lockref->lock);      /* slow path: contended or held */
    if (lockref->count > 0) {
        lockref->count++;
        retval = true;
    }
    spin_unlock(&lockref->lock);
    return retval;
}

Three details carry the correctness argument. The loop condition arch_spin_value_unlocked() tests the lock bits in the value that is about to be compared and exchanged, so the fast path is attempted only when the lock was observed free; if a writer holds it, the word differs and the loop is skipped entirely. The cmpxchg then covers both halves, so a writer that acquires the lock between the load and the store causes the exchange to fail rather than corrupting the count. And the whole sequence is not merely an optimization of taking the lock — it is equivalent to having taken it, which is what lets the slow path remain an ordinary spin_lock().

The retry = 100 bound is the concession to reality. Under heavy contention a cmpxchg loop can fail repeatedly, and a lockless path that spins indefinitely is worse than a lock. After a hundred failures the code gives up and takes the spinlock, which at least queues fairly. The BUILD_BUG_ON(sizeof(old) != 8) and the SPINLOCK_SIZE <= 4 test in the header are what make the trick safe to compile: with lockdep or spinlock debugging enabled a spinlock_t is much larger than four bytes, the union collapses to the plain struct, and every operation takes the real lock.

Both of this book's example architectures enable the fast path — arm64 selects ARCH_USE_CMPXCHG_LOCKREF unconditionally, x86-64 selects it whenever X86_CX8 is available, which on 64-bit is always. The pattern is worth recognizing beyond the dentry cache, because it generalizes: when a lock protects a structure but one hot field could be updated atomically, placing that field beside the lock lets a single compare-and-exchange do both jobs.

The Big Kernel Lock (Removed)

The Big Kernel Lock (BKL), still widely used in Linux 2.6, has been completely removed from the kernel. It was a coarse-grained global lock from Linux 2.0 that allowed only one processor in kernel mode at a time. Its unusual semantics (automatically dropped across schedule(), recursive acquisition, later semaphore-based) made it error-prone. Final removal: Linux 2.6.39 (2011). Modern code uses fine-grained primitives instead.

Memory Descriptor Locking

An address space is shared by every thread of a process, and the structure describing it — the mm_struct and its tree of VMAs — is read on every page fault and modified by every mmap(), munmap() and mprotect(). Faults vastly outnumber modifications, which makes this look like a textbook reader/writer problem, and for many years it was solved that way. The trouble is that a heavily threaded process generates faults on many CPUs at once, and a single reader/writer semaphore per address space serializes their bookkeeping even when they are faulting on completely unrelated regions.

Linux 7.0.12 therefore has two mechanisms layered on top of each other: the address-space-wide lock that has always been there, and a finer per-VMA scheme that most faults can use instead. The second is a much better illustration of the combinations described at the start of this section, so it is worth understanding the first well enough to see what the second is avoiding.

mmap_lock: The Traditional Approach

Each mm_struct contains a read/write semaphore mmap_lock (renamed from mmap_sem in 5.8). It is a sleeping lock, which it has to be: fault handling can block on I/O while a page is read from disk, and it is not acceptable to hold a spinlock across that.

/* Page fault handler — shared access: */
mmap_read_lock(mm);
vma = find_vma(mm, address);
/* ... handle fault ... */
mmap_read_unlock(mm);

/* mmap/munmap — exclusive access: */
if (mmap_write_lock_killable(mm))
    return -EINTR;
/* ... modify VMA tree ... */
mmap_write_unlock(mm);

VMA Locks: Per-VMA Locking

The per-VMA lock lets a page fault take a lock on the single region it is faulting in, leaving mmap_lock untouched. Faults on different regions then proceed with no shared cache line at all, which is where the reported improvements on threaded workloads — up to 2.5× — come from.

The name is slightly misleading, because in 7.0.12 there is no lock object. Under CONFIG_PER_VMA_LOCK a VMA carries a reference count and a sequence number:

/* include/linux/mm_types.h — struct vm_area_struct (excerpt) */
#ifdef CONFIG_PER_VMA_LOCK
    unsigned int vm_lock_seq;        /* mmap_lock generation a writer stamped */
#endif
    refcount_t vm_refcnt ____cacheline_aligned_in_smp;

/* Readers occupy the low bits; the writer sets bit 30 to lock them out. */
#define VM_REFCNT_EXCLUDE_READERS_BIT   (30)
#define VM_REFCNT_EXCLUDE_READERS_FLAG  (1U << VM_REFCNT_EXCLUDE_READERS_BIT)
#define VM_REFCNT_LIMIT                 (VM_REFCNT_EXCLUDE_READERS_FLAG - 1)

Read-locking a VMA is the try-get pattern from earlier in this section, applied to a lock rather than to an object's lifetime:

/* mm/mmap_lock.c — vma_start_read(), abridged.
 * IMPORTANT: RCU read lock must be held on entry; released on error. */
static inline struct vm_area_struct *vma_start_read(struct mm_struct *mm,
                                                    struct vm_area_struct *vma)
{
    int oldcnt;

    /* Cheap pessimistic check: was this VMA write-locked in the
     * current mmap_lock generation? */
    if (READ_ONCE(vma->vm_lock_seq) == READ_ONCE(mm->mm_lock_seq.sequence))
        goto err;

    /* Try to take a reference. Fails if the count is zero (detached) or
     * if the writer's EXCLUDE_READERS flag has pushed it past the limit. */
    if (unlikely(!__refcount_inc_not_zero_limited_acquire(&vma->vm_refcnt,
                                                          &oldcnt,
                                                          VM_REFCNT_LIMIT))) {
        vma = oldcnt ? NULL : ERR_PTR(-EAGAIN);  /* EAGAIN = detached */
        goto err;
    }

    /* Revalidate: the VMA may have been freed and reattached elsewhere. */
    if (unlikely(vma->vm_mm != mm))
        goto err_unstable;

    if (unlikely(vma->vm_lock_seq == raw_read_seqcount(&mm->mm_lock_seq))) {
        vma_refcount_put(vma);
        goto err;
    }
    return vma;
}

The two fields divide the work between them, and it is easy to assume the division is the other way round. The reference count is the read lock: a reader holds one, several readers can hold one at once, and a writer sets a bit that readers cannot touch and then waits for the count to drain, which is what makes vma_start_write() exclusive. The sequence number is the write lock: a VMA is write-locked precisely when its vm_lock_seq equals the mm's mm_lock_seq, which is why the cheap check above bails out on equality — it is refusing to read-lock a VMA that a writer currently owns.

Recording the write lock as a comparison rather than as state is what makes the write side affordable. An mmap() may need to write-lock many VMAs, and releasing them individually would be proportional to their number. Instead every release of the mmap_lock calls vma_end_write_all(), which advances mm->mm_lock_seq once; every VMA stamped with the old value ceases to match, and all of them are released together in constant time. The kernel's own documentation makes the consequence explicit — VMA write locks are never held across separate mmap_lock write sections, because dropping the outer lock ends them all by construction.

The other essential property is that the function is permitted to be wrong in one direction only. It may report failure for a VMA that was in fact lockable — if the sequence counter overflows, or a race makes the pessimistic check fire spuriously — and the caller simply falls back to mmap_lock, which is correct but slower. It may never report success for a VMA that was not locked. Every check above is arranged around that asymmetry, and it is what makes an aggressive lockless fast path safe: the failure mode is a performance loss, not a correctness loss.

/* mm/mmap_lock.c — the fault path entry point */

    vma = vma_start_read(mm, vma);
    if (IS_ERR_OR_NULL(vma)) {
        if (PTR_ERR(vma) == -EAGAIN) {  /* replaced under us — look again */
            count_vm_vma_lock_event(VMA_LOCK_MISS);
            mas_set(&mas, address);
            goto retry;
        }
        goto inval;                     /* fall back to mmap_lock */
    }
    rcu_read_unlock();                  /* the VMA lock now holds it stable */

    /* The VMA is locked, but is it still the one covering our address? */
    if (unlikely(address < vma->vm_start || address >= vma->vm_end)) {
        vma_end_read(vma);
        goto inval;
    }
    return vma;

inval:
    count_vm_vma_lock_event(VMA_LOCK_ABORT);
    return NULL;
}

Note where rcu_read_unlock() sits. RCU is used only to keep the VMA allocated long enough to attempt the reference; once the reference is held the VMA cannot be freed, so the RCU section ends and the fault handler is free to sleep — which it must be able to do. This is the RCU-plus-reference-count combination in its most literal form, and it is the reason the acquisition had to be inc_not_zero rather than inc.

Note also the address re-check after locking. Finding a VMA and locking it are separate steps, and in between the region may have been split or replaced, so the answer to the original question — which VMA covers this address? — is only trustworthy once something prevents it from changing. Successes and both kinds of failure are counted in /proc/vmstat as vma_lock_success, vma_lock_miss and vma_lock_abort, which makes the fallback rate measurable on a live system.

RCU-Protected Data Structures

RCU is used extensively for read-mostly data, and the PID lookup subsystem is the textbook case: the mapping from a PID to a task_struct is read constantly — by every signal delivery, every /proc access, every wait() — and written only when processes are created or destroyed.

What the example below really demonstrates is the boundary rule that governs every RCU lookup. Inside rcu_read_lock() the object cannot be freed, so the pointer is safe to dereference; the instant rcu_read_unlock() runs, that guarantee ends. Any pointer the caller wants to keep must therefore be converted into something stronger — here, a reference count — before the read-side critical section closes. Note the ordering in find_get_task_by_vpid(): the get_task_struct() is inside the section, not after it.

/* kernel/pid.c — PID lookup using RCU */

/* Reader: find task by PID (lock-free, zero overhead) */
struct pid *get_task_pid(struct task_struct *task, enum pid_type type)
{
    struct pid *pid;
    rcu_read_lock();
    pid = get_pid(rcu_dereference(*task_pid_ptr(task, type)));
    rcu_read_unlock();
    return pid;
}

struct task_struct *find_get_task_by_vpid(pid_t nr)
{
    struct task_struct *task;
    rcu_read_lock();
    task = find_task_by_vpid(nr);
    if (task) get_task_struct(task);    /* refcount before unlock */
    rcu_read_unlock();
    return task;
}

/* Writer: swap PIDs (rare, under tasklist_lock) */
void exchange_tids(struct task_struct *left, struct task_struct *right)
{
    rcu_assign_pointer(left->thread_pid, pid2);
    rcu_assign_pointer(right->thread_pid, pid1);
}

When the Object Can Be Recycled: SLAB_TYPESAFE_BY_RCU

The PID example gets to use a plain get_task_struct() because a task_struct is freed through RCU: once the lookup found it, no grace period has elapsed, so it cannot yet have been released. Some subsystems cannot afford that. Deferring every free by a grace period delays memory reclaim, and for objects allocated and destroyed as rapidly as sockets that delay is unacceptable.

SLAB_TYPESAFE_BY_RCU is the compromise, and its guarantee is much weaker than it first appears. The kernel's own header is emphatic about it:

/* include/linux/slab.h */
/* define SLAB_TYPESAFE_BY_RCU - **WARNING** READ THIS!
 *
 * This delays freeing the SLAB page by a grace period, it does _NOT_
 * delay object freeing. This means that if you do kmem_cache_free()
 * that memory location is free to be reused at any time. Thus it may
 * be possible to see another object there in the same RCU grace period.
 * ... */

What survives is the type, not the object. A pointer obtained under RCU still points at correctly formed memory of the right kind — so reading its reference count is safe — but it may by now describe a completely different socket. The lookup therefore needs two steps, and their order is not negotiable:

/* The pattern documented in include/linux/slab.h */
begin:
    rcu_read_lock();
    obj = lockless_lookup(key);
    if (obj) {
        if (!try_get_ref(obj)) {        /* 1. acquire — may fail if freed */
            rcu_read_unlock();
            goto begin;
        }
        if (obj->key != key) {          /* 2. THEN verify identity */
            put_ref(obj);
            rcu_read_unlock();
            goto begin;
        }
    }
    rcu_read_unlock();

Verifying identity first and acquiring afterwards would be useless: the object could be recycled in the gap between the two. The reference must be taken first, precisely so that it pins whatever identity the object turns out to have, and only then is the check meaningful. This is why refcount_inc_not_zero() exists as a distinct operation rather than as an optimization — it is the only acquisition that is safe to attempt on memory whose contents you do not yet trust.

Linux 7.0.12 supplies the memory ordering this requires in dedicated helpers rather than leaving it to each subsystem: refcount_inc_not_zero_acquire() and refcount_add_not_zero_acquire() on the acquiring side, and refcount_set_release() on the initializing side, so that a newly allocated object is fully constructed before its count becomes non-zero and visible to a concurrent lookup. The per-VMA lock discussed above uses exactly these primitives.

Seqlock-Protected Timekeeping

Timekeeping is the extreme case of the read/write asymmetry named at the start of this section. Reading the clock is among the most frequent operations a system performs; setting it happens when an administrator or NTP intervenes, and adjusting it happens on a timer tick. A reader/writer lock would be absurd here — readers would write to a shared cache line millions of times a second purely to announce that they are reading. Seqcounts let readers announce nothing at all.

The data is laid out so that the whole read is one cache line, and the sequence counter is the first thing in it:

/* kernel/time/timekeeping.c */
/*
 * The most important data for readout fits into a single 64 byte
 * cache line.
 */
struct tk_data {
    seqcount_raw_spinlock_t seq;
    struct timekeeper       timekeeper;
    struct timekeeper       shadow_timekeeper;
    raw_spinlock_t          lock;
} ____cacheline_aligned;

static struct tk_data timekeeper_data[TIMEKEEPERS_MAX];
#define tk_core (timekeeper_data[TIMEKEEPER_CORE])

/* Reader: get current time (millions of times/second) */
void ktime_get_ts64(struct timespec64 *ts)
{
    struct timekeeper *tk = &tk_core.timekeeper;
    struct timespec64 tomono;
    unsigned int seq;
    u64 nsec;

    do {
        seq = read_seqcount_begin(&tk_core.seq);
        ts->tv_sec = tk->xtime_sec;
        nsec = timekeeping_get_ns(&tk->tkr_mono);
        tomono = tk->wall_to_monotonic;
    } while (read_seqcount_retry(&tk_core.seq, seq));

    ts->tv_sec += tomono.tv_sec;
    ts->tv_nsec = 0;
    timespec64_add_ns(ts, nsec + tomono.tv_nsec);
}

The counter is a seqcount_raw_spinlock_t rather than a bare seqcount_t, and the associated lock is the tk_core.lock in the same structure. Declaring the writer's lock as part of the counter's type buys two things described earlier in this chapter. Lockdep can then verify that every write section really is serialized by that lock, rather than trusting the author. And for associated lock types that do not implicitly disable preemption, the write-side helpers add the preemption protection themselves — a seqcount writer that gets preempted leaves the counter odd, stalling every reader until it is scheduled again. It is a raw spinlock here because the update runs from the timer interrupt and must not become a sleeping lock on PREEMPT_RT.

Notice also what the reader does outside the retry loop. Only the raw field reads are inside it; the arithmetic that turns them into a timespec64 is done afterwards, on the local copies. Keeping computation out of the loop matters more than usual here, because any work inside it is work that will be thrown away and repeated if a writer intervenes.

The Shadow Timekeeper: Shortening the Write Side

Seqcount readers do not block writers, but writers very much disturb readers: for the whole duration of a write critical section, every reader that starts spins and retries. The update path is not short — it recomputes NTP state, derived ktime_t values, leap-second state, and pushes new values to the vDSO and to paravirtualized clocks. Doing all of that between write_seqcount_begin() and write_seqcount_end() would stall readers on every tick.

The kernel avoids it by keeping a second, private copy of the entire timekeeper. Writers modify the shadow at leisure under tk_core.lock, and the seqcount protects only the final publication:

/* kernel/time/timekeeping.c */
static void timekeeping_update_from_shadow(struct tk_data *tkd, unsigned int action)
{
    struct timekeeper *tk = &tkd->shadow_timekeeper;

    lockdep_assert_held(&tkd->lock);

    write_seqcount_begin(&tkd->seq);
    /* ... derived values recomputed, vDSO and fast timekeepers updated ... */

    /*
     * Update the real timekeeper.
     *
     * We could avoid this memcpy() by switching pointers, but that has
     * the downside that the reader side does not longer benefit from
     * the cacheline optimized data layout of the timekeeper and requires
     * another indirection.
     */
    memcpy(&tkd->timekeeper, tk, sizeof(*tk));
    write_seqcount_end(&tkd->seq);
}

The comment records a deliberate trade that is easy to get backwards. Swapping two pointers would obviously be cheaper than copying a whole structure — but it would force every reader to dereference a pointer before touching the data, costing an indirection and giving up the guaranteed cache-line layout. Since readers outnumber writers by many orders of magnitude, the kernel pays a memcpy on the rare path to save one load on the common one. When a data structure appears to be doing unnecessary work, it is worth asking which side of the asymmetry the work is on.

Reading the Clock from an NMI: Latch Seqcounts

The retry loop has one fatal prerequisite: the reader must be able to retry. An NMI handler that interrupts the timer interrupt in the middle of its write critical section can never observe an even sequence number, no matter how many times it loops — the writer it is waiting for is the code it interrupted, and that code cannot resume until the NMI returns. A plain seqcount read from NMI context is a guaranteed hang.

The kernel's answer is the latch, a seqcount paired with two copies of the data where the low bit of the counter selects which copy is live:

/* kernel/time/timekeeping.c */
/**
 * struct tk_fast - NMI safe timekeeper
 * @seq:  Sequence counter for protecting updates. The lowest bit
 *        is the index for the tk_read_base array
 * @base: tk_read_base array. Access is indexed by the lowest bit of @seq.
 */
struct tk_fast {
    seqcount_latch_t    seq;
    struct tk_read_base base[2];
};

static void update_fast_timekeeper(const struct tk_read_base *tkr,
                                   struct tk_fast *tkf)
{
    struct tk_read_base *base = tkf->base;

    write_seqcount_latch_begin(&tkf->seq);  /* force readers off to base[1] */
    memcpy(base, tkr, sizeof(*base));       /* update base[0] */
    write_seqcount_latch(&tkf->seq);        /* force readers back to base[0] */
    memcpy(base + 1, base, sizeof(*base));  /* update base[1] */
    write_seqcount_latch_end(&tkf->seq);
}

The writer never modifies the copy readers are currently directed at. It flips the latch to send readers to the other copy, updates the now-idle one, flips back, and updates the other — so at every instant one complete, self-consistent copy is available to be read. The kernel's own description of the technique states the trade plainly: it is multiversion concurrency control, it allows queries during non-atomic modifications, and the price is storing the entire structure twice.

The reader still has a retry loop, and the difference from an ordinary seqcount is not that the loop is gone but that it is guaranteed to finish. An ordinary seqcount reader that interrupted its writer would spin forever, because the only code that can make the sequence even again is the code it is standing on. A latch reader is never waiting for the writer to complete anything — it selects a copy, reads it, and re-checks; the writer is suspended and cannot advance the counter, so the check succeeds and the loop exits. The reader may come away with data from before the update, which for a clock means a timestamp a fraction of a tick behind, and that is a far better outcome than hanging a machine from an NMI. The comment on write_seqcount_latch_begin() notes the corollary: if you can guarantee that queries never interrupt modifications — if all your concurrency is between CPUs — you do not need a latch at all.

This is what makes ktime_get_mono_fast_ns() safe to call from perf sampling, tracing and the crash paths. The same technique backs sched_clock() and the printk timestamp ring, for the same reason: all three must produce a timestamp in contexts where blocking or retrying indefinitely is not an option.

Per-CPU Statistics

Statistics counters are the case where the cheapest correct answer is to abolish the sharing rather than to synchronize it. A global counter incremented by every CPU is a single cache line ping-ponging across the machine, and the cost is entirely wasted — nobody reads the value on the fast path. Giving each CPU its own counter removes the contention completely, at the price of making the total expensive and slightly stale.

/* include/linux/vmstat.h — VM event counters */
DECLARE_PER_CPU(struct vm_event_state, vm_event_states);

/* Fast path: no lock, no cross-CPU atomic */
static inline void count_vm_event(enum vm_event_item item) {
    this_cpu_inc(vm_event_states.event[item]);
}

/* Caller already has preemption disabled — skip the protection */
static inline void __count_vm_event(enum vm_event_item item) {
    raw_cpu_inc(vm_event_states.event[item]);
}

/* Slow path: sum across CPUs (for /proc/vmstat) */
void all_vm_events(unsigned long *ret) {
    int cpu;
    for_each_online_cpu(cpu) {
        struct vm_event_state *this = &per_cpu(vm_event_states, cpu);
        for (int i = 0; i < NR_VM_EVENT_ITEMS; i++)
            ret[i] += this->event[i];
    }
}

The summing loop shows what was given up. It is not atomic with respect to anything: a CPU may increment its counter while the loop is partway through, so the total can correspond to no instant that ever existed. For statistics reported through /proc/vmstat that is entirely acceptable, and recognizing when it is not acceptable is the whole skill in using per-CPU data.

What this_cpu_inc() Actually Compiles To

The fast path is often described as a single instruction, and on x86-64 it is. The %gs segment base already points at this CPU's per-CPU area, so the increment is one read-modify-write instruction against a segment-relative address:

/* arch/x86/include/asm/percpu.h — percpu_unary_op() */
asm qual (__pcpu_op_##size(op) __percpu_arg([var])
    : [var] "+m" (__my_cpu_var(_var)));
/* this_cpu_inc(var)  →  incq %gs:var */

A single instruction cannot be interrupted partway through, so this is safe against interrupts and against preemption without any further precautions. That property is an accident of the x86 addressing modes, and it does not survive the move to arm64. There is no per-CPU-relative read-modify-write instruction, so the same operation becomes a three-part sequence:

/* arch/arm64/include/asm/percpu.h */
#define _pcp_protect(op, pcp, ...)          \
({                                          \
    preempt_disable_notrace();              \
    op(raw_cpu_ptr(&(pcp)), __VA_ARGS__);   \
    preempt_enable_notrace();               \
})

#define this_cpu_add_8(pcp, val)  _pcp_protect(__percpu_add_case_64, pcp, val)

/* and the operation itself, LL/SC form: */
"1: ldxr    %[tmp], %[ptr]      \n"
"   add     %[tmp], %[tmp], %[val]  \n"
"   stxr    %w[loop], %[tmp], %[ptr]\n"
"   cbnz    %w[loop], 1b"
/* (replaced by a single LSE  ldadd  on CPUs that have it) */

The sequence has two protections doing two different jobs, and it is worth being precise about which does what. preempt_disable() does not provide atomicity; it guarantees that the CPU whose address was computed is still the CPU executing the update. Without it the task can migrate in between, and the increment lands on the CPU it has just left. The kernel documentation puts the x86 property this way: because the offset calculation and the operation happen in one instruction, "there are no atomicity issues between the calculation of the offset and the operation on the data", so no preemption protection is needed — and architectures that cannot do both in one instruction must supply it themselves.

Atomicity is a separate concern, and it is supplied by the ldxr/stxr pair. Disabling preemption does not disable interrupts, so a handler on the same CPU can modify the same counter mid-update; a plain load-add-store would silently lose one of the two increments. The exclusive monitor prevents it: the handler's own stxr clears the monitor, the interrupted stxr fails, and the loop retries.

That division explains the raw_-prefixed variants, and the difference between them is much starker than it looks. On x86-64, raw_cpu_inc() and this_cpu_inc() generate the same instruction and the distinction is invisible. On arm64 they are not related at all: arm64 supplies no raw_cpu_add, so it falls back to the generic definition, which is a plain C *raw_cpu_ptr(&pcp) += val — neither preemption-protected nor atomic. Using it where the caller has not already disabled both is a genuine, silently-lost-update bug that testing on x86-64 cannot reveal. This is why __count_vm_event() exists alongside count_vm_event(): it is a promise by the caller, not a hint to the compiler.

For pure statistics the migration hazard happens to be benign — an increment applied to the wrong CPU's counter still lands in the eventual sum — but this_cpu operations are a general interface, and for per-CPU data whose identity matters, such as freelists, softirq state or per-CPU buffers, updating the instance belonging to a CPU you are no longer running on is straightforwardly wrong.

When the Total Is Read Often: percpu_counter

Plain per-CPU counters assume the sum is needed rarely. Some counters — a filesystem's free-block count, a memory cgroup's page count — are consulted often enough that walking every CPU each time would be worse than the contention it avoided. percpu_counter is the hybrid: a shared total plus per-CPU deltas that are folded into it whenever one grows past a batch threshold.

/* lib/percpu_counter.c */
void percpu_counter_add_batch(struct percpu_counter *fbc, s64 amount, s32 batch)
{
    s64 count;
    unsigned long flags;

    count = this_cpu_read(*fbc->counters);
    do {
        if (unlikely(abs(count + amount) >= batch)) {
            /* Spill the local delta into the shared total. */
            raw_spin_lock_irqsave(&fbc->lock, flags);
            count = __this_cpu_read(*fbc->counters);
            fbc->count += count + amount;
            __this_cpu_sub(*fbc->counters, count);
            raw_spin_unlock_irqrestore(&fbc->lock, flags);
            return;
        }
    } while (!this_cpu_try_cmpxchg(*fbc->counters, &count, count + amount));
}

/* lib/percpu_counter.c — batch size scales with machine size */
percpu_counter_batch = max(32, nr_online_cpus * 2);

Reading fbc->count alone is cheap and approximate: it can be off by up to batch per CPU in either direction. That bound is the useful part. Because the error is bounded, questions such as is this counter above a threshold? can often be answered from the shared value alone, and percpu_counter_compare() does exactly that — consulting the exact sum only when the approximate value falls within the error margin of the threshold. Choosing between a plain per-CPU counter and a percpu_counter comes down to whether an answer with a known error bound is good enough, and how often anyone asks.

Scope-Based Locking in Practice

Every example so far has been about choosing the right mechanism. This one is about a failure mode that afflicts all of them equally: a correct locking design undone by a path that forgets to unlock. Error paths are where it happens, because they are numerous, individually rare, and rarely tested. Scope-based locking removes the possibility rather than the mistake — the release is attached to the scope by the compiler, so there is no path out of the block, including goto and early return, that can skip it. Linux 7.0.12 subsystems increasingly use guard() and scoped_guard() for this reason:

/* kernel/kthread.c — guard() replaces manual lock/unlock */
static int kthread_affinity_notify(...) {
    guard(mutex)(&kthread_affinity_lock);
    /* ... runs with lock held, auto-unlock at scope exit ... */
    return 0;
}

/* kernel/futex/core.c — scoped_guard() for conditional sections */
static void futex_pivot_hash(struct mm_struct *mm) {
    scoped_guard(mutex, &mm->futex_hash_lock) {
        struct futex_private_hash *fph = mm->futex_phash_new;
        if (fph) {
            mm->futex_phash_new = NULL;
            __futex_pivot_hash(mm, fph);
        }
    }
    /* mutex auto-unlocked, even on early return */
}

What Changed Since Linux 2.6

This section summarizes how the synchronization interfaces changed between Linux 2.6 and 7.0.12, and which 2.6-era habits still apply.

The obvious way to write such a section is as a list of things that were added, and that would give a misleading impression. In several of the places that matter most, the kernel of 7.0.12 offers a programmer fewer choices than 2.6 did, not more. The Big Kernel Lock is gone. Counting semaphores are no longer an acceptable way to express mutual exclusion. Read-copy-update, which in 2.6 had three separate update sides, now has one. Where the interface did grow — guard(), local_lock_t, ww_mutex, the typed seqcount_LOCKNAME_t — it usually grew in order to state in the type system a constraint that used to live only in a comment, so that a violation becomes a build error or a lockdep splat rather than a rare crash on someone else's machine.

Five themes account for nearly every entry in the table that follows. They are worth having in mind, because they also predict where the kernel is going next.

Waiting Became Fair, and Local

A 2.6 spinlock was test-and-set: every waiting CPU repeatedly wrote the same cache line, and whichever CPU happened to observe the release first won. On a two-way machine this is fine. On a many-core machine it is doubly bad — each attempt invalidates the line in every other waiter's cache, so contention consumes interconnect bandwidth in proportion to the number of waiters, and because the winner is decided by cache-coherence timing rather than arrival order, a CPU can be starved indefinitely.

The fix arrived in two steps: ticket locks made acquisition fair (first-come, first-served), and queued locks made it fair and local, by moving the spinning off the shared lock word. The qualification matters: as From Ticket Locks to Queued Spinlocks described, the first contender still spins on the lock word itself via the pending byte, because for the common two-CPU case that is cheaper than building a queue. It is from the second contender onward that each waiter spins on its own per-CPU MCS node. The same idea has since been applied wherever the kernel spins. Both architectures this book covers select ARCH_USE_QUEUED_SPINLOCKS and ARCH_USE_QUEUED_RWLOCKS, so spinlock_t and rwlock_t are both queued; and the MCS queue in include/linux/osq_lock.h supplies the same property to the optimistic-spinning paths of struct mutex and struct rw_semaphore.

The Update Side Consolidated

RCU is the clearest example, and the one most likely to mislead a reader who assumes that fifteen years of development can only have added things.

In 2.6, RCU was three implementations. rcu, rcu_bh and rcu_sched each maintained a separate grace period and each had its own updater, so a writer had to know which reader-side marker its readers used and call the matching one of synchronize_rcu(), synchronize_rcu_bh() or synchronize_sched(). Getting that pairing wrong produced a use-after-free that testing was unlikely to reproduce.

The flavors were merged around v4.20. There is now one grace period; synchronize_rcu_bh() and synchronize_sched() no longer exist, and synchronize_rcu() waits for readers of every kind — including preemption-disabled and bh-disabled regions. The reader-side markers survive, and Documentation/RCU/whatisRCU.rst still describes three flavors of usage, but they are now annotations that describe the context a reader runs in rather than selectors for different machinery. The genuinely separate mechanisms that remain — SRCU, and the RCU-Tasks family used by tracing and BPF — exist because they solve problems the consolidated implementation deliberately does not.

The same direction of travel removed the BKL in 2.6.39 and displaced down()/up() in favour of struct mutex. In each case a general-purpose facility was retired because a more specific one could be checked.

Ordering Became Explicit, Then Formal

A 2.6 programmer reasoning about memory ordering had mb(), rmb(), wmb() and their smp_ variants, placed by judgement and justified in prose. Two things changed.

First, ordering became a property of the operation rather than a separate instruction placed nearby. smp_load_acquire() and smp_store_release() attach the ordering to the access it applies to, which is both cheaper on ARM64 — where ldar and stlr are single instructions — and far harder to misread, because there is no question about which accesses the barrier was meant to separate. The atomic operations gained a full set of _relaxed, _acquire and _release variants, and that set is now large enough that the kernel generates it: the scripts in scripts/atomic/ emit the fallbacks so that no architecture has to hand-write, and hand-mistake, an operation it does not implement natively. READ_ONCE() and WRITE_ONCE() made the weaker but more pervasive claim — this access is shared — visible to the compiler and to the reader.

Second, and more consequentially, the memory model stopped being only prose. Documentation/memory-barriers.txt is still there and is still the document to read first. tools/memory-model/ contains a formal specification of Linux's ordering rules in the cat and bell languages, together with a suite of litmus tests. A question of the form “does this pattern of accesses guarantee that CPU 1 sees the store?” that in 2.6 could only be settled by asking someone who knew can now be settled by running the model.

The Toolchain Became a Participant

In 2.6, the correctness of a locking scheme was entirely the programmer's responsibility. CONFIG_DEBUG_SPINLOCK caught a few gross errors; everything else was review and luck. Today a substantial fraction of the analysis is mechanical, and the design of new interfaces is visibly shaped by the wish to keep it that way:

  • lockdep infers a lock ordering from a single correct run and reports the cycle the first time an inconsistent order is taken — the deadlock never has to happen.
  • KCSAN reports data races the run did not actually lose, and data_race() lets a programmer state that a particular race is intentional, which turns an unmarked access into a reviewable claim.
  • refcount_t saturates instead of wrapping, which converts a large family of use-after-free exploits into a harmless warning, and its try-get operations are __must_check so the compiler objects if the result is ignored.
  • guard() and scoped_guard() use the compiler's cleanup attribute to tie release to scope exit, making the missing unlock unrepresentable rather than merely discouraged.
  • Sparse's __rcu annotation makes dereferencing an RCU-protected pointer without rcu_dereference() a diagnosable error.

The common thread is that each of these takes a rule that a careful programmer already followed and gives it a representation a machine can check.

Real Time Stopped Being a Fork

In 2.6, PREEMPT_RT was an out-of-tree patch series maintained alongside the kernel. In 7.0.12 it is a configuration option, and both architectures this book covers select ARCH_SUPPORTS_RT. The preemption model itself has become more flexible in the process: alongside the traditional compile-time choice there is PREEMPT_DYNAMIC, which selects the model at boot, and PREEMPT_LAZY, which behaves much like full preemption but is less eager to preempt SCHED_NORMAL tasks, in order to reduce lock-holder preemption.

For ordinary kernel code the consequence is subtle and easy to miss. spinlock_t is no longer a promise about implementation. On PREEMPT_RT it becomes an rt-mutex: it sleeps, it participates in priority inheritance, and it does not disable preemption. Code that genuinely requires the classic behaviour — because it runs in a context that cannot sleep at all — must now say so by using raw_spinlock_t. This is the reason the chapter has been insistent about a distinction that on a non-RT kernel makes no observable difference whatsoever.

Summary

This chapter began with a question that sounds simple — when is synchronization necessary? — and the length of what followed is the honest answer. The kernel offers a layered set of primitives, from per-CPU data that avoids sharing altogether, through atomic operations and busy-wait spinlocks, to sleeping locks with priority inheritance and deadlock avoidance. Choosing among them is not a matter of picking the fastest; it is a matter of establishing which contexts touch the data, and then selecting the cheapest primitive that is legal in all of them.

A few principles survive the detail:

  • Avoid sharing before optimising it. Per-CPU data removes the problem rather than managing it. It is not free — it costs memory proportional to the CPU count, reading the total means summing, and on ARM64 even this_cpu_inc() is a preempt-disabled read-modify-write rather than a single instruction — but nothing that shares a cache line will beat it.
  • Prefer the lightest primitive that is legal. Uncontended, an atomic beats a spinlock and a spinlock beats a mutex. Under sustained contention the ordering can invert, because a spinning CPU does no work while a sleeping one yields it; this is why a long critical section belongs behind a sleeping lock even when the code could technically use a spinlock.
  • Use RCU where reads dominate. On a non-preemptible kernel the read side genuinely compiles to nothing, but the cost has moved rather than vanished: writers pay grace-period latency, freeing is deferred, and readers must not block. RCU is unbeatable for read-mostly data and a poor fit for anything else.
  • Let the scope release the lock. guard() and scoped_guard() make the missing unlock unrepresentable rather than merely unlikely.
  • Let the tooling do the proving. CONFIG_PROVE_LOCKING finds lock-order inversions from a single correct run, and KCSAN finds races the run did not lose. Neither replaces thinking, and both find things thinking reliably misses.
  • Write as though PREEMPT_RT is enabled. Code that distinguishes spinlock_t from raw_spinlock_t according to what it actually requires will work on an RT kernel without modification. Code that assumes spinlock_t disables preemption will not, and will appear entirely correct until someone enables the option.

The direction of travel over twenty years is consistent, and it is not simply toward more primitives. The Big Kernel Lock is gone, counting semaphores are no longer an acceptable way to say “mutual exclusion”, and RCU's three update sides have become one. What has grown is the amount of the programmer's reasoning that is now written down somewhere a machine can check it — in a lock class, in a type, in an annotation, or in the formal memory model. The remaining hard part is the part this chapter opened with, and no tool has yet automated it: deciding which data is shared, and with whom.
